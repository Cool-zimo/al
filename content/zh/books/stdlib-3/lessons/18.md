# 日志实战：给开发者看的 vs 给用户看的

> 这一课讲日志的两条路线：开发者需要详细的异常堆栈和上下文，用户只需要一句人话。以及异常时记 exc_info、按天切分文件的技巧。

## 两类受众，两种日志

同一个系统里有两类人看日志，需求完全不同：

| 受众 | 需要什么 | 例子 |
|---|---|---|
| 开发者 | 异常堆栈、变量值、调用链 | `ERROR order.py:45 process_order() - KeyError: 'sku'` |
| 终端用户 | 一句人话，能看懂 | `订单提交失败，请稍后重试` |

**混着写是灾难**：把 `Traceback (most recent call last)...` 打给用户，用户看不懂还以为程序崩了；只给用户写"操作失败"，开发者排查时没有任何线索。

```python
import logging

dev_logger = logging.getLogger("dev")
dev_logger.addHandler(logging.StreamHandler())
dev_logger.handlers[0].setFormatter(
    logging.Formatter("%(levelname)s %(filename)s:%(lineno)d %(funcName)s - %(message)s")
)

def process_order(order):
    try:
        result = order["sku"] / order["qty"]
    except KeyError as e:
        # 给开发者：带异常堆栈
        dev_logger.error(f"订单字段缺失: {e}", exc_info=True)
        # 给用户：一句人话
        return "订单信息不完整，请检查后重试"
    return result

print(process_order({"qty": 2}))
```

输出：

```
ERROR 18_practice.py:12 process_order - 订单字段缺失: 'sku'
Traceback (most recent call last):
  File "18_practice.py", line 10, in process_order
    result = order["sku"] / order["qty"]
KeyError: 'sku'
订单信息不完整，请检查后重试
```

**`exc_info=True` 是关键**：它会把当前异常的完整堆栈写进日志，没有它你只看到一句"出错了"，却不知道在哪一行。

## 翻车现场：异常被吞掉，日志里什么都没有

李四写了一个"万能"的异常处理，什么异常都 `except Exception`，然后只打了个 `error("出错了")`。

```python
import logging

logging.basicConfig(level=logging.ERROR, format="%(message)s")

def divide(a, b):
    try:
        return a / b
    except Exception:
        logging.error("出错了")   # 没记 exc_info，没记变量值
        return None

divide(1, 0)
```

输出：

```
出错了
```

**"出错了"三个字毫无排查价值**——不知道是什么异常、什么参数、哪一行。正确写法：

```python
def divide(a, b):
    try:
        return a / b
    except Exception as e:
        logging.error(f"除法失败: a={a}, b={b}, 异常={e}", exc_info=True)
        return None

divide(1, 0)
```

输出：

```
除法失败: a=1, b=0, 异常=division by zero
Traceback (most recent call last):
  File "<stdin>", line 3, in divide
ZeroDivisionError: division by zero
```

**打日志时把关键变量的值也写进去**，这是事后排查的唯一线索。否则你只能靠猜。

## 翻车现场：把堆栈直接展示给用户

```python
import logging

def pay(amount):
    try:
        # 模拟支付异常
        raise ConnectionError("银行接口超时")
    except Exception as e:
        return str(e)  # 直接把技术异常返回给用户

print(pay(100))
```

输出：

```
银行接口超时
```

看着还行？但如果是个未捕获的内部异常：

```
TypeError: 'NoneType' object is not subscriptable
  File "/app/payment.py", line 88, in _do_pay
    bank_resp["data"]["code"]
```

**把内部异常原文给用户看会暴露代码结构、第三方库版本、服务器路径**，既难看又不安全。正确做法：

```python
def pay(amount):
    try:
        raise ConnectionError("银行接口超时")
    except Exception:
        logging.exception("支付失败，稍后人工跟进")  # 开发者看详细堆栈
        return "支付暂时无法完成，已记录，我们会尽快处理"  # 用户看人话

print(pay(100))
```

输出：

```
支付暂时无法完成，已记录，我们会尽快处理
```

## 按天切分：别让日志文件涨到几十 GB

长期运行的程序（Web 服务、爬虫）日志会一直涨，单个文件几十 GB，打开都打不开。用 `TimedRotatingFileHandler` 按时间切分：

```python
import logging
from logging.handlers import TimedRotatingFileHandler

logger = logging.getLogger("app")
logger.setLevel(logging.INFO)

# 每天凌晨切分，保留 7 天的备份
handler = TimedRotatingFileHandler(
    "app.log",
    when="midnight",   # 切分时机：午夜
    interval=1,        # 间隔：1 天
    backupCount=7      # 保留几个备份
)
handler.setFormatter(logging.Formatter("%(asctime)s %(levelname)s %(message)s"))
logger.addHandler(handler)

logger.info("服务启动")
```

**切分后会生成 `app.log.2026-09-28`、`app.log.2026-09-29` 这样的文件**，超过 7 个自动删除最老的。同类还有 `RotatingFileHandler`，按文件大小切分（比如单个文件超 10MB 就切）。

## 小结

- 日志有两类受众：开发者要堆栈和变量，用户要一句人话
- `exc_info=True`（或 `logging.exception`）记录完整异常堆栈，是排查问题的核心
- 异常日志要带关键变量值，否则无法还原现场
- 绝不要把内部异常原文返回给用户，要翻译成友好提示
- `TimedRotatingFileHandler` 按时间切分，`RotatingFileHandler` 按大小切分
- 长期运行的程序必须做日志切分，否则单文件会涨到无法管理

  import io
  import sys

  logging.basicConfig(level=logging.ERROR, format="%(message)s")

  def safe_divide(a, b):

          return a / b
      except ZeroDivisionError:
          logging.exception(f"除法失败: a={a}, b={b}")

  print(safe_divide(10, 2))
  print(safe_divide(10, 0))

- assert "5.0" in __out
