# 为什么要有测试

> 这一课讲测试的必要性：改了一行代码不知道有没有弄坏别的、手动点一遍有多慢。测试是给代码买的保险，花小钱省大钱。

## 改了一行，坏了三个地方

张三写了一个购物车结算函数：

```python
def checkout(cart, vip=False):
    total = sum(item["price"] * item["qty"] for item in cart)
    if vip:
        total *= 0.9   # VIP 打九折
    return round(total, 2)
```

后来产品经理说"VIP 要打八折"，张三改了一行：

```python
    if vip:
        total *= 0.8   # 改了这里
```

**看起来没问题？** 但如果代码里还有"满 100 减 10"的优惠逻辑、积分计算、运费计算，它们都引用了折扣后的金额。改了 0.9 到 0.8，所有依赖它的地方都要同步验证。手动一个个点，一天就过去了。

**测试的价值**：改完跑一遍 `pytest`，30 秒告诉你哪些地方坏了。

## 手动测试有多慢

李四的 Web 项目有 50 个接口。每次发版他要手动测：

| 步骤 | 操作 | 耗时 |
|---|---|---|
| 登录 | 打开浏览器、输入账号密码 | 30 秒 |
| 下单 | 选商品、填地址、点提交 | 1 分钟 |
| 退款 | 找到订单、点退款 | 1 分钟 |
| 查看订单 | 翻页、筛选 | 30 秒 |
| ... | 50 个接口 | **约 2 小时** |

**每次改代码都要重复这 2 小时。** 如果一天改 3 次，一天 6 小时在手动测试。自动化测试跑一遍 30 秒。

## 一个没有测试的真实事故

某电商网站的优惠券计算函数：

```python
def calc_coupon(total, coupon):
    if coupon["type"] == "percent":
        return total * coupon["value"] / 100
    elif coupon["type"] == "fixed":
        return min(total, coupon["value"])
    return 0
```

有人加了个新优惠券类型 "shipping"（运费券），在调用处加了个判断，却忘了在 `calc_coupon` 里加：

```python
def apply_coupon(order, coupon):
    discount = calc_coupon(order["total"], coupon)
    order["total"] -= discount
    if coupon["type"] == "shipping":   # 新增逻辑
        order["shipping"] = 0
    return order
```

**结果**：用户选了运费券，`calc_coupon` 返回 0（不认识的类型），运费没减，用户多付了钱。如果有个测试覆盖"运费券把运费清零"，这个问题在上线前就被抓到了。

## 翻车现场：用 print 当测试

```python
def add(a, b):
    return a + b

print(add(1, 2))       # 3
print(add(-1, 1))      # 0
print(add(0, 0))       # 0
print("都对了！")
```

输出：

```
3
0
0
都对了！
```

**"都对了"是张三自己看出来的**，不是机器验证的。张三今天看了，明天忘了；李四不知道该看什么；三个月后谁都不敢改这个函数。print 测试的致命问题：

- **没有自动判断**：要人眼看输出，人会看漏
- **没有回归保护**：改了代码不会自动重跑
- **不能批量**：几十个用例没法一眼看完
- **输出混在正式代码里**：上线前得删掉

## 翻车现场：改了测试让它通过

王五写了个测试，发现代码有 bug，他不修代码，而是改了测试的期望值：

```python
# 代码（有 bug）
def discount(total, vip):
    return total * 0.9 if vip else total

# 测试
def test_discount():
    assert discount(100, True) == 90   # 90，通过
    assert discount(100, False) == 90  # 应该是 100，但王五改成了 90
```

**这是自欺欺人**。测试的意义是"抓住代码和预期的偏差"，改期望值等于告诉测试"我预期它就是错的"。正确的做法是修代码，让它符合真实业务预期。

## 翻车现场：测试只在开发机上跑过

```bash
$ python test_cart.py
全部通过！

$ ssh prod-server
$ python test_cart.py
ImportError: No module named 'requests'
```

**开发环境装了所有依赖，生产环境没装。** 测试只在自己机器上跑过，等于没跑。正确做法：用虚拟环境 + `requirements.txt` 锁定依赖，CI（持续集成）在干净的机器上自动跑测试。

## 小结

- 改一行代码可能影响多处，测试是快速回归验证的唯一手段
- 手动测试耗时且不可重复，自动化测试 30 秒跑完全部用例
- print 不是测试：没有自动判断、没有回归保护、不能批量
- 测试期望值不能为了通过而改，那是自欺欺人
- 测试必须在干净环境（CI）上跑，不能只信开发机
- 测试是给代码买的保险：平时觉得没用，出事时救命
