# 为什么集合的 `in` 这么快

> 上一课讲了集合查找飞快。这一课不背公式、不讲大 O，而是用一个直觉讲清楚：**为什么集合查一个元素比列表快得多**。
>
> 理解了这点，你就知道什么时候该用集合、什么时候用列表。

## 一、一个直观的实验

先做个小实验，感受一下差距。我们不记时间，只看**要比较多少次**。

假设要在名单里找人。名单是一万个名字，你要找的"张三"在最后：

### 用列表：一个个比过去

```python
names = ["用户0001", "用户0002", ..., "用户9999"]     # 一万个
# 找 "用户9999"
```

列表是"一排"，要找就得**从头到尾挨个看**：第 1 个不是、第 2 个不是……一直比到第 9999 个才找到。

如果运气差，"张三"刚好在最后或不存在，就得**比完全部一万个**才死心。

### 用集合：算一下就跳过去

```python
names = {"用户0001", "用户0002", ..., "用户9999"}
# 找 "用户9999"
```

集合不一排排比。它**先把每个名字编成一个编号**，然后根据编号直接"跳"到那个位置看一眼 —— 命中就找到了。

⚠️ **关键区别：列表靠"比"，集合靠"算"。**

- 列表找东西：**逐个比对**，最多比一万次
- 集合找东西：**算一次编号**，直接定位，一次就够

这就是为什么不管集合里有一千个还是一百万个元素，**集合的 `in` 判断几乎一样快**，而列表的元素越多就越慢。

## 二、哈希表的直觉

这个"算编号、直接跳"的机制，叫**哈希表（hash table）**。字典和集合都是这么干的。

### 怎么"算编号"

Python 会对每个放进集合的元素调用它的**哈希函数**，得到一个数字（就像给每个名字发一个"学号"）：

```python
print(hash("张三"))         # 某个整数，比如 123456789
print(hash(42))             # 42
print(hash("张三"))         # 同一个字符串，永远得到同一个数字
```

同一个对象，不管什么时候算，哈希值**都一样**。这就是为什么"会变"的东西（列表）不能放进集合 —— 它要是变了，哈希值也变，就找不回来了。

### 怎么"跳过去"

拿到哈希值后，Python 用它**算出这个元素应该存在哪个"格子"里**，直接去那个格子看一眼。

可以类比成：

> 你进图书馆找书。列表是"把所有书摊在地上，你一本本翻"；集合是"按索书号直接去对应书架抽一本"。

⚠️ **翻车：以为集合内部"排过序"。**

不是的。集合没有顺序，它只是"按编号分了格子"。这和"二分查找"那种"有序才能快"是两码事 —— 集合无序，照样快。

## 三、冲突：两个元素算到同一个格子

现实中难免有两个元素算到同一个编号（就像两个同学被分到同一个座位）。Python 的处理是**让这个格子挂一串**，真撞上了就在那一小格里再比一下。

所以严格来说，集合的 `in` 不是**永远**只查一次 —— 运气特别差时得多比几下。但那"一小串"通常很短，绝大多数时候就是一次命中。

这就是为什么我们强调**"几乎一样快"**而不是"永远一次"。

⚠️ **翻车：以为集合绝对比列表快、所有场景都用集合。**

不是。哈希表有额外开销：算哈希、维护格子都要成本。当数据**很少**时（比如十几个元素），列表那点逐个比对的开销可以忽略不计，集合反而更慢一点。

**经验判断**：

| 数据量 | 推荐 |
|---|---|
| 十几个以内 | 列表、集合都行，用列表更省心 |
| 成百上千以上、且频繁做 `in` 判断 | **集合**，优势明显 |
| 需要保留顺序或允许重复 | 列表 |

## 四、字典和集合是同一套机制

上一章讲字典时说的"键必须是可哈希的"，就是这个原因 —— **字典和集合用的是同一套哈希表机制**。

```python
d = {}
d["张三"] = 92       # 算 "张三" 的哈希 → 跳到对应格子 → 存 92

s = set()
s.add("张三")        # 算 "张三" 的哈希 → 跳到对应格子 → 存它自己
```

一个存"键→值"，一个只存"元素在不在"，**底层原理完全一样**。

⚠️ **翻车：想当然地以为字典/集合会"自动变快"。**

如果你建了一个列表、然后频繁在里面 `in` 查找，Python **不会**自动帮你转成集合。得你自己决定数据结构：

```python
data = ["a", "b", "c", ...]        # 列表
"target" in data                   # 慢，逐个比

# 改进：查之前转成集合
lookup = set(data)
"target" in lookup                 # 快
```

**一次转换，终身受益** —— 只要 `data` 不再变，转一次集合，后面成千上万次查找都飞快。

## 五、什么时候用集合

给一个判断清单：

- 频繁判断"在不在"？→ 用集合 ✅
- 需要去重？→ 用集合 ✅
- 需要做交集/并集/差集？→ 用集合 ✅
- 需要保留顺序？→ 用列表 ❌
- 需要允许重复？→ 用列表 ❌
- 需要键值映射？→ 用字典 ❌

一句话：**集合的强项是"判断存在"和"集合运算"，不是"存东西的顺序"。**

⚠️ **翻车：为了"快"而用集合，结果丢了顺序。**

```python
# 本来想保留用户操作的顺序
steps = ["登录", "浏览", "加购", "支付"]
# 有人"优化"成集合
steps = {"登录", "浏览", "加购", "支付"}
print(steps)        # 顺序乱了！
```

顺序有业务意义时，宁可承受列表的查找开销，也别用集合。要"既保序又快速查找"，用"列表存顺序 + 集合辅助查找"的组合（上一课 dedup 的例子就是这么干的）。

## 小结

- 列表找东西靠**逐个比对**，越往后越慢；集合靠**算哈希、直接定位**
- 这个机制叫**哈希表**，字典和集合都靠它
- 集合不是"有序"，是"分了格子"；冲突时格子内再比
- 数据量大、频繁 `in` 判断时用集合，优势明显；数据很少时列表更简单
- 字典和集合是同一套机制，所以键和集合元素都必须可哈希

  words = ["苹果", "香蕉", "苹果", "橙子", "香蕉", "苹果", "葡萄"]

- assert "7" in __out
