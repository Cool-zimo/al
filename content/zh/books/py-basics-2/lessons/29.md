# 递归：自己调用自己

> 递归是"函数自己调用自己"。听起来像绕口令，但它天然适合处理**层层嵌套、能拆成更小同类问题**的结构。
>
> 这一课讲两件事：**怎么写对**（必须有终止条件），以及**什么时候该用、什么时候不该用**。

## 一、最简单的递归：阶乘

阶乘 `n! = n × (n-1) × ... × 1`，定义里本身就含有"更小的同类问题"：

```python
def factorial(n):
    if n <= 1:                # 终止条件
        return 1
    return n * factorial(n - 1)   # 自己调用自己

print(factorial(5))        # 120
```

执行过程：

```
factorial(5)
= 5 * factorial(4)
= 5 * 4 * factorial(3)
= 5 * 4 * 3 * factorial(2)
= 5 * 4 * 3 * 2 * factorial(1)
= 5 * 4 * 3 * 2 * 1
= 120
```

每一步都在"把问题缩小一点"，直到缩到最小（n<=1）就停。

⚠️ **翻车：忘了写终止条件。**

```python
def factorial(n):
    return n * factorial(n - 1)       # 没有终止条件！

factorial(5)
# ✗ RecursionError: maximum recursion depth exceeded
```

永远不返回、永远在调用自己，直到 Python 的递归深度上限（默认 1000）被突破，抛出 `RecursionError`。**没有终止条件的递归是必炸的**。

⚠️ **翻车：终止条件写错，边界漏了。**

```python
def factorial(n):
    if n == 1:            # 只处理 n==1，n==0 会无限递归
        return 1
    return n * factorial(n - 1)

factorial(0)              # RecursionError
```

`n == 1` 只接住了 1，没接住 0。写递归时**要把"最小的问题"想周全**，边界漏一个就炸。

## 二、递归的两条铁律

**1. 必须有终止条件（基线条件）**，否则无限递归。

**2. 每次递归都要让问题"变小"**，朝着终止条件靠近。

```python
def count_down(n):
    if n <= 0:                # 终止条件
        return
    print(n)
    count_down(n - 1)         # 问题变小：n-1

count_down(3)
# 3
# 2
# 1
```

`n` 每次减 1，最终会到 0，命中终止条件。**如果写成 `count_down(n)`（不减 1），就永远到不了 0，必炸**。

## 三、递归 vs 循环：算斐波那契

斐波那契数列：1, 1, 2, 3, 5, 8...（每个数是前两个数之和）。

**递归版：**

```python
def fib(n):
    if n <= 2:
        return 1
    return fib(n - 1) + fib(n - 2)

print(fib(6))        # 8
```

代码几乎就是数学定义本身，**读起来极清楚**。但效率很差——`fib(6)` 要算两遍 `fib(5)` 和 `fib(4)`，重复计算爆炸式增长。

**循环版：**

```python
def fib(n):
    a, b = 1, 1
    for _ in range(n - 2):
        a, b = b, a + b
    return b

print(fib(6))        # 8
```

循环版每个数只算一次，**快得多**。

⚠️ **翻车：递归算大数的斐波那契，慢到怀疑人生。**

```python
fib(50)        # 要算很久，还会 RecursionError
```

`fib(50)` 的递归版本要做大约 2^50 次调用，浏览器里的 Pyodide 会直接卡死或报错。**这种"重复子问题多"的场景，递归不是好选择**。

## 四、什么时候适合用递归

递归适合**结构本身就在嵌套**的场景：

**场景一：层层嵌套的数据（文件目录树）**

```python
def walk(dir_path, indent=0):
    print("  " * indent + dir_path)
    # 假设有个 list_dir 返回子目录
    # for sub in list_dir(dir_path):
    #     walk(sub, indent + 1)

walk("/home")
```

目录里套目录，递归天然贴合。

**场景二：分治（快速排序）**

```python
def quick_sort(nums):
    if len(nums) <= 1:            # 终止：空或单个元素天然有序
        return nums
    pivot = nums[0]
    left = [x for x in nums[1:] if x < pivot]
    right = [x for x in nums[1:] if x >= pivot]
    return quick_sort(left) + [pivot] + quick_sort(right)

print(quick_sort([3, 1, 4, 1, 5, 9, 2, 6]))
# [1, 1, 2, 3, 4, 5, 6, 9]
```

每次把问题劈成两半，分别排序再拼起来。**结构清晰，代码几乎就是算法描述本身**。

⚠️ **翻车：递归改列表却忘了接收返回值。**

```python
nums = [3, 1, 2]
quick_sort(nums)          # 算出了新列表，但没接住
print(nums)               # [3, 1, 2] —— 原列表没变
```

`quick_sort` 返回的是**新列表**，原列表不会被改动。要拿到结果就得 `nums = quick_sort(nums)`。

## 五、递归的最大深度

Python 为了防止无限递归拖垮解释器，设了**递归深度上限**（默认 1000）：

```python
def forever(n):
    return forever(n + 1)

forever(0)
# RecursionError: maximum recursion depth exceeded
```

这不是 bug，是保护机制。**如果你的递归深度可能超过 1000，就别用递归**（比如遍历几万个节点的链表）。

⚠️ **翻车：用递归遍历很深的链。**

```python
def sum_list(nums, i=0):
    if i >= len(nums):
        return 0
    return nums[i] + sum_list(nums, i + 1)

sum_list(list(range(2000)))      # RecursionError
```

2000 层递归超过了默认上限。**这种"线性遍历"就该用 for 循环**，别硬上递归。

## 六、一个更安全的写法：尾递归思想

Python **不优化尾递归**，但把"累积的结果"作为参数传下去，能减少中间计算：

```python
def factorial_tail(n, acc=1):
    if n <= 1:
        return acc
    return factorial_tail(n - 1, acc * n)

print(factorial_tail(5))        # 120
```

虽然 Python 不会把它优化成循环（该超深还是会超深），但这种"把中间结果传下去"的写法**思想清晰、也方便改成循环**：

```python
def factorial_loop(n):
    acc = 1
    for i in range(2, n + 1):
        acc *= i
    return acc
```

**能用循环就用循环，递归留给"结构天然嵌套"的场景**——这是 Python 的实用主义原则。

## 小结

- 递归 = 函数自己调用自己，适合"能拆成更小同类问题"的场景
- 两条铁律：**必须有终止条件** + **每次递归都要让问题变小**
- 没有终止条件或终止条件写错 → `RecursionError`
- 递归的代码读起来像数学定义，但效率常不如循环（重复子问题多）
- Python 默认递归上限 1000，深度大就用循环
- 目录树、分治排序这类"结构天然嵌套"的问题，递归最合适
