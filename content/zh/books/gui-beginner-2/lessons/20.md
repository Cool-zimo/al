# 帧率控制：Clock 与 tick，为什么不能让它跑满 CPU

> 前面的游戏循环"能跑"，但跑得越快越好吗？这一节学 `pygame.time.Clock`，让游戏锁定帧率、省 CPU，顺便理解"帧率"和"速度"的关系。

## 问题：不控帧的游戏会跑多快

**回顾之前的循环：**

```python
while running:
    for event in pygame.event.get():
        ...
    player_x += speed
    screen.fill(BLACK)
    pygame.draw.rect(screen, RED, (player_x, 200, 50, 50))
    pygame.display.flip()
```

**这段循环没有任何限速。** 它会以**CPU 允许的最快速度**疯狂转：现代机器可能跑到几千 FPS。

**后果**：

1. **CPU 占用 100%**：一个"什么都没做"的小窗口把一整个核心跑满，电脑发烫、风扇狂转。
2. **速度随机器不同**：玩家 A 的电脑快（3000 FPS），球每秒移动 3000×4=12000 像素；玩家 B 的电脑慢（500 FPS），球每秒只走 2000 像素。**同一个游戏，两台机器速度差 6 倍。**

**这和第 8 课 tkinter 的"固定步长"问题是同一个根因**——帧率不固定，速度就不固定。

## 用 Clock 控帧

**`pygame.time.Clock()` 创建一个时钟对象，`clock.tick(目标FPS)` 控制帧率：**

```python
import pygame

pygame.init()
screen = pygame.display.set_mode((800, 600))
clock = pygame.time.Clock()          # 创建时钟

player_x = 375
speed = 4

running = True
while running:
    for event in pygame.event.get():
        if event.type == pygame.QUIT:
            running = False

    player_x += speed
    if player_x <= 0 or player_x >= 750:
        speed = -speed

    screen.fill((0, 0, 0))
    pygame.draw.rect(screen, (255, 0, 0), (player_x, 275, 50, 50))
    pygame.display.flip()

    clock.tick(60)                   # 锁定 60 FPS

pygame.quit()
```

**`clock.tick(60)` 的意思是："这一帧到此为止，如果还没到 1/60 秒，就睡到时间到。"** 这样循环稳定跑在 60 FPS，CPU 占用降到很低。

## tick 的返回值：实际帧间隔

**`tick()` 返回上一帧到现在经过的毫秒数**，可以用来算 dt：

```python
clock = pygame.time.Clock()

while running:
    dt = clock.tick(60)              # dt 约 16.7（毫秒）
    # 用 dt 做帧率无关的移动
    player_x += speed * (dt / 1000) * 60   # 归一化到 60FPS 基准
```

**但 pygame 里更常见的做法是：直接用固定步长 + tick 锁帧**，因为 tick 已经保证了帧率稳定，速度自然就一致了。真正的"dt 物理"在复杂游戏里才需要。

## 翻车现场一：忘了调用 tick，CPU 跑满

```
while running:
    ...
    pygame.display.flip()
    # clock.tick(60)  忘记调用
```

**症状**：窗口能跑，但 CPU 占用 100%，电脑发烫。

**原因**：没有 tick 就没有任何休眠，循环以最大速度转。这是 pygame 新手最常见的性能 bug。

**修复**：循环末尾加 `clock.tick(目标帧率)`。

## 翻车现场二：tick 传了 0 或负数

```
clock.tick(0)     # 不限制，等同于没调
clock.tick(-1)    # 报错
```

**`tick(0)` 等于"不限制帧率"，白写。传正数才有意义。**

## 翻车现场三：把 tick 放在循环开头

```
while running:
    clock.tick(60)          # 放开头
    for event in pygame.event.get():
        ...
    pygame.display.flip()
```

**技术上能跑，但不规范。** 标准做法是放在**循环末尾**（渲染之后）。逻辑上"tick 收尾这一帧"更清晰，也避免首帧延迟。

**但更根本的问题**：放开头会导致**事件处理和渲染被 tick 的休眠"卡"在中间**，影响响应及时性。放末尾让"处理+渲染"一气呵成，然后才休眠。

## 翻车现场四：以为 tick 能让慢机器加速

**`tick(60)` 只能保证"不超过 60"，不能保证"达到 60"。** 如果某帧逻辑太重（大量计算、加载文件），实际帧率会低于 60，tick 也无能为力。

**对策**：优化重逻辑、用 `pygame.time.get_ticks()` 做分帧处理、把耗时任务放线程。

## 目标帧率怎么选

**常见选择：**

| 帧率 | 适用 |
|---|---|
| 60 FPS | 主流，流畅（tick=16.7ms） |
| 30 FPS | 简单游戏、移动端省电 |
| 120 FPS | 高刷屏，需要显示器支持 |

**`clock.tick(60)` 是 pygame 项目的标配**，几乎每个教程都这么写。

## 用 get_fps 显示实际帧率

**`clock.get_fps()` 返回平滑后的实际帧率（浮点）：**

```python
font = pygame.font.SysFont(None, 24)
fps_text = font.render(f"{clock.get_fps():.0f} FPS", True, (255, 255, 255))
screen.blit(fps_text, (10, 10))
```

**调试时显示 FPS 是好习惯**，能直观看到卡顿。第 26 课会讲字体渲染。

## 锁定帧率 vs 帧率无关

**两套思路：**

| 思路 | 做法 | 适用 |
|---|---|---|
| 锁帧 + 固定步长 | `tick(60)` + 每帧固定位移 | pygame 小游戏，简单可靠 |
| 不锁帧 + dt | 算每帧 dt，位移 = 速度×dt | 物理精确、跨平台一致 |

**pygame 官方例子和大多数小游戏用第一种**：`tick(60)` 已经让帧率足够稳定，速度自然一致，简单省心。这一课先掌握 tick 控帧，dt 的做法你已经在 tkinter 第 8 课学过了，原理相通。

## 小结

- 不控帧 → CPU 跑满、速度随机器变化
- `clock = pygame.time.Clock()` + `clock.tick(60)` 锁 60 FPS
- tick 让循环在每帧之间休眠，大幅降低 CPU
- tick 放循环**末尾**（渲染之后）
- tick(0) 等于没限制；tick 只能限速不能加速
- 60 FPS 是 pygame 主流选择
- 简单游戏用"锁帧+固定步长"即可
