# 为什么游戏用 pygame：tkinter 做游戏的瓶颈

> 学了这么多 tkinter，你已经能做画板、做弹球。但真要做游戏，大家都会推荐 pygame。这一节讲清楚"为什么"，帮你理解两个库各自的位置。

## tkinter 是"界面库"，不是"游戏引擎"

**tkinter 的定位是"做桌面应用的界面"**：按钮、表单、对话框、菜单、表格。它的核心模型是"事件驱动"——用户点了什么、输入了什么，程序响应。

**游戏需要的是"连续刷新"**：哪怕没有任何输入，画面也要每帧更新（物理、动画、AI）。这是两套完全不同的范式。

| 维度 | tkinter | pygame |
|---|---|---|
| 范式 | 事件驱动 | 游戏循环（主动刷新） |
| 渲染 | 矢量图形（Canvas） | 像素 Surface 位图 |
| 帧率控制 | 靠 after 近似 | 内置 Clock 精确控制 |
| 图像 | PhotoImage 有限格式 | 支持 PNG/JPG 等，透明、缩放 |
| 声音 | 无 | 内置 mixer |
| 输入 | 事件绑定 | 持续按键检测、鼠标状态 |
| 碰撞 | 自己算坐标 | 内置 Rect 碰撞检测 |
| 硬件加速 | 弱 | 有（SDL2） |
| 适合场景 | 工具、界面、小动画 | 2D 游戏 |

## tkinter 做游戏的四个瓶颈

**一、帧率不精确。** `after(20, ...)` 只是"尽量 20ms"，实际受主线程其他任务影响。做不了稳定的 60 帧。

**二、渲染慢。** Canvas 每帧 `coords` 重绘大量图形，性能随图形数量急剧下降。pygame 用 Surface 位图 + 硬件加速，几千个精灵也能跑。

**三、没有声音。** tkinter 压根没考虑音频。游戏需要音效、背景音乐，得自己外接。

**四、输入模型不匹配。** 游戏需要"持续按住方向键移动"，tkinter 的按键是"按一次触发一次"，模拟持续按键很别扭。

## 游戏循环：pygame 的核心范式

**pygame 程序不是"等事件触发"，而是"主动不停地跑"：**

```python
import pygame

pygame.init()
screen = pygame.display.set_mode((800, 600))

running = True
while running:
    # 1. 处理事件（要不要退出）
    for event in pygame.event.get():
        if event.type == pygame.QUIT:
            running = False

    # 2. 更新状态（移动、物理、AI）
    # ...

    # 3. 重绘画面
    screen.fill((255, 255, 255))
    # ... 画东西
    pygame.display.flip()

pygame.quit()
```

**这就是"游戏循环"的三步曲：处理输入 → 更新状态 → 渲染。** 它不停地转，驱动整个游戏。

**对比 tkinter**：tkinter 是"被动响应"，pygame 是"主动循环"。后者给程序员对每一帧的完全控制权。

## pygame 能做什么

**pygame 适合做 2D 游戏**：平台跳跃、弹球、飞机大战、贪吃蛇、俄罗斯方块、塔防、卡牌（带动画的）……

**它不适合做什么**：3A 大作（没有 3D 管线）、需要精美 UI 的商业应用（UI 控件得自己画）。

**典型定位**：独立游戏、游戏原型、教学、Game Jam、2D 小游戏。

## 翻车现场一：以为 pygame 能直接"嵌入 tkinter"

```
# 想在一个 tkinter 窗口里塞 pygame 画面
```

**tkinter 的 Canvas 和 pygame 的 Surface 是两套完全不同的渲染系统**，不能互相嵌入。要用 pygame，就整个窗口交给 pygame 管理。

**如果非要"界面 + 游戏"，常见做法是**：主界面用 tkinter，点"开始游戏"后启动一个独立的 pygame 窗口；或者反过来，pygame 里自己画 UI。

## 翻车现场二：用 tkinter 的 after 习惯写 pygame

**pygame 里绝对不能这样：**

```
while True:
    pygame.display.flip()
    time.sleep(0.02)
```

**没处理事件队列 → 窗口"无响应"、关不掉**（第 17 课细讲）。pygame 的循环里**必须**每帧调用 `pygame.event.get()` 或 `pygame.event.pump()` 排空事件队列。

## 翻车现场三：把游戏状态放在全局、到处改

**tkinter 程序常见全局变量到处传。游戏状态更复杂（玩家、敌人、分数、关卡），全塞全局会失控。**

**pygame 的最佳实践是面向对象**：把玩家写成类、把敌人写成类，状态封装在对象里。第 21 课讲 Sprite 时会正式引入。

## 为什么还要学 tkinter

**既然 pygame 更适合游戏，为什么前面学 tkinter？**

1. **tkinter 是 Python 标准库**，装好 Python 就有，零安装成本，做工具、做界面最快。
2. **学 tkinter 理解的是 GUI 通用概念**：事件、布局、控件、回调——这些在 Qt、Web 前端、pygame 的 UI 部分都通用。
3. **很多程序"主体是界面，游戏是其中一小块"**：比如一个学习软件里嵌入个小动画，用 tkinter 更轻量。
4. **tkinter 的输入框、按钮、菜单做配置面板、存档管理很方便**，做游戏配套工具（关卡编辑器）比 pygame 快得多。

**所以这本书的路线是：用 tkinter 打 GUI 基础，用 pygame 打开游戏世界。** 两个都懂，你才真正灵活。

## 小结

- tkinter 是事件驱动的界面库；pygame 是主动刷新的游戏库
- tkinter 瓶颈：帧率不稳、渲染慢、无声音、输入模型不匹配
- 游戏循环三步：处理事件 → 更新状态 → 渲染
- pygame 适合 2D 游戏，不适合 3D 大作
- pygame 窗口不能嵌入 tkinter，需独立窗口
- 学 tkinter 的价值：标准库、通用 GUI 概念、做工具快
