# 27 分页：为什么 API 不肯一次把数据都给你

> 你请求"我的所有仓库"，服务器只回了 30 条，然后告诉你"还有下一页"。你觉得它小气。其实分页是为了**保护双方**——这一课讲清三种分页长什么样、各自什么时候会出错，以及**为什么你写的分页循环可能会静默漏掉数据**。

## 先接受一个事实：分页不是"小气"

```python
import requests

r = requests.get("https://api.github.com/users/Cool-zimo/repos", timeout=10)
data = r.json()
print(len(data))        # 30
```

你明明可能有 200 个仓库，为什么只给 30 个？

**三个理由，每一个都很实在：**

**一、服务器扛不住。**

如果你的账号有 5 万个仓库（机器人的账号很常见），一次性序列化 5 万个对象要占几百 MB 内存、几秒 CPU。**这还只是一个用户的请求**——同时来 100 个这样的请求，服务器就跪了。

**二、网络扛不住。**

几百 MB 的响应要传几十秒。**在这几十秒里任何一点网络抖动都会让整个请求失败**，然后从头再来。分成 30 条一页，任何一页失败只重传那一页。

**三、你大概率也不需要全部。**

大部分场景是"显示第一页，用户往下滚再加载下一页"。**一次全给，99% 的数据是白传的。**

> **类比**：你去图书馆借 200 本书，管理员不会一次性把 200 本搬给你——他一次给你 20 本，你读完再来。**分页是"按需取用"，不是"故意刁难"。**

## 三种分页长什么样

这是最关键的认知：**分页没有统一标准**。不同 API 用不同的方式，你必须看文档才知道是哪种。

### 样式一：页码式（page / per_page）

```
GET /repos?page=1&per_page=30
GET /repos?page=2&per_page=30
```

**最常见、最好理解。** 你告诉服务器"第几页、每页几条"。

**识别方法**：参数里有 `page` 或 `page_num`。

### 样式二：偏移式（offset / limit）

```
GET /items?offset=0&limit=30
GET /items?offset=30&limit=30
GET /items?offset=60&limit=30
```

**注意 offset 是"跳过多少条"，不是"第几页"**：

```
offset = (page - 1) * limit
```

**识别方法**：参数里有 `offset` 或 `skip`。

### 样式三：游标式（cursor / after）

```
GET /items?limit=30
GET /items?limit=30&after=eyJpZCI6MTIzfQ    ← 上一页最后一条的"游标"
GET /items?limit=30&after=eyJpZCI6MTU2fQ
```

服务器返回一个**不透明的游标字符串**（通常是 base64），意思是"从这里继续"。

**识别方法**：响应里有个 `next_cursor` / `cursor` / `after` 字段，或者参数里有 `cursor`。

**这是最健壮的一种**，原因后面讲。

## 页码式分页：从最简单的循环开始

```python
import requests

def fetch_all_repos(user, token=None):
    """拉取某个用户的所有仓库"""
    all_repos = []
    page = 1

    headers = {}
    if token:
        headers["Authorization"] = f"Bearer {token}"

    with requests.Session() as s:                    # ① 用 Session 复用连接
        s.headers.update(headers)

        while True:
            r = s.get(                               # ② 请求一页
                f"https://api.github.com/users/{user}/repos",
                params={"page": page, "per_page": 100},   # ③ 100 是上限
                timeout=10,
            )
            r.raise_for_status()                     # ④ 出错就抛

            batch = r.json()
            if not batch:                            # ⑤ 空了 → 结束
                break

            all_repos.extend(batch)                  # ⑥ 累加
            page += 1                                # ⑦ 下一页

    return all_repos
```

> **逐行拆解**
>
> - **① `Session`**：上一课刚讲——分页意味着几十个请求，不复用连接会慢好几倍
> - **② `s.get(...)`**：请求第 `page` 页
> - **③ `per_page=100`**：**GitHub 的上限就是 100**，写 200 会被当成 100。每个 API 的上限不同，**看文档**
> - **④ `raise_for_status()`**：分页循环里**必须**有。否则一个 404 会返回空列表，你的循环会以为"没数据了"而正常结束——**静默地拿到不完整的数据**
> - **⑤ `if not batch: break`**：**终止条件**。这是页码式最通用的判断——空数组说明翻过头了
> - **⑥ `extend`** 不是 `append`：`append` 会把整个列表当成一个元素塞进去
> - **⑦ `page += 1`**

**这里最容易写错的是 ④。** 想象一下没有它的情况：token 过期 → 服务器返回 401 + 一段 JSON 错误信息 → `r.json()` 拿到的是一个**字典**（不是列表）→ `if not batch` 对空字典也成立 → 循环正常结束 → **你拿到 0 条数据，函数还返回得理直气壮**。

## 终止条件：你怎么知道翻完了？

**这是分页最容易出 bug 的地方。** 有四种判断方式，可靠性差别很大。

### 判断一：返回空数组（最通用）

```python
if not batch:
    break
```

✅ **优点**：几乎所有 API 都适用
❌ **缺点**：**要多发一次请求**（翻到空页才知道结束）

### 判断二：返回条数少于 per_page

```python
if len(batch) < 100:      # 少于请求的每页条数
    break                  # 说明这是最后一页
```

✅ **优点**：**不用多发那一次空请求**
❌ **缺点**：**只在"总数恰好整除"时会有问题**——比如总共 200 条、每页 100 条，最后一页正好 100 条，你会再发一次请求拿到空数组。**所以这个判断要配合空数组判断一起用**

```python
# ✅ 稳妥写法：两个判断都要
if len(batch) < per_page or not batch:
    break
```

### 判断三：响应里有 total 字段

很多 API 会告诉你总数：

```json
{
  "total": 137,
  "page": 1,
  "per_page": 100,
  "items": [...]
}
```

```python
total = data["total"]
all_items.extend(data["items"])
if len(all_items) >= total:      # ① 够了就停
    break
```

> - **① 用已收集的数量和总数比**，而不是"页数 × 每页数"——后者在总数不整除时会算错

✅ **优点**：能提前算出要发几次请求，还能显示进度
❌ **缺点**：**不是所有 API 都有 total**；而且 **`total` 可能在分页过程中变化**（有新数据进来）

### 判断四：响应里有 next 链接（最可靠）

```json
{
  "items": [...],
  "next": "https://api.example.com/items?page=2",
  "has_more": true
}
```

```python
while url:                        # ① url 是下一页的链接
    r = s.get(url, timeout=10)
    r.raise_for_status()
    data = r.json()
    all_items.extend(data["items"])
    url = data.get("next")        # ② 没有 next 就是 None → 循环结束
```

✅ **优点**：**服务器直接告诉你下一页在哪**，你不用猜
❌ **缺点**：要按 API 给的字段名来

## GitHub 的 Link 头：最优雅的一种

GitHub 不用响应体里的字段，而是**塞进响应头**：

```
Link: <https://api.github.com/user/repos?page=2>; rel="next",
      <https://api.github.com/user/repos?page=7>; rel="last"
```

这一行告诉你**两件事**：下一页是 page=2，最后一页是 page=7。**你甚至不用循环试错，直接知道一共几页。**

### 自己解析

```python
import re
import requests

def parse_link_header(link):
    """把 Link 头解析成 {rel: url} 字典"""
    result = {}
    if not link:
        return result

    for part in link.split(","):                       # ① 按逗号切
        m = re.search(r'<([^>]+)>;\s*rel="?(\w+)"?', part)   # ② 正则提取
        if m:
            result[m.group(2)] = m.group(1)            # ③ rel → url

    return result

r = requests.get("https://api.github.com/users/Cool-zimo/repos", timeout=10)
links = parse_link_header(r.headers.get("Link"))
print(links)
# {'next': 'https://api.github.com/user/repos?page=2',
#  'last': 'https://api.github.com/user/repos?page=7'}
```

> **逐行拆解**
>
> - **① `split(",")`**：Link 头里多个链接用逗号分隔
> - **② 正则 `<([^>]+)>;\s*rel="?(\w+)"?`**：
>   - `<([^>]+)>` 匹配尖括号里的 URL（`[^>]` 是"非 `>` 的任意字符"）
>   - `;\s*rel=` 匹配中间的分号和 rel
>   - `"?(\w+)"?` 匹配 rel 的值，**引号可有可无**
> - **③ 存成 `{rel: url}`**，之后 `links.get("next")` 就行

**为什么不用 split 而用正则**：你自己写 `part.split(";")` 也能跑，但 Link 头的格式细节（空格、引号、多个参数）很容易让 split 出错。**正则更稳。**

### requests 其实已经帮你解析好了

**好消息：你不用写上面的函数。** requests 内置了：

```python
import requests

r = requests.get("https://api.github.com/users/Cool-zimo/repos", timeout=10)
print(r.links)
# {'next': {'url': 'https://...page=2', 'rel': 'next'},
#  'last': {'url': 'https://...page=7', 'rel': 'last'}}

next_url = r.links.get("next", {}).get("url")     # ① 直接拿
if next_url:
    r2 = requests.get(next_url, timeout=10)
```

> - **① `r.links`** 是 requests 自动解析好的。**有就直接用，没有才自己写**

**用 Link 头的完整分页**：

```python
import requests

def fetch_all_with_link(url, headers=None):
    """跟随 Link 头的 next 一直翻到底"""
    items = []

    with requests.Session() as s:
        if headers:
            s.headers.update(headers)

        while url:                                    # ① url 为 None 时结束
            r = s.get(url, timeout=10)
            r.raise_for_status()

            items.extend(r.json())                    # ② 累加本页

            url = r.links.get("next", {}).get("url")  # ③ 下一页

    return items
```

> - **① `while url`**：第一次是初始 URL，之后是 next。**服务器不给 next 就是 None，循环自然结束**
> - **③ 这一行是整个分页的核心** —— 服务器说下一页在哪，我们就去哪

## 偏移式的致命缺陷：会漏数据

页码式和偏移式看起来差不多，但在**数据会变动**的场景下，偏移式有严重问题。

### 问题演示

假设按时间倒序取数据，每页 3 条：

```
第 1 次请求 offset=0  → 拿到 [D, C, B]      （最新的三条）
                                             ↓
                          此刻有人发了一条新数据 E
                                             ↓
第 2 次请求 offset=3  → 跳过前 3 条 → 拿到 [B, A, ?]
                                    ↑
                              现在前三条是 [E, D, C]
                              跳过它们 → 从 B 开始
                              → B 被取了两次！而 E 永远取不到
```

**两个后果**：
1. **B 重复**（第 1 页和第 2 页都出现了 B）
2. **E 丢失**（它插到了前面，把别人挤到了你已经取过的范围）

> **类比**：你按页码翻一本活页笔记本，有人在你翻页的时候往前面插了一页——**后面所有内容的页码都变了**，你会重复看到一页、并且永远漏掉一页。

### 游标式为什么没这个问题

游标记录的是**"上一条数据是谁"**，不是"跳过几条"：

```
第 1 次：取 3 条 → 返回 [D, C, B]，游标 = "B 的 ID"
                                    ↓ 插入 E
第 2 次：从" B 的 ID "之后取 3 条 → 拿到 [A, ?, ?]     ← 正确！
```

**游标指向具体的数据**，不管前面插了多少新数据，从 B 之后继续取依然是对的。

**结论**：**数据会实时变动的 API（时间线、消息流、订单列表）必须用游标式。** 页码式/偏移式只适合"数据基本不变"的场景（比如仓库列表）。

## 写一个通用的分页拉取器

把所有情况收敛成一个函数，**用生成器**（这样内存友好，第 25 课讲过流式思想）：

```python
import requests

def paginate(url, params=None, page_param="page", per_page=100,
             max_pages=100, session=None, **kwargs):
    """
    通用分页生成器：一页一页产出，边取边用

    :param url: 起始 URL
    :param page_param: 页码参数名（page 或 offset 之类）
    :param per_page: 每页条数
    :param max_pages: 安全阀，防止死循环
    :param session: 可选的 Session（复用连接）
    """
    s = session or requests.Session()       # ① 没给就自建
    own_session = session is None           #    记下是不是自己建的
    base_params = dict(params or {})        # ② 拷贝，避免改动调用方的字典

    try:
        for page in range(1, max_pages + 1):        # ③ 有上限的循环
            req_params = dict(base_params)
            req_params[page_param] = page           # ④ 页码
            req_params["per_page"] = per_page

            r = s.get(url, params=req_params, timeout=10, **kwargs)
            r.raise_for_status()

            batch = r.json()
            if not batch:                           # ⑤ 空了就停
                return

            yield batch                             # ⑥ 产出一页，暂停在这里

            if len(batch) < per_page:               # ⑦ 最后一页
                return
    finally:
        if own_session:
            s.close()                               # ⑧ 自己建的自己关
```

**用法**：

```python
# 边取边处理，不占内存
for batch in paginate("https://api.github.com/users/Cool-zimo/repos"):
    for repo in batch:
        print(repo["name"])

# 或者真的要全部
all_repos = [repo for batch in paginate(url) for repo in batch]
```

> **逐行拆解**
>
> - **① `session or requests.Session()`**：允许调用方传入自己的 Session（复用连接），不传就自建
> - **② `dict(params or {})`**：**拷贝**。直接改 `params` 会污染调用方传进来的字典——这是很隐蔽的副作用
> - **③ `range(1, max_pages + 1)`**：**用 for 而不是 while True**。这是安全阀——**哪怕终止条件写错，最多翻 100 页就停，不会把 API 打挂**
> - **④ `req_params[page_param]`**：页码参数名可配置，兼容 `page` / `offset` / `page_num`
> - **⑥ `yield batch`**：**生成器**。产出一页后函数暂停，调用方处理完再继续。**内存中永远只有一页**
> - **⑧ `finally` 里关闭**：只关自己建的。**关掉调用方传进来的 Session 是不礼貌的**——人家可能还要用

### 为什么用生成器而不是返回大列表

```python
# ❌ 一次性返回全部：10 万条数据全在内存里
def fetch_all(url):
    result = []
    ...
    return result        # 内存里 10 万个对象

# ✅ 生成器：用一页丢一页
def paginate(url):
    ...
    yield batch          # 内存里永远只有 100 个
```

**这就是第 25 课"流式"思想的延续**：你不一定需要全部数据在内存里，你需要的往往是"遍历一遍"。

## 翻车现场

### 翻车一：while True 没有安全阀

```python
# ❌ 危险
while True:
    r = s.get(url, params={"page": page})
    data = r.json()
    if not data:
        break
    ...
```

**现象**：一旦终止条件判断错了（比如 API 改了返回结构），**这个循环永远不结束**，你的程序在疯狂地打 API。

**后果**：**轻则被限流（第 28 课），重则你的 IP 被封。** 而且因为是死循环，日志会瞬间刷满硬盘。

**教训**：**永远给分页循环加上限**。`for page in range(1, max_pages+1)` 比 `while True` 安全一个数量级。

### 翻车二：偏移式分页漏数据

```python
# ❌ 在实时数据上用 offset
for offset in range(0, 1000, 50):
    r = s.get(url, params={"offset": offset, "limit": 50})
```

**现象**：结果里有重复项，或者"明明应该有这条数据却没拿到"。**而且只在数据频繁变动时才会出现**——测试环境数据不动，一切正常，上线才炸。

**原因**：前面讲过，插入新数据会让偏移错位。

**教训**：**实时数据用游标**。如果 API 只支持 offset，就**一次性快速拉完**（减少变动窗口），或者**按时间倒序 + 记录已处理的最大 ID 去重**。

### 翻车三：以为 per_page 可以无限大

```python
# ❌ 自作聪明
r = s.get(url, params={"per_page": 10000})     # 想一次全拿
```

**现象**：服务器返回 100 条（或 30 条），你以为拿到了全部。

**原因**：**每个 API 都有上限，超了会被静默截断。** GitHub 是 100，很多 API 是 50 或 20。

**教训**：**看文档确认上限**。而且要验证：

```python
# ✅ 验证一下实际拿到了几条
print(len(r.json()))      # 如果是 100，说明可能被截断了，还要翻页
```

### 翻车四：把所有页都存进列表然后内存爆了

```python
# ❌ 数据量大时会爆
all_data = []
for page in range(1, 1000):
    all_data.extend(fetch_page(page))
```

**现象**：拉 10 万条数据，内存占用几个 GB，程序被 OOM kill。

**原因**：**你其实不需要全部数据同时在内存里**——你可能只是要统计、要过滤、要写文件。

**教训**：用生成器**边取边处理**，或者边取边写盘。

### 翻车五：忘了 raise_for_status

```python
# ❌ 致命
batch = r.json()
if not batch:
    break
```

**现象**：token 失效后，函数返回**空列表或残缺数据**，而且**不报错**。你以为"这个用户没有仓库"。

**原因**：401 响应体是 `{"message": "Bad credentials"}` 这样的字典，`if not batch` 对空字典/非空字典的判断可能都不对，然后循环莫名结束或继续。

**教训**：**分页循环里的 `raise_for_status()` 是强制项**。它是唯一能区分"真的没数据"和"出错了"的东西。

## 为什么这对你写代码有用

**一、API 的设计约束，往往是为了保护你自己。**

分页看起来麻烦，但它让"大请求"变成"多个小请求"，任何一个失败都能单独重试。**很多你觉得"API 设计得不好"的地方，其实是它在替你承担风险。**

**二、终止条件的正确性比循环体重要得多。**

循环体写错，你拿到错误数据；终止条件写错，你要么死循环打挂 API，要么静默拿到不完整数据。**静默的不完整是最坏的失败——因为它看起来像成功。**

**三、"看起来能工作"和"在变动下还能工作"是两件事。**

偏移式分页在测试环境完美运行，上线后数据一动就漏。这类 bug 的共同特征是：**它在静态下正确，在动态下失效**。判断方法是问自己："**在我遍历的过程中，这个集合会变吗？**"

## 小结

- **分页的三个理由**：服务器扛不住、网络扛不住、你大概率用不完
- **三种样式**：页码式 `page/per_page`、偏移式 `offset/limit`、游标式 `cursor/after`
- **`offset = (page-1) * limit`**
- **终止条件四种**：空数组（最通用）、少于 per_page（省一次请求，要配合空判断）、total 字段、next 链接（最可靠）
- **GitHub 的 Link 头**：`r.links` requests 已自动解析，`r.links["next"]["url"]`
- **偏移式会漏数据**：遍历期间插入新数据导致重复+丢失；**实时数据必须用游标**
- **`for page in range(1, max_pages+1)` 而不是 `while True`** —— 安全阀
- **`per_page` 有上限**，超了静默截断，看文档
- **用生成器 `yield` 边取边处理**，不要全堆进内存
- **分页循环里 `raise_for_status()` 是强制项**，否则错误会伪装成"没数据"
- ❌ 别 while True；别在实时数据上用 offset；别以为 per_page 能无限大；别一次性装进内存；别省 raise_for_status

```quiz
type: choice
exam: true
q: 为什么在实时变动的数据（如消息流、时间线）上不应该用 offset 分页？
options:
- offset 分页比较慢
- 遍历期间若有新数据插入，会让后续 offset 整体错位，导致部分数据重复、部分数据永远取不到
- offset 不支持 limit
- offset 已被废弃
answer: 1
explain: offset 是"跳过 N 条"，是个相对位置。前面插入一条新数据，所有数据的位置都后移一位，你下一次跳过 N 条就会重复看到上一页的最后一条，并且永远漏掉最新那条。游标（cursor）记录的是具体数据的 ID，不受插入影响，所以实时数据必须用游标
```

```quiz
type: choice
exam: true
q: 关于分页循环的终止条件，最安全的做法是？
options:
- while True 配合 if not batch: break
- 用 for page in range(1, max_pages + 1) 限定最大页数，配合空数组和"少于 per_page"双重判断
- 只判断返回条数少于 per_page
- 固定翻 10 页
answer: 1
explain: while True 一旦终止条件失效就会死循环，疯狂打 API 直到被限流或封 IP。for 加 max_pages 是安全阀。两个判断配合是因为：总数恰好整除时最后一页正好满，只看"少于 per_page"会多翻一次空页；只看空数组则每次都要多一次请求。双重判断既省请求又不会漏
```
