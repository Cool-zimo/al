# 08 头部：HTTP 的元数据系统

> HTTP/0.9 的请求只有一行 `GET /index.html`，没有头部。今天你随便打开一个网页，请求头有十几个、响应头有二三十个。这一课讲清楚：头部到底是什么、为什么它是"键值字典"而不是别的形状、哪些头你必须认识，以及一个关于 `X-` 前缀的、延续了 30 年的乌龙。

## 为什么需要头部

回到第 4 课。HTTP/0.9 没有头部，因为当时的请求里没有任何"额外信息"要表达——就一个动作（GET）和一个目标（路径）。

然后很快就出问题了：

**问题一**：浏览器想告诉服务器"我是 Netscape，我能显示图片"。没地方说。

**问题二**：服务器想告诉浏览器"这是 HTML 还是图片"。没地方说。

**问题三**：用户填了表单，服务器想知道"这份数据有多长"。没地方说。

**问题四**：一台服务器上跑了两个网站，服务器想知道"你要访问哪个域名"。**没地方说**——这个最致命，第 4 课讲过，它就是 HTTP/1.1 必须引入 Host 头的原因。

于是 HTTP/1.0（RFC 1945）正式引入了头部。设计极其简单——**就是一堆纯文本的键值对**：

```text
GET /index.html HTTP/1.0
User-Agent: NCSA_Mosaic/2.0 (Windows 3.1)
Accept: text/html
```

每行一个，格式是 `名字: 值`，头部和正文之间用一个**空行**隔开。

## 为什么是文本，而且是这个形状

这个设计有三个影响深远的后果，值得单独说：

### 后果一：你可以用 telnet 手写一个 HTTP 请求

因为头部是纯文本，理论上你用任何能发文本的工具都能发 HTTP 请求：

```text
$ telnet example.com 80
GET / HTTP/1.1
Host: example.com

```

敲两下回车（那个空行），服务器就返回响应了。**没有任何一行代码，纯手工打字。**

这在当年不是炫技，是**调试手段**。今天你有 curl、有 Postman、有浏览器 devtools，但理解"HTTP 就是文本"这件事，会让你在看到抓包内容时心里有底。

### 后果二：扩展起来毫无成本

想在请求里加一个自定义信息？加一行 `My-Thing: hello` 就行。服务器不认识就忽略，认识就处理。

**这就是为什么头部能以几十个的速度增长，而 HTTP 版本号 30 年才从 1.1 走到 3。** 头部的可扩展性吸收了绝大部分新需求。相比之下，那些用二进制格式、字段固定的协议，加一个字段就要发新版。

### 后果三：它变大了，而且每次都重复发

这是代价。每个请求都要带上十几个头，其中 `Cookie`、`User-Agent`、`Accept-Language` 这些几乎每次都一样。

**HTTP/2 的头部压缩（HPACK）就是专门来解决这个的**——第 5 课讲过，它维护一张"头部字典"，重复的头只发一个索引号。

## 头部的四个规矩

### 规矩一：名字不区分大小写

```text
Content-Type: application/json
content-type: application/json
CONTENT-TYPE: application/json
```

**这三种完全等价。** 规范明确说了头部字段名是大小写不敏感的。

`requests` 用 `CaseInsensitiveDict` 来实现这一点：

```python
import requests

r = requests.get("https://api.github.com", timeout=10)
print(r.headers["content-type"])     # ① 小写能取到
print(r.headers["Content-Type"])     # ② 大写也能取到
print(r.headers["CONTENT-TYPE"])     # ③ 全大写还是能取到
```

> **逐行拆解**
>
> - **①②③** 三行输出完全一样。这不是巧合，是 `requests` 特意把响应头存成了 `CaseInsensitiveDict`
> - **为什么要在意**：服务器今天返回 `Content-Type`，明天改成 `content-type`，你的代码还能跑。**如果你的代码是自己解析原始文本的，这个坑会咬你**

### 规矩二：头部和正文之间必须有空行

一个请求／响应长这样：

```text
请求行 / 状态行
头部1: 值1
头部2: 值2
              ← 这个空行必须有
正文内容……
```

**少这个空行，服务器就不知道头部到哪儿结束。** 手写协议时最常见的错误就是漏了它。

### 规矩三：同一个头可以出现多次

比如 `Set-Cookie`，服务器可以下多个 cookie，就发多行 `Set-Cookie`。

**这时候用 `r.headers["Set-Cookie"]` 只能拿到其中一个**——这是 HTTP 头部处理里的经典陷阱。

### 规矩四：顺序不重要（除了一个例外）

规范说头部字段的顺序**没有语义**（除非该字段自己定义了）。服务器不应该依赖 `Accept` 在 `Host` 前面。

唯一的例外是 **Host**：它必须是 HTTP/1.1 请求里的第一个头（因为服务器要先知道你要访问哪个站点）。

## 你必须认识的请求头

| 头 | 作用 | 不带的后果 |
|---|---|---|
| **Host** | 目标域名（HTTP/1.1 必需） | 服务器返回 400 |
| **User-Agent** | 我是谁（浏览器/爬虫标识） | 很多网站直接拒绝 |
| **Accept** | 我能接受什么格式 | 服务器不知道给你 JSON 还是 XML |
| **Accept-Encoding** | 我支持哪些压缩（gzip/br） | 拿不到压缩，流量翻倍 |
| **Authorization** | 身份凭证 | 401 |
| **Content-Type** | 我发的正文是什么格式 | 服务器解析失败 |
| **Content-Length** | 正文有多长 | 服务器不知道读到哪儿停 |
| **Cookie** | 会话信息 | 每次都是"新用户" |
| **Referer** | 我从哪个页面来的 | 防盗链失效 |
| **If-None-Match** | 我有这个版本（ETag） | 拿不到 304，无法省流量 |

## 你必须认识的响应头

| 头 | 作用 |
|---|---|
| **Content-Type** | 正文是什么格式（**带字符集**才是完整的） |
| **Content-Length** | 正文字节数 |
| **Set-Cookie** | 下发 cookie |
| **Cache-Control** | 怎么缓存 |
| **ETag** | 资源指纹（配合 304） |
| **Location** | 重定向目标（配合 3xx） |
| **WWW-Authenticate** | 401 时必须带，说明怎么认证 |
| **Retry-After** | 429/503 时告诉你要等多久 |
| **Access-Control-Allow-Origin** | 跨域许可（CORS） |

## 代码：requests 里的头部

### 发送自定义头

```python
import requests

headers = {                                   # ① 用字典组织
    "User-Agent": "MyApp/1.0",                #    身份标识
    "Accept": "application/json",             #    我只要 JSON
    "Accept-Language": "zh-CN",               #    我要中文
}

r = requests.get(                             # ② 用 headers= 传入
    "https://api.github.com/user",
    headers=headers,                          #    注意是关键字参数
    timeout=10,
)
```

> **逐行拆解**
>
> - **①** 头部就是一个普通 dict。**键是头名，值是字符串**
> - **②** `headers=` 是关键字参数。**不要写成第二个位置参数**——`requests.get()` 的第二个位置参数是 `params`，把 headers 传进去会静默变成查询参数，请求发出去了但头没设上，你会困惑很久

### 头部的值是字符串，不是数字

```python
# ❌ 错误
headers = {"X-Count": 42}            # 整数，某些情况下会出错

# ✅ 正确
headers = {"X-Count": "42"}          # 字符串
```

HTTP 头部是**文本协议**，值必须是字符串。`requests` 有时会帮你转换，但这不是保证——**始终用字符串**。

### 读取响应头：用 .get()，不要用 []

```python
r = requests.get("https://api.github.com/user", timeout=10)

print(r.headers.get("Content-Type"))       # ① 推荐
print(r.headers.get("X-RateLimit-Remaining"))  # ② 可能是 None
# print(r.headers["X-RateLimit-Limit"])    # ③ 不存在时抛 KeyError
```

> **逐行拆解**
>
> - **①** `.get()` 拿不到时返回 `None`，不抛异常
> - **②** GitHub 的限流剩余次数就在这个头里。**不存在时返回 None 是完全正常的**（比如被限流前没有，或者服务器版本变了）
> - **③** 用 `[]` 访问不存在的头会抛 `KeyError`。**除非你确定它一定存在，否则用 `.get()`**

### 看看一次真实请求到底发了什么头

这个技巧非常有用——**不确定自己发出去的请求长什么样，就打出来看**：

```python
import requests

r = requests.get("https://api.github.com/user", timeout=10)

print("—— 我发出去的头 ——")
for k, v in r.request.headers.items():      # ① 注意是 r.request.headers
    print(f"{k}: {v}")

print("—— 服务器返回的头 ——")
for k, v in r.headers.items():              # ② 这个是响应的
    print(f"{k}: {v}")
```

> **逐行拆解**
>
> - **①** **`r.request.headers` 是请求头，`r.headers` 是响应头。** 这两个混淆是新手最常见的错误之一——`r.headers` 拿到的是服务器回给你的，不是你发出去的
> - **②** `r.headers` 才是响应头
>
> **为什么这个技巧重要**：当你发现"我明明设了 Authorization 头，服务器却说 401"，第一件事就是打印 `r.request.headers` 看看它到底发没发。十次里有八次是这个头被重定向丢掉了，或者根本没设上

## 关于 X- 前缀的乌龙

你可能见过 `X-Requested-With`、`X-API-Key` 这类以 `X-` 开头的头。它的来历值得一提，因为它已经被官方废弃了，但全世界还在用。

### 起因

1982 年，邮件标准 RFC 822 里规定：**自定义的、非标准的邮件头必须以 `X-` 开头**，以免和标准头冲突。这是个好设计。

### 蔓延

后来人们把这个约定带进了 HTTP。于是 1990-2000 年代，所有自定义 HTTP 头都加 `X-`：

```text
X-Forwarded-For: 客户端真实IP
X-Requested-With: XMLHttpRequest
X-RateLimit-Remaining: 剩余次数
```

### 问题

问题在于：**一旦一个 `X-` 头被广泛使用，它事实上就成了标准。这时候你想去掉 `X-` 前缀就晚了**——所有现存代码都写着 `X-`，改了就全崩。

所以你看到 `X-Forwarded-For` 明明天天在用，却永远带着"非标准"的标记。**它已经标准了，但名字改不掉了。**

### 官方叫停

2012 年，RFC 6648 明确说：**不要再给新头部加 `X-` 前缀了**。理由是：既然去掉 `X-` 在事实上不可能，那这个前缀就失去了意义，反而造成混乱。

**但是**——全世界的开发者不约而同地无视了这个建议。今天你看到的新 API 里，`X-API-Key`、`X-Request-ID` 依然遍地都是。

**给你的建议**：**跟随你调用的那个 API 的文档**——它写 `X-API-Key` 你就写 `X-API-Key`，别自作主张去掉。如果 API 是你自己设计的，用不带前缀的名字（如 `Api-Key`）更符合现行规范，但要准备好被同事问"为什么不加 X-"。

## 翻车现场

### 翻车一：手动设置 Content-Length

```python
# ❌ 错误示范
data = '{"name": "张三"}'
requests.post(
    url,
    data=data.encode("utf-8"),
    headers={"Content-Length": str(len(data))},   # 手动算长度
)
```

**现象**：有时候服务器收到的数据被截断，有时候一直等待直到超时。

**原因**：`len(data)` 数的是**字符数**，而 `Content-Length` 必须是**字节数**。中文在 UTF-8 里一个字占 3 个字节：

```python
s = "张三"
print(len(s))                       # 2   ← 字符数
print(len(s.encode("utf-8")))       # 6   ← 字节数 ★ 这才是 Content-Length
```

你告诉服务器"我发 2 字节"，实际发了 6 字节，服务器读到第 2 个字节就认为结束了——**剩下 4 个字节被当成下一个请求**，或者直接丢弃。

**教训**：**永远让 `requests` 自己算 `Content-Length`**。它是自动的，不要手动设。

### 翻车二：同时用 json= 和手动 Content-Type

```python
# ❌ 错误示范
requests.post(
    url,
    json={"name": "张三"},
    headers={"Content-Type": "application/x-www-form-urlencoded"},  # 手动改了
)
```

**现象**：服务器报"无法解析请求体"。

**原因**：`json=` 参数会自动帮你设 `Content-Type: application/json`。你手动又设了一个表单类型，结果**正文是 JSON，但声明自己是表单**——服务器按表单去解析 JSON，当然失败。

**教训**：**用了 `json=` 就别手动设 Content-Type**。这两者必须一致。第 17 课会详细讲这两者的区别。

### 翻车三：重定向把 Authorization 头丢了

```python
# 请求 A 站点，它 302 重定向到 B 站点
r = requests.get("https://a.com/data", headers={"Authorization": "Bearer xxx"})
```

**现象**：A 站点返回 302，你自动跟到了 B 站点，然后 B 说 401。

**原因**：**`requests` 在跨域重定向时，会故意丢掉 `Authorization` 头**。这是刻意的，不是 bug。

为什么？因为如果你带着给 A 的凭证去访问 B，**等于把 A 的密码交给了 B**。这是严重的安全问题。所以 `requests` 出于安全考虑默认会剥离它。

**教训**：**需要跨域名重定向时保留认证头，你得自己处理**——要么手动跟随重定向（`allow_redirects=False` 然后自己发第二个请求），要么确认两个域名是同一个服务。

## 为什么这对你写代码有用

1. **`r.headers` 是响应头，`r.request.headers` 是请求头**。这个混淆会浪费你大量时间——调试任何"我设了但没生效"的问题，第一步都是打印 `r.request.headers`
2. **用 `.get()` 读头**。服务器不保证一定给你某个头，用 `[]` 会在生产环境抛 `KeyError`
3. **头名大小写不敏感**，但**头部的值可能是任意字符串**——`Content-Length` 拿到的 `"1234"` 是字符串，要 `int()` 才能做数学
4. **不要手动设 `Content-Length` 和 `Content-Type`**（配合 `json=` 时）。让库去算
5. **重定向会丢 Authorization**，这是安全设计，别当成 bug 去"修"

## 小结

- 头部是**纯文本键值对**，HTTP/1.0 引入，为了表达"额外信息"
- 因为是文本，**你能用 telnet 手写请求**，也**因此获得了极强的可扩展性**
- 代价是**每个请求都重复发一大堆头**——HTTP/2 的 HPACK 就是来压缩它的
- **头名不区分大小写**（`requests` 用 `CaseInsensitiveDict` 实现）；**头值必须是字符串**
- **头部和正文之间必须有空行**，手写协议时最容易漏
- 同一个头可以出现多次（如 `Set-Cookie`），用 `[]` 只能拿到一个
- **必须认识**：请求头的 Host / User-Agent / Accept / Authorization / Content-Type；响应头的 Content-Type / Set-Cookie / ETag / Location / Retry-After
- **`X-` 前缀来自 1982 年的邮件标准，2012 年被 RFC 6648 废弃，但全世界还在用**
- ❌ 别手动设 `Content-Length`（字符数 ≠ 字节数）；别在 `json=` 时手动改 Content-Type
