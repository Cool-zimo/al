# 24 重试与退避：让程序在网络抖动中活下来

> 第 15 课给了一个简单重试，这一课把它做对：**什么该重试、什么不该、间隔怎么算、怎么避免把服务器打挂**。这是区分"能跑的脚本"和"能上线的服务"的分水岭。

## 先想清楚：什么该重试

回顾第 7 课和第 15 课的结论：

| 情况 | 该重试吗 | 为什么 |
|---|---|---|
| **连接超时 / 连接失败** | ✅ | 网络抖动，可能下次就通了 |
| **读取超时** | ⚠️ 谨慎 | 可能是服务器慢，猛重试会加重负担 |
| **429 限流** | ✅ | 服务器明确说"过会儿再来" |
| **500 / 502 / 503 / 504** | ✅ | 服务器临时故障，可能恢复 |
| **400 / 401 / 403 / 404 / 422** | ❌ | 请求本身有错，重试一万次也一样 |
| **SSL 错误** | ❌ | 可能是中间人攻击 |

**核心判断**：

> **重试的前提是"再来一次有可能成功"。**

4xx 不满足这个前提——你的请求是错的，**它不会因为多发几次就变对**。

## 指数退避：为什么不能固定间隔

### 固定间隔的问题

```python
# ❌ 不好
for i in range(5):
    try:
        return requests.get(url, timeout=10)
    except:
        time.sleep(1)        # 每次都等 1 秒
```

**问题**：

1. **服务器需要恢复时间**。1 秒不够的话，5 次都是在它还没恢复时打过去
2. **多个客户端会同步**。如果 100 个客户端都失败、都等 1 秒、都同时重试——**惊群效应**，服务器刚恢复又被打垮
3. **浪费额度**：对限流来说，快速重试只会让你更快被封

### 指数退避

```python
wait = base * (2 ** attempt)
```

```
第 1 次失败 → 等 1 秒
第 2 次失败 → 等 2 秒
第 3 次失败 → 等 4 秒
第 4 次失败 → 等 8 秒
```

**好处**：

- **给服务器越来越长的恢复时间**
- **越往后重试越稀疏**，不会持续施压
- 重试几次后就基本放弃了，不会无限骚扰

### 必须封顶

```python
wait = min(base * (2 ** attempt), cap)
```

**不封顶会发生什么**？第 20 次重试要等 `2^20 = 1048576` 秒 ≈ **12 天**。程序会挂在那儿。

**建议 cap = 60 秒**（最多等一分钟）。

## 抖动（Jitter）：解决惊群

**指数退避还有个问题**：如果 100 个客户端同时失败，它们的退避节奏是**完全一样**的——1s、2s、4s、8s……于是它们会在**同一时刻**集体重试。

**这就是"惊群"（thundering herd）**。

**解决办法**：**在等待时间里加随机抖动**。

```python
import random
import time

def backoff_with_jitter(attempt, base=1, cap=60):
    """指数退避 + 抖动"""
    delay = min(base * (2 ** attempt), cap)      # ① 指数部分
    jitter = random.uniform(0, delay * 0.1)      # ② 加最多 10% 的随机
    return delay + jitter

# 或者更常见的做法：在 [0, delay] 之间随机取
def backoff_full_jitter(attempt, base=1, cap=60):
    """Full Jitter（AWS 推荐）"""
    delay = min(base * (2 ** attempt), cap)
    return random.uniform(0, delay)              # ③ 完全随机
```

> **逐行拆解**
>
> - **①** 标准的指数退避
> - **② 加性抖动**：在固定延迟上再加一点随机（最多 10%）
> - **③ Full Jitter**：直接在 `[0, delay]` 区间随机。**AWS 的官方博客推荐这个**——它把重试分散得最开
>
> **Full Jitter 的效果**：客户端的平均等待时间只有固定退避的一半，但**重试被彻底打散**，服务器压力峰值大幅降低

**记忆**：**固定退避 + 抖动 = 正确的重试**。

## 尊重 Retry-After

**服务器告诉你等多久时，就按它说的等**。

```python
import requests
import time

r = requests.get(url, timeout=10)

if r.status_code == 429:
    retry_after = r.headers.get("Retry-After")

    if retry_after is not None:
        try:
            wait = int(retry_after)               # ① 通常是秒数
        except ValueError:
            wait = 60                             # ② 也可能是 HTTP 日期，简化处理
        print(f"服务器要求等 {wait} 秒")
        time.sleep(wait)
```

> **逐行拆解**
>
> - **①** `Retry-After` 通常是**秒数**
> - **②** 规范也允许是 HTTP 日期格式（如 `Wed, 21 Oct 2026 07:28:00 GMT`）。**简化处理：解析不了就等 60 秒**
>
> **为什么要尊重它**：服务器比你更清楚自己什么时候能恢复。**无视它硬重试，只会让你被封得更久**

## 自己实现一个完整的重试

把上面的东西组合起来：

```python
import requests
import time
import random
import logging

# ① 哪些状态码可以重试
RETRY_STATUS = {429, 500, 502, 503, 504}

# ② 哪些异常可以重试
RETRY_EXCEPTIONS = (
    requests.exceptions.ConnectTimeout,
    requests.exceptions.ReadTimeout,
    requests.exceptions.ConnectionError,
)

def fetch_with_retry(url, tries=4, timeout=10, base=1, cap=60, **kwargs):
    """带指数退避和抖动的 GET 请求"""
    last_error = None

    for attempt in range(tries):
        try:
            r = requests.get(url, timeout=timeout, **kwargs)

            # ③ 状态码决定是否重试
            if r.status_code in RETRY_STATUS:
                last_error = f"HTTP {r.status_code}"

                # ④ 优先用服务器给的 Retry-After
                wait = None
                ra = r.headers.get("Retry-After")
                if ra:
                    try:
                        wait = int(ra)
                    except ValueError:
                        wait = None

                if wait is None:                      # ⑤ 否则自己算
                    wait = min(base * (2 ** attempt), cap)
                    wait = random.uniform(0, wait)     #    Full Jitter
            else:
                return r                              # ⑥ 不用重试，直接返回

        except RETRY_EXCEPTIONS as e:                 # ⑦ 网络错误
            last_error = str(e)
            wait = min(base * (2 ** attempt), cap)
            wait = random.uniform(0, wait)

        # ⑧ 最后一次不再等待
        if attempt == tries - 1:
            break

        logging.warning(f"第 {attempt+1}/{tries} 次失败（{last_error}），等 {wait:.1f}s")
        time.sleep(wait)

    raise RuntimeError(f"重试 {tries} 次仍然失败: {last_error}")
```

> **逐行拆解**
>
> - **①** 可重试的状态码集合。**用集合而不是列表**，查找更快且语义清晰
> - **②** 可重试的异常元组。**注意不包括 SSLError**
> - **③** **先判状态码**。不在重试集合里就直接返回（包括 4xx，它们不重试）
> - **④** **优先尊重 `Retry-After`**
> - **⑤** 没有就用指数退避 + Full Jitter
> - **⑥** 成功（或不可重试的错误）**直接返回，不重试**
> - **⑦** 网络错误走另一条分支
> - **⑧** **最后一次失败不等待**——再等也没用了，直接抛异常
>
> **关键点**：**最后抛异常而不是返回 None**。第 15 课讲过——静默返回 None 会让调用方以为成功了。

## 用 urllib3 的 Retry（推荐）

`requests` 底层用 `urllib3`，它**自带重试机制**，比手写更完善：

```python
import requests
from requests.adapters import HTTPAdapter
from urllib3.util.retry import Retry

# ① 配置重试策略
retry = Retry(
    total=3,                      # 总共最多重试 3 次
    backoff_factor=1,             # ② 退避系数：等待 = factor * (2 ** (重试次数-1))
    status_forcelist=[429, 500, 502, 503, 504],   # ③ 哪些状态码重试
    allowed_methods=["GET", "HEAD"],              # ④ 只对安全方法重试
    respect_retry_after_header=True,              # ⑤ 尊重 Retry-After
    raise_on_status=False,                        # ⑥ 重试完还是失败就返回响应
)

# ⑦ 挂载到 Session
s = requests.Session()
s.mount("https://", HTTPAdapter(max_retries=retry))
s.mount("http://", HTTPAdapter(max_retries=retry))

r = s.get("https://api.github.com/user", timeout=10)
```

> **逐行拆解**
>
> - **① `Retry(...)`** 是 urllib3 的策略对象
> - **② `backoff_factor=1`**：等待时间 = `1 * (2 ** (n-1))`，即 0s、1s、2s、4s（**第一次不等待**）。**它自带抖动**
> - **③** 只对这几个状态码重试。**4xx 不在里面**
> - **④ `allowed_methods`**：**只对幂等方法重试**！这是关键——**POST 不应该自动重试**（可能造成重复下单）。第 6 课的幂等性在这里派上用场
> - **⑤** 尊重 `Retry-After`
> - **⑥ `raise_on_status=False`**：重试耗尽后**返回最后的响应**而不是抛异常，让你自己处理
> - **⑦ `s.mount()`** 把适配器挂到 Session 上。**注意 http 和 https 都要挂**
>
> **这是生产环境的推荐做法**。它经过了充分测试，比你手写的可靠。

### urllib3 Retry 的等待时间

```
backoff_factor = 1 时：
第 1 次重试前：等 0 秒
第 2 次重试前：等 2 秒 (1 * 2^1)
第 3 次重试前：等 4 秒 (1 * 2^2)
```

**公式**：`backoff_factor * (2 ** (retry_count - 1))`

**注意**：**urllib3 的重试次数不包含首次请求**。`total=3` 意味着"最多重试 3 次"，即**最多发 4 次请求**。

## 幂等性：POST 能不能重试？

**第 6 课的核心知识在这里兑现**：

| 方法 | 幂等 | 能自动重试吗 |
|---|---|---|
| GET | ✅ | ✅ **可以** |
| HEAD | ✅ | ✅ **可以** |
| PUT | ✅ | ✅ 可以（但要小心并发） |
| DELETE | ✅ | ✅ 可以 |
| **POST** | ❌ | ❌ **默认不该** |
| PATCH | ❌ 不保证 | ❌ 默认不该 |

**为什么 POST 不能自动重试**：

```
POST /orders  → 创建订单
超时了，你不知道订单建没建
重试 → 可能创建了两个订单
```

### 如果要重试 POST

**方案一：幂等键**（第 6 课讲过）

```python
import uuid

key = str(uuid.uuid4())
for attempt in range(3):
    r = requests.post(url, json=data,
                      headers={"Idempotency-Key": key},   # 同一个 key
                      timeout=10)
    if r.ok:
        break
```

**方案二：先查询再决定**

```python
# 超时后，先查一下订单是否已创建
r = requests.get(f"{url}?order_ref={ref}", timeout=10)
if r.json()["exists"]:
    print("其实已经创建成功了")
else:
    requests.post(url, json=data, timeout=10)      # 确认没有才重试
```

**注意**：**方案二有竞态条件**（查和创建之间可能有别的请求插入）。**幂等键是更正确的方案**——但它需要服务器支持。

## 全局设置 vs 每次设置

**推荐 Session 级别**（第 26 课会详细讲 Session）：

```python
s = requests.Session()
adapter = HTTPAdapter(max_retries=retry)
s.mount("https://", adapter)
s.mount("http://", adapter)

# 之后所有请求都有重试
```

**好处**：
- 写一次，全站生效
- 自动复用连接池（第 26 课）
- 不用每个请求都传参数

## 翻车现场

### 翻车一：对 4xx 重试

```python
# ❌ 错误
retry = Retry(total=3, status_forcelist=[400, 401, 403, 404, 500])
```

**现象**：请求参数写错了，重试 3 次，每次都 400。浪费 3 次额度和几秒时间。

**更糟的情况**：403 重试。权限不足，重试一万次也不够。

**教训**：**status_forcelist 只放 429 和 5xx**。

### 翻车二：对 POST 自动重试

```python
# ❌ 危险（如果 allowed_methods 包含 POST）
retry = Retry(total=3, allowed_methods=["GET", "POST"])
```

**现象**：下单接口超时，自动重试，用户收到两个订单、被扣两次钱。

**原因**：POST 不幂等。

**教训**：**`allowed_methods` 只放幂等方法**。urllib3 的默认值已经是这样的，**别改它**。

### 翻车三：退避不封顶

```python
# ❌ 错误
wait = 2 ** attempt        # 没有 cap
```

**现象**：重试到十几二十次时，等待时间变成几小时甚至几天。程序"卡住"了，你以为它死了。

**教训**：**必须 `min(..., cap)`**。

### 翻车四：重试次数算错

```python
retry = Retry(total=3)
```

**以为**：最多发 3 次请求。
**实际**：**最多发 4 次**（首次 + 3 次重试）。

**为什么重要**：如果你有严格的请求额度，**这个"差一"会让你超预算**。

**教训**：**记住 `total` 是"重试次数"，不含首次**。

## 为什么这对你写代码有用

1. **4xx 绝不重试**——这是最重要的一条
2. **指数退避 + 抖动**是标准做法，固定间隔会引发惊群
3. **尊重 `Retry-After`**，服务器比你清楚
4. **POST 默认不重试**，除非有幂等键
5. **用 urllib3 的 `Retry`**，别手写（除非有特殊需求）
6. **必须封顶**，否则等待时间会爆炸
7. **`total` 不含首次请求**，算额度时注意

## 小结

- **可重试**：连接失败/超时、429、5xx。**不可重试**：4xx、SSL 错误
- **指数退避** `base * 2^n`，**给服务器恢复时间**
- **必须封顶**（cap=60），否则等待时间爆炸
- **加抖动**解决惊群，**Full Jitter**（`uniform(0, delay)`）是 AWS 推荐
- **尊重 `Retry-After`** 头
- **urllib3 的 `Retry`** 是生产推荐：`total` / `backoff_factor` / `status_forcelist` / `allowed_methods`
- **`allowed_methods` 只放幂等方法**——POST 不重试（除非有幂等键）
- **`total` 不含首次**（total=3 → 最多 4 次请求）
- **重试耗尽要抛异常**，不要静默返回 None
- ❌ 别对 4xx 重试；别对 POST 自动重试；别忘封顶
