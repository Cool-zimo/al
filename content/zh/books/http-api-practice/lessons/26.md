# 26 Session 与连接复用：为什么你的循环慢了十倍

> 写一个循环，向同一个 API 发 100 个请求，你可能要等十几秒。改一行代码——把 `requests.get()` 换成 `session.get()`——同样的 100 个请求，两秒就跑完了。**这一课讲清这十倍差距到底差在哪，以及 Session 除了"快"还给你什么。**

## 先看一个你会觉得莫名其妙的现象

```python
import requests
import time

url = "https://httpbin.org/get"

# 写法 A：每次都用 requests.get
start = time.time()
for i in range(10):
    requests.get(url, timeout=10)
print(f"requests.get  : {time.time() - start:.2f} 秒")

# 写法 B：用 Session
start = time.time()
with requests.Session() as s:
    for i in range(10):
        s.get(url, timeout=10)
print(f"Session       : {time.time() - start:.2f} 秒")
```

**典型输出**（数字会因网络而异，但比例惊人地稳定）：

```
requests.get  : 6.83 秒
Session       : 0.94 秒
```

**同样的 10 个请求，7 倍差距。** 如果你的脚本要发 1000 个请求，这就是"跑 11 分钟"和"跑 1 分半"的区别。

很多人第一次看到会觉得"Session 是不是有什么黑魔法"。没有。它只是**没有把已经建好的连接扔掉**。

要理解这句话，得先知道一次请求背后到底发生了多少事。

## 一次请求背后：你以为是一步，其实是六步

当你写下 `requests.get("https://api.github.com/user")` 这一行时，底下发生的是：

```
① DNS 查询         → api.github.com 的 IP 是多少？
② TCP 三次握手     → 你好 / 收到 / 好，通道建好了
③ TLS 握手         → 加密通道协商（HTTPS 才有，但现在几乎全是）
④ 发送 HTTP 请求   → GET /user HTTP/1.1 ...
⑤ 等待并接收响应   → 服务器处理 + 数据传回
⑥ 关闭连接         → 四次挥手，再见
```

**只有第 ④⑤ 步是"真正办事"的**，①②③⑥ 全是**准备工作和收尾工作**。

### 一个比喻：打电话 vs 发传真

- **TCP 握手**：你拨号，对方接起来说"喂"，你说"是我"——**确认双方都在线、都能听见**。物理上就是三个数据包来回跑一趟
- **TLS 握手**：确认完在线之后，你们还要商量"接下来用哪种暗号说话"，交换密钥——**又是一趟来回**
- **HTTP 请求**：你终于说正事了
- **关闭连接**：挂电话

**问题在于**：如果你每问一件事就挂断电话、重新拨号、重新对暗号——那么大部分时间都花在拨号和对暗号上了，而不是在说正事。

### 用数字说话：RTT

网络里有个概念叫 **RTT（Round-Trip Time，往返时延）**——一个数据包从你这儿跑到服务器再跑回来的时间。

- 国内访问国内服务器：可能 **5~30ms**
- 国内访问美国服务器：通常 **150~300ms**

**每一趟"来回"就要一个 RTT。** 那么一次 HTTPS 请求的准备成本：

| 步骤 | 需要几个 RTT | 备注 |
|---|---|---|
| DNS 查询 | 0~1 | **本地有缓存就是 0** |
| TCP 三次握手 | **1** | 躲不掉 |
| TLS 1.2 握手 | **2** | |
| TLS 1.3 握手 | **1** | 较新的服务器支持 |
| HTTP 请求+响应 | **1** | 真正办事 |

也就是说：**发一个 HTTPS 请求，有 2~3 个 RTT 是在做准备工作，只有 1 个 RTT 是在办事。**

访问美国服务器、RTT=200ms 的情况下：

```
不复用连接：每个请求 ≈ 3 个 RTT = 600ms 准备 + 200ms 办事
复用连接  ：每个请求 ≈ 0 个 RTT 准备 + 200ms 办事
```

**这就是为什么复用连接能带来数倍提速** —— 你省掉的不是"办事"的时间，而是每次"重新拨号+对暗号"的时间。

## 为什么 `requests.get()` 不复用

看这个：

```python
import requests

requests.get("https://httpbin.org/get")     # 建连接 → 请求 → 关闭
requests.get("https://httpbin.org/get")     # 建连接 → 请求 → 关闭（重新来一遍）
```

**`requests.get()` 是一个"一次性"函数**。它的内部实际上是这样：

```python
def get(url, params=None, **kwargs):
    # 内部真实实现（简化后）
    with sessions.Session() as session:      # ① 新建一个 Session
        return session.request("GET", url, params=params, **kwargs)
    # ② with 结束 → Session 关闭 → 连接池销毁 → 连接全部丢弃
```

> **逐行拆解**
>
> - **① 每次调用都新建一个 Session**。这是关键——**`requests.get()` 从来不是"没有 Session"，而是"每次都用一个临时的新 Session"**
> - **② 用完立刻销毁**。刚建好的 TCP 连接、刚协商好的 TLS 密钥，**全部作废**

**所以真相是**：不是 `requests.get()` 不支持复用，而是它**用完就扔**。你每次调用都在重复付那 2~3 个 RTT 的"建连税"。

## Session：把连接留下来

```python
import requests

with requests.Session() as s:                    # ① 建一个 Session
    for i in range(10):
        r = s.get("https://httpbin.org/get", timeout=10)   # ② 用 s.get 而不是 requests.get
        print(r.status_code)
# ③ with 结束，Session 关闭，连接池释放
```

> **逐行拆解**
>
> - **① `requests.Session()`**：创建一个**带连接池的对象**。此时还没连任何服务器
> - **② `s.get(...)`**：第一次调用时建立连接（付建连税）；**请求结束后连接不关闭，放回池里**。第二次调用直接从池里取出用——**零建连成本**
> - **③ `with`**：Session 实现了上下文管理器。**用完一定要关**，否则连接池不释放

**为什么用 `with`**：Session 持有的连接是**真正的操作系统 socket**。不关闭的话，这些 socket 会一直占着，直到 Python 进程退出。在长期运行的服务里，这就是**文件描述符泄漏**。

### 不用 with 的写法（及为什么它更危险）

```python
import requests

s = requests.Session()
try:
    r = s.get("https://httpbin.org/get", timeout=10)
    print(r.status_code)
finally:
    s.close()          # ① 必须！
```

> - **① `s.close()`**：等价于 `with` 块结束时做的事。**忘记它，连接就泄漏了**

**建议**：能用 `with` 就用 `with`。`try/finally` 的唯一用途是"Session 的生命周期跨越了函数边界"（比如作为对象的属性长期存在）。

## Session 的三个"白送"的好处

除了快，Session 还给你三样东西。这三样在实战里甚至比"快"更重要。

### 好处一：Cookie 自动保持（登录态）

**这是最有用的一个。**

```python
import requests

with requests.Session() as s:
    # 第一步：登录
    r = s.post("https://httpbin.org/cookies/set/session_id/abc123", timeout=10)
    print("登录响应:", r.status_code)

    # 第二步：访问需要登录的页面
    r = s.get("https://httpbin.org/cookies", timeout=10)
    print(r.json())
    # {'cookies': {'session_id': 'abc123'}}     ← cookie 自动带上了！
```

> **逐行拆解**
>
> - **第一次 POST**：服务器在响应里返回 `Set-Cookie: session_id=abc123`。Session **自动把它存进自己的 cookie jar**
> - **第二次 GET**：Session **自动在请求头里加上 `Cookie: session_id=abc123`**。你一个字都不用写

**如果不用 Session**，你得手动来：

```python
# ❌ 不用 Session 的痛苦写法
r1 = requests.post("https://httpbin.org/cookies/set/session_id/abc123")
cookie_value = r1.cookies["session_id"]            # 手动取出

r2 = requests.get("https://httpbin.org/cookies",
                  cookies={"session_id": cookie_value})   # 手动带上
```

一次两次还行，一个需要登录的网站有五六个请求，你就要手动传五六个 cookie——**而且一旦服务器改了 cookie 的内容，你的代码就静默失效**。

> **这正好呼应第 10 课**：HTTP 本身是无状态的，Cookie 是"外挂"的 remember 机制。Session 帮你把这个外挂管理起来了。

### 好处二：默认请求头

重复写同一个 header 是常见的坏味道：

```python
# ❌ 每个请求都写一遍
headers = {"Authorization": "Bearer ghp_xxx", "User-Agent": "MyApp/1.0"}
requests.get(url1, headers=headers)
requests.get(url2, headers=headers)
requests.get(url3, headers=headers)
```

用 Session 设一次：

```python
import requests

with requests.Session() as s:
    s.headers.update({                                  # ① 设默认头
        "Authorization": "Bearer ghp_xxx",
        "User-Agent": "MyApp/1.0",
        "Accept": "application/json",
    })

    s.get("https://api.github.com/user", timeout=10)     # ② 自动带上
    s.get("https://api.github.com/repos", timeout=10)    #    自动带上
```

> **逐行拆解**
>
> - **① `s.headers.update(...)`**：改的是 Session 自己的 headers 字典。**注意是 `update` 而不是赋值**——Session 默认已经有 `Accept-Encoding`、`User-Agent: python-requests/...` 等头，直接赋值会把它们全清掉
> - **② 之后每个请求都自动带**

#### 合并规则：单次请求的头优先

这是很容易踩的一个点。**单次请求传的 headers 不是"替换"，是"合并"**：

```python
import requests

with requests.Session() as s:
    s.headers.update({"User-Agent": "MyApp/1.0"})

    r = s.get("https://httpbin.org/headers",
              headers={"User-Agent": "Special/2.0"},      # ① 临时覆盖
              timeout=10)
    print(r.json()["headers"]["User-Agent"])   # Special/2.0   ← 单次优先
```

> - **① 这次请求的 User-Agent 是 `Special/2.0`，不是 `MyApp/1.0`**
>
> **规则**：requests 会把 Session 的 headers 和本次的 headers **合并成一个新字典**（本次的覆盖同名的），**用完之后新的字典被丢弃**，不影响 Session 本身。
>
> 所以下一次不传 headers 的请求，User-Agent 还是 `MyApp/1.0`。

**这个"临时覆盖"的行为非常有用**——比如绝大多数请求都用 JSON，只有上传文件那次要改 Content-Type，直接在单次请求里覆盖就行。

### 好处三：默认 params / auth / 其他

凡是 `requests.get()` 能传的参数，几乎都能在 Session 上设默认值：

```python
import requests

with requests.Session() as s:
    s.params.update({"api_key": "xxxx"})        # ① 默认查询参数
    s.auth = ("user", "pass")                   # ② 默认认证（第 21 课）
    s.proxies = {"https": "http://127.0.0.1:7890"}   # ③ 代理

    s.get("https://httpbin.org/get", timeout=10)
```

> - **① `s.params`**：之后每个请求的 URL 都会自动带上 `?api_key=xxxx`
> - **② `s.auth`**：Basic 认证（第 21 课讲过）
> - **③ `s.proxies`**：**全局走代理**，在公司内网环境里很常用

**注意**：`s.params` 和单次请求的 `params` **也是合并**，规则和 headers 一样。

## 连接池：Session 内部的真相

Session 不是"一个连接"，而是**一个池子**。

```python
import requests

s = requests.Session()
print(s.adapters)           # ① 挂载了哪些适配器
# {'https://': <requests.adapters.HTTPAdapter object at 0x...>,
#  'http://':  <requests.adapters.HTTPAdapter object at 0x...>}
```

> - **① `s.adapters`** 是一个字典：**URL 前缀 → 适配器**。默认有两条规则：`https://` 和 `http://` 各自一个
>
> **适配器（HTTPAdapter）** 才是真正管连接池的东西。查找规则是**最长前缀匹配**——`https://api.github.com/` 会比 `https://` 优先命中。

### 两个关键参数

```python
from requests.adapters import HTTPAdapter
import requests

s = requests.Session()
adapter = HTTPAdapter(
    pool_connections=10,      # ① 池的数量
    pool_maxsize=10,          # ② 每个池最多几条连接
    max_retries=0,            # ③ 建连失败重试（第 24 课用的是另一个机制）
)
s.mount("https://", adapter)   # ④ 挂载生效
```

> **逐行拆解**
>
> - **① `pool_connections=10`**：**能同时记住多少个"主机"**。访问 `github.com`、`httpbin.org`、`example.com` 各占一个。默认 10
> - **② `pool_maxsize=10`**：**每个主机最多保留几条连接**。默认 10
> - **③ `max_retries=0`**：连接层面的重试。**注意和第 24 课的 `urllib3.Retry` 不是一回事**（那个是 HTTP 层的重试），这里是"连不上重连几次"
> - **④ `s.mount(...)`**：把适配器装到某个 URL 前缀上，**必须在发请求之前做**

### 默认值 10 什么时候不够

**单线程几乎永远不会不够**——你一次只能用一个连接。

**并发的时候就不够了**（第 29 课会详细讲并发）。如果你开 50 个线程共享一个 Session：

```
WARNING: Connection pool is full, discarding connection: api.github.com
```

**这条警告的意思是**：池子满了，有一条连接用完之后**没地方放，被直接丢弃**——下次要用还得重新建。

**后果不是报错，是静默变慢。** 你的并发程序会一边丢弃连接一边重建，性能退化到接近"不复用"，而且你只看日志的话只会看到一堆警告，不会看到失败。

```python
# 并发场景的正确配置
adapter = HTTPAdapter(pool_connections=50, pool_maxsize=50)
s.mount("https://", adapter)
```

**经验值**：`pool_maxsize` 设成**你的并发数**。50 个线程就设 50。

## 什么时候不该用 Session

用 Session 不是无条件的。这三种情况要想一下：

### 一、只发一个请求

```python
# 这种时候用 requests.get() 完全没问题，还少写一行
r = requests.get("https://api.github.com/user", timeout=10)
```

Session 的价值在于**复用**。只发一次，复用不上，白建一个对象。

### 二、多线程共享一个 Session

**这是最容易出错的地方。** requests 的 Session **不是严格线程安全的**。

```python
# ❌ 危险：多线程共享一个 Session
s = requests.Session()
def worker(url):
    return s.get(url)          # 多个线程同时改同一个 Session 的内部状态

# ✅ 正确：每个线程一个 Session
def worker(url):
    with requests.Session() as s:
        return s.get(url)
```

> **为什么**：Session 内部有 cookie jar、连接池这些**共享的可变状态**。多个线程同时读写，可能出现 cookie 被覆盖、连接被两个线程同时取出之类的竞态。
>
> **但注意**：**每个线程一个 Session，就失去了连接复用的好处**（线程 A 的连接线程 B 用不了）。这看似矛盾，实际上的解法是——如果真要高并发复用，应该用**异步**（第 29 课会讲）。对多线程场景，推荐"每线程一个 Session"，简单且安全。

### 三、跨请求需要完全隔离

有些场景你**不希望** cookie 或 header 被带过去：

```python
# 测试 A 用户的权限 —— 结果 Session 里还留着 B 用户的 cookie
s.get(...)   # 上一轮测试留下的登录态
```

**这种"串味"在写测试时特别致命**：测试之间互相污染，表现为"单独跑通过，一起跑就失败"。解法是每次测试新建 Session。

> **顺带一提**：这和你可能遇到过的"多账号串了"是同一类问题——**共享的可变状态在作用域上出了问题**。

## 翻车现场

### 翻车一：Session 创建后一直不关

```python
# ❌ 错误
import requests

def fetch_all(urls):
    s = requests.Session()          # 建了
    results = [s.get(u, timeout=10) for u in urls]
    return results                  # 返回了，但 s 还活着，连接没释放

# 调用一万次 → 一万个 Session，每个都占着 socket
```

**现象**：程序跑久了越来越慢，最后报 `OSError: [Errno 24] Too many open files`。

**原因**：每个 Session 的 socket 没关闭，文件描述符耗尽。

**教训**：用 `with`，或者在 `finally` 里 `close()`。**这是个"慢性的" bug——跑几分钟没事，跑几小时崩。**

### 翻车二：以为 Session 是"全局单例"

```python
# ❌ 想法："我在模块开头建一个全局 Session，全程序复用，最省"
import requests
S = requests.Session()        # 模块级全局

def a(): return S.get(url1)
def b(): return S.post(url2, json=data)
```

**现象**：功能正常，但**一旦引入多线程就出诡异 bug**；而且程序退出前连接一直占着。

**原因**：全局可变状态 + 非线程安全。

**教训**：**Session 的作用域应该和"一批相关请求"对齐**，不是和"整个程序"对齐。一个函数里发 10 个请求 → 函数内 `with`；一个对象持续发请求 → 作为实例属性，并在对象销毁时 `close()`。

### 翻车三：池满警告当没看见

```
WARNING: Connection pool is full, discarding connection: api.github.com
```

**现象**：日志刷屏，但程序照常返回结果，于是被忽略。

**原因**：并发数超过 `pool_maxsize`，连接被丢弃后重建。

**后果**：**性能静默退化**。你可能以为是 API 慢，其实是自己的连接池太小。

**教训**：看到这条警告就去调 `pool_maxsize`。**它是警告不是错误，但它的代价是"你的优化白做了"。**

### 翻车四：mount 在发请求之后

```python
# ❌ 顺序错了
s = requests.Session()
s.get("https://api.github.com/user")          # ① 先发了请求
adapter = HTTPAdapter(pool_maxsize=50)
s.mount("https://", adapter)                  # ② 再挂载 → 对已建的连接无效
```

**原因**：① 那次请求用的是默认适配器，连接已经建好并放进旧池子了。

**教训**：**`mount` 必须在任何请求之前做**。这是个很隐蔽的坑——代码看起来"配置都写了"，但因为顺序问题没生效。

### 翻车五：直接给 s.headers 赋值

```python
# ❌ 错误：把 Session 自带的默认头全清了
s.headers = {"Authorization": "Bearer xxx"}

# ✅ 正确：在原有基础上加
s.headers.update({"Authorization": "Bearer xxx"})
```

**现象**：请求莫名其妙失败，或者服务器返回奇怪的格式。

**原因**：Session 默认带 `Accept-Encoding: gzip, deflate`、`Accept: */*` 等头。直接赋值会把它们全清掉，**服务器可能因此不返回 gzip 压缩，或者不知道该返回什么格式**。

**教训**：**永远用 `update`，不要用 `=`**。

## 为什么这对你写代码有用

这一课看起来是"性能优化"，但它背后的三个观念会反复用到：

**一、准备成本往往大于办事成本。**

一次 HTTP 请求里，真正"办事"的只占 1 个 RTT，准备工作占 2~3 个。这个比例在工程里到处都是——数据库查询的连接建立、文件读写的打开关闭、进程的启动。**识别出"哪些成本可以摊薄"，是性能优化的第一步。**

**二、状态该放在哪一层，决定了代码的复杂度。**

Cookie 是 HTTP 层的状态（服务器给的），Session 是客户端的状态容器。Session 帮你把"服务器给的状态"自动回传——**这就是"把状态放在正确的层"带来的简化**。对比一下手动传 cookie 的写法，复杂度差距一目了然。

**三、共享的可变状态是 bug 的温床。**

Session 快，是因为它**共享**连接；Session 在多线程下出问题，也是因为**共享**。同一个特性，在一个场景是优点，在另一个场景是缺陷。**判断标准是：这个共享的东西，会不会被两个执行流同时改。**

## 小结

- **一次 HTTPS 请求的成本**：DNS(0~1) + TCP(1) + TLS(1~2) + 办事(1)，**准备占大头**
- **`requests.get()` 每次新建并销毁 Session** —— 不是不支持复用，是用完就扔
- **Session 复用连接**：第一次付建连税，之后零成本，提速数倍
- **必须关闭**：用 `with`，或 `finally: s.close()`，否则 socket 泄漏
- **Session 的三个附加价值**：Cookie 自动保持（登录态）、默认 headers、默认 params/auth/proxies
- **headers/params 是合并不是替换**：单次请求覆盖同名项，用后即弃，不影响 Session
- **默认头用 `update` 不要用 `=`**，否则会清掉 Session 自带的头
- **连接池**：`HTTPAdapter(pool_connections=, pool_maxsize=)`，`s.mount()` **必须在请求前**
- **池满会静默变慢**：看到 `Connection pool is full` 就把 `pool_maxsize` 调到并发数
- **Session 非线程安全**：多线程下每个线程一个
- ❌ 别建了不关；别做成全局单例；别忽略池满警告；别在请求后 mount；别给 headers 直接赋值

q: requests.get() 和 session.get() 的核心区别是什么？

- requests.get() 内部每次新建并立即销毁一个临时 Session，连接用完就丢；Session 保留连接池，后续请求复用已建立的连接，省掉 TCP/TLS 握手开销
