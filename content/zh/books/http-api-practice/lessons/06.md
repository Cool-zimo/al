# 06 方法与幂等性：为什么刷新页面会弹"是否重新提交"

> 你一定见过这个场景：填完表单点提交，然后手贱按了一下 F5，浏览器立刻弹出一个警告框——"确认重新提交表单？"。而刷新一篇普通文章，从来不会弹这个框。为什么浏览器要区别对待？因为它知道：刚才那次请求是 POST，再来一次可能有后果。这一课讲清楚这背后的整套约定。

## 一个只有 GET 的世界

回到第 4 课讲的 HTTP/0.9。1991 年那一版的协议里，**只有一种方法：GET**。

整个请求只有一行：

```text
GET /index.html
```

没有请求头，没有版本号，没有方法之外的任何东西。为什么？因为那时候的 Web 就是一件事：**取文档**。

没有登录框，没有购物车，没有评论区，没有"点赞"。网页是只读的——有人用编辑器写好 HTML 文件放在服务器上，别人用浏览器把它取下来看。**"取"是唯一的操作，所以只需要一种方法。**

这个状态持续到 1993 年。Marc Andreessen 和 Eric Bina 在 NCSA 做出 Mosaic 浏览器时，加了一个东西：**`<form>` 表单**。用户可以在网页上填东西，然后提交。

麻烦来了：**提交上去的数据要怎么发？**

用 GET 也能发——把字段拼在 URL 后面：

```text
GET /search?q=python
```

但这样有几个硬伤：

1. **URL 长度有限**。早期的服务器和浏览器对 URL 长度有各种限制（IE 曾经是 2083 个字符），写长文章会直接被截断
2. **内容全暴露在 URL 里**。密码、正文、一大段文本全都显示在地址栏，还会被存进浏览器历史
3. **语义不对**。"搜索"确实只是"取"，但"下单"显然不是在取东西——你是在让服务器**做一件事**

于是 HTTP/1.0（RFC 1945，1996 年）新增了两个方法：

- **POST** —— 我要提交数据，请服务器处理
- **HEAD** —— 和 GET 一样，但**只要响应头，不要正文**

到 HTTP/1.1（RFC 2616，1999 年）又补了一批：

- **PUT** —— 把资源**整个替换**成我发的这个
- **DELETE** —— 删掉这个资源
- **OPTIONS** —— 你支持哪些方法？
- **TRACE** —— 把我发的请求原样回给我（用来调试代理，现在基本被禁用了，因为有安全风险）
- **CONNECT** —— 给我建一条隧道（主要给 HTTPS 代理用）

**PATCH** 是后来单独加的，RFC 5789，2010 年 3 月才发布——比 HTTP/1.1 晚了整整 11 年。它解决的是"我只想改一个字段，为什么要把整个对象都发一遍"。

## 方法不是"函数名"，是"意图声明"

这是最容易误解的一点，必须先说清楚：

> **方法告诉服务器"我打算干什么"，但服务器完全可以不当回事。**

```
GET    /users/123      →  我是来读的，你别改任何东西
DELETE /users/123      →  我想删掉它
```

服务器收到 `GET /users/123` 之后，**技术上完全可以顺手把 123 号用户删掉**。没有任何机制阻止它。HTTP 是**约定（convention）**，不是**强制（enforcement）**。

那约定还有什么用？用处大了：

1. **浏览器靠它决定要不要警告你**（就是开头那个弹框）
2. **缓存靠它决定能不能缓存**（GET 的响应可以缓存，POST 的不应该）
3. **爬虫靠它决定敢不敢访问**（遵守约定的爬虫不会去 GET 一个删除链接……实际上正经爬虫根本不访问 DELETE）
4. **中间件靠它决定能不能自动重试**（下一节你就知道这有多重要）

所以方法的价值不在于"强制"，而在于**让整条链路上的各方都能预测你的行为**。

## 两个正交的属性：安全 与 幂等

HTTP 规范给每个方法定义了两个属性。这两个词很多人混着用，但它们**完全不是一回事**：

### 安全（safe）

> 安全方法**不应该**改变服务器的状态。

也就是说，安全方法应当是"只读"的。GET、HEAD、OPTIONS 都是安全方法。

注意措辞是"不应该"——同上，服务器照样可以乱来。但从调用方的角度，**调用安全方法时你不该预期服务器会发生变化**。

### 幂等（idempotent）

这个词来自数学（拉丁语 *idem* "相同" + *potens* "能力"）。定义是：

> 幂等方法：做 1 次和做 N 次，**服务器最终状态相同**。

注意关键：**看的是最终状态，不是响应内容**。

举个例子，`DELETE /users/123`：

```
第 1 次：用户存在 → 删掉 → 返回 200，用户没了
第 2 次：用户不存在 → 返回 404，用户还是没了
```

两次的**响应不一样**（200 vs 404），但**服务器状态一样**（用户都不存在）。所以 DELETE 是幂等的。

这个区别非常关键，很多人第一次学会把"幂等"理解成"返回结果一样"，然后就搞不懂为什么 DELETE 是幂等的。

### 速查表

| 方法 | 安全 | 幂等 | 一句话 |
|---|---|---|---|
| `GET` | ✅ | ✅ | 取，不改 |
| `HEAD` | ✅ | ✅ | 取头部，不改 |
| `OPTIONS` | ✅ | ✅ | 问支持什么，不改 |
| `TRACE` | ✅ | ✅ | 回显请求（现已基本禁用） |
| `POST` | ❌ | ❌ | 提交，会改，重复有后果 |
| `PUT` | ❌ | ✅ | 整体替换，改 N 次结果一样 |
| `PATCH` | ❌ | ❌（不保证） | 部分修改，取决于怎么改 |
| `DELETE` | ❌ | ✅ | 删，删 N 次结果一样 |

`POST` 是唯一一个**既不安全也不幂等**的常用方法。这不是设计缺陷——恰恰相反，**这正是它的用途**：当你要做一件"每次都该有新效果"的事（下一单、发一条消息），就该用 POST。

## 幂等性到底值多少钱：重试

现在回到第 1 课讲的端到端原则。网络是**不可靠**的，网络层故意不管可靠性，所以：

> 你发了一个请求，**超时了**。服务器到底收到没有？**你永远不知道。**

可能是请求根本没到，也可能是请求到了、活干完了、但响应在回来的路上丢了。这两种情况**对你来说完全一样**：都是超时。

这时候你只有两个选择：

1. **不重试** —— 如果是第二种情况（活已经干完了），那没问题
2. **重试** —— 如果是第二种情况，你就**干了两次**

**如果请求是幂等的，你可以闭着眼重试。** 因为做 1 次和做 N 次状态一样，多试几次没有任何后果。

**如果请求不幂等，重试就是一场赌博。** 用户点了"支付"，超时了，你重试——用户被扣了两次钱。

这就是幂等性全部的现实意义：**它让"不确定"变得可以处理。**

实际工程里，为了能让不幂等的操作安全地重试，人们会给请求带上一个**幂等键（idempotency key）**：

```python
import uuid                       # ① 生成唯一 ID 的标准库
import requests

key = str(uuid.uuid4())           # ② 随机生成一个全局唯一的字符串

r1 = requests.post(               # ③ 第一次下单
    "https://api.example.com/orders",
    json={"item": "book", "qty": 1},
    headers={"Idempotency-Key": key},   #    带上幂等键
    timeout=10,
)

# 假设这里超时了，你不知道订单建没建成
r2 = requests.post(               # ④ 重试：用同一个 key
    "https://api.example.com/orders",
    json={"item": "book", "qty": 1},
    headers={"Idempotency-Key": key},   #    ★ 关键：同一个 key
    timeout=10,
)
```

> **逐行拆解**
>
> - **①** `uuid` 是 Python 标准库，不需要 `pip install`。它专门用来生成唯一标识符
> - **②** `uuid4()` 生成的是**随机** UUID（第 4 版），重复概率低到可以在工程上视为零。`str()` 是因为 HTTP 头的值必须是字符串
> - **③** 第一次请求带上 `Idempotency-Key` 头。服务器看到这个头，就把 key 记下来，和这次创建的订单关联
> - **④** 重试时**必须用同一个 key**。服务器收到后查一下：这个 key 我已经处理过了 → 那就**不新建订单**，直接把上次的结果返回

**注意**：`Idempotency-Key` 不是 HTTP 标准头，是业界约定（Stripe、PayPal 等支付 API 都在用）。服务器得主动支持才行——它不会自动生效。

## PUT 与 PATCH：整体替换 vs 局部修改

这两个最容易混。用一个具体例子：

用户 `123` 现在的数据是：

```json
{"id": 123, "name": "张三", "email": "zhang@example.com", "age": 30}
```

### PUT：给你完整的新对象

```python
requests.put(
    "https://api.example.com/users/123",
    json={"id": 123, "name": "张三丰", "email": "zhang@example.com", "age": 30},
)
```

你必须把**所有字段都发过去**，哪怕只改了 `name`。漏掉的字段，服务器按约定应当**置空或保留为默认值**。

**为什么它幂等？** 发 1 次，对象变成 A；发 10 次，对象还是 A。状态不变。

### PATCH：只给要改的字段

```python
requests.patch(
    "https://api.example.com/users/123",
    json={"name": "张三丰"},           # 只发一个字段
)
```

只发要改的那一个。

**为什么它不保证幂等？** 取决于"改"的语义：

```
{"name": "张三丰"}          → 幂等。设 1 次和设 10 次一样
{"age": 30}                → 幂等。设值型操作都幂等
{"balance": "+100"}        → 不幂等。发 10 次加 1000
{"tags": ["a"]}            → 看实现是"追加"还是"覆盖"
```

**判断口诀**：如果 PATCH 的语义是**"设成这个值"**，就幂等；如果是**"在这个基础上加/减"**，就不幂等。

所以规范里 PATCH 被写成"不保证幂等"——它取决于你发的那部分数据是什么语义。

## 代码：requests 里的方法

`requests` 为每个方法都提供了一个同名函数，但它们**底层都走同一个入口**：

```python
import requests                    # ① 导入库

# ② 七个方法，每个都有一个同名函数
requests.get(url)                  #     GET    —— 取资源
requests.post(url, json=...)       #     POST   —— 提交
requests.put(url, json=...)        #     PUT    —— 整体替换
requests.patch(url, json=...)      #     PATCH  —— 部分修改
requests.delete(url)               #     DELETE —— 删除
requests.head(url)                 #     HEAD   —— 只要响应头
requests.options(url)              #     OPTIONS—— 问支持什么

# ③ 它们本质上都是这个通用函数的马甲
requests.request("GET", url)       #     等价于 requests.get(url)
requests.request("POST", url, json=...)
```

> **逐行拆解**
>
> - **①** 老规矩，`requests` 是第三方库，得先 `pip install requests`
> - **②** 这七个函数存在的意义**只是让你少打几个字**——`requests.get(u)` 比 `requests.request("GET", u)` 省事。它们的参数完全一样
> - **③** `requests.request()` 是真正的入口。第一个参数是方法名字符串。**当你要把方法做成变量时（比如写个能发任意方法的工具），用这个**

第二条值得多说一句：你在第 30 课写一个命令行 HTTP 工具时会发现，用户输入的 `GET` / `POST` 是个**字符串**。这时候 `requests.request(method_str, url)` 就比一长串 `if method == "GET": ... elif ...` 干净得多。

### HEAD：只取头部，省掉整个下载

HEAD 的响应**没有正文**，只有状态行和头部。它的典型用途是：**先看一眼，再决定下不下载**。

```python
import requests

r = requests.head(                      # ① 用 HEAD，不是 GET
    "https://api.github.com/repos/psf/requests",
    timeout=10,
)

print(r.status_code)                    # ② 200 表示资源存在
print(r.headers.get("Content-Length"))  # ③ 文件大小（字节），不下载就知道
print(r.headers.get("Content-Type"))    # ④ 是什么类型
print(len(r.content))                   # ⑤ 永远是 0 —— HEAD 没有正文
```

> **逐行拆解**
>
> - **①** 把 `get` 换成 `head`，其余一个字都不用改。这就是方法语义的价值：**换方法 = 换意图，不用改别的**
> - **②** HEAD 的状态码和 GET 一致。404 说明不存在，403 说明没权限——**不下载正文就能判断**
> - **③** `Content-Length` 是**服务器声明**的字节数。**注意它是"声明"，不是"保证"**——服务器可以撒谎，也可以压根不给这个头（分块传输时就没有）。所以要用 `r.headers.get(...)` 而不是 `r.headers[...]`，拿不到时返回 `None` 而不是抛 `KeyError`
> - **④** `Content-Type` 告诉你这是 JSON 还是 HTML 还是图片
> - **⑤** `r.content` 永远是 `b""`。这不是 bug，是 HEAD 的定义：**响应结构与 GET 相同，但没有正文**

**实际用途**：你要写一个"批量下载器"，先 HEAD 一下拿到文件大小，超过 100MB 就跳过——**省下了整个文件的流量**。这就是 HEAD 存在的意义。

### OPTIONS：问问服务器支持什么

```python
import requests

r = requests.options(              # ① 发 OPTIONS
    "https://api.github.com/user",
    timeout=10,
)

print(r.headers.get("Allow"))      # ② 服务器告诉你它允许哪些方法
print(r.headers.get("Access-Control-Allow-Methods"))  # ③ CORS 相关
```

> **逐行拆解**
>
> - **①** OPTIONS 是安全方法，可以放心发——它不应改变任何东西
> - **②** `Allow` 头是 OPTIONS 的标准响应头，列出该资源支持的方法。比如 `GET, HEAD, PATCH`。**但很多服务器不返回这个头**，所以拿不到 `None` 是正常的，别当成错误
> - **③** 跨域（CORS）场景下，浏览器会先自动发一个 OPTIONS 请求做"预检"（preflight），确认服务器允许跨域后才发真正的请求。**你在浏览器里看到的那些莫名其妙的 OPTIONS 请求，就是这个**

## 翻车现场

### 翻车一：用 GET 传密码

```python
# ❌ 错误示范
requests.get("https://api.example.com/login?user=admin&password=123456")
```

**现象**：功能正常，登录成功，测试全过。上线三个月后，发现密码出现在了至少五个地方：

1. **浏览器地址栏**（同事路过时看得一清二楚）
2. **浏览器历史记录**（家里人打开你的电脑就能看到）
3. **服务器访问日志**（`/var/log/nginx/access.log` 里明文躺着）
4. **代理 / CDN 的日志**（请求经过的所有中间设备都会记）
5. **`Referer` 头**（如果这个页面里有任何外链图片，浏览器会把完整 URL 当 Referer 发给那个外链站点）

**原因**：URL 从设计上就不该承载敏感信息。它是"资源的地址"，是公开可见的标识符。

**教训**：任何密码、token、身份证号，**必须放在请求体（body）或请求头里，绝不能放 URL**。

### 翻车二：把删除做成 GET

```python
# ❌ 错误示范：用 GET 删除
requests.get("https://api.example.com/users/123/delete")
```

**现象**：本地测试一切正常。上线后，用户数据莫名其妙大量丢失。

**原因**：GET 是安全方法，各方都按"安全"来对待它：

- **浏览器预加载**：现代浏览器会预先抓取页面里的链接，用户还没点就已经访问了
- **爬虫**：搜索引擎爬虫会遍历它找到的所有 GET 链接
- **缓存**：CDN 会缓存这个 URL 的响应，第二次访问直接返回缓存——**甚至不会打到你的服务器**
- **历史记录**：用户手滑点到历史里的这个地址，就删掉了

**教训**：**GET 只能用于"读"。任何改变状态的操作，用 POST / PUT / DELETE / PATCH。**

这条最讽刺的地方在于：**你自己写的删除链接，被别人"正常地"访问了一下，数据就没了**。而你没法怪对方——是你先破坏约定的。

## 为什么这对你写代码有用

把这一课和前面几课连起来：

1. **和第 1 课的端到端原则直接相关**。网络不可靠 → 你必须处理超时 → 你必须决定要不要重试 → **幂等性决定了你敢不敢重试**。这一整条链是串起来的
2. **方法选错了，bug 会很晚才暴露**。用 GET 做删除，本地测试永远测不出来——因为本地没有爬虫、没有 CDN、没有预加载。等你上线、数据被搜索引擎爬没了，才知道错了
3. **"幂等"是设计出来的，不是天生的**。POST 天生不幂等，但加一个 `Idempotency-Key` 头就能让它变成可重试的。**需要可靠重试时，先想这个**
4. **`requests.request()` 记住它**。等你写工具需要把方法当变量传时，只有它能用

## 小结

- HTTP/0.9 只有 **GET**，因为那时候 Web 是只读的。表单出现后才有了 POST
- **方法声明的是意图，不是强制**。服务器可以违背，但整条链路（浏览器、缓存、爬虫）都按约定行事
- **安全** = 不改状态；**幂等** = 做 1 次和 N 次**最终状态相同**。两者正交
- DELETE 是幂等的，虽然第 2 次返回 404——**幂等看的是状态，不是响应**
- **幂等性的全部价值：让你能安全地重试**。网络不可靠，这是刚需
- **PUT 整体替换（幂等），PATCH 部分修改（"设值"幂等，"增减"不幂等）**
- `requests` 的七个方法都是 `requests.request(method, url)` 的马甲
- **HEAD 只要头不要正文**，能不下载就知道大小
- ❌ **绝不用 GET 传敏感信息，绝不用 GET 做写操作**

```quiz
explain: 这是幂等最常见的误解。幂等的定义是"做 1 次和做 N 次，服务器的最终状态相同"，不是"响应相同"。第一次删掉用户，第二次用户已经不存在——两次之后状态完全一致（用户都没有），所以幂等
```
