# 04 三个版本：从"一行字"到统治世界近二十年

> 1991 年的 HTTP 只有一条命令，没有状态码，没有头部，甚至连版本号都没有。五年后它长出了状态码和头部。又过了一年，它变成了我们今天还在用的 HTTP/1.1——然后这个版本统治了将近二十年。

## HTTP/0.9：一行字就够了（1991）

Berners-Lee 最初实现的那个版本，简单到几乎不像一个协议。

后来为了区分，人们把它叫做 **HTTP/0.9**（这个版本号是事后追认的，当时并没有"0.9"这个叫法）。

### 请求长什么样

只有一行：

```
GET /index.html
```

就这样。

注意缺了什么：

- **没有版本号**（没有 `HTTP/0.9`）
- **没有请求头**
- **只有 GET 一个方法**
- **路径就是纯路径**，不能带查询参数

### 响应长什么样

**只有 HTML 正文，没有任何别的东西。**

```
<html>
  <body>Hello</body>
</html>
```

没有状态码，没有响应头，没有 `Content-Type`。

服务器把 HTML 发完之后，**直接关闭 TCP 连接**。连接关闭就是"我说完了"的信号。

### 这个设计有多简陋

这意味着：

- **你无法知道请求成功还是失败**。如果出错了，服务器只能返回一个写着错误信息的 HTML 页面——客户端没办法区分这是"正常的网页"还是"错误页"
- **你无法知道返回的是什么类型**。全是 HTML，传不了图片、传不了二进制
- **缓存、压缩、语言协商，一律没有**

### 但它确实能用

为什么？因为它要解决的那件事——**取一份超文本文档**——用这些就够了。

这是一个重要的原则：**协议的第一版只要解决当时的问题就行，不要为想象中的未来过度设计。** 后面的版本会补上需要的东西。

## HTTP/1.0：长出状态码和头部（1996）

随着 Web 开始爆发，0.9 立刻不够用了。

1996 年 5 月，**RFC 1945** 发布，定义了 **HTTP/1.0**。

### 加了什么

**1. 版本号**

请求里必须写明版本：

```
GET /index.html HTTP/1.0
```

**2. 状态码**

响应第一行是状态行：

```
HTTP/1.0 200 OK
```

现在客户端能一眼看出成功还是失败了。

**3. 请求头和响应头**

这是最大的变化。头部是一个可扩展的 **键值对** 系统：

```
GET /index.html HTTP/1.0
User-Agent: Mozilla/1.0
Accept: text/html
```

响应也带头部：

```
HTTP/1.0 200 OK
Content-Type: text/html
Content-Length: 1234
```

**头部为什么重要？** 因为它让协议**可扩展**。以后要加新功能，不用改协议的结构，只要定义一个新的头字段就行。这个设计支撑了后面三十年的所有扩展。

**4. 更多方法**

0.9 只有 GET。1.0 加了 **POST** 和 **HEAD**。

**5. Content-Type**

现在能传 HTML 之外的东西了——图片、纯文本、二进制。这是 Web 从"文档系统"变成"多媒体平台"的前提。

### HTTP/1.0 的致命问题：每个请求都要新建连接

这是 1.0 最大的短板，也是它很快被 1.1 取代的原因。

**1.0 的默认行为是：一个请求，建一次 TCP 连接，用完就关。**

但建立 TCP 连接要**三次握手**：

```
客户端 → 服务器: SYN         （我要连你）
服务器 → 客户端: SYN-ACK     （好的，我也准备好了）
客户端 → 服务器: ACK          （收到，开始吧）
```

这三次往返所花的时间，可能比传输数据本身还长（尤其在 1990 年代的网络条件下）。

**现在打开一个网页要加载几十个资源**（HTML、CSS、JS、图片…），每个都要握手一次。结果是页面慢得不能忍。

更糟的是，TCP 有个机制叫**慢启动（slow start）**：新建的连接一开始不敢发太多数据，要慢慢试探带宽。每次新建连接都要重新"热机"，带宽根本跑不满。

### 一个半官方的补丁：Connection: keep-alive

1.0 的规范里没有定义持久连接。但实现者实在受不了，于是搞了个非标准的做法：

```
GET /a.html HTTP/1.0
Connection: keep-alive
```

客户端加这个头，意思是"别关，我还要用"。如果服务器也认识，它就保持连接不关。

**问题是：这是非标准的。** 双方都得认识这个头，而且中间如果有代理服务器，可能有一方不认识，连接照样被关掉。**行为不可靠。**

这就是为什么 1.1 要把它变成标准。

### HTTP/1.0 还有一个没考虑到的问题：一台服务器只能放一个网站

1.0 的请求里**没有 Host 头**：

```
GET /index.html HTTP/1.0
```

服务器收到这个请求，知道客户端要 `/index.html`，但——**不知道客户端要的是哪个网站的 `/index.html`**。

在当时这可能不是问题：一台服务器跑一个网站，一个 IP 对应一个域名。

但很快，虚拟主机（virtual hosting）普及了：**一台服务器、一个 IP，托管几十个不同的网站**。`www.a.com` 和 `www.b.com` 解析到同一个 IP。

这时候服务器就傻了：你来要 `/index.html`，我该给你谁的？

**HTTP/1.1 用 Host 头解决了这个问题，而且把它定为强制项。**

## HTTP/1.1：我们今天还在用的版本（1997）

HTTP/1.1 来得很快。**1997 年 1 月，RFC 2068** 发布——距离 1.0 只有半年多。

后来经过几次修订：**RFC 2616（1999）**，再到 **RFC 7230-7235（2014）** 把一份大文档拆成六份。

### 关键改进一：默认持久连接

这是最重要的一条。

**HTTP/1.1 默认保持连接不关。**

```
GET /a.html HTTP/1.1
Host: www.example.com
```

发完这个请求，连接**保持打开**，可以接着发第二个请求，不用重新握手。

如果要关闭，得显式说明：

```
Connection: close
```

**注意"默认"这两个字的翻转：**

| 版本 | 默认行为 | 要改变默认，得说 |
|---|---|---|
| HTTP/1.0 | 用完就关 | `Connection: keep-alive` |
| HTTP/1.1 | 保持打开 | `Connection: close` |

这个翻转很重要。如果你写的代码发的是 HTTP/1.0 但没带 keep-alive，每个请求都会重建连接。

### 关键改进二：Host 头变成必需

HTTP/1.1 规定：**每个请求必须带 Host 头**。

```
GET /index.html HTTP/1.1
Host: www.example.com
```

有了它，一台服务器就能区分你要访问哪个网站。

**规范里明确写着：HTTP/1.1 请求如果没有 Host 头，服务器应该返回 400 Bad Request。**

这就是为什么你在第 03 课用 telnet 手工敲的时候，`Host:` 那一行不能省。

#### 这对虚拟主机意味着什么

有了 Host 头，一台机器托管几百个网站成为可能：

```
同一个 IP: 1.2.3.4
├── Host: www.a.com  → 返回 A 网站的首页
├── Host: www.b.com  → 返回 B 网站的首页
└── Host: www.c.com  → 返回 C 网站的首页
```

**这是现代网站托管和云服务的基石。** 没有 Host 头，一个 IP 只能服务一个域名，成本会高到无法想象。

#### 对你的实际意义

你调 API 时，如果自己拼 HTTP 请求（不是用 requests），**忘了 Host 头会得到 400**。这是一个很常见的坑，而且报错信息通常不会提示你"缺了 Host"。

### 关键改进三：管道化（Pipelining）—— 一个失败的设计

1.1 定义了一个叫 **pipelining** 的机制：客户端可以**不等前一个响应回来，就连续发多个请求**。

```
请求1 → 请求2 → 请求3        （连着发出去）
   ← 响应1 ← 响应2 ← 响应3   （按顺序回来）
```

听起来很好——省掉了等待时间。但**它在实际中基本没被使用**，原因是一个致命问题：

**响应必须按请求的顺序返回。** 如果请求1 处理得很慢，请求2 和 3 的响应即使先算好了，也必须等着——**被堵在后面**。

这叫**队头阻塞（Head-of-Line Blocking）**。

结果就是：pipelining 不但没带来多少性能提升，还引入了一堆实现上的复杂性（比如某个请求失败了怎么恢复）。**大多数浏览器最终默认关闭了它。**

> **这是一个值得记住的教训**：一个设计"听起来对"，不代表它在真实环境里能用。pipelining 在理论上完美，但在有代理、有慢请求、有失败重试的真实网络里，它的代价超过了收益。
>
> HTTP/2 后来用了完全不同的思路解决这个问题（第 05 课）。

### 关键改进四：分块传输（Chunked Transfer）

HTTP/1.0 里，服务器必须在响应头里给出 `Content-Length`（内容有多长）。

但有个问题：**如果内容是动态生成的，服务器在开始发送时可能还不知道总长度。**

比如一个数据库查询结果，你要全部查完才知道有多少字节。或者一个实时生成的报告。

HTTP/1.1 引入了 **分块传输编码**：

```
Transfer-Encoding: chunked
```

服务器把内容切成一块一块发，每块前面写上这块的长度，最后发一个长度为 0 的块表示结束：

```
5\r\n        ← 第一块 5 字节
hello\r\n    ← 内容
6\r\n        ← 第二块 6 字节
 world\r\n
0\r\n        ← 长度为 0，结束
\r\n
```

这样服务器**不需要事先知道总长度**就能开始发送。

### 关键改进五：更完善的缓存机制

1.0 的缓存很粗糙（主要靠 `Expires`，给一个绝对过期时间）。

1.1 引入了更精细的控制：

- **`Cache-Control`**：相对过期时间（`max-age=3600` 表示一小时内有效）、`no-cache`、`no-store` 等
- **`ETag`**：资源的指纹。客户端下次请求带上 `If-None-Match`，服务器比对一下，没变就返回 **304 Not Modified**（不带正文，省流量）
- **`If-Modified-Since`**：类似，但按时间比对

**304 是个很妙的设计**：服务器不传正文，只说"你缓存的那个还是最新的"。客户端直接用本地缓存。**省掉了整个响应体的传输。**

你以后调 API 时如果看到 304，不要当成错误——**它是"没变化"的意思，是正常的**。

### 其他改进

- **Range 请求**：可以只请求文件的一部分（`Range: bytes=0-999`），用于断点续传。服务器返回 **206 Partial Content**
- **更多方法**：PUT、DELETE、OPTIONS、TRACE
- **更好的内容协商**：`Accept-Language`、`Accept-Encoding`（gzip 压缩）
- **100 Continue**：客户端要发很大的请求体时，先问一句"你收吗"，服务器回 100 表示"收"，再发正文

## 为什么 HTTP/1.1 活了这么久

HTTP/1.1 是 1997 年定稿的。HTTP/2 是 **2015 年**才发布的。

**中间隔了 18 年。**

在一个技术迭代以月计的领域，一个协议活 18 年是很不寻常的。为什么？

**1. 它足够好。**

持久连接、Host、缓存、分块传输——这些解决了当时的核心痛点。大部分场景下它不慢到让人无法忍受。

**2. 它是文本协议，容易实现和调试。**

所有语言、所有框架、所有工具都支持它。换协议的迁移成本极高。

**3. 工程师在它之外找到了变通办法。**

既然每个连接都有队头阻塞，那就**多开几个连接**。浏览器对同一个域名开 6-8 个并发连接，绕开了单连接的限制。

既然头部冗长，那就**压缩内容、合并文件、用 CDN**。

**这些变通手段非常有效，以至于把 HTTP/1.1 的寿命延长了十几年。** 直到移动互联网时代，这些 workaround 的成本才开始超过换协议的成本。

**4. 换协议的代价太大。**

服务器、客户端、代理、防火墙、负载均衡——整条链路上的每一个设备都要支持。任何一个环节不认识新协议，通信就失败。

### 一个有趣的历史细节：Google 等不及了

HTTP/1.1 的问题在 2000 年代末越来越明显，但标准化进程很慢。

Google 的做法是：**不等标准，自己做一个。**

2009 年，Google 宣布了 **SPDY**（读作 "speedy"），一个实验性协议，在保持 HTTP 语义的前提下，改掉了传输层的问题：

- 二进制分帧
- 多路复用（一个连接上并发多个请求，彻底解决队头阻塞）
- 头部压缩
- 服务器推送

Google 在 Chrome 和自己的服务里部署了 SPDY，实测性能提升明显。

**后来 SPDY 成了 HTTP/2 的基础。** HTTP/2 的规范很大程度上就是"SPDY 的标准化版本"。

这是一个很有意思的模式：**当标准太慢时，有能力的公司会先用事实标准开路，然后再把它变成正式标准。**

## 版本演进一览表

| 版本 | 时间 | 关键变化 |
|---|---|---|
| **0.9** | 1991 | 只有 GET，无状态码、无头部，只返回 HTML，发完即关闭 |
| **1.0** | 1996 (RFC 1945) | 版本号、状态码、头部、POST/HEAD、Content-Type；**每请求一连接** |
| **1.1** | 1997 (RFC 2068) | **默认持久连接**、**Host 头必需**、分块传输、完善缓存、Range 请求 |
| **2** | 2015 (RFC 7540) | 二进制、多路复用、头部压缩、服务器推送 |
| **3** | 2022 (RFC 9114) | 底层从 TCP 换成 QUIC（基于 UDP） |

## 为什么这节课对你写代码有用

### 一、Host 头是必需的，忘了会 400

如果你自己拼 HTTP 报文（不用库），**Host 头不能省**。这是 HTTP/1.1 的强制要求。

用 requests 之类的库时它会自动带上，你不用管。但一旦你调试、抓包、或者写底层代码，这个坑会等你。

### 二、持久连接意味着"连接"是个可复用的资源

HTTP/1.1 默认保持连接。这意味着**反复用同一个连接发请求是快的**，每次新建是慢的。

`requests` 的 `Session` 就是干这个的（第 26 课）。你现在只需要知道：**如果你要发很多请求，用 Session 会明显更快。**

### 三、304 不是错误

你调 API 时可能看到 304。它不是失败，是"你的缓存还有效，我不重复传了"。**正确处理 304 能大大减少流量。**

### 四、队头阻塞是理解 HTTP/2 的钥匙

1.1 的队头阻塞（包括 pipelining 为什么会失败）是理解 HTTP/2 为什么那么设计的关键。**下一课就讲它。**

### 五、Content-Length 和 chunked 二选一

服务器要么告诉你总长度，要么用分块。**不会两个都有。** 你解析响应时要注意这一点。

## 小结

- **HTTP/0.9（1991）**：只有一行 `GET /path`，无状态码无头部，只返回 HTML，**发完关闭连接**。版本号是事后追认的
- **HTTP/1.0（1996, RFC 1945）**：长出**版本号、状态码、头部**，加了 POST/HEAD 和 Content-Type；**致命短板是每请求都要新建 TCP 连接**（三次握手 + 慢启动）
- 1.0 时代用非标准的 `Connection: keep-alive` 打补丁，**不可靠**
- **HTTP/1.1（1997, RFC 2068）**：**默认持久连接**（要关闭得显式写 `Connection: close`）
- **Host 头成为必需**——它让**虚拟主机**（一个 IP 托管多个网站）成为可能，是现代云服务的基石。缺了它服务器应返回 400
- **管道化（pipelining）失败了**：响应必须按序返回，导致**队头阻塞**，浏览器最终默认关闭它
- **分块传输**（`Transfer-Encoding: chunked`）让服务器不用预知总长度就能开始发
- **缓存增强**：`Cache-Control`、`ETag` + **304 Not Modified**（不是错误，是"没变化，用缓存"）
- 1.1 统治了 **18 年**（1997-2015），因为足够好、是文本协议、且有"多开连接"等变通手段
- **Google 等不及标准，2009 年做了 SPDY，后来成了 HTTP/2 的基础**
