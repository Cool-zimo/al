# 03 协议是什么：为什么 HTTP 故意让你能用键盘敲出来

> 大部分网络协议是一串你看不懂的二进制。HTTP 不是——它是纯文本，你可以用系统自带的 `telnet` 手工敲一个请求，服务器会真的回你。这个设计不是巧合，而是决定了它后来的一切。

## 先说清楚：什么是"协议"

"协议"这个词听起来很抽象。其实它就是**一套说话的规矩**。

### 一个日常的例子

你给朋友打电话：

1. 你拨号，对方拿起电话说"喂"
2. 你说"是我"
3. 对方说"啊是你啊"
4. 然后开始说正事
5. 说完，两边说"拜拜"，挂断

这整个过程就是一套协议。注意它有几个特征：

- **有固定的开场**——"喂"和"是我"。如果对方拿起电话直接开始讲正事，你会觉得奇怪
- **有来回**——你说一句，对方回一句，不是单向广播
- **有固定的收场**——"拜拜"之后才挂断
- **有隐含的规则**——谁先说话、什么时候可以打断、沉默多久算断了

如果两个人来自不同文化，这些规矩可能不一样（比如日本人打电话的开场白更长），就会出现"对话卡住"的情况。

**计算机协议就是这套东西，只是参与者是两台机器，规矩被写成精确的文档。**

### 协议的三个要素

任何协议都可以拆成三件事：

**1. 语法（syntax）：数据长什么样**

比如 HTTP 请求的第一行必须是：

```
GET /index.html HTTP/1.1
```

三个部分，中间用空格隔开，顺序不能变。写成 `GET HTTP/1.1 /index.html` 就是错的。

这就好比"喂"必须在最前面说。

**2. 语义（semantics）：每个部分是什么意思**

`GET` 表示"我要取东西"，不是"我要删东西"。`/index.html` 是路径。`HTTP/1.1` 是我说的版本。

光有语法没有语义，双方能对齐格式但不知道对方要干什么。

**3. 时序（timing）：谁先谁后，什么条件下做什么**

HTTP 规定：**客户端先发请求，服务器收到后才回响应。** 服务器不能主动给你发东西（在没有特殊机制的情况下）。

这就好比"对方拿起电话说喂之后，你才能说话"。

**这三件事任何一件没约定好，通信就会失败。** 你以后调 API 遇到的绝大部分错误，本质上都是这三件事里某一件没对上——格式不对、含义理解错了、或者顺序错了。

## HTTP 在整栋楼的第几层

网络协议是分层的。理解 HTTP 在哪一层，能解释很多你以后会遇到的怪事。

### 为什么分层

想象寄信：

- 你写信的内容（"妈，我挺好的"）——**你关心**
- 信封上写地址、贴邮票——**你关心**
- 邮车怎么把信从北京运到上海——**你不关心**
- 邮车走哪条高速、司机叫什么——**你更不关心**

分工是清楚的：**每一层只用自己的下一层，不关心下面具体怎么实现。**

网络协议也是这样。每一层给上一层提供服务，同时调用下一层的服务。**层与层之间的接口是标准化的，内部实现可以随便换。**

### 两套模型

有两种常见的分层模型，你要知道的是它们大致对应：

**OSI 七层模型**（理论模型，教科书爱用）：

| 层 | 名字 | 干什么 |
|---|---|---|
| 7 | 应用层 | HTTP、FTP、SMTP |
| 6 | 表示层 | 加密、压缩、编码 |
| 5 | 会话层 | 建立和管理会话 |
| 4 | 传输层 | TCP、UDP |
| 3 | 网络层 | IP |
| 2 | 数据链路层 | 以太网、WiFi |
| 1 | 物理层 | 电缆、光纤、无线电 |

**TCP/IP 四层模型**（实际用的）：

| 层 | 对应 OSI | 例子 |
|---|---|---|
| 应用层 | 5-7 层合并 | **HTTP**、DNS、SMTP |
| 传输层 | 4 | TCP、UDP |
| 网际层 | 3 | IP |
| 网络接口层 | 1-2 | 以太网、WiFi |

**HTTP 在应用层，最上面那层。**

### 分层的实际后果：封装

当你发一个 HTTP 请求时，数据是这样被一层层包起来的：

```
HTTP 请求:  GET /index.html HTTP/1.1\r\nHost: ...\r\n\r\n
                ↓ 加上 TCP 头（端口号、序号、校验和）
TCP 段:     [TCP头][HTTP请求]
                ↓ 加上 IP 头（源 IP、目标 IP）
IP 包:      [IP头][TCP头][HTTP请求]
                ↓ 加上以太网头（MAC 地址）
以太网帧:   [帧头][IP头][TCP头][HTTP请求][帧尾]
```

发送方从上层往下**加头**，接收方从下层往上**剥头**。

**HTTP 这一层看到的只有自己那部分，它不知道也没法控制下面发生了什么。**

这条要记住，因为它解释了一件你以后一定会撞上的事：

> **HTTP 无法知道底层连接什么时候断了。**

TCP 断开了，IP 重传了，WiFi 切换了——**HTTP 这一层是看不见的**。它只能发现"我等了很久没收到回答"，这就是**超时**。

所以你写代码时必须设 `timeout`：**不是因为 HTTP 不可靠，而是因为它被设计成看不见底层的可靠性**。第 15 课会专门讲这个。

## 为什么 HTTP 是文本协议

这是本课最重要的部分。

### 两种协议：二进制 vs 文本

**二进制协议**：数据是一串字节，每个字节（甚至每个 bit）都有精确含义。紧凑、高效，但**人看不懂**。

比如 DNS、TLS、以及后来的 HTTP/2，都是二进制的。你抓包看到的是一堆十六进制数字。

**文本协议**：数据就是可读的字符。HTTP/1.1 就是这样的。

一个完整的 HTTP 请求长这样（这是真实能发出去的）：

```
GET /index.html HTTP/1.1
Host: www.example.com
User-Agent: my-test-client

```

就这些。**纯 ASCII 文本，人能读懂每一行。**

### 为什么这么设计

Berners-Lee 在 1990 年设计 HTTP 时选择了纯文本，原因非常实际：

**1. 人可以直接调试**

1990 年没有成熟的 HTTP 调试工具。如果协议是二进制的，你要写一个专门的解析器才能看到自己发的是什么。

文本协议意味着：**任何能看文本的东西都能看 HTTP**。你可以用 `telnet` 手工发一个请求，用 `cat` 看响应，用 `grep` 过滤。

**2. 出错时能看懂**

服务器返回一个错误，如果是二进制的，你得查文档对照字节含义。文本协议直接给你一行人类可读的消息。

**3. 不需要专门的库**

任何能读写字符串的程序都能实现 HTTP。这在 1990 年很重要——当时的网络库非常少。

### 亲自试一次

这是本课唯一需要动手的地方，而且**值得真的做一遍**，因为做过之后你对 HTTP 的理解会完全不一样。

打开你的终端，输入：

```bash
telnet example.com 80
```

看到连接成功之后，**逐行敲**下面这段（注意最后要有一个空行）：

```
GET / HTTP/1.1
Host: example.com

```

然后你会看到服务器返回一大段文本，开头是：

```
HTTP/1.1 200 OK
```

**你刚才没有用浏览器，没有用任何库，只用键盘敲了几行字，就完成了一次 HTTP 请求。**

> **逐行拆解**
>
> - **`telnet example.com 80`**：telnet 是一个"把你的键盘输入原样发给对方"的工具。`80` 是 HTTP 的默认端口（下一节讲为什么是 80）
> - **`GET / HTTP/1.1`**：请求行。三个部分——方法 `GET`、路径 `/`、协议版本 `HTTP/1.1`
> - **`Host: example.com`**：请求头。这一行在 HTTP/1.1 里是**必需的**（第 04 课会讲为什么）
> - **空行**：这是关键。**头部结束的标志就是一个空行**。你不敲这个空行，服务器会一直等你，直到超时
> - **`HTTP/1.1 200 OK`**：状态行。`200` 是状态码，`OK` 是原因短语

**如果你第一次敲，最可能失败的地方就是忘了那个空行。** 这不是小细节——它是 HTTP 报文格式的核心约定，后面讲请求头时会反复遇到。

> **Windows 用户注意**：新版 Windows 默认不装 telnet，需要在"启用或关闭 Windows 功能"里打开。如果嫌麻烦，第 11 课会用 Python 做到同样的事。

### 文本协议的代价

当然，纯文本不是免费的。它的缺点是：

- **冗长**。一个请求头几十上百字节，重复的字段每次都要重发
- **解析慢**。要按字符扫描、找换行、切字符串
- **有歧义**。空格、换行、编码的处理容易出错（这也是安全漏洞的常见来源，比如"请求走私"）

**HTTP/2 后来正是为了解决这些问题，改成了二进制。** 第 05 课会讲。

所以这是一个清晰的取舍：

| | 文本（HTTP/1.1） | 二进制（HTTP/2） |
|---|---|---|
| 人能读懂 | ✅ 可以 telnet 手工敲 | ❌ 需要工具 |
| 体积 | 大 | 小（有压缩） |
| 解析速度 | 慢 | 快 |
| 调试难度 | 低 | 高 |

**1990 年选文本是对的**（好调试、好实现），**2015 年改二进制也是对的**（性能成了瓶颈）。技术选择没有绝对的对错，只有"哪个阶段更痛"。

## 端口 80：一个 1990 年定下的数字

你刚才用 `telnet example.com 80` 连到了 80 端口。为什么是 80？

### 端口是什么

一台机器只有一个 IP 地址，但上面跑着很多网络程序：网页服务、邮件服务、SSH……

IP 地址把你送到**正确的机器**，端口号把你送到**机器上正确的程序**。

端口号是 0-65535 的一个数字。

### 为什么 HTTP 是 80

80 这个数字是 **IANA**（互联网号码分配局，负责全球互联网编号的机构）分配给 HTTP 的"知名端口"（well-known port）。

IANA 维护着一张表，把 0-1023 这段分配给各种常用服务：

| 端口 | 服务 |
|---|---|
| 21 | FTP |
| 22 | SSH |
| 25 | SMTP（发邮件） |
| 53 | DNS |
| **80** | **HTTP** |
| 443 | HTTPS |

**这个分配是在 HTTP 还很早期就定下的**，当时只是"挑一个没被占用的号"。没有特别的含义。

**但因为它是默认值，浏览器在你不写端口时就自动用 80。** 所以三十多年后，全世界的 Web 流量依然跑在 80 和 443 上。

### 实操意义

**默认端口可以省略。** 这些写法是等价的：

```
http://example.com:80/index.html
http://example.com/index.html       ← 省略了 :80
```

HTTPS 同理，默认 443。

**但非默认端口必须写出来**：

```
http://localhost:8000/       ← 本地开发常见，8000 必须写
```

你以后写本地服务、调测试接口时，`localhost:8000` 这种写法会非常常见。**端口不写就是 80，写错了就连接失败。**

## 无状态：HTTP 最出名也最容易被误读的特性

你会到处看到一句话：**HTTP 是无状态协议（stateless）**。

### 这是什么意思

**服务器不会记住你上一次请求做了什么。**

每一个请求都是独立的。服务器处理完就忘了。你发第二个请求时，服务器**完全不知道**你刚才发过第一个。

举个具体的例子：

```
你: GET /login  (带用户名密码)
服务器: 200 OK，登录成功
你: GET /my-profile
服务器: 200 OK，这是你的个人资料
你: GET /my-profile
服务器: 200 OK，这是你的个人资料
```

注意后两个请求——**服务器不知道"你"是谁**。它没有记住你刚才登录过。

### 为什么这么设计

回到第 01、02 课讲的：Berners-Lee 要解决的问题是**文档互相链接**。

取一份文档，这是一次独立的动作。取完了，这次交互就结束了。**根本不需要状态。**

而且无状态有个巨大的好处：**简单且可扩展**。

服务器不需要为每个客户端保存任何东西，意味着：

- 服务器崩溃重启，不影响任何客户端
- 请求可以发给**任何一台**服务器（所以能负载均衡、能加机器）
- 不需要处理"会话过期""内存占用"这些问题

如果 HTTP 一开始就是有状态的，负载均衡和多服务器部署会困难得多。

### 代价：状态被硬加回来了

无状态在"取文档"时完美，但一旦你要做**登录、购物车、个性化**，就立刻不够用了。

于是后来加了一系列机制把状态补回来：

- **Cookie**（第 10 课）：服务器让浏览器存一小段数据，下次请求带上
- **Session**：服务器存状态，只把 ID 给浏览器
- **Token / JWT**（第 22 课）：把状态编码进一个字符串，每次请求带上

**所有这些机制的本质都一样：在请求里附带额外的信息，让服务器能"认出你"。**

理解这一点，你就明白了为什么调 API 时总要带 `Authorization` 头——**因为 HTTP 本身不记得你是谁，你必须每次都自报家门。**

### 一个常见误解

有人把"HTTP 无状态"理解成"HTTP 不能保持连接"。

**这是两回事。**

- **无状态**讲的是**语义**：服务器不记你的身份和历史
- **持久连接**（HTTP/1.1 的 keep-alive）讲的是**传输**：TCP 连接能不能复用

HTTP/1.1 可以保持 TCP 连接复用（第 04 课），但**每一个请求在语义上仍然是独立的**。连接复用只是省了重新握手的时间，服务器并没有因此记住你。

## 请求-响应：一个不能反过来的顺序

HTTP 是严格的**请求-响应模型**：

1. 客户端发一个请求
2. 服务器回一个响应
3. 一次交互结束

**服务器不能主动给客户端发东西。**

这条限制在今天看来很别扭——你用的消息推送、实时聊天、股票行情，都需要服务器主动推。但 HTTP 最初没有这个能力。

### 后来怎么解决的

为了绕过"服务器不能主动推"，工程师们想了一系列办法：

| 技术 | 做法 |
|---|---|
| **轮询** | 客户端每隔几秒问一次"有新数据吗" |
| **长轮询** | 客户端发请求，服务器**故意不回**，等有数据了才回 |
| **SSE** | 服务器保持连接，持续地往外推文本 |
| **WebSocket** | 另起一个协议，升级成真正的双向通道 |

注意前三个**本质上还是请求-响应**——只是把"响应"的时间拖长了。WebSocket 才是真正跳出了这个模型（它用 HTTP 握手，之后就不再是 HTTP 了）。

### 对你写代码的意义

你调 API 时的基本心智模型永远是这个：

```python
r = requests.get(url)        # ① 你发请求，然后停在这里等
print(r.status_code)         # ② 拿到响应，才能看结果
```

> **逐行拆解**
>
> - **①** 这一行是**阻塞**的：程序停在这里，直到服务器响应或者超时。这是请求-响应模型在你代码里的直接体现——**你不发请求，就永远收不到东西**
> - **②** 响应是"这一次请求的回答"。如果你想再要一次，就得再发一次请求。`r` 不会自动更新

**你永远不能写"等服务器通知我"这样的代码。** 只能写"我主动去问"。

## 为什么这节课对你写代码有用

### 一、分层决定了你能控制什么

HTTP 看不见 TCP。所以：

- **连接断了它不知道**，只能表现为超时 → 你必须设 `timeout`
- **重传是 TCP 干的**，HTTP 不管 → 你不用自己写重试逻辑，但要处理"等太久"
- **IP 换了它不知道** → 手机从 WiFi 切到 4G，正在进行的请求会失败

### 二、文本协议让你能自己看

你以后调 API 出问题，第一件事**不应该是改代码**，而是**看看实际发了什么、收到了什么**。

因为 HTTP 是文本的，这件事很容易做——后面会教你用 Python 把原始报文打印出来。

**绝大多数"API 调不通"的问题，看一眼原始报文就明白了。** 参数拼错了、头没带、编码不对，全都一目了然。

### 三、无状态决定了认证的写法

因为服务器不记得你，**每个请求都要带身份信息**。这不是某个 API 的怪癖，这是 HTTP 的设计决定的，所有 API 都这样。

### 四、默认端口省事，但也是坑

`localhost:8000`、`localhost:3000`、`localhost:8080`——本地开发时这些端口各不相同。**写错端口是最常见的"连接被拒绝"的原因**，而且报错信息往往不说人话。

## 小结

- **协议 = 语法 + 语义 + 时序**。以后调 API 出错，基本都是这三样里某一件没对上
- HTTP 在**应用层**（TCP/IP 模型最上层），它**看不见底层**，所以连接断开只能表现为**超时**
- 数据从上层往下**一层层加头**，接收方从下层往上**层层剥头**
- **HTTP/1.1 是纯文本协议**——这是 1990 年为"好调试、好实现"刻意选的，代价是冗长和解析慢（HTTP/2 因此改二进制）
- **可以用 `telnet example.com 80` 手工发请求**：请求行 + 请求头 + **一个空行**（忘敲空行是新手第一大坑）
- **端口 80 是 IANA 分配的知名端口**，没有特殊含义，只是默认值；HTTPS 是 443；非默认端口必须写出来
- **无状态**：服务器不记得你上一次请求。好处是简单可扩展，代价是登录/购物车必须靠 Cookie、Token 额外补
- **无状态 ≠ 不能保持连接**。keep-alive 复用的是 TCP 连接，语义上每个请求仍独立
- **请求-响应模型**：服务器不能主动推。轮询、长轮询、SSE 都是变通的拖长响应，WebSocket 才真正跳出

explain: 这正是浏览器做的事——你不写端口，它按协议补上默认值。所以 http://a.com 和 http://a.com:80 完全等价。归一化大小写很关键：URL 的协议部分按规范是大小写不敏感的，但字典的键是精确匹配的
```

q: 关于 HTTP 的"无状态"（stateless），下面哪个说法是对的？
options:
- 无状态意味着 HTTP 不能复用 TCP 连接，每次都要重新握手
- 无状态意味着服务器不记得客户端上一次请求做过什么；但 HTTP/1.1 仍可以复用 TCP 连接（keep-alive）
- 无状态是因为 HTTP 用 UDP 而不是 TCP
- 无状态只在使用 Cookie 时才成立
answer: 1
explain: 无状态讲的是语义（服务器不记你的身份和历史），keep-alive 讲的是传输（TCP 连接复用）。两者是不同层面的事：HTTP/1.1 可以复用连接省去握手开销，但每个请求在语义上依然完全独立，服务器仍不记得你
```
