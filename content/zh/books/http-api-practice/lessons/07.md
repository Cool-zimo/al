# 07 状态码的哲学：为什么 404 不直接返回 200 加一句"没找到"

> 几乎每个刚学 API 的人都会问同一个问题：找不到资源，返回 200 然后在 JSON 里写 `{"error": "not found"}` 不就行了？为什么要专门发明一个 404？这一课回答这个问题，并且把最常用的十几个状态码逐个拆开讲——包括那个最容易被搞混的 401 和 403。

## 状态码是给程序看的，不是给人看的

先说结论，因为这是理解全部状态码的钥匙：

> **HTTP 状态码存在的唯一目的，是让客户端程序在"不读响应正文"的情况下，就能判断这次请求的结果属于哪一类。**

想象一个缓存服务器。它拿到一个响应，需要在**极短时间内**决定：这个响应我能缓存吗？

- 如果状态码是 **200**：可以缓存
- 如果状态码是 **404**：可以短期缓存
- 如果状态码是 **500**：绝对不能缓存

它做这个判断的时候，**根本不会去读你的 JSON 正文**。它只看状态行那三个数字。

如果你的 API 无论什么都返回 200，那么：

- 缓存会把**错误响应也缓存起来**，然后未来几十分钟里所有用户都拿到"没找到"
- 浏览器不知道该不该重试
- 监控系统的"错误率"永远是 0%，直到用户投诉你才发现服务早就挂了
- 负载均衡器不知道要把这台机器摘掉

**这就是为什么状态码不能省。** 它不是给人看的提示文字，是**协议的语义层**，是让整条链路上所有不认识你的程序都能正确行事的基础。

## 三位数字的结构

状态码是三位十进制数。**第一位数字决定了类别**：

| 首位 | 类别 | 一句话 | 谁该行动 |
|---|---|---|---|
| **1xx** | 信息 | 收到，继续 | 客户端继续发 |
| **2xx** | 成功 | 你要的东西好了 | 客户端处理响应 |
| **3xx** | 重定向 | 去别处找 | 客户端自动跳转 |
| **4xx** | 客户端错误 | 你的请求有问题 | 客户端改请求 |
| **5xx** | 服务器错误 | 我出问题了 | 可以重试 |

**后两位是这一类中的具体编号**，规范只定义了常见的那些，剩下的留给你自己扩展（很多公司会用 4xx 里没被占用的数字表示特定业务错误，这是允许的）。

一个记忆技巧：**"4 是你错了，5 是我错了"**。这个区分极其重要，因为它决定了**该谁去修**：

```
4xx → 是你的请求写得不对，改你的代码，重试没用
5xx → 是服务器出问题了，重试可能有用
```

## 1xx：我还在听

1xx 是"临时响应"，表示请求已收到，还在处理中。

最重要的是 **100 Continue**：

当客户端要发一个很大的请求体时，它可以先发头部，带上：

```text
Expect: 100-continue
```

服务器看一眼头部，如果觉得可以（比如认证没问题），就回一个 `100 Continue`，客户端这才把几 GB 的正文发过去。**如果服务器直接回 417（期望不满足）或 401，客户端就不用白白上传几 GB 了。**

**日常写 Python 你几乎不会遇到 1xx**，因为 `requests` 会自动处理。但你要知道它存在，否则在抓包时看到一个 `100` 会以为是错误。

`101 Switching Protocols` 你应该见过——**WebSocket 连接建立时就是它**。客户端说"我想升级成 WebSocket"，服务器说 `101`，然后双方就不再说 HTTP 了。

## 2xx：成了

### 200 OK

最常见的成功。**注意：200 只代表"请求被成功处理"，不代表"返回了你想要的东西"。**

这句话听起来像废话，但它是新手最大的坑。看这个：

```python
r = requests.get("https://api.example.com/user", timeout=10)
print(r.status_code)      # 200
print(r.json())           # {"error": "invalid token"} ← 也是 200！
```

有些 API 设计糟糕，认证失败也返回 200。**所以永远要先看状态码，再看正文**——但更不能只看状态码。

### 201 Created

**创建了新资源**。和 200 的区别是语义：`POST /users` 成功创建了一个用户，应该返回 **201**，不是 200。

规范的完整约定还要求 201 的响应带一个 **`Location` 头**，指向新资源的地址：

```text
HTTP/1.1 201 Created
Location: /users/456
```

### 202 Accepted

**收到了，但还没处理完**。典型场景：你提交一个耗时任务（转码视频、生成报表），服务器不让你干等，直接回 202，然后给你一个任务 ID 让你去轮询。

这在异步 API 里非常常见。

### 204 No Content

**成功了，但没有正文**。

DELETE 成功后通常返回 204。它和 200 的区别：**204 的响应体必须是空的**，浏览器不应该刷新页面。

```python
r = requests.delete(url, timeout=10)
if r.status_code == 204:
    print("删除成功，且没有返回内容")
print(r.content)          # b"" —— 一定是空的
```

**注意 204 的一个坑**：`r.json()` 会抛异常，因为没有 JSON 可解析。**所以判断删除成功要用 `== 204`，不要无脑 `.json()`。**

## 3xx：去别处

### 301 vs 302：永久 vs 临时

这两个的区别直接影响**浏览器会不会缓存这个跳转**：

| | 含义 | 缓存跳转吗 | SEO |
|---|---|---|---|
| **301** | 永久搬家了 | ✅ 记住，以后直接去新地址 | 权重转移给新地址 |
| **302** | 临时去那儿 | ❌ 每次都先来问 | 权重保留在原地址 |

**实际影响**：如果你的网站从 HTTP 迁到 HTTPS，用 301，用户第二次访问就直奔 HTTPS，快。用 302，每次都要先访问 HTTP 再跳转一次，慢，而且有被劫持的风险。

### 304 Not Modified：省流量的关键

这个状态码有点特殊——**它不算错误，是一种"你已经有最新版了"的成功**。

流程是这样的：

1. 浏览器第一次请求，服务器返回资源 + 一个 `ETag`（资源的指纹，比如内容的哈希）
2. 浏览器缓存下来
3. 第二次请求时，浏览器带上 `If-None-Match: <上次的ETag>`
4. 服务器比对：指纹没变 → 返回 **304**，**不返回正文**
5. 浏览器看到 304，就直接用本地缓存

**省下了整个响应体的传输**，只花了一个极小的头部往返。这是 Web 性能优化的基础机制之一。

```python
import requests

r1 = requests.get("https://api.github.com/user", timeout=10)
etag = r1.headers.get("ETag")           # ① 拿到指纹

r2 = requests.get(                       # ② 再请求一次，带上指纹
    "https://api.github.com/user",
    headers={"If-None-Match": etag},     #    告诉服务器"我有这个版本"
    timeout=10,
)

print(r2.status_code)                    # ③ 可能是 200（变了）或 304（没变）
if r2.status_code == 304:
    print("内容没变，用缓存，省了整个响应体")
```

> **逐行拆解**
>
> - **①** `ETag` 是服务器给这个资源算的指纹。它不是标准规定必须有的，但主流服务都会给
> - **②** `If-None-Match` 是**条件请求头**。语义是"如果这个资源的指纹不是我给的这个，才把内容发给我"
> - **③** **关键**：`requests` 处理 304 时，`r2.text` 是空的。**你必须先判断状态码，不能直接用 `r2.text`**——否则会拿到空字符串还以为内容变空了

## 4xx：你错了

### 400 Bad Request

请求本身有问题：JSON 格式错、参数缺了、字段类型不对。

**这是"我没法解析你说的话"**。

### 401 Unauthorized vs 403 Forbidden：最容易混的一对

这是全 HTTP 里**最容易搞错的一组**，值得单独拆开：

| | 401 | 403 |
|---|---|---|
| 直译 | 未授权 | 禁止 |
| **真实含义** | **你还没证明你是谁** | **我知道你是谁，但你不配** |
| 类比 | 进大楼要刷卡，你没带卡 | 你刷了卡，但你是访客，进不了机房 |
| 该做什么 | 去认证，带上 token | **别重试了**，换账号或申请权限 |
| 响应应带 | `WWW-Authenticate` 头 | 无 |

**记忆法**：
- **401 = 没带身份证**（Unauthorized 这个名字起得不好，它其实是"未认证 Unauthenticated"的意思）
- **403 = 身份证带了，但级别不够**

这个区分的实际意义：**401 你重试带上 token 就能成功，403 你重试一万次也没用**。所以看到 403 就不要写自动重试逻辑了。

### 404 Not Found

资源不存在。

**一个设计上的常见争议**：用户 A 请求用户 B 的私有资源，应该返回 404 还是 403？

从"信息泄露"角度考虑，**应该返回 404**：如果返回 403，攻击者就知道了"这个 ID 的资源确实存在"，从而可以枚举。**返回 404 等于不承认它的存在**。这是安全上的常见做法。

### 405 Method Not Allowed

方法不被支持。比如对一个只读资源发 PUT。

规范要求这个响应**必须带 `Allow` 头**，告诉客户端哪些方法是可以的：

```text
HTTP/1.1 405 Method Not Allowed
Allow: GET, HEAD
```

### 409 Conflict

**请求本身没问题，但和服务器当前状态冲突**。典型：创建一个已存在的用户名。

和 400 的区别：**400 是"你这话我听不懂"，409 是"我听懂了，但现在这么做会打架"**。

### 418 I'm a teapot

这是个**正经写进 RFC 的彩蛋**。来自 RFC 2324（超文本咖啡壶控制协议，1998 年 4 月 1 日发布）：

```text
418 I'm a teapot
（我是一个茶壶）
```

语义是"服务器拒绝用茶壶煮咖啡"。它本来是愚人节 RFC，但被保留下来了。**有些服务真的会用它来表示"我不想处理这个请求"**。

知道它的意义在于：**当你在日志里看到 418，不要以为是框架出 bug 了**。

### 429 Too Many Requests

**限流**。你请求太频繁了。

关键是它**必须配合 `Retry-After` 头**，告诉你要等多久：

```python
import requests
import time

r = requests.get("https://api.github.com/rate_limit", timeout=10)

if r.status_code == 429:                      # ① 被限流了
    wait = int(r.headers.get("Retry-After", 60))  # ② 服务器说要等多久
    print(f"被限流，等待 {wait} 秒")
    time.sleep(wait)                            # ③ 真的等
    r = requests.get("https://api.github.com/rate_limit", timeout=10)
```

> **逐行拆解**
>
> - **①** 一定要显式判断 429。不判断的话，你会拿到一个"错误响应"还当成正常数据处理
> - **②** `Retry-After` 的单位是**秒**（也可能是 HTTP 日期，但秒更常见）。`get(..., 60)` 的 60 是**兜底**：服务器没给这个头时默认等 60 秒
> - **③** `time.sleep()` 会**阻塞整个程序**。写爬虫时这没问题，写 Web 服务时这会卡死——那时要用异步方案（第 29 课讲）

**429 是唯一一个明确告诉你"过会儿再来"的错误码**，所以它是可重试的。

## 5xx：我错了

### 500 Internal Server Error

服务器代码抛异常了。**对你来说意味着：这大概率不是你的错**。

### 502 vs 503 vs 504：三个"服务器挂了"的区别

这三个最容易混，但区别很实际：

| | 名字 | 谁出问题 | 典型场景 |
|---|---|---|---|
| **502** | Bad Gateway | **网关/代理**收到了上游的无效响应 | Nginx 后面的 Python 进程崩了 |
| **503** | Service Unavailable | **服务器忙不过来或正在维护** | 流量突增、重启中 |
| **504** | Gateway Timeout | **网关等上游等超时了** | 后端查询跑了 60 秒还没完 |

**对你写代码的实际意义**：

- **502 / 504**：是后端的问题，**可以稍后重试**
- **503**：看情况。如果是维护，等 `Retry-After`；如果是过载，你重试反而会让它更糟（**这时候应该退避，第 24 课讲**）

## 代码：requests 里怎么用状态码

```python
import requests

r = requests.get("https://api.github.com/user", timeout=10)

print(r.status_code)        # ① 整数：200、404、500……
print(r.reason)             # ② 文字："OK"、"Not Found"
print(r.ok)                 # ③ 布尔：状态码 < 400 时为 True

r.raise_for_status()        # ④ 4xx/5xx 时抛异常，2xx/3xx 时什么都不做
```

> **逐行拆解**
>
> - **①** `status_code` 是**整数**，不是字符串。写 `r.status_code == "200"` 永远 False——这是个极常见的低级错误
> - **②** `reason` 是状态行里的文字说明。**它只是给人看的，别用它做判断**（不同服务器写的文案不一样）
> - **③** `r.ok` 等价于 `r.status_code < 400`。注意 **3xx 也算 ok**（重定向不是错误）。这是最方便的快速判断
> - **④** `raise_for_status()` 抛的是 `requests.exceptions.HTTPError`。**2xx 和 3xx 时它静默返回 None**——所以可以安全地放在任何请求后面

**`raise_for_status()` 的价值**：它让你不用写十几个 `if status == ...`。一行搞定"非 2xx/3xx 就抛异常"。

配套的写法是：

```python
import requests

try:
    r = requests.get("https://api.example.com/data", timeout=10)
    r.raise_for_status()                  # ① 4xx/5xx 在这里变成异常
    data = r.json()                       # ② 只有到这里才解析
except requests.exceptions.HTTPError as e:
    print(f"HTTP 错误: {e}")               # ③ 捕获
except requests.exceptions.Timeout:
    print("超时了")
```

> **逐行拆解**
>
> - **①** 放在请求之后、解析之前。**顺序不能反**——先确认响应正常，再解析
> - **②** 只有通过了 ① 才会执行。这样你永远不会在一个 HTML 错误页上调用 `.json()`
> - **③** `HTTPError` 只覆盖 4xx/5xx。**网络问题（超时、连接失败）是另外的异常类型**，所以还需要捕获 `Timeout`、`ConnectionError`

**注意第 24 课会展开**：这里只捕获了两种，实际工程里还要处理重试。

## 翻车现场

### 翻车一：只判断 200

```python
# ❌ 错误示范
r = requests.get(url, timeout=10)
if r.status_code == 200:
    return r.json()
# 其他情况什么都不做，返回 None
```

**现象**：服务器返回 201（创建成功）或 204（删除成功），你的代码当成失败，静默返回 `None`。调用方拿到 `None` 后继续跑，几步之后才崩，而且崩的地方离这里很远。

**原因**：**2xx 有七八个**，不只是 200。

**教训**：判断成功用 `r.ok`（等价于 < 400），不要用 `== 200`。

### 翻车二：403 还在疯狂重试

```python
# ❌ 错误示范
for i in range(5):                    # 重试 5 次
    r = requests.get(url, timeout=10)
    if r.ok:
        break
    time.sleep(1)
```

**现象**：权限不足（403）或参数错误（400），重试 5 次，每次都是同样的错误，白白浪费 5 秒，还把服务器的限流额度耗光。

**原因**：**4xx 是不可重试的错误**——你再发一万次，请求还是错的。

**教训**：**重试只对 5xx 和 429 有意义**。4xx 应该立刻失败并报错给人看。

## 为什么这对你写代码有用

1. **状态码是协议层，不是应用层**。所有不认识你的中间件（缓存、负载均衡、监控、CDN）都靠它工作。返回 200 + body 里的 error 字段，等于让整条链路全部瞎掉
2. **第一位数字决定"该谁修"**：4xx 改你的代码，5xx 找后端
3. **401 和 403 的区别决定要不要重试**：401 补 token 重试，403 放弃
4. **429 是唯一"友好"的错误**，它告诉你等多久，一定要用 `Retry-After`
5. **`raise_for_status()` 是你的默认动作**，除非你有明确理由要手动处理每种状态码

## 小结

- 状态码**给程序看**，让客户端不看正文就能分类。**全部返回 200 会让缓存、监控、负载均衡全瞎**
- **首位定类别：4 是你错了，5 是我错了**
- **2xx 不止 200**：201 创建、202 异步受理、204 成功但无正文（**别对它 `.json()`**）
- **301 永久（可缓存跳转）/ 302 临时**；**304 用 ETag 省掉整个响应体**
- **401 = 没带身份证（可补救），403 = 带了但级别不够（别重试）**——最容易混的一对
- **409 是"听懂了但状态冲突"，400 是"听不懂"**
- **429 必须配合 `Retry-After`，是可重试的**
- **502 上游返错了 / 503 忙或维护 / 504 上游超时**
- `r.ok` = 状态码 < 400；**`raise_for_status()` 是非 2xx/3xx 抛异常**
- ❌ **别只判断 `== 200`，别对 4xx 做重试**
