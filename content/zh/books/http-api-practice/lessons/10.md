# 10 Cookie 与状态：HTTP 是怎么"记住"你的

> 第 3 课讲过：HTTP 是**无状态**的——服务器不记得你上一次请求做了什么。但现实里你登录一次，之后逛一整天都不用重新登录。这个"记住"是怎么实现的？答案就是 Cookie。这一课讲它的发明故事、工作原理、那些让人头疼的属性，以及为什么它成了隐私问题的中心。

## 无状态带来的麻烦

1994 年，网景公司（Netscape）在做一件事：给 Mosaic 之后的新浏览器做一个**购物车**。

问题很直接：

```
用户把商品 A 加进购物车  → 服务器记下"A"
用户把商品 B 加进购物车  → 服务器记下……什么？
```

**HTTP 是无状态的**。第二个请求到达时，服务器完全不知道"刚才那个把 A 加进来的人"和"现在这个"是同一个人。它只看到一个孤立的请求。

当时的程序员想了很多办法，都很别扭：

- **把状态藏在 URL 里**：`?session=abc123`。问题是 URL 会暴露、会被收藏、会串
- **隐藏表单字段**：每次请求都在表单里塞一个 `<input type="hidden">`。问题是只能用 POST，而且每个页面都要手动加
- **IP 地址识别**：完全不可靠。一个公司几百人共用一个出口 IP

## Lou Montulli 的发明

1994 年，网景的工程师 **Lou Montulli** 提出了 Cookie。

**他的思路**：既然服务器记不住，那就**让客户端帮忙记**。

具体做法：

1. 服务器在**响应**里加一个头：`Set-Cookie: cart=A`
2. 浏览器看到后，把 `cart=A` **存到硬盘上**
3. 以后这个浏览器访问**同一个域名**时，自动在**请求**里带上：`Cookie: cart=A`
4. 服务器读到 `Cookie`，就知道"哦，是那个购物车里有 A 的人"

**关键洞察**：状态存在**客户端**，每次请求自动带上。**服务器依然是无状态的**——它只是每次都被告知了状态。

这个设计非常聪明：**它保持了 HTTP 无状态的本质，同时实现了"有状态"的体验**。服务器代码不需要在内存里保存任何东西。

### 名字的来历

"Cookie" 来自编程术语 **magic cookie**——一小段在程序之间传递、接收方原样返回的数据。这个词本身源自"幸运饼干"（fortune cookie），里面有张写着字的小纸条。

Montulli 后来说过，他当时只是想找个好记的词。

### 一个惊人的细节

Cookie 规范从 1994 年到 2011 年，**没有正式的标准文档**。全世界的浏览器都是照着网景当年发的一份**非正式说明**实现的。

直到 2011 年，RFC 6265 才把它正式标准化——**中间隔了 17 年**。

## 工作原理：两个头

### Set-Cookie（服务器 → 浏览器）

```text
HTTP/1.1 200 OK
Set-Cookie: session_id=abc123; Path=/; HttpOnly
```

### Cookie（浏览器 → 服务器）

```text
GET /cart HTTP/1.1
Cookie: session_id=abc123
```

**注意这两个头的性质完全不同**：

- `Set-Cookie` 是**响应头**，可以出现**多次**（下多个 cookie）
- `Cookie` 是**请求头**，把该网站的所有 cookie 用 `; ` 拼成**一个长字符串**

## Cookie 的属性：这才是麻烦的开始

一个完整的 Set-Cookie 长这样：

```text
Set-Cookie: id=a3fWa; Expires=Thu, 31 Oct 2026 07:28:00 GMT; Path=/; Domain=.example.com; Secure; HttpOnly; SameSite=Lax
```

逐个拆开：

### Expires / Max-Age：能活多久

| | 说明 |
|---|---|
| **Expires** | 一个具体的过期时间点（GMT 格式） |
| **Max-Age** | 还能活多少**秒** |

**两者都设置时，`Max-Age` 优先。**

**都不设置 → 会话 Cookie（session cookie）**：浏览器关闭就消失。

**设置了未来时间 → 持久 Cookie**：存到硬盘上，关掉浏览器、重启电脑都还在，直到过期。

> **实际意义**：你在网站上勾"记住我"，就是服务器把 cookie 的 `Max-Age` 设成了 30 天。不勾就是会话 cookie。

### Domain 和 Path：发给哪些请求

```text
Domain=.example.com      ← shop.example.com 和 www.example.com 都能收到
Path=/admin              ← 只有 /admin 开头的路径才发送
```

**Domain 的规则最容易踩坑**：

- 不写 Domain → **只对当前域名发送**（最严格，也叫 host-only cookie）
- 写了 `.example.com` → 所有子域名都能收到

**注意**：**cookie 的 Domain 只能设为当前域名或其父域名**。服务器 `shop.example.com` **不能**设置 `Domain=google.com`——浏览器会直接拒绝。这是安全限制。

### Secure：只能走 HTTPS

```text
Secure          ← 只在 HTTPS 连接上发送
```

**没有 Secure 的 cookie 会在 HTTP 明文传输中被发出去**，等于在公共 WiFi 上广播你的登录凭证。

**今天的建议：所有 cookie 都应该带 Secure。**

### HttpOnly：JS 碰不到

```text
HttpOnly        ← document.cookie 读不到它
```

这是防 XSS 的关键：

```
没有 HttpOnly：页面里的恶意 JS 可以 document.cookie 偷走 session_id
有 HttpOnly：JS 读不到，只有浏览器发请求时自动带上
```

**注意**：HttpOnly 只挡 JS，**不挡你在浏览器 devtools 里看**。它防的是"别人的脚本"，不是"你自己的眼睛"。

### SameSite：防 CSRF

这是**2016 年才加入**的属性，也是最重要的安全属性之一。先看它防什么。

**CSRF（跨站请求伪造）**攻击场景：

1. 你登录了银行 `bank.com`，浏览器存着 session cookie
2. 你访问了恶意网站 `evil.com`
3. `evil.com` 的页面里有一行：`<img src="https://bank.com/transfer?to=attacker&amount=10000">`
4. 浏览器加载这个"图片"时，**会自动带上 bank.com 的 cookie**
5. 银行服务器看到请求带着有效的 session → **转账成功**

**你什么都没做，钱没了。**

`SameSite` 就是来治这个的。三个值：

| 值 | 行为 | 用途 |
|---|---|---|
| **Strict** | 跨站请求**完全不发** cookie | 最安全，但从外链点进来会"没登录" |
| **Lax** | 跨站的**顶层导航**（点链接）发，其他不发 | **现在的默认值**，平衡安全与体验 |
| **None** | 跨站都发（**必须配合 Secure**） | 需要跨站的场景（如嵌入式组件） |

**重点**：现代浏览器（Chrome 80+，2020 年）**默认把没声明 SameSite 的 cookie 当作 Lax**。这意味着**老网站的跨站 cookie 会突然失效**——2020 年很多网站因为这个"莫名其妙"坏掉。

## Cookie vs Session：常被混淆的两个词

这两个词经常被混着说，但它们**不是一个层面的东西**：

| | Cookie | Session |
|---|---|---|
| **是什么** | 一个**传输机制**（HTTP 头） | 一种**服务器端的存储** |
| **存在哪** | 客户端（浏览器） | 服务器端（内存/Redis/数据库） |
| **典型内容** | 一个 ID 字符串 | 完整的用户数据 |
| **关系** | Session **通常靠 Cookie 传递 ID** | 依赖 Cookie，但不是 Cookie 本身 |

典型流程：

```
1. 用户登录，提交用户名密码
2. 服务器验证通过，在 Redis 里存一份 {"user_id": 123, "role": "admin"}，id 是 sess_xyz
3. 服务器返回 Set-Cookie: session=sess_xyz
4. 浏览器存下 session=sess_xyz
5. 之后每次请求自动带 Cookie: session=sess_xyz
6. 服务器拿 sess_xyz 去 Redis 查，得到完整用户信息
```

**所以**：Cookie 里只放一个**钥匙**，真正的东西（Session）存在服务器。

### 为什么不放全部数据在 Cookie 里？

技术上可以（有人这么做，叫"JWT 存 cookie"），但有两个硬问题：

1. **大小限制**：单个 cookie **不能超过 4KB**，每个域名一般**最多 50 个 cookie**
2. **用户能改**：cookie 存在用户硬盘上，用户可以随便改。**你绝不能信任 cookie 里的"role=admin"**

## 第三方 Cookie 与隐私

上面说的都是**第一方 cookie**（你访问的网站给你下的）。

**第三方 cookie** 是：你访问 `news.com`，而页面里嵌了 `ad.com` 的广告图片，广告商给你下了一个 `ad.com` 的 cookie。

**这就是广告追踪的原理**：

```
你访问 news.com   → ad.com 记下"这个人看过新闻"
你访问 shop.com   → ad.com 记下"这个人看过商品 X"
你访问 blog.com   → ad.com 记下"这个人看过文章 Y"
```

`ad.com` 从没被你直接访问过，但它通过嵌在各家网站里的资源，**拼出了你的完整画像**。

这引发了持续二十年的隐私争议。结果就是：

- **Safari（2017）**：默认**完全阻止**第三方 cookie
- **Firefox（2019）**：默认阻止已知的追踪器
- **Chrome**：承诺 2020 年起逐步淘汰，实际推进被反复推迟

## 代码：requests 里的 Cookie

### 读取响应下发的 Cookie

```python
import requests

r = requests.get("https://httpbin.org/cookies/set?name=cool", timeout=10)

print(r.cookies)                          # ① RequestsCookieJar 对象
print(dict(r.cookies))                    # ② {'name': 'cool'}
print(r.cookies.get("name"))              # ③ 'cool'
```

> **逐行拆解**
>
> - **①** `r.cookies` 不是普通 dict，是 `RequestsCookieJar`。**但它支持大部分 dict 操作**
> - **②** 想当普通字典用，`dict()` 转一下
> - **③** `.get()` 拿不到返回 `None`，不抛异常

### 发送 Cookie

```python
import requests

# 方式一：用字典
r = requests.get(
    "https://httpbin.org/cookies",
    cookies={"session": "abc123"},         # ① 字典形式
    timeout=10,
)

# 方式二：手动设置头（不推荐）
r = requests.get(
    "https://httpbin.org/cookies",
    headers={"Cookie": "session=abc123"},  # ② 手动拼字符串
    timeout=10,
)
```

> **逐行拆解**
>
> - **①** 推荐。`requests` 会帮你正确编码
> - **②** 能用但麻烦。**如果值里有特殊字符（空格、`;`、中文），你得自己处理编码**。而且**如果发生了重定向，手动设置的 Cookie 头不会自动更新**，而 `cookies=` 参数会的

### 自动维持会话：Session 对象

**这才是真实项目里最常用的**：

```python
import requests

s = requests.Session()                    # ① 创建一个会话

r1 = s.get("https://httpbin.org/cookies/set?user=cool", timeout=10)
# 服务器下发了 cookie，Session 自动保存

r2 = s.get("https://httpbin.org/cookies", timeout=10)
print(r2.text)                            # ② 能看到刚才的 cookie 被自动带上了
```

> **逐行拆解**
>
> - **①** `Session` 对象**自带一个 cookie jar**，会**自动存储服务器下发的所有 cookie**
> - **②** 第二次请求**自动带上**了第一次拿到的 cookie。**你什么都不用做**

**对比一下不用 Session 的情况**：

```python
# ❌ 不用 Session：cookie 丢了
requests.get("https://httpbin.org/cookies/set?user=cool", timeout=10)
r = requests.get("https://httpbin.org/cookies", timeout=10)
print(r.text)        # {"cookies": {}} ← 空的！
```

**`requests.get()` 每次都是独立的**，cookie 不会跨请求保留。

> **这是新手第二常见的困惑**："我明明登录成功了，为什么下一个请求还是未登录？"答案就是你用了 `requests.get()` 而不是 `session.get()`

**完整的登录流程应该是这样**：

```python
import requests

s = requests.Session()                                  # ① 全程用这一个对象

r = s.post(                                             # ② 登录
    "https://example.com/login",
    json={"username": "cool", "password": "xxx"},
    timeout=10,
)
r.raise_for_status()                                    # ③ 确认登录成功

r = s.get("https://example.com/profile", timeout=10)    # ④ 带着 session 访问
print(r.json())                                         #    能拿到个人信息
```

> **逐行拆解**
>
> - **①** 一个 Session 贯穿全程。**不要混着用 `s.get()` 和 `requests.get()`**——后者的 cookie 不会存进 session
> - **②** 登录请求
> - **③** 老规矩：先看状态码
> - **④** 此时 cookie 已经自动带上了

## 翻车现场

### 翻车一：混用 Session 和 requests

```python
# ❌ 错误示范
s = requests.Session()
s.post("https://example.com/login", json={...})      # 登录，cookie 进了 session

requests.get("https://example.com/profile")          # ← 用的是模块级函数！
# 结果：401 未登录
```

**现象**：登录明明成功了，下一个请求还是 401。

**原因**：`requests.get()` 是**模块级函数**，它**每次创建一个全新的临时 Session**，用完就丢。它**不会**用你那个 `s` 里的 cookie。

**教训**：**一旦决定用 Session，全程只用 `s`。** 混用是这类 bug 的头号来源。

### 翻车二：把敏感信息放 Cookie 并信任它

```python
# ❌ 服务端错误设计
Set-Cookie: role=admin; user_id=123

# 攻击者改一下
Cookie: role=admin; user_id=1        ← 改成别人的 ID
```

**现象**：越权漏洞。用户能看别人的数据，甚至提权成管理员。

**原因**：**Cookie 存在用户的硬盘上，用户可以任意修改。** 你在里面写什么都没用，因为服务器收到的可能是伪造的。

**教训**：**Cookie 里只放一个不可猜测的随机 ID**，真实数据存服务器端。**永远不要相信 Cookie 里的业务数据。**

### 翻车三：忘了 Session 要关闭

```python
# ⚠️ 不完美
for user in users:
    s = requests.Session()              # 每次循环新建一个
    s.get(...)
    # 忘记 s.close()
```

**现象**：跑久了连接数暴涨，出现 `Too many open files`，或者服务器报"连接数过多"。

**原因**：Session 会**复用底层 TCP 连接**（第 26 课详细讲）。不关闭的话，连接池里的连接不会释放。

**教训**：**用 `with` 语句**，或者一个 Session 复用到底：

```python
with requests.Session() as s:           # ✅ 自动关闭
    for user in users:
        s.get(...)
```

## 为什么这对你写代码有用

1. **Cookie 让无状态的 HTTP 实现了"记住你"**，而服务器代码依然无状态。这个思路影响了后来所有的 Web 架构
2. **Session 对象是你处理登录态的默认选择**。`requests.get()` 是"一次性"的
3. **混用 `s.get()` 和 `requests.get()` 是 bug 之源**——这是这课最该记住的一条
4. **Cookie 是用户可控的，绝不能信任其中的业务数据**
5. **别忘了 `with` 或 `close()`**，否则长跑脚本会耗尽连接

## 小结

- **HTTP 无状态**，1994 年 Lou Montulli 发明 Cookie 解决"记住用户"，**思路是把状态存在客户端**
- **1994 到 2011 年没有正式标准**，只有网景的一份说明；RFC 6265 才标准化
- **两个头**：`Set-Cookie`（响应，可多次）、`Cookie`（请求，拼成一个串）
- **属性**：`Expires`/`Max-Age` 存活时间 · `Domain`/`Path` 作用范围 · `Secure` 仅 HTTPS · `HttpOnly` JS 不可读 · **`SameSite` 防 CSRF**
- **没设过期时间 = 会话 cookie**，关浏览器就没；设了 = 持久 cookie
- **Cookie 是传输机制，Session 是服务端存储**。Cookie 里放钥匙，数据存服务器
- **第三方 cookie 是广告追踪的基础**，主流浏览器已在逐步封杀
- **`requests.Session()` 自动管理 cookie**，跨请求自动带上
- ❌ **别混用 `s.get()` 和 `requests.get()`**；**别信任 cookie 里的业务数据**；**别忘 `close()`**
