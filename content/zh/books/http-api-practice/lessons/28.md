# 28 速率限制：为什么你的程序跑着跑着突然 403

> 脚本跑得好好的，突然全部请求开始返回 403。你检查 token，没问题；检查权限，也没问题。**这是被限流了**——这一课讲清服务器为什么要限流、怎么知道自己还剩多少配额、被限了之后该怎么等，以及**一个 90% 的人都会踩的时间戳陷阱**。

## 先分清两个"禁止"

被拒绝时，状态码决定了你该怎么做：

| 状态码 | 含义 | 该重试吗 |
|---|---|---|
| **401** | 没认证 / token 无效 | ❌ 重试没用，先修认证 |
| **403** | **认证成功，但你不被允许** | ⚠️ 看原因 |
| **429** | **请求太频繁** | ✅ 等一会儿再试 |
| **403 + 限流头** | **被限流了**（很多 API 用 403 表示限流） | ✅ 等 |

**关键陷阱**：**429 是"专门的限流状态码"，但很多 API 用 403 表示限流。** GitHub 就是后者。

所以你不能只看状态码，要**看响应头**：

```python
import requests

r = requests.get("https://api.github.com/rate_limit", timeout=10)
print(r.status_code)
print(r.headers.get("X-RateLimit-Remaining"))    # 剩余的配额
```

**判断规则**：看到 403 或 429，**先看有没有限流相关的头**，别急着去查权限。

## 为什么要限流

不是服务器"小气"，是三件很现实的事：

**一、防止单个用户拖垮服务。**

一个 API 服务同时服务几十万用户。如果某个用户写了个死循环每秒发 1000 个请求，**其他所有人的体验都会变差**。限流保证"每个用户最多用这么多"。

**二、防止滥用和爬虫。**

不限制的话，一个人可以在几分钟内把整个数据库搬走。

**三、成本。**

服务器的带宽、CPU 都要钱。**无限的免费配额是不存在的。**

## GitHub 的限流规则

用 GitHub 举例是因为它很典型，而且你马上就能试：

| 场景 | 配额 |
|---|---|
| **未认证**（不带 token） | **60 次/小时** |
| **已认证**（带 token） | **5000 次/小时** |

**60 次/小时**是什么概念？**平均每分钟 1 次。** 你手动点几下就超了。

这就是为什么**几乎所有教程都让你配 token**——不是为了"更安全"，单纯是为了**从 60 涨到 5000**。

### 看看自己的配额

```python
import requests
import os

token = os.environ.get("GITHUB_TOKEN", "")       # ① 从环境变量取
headers = {"Authorization": f"Bearer {token}"} if token else {}

r = requests.get("https://api.github.com/rate_limit", timeout=10, headers=headers)
data = r.json()

core = data["resources"]["core"]
print(f"上限    : {core['limit']}")               # 5000 或 60
print(f"剩余    : {core['remaining']}")
print(f"重置时间: {core['reset']}")
```

**典型输出**：

```
上限    : 5000
剩余    : 4987
重置时间: 1761091200
```

> **逐行拆解**
>
> - **① `os.environ.get(...)`**：**token 绝不写进代码**（第 22 课讲过）
> - **`core['reset']`** 是个 **10 位整数秒级时间戳**，比如 `1761091200`。**这是 UTC 时间**，下一节讲它有多坑

### 三个限流头

每次请求，响应头里都带着：

| 头 | 含义 |
|---|---|
| `X-RateLimit-Limit` | 总配额（5000） |
| `X-RateLimit-Remaining` | **还剩多少次** |
| `X-RateLimit-Reset` | **配额重置的时间戳** |

```python
r = requests.get("https://api.github.com/user", timeout=10, headers=headers)

print(r.headers.get("X-RateLimit-Limit"))        # 5000
print(r.headers.get("X-RateLimit-Remaining"))    # 4986
print(r.headers.get("X-RateLimit-Reset"))        # 1761091200
```

**这三个头在每一个响应里都有**，不需要额外请求。

## 90% 的人会踩的坑：reset 是 UTC 时间戳

`X-RateLimit-Reset: 1761091200` 这个数字怎么读？

**它是 UTC 时间的 Unix 时间戳**（从 1970-01-01 00:00:00 UTC 算起的秒数）。

### 错误做法：直接和本地时间比

```python
# ❌ 错误
import time
reset = int(r.headers["X-RateLimit-Reset"])
if reset > time.time():          # ① 看起来对，其实对吗？
    time.sleep(reset - time.time())
```

> - **① `time.time()` 返回的也是 Unix 时间戳**（UTC 基准），**所以这个比较其实是对的**——只要你别把它转成本地时间字符串又转回来

**真正的坑在"显示"和"计算等待秒数"这两件事上**：

```python
# ❌ 错误：当成"还要等多久"来 sleep
reset = int(r.headers["X-RateLimit-Reset"])
time.sleep(reset)          # 睡 1761091200 秒 ≈ 55 年！！！
```

**这个错误很蠢但真的会犯**：`reset` 是**绝对时间戳**（"什么时候重置"），不是**相对秒数**（"还要多久"）。

### 正确做法

```python
import time
from datetime import datetime, timezone

reset = int(r.headers["X-RateLimit-Reset"])

# ① 算出还要等多少秒
wait = reset - time.time()
print(f"还要等 {max(0, int(wait))} 秒")

# ② 转成可读时间（UTC）
print(datetime.fromtimestamp(reset, tz=timezone.utc))
# 2025-10-22 08:00:00+00:00

# ③ 转成本地时间（东八区）
from datetime import timedelta
local = datetime.fromtimestamp(reset, tz=timezone(timedelta(hours=8)))
print(local)
# 2025-10-22 16:00:00+08:00
```

> **逐行拆解**
>
> - **① `reset - time.time()`**：两者都是 UTC 基准的时间戳，**相减就是秒数**。`max(0, ...)` 防止已经过期算成负数
> - **② `datetime.fromtimestamp(reset, tz=timezone.utc)`**：**必须传 `tz`**。不传的话 Python 会用**你系统的本地时区**——结果会差 8 个小时，你会以为"还有 8 小时才重置"其实是"已经重置了"
> - **③ 东八区**：`timezone(timedelta(hours=8))`

**一句话记住**：**`X-RateLimit-Reset` 是"时刻"不是"时长"。**

## 主动检查：别等被拒绝才知道

**最好的限流处理是"不被限流"。**

```python
import requests
import time
import os

class RateLimiter:
    """主动检查 GitHub 配额，快用完就等"""

    def __init__(self, session, min_remaining=10):
        self.s = session
        self.min_remaining = min_remaining      # ① 低于这个数就等

    def check(self, response):
        """每次请求后调用，必要时等待"""
        remaining = response.headers.get("X-RateLimit-Remaining")
        if remaining is None:
            return                              # ② 没有这个头就不管

        remaining = int(remaining)
        if remaining >= self.min_remaining:
            return                              # ③ 还够，直接走

        reset = int(response.headers["X-RateLimit-Reset"])
        wait = reset - time.time() + 1          # ④ +1 秒保险
        if wait > 0:
            print(f"配额只剩 {remaining}，等待 {int(wait)} 秒")
            time.sleep(wait)
```

**用法**：

```python
with requests.Session() as s:
    s.headers.update({"Authorization": f"Bearer {os.environ['GITHUB_TOKEN']}"})
    limiter = RateLimiter(s)

    for i in range(200):
        r = s.get(f"https://api.github.com/repos/Cool-zimo/repo{i}", timeout=10)
        limiter.check(r)        # ① 每次请求后检查
        if r.status_code == 200:
            print(r.json()["full_name"])
```

> **逐行拆解**
>
> - **① `min_remaining=10`**：**留一点余量**。等到 0 才处理就晚了——因为可能还有并发的请求在跑
> - **② 没有限流头就跳过**：不是所有 API 都有
> - **④ `+1` 秒**：服务器重置可能有几秒延迟，多等 1 秒避免"刚醒过来又被拒"

## 被动应对：收到 429 时看 Retry-After

**不管你多小心，总会被限。** 这时正确的做法是**听服务器的话**。

服务器会在响应里告诉你等多久：

```
HTTP/1.1 429 Too Many Requests
Retry-After: 60
```

**`Retry-After` 是"还要等多少秒"**（这次是**相对值**，和 `X-RateLimit-Reset` 不同！）。

```python
import requests
import time

def fetch_with_retry(url, headers=None, max_wait=300):
    """被限流时按 Retry-After 等待后重试"""
    for attempt in range(5):
        r = requests.get(url, headers=headers, timeout=10)

        if r.status_code == 429:                          # ① 明确的限流
            wait = int(r.headers.get("Retry-After", 60))  # ② 服务器说等多久
            if wait > max_wait:
                print(f"要等 {wait} 秒，太久了，放弃")
                return None
            print(f"被限流，等 {wait} 秒")
            time.sleep(wait)
            continue                                      # ③ 重试

        if r.status_code == 403:                          # ④ 有些 API 用 403
            remaining = r.headers.get("X-RateLimit-Remaining")
            if remaining == "0":                          # ⑤ 确认是限流
                reset = int(r.headers["X-RateLimit-Reset"])
                wait = min(reset - time.time() + 1, max_wait)
                print(f"配额耗尽，等 {int(wait)} 秒")
                time.sleep(max(0, wait))
                continue
            # 不是限流，是真正的权限问题
            print("403 但不是限流，检查权限")
            return None

        r.raise_for_status()
        return r

    return None
```

> **逐行拆解**
>
> - **① `429`**：标准的"请求太频繁"
> - **② `Retry-After`**：**相对秒数**，直接 `time.sleep()` 就行。**注意和 `X-RateLimit-Reset`（绝对时间戳）的区别**
> - **③ `continue`**：回到循环开头重试
> - **④ `403`**：**关键**——不要一看到 403 就当权限问题
> - **⑤ `remaining == "0"`**：**这才是判断 403 是不是限流的依据**。配额还剩 500 却给你 403，那是真的没权限

**两个"等"的区别，这是本课最重要的对比：**

| 头 | 值类型 | 怎么用 |
|---|---|---|
| `Retry-After` | **相对秒数** | `time.sleep(wait)` |
| `X-RateLimit-Reset` | **绝对时间戳** | `time.sleep(reset - time.time())` |

## 自己实现发送速率控制

除了"配额用完才等"，更好的做法是**主动控制发送速度**，让自己的程序从头到尾匀速。

### 最简单的：固定间隔

```python
import time
import requests

def fetch_slowly(urls, delay=0.5):
    """每个请求之间固定间隔 delay 秒"""
    results = []
    with requests.Session() as s:
        for i, url in enumerate(urls):
            if i > 0:                    # ① 第一个不用等
                time.sleep(delay)
            r = s.get(url, timeout=10)
            results.append(r)
    return results
```

**优点**：简单，适用于"没有明确配额头的 API"
**缺点**：**慢**。5000 个请求 × 0.5 秒 = 42 分钟

### 更聪明：令牌桶

**思路**：想象一个桶，每秒往里放 N 个"令牌"。发请求要取一个令牌，**取不到就等**。

**好处**：既能限制平均速率，又允许短时间的突发（桶里攒了令牌就能连发几个）。

```python
import time
import threading

class TokenBucket:
    """令牌桶限流器"""

    def __init__(self, rate, capacity=None):
        """
        :param rate: 每秒放几个令牌（平均速率）
        :param capacity: 桶容量（允许的突发量），默认等于 rate
        """
        self.rate = rate
        self.capacity = capacity or rate
        self.tokens = self.capacity          # ① 初始是满的
        self.last = time.time()
        self.lock = threading.Lock()         # ② 多线程安全

    def _refill(self):
        """按经过的时间补充令牌"""
        now = time.time()
        elapsed = now - self.last            # ③ 距上次过了多久
        self.tokens = min(                   # ④ 补充但不能超过容量
            self.capacity,
            self.tokens + elapsed * self.rate
        )
        self.last = now

    def acquire(self, count=1):
        """取 count 个令牌，不够就阻塞等待"""
        with self.lock:                      # ⑤ 加锁
            self._refill()
            if self.tokens < count:
                # 算出要等多久
                deficit = count - self.tokens
                wait = deficit / self.rate
                time.sleep(wait)             # ⑥ 睡够
                self._refill()

            self.tokens -= count             # ⑦ 扣掉
```

**用法**：

```python
bucket = TokenBucket(rate=10)        # 每秒最多 10 个请求

for url in urls:
    bucket.acquire()                 # ① 取一个令牌（可能等待）
    requests.get(url, timeout=10)
```

> **逐行拆解**
>
> - **① 初始满桶**：所以**开头可以连发 capacity 个**（突发），之后才被限制到平均速率
> - **② `threading.Lock`**：多线程下 `_refill` 和 `acquire` 不能同时进行（第 26 课讲过共享可变状态的问题）
> - **③ `elapsed`**：这次和上次的时间差
> - **④ `min(capacity, ...)`**：**满了就不再攒**——否则你空闲一小时回来，桶里有 36000 个令牌，等于没限制
> - **⑥ `time.sleep(wait)`**：**注意这是阻塞的**。在异步程序里要用 `await asyncio.sleep()`（第 29 课）
> - **⑦ 扣减**

**为什么要 capacity 这个概念**：真实场景往往是"平时慢慢发，偶尔要连发几个"。桶容量让你能攒一点额度，需要时一次性用掉。

## GitHub 的次要限制（容易忽略）

除了 5000 次/小时，GitHub 还有**次要限制**，专门防止"短时间猛发"：

- **每分钟最多 100 个点**（不同操作消耗不同的点）
- **同一时间最多 100 个并发请求**
- **每秒最多 80 个内容写入**

**违反次要限制的表现**：**403 或 429，但 `X-RateLimit-Remaining` 还有几千。**

```python
# 遇到这种情况：配额明明还有，却被拒了
print(r.headers.get("X-RateLimit-Remaining"))    # 4986  ← 明明还有！
print(r.status_code)                             # 403
```

**这时的做法**：**不要重试，直接减速**。次要限制靠"慢下来"解决，不是靠"等一小时"。

```python
# 遇到"配额还有但被拒"，减速而不是等重置
if r.status_code in (403, 429) and int(r.headers.get("X-RateLimit-Remaining", 0)) > 100:
    print("次要限制，减速")
    time.sleep(5)          # 慢下来就行
```

## 翻车现场

### 翻车一：把限流的 403 当成权限问题

```python
# ❌ 错误判断
r = requests.get(url, headers=headers)
if r.status_code == 403:
    print("没有权限！")           # 可能根本不是权限问题
    return None
```

**现象**：程序"莫名其妙"认为全部资源都没权限，而你在网页上明明能访问。

**原因**：把限流的 403 和权限的 403 混为一谈。

**教训**：**403 时一定要看 `X-RateLimit-Remaining`**。是 0 就是限流，不是 0 才是权限。

### 翻车二：把 reset 当成"还要等多久"

```python
# ❌ 灾难
reset = int(r.headers["X-RateLimit-Reset"])
time.sleep(reset)          # 睡 55 年
```

**现象**：程序"卡住"，你以为网络问题，强行杀掉。

**原因**：`reset` 是绝对时间戳（约 17 亿秒），不是时长。

**教训**：**`time.sleep(reset - time.time())`**。而且要 `max(0, ...)`。

### 翻车三：用本地时区解析 reset

```python
# ❌ 错误
import datetime
reset = int(r.headers["X-RateLimit-Reset"])
print(datetime.datetime.fromtimestamp(reset))     # 用了系统本地时区
# 2025-10-22 16:00:00    ← 你以为是 UTC，其实是本地时间
```

**现象**：算出的等待时间差了 8 小时（在中国的话）。**可能表现为"等太久"或"醒来还是被限"**。

**注意**：`reset - time.time()` 这个**减法本身是对的**（两者都是 UTC 基准）。**错的是把它转成"可读时间"显示时没指定时区。**

**教训**：显示时**显式传 `tz=timezone.utc`**。

### 翻车四：并发请求无视限流

```python
# ❌ 50 个线程同时发，瞬间打满配额
from concurrent.futures import ThreadPoolExecutor

with ThreadPoolExecutor(max_workers=50) as ex:
    ex.map(lambda u: requests.get(u, headers=headers), urls)
```

**现象**：几秒钟就把 5000 次配额用完，然后全部请求开始 403。

**原因**：**限流是按"账号"算的，不是按"线程"算的**。50 个线程快，但配额只有一份。

**教训**：**并发要配合限流**。多个线程共享一个令牌桶（所以要加锁），或者干脆降低并发数。这是第 29 课的重点。

### 翻车五：不看 Retry-After 自己瞎等

```python
# ❌ 猜一个时间
if r.status_code == 429:
    time.sleep(1)          # 服务器明明说要等 60 秒
```

**现象**：重试还是 429，再重试还是 429……**最后被封得更久。**

**原因**：**服务器明确告诉你要等多久，你没听。**

**教训**：**永远优先用 `Retry-After`**。没有这个头时才用指数退避（第 24 课）。**有些服务器对"不听话的客户端"会加重惩罚。**

## 为什么这对你写代码有用

**一、限制不是障碍，是契约的一部分。**

配额、速率、并发上限，这些和 URL、参数一样是 API 契约的一部分。"能调通"不等于"能用对"。**一个不尊重限流的程序，不是"快"，是"很快就不能用了"。**

**二、服务器会告诉你怎么办，要学会读。**

`X-RateLimit-*`、`Retry-After` 这些头存在的意义就是**让客户端能自我调节**。不读它们而自己猜，是放弃了一个免费的正确信息来源。

**三、"时刻"和"时长"是两种东西。**

这是本课的隐藏主题。`X-RateLimit-Reset` 是时刻，`Retry-After` 是时长，**两者的处理方式完全不同**。在系统里到处都有这种区分：绝对时间 vs 相对时间、Unix 时间戳 vs 时间间隔。**拿到一个数字，先问它是"什么时候"还是"多久"。**

## 小结

- **401 / 403 / 429 的区别**：401 是没认证；403 可能是权限也可能是限流；**429 明确是限流**
- **判断 403 是不是限流**：看 `X-RateLimit-Remaining`，是 0 就是限流
- **GitHub 配额**：未认证 60/小时，认证 5000/小时
- **`X-RateLimit-Reset` 是绝对 UTC 时间戳**（"什么时候重置"），**`Retry-After` 是相对秒数**（"还要多久"）
- **等待的正确写法**：`time.sleep(max(0, reset - time.time() + 1))`，**不能直接 sleep(reset)**
- **显示时间戳要显式指定时区**：`datetime.fromtimestamp(reset, tz=timezone.utc)`
- **主动检查优于被动挨打**：每次请求后看 remaining，低于阈值就提前等
- **令牌桶**：`rate` 控平均速率，`capacity` 允许突发，多线程要加锁
- **GitHub 次要限制**：配额还有却被拒 → 是次要限制，**减速而不是等重置**
- **并发不减少配额消耗**：限流按账号算，50 个线程只是更快耗尽
- ❌ 别把限流 403 当权限问题；别直接 sleep(reset)；别忽略时区；别无视 Retry-After
