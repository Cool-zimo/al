# 09 内容协商与编码：为什么你拿到的是乱码

> 你一定遇到过：`r.text` 打印出来是一堆 `æ\x97\xa0` 这样的怪东西，或者中文全变成了问号。这一课从"客户端和服务器怎么商量用什么格式说话"讲起，一路讲到字符集、压缩、以及 `r.text` / `r.content` / `r.encoding` 三者的关系。学完你再也不会被乱码卡住。

## 内容协商：同一份资源，多种表示

先看一个场景。

同一个 URL `https://example.com/report`，服务器上有这份报告的三种版本：

- 中文的 PDF
- 英文的 HTML
- 英文的 JSON

**客户端要哪一个？** 你不能指望客户端猜，也不能给每个版本都发一个不同的 URL（那样就得维护三套地址）。

HTTP 的解决方案叫**内容协商（Content Negotiation）**：

> 客户端在请求头里声明"我能接受什么、我更喜欢什么"，服务器根据这些声明选一个最合适的版本返回。

这就是 `Accept` 系列头部存在的全部理由。

## Accept 系列：四个"我能接受"

### Accept：我要什么格式

```text
Accept: application/json
```

告诉服务器：我只要 JSON，别的我处理不了。

也可以给**多个选项和优先级**：

```text
Accept: application/json, text/html;q=0.9, */*;q=0.8
```

这里的 `q` 是**质量因子（quality factor）**，取值 0 到 1，默认 1。上面的意思是：

1. 优先给 JSON（q=1，省略了）
2. 没有 JSON 就给 HTML（q=0.9）
3. 都没有就随便给（`*/*`，q=0.8）

**q=0 表示"绝对不要"**：

```text
Accept: text/html, application/xml;q=0
```

意思是：要 HTML，**绝不要 XML**。

### Accept-Encoding：我支持什么压缩

```text
Accept-Encoding: gzip, deflate, br
```

三种常见压缩算法：

| 算法 | 来源 | 现状 |
|---|---|---|
| **gzip** | GNU zip，1992 | 最通用，到处都支持 |
| **deflate** | zlib | 支持但用得少 |
| **br** | Brotli，Google 2015 | 压缩率比 gzip 高约 20%，现代浏览器都支持 |

**这个头的实际价值巨大**：一个 500KB 的 JSON，gzip 后可能只有 50KB，传输量减少 90%。

`requests` **默认就会发** `Accept-Encoding: gzip, deflate`，并且**收到压缩响应后自动解压**——所以你从来不需要手动处理。

### Accept-Language：我要什么语言

```text
Accept-Language: zh-CN, zh;q=0.9, en;q=0.8
```

意思是：优先简体中文，其次中文，最后英文。

**浏览器会自动带上这个头**（根据你的系统语言设置）。所以同一个网站，中国人打开是中文，美国人打开是英文——**服务器就是靠这个头判断的**。

### Accept-Charset：我要什么字符集

```text
Accept-Charset: utf-8
```

**这个头基本上已经没人用了。** 原因很实际：今天 98% 以上的网页都是 UTF-8，再协商没意义。而且这个头还有个风险——如果客户端声明只接受一种字符集，而服务器只有另一种，服务器会返回 **406 Not Acceptable**，反而坏事。

现代浏览器**不再发送** `Accept-Charset`。这是个**被现实淘汰的头部**。

## 服务器的回应：Content-Type

服务器选好版本后，用 `Content-Type` 告诉客户端"我给你的是什么"：

```text
Content-Type: application/json; charset=utf-8
```

这一个头包含两部分：

```
application/json    ← MIME 类型：这是什么东西
charset=utf-8       ← 字符集：文字用什么编码
```

### MIME 类型

MIME（Multipurpose Internet Mail Extensions）**也来自邮件标准**——又是一个"邮件协议的东西被搬进 HTTP"的例子。

常见的：

| MIME | 含义 |
|---|---|
| `text/html` | HTML 网页 |
| `text/plain` | 纯文本 |
| `application/json` | JSON 数据 |
| `application/xml` | XML |
| `application/octet-stream` | 二进制流（下载文件时的兜底） |
| `image/png` / `image/jpeg` | 图片 |
| `application/pdf` | PDF |
| `multipart/form-data` | 表单（含文件上传） |
| `application/x-www-form-urlencoded` | 简单表单 |

### charset 才是乱码的根源

**划重点**：

> `application/json` 只告诉你"这是 JSON"，**不告诉你里面的中文用什么编码**。charset 才管这个。

**JSON 规范（RFC 8259）规定 JSON 必须是 UTF-8**，所以理论上 JSON 不需要 charset。但 HTML 没有这个规定，所以你会看到：

```text
Content-Type: text/html; charset=gbk      ← 老中文网站
Content-Type: text/html; charset=utf-8    ← 现在的主流
```

**GBK 是中文特有的编码**（还有 GB2312、GB18030）。如果一个页面是 GBK 编码的，而你的程序按 UTF-8 去解码，就会得到乱码。

## 乱码是怎么产生的

编码（encode）和解码（decode）必须**用同一套规则**：

```
你的文字  --encode-->  字节流  --decode-->  显示的文字
   "中"      UTF-8      E4 B8 AD    UTF-8      "中"
   "中"      GBK        D6 D0       GBK         "中"
   "中"      UTF-8      E4 B8 AD    GBK         "涓" ← 乱码
```

**乱码的本质：用错误的规则去解读字节流。**

注意一个关键点：**乱码不是数据坏了**。字节一个都没丢，只是你解读错了。只要换回正确的编码重新解读，内容就回来了。

```python
s = "中文"
b_utf8 = s.encode("utf-8")      # b'\xe4\xb8\xad\xe6\x96\x87'
b_gbk  = s.encode("gbk")        # b'\xd6\xd0\xce\xc4'

print(b_utf8.decode("gbk"))     # '涓枃' ← 用错规则，出现乱码
print(b_utf8.decode("utf-8"))   # '中文' ← 换回来就好了
```

## requests 的三个属性：content / text / encoding

这是本课最实用的部分。

```python
import requests

r = requests.get("https://example.com", timeout=10)

r.content      # ① bytes：原始字节，没做任何解读
r.text         # ② str：把 content 按某种编码解码后的文本
r.encoding     # ③ 解码时用的编码（可能是猜的！）
```

### r.content：原始字节

**永远是 `bytes` 类型**。它是服务器发来的原始数据，一个字节都没动过。

**什么时候用它**：

- 下载图片、PDF、压缩包（**二进制文件必须用 `.content`**）
- 出现乱码时，从这里重新解码

```python
# 下载图片：必须用 content
r = requests.get("https://example.com/photo.jpg", timeout=10)
with open("photo.jpg", "wb") as f:      # 注意是 "wb"，二进制写
    f.write(r.content)                   # 写字节，不是字符串
```

> **逐行拆解**
>
> - **`"wb"`**：`w` 是写，`b` 是二进制模式。**写字节必须带 `b`**，用 `"w"` 会报 `TypeError`
> - **`r.content`**：不能写 `r.text`。图片不是文本，用 `.text` 会经过一次解码，**图片数据会被破坏，文件打不开**

### r.text：解码后的字符串

`r.text` = `r.content.decode(r.encoding)`。

**问题在于 `r.encoding` 可能是猜的。**

### r.encoding：这个编码可能是错的

`requests` 决定 `r.encoding` 的规则是：

1. **看 HTTP 响应头的 `Content-Type` 里有没有 charset**。有就信它
2. **没有 charset，且 Content-Type 是 `text/*`** → 按 RFC 规定默认 **ISO-8859-1（Latin-1）**
3. **是 `application/json`** → 默认 **UTF-8**
4. **都没有** → 用 `apparent_encoding` 去猜

**坑在哪**：很多老旧的中文网站（GBK 编码）**在 HTTP 头里不写 charset**，而在 HTML 里用 `<meta charset="gbk">` 声明。

按上面的规则 2，`requests` 会用 ISO-8859-1 去解码 GBK 的字节 → **乱码**。

```python
r = requests.get("http://old-chinese-site.com", timeout=10)
print(r.encoding)              # 'ISO-8859-1' ← 猜错了
print(r.text[:20])             # 'ÖÐÎÄµÄÍøÕ¾' ← 乱码
```

### apparent_encoding：让它重新猜

`requests` 内置了一个"编码探测器"（基于 `chardet` / `charset_normalizer`），它会**分析字节内容**来猜测真实编码：

```python
r = requests.get("http://old-chinese-site.com", timeout=10)

print(r.encoding)               # 'ISO-8859-1' ← 头部说的（错的）
print(r.apparent_encoding)      # 'GB2312'      ← 分析内容猜的（对的）

r.encoding = r.apparent_encoding    # ① 手动纠正
print(r.text[:20])              # '中文的网站' ← 正常了
```

> **逐行拆解**
>
> - **`r.apparent_encoding`** 是一个**属性**，不是方法——**不要加括号**
> - **①** 这一行是修乱码的标准操作。**把 encoding 改成探测出来的值，然后重新访问 `r.text`**
> - **顺序很重要**：必须在访问 `r.text` **之前**改 `r.encoding`。因为 `r.text` 是**每次访问时现算的**——改了 encoding 之后再读 `r.text`，会用新编码重新解码

### 终极方案：直接操作 content

如果你觉得上面这些规则太绕，**有个永不失败的方案**：

```python
r = requests.get(url, timeout=10)

# 方案 A：我知道它就是 UTF-8
text = r.content.decode("utf-8")

# 方案 B：我允许极少数字符解不出来时容错
text = r.content.decode("utf-8", errors="replace")

# 方案 C：我不知道编码，让探测器猜
text = r.content.decode(r.apparent_encoding or "utf-8")
```

> **逐行拆解**
>
> - **A** 最干脆。**API 返回的 JSON 几乎一定是 UTF-8**，直接这么写最稳
> - **B** `errors="replace"` 表示遇到解不出来的字节时**用 `�` 替代**而不是抛异常。**默认是 `errors="strict"`，即抛 `UnicodeDecodeError`**
> - **C** `apparent_encoding` 偶尔会返回 `None`（内容太少猜不出来），所以加 `or "utf-8"` 兜底

## 压缩：requests 帮你做了，但要知道

```python
import requests

r = requests.get("https://api.github.com/user", timeout=10)

print(r.headers.get("Content-Encoding"))    # ① 可能是 'gzip'
print(len(r.content))                       # ② 解压后的长度
```

> **逐行拆解**
>
> - **①** `Content-Encoding: gzip` 表示服务器把正文用 gzip 压缩后发的
> - **②** **`r.content` 拿到的是解压之后的字节**。这是 `requests` 自动做的——它看到 `Content-Encoding: gzip` 就自动解压

**所以你永远不需要手动 gzip 解压。** 但要理解：**网络上传输的是压缩后的数据，你看到的 `len(r.content)` 是解压后的大小**。这两者可能差 10 倍。

一个相关但不同的头：

| 头 | 含义 | 是否自动处理 |
|---|---|---|
| `Content-Encoding` | 传输时压了一下（gzip） | ✅ requests 自动解压 |
| `Transfer-Encoding: chunked` | 分块传输（不知道总长度） | ✅ urllib3 自动处理 |
| `Content-Type` 里的 charset | 字符编码 | ❌ **要你自己保证正确** |

**charset 是唯一需要你操心的**，因为它可以被猜错，而压缩和分块都是机器对机器、不会错的。

## 翻车现场

### 翻车一：用 r.text 下载图片

```python
# ❌ 错误示范
r = requests.get("https://example.com/photo.jpg", timeout=10)
with open("photo.jpg", "w") as f:       # 用了 "w" 而不是 "wb"
    f.write(r.text)                      # 用了 .text 而不是 .content
```

**现象**：文件保存成功了，大小也差不多，但**双击打不开**，图片查看器说"文件已损坏"。

**原因**：`.text` 把二进制图片数据当文本解码了一次，某些字节序列在 UTF-8 里不合法，被替换成了 `U+FFFD` 之类的替代字符。**图片数据被永久破坏了。**

**教训**：**所有二进制文件（图片/视频/压缩包/PDF/Excel），一律用 `r.content` + `"wb"`。**

### 翻车二：JSON 响应却用 apparent_encoding

```python
# ❌ 没必要
r = requests.get("https://api.example.com/data", timeout=10)
r.encoding = r.apparent_encoding      # 多此一举，还有风险
data = r.json()
```

**现象**：大部分时候正常，偶尔出现解析失败。

**原因**：**JSON 规范规定必须是 UTF-8**。`apparent_encoding` 是按统计分析猜的，**对短内容会猜错**。你用一个可能猜错的值覆盖了一个确定正确的值。

**教训**：**API 返回的 JSON，直接用 `r.json()`，不要动 `r.encoding`。** `r.json()` 内部会正确处理 UTF-8。

### 翻车三：忘了 encoding 要在读 text 之前改

```python
# ❌ 错误示范
r = requests.get(url, timeout=10)
print(r.text)                         # 先读了（已经用错编码缓存了吗？）
r.encoding = "gbk"                    # 再改
print(r.text)                         # 期望变正常
```

**现象**：**实际上第二次会正常。** 因为 `r.text` 不是缓存的，是每次访问现算的。

**但这个写法很危险**——因为它依赖"text 不缓存"这个实现细节。**而且如果中间有其他代码读了 `r.text`，你就不知道读到的是哪一版了。**

**教训**：**拿到响应后，先定编码，再读内容。** 顺序固定下来，别依赖实现细节。

## 为什么这对你写代码有用

1. **乱码不是数据损坏**。字节都在，只是解码规则错了。知道这一点，你遇到乱码就不会慌
2. **`r.content` 是真相，`r.text` 是解读**。拿不准的时候从 `content` 手动 decode，永远可控
3. **API 返回的 JSON 永远用 `r.json()`**，不要手动处理编码
4. **二进制文件永远用 `r.content` + `"wb"`**
5. **只有"老中文网站"才需要 `apparent_encoding`**——那是 HTML 不声明 charset 的历史遗留问题
6. **压缩是自动的，你不用管**，但要知道 `len(r.content)` 是解压后的大小

## 小结

- **内容协商**：客户端用 `Accept` 系列声明偏好，服务器挑一个版本返回。`q=` 是优先级
- `Accept` 格式 · `Accept-Encoding` 压缩 · `Accept-Language` 语言 · **`Accept-Charset` 已被淘汰**
- **`Content-Type` = MIME 类型 + charset**。MIME 说"是什么"，charset 说"文字怎么编码"
- **乱码的本质是用错的编码解读字节**。数据没坏，换回对的编码就好
- `r.content` = 原始字节 · `r.text` = 按 `r.encoding` 解码的文本 · **`r.encoding` 可能是猜的**
- **修乱码标准操作**：`r.encoding = r.apparent_encoding`（**要在读 `.text` 之前**）
- **`apparent_encoding` 是属性，不加括号**，偶尔返回 None 要兜底
- **JSON 一定是 UTF-8，别用 apparent_encoding 覆盖它**
- **二进制文件用 `.content` + `"wb"`**；**压缩是自动解压的**
- `errors="replace"` 让解码失败时不抛异常而是用 `�` 替代
