# 15 超时与错误：让程序在出事时活下来

> 第 11 课我说过"每个请求都要带 timeout"。这一课把"超时之后会发生什么"讲完，并且把 `requests` 的整套异常体系铺开——哪些异常该重试、哪些该立刻失败、怎么捕获才不会漏。

## 超时之后会发生什么

```python
import requests

try:
    r = requests.get("https://httpbin.org/delay/20", timeout=3)
except requests.exceptions.Timeout:
    print("超时了")
```

`httpbin.org/delay/20` 会**故意延迟 20 秒**才响应。我们设了 3 秒超时，所以 3 秒后会抛出 `Timeout` 异常。

**注意**：**超时抛的是异常，不是返回 None**。如果你不捕获，程序会直接崩溃退出。

## requests 的异常体系

`requests` 的所有异常都继承自 `RequestException`。继承关系是：

```
RequestException                    ← 所有 requests 异常的祖先
├── Timeout                         ← 超时
│   ├── ConnectTimeout              ← 连接阶段超时（TCP 握手没完成）
│   └── ReadTimeout                 ← 连接上了，但读数据超时
├── ConnectionError                 ← 连接失败
│   ├── ProxyError                  ← 代理出问题
│   └── SSLError                    ← SSL/TLS 证书问题
├── HTTPError                       ← raise_for_status() 抛的（4xx/5xx）
├── TooManyRedirects                ← 重定向次数超限
├── URLRequired / MissingSchema     ← URL 不合法（比如忘了写 https://）
└── InvalidURL / InvalidHeader      ← URL 或头不合法
```

**这个继承树决定了捕获顺序**。

### 为什么顺序重要

```python
# ❌ 错误顺序
try:
    r = requests.get(url, timeout=10)
except requests.exceptions.RequestException:      # 父类在前！
    print("出错了")                                # 所有错误都进这里
except requests.exceptions.Timeout:               # 永远执行不到
    print("超时了")
```

**Python 的 `except` 是自上而下匹配，匹配到第一个就停。** 因为 `Timeout` 是 `RequestException` 的子类，父类在前面会**把所有子类都吃掉**，后面的分支永远不执行。

```python
# ✅ 正确顺序：子类在前，父类在后
try:
    r = requests.get(url, timeout=10)
except requests.exceptions.Timeout:
    print("超时")
except requests.exceptions.ConnectionError:
    print("连不上")
except requests.exceptions.RequestException as e:
    print(f"其他错误: {e}")
```

**口诀**：**具体的在前，通用的在后。**

## 各个异常该做什么

这是本课最有价值的部分——**不同异常的处理策略完全不同**：

| 异常 | 含义 | 该重试吗 | 该做什么 |
|---|---|---|---|
| `ConnectTimeout` | 连不上（3 秒内没建立 TCP） | ✅ 可以 | 等一会儿重试 |
| `ReadTimeout` | 连上了但服务器处理太慢 | ⚠️ 谨慎 | 可能服务器压力大，别猛重试 |
| `ConnectionError` | DNS 失败 / 拒绝连接 | ✅ 可以 | 检查网络，重试 |
| `SSLError` | 证书问题 | ❌ 不要 | **别忽略它**，可能是中间人攻击 |
| `HTTPError`（4xx） | 你的请求有问题 | ❌ 不要 | 改你的代码 |
| `HTTPError`（5xx） | 服务器出错 | ✅ 可以 | 退避后重试 |
| `TooManyRedirects` | 重定向循环 | ❌ 不要 | URL 有问题 |
| `MissingSchema` | URL 没写协议 | ❌ 不要 | 改代码，加 `https://` |

**核心判断**：

> **网络层的错（连不上、超时）可以重试；应用层的错（4xx）不要重试。**

## timeout 的两个阶段

第 11 课提过，这里展开：

```python
requests.get(url, timeout=(3.05, 27))
#                         ↑     ↑
#                      连接超时  读取超时
```

**两个阶段的区别**：

```
[连接阶段]  DNS → TCP握手 → TLS握手      ← 受 connect timeout 限制
[读取阶段]  发请求 → 等服务器处理 → 收响应  ← 受 read timeout 限制
```

### 什么时候需要分开

**场景**：你要调一个"有时候要算 30 秒"的 API，但网络本身很快。

```python
# 连接只要 3 秒够（网络好），但处理可能要 30 秒
requests.get(url, timeout=(3, 30))
```

如果只写 `timeout=30`，那么"服务器根本关了"这种情况你也要等 30 秒。**分开写，连不上 3 秒就知道**。

### 一个常见误解

> **读取超时不是"总共最多等 27 秒"，而是"两次收到数据之间最多等 27 秒"。**

这意味着：如果服务器每隔 20 秒给你发一点点数据（比如流式响应），**你可以永远等下去**。

**这不是 bug**，是设计允许流式传输。但如果你要严格限制总时长，得自己实现——第 24 课会用别的方式处理。

## 完整的错误处理模板

这是你后面会反复用到的骨架，**建议背下来**：

```python
import requests
import logging

def fetch(url, timeout=10):
    """发一个 GET 请求，处理各种可能出错的情况"""
    try:
        r = requests.get(url, timeout=timeout)

    except requests.exceptions.ConnectTimeout:
        # ① 连不上：可能是网络问题，也可能是对方挂了
        logging.warning(f"连接超时: {url}")
        return None

    except requests.exceptions.ReadTimeout:
        # ② 连上了但没响应：对方处理太慢
        logging.warning(f"读取超时: {url}")
        return None

    except requests.exceptions.SSLError as e:
        # ③ 证书问题：不要忽略！
        logging.error(f"SSL 错误: {url} -> {e}")
        return None

    except requests.exceptions.ConnectionError as e:
        # ④ 其他连接问题：DNS 失败、拒绝连接
        logging.warning(f"连接失败: {url} -> {e}")
        return None

    except requests.exceptions.TooManyRedirects:
        # ⑤ 重定向循环
        logging.error(f"重定向次数过多: {url}")
        return None

    except requests.exceptions.RequestException as e:
        # ⑥ 兜底：任何没想到的 requests 错误
        logging.error(f"请求异常: {url} -> {e}")
        return None

    # ⑦ 到这里说明请求成功发出并收到响应了
    try:
        r.raise_for_status()          # 4xx/5xx 在这里变成异常
    except requests.exceptions.HTTPError as e:
        logging.error(f"HTTP {r.status_code}: {url}")
        return None

    # ⑧ 全部通过
    return r
```

> **逐行拆解**
>
> - **①②③④⑤⑥** 六个 `except`，从具体到通用。**注意 `RequestException` 在最后兜底**
> - **`logging` 而不是 `print`**：生产代码用 `logging`。它可以分级别（warning/error）、可以写文件、可以随时关掉。`print` 做不到这些
> - **返回 `None` 而不是抛异常**：让调用方决定怎么办。调用方写 `if data is None: ...`
> - **⑦ `raise_for_status()` 单独放在后面**：因为它要等请求成功收到响应后才能判断。**放在 `try` 外面是因为它是另一个阶段的错误**
> - **⑧** 只有全部通过才返回响应对象

**使用方式**：

```python
r = fetch("https://api.github.com/user")
if r is None:
    print("失败了，跳过")
else:
    print(r.json())
```

## 日志：为什么不用 print

这是从"写脚本"到"写项目"的分水岭：

```python
# 脚本级
print("出错了")

# 项目级
import logging
logging.basicConfig(level=logging.INFO)
logging.warning("连接超时: %s", url)
```

**`logging` 的好处**：

1. **分级**：`debug` / `info` / `warning` / `error` / `critical`。上线后你可以只显示 error
2. **自动带时间和位置**：一行配置就能输出 `[2026-10-21 10:30:15] WARNING 连接超时`
3. **可以写文件**：`logging.basicConfig(filename="app.log")`
4. **不用改代码就能开关**：改一个 level 参数

**代价**：多了两行配置。对于超过 200 行的脚本，这个代价完全值得。

## TooManyRedirects：重定向循环

```python
# 默认最多跟随 30 次重定向
r = requests.get("https://httpbin.org/redirect/10", timeout=10)   # OK

# 超过 30 次
r = requests.get("https://httpbin.org/redirect/50", timeout=10)
# requests.exceptions.TooManyRedirects: Exceeded 30 redirects
```

**什么时候会遇到真实场景**：

- **Cookie 配置错误**：服务器因为你没带 cookie 就重定向到登录页，登录页又重定向回来 → **无限循环**
- **URL 规则写错**：A 重定向到 B，B 又重定向到 A

**可以自己设上限**：

```python
s = requests.Session()
s.max_redirects = 5          # 最多跟 5 次

r = s.get(url, timeout=10)
```

**为什么默认 30 次太多**：每次重定向都是一个完整的请求往返。30 次重定向意味着巨大的延迟。**生产环境建议设小一点**。

## SSLError：绝对不要忽略

```python
import requests

r = requests.get("https://self-signed.example.com", timeout=10)
# requests.exceptions.SSLError: certificate verify failed
```

**网上最常见的"解决方案"**：

```python
# ❌❌❌ 危险
r = requests.get(url, verify=False, timeout=10)
```

**这做了什么**：**关闭证书验证**。这意味着：

- 你不再确认对方是不是真的那个服务器
- **中间人攻击可以成功**：攻击者伪造一个证书，你照样连接
- `requests` 会打印一堆警告，但**还是会连**

**什么时候可以用 `verify=False`**：

- 本地开发时访问自签名证书的测试服务
- **而且你完全清楚风险**

**正确的做法**：如果是公司内网的自签名证书，把 CA 证书加进来：

```python
r = requests.get(url, verify="/path/to/company-ca.pem", timeout=10)
```

这样**依然在验证**，只是信任了你指定的 CA。

## 一个简单的重试（详细版在第 24 课）

```python
import requests
import time

def fetch_with_retry(url, tries=3, timeout=10):
    """失败时重试几次"""
    for i in range(tries):
        try:
            r = requests.get(url, timeout=timeout)
            r.raise_for_status()
            return r                            # ① 成功就返回
        except requests.exceptions.RequestException as e:
            if i == tries - 1:                  # ② 最后一次还失败
                raise                            #    抛出，不再试
            wait = 2 ** i                        # ③ 退避：1s, 2s, 4s
            print(f"第 {i+1} 次失败，等 {wait}s 重试: {e}")
            time.sleep(wait)
```

> **逐行拆解**
>
> - **①** 成功立即返回，不再循环
> - **②** **最后一次失败就抛出**，不要无声地返回 None。否则调用方以为成功了
> - **③** `2 ** i` 是**指数退避**：第一次等 1 秒，第二次 2 秒，第三次 4 秒。**给服务器恢复的时间，也避免你把自己的 IP 打进黑名单**
>
> **这个版本的局限**：它对**所有**异常都重试，包括 4xx。第 24 课会做正确处理（只对网络错误和 5xx 重试）。

## 翻车现场

### 翻车一：except 顺序写反

```python
# ❌ 错误
try:
    r = requests.get(url, timeout=10)
except Exception:                    # 最通用的在最前
    print("出错了")
except requests.exceptions.Timeout:  # 永远不执行
    print("超时")
```

**现象**：超时时打印"出错了"，你永远不知道是超时还是别的。

**原因**：`Exception` 是所有异常的父类，它吃掉了一切。

**教训**：**从具体到通用**。而且**不要用裸 `except Exception`**——它会连 `KeyboardInterrupt`（Ctrl+C）都吃掉。

### 翻车二：捕获了但什么都不做

```python
# ❌ 最糟糕的写法
try:
    r = requests.get(url, timeout=10)
    return r.json()
except:
    pass            # 静默吞掉所有错误
```

**现象**：程序"正常"运行，但什么都没干。你查一整天不知道为什么数据是空的。

**原因**：**`except: pass` 吞掉了一切错误信息**。

**教训**：**永远不要写空的 `except`**。至少要 `logging.error(...)`。如果真的想忽略某个特定错误，就**只捕获那一个**，并写注释说明为什么忽略。

### 翻车三：以为 retry 能解决一切

```python
# ❌ 对 400 也重试
for i in range(5):
    r = requests.post(url, json={"bad": "data"}, timeout=10)
    if r.ok:
        break
```

**现象**：请求参数写错了，重试 5 次，每次都 400，浪费 5 次请求额度和 5 秒。

**原因**：第 7 课讲过——**4xx 是"你的请求错了"，重发一万次还是错**。

**教训**：**只对网络错误和 5xx 重试**。第 24 课会给出正确实现。

## 为什么这对你写代码有用

1. **不捕获异常 = 程序崩溃**。网络请求失败是常态，不是意外
2. **`except` 从具体到通用**，父类在前会吃掉子类
3. **不同异常策略不同**：连不上可以重试，4xx 要改代码，SSL 错误别忽略
4. **`raise_for_status()` 放在收到响应之后**——它是另一个阶段的判断
5. **用 `logging` 不用 `print`**，这是脚本和项目的分水岭
6. **不要写 `except: pass`**，那是亲手销毁证据
7. **重试要退避**，而且只对可重试的错误重试

## 小结

- **超时抛异常，不返回 None**。不捕获就崩溃
- **异常继承树**：`RequestException` 是祖先，下面有 `Timeout`、`ConnectionError`、`HTTPError` 等
- **`except` 必须从具体到通用**，否则父类吃掉子类
- **`timeout=(3, 27)`** 分别设连接超时和读取超时
- **读取超时是"两次数据之间的间隔"**，不是总时长
- **`ConnectTimeout` / `ConnectionError` 可重试；`SSLError` / 4xx 不要重试**
- **`raise_for_status()` 把 4xx/5xx 变成 `HTTPError`**
- **`TooManyRedirects`** 通常是 cookie 或 URL 规则问题
- **`verify=False` 关闭证书验证，有安全风险**，只在本地开发用
- **用 `logging` 不用 `print`**；**绝不写 `except: pass`**
