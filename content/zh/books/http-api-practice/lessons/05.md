# 05 HTTP/2 与 HTTP/3：一个坑填了，脚下又塌了一个

> HTTP/2 用多路复用彻底解决了上一课留下的队头阻塞。上线后大家发现：确实快了，但一旦网络丢包，反而比 HTTP/1.1 更惨。原因不在 HTTP，在 TCP。于是有了 HTTP/3。

## 先回顾：1.1 到底卡在哪

上一课结尾说到，HTTP/1.1 有个绕不开的问题：**队头阻塞**。

在一条连接上，请求必须排队。前一个没回来，后面的就得等。

工程师们的解决办法是**多开连接**——浏览器对同一域名开 6 到 8 个 TCP 连接，把请求分摊开。

### 这个办法的代价

多开连接能绕开队头阻塞，但代价不小：

- **每个连接都要三次握手 + 慢启动**，8 个连接就是 8 次
- **HTTP 头部无法在连接之间共享**，每个连接都要重发一遍 `User-Agent`、`Cookie`、`Accept` 这些重复的字段
- **服务器要为 8 个连接各维护一套状态**，内存和 CPU 都翻倍

**更关键的是：6-8 个并发连接这个数字是个经验值，不是最优解。** 请求少了浪费，请求多了照样排队。

到了 2010 年代，情况变得更糟：

- **网页越来越重**。一个页面几百个资源很常见
- **移动网络普及**。手机的延迟和丢包率远高于有线网络，TCP 握手的代价被放大
- **HTTPS 普及**。在 TLS 之上再握手，往返次数更多

**所有变通手段的成本，终于超过了换协议的成本。**

## HTTP/2：2015 年，RFC 7540

HTTP/2 在 **2015 年 5 月** 发布（RFC 7540），基本上就是 Google SPDY 的标准化版本。

它做了一个非常聪明的取舍：

> **不改变 HTTP 的语义，只改变传输方式。**

什么意思？

- 方法还是 `GET` / `POST`
- 状态码还是 `200` / `404` / `500`
- 头部还是那些字段
- URL 还是那个 URL

**变的只是这些字节怎么被打包和传输。**

这个取舍极其重要：**上层应用几乎不用改代码**。你的 API 路径、参数、状态码逻辑，全部照旧。只有传输层换掉了。

### 核心改动一：二进制分帧

HTTP/1.1 是文本，一行一行的。HTTP/2 把所有东西切成**帧（frame）**。

```
HTTP/1.1:  GET /index.html HTTP/1.1\r\nHost: ...\r\n\r\n
              ↑ 纯文本，按字符解析

HTTP/2:    [HEADERS 帧][DATA 帧][DATA 帧]
              ↑ 二进制，按帧解析
```

每个帧有固定的结构：

```
+-----------------------------------------------+
| 长度 (24位)  | 类型 (8位) | 标志 (8位)         |
+-----------------------------------------------+
| 流标识符 (31位)                                |
+-----------------------------------------------+
| 帧载荷 (长度字段指定的字节数)                    |
+-----------------------------------------------+
```

常见的帧类型：

| 类型 | 作用 |
|---|---|
| `HEADERS` | 承载请求头或响应头 |
| `DATA` | 承载正文 |
| `SETTINGS` | 连接参数协商 |
| `RST_STREAM` | 取消一个流 |
| `PING` | 保活 / 测延迟 |

**为什么改成二进制？**

- **解析快**。读固定的字节偏移，不用扫描字符串找换行
- **没有歧义**。不会出现"换行符到底算不算内容"这类边界问题（这类歧义正是 HTTP/1.1 请求走私漏洞的根源）
- **更紧凑**

**代价**：人看不懂了。你没法再用 telnet 手工敲一个 HTTP/2 请求。

> **这是一个真实的取舍**：HTTP/2 牺牲了"可手工调试"，换取了性能和安全。今天要调试 HTTP/2，你得用专门的工具（比如 Wireshark，或者浏览器 DevTools 里的协议列）。

### 核心改动二：多路复用（Multiplexing）

**这是 HTTP/2 最重要的一条，也是它解决队头阻塞的方式。**

在 HTTP/1.1 里，一条连接上请求必须排队。

在 HTTP/2 里，**一条连接上可以同时跑很多个请求**，每个请求是一个独立的**流（stream）**，用帧头里的"流标识符"区分。

```
一条 TCP 连接
├── 流 1: 请求 index.html
├── 流 3: 请求 style.css
├── 流 5: 请求 app.js
└── 流 7: 请求 logo.png
```

这些流的帧**交错发送**：

```
[流1 HEADERS][流3 HEADERS][流1 DATA][流5 HEADERS][流3 DATA][流1 DATA]...
```

服务器收到后按流标识符重新组装。**哪个流先算完，哪个流的帧就先发回来——不需要排队。**

**队头阻塞，就这样解决了。**

对比一下：

| | HTTP/1.1 | HTTP/2 |
|---|---|---|
| 并发请求 | 靠开多条连接 | **一条连接上多个流** |
| 慢请求会堵别人 | 会 | **不会** |
| 需要的连接数 | 6-8 个 | **1 个** |
| 每个连接的握手开销 | 6-8 次 | **1 次** |

这就是为什么 HTTP/2 上线后性能提升明显：**握手少了，慢启动少了，队头阻塞没了。**

### 核心改动三：头部压缩（HPACK）

HTTP/1.1 的每个请求都带着一大堆重复的头部：

```
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) ...
Accept: text/html,application/xhtml+xml,...
Accept-Language: zh-CN,zh;q=0.9,...
Cookie: session=abc123; theme=dark; ...
```

`User-Agent` 那一行可能就 100 多个字节，**每个请求都原样重发一遍**。

一个页面几百个请求，光头部就浪费几十 KB。

HTTP/2 用 **HPACK** 压缩头部，原理是：

**1. 静态表**

协议内置了一张表，包含 61 个最常见的头部字段。发 `:method: GET` 时不用写字面量，直接发一个数字索引就行。

**2. 动态表**

连接两端各自维护一张表，记录本次连接中出现过的头部。第二次发同样的内容时，只发索引。

**3. 霍夫曼编码**

必须发字面量时（比如一个新的 Cookie 值），用霍夫曼编码压缩字符串。

**效果**：头部体积通常能压掉 **50%-90%**。对 `Cookie` 特别长的站点，效果更明显。

> **注意一个细节**：动态表是**在连接上维护的**。这意味着 HTTP/2 的头部压缩**依赖连接保持**——这也是它和存储转发式的中间设备容易冲突的原因之一。

### 核心改动四：服务器推送（Server Push）

HTTP/1.1 里，服务器只能被动响应。

HTTP/2 允许服务器**主动推送**：

```
客户端: 我要 index.html
服务器: 好，给你 index.html —— 顺便，我知道你还需要 style.css 和 app.js，一起给你
```

听起来很美好，能省掉一个"收到 HTML → 解析 → 再请求 CSS/JS"的往返。

**但实际上，服务器推送失败了。**

原因很实际：

- **服务器很难判断客户端缓存里有什么**。推了一个客户端已经缓存的资源，纯粹浪费带宽
- **实现复杂**，浏览器端的行为不一致
- **CDN 和缓存策略让这个判断更难**

结果：**主流浏览器陆续移除了对 Server Push 的支持**。Chrome 在 2022 年移除了它。

> **这是继 pipelining 之后，HTTP/2 里第二个"听起来很好但失败了"的设计。** 值得记住： speculative（推测式）的优化，在真实环境里经常因为"猜不准"而变成负优化。
>
> 替代方案是更早的、更笨但更可靠的做法：`Link: rel=preload` 响应头——服务器**提示**客户端去预加载，而不是直接推。

### 核心改动五：流优先级

每个流可以设优先级，告诉服务器"这个更重要"。

比如 HTML 最重要，CSS 次之，图片最后。服务器可以据此分配带宽。

**实际效果也有限**——因为优先级只是建议，服务器可以无视，而且中间的代理也可能不传递。

## HTTP/2 的问题：它把队头阻塞推到了下一层

HTTP/2 上线后，测速结果有个反直觉的现象：

**在网络好的时候，HTTP/2 明显更快。但在丢包率高的时候，HTTP/2 反而比 HTTP/1.1 更慢。**

为什么？

### 关键：TCP 层的队头阻塞

HTTP/2 解决的是**应用层**的队头阻塞——多个流之间不用排队了。

但所有这些流，**都跑在同一条 TCP 连接上**。

而 TCP 有一个铁律：**数据必须按序交付。**

TCP 保证：你发过去的字节流，对方收到的顺序必须和你发的一致。如果中间某个包丢了，TCP 必须等它重传回来，**后面的所有数据即使已经到了，也不能交给上层，必须等着**。

```
TCP 层：
  包1  包2  包3  包4  包5
        ↑ 丢了
        ↓
  包1  [等重传] 包3 包4 包5  ← 包3/4/5 已经到了，但不能交付
```

所以在 HTTP/2 里：

- 流 1、3、5、7 的帧**全部混在同一条 TCP 连接上**
- 一个 TCP 包丢了 → **所有流都要等这个包重传**
- 丢包率越高，等待越久

**HTTP/1.1 有 6-8 条连接，一个连接丢包，其他 5-7 条还能继续。**
**HTTP/2 只有 1 条连接，它一卡，全部卡住。**

这就是为什么高丢包环境下 HTTP/2 反而更慢——**它把所有的鸡蛋放进了同一个篮子**。

### 问题的根源：TCP 改不动

你可能会想：那就改 TCP 啊。

**改不动。**

原因有两个：

**1. TCP 在操作系统内核里。**

TCP 的实现在操作系统内核中。要改 TCP 的行为，需要**全世界的操作系统都升级内核**——服务器、客户端、路由器、防火墙。这个周期以十年计。

**2. 中间设备会"帮忙"。**

网络中间有大量设备（防火墙、NAT、负载均衡器）会检查甚至修改 TCP 包。它们对 TCP 的格式有硬编码的假设。**你改了 TCP 的格式，这些设备会认为是非法包，直接丢弃。**

这被称为**协议僵化（protocol ossification）**：一个协议用得越久、中间设备越多，就越改不动。

## HTTP/3：换个地基（2022）

既然 TCP 改不动，那就**不用 TCP**。

HTTP/3 的做法：底层换成 **QUIC**——一个**基于 UDP** 的传输协议。

**2022 年 6 月，RFC 9114** 发布，HTTP/3 正式标准化。

### 为什么用 UDP

UDP 是一个非常简单的协议：**只管把数据报发出去，不管顺序、不管可靠性、不管重传。**

它简单到几乎没有任何可改的东西，所以：

- **中间设备对 UDP 的假设最少**（它太简单了，没什么可假设的）
- **UDP 的实现在应用层**（不在内核深处），改起来容易

所以 QUIC 的思路是：

> **用 UDP 打底（这样能穿过所有中间设备），然后自己在 UDP 之上重新实现一套更好的可靠传输。**

**把传输层的功能从内核搬到了用户空间。** 这样想改就改，不用等操作系统升级。

### QUIC 解决了什么

**1. 彻底的队头阻塞隔离**

QUIC 自己实现了可靠性，而且是**按流**做的：

- 每个流有独立的序号和重传逻辑
- **流 3 丢包了，只有流 3 要等。流 1、5、7 完全不受影响。**

这才是真正的多路复用——**不仅在应用层，在传输层也隔离了。**

**2. 更快的连接建立**

TCP + TLS 的握手要多次往返（TCP 三次握手 + TLS 握手）。

QUIC **把传输握手和加密握手合并了**：

- 首次连接：**1 次往返**（1-RTT）就能建立安全连接
- 重连：**0-RTT**——客户端缓存过密钥的话，第一个包就能带上数据

对移动网络（延迟高）来说，这个提升非常明显。

**3. 连接迁移**

TCP 用一个四元组标识连接：**（源IP, 源端口, 目标IP, 目标端口）**。

你的手机从 WiFi 切到 4G，**IP 变了，连接就断了**，所有进行中的请求失败，要重新握手。

QUIC 用一个**连接 ID** 标识连接，和 IP 无关。

**IP 变了，连接 ID 不变，连接继续。** 手机切网络时正在进行的传输不会中断。

这个对移动端体验的提升是巨大的——你坐电梯、出地铁、切换 WiFi 时，请求不会突然失败。

**4. 强制加密**

QUIC **内置加密，无法关闭**。没有"明文 QUIC"这种东西。

这提升了隐私，但也带来一个副作用：**一些依赖明文检查的中间设备（比如某些企业防火墙）无法检查 QUIC 流量**，所以有些网络会直接屏蔽 UDP 443。

### HTTP/3 的结构

```
HTTP/3 = HTTP/2 的语义 + QUIC 传输
```

也就是说：

- 方法、状态码、头部语义——**和 HTTP/2 一样**
- 传输层——从 TCP+TLS 换成 QUIC

**你的应用代码不需要改。** 这也是为什么它被设计成这样——语义不变，只换传输。

### 现状

HTTP/3 的采用在快速增长，但不是 everywhere：

- 主流浏览器（Chrome、Firefox、Safari、Edge）都支持
- 大网站和 CDN（Google、Cloudflare、Facebook）已经启用
- **有些网络会屏蔽 UDP**，导致 HTTP/3 不可用

**所以实际部署的做法是：先尝试 HTTP/3，失败了自动降级到 HTTP/2。** 这个协商通过 HTTPS 的 `Alt-Svc` 响应头完成。

## 三个版本的传输层对比

| | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| 传输层 | TCP | TCP | **QUIC (UDP)** |
| 报文格式 | 文本 | **二进制帧** | 二进制帧 |
| 一条连接并发 | 1 个请求 | **多个流** | 多个流 |
| 应用层队头阻塞 | 有 | **无** | 无 |
| **传输层**队头阻塞 | **有** | **有** | **无** |
| 头部压缩 | 无 | **HPACK** | QPACK |
| 连接建立 | TCP握手+TLS | TCP握手+TLS | **1-RTT / 0-RTT** |
| 网络切换 | 断开 | 断开 | **连接迁移** |

**注意这张表最关键的一行：传输层队头阻塞。** HTTP/2 没解决它，HTTP/3 解决了。这就是为什么有了 HTTP/2 还要有 HTTP/3。

## 为什么这节课对你写代码有用

### 一、你几乎不用关心用的是哪个版本

这是最重要的结论之一。

**HTTP/2 和 HTTP/3 都刻意保持了语义不变。** 你的代码里写的是：

```python
r = requests.get("https://api.example.com/users")
```

**不管底层跑的是 1.1、2 还是 3，这行代码都一样。** 版本协商由客户端库和服务器自动完成。

（严格说：Python 的 `requests` 目前只支持 HTTP/1.1。要用到 HTTP/2 需要 `httpx` 之类的库。但**从你的代码角度看，API 是一样的**。）

### 二、队头阻塞解释了"为什么批量请求要并发"

你以后要发很多请求时，会发现**串行发很慢**。

原因就是队头阻塞：**一个慢请求会拖住后面所有请求。**

解决办法（第 29 课会讲）：用并发，让多个请求同时进行。

### 三、丢包环境下"更先进"不一定是更快

HTTP/2 在高丢包环境下比 1.1 慢——这个事实提醒你：

**性能测试要在真实条件下做。** 在你办公室的 WiFi 上测出来的结论，可能在用户的 4G 网络上完全相反。

### 四、连接迁移解释了移动端为什么容易失败

你的手机 App 请求失败，不一定是服务器的问题——**可能是 IP 变了，TCP 连接断了。**

这也是为什么移动端要有重试机制（第 24 课）。

### 五、"改不动"是真实存在的约束

TCP 改不动不是因为没人想改，而是因为**全世界的内核和中间设备**。

理解这一点，你以后面对"为什么这个老系统不改成更好的方案"时，会想到：**技术债有时候不是懒，是迁移成本真的高到不可能。**

## 小结

- HTTP/1.1 靠**多开 6-8 条连接**绕开队头阻塞，代价是多次握手、头部重复、服务器状态翻倍
- **HTTP/2（2015, RFC 7540）** = SPDY 的标准化。**不改变语义，只改变传输**
- 四个核心改动：**二进制分帧**、**多路复用（一条连接多个流，解决应用层队头阻塞）**、**HPACK 头部压缩**（静态表+动态表+霍夫曼，省 50%-90%）、服务器推送
- **服务器推送失败了**（浏览器已移除）——推测式优化常常因为"猜不准"变成负优化，替代方案是 `Link: rel=preload`
- **HTTP/2 没解决 TCP 层的队头阻塞**：所有流共用一条 TCP 连接，一个包丢了全都要等。**高丢包环境下 HTTP/2 反而比 1.1 慢**
- **TCP 改不动**：实现在内核里，且中间设备对 TCP 格式有硬编码假设（**协议僵化**）
- **HTTP/3（2022, RFC 9114）** 把底层换成 **QUIC（基于 UDP）**——UDP 太简单，中间设备没什么可假设的，于是把传输层功能搬到用户空间自己实现
- QUIC 的四个好处：**按流隔离丢包**（真正的无队头阻塞）、**1-RTT/0-RTT 建连**、**连接迁移**（切网络不断线）、强制加密
- **HTTP/3 = HTTP/2 的语义 + QUIC 传输**，应用代码不用改
- 实际部署：先试 HTTP/3，失败降级到 HTTP/2（通过 `Alt-Svc` 协商）

- 因为 HTTP/2 不支持并发
- 因为 HTTP/2 强制加密，加密计算拖慢了速度
answer: 1
explain: 这正是"应用层队头阻塞解决了，传输层没有"。HTTP/1.1 有 6-8 条连接，一条卡住其他还能走；HTTP/2 把所有流塞进一条 TCP 连接，TCP 按序交付的铁律意味着一个丢包卡住全部。这也是 HTTP/3 必须换掉 TCP 的根本原因
