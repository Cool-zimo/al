# 16 请求体与 Content-Type：把数据送出去

> 前面几课都在"取"东西（GET）。这一课开始讲"送"——POST、PUT、PATCH 怎么把数据放进请求里发出去。核心是两个参数 `data=` 和 `json=`，以及那个决定服务器能不能正确解析你的 `Content-Type` 头。

## 请求体是什么

回忆第 3 课的报文结构：

```text
POST /users HTTP/1.1          ← 请求行
Host: api.example.com         ← 头部
Content-Type: application/json
Content-Length: 27
                              ← 空行
{"name": "张三", "age": 30}    ← 请求体（body）
```

**请求体就是空行后面的那部分数据**。GET 通常没有请求体（有也不该有语义），POST/PUT/PATCH 靠它传数据。

### 为什么 GET 不该有请求体

技术上 `requests.get(url, json=...)` 能发出去，但：

1. **很多服务器直接忽略** GET 的请求体
2. **某些代理会丢掉它**
3. **语义上 GET 是"取"，带请求体是错的**

**要传数据给 GET，用查询参数（`params=`）**。

## Content-Type：告诉服务器"我发的是什么"

这是本课的核心。

> **`Content-Type` 请求头告诉服务器：请求体是什么格式，你该怎么解析它。**

服务器不知道你发了什么。它只看这个头：

```
Content-Type: application/json        → 按 JSON 解析
Content-Type: application/x-www-form-urlencoded  → 按表单解析
Content-Type: text/plain              → 当纯文本
Content-Type: multipart/form-data     → 按多部分表单解析（文件上传）
```

**如果头声明的格式和实际内容不一致，服务器就会解析失败**。这是本课要防的头号问题。

## requests 的两个参数：data= 和 json=

`requests` 提供了两种方式发送请求体。**它们的区别是新手最大的困惑点**。

### json=：发 JSON

```python
import requests

r = requests.post(
    "https://httpbin.org/post",
    json={"name": "张三", "age": 30},        # ① 传 Python 字典
    timeout=10,
)

print(r.request.headers["Content-Type"])     # ② application/json
print(r.request.body)                        # ③ 看实际发出去的
```

> **逐行拆解**
>
> - **①** 你给的是**Python 字典**，`requests` 会帮你：
>   1. 用 `json.dumps()` 转成 JSON 字符串
>   2. 编码成 UTF-8 字节
>   3. 自动设置 `Content-Type: application/json`
> - **②** 确认它自动加了正确的头
> - **③** `r.request.body` 是**发出去的字节**。你会看到 `b'{"name": "\xe5\xbc\xa0\xe4\xb8\x89", "age": 30}'`

**③ 有个重要细节**：中文被编码成了 `\xe5\xbc\xa0` 这样的字节，但**如果你打印它，可能看到的是 `{"name": "张三", ...}`**——因为 `requests` 内部把 body 存成了 str。这不重要，重要的是服务器收到的是 UTF-8 字节。

### data=：发原始内容

```python
import requests

# 传字典 → 变成表单格式
r = requests.post(
    "https://httpbin.org/post",
    data={"name": "张三", "age": 30},        # ① 同样传字典
    timeout=10,
)

print(r.request.headers["Content-Type"])
# application/x-www-form-urlencoded          ← ② 注意！和 json= 不一样
print(r.request.body)
# name=%E5%BC%A0%E4%B8%89&age=30             ← ③ 表单格式
```

> **逐行拆解**
>
> - **①** 同样是字典，但因为用了 `data=`，处理方式完全不同
> - **②** `data=` + 字典 → 自动设成 **表单类型**
> - **③** 字典被转成了 `name=xxx&age=30` 的形式，并做了 URL 编码（第 13 课讲过）

**这就是关键区别**：

| 参数 | 传字典时 | 自动的 Content-Type | 编码结果 |
|---|---|---|---|
| `json=` | 字典 | `application/json` | `{"name": "张三", "age": 30}` |
| `data=` | 字典 | `application/x-www-form-urlencoded` | `name=%E5%BC%A0%E4%B8%89&age=30` |

**同一个字典，两种完全不同的请求**。服务器只认其中一种。

### data= 传字符串：完全不做转换

```python
import requests

r = requests.post(
    "https://httpbin.org/post",
    data='{"name": "张三"}',                 # ① 传字符串
    timeout=10,
)

print(r.request.headers["Content-Type"])     # ② 没有 Content-Type！
```

> **逐行拆解**
>
> - **①** `data=` 收到字符串时，**原样发送，不做任何转换**
> - **②** **`requests` 不会自动加 Content-Type**。因为你没告诉它这是什么格式
>
> **这是个坑**：服务器收到一堆字节，不知道是 JSON 还是别的，可能解析失败。

**正确做法**：手动指定：

```python
r = requests.post(
    "https://httpbin.org/post",
    data='{"name": "张三"}',
    headers={"Content-Type": "application/json"},    # ① 手动声明
    timeout=10,
)
```

> **①** 内容和声明一致，服务器才能正确解析。

### data= 传字节：也不做转换

```python
r = requests.post(
    url,
    data=b"\x00\x01\x02",                    # 二进制数据
    headers={"Content-Type": "application/octet-stream"},
    timeout=10,
)
```

**什么时候用**：上传二进制内容（图片原始数据、protobuf 等）。

## 三种用法的选择指南

| 你要发什么 | 用什么 | 需要手动设 Content-Type 吗 |
|---|---|---|
| **JSON 数据**（最常见） | `json={...}` | ❌ 自动 |
| **表单数据**（模拟网页表单） | `data={...}` | ❌ 自动 |
| **纯文本** | `data="字符串"` | ✅ 要手动 |
| **二进制** | `data=b"..."` | ✅ 要手动 |
| **文件上传** | `files={...}` | ❌ 自动（第 25 课） |

**绝大多数 API 用 `json=`。** 表单主要出现在两种场景：
1. 老式网页表单
2. OAuth 的 token 接口（很多要求表单格式）

## 自己序列化 JSON 的陷阱

有人喜欢自己转 JSON：

```python
# ❌ 多余且有风险
import json
r = requests.post(url, data=json.dumps({"name": "张三"}), timeout=10)
# 忘了设 Content-Type → 服务器不知道这是 JSON
```

**为什么用 `json=` 更好**：

1. **自动设 Content-Type**
2. **自动处理中文**：`json.dumps()` 默认 `ensure_ascii=True`，会把中文转成 `\u5f20\u4e09` 转义序列。虽然合法但可读性差，而且**某些服务器处理不好**。用 `json=` 时 `requests` 内部也用 dumps，但行为一致可预期
3. **少写一行**

如果你**必须**自己 dumps（比如要控制格式），记得手动设头：

```python
import json

payload = json.dumps({"name": "张三"}, ensure_ascii=False).encode("utf-8")
r = requests.post(
    url,
    data=payload,
    headers={"Content-Type": "application/json; charset=utf-8"},    # ①
    timeout=10,
)
```

> **①** 注意加了 `charset=utf-8`。**JSON 规范规定必须是 UTF-8**，写上更明确。

## 看一个真实的对照实验

用 httpbin 把两种方式的结果都打出来，**这是理解它们区别的最好方法**：

```python
import requests
import json

payload = {"name": "张三", "tags": ["a", "b"]}

print("=== 用 json= ===")
r1 = requests.post("https://httpbin.org/post", json=payload, timeout=10)
d1 = r1.json()
print("Content-Type:", d1["headers"].get("Content-Type"))
print("服务器解析出的 json:", d1["json"])
print("服务器解析出的 form:", d1["form"])

print("\n=== 用 data= ===")
r2 = requests.post("https://httpbin.org/post", data=payload, timeout=10)
d2 = r2.json()
print("Content-Type:", d2["headers"].get("Content-Type"))
print("服务器解析出的 json:", d2["json"])
print("服务器解析出的 form:", d2["form"])
```

**你会看到**：

```
=== 用 json= ===
Content-Type: application/json
服务器解析出的 json: {'name': '张三', 'tags': ['a', 'b']}
服务器解析出的 form: {}          ← 表单是空的

=== 用 data= ===
Content-Type: application/x-www-form-urlencoded
服务器解析出的 json: None        ← JSON 是空的
服务器解析出的 form: {'name': '张三', 'tags': ['a', 'b']}
```

**这就是最直观的证明**：服务器根据 Content-Type 决定怎么解析，走的是**两条完全不同的路**。

> **逐行拆解**
>
> - **`d1["json"]` / `d1["form"]`**：httpbin 把两种解析结果都返回了。**这让你能亲眼看到服务器怎么处理**
> - **注意 `tags` 列表**：`data=` 时列表会变成 `tags=a&tags=b`（第 13 课讲过的重复键），服务器可能只取到一个

## PUT 和 PATCH 也一样

```python
import requests

# PUT：整体替换，用 json=
requests.put(url, json={"name": "new", "age": 30}, timeout=10)

# PATCH：部分修改，用 json=
requests.patch(url, json={"name": "new"}, timeout=10)
```

**`json=` 和 `data=` 在这两个方法上行为完全一致**。第 6 课讲过 PUT 和 PATCH 的语义区别，这里只是换了个方法名。

## 翻车现场

### 翻车一：json= 和 data= 混用

```python
# ❌ 错误
r = requests.post(
    url,
    json={"a": 1},
    data={"b": 2},          # 两个都传
    timeout=10,
)
```

**现象**：只发了一个，另一个丢了。而且不报错。

**原因**：**同时传 `json=` 和 `data=` 时，`json=` 优先，`data=` 被忽略**。

**教训**：**永远只传一个**。

### 翻车二：手动设了错误的 Content-Type

```python
# ❌ 错误
r = requests.post(
    url,
    json={"name": "张三"},
    headers={"Content-Type": "application/x-www-form-urlencoded"},   # 手动改了
    timeout=10,
)
```

**现象**：服务器报"无法解析请求体"或者拿到空数据。

**原因**：第 8 课讲过——**正文是 JSON，但声明自己是表单**。服务器按表单去解析 JSON 字符串，当然失败。

**教训**：**用了 `json=` 就别碰 Content-Type**。

### 翻车三：以为 data= 传字符串会自动识别

```python
# ❌ 错误
r = requests.post(url, data='{"name": "张三"}', timeout=10)
# 没有 Content-Type，服务器不知道这是 JSON
```

**现象**：有些服务器能猜（看内容像 JSON 就当 JSON 处理），有些直接拒绝。**时好时坏**。

**原因**：`data=` 传字符串时 requests 完全不帮你设头。

**教训**：**手动加 `Content-Type: application/json`**，或者直接用 `json=`。

### 翻车四：中文变成了 \uXXXX

```python
import json
print(json.dumps({"name": "张三"}))
# {"name": "\u5f20\u4e09"}     ← 中文被转义了
```

**现象**：你看到请求体里中文变成了 `\u5f20` 这种东西，以为乱码了。

**原因**：**这不是乱码，是 JSON 的合法转义**。JSON 允许用 `\uXXXX` 表示任意字符，解析后会还原成"张三"。

**要不要改**：通常不用。`\u` 转义是合法的 JSON，所有标准解析器都能还原。

**如果一定要发真实中文**（比如为了可读性、或对方解析器有 bug）：

```python
import json
s = json.dumps({"name": "张三"}, ensure_ascii=False)    # 关键参数
print(s)
# {"name": "张三"}
```

## 为什么这对你写代码有用

1. **`json=` 和 `data=` 对同一个字典会产生完全不同的请求**。选错就 400
2. **`json=` 自动设 Content-Type，`data=` 传字符串不会**——这是最容易出事的地方
3. **不要手动改 Content-Type**（配合 `json=` 时）
4. **不要同时传 `json=` 和 `data=`**，前者优先且不报错
5. **`\uXXXX` 不是乱码**，是合法的 JSON 转义
6. **用 httpbin 验证**：不确定发成什么样，就 POST 到 `httpbin.org/post` 看回显

## 小结

- **请求体**是空行后面的数据，POST/PUT/PATCH 靠它传内容；**GET 不该带请求体**
- **`Content-Type` 告诉服务器怎么解析请求体**。声明和实际不一致就解析失败
- **`json={dict}`** → 自动转 JSON 字符串 + 自动设 `application/json`
- **`data={dict}`** → 自动转表单 `k=v&k=v` + 自动设 `x-www-form-urlencoded`
- **`data="字符串"`** → **原样发送，不设 Content-Type**（要手动设！）
- **大多数 API 用 `json=`**；表单用于老式网页和 OAuth token 接口
- **别混用 `json=` 和 `data=`**（json 优先，不报错）；**用 `json=` 时别手动改 Content-Type**
- **`data=` 传字符串时不会自动加头**，必须手动设
- **`\uXXXX` 是合法 JSON 转义不是乱码**，要真实中文用 `ensure_ascii=False`
