# 23 OAuth：让第三方应用"受限地"访问你的账号

> 你一定点过"使用 GitHub 登录"。点完之后，那个网站能看到你的 GitHub 用户名和头像，但**不能**删你的仓库——它是怎么做到的？答案是 OAuth。这一课讲清它的完整流程，以及为什么它是三种认证方式里最复杂的。

## OAuth 要解决什么问题

### 场景

有一个第三方应用（比如一个在线代码编辑器）想读取你 GitHub 上的仓库列表。

**最糟糕的方案**：你把 GitHub 用户名和密码给它。

**后果**：

- 它有了你的**完整密码**
- 它能做**你能做的任何事**（删仓库、改设置、看私密数据）
- 你**没法只收回它的权限**，只能改密码（而改密码会影响所有其他应用）
- 它如果把密码存错了，泄露的是你的全部账号

**OAuth 的方案**：

> **不把密码给第三方。让 GitHub 亲自发给第三方一个"受限的凭证"。**

```
第三方 → GitHub: "这个用户想让我读他的仓库，可以吗？"
GitHub → 用户:   "该应用要读你的仓库，同意吗？"
用户 →   GitHub: "同意" （只在这一步输入密码，且只在 GitHub 的页面上）
GitHub → 第三方: "给你一个 token，只能读仓库，30 天有效"
```

**核心洞察**：

> **你的密码从头到尾没有离开 GitHub。** 第三方拿到的只是一个受限的、可撤销的 token。

## 三个角色

OAuth 有三个参与者，名字要记清：

| 角色 | 英文 | 例子 |
|---|---|---|
| **资源所有者** | Resource Owner | **你**（用户） |
| **客户端** | Client | 第三方应用（在线编辑器） |
| **授权服务器** | Authorization Server | GitHub 的认证服务 |

**还有一个**：**资源服务器**（Resource Server）——存数据的地方（GitHub API）。**它常常和授权服务器是同一个**，所以经常合并说。

## 授权码流程（最常用）

OAuth2 有好几种流程，**授权码模式（Authorization Code Flow）** 是最常用、最安全的一种。

### 完整流程图

```
① 客户端把用户重定向到 GitHub
   https://github.com/login/oauth/authorize
     ?client_id=xxx
     &redirect_uri=https://myapp.com/callback
     &scope=repo
     &state=random_string

② 用户在 GitHub 页面上登录并点"授权"
   （这一步在 GitHub，客户端完全看不到用户输入了什么）

③ GitHub 把用户重定向回客户端，带上一个"授权码"
   https://myapp.com/callback?code=abc123&state=random_string

④ 客户端【在服务器端】用授权码 + client_secret 换 token
   POST https://github.com/login/oauth/access_token
   （这个请求不经过浏览器，client_secret 不会暴露）

⑤ GitHub 返回 access_token
   {"access_token": "gho_xxxx", "scope": "repo"}

⑥ 客户端用 token 调 API
   GET https://api.github.com/user/repos
   Authorization: Bearer gho_xxxx
```

### 为什么要有第 ③④ 步（不能直接给 token？）

**这是个好问题**。为什么不直接在 ③ 就把 token 给客户端，非要绕一圈？

**原因**：

- **③ 是通过浏览器重定向传的**，URL 里的参数会出现在**浏览器历史、Referer 头、各种日志**里
- **`code`（授权码）是一次性的、几分钟就过期**，泄露了也用不了（因为换 token 还需要 `client_secret`）
- **`access_token` 是长期有效的**，泄露了就完蛋

**所以**：**把"长期凭证"的传递放在服务器到服务器的通道里（④）**，那里是加密的、不经过浏览器。

### 每一步的细节

#### ① 构造授权 URL

```python
import secrets
import urllib.parse

client_id = "your_client_id"
redirect_uri = "https://myapp.com/callback"
scope = "repo"

state = secrets.token_urlsafe(16)      # ① 随机 state，防 CSRF
# 把它存进 session / 数据库，第 ③ 步要验证

params = {
    "client_id": client_id,
    "redirect_uri": redirect_uri,
    "scope": scope,
    "state": state,
}
auth_url = "https://github.com/login/oauth/authorize?" + urllib.parse.urlencode(params)
print(auth_url)
# 把用户重定向到这个 URL
```

> **① `secrets.token_urlsafe(16)`** 生成一个随机的、URL 安全的字符串。
>
> **为什么需要 `state`**：**防 CSRF**。第 ③ 步 GitHub 会把 state 原样带回来，**你要验证它和你发出去的一致**。不一致说明这个回调可能是攻击者伪造的。
>
> **注意**：**不要用 `random` 模块**，用 `secrets`——后者是密码学安全的随机数。

#### ③ 处理回调

```python
# 假设这是你的回调处理函数（Flask 风格的伪代码）
def handle_callback(request):
    code = request.args.get("code")
    returned_state = request.args.get("state")

    # ① 验证 state（防 CSRF）
    if returned_state != saved_state:
        return "state 不匹配，可能是 CSRF 攻击", 403

    # ② 检查用户是否拒绝了授权
    if not code:
        return "用户拒绝了授权", 400

    # ③ 用 code 换 token（下一步）
    token = exchange_code_for_token(code)
```

#### ④ 用授权码换 token

```python
import requests

def exchange_code_for_token(code):
    r = requests.post(
        "https://github.com/login/oauth/access_token",
        data={                                   # ① 注意是 data= 不是 json=
            "client_id": CLIENT_ID,
            "client_secret": CLIENT_SECRET,       # ② 只在服务器端
            "code": code,
            "redirect_uri": REDIRECT_URI,
        },
        headers={"Accept": "application/json"},   # ③ 让 GitHub 返回 JSON
        timeout=10,
    )
    r.raise_for_status()
    return r.json()["access_token"]
```

> **逐行拆解**
>
> - **① `data=`**：第 17 课讲过——**OAuth2 规范（RFC 6749）要求表单格式**。用 `json=` 会被拒绝
> - **② `client_secret`**：**只能出现在服务器端**。这就是为什么第 ④ 步必须在后端做
> - **③ `Accept: application/json`**：GitHub 默认返回表单格式的字符串，加这个头让它返回 JSON
>
> **这是"发的是表单、要的是 JSON"的典型例子**——第 17 课的原话。

#### ⑥ 用 token 调 API

```python
import requests

def get_user_repos(access_token):
    r = requests.get(
        "https://api.github.com/user/repos",
        headers={
            "Authorization": f"Bearer {access_token}",
            "Accept": "application/vnd.github+json",
            "User-Agent": "MyApp/1.0",
        },
        timeout=10,
    )
    r.raise_for_status()
    return r.json()
```

**到第 ⑥ 步就和第 22 课一样了**——OAuth 的复杂之处在于**前面五步**，拿到 token 之后就是普通的 Bearer 认证。

## client_secret 为什么是"机密"

**这是 OAuth 安全的核心**：

```
client_id      = 公开的（就像你的用户名）
client_secret  = 机密的（就像你的密码）
```

**`client_secret` 的作用**：证明"这个请求确实是我这个应用发的，不是别人冒充的"。

**如果它泄露**：攻击者可以冒充你的应用。**所以**：

- **绝不能出现在前端 JS 里**（用户打开 F12 就能看到）
- **绝不能出现在移动端 App 里**（App 可以被反编译）
- **只能存在你的服务器上**

### 纯前端/移动端怎么办？PKCE

**问题**：如果你的应用是纯前端（SPA）或者手机 App，**没有服务器**，`client_secret` 放哪都不安全。

**解决**：**PKCE**（Proof Key for Code Exchange，读作 "pixy"）。

**原理**：不用固定的 secret，而是**每次授权动态生成一对值**：

```
1. 客户端生成一个随机字符串 code_verifier
2. 对它做 SHA256 哈希，得到 code_challenge
3. 第 ① 步请求时带上 code_challenge
4. 第 ④ 步换 token 时带上 code_verifier（原始值）
5. 服务器验证：hash(code_verifier) == code_challenge ?
```

**为什么这样安全**：即使攻击者截获了 `code`，他也没有 `code_verifier`，换不了 token。

```python
import secrets
import hashlib
import base64

# ① 生成随机 verifier
verifier = secrets.token_urlsafe(32)

# ② 计算 challenge = base64url(sha256(verifier))
digest = hashlib.sha256(verifier.encode("ascii")).digest()
challenge = base64.urlsafe_b64encode(digest).rstrip(b"=").decode("ascii")

print(f"verifier  = {verifier}")     # 第 ④ 步用
print(f"challenge = {challenge}")    # 第 ① 步用
```

> **逐行拆解**
>
> - **①** `secrets.token_urlsafe(32)` 生成密码学安全的随机串
> - **②** PKCE 规定用 **S256** 方法：SHA256 哈希 + base64url 编码 + **去掉末尾的 `=`**（`rstrip(b"=")`）
>
> **注意**：**PKCE 现在被推荐用于所有场景**，包括有服务器的 Web 应用。它是 OAuth 2.1 的强制要求。

## OAuth 的其他流程（简单了解）

| 流程 | 用途 | 你还用吗 |
|---|---|---|
| **授权码 + PKCE** | 有用户参与的标准场景 | ✅ **推荐** |
| 隐式（Implicit） | 老式纯前端 | ❌ **已废弃**，有安全问题 |
| 密码（Password） | 用户把密码直接给应用 | ❌ **已废弃**，违背 OAuth 初衷 |
| 客户端凭证（Client Credentials） | 服务器访问自己的资源，无用户 | ✅ 用于 M2M（机器对机器） |

**记住**：**隐式流程和密码流程都已被 OAuth 2.1 废弃**。看到老教程还在教它们，说明教程过时了。

## 你什么时候需要写 OAuth 代码

**说实话：大部分时候你不需要从零写。**

**选项一：用现成的库**

```bash
pip install authlib        # 或者 requests-oauthlib
```

```python
from authlib.integrations.requests_client import OAuth2Session

client = OAuth2Session(client_id, client_secret, scope="repo")
uri, state = client.create_authorization_url(
    "https://github.com/login/oauth/authorize")
# 重定向用户到 uri

# 回调里：
token = client.fetch_token(
    "https://github.com/login/oauth/access_token",
    code=request.args.get("code"),
)
```

**库帮你处理了**：state 生成校验、PKCE、token 刷新、错误分类。**用库**。

**选项二：直接用 PAT**（第 22 课）

**如果只是你自己用**（写个脚本管理自己的仓库），**根本不需要 OAuth**——去 GitHub 生成一个 Personal Access Token 就行了。

**OAuth 是给"别人的应用要访问别人的账号"用的**。你自己访问自己的账号，PAT 足够。

## 翻车现场

### 翻车一：把 client_secret 写在前端

```javascript
// ❌ 灾难（前端 JS）
const CLIENT_SECRET = "abc123";   // 用户 F12 就能看到
```

**后果**：任何人都能冒充你的应用，用户授权后的数据也会流到攻击者那里。

**教训**：**`client_secret` 只在服务器端**。纯前端用 PKCE。

### 翻车二：不验证 state

```python
# ❌ 危险
code = request.args.get("code")
token = exchange_code_for_token(code)      # 没验证 state
```

**后果**：**CSRF 攻击**。攻击者构造一个回调请求，用的是**他自己的授权码**，结果你的账号被绑定到了攻击者的 GitHub。

**教训**：**必须验证 state**。这是 OAuth 里最容易漏、后果最严重的一步。

### 翻车三：以为 OAuth 和"登录"是一回事

**常见误解**："用 GitHub 登录" = OAuth？

**准确说法**：

- **OAuth 解决的是"授权"**——让应用访问你的数据
- **登录（认证）是另一个问题** —— 确认"你是谁"

**OpenID Connect (OIDC)** 是建立在 OAuth2 之上的认证层，专门解决登录问题。它多返回一个 **id_token**（JWT），里面有用户身份信息。

**实践建议**：**如果你要做"用 X 登录"，用 OIDC 而不是裸 OAuth2**。

### 翻车四：token 不加密就存起来

```python
# ❌ 危险
with open("tokens.txt", "w") as f:
    f.write(access_token)      # 明文存盘
```

**后果**：服务器上任何能读这个文件的人/程序都能拿到用户的 token。

**教训**：**token 要加密存储**，或者用系统的密钥管理服务。至少**文件权限设成 600**。

## 为什么这对你写代码有用

1. **OAuth 的核心是"不把密码给第三方"**——理解这一点，其他都是细节
2. **授权码流程多绕一步（④）是为了让长期凭证不经过浏览器**
3. **`data=` 不是 `json=`**（OAuth2 规范要求表单）
4. **`state` 必须验证**，不验证会有 CSRF
5. **`client_secret` 只在服务器端**；纯前端用 PKCE
6. **大部分时候不需要自己写**——自己用就 PAT，做产品就用 authlib
7. **拿到 token 之后就是第 22 课的 Bearer 认证**

## 小结

- **OAuth 解决"第三方受限访问"**：你的密码从不离开授权服务器
- **三个角色**：资源所有者（你）· 客户端（第三方）· 授权服务器（GitHub）
- **授权码流程 6 步**：授权 URL → 用户同意 → 回调带 code → **后端换 token** → 拿到 token → 调 API
- **多绕第 ④ 步是为了让 access_token 不经过浏览器**
- **换 token 用 `data=`（表单）**，但 `Accept` 可以是 JSON
- **`state` 防 CSRF，必须验证**（用 `secrets` 生成）
- **`client_secret` 只能放服务器端，绝不进前端**
- **纯前端/移动端用 PKCE**（动态 verifier + challenge 代替固定 secret）
- **隐式流程和密码流程已废弃**
- **自己用就 PAT；做产品用 `authlib`**
- ❌ 别把 secret 写前端；别漏 state 校验；别明文存 token
