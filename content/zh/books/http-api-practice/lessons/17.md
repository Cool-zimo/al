# 17 表单 vs JSON：三种 enctype 的完整拆解

> 上一课讲了 `data=` 会生成表单格式。这一课把表单彻底讲透：它从哪来、有哪三种、为什么文件上传必须用它、以及那些"看起来像乱码"的 boundary 到底是什么。

## 表单从哪来：HTML 的 <form>

表单格式不是为 API 设计的，它来自 **1993 年的 HTML 表单**。

```html
<form action="/login" method="post">
  <input name="username" value="cool">
  <input name="password" type="password">
  <button type="submit">登录</button>
</form>
```

用户填完点提交，**浏览器负责把表单内容编码成请求体发出去**。编码方式由 `enctype` 属性决定：

```html
<form enctype="application/x-www-form-urlencoded">   <!-- 默认 -->
<form enctype="multipart/form-data">                  <!-- 上传文件时 -->
<form enctype="text/plain">                           <!-- 几乎没人用 -->
```

**关键点**：**这是浏览器的行为，不是 HTTP 的规定**。HTTP 只管传字节，`enctype` 是 HTML 层面的约定，被沿用到了 API 领域。

## 三种 enctype

### 一、application/x-www-form-urlencoded（默认）

**长什么样**：

```text
POST /login HTTP/1.1
Content-Type: application/x-www-form-urlencoded

username=cool&password=secret123
```

**规则**：`键=值`，用 `&` 连接，**和 URL 查询串完全一样的编码**（所以名字里有 `urlencoded`）。

**这就是 `data={dict}` 产生的格式**（上一课讲过）。

**优点**：简单、体积小
**缺点**：
- **只能表达扁平的键值对**，没有嵌套
- **所有值都是字符串**（没有数字、布尔、数组）
- **二进制数据要编码，体积膨胀约 33%**

### 二、multipart/form-data（文件上传专用）

**长什么样**：

```text
POST /upload HTTP/1.1
Content-Type: multipart/form-data; boundary=----WebKitFormBoundary7MA4YWxk

------WebKitFormBoundary7MA4YWxk
Content-Disposition: form-data; name="username"

cool
------WebKitFormBoundary7MA4YWxk
Content-Disposition: form-data; name="avatar"; filename="photo.jpg"
Content-Type: image/jpeg

（这里是图片的原始二进制字节）
------WebKitFormBoundary7MA4YWxk--
```

**规则**：

1. 用一串**分隔符（boundary）**把各个字段隔开
2. 每个字段有自己的小头部（`Content-Disposition`）
3. **二进制数据原样放**，不做任何编码

**boundary 是什么**：一串随机的字符，**必须保证不会出现在你的数据里**（否则会被误判为分隔符）。浏览器生成一长串随机字符串来降低碰撞概率。

**为什么需要它**：上传图片时，图片里有任意字节，包括 `&`、`=`、换行这些。**如果用 urlencoded，全都要转义，而且服务器要处理巨大的单行字符串**。multipart 直接分段，干净利落。

### 三、text/plain（几乎不用）

```text
username=cool
password=secret123
```

就是纯文本的 `键=值`，换行分隔。**不做 URL 编码**。

**为什么几乎没人用**：不编码意味着值里有 `&` 或换行就出问题；而且没有标准解析规则，各服务器实现不一致。

**它唯一的价值**：调试时肉眼可读。生产环境不要用。

## 对比：为什么 API 都用 JSON

| | urlencoded | multipart | **JSON** |
|---|---|---|---|
| 嵌套结构 | ❌ | ❌ | ✅ |
| 数组 | ⚠️ 靠重复键 | ❌ | ✅ |
| 类型（数字/布尔） | ❌ 全是字符串 | ❌ | ✅ |
| 二进制 | ⚠️ 膨胀 33% | ✅ 原样 | ❌ 需 base64 |
| 可读性 | 一般 | 差 | 好 |
| API 支持度 | 一般 | 少 | **绝大多数** |

**结论**：

- **普通 API 调用 → JSON**
- **有文件上传 → multipart**
- **urlencoded → 只在对方明确要求时（老表单、OAuth token）**

## requests 里怎么用 multipart

### 用 files= 触发

**关键机制**：**`requests` 只有在你传了 `files=` 时才使用 multipart**。

```python
import requests

r = requests.post(
    "https://httpbin.org/post",
    files={"avatar": ("photo.jpg", b"fake-image-bytes", "image/jpeg")},
    timeout=10,
)

print(r.request.headers["Content-Type"])
# multipart/form-data; boundary=...     ← ① 自动切成了 multipart
```

> **①** 只要你传了 `files=`，`requests` 就自动：
> - 把 Content-Type 改成 `multipart/form-data`
> - 生成一个随机 boundary
> - 按格式拼好请求体
>
> **你完全不用关心 boundary**。

### files= 的三种写法

```python
import requests

# 写法一：从磁盘读文件（最常用）
with open("photo.jpg", "rb") as f:
    r = requests.post(url, files={"avatar": f}, timeout=10)

# 写法二：指定文件名和内容类型（推荐）
with open("photo.jpg", "rb") as f:
    r = requests.post(
        url,
        files={"avatar": ("photo.jpg", f, "image/jpeg")},   # ① 元组
        timeout=10,
    )

# 写法三：内存中的字节（不用落盘）
r = requests.post(
    url,
    files={"avatar": ("photo.jpg", b"\x89PNG...", "image/png")},
    timeout=10,
)
```

> **逐行拆解**
>
> - **写法一** 最简单，但**服务器拿到的文件名是 `avatar`（字典的键）**，不是 `photo.jpg`。很多服务器需要真实文件名
> - **写法二 ①** 元组格式是 `(文件名, 文件对象或字节, MIME类型)`。**推荐这个**——文件名和类型都明确
> - **写法三** 适合"内容在内存里"（比如刚生成的图片、从别处下载的）

### 混合：表单字段 + 文件

```python
import requests

r = requests.post(
    url,
    data={"username": "cool", "description": "我的头像"},    # ① 普通字段
    files={"avatar": ("photo.jpg", b"...", "image/jpeg")},   # ② 文件
    timeout=10,
)
```

> **① ②** **`data=` 和 `files=` 可以同时用**。普通字段走 `data=`，文件走 `files=`。
>
> **注意**：这时候整体是 multipart 格式，**`data=` 里的字段也被编进了 multipart 的各个分段**，而不是 urlencoded。

**这就是为什么 `data=` 和 `files=` 不像 `json=` 和 `data=` 那样互斥**——它们分工不同。

## 实战：OAuth 的 token 接口要求表单

这是你**一定会遇到**的场景。

大多数 OAuth2 服务（GitHub、Google、微信……）换取 token 的接口**明确要求 `application/x-www-form-urlencoded`**，即使其他接口都用 JSON：

```python
import requests

r = requests.post(
    "https://github.com/login/oauth/access_token",
    data={                                   # ① 注意是 data= 不是 json=
        "client_id": "your_client_id",
        "client_secret": "your_secret",
        "code": "the_code_you_got",
    },
    headers={"Accept": "application/json"},   # ② 但要求响应是 JSON
    timeout=10,
)

token = r.json()["access_token"]
```

> **逐行拆解**
>
> - **①** **`data=` 而不是 `json=`**。这是 OAuth2 规范（RFC 6749）要求的。用 `json=` 会被拒绝
> - **②** `Accept` 是"我要什么响应"，**和 `Content-Type`（我发什么）是两回事**。这里发的是表单，要的是 JSON
>
> **这是本课最容易踩的坑**：请求用表单、响应用 JSON 是完全正常的组合。两个头各管各的。

## 对照实验：看服务器怎么解析

```python
import requests

# A: 纯 data=（urlencoded）
rA = requests.post("https://httpbin.org/post",
                   data={"user": "cool", "tag": ["a", "b"]}, timeout=10)
dA = rA.json()
print("A Content-Type:", dA["headers"]["Content-Type"])
print("A form:", dA["form"])
print("A json:", dA["json"])

# B: data= + files=（multipart）
rB = requests.post("https://httpbin.org/post",
                   data={"user": "cool"},
                   files={"f": ("a.txt", b"hello", "text/plain")}, timeout=10)
dB = rB.json()
print("B Content-Type:", dB["headers"]["Content-Type"])
print("B form:", dB["form"])
print("B files:", dB["files"])
```

**观察点**：

- **A 的 `tag` 列表**：变成 `tag=a&tag=b`，服务器解析成数组还是只取最后一个，**取决于服务器实现**。这是 urlencoded 表达数组的唯一办法，很脆弱
- **B 的 Content-Type**：带了 boundary
- **B 的 form 和 files 分开**：httpbin 把普通字段和文件分别展示

## 翻车现场

### 翻车一：文件上传用了 json=

```python
# ❌ 错误
r = requests.post(url, json={"avatar": open("photo.jpg", "rb")}, timeout=10)
# TypeError: Object of type BufferedReader is not JSON serializable
```

**现象**：直接报错。

**原因**：**JSON 不能表达二进制**。文件对象无法序列化。

**教训**：**有文件上传就用 `files=`**。如果 API 非要 JSON，就得把文件 base64 编码成字符串（体积 +33%，第 25 课讲）。

### 翻车二：用了 files= 还手动设 Content-Type

```python
# ❌ 错误
r = requests.post(
    url,
    files={"f": ("a.txt", b"x")},
    headers={"Content-Type": "multipart/form-data"},     # 手动设，但没 boundary
    timeout=10,
)
```

**现象**：服务器报"无法解析 multipart"或拿到空数据。

**原因**：**`multipart/form-data` 必须带 `boundary=xxx`**。你手动设的头里没有 boundary，服务器不知道怎么切分。

**教训**：**用 `files=` 时不要手动设 Content-Type**，让 requests 生成完整的值（包含 boundary）。

### 翻车三：OAuth 用了 json=

```python
# ❌ 错误
r = requests.post(token_url, json={"client_id": ..., "code": ...}, timeout=10)
# 400 Bad Request
```

**现象**：400，错误信息常常含糊不清（"invalid request"）。

**原因**：对方要求表单，你发了 JSON。

**教训**：**OAuth token 接口几乎都用 `data=`。** 不确定就看文档里的示例——如果示例是 `curl -d "a=b"`，那就是表单。

## 为什么这对你写代码有用

1. **表单来自 1993 年的 HTML**，不是 HTTP 的规定。它有三种 enctype
2. **urlencoded = 和查询串一样的编码**，只能表达扁平键值
3. **multipart 用 boundary 分段**，是唯一能原样传二进制的格式
4. **`files=` 才会触发 multipart**，而且要**让 requests 自己生成 boundary**
5. **`data=` + `files=` 可以同时用**——它们不互斥，分工不同
6. **OAuth token 接口通常用 `data=`**，即使响应是 JSON。**Content-Type 和 Accept 各管各的**

## 小结

- **表单来自 HTML `<form>`**，编码方式由 `enctype` 决定，被沿用到了 API
- **三种 enctype**：`x-www-form-urlencoded`（默认，扁平键值）· `multipart/form-data`（文件上传）· `text/plain`（几乎不用）
- **multipart 用 boundary 分段**，二进制原样传输，**必须带 boundary 参数**
- **API 普遍用 JSON**（支持嵌套、数组、类型）；**有文件上传用 multipart**
- **`files=` 才触发 multipart**，requests 自动生成 boundary——**别手动设 Content-Type**
- **`files=` 推荐元组写法** `(文件名, 内容, MIME类型)`
- **`data=` + `files=` 可以共存**，普通字段进 form，文件进 files
- **OAuth token 接口用 `data=`**（表单），**但 `Accept` 仍可以是 JSON**
- ❌ 别用 `json=` 传文件；别手动设不带 boundary 的 multipart 头
