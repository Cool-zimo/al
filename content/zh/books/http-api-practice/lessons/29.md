# 29 并发请求：把 100 个请求从 100 秒压到 5 秒

> 100 个请求，每个耗时 1 秒，串行要 100 秒。开 20 个并发，理论上 5 秒。**但直接把线程数拉到 200 不会更快，反而可能把 API 打挂、把你自己的账号封掉。** 这一课讲清并发为什么能加速、Python 的 GIL 会不会拖后腿、三种方案的取舍，以及**并发必须配限流**。

## 先看时间都花在哪了

```python
import requests
import time

urls = ["https://httpbin.org/delay/1"] * 20      # 每个请求服务器故意睡 1 秒

start = time.time()
for url in urls:
    requests.get(url, timeout=10)
print(f"串行: {time.time() - start:.1f} 秒")     # 约 20 秒
```

**这 20 秒里，你的 CPU 在干什么？**

**几乎什么都没干。**

```
发起请求 ──→ [等待 1 秒] ──→ 收到响应 ──→ 发起下一个 ──→ [等待 1 秒] ──→ ...
              ↑
         CPU 在这段时间里完全空闲
```

**网络等待是"空等"**——数据在网络上跑，你的程序只是挂在那儿。CPU 闲着，但你没让它去干别的。

**并发的本质就是：在等待的时候，去发下一个请求。**

```
线程1: 发起 ──→ [等] ──→ 收到
线程2:   发起 ──→ [等] ──→ 收到
线程3:     发起 ──→ [等] ──→ 收到
...
20 个请求的"等待时间"重叠在了一起
```

## GIL：Python 的并发"枷锁"，以及为什么这里不影响你

你可能听说过 **GIL（Global Interpreter Lock，全局解释器锁）**，说"Python 的多线程是假的"。

**这句话对一半。**

### GIL 是什么

CPython（你装的 Python）有一个全局锁，**同一时刻只有一个线程能执行 Python 字节码**。

**所以**：纯计算任务（比如算圆周率），开 10 个线程**不会有任何加速**——因为任何时刻只有一个在跑。

### 但 I/O 操作会释放 GIL

**关键**：当线程执行 **I/O 操作**（发网络请求、读文件）时，**它会主动释放 GIL**，让别的线程跑。

```
线程1: 发请求 → 进入等待 → 【释放 GIL】 → ... → 收到 → 【重新获取 GIL】→ 处理
                              ↓
线程2:              【拿到 GIL】→ 发请求 → 进入等待 → 【释放 GIL】
```

**所以**：**I/O 密集型任务（网络请求）能从多线程获得实实在在的加速。**

> **一句话**：GIL 阻碍的是"并行计算"，不阻碍"并行等待"。**HTTP 请求 99% 的时间在等待**，所以多线程对它是有效的。

## 方案一：ThreadPoolExecutor（最推荐入门）

标准库自带，不用装任何东西。

```python
import requests
from concurrent.futures import ThreadPoolExecutor
import time

urls = ["https://httpbin.org/delay/1"] * 20

def fetch(url):
    """每个线程执行这个函数"""
    r = requests.get(url, timeout=10)          # ① 在线程里发请求
    return r.status_code

start = time.time()
with ThreadPoolExecutor(max_workers=10) as ex:    # ② 10 个线程
    results = list(ex.map(fetch, urls))           # ③ 提交任务
print(f"并发: {time.time() - start:.1f} 秒")       # 约 2 秒
print(results)                                     # [200, 200, ...]
```

> **逐行拆解**
>
> - **① `fetch(url)`**：**一个普通函数**。它不知道自己在线程里——这是线程池最好用的地方
> - **② `max_workers=10`**：**同时最多 10 个线程**。这是关键参数，后面讲怎么定
> - **③ `ex.map(func, iterable)`**：把 `urls` 里每一项交给 `fetch`，**自动分配线程**。`map` 返回的结果**顺序和输入一致**
> - **`with`**：线程池会在退出时自动 `join`（等待所有线程完成）

**20 秒 → 2 秒，10 倍。**

### 什么时候要 as_completed 而不是 map

`map` 的问题是：**必须等全部完成才能拿到第一个结果**。如果你要**边完成边处理**（比如显示进度），用 `as_completed`：

```python
from concurrent.futures import ThreadPoolExecutor, as_completed

with ThreadPoolExecutor(max_workers=10) as ex:
    # ① 先全部提交，拿到 future 对象
    future_to_url = {ex.submit(fetch, url): url for url in urls}

    for i, future in enumerate(as_completed(future_to_url), 1):   # ② 谁先完成先拿谁
        url = future_to_url[future]
        try:
            result = future.result()          # ③ 取结果，异常在这里抛出
            print(f"[{i}/{len(urls)}] {url} → {result}")
        except Exception as e:
            print(f"[{i}/{len(urls)}] {url} 失败: {e}")
```

> **逐行拆解**
>
> - **① `ex.submit()`** 返回一个 **Future**（"未来会有的结果"）。用字典把 future 和 url 关联起来——**因为 as_completed 不保证顺序，你得自己记住谁是谁**
> - **② `as_completed(futures)`**：**谁先完成就先产出谁**。注意**结果顺序是乱的**
> - **③ `future.result()`**：**取结果。如果 `fetch` 里抛了异常，异常会在这一行重新抛出**
> - **`try/except` 包住 `result()`**：**必须**。否则一个请求失败会让整个循环崩掉，剩下的结果全丢了

### 顺序问题（很重要）

```python
# map: 结果顺序 == 输入顺序
results = list(ex.map(fetch, urls))       # 可靠

# as_completed: 结果顺序 == 完成顺序（乱的）
for f in as_completed(futures): ...       # 想要顺序就得自己对应
```

**如果你需要"第 3 个 URL 的结果"，用 `map`。** 如果你只是要"全部拿到"，用 `as_completed` 还能显示进度。

## 方案二：线程 + Session（注意线程安全）

第 26 课讲过：**Session 不是线程安全的**。所以在并发里要**每个线程一个 Session**。

### 用 threading.local()

```python
import requests
import threading
from concurrent.futures import ThreadPoolExecutor

# ① 线程局部变量：每个线程有自己的副本
_local = threading.local()

def get_session():
    """为当前线程返回专属的 Session"""
    if not hasattr(_local, "session"):     # ② 这个线程还没建过
        _local.session = requests.Session()
        _local.session.headers.update({"User-Agent": "MyApp/1.0"})
    return _local.session                  # ③ 返回本线程的那一个

def fetch(url):
    s = get_session()                      # ④ 拿到本线程的 Session
    return s.get(url, timeout=10).status_code

with ThreadPoolExecutor(max_workers=10) as ex:
    results = list(ex.map(fetch, urls))
```

> **逐行拆解**
>
> - **① `threading.local()`**：一个特殊的容器，**每个线程看到的是不同的内容**。线程 A 写入的东西，线程 B 看不到
> - **② `hasattr(_local, "session")`**：检查**当前线程**有没有建过 Session
> - **③ 复用**：同一个线程内的后续请求会复用这个 Session（连接复用生效！）
> - **④ 每个线程调 `fetch` 时拿到的是自己的 Session**

**好处**：既避免了线程安全问题，又**让同一个线程内的多次请求复用连接**。

**记得关闭**（线程池退出时）：

```python
# 简单场景可以不关（进程退出会回收）
# 长期运行的服务要关：
def close_all():
    if hasattr(_local, "session"):
        _local.session.close()
```

**实际上**：脚本跑完就退出的话，不关也没事（操作系统会回收）。**长期运行的服务必须关。**

## 方案三：asyncio + aiohttp（高并发首选）

**线程的代价**：每个线程要占约 8MB 内存（栈空间）。**开 1000 个线程 = 8GB。**

**异步（async）没有这个问题**——它在**一个线程内**切换任务，开销极小。

### 先理解 async/await

```python
import asyncio

async def fetch(url):          # ① async 定义协程
    print("开始", url)
    await asyncio.sleep(1)     # ② await：让出控制权，去做别的事
    print("完成", url)
    return url

async def main():
    # ③ 并发跑三个
    results = await asyncio.gather(
        fetch("a"), fetch("b"), fetch("c")
    )
    return results

asyncio.run(main())            # ④ 启动事件循环
```

**输出**（注意顺序）：

```
开始 a
开始 b
开始 c
完成 a      ← 几乎同时完成
完成 b
完成 c
```

> **逐行拆解**
>
> - **① `async def`**：定义的是**协程**（coroutine），不是普通函数。调用它不会立即执行
> - **② `await`**：**这是关键**。遇到 `await` 时，当前协程**暂停并让出控制权**，事件循环去跑别的协程。**等 await 的东西好了，再回来继续**
> - **③ `asyncio.gather()`**：**并发运行多个协程**，等全部完成
> - **④ `asyncio.run()`**：启动事件循环（Python 3.7+）

**如果不加 `await`**：

```python
# ❌ 这样是串行，不是并发
async def main():
    await fetch("a")      # 等 a 完成
    await fetch("b")      # 再等 b
    await fetch("c")
# 总共 3 秒
```

**`await` 一个协程 = 等它完成**。**要并发必须用 `gather` 或 `create_task`。**

### 用 aiohttp 发请求

**`requests` 是同步库，不能在 async 里用**（它会阻塞整个事件循环）。

需要 `aiohttp`：

```bash
pip install aiohttp
```

```python
import aiohttp
import asyncio
import time

async def fetch(session, url):
    async with session.get(url, timeout=10) as r:    # ① async with
        return r.status

async def main(urls):
    async with aiohttp.ClientSession() as session:   # ② 一个 Session 给所有协程用
        tasks = [fetch(session, url) for url in urls]    # ③ 建任务列表
        results = await asyncio.gather(*tasks)           # ④ 并发执行
        return results

urls = ["https://httpbin.org/delay/1"] * 100
start = time.time()
results = asyncio.run(main(urls))
print(f"100 个请求: {time.time() - start:.1f} 秒")     # 约 2-3 秒
```

> **逐行拆解**
>
> - **① `async with session.get(...)`**：aiohttp 的响应也要用 `async with` 关闭
> - **② `aiohttp.ClientSession()`**：**异步版的 Session**。注意——**aiohttp 的 Session 是设计为共享的**（和 requests 不同），一个 Session 给所有协程用是正确做法
> - **③ 列表推导建任务**：此时**还没执行**
> - **④ `asyncio.gather(*tasks)`**：`*` 把列表展开成多个参数。**这一行才真正开始并发执行**
> - **`asyncio.run()`**：整个程序只需要调一次

**100 个请求只要 2-3 秒，而且内存占用极小。**

### 限制并发数：信号量

**问题**：`gather` 会**同时发起全部 100 个请求**。这可能把服务器打挂，或者触发限流（第 28 课）。

**解决**：用**信号量（Semaphore）**限制"同时在飞的请求数"。

```python
import aiohttp
import asyncio

async def fetch(session, url, sem):
    async with sem:                          # ① 获取一个"许可"
        async with session.get(url, timeout=10) as r:
            return r.status
    # ② 离开 async with 时自动归还许可

async def main(urls, limit=10):
    sem = asyncio.Semaphore(limit)           # ③ 最多同时 10 个
    async with aiohttp.ClientSession() as session:
        tasks = [fetch(session, url, sem) for url in urls]
        return await asyncio.gather(*tasks)

results = asyncio.run(main(urls, limit=10))
```

> **逐行拆解**
>
> - **① `async with sem`**：**信号量是个计数器**。`async with` 进入时 -1，退出时 +1。**减到 0 时，后续协程会在这里挂起等待**
> - **② 自动归还**：`async with` 保证即使抛异常也会归还（和 `with` 一样）
> - **③ `Semaphore(limit)`**：**许可总数 = 最大并发数**

**这就是"并发 + 限流"的标准组合。** 100 个请求，最多同时 10 个在飞，跑完一个补一个。

## 并发数到底设多少

**不是越大越好。** 三个制约因素：

### 一、你自己的资源

| 方案 | 上限参考 |
|---|---|
| 线程 | **20~50**。再多，线程切换开销抵消收益，内存也涨 |
| 异步 | **可以几百**。但也要考虑对方服务器 |

### 二、对方的限制

**这是真正决定性的。** 第 28 课讲过 GitHub 的次要限制：**每分钟 100 个点、并发 100**。

**超过对方限制的后果**：403/429，甚至临时封禁。

### 三、礼貌

**你一个人把别人的服务打慢，其他人就遭殃。** 公共 API 通常建议 **5~10 并发**。

**经验值**：

```python
# 公共 API：保守
max_workers = 5

# 自己的服务 / 明确允许：可以大
max_workers = 20

# 不确定：从 5 开始，慢慢加，观察对方响应时间
```

## 三种方案怎么选

| | ThreadPoolExecutor | asyncio + aiohttp |
|---|---|---|
| **装东西** | 不用（标准库） | 要 `pip install aiohttp` |
| **代码改动** | **小**（普通函数） | **大**（全部要 async） |
| **并发上限** | 几十 | **几百到几千** |
| **内存** | 每线程 ~8MB | **极小** |
| **适合** | 脚本、几十个请求 | 服务、成百上千请求 |
| **Session** | 每线程一个 | 一个共享 |
| **生态** | requests 生态成熟 | 部分库不支持 async |

**建议**：
- **请求数 < 50**：用线程池，简单够用
- **请求数 > 100 或要写成服务**：用 asyncio
- **已有大量 requests 代码**：线程池，别重写

## 翻车现场

### 翻车一：多线程共享一个 Session

```python
# ❌ 危险
s = requests.Session()
def fetch(url):
    return s.get(url)          # 10 个线程用同一个 s

with ThreadPoolExecutor(max_workers=10) as ex:
    ex.map(fetch, urls)
```

**现象**：偶发的诡异错误——cookie 串了、连接异常、偶尔 `ConnectionError`。**而且复现不了**，有时跑十次才出一次。

**原因**：Session 内部状态（cookie jar、连接池）被并发读写。

**教训**：**用 `threading.local()` 给每个线程一个 Session**（第 26 课讲过）。

### 翻车二：并发数开太大

```python
# ❌ 贪心
with ThreadPoolExecutor(max_workers=500) as ex:
    ex.map(fetch, urls)
```

**现象**：前几秒很快，然后**大量 429/403**，甚至 IP 被封。

**原因**：瞬间几百个请求打过去，触发对方限流。

**后果**：**比慢还糟糕**——不仅这次失败，还可能被封一段时间。

**教训**：**并发必须配限流**。宁可慢一点也要稳。

### 翻车三：as_completed 里不捕获异常

```python
# ❌ 一个失败全崩
for future in as_completed(futures):
    result = future.result()      # ① 这里抛异常
    process(result)               #     后面的全不执行了
```

**现象**：100 个请求里第 5 个失败 → **程序崩溃，剩下 95 个的结果全丢**。

**原因**：`future.result()` 会把子线程里的异常重新抛出。

**教训**：**每个 `future.result()` 都要包 `try/except`**。

### 翻车四：在 async 里用 requests 或 time.sleep

```python
# ❌ 致命
async def fetch(session, url):
    time.sleep(1)                       # ① 阻塞整个事件循环！
    r = requests.get(url)               # ② 也是阻塞的！
    return r.status_code
```

**现象**：**完全没有并发效果**，甚至比串行还慢。而且整个事件循环卡住，所有协程都停了。

**原因**：`time.sleep()` 和 `requests.get()` 都是**同步阻塞**的。在 async 函数里调用它们，**会阻塞整个事件循环**——所有其他协程都没机会跑。

**教训**：
- `time.sleep(1)` → `await asyncio.sleep(1)`
- `requests.get()` → `aiohttp` 的 `session.get()`
- **规则：async 函数里不能有任何阻塞调用**

### 翻车五：以为线程越多越快

```python
# ❌ 以为 500 线程比 20 线程快 25 倍
```

**实际**：

| 线程数 | 耗时 |
|---|---|
| 1 | 20.0 秒 |
| 10 | 2.1 秒 |
| 20 | 1.5 秒 |
| 50 | 1.4 秒 |
| 200 | 1.6 秒 ← **反而变慢** |

**原因**：
1. **线程切换有开销**（上下文切换）
2. **对方服务器的吞吐上限**——它一秒只能处理这么多
3. **你自己的带宽上限**

**教训**：**并发有收益递减点**。超过之后只是增加开销和风险。

## 为什么这对你写代码有用

**一、先搞清楚"等待"和"计算"的比例。**

并发只对"等待型"任务有效。如果你的任务是 CPU 密集（图像处理、大量计算），多线程没用，要用多进程。**判断方法：看 CPU 占用率。** 请求发出去时 CPU 是 0% → 等待型，适合并发。

**二、能力越大，责任越大。**

并发让你从"打不死"变成"能打死对方"。**限流不是可选项，是并发的配套。** 一个不做限流的并发程序，本质上是攻击工具。

**三、选择合适的复杂度。**

线程池够用就不要上 asyncio。async 会让**所有调用链都变成 async**（"函数染色"问题）——一个 async 函数里不能调用普通阻塞函数，这个约束会传染到整个代码库。**引入复杂度之前先确认收益。**

## 小结

- **并发的价值**：网络等待是空等，让等待时间重叠
- **GIL 不阻碍 I/O 并发**：线程在 I/O 时释放 GIL，所以网络请求能从多线程受益
- **线程池**：`ThreadPoolExecutor(max_workers=)`，标准库，改动小
- **`map` 保序，`as_completed` 边完成边处理**
- **`future.result()` 会重抛异常，必须 try/except**
- **Session 线程不安全**：用 `threading.local()` 每线程一个
- **asyncio + aiohttp**：高并发首选，但代码要全部 async 化
- **async 里禁止阻塞调用**：`time.sleep` → `await asyncio.sleep`；`requests` → `aiohttp`
- **Semaphore 限并发**：`async with sem`，这是并发的必需品
- **并发数**：公共 API 5~10，自己的服务 20~50，**再多收益递减且危险**
- ❌ 别共享 Session；别开太大；别不捕获异常；别在 async 里用 requests；别以为越多越快
