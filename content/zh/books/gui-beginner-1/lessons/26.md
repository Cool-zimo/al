# 实战第一步：把"文本统计工具"想清楚再动手

> 前面 25 课都是零散知识点。从这一章开始，我们要用 5 节课的时间，做出一个真正能用的小工具：**文本统计工具**。它会统计一段文字的字数、行数、词频，还能把结果保存成文件。第一件事不是写代码，而是想清楚它到底要干什么。

## 我们要做什么

**一句话需求：用户粘贴一段文字，程序立刻算出它的字数、行数、词频，并能保存结果。**

听起来简单，但"想清楚"和"做出来的东西能用"之间，隔着一整个需求拆解的过程。很多人一上来就敲代码，写着写着发现功能越加越多、界面越改越乱，最后放弃——不是不会写，而是没想清楚要写什么。

**先不谈代码，用大白话列功能清单：**

| 编号 | 功能 | 说明 |
|---|---|---|
| F1 | 输入文字 | 一个大的多行输入框，能粘贴长文本 |
| F2 | 统计字数 | 算出总字符数（含空格、标点） |
| F3 | 统计行数 | 按换行符算一共有几行 |
| F4 | 统计词频 | 找出出现最多的几个词 |
| F5 | 显示结果 | 把统计数字清楚地展示出来 |
| F6 | 保存结果 | 把统计结果存成 txt 文件 |
| F7 | 清空输入 | 一键清空输入框，方便重新统计 |

**这 7 条就是我们的全部需求。** 每一条后面都对应着具体的代码实现，但它们彼此独立——这正是"可拆解"的意义。

## 为什么先做需求拆解

**需求拆解的本质是把"模糊的想法"翻译成"明确的任务清单"。**

举个例子。假设用户说："我想要一个统计文字的东西。"这句话里有至少三个歧义：

1. **"字数"到底算什么？** 含不含空格？含不含标点？中英文混排时"词"怎么算？
2. **"词频"怎么定义？** 中文没有空格分词，是按字算还是按词算？
3. **结果怎么展示？** 就几个数字，还是要排个排行榜？

**如果不先定下来，写代码的时候会反复返工。** 比如你先按"英文空格分词"写完了，用户说"我要统计中文"——整个词频模块都得重写。

**所以我们现在就定：**

- **字数**：`len(text)`，算所有字符，包括空格和标点。简单、无歧义。
- **行数**：按换行符 `\n` 切分，行数 = 切分后的片段数。空文本算 0 行。
- **词频（中文版）**：中文按"字"统计——每个汉字的出现次数。这是最简单的实现，先把工具做出来，后续可以升级为分词库。
- **结果展示**：用 Text 控件显示多行结果，比 Label 更合适（内容多、可滚动）。
- **保存**：用 `tkinter.filedialog` 弹出"另存为"对话框。

## 界面草图：先画，再写

**在敲第一行代码之前，先画出界面长什么样。** 这一步极其重要——它能让你提前发现布局问题。

```
+---------------------------------------------------+
|  文本统计工具                              [菜单]  |
+---------------------------------------------------+
|                                                   |
|  [请粘贴或输入文本到这里]                          |
|  +---------------------------------------------+  |
|  | 这是一段示例文本，                             |  |
|  | 用来演示文本统计工具的效果。                    |  |
|  | 可以粘贴任意长的内容。                          |  |
|  +---------------------------------------------+  |
|                                                   |
|  [开始统计]    [清空]    [保存结果]               |
|                                                   |
|  统计结果：                                       |
|  +---------------------------------------------+  |
|  | 总字符数：42                                  |  |
|  | 总行数：3                                     |  |
|  | 词频 Top 5：                                  |  |
|  |   文: 3 本: 2 示: 1 ...                       |  |
|  +---------------------------------------------+  |
+---------------------------------------------------+
```

**从草图能读出的布局信息：**

- 上方一个**多行文本框**（Text 控件）用于输入
- 中间一排**三个按钮**
- 下方一个**只读多行文本框**用于显示结果

这就是典型的"上中下"三段式布局。在 tkinter 里，用 Frame 把这三段包起来最清晰。

## 把功能拆成"函数清单"

**界面定下来了，接下来把功能清单翻译成函数名。** 这一步是"逻辑与界面分离"的起点（第 28 课会深入讲），现在先有个雏形：

```
# 界面相关
setup_input_area(root)        # 搭建输入区
setup_button_area(root)       # 搭建按钮区
setup_result_area(root)       # 搭建结果显示区

# 业务逻辑相关
count_chars(text) -> int      # 统计字符数
count_lines(text) -> int      # 统计行数
count_word_freq(text) -> dict # 统计词频，返回字典
format_result(stats) -> str   # 把统计结果格式化成字符串

# 交互相关
on_count()                    # 按钮"开始统计"的回调
on_clear()                    # 按钮"清空"的回调
on_save()                     # 按钮"保存结果"的回调
```

**看这 11 个函数，你会发现它们分三类：搭界面的、算数据的、处理交互的。** 混在一起写就会变成"意大利面条代码"，分开写就能各管各的。这就是后面几课要反复强调的核心思想。

## 优先级：MVP 先行

**别想着一次做完所有功能。** 我们分两步走：

**MVP（最小可用版本）— 先实现 F1、F2、F3、F5：**

- 能输入文字
- 能统计字数和行数
- 能显示结果

**V2（增强版本）— 再加 F4、F6、F7：**

- 加上词频统计
- 加上保存文件
- 加上清空按钮

**为什么这么分？** 因为 MVP 能跑起来，你就有正反馈，有动力继续做 V2。如果一上来就试图实现所有功能，很容易被某个难点卡住，然后整个项目烂尾。

## 翻车现场一：不做需求拆解，边写边改

**症状**：代码写了一半，发现"词频怎么定义"没想清楚，回去改数据结构，改完发现界面也得改，改完界面发现统计函数又废了——循环往复，最后删库跑路。

**原因**：没有提前确定"输入是什么、输出是什么、中间怎么算"。

**预防**：

1. **先写需求清单**（就是本节开头的那张表）
2. **先画界面草图**
3. **先写函数签名**（函数名 + 参数 + 返回值），不写实现
4. 确认无误后，再逐个填实现

**这叫"自上而下"的设计思路。** 你现在是初学者，可能觉得"想这么多浪费时间，直接写不就行了"。等你被返工折磨过一次，就会明白：想清楚 10 分钟，能省下 2 小时改代码。

## 翻车现场二：需求无边界，功能越加越多

**症状**：本来只想做个"统计字数"的小工具，结果加着加着，变成了"支持 Markdown 语法高亮、支持多种语言分词、支持导出 PDF"的巨无霸。

**原因**：没有给自己设边界。

**预防**：写需求清单时，给每条功能标上优先级：

| 优先级 | 含义 |
|---|---|
| P0 | 必须做，不做就没法用 |
| P1 | 应该做，锦上添花 |
| P2 | 可以不做，做了更好 |

**我们只做 P0 和 P1。** P2 全部砍掉——至少在这个课程项目里砍掉。做好了基础版，你有兴趣可以自己加 P2，那是练习，不是任务。

## 翻车现场三：把"能运行"当成"做完了"

**症状**：代码能跑，点了按钮能出数字，就觉得项目完成了。但用户一用就发现问题：空文本崩溃、中文乱码、大文件卡死。

**原因**：只验证了"正常路径"，没考虑"异常路径"。

**预防**：写完 MVP 后，主动测试以下场景：

- 输入为空，点统计
- 输入只有一个字符
- 输入 10000 行的大文本
- 输入带 emoji 或特殊符号的文本
- 保存时用户取消对话框

**第 30 课会专门讲这些"异常兜底"的处理。** 现在你只要记住：一个项目做完的标志不是"能跑"，而是"该崩的地方都兜住了"。

## 小结

- 做项目第一步不是写代码，而是**列需求清单**
- 需求清单要明确"算什么、怎么展示、怎么保存"
- 先画**界面草图**，再决定用什么控件、怎么布局
- 把功能拆成**函数清单**，分界面、业务、交互三类
- **MVP 先行**：先做出最小可用版本，再加增强功能
- 给功能标**优先级**，砍掉 P2，控制边界
- 做完后要测**异常路径**，不只是正常路径
