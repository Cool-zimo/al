# 异常处理巩固

> 这一课不重新讲概念。它做三件事：**用三十秒回顾要点、纠正最容易犯的三个错、用题目检验你是不是真的会了**。
> 如果你发现回顾部分有任何一句看着陌生，先回去看《学习篇》第 21 课，再回来做题。

## 三十秒速览

```python
try:
    x = int(input("请输入数字："))   # 可能抛 ValueError
    y = 10 / x                      # 可能抛 ZeroDivisionError
except ValueError:
    print("输入的不是数字")
except ZeroDivisionError:
    print("不能除以零")
else:
    print("计算结果是", y)          # 没抛异常才执行
finally:
    print("不管怎样我都会执行")     # 始终执行
```

| 子句 | 何时执行 | 常见用途 |
|---|---|---|
| `try` | 放可能出错的代码 | 包裹"不确定能否成功"的操作 |
| `except E:` | `try` 里抛了异常 `E` | 给出替代方案或提示 |
| `else:` | `try` 里**没有**抛异常 | 放"成功才做"的逻辑 |
| `finally:` | 无论如何 | 释放资源、收尾 |

`raise` 用来主动抛异常，`raise` 单独一行会**把当前异常原样重新抛出**。

## 最容易错的三件事

### 一、裸 `except:` 把键盘中断都吞掉了

```python
# WRONG
try:
    do_something()
except:                     # 等价于 except BaseException:
    print("出错了")
```

裸 `except:` 捕获的是 `BaseException`，**包括 `KeyboardInterrupt`（Ctrl+C）和 `SystemExit`**。结果就是用户按 Ctrl+C 想中断程序，程序却假装什么都没发生继续跑——这在命令行工具里是灾难。

更要命的是它会掩盖真正的 bug：

```python
try:
    result = 100 / n
except:
    result = None            # n 是 None、是字符串、是零……全都是一个提示
```

```python
# RIGHT
try:
    result = 100 / n
except ZeroDivisionError:
    print("除数不能为零，请检查输入")
    result = None
```

**只捕获你知道怎么处理的异常**。不知道怎么处理，就别捕获，让异常往上冒泡，调用栈会告诉你真正的问题在哪。

### 二、`except` 的顺序：子类必须写在前面

```python
# WRONG
try:
    x = int(input())
    y = 10 / x
except Exception:
    print("一般错误")
except ZeroDivisionError:    # 永远命中不了
    print("除以零")
```

`Exception` 是 `ZeroDivisionError` 的父类。`except Exception` 写在前面，会先把所有异常一口吞掉，下面那个分支就成了死代码。

```python
# RIGHT：越具体越靠前
try:
    x = int(input())
    y = 10 / x
except ValueError:
    print("请输入合法的数字")
except ZeroDivisionError:
    print("不能除以零")
except Exception as e:
    print(f"其他错误：{e}")
```

**判断口诀：先子后父，先具体后宽泛。** 这个顺序写反，是代码审查里最容易被抓出来的错误之一。

### 三、`else` 和 `finally` 的职责被混为一谈

```python
# WRONG：把"成功才做"的事塞进 try
try:
    data = load_data()
    print(f"加载了 {len(data)} 条")   # 这句其实不会抛异常，却待在 try 里
    save_result(process(data))
except IOError:
    print("读取失败")
```

`try` 块应该**尽量短**，只包裹那一行真正会出错的代码。否则一旦 `print` 或 `save_result` 抛错，会被错误地归到"读取失败"里。

```python
# RIGHT：try 只管加载
try:
    data = load_data()
except IOError:
    print("读取失败")
else:
    print(f"加载了 {len(data)} 条")
    save_result(process(data))
finally:
    cleanup()
```

`else` = 成功后的逻辑；`finally` = 无论如何都要做的收尾（关文件、还连接、删临时文件）。`finally` 里如果写了 `return`，会**覆盖**前面 `try`/`else` 的返回值，这是面试常考点：

```python
def f():
    try:
        return 1
    finally:
        return 2     # 函数最终返回 2，try 里的 return 1 被覆盖

print(f())           # 2
```

## 翻车现场：重新抛出必须留 `raise` 这一行孤零零的

```python
import json

def load_config(path):
    try:
        with open(path) as f:
            return json.load(f)
    except json.JSONDecodeError as e:
        print("配置格式有误，已使用默认配置")
        raise e          # 看起来没错，其实有问题
```

**问题一：多此一举。** `raise e` 会重新抛出这个异常，但调用栈会从 `raise e` 这一行开始，把原始的 `json.load` 那一行信息截断——调试时定位不到真正出事的代码。

**问题二：如果 `e` 是普通异常类而不是实例，`raise e` 会新建一个实例抛出，丢了原始上下文。**

正确写法是**单独一个 `raise`**：

```python
import json

def load_config(path):
    try:
        with open(path) as f:
            return json.load(f)
    except json.JSONDecodeError:
        print("配置格式有误，已使用默认配置")
        raise                # 原样重新抛出，完整保留调用栈
```

这条规则还有一个实用场景——**记录日志后继续上抛**：捕获、记日志、再 `raise` 让上层决定怎么处理，而不是就地吞掉。这正是"只捕获你知道怎么处理的异常"的反面：记录日志不算"处理"，你依然需要把它抛给能处理的人。

## 小结

- 别写裸 `except:`，至少写 `except Exception`，并尽量具体到异常类型
- `except` 顺序是**先子后父**，父类在前会屏蔽子类分支
- `try` 块要短，`else` 放成功逻辑，`finally` 放收尾，`finally` 里的 `return` 会覆盖前面的返回值
- 重新抛出用单独的 `raise`，别用 `raise e`
- 不知道怎么处理的异常就别捕获，让它冒泡
