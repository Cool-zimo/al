# 递归的三要素：终止条件、递推关系、返回值

> 递归不是"自己调用自己"这么简单。真正写好一个递归函数，只需要想清楚三件事：什么时候停、怎么把大问题拆小、拆完之后拿什么回来。

## 一个函数自己调用自己，到底发生了什么

先别急着记定义。看一个你一定写过的例子：

```python
def factorial(n):
    if n <= 1:
        return 1
    return n * factorial(n - 1)

print(factorial(5))   # 120
```

`factorial(5)` 返回 `5 * factorial(4)`，`factorial(4)` 又返回 `4 * factorial(3)`……一直往下钻，直到 `factorial(1)` 直接返回 1，然后一层层把结果乘回来。

**递归的本质：把"大问题"拆成"小一号的同一种问题"，直到小到不用再拆。**

它和循环不是一回事。循环是"反复做同一件事"，递归是"反复调用同一个函数去解决更小的自己"。能写循环的地方不一定能写递归，能写递归的地方也未必适合循环——但理解递归的第一步，是承认它很反直觉：**函数在没写完的时候，就调用了自己。**

## 三要素之一：终止条件（Base Case）

递归最要紧的事是"停得下来"。那个让递归不再继续调用的分支，叫**终止条件**（base case）。

阶乘的终止条件是 `n <= 1` 时返回 1。斐波那契的终止条件是 `n <= 1` 时返回 `n` 本身。没有终止条件，递归就会一直往下钻，直到 Python 把它拦下来。

```python
def factorial(n):
    if n <= 1:        # ← 终止条件
        return 1
    return n * factorial(n - 1)
```

**怎么找终止条件？** 问自己：这个问题的"最小、最简单、一眼就知道答案"的版本是什么？

- 阶乘：`factorial(1)` 和 `factorial(0)` 都是 1，不用再拆。
- 斐波那契：`fib(0) = 0`、`fib(1) = 1`，这是数列的起点。
- 数组求和：`sum([])` 是 0，空数组不用再拆。

**终止条件写错，比不写还隐蔽。** 因为程序可能能跑、能出结果，但结果就是错的。

## 三要素之二：递推关系（Recursive Relation）

递推关系就是"大问题怎么变成小问题"。它决定了递归的**形状**——是线性的、树状的，还是分叉的。

**阶乘是线性的**：`n! = n × (n-1)!`

```python
def factorial(n):
    if n <= 1:
        return 1
    return n * factorial(n - 1)   # ← 这里就是递推关系
```

每一层只调用一次自己，形成一条链。计算 `factorial(5)` 要 5 层调用，时间复杂度 O(n)，空间复杂度 O(n)（因为每层都要占一个栈帧）。

**斐波那契是树状的**：`F(n) = F(n-1) + F(n-2)`

```python
def fib(n):
    if n <= 1:
        return n                 # ← 终止条件
    return fib(n - 1) + fib(n - 2)   # ← 一次调用变成两次！
```

每一层调用**两个**自己。这就是递归树，它会指数级爆炸。

## 翻车现场：忘了终止条件，直接 RecursionError

```python
# WRONG：没有终止条件
def factorial(n):
    return n * factorial(n - 1)   # 永远在调用，永远停不下来

print(factorial(5))
```

报错：

```
RecursionError: maximum recursion depth exceeded
```

Python 默认的最大递归深度是 1000（`sys.getrecursionlimit()` 可查）。**这不是 Python 的小气，而是它在保护你**——无限递归会一直吃内存，直到程序崩溃。Python 主动在 1000 层时把你掐掉，比真把内存吃光要温柔得多。

**真正的坑在于：忘写终止条件时，代码看起来完全正常。** 缩进、语法、逻辑都对，只是少了那两行 `if`。这种 bug 编译器查不出来，只能靠你自己想清楚"边界在哪"。

## 三要素之三：返回值（Return Value）

递归函数**必须有返回值**（除非是纯副作用操作）。而且每一层的返回值都要被上一层**用到**。

看阶乘的返回值是怎么一层层流回来的：

```
factorial(5)
= 5 * factorial(4)
= 5 * (4 * factorial(3))
= 5 * (4 * (3 * factorial(2)))
= 5 * (4 * (3 * (2 * factorial(1))))
= 5 * (4 * (3 * (2 * 1)))
= 5 * (4 * (3 * 2))
= 5 * (4 * 6)
= 5 * 24
= 120
```

**返回值被"包"在最外层的表达式里。** 如果你想当然地写 `factorial(n - 1)` 却忘了 `return` 它，上一层拿到的就是 `None`，整个表达式就炸了。

## 翻车现场：忘了 return，拿到 None 然后 TypeError

```python
# WRONG：递归分支没写 return
def factorial(n):
    if n <= 1:
        return 1
    n * factorial(n - 1)   # ← 算出来了，但没 return！返回 None

print(factorial(5))
```

报错：

```
TypeError: unsupported operand type(s) for *: 'int' and 'NoneType'
```

`n * factorial(n - 1)` 这个表达式算出了结果，但**没有把它交给 `return`**，函数默认返回 `None`。于是上一层拿到 `None`，试图算 `4 * None`，直接 TypeError。

**这个坑特别阴**：因为递归下去的每一层其实都"算对"了，只是结果没被传回来。单步调试时你会看到最深处返回了 1，但上一层拿到的却是 None。**看到 `NoneType` 报错，先检查是不是漏了 `return`。**

## 斐波那契：一个漂亮但极慢的递归

```python
def fib(n):
    if n <= 1:
        return n
    return fib(n - 1) + fib(n - 2)

for i in range(10):
    print(f"fib({i}) = {fib(i)}")
```

输出：

```
fib(0) = 0
fib(1) = 1
fib(2) = 1
fib(3) = 2
fib(4) = 3
fib(5) = 5
fib(6) = 8
fib(7) = 13
fib(8) = 21
fib(9) = 34
```

数列是对的。但它有多慢？

## 翻车现场：fib(50) 要跑半分钟

```python
import time

def fib(n):
    if n <= 1:
        return n
    return fib(n - 1) + fib(n - 2)

t0 = time.time()
print(fib(35))        # 9227465
print(f"耗时 {time.time() - t0:.2f} 秒")
```

输出（视机器而定）：

```
9227465
耗时 1.83 秒
```

`fib(40)` 大约要十几秒，`fib(50)` 能跑到你怀疑人生。为什么？

## 递归树：为什么 fib 是 O(2^n)

把 `fib(5)` 的调用过程画成一棵树：

```
                        fib(5)
                     /            \
              fib(4)              fib(3)
             /      \             /     \
        fib(3)      fib(2)    fib(2)   fib(1)
       /    \       /   \     /   \
  fib(2) fib(1) fib(1) fib(0) fib(1) fib(0)
  /   \
fib(1) fib(0)
```

**注意 `fib(3)` 被算了两次，`fib(2)` 被算了三次。** 同样的输入、同样的计算，反复重来。这棵树大约有 2^n 个节点（严格说是 ~1.618^n，黄金比例那个根，但渐近意义上就是 O(2^n)）。

**n 每增加 1，运行时间几乎翻倍。** 这就是指数爆炸的恐怖之处：n=5 只要微秒，n=50 就要亿级次调用。

**关键洞察：慢不是因为递归，而是因为重复计算。** 下一章会讲怎么用"记忆化"把 fib 从 O(2^n) 救回 O(n)，那是动态规划的核心思想。这里你只需要记住：**如果递归过程中同一个子问题被反复求解，它就是慢的根源。**

## 线性递归 vs 树形递归

| 特征 | 阶乘 factorial | 斐波那契 fib |
|---|---|---|
| 每层调用次数 | 1 次 | 2 次 |
| 递归形状 | 一条链 | 一棵树 |
| 时间复杂度 | O(n) | O(2^n) |
| 空间复杂度 | O(n)（栈深度） | O(n)（最深的一条链） |
| 会不会重复计算 | 不会 | 会，严重 |

**同样是递归，性能可以差出指数级。** 区别只在于"每层调用几个自己"。

## 翻车现场：n 的类型不对，无限递归

```python
# WRONG：传入浮点数，n 永远不等于 1
def factorial(n):
    if n == 1:        # ← 用 == 而不是 <=，而且浮点数可能永远到不了 1
        return 1
    return n * factorial(n - 1)

print(factorial(5.0))
```

`5.0 - 1` 没问题，但如果参数是 `5.1`，它会一路减下去：`4.1、3.1、2.1、1.1、0.1、-0.9……` 永远不等于 1，直到 RecursionError。

**即使参数是 `5.0`，这个写法也脆弱。** 更好的终止条件是 `if n <= 1` 或 `if n in (0, 1)`，并且通常递归函数要约定"只接受非负整数"。如果你写的是通用工具函数，第一件事应该是校验输入：

```python
def factorial(n):
    if not isinstance(n, int) or n < 0:
        raise ValueError("factorial 只接受非负整数")
    if n <= 1:
        return 1
    return n * factorial(n - 1)
```

**防御式编程在递归里格外重要**，因为一次非法输入会一路往下传，直到炸掉。

## 三要素速查表

写任何递归函数，提笔之前先回答这三个问题，按顺序：

1. **终止条件**：最小的、不用再拆的情况是什么？返回什么？
2. **递推关系**：大问题怎么拆成小一号的自己？调用几次？
3. **返回值**：每一层的结果怎么被上一层用？必须 `return` 吗？

**这三件事想清楚，递归就成功了一大半。** 剩下的是代码实现——而实现里最容易错的，永远是"忘了 return"和"终止条件写错或漏写"。

## 小结

- 递归三要素：**终止条件**（停）、**递推关系**（拆）、**返回值**（合）
- 终止条件是递归的"刹车"，漏写会得到 `RecursionError: maximum recursion depth exceeded`
- 漏写 `return` 是最隐蔽的坑，表现为 `TypeError: NoneType`，因为上一层拿到了 `None`
- 阶乘是线性递归（每层 1 次调用），O(n)；斐波那契朴素写法是树形递归（每层 2 次调用），O(2^n)
- 树形递归慢的根源是**重复计算同一个子问题**，fib(3)、fib(2) 被反复求解
- 递归参数要做防御式校验：浮点数、负数都可能让终止条件永远触发不了
