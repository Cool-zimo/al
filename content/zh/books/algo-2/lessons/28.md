# 递归改迭代：什么时候必须改，怎么改

> 递归写起来漂亮，跑起来可能炸。这一课讲三件事：递归什么时候会炸、用 `sys.setrecursionlimit` 是不是真的能救你、以及把递归改写成迭代的三种套路。

## 递归不是免费的：它吃栈

每一层递归调用都要在调用栈上压一帧。栈的大小是有限的——Python 默认最多 1000 层。

```python
import sys
print(sys.getrecursionlimit())   # 1000
```

这意味着**任何递归深度超过 1000 的输入，都会直接炸给你看。**

```python
def factorial(n):
    if n <= 1:
        return 1
    return n * factorial(n - 1)

print(factorial(500))    # 能跑
print(factorial(2000))   # RecursionError!
```

**factorial(2000) 本身只需要 2000 次乘法，计算量完全不成问题。它炸，纯粹是因为栈不够深。**

这类场景在实际里太常见了：处理一个几万行的文件、遍历一棵很深的树、解析一个很深的 JSON。数据本身没问题，递归的深度把它害死了。

## 翻车现场：sys.setrecursionlimit 治标不治本

Python 留了个后门：

```python
import sys
sys.setrecursionlimit(100000)   # 把上限调高
```

**这能解决 `RecursionError` 吗？能，但只是把爆炸的时间往后推了推。**

```python
import sys
sys.setrecursionlimit(100000)

def factorial(n):
    if n <= 1:
        return 1
    return n * factorial(n - 1)

print(factorial(50000))   # RecursionError: maximum recursion depth exceeded
                          # 虽然 limit 是 100000，但 Python 自己的启动栈也占了几百层
```

**更糟的是**：你调得太高，比如 `setrecursionlimit(10000000)`，程序不会报错，而是**直接 Segmentation fault（段错误）崩掉**——Python 的异常处理都来不及介入，进程就没了。

```python
import sys
sys.setrecursionlimit(10000000)

def infinite():
    return infinite()

infinite()
# 进程直接 Segmentation fault，连 RecursionError 都看不到
```

**为什么这是错的**：`setrecursionlimit` 只是提高了 Python 层的检查阈值，并没有给栈真正分配更多内存。栈空间是操作系统给的，通常只有几 MB。你告诉 Python "放心去递归吧"，Python 信了，然后一路压栈压到操作系统忍无可忍，把进程杀掉。

**结论：`setrecursionlimit` 只能用来处理"深度刚好超过 1000 一点点"的合法场景（比如 2000 层的树）。如果你需要 10 万层递归，这个方案从根上就是错的。**

## 什么时候必须改迭代

| 场景 | 能不能用递归 | 说明 |
|---|---|---|
| 深度有限（< 1000） | 可以 | 尾递归、树遍历都没问题 |
| 深度可能很大（处理数据规模相关） | 必须改 | 列表求和、链/树遍历 |
| 需要回溯（状态要撤销） | 不一定 | 递归很自然，但可以用显式栈模拟 |
| 分治（归并、快排） | 可以 | 深度只有 log n，很安全 |

**一句话判断标准：如果递归深度和"输入数据规模 n"成正比，就必须考虑改迭代。** 如果深度只和 log n 成正比（如分治），就不用担心。

## 套路一：线性递归 → while 循环（累加器）

最直观的改写。以阶乘为例：

```python
# 递归版
def factorial_rec(n):
    if n <= 1:
        return 1
    return n * factorial_rec(n - 1)

# 迭代版
def factorial_iter(n):
    result = 1
    for i in range(2, n + 1):
        result *= i
    return result
```

**关键技巧：把"每一层要算的东西"放进一个变量，用循环模拟"一层层往下走"。**

再看求和：

```python
# 递归
def sum_list(nums):
    if not nums:
        return 0
    return nums[0] + sum_list(nums[1:])

# 迭代
def sum_list_iter(nums):
    total = 0
    for x in nums:
        total += x
    return total
```

**这种改写几乎是机械的**：递归里的"递减排掉的那个 1"，对应迭代里"累加器往前走一步"。

## 套路二：尾递归 → while 循环（直接改参数）

如果一个递归是**尾递归**（递归调用是函数里最后一件事，返回的就是它，不做额外计算），改写尤其干净——直接把参数当状态，用 while 循环转一圈。

```python
# 尾递归版（返回的就是递归调用，不再加工）
def factorial_tail(n, acc=1):
    if n <= 1:
        return acc
    return factorial_tail(n - 1, acc * n)

# 迭代版：把参数当循环变量
def factorial_iter(n):
    acc = 1
    while n > 1:
        acc *= n
        n -= 1
    return acc
```

**对比一下形状：**

| 尾递归 | while 迭代 |
|---|---|
| `factorial_tail(n-1, acc*n)` | `n -= 1; acc *= n` |
| 参数 `n`、`acc` | 循环变量 `n`、`acc` |
| 终止条件 `n <= 1` | 循环条件 `n > 1` |

**尾递归和迭代几乎是同一个东西的两种写法。** 在 Scheme、Scala 这类语言里，尾递归会被编译器自动优化成循环（尾调用优化，TCO）。**但 Python 不做尾调用优化**——所以即使在 Python 里写尾递归，10000 层照样炸。这一点必须清楚。

## 套路三：树形递归 → 显式栈（Stack）

有些递归是"没法直接变循环"的，比如树的遍历、回溯。这种要用**显式栈**来模拟调用栈。

```python
# 递归版：二叉树先序遍历
def preorder(node):
    if node is None:
        return
    print(node.val)
    preorder(node.left)
    preorder(node.right)

# 迭代版：显式栈
def preorder_iter(root):
    if root is None:
        return
    stack = [root]
    while stack:
        node = stack.pop()
        print(node.val)
        if node.right:
            stack.append(node.right)
        if node.left:
            stack.append(node.left)
```

**显式栈的优势：你在堆上分配栈，堆比调用栈大得多（几 GB vs 几 MB）。** 调用栈深度受系统限制，列表可以装下几百万个元素。

**代价：代码变长、变难读。** 递归的优雅换来的是空间限制；迭代的丑换来的是不炸。

## 翻车现场：改迭代时忘了初始化累加器

```python
# WRONG：忘了给 result 赋初值
def factorial_iter(n):
    for i in range(2, n + 1):
        result *= i     # UnboundLocalError!
    return result
```

报错：

```
UnboundLocalError: local variable 'result' referenced before assignment
```

**这类 bug 在"递归改迭代"里特别常见**，因为你脑子里想的是"每层的结果自动传回来"，转换成迭代时就容易漏掉"把结果先归零/赋初值"。所有迭代版的第一行几乎永远是 `result = 初始值`。

正确写法：

```python
def factorial_iter(n):
    result = 1        # ← 初值就是递归的终止条件返回值
    for i in range(2, n + 1):
        result *= i
    return result
```

**规律：迭代里的累加器初值 = 递归终止条件返回的值。** 想清楚递归的 base case 返回什么，那个数就是你的初值。

## 翻车现场：循环条件写错，多算一次或少算一次

```python
# WRONG：range 写成了 range(1, n+1)，多乘了一次 1（这个其实无害）
# 真正有害的：条件判断错了
def factorial_iter(n):
    result = 1
    i = 1
    while i <= n:     # ← 当 n=0 时，i=1 > n=0，循环不进，返回 1。看起来对？
        result *= i
        i += 1
    return result

print(factorial_iter(0))   # 1，正确
print(factorial_iter(5))   # 120，正确
```

这个例子其实结果对。真正容易错的场景是**含 0 的边界**：

```python
# WRONG：n=0 时需要返回 1，但循环条件是 i < n
def factorial_iter(n):
    result = 1
    i = 2
    while i < n:      # n=0 时：i=2, 2<0 为假，不进循环，返回 1 —— 碰巧对
        result *= i   # n=2 时：i=2, 2<2 为假，不进循环，返回 1 —— 错了！应该是 2
        i += 1
    return result

print(factorial_iter(2))   # 1，但正确答案是 2
```

**边界条件在递归里靠终止条件自动处理，在迭代里要你手动写对。** 这也是递归更不容易出错的原因——终止条件写在最前面，一眼就能看到；迭代的边界藏在循环条件和初值里，容易漏。

**改写的自检清单**：用 n=0、n=1、n=2 这三个最小输入各跑一遍，再跑一个正常输入。边界对了，通常就对了。

## 什么时候不该改

递归不是敌人。以下场景递归是对的、优雅的、高效的：

```python
# 分治：深度只有 log n
def mergesort(nums):
    if len(nums) <= 1:
        return nums
    mid = len(nums) // 2
    left = mergesort(nums[:mid])
    right = mergesort(nums[mid:])
    return merge(left, right)
# n=1000000 时深度只有 20 层，离 1000 远得很

# 树的遍历：树通常很矮
def dfs(node):
    if node is None: return
    dfs(node.left)
    dfs(node.right)
# 平衡的二叉树 100 万个节点只有 20 层深
```

**判断标准再强调一遍：深度是否与 n 成正比。** 成正比 → 必须改；只和 log n 成正比 → 放心用。

## 小结

- 递归吃栈：每层一帧，Python 默认上限 1000 层
- `sys.setrecursionlimit` 治标不治本，调太高会 Segmentation fault，连异常处理都来不及
- **深度与 n 成正比就必须改迭代**；深度只与 log n 成正比（分治、平衡树）则安全
- 三种改写套路：线性递归→累加器循环、尾递归→while 改参数、树形递归→显式栈
- 迭代累加器的初值 = 递归终止条件的返回值
- 迭代改写后务必用 n=0、n=1、n=2 三个边界输入自检
