# 递归的执行过程：调用栈、递归树与 print 调试

> 递归最难的地方不是"写"，而是"看不清它在干嘛"。这一课给你三样工具：调用栈、递归树、缩进 print。看完这一课，递归对你来说就是透明的。

## 调用栈：函数在"叠罗汉"

计算机是怎么执行递归的？靠一个叫**调用栈（call stack）** 的东西。

每次调用一个函数，系统就在栈上压入一帧（stack frame），里面装着：这个函数的参数、局部变量、执行到哪一行了。**函数没执行完之前，它的帧一直留在栈上。**

以 `factorial(4)` 为例：

```
调用 factorial(4)   → 栈: [factorial(4)]
  factorial(4) 调用 factorial(3)
调用 factorial(3)   → 栈: [factorial(4), factorial(3)]
  factorial(3) 调用 factorial(2)
调用 factorial(2)   → 栈: [factorial(4), factorial(3), factorial(2)]
  factorial(2) 调用 factorial(1)
调用 factorial(1)   → 栈: [factorial(4), factorial(3), factorial(2), factorial(1)]
  factorial(1) 返回 1 ← 栈顶弹出
  factorial(2) 算 2*1=2，返回 2 ← 弹出
  factorial(3) 算 3*2=6，返回 6 ← 弹出
  factorial(4) 算 4*6=24，返回 24 ← 弹出
栈空，结束。
```

**这就是"展开—归约"（unwind）**：先一路往下压栈（展开），到终止条件后一路往上弹出（归约）。

栈的深度就是递归的深度。阶乘 `n!` 要压 n 层栈。斐波那契 `fib(n)` 最深的一条链也是 n 层。

**关键点：栈帧是占内存的。** 每一层都保留着自己的局部变量和返回地址。这就是为什么递归有空间代价——它不是"免费"的，它在吃栈。

## 用 print 看递归：缩进就是深度

想看清递归的执行顺序，最有效的土办法是 **print + 缩进**。缩进量 = 递归深度，一眼就能看出"现在钻到第几层了"。

```python
def factorial(n, depth=0):
    indent = "  " * depth
    print(f"{indent}factorial({n}) 被调用")
    if n <= 1:
        print(f"{indent}→ 终止条件触发，返回 1")
        return 1
    result = n * factorial(n - 1, depth + 1)
    print(f"{indent}factorial({n}) 返回 {result}")
    return result

factorial(4)
```

输出：

```
factorial(4) 被调用
  factorial(3) 被调用
    factorial(2) 被调用
      factorial(1) 被调用
      → 终止条件触发，返回 1
    factorial(2) 返回 2
  factorial(3) 返回 6
factorial(4) 返回 24
```

**看这段输出的三个收获：**

1. **"被调用"是往右缩进的**（栈在加深）。
2. **"返回"是往左回退的**（栈在弹出）。
3. **返回值在"回退"阶段才真正算出来**——因为 `n * factorial(n-1)` 必须等 `factorial(n-1)` 先返回。

**这个技巧是你调试递归的瑞士军刀。** 不用 IDE 的单步调试，不用断点，就靠缩进 print，递归在你面前就是透明的。写回溯、分治、树的遍历时，它尤其好用。

## 翻车现场：print 写在了 return 之前，看不到返回值

```python
# WRONG：在 return 之前 print，但没把结果存下来
def factorial(n):
    if n <= 1:
        return 1
    print(f"正在算 {n} * factorial({n-1})")
    return n * factorial(n - 1)   # ← 看不到这层的计算结果

factorial(4)
```

输出只有：

```
正在算 4 * factorial(3)
正在算 3 * factorial(2)
正在算 2 * factorial(1)
```

**你看不到 2、6、24 这些中间结果**，因为 `return n * factorial(n-1)` 这一步没人打印。调试时你会发现"它算到哪一步了我知道，但每步算出啥了我不知道"。

正确写法：**先把结果存进变量，打印，再返回。**

```python
def factorial(n, depth=0):
    indent = "  " * depth
    if n <= 1:
        print(f"{indent}base: {n} → 1")
        return 1
    print(f"{indent}进入: factorial({n})")
    result = n * factorial(n - 1, depth + 1)
    print(f"{indent}退出: factorial({n}) = {result}")
    return result
```

**规律：`print` 放在递归调用之前，看"展开"；放在递归调用之后，看"归约"。** 两个都放，就是完整的执行轨迹。

## 递归树：fib 的指数爆炸长什么样

`fib(5)` 的完整调用：

```
fib(5)
├── fib(4)
│   ├── fib(3)
│   │   ├── fib(2)
│   │   │   ├── fib(1) → 1
│   │   │   └── fib(0) → 0
│   │   └── fib(1) → 1
│   └── fib(2)
│       ├── fib(1) → 1
│       └── fib(0) → 0
└── fib(3)
    ├── fib(2)
    │   ├── fib(1) → 1
    │   └── fib(0) → 0
    └── fib(1) → 1
```

数一下叶节点（终止条件返回的地方）：1、0、1、1、0、1、0、1——一共 8 个。

**树越往下分叉越多，节点数约等于 2^n。** 这就是 fib(50) 慢到没法用的原因：它要生成的调用节点是天文数字。

## 用生成器/计数器实测 fib 的重复计算

光说不练。我们来数一下 `fib(n)` 总共被调用了多少次：

```python
call_count = 0

def fib(n):
    global call_count
    call_count += 1
    if n <= 1:
        return n
    return fib(n - 1) + fib(n - 2)

for n in range(11):
    call_count = 0
    result = fib(n)
    print(f"fib({n}) = {result:>3}, 调用次数 = {call_count:>4}")
```

输出：

```
fib(0) =   0, 调用次数 =    1
fib(1) =   1, 调用次数 =    1
fib(2) =   1, 调用次数 =    3
fib(3) =   2, 调用次数 =    5
fib(4) =   3, 调用次数 =    9
fib(5) =   5, 调用次数 =   15
fib(6) =   8, 调用次数 =   25
fib(7) =  13, 调用次数 =   41
fib(8) =  21, 调用次数 =   67
fib(9) =  34, 调用次数 =  109
fib(10) = 55, 调用次数 =  177
```

**`fib(10)` 要调用 177 次，但真正不同的输入只有 0~10 这 11 个。** 剩下 166 次全是重复计算。这个浪费是指数级的——`fib(30)` 要调用 269 万次。

**这个实验的结论比任何抽象解释都更有冲击力：递归树上的重复节点，就是性能的敌人。** 下一章的动态规划、记忆化，本质上都是"把递归树上的重复节点砍掉"。

## 翻车现场：全局变量没重置，调试信息串台

```python
# WRONG：多次调用之间忘了重置计数器
call_count = 0

def fib(n):
    global call_count
    call_count += 1
    if n <= 1:
        return n
    return fib(n - 1) + fib(n - 2)

fib(5)
print(call_count)   # 15
fib(5)
print(call_count)   # 30 ← 不是 15！累计了！
```

**这是全局变量的经典坑。** 你以为第二次调用会从 15 重新开始，但它是在 15 的基础上继续累加。调试递归时如果用全局变量统计调用次数、最大深度，每次测试前必须重置。

更好的写法是用一个可变对象（比如列表）作为参数传进去，避免全局变量：

```python
def fib(n, counter=None):
    if counter is not None:
        counter[0] += 1
    if n <= 1:
        return n
    return fib(n - 1, counter) + fib(n - 2, counter)

counter = [0]
fib(5, counter)
print(counter[0])   # 15
fib(5, counter)
print(counter[0])   # 30 ← 还是累计，因为传的是同一个列表
# 正确：重新创建
counter = [0]
fib(5, counter)
print(counter[0])   # 15
```

**教训：递归调试用的辅助变量，要么作为参数传进去（每次重新创建），要么每次调用前显式重置。** 别依赖全局状态。

## 递归的两个阶段：展开与归约

每个递归都分两阶段，这一点必须刻在脑子里：

```
阶段一「展开」：还没到终止条件，一路往下调用自己
阶段二「归约」：到终止条件后，一层层返回、合并结果
```

**代码里"递归调用之前"的逻辑属于展开阶段，"递归调用之后"的逻辑属于归约阶段。**

```python
def example(n, depth=0):
    indent = "  " * depth
    print(f"{indent}[展开] 进入 {n}")        # ← 展开阶段（往下走时执行）
    if n <= 0:
        print(f"{indent}[终止] 返回 0")
        return 0
    result = example(n - 1, depth + 1)
    print(f"{indent}[归约] {n} 拿到 {result}")   # ← 归约阶段（往上走时执行）
    return result + 1
```

**这个"前后顺序"在回溯算法里是命脉**：做选择在展开阶段，撤销选择在归约阶段。忘了撤销，就是第 30 课的经典翻车。

## 翻车现场：在归约阶段做"有副作用"的操作，导致重复执行

```python
# WRONG：把本该只做一次的事放进了递归，结果被反复执行
results = []

def collect(n):
    if n <= 0:
        return
    collect(n - 1)
    results.append(n)   # ← 看起来只 append 一次？其实每层都 append

collect(3)
print(results)   # [1, 2, 3]  看起来对
```

这个例子恰好结果是对的。但如果你把它改成 `print`：

```python
def show(n):
    if n <= 0:
        return
    show(n - 1)
    print(n)   # 归约阶段：1 2 3

show(3)
```

输出是 `1 2 3`。**如果你以为"归约阶段每层只走一次"，那恭喜你，想对了。** 归约阶段确实每层只走一次，展开阶段也是。递归的每一层都只执行一遍自己的代码——问题从来不是"执行几遍"，而是"你建了多少层"。

**真正容易错的反面是：把副作用操作放在错误的阶段，导致顺序不符合预期。** 比如你想先打印后递归（展开阶段打印），结果是 `3 2 1`；想先递归后打印（归约阶段打印），结果是 `1 2 3`。**前序 vs 后序遍历的顺序差异，根源就在这里。**

## 小结

- 递归靠**调用栈**执行：每层调用压一帧，返回时弹出；栈深度 = 递归深度
- 栈帧占内存，所以递归有空间代价，不是免费的
- **print + 缩进**是最有效的递归调试法：缩进量 = 深度，一眼看清执行轨迹
- 递归分两阶段：**展开**（递归调用前）和**归约**（递归调用后）
- 递归树的节点数决定时间开销；fib 的树是 2^n 级，慢源于重复节点
- 调试用的全局计数器每次测试前要重置，否则结果会串台累加
