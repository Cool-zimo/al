# pickle 的安全警告：绝不能 unpickle 不信任的数据

> 这一课只讲一件事，但它是整个标准库里最要命的安全红线：**只要你能构造一个 pickle 字节串，就能在反序列化那台机器上执行任意代码。** 不信？这一课当场演示给你看。

## 先看现场：一个 pickle 能弹出计算器

下面这段代码，就是完整攻击的全部代码。把它跑起来，你会看到 `"恶意代码已执行"` 被打出来——而"触发点"仅仅是一次 `pickle.loads`。

```python
import pickle

class Bomb:
    def __reduce__(self):
        # __reduce__ 告诉 pickle：还原时调用谁、传什么参数
        return (print, ("恶意代码已执行",))

b = Bomb()
data = pickle.dumps(b)        # 看起来就是一堆无害的字节
print("字节串:", data[:30], "...")

pickle.loads(data)            # 这里就执行了 print("恶意代码已执行")
```

输出：

```
字节串: b'\x80\x04\x95\x1a\x00\x00\x00\x00\x00\x00\x00\x8c\x05print\x94\x8c\x10 ...'
恶意代码已执行
```

**注意整个过程的因果关系**：攻击者只需要让你 `loads` 一个他给的字节串，不需要你的源码、不需要你的密码、不需要任何别的权限。反序列化那一刻，`__reduce__` 返回的 callable 就被调用了。

## `__reduce__` 是后门，而且是设计如此

`__reduce__` 不是漏洞，是 pickle 的**正式协议**——它用来告诉序列化器"怎么重建这个对象"。可被重建的入口包括：

- 任意模块里的任意函数：`os.system`、`subprocess.run`、`shutil.rmtree`……
- 任意构造函数：`int`（当 callable 用）、`exec`、`eval`……
- 攻击者可以链式调用，先 import 再执行。

把 `print` 换成真正危险的东西试试（**仅在你自己的机器上，且明确知道后果**）：

```python
import pickle
import os

class Bomb:
    def __reduce__(self):
        return (os.system, ("echo PWNED && id",))

data = pickle.dumps(Bomb())
pickle.loads(data)        # 会执行 shell 命令
```

## 翻车现场一：把"用户上传"直接 loads

```python
# WRONG —— 真实项目里出现过无数次
import pickle

def load_user_session(uploaded_bytes):
    # 用户上传的"会话文件"，直接反序列化
    return pickle.loads(uploaded_bytes)   # 致命
```

**任何外部来源的数据都不该进 `pickle.loads`**，包括但不限于：网络报文、HTTP 请求体、用户上传的文件、消息队列里的消息、第三方 API 返回值、数据库里"不知道谁写的"的 blob 字段。

判定标准只有一条：**数据是不是你自己用同一个版本的代码、在同一套可信环境里 dump 出来的？** 不是，就不能 loads。

## 翻车现场二：以为"看一眼字节串"能防住

有人会说："我先检查一下字节串里有没有 `os` 再决定要不要 loads。"

```python
# WRONG —— 毫无意义
import pickle

data = pickle.dumps({"safe": "data"})
if b"os" not in data and b"system" not in data:
    pickle.loads(data)
```

这不顶用，有三个原因：

1. pickle 的 opcode 可以编码成多种形式，`b"os"` 只是其中一种字节表象；
2. 攻击者可以 `__import__('o'+'s')`，拼接绕过字符串检查；
3. **你一旦 loads，就已经执行了**——检查在之后发生没有意义。

防护只能在 `loads` **之前**做，而最有效的手段就是"永远不 loads 不可信数据"。

## 翻车现场三：以为换成 JSON 就自动安全

"那我用 JSON 不就行了？"——方向对，但别想当然。JSON 本身不会执行代码，但你的 `json.loads` 之后如果立刻 `eval()` 或 `getattr()` 用户给的字符串，照样中招。真正安全的是**数据格式 + 你的处理逻辑**一起守好。

```python
import json

# WRONG
data = json.loads('{"op": "delete", "path": "/etc/passwd"}')
op = data["op"]
# 用用户输入的字符串去 getattr 或反射，同样是命令注入入口
```

## 安全的替代方案

| 场景 | 推荐 |
|---|---|
| 和外部系统/前端/其他语言交换数据 | **JSON**（第 2~3 章），或 MessagePack、Protobuf |
| 同一套代码内部、可信环境里临时落盘 | **pickle**（注意协议版本） |
| 需要加密且跨语言 | JSON + 签名（HMAC）或 JWT |
| 长期存档、版本会演进 | JSON / YAML + 显式版本号字段 |

**如果你必须用 pickle 做跨进程通信**（比如 multiprocessing、Celery 早期版本），那就把通道做成**可信通道**：本地 Unix socket、带认证的队列、签名校验。绝不要把 pickle 暴露在公网端口上。

## 那 signed pickle 行不行？

可以，但别自己造轮子。用 `hmac` 对字节串做签名，接收方先验签再 loads：

```python
import pickle
import hmac
import hashlib

SECRET = b"只有我自己知道的密钥"

def dump_signed(obj):
    raw = pickle.dumps(obj)
    sig = hmac.new(SECRET, raw, hashlib.sha256).digest()
    return sig + raw          # 签名在前，数据在后

def load_signed(signed):
    sig, raw = signed[:32], signed[32:]
    expect = hmac.new(SECRET, raw, hashlib.sha256).digest()
    if not hmac.compare_digest(sig, expect):
        raise ValueError("签名不匹配，数据可能被篡改")
    return pickle.loads(raw)

data = dump_signed({"user": "张三"})
print(load_signed(data))                 # {'user': '张三'}

# 篡改：改一个字节
bad = bytearray(data); bad[40] ^= 1
try:
    load_signed(bytes(bad))
except ValueError as e:
    print("拦截到:", e)
```

输出：

```
{'user': '张三'}
拦截到: 签名不匹配，数据可能被篡改
```

**注意**：签名只保证"数据没被改"，不保证"数据里没炸弹"。如果签名和数据的密钥都在同一方手里，这没问题；但一旦把签名能力开放给外部，签名本身就形同虚设。所以**签名 = 认证来源，不等于消毒**。

## 小结

- `pickle.loads` 会执行字节串里的 `__reduce__` 指令，**能跑任意代码**——这是设计特性，不是 bug
- 绝对不要 unpickle 来自网络、用户上传、第三方接口、数据库未知字段的数据
- 检查字节串内容、黑名单关键字都没用，**唯一有效的是"来源是否可信"**
- 对外交换用 JSON/MessagePack/Protobuf；内部可信环境才用 pickle
- 必须做跨进程 pickle 时，走可信通道 + HMAC 签名；签名只管认证，不管消毒
