# 第 26 课 · 数据管道工具：项目设计

> 把前 5 章学的所有工具装进一个真实项目——一份能跑的命令行数据管道。

## 为什么要做这个项目

前面 25 课你学会了 JSON、CSV、INI 的读写，学会了 `decimal` 算钱、`enum` 管状态、`dataclasses` 承载结构。但这些都是零散的工具。**真实开发里它们要串成一条流水线**，一个文件从读入到清洗到输出，中间任何一环出问题都不能让整个程序崩掉。

张三在杭州一家电商公司做数据支持，每天要处理来自三个部门的数据：

- 技术部给的 JSON（接口导出）
- 财务部给的 CSV（Excel 另存为）
- 运营部给的 INI（手工维护的配置表）

三份格式不同，但描述的都是同一件事——**交易记录**。张三需要把它们读进来、统一成同一种内部结构、清洗校验、最后输出成统一格式的报告。

这就是我们要做的东西：**数据管道工具（data pipeline）**。

## 管道的四层结构

一个健壮的管道必须分层。四层各司其职，互不干扰：

```
┌─────────────┐
│  读取层 load │  JSON / CSV / INI → list[dict]
├─────────────┤
│  转换层 norm │  list[dict] → list[Record]
├─────────────┤
│  校验层 check│  逐条校验 → (通过列表, 失败列表)
├─────────────┤
│  输出层 dump │  通过列表 → JSON / CSV 文件
└─────────────┘
```

**为什么必须分层？** 因为每一层的"变化原因"不同：

- 读取层变化是因为"来了新格式"（比如明天有人给 XML）
- 校验层变化是因为"业务规则改了"（比如金额门槛从 0.01 涨到 1）
- 输出层变化是因为"领导要换个报表样式"

如果四层全写在一个函数里，改任何一处都要重读整个函数。分层后，**每一层都能独立测试、独立替换**。

## 统一的内部数据结构

三份输入格式不同，但内部统一成同一种结构——`list[dict]`：

```python
# 无论 JSON / CSV / INI，最终都变成这样：
records = [
    {"id": "T001", "amount": "19.90", "status": "paid", "qty": 2},
    {"id": "T002", "amount": "5.00",  "status": "pending", "qty": 1},
]
```

**每个 dict 的 key 固定为 `id` / `amount` / `status` / `qty`**。读取层负责把不同格式的字段名"翻译"成这套标准名。比如 CSV 里可能叫 `订单号,金额,状态,数量`，INI 里可能 `id = T001`，读取层把它们全部映射到 `id/amount/status/qty`。

这一步叫做**标准化（normalization）**，是管道的灵魂。

## 用 dataclass 承载记录

dict 灵活但容易出错——字段名拼错到运行时才发现。用 dataclass 锁定结构：

```python
from dataclasses import dataclass
from decimal import Decimal
from enum import Enum

class Status(Enum):
    PENDING = "pending"
    PAID = "paid"
    SHIPPED = "shipped"

@dataclass
class Record:
    id: str
    amount: Decimal
    status: Status
    qty: int
```

`Record` 是我们的**领域模型**。所有业务逻辑（校验、计算、转换）都围绕它展开，不再和 dict 的 key 纠缠。

## 为什么不做成一个大函数

```python
# WRONG：所有逻辑塞在一起
def process(filepath):
    # 判断扩展名、打开文件、解析、转换、校验、输出……
    # 200 行
    pass
```

上面这种写法有三个致命问题：

1. **没法测试**——想测校验逻辑必须准备一个真实文件
2. **没法复用**——换个输入格式就要改这个函数
3. **出错难定位**——报错在第 150 行，你不知道是解析错了还是校验错了

正确的做法是每层一个函数，每层只做一件事，每层都能单独调用单独测。

## 本项目要交付的东西

到本章结束，你会有一个完整可跑的命令行工具：

```bash
python pipe.py input.json output.csv
python pipe.py orders.csv report.json
python pipe.py data.ini result.csv
```

它会自动识别输入格式、清洗校验、输出结果，并给出一份校验报告告诉用户哪些记录有问题。

## 小结

- 数据管道分四层：读取 → 转换 → 校验 → 输出，每层独立可替换
- 统一的内部结构是 `list[dict]`，key 固定为标准名 `id/amount/status/qty`
- 用 dataclass 承载领域模型，避免 dict 的 key 拼写错误
- 分层是为了可测试、可复用、易定位问题
- 本项目最终形态是一个命令行工具，自动识别格式并完成全流程

## 翻车现场一：dict 的 key 拼错到运行时才爆

```python
from dataclasses import dataclass
from decimal import Decimal
from enum import Enum

class Status(Enum):
    PENDING = "pending"
    PAID = "paid"

@dataclass
class Record:
    id: str
    amount: Decimal
    status: Status
    qty: int

raw = {"id": "T001", "amount": "19.90", "status": "paid", "qty": 2}
# WRONG：手写 dict 取值，key 拼错
# print(raw["amout"])    # KeyError: 'amout'
```

**用 dataclass 后 `r.amount` 如果拼错会在开发时立刻被 IDE 标红**，而 `raw["amout"]` 要等到运行时才爆。这就是为什么要尽早把 dict 转成领域模型。

## 翻车现场二：Decimal 直接用 float 构造

```python
from decimal import Decimal

# WRONG
d = Decimal(19.90)
print(d)
# 正确
print(Decimal("19.90"))
```

输出：

```
19.9000000000000003552713678800500929355621337890625
19.90
```

**从外部数据构造 Decimal 一律用字符串**，这是第 5 章的教训，在本项目里同样适用——金额从 JSON/CSV 读进来第一时间就要 `Decimal(str(...))`。
