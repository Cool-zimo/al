# 数据变更通知：beginInsertRows/endInsertRows，直接改内部列表不通知 view 就不会刷新（经典坑）

> 这是 Model/View 最核心、也最容易被忽略的一课。前面几课的信号都是"自动"的，这一课要讲的是你必须**手动**发出的通知：告诉 view"我要插一行了""我删完一行了"。漏掉就是 bug。

## 为什么需要 begin/end 这一对

**直接改内部数据，view 不会知道。** 这是 Model/View 解耦的必然结果——model 和 view 是两个独立对象，你改了 model 的内部列表，view 无从得知。

```python
# 纯逻辑演示：直接改内部列表，不通知
class SilentModel:
    def __init__(self):
        self._rows = [["张三", 92], ["李四", 85]]

    def add_row(self, row):
        self._rows.append(row)          # 直接改内部列表
        # ❌ 没有通知任何人

model = SilentModel()
model.add_row(["王五", 77])
print("内部数据已经变成:", model._rows)
# 但 view 还画着旧的两行——它不知道
```

**解决方案是 model 主动发信号。但信号不能乱发，得按 Qt 的"事务"协议来：先说"我要开始了"，再改数据，再说"我结束了"。**

```
# 伪代码示意这个"事务"结构
def insert_row(self, row, data):
    self.beginInsertRows(QModelIndex(), row, row)   # ① 事务开始
    self._rows.insert(row, data)                    # ② 真正改数据
    self.endInsertRows()                            # ③ 事务结束
```

**begin 和 end 必须成对出现，中间只做数据修改。** 这对调用告诉 view："接下来这行区间会发生结构变化，你做好准备、等我说结束再重画。"

## 翻车现场一：直接 append 不通知，view 不刷新（本课头号坑）

**症状：点击"添加一行"按钮，内部数据确实多了一行（print 能看到），但表格界面毫无反应，要手动拖一下窗口或点别处才偶尔刷新。**

**这是 Model/View 最高频的 bug，没有之一。**

```
def add_student(self):
    self._rows.append(["新同学", 60])    # ❌ 内部列表改了，view 不知道
    print("现在有", len(self._rows), "行")  # 数字是对的
    # 但表格还是显示旧行数
```

**原因：view 只在收到结构变化信号（rowsInserted / rowsRemoved / layoutChanged）时才调整自己的行数、滚动条、选中状态。** 你悄无声息地改了底层数据，view 无从感知。

**✅ 正确做法：用 beginInsertRows / endInsertRows 包住修改。**

```
def add_student(self, row_data):
    row = self.rowCount()
    self.beginInsertRows(QModelIndex(), row, row)   # 起始行=结束行=要插的位置
    self._rows.append(row_data)
    self.endInsertRows()                             # 必须配对调用
    # 此时 view 自动重画，新行出现
```

**beginInsertRows 的三个参数：`parent`（表格里永远是 QModelIndex()）、`first`（插入区间起始行）、`last`（插入区间结束行）。** 插一行就是 first==last；插多行就传区间。

## 翻车现场二：begin/end 没配对，直接崩溃

**症状：程序崩了，报 `ASSERT failure in QAbstractItemModel::endInsertRows: "Called endInsertRows() with no matching beginInsertRows()"`。**

```
def add_student(self, row_data):
    # ❌ 漏了 begin
    self._rows.append(row_data)
    self.endInsertRows()
    # 断言失败，程序退出
```

**或者反过来：**

```
def add_student(self, row_data):
    self.beginInsertRows(QModelIndex(), self.rowCount(), self.rowCount())
    if some_condition:
        return                 # ❌ 提前 return，endInsertRows 没被调用
    self._rows.append(row_data)
    self.endInsertRows()
```

**原因：Qt 内部用一个计数器跟踪"是否处于结构变化中"。begin 加一、end 减一，不等就断言失败。** 提前 return 是最常见的"失配"原因。

**✅ 正确做法：把修改和 end 放在同一个作用域，异常也要兜底。**

```
def add_student(self, row_data):
    row = self.rowCount()
    self.beginInsertRows(QModelIndex(), row, row)
    try:
        self._rows.append(row_data)
    finally:
        self.endInsertRows()        # ✅ 无论是否异常都配对
```

**try/finally 是这条纪律的最佳实践。** 哪怕中间抛异常，finally 保证 end 被调用，Qt 的内部状态不会乱。

## 插入行的正确写法（含位置参数）

**插入到末尾用 append，插入到中间用 insert。两者都要包在 begin/end 里。**

```
def insert_student(self, position, row_data):
    if position < 0 or position > self.rowCount():
        return
    self.beginInsertRows(QModelIndex(), position, position)
    self._rows.insert(position, row_data)
    self.endInsertRows()
```

**删除用 beginRemoveRows / endRemoveRows，参数含义完全相同。**

```
def remove_student(self, position):
    if position < 0 or position >= self.rowCount():
        return
    self.beginRemoveRows(QModelIndex(), position, position)
    self._rows.pop(position)
    self.endRemoveRows()
```

**注意删除时 begin 的区间要在"删除前"的状态里算。** 你不能先 pop 再 begin，因为 begin 那一刻 view 还要用旧的 rowCount 去校验区间合法性。

## 翻车现场三：先改数据再 begin，顺序反了

**症状：界面偶尔出现"最后一行重复显示"或者干脆崩。

```
def add_student(self, row_data):
    self._rows.append(row_data)                              # ❌ 先改了
    self.beginInsertRows(QModelIndex(), len(self._rows)-1, len(self._rows)-1)
    self.endInsertRows()
```

**原因：Qt 在 begin 那一刻会去问 model 当前的 rowCount 作为"基线"。** 你先 append 了，rowCount 已经变了，begin 拿到的基线是错的，view 计算"新插入了哪些行"就对不上。

**✅ 正确做法：永远是 begin → 改 → end，顺序不可颠倒。**

```
def add_student(self, row_data):
    row = self.rowCount()                    # 先记住插入位置（基于旧 rowCount）
    self.beginInsertRows(QModelIndex(), row, row)
    self._rows.append(row_data)             # 再改
    self.endInsertRows()
```

**这个顺序问题在批量操作时尤其致命。** 记住口诀：先通知、再动手、再结束。

## 批量操作：一次插入多行

**插入一个区间时，first 和 last 是你要插入的那些行在"插入后"的行号区间。**

```
def insert_many(self, position, rows):
    n = len(rows)
    if n == 0:
        return
    self.beginInsertRows(QModelIndex(), position, position + n - 1)
    for r in reversed(rows):                # 从后往前插，位置才对
        self._rows.insert(position, r)
    self.endInsertRows()
```

**为什么 reversed？** 在位置 2 连续插 3 行，如果从前插，第一行插进去后原来的第 2 行就变成第 3 行了，后续插入位置全错。从后往前插，位置 2 始终是锚点。

## 翻车现场四：layoutChanged 滥用——刷新全部的重型武器

**症状：每次改数据都调用 `self.layoutChanged.emit()`，功能能用，但大数据量下界面明显卡顿。

```
def shuffle(self):
    random.shuffle(self._rows)
    self.layoutChanged.emit()       # ❌ 通知 view "整个布局都变了"，全部重画
```

**原因：`layoutChanged` 是最重的通知，意思是"所有东西都变了，你给我全量重画"。** 一千行的表格，改一个单元格就 layoutChanged，等于让 view 白干一千次活。

**✅ 正确做法：能用结构信号（rowsInserted/rowsRemoved）就用结构信号，数据值变了用 dataChanged，layoutChanged 留给"行列数都变了"的场景。**

| 通知 | 适用场景 | 代价 |
|---|---|---|
| `dataChanged` | 值变了、单元格样式变了 | 最轻，只重画指定区域 |
| `rowsInserted` / `rowsRemoved` | 增删行 | 中，重排结构 |
| `layoutChanged` | 行列数变化、整体重排 | 最重，全量重画 |

## 小结

- 直接改内部列表 view 不会刷新，必须手动发通知——这是 Model/View 的头号坑
- beginInsertRows / endInsertRows 必须成对，顺序永远是 begin → 改 → end
- begin 的 first/last 基于"改之前"的 rowCount，先记住位置再动手
- 提前 return 会导致 begin/end 失配，用 try/finally 兜底
- 批量插入从后往前插，位置锚点才不会漂移
- layoutChanged 是重型武器，能不用就不用，优先 dataChanged 和结构信号
