# 为什么要有 Model/View：QTableWidget 用着好好的为什么还要换

> 你用 QTableWidget 写过一个 100 行的表格，很爽。然后产品经理说"要一万行、要实时排序、要按关键字过滤"，你的代码就崩了。

## 先承认 QTableWidget 很好用

**QTableWidget 是 Qt 给"懒人"的礼物。数据少的时候，它是完美的。**

你给它几行几列，然后一行行 `setItem(row, col, QTableWidgetItem(...))`，单元格里想放什么都行。改数据的时候直接拿 `item(row, col).setText(...)`，显示立刻变。这就是"直接操作控件"的直觉，谁用谁知道。

```
from PySide6.QtWidgets import QApplication, QTableWidget, QTableWidgetItem

app = QApplication([])

table = QTableWidget(3, 2)                 # 3 行 2 列
table.setHorizontalHeaderLabels(["姓名", "成绩"])

table.setItem(0, 0, QTableWidgetItem("张三"))
table.setItem(0, 1, QTableWidgetItem("92"))
table.setItem(1, 0, QTableWidgetItem("李四"))
table.setItem(1, 1, QTableWidgetItem("85"))

table.show()
app.exec()
```

**这段代码的隐含前提：每一行数据都"长"在一个 QTableWidgetItem 对象身上。** 数据是控件的一部分，而不是一份独立存在的数据。这个前提在数据量小的时候无伤大雅，数据量大了就是灾难。

## 毛病一：一万行就卡

**QTableWidget 是真的一万个 QTableWidgetItem 都建出来。** 每一行、每一列都是一个独立的对象，都有坐标、样式、状态、信号连接。一万行 × 十列 = 十万个对象同时活着。

```
# ❌ 一万行直接塞进去
table = QTableWidget(10000, 10)
for r in range(10000):
    for c in range(10):
        table.setItem(r, c, QTableWidgetItem(f"数据{r}-{c}"))
# 窗口弹出来要卡好几秒，滚动时还可能一卡一卡的
```

**它卡在三个地方。** 一是内存：十万个对象，光 Python 对象头就占掉几十 MB，加上 Qt 内部的 C++ 对象。二是创建耗时：循环里 new 十万个对象，构造函数和信号槽连接加起来很可观。三是渲染：即使用了视口裁剪，QTableWidget 在布局阶段还是要给这些 item 留位置、算大小。

**Model/View 的解法：view 只问 model"第 r 行第 c 列是什么"，model 现算现给。** 一万个单元格，但屏幕上只显示 30 行，那 model 就只被问 300 次。滚走再滚回来，问的还是那 300 个。这就是"按需取数"，也叫惰性渲染。

## 毛病二：改数据要手写一堆 setItem

**真实项目里，你的数据通常是一个列表、一个字典、一个从数据库读出来的东西。QTableWidget 强迫你把它"摊"成单元格。**

```
# 你的真实数据
students = [
    {"姓名": "张三", "语文": 92, "数学": 88, "英语": 95},
    {"姓名": "李四", "语文": 85, "数学": 91, "英语": 78},
]

# ❌ 手动摊平成单元格
table = QTableWidget(len(students), 4)
for r, s in enumerate(students):
    table.setItem(r, 0, QTableWidgetItem(s["姓名"]))
    table.setItem(r, 1, QTableWidgetItem(str(s["语文"])))
    table.setItem(r, 2, QTableWidgetItem(str(s["数学"])))
    table.setItem(r, 3, QTableWidgetItem(str(s["英语"])))

# 现在数据改了怎么办？
students[0]["语文"] = 99
# 你还得记得同步改表格，不然显示就错了：
table.item(0, 1).setText("99")   # 漏写这一句，界面就和数据不一致
```

**这就是"数据与显示耦合"的代价：你要在两个地方维护同一份事实。** 加一行要改数据也要加 item，删一行要删两边，改一个值要改两边。代码一长，漏同步是必然的，不是偶然的。

## 翻车现场一：数据改了但界面没改，查了半天发现是忘了同步

**症状：明明 `students[0]["语文"] = 99` 执行了，表格显示还是 92。打断点发现数据是对的，UI 没刷新。**

```
students[0]["语文"] = 99
print(students[0])          # {'姓名': '张三', '语文': 99, ...} 数据是对的
# 表格还是显示 92 —— 因为没人通知表格
```

**原因：QTableWidget 不认识你的 `students` 列表。** 它是从 item 里取显示内容的，而 item 里还是 "92"。这两者是两条平行线，你改哪一边另一边都不知道。

**✅ 正确做法（QTableWidget 世界里的补救）：每次改数据后手动同步，或者用 setData 直接改 item 的值。**

```
# ✅ 要么改 item，要么两个一起改，选一种并坚持
students[0]["语文"] = 99
table.item(0, 1).setText(str(students[0]["语文"]))   # 两个一起改
```

**但这个补救治标不治本。真正的答案是：让界面直接读你的数据，而不是读一堆 item。** 这就是 Model/View——你维护一份数据，view 每次需要显示就去你的数据里取，数据一变你通知 view "我这儿变了"，view 自动重画。永远只有一份事实。

## 翻车现场二：想排序要先 copy 一份再塞回去

**症状：PM 要"点列表头就能排序"。你发现 QTableWidget 自带 `sortItems`，但只对字符串排，数字按字符串排出来 100 排在 9 后面。**

```
table.setItem(0, 1, QTableWidgetItem("9"))
table.setItem(1, 1, QTableWidgetItem("100"))
table.sortItems(1, Qt.AscendingOrder)
# 顺序变成 100, 9 —— 因为 QTableWidgetItem 默认按文本比较
```

**原因：QTableWidgetItem 存的是"显示文本"，排序时默认按文本比较。** 你可以 `setData` 存一个数值角色进去再排序，但写起来很别扭。

**✅ 正确做法：换 Model/View，model 直接存真实数据类型（int），排序时按数值比。**

```
# model 里的 data() 返回真正的 int，排序自然按数字大小
def data(self, index, role):
    if role == Qt.DisplayRole:
        return self._rows[index.row()][index.column()]   # 这是个 int
```

**排序、过滤这些操作，本质是"对数据做变换"。** 数据在 model 里，变换就是顺理成章的事。数据摊在 item 里，你就得把 item 一个个捞出来再摆回去，痛苦。

## 翻车现场三：想加个"按关键字过滤"功能，只能重建整个表格

**症状：PM 又来，要一个搜索框，输入"张"只显示姓张的。**

```
# ❌ QTableWidget 的思路：先把现在的显示清空，再按过滤结果重新塞
table.setRowCount(0)                        # 清空
for s in students:
    if keyword in s["姓名"]:
        r = table.rowCount()
        table.insertRow(r)
        table.setItem(r, 0, QTableWidgetItem(s["姓名"]))
        # ... 又是一大段重复代码
# 问题是：过滤前的选中状态、滚动位置全丢了
```

**✅ Model/View 的思路：加一层 ProxyModel，过滤交给它，原数据一行不动。**

```
proxy = QSortFilterProxyModel()
proxy.setSourceModel(model)
proxy.setFilterFixedString("张")
proxy.setFilterKeyColumn(0)
view.setModel(proxy)        # view 只跟 proxy 说话
```

**原 model 始终是原封不动的完整数据，proxy 在中间做筛选，view 只负责画。** 这个"中间加一层代理"的招式，是 Model/View 最漂亮的产物之一。

## 本章主线：Model/View 到底在说什么

**一句话：数据归数据，显示归显示，中间用一套协议（model）接起来。**

| | QTableWidget | Model/View |
|---|---|---|
| 数据存在哪 | 散落在 item 里 | 你自己维护一份 |
| 一万个对象 | 真建一万个 | 只渲染看得见的 |
| 改数据要不要同步 | 要，手动 | 不要，通知刷新即可 |
| 排序/过滤 | 重建或 hack | 换 model 或加 proxy |

**这一章你会学到：model 和 view 怎么分工（02），QStandardItemModel 怎么快速上手（03），怎么自己写一个 model（04），以及"通知刷新"这套协议到底长啥样（05）。** 下一章是排序过滤和委托，那是 Model/View 真正发光的地方。

## 小结

- QTableWidget 好用但把数据存在 item 里，数据与显示耦合
- 一万行真建十万个对象，卡在内存、创建耗时和布局
- 改数据必须手动同步，漏一次就是一次显示 bug
- 排序默认按文本，过滤只能重建，都是"操作控件"思路的代价
- Model/View 让界面读你的数据、数据一变就通知刷新，永远只有一份事实
- 代理（proxy）能在不改原数据的情况下做排序和过滤

```quiz
  import time
  from PySide6.QtWidgets import (

      {"姓名": f"用户{i}", "优先级": i % 5 + 1, "备注": f"备注内容{i}"}
```

```quiz
- QTableWidget 用惰性渲染，只渲染当前可见的单元格，所以一万行不卡
- Model/View 里 view 必须认识数据的具体类型才能显示

answer: 0

```
