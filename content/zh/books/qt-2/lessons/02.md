# Model 与 View 分工：QAbstractItemModel、QTableView、index 与 row/column

> 上一课你信了 Model/View 的好。这一课要拆开看：model 是数据的"接口"，view 是数据的"嘴替"，两者靠一套协议说话，model 从头到尾不认识任何 widget。

## 三者各干一件事

**Model/View 不是三个新类，而是三个角色的分工。Qt 里常见的是 Model 和 View 配对，Delegate 是可选第三角色（后面第 2 章讲）。**

| 角色 | 类 | 职责 |
|---|---|---|
| Model | `QAbstractItemModel` 及其子类 | 存数据、回答"第 r 行 c 列是啥" |
| View | `QTableView` / `QListView` / `QTreeView` | 管显示、管鼠标键盘、管选中 |
| （先提一句）Delegate | `QStyledItemDelegate` | 管单元格怎么画、怎么编辑 |

**核心思想：model 不知道自己被谁显示，view 不知道数据长啥样。** 这是解耦最彻底的样子。

```
from PySide6.QtWidgets import QApplication, QTableView
from PySide6.QtCore import QStringListModel

app = QApplication([])

# model：一份字符串列表的"接口"
model = QStringListModel(["苹果", "香蕉", "橙子"])

# view：一个只管画表格的东西
view = QTableView()
view.setModel(model)      # 把它俩接起来
view.show()
app.exec()
```

**注意 `setModel` 这一步。view 拿到 model 后，会自己问 model："你有多少行？每行每列是什么？"model 只负责回答，从不主动说"view 你该刷新了"。**

## index：view 问问题的"坐标"

**model 不暴露"第 5 行"这个对象。它用的是 `QModelIndex`——一个临时的、轻量的坐标凭证。**

view 想画第 2 行第 1 列，就先问 model 要这个位置的 index：

```
index = model.index(row=2, column=1)   # 拿到 QModelIndex
value = model.data(index, Qt.DisplayRole)   # 再问这个位置的值
```

**index 是个临时通行证，不是数据本身。** 它只记录 (行, 列, 父节点) 和一个指向 model 的指针。它很小、很便宜，可以随手造、随手扔。它的存在是为了让 view 不需要"持有"数据对象——数据始终归 model 管。

**为什么不直接用 model.get(row, col)？** 因为树形结构（QTreeView）里，"第几个子节点"这个坐标只有在父节点确定的情况下才有意义。index 里带着父节点的信息，这套 API 才能同时服务表格和树。表格只有一层，"父节点"永远是 `QModelIndex()`（无效 index，代表根），看起来有点啰嗦，但换到树形结构就完全一样地工作。

## 翻车现场一：忘了 index 的 parent 参数，树形结构全错

**症状：切换到 QTreeView，数据死活显示不出来，或者只显示顶层。**

```
# ❌ 表格写习惯了，写树形 model 时把 parent 丢了
def index(self, row, column, parent=QModelIndex()):
    # 直接拿自己的内部列表
    return self.createIndex(row, column, None)   # 没看 parent 是谁
```

**原因：树的第二层节点，"第 0 行"指的是"某个父节点的第 0 个子节点"，不是"全树第 0 行"。** 忽略 parent，所有节点都当成顶层处理，结果就是层级乱掉。

**✅ 正确做法：先根据 parent 找到"我是哪个父节点"，再取它的第 row 个子节点。**

```
def index(self, row, column, parent=QModelIndex()):
    if not parent.isValid():
        parent_node = self._root
    else:
        parent_node = parent.internalPointer()
    if row < 0 or row >= len(parent_node.children):
        return QModelIndex()
    child = parent_node.children[row]
    return self.createIndex(row, column, child)   # 把节点指针塞进 index
```

**`createIndex(row, column, ptr)` 的第三个参数就是给 index 挂一块自定义数据（通常是内部节点的指针），取的时候用 `index.internalPointer()`。** 这是自定义 model 最常打的配合。

## model 不认识 widget，这是好事

**model 的代码里不该出现 QPushButton、不该 import QLabel、不该调任何 QWidget 的方法。** 它的世界里只有数据、index、role 和信号。

```
# ❌ 一个典型的耦合错误
class BadModel(QAbstractTableModel):
    def __init__(self, table_widget):
        super().__init__()
        self._table = table_widget    # ❌ model 持有了 view 的引用

    def data(self, index, role):
        val = self._rows[index.row()][index.column()]
        if role == Qt.DisplayRole:
            self._table.some_label.setText(...)   # ❌ model 直接改界面
            return str(val)
```

**这个错误会把你重新拖回"数据与显示耦合"的泥潭。** model 一旦知道 view 的存在，你就没法把它换到另一个 view 上——比如同一份数据既想用 QTableView 显示，又想用 QListView 显示，还想在 QComboBox 里做下拉。这三者都能接同一个 model，前提是 model 对它们一无所知。

## 翻车现场二：把 model 绑死在某个 widget 上，想复用就重写

**症状：你在 A 窗口写好了 model，B 窗口想用同一份数据，发现 model 构造函数要求传一个 QPushButton，而 B 窗口没有这个按钮。**

```
class ScoreModel(QAbstractTableModel):
    def __init__(self, submit_btn):
        super().__init__()
        self._submit_btn = submit_btn     # 这个按钮是 A 窗口的
        self._submit_btn.setEnabled(False)

# B 窗口想复用 → 报错，没有 submit_btn 可传
```

**✅ 正确做法：model 只发信号，让 view 或 controller 决定"该不该让按钮可用"。**

```
class ScoreModel(QAbstractTableModel):
    data_dirty = Signal(bool)    # 数据是否被修改过

    def setData(self, index, value, role):
        # 改数据...
        self.data_dirty.emit(True)   # 告诉外界"脏了"
        return True

# view 层自己决定按钮状态
model.data_dirty.connect(submit_btn.setEnabled)
```

**这就是 MVC 里 C 的位置：controller 负责把 model 的信号接到 view 的槽上。** model 只喊"我变了"，至于"变了之后要不要让按钮亮起来"，那是 controller 的活。

## role：同一个单元格的多种问法

**view 问 model 的不是只有"显示什么"，还有"编辑时是什么值""排序用什么""背景色是什么"。这些不同的问法就是 role。**

| Role | 问的是什么 |
|---|---|
| `Qt.DisplayRole` | 显示给用户的文本 |
| `Qt.EditRole` | 编辑时取到的原始值 |
| `Qt.DecorationRole` | 图标 |
| `Qt.ForegroundRole` / `BackgroundRole` | 前景色 / 背景色 |
| `Qt.TextAlignmentRole` | 对齐方式 |
| `Qt.UserRole` | 你自定义的任何东西 |

**DisplayRole 和 EditRole 分开是这套设计的精髓。** 显示时你想给数字加千分位、加单位、四舍五入，但编辑时你希望拿到原始数值。如果只有一个 role，这两件事会互相打架。

```
def data(self, index, role):
    value = self._rows[index.row()][index.column()]
    if role == Qt.DisplayRole:
        return f"{value:,} 元"          # 显示：1,000,000 元
    if role == Qt.EditRole:
        return value                     # 编辑：1000000
    return None
```

**role 是 model 对外提供的"维度"。** 你提供多少维度，view 就能做多花哨的事。什么都不提供（只管 DisplayRole），就是一个朴素表格；把对齐、颜色、图标都提供上，就是一个报表级的界面。

## 小结

- model 管数据、view 管显示、delegate 管编辑与绘制，三者靠协议通信
- model 不认识任何 widget，只通过 index 和 role 回答问题
- index 是临时坐标凭证，表格里 parent 是无效 index，树形里要查 parent
- `createIndex(row, col, ptr)` 第三个参数存自定义节点指针，用 `internalPointer()` 取
- model 一旦持有 view 引用就失去复用能力，该用信号通知外界
- role 区分"显示什么"和"编辑什么"，是数据多样性的基础
