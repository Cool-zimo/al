# 建表：CREATE TABLE

> 连接会开了，这一课把第一册定的数据模型落成真正的 SQL 建表语句。表建得对不对，决定后面所有查询是顺畅还是处处别扭。

## 完整的建表语句

**对着第 2 课的数据模型，写出 records 表的建表 SQL：**

```sql
CREATE TABLE IF NOT EXISTS records (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    amount      REAL    NOT NULL,
    category    TEXT    NOT NULL,
    date        TEXT    NOT NULL,
    note        TEXT,
    type        TEXT    NOT NULL DEFAULT '支出',
    created_at  TEXT    NOT NULL
);
```

**逐字段解释：**

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | INTEGER | PK AUTOINCREMENT | 主键自增，插入时留空 |
| amount | REAL | NOT NULL | 金额，必须是数字 |
| category | TEXT | NOT NULL | 分类，不允许空 |
| date | TEXT | NOT NULL | 日期，YYYY-MM-DD |
| note | TEXT | 可空 | 备注，允许不填 |
| type | TEXT | NOT NULL DEFAULT '支出' | 收入/支出，默认"支出" |
| created_at | TEXT | NOT NULL | 录入时间，系统填 |

## 为什么用 IF NOT EXISTS

**如果你连着运行两次 `CREATE TABLE records(...)`，第二次会报错：`table records already exists`。**

**解决**：加上 `IF NOT EXISTS`，已经存在就跳过，不报错。

**这在桌面应用里尤其重要**：你的程序每次启动都会执行一次"建表（如果不存在）"的初始化，加上这句，首次启动建表、之后启动直接跳过，一套代码两用。

## 字段类型在 SQLite 里的真相

**SQLite 的类型系统和别的数据库不太一样，这里要专门说清楚。**

**SQLite 只有五种"存储类"**：NULL、INTEGER、REAL、TEXT、BLOB。你写 `VARCHAR(50)`、`DECIMAL(10,2)`、`DATETIME`，SQLite 其实**都认**，但不会真的按"长度 50"或"小数 2 位"去约束。

**这意味着：**

- `amount REAL` 存的是浮点，不保证两位小数；
- `date TEXT` 存的是字符串，不校验格式；
- `category VARCHAR(10)` 和 `category TEXT` 在 SQLite 里几乎没区别。

**那还要不要写类型？要。** 理由是：给人看、给工具看。你写了 `REAL`，读代码的人就知道这里存数字；迁移到其他数据库时，类型提示也有用。

## NOT NULL 与默认值

**`NOT NULL` 是数据完整性的第一道防线。** 加了它，插入时空着这个字段会直接报错，不会存进一行"半空"的记录。

**`DEFAULT '支出'` 让插入更省事**：当你不指定 `type` 时，数据库自动填 `'支出'`。收入那笔你可以显式写 `type='收入'`。

## 主键 AUTOINCREMENT 的细节

**写 `INTEGER PRIMARY KEY` 时，这一列就自动变成自增的"行号"，你插入留 NULL 它会自动给一个。**

**那为什么还要写 `AUTOINCREMENT`？** 区别很微妙：

- `INTEGER PRIMARY KEY`：插入留 NULL，SQLite 给它当前最大 id + 1；
- `INTEGER PRIMARY KEY AUTOINCREMENT`：额外保证 id **单调递增、永不复用**。

**举个例**：表里有 id 1、2、3，你删掉 id 3，然后插入新行。

- 不加 AUTOINCREMENT：新行会拿到 id 3（复用刚删除的最大编号）；
- 加了 AUTOINCREMENT：新行拿 id 4（严格递增）。

**本项目用 AUTOINCREMENT**，因为记账记录"被删除后 id 不该复用"，这样日志、外键引用才稳定。

## 初始化建表的时机

**把建表逻辑放进 `db.py`，程序启动时调一次：**

```python
import sqlite3

_SCHEMA = """
CREATE TABLE IF NOT EXISTS records (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    amount     REAL    NOT NULL,
    category   TEXT    NOT NULL,
    date       TEXT    NOT NULL,
    note       TEXT,
    type       TEXT    NOT NULL DEFAULT '支出',
    created_at TEXT    NOT NULL
);
"""

def init_db(path="ledger.db"):
    conn = sqlite3.connect(path)
    conn.execute(_SCHEMA)
    conn.commit()
    return conn
```

**`main.py` 第一行就调 `init_db()`**，之后整个程序都可以假定"表一定存在"。

## 翻车现场一：字段类型写错导致金额存成字符串

```sql
-- 错误：手滑把 REAL 写成 TEXT
CREATE TABLE records (
    amount TEXT NOT NULL,
    ...
);
```

**症状**：插入 `"38.5"`（字符串）能成功，`SUM(amount)` 却返回奇怪结果——SQLite 会把能转数字的字符串转掉，但 `"38.5元"` 直接变 0。

**原因**：类型名写错了，约束失效。

**解决**：建表后立刻插一条测试数据、跑一遍 `SELECT SUM(amount)`，确认返回数字。

## 翻车现场二：忘了建表就先查询

```python
conn = sqlite3.connect("ledger.db")
cur = conn.cursor()
cur.execute("SELECT * FROM records")   # sqlite3.OperationalError: no such table
```

**症状**：`OperationalError: no such table: records`。

**原因**：建表语句根本没执行过（可能写在函数里但从没调用）。

**解决**：确认 `init_db()` 在第一次查询之前被调用。可以把建表放在 `get_conn()` 内部，做到"取连接时自动建表"。

## 翻车现场三：改表结构要小心

**项目中期你想加一个 `account` 字段（记录从哪个账户支出）。新手会直接改建表 SQL 重跑一遍。**

**症状**：表里已经有数据，你改了 `_SCHEMA` 重跑，加了 `IF NOT EXISTS` 的 `CREATE TABLE` 会**直接跳过**——因为它发现表已经存在，不动它。你新加的字段根本没加上。

**解决**：已经上线的库要改结构，得用 `ALTER TABLE records ADD COLUMN account TEXT;`。开发阶段可以先删掉旧的 `ledger.db` 让它重建。

## 小结

- 建表用 `CREATE TABLE IF NOT EXISTS`，首次启动建、之后跳过
- SQLite 类型只认五种存储类，写类型主要是为了给人看
- NOT NULL + DEFAULT 守住数据完整性
- AUTOINCREMENT 保证 id 严格递增、不复用
- 建表逻辑集中在 `init_db()`，main.py 启动时先调它
- 改表结构要用 ALTER TABLE，不能靠重跑 CREATE
