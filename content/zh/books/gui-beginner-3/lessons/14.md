# 输入校验：金额必须是数字、分类不能空

> 表单能填了，但用户什么都可能输入：金额框填"abc"、日期框填"昨天"、分类框空着就点保存。这一课把这些"脏数据"拦在数据层之外，不让它们进数据库。

## 校验放在逻辑层

**按第 3 课的分层，校验属于逻辑层。新建 `logic.py`：**

```python
import re

def validate(date, amt, cat, note=""):
    """返回 (ok: bool, msg: str)"""
    if not date:
        return False, "日期不能为空"
    if not _is_valid_date(date):
        return False, "日期格式应为 YYYY-MM-DD"
    if not amt:
        return False, "金额不能为空"
    try:
        f = float(amt)
    except ValueError:
        return False, "金额必须是一个数字"
    if f <= 0:
        return False, "金额必须大于 0"
    if not cat:
        return False, "请选择一个分类"
    return True, ""
```

**校验函数的标准签名是返回 `(是否通过, 错误信息)`。** 这样界面层拿到结果就能决定：不通过就弹窗，通过就往下走。

## 金额校验：能转 float 才是数字

**判断"是不是数字"，别用正则去猜，直接试转换：**

```python
try:
    f = float(amt_str)
except ValueError:
    return False, "金额必须是一个数字"
```

**为什么不用正则？** 因为合法数字的形式比你想象的多：`1.5`、`0.5`、`.5`、`1e3`、`-3`、`+2.0` 全都能被 `float()` 接受。自己写正则容易漏，也会误伤合法输入。

**要不要允许负数？** 本项目不——支出和收入已经用"类型"字段区分，金额一律为正。所以额外校验 `f > 0`。

**金额要不要限制小数位？** 记账本分位到角就够，可以在校验里加 `round(f, 2)`，或者干脆不管（SQLite 存的是浮点，显示时格式化）。

## 日期校验：格式 + 合法性

**日期要同时满足"格式对"和"值合法"：**

```python
from datetime import datetime

def _is_valid_date(s):
    try:
        d = datetime.strptime(s, "%Y-%m-%d")
    except ValueError:
        return False
    return True
```

**`datetime.strptime("2026-02-30", "%Y-%m-%d")` 会抛 ValueError**，因为 2 月没有 30 号。光靠正则 `^\d{4}-\d{2}-\d{2}$` 只能验格式、验不出"2 月 30 号"这种假日期。

**更宽松的做法**：如果你希望用户能填"昨天"这种自然语言，就得引入 `dateparser` 之类的第三方库——但这违背了本项目"尽量标准库"的原则，所以坚持 `YYYY-MM-DD`。

## 分类校验：非空

**分类用 Combobox readonly 后，理论上不会是空——但用户可能在第一项就是空、或者程序刚启动时没 set 默认值。**

**防御性校验：**

```python
if not cat:
    return False, "请选择一个分类"
```

**哪怕你确信 Combobox 一定有值，也写这一行。** 防御性编程的回报在你改代码、重构、加新字段时体现：哪天你把 Combobox 改成允许输入了，校验还在，不至于漏数据。

## 统一提示：messagebox

**校验不通过时弹错误框：**

```python
ok, msg = logic.validate(date, amt, cat)
if not ok:
    mb.showerror("输入有误", msg)
    return
```

**用 `showerror`（标题+红色图标）表示错误，`showinfo` 表示成功。** 别全用 showinfo，用户视觉上分不清是报错还是通知。

## 翻车现场一：用 float 判断金额，但忘了捕获科学计数

**症状**：你以为 `float("1e3")` 会报错，结果它返回 1000.0，通过了校验，进了数据库。

**这不是 bug，是 feature**——但可能不符合产品预期。用户填了 `1e3` 你真要接受吗？

**决策**：记账本场景下，把 `1e3` 存成 1000 是可以接受的。真正要避免的是"abc""十二元"这种。**保持 `float()` 转换 + `> 0` 判断即可。** 如果实在想禁止科学计数，再用正则 `^[0-9]+(\.[0-9]+)?$` 额外限制。

## 翻车现场二：校验散落在回调各处

```python
def on_add():
    if not date_var.get():
        mb.showerror("错", "日期不能为空")
        return
    try:
        float(amt_var.get())
    except ValueError:
        mb.showerror("错", "金额必须是数字")
        return
    # 分类、备注... 又是好几行
    db.add_record(...)
```

**症状**：校验逻辑和界面控件绑定在一起。哪天你想在"导入 CSV"功能里也校验一遍，只能复制粘贴。

**原因**：没把校验独立成逻辑层函数。

**解决**：抽到 `logic.validate(...)`，CSV 导入和按钮回调都调它。

## 翻车现场三：错误信息只说"格式错误"，用户不知道怎么改

**症状**：`mb.showerror("错", "日期格式错误")`——用户一脸懵：到底要什么格式？

**解决**：错误信息要**具体到可操作**：

```python
return False, "日期格式应为 YYYY-MM-DD，例如 2026-09-27"
```

**好错误信息 = 指出哪错 + 说明正确格式 + 给例子。** 这是提升"专业感"成本最低的一步。

## 小结

- 校验放逻辑层，返回 (是否通过, 错误信息)
- 金额用 float() 试转换，别用正则猜
- 日期用 datetime.strptime 验格式+合法性，能识别 2 月 30 号
- 分类即使 readonly 也要做非空防御
- 错误信息要具体到可操作：指出错在哪、给正确格式和例子
- 校验逻辑集中，避免散落在各回调里
