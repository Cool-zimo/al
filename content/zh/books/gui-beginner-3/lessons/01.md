# 我们要做什么：记账本的需求清单

> 前两册你学会了"造零件"——按钮、输入框、画布、表格。这一册你要做的是"组装一台机器"：一个真正能用的桌面应用。第一件事不是写代码，而是把"要做成什么样"想清楚。

## 为什么要先想清楚

**很多新手一拿到题目就开 IDE。** 结果写到一半发现"分类"和"标签"是两套东西，数据库得推翻重来；或者界面做完了，发现用户真正想要的是"按月汇总"，而不是"全部列出来"。

**这一册你做的项目叫 Ledger（个人记账本）。** 它小到一两周能做完，又大到能练完一个桌面应用的全部环节：数据怎么存、界面怎么搭、图表怎么画、最后怎么打包发给别人。

## 先问自己三个问题

**在敲第一行代码之前，先把这三个问题写下来：**

1. 这个软件**给谁用**？（给作者自己记账用，单用户、单电脑）
2. 它**要做什么**？（记一笔收支、查看历史、按分类统计、数据存盘）
3. 它**不做什么**？（不做多用户、不做联网同步、不做预算提醒）

**这三个问题的答案决定了后面所有技术选择。** 比如"单用户、数据存盘"意味着我们用 SQLite 单文件数据库就够了；"不做联网"意味着不需要服务器、不需要账号体系。

## 需求清单：四件必须能做的事

**我们把它压缩成四条核心需求，每条都要能被验证：**

| 编号 | 需求 | 怎么验证 |
|---|---|---|
| F1 记一笔 | 能录入一条收支：金额、分类、日期、备注 | 录完后能在列表里看到这条 |
| F2 看列表 | 能看到所有记录，按时间倒序排列 | 列表能滚动、能显示金额和分类 |
| F3 按分类统计 | 能看出钱花在哪：各类花了多少、占比多少 | 有饼图或柱状图展示 |
| F4 存下来 | 关掉软件再打开，数据还在 | 重启软件后记录不丢 |

**这四条就是这一册的"教学路线图"。** F1、F2、F4 对应第 2~4 章（数据层 + 界面），F3 对应第 5 章（图表），打包交付是第 6 章。

## 顺便定下"不做"的事

**明确"不做什么"和"做什么"同样重要，它能防止你越写越膨胀：**

- 不做多用户登录
- 不做数据加密（单机自用，权限靠操作系统）
- 不做跨设备同步
- 不做自动分类、OCR 识别
- 不引第三方 GUI 库（只用 tkinter 标准库）

**为什么强调"不引第三方 GUI 库"？** 因为这一册的目标是"完整桌面项目"。第三方库一旦引入，打包体积和依赖管理都会变复杂，而你此时最需要的是把标准库玩透。

## 翻车现场一：跳过需求直接写代码

**症状**：代码写了一个周末，回头发现"分类"写死在界面上，想加一个"交通"分类就得改源码；或者金额存成了字符串，"统计总和"时还得一条条转换。

**原因**：没有先定义"一条记录长什么样"（这就是下一课要讲的数据模型）。**需求不清，数据结构就定不下；数据结构定不下，代码只能边写边返工。**

## 翻车现场二：需求写成"要做一个好用的记账软件"

**"好用"不是需求，是形容词。** 它没法验证、没法测试。换成可验证的描述：

- 模糊："界面要好看"
- 可验证："窗口宽 800、高 600，录入区在底部、列表占中间 70% 高度"

**每个需求都要能回答"我怎么知道做完了"。**

## 小结

- 动手前先想清楚"给谁用、做什么、不做什么"
- 四条核心需求：记一笔、看列表、按分类统计、存盘
- 明确"不做什么"能防止项目膨胀
- 需求要可验证，形容词不是需求

```quiz
type: local

starter: |
  # 我的非核心需求：提醒我超支
  # 改写成可验证的需求：
  # 1.
  # 2.
checklist:
- 写出的每条需求都是动词开头的具体动作
- 每条都能被验证"做完了还是没做完"
- 没有出现"好用""美观""友好"这类形容词
```
