# 数据同步：本地缓存 + 网络更新、乐观更新

> 这一节讲真实应用的常见模式：先展示缓存、再更新网络，以及"先假装成功"的乐观更新。

## 模式一：缓存优先（Cache First）

**流程**：先读本地缓存立刻展示，同时发起网络请求，拿到新数据后再更新界面。

```javascript
async function loadProfile() {
  // 第 1 步：先展示缓存（快）
  const cached = localStorage.getItem('profile');
  if (cached) {
    renderProfile(JSON.parse(cached));
  } else {
    showLoading();
  }

  // 第 2 步：再请求网络（慢）
  try {
    const res = await fetch('/api/profile');
    if (!res.ok) throw new Error('网络错误');
    const fresh = await res.json();

    // 第 3 步：更新缓存 + 更新界面
    localStorage.setItem('profile', JSON.stringify(fresh));
    renderProfile(fresh);
  } catch (error) {
    if (!cached) showError(error.message);
    // 有缓存时静默失败，用户至少看到旧数据
  }
}
```

这样用户体验是：**瞬间看到内容**，即使网络慢也不白屏。

翻车现场一：网络失败时清掉了旧缓存，导致用户看到空白。

```javascript
// ❌ 失败时也清空
async function load() {
  const cached = getCache();
  render(cached);
  try {
    const fresh = await fetchData();
    saveCache(fresh);
  } catch (e) {
    clearCache();   // 错误！网络挂了却把还能看的旧数据删了
    render(null);
  }
}

// ✅ 失败只更新 UI 提示，保留缓存
async function load() {
  const cached = getCache();
  render(cached);
  try {
    const fresh = await fetchData();
    saveCache(fresh);
    render(fresh);
  } catch (e) {
    showToast('网络异常，显示的是缓存数据');  // 缓存保留，只是提示一下
  }
}
```

后果：网络失败时把还能用的旧缓存删掉，等于**把降级方案也毁了**。用户本来能看到上次的数据，现在变成空白。缓存存在的意义就是在网络不可用时兜底，删掉就违背了初衷。

## 模式二：乐观更新（Optimistic Update）

**流程**：用户操作 → **先立刻更新界面**（假装成功）→ 再发请求 → 成功就保留，失败就回滚。

```javascript
async function toggleLike(postId) {
  // 1. 先立刻改 UI
  const post = getPost(postId);
  post.liked = !post.liked;
  post.likes += post.liked ? 1 : -1;
  render(post);

  // 2. 再发请求
  try {
    await fetch(`/api/posts/${postId}/like`, { method: 'POST' });
    // 成功，什么都不用做
  } catch (error) {
    // 3. 失败：回滚
    post.liked = !post.liked;
    post.likes += post.liked ? 1 : -1;
    render(post);
    showToast('点赞失败，已撤销');
  }
}
```

这样用户**感觉操作瞬间生效**，网络慢也不会卡手。

翻车现场二：乐观更新后请求失败，但忘了保存"原始状态"，回滚不回去。

```javascript
// ❌ 没有保存原始值，回滚错误
async function updateName(newName) {
  const oldName = user.name;
  user.name = newName;     // 直接改了
  render(user);
  try {
    await saveName(newName);
  } catch (e) {
    user.name = oldName;   // 简单场景还能用
    render(user);
  }
}

// ❌ 复杂对象就麻烦了：改了多个字段，回滚时容易漏
async function updateProfile(changes) {
  const oldProfile = profile;   // 只是引用拷贝！
  Object.assign(profile, changes);  // 原始对象已被改，oldProfile 也变了
  render(profile);
  try {
    await saveProfile(profile);
  } catch (e) {
    profile = oldProfile;  // oldProfile 已经被改过，回滚无效
  }
}

// ✅ 回滚前深拷贝一份快照
async function updateProfile(changes) {
  const snapshot = structuredClone(profile);  // 保存原始快照
  Object.assign(profile, changes);
  render(profile);
  try {
    await saveProfile(profile);
  } catch (e) {
    profile = snapshot;   // 用快照完整回滚
    render(profile);
    showToast('保存失败');
  }
}
```

后果：只保存引用而没有深拷贝，快照和原对象指向同一块内存，回滚时快照已经被改过了，等于**没有备份**。复杂对象乐观更新前一定要 `structuredClone` 一份快照。

## 两种模式对比

| 模式 | 核心思路 | 适用场景 |
|---|---|---|
| 缓存优先 | 先展示旧的，再悄悄换新 | 内容展示、列表、个人资料 |
| 乐观更新 | 先假装成功，失败再回滚 | 点赞、开关、即时编辑 |

## 与 Python 的对比

这类"本地优先 + 后台同步"的模式在前端特别常见（尤其 PWA / 离线应用），Python 服务端更多是"请求-响应"的直接模式。JS 因为是单线程 + 异步，天然适合这种"先响应、后同步"的体验优化。

## 小结

- **缓存优先**：先展示缓存 → 请求网络 → 更新缓存和界面；网络失败时保留缓存做兜底。
- 网络失败**不要清空**还能用的旧缓存。
- **乐观更新**：先改 UI → 发请求 → 成功保留 / 失败回滚。
- 乐观更新前用 `structuredClone` 保存**快照**，引用拷贝不能用于回滚。
- 两种模式都是为了优化用户体验（即时反馈 vs 不白屏）。
