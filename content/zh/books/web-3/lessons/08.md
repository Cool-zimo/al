# fetch 不会因 HTTP 404/500 而 reject

> 这是 fetch 最经典的坑：**网络层面的成功 ≠ 业务层面的成功**，需要手动检查 `res.ok`。

## 坑的本质

`fetch` 只在**网络层面真正失败**时（断网、DNS 解析失败、被拦截）才会 reject。只要服务器**返回了 HTTP 响应**（哪怕是 404、500），fetch 的 Promise 都会 **fulfilled（resolve）**。

```javascript
// 假设请求一个不存在的接口，服务器返回 404
fetch('/api/not-exist')
  .then(res => {
    console.log(res.status);  // 404
    console.log(res.ok);      // false
    // ⚠️ 这里 Promise 是成功的，会走进 then，不是 catch！
    return res.json();
  })
  .then(data => {
    // 404 页面的内容可能不是合法 JSON
    console.log(data);  // 可能报错或得到意外数据
  })
  .catch(error => {
    console.error('这里其实进不来');  // 404 不会触发
  });
```

翻车现场一：以为 404/500 会自动进 catch，结果错误处理没生效。

```javascript
// ❌ 错误写法
async function getUser() {
  const res = await fetch('/api/user/999');  // 用户不存在，返回 404
  const data = await res.json();   // 仍然往下走
  return data;   // 返回了 404 页面的内容，不是用户信息
}

const user = await getUser();
console.log(user.name);  // 可能 TypeError
```

后果：404 时 fetch **不会 reject**，代码继续往下执行。如果 404 响应体不是合法 JSON，`res.json()` 会抛异常；如果是 HTML 错误页，`data` 就是一段字符串。两种情况调用方都会拿到意料之外的数据。

## 解决：手动检查 res.ok

正确做法是**每次请求都检查响应状态**：

```javascript
async function getUser(id) {
  const res = await fetch(`/api/user/${id}`);
  if (!res.ok) {
    // 手动抛出错误，让流程进 catch
    throw new Error(`请求失败：${res.status} ${res.statusText}`);
  }
  return res.json();
}

// 调用
try {
  const user = await getUser(999);
  console.log(user);
} catch (error) {
  console.error(error.message);  // 请求失败：404 Not Found
}
```

`res.ok` 是 `res.status` 在 **200~299** 区间时为 `true` 的快捷属性，比手动判断 `status === 200` 更省事。

## 封装一个安全的请求函数

把"检查状态"的逻辑抽出来，业务代码就不用反复写：

```javascript
async function safeFetch(url, options = {}) {
  const res = await fetch(url, options);
  if (!res.ok) {
    throw new Error(`HTTP ${res.status}: ${res.statusText}`);
  }
  // 根据 Content-Type 决定怎么读
  const contentType = res.headers.get('content-type') || '';
  if (contentType.includes('application/json')) {
    return res.json();
  }
  return res.text();
}

// 使用
try {
  const data = await safeFetch('/api/user/1');
} catch (error) {
  console.error(error);  // 网络错误 和 HTTP 错误 都会到这里
}
```

这样**网络错误和 HTTP 错误都走同一条 catch 路径**，业务代码不用区分。

翻车现场二：只在 then 里检查 status，忘了 500 也可能返回 JSON 错误信息。

```javascript
// ❌ 只看状态码，不处理错误体的格式
async function load() {
  const res = await fetch('/api/data');
  if (res.status === 200) {
    return res.json();
  }
  // 404/500 走到这里，但错误体可能是 { message: '...' } 的 JSON
  throw new Error('出错了');
}

// ✅ 尝试读取错误体
async function load() {
  const res = await fetch('/api/data');
  if (!res.ok) {
    let msg = res.statusText;
    try {
      const errBody = await res.json();
      msg = errBody.message || msg;  // 优先用服务端给的错误信息
    } catch (e) {
      // 错误体不是 JSON，忽略
    }
    throw new Error(msg);
  }
  return res.json();
}
```

后果：很多后端在 4xx/5xx 时会在响应体里返回 `{ message: '用户不存在' }` 这样的结构化错误信息。如果只抛一个通用的"出错了"，就丢失了服务端给出的具体原因，前端难以提示用户。

## 什么时候 fetch 才会 reject

| 情况 | fetch 是否 reject |
|---|---|
| 断网 / 服务器不可达 | ✅ reject（TypeError） |
| CORS 被浏览器拦截 | ✅ reject（TypeError） |
| HTTP 404 | ❌ resolve，res.ok = false |
| HTTP 500 | ❌ resolve，res.ok = false |
| HTTP 200 | ❌ resolve，res.ok = true |

## 与 Python 的对比

Python 的 `requests` 默认也是**不抛异常**的，需要手动判断：

```python
# Python requests：同样要手动检查
r = requests.get('/api/user/999')
r.raise_for_status()  # 主动抛异常，类似我们手动检查 res.ok
data = r.json()
```

JS 和 Python 在这点上设计一致——都把"HTTP 状态码"和"是否抛异常"分开处理，需要开发者显式判断。

## 小结

- fetch **只在网络层面失败时 reject**，404/500 都会正常 resolve。
- 必须**手动检查 `res.ok` 或 `res.status`**，否则错误会被静默忽略。
- 推荐封装 `safeFetch`：检查状态 + 按 Content-Type 读响应体。
- 错误体可能也是 JSON，应尝试读取 `message` 给出更具体的提示。
- 网络错误、CORS 拦截才是 fetch 会 reject 的场景。
