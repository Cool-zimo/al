# 回调：callback 与回调地狱

> 这一节讲异步最初的样子——回调，以及为什么嵌套多了会变成"地狱"。

## 什么是回调

回调（callback）就是**把一个函数作为参数传给另一个函数，让它在某个时刻（通常是操作完成时）被调用**。

```javascript
// 最基本的回调
function fetchData(callback) {
  setTimeout(() => {
    const data = { name: '张三', age: 28 };
    callback(data);  // 数据就绪后调用回调
  }, 1000);
}

fetchData((data) => {
  console.log('拿到数据：', data.name);  // 1 秒后输出：拿到数据：张三
});
```

这里 `callback` 不是 JS 的关键字，只是一个约定俗成的参数名。你完全可以写成 `onDone`、`handler` 或 `cb`。

## 异步回调的价值

回调让"**现在注册，将来执行**"成为可能。同步代码做不到这点——它必须拿到结果才能往下走。

```javascript
// 模拟读取用户，再根据用户读其文章列表
function getUser(id, callback) {
  setTimeout(() => {
    callback({ id, name: '李四' });
  }, 500);
}

getUser(1, (user) => {
  console.log('用户：', user.name);
});
```

翻车现场一：回调里忘了处理"没有结果"的情况，导致逻辑断层。

```javascript
// ❌ 没考虑查找不到的情况
function findUser(id, callback) {
  const users = [{ id: 1, name: '张三' }, { id: 2, name: '李四' }];
  const found = users.find(u => u.id === id);
  callback(found);  // id=3 时 found 是 undefined，调用方拿到 undefined
}

findUser(3, (user) => {
  console.log(user.name.toUpperCase());  // TypeError: Cannot read properties of undefined
});
```

后果：回调拿到 `undefined` 后直接访问属性，抛出运行时错误，后面的代码全部中断。正确的做法是**给回调传两个值：错误和结果**，这就是 Node.js 经典的"错误优先回调"约定：

```javascript
// ✅ 错误优先：第一个参数是 err
function findUser(id, callback) {
  const users = [{ id: 1, name: '张三' }];
  const found = users.find(u => u.id === id);
  if (!found) {
    callback(new Error('用户不存在'), null);
  } else {
    callback(null, found);
  }
}

findUser(3, (err, user) => {
  if (err) {
    console.error(err.message);
    return;
  }
  console.log(user.name);
});
```

## 回调地狱：嵌套缩进失控

当后续步骤依赖前一步的结果时，回调会一层套一层：

```javascript
// ❌ 回调地狱：嵌套越来越深，越来越难读
getUser(1, (user) => {
  getPosts(user.id, (posts) => {
    getComments(posts[0].id, (comments) => {
      getAuthor(comments[0].authorId, (author) => {
        console.log('终于拿到作者：', author.name);
        // 如果还要继续嵌套，代码会一直向右推进
      });
    });
  });
});
```

这种代码的问题不仅是**缩进失控**（俗称"向右箭头"），还有三个痛点：

1. **错误处理重复**：每一层都要判断错误，代码大量冗余。
2. **难以复用**：嵌套的回调很难抽成独立函数。
3. **难以追踪流程**：加个分支或条件判断会让结构更混乱。

翻车现场二：在循环里用异步回调，下标错乱。

```javascript
// ❌ 经典的"循环 + 异步"下标陷阱
const names = ['张三', '李四', '王五'];
for (var i = 0; i < names.length; i++) {
  setTimeout(() => {
    console.log(names[i]);  // 三次都输出 undefined
  }, 100);
}
```

后果：三次都输出 `undefined`。原因是 `var` 没有块级作用域，`i` 是共享的，等 `setTimeout` 回调执行时循环早就结束了，`i` 的值是 `3`。解决办法是用 `let`（块级作用域）或把下标传进闭包。

```javascript
// ✅ 用 let
for (let i = 0; i < names.length; i++) {
  setTimeout(() => {
    console.log(names[i]);  // 张三 / 李四 / 王五
  }, 100);
}
```

## 回调地狱的解药预告

回调地狱的本质是**"用嵌套表达顺序"**。后续的两种方案分别解决了这个问题：

- **Promise**：用 `.then()` 的链式调用把嵌套**拍平**成从上到下的流程。
- **async/await**：用同步的写法表达异步，代码看起来就像一行行往下走。

```javascript
// ✅ 用 async/await 改写上面的嵌套
async function loadAuthor() {
  const user = await getUser(1);
  const posts = await getPosts(user.id);
  const comments = await getComments(posts[0].id);
  const author = await getAuthor(comments[0].authorId);
  console.log('作者：', author.name);
}
```

## 与 Python 的对比

Python 的回调机制类似，但生态更常用**生成器 + yield** 或 `asyncio` 协程来表达异步流程，很少看到深层回调嵌套。JS 因为历史原因，早期大量 API 都是回调风格（如 Node.js 的文件系统模块），所以"回调地狱"是 JS 特有的高频面试题。

## 小结

- 回调是"把函数作为参数、将来调用"的异步模式，参数名无特殊含义。
- 回调要遵循**错误优先**约定：`callback(err, result)`，先判 `err`。
- 多层依赖产生的嵌套就是**回调地狱**：缩进失控、错误处理冗余、难以复用。
- 循环里的异步回调要注意 `var` 的共享下标问题，改用 `let`。
- Promise 和 async/await 是回调地狱的两代解药。
