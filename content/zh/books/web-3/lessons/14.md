# IndexedDB 简介：何时该用，何时不必

> 这一节给你一张"存储选型图"，搞清楚 IndexedDB 和 localStorage 的边界。

## 什么是 IndexedDB

IndexedDB 是浏览器提供的**大型、结构化、事务型**本地数据库。相比 localStorage 它有三个量级上的不同：

| 维度 | localStorage | IndexedDB |
|---|---|---|
| 容量 | 约 5MB | **数百 MB 甚至更多** |
| 数据类型 | 只能存字符串 | 可存**任意 JS 值**（含对象、二进制、Blob） |
| 读写 | 同步（阻塞主线程） | **异步**（不阻塞） |
| 查询 | 只能按 key 全遍历 | **支持索引、范围查询** |
| 事务 | 无 | 有（ACID） |

## 最朴素的使用：存一条数据

IndexedDB 的 API 比较冗长，这里只演示核心流程：

```javascript
// 打开（或创建）数据库
const request = indexedDB.open('my-app', 1);

request.onupgradeneeded = (event) => {
  const db = event.target.result;
  // 创建一个"对象仓库"，类似表
  if (!db.objectStoreNames.contains('users')) {
    db.createObjectStore('users', { keyPath: 'id' });
  }
};

request.onsuccess = (event) => {
  const db = event.target.result;
  console.log('数据库打开成功');
  // 后续增删改查都基于 db
};
```

因为原生 API 写起来很啰嗦，实际项目通常用封装库（如 `idb`、`Dexie.js`）。

## 用 idb 库：async/await 风格

```javascript
import { openDB } from 'idb';

const db = await openDB('my-app', 1, {
  upgrade(db) {
    db.createObjectStore('users', { keyPath: 'id' });
  }
});

// 增
await db.add('users', { id: 1, name: '张三' });

// 查
const user = await db.get('users', 1);

// 改
await db.put('users', { id: 1, name: '李四' });

// 删
await db.delete('users', 1);

// 遍历
const all = await db.getAll('users');
```

## 何时该用 IndexedDB

**适合的场景：**

- 需要存**大量数据**（远超 5MB）：离线文档、聊天记录、音乐/视频元数据
- 需要**按字段查询或范围查询**：如"取分数大于 90 的记录"
- 需要存**二进制数据**：图片、文件 Blob
- 需要**事务保证**：一批操作要么全成要么全败

```javascript
// 例：离线消息应用，存上千条消息并支持按时间范围查询
const messages = await db.getAllFromIndex('messages', 'by-time',
  IDBKeyRange.bound(lastSync, Date.now()));
```

翻车现场一：为了存一个用户名就用 IndexedDB，纯属杀鸡用牛刀。

```javascript
// ❌ 过度设计：只存一个字符串，却要打开数据库、建表、走事务
const db = await openDB('app', 1, { upgrade(db) { db.createObjectStore('kv'); } });
await db.put('kv', '张三', 'name');
const name = await db.get('kv', 'name');

// ✅ 这种情况 localStorage 一行搞定
localStorage.setItem('name', '张三');
const name = localStorage.getItem('name');
```

后果：IndexedDB 的**异步 API + 建库/建表/版本升级**带来的复杂度远高于 localStorage。为了存几个字符串引入它，代码量翻倍、出错概率上升，收益几乎为零。

## 何时不必用

**以下场景坚持用 localStorage：**

- 数据量小（几个配置项、token、用户偏好）
- 只需 key-value 存取，无查询需求
- 想保持代码简单、无第三方依赖

**以下场景干脆别存本地：**

- 敏感信息（密码、银行卡）：应存服务端
- 需要多设备同步：本地存储无法跨设备

翻车现场二：把敏感信息（token）长期存在 IndexedDB，认为"比 localStorage 安全"。

```javascript
// ❌ 误区：IndexedDB 不比 localStorage 更安全
await db.put('auth', { token: 'sk-xxx', password: '123456' });

// ✅ 两者都运行在客户端，都可读；敏感信息存服务端，前端只持有短期令牌
```

后果：IndexedDB 和 localStorage 都位于客户端，**安全级别相同**。任何能执行 JS 的攻击者都能读取两者。本地存储都不该放真正敏感的信息，token 也应设短过期时间。

## 选型小结

| 需求 | 选择 |
|---|---|
| 几个配置项 / token | localStorage |
| 5MB 以内，结构简单 | localStorage |
| 大量数据、需查询/索引 | IndexedDB |
| 二进制 / Blob | IndexedDB |
| 离线应用、数据同步 | IndexedDB |

## 与 Python 的对比

Python 本地持久化常用 `sqlite3`（关系型、结构化查询）或 `pickle`（序列化）。IndexedDB 更接近 SQLite 的定位，但它是 NoSQL 的键值/对象存储。

```python
# Python sqlite3：结构化、支持 SQL 查询
import sqlite3
conn = sqlite3.connect('app.db')
conn.execute('CREATE TABLE IF NOT EXISTS users (id INT, name TEXT)')
```

```javascript
// JS IndexedDB：对象存储 + 索引查询，API 异步
const db = await openDB('app', 1);
await db.add('users', { id: 1, name: '张三' });
```

## 小结

- IndexedDB 是大型、异步、可索引的本地数据库，容量远大于 localStorage。
- **原生 API 冗长**，实战推荐用 `idb` / `Dexie.js` 封装库。
- 存几个字符串、配置项 → localStorage 足够，别过度设计。
- 大量数据、需查询、二进制 → IndexedDB。
- IndexedDB 和 localStorage **安全级别相同**，敏感信息都不该长期存本地。
