# 加缓存、防抖搜索与请求竞态处理

> 这一节解决三个实战高频问题：把结果存到 localStorage、让搜索输入别太勤快、以及处理"后发先至"的脏数据。

## localStorage 缓存：存什么、多久过期

localStorage 只能存字符串，对象和数组要先 `JSON.stringify`。

```javascript
const CACHE_KEY = 'weather_cache';
const CACHE_TTL = 10 * 60 * 1000;   // 10 分钟

function saveCache(data) {
  const payload = { data, savedAt: Date.now() };
  localStorage.setItem(CACHE_KEY, JSON.stringify(payload));
}

function readCache() {
  const raw = localStorage.getItem(CACHE_KEY);
  if (!raw) return null;
  try {
    const { data, savedAt } = JSON.parse(raw);
    if (Date.now() - savedAt > CACHE_TTL) return null;   // 过期
    return data;
  } catch (e) {
    return null;   // 解析失败也视为无缓存
  }
}
```

缓存要带**时间戳**，过期就当没有。否则用户永远看到昨天的天气。

## 缓存与请求的组合

```javascript
async function search(city) {
  const cache = readCache();
  if (cache && cache.city === city) {
    render(cache);          // 命中缓存：直接渲染，不发请求
    return;
  }
  showStatus('loading');
  try {
    const data = await getWeather(city);
    saveCache(data);
    render(data);
    showStatus('success');
  } catch (e) {
    // 请求失败但本地有旧缓存：降级显示旧数据
    if (cache) render(cache);
    showStatus('error', e.message);
  }
}
```

策略：**先读缓存 → 有就渲染 → 再发请求更新**。失败时若有旧缓存，降级显示旧数据，总比一片空白强。

翻车现场一：直接 `JSON.parse` 缓存，坏数据让整个应用崩溃。

```javascript
// ❌ 缓存被手动改坏，应用直接白屏
const data = JSON.parse(localStorage.getItem(CACHE_KEY));

// ✅ 包一层 try/catch，解析失败当无缓存
let data = null;
try { data = JSON.parse(raw); } catch (e) { data = null; }
```

后果：localStorage 可被用户或其他脚本改写，里面可能是 `undefined`、`"{bad json"` 或格式不符的对象。裸 `JSON.parse` 抛异常会让后续代码全不执行。

## 防抖搜索：等他停下再发

用户连续输入"北""北京""北京市"，你不想每个字都发请求。

```javascript
function debounce(fn, delay) {
  let timer = null;
  return function (...args) {
    clearTimeout(timer);
    timer = setTimeout(() => fn.apply(this, args), delay);
  };
}

const onInput = debounce((city) => {
  if (city) search(city);
}, 400);

cityInput.addEventListener('input', (e) => {
  onInput(e.target.value.trim());
});
```

`delay` 通常取 300~500ms。太短没效果，太长用户觉得卡。

## 请求竞态：后发先至问题

这是搜索联想最经典的坑。用户先输"北京"（请求 A），再输"上海"（请求 B）。**B 可能比 A 先回来**，这时如果直接用 A 的结果覆盖，页面就会显示"上海输入框里是北京天气"。

```javascript
// ❌ 后到的 A 覆盖掉先到的 B
async function search(city) {
  const data = await getWeather(city);
  render(data);     // A 回来时 city 已经是 '上海'，却渲染了北京的旧数据
}

// ✅ 方案：请求时记录当前序列号，回调时校验
let seq = 0;
async function search(city) {
  const mySeq = ++seq;                  // 取号
  try {
    const data = await getWeather(city);
    if (mySeq !== seq) return;          // 我已经不是最新的了，丢弃
    render(data);
  } catch (e) {
    if (mySeq !== seq) return;
    showStatus('error', e.message);
  }
}
```

每次新请求 `seq++`，只有序列号等于当前最新值的回调才允许更新页面。这就是**"取号 + 校验"**模式。

翻车现场二：AbortController 写错位置，取消的是最新的请求。

```javascript
// ❌ 每次新输入都 new 一个新的，反而取消了刚发的正确请求
let controller = null;
async function search(city) {
  controller = new AbortController();     // 上一行的 controller 被覆盖
  const data = await fetch(url, { signal: controller.signal });
}

// ✅ 发新请求前先 abort 掉旧的
let controller = null;
async function search(city) {
  if (controller) controller.abort();     // 先取消旧请求
  controller = new AbortController();     // 再建新的
  const data = await fetch(url, { signal: controller.signal });
}
```

后果：顺序写反，新请求刚发出就被自己的下一行取消。正确顺序是**先 abort 旧的、再创建新的**。

## 小结

- localStorage 只存字符串，`JSON.stringify` 存入、`JSON.parse` 取出并包 try/catch。
- 缓存带 `savedAt` 时间戳，过期视为无缓存。
- 策略：命中缓存先渲染 → 再发请求更新 → 失败降级旧数据。
- 防抖等"安静 300~500ms"再发，减少无效请求。
- 竞态用**序列号校验**或 **AbortController 取消旧请求**处理。
