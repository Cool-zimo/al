# 为什么需要异步：JS 单线程与事件循环

> 这一节回答"为什么 `alert` 能卡住整个页面"，以及为什么耗时操作必须异步执行。

## JS 是单线程的

"单线程"意味着**同一时刻 JS 引擎只能执行一条指令**。浏览器里，页面的渲染、事件处理、JS 执行共用一条主线程（更准确地说，JS 执行时渲染会被暂停）。

```javascript
// 假设这是一个耗时 3 秒的同步计算
function heavyTask() {
  let sum = 0;
  for (let i = 0; i < 3_000_000_000; i++) {
    sum += i;
  }
  return sum;
}
heavyTask();
console.log('算完了');
```

在执行 `heavyTask()` 的这 3 秒里，页面**完全卡死**：按钮点不动、动画不动、输入框输不进字。因为主线程被这条循环占住了，其他任何事情都得排队。

翻车现场一：用同步循环"等一秒"再执行。

```javascript
// ❌ 常见错误：用循环模拟 sleep
function sleepSync(ms) {
  const start = Date.now();
  while (Date.now() - start < ms) {
    // 空转，什么也不做，就是不让出主线程
  }
}

console.log('开始');
sleepSync(2000);      // 页面卡 2 秒
console.log('结束');   // 2 秒后才输出
```

后果：这个 `sleepSync` 看似"等了 2 秒"，实则是让 CPU 空转 2 秒，**期间整个页面无响应**。用户看到的是白屏或卡死。JS 里想"等一会儿"绝不能这么写，必须用异步（计时器、Promise、async/await）。

## 异步：把耗时任务交给别人

文件读取、网络请求、计时器这些操作，JS 自己不干，而是**委托给浏览器提供的底层能力**（Web APIs），自己先继续执行后面的代码。等操作完成，再回过头来执行事先注册好的回调。

```javascript
console.log('1');
setTimeout(() => {
  console.log('2');  // 这个函数是回调，稍后才执行
}, 0);
console.log('3');
// 输出顺序：1 → 3 → 2
```

`setTimeout` 的延迟写 `0` 也不代表"立刻执行"，而是"尽快把回调放入任务队列"。当前同步代码必须先跑完。

## 事件循环：回调排队和执行的机制

事件循环（Event Loop）的工作可以简化成一句话：**主线程空闲时，去任务队列里取一个回调来执行。**

```
┌──────────────────────────────────────┐
│  JS 主线程（调用栈）                  │
│    ↓ 栈空了                          │
│  事件循环：从队列取出一个回调 → 压栈执行 │
│    ↓                                 │
│  任务队列：存放已经就绪的回调          │
└──────────────────────────────────────┘
```

浏览器里的队列其实分两种：**宏任务**（macrotask，如 `setTimeout`、`setInterval`、I/O）和**微任务**（microtask，如 Promise 的 `.then`）。微任务的优先级更高——**每次一个宏任务执行完后，会先把微任务队列清空，再取下一个宏任务。**

```javascript
console.log('A');

setTimeout(() => console.log('B'), 0);       // 宏任务

Promise.resolve().then(() => console.log('C')); // 微任务

console.log('D');
// 输出顺序：A → D → C → B
```

翻车现场二：误以为 `setTimeout(..., 0)` 能精确控制顺序，结果被微任务插队。

```javascript
// ❌ 想当然的代码
setTimeout(() => console.log('宏任务1'), 0);
Promise.resolve().then(() => console.log('微任务1'));
setTimeout(() => console.log('宏任务2'), 0);
// 实际输出：微任务1 → 宏任务1 → 宏任务2
// 微任务会在所有排队的宏任务之前执行
```

后果：如果你的代码依赖"宏任务之间交替执行"的节奏，而中间有人塞了一个微任务（比如某个 Promise `.then`），执行顺序就会出乎意料。写代码时不要假定 `setTimeout(0)` 的回调是"下一行立刻执行"。

## 为什么网络请求必须异步

网络请求（访问服务器）动辄几十到几百毫秒，甚至更久。如果同步发起请求：

```javascript
// ❌ 同步请求（已废弃的 API，仅作原理说明）
const data = fetchSync('/api/data');  // 假设存在：页面会卡到响应回来
render(data);
```

这行代码会让页面卡住几秒。而异步写法让 JS 在"等响应"期间继续处理用户操作：

```javascript
// ✅ 异步写法（示意，第 6 课会讲 fetch 细节）
fetch('/api/data')
  .then(response => response.json())
  .then(data => render(data));
console.log('我先往下走，响应回来再渲染');
```

## 与 Python 的对比

Python 默认也是单线程串行，但有个关键区别：**Python 的 `time.sleep(1)` 是真的让当前线程睡 1 秒，这 1 秒内线程不干活；而 JS 的 `setTimeout` 是把回调交给事件循环，主线程立刻腾出手做别的事。**

```python
# Python：同步等待，线程被占用
import time
time.sleep(2)
print("2 秒后")
```

```javascript
// JS：注册回调后立刻继续
setTimeout(() => console.log('2 秒后'), 2000);
console.log('我不等，马上输出');
```

JS 的异步是"非阻塞"的：等待期间主线程不空闲，而是去处理其他任务。

## 小结

- JS 是单线程的，耗时同步操作会卡死页面。
- 异步操作（计时器、网络、事件）委托给浏览器，通过回调通知结果。
- 事件循环在**主线程空闲时**从队列取回调执行。
- **微任务优先级高于宏任务**：每次宏任务结束后会先清空微任务队列。
- 想"等一会儿"用异步，绝不能用空转循环模拟 sleep。
