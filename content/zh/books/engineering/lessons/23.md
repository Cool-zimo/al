# 容器化入门：让"我这儿能跑"变成"哪儿都能跑"

> 同事的机器上跑得好好的脚本，到你的机器上报错；CI 里通过，生产环境却崩了。差的往往不是代码，而是环境。Docker 把代码连同它的操作系统、依赖、运行时一起打包，换来一句："在我机器上能跑"终于不再是一句笑话。

## 为什么要用 Docker

开发中最常见的扯皮现场，就是环境不一致：

```text
同事：我这儿能跑啊，Python 3.11，依赖都装好了。
你：  我这是 3.9，装不上那个包。
运维：生产是 3.8，跑起来结果还不一样。
```

三台机器，三个 Python 版本，三个结果。问题不在于谁对谁错，而在于**代码没有和环境绑定在一起**。

Docker 的解法是：把应用和它需要的一切（操作系统、Python 解释器、依赖库、环境变量）打成一个**镜像（image）**，然后这个镜像在任何装了 Docker 的机器上运行，得到的都是同一个**容器（container）**。

- 镜像 = 一个打包好的"模板"，像 ISO 安装盘，是静态文件
- 容器 = 镜像跑起来后的"实例"，像用安装盘装好的那台机器，是运行中的进程

一个镜像可以启动任意多个容器。你本地能跑的容器，丢到 CI、丢到服务器，行为一致。

**翻车现场：以为装了 Docker 就等于环境一致**

```text
# WRONG：镜像里用的版本和本地实际跑的版本不同
FROM python:latest          # 本地是 3.11，某天 latest 悄悄变成 3.13
RUN pip install requests    # 装的是当天最新版
```

```text
三周后的报错：
TypeError: requests.get() missing 1 required positional argument: 'xxx'
# 因为 requests 升了大版本，签名变了
```

**后果**：`latest` 是浮动标签，每次构建可能拉到不同版本，今天能跑的镜像明天就构建失败或行为异常。环境"看起来一致"，其实随缘。

## 镜像与容器的关系

可以用一个类比理解：**镜像之于容器，如同类之于对象**。

```text
镜像（Image）                容器（Container）
├─ 静态文件，可复制分发       ├─ 运行中的实例
├─ 由 Dockerfile 构建        ├─ 由镜像启动：docker run
├─ 只读                      ├─ 有读写层，可改可删
└─ 存在仓库里（如 Docker Hub）└─ 停止后状态可保留或丢弃
```

关键概念：

1. **分层（layer）**：Dockerfile 里每一条指令通常产生一层。比如 `FROM` 是一层，`RUN pip install` 又是一层。层会被缓存，改动某一层时，它之后的层都要重做。
2. **写时复制**：所有容器共享同一个只读镜像，各自再叠一层可写层。容器删了，那层可写内容默认也没了。
3. **一次构建，多处运行**：镜像构建一次，推到仓库，CI、测试、生产都拉同一个镜像，保证"开发测的那个"就是"上线跑的那个"。

```bash
# 常见操作
docker build -t myapp:1.0 .      # 用当前目录的 Dockerfile 构建镜像
docker images                    # 查看本地镜像
docker run -p 8000:8000 myapp:1.0   # 启动容器，把 8000 端口映射出来
docker ps                        # 查看运行中的容器
docker stop <容器id>              # 停止容器
docker rmi myapp:1.0             # 删除镜像
```

## 写一个简单 Dockerfile

Dockerfile 是构建镜像的"菜谱"，一行一条指令。下面是一个最小可用的 Python 项目镜像：

```dockerfile
# 1. 指定基础镜像，锁死具体版本
FROM python:3.11-slim

# 2. 设置工作目录（容器内）
WORKDIR /app

# 3. 先复制依赖清单，利用缓存
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# 4. 再复制源码
COPY . .

# 5. 暴露端口（声明用，实际映射靠 docker run -p）
EXPOSE 8000

# 6. 启动命令
CMD ["python", "app.py"]
```

几个要点：

- **基础镜像带版本标签**：`python:3.11-slim` 而非 `python:latest`。"slim" 是精简版，体积更小。
- **先 COPY 依赖清单、再 COPY 代码**：因为 Docker 是按层缓存的。源码天天改，依赖很少改；把 `requirements.txt` 先复制安装，依赖不变时这一层直接命中缓存，不用重装几百兆的包。
- **CMD 用 exec 形式**（JSON 数组）：这样进程是 PID 1，能正确接收停止信号。

**翻车现场：把整个工作目录都塞进镜像**

```dockerfile
# WRONG
FROM python:3.11-slim
WORKDIR /app
COPY . .                       # 把 .git、__pycache__、.venv、.env 全复制进去了
RUN pip install -r requirements.txt
CMD ["python", "app.py"]
```

```text
构建日志：
Step 4/5 : COPY . .
 ---> 1.2GB                     # 镜像本该只有 150MB
# 镜像里还带着几百 MB 的 .git 历史和本地虚拟环境
```

**后果**：镜像臃肿、推送拉取慢、CI 缓存失效频繁；更致命的是敏感文件（`.env`、密钥）可能被打进镜像，推到公开仓库后等于公开泄露。

## 不要把密钥打进镜像

这是容器化最容易犯的**安全事故**。镜像一旦构建，里面有什么就永远有什么——即使你下一行 `RUN rm .env`，密钥依然留在前面的只读层里，谁拿到镜像都能 `docker history` 或直接挂载读取。

```text
# WRONG：在 Dockerfile 里硬编码密钥
ENV DATABASE_PASSWORD=supersecret123
COPY .env .env
RUN echo "API_KEY=sk-xxxxxx" >> /app/config.py
```

正确做法：

1. **用 `.dockerignore` 排除敏感文件**（见下节）
2. **运行时通过环境变量注入**：`docker run -e DATABASE_PASSWORD=xxx`，或配合 `.env` 文件只在运行时挂载
3. **生产用密钥管理服务**：如 Docker Secrets、Kubernetes Secret、云厂商的密钥服务
4. **镜像扫描**：用 `docker scan` 或 CI 里的工具扫描镜像漏洞

```bash
# 正确：运行时注入，镜像里根本没有密钥
docker run \
  -e DATABASE_PASSWORD="$DB_PASS" \
  -e API_KEY="$API_KEY" \
  myapp:1.0
```

**翻车现场：以为删掉就没了**

```dockerfile
# WRONG：自欺欺人
COPY .env .env
RUN cat .env >> /app/config.py && rm .env
```

```text
事后检查：
$ docker history myapp:1.0
<missing>   RUN cat .env >> /app/config.py && rm .env
# .env 的内容已经写进 config.py 这一层，且上一层的 COPY 里还有一份
```

**后果**：攻击者只要拿到镜像（哪怕是私有仓库，也可能被越权访问），就能还原出全部密钥。这类事故在业内屡见不鲜，修复成本远高于一开始做对。

## .dockerignore：构建时的"黑名单"

`.dockerignore` 作用和 `.gitignore` 类似，但它控制的是**哪些文件不会被 COPY 进镜像**。写法几乎一样：

```text
# .dockerignore
.git
.gitignore
.env
*.env
.venv
venv
__pycache__
*.pyc
.pytest_cache
.mypy_cache
node_modules
README.md
tests/
docker-compose.yml
.DS_Store
```

为什么必须配：

- **安全**：挡住 `.env`、密钥文件、本地配置
- **体积**：挡住 `.git`（往往几百 MB）、`.venv`、缓存目录
- **缓存命中**：挡住 `tests/` 等无关文件，改测试不会让源码层失效

```bash
# 验证 .dockerignore 是否生效
docker build -t myapp:test .
docker run --rm -it myapp:test ls -la /app
# 检查输出里有没有 .env、.git、__pycache__ 等不该出现的文件
```

## 小结

- Docker 解决环境不一致：镜像打包代码+环境，容器是镜像的运行实例
- 镜像只读、可分发；容器有可写层，停止后可丢弃
- Dockerfile 写镜像菜谱：基础镜像锁版本、先装依赖再复制代码以利用缓存
- **绝不把密钥打进镜像**，用 `.dockerignore` 排除 + 运行时注入环境变量
- `.dockerignore` 同时保护安全、控制体积、提高缓存命中率

```quiz
type: choice
q: 你的 Dockerfile 里先 COPY . . 复制了全部源码和依赖，再 RUN pip install。为什么推荐反过来——先只复制 requirements.txt 安装依赖，再复制源码？
options:
- 因为 pip 必须先看到 requirements.txt 才能工作
- 因为依赖很少变而源码天天改，先装依赖可以让这一层命中缓存，避免每次改代码都重装几百兆的包
- 因为 COPY . . 只能放在 Dockerfile 最后一行
- 因为先复制源码会导致镜像无法启动
answer: 1
explain: Docker 按层缓存。把变化少的依赖安装提前，变化多的源码复制放后面，能让依赖层在源码改动时依然命中缓存，大幅加快构建。
```
