# 测试金字塔：不是所有测试都要从界面跑一遍

> 你给项目写了 200 个测试，全都是"启动浏览器、点按钮、看页面"。跑一次 40 分钟，CI 天天红，没人再看了。测试越多越慢，最后大家连本地都不跑——这不是测试，是负担。测试金字塔要解决的正是"测多少、测在哪一层"。

## 三层各管什么

测试金字塔分三层，从上到下数量递减、速度递增、定位能力递减。

| 层级 | 管什么 | 速度 | 数量占比 | 典型工具 |
|---|---|---|---|---|
| 端到端测试（E2E） | 整个系统串起来能不能跑通 | 秒到分钟级 | 10% 以内 | Selenium、Playwright |
| 集成测试 | 模块之间接得上（数据库、网络、文件系统） | 毫秒到秒级 | 20%~30% | pytest + 真实数据库 |
| 单元测试 | 单个函数、单个类的行为正确 | 微秒级 | 60%~80% | pytest + unittest |

**单元测试**只测一个函数或方法，不连数据库、不发网络请求、不读文件。它跑得最快，定位最准——失败了直接知道是哪个函数错了。

```python
# 要测的函数
def calculate_discount(price, vip_level):
    if price < 0:
        raise ValueError("价格不能为负")
    rates = {1: 0.05, 2: 0.10, 3: 0.20}
    return round(price * (1 - rates.get(vip_level, 0)), 2)

# 单元测试：传参、断言、结束，全程不碰外部资源
def test_calculate_discount():
    assert calculate_discount(100, 1) == 95.0
    assert calculate_discount(100, 3) == 80.0
    assert calculate_discount(100, 99) == 100.0  # 未知等级不打折
```

**集成测试**验证"我的代码和真实依赖能不能配合"。比如订单服务写进 PostgreSQL 后能不能读出来，消息发出去能不能被消费者收到。它允许连真实数据库，但不启动整个 Web 服务。

**端到端测试**从用户视角走完整流程：打开浏览器 → 登录 → 下单 → 支付 → 看到订单。它最贴近真实，但慢、脆、难定位。

## 为什么比例这么定

**越靠上，反馈越慢。** 一个单元测试平均 1 毫秒，1000 个也就 1 秒。一个 E2E 测试从启动浏览器到关掉要 30 秒，200 个就是 100 分钟。开发时你每改一行就想跑测试，E2E 为主的套件会逼你放弃本地验证。

**越靠上，失败越难定位。** 单元测试失败，报错指向具体一行断言。E2E 失败，你只知道"支付没成功"——是前端按钮没渲染、后端接口 500、数据库连不上，还是第三方支付沙箱挂了？

**越靠上，越容易被环境干扰。** 网络抖动、测试数据脏了、另一个测试改了全局状态，都能让 E2E 随机失败（flaky test）。单元测试不依赖这些，确定性高。

## 只写端到端测试的代价

这是新手项目最常见的错误：觉得"从界面跑通了才是真的测过"，于是全部测试都是 E2E。代价是实实在在的。

**翻车现场：200 个 E2E，CI 一次跑 47 分钟**

```text
$ pytest tests/
tests/test_login.py::test_login_success                PASSED  31.2s
tests/test_login.py::test_login_wrong_password         PASSED  28.7s
tests/test_order.py::test_create_order                 PASSED  42.1s
...
=====================================
200 passed in 47 minutes 12 seconds
```

**后果**：开发者提交后去吃午饭才能看到结果。CI 天天红，因为总有几个测试被网络抖动搞挂。一个月后没人看 CI 了，测试形同虚设。

**翻车现场：E2E 失败但不知道错在哪**

```text
$ pytest tests/test_checkout.py::test_checkout_flow
>       assert page.locator(".order-success").is_visible()
E       AssertionError: 订单成功页面没有渲染
```

查了三小时，发现是商品价格计算函数里的边界判断写错了。一个本该 1 毫秒定位的问题，花了 3 小时。

**正确做法：把同一个场景拆到不同层**

同一个"下单"功能，金字塔的做法是：

```python
# 单元测试：价格计算逻辑（占 70%）
def test_price_calculator_boundary():
    assert calculate_total([{"price": 10, "qty": 3}], discount=0.1) == 27.0
    assert calculate_total([], discount=0) == 0

# 集成测试：订单能写进真实数据库、能被查出来（占 20%）
def test_order_persisted(db_connection):
    order_id = create_order(db_connection, user_id=1, items=[1, 2])
    assert get_order(db_connection, order_id)["status"] == "paid"

# 端到端测试：从登录到看到订单成功页，只保留 2~3 个关键路径（占 10%）
def test_happy_path_checkout(browser):
    browser.goto("/login")
    # ...只验证主流程通不通
```

**关键判断：一个新功能该怎么分配测试？** 业务逻辑复杂的部分多写单测，接口对接部分写集成测试，只留少数几个"黄金路径"做 E2E。

## 金字塔不是银弹

有些场景例外：纯前端项目或 CLI 工具，对外接口就是唯一入口，E2E 占比自然高；数据库引擎本身，内部逻辑和外部接口几乎重合。比例只是经验值，不是教条。但"全部都是 E2E"在任何情况下都说不通。

## 小结

- 金字塔从下到上：单元测试（60~80%）→ 集成测试（20~30%）→ E2E（10% 以内）
- 越往上越慢、越脆、越难定位，所以数量要越少
- 只写 E2E 的后果：CI 超时、随机失败、失败难定位、最终被弃用
- 正确做法：把同一场景按"逻辑 / 对接 / 主流程"拆到不同层
- 比例是经验值，接口型项目可偏高，但全 E2E 一定有问题

```quiz
options:
- 买更快的服务器跑 CI，让 E2E 也变快
- 把大量逻辑层的验证下沉为单元测试，只保留少数几个关键路径做 E2E
- 把 E2E 测试全部删掉，只保留手动测试
- 减少测试数量，每个功能只测一条线
answer: 1
explain: 根因是测试分布不合理，E2E 承担了本该由单测承担的逻辑验证。把逻辑验证下沉为单测，速度快、定位准，E2E 只保留关键路径，CI 时间和可维护性都能恢复。
```

```quiz
- 金字塔意味着 E2E 测试数量最多，因为它们最重要
```
