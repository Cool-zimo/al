# 依赖管理：把"在我机器上能跑"变成"在哪都能跑"

> 张三发给你一个项目，README 只写了一句"pip install 一下就能跑"。你装完跑起来，第一行就报 `ImportError`。原因不是代码有问题，是没人说清楚它到底需要什么——依赖管理就是解决"需要什么、要哪个版本"。

## requirements.txt 与 pyproject.toml

两种最常见的依赖清单格式，别搞混。

**requirements.txt** 是"安装说明书"，简单直白：

```txt
requests==2.31.0
pandas>=2.0,<3.0
python-dotenv
```

每行一个包，`==` 锁定版本，`>=` 表示最低版本，`python-dotenv` 不带版本号表示随便哪个都行。它只干一件事：告诉 pip 装什么。

**pyproject.toml** 是"项目说明书"，PEP 621 标准，信息更多：

```toml
[project]
name = "myapp"
version = "0.1.0"
dependencies = [
    "requests>=2.28",
    "pandas>=2.0,<3.0",
]

[project.optional-dependencies]
dev = ["pytest>=7", "ruff"]
```

它除了依赖，还写项目名、版本、入口点、可选依赖组。现在新建项目**推荐用 pyproject.toml**，因为它是一份完整描述，而 requirements.txt 只是安装清单。

| 对比项 | requirements.txt | pyproject.toml |
|---|---|---|
| 定位 | 安装清单 | 项目完整描述 |
| 谁在用 | pip 直接读 | pip、poetry、hatch、uv 都读 |
| 能写版本吗 | 能 | 能 |
| 能写作者、许可证 | 不能 | 能 |
| 上手难度 | 极低 | 稍高 |

## 为什么要锁版本

不锁版本，等于把项目的命运交给"今天 PyPI 上最新的那个版本"。

**翻车现场：半年后重新安装，全崩了**

```txt
# requirements.txt —— 没有锁版本
requests
pandas
flask
```

```bash
# 张三半年前开发时
$ pip install -r requirements.txt
Successfully installed requests-2.28.0 pandas-1.5.0 flask-2.2.0

# 李四半年后拉代码重装
$ pip install -r requirements.txt
Successfully installed requests-2.31.0 pandas-2.1.0 flask-3.0.0

$ python main.py
Traceback (most recent call last):
  File "main.py", line 3, in <module>
    from flask import Flask, Request
AttributeError: 'Request' is not exported from flask
```

**错误输出**：`AttributeError`。Flask 3.0 重构了导出，`Request` 改了位置。代码一行没改，环境变了，就挂了。

**锁版本就是把这种不确定性消除**：

```txt
requests==2.31.0
pandas==2.1.0
flask==3.0.0
```

现在全世界任何机器、任何时间装出来的环境都一模一样。代价是你得定期手动升级并测试，但这个代价远小于"随机哪天突然挂掉"。

## pip freeze 的坑

`pip freeze` 能一键导出当前环境所有包及其精确版本，听起来完美。但它有个大坑：**它导出的是环境里所有包，包括间接依赖**。

```bash
(.venv) $ pip freeze > requirements.txt
(.venv) $ cat requirements.txt
requests==2.31.0
charset-normalizer==3.3.0
idna==3.4
urllib3==2.1.0
certifi==2023.11.17
pandas==2.1.0
numpy==1.26.0
python-dateutil==2.8.2
pytz==2023.3
six==1.16.0
```

你只装了 `requests` 和 `pandas`，结果导出了十个包。这些间接依赖（`charset-normalizer`、`six`、`pytz`）是被你的直接依赖拉进来的。

**坑在哪**：版本被写死了。两个月后 `requests` 发新版，优化了性能还修了一个你用得到的安全漏洞，但你 `pip install -r requirements.txt` 装出来的还是旧的，因为所有间接依赖都被钉死了，pip 没法自动挑选兼容版本。

**正确做法**是区分**直接依赖**和**锁定文件**：

- 直接依赖（你 `import` 的那些）手动写在 `requirements.txt`，用 `>=` 或 `==` 都行，由你控制
- 真要严格复现，用锁定文件：`pip-tools` 的 `requirements.lock`、`poetry.lock`、`uv.lock`

简单项目可以只维护一份直接依赖清单；要可复现构建，就得有锁定文件。

## 直接依赖和间接依赖的区别

| 类型 | 含义 | 你在代码里 import | 该不该手写进清单 |
|---|---|---|---|
| 直接依赖 | 你自己写的代码里 `import` 的库 | 是 | 必须 |
| 间接依赖 | 你依赖的库又依赖的库 | 否 | 通常让工具管 |

比如你 `import requests`，`requests` 依赖 `urllib3`，那 `urllib3` 就是间接依赖。你不该在清单里写 `urllib3==x.x.x`，除非你确实需要锁定它——让 pip 自己挑兼容版本就好。

**翻车现场：手写了一堆间接依赖**

```txt
# WRONG：把 pip freeze 的结果直接当 requirements.txt 用，还手动加了注释
requests==2.31.0
urllib3==2.1.0        # requests 依赖它
certifi==2023.11.17   # requests 依赖它
charset-normalizer==3.3.0  # requests 依赖它
pandas==2.1.0
numpy==1.26.0         # pandas 依赖它
```

半年后想升级 `requests`，发现 `urllib3` 被钉在 2.1.0，`requests` 新版本要求 `urllib3>=2.2`，冲突。你花了半小时排查，发现罪魁祸首是自己手写的那行。

## 小结

- `requirements.txt` 是安装清单，`pyproject.toml` 是项目完整描述，新项目推荐后者
- 锁版本（`==`）是为了可复现，不锁就是让命运交给"最新版"
- `pip freeze` 会把间接依赖一起导出，直接当依赖清单用会导致无法自动升级
- 维护直接依赖，让工具管理间接依赖，是更合理的分工
- 简单项目写清单即可，要严格复现构建需要锁定文件

```quiz

q: 你在维护一个内部小工具，只用到了 requests 和 pandas。requirements.txt 应该怎么写最合理？
options:
- pip freeze 的结果原样用，越多越安全
- 只写 requests 和 pandas 及其版本，不管它们的间接依赖
- 把所有间接依赖都手写进去并锁定版本
- 留空，让用的人自己 pip install
answer: 1
explain: 只维护直接依赖是更合理的做法。手写间接依赖会钉死它们的版本，日后升级直接依赖时容易冲突。pip freeze 结果适合做锁定文件，不适合当手写清单。
```
