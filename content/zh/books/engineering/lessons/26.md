# 性能优化入门：先测量，再动手

> 优化的第一原则是"别猜"——凭感觉改代码，往往改了个寂寞，甚至改出 bug。这一课带你用 `cProfile` 和 `timeit` 找到真正的瓶颈，再谈怎么改。

## 为什么不能凭感觉优化

程序慢，人的直觉几乎总是错的。你盯着那段"看起来很丑"的循环，花两小时优化它，最后发现热点在别处——数据库查询、一次全量遍历、一个被反复调用的函数。这就是著名的"过早优化是万恶之源"想说的：**在你不知道瓶颈在哪之前，任何优化都是赌博**。

更糟的是，优化过的代码往往更难读、更容易出错。为 1% 的性能换 20% 的可读性，通常不划算。所以正确顺序是：

1. **测量**：跑一次 profile，拿到真实数据
2. **定位**：找到占时间最多的函数 / 行
3. **优化**：只改热点，并且只改一处先验证
4. **复测**：再跑一遍，确认真的变快了

**翻车现场：猜错了方向**

```python
# WRONG：觉得列表推导式"不够快"，换成手写的 for 循环
result = []
for i in range(100000):
    if i % 2 == 0:
        result.append(i * i)

# 其实瓶颈根本不在这里，而在下面这句：
rows = load_from_db()   # 一次全表扫描，占了 95% 的时间
```

```text
$ python -m cProfile -s cumulative app.py
         500 function calls in 3.200 seconds

   Ordered by: cumulative time

   ncalls  tottime  cumtime  filename:lineno(function)
        1  0.000    3.198    db.py:42(load_from_db)
  100000  0.045    0.045    app.py:10(<listcomp>)
# 列表推导式只用了 0.045 秒，优化它毫无意义
```

**教训**：测量之后你会发现，大部分时间都花在少数人知道的地方。优化前先 profile，这是纪律不是建议。

## 测量工具一：timeit 测小段代码

`timeit` 用来比较"一小段代码"谁更快。它会自动跑很多次取平均，排除系统波动的干扰。**不要用 `time.time()` 手动掐表**，那是手工作坊的做法。

```python
import timeit

setup = "data = list(range(1000))"

stmt_a = """
result = []
for x in data:
    if x % 2 == 0:
        result.append(x)
"""

stmt_b = "result = [x for x in data if x % 2 == 0]"

t_a = timeit.timeit(stmt_a, setup, number=10000)
t_b = timeit.timeit(stmt_b, setup, number=10000)

print(f"for 循环: {t_a:.3f}s")
print(f"列表推导: {t_b:.3f}s")
print(f"快了 {t_a / t_b:.1f} 倍")
```

命令行也能用，适合临时对比：

```bash
$ python -m timeit -s "data = list(range(1000))" "[x for x in data if x % 2 == 0]"
50000 loops, best of 5: 6.23 usec per loop
```

**翻车现场：测了一个不稳定的结果**

```python
# WRONG：number 太小，系统抖动盖过了真实差异
t_a = timeit.timeit(stmt_a, setup, number=1)
t_b = timeit.timeit(stmt_b, setup, number=1)
print(t_a < t_b)   # 有时 True 有时 False，毫无意义
```

```text
第一次：for 循环: 0.00012s
第二次：for 循环: 0.00008s
# number=1 时，噪声比信号还大
```

**正确做法**：让 `timeit` 跑足够多次（默认 number 会根据耗时自动调整），看的是"多次运行的平均值"，不是某一次。

## 测量工具二：cProfile 找热点

`timeit` 适合比大小段代码，`cProfile` 适合给整个程序做"体检"——它会告诉你每个函数被调用多少次、花了多少时间。

```python
import cProfile, pstats

def load_data():
    return [x for x in range(100000)]

def process(data):
    result = []
    for x in data:
        result.append(x * x)   # 热点：被循环调用十万次
    return result

def report(result):
    return sum(result)

cProfile.run("report(process(load_data()))", "stats.prof")
```

用 `pstats` 看排序结果，或直接命令行：

```bash
$ python -m cProfile -s tottime my_script.py
```

| 列名 | 含义 |
|---|---|
| ncalls | 被调用次数 |
| tottime | 函数本身耗时（不含它调用的） |
| cumtime | 累计耗时（含它调用的） |
| percall | 平均每次调用耗时 |

**怎么读**：先看 `tottime` 排前面的，那是真正"自己干活慢"的地方；再看 `ncalls` 异常大的，那可能是被不该反复调用的地方。

## 常见瓶颈与对策

下面这些是最常见的"慢"，都配有可复现的例子。注意：**不要背优化口诀，要看 profile 数据再决定用哪一个**。

**瓶颈 1：循环里的重复计算**

```python
# WRONG：每次循环都重新算 len(items)（Python 其实会优化这个，
# 这里只是示意；真正的问题往往是更重的计算）
def normalize(items):
    result = []
    for i in range(len(items)):
        for j in range(len(items)):    # O(n²)，n 大时灾难
            result.append(items[i] + items[j])
    return result
```

```python
# RIGHT：把不变的计算提到循环外
def normalize(items):
    n = len(items)
    result = []
    for i in range(n):
        for j in range(n):
            result.append(items[i] + items[j])
    return result

# 更彻底：如果算法本身是 O(n²) 且 n 很大，考虑换算法，而不是换写法
```

**瓶颈 2：字符串拼接用 `+` 在循环里**

```python
# WRONG：每次 += 都创建新字符串，O(n²)
parts = []
for line in lines:
    parts += line   # 逐字符拼接

# RIGHT：收集到列表，最后 join
parts = []
for line in lines:
    parts.append(line)
result = "".join(parts)
```

**瓶颈 3：不必要的全量遍历**

```python
# WRONG：已经在第 5 个元素找到答案，还要继续扫完全部
def find_user(users, target):
    found = None
    for u in users:
        if u.name == target:
            found = u
    return found

# RIGHT：找到就返回，或者用 next(...) + 生成器表达式
def find_user(users, target):
    for u in users:
        if u.name == target:
            return u
    return None
```

**翻车现场：为了"性能"写丑代码**

```python
# WRONG：看似优化，实则难读且 profile 显示毫无收益
def weird_square(data):
    return list(map(lambda x: x*x, filter(lambda x: x % 2 == 0, data)))
```

```text
$ python -m cProfile -s tottime app.py
   ncalls  tottime  cumtime
        1  0.002    0.002    app.py:20(<listcomp>)
# 两种写法耗时几乎一样，但 listcomp 一眼能看懂
```

**教训**：如果 profile 显示差异不到 10%，优先选更清晰、更好维护的写法。**可读性本身就是性能**——因为好读的代码才有人愿意去优化它。

## 优化的边界

优化要讲投入产出。下面这条规则很实用：

> **先让代码正确、清晰，再让它快。**

- 90% 的场景，选对数据结构（dict 查表 vs list 遍历）比抠循环写法重要得多
- 真的遇到瓶颈，先看能不能**减少调用次数**、**换算法复杂度**，再看微观写法
- 如果优化让代码变得难以维护，而收益只有几个百分点，那就别优化
- 测量、优化、再测量——形成闭环，别凭感觉收工

**翻车现场：优化引入了 bug**

```python
# WRONG：为了省一次遍历，"顺手"改了逻辑
def get_active(users):
    active = []
    for u in users:
        if u.is_active:
            active.append(u)
    return active

# 优化后
def get_active(users):
    return [u for u in users if u.is_active]   # 看起来等价，但忘了保留排序
```

```text
测试输出：
expected: [u3, u1, u2]   # 原逻辑里 active 是按原顺序
actual:   [u1, u2, u3]   # 新逻辑改变了顺序
```

**教训**：优化前先有测试覆盖当前行为，优化后立刻复测。没有测试的优化就是在赌。

## 小结

- 优化第一步永远是测量，凭感觉等于猜
- `timeit` 比大小段代码，`cProfile` 给整个程序做体检
- 看 profile 时关注 `tottime`（自己慢）和 `ncalls`（调用太多次）
- 常见瓶颈：循环里重复计算、字符串拼接、不必要的全量遍历
- 收益小、可读性差的优化不做；优化前后都要测试验证
