# 代码评审：评审不是找茬，是共同负责

> 你提了一个 PR，同事留了 20 条评论，其中 15 条是"这里少个空格""变量名不好"。你花了两天改格式，真正的设计问题一个没讨论。代码评审是项目质量的第一道关口，做歪了就是浪费时间。

## 评审看什么

评审不是检查代码能不能跑——CI 已经跑过了。评审看的是**代码之外的事**：

1. **设计是否合理**：这个改动放在这里对吗？有没有更简单的方案？是不是在错误的抽象层级上解决？
2. **可读性**：六个月后来的人能不能看懂？命名、注释、结构是否自解释？
3. **测试覆盖**：边界情况测了吗？异常路径测了吗？改了逻辑有没有同步改测试？
4. **对现有代码的影响**：这个改动会不会让别的模块出问题？有没有改到公共 API？
5. **安全与配置**：有没有硬编码密钥？输入有没有校验？权限检查有没有遗漏？

**翻车现场：评审变成了格式检查**

```text
PR #128: 实现订单导出功能
  ├─ utils.py:42 这里应该有两个空格
  ├─ models.py:88 行太长，换行一下
  ├─ api.py:12 引号风格不统一
  ├─ ...
```

格式问题应该由 black / ruff 自动抓，不应该占用人的注意力。**如果评审里出现格式评论，说明工具链没配好**。

## 怎么提意见

**提意见的三条原则**：

**1. 说清 why，不只说 what**

```text
# 差
- 把这个函数名改成 fetch_and_cache

# 好
- 函数名 fetch_user 暗示是纯查询，但实际会写缓存。
  建议改成 find_user_or_load_cache，让调用方意识到有副作用。
```

**2. 区分"必须改"和"可以讨论"**

```text
# 必须改（阻塞合并）
- 这里没做输入校验，恶意数据会直接进 SQL。
  必须加参数化查询，否则不能合并。

# 可以讨论（不阻塞）
- 个人偏好：我觉得用 dataclass 比 dict 更清晰，
  但如果团队没这个约定就不强求，你觉得呢？
```

GitHub / GitLab 支持用前缀标记：

- `blocking:` 或 `must:` —— 合并前必须解决
- `nit:` —— 吹毛求疵，可忽略
- `question:` —— 提问，不要求改动

**3. 对代码，不对人**

```text
# 差
- 你又忘了处理 None 的情况

# 好
- 这里 user 可能是 None（line 30 返回了 None），
  后面第 45 行直接用了，会抛 AttributeError。
```

前者针对人，后者针对代码和问题本身。

## 怎么接受意见

**评审者给了意见，你的回应方式决定了评审的效率**。

**不要当场防御**：

```text
评审者：这个循环可以提前 break，否则会多跑几轮
你：可是数据量很小，性能不是问题
# 这是在辩论，不是在解决
```

**正确做法：先理解再回应**

```text
你：明白，已改为提前 break。顺便确认下，如果未来数据量
    变大，这个改动也能覆盖，谢谢。
```

如果确实不同意，说明理由而不是情绪：

```text
你：这里我没用参数化查询，而是用了白名单校验 + 转义，
    因为查询条件里有动态表名，参数化不支持。
    白名单在 line 12，你看这样处理可以吗？
```

把讨论聚焦在**方案和理由**上，而不是"谁对谁错"。

**翻车现场：批量"解决"所有评论**

```text
评审者提了 15 条意见 → 你点 "Resolve conversation" × 15
→ 实际只改了 3 条，其余没动
```

**后果**：评审者以为都改了，合并通过，剩下的 12 个问题悄悄进了 main。点"已解决"之前，**代码必须真的改了**。

## 小结

- 评审看设计、可读性、测试、影响面、安全，不是看格式
- 格式问题交给工具，人的精力留给设计
- 提意见要说清 why、区分必须改和可讨论、对事不对人
- 接受意见先理解再回应，不同意就给理由和方案
- "已解决"意味着代码真的改了，不是把评论关掉

answer: 1
