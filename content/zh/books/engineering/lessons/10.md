# 错误处理哲学：异常不该被看见，更不该被吞掉

> 你写的接口半夜报警：500 错误，日志里只有 `Internal Server Error`，没有堆栈，没有上下文。你花了四个小时才定位到是一个 `except:` 把异常吞掉了。错误处理的全部艺术，都在"该抓的时候抓，不该抓的时候让它往上冒"。

## 什么时候捕获

异常只在该处理的时候处理。判断标准：**你能对这个异常做什么？**

```python
# 能处理：重试、降级、给用户友好提示
def fetch_user(user_id):
    try:
        return db.find(user_id)
    except ConnectionError:
        # 能做什么：重试一次
        return db.find(user_id)
```

```python
# 不能处理：让上层决定
def parse_config(path):
    with open(path) as f:
        return json.load(f)
    # FileNotFoundError、json.JSONDecodeError 都不该在这里抓
    # 调用方知道该弹窗、还是用默认值、还是崩溃
```

**翻车现场：在函数里把异常转成返回值**

```python
# WRONG：用返回值表示失败
def read_file(path):
    try:
        with open(path) as f:
            return f.read()
    except Exception:
        return None
```

调用方：

```python
content = read_file("config.json")
if content is None:
    # 是文件不存在？还是权限问题？还是编码错误？全丢了
    print("读取失败")
```

**错误输出**：只打印"读取失败"，完全无法定位是哪种失败。异常对象本来带着类型和堆栈，被你用一个 `None` 抹平了。

## 不要吞掉异常

**最危险的一行 Python 代码**：

```python
try:
    do_something()
except:
    pass
```

`except:`（不带任何类型）会捕获**所有**异常，包括 `KeyboardInterrupt`（Ctrl+C）、`SystemExit`。`pass` 是什么都不做。

**翻车现场：裸 except + pass 让 bug 隐形**

```python
# WRONG
def send_notification(user, msg):
    try:
        smtp.send(user.email, msg)
    except:
        pass  # 发送失败就算了，不重要
```

上线后用户投诉"没收到通知"。你查日志——什么都没有，因为异常被 `pass` 吞了。你只能加日志重发一版，再等下一次复现。

**改成**：至少打日志。

```python
import logging

def send_notification(user, msg):
    try:
        smtp.send(user.email, msg)
    except Exception as e:  # 捕获具体异常，不是裸 except
        logging.exception("通知发送失败 user=%s", user.id)
        # 还可以：重试、进队列、抛自定义异常
```

`logging.exception` 会自动带上完整堆栈，这是排查问题的关键。

**如果要捕获所有异常，至少别吞 `KeyboardInterrupt`**：

```python
try:
    do_work()
except Exception:  # 不捕获 BaseException 子类（KeyboardInterrupt、SystemExit）
    handle_error()
```

`except Exception` 比 `except:` 好，因为它放过 `KeyboardInterrupt`——否则你 Ctrl+C 都停不掉程序。

## 自定义异常

标准库异常够用时就用标准的（`ValueError`、`FileNotFoundError`）。但当你的库/模块需要表达**领域特定的失败原因**时，自定义异常能让调用方精确区分。

```python
class InsufficientBalanceError(Exception):
    """余额不足"""

class OrderCancelledError(Exception):
    """订单已取消，无法继续操作"""
```

```python
def pay(order, amount):
    if order.status == "cancelled":
        raise OrderCancelledError(f"订单 {order.id} 已取消")
    if balance < amount:
        raise InsufficientBalanceError(
            f"余额不足：需要 {amount}，当前 {balance}"
        )
```

调用方：

```python
try:
    pay(order, 100)
except InsufficientBalanceError as e:
    show_message("余额不足，请充值")
except OrderCancelledError as e:
    show_message("该订单已取消")
```

**翻车现场：全用 Exception，调用方分不清**

```python
# WRONG
def pay(order, amount):
    if order.status == "cancelled":
        raise Exception("订单已取消")
    if balance < amount:
        raise Exception("余额不足")
```

调用方只能 `except Exception`，捕获到什么错都得用字符串判断——**用字符串当错误码是最脆弱的设计**，因为文案一改逻辑就坏。

## assert 不能用于参数校验

`assert` 是为**内部不变量**设计的，不是给用户的输入校验用的。

```python
def withdraw(account, amount):
    assert amount > 0, "金额必须为正"
    ...
```

**问题**：Python 可以用 `-O`（优化模式）启动，此时所有 `assert` 语句会被**删除**。

```bash
$ python -O main.py
# 所有 assert 语句不执行
```

**翻车现场：优化模式下参数校验失效**

```python
def divide(a, b):
    assert b != 0, "除数不能为 0"
    return a / b
```

```bash
$ python main.py
>>> divide(1, 0)
AssertionError: 除数不能为 0
$ python -O main.py
>>> divide(1, 0)
ZeroDivisionError: division by zero
```

**错误输出**：优化模式下 `assert` 被去掉，直接抛出 `ZeroDivisionError`——行为不一致。更糟的是生产环境如果用了优化模式，你的校验形同虚设。

**参数校验用 `if` + 抛异常**：

```python
def withdraw(account, amount):
    if amount <= 0:
        raise ValueError(f"金额必须为正，收到 {amount}")
    ...
```

`raise ValueError` 永远不会被优化掉。

**那 assert 用在哪？** 用在"按理说不可能发生"的内部检查：

```python
def _internal_sort(items):
    # 内部不变量：输入一定是列表
    assert isinstance(items, list)
    ...
```

如果这条 assert 触发了，说明**你自己的代码有 bug**，不是用户的问题。

## 小结

- 能处理才抓（重试、降级、提示），不能处理就让它往上冒
- 别用 `except: pass`，至少要记日志；用 `except Exception` 而非裸 `except`
- 领域特定错误用自定义异常，让调用方能精确区分
- `assert` 会被 `-O` 优化掉，参数校验用 `if` + `raise`
- `assert` 只用于内部不变量，触发说明你自己有 bug
