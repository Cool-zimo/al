# 函数设计：一个函数只做一件事

> 你打开一个 400 行的函数，里面又解析又校验又查数据库又发邮件还顺手写了日志。你想改"发邮件失败时的重试逻辑"，但不敢动，因为你怕牵一发动全身。函数设计的全部问题，都源于一个函数做了太多事。

## 一个函数只做一件事

这不是修辞，是可执行的标准：**如果你的函数描述里用了"并且""然后""同时"这样的连接词，它就做了不止一件事**。

```python
# WRONG：做了三件事
def process_order(order):
    # 1. 校验
    if order.amount <= 0:
        raise ValueError("金额非法")
    # 2. 写数据库
    db.insert(order)
    # 3. 发邮件
    smtp.send(f"订单 {order.id} 已创建")
```

拆开之后：

```python
def validate_order(order):
    if order.amount <= 0:
        raise ValueError("金额非法")

def save_order(order):
    db.insert(order)

def notify_order_created(order):
    smtp.send(f"订单 {order.id} 已创建")

def process_order(order):
    validate_order(order)
    save_order(order)
    notify_order_created(order)
```

顶层函数 `process_order` 现在读起来像一份流程清单——这正是好代码该有的样子。**每个函数只在一个抽象层级上工作**，不在一个函数里既写"校验金额"这种细节，又写"保存并通知"这种流程。

## 参数不要太多

参数列表是函数的接口。接口越宽，调用方越容易传错。

```python
# WRONG：7 个参数，调用时根本记不住顺序
def create_user(name, email, phone, age, city, country, is_admin):
    ...
```

**翻车现场：参数顺序传错，没报错但数据全错**

```python
# WRONG
create_user("张三", "zhangsan@qq.com", "13800138000", 25, "杭州", "中国", False)

# 三个月后加了新字段，调用方忘了更新
create_user("李四", "lisi@qq.com", "13900139000", 30, "北京", "中国", False)
# 其实李四该是管理员，但调用方漏传了
```

这种 bug 不报错，只是"数据悄悄错了"，比崩溃难查一百倍。

**解法：用数据结构打包参数**

```python
from dataclasses import dataclass

@dataclass
class UserSpec:
    name: str
    email: str
    phone: str
    age: int
    city: str
    country: str
    is_admin: bool = False

def create_user(spec: UserSpec):
    ...
```

现在调用是 `create_user(UserSpec(name="张三", email="...", ...))`——**每个参数都有名字**，漏传会报错，传错顺序也不怕。

经验法则：**参数超过 3~4 个就该考虑打包成对象**。不是硬性规定，但值得停下来想想"这些参数是不是同一个东西的不同属性"。

## 副作用要显式

**翻车现场：藏在深处的全局状态修改**

```python
# WRONG：函数名像纯函数，实际改了全局状态
_users_cache = {}

def get_user(user_id):
    if user_id in _users_cache:
        return _users_cache[user_id]
    user = db.fetch(user_id)
    _users_cache[user_id] = user  # 副作用藏在这里
    return user
```

调用方不知道它改了缓存。测试时同一个 `user_id` 第一次和第二次返回的结果一样（看起来正常），但缓存的累积效应在长流程里会引出诡异 bug。

**改进：让副作用显式化**

```python
def get_user(user_id, cache=None):
    if cache is not None and user_id in cache:
        return cache[user_id]
    user = db.fetch(user_id)
    if cache is not None:
        cache[user_id] = user
    return user
```

现在调用方**看见**了 cache 这个参数，就知道状态可能被改。更进一步：默认不传 cache，函数就是纯的；只有明确传入才启用缓存。这种"默认纯、按需有副作用"的设计很常见。

## 什么时候该拆

不是所有长函数都该拆。判断标准是**是否只有一个抽象层级**：

```python
def generate_report(orders):
    # 这些都是同一层级：流程步骤
    validated = [validate(o) for o in orders]
    summary = calculate_summary(validated)
    rendered = render_html(summary)
    send_email(rendered)
```

这个 `generate_report` 虽然四步，但每一步都是**调用一个函数**，抽象层级统一，不用拆。

反过来：

```python
def generate_report(orders):
    # 第一步：内联了 40 行校验逻辑
    for o in orders:
        if o.amount < 0:
            ...
        if not o.email:
            ...
        # 20 行各种校验
    # 第二步：内联了统计
    total = 0
    for o in orders:
        total += o.amount
        # 又 15 行统计
    # 第三步：内联了 HTML 拼接
    html = "<html>"
    for item in summary:
        html += f"<li>{item}</li>"
    # 又 30 行拼接
```

这种"同一个函数里混合了细节实现和流程控制"的就该拆。

## 小结

- 函数描述里出现"并且""然后"就该拆
- 顶层函数读起来应该像流程清单
- 参数超 3~4 个考虑打包成对象，避免顺序传错
- 副作用要显式：让调用方看得见状态变化
- 是否该拆的判断标准是"抽象层级是否统一"

- 把参数顺序记在注释里，调用时对照

answer: 1
explain: 相关参数打包成对象是标准解法：调用时每个字段都有名字，漏传、错序都能被检查出来。注释不可靠；全局变量会让依赖关系更隐蔽；拆成 7 个单参数函数反而把逻辑切碎了。
