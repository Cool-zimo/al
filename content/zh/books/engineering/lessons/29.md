# 部署与运维：从"本地能跑"到"线上在跑"

> "在我机器上能跑"是程序员最经典的笑话，也是最昂贵的一类故障。这一课讲本地和生产之间的真实差距：进程怎么管、怎么知道服务活着、出问题怎么回滚，以及一份**上线前必须过一遍的检查清单**。

## 本地能跑 vs 线上在跑，差了什么

本地跑一个脚本，是你在终端里手动敲命令、看着输出、出错了你当场处理。线上服务则完全不同：它**没人盯着、会自己崩、崩了要自己起来、还得能同时服务很多请求**。

| 维度 | 本地 | 线上 |
|---|---|---|
| 启动 | 手动敲命令 | 进程管理器自动拉起 |
| 崩溃 | 你看到报错 | 自动重启 + 告警 |
| 配置 | 写死在代码里 | 环境变量 / 配置中心 |
| 日志 | 终端输出 | 落盘 + 集中收集 |
| 健康检查 | 不用 | 必须，供负载均衡判断 |
| 回滚 | 手动 git checkout | 一键切回上一版本 |
| 资源 | 独占你的电脑 | 受限、要监控用量 |

**翻车现场：以为 `python app.py` 就是部署**

```bash
# WRONG：终端一关，服务就死
$ ssh server
$ python app.py
 * Running on http://0.0.0.0:8000
# 关掉 SSH 会话 → 进程收到 SIGHUP → 服务下线
```

```text
用户反馈：
网站打不开，但代码明明没改过
# 原因：会话结束，前台进程被杀
```

**正确做法**：用进程管理器（systemd、supervisor）或容器编排（Docker Compose、K8s）来托管进程，保证崩溃能重启、开机能自启。

## 进程管理：让服务自己站起来

最典型的两种场景：

**systemd（Linux 服务器首选）**

```ini
# /etc/systemd/system/myapp.service
[Unit]
Description=My Python App
After=network.target

[Service]
Type=simple
User=appuser
WorkingDirectory=/opt/myapp
EnvironmentFile=/opt/myapp/.env
ExecStart=/opt/myapp/.venv/bin/python -m myapp.cli
Restart=on-failure       # 崩了自动拉起
RestartSec=5
StandardOutput=append:/var/log/myapp/out.log
StandardError=append:/var/log/myapp/err.log

[Install]
WantedBy=multi-user.target
```

```bash
$ sudo systemctl daemon-reload
$ sudo systemctl enable --now myapp      # 开机自启 + 立即启动
$ sudo systemctl status myapp
$ sudo systemctl restart myapp           # 发布后重启
```

**容器方式（Docker Compose）**

```yaml
# docker-compose.yml
services:
  app:
    build: .
    restart: unless-stopped             # 退出就重启，除非手动停
    env_file: .env
    ports:
      - "8000:8000"
    healthcheck:
      test: ["CMD", "python", "-c", "import urllib.request; urllib.request.urlopen('http://localhost:8000/health')"]
      interval: 30s
      timeout: 3s
      retries: 3
```

**翻车现场：重启策略设错**

```yaml
# WRONG：总在失败的容器上无限重启
restart: always
# 应用配置错了，启动就崩 → 一秒崩一次、重启一万次
```

```text
系统日志：
myapp[12345]: ConfigurationError: missing DATABASE_URL
myapp[12346]: ConfigurationError: missing DATABASE_URL
myapp[12347]: ConfigurationError: missing DATABASE_URL
# 无限循环重启，CPU 飙高，日志爆炸
```

**教训**：`restart: on-failure` / `unless-stopped` 比 `always` 安全；配合 `RestartSec` 做退避，避免疯狂重启。

## 健康检查：让外部知道你还活着

健康检查是负载均衡器、编排系统判断"要不要给你流量"的依据。**它必须是一个独立的轻量端点**，不能和业务逻辑耦合——一个 `/health` 应该只检查进程本身能不能响应，顶多顺便探一下最关键依赖（如数据库）是否可达。

```python
from http.server import BaseHTTPRequestHandler, HTTPServer
import json

class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        if self.path == "/health":
            self.send_response(200)
            self.send_header("Content-Type", "application/json")
            self.end_headers()
            self.wfile.write(json.dumps({"status": "ok"}).encode())
        elif self.path == "/ready":
            # 就绪检查：连得上数据库才算就绪
            db_ok = check_db()
            code = 200 if db_ok else 503
            self.send_response(code)
            self.end_headers()
        else:
            self.send_response(404)
            self.end_headers()

def check_db():
    # 真实场景里测一次轻量查询，失败时返回 False
    return True

if __name__ == "__main__":
    HTTPServer(("0.0.0.0", 8000), Handler).serve_forever()
```

两种检查的分工：

| 端点 | 回答的问题 | 失败意味着 |
|---|---|---|
| `/health` | 进程在不在 | 进程死了，重启 |
| `/ready` | 能不能接流量 | 依赖没就绪，摘流量，别杀我 |

**翻车现场：把健康检查做成重查询**

```python
# WRONG：健康检查跑了一个全表 COUNT
def health():
    rows = db.query("SELECT COUNT(*) FROM huge_table")  # 30 秒
    return 200 if rows > 0 else 503
```

```text
负载均衡每 5 秒探一次 → 数据库被打满
# 健康检查本身变成了 DDoS 来源
```

**教训**：健康检查要**轻**，只探存活和关键依赖的可达性，不做任何重操作。

## 回滚预案：上线一定会出事，所以必须能退回

没有回滚方案的上线，本质是拿线上环境赌博。回滚要满足三个条件：**快、确定、可重复**。

**基于容器的回滚**（最简单可靠）：

```bash
# 发布新版本
$ docker build -t myapp:v1.2.0 .
$ docker tag myapp:v1.2.0 myapp:latest

# 出问题，立刻回退
$ docker tag myapp:v1.1.0 myapp:latest
$ docker compose up -d
# 从 1.2.0 回到 1.1.0，分钟级
```

**基于 systemd 的回滚**（配合版本目录）：

```bash
# WRONG：直接在线上目录改代码
$ ssh server "cd /opt/myapp && git pull"
# 一旦有问题，只能 git revert，且可能和新提交冲突
```

```bash
# RIGHT：维护一份 current 软链接，切换即回滚
$ ls /opt/myapp/
v1.1.0/  v1.2.0/  current -> v1.2.0

$ sudo systemctl stop myapp
$ ln -sfn /opt/myapp/v1.1.0 /opt/myapp/current
$ sudo systemctl start myapp
# 回滚完成
```

**翻车现场：回滚时才发现上一个版本没留**

```text
上线 v1.3.0 后发现数据错误
→ 想回滚
→ 但 v1.2.0 的镜像已经被 docker build 覆盖了
→ 只能现场修，线上故障持续 2 小时
```

**教训**：每个发布版本都要有**可追溯的构建产物**（打 tag 的镜像、归档的源码包）。回滚不是"重新拉一次代码"，而是"切回那个已经验证过的东西"。

## 上线前检查清单

这是本课的核心交付物，也是贯穿全章的"收官工具"雏形。**每次上线前逐条过一遍，少一条就别发**。

- [ ] **依赖锁定**：`requirements.txt` / `pyproject.lock` 已生成，版本固定
- [ ] **依赖审计**：`pip-audit` 通过，无已知高危漏洞
- [ ] **密钥不进库**：`.env`、密钥、token 已 gitignore，全部走环境变量或 KMS
- [ ] **配置外置**：所有环境相关配置通过环境变量 / 配置文件注入
- [ ] **测试通过**：`pytest` 全绿，关键路径有覆盖
- [ ] **CI 通过**：自动化检查（lint、测试、安全扫描）全绿
- [ ] **代码评审完成**：至少一人 review 并 approve
- [ ] **日志规范**：用 `logging` + 结构化格式，敏感信息已脱敏，带 request_id
- [ ] **健康检查就绪**：`/health` 和 `/ready` 端点可用
- [ ] **进程托管**：有 systemd / Compose / K8s 配置，`restart` 策略正确
- [ ] **监控告警**：日志收集、错误率、延迟、资源用量有监控和告警
- [ ] **回滚方案**：上一个版本的镜像/包已保留，回滚步骤已演练过
- [ ] **数据库迁移**：已备份，迁移脚本可正向/回滚，先在预发验证
- [ ] **文档同步**：README、CHANGELOG、运维手册已更新
- [ ] **灰度计划**：是否先小流量验证，再全量放开

**翻车现场：跳过清单赶发布**

```text
PM：今天必须发，清单下次再说
开发：（心虚地）行吧
→ 上线 20 分钟后：500 满屏
→ 排查：忘了配环境变量 DATABASE_URL
→ 回滚：上一个版本镜像没留
→ 总故障时长：3 小时 42 分
```

**教训**：清单看起来啰嗦，但它对抗的是"赶时间时的集体失忆"。**越紧急，越要按清单走**。

## 小结

- "本地能跑"到"线上在跑"的核心差距：进程要托管、崩溃要自启、配置要外置、健康要可探
- 进程用 systemd 或容器编排托管，重启策略选 `on-failure`/`unless-stopped`
- 健康检查分 `/health`（存活）和 `/ready`（就绪），都要轻量
- 回滚要快、确定、可重复，依赖保留每个版本的构建产物
- 上线前逐条过检查清单，这是对抗紧急场景下遗漏的最后一道防线

```quiz

q: 关于健康检查端点，正确的是？
options:
- /health 应该做一次全表 COUNT 来确保数据库数据完整
- /health 只探进程存活，/ready 探关键依赖是否就绪，都要轻量
- 健康检查越重越保险，能发现更多问题
- 有了监控就不需要健康检查了
answer: 1
explain: 健康检查要轻量；/health 探存活、/ready 探就绪，二者分工不同。重健康检查本身会成为负担。
```
