# 虚拟环境：给每个项目一个独立的小房间

> 你电脑上有三个项目，一个要用 Django 3，一个要用 Django 5，还有一个脚本是三年前写的、谁也不知道依赖什么版本。如果不隔离，它们迟早互相踩脚——虚拟环境就是给每个项目单独一间房，互不打扰。

## 为什么不能直接装到系统 Python

新手最常见的做法：`pip install requests`，然后能用，很开心。问题在半年后暴露。

系统 Python 是操作系统自己用的。Ubuntu 的 `apt`、macOS 的一些系统工具都依赖它。你往里装包、升级包，等于在别人的房子里挪家具。

**翻车现场：升级了系统 Python 的包，结果系统命令坏了**

```bash
# WRONG：直接往系统 Python 里装
$ sudo pip install --upgrade requests
$ sudo pip install -r requirements.txt
# 看起来一切正常
$ sudo apt update
Traceback (most recent call last):
  File "/usr/bin/apt", line 3, in <module>
    import apt_pkg
ModuleNotFoundError: No module named 'apt_pkg'
```

**错误输出**：系统自带的 `apt` 命令因为某个依赖被你升级到不兼容版本而崩溃。修复它要花一个小时，而这一个小时本不该存在。

更隐蔽的问题是**依赖冲突**。项目 A 需要 `requests==2.28`，项目 B 需要 `requests==2.31`。系统里只能有一个，装了 B 的版本，A 就可能在某个你没测过的代码路径上报错。

虚拟环境解决的就是这两件事：隔离项目、不动系统。

## venv 怎么建

Python 3.3+ 内置了 `venv` 模块，不需要额外安装。

```bash
# 在你的项目根目录下执行
$ python3 -m venv .venv
```

这会在当前目录创建一个 `.venv/` 文件夹，里面是一份独立的 Python 解释器副本和一套空的 `site-packages`。从此这个目录里 `python` 和 `pip` 都只认这个房间里的包。

不同系统的激活方式：

```bash
# macOS / Linux
$ source .venv/bin/activate

# Windows (cmd)
> .venv\Scripts\activate

# Windows (PowerShell)
> .venv\Scripts\Activate.ps1
```

激活后提示符前面会多一个 `(.venv)`：

```bash
(.venv) $ which python
/data/workspace/myproject/.venv/bin/python
```

## 为什么要激活

"激活"做的事其实很简单：把虚拟环境的 `bin/` 目录塞到 `PATH` 最前面。这样你敲 `python` 或 `pip` 时，shell 找到的是 `.venv/bin/python` 而不是系统的。

**翻车现场：忘了激活，装了一晚上包，第二天全没了**

```bash
$ cd myproject
$ pip install requests pandas numpy
Successfully installed requests-2.31.0 pandas-2.1.0 numpy-1.26.0
$ python -c "import requests; print(requests.__version__)"
2.31.0
# 第二天
$ cd myproject
$ python -c "import requests"
Traceback (most recent call last):
  ModuleNotFoundError: No module named 'requests'
```

**错误输出**：`ModuleNotFoundError`。因为昨天没激活，包装到了系统 Python 或者其他某个虚拟环境里。今天打开一个新终端，不在任何环境里，`requests` 自然找不到。

如果你实在不想激活，也可以用完整路径调用：

```bash
$ .venv/bin/pip install requests
$ .venv/bin/python main.py
```

效果一样，只是麻烦。激活就是为了省这几下键盘。

## .gitignore 该忽略什么

虚拟环境目录**绝对不能**提交到 Git。它有几百 MB，包含和你操作系统绑定的二进制文件，别人 clone 过去也用不了。

在项目根目录放一个 `.gitignore`：

```gitignore
# 虚拟环境
.venv/
venv/
env/

# Python 编译缓存
__pycache__/
*.pyc
*.pyo

# 敏感配置
.env
.env.local

# 编辑器
.vscode/
.idea/
```

**翻车现场：不小心把 .venv 提交上去了**

```bash
$ git add .
$ git status
On branch main
Changes to be committed:
  new file:   .venv/bin/python3.11
  new file:   .venv/lib/python3.11/site-packages/numpy/...
  ...（8000 多个文件）
```

**后果**：仓库体积从几百 KB 暴涨到几百 MB，clone 一次要五分钟，CI 跑一次也要下载全部。队友想打死你。

如果已经提交了，不是 `git rm` 一下就完事——文件还在 Git 历史里，仓库依然臃肿。要彻底清理需要用 `git filter-repo`，那是另一个故事了。

## 虚拟环境的生命周期

一个好习惯：**每个项目一个环境，环境从 requirements 重建**。

```bash
# 新机器上拿到项目，三步恢复环境
$ git clone <repo>
$ cd repo
$ python3 -m venv .venv
$ source .venv/bin/activate
(.venv) $ pip install -r requirements.txt
```

虚拟环境本身是**可丢弃的**。`.venv` 目录随时可以删掉重建，真正有价值的"环境说明书"是 `requirements.txt`（下一课讲）。所以 `.venv` 进 `.gitignore`，`requirements.txt` 必须进 Git——这个区分很重要。

## 小结

- 系统 Python 属于操作系统，别往里装项目依赖
- `python3 -m venv .venv` 建环境，`source .venv/bin/activate` 激活
- 激活的本质是改 `PATH`，忘了激活就会装错地方
- `.venv/`、`__pycache__/`、`.env` 都要进 `.gitignore`
- 环境可丢弃，依赖清单不可丢弃——这是核心原则

```quiz
type: choice
q: 你在新机器上 clone 了一个项目，想安装它的依赖。下面哪个做法是正确的？
options:
- 直接 `pip install -r requirements.txt`，不用管虚拟环境
- 先 `python3 -m venv .venv`，激活后 `pip install -r requirements.txt`
- 先 `sudo pip install -r requirements.txt`，装到系统 Python 更稳定
- 把项目文件夹拷到旧的 .venv 里复用
answer: 1
explain: 正确流程是建环境、激活、安装。直接装会污染系统 Python；sudo 装更危险；旧 .venv 里的二进制和路径都和当前机器不匹配，复用会出各种奇怪问题。
```
