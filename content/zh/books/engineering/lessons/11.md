# git 基本工作流：add / commit / push 三段式

> 你改了三个文件，想提交。"git add . 然后 git commit -m 'update' 然后 git push"——这能跑，但这是把 git 当网盘用。真正的工作流里，每次提交都是一个**有意义的节点**，能让人看懂你做了什么、能让你随时回退。

## 三段式：工作区 → 暂存区 → 仓库

git 有三个区域，理解它就不会再问"我改了怎么没提交上"：

```text
工作区（Working Directory）    你正在编辑的文件，磁盘上真实存在
        │  git add
        ▼
暂存区（Staging Area / Index）  你"打算"放进这次提交的东西
        │  git commit
        ▼
仓库（Repository / HEAD）       永久记录，有提交历史
        │  git push
        ▼
远程（Remote）                  GitHub / GitLab 上的版本
```

**翻车现场：git add . 把不该提交的东西全加进去了**

```bash
$ git status
On branch main
Changes not staged for commit:
        modified:   src/main.py
        modified:   src/config.py
Untracked files:
        .env
        __pycache__/main.cpython-311.pyc
        .venv/lib/python3.11/site-packages/numpy/...（几千个文件）

$ git add .
$ git status
# .env 和 .venv 全进暂存区了
```

**后果**：敏感配置和几百 MB 的虚拟环境被推到远程。`.gitignore` 配晚了，补救很痛苦。

**正确做法：精确 add，或者用交互式**

```bash
# 只加你改的业务文件
$ git add src/main.py src/config.py

# 或者交互式，逐个确认
$ git add -p
```

`git add -p`（-p 是 patch）会逐段问你"这块改动要加入暂存区吗"，粒度比文件还细——你在一个文件里改了两处，只想提交其中一处时特别有用。

## 提交粒度：一个提交一件事

**翻车现场：一个大杂烩提交**

```bash
$ git commit -m "update"
```

`git show` 出来 500 行 diff，改了登录逻辑、顺手格式化了三个文件、还修了测试、顺便改了 README 里的错别字。

三天后你想回退"登录逻辑的改动"，但它是和格式化、README 揉在同一个提交里的。你没法只回退登录部分——**提交粒度过粗，等于丧失了版本控制的价值**。

**好的提交**：一个提交只做一件事，且这个"一件事"在标题里能说清。

```bash
$ git log --oneline
a3f2c1e 修复：登录失败时密码框不保留输入内容
d7b8e91 重构：把校验逻辑从 views.py 抽到 validators.py
5c0a2b7 新增：支持手机号登录
```

每个标题都是一个**独立的、可回退的**改动单元。

## 怎么控制粒度：先把改动分成小块

实操方法：开一个新分支，一个小目标一个小提交。

```bash
$ git checkout -b feature/phone-login

# 第一步：加数据模型字段
$ git add models.py
$ git commit -m "新增 User.phone 字段"

# 第二步：加校验
$ git add validators.py
$ git commit -m "新增手机号格式校验"

# 第三步：接登录接口
$ git add api/auth.py
$ git commit -m "登录接口支持手机号"
```

三个提交，每个都能单独 review、单独回退。

**翻车现场：提交到一半发现还有个小改动**

```bash
$ git commit -m "重构：拆分校验模块"
# 提交完才发现 validators.py 里有个 typo
```

不要为此开个新提交 "fix typo"，可以用 `git commit --amend` 合并进上一个提交（只限**还没 push** 的提交）。已 push 的提交用 amend 会改写历史，需要 force push，队友会恨你。

## 常用工作流命令

```bash
# 看当前状态（最常打的四个字）
$ git status

# 看改了什么（工作区 vs 暂存区）
$ git diff

# 看暂存区 vs 上次提交（即将提交的改动）
$ git diff --staged

# 看提交历史
$ git log --oneline

# 放弃工作区的改动（危险，不可恢复）
$ git checkout -- src/main.py

# 放弃暂存（改动还在工作区）
$ git reset HEAD src/main.py

# 拉取远程更新并合并
$ git pull

# 推送到远程
$ git push
```

**翻车现场：没 pull 就 push，被拒绝**

```bash
$ git push
To github.com:you/repo.git
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'github.com:you/repo.git'
hint: Updates were rejected because the remote contains work that you do
hint: not have locally.
```

**错误输出**：push 被拒绝，因为远程有你本地没有的提交（比如同事刚推了一个）。解决：`git pull --rebase` 先把远程的拿下来，再把你的提交叠上去，然后 push。

## 小结

- git 三区：工作区 → 暂存区 → 仓库 → 远程
- 别用 `git add .` 一把抓，精确 add 或用 `git add -p`
- 一个提交只做一件事，粒度够细才能回退和 review
- 常用 git status / git diff / git log 掌握当前状态
- 推送前先 pull，冲突了先 rebase 再 push

```quiz
options:
- git add . 然后 commit，两个一起交
- git add login.py 然后 commit，utils.py 的改动留在工作区
- git commit 不带 add，git 会自动找到改动
- 先 git stash 全部，再提交 login.py
answer: 1
explain: git add 后面跟具体文件名，只有这个文件进暂存区，其余改动留在工作区，下次再提交。git add . 会两个一起加；git commit 不带 add 只提交已暂存的内容（这里是空的）。
```
