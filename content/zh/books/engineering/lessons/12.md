# 写好的提交信息：fix 不算信息

> 半年后你要在 5000 个提交里找"那次改了登录超时的提交"。你搜 `git log --grep="fix"`，命中 800 条。提交信息是给未来的你建的索引，`fix` 不是索引。

## 为什么 "fix" 这种不算

`git log` 是项目的**行为记录**。好的提交信息让你在不看 diff 的情况下就知道项目发生了什么。

```bash
$ git log --oneline
f3a1b2c fix
e8d7c6b update
a9b8c7d 改了点东西
d2e3f4a fix bug
```

这四条信息提供了**零信息量**。你只知道"改过"，不知道改了什么、为什么改、影响哪里。

**翻车现场：靠提交信息排查线上问题**

```bash
$ git log --oneline --since="2024-01-01" | grep -i fix
a1b2c3d fix
d4e5f6g fix login
h7i8j9k fix bug
```

线上出问题时，运维要靠提交历史判断"哪个版本引入了问题"。全是 `fix` 的历史等于没有历史，只能逐个版本回退试。

## Conventional Commits 简介

[Conventional Commits](https://www.conventionalcommits.org/) 是一套轻量约定，格式：

```text
<类型>(<作用域>): <主题>

<正文>

<脚注>
```

**类型（type）**是这套规范的核心：

| 类型 | 含义 |
|---|---|
| `feat` | 新功能 |
| `fix` | 修 bug |
| `docs` | 只改文档 |
| `style` | 格式化、缺分号等（不改逻辑） |
| `refactor` | 重构（既不修 bug 也不加功能） |
| `perf` | 性能优化 |
| `test` | 加测试或改测试 |
| `chore` | 构建、依赖、工具链等杂项 |
| `build` | 构建系统或外部依赖变更 |

**好例子**：

```text
feat(auth): 支持手机号验证码登录

在登录页新增手机号+验证码入口，沿用现有的 session 管理逻辑。
验证码有效期 5 分钟，连续失败 5 次锁定 15 分钟。

Closes #123
```

```text
fix(payment): 修复超时时间过短导致的偶发失败

原 3 秒超时在高并发下经常触发，调至 10 秒并加上指数退避重试。
```

```text
refactor(utils): 把日期格式化函数抽到独立模块

不涉及逻辑变更，仅移动代码位置。
```

**格式要点**：

- 主题行不超过 72 字符（终端里 `git log --oneline` 能完整显示）
- 主题用祈使句（"新增"而非"新增了"，"修复"而非"修复了"）
- 正文解释 **why**（为什么这么改），不是 what（diff 已经告诉你 what）
- 正文和主题之间空一行

**翻车现场：主题行写成小说**

```text
fix: 我改了一下那个之前张三说的登录的时候有时候会失败的问题，
后来发现是超时时间设得太短了，我在本地测了好多次，
然后问了李四，他觉得 10 秒比较合适，所以改成了 10 秒，
另外我还顺手改了……
```

主题行 200 字，正文是流水账。看 `git log --oneline` 的人什么都看不到（被截断了），看正文的人被噪音淹没。

## 范围（scope）的价值

`feat(auth)` 里的 `auth` 是作用域，告诉你改动在哪个模块。这在多模块项目里是极有价值的筛选维度：

```bash
$ git log --oneline | grep "payment"
$ git log --oneline --grep="payment"
```

不用 scope 的话，只能靠关键词猜。加了 scope，筛选是确定性的。

## 小结

- `fix` 之类的信息等于零信息量，无法检索、无法定位
- Conventional Commits：`type(scope): subject` + 正文
- 类型表达意图（feat/fix/refactor/docs/...）
- 主题行用祈使句、不超 72 字符
- 正文讲 why，不讲 what（diff 已经是 what）
- scope 是模块名，是可靠的筛选维度

## 随堂练习

```quiz
type: choice
q: 下面哪个提交信息最符合 Conventional Commits 规范？
options:
- fix: 我修了一下那个登录的问题
- fix(auth): 登录失败时密码框不保留输入内容
- update: 更新了一些东西
- feat: 新增功能
answer: 1
explain: "fix(auth): 登录失败时密码框不保留输入内容" 类型明确（fix）、scope 准确（auth）、主题清晰讲清改了什么。其他几个要么没有 scope，要么主题模糊。
```

## 本节测验

```quiz
type: choice
exam: true
q: 关于提交信息正文该写什么，正确的是？
options:
- 正文应该逐行描述改了哪些代码，和 diff 对应
- 正文应该解释为什么这么改（背景、动机、取舍），而不是重复 diff 的内容
- 正文越长越好，写得越详细越专业
- 提交信息只需要标题，正文没必要写
answer: 1
explain: 正文的价值在于记录 diff 无法体现的"为什么"——当时的背景、决策依据、权衡。重复描述代码改动（what）是冗余的，因为 git show 已经能看到。
```
