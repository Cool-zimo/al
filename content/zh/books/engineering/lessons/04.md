# 项目目录结构：让新人 30 秒看懂你的项目

> 你打开一个开源项目，根目录里 `main.py`、`utils.py`、`test_main.py`、`data.csv`、`config.ini` 全摊在一起。你想改个功能，不知道从哪下手。好的目录结构本身就是一份导航图。

## src 布局 vs 扁平布局

**扁平布局**（flat layout）：所有代码文件平铺在根目录。

```text
myproject/
├── main.py
├── utils.py
├── models.py
├── config.py
├── tests/
│   └── test_main.py
├── requirements.txt
└── README.md
```

**src 布局**：源代码统一放进一个 `src/` 目录。

```text
myproject/
├── src/
│   └── myproject/
│       ├── __init__.py
│       ├── main.py
│       ├── utils.py
│       └── models.py
├── tests/
│   └── test_main.py
├── pyproject.toml
└── README.md
```

**区别不是好看不好看，是测试行为不一样**。

扁平布局下，`tests/` 和源码在同一级，你跑测试时 Python 从根目录启动，直接 `import main` 就能导入。问题来了：**测试测的是你磁盘上的源码，而不是"安装后的包"**。如果你漏了某个文件没装进包里，测试照样能过，因为测试根本没走安装路径。

src 布局强制你**先把包装好**（pip install -e .），测试导入的是安装的版本。这样本地测试和实际使用走的是同一条路径，漏装文件会在测试阶段就暴露。

## 为什么要有 tests/ 和 README

**tests/ 存在的意义**不只是"放测试文件"。它传达一个信号：这个项目有测试，且测试和被测试代码是分开的。

```text
tests/
├── __init__.py
├── test_user.py
├── test_order.py
└── conftest.py
```

按模块对应命名（`test_xxx.py` 测 `xxx.py`），一目了然。测试文件放在 `tests/` 里，导入时用 `from myproject import user`，和用户的导入方式完全一致——这也是为什么 src 布局更严谨。

**README** 是项目的门面。至少写清三件事：

1. 这个项目做什么（一句话）
2. 怎么装、怎么跑
3. 怎么测试

```markdown
# 订单处理服务

把 CSV 订单批量导入数据库，支持去重和格式校验。

## 安装

    python3 -m venv .venv
    source .venv/bin/activate
    pip install -r requirements.txt

## 运行

    python -m order_service --input orders.csv

## 测试

    pytest
```

**翻车现场：没有 README，新人花两天才跑起来**

```text
myproject/
├── app.py
├── config_dev.ini
├── config_prod.ini
└── run.sh
```

新人 clone 下来，不知道要装什么、用哪个配置文件、`./run.sh` 要不要先给权限。于是发消息问你，你不在，他又去翻代码，最后猜了一个配置跑起来——结果连的是生产库。

## 可编辑安装 pip install -e

开发时你改了代码，希望立刻生效，又希望测试能像用户那样导入。可编辑安装就是干这个的。

```bash
# 在项目根目录（有 pyproject.toml 的地方）
$ pip install -e .
```

`-e` 是 editable（可编辑）的意思。它不拷贝代码，而是在环境里创建一个指向你源码目录的链接。从此：

```python
# 不管你在哪个目录，都能这样导入
from myproject import utils

# 改了 utils.py 立刻生效，不用重新安装
```

这解决了扁平布局的经典问题——**循环导入陷阱**：

```text
# WRONG：扁平布局 + 直接跑脚本
myproject/
├── main.py        # from utils import helper
└── utils.py       # def helper(): ...

$ cd myproject
$ python main.py   # 能跑

$ cd ..
$ python -m myproject.main
ModuleNotFoundError: No module named 'myproject'
```

可编辑安装后，不管从哪启动，`myproject` 都是一个正规的包，导入路径统一。

## 一个推荐的完整结构

```text
myproject/
├── src/
│   └── myproject/
│       ├── __init__.py
│       ├── main.py
│       ├── api/
│       │   ├── __init__.py
│       │   └── client.py
│       └── core/
│           ├── __init__.py
│           └── engine.py
├── tests/
│   ├── __init__.py
│   ├── conftest.py
│   └── test_engine.py
├── docs/
│   └── design.md
├── .gitignore
├── pyproject.toml
├── README.md
└── LICENSE
```

子包按职责分层（`api/`、`core/`），测试镜像源码结构，文档独立成目录。

## 小结

- src 布局强制走安装路径，让本地测试和实际使用一致
- 扁平布局简单但容易掩盖"漏装文件"这类问题
- tests/ 按模块对应命名，和被测代码分离
- README 至少写清：做什么、怎么装、怎么跑、怎么测
- `pip install -e .` 让开发态和安装态的导入路径统一

## 随堂练习

```quiz
type: choice
q: 你刚接手一个扁平布局的老项目，根目录里 main.py 直接 `import utils`。你打算加测试。下面哪种做法最合理？
options:
- 直接建 tests/ 测试，反正能跑就行
- 改成 src 布局并做可编辑安装，让测试和用户的导入方式一致
- 把所有 import 都改成相对导入
- 把测试文件放到和源码同一个目录
answer: 1
explain: src 布局 + 可编辑安装能保证测试走的是安装路径，和用户实际使用情况一致，是更严谨的长期方案。直接建 tests 能跑但不严谨；相对导入在包内可行但解决不了测试路径问题。
```
