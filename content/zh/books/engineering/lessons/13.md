# 分支策略：为什么不能直接在 main 上改

> 你直接在 main 上改代码，推上去，CI 挂了，同事拉到一半的代码跑不起来。更糟的是，你改到一半发现思路不对，想撤销——但 main 的历史已经被你污染了。分支存在的意义就是：**把"进行中的工作"和"能用的版本"隔离开**。

## 为什么不能直接在 main 上改

`main`（或 `master`）应该始终是可用的、可部署的状态。这是团队的约定，也是自动化流程的假设。

```bash
$ git checkout main
$ vim login.py
$ git commit -am "改登录"
$ git push
```

**翻车现场：main 上改到一半，紧急 bug 来了**

```bash
$ git checkout main
$ vim login.py
# 改到一半，登录模块处于半工作状态
$ git status
modified:   login.py
# 突然线上报 bug，要立刻修
$ git checkout -b hotfix/urgent
error: Your local changes to the following files would be lost:
        login.py
```

**错误输出**：因为工作区有未提交的改动，切分支会被拦。你被迫先 commit 一个"半成品"到 main，或者 stash。无论哪种，main 都被污染了。

**正确做法：从 main 开出 feature 分支再改**

```bash
$ git checkout main
$ git pull
$ git checkout -b feature/phone-login
# 在这里随便改，改到一半也没关系
$ git commit -am "WIP: 登录重构进行中"
```

你的半成品在 `feature/phone-login` 上，main 始终是干净的。紧急 bug 来了，直接切回 main 开 hotfix 分支。

## feature 分支工作流

标准流程：

```bash
# 1. 确保 main 是最新
$ git checkout main
$ git pull

# 2. 开分支
$ git checkout -b feature/order-export

# 3. 在分支上开发、提交
$ git add src/export.py
$ git commit -m "feat(export): 支持导出 CSV"
$ git add tests/test_export.py
$ git commit -m "test(export): 覆盖 CSV 导出边界情况"

# 4. 推到远程（第一次需要 -u）
$ git push -u origin feature/order-export

# 5. 在 GitHub / GitLab 上发 Pull Request / Merge Request

# 6. 评审通过后合并，然后删分支
$ git checkout main
$ git pull
$ git branch -d feature/order-export
```

分支名建议带**前缀和用途**：`feature/xxx`、`fix/xxx`、`hotfix/xxx`、`refactor/xxx`，和提交类型对应。

## 合并 vs rebase

两种把分支整合进 main 的方式。

**merge（合并）**：保留分支历史，生成一个合并提交。

```bash
$ git checkout main
$ git merge feature/order-export
```

结果：

```text
*   a1b2c3d Merge branch 'feature/order-export'  ← 合并提交
|\
| * d4e5f6g feat: 加 CSV 导出
| * e7f8g9h feat: 加导出按钮
* | f1a2b3c fix: 修分页 bug
|/
* g4h5i6j feat: 分页功能
```

历史**忠实地反映了开发过程**，但分叉多的时候看起来像意大利面。

**rebase（变基）**：把你的分支提交"搬"到 main 的最新位置，形成直线。

```bash
$ git checkout feature/order-export
$ git rebase main
```

结果：

```text
* e7f8g9h feat: 加导出按钮
* d4e5f6g feat: 加 CSV 导出
* f1a2b3c fix: 修分页 bug
* g4h5i6j feat: 分页功能
```

历史是**一条直线**，没有合并节点，看起来更干净。

**什么时候用哪个**：

| 场景 | 推荐 |
|---|---|
| 本地分支还没推过 | rebase（整理历史） |
| 分支已推到远程，且别人也在上面工作 | merge（rebase 会改写历史，队友会冲突） |
| 想保留完整的开发分叉过程 | merge |
| 想保持主线线性 | rebase |

**翻车现场：对已推送的分支做 rebase**

```bash
$ git push origin feature/x
# 同事拉了这个分支开始工作
$ git rebase main
$ git push
# 被拒绝：历史不一致
$ git push --force
# 同事再 pull，历史乱了
```

**后果**：你改写了公共分支的历史，同事的本地分支基于旧历史，pull 会产生大量冲突，严重的需要 `git reflog` 救援。

**规则：已经推给别人的分支，只 merge 不 rebase。只有你自己本地的、还没 push 的提交才 rebase。**

## 小结

- main 必须始终是可用的、可部署的状态
- 所有改动在 feature/fix/hotfix 分支上进行
- 分支工作流：开分支 → 开发 → push → PR → 合并 → 删分支
- 未推送的提交用 rebase 整理，已推送的用 merge
- 永远不要对公共分支做 force push + rebase

## 随堂练习

```quiz
type: choice
q: 你在 feature/login 分支上做了 3 个提交，还没推送到远程。你想把这 3 个提交整理成 1 个干净的提交再推。正确做法是？
options:
- git merge main，保留 3 个提交
- git rebase -i HEAD~3，把 3 个提交合并成一个
- 直接 push，提交数量无所谓
- 删掉分支重新来
answer: 1
explain: 交互式 rebase（git rebase -i HEAD~3）可以让你把多个提交合并（squash）成一个。因为还没推送，改写历史是安全的。merge 不会减少提交数；直接 push 会把 3 个提交都推上去。
```
