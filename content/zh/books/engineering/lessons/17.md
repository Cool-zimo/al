# pytest 实战：fixture、参数化与测试隔离

> 你写了 50 个测试，每个都复制一遍"建数据库、插测试数据、删数据库"的代码。后来数据库 schema 改了，你改了 50 遍。fixture 就是用来消除这种重复的。而"测试之间互相污染"是新手最容易踩的坑。

## fixture：把准备和清理交给 pytest

`fixture` 是 pytest 的依赖注入机制。测试函数把 fixture 名写进参数，pytest 自动调用它并传入结果。

```python
import pytest

@pytest.fixture
def sample_users():
    # setup：准备测试数据
    return [
        {"id": 1, "name": "张三", "age": 28},
        {"id": 2, "name": "李四", "age": 17},
        {"id": 3, "name": "王五", "age": 35},
    ]

def test_filter_adults(sample_users):
    adults = [u for u in sample_users if u["age"] >= 18]
    assert len(adults) == 2

def test_find_by_name(sample_users):
    result = [u for u in sample_users if u["name"] == "张三"]
    assert result[0]["id"] == 1
```

`sample_users` 不用在每个测试里手写一遍，pytest 自动注入。测试函数只关心"我要什么数据"，不关心"数据怎么来"。

**fixture 的作用域（scope）**：默认每个测试函数重新执行一次（`function`）。还有 `module`（每个模块一次）、`session`（整个测试会话一次）。数据库连接这种重资源适合用 `session` 级，避免反复连接。

```python
@pytest.fixture(scope="session")
def db_connection():
    conn = create_connection("sqlite:///:memory:")
    yield conn          # 测试用这个 conn
    conn.close()        # 所有测试跑完后执行清理
```

`yield` 之前的代码是 setup，之后的代码是 teardown。这是 pytest fixture 处理"清理"的标准写法。

## 参数化：一份逻辑，多组输入

同一个函数要测 10 组输入输出，最蠢的写法是复制 10 遍测试函数。`@pytest.mark.parametrize` 用一组数据生成多个测试用例。

```python
import pytest

def parse_age(text):
    """把输入转成年龄整数，非法返回 None"""
    if not text or not str(text).strip():
        return None
    try:
        n = int(str(text).strip())
    except ValueError:
        return None
    return n if n >= 0 else None

@pytest.mark.parametrize("text,expected", [
    ("18", 18),
    ("  25  ", 25),
    ("0", 0),
    ("", None),
    ("  ", None),
    ("abc", None),
    ("-3", None),
    ("18.5", None),
])
def test_parse_age(text, expected):
    assert parse_age(text) == expected
```

运行后你会看到 8 个独立用例，每个都单独通过或失败，哪组输入挂了一目了然。

```text
$ pytest tests/test_parser.py -v
tests/test_parser.py::test_parse_age[18-18] PASSED
tests/test_parser.py::test_parse_age[abc-None] PASSED
...
```

## conftest.py：共享 fixture

当多个测试模块都要用同一个 fixture 时，不要复制粘贴。在项目根或某个目录下建 `conftest.py`，里面的 fixture 对该目录及其子目录的所有测试自动可见。

```python
# tests/conftest.py
import pytest

@pytest.fixture
def tmp_log_dir(tmp_path):
    log_dir = tmp_path / "logs"
    log_dir.mkdir()
    return log_dir

@pytest.fixture(scope="module")
def app_config():
    return {"debug": True, "max_retries": 3, "timeout": 30}
```

```python
# tests/test_logger.py
def test_log_writes_file(tmp_log_dir):        # tmp_log_dir 来自 conftest.py
    log_file = tmp_log_dir / "app.log"
    log_file.write_text("hello")
    assert log_file.read_text() == "hello"
```

**规则：`conftest.py` 里不要写测试，只放 fixture 和钩子。** 测试文件要能单独 `pytest tests/test_xxx.py` 跑通，fixture 自动被找到。

## 测试之间必须互相隔离

这是新手最容易踩的坑。**每个测试都应该能独立运行，且能按任意顺序运行。**

**翻车现场：测试 A 污染了测试 B**

```python
# WRONG
cart = []

def test_add_item():
    cart.append("apple")
    assert len(cart) == 1

def test_cart_starts_empty():
    assert cart == []      # 如果先跑了 test_add_item，这里就挂了
```

```text
$ pytest tests/test_cart.py::test_cart_starts_empty
>       assert cart == []
E       AssertionError: assert ['apple'] == []
```

**错误原因**：`cart` 是模块级全局变量，一个测试对它的修改会留给下一个测试。pytest 默认不保证测试执行顺序。

**正确做法：用 fixture 每次重建**

```python
@pytest.fixture
def cart():
    return []              # 每个测试拿到一个全新的空列表

def test_add_item(cart):
    cart.append("apple")
    assert len(cart) == 1

def test_cart_starts_empty(cart):
    assert cart == []       # 永远通过
```

**翻车现场：测试靠数据库"残留数据"通过**

```python
# WRONG
def test_create_user(db):
    create_user(db, "alice")       # 插入 alice
    assert count_users(db) == 1

def test_user_unique(db):
    create_user(db, "alice")       # 依赖上一条没被清理
    create_user(db, "alice")       # 期望唯一约束报错
```

第一个测试先跑时，alice 已存在，第二个测试抛的是"重复用户"而不是预期的"唯一约束"。换个顺序两个都挂。

**正确做法：用 fixture 的 teardown 清理，或者每个测试用独立事务**

```python
@pytest.fixture
def clean_db(db_connection):
    yield db_connection
    # teardown：删掉本测试产生的数据
    db_connection.execute("DELETE FROM users WHERE name = 'alice'")
```

**三条隔离铁律**：

1. 不在模块/类级别放可变状态（列表、字典、计数器）
2. 共享资源通过 fixture 注入，fixture 负责每次重建或清理
3. 跑 `pytest -p no:randomly` 之外，更要默认测试顺序无关

## 小结

- fixture 是 pytest 的依赖注入，`@pytest.fixture` 装饰，测试函数写参数名即可用
- `yield` 前后分别是 setup 和 teardown，适合管理资源生命周期
- 用 `scope` 控制 fixture 频率：`function`（默认）/ `module` / `session`
- `@pytest.mark.parametrize` 一份逻辑测多组输入，失败定位精准
- `conftest.py` 放共享 fixture，让多个模块复用，且不必 import
- 测试必须互相隔离：不共享可变全局状态，用 fixture 重建和清理

## 随堂练习

```quiz
type: choice
q: 你想让一组测试共用同一个昂贵的数据库连接，但又不希望连接在每次测试后都关闭重连。正确的 fixture 写法是？
options:
- @pytest.fixture 默认即可，pytest 会自动复用
- @pytest.fixture(scope="session")，并在 yield 之后关闭连接
- 把连接写成模块级全局变量，手动管理
- @pytest.fixture(scope="function") 并在 yield 前关闭
answer: 1
explain: scope="session" 让 fixture 在整个测试会话中只执行一次，避免反复连接；用 yield 写法可以在所有测试跑完后执行关闭动作。默认 scope 是 function，每次测试都会重连。
```

## 本节测验

```quiz
type: choice
exam: true
q: 下面哪种情况最可能导致"单独跑测试 A 通过、单独跑测试 B 通过，但一起跑就失败"？
options:
- 测试 A 和 B 都用了 fixture，但 fixture 的 scope 设成了 session
- 测试 A 修改了某个模块级全局列表，测试 B 假设该列表是空的
- 测试 A 和 B 都用了 parametrize
- 测试 A 和 B 分别在两个不同文件里
answer: 1
explain: 模块级全局可变状态会被一个测试修改并遗留给下一个测试，破坏隔离。fixture 的 scope=session 是有意设计的共享，不会导致随机失败；parametrize 和文件位置都不破坏隔离。
```

```quiz
type: function
exam: true
q: 实现一个函数 build_cart_fixture(initial_items)，模拟"每次调用都返回一份全新购物车"的隔离逻辑。规则：initial_items 是初始商品列表（可能为 None，视为空列表）。返回一个新的列表，包含 initial_items 的所有元素。关键点：返回的列表必须是新对象，不能和传入的列表是同一个引用，这样多个"测试"各自修改不会互相污染。提示：判断标准是返回的列表与传入列表不是同一个对象（用 is 判断）。
func: build_cart_fixture
starter: |
  def build_cart_fixture(initial_items):
      # 在这里补全
      return None
cases: |
  (["apple", "banana"], ["apple", "banana"]) -> ["apple", "banana"]
  ([], []) -> []
  (None, []) -> []
hint: 用 list() 或切片 [:] 复制一份新列表；对 None 要先转成空列表。用 (build_cart_fixture(x) is x) 应该为 False 才说明是新对象。
explain: 测试隔离的本质就是"每次拿到独立的状态"，这个函数模拟 fixture 每次重建的逻辑。
```
