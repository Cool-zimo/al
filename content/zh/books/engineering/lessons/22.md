# 打包与发布：从源码到能 `pip install` 的包

> 你的项目写好了，同事说"发给我用用"。你把整个目录压缩发过去，对方解压、手动配路径、import 报错。这就是没打包。打包就是把项目变成标准的、可分发的形式，让任何人一条 `pip install` 就能装上。

## 构建产物：sdist 和 wheel

Python 打包有两种产物：

| 产物 | 是什么 | 特点 |
|---|---|---|
| `sdist`（源码分发包） | 源码 + 构建脚本的压缩包（.tar.gz） | 需要用户本地有编译环境，安装慢 |
| `wheel`（轮子，.whl） | 预构建好的二进制包 | 安装即解压，不需编译，快 |

**优先发 wheel。** wheel 安装速度可以快一个数量级，且不需要用户装 C 编译器。sdist 作为源码备份一般也会同时上传。

```bash
# 用 build 工具同时构建两种
$ pip install build
$ python -m build
# 生成：
#   dist/yourpkg-0.1.0.tar.gz      (sdist)
#   dist/yourpkg-0.1.0-py3-none-any.whl   (wheel)
```

## pyproject.toml 的构建配置

`pyproject.toml` 是 PEP 518/621 规定的项目配置入口。构建相关的信息写在这里：

```toml
[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[project]
name = "mypackage"
version = "0.1.0"
description = "一个示例工具包"
readme = "README.md"
requires-python = ">=3.10"
license = {text = "MIT"}
authors = [{name = "张三", email = "zs@example.com"}]
keywords = ["demo", "tool"]
classifiers = [
    "Programming Language :: Python :: 3",
    "License :: OSI Approved :: MIT License",
    "Operating System :: OS Independent",
]

dependencies = [
    "requests>=2.28",
    "rich>=13.0",
]

[project.optional-dependencies]
dev = ["pytest>=8.0", "ruff"]

[project.scripts]
mypkg-cli = "mypackage.cli:main"

[tool.hatch.build.targets.wheel]
packages = ["src/mypackage"]
```

**关键字段解释**：

- `[build-system]`：声明用哪个构建后端（`hatchling`、`setuptools`、`flit` 都行）及其依赖
- `[project]`：项目元信息，PyPI 页面上显示的正是这里的内容
- `dependencies`：运行时依赖，用户装你的包时自动安装
- `[project.optional-dependencies]`：可选依赖组，`pip install mypackage[dev]` 才装
- `[project.scripts]`：生成命令行入口，`pip install` 后可直接执行 `mypkg-cli`
- `[tool.hatch.build.targets.wheel]`：告诉后端哪些目录要打包进去

**翻车现场：忘记声明依赖**

```toml
# WRONG：pyproject.toml 里没写 dependencies
[project]
name = "mypackage"
version = "0.1.0"

# 安装后
$ mypkg-cli
ModuleNotFoundError: No module named 'requests'
```

```text
用户装了你的包，但 requests 没被装上。
因为 dependencies 没声明，pip 不知道要装它。
```

**正确做法：把所有运行时依赖写进 `dependencies`**，开发期用的（pytest、ruff）放 `[project.optional-dependencies]` 的 `dev` 组。

## 发布到 PyPI 的流程

**第 1 步：注册账号**

去 [TestPyPI](https://test.pypi.org) 和 [PyPI](https://pypi.org) 注册账号，生成 API token（别用密码，token 可撤销）。

**第 2 步：本地构建**

```bash
$ rm -rf dist/ build/
$ python -m build
$ ls dist/
mypackage-0.1.0.tar.gz  mypackage-0.1.0-py3-none-any.whl
```

**第 3 步：检查产物**

```bash
$ pip install twine
$ twine check dist/*     # 检查 README、元信息是否合规
$ python -m pip install dist/*.whl   # 本地装一遍验证能不能用
```

**第 4 步：先发到 TestPyPI 试水**

```bash
$ twine upload --repository testpypi dist/*
# 用 TestPyPI 的 token
# 然后去 https://test.pypi.org 看页面、试着装一下
$ pip install --index-url https://test.pypi.org/simple/ mypackage
```

**第 5 步：正式发布到 PyPI**

```bash
$ twine upload dist/*    # 用正式 PyPI 的 token
# 完成，全世界都能 pip install 了
```

**翻车现场：token 泄露**

```text
# 把 token 写进 CI 配置文件的明文里然后 push
$ git push
> token 出现在 commit 历史中，被爬虫抓取，攻击者发布了恶意版本
```

**正确做法：token 只放 GitHub Secrets / CI 的加密变量**，用 `${{ secrets.PYPI_TOKEN }}` 注入，永不出现在文件里。

**翻车现场：重复发布同一版本**

```bash
$ twine upload dist/*
403 Client Error: File already exists.
```

PyPI **不允许覆盖已发布的版本**。一旦 `0.1.0` 发出去，就只能发 `0.1.1`。所以在上传前务必本地验证，避免"为了修一个小错被迫升版本"。

## 现代简化流程：一键发布

很多项目用 GitHub Actions 在打 tag 时自动构建并发布：

```yaml
name: Publish
on:
  push:
    tags: ["v*"]
jobs:
  publish:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install build twine
      - run: python -m build
      - run: twine upload dist/*
        env:
          TWINE_USERNAME: __token__
          TWINE_PASSWORD: ${{ secrets.PYPI_TOKEN }}
```

打一个 `v0.1.0` 的 tag 推送，发布自动完成。

## 小结

- 两种产物：sdist（源码包）和 wheel（预构建包），优先发 wheel
- `python -m build` 同时构建两种产物
- `pyproject.toml` 声明元信息、依赖、入口；运行时依赖写 `dependencies`
- 发布流程：构建 → twine check → TestPyPI 试水 → 正式 PyPI
- PyPI 不允许覆盖版本，发前务必本地验证
- token 只放 CI Secrets，绝不进仓库历史

```quiz
type: choice
q: 你第一次发布包，想确认 README 和元信息在 PyPI 页面上显示正常、wheel 能被正确安装。推荐的试水方式是？
options:
- 直接发到正式 PyPI，反正可以随时删掉重发
- 先用 twine 上传到 TestPyPI 试装一遍，确认无误后再发正式 PyPI
- 把包发给几个同事手动安装测试
- 在 GitHub 上建个 release 就足够了
answer: 1
explain: TestPyPI 是官方提供的隔离测试仓库，用来模拟正式发布流程。PyPI 不允许覆盖已发布的版本，一旦发错只能升号，所以试水是必要步骤。
```
