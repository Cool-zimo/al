# 日志与可观测性：线上出问题，你靠什么知道

> 本地开发可以随便 print，线上不行。生产环境的 bug 转瞬即逝，你需要的是**可检索、可追溯、能串联一条请求**的日志记录。这一课讲清楚日志该怎么记、记什么，以及**什么绝对不能记**。

## 为什么 print 不够用

`print` 是开发时的好帮手，但上到生产就暴露出三大缺陷：

1. **没有级别**——分不清这是调试信息还是致命错误，全混在一起
2. **没有上下文**——只知道"出错了"，但哪次请求、哪个用户、什么参数？全不知道
3. **不可检索**——日志量大了以后，靠肉眼翻文本等于没记

生产环境出问题，你的排查路径是：**告警 → 定位服务 → 按时间/请求 ID 过滤日志 → 还原现场**。这条路每一步都依赖结构化、带上下文的日志。

Python 标准库自带 `logging` 模块，够用了，不需要额外装东西：

```python
import logging

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s [%(levelname)s] %(name)s: %(message)s",
)
logger = logging.getLogger(__name__)

logger.debug("调试信息，生产环境默认不显示")
logger.info("服务启动完成")
logger.warning("配置文件缺失，使用默认值")
logger.error("数据库连接失败: %s", err)
```

## 结构化日志：机器可读才有用

"一行纯文本"人眼看着舒服，但机器不好解析。结构化日志（典型是 JSON 格式一行一条）的好处是：**能用工具按字段过滤、聚合、统计**。

```python
import json, logging

class JsonFormatter(logging.Formatter):
    def format(self, record):
        payload = {
            "ts": self.formatTime(record),
            "level": record.levelname,
            "logger": record.name,
            "msg": record.getMessage(),
        }
        # 把额外字段（如 user_id、request_id）也带上
        for k, v in record.__dict__.items():
            if k not in payload and not k.startswith("_"):
                payload[k] = v
        return json.dumps(payload, ensure_ascii=False)

handler = logging.StreamHandler()
handler.setFormatter(JsonFormatter())
logger = logging.getLogger("app")
logger.addHandler(handler)
logger.setLevel(logging.INFO)

logger.info("user login", extra={"user_id": 42, "ip": "127.0.0.1"})
```

输出：

```text
{"ts": "2026-09-29 10:00:00,123", "level": "INFO", "logger": "app", "msg": "user login", "user_id": 42, "ip": "127.0.0.1"}
```

**翻车现场：用字符串拼接塞进 message**

```python
# WRONG：所有信息糊进一条字符串，事后没法按 user_id 过滤
logger.info(f"user {user_id} login from {ip} with token {token}")
```

```text
检索时想找"user_id=42 的所有日志"，只能靠正则去扒文本
# 而且 token 还被记下来了（见下一节）
```

**正确做法**：用 `extra={}` 传结构化字段，message 只写事件名。这样"按 user_id 过滤"就是一次精确查询，而不是全文正则。

## 什么绝不能记：敏感信息红线

这是本课最重要的一条。**日志会进文件、进集中式日志系统、进备份、可能被多方看到**——一旦把密码、token、密钥写进去，就等于二次泄露。

```python
# WRONG：记了密码
logger.info(f"login failed for user={name} password={password}")
# WRONG：记了 token
logger.info(f"calling api with token={api_key}")
# WRONG：记了完整身份证 / 手机号
logger.info(f"user id_card={id_card} phone={phone}")
```

```text
后果：
- 日志文件落地，任何能读服务器的人都能看到
- 集中式日志（ELK 等）保留 30 天以上，泄露窗口被拉长
- 备份、监控截图、告警通知都可能带出敏感字段
```

**正确做法**：只记脱敏后的信息，足够定位问题即可。

```python
import re

SENSITIVE_KEYS = {"password", "passwd", "token", "api_key", "secret", "authorization"}

def sanitize(record):
    """对 dict 类型的负载做脱敏，返回新 dict，原对象不动"""
    if not isinstance(record, dict):
        return record
    out = {}
    for k, v in record.items():
        if k.lower() in SENSITIVE_KEYS:
            out[k] = "***"
        else:
            out[k] = v
    return out

# 用法
payload = {"user": "alice", "password": "s3cret", "token": "tk_123"}
logger.info("auth attempt", extra=sanitize(payload))
# 输出里 password 和 token 都变成 ***
```

**翻车现场：只脱敏了 password，忘了 token**

```python
def log_auth(user, pwd, token):
    safe = {"user": user, "pwd": "***"}   # 只处理了 pwd
    logger.info("auth", extra=safe)
    # token 被直接拼进了别处
    logger.info(f"token used: {token}")    # 泄露
```

```text
合规审计结果：
发现 1 处敏感字段未脱敏 → 整批日志需要清理 + 密钥轮换
```

**教训**：脱敏要**覆盖所有已知敏感字段名**，并做统一拦截，而不是在每一处手写"打码"。字段名要小写比对，避免 `Token`/`TOKEN` 绕过。

## 请求 ID 追踪：把一次请求串起来

一个用户请求会穿过很多函数、很多服务，中间可能并发处理上百个请求。**只靠时间顺序翻日志是找不到一次请求的完整路径的**——你需要一个贯穿始终的 `request_id`。

```python
import uuid, logging, contextvars

# contextvars 是 Python 3.7+ 的上下文变量，能在异步/多线程间隔离
request_id_var: contextvars.ContextVar[str] = contextvars.ContextVar("request_id")

class RequestIdFilter(logging.Filter):
    def filter(self, record):
        record.request_id = request_id_var.get("unknown")
        return True

logger = logging.getLogger("app")
logger.addFilter(RequestIdFilter())

def handle_request(user_input):
    request_id_var.set(str(uuid.uuid4())[:8])
    logger.info("request start", extra={"input_len": len(user_input)})
    result = process(user_input)          # 内部任何地方打日志都带 request_id
    logger.info("request done", extra={"result_len": len(result)})
    return result

def process(data):
    logger.info("processing step1")       # 自动带 request_id
    return data.upper()
```

输出：

```text
2026-09-29 10:00:00 [INFO] app: request start | request_id=a1b2c3d4 input_len=5
2026-09-29 10:00:00 [INFO] app: processing step1 | request_id=a1b2c3d4
2026-09-29 10:00:00 [INFO] app: request done | request_id=a1b2c3d4 result_len=5
```

**翻车现场：用线程局部变量当请求 ID 载体，却跑在异步环境**

```python
# WRONG：threading.local() 在 asyncio 里不按协程隔离
import threading
_local = threading.local()

async def handle():
    _local.rid = uuid.uuid4()
    await fetch()              # 切换到别的协程，rid 可能被覆盖
    logger.info("done")        # request_id 串了
```

```text
日志结果：
request_id 在并发请求间互相串号，排查时完全无法定位
```

**正确做法**：Python 3.7+ 用 `contextvars.ContextVar`，它是为异步场景设计的，能正确隔离每个协程/请求的上下文。

## 记什么、不记什么：一张速查表

| 该记 | 不该记 |
|---|---|
| 事件名、时间、级别 | 密码、token、API key |
| request_id、user_id（脱敏） | 完整身份证号、手机号、银行卡号 |
| 输入长度 / 类型，不记原文 | 大段请求体原文（除非必要且脱敏） |
| 耗时、状态码、错误类型 | 堆栈里的敏感字段值 |
| 外部调用的目标服务名 | 内部网络拓扑细节（安全考虑） |

**黄金原则**：日志是为了**复现和定位问题**，不是为了保存业务数据。够定位就行，别贪多。

## 小结

- `print` 没有级别和上下文，线上必须用 `logging`
- 结构化日志（JSON）才能被工具过滤、聚合、统计
- 敏感信息（密码、token、密钥）**绝对不能进日志**，要做统一脱敏
- 请求 ID 贯穿一次请求的所有日志，是排查分布式/并发问题的关键
- 用 `contextvars` 而不是线程局部变量来携带请求上下文
- 记日志的尺度：够定位问题即可，别当业务数据库用
