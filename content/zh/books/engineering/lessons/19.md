# 覆盖率：100% 不等于没 bug

> 你看到报告上"覆盖率 100%"，心里踏实了。但第二天线上报 bug：用户名为空字符串时崩溃。覆盖率是"代码被执行过"的度量，不是"代码被验证正确"的度量。看懂覆盖率要会看**哪一行没覆盖**，而不是只盯那个百分比。

## 覆盖率到底测什么

行覆盖率（line coverage）回答的是：每一行代码**有没有被执行过**。它不回答"执行的结果对不对"。

```python
def divide(a, b):
    if b == 0:
        raise ValueError("除数不能为零")
    return a / b

# 测试
def test_divide():
    assert divide(6, 3) == 2
```

这份测试能让 `divide` 的覆盖率接近 100%（正常分支都走了），但完全没碰 `b == 0` 的异常分支。任何输入 `b=0` 的调用都会崩——而你不知道。

## 怎么测覆盖率

用 `coverage` 工具跑 pytest，生成报告：

```bash
# 安装
$ pip install coverage

# 跑测试并收集覆盖率
$ coverage run -m pytest tests/

# 看终端报告
$ coverage report -m
Name                Stmts   Miss  Cover   Missing
-------------------------------------------------
src/calculator.py      28      3    89%   42, 57-58
src/parser.py          40      0   100%
-------------------------------------------------
TOTAL                  68      3    96%

# 生成 HTML 报告，浏览器打开看每一行有没有被覆盖
$ coverage html
$ open htmlcov/index.html
```

`-m` 参数会在报告里列出**没被覆盖的行号**（`Missing` 列），这是最有价值的信息。

## 100% 覆盖率为何不等于没 bug

**反例一：走了代码，没断言**

```python
def withdraw(balance, amount):
    if amount > balance:
        raise ValueError("余额不足")
    return balance - amount

def test_withdraw():
    withdraw(100, 30)    # 调用了，没断言
    withdraw(50, 100)    # 调用了，没断言
```

覆盖率 100%，但测试什么都没验证。函数就算返回 `None`，测试照样绿。

**反例二：没测边界**

```python
def get_discount(total):
    if total >= 1000:
        return 0.2
    elif total >= 500:
        return 0.1
    return 0

def test_get_discount():
    assert get_discount(500) == 0.1
```

只测了 `500`。`499` 返回 0、`1000` 返回 0.2 这些边界都没测。覆盖率满的，边界 bug 照样有。

**反例三：没测异常路径**

```python
def load_config(path):
    try:
        with open(path) as f:
            return json.load(f)
    except FileNotFoundError:
        return {"default": True}
```

只测"文件存在"的情况，异常分支覆盖不到。生产环境配置文件缺失，行为完全没被验证过。

**翻车现场：把覆盖率当 KPI**

```text
老板：覆盖率必须 90% 以上，否则不合并。
开发：写一堆无断言的测试、测 getter/setter、测一行 return 的空函数。
结果：覆盖率 92%，核心业务逻辑零验证。
```

覆盖率一旦成为硬性指标，就会被"凑数"——这不是覆盖率的问题，是用错了指标。

## 看覆盖率该看什么

| 该看的 | 不该只看的 |
|---|---|
| 哪些**重要函数/模块**没覆盖 | 总百分比一个数字 |
| `Missing` 列里的**具体行号** | 数字是不是整数 |
| 分支是否都走到（用 `--branch`） | 测试数量够不够多 |
| 异常路径、边界值有没有被测 | 是不是 100% |

带分支覆盖率：

```bash
$ coverage run --branch -m pytest tests/
$ coverage report -m
Name                Stmts   Miss Branch BrPart  Cover   Missing
----------------------------------------------------------------
src/calculator.py      28      0     12      1     97%   42->45
```

`BrPart` 是"部分覆盖的分支"：那行 `if` 走了 True 但没走 False（或反过来）。`42->45` 告诉你第 42 行的 False 分支没走到。

**正确的用法**：把覆盖率当**发现盲区的工具**，不当**质量证书**。看到 `Missing` 列里有核心业务逻辑的行，就去补测试；那些确实无法覆盖的代码（防御性兜底、平台相关分支），心里有数就行。

## 覆盖率的目标值

别定死数字。更合理的做法是：

- 核心业务模块、计算逻辑：**尽量高**（90% 以上）
- 胶水代码、CLI 参数解析、框架自动生成代码：可以适当放宽
- 新增代码的**增量覆盖率**（diff coverage）作为 PR 门槛更合理

有些团队用 `diff-cover` 只检查本次改动行的覆盖率，比全量 90% 的门槛更贴合实际。

## 小结

- 覆盖率是"代码被执行过"的度量，不是"代码正确"的度量
- 测覆盖率用 `coverage run -m pytest` + `coverage report -m`
- `--branch` 能发现"走了 if 没走 else"的部分覆盖
- 100% 覆盖也可能漏掉：无断言测试、未测边界、未走异常路径
- 别把覆盖率当 KPI，会催生凑数的无效测试
- 看 `Missing` 列和未覆盖的分支，比看总百分比更有价值
