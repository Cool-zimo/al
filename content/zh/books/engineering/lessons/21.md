# 语义化版本号：major.minor.patch 各自什么时候加

> 你发了一个小改动，顺手把版本号从 1.2.3 跳到 2.0.0。所有依赖你的项目被迫检查有没有不兼容。版本号不是自增的数字，它是给用户的**契约**：看到 1.3.0，用户知道可以放心升级；看到 2.0.0，知道要准备改代码。

## 三段号各自什么时候加

语义化版本号（Semantic Versioning，SemVer）格式：`MAJOR.MINOR.PATCH`，如 `2.13.7`。

**PATCH（修订号）**：做了**向后兼容的 bug 修复**。不改任何接口，不改任何行为语义，只修 bug。

```text
1.2.3 → 1.2.4   修了一个空指针，调用方式完全不变
```

**MINOR（次版本号）**：做了**向后兼容的功能新增**。加了新功能、新参数（带默认值）、新模块，但旧代码照样能用。

```text
1.2.4 → 1.3.0   新增了 export_csv() 函数，旧的 import_json() 行为不变
```

**MAJOR（主版本号）**：做了**不兼容的 API 变更**。删除了函数、改了参数顺序、改了返回值类型、改了行为语义。

```text
1.3.0 → 2.0.0   get_user() 返回值从 dict 改成对象，旧调用方全挂
```

**翻车现场：把 bug 修复升级成主版本**

```text
# WRONG：项目发布规范混乱
v1.0.1 → v1.1.0   "修了个 bug，顺手加了个小功能"
v1.1.0 → v2.0.0   "其实没啥不兼容，就是觉得该升了"
```

```text
依赖方日志：
WARNING  bumped to 2.0.0, assuming breaking change, blocking upgrade
```

**后果**：用户看到大版本号，默认你有破坏性改动，不敢升级。你的"无关紧要的升级"反而拖慢了生态采用。版本号失去信号意义。

## 什么是"破坏性变更"

判断标准很简单：**现有用户不改一行代码，升级后还能不能正常工作。**

| 变更 | 算不算破坏 |
|---|---|
| 新增函数、新增可选参数（带默认值） | 不算 |
| 修 bug（包括让"错误行为"变正确） | 不算（算 patch，除非用户依赖了那个 bug） |
| 重命名函数 | 算 |
| 删除函数或参数 | 算 |
| 改参数顺序、改默认值 | 算 |
| 改返回类型或字段名 | 算 |
| 内部实现重写但接口不变 | 不算（对用户透明） |

**注意"依赖 bug 的行为"**：如果一个"bug"已经被大量用户当成特性用了（比如函数本该返回列表却返回了 None，有人专门写了 `if result is None` 兼容），修正它可能破坏他们。这种情况要谨慎，通常值得一次 MINOR 加警告，再下个 MAJOR 删掉旧行为。

## 预发布版本和构建元数据

版本号后面还能带后缀：

```text
1.3.0-alpha.1    预发布：内部测试版，不稳定
1.3.0-beta.2     预发布：功能冻结，对外公测
1.3.0-rc.1       预发布：发布候选，基本可用
1.3.0            正式版
```

预发布版本**优先级低于正式版**。包管理器会把 `1.3.0-alpha` 视为比 `1.3.0` 旧，所以 `pip install >=1.3.0` 不会拉到 alpha。

构建元数据（加号后面）不参与比较：

```text
1.3.0+build.123   和 1.3.0 是同一个版本，只是构建号不同
```

## 为什么不能随意跳版本

版本号是**你和用户之间的承诺**。具体影响：

**1. 依赖方据此决定升级策略**

```toml
# 别人的 pyproject.toml
dependencies = [
    "mypackage>=1.3,<2.0",   # 只接受向后兼容的更新
]
```

他们写 `<2.0` 是因为相信你：MAJOR 不加，接口就不会坏。你随便跳 2.0，他们的约束就失效了，升级可能崩。

**2. 包管理器靠它做依赖解析**

`pip`、`poetry` 看到 `^1.3.0`（兼容区间）会自动接受 `1.4.0`、`1.9.0`，但不会接受 `2.0.0`。乱跳版本会让自动更新和锁文件机制全部失灵。

**3. 随意跳版会让"版本号"失去信号意义**

```text
v1 → v2：什么都没改
v2 → v3：只是改了 README
# 从此没人看你的版本号，CHANGELOG 也没人读
```

版本号变廉价后，用户只能逐个版本手动检查，成本极高。

## 如何正确发布

1. 先想清楚这次改动的**最大影响**属于哪一级，从它往下定号
2. 破坏性改动 → MAJOR；只加功能 → MINOR；只修 bug → PATCH
3. 同时有多种变更时，取**最高**那一级
4. 改完 `pyproject.toml` 的 `version` 字段
5. 写 CHANGELOG，标明 Added / Changed / Fixed / Removed
6. 打 git tag：`git tag v1.3.0 && git push origin v1.3.0`

## 小结

- `MAJOR.MINOR.PATCH`：不兼容变更 / 向后兼容新功能 / 向后兼容修复
- 判断破坏性：现有用户不改代码，升级后还能不能用
- 预发布后缀 `-alpha`、`-beta`、`-rc` 优先级低于正式版
- 版本号是给用户的契约，乱跳版本会破坏依赖方的自动更新和信任
- 发布流程：定版本 → 改 `version` → 写 CHANGELOG → 打 tag

```quiz
type: choice

options:
- 1.2.3 → 2.0.0，因为改动不止一处
- 1.2.3 → 1.3.0，新增带默认值的参数是向后兼容的功能新增，bug 修复也归到这次
- 1.2.3 → 1.2.4，因为 bug 修复比功能新增更重要
- 1.2.3 → 1.3.1，PATCH 和 MINOR 要同时加
answer: 1
explain: 新增带默认值的可选参数是向后兼容的功能变更，归为 MINOR；bug 修复也包含在这次发布里。取最高一级即可，不需要同时加 PATCH，发布后版本为 1.3.0。
```
