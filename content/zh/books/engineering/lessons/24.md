# 文档：README、CHANGELOG 与设计文档

> 代码写完不是终点，别人（包括三个月后的你自己）能看懂、能跑起来、敢改，才算交付。文档是项目里最容易被跳过、却最常被人骂的部分。一份好的 README 能让新人十分钟跑起来；一份坏的 README 能让一个不错的项目无人问津。

## README 该写什么

README 是项目的门面，是别人打开仓库第一个看到的东西。一份合格的开源项目 README 至少包含这几节，按顺序排：

1. **项目简介**：一句话说清这是干什么的、解决什么问题、适合谁用
2. **安装方法**：从零到能跑的完整命令，包含 Python 版本、依赖安装、系统级依赖（如果有）
3. **快速开始 / 使用示例**：最小可运行例子，最好能直接复制粘贴
4. **配置说明**：环境变量、配置文件、需要用户提供什么参数
5. **基本用法**：常见操作、命令行参数、API 入口
6. **如何贡献**：分支规范、提 PR 流程、代码风格、要不要先开 issue
7. **测试与开发**：怎么跑测试、怎么搭开发环境
8. **许可证**：用的什么 license

一个简版骨架：

```markdown
# 项目名

一句话简介。

## 安装

    python -m venv .venv && source .venv/bin/activate
    pip install -r requirements.txt

## 快速开始

    python app.py --input data.csv --output result.json

## 配置

需要设置环境变量 `DATABASE_URL` 和 `API_KEY`（见 `.env.example`）。

## 如何贡献

1. Fork 并创建分支
2. 跑通测试：pytest
3. 提交 PR

## 许可证

MIT
```

## 为什么"跑不起来"的 README 是最常见问题

README 最大的坑不是写得少，而是**写的不对、跑不通**。典型症状：

- 写着 `pip install` 但没说 Python 版本，3.8 跑不了
- 命令复制下来直接报错：路径不对、缺了激活虚拟环境的步骤、依赖顺序错了
- 提到了一个配置文件，但仓库里根本没有，也没说格式
- 快速开始用的是已删除的旧 API
- 装完之后不知道下一步该敲什么命令

```text
新手日志：
$ git clone <repo>
$ pip install -r requirements.txt
ERROR: Could not find a version that satisfies the requirement django==5.0
# README 一个字没提需要 Python 3.10+
```

**为什么这是最致命的问题**：用户/同事/你自己 clone 下来跑不起来，通常只会尝试两三次，然后放弃。一个"跑不起来"的 README，等于把潜在用户和未来的你自己挡在门外。代码质量再高也没人用得上。

**翻车现场：把 README 当"已经做过的事"写完就忘**

```text
# WRONG：重构后没更新 README
仓库现状：主入口已从 app.py 改成 cli.py，参数从 --file 改成 --input
README 还写着：
    python app.py --file data.csv
```

```text
反馈：
issue #47：按照 README 运行提示找不到 app.py，请问项目结构变了吗？
issue #48：--file 参数报错，是文档写错了还是命令错了？
```

**后果**：文档和代码脱节，用户第一印象就是"这项目没人维护"，信任崩塌。README 是代码的一部分，改了 API 就要同步改文档。

## CHANGELOG 有什么用

CHANGELOG 是给用户看的变更记录，按版本倒序排列，说明每个版本改了什么。它不是 git log——git log 是给开发者看的"我哪天提交了什么"，CHANGELOG 是给用户看的"升级到 1.3.0 你能得到什么、要注意什么"。

主流格式（Keep a Changelog 风格）：

```markdown
# Changelog

## [1.3.0] - 2026-09-20
### Added
- 新增 export_csv() 函数
- 支持通过环境变量配置超时时间

### Changed
- import_json() 现在接受可选参数 encoding

## [1.2.4] - 2026-08-15
### Fixed
- 修复空文件导致的崩溃

## [1.2.3] - 2026-07-02
### Removed
- 删除了已弃用的 old_api()（自 1.0 起弃用）
```

分类通常是：`Added`（新功能）、`Changed`（变更）、`Deprecated`（弃用）、`Removed`（删除）、`Fixed`（修复）、`Security`（安全修复）。

**CHANGELOG 的作用**：

- 用户决定要不要升级、要不要改代码（配合 SemVer 看破坏性变更）
- 维护者回顾项目演进，避免"我到底改了什么"的困惑
- 出问题时定位是哪个版本引入的

**翻车现场：用 git log 当 CHANGELOG**

```text
# WRONG：CHANGELOG.md 内容
## 变更记录
- fix bug
- update
- WIP
- 改了一些东西
- merge master
```

**后果**：没人看得懂，等于没有。CHANGELOG 要写"对用户有意义的事"，而不是提交习惯。

## 什么时候该写设计文档

不是所有代码都需要设计文档。判断标准：**这个决定如果做错了，返工成本高不高？**

值得写设计文档的场景：

- 引入新的核心抽象或架构（比如从单体拆成多模块）
- 选技术栈或第三方依赖（要写清楚为什么选 A 不选 B）
- 设计对外 API 或数据格式（影响所有调用方）
- 跨多个模块/多人的大改动
- 性能、安全相关的关键设计

不必写设计文档的场景：

- 改一个函数的实现细节
- 修 bug、补测试
- 重构内部逻辑但接口不变

设计文档通常包含：**背景与目标 / 方案对比 / 最终方案 / 影响面 / 风险和备选 / 废弃计划**。它不必很长，几页 markdown 即可，关键是让评审者看到你的思路和取舍。

**翻车现场：先写代码、事后补文档**

```text
# WRONG 流程
1. 花两周写完一个大功能，直接提了个 3000 行的 PR
2. 评审被打回：为什么用 Redis 不用数据库？
3. 答辩时现场画图解释设计
4. 最后被要求补设计文档
```

```text
评审意见：
"这方案整体可行，但为什么选了消息队列而不是定时任务？这个应该在动手前讨论清楚。"
```

**后果**：返工成本极高。设计文档的价值在于**提前暴露分歧**，而不是事后为代码辩护。

## 小结

- README 是门面：简介、安装、快速开始、配置、用法、贡献、测试、许可证，缺一不可
- "跑不起来"的 README 是最致命问题：命令要能直接复制粘贴、版本要明确、配置要齐
- 改了代码就要同步改 README，文档是代码的一部分
- CHANGELOG 给用户看变更、给用户决定升级，要写"对用户有意义的事"
- 设计文档用在返工成本高的关键决策上，重在提前暴露分歧

## 随堂练习

```quiz
type: choice
q: 你重构了一个项目，把主入口从 app.py 改成了 cli.py，参数也改了。README 和 CHANGELOG 该怎么处理？
options:
- README 不用改，反正代码能跑；CHANGELOG 也不用写，因为用户看不到内部改动
- 只改 CHANGELOG，README 反正没人看
- 同步更新 README 的安装和快速开始示例，并在 CHANGELOG 对应版本下记录这次变更（若接口变了要标为破坏性变更）
- 把 README 全部删掉重写，因为旧内容已经过时
answer: 2
explain: 文档是代码的一部分，改了接口必须同步改 README，否则用户按旧文档跑会报错；CHANGELOG 记录变更供用户判断升级影响。不需要删掉重写，只需同步改动处。
```
