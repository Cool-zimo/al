# 实战：给一个已有小项目做工程化改造

> 这是第 5 章的收尾大项目。前面几课分别讲了版本号、打包、容器、文档，这一课把它们串起来：拿到一个"能跑的脚本"，把它改造成"能交付的项目"。你会经历真实改造的全流程——补测试、加 CI、写 README、定版本号、加 .gitignore，看到零散的知识点怎么组成一个完整交付物。

## 起点：一个能跑但没法交付的项目

下面是一个典型的"能跑的脚本"项目，功能是从 CSV 读取数据、做清洗、输出 JSON。代码能用，但没人敢碰、没法协作、没法上线。

```text
data_tool/
├── data_tool.py      # 全部逻辑堆在一个 400 行的文件里
├── config.py         # 硬编码了数据库密码
├── data.csv          # 一份测试数据
├── .env              # 里面写了 API_KEY=sk-xxxxx
└── run.sh            # 一行：python data_tool.py
```

`data_tool.py` 长这样（节选）——密钥硬编码、逻辑全挤在一个函数、输入输出路径写死：

```python
import csv, json, os, sys

API_KEY = "sk-abcdef123456"   # 硬编码密钥

def load_data(path):
    rows = []
    with open(path, encoding="utf-8") as f:
        for r in csv.DictReader(f):
            rows.append(r)
    return rows

def clean(row):
    if not row.get("name"):
        return None
    row["name"] = row["name"].strip()
    row["age"] = int(row["age"]) if row.get("age") else 0
    return row

def main():
    data = load_data("data.csv")
    cleaned = [clean(r) for r in data if clean(r)]
    with open("out.json", "w") as f:
        json.dump(cleaned, f, ensure_ascii=False)
    print("done")

if __name__ == "__main__":
    main()
```

**问题清单**（先看清再动手）：

| 问题 | 后果 |
|---|---|
| 没有测试 | 改一行代码不知道有没有搞坏别的 |
| 密钥硬编码 | 一提交就泄露，推到远程就公开 |
| 没有 .gitignore | `.env`、缓存、虚拟环境全进版本库 |
| 没有 README | 新人不知道怎么装、怎么跑 |
| 没有版本号、没打包 | 别人没法当库引用，也没法发布 |
| 没有 CI | 没人帮你跑测试，错误只能靠人肉 |

## 改造目标：从脚本到项目

改造不是重写。目标是在**不破坏现有功能**的前提下，补齐交付所需的工程要素。改造顺序有讲究：先控制风险（密钥、gitignore），再补质量（测试、CI），最后补交付物（README、版本、打包、容器）。

最终结构（一个包 + 一个测试目录 + 各种配置）：

```text
data_tool/
├── data_tool/           # 包：loader.py / cleaner.py / cli.py
├── tests/               # test_loader.py / test_cleaner.py
├── .gitignore  .dockerignore
├── Dockerfile  README.md  CHANGELOG.md
├── pyproject.toml  requirements.txt
└── data.csv
```

**翻车现场：一上来就重构全部代码**

```text
# WRONG 顺序
第 1 天：把 400 行拆成 20 个文件、换了新的目录结构
第 2 天：发现跑不通，git diff 几千行，无从排查
第 3 天：回滚，一切重来
```

```text
教训：
error: too many changes in one commit, cannot bisect
# 一次动太多东西，出错时无法定位是哪一步引入的
```

**正确做法**：一次只做一类改造、一个小提交、每步都跑得起来。先锁密钥，再补测试，再拆文件，再补 CI……

## 第一步：控制风险——.gitignore 和密钥清理

先解决最紧急的：把 `.env` 从版本库里隔离出去，并清理历史里可能已经提交过的密钥。

```gitignore
# .gitignore
.env
*.env
__pycache__/
*.pyc
.venv/
venv/
.pytest_cache/
.mypy_cache/
build/
dist/
*.egg-info/
.DS_Store
```

```bash
git rm --cached .env        # 已从历史移除的还要清理历史（git filter-repo --invert-paths --path .env）
# 清理后务必轮换（重置）泄露的密钥，老密钥一律作废
```

**原则**：一旦发现密钥泄露，光删文件不够，必须轮换密钥。仓库历史、fork、CI 缓存里都可能有副本。

## 第二步：拆模块、补测试

把 `data_tool.py` 拆成三个职责单一的模块，并先写测试。注意顺序是**先测试再拆**，因为测试能验证拆分没有改坏行为。

```python
# data_tool/loader.py
import csv

def load_data(path):
    with open(path, encoding="utf-8") as f:
        return list(csv.DictReader(f))
```

```python
# data_tool/cleaner.py —— 返回新 dict，空名字返回 None
def clean(row):
    if not row.get("name"):
        return None
    result = dict(row)
    result["name"] = result["name"].strip()
    result["age"] = int(result["age"]) if result.get("age") else 0
    return result
```

```python
# data_tool/cli.py
import json, sys
from .loader import load_data
from .cleaner import clean

def main(argv=None):
    argv = argv if argv is not None else sys.argv[1:]
    if not argv:
        print("usage: data_tool <input.csv> [output.json]")
        return 1
    data = load_data(argv[0])
    cleaned = [r for r in (clean(x) for x in data) if r is not None]
    out = argv[1] if len(argv) > 1 else "out.json"
    with open(out, "w", encoding="utf-8") as f:
        json.dump(cleaned, f, ensure_ascii=False)
    print(f"wrote {len(cleaned)} rows to {out}")
    return 0
```

测试（放在 `tests/` 下，用 `pytest` + `parametrize` 覆盖多种输入）：

```python
# tests/test_cleaner.py
import pytest
from data_tool.cleaner import clean

@pytest.mark.parametrize("row,expected", [
    ({"name": "  Alice  ", "age": "30"}, {"name": "Alice", "age": 30}),
    ({"name": "", "age": "20"}, None),          # 空名字 → 丢弃
    ({"age": "20"}, None),                      # 缺名字 → 丢弃
    ({"name": "Bob", "age": ""}, {"name": "Bob", "age": 0}),
])
def test_clean(row, expected):
    assert clean(row) == expected
```

```python
# tests/test_loader.py
from data_tool.loader import load_data

def test_load_data(tmp_path):
    f = tmp_path / "t.csv"
    f.write_text("name,age\nAlice,30\n", encoding="utf-8")
    assert load_data(str(f)) == [{"name": "Alice", "age": "30"}]
```

跑测试（`tmp_path` 是 pytest 提供的临时目录 fixture，自动清理）：

```bash
$ pytest -v
tests/test_cleaner.py::test_clean[...] PASSED
tests/test_loader.py::test_load_data PASSED
```

**翻车现场：重构时把行为改了**

```python
# WRONG：重构时"顺手优化"
def clean(row):
    if not row.get("name"):
        row["name"] = "(unknown)"   # 原本是返回 None，现在改成填空字符串
        return row
    ...
```

```text
$ pytest
FAILED tests/test_cleaner.py::test_clean[...] - AssertionError: expected None, got {...}
# 但功能"看起来"还能跑，手工测试没发现
```

**后果**：没有测试时，这种"顺手改"没人发现；有了测试，立刻报警。这就是测试的价值——它锁住行为。

## 第三步：加 CI，让自动化替你守门

CI 在每次 push / PR 自动跑测试、检查格式。这里用 GitHub Actions 举例（`matrix` 同时在 3.9 和 3.11 两个版本上验证兼容性）：

```yaml
# .github/workflows/ci.yml
name: CI
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        python: ["3.9", "3.11"]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: ${{ matrix.python }}
      - run: pip install -r requirements.txt pytest
      - run: pytest -v
```

CI 的价值不是"省事"，而是**把纪律变成强制**：不跑测试就合并不了，格式不对就过不了。

## 第四步：定版本号、写 CHANGELOG

给项目一个起点版本，并说明这次改造做了什么（`0.1.0` 表示功能尚不稳定、接口还可能变）：

```text
# CHANGELOG.md
## [0.1.0] - 2026-09-29
### Added
- 项目工程化改造：拆分为 loader/cleaner/cli 模块
- 补充单元测试（loader、cleaner）
- 新增 CI 配置
- 新增 README 和 CHANGELOG

### Changed
- clean() 保持原有行为不变，仅调整内部实现
```

版本号用 `0.1.0` 而非 `1.0.0`：功能还不稳定、接口还可能变，0.x 阶段是合适的表态。

## 第五步：打包、容器化、写 README

`pyproject.toml` 描述元数据并声明命令行入口 `data_tool = data_tool.cli:main`；`Dockerfile` 锁 `python:3.11-slim`、先装依赖再复制代码、用 exec 形式 CMD（注意 `.dockerignore` 排除 `.env`）；`README.md` 写清项目干什么、怎么装、怎么用、怎么跑测试、怎么贡献。

```toml
[project]
name = "data_tool"
version = "0.1.0"
description = "CSV 数据清洗小工具"
requires-python = ">=3.9"
dependencies = []

[project.scripts]
data_tool = "data_tool.cli:main"

[build-system]
requires = ["setuptools>=68"]
build-backend = "setuptools.build_meta"
```

`Dockerfile`（`.dockerignore` 排除 `.env`）：

```dockerfile
FROM python:3.11-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["python", "-m", "data_tool.cli", "data.csv", "out.json"]
```

**翻车现场：交付前忘了跑一遍"全新环境"**

```text
# WRONG：在自己配好的机器上验证
$ pytest         # 能跑，因为全局装了 pytest
$ python -m data_tool.cli data.csv out.json   # 能跑
然后就打了 tag、发布了。
```

```text
新人机器上：
$ git clone <repo> && cd data_tool && pytest
pytest: command not found   # 没写进 requirements-dev.txt，README 也没说明
```

**后果**：在自己机器上"能用"毫无意义。必须在干净环境（容器、新虚拟机、CI）里验证一遍，确认 README 每一步都能跑通。

## 小结

- 改造顺序：先控风险（.gitignore + 清理密钥）→ 补质量（测试 + CI）→ 补交付物（README、版本、打包、容器）
- 一次只做一类改造、保持可运行，避免一次动几千行无从排查
- 重构前后用测试锁住行为，避免"顺手改"引入回归
- 密钥泄露要轮换，光删文件不够
- 交付前必须在全新环境验证 README 的每一步都能跑通
