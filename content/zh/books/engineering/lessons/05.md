# 配置管理：密钥、开关和"在我机器上能跑"

> 张三把数据库密码写在了代码里，`git push` 上去，全公司都能看到。更糟的是，生产库和测试库用的是同一个密码。配置管理的核心原则就一条：**会变的东西别写死在代码里**。

## 配置不能硬编码

"配置"指的是那些**因环境而异、因部署而异、但不属于业务逻辑**的东西：

- 数据库连接串、API 地址
- 密钥、Token、密码
- 功能开关（灰度开关、调试模式）
- 超时时间、重试次数
- 日志级别

写死在代码里是什么后果？

```python
# WRONG：配置硬编码
DATABASE_URL = "mysql://root:123456@192.168.1.100:3306/prod_db"
API_KEY = "sk-prod-abcdefghijklmn"
DEBUG = True

def get_user(uid):
    print(f"连接数据库: {DATABASE_URL}")  # 调试语句，忘了删
    ...
```

**翻车现场：测试连上了生产库**

```python
# WRONG：忘了改
DATABASE_URL = "mysql://root:123456@10.0.0.5:3306/prod_db"
DEBUG = True

# 张三本地跑测试
$ python manage.py test
Creating test database...
# 测试真的在清理生产库的数据
```

**后果**：测试套件一启动就把生产库清了。因为配置写死，谁也没注意到测试指向了生产环境。这种事故一旦发生，职业生涯都会留下记录。

## 环境变量 vs 配置文件

两种主流方案。

**环境变量**：从进程环境读取，适合密钥、部署相关的敏感信息。

```python
import os

database_url = os.environ["DATABASE_URL"]
api_key = os.environ["API_KEY"]
debug = os.environ.get("DEBUG", "false").lower() == "true"
```

**配置文件**：适合非敏感的、结构化的、经常调的参数。

```yaml
# config.yaml
database:
  host: localhost
  port: 3306
  name: app_db
server:
  host: 0.0.0.0
  port: 8000
  timeout: 30
```

| 对比项 | 环境变量 | 配置文件 |
|---|---|---|
| 适合放什么 | 密钥、Token、部署地址 | 业务参数、超时、开关 |
| 敏感信息安全 | 相对安全（不进代码库） | 不该放敏感信息 |
| 结构复杂度 | 扁平，难表达嵌套 | 支持嵌套、列表 |
| 12-Factor 兼容 | 是（推荐） | 不推荐放密钥 |
| 本地开发体验 | 要手动 export 或写 .env | 直接改文件 |

**12-Factor App** 的原则是：配置应该存在于环境变量中。这样同一份代码在不同环境（开发、测试、生产）部署时，只需切换环境变量，不用改代码、不用改配置文件。

## .env 与 python-dotenv

环境变量有个痛点：本地开发时每次都要手动 `export`，很烦。`.env` 文件就是这个问题的答案。

```text
# .env（项目根目录，不提交到 Git）
DATABASE_URL=mysql://root:123456@localhost:3306/dev_db
API_KEY=sk-test-xxxxxxxx
DEBUG=true
```

```python
# main.py
from dotenv import load_dotenv
import os

load_dotenv()  # 从 .env 文件加载到环境变量

database_url = os.environ["DATABASE_URL"]
api_key = os.environ["API_KEY"]
```

`load_dotenv()` 读取 `.env` 并把它写进 `os.environ`。部署到服务器时，不设 `.env`，直接用系统的环境变量即可——**生产环境不依赖 .env 文件**。

**关键点：`.env` 必须进 `.gitignore`**。

```gitignore
.env
.env.local
.env.*.local
```

**翻车现场：.env 进了 Git 历史**

```bash
$ git add .env
$ git commit -m "add env"
$ git push
```

即使下一秒删掉 `.env` 再提交，密钥依然在 Git 历史里，任何人 clone 都能看到。修复办法是 `git filter-repo` 重写历史，同时**必须轮换所有泄露的密钥**——假设它已经被别人拿到了。

## 密钥绝不能进代码库

这条要单独强调，因为它是不可逆的。

- 代码库里的密钥，等于贴在办公室门口的钥匙
- Git 历史会一直留着它，删掉也没用
- 泄露后的处理不是"删掉就行"，是"换一把新钥匙"
- 包括测试用的密钥，测试密钥也该按真实密钥的标准管

**正确的密钥管理流程**：

```bash
# 1. 本地开发：用 .env，加载进环境变量
$ echo "API_KEY=xxx" > .env

# 2. 生产部署：用平台的环境变量管理
#    Heroku: heroku config:set API_KEY=xxx
#    Vercel: 在面板里填
#    Kubernetes: Secret 对象
#    服务器: systemd 的 EnvironmentFile 或部署脚本 export
```

## 小结

- 配置（连接串、密钥、开关、超时）不能硬编码在代码里
- 环境变量适合密钥和部署差异，配置文件适合结构化业务参数
- `.env` 用 python-dotenv 加载，方便本地开发
- `.env` 必须进 `.gitignore`，进了历史就等于泄露
- 密钥泄露的处理是**轮换**，不是删除
