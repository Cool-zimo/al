# mock 与打桩：隔离外部依赖，但别 mock 一切

> 你的函数要发 HTTP 请求、查数据库、读系统时间。不 mock，测试要联网、要起数据库、时间不可控，测试又慢又随机失败。mock 就是"用替身代替真对象"。但 mock 用多了，测出来的不是真实行为，是替身的行为。

## 为什么要 mock

三类依赖必须隔离：

**1. 不可控的依赖**：网络请求、第三方 API、系统时间。你不拥有它们，也无法保证它们在线、返回一致。

**2. 有副作用的依赖**：发邮件、扣款、写文件。你总不能每次跑测试都真发一封邮件。

**3. 慢的依赖**：连真实数据库一次几十毫秒，1000 个测试就是半分钟。

**翻车现场：测试真发了 HTTP 请求**

```python
# WRONG
import requests

def get_user_name(user_id):
    resp = requests.get(f"https://api.example.com/users/{user_id}")
    return resp.json()["name"]

def test_get_user_name():
    assert get_user_name(1) == "张三"     # 需要联网、需要服务在线
```

```text
$ pytest tests/test_user.py
E   requests.exceptions.ConnectionError: ...
```

CI 机房网络偶尔抖动，测试随机挂。而且这个测试跑的是"网络通不通"，不是"我的代码对不对"。

**正确做法：mock 掉 requests.get，验证它怎么被调用**

```python
from unittest.mock import patch

def get_user_name(user_id):
    resp = requests.get(f"https://api.example.com/users/{user_id}")
    return resp.json()["name"]

@patch("requests.get")
def test_get_user_name(mock_get):
    # 构造替身返回值：让 resp.json() 返回指定字典
    mock_get.return_value.json.return_value = {"name": "张三"}
    mock_get.return_value.status_code = 200

    result = get_user_name(1)

    assert result == "张三"
    # 顺带验证：确实请求了正确 URL、传了正确参数
    mock_get.assert_called_once_with("https://api.example.com/users/1")
```

测试现在只依赖 `get_user_name` 的逻辑，不依赖网络。

## monkeypatch：替换模块里的对象

pytest 内置的 `monkeypatch` fixture 专门用来临时替换属性、环境变量、字典项，测试结束后自动还原。

```python
import os
import time

def is_promotion_period():
    return time.localtime().tm_mon == 11  # 11 月是促销月

def get_db_url():
    return os.environ.get("DATABASE_URL", "sqlite:///default.db")

def test_promotion_in_november(monkeypatch):
    # 把 time.localtime 替换成返回"11 月"的假函数
    class FakeTime:
        tm_mon = 11
    monkeypatch.setattr(time, "localtime", lambda: FakeTime())
    assert is_promotion_period() is True

def test_default_db_url(monkeypatch):
    monkeypatch.delenv("DATABASE_URL", raising=False)
    assert get_db_url() == "sqlite:///default.db"

def test_custom_db_url(monkeypatch):
    monkeypatch.setenv("DATABASE_URL", "postgres://prod:5432/app")
    assert get_db_url() == "postgres://prod:5432/app"
```

`monkeypatch` 的好处是**自动还原**：测试结束，被替换的属性恢复原状，不会污染其他测试。

## 什么时候不该 mock

mock 是有代价的。下面三种情况用了 mock 反而更糟。

**1. 不该 mock 你自己的业务代码**

```python
# WRONG：mock 掉自己要测的函数
@patch("mymodule.calculate_total")
def test_checkout(mock_calc):
    mock_calc.return_value = 100
    assert checkout(["a", "b"]) == 100   # 什么都没测到
```

你把 `calculate_total` 替换成了"永远返回 100"，那这个测试验证的是"100 等于 100"。**被测试的函数和被 mock 的函数如果是同一块业务代码，等于跳过了真正的逻辑。**

**2. 不该过度 mock 导致测试与实现耦合**

```python
# WRONG：mock 到内部方法，实现一改测试全挂
@patch("mymodule.Order._validate_items")
@patch("mymodule.Order._check_inventory")
@patch("mymodule.Order._deduct_balance")
@patch("mymodule.Order._write_to_db")
def test_create_order(m1, m2, m3, m4):
    Order.create()
    m4.assert_called_once()     # 一旦重构方法名，立刻挂
```

这种测试把内部实现细节钉死了。重构时你改了方法名，业务行为没变，但测试全红。**mock 要停在模块边界上，不要 mock 私有方法。**

**3. 不该用 mock 替代集成测试**

mock 告诉你"我按预期调用了依赖"，但**不告诉你依赖真的能用**。请求拼对了，对方 API 的字段改了你也发现不了。这种对接正确性要靠集成测试（用真实数据库、真实本地服务）来补。

**翻车现场：mock 全绿，上线就崩**

```python
@patch("requests.get")
def test_fetch_profile(mock_get):
    mock_get.return_value.json.return_value = {"nickname": "Tom"}
    assert fetch_profile(1) == "Tom"    # 测试通过

# 上线后：真实 API 返回的字段是 "display_name" 而不是 "nickname"
# 测试全绿，生产环境 KeyError
```

**正确做法：关键外部对接用集成测试或契约测试（contract test）覆盖**，mock 只用于单元测试。

## mock 的判断标准

| 场景 | 该不该 mock |
|---|---|
| 第三方 HTTP API | 应该 |
| 系统时间、随机数 | 应该 |
| 发邮件、扣款、短信 | 应该 |
| 自己写的业务逻辑函数 | 不应该 |
| 私有方法、内部实现细节 | 不应该 |
| 数据库（在集成测试里） | 不应该 |
| 数据库（在单元测试里，函数不该直连 DB） | 应该，但要额外有集成测试 |

**一句话：mock 依赖，不 mock 被测对象；mock 边界，不 mock 内部。**

## 小结

- mock 用来隔离不可控、有副作用、慢的外部依赖
- `unittest.mock.patch` 替换对象，`mock.return_value` 设定返回值
- pytest 的 `monkeypatch` fixture 替换属性/环境变量，自动还原
- 不该 mock 自己的业务代码、私有方法、数据库对接逻辑
- mock 只能证明"调用方式对"，不能证明"对接能用"，需要集成测试补位
- 原则：mock 依赖，不 mock 被测对象；mock 边界，不 mock 内部

```quiz
type: choice
exam: true
q: 下面哪个场景最适合用 mock？
options:
- 验证自己写的订单金额计算函数是否正确
- 测试"调用支付网关扣款"的函数是否传了正确的金额和订单号
- 验证用户表插入数据库后能否被正确查询出来
- 验证自己写的 JSON 解析逻辑是否健壮
answer: 1
explain: 支付网关是外部依赖（有真实副作用、不可控），适合 mock 并验证调用参数。金额计算、JSON 解析是自己的业务逻辑，应直接测；数据库插入查询属于对接正确性，应用集成测试而非 mock。
```
