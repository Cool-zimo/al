# CI 基础：为什么不能靠"我本地跑过了"

> 你本地跑过测试，提交、推送、合并。第二天同事拉代码，测试挂了——他的环境里 `pandas` 版本和你不一样。再后来有人忘跑测试直接推，bug 进了 main。"我本地是好的"是软件工程里最没用的一句话，因为它不成立于别人的机器上。CI 就是把"构建 + 检查 + 测试"固化成每次提交必跑的动作。

## 为什么要有 CI

CI（Continuous Integration，持续集成）的核心是：**频繁地把代码集成到主干，每次集成都自动跑一遍验证**。它的价值不在于"跑得多快"，在于"每次提交都跑，且人人一致"。

**翻车现场：本地能跑，CI 挂了**

```text
$ git push origin feature/login
# 过了 2 分钟收到邮件
> CI FAILED: ModuleNotFoundError: No module named 'requests'
```

原因：作者装了 `requests` 但没写进 `requirements.txt`，本地有，CI 干净环境里没有。

**翻车现场：忘记跑测试**

```text
同事：我改了一行，很简单，不用跑测试。
同事：git push
> CI FAILED: 12 tests failed
# 一个本该 30 秒发现的问题，拖到了推送之后
```

**CI 解决的是"验证标准不一致"的问题**：本地环境千差万别，CI 是同一台干净机器、同一套命令、同一个结果。它能跑过，别人才能放心拉。

## GitHub Actions 基本结构

GitHub Actions 的配置文件放在 `.github/workflows/` 目录下，YAML 格式。

```yaml
# .github/workflows/ci.yml
name: CI

# 触发条件：push 和 PR 都跑
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

# 环境变量：全局可用
env:
  PYTHON_VERSION: "3.12"

jobs:
  lint-and-test:
    runs-on: ubuntu-latest          # 运行环境
    steps:
      - uses: actions/checkout@v4   # 步骤 1：拉代码

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: ${{ env.PYTHON_VERSION }}

      - name: Install dependencies
        run: |
          python -m pip install --upgrade pip
          pip install -r requirements.txt
          pip install pytest ruff

      - name: Lint
        run: ruff check .

      - name: Test
        run: pytest tests/ -v
```

**几个关键概念**：

- `on`：什么时候跑。常见 `push`、`pull_request`，也可以定时（`schedule`）跑。
- `jobs`：一个 workflow 可以有多个 job，默认并行。这里只有一个 `lint-and-test`。
- `runs-on`：跑在哪台机器。`ubuntu-latest` 最常用，还有 `windows-latest`、`macos-latest`。
- `steps`：按顺序执行的步骤。`uses` 引用现成的 action，`run` 执行 shell 命令。
- `actions/checkout@v4`：几乎每个 workflow 的第一步，把仓库代码拉到 runner 上。

## 一次提交自动跑 lint + test

**正确的 workflow 应该先做快的检查，再做慢的检查**——lint 几秒，测试几十秒，先跑 lint，格式不对就别浪费时间跑测试。

```yaml
jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install ruff
      - run: ruff check .

  test:
    runs-on: ubuntu-latest
    needs: lint                # 等 lint 通过才跑
    strategy:
      matrix:
        python-version: ["3.10", "3.11", "3.12"]   # 多版本矩阵
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: ${{ matrix.python-version }}
      - run: pip install -r requirements.txt pytest
      - run: pytest tests/ --tb=short
```

`needs: lint` 表示 test 依赖 lint 先通过。`strategy.matrix` 让测试在 3 个 Python 版本上各跑一遍，一次性发现版本兼容问题。

**翻车现场：secrets 泄露**

```yaml
# WRONG
- name: Deploy
  run: |
    echo "密码是 ${{ secrets.DB_PASSWORD }}"
    deploy.sh
```

```text
> 日志里出现了明文密码：密码是 s3cret!
```

即使用了 `secrets`，如果 `echo` 出来就会写进日志，谁有 workflow 日志权限谁就能看到。**规则：密钥只通过环境变量传给真正需要它的进程，绝不打印、不拼进 URL、不写进文件。**

正确做法：

```yaml
- name: Deploy
  env:
    DB_PASSWORD: ${{ secrets.DB_PASSWORD }}
  run: deploy.sh        # 脚本从环境变量读取，日志里看不到
```

## CI 的常见套路

| 场景 | 做法 |
|---|---|
| 多版本兼容 | `strategy.matrix` 矩阵跑多个 Python 版本 |
| 慢任务（部署、打包） | 单独 job，`needs` 测试 job，测试过才执行 |
| 缓存依赖加速 | `actions/cache` 缓存 pip 下载目录 |
| 只在特定分支跑 | `if: github.ref == 'refs/heads/main'` |
| 定时跑慢测试 | `schedule: - cron: "0 0 * * *"`（每天一次） |

**一个健康的 CI 应该 5 分钟内跑完**。跑太久大家就不等了，不等就不会看，不看 CI 就废了。这是和测试金字塔同一个道理。

## 小结

- CI 的价值是固化验证流程，保证"人人一致、次次都跑"
- GitHub Actions 配置在 `.github/workflows/*.yml`
- 核心结构：`on`（触发）→ `jobs` → `runs-on` → `steps`（`uses` / `run`）
- 先跑快的 lint，通过再跑慢的 test；用 `needs` 串联
- 用 `strategy.matrix` 多 Python 版本验证兼容性
- 密钥用 `secrets` 且只注入环境变量，绝不打印到日志

## 随堂练习

```quiz
type: choice
q: 你给项目配了 CI，但每次跑要 25 分钟，开发者都不等结果就推送了，CI 名存实亡。最合理的优化方向是？
options:
- 把 CI 关掉，靠代码评审保证质量
- 调整测试金字塔让单测占多数、缩短测试时间，并把 lint 和 test 拆分让快的检查先跑
- 加更多测试，覆盖更全
- 只在周五跑一次 CI
answer: 1
explain: CI 反馈慢是它失效的主因。缩短测试时间（单测为主、E2E 精简）并保证快的检查先出结果，才能让开发者愿意等结果。关掉 CI 或低频运行都放弃了持续集成的价值。
```
