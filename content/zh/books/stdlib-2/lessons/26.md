# 项目设计：智能文件整理器

> 前面五章你学会了一堆零件——时间、路径、文件、归档。这一章把它们装成一台机器：一个能真的整理你下载目录的工具。

## 这个工具要解决什么问题

打开你的"下载"目录，是不是一片混乱？PDF、图片、安装包、压缩包、临时文件全挤在一起。张三的下载目录里有 3000 多个文件，找个合同要翻五分钟。李四的习惯是手动建几个文件夹，每周拖一次，但"视频""电影""clip"三个目录里的东西其实是一类，拖了几次就忘了规则。

**智能文件整理器**的目标：扫一遍目录 → 按规则自动分类 → 把文件移到对应子目录 → 输出一份整理报告。全程不删任何东西，且每一步都可预览、可撤销。

```python
# 最终效果（伪代码）
$ python organize.py ~/Downloads --preview
[预览] 将移动 1284 个文件
  Images/  -> 412 个 (jpg/png/webp)
  Docs/    -> 267 个 (pdf/docx/xlsx)
  Archives/-> 198 个 (zip/tar.gz/7z)
  Media/   -> 96 个 (mp4/mkv/mp3)
  其他/    -> 311 个

$ python organize.py ~/Downloads --apply
✓ 完成，1284 个文件已整理

$ python organize.py ~/Downloads --undo last
✓ 已撤销 1284 个文件的移动
```

## 为什么要分层：四个独立模块

大项目最容易犯的错误是"一个函数写到底"——扫描、分类、移动、记日志全混在一起。这样没法测试，一改就崩。我们把工具拆成四个层，每层只做一件事：

| 模块 | 职责 | 依赖的标准库 | 输入 → 输出 |
|---|---|---|---|
| **Scanner** 扫描层 | 遍历目录、收集文件元信息 | `pathlib`、`os` | 目录路径 → 文件信息列表 |
| **Classifier** 分类层 | 按规则给文件打类别标签 | `pathlib`、`datetime` | 文件信息 → 类别字符串 |
| **Planner** 规则层 | 决定目标路径、处理规则冲突 | `datetime`、`fnmatch` | 文件+规则 → 目标路径 |
| **Executor** 执行层 | 真正移动文件、记日志、支持撤销 | `shutil`、`json`、`tempfile` | 计划 → 操作结果 |

```python
# 数据在层与层之间流动的形态（一个字典，纯净、可序列化）
file_info = {
    "src": "/home/zhangsan/Downloads/合同.pdf",
    "name": "合同.pdf",
    "ext": ".pdf",
    "size": 204800,
    "mtime": "2026-09-20T10:30:00",
}
# Scanner 产出它 → Classifier 加上 "category": "Docs"
#               → Planner 加上 "dest": "Docs/2026-09/合同.pdf"
#               → Executor 真正去移动
```

**关键设计**：前三层都是纯函数——接收数据、返回数据，不碰真实文件系统（测试时）。只有 Executor 才做真实 IO。这就是为什么你能在不读写文件的情况下把核心逻辑测个遍。

## 安全设计：先预览，再执行

文件整理最怕两件事：**误删**和**无法撤销**。真实工具的分水岭就在这里。

**第一原则：永远先做预览（dry-run）。** 默认行为应该是"只告诉我你会做什么"，用户显式加 `--apply` 才真动手。

```python
class Organizer:
    def __init__(self, root):
        self.root = Path(root)
        self.plan = []          # 操作计划
        self.log_path = None    # 日志路径（撤销用）

    def scan(self):        # 层 1
        ...
    def classify(self):    # 层 2
        ...
    def plan_moves(self):  # 层 3
        ...

    def preview(self):
        """只打印，不碰文件"""
        print(f"[预览] 将处理 {len(self.plan)} 个文件")
        by_cat = {}
        for item in self.plan:
            by_cat[item["category"]] = by_cat.get(item["category"], 0) + 1
        for cat, n in sorted(by_cat.items(), key=lambda x: -x[1]):
            print(f"  {cat:<12} -> {n} 个")
        print("\n提示：加 --apply 才会真正执行。")

    def apply(self):       # 层 4
        """先记日志，再逐个移动，失败不中断"""
        ...
```

**第二原则：可撤销靠操作日志。** 每次真正执行前，把完整计划（源路径、目标路径、时间戳）写成一份 JSON 日志。撤销时读取日志，把每个文件移回去。这是第 29 课的重点。

## 翻车现场：先移动、后记录，撤销时日志已经不完整

最常见的错误是把"执行"和"记日志"写成两步，且先执行完再去写日志。一旦中途出错，日志和现实就脱节了。

```python
import shutil, json, os

# WRONG：先移动，最后才统一写日志
def apply_wrong(plan):
    for item in plan:
        shutil.move(item["src"], item["dest"])
    # 如果第 3 个文件移动时抛异常，前面 2 个已经移走，日志还没生成
    with open("ops.log", "w") as f:
        json.dump(plan, f)
    print("日志已写入")

plan = [
    {"src": "a.txt", "dest": "Text/a.txt"},
    {"src": "b.txt", "dest": "Text/b.txt"},
    {"src": "c.txt", "dest": "/root/no_perm/c.txt"},  # 抛 PermissionError
]
apply_wrong(plan)
# Traceback: PermissionError
# 此时 a.txt、b.txt 已移动，ops.log 不存在 → 无法撤销
```

正确做法是**先写日志，再执行**；执行中每完成一步就更新日志状态。这样哪怕中途崩溃，日志本身是完整可信的。第 29 课给出完整实现。

## 翻车现场：原地修改遍历结果

在遍历目录的同时往里创建新子目录，如果处理不当会让扫描层"看到"自己刚建的目录，形成循环或重复分类。

```python
from pathlib import Path

# WRONG：边遍历边建目录，分类时可能把目标目录也算进去
def classify_inplace(root):
    cats = {}
    for p in Path(root).rglob("*"):
        if p.is_file():
            ext = p.suffix.lower()
            if ext in {".jpg", ".png"}:
                cats.setdefault("Images", []).append(p)
            # 如果这一步顺手创建了 Images/，下一次迭代就会扫到它
    return cats

# 正确：扫描和分类完全分离，分类阶段只读不写
def classify_only(files):
    cats = {}
    for f in files:          # files 是已经冻结的列表
        ext = f["ext"]
        if ext in {".jpg", ".png"}:
            cats.setdefault("Images", []).append(f["src"])
    return cats
```

分层设计的另一个好处：**数据先冻结成列表，后续操作不会互相污染**。

这一章的五个文件对应五个功能点，做完就是一个能跑的完整工具：

3. **第 29 课 执行与撤销**：生成计划 → 预览 → 执行 → 写日志 → 撤销
4. **第 30 课 收官**：用 `sys.argv` 串成命令行工具，加进度反馈和异常处理

## 小结

- 整理器四层：Scanner 扫描 → Classifier 分类 → Planner 规则 → Executor 执行
- 前三层是**纯函数**，只处理数据；只有 Executor 做真实 IO，方便测试
- **先预览、后执行**：默认 dry-run，用户显式确认才动手
- **先写日志、再执行**：日志是撤销的唯一依据，绝不能事后补
- 数据在各层之间以字典流动，结构稳定、可序列化
