# Writing for Humans

> Comments don't make programs run faster. They stop you from collapsing three months later. This lesson covers why they matter and how to write them without wasting them.

## What a comment looks like

Write a `#` and Python **completely ignores** everything from there to the end of the line:

```python
# This is a comment, Python can't see it
print("this line runs")   # so is this — comments can trail code
```

Run it and only "this line runs" appears. Comments are sticky notes on the code; only humans can read them.

## What are they actually for? An uncomfortable truth

The conclusion first:

> **Code is read far more often than it is written.**

Every line you write gets read several times by you (while debugging), by colleagues, and by future you. And future you is almost a different person — you'll stare at your own code and think, "what is this?"

Comments are the trail of breadcrumbs you leave for that future self.

### Without comments

```python
d = 30
t = 2.5
v = d / t
print(v)
```

Readable? Barely. `v` is probably speed. But is `d` distance or days? Metres or kilometres?

### With comments

```python
# Average speed from home to the office
d = 30      # distance, in kilometres
t = 2.5     # time taken, in hours
v = d / t   # speed = distance / time
print(v)
```

Not one line of code changed, and now anyone can read it.

## Good comments vs bad comments

This is the real lesson. **More isn't better; being in the right place is.**

### ❌ Bad: restating the code

```python
print("Hello")   # print "Hello"
```

Pure noise. The code already says it prints "Hello"; the comment repeats it and adds a line to maintain.

### ✅ Good: explaining why

```python
# Must be 0.1 here, not an int — the upstream API only accepts floats
price = 0.1
```

**Code says what it does. Comments say why.** "Why" is the one thing code cannot express — that's where comments belong.

### Three genuinely useful kinds

**1. Explain intent**

```python
# Sort by time first — the dedup logic below depends on order
data.sort(key=lambda x: x["time"])
```

**2. Mark work-in-progress**

```python
# TODO: wire this up to the real payment API; fake data for now
```

`TODO` is a convention among programmers meaning "I know this is incomplete, I'll come back."

**3. Temporarily disable code**

While debugging you often want "skip this line and see". Rather than deleting it, comment it out:

```python
print("this runs")
# print("skip this one for now")
print("this runs too")
```

Deleted code is gone forever; commented code is one keystroke from returning. This is by far the **most frequent** use of comments.

## Multi-line comments?

Python has no dedicated block-comment syntax. Two approaches:

**Method 1: `#` on each line (the proper way)**

```python
# Calculates the discounted price
# price is the original, rate is the discount (0.8 = 20% off)
# Returns a value rounded to two decimals
```

**Method 2: triple-quoted string (not technically a comment, but similar in effect)**

```python
"""
Calculates the discounted price
price is the original, rate is the discount
"""
```

Three quotes make a **docstring**, usually written at the top of a function or file as documentation. Technically it's a string; assigned to nothing, it doesn't affect the program — so it looks like a comment.

**Stick with method one for now** — simple, and it can't go wrong.

## Two iron rules

1. **When code changes, the comment changes with it.** A wrong comment is worse than none — it makes you believe something false.
2. **If a good name can say it, don't comment it.** Renaming `d` to `distance_km` beats a comment saying "d is distance" a hundred times over. (Naming is the next chapter.)
