# How Recursion Runs: the Call Stack, the Recursion Tree, and Print Debugging

> The hardest part of recursion is not "writing it" but "seeing what it is doing." This lesson gives you three tools: the call stack, the recursion tree, and indented print. By the end of this lesson recursion will be transparent to you.

## The call stack: functions doing a stack of planks

How does a computer execute recursion? With something called the **call stack**.

Every time a function is called, the system pushes a frame onto the stack containing the function's parameters, local variables, and which line it is executing. **Until the function finishes, its frame stays on the stack.**

Take `factorial(4)` as an example:

```
call factorial(4)   -> stack: [factorial(4)]
  factorial(4) calls factorial(3)
call factorial(3)   -> stack: [factorial(4), factorial(3)]
  factorial(3) calls factorial(2)
call factorial(2)   -> stack: [factorial(4), factorial(3), factorial(2)]
  factorial(2) calls factorial(1)
call factorial(1)   -> stack: [factorial(4), factorial(3), factorial(2), factorial(1)]
  factorial(1) returns 1 <- top of stack pops
  factorial(2) computes 2*1=2 and returns 2 <- pops
  factorial(3) computes 3*2=6 and returns 6 <- pops
  factorial(4) computes 4*6=24 and returns 24 <- pops
stack empty, done.
```

**This is "unwind":** first it keeps pushing downward (expansion), then after reaching the base case it pops back upward (reduction).

The depth of the stack is the depth of the recursion. Factorial `n!` pushes n frames. The deepest chain of Fibonacci `fib(n)` is also n frames deep.

**Key point: stack frames consume memory.** Each layer keeps its own local variables and return address. That is why recursion has a space cost — it is not "free," it eats the stack.

## Watching recursion with print: indentation is depth

The most effective low-tech way to see the order of recursion is **print + indentation**. The indentation equals the recursion depth, so at a glance you know "which layer am I drilling into now."

```python
def factorial(n, depth=0):
    indent = "  " * depth
    print(f"{indent}factorial({n}) called")
    if n <= 1:
        print(f"{indent}-> base case triggered, returning 1")
        return 1
    result = n * factorial(n - 1, depth + 1)
    print(f"{indent}factorial({n}) returns {result}")
    return result

factorial(4)
```

Output:

```
factorial(4) called
  factorial(3) called
    factorial(2) called
      factorial(1) called
      -> base case triggered, returning 1
    factorial(2) returns 2
  factorial(3) returns 6
factorial(4) returns 24
```

**Three things to take away from this output:**

1. **"Called" indents to the right** (the stack is getting deeper).
2. **"Returns" steps back to the left** (the stack is popping).
3. **The return value is only truly computed during the "stepping back" phase** — because `n * factorial(n-1)` must wait for `factorial(n-1)` to return first.

**This technique is your Swiss Army knife for debugging recursion.** No IDE single-stepping, no breakpoints — just indented print, and recursion is transparent in front of you. It is especially useful when writing backtracking, divide-and-conquer, and tree traversals.

## WRONG: printing before return leaves the return value invisible

```python
# WRONG: prints before return, but never stores the result
def factorial(n):
    if n <= 1:
        return 1
    print(f"computing {n} * factorial({n-1})")
    return n * factorial(n - 1)   # <- you never see this layer's result

factorial(4)
```

Output:

```
computing 4 * factorial(3)
computing 3 * factorial(2)
computing 2 * factorial(1)
```

**You cannot see the intermediate results 2, 6, or 24**, because nobody prints the step `return n * factorial(n-1)`. While debugging you will realize "I know which step it reached, but I do not know what it computed at each step."

The correct approach: **store the result in a variable first, print it, then return it.**

```python
def factorial(n, depth=0):
    indent = "  " * depth
    if n <= 1:
        print(f"{indent}base: {n} -> 1")
        return 1
    print(f"{indent}enter: factorial({n})")
    result = n * factorial(n - 1, depth + 1)
    print(f"{indent}exit: factorial({n}) = {result}")
    return result
```

**Rule: a print placed before the recursive call shows "expansion"; a print placed after the recursive call shows "reduction."** Put both in and you get the complete execution trace.

## The recursion tree: what Fibonacci's exponential explosion looks like

The full call tree of `fib(5)`:

```
fib(5)
├── fib(4)
│   ├── fib(3)
│   │   ├── fib(2)
│   │   │   ├── fib(1) -> 1
│   │   │   └── fib(0) -> 0
│   │   └── fib(1) -> 1
│   └── fib(2)
│       ├── fib(1) -> 1
│       └── fib(0) -> 0
└── fib(3)
    ├── fib(2)
    │   ├── fib(1) -> 1
    │   └── fib(0) -> 0
    └── fib(1) -> 1
```

Count the leaf nodes (where the base case returns): 1, 0, 1, 1, 0, 1, 0, 1 — eight in total.

**The tree branches more and more as it goes down, and the number of nodes is roughly 2^n.** That is why `fib(50)` is too slow to be usable: it has to generate an astronomical number of call nodes.

## Measuring Fibonacci's repeated computation with a counter

Talking is not enough. Let us count how many times `fib(n)` is called in total:

```python
call_count = 0

def fib(n):
    global call_count
    call_count += 1
    if n <= 1:
        return n
    return fib(n - 1) + fib(n - 2)

for n in range(11):
    call_count = 0
    result = fib(n)
    print(f"fib({n}) = {result:>3}, calls = {call_count:>4}")
```

Output:

```
fib(0) =   0, calls =    1
fib(1) =   1, calls =    1
fib(2) =   1, calls =    3
fib(3) =   2, calls =    5
fib(4) =   3, calls =    9
fib(5) =   5, calls =   15
fib(6) =   8, calls =   25
fib(7) =  13, calls =   41
fib(8) =  21, calls =   67
fib(9) =  34, calls =  109
fib(10) = 55, calls =  177
```

**`fib(10)` takes 177 calls, but there are only 11 genuinely distinct inputs from 0 to 10.** The remaining 166 calls are all repeated computation. This waste is exponential — `fib(30)` takes 2.69 million calls.

**This experiment is more striking than any abstract explanation: the duplicate nodes on the recursion tree are the enemy of performance.** The memoization and dynamic programming in the next lesson are essentially both "cutting away the duplicate nodes on the recursion tree."

## WRONG: a global counter is never reset, and debug info bleeds across calls

```python
# WRONG: forgot to reset the counter between calls
call_count = 0

def fib(n):
    global call_count
    call_count += 1
    if n <= 1:
        return n
    return fib(n - 1) + fib(n - 2)

fib(5)
print(call_count)   # 15
fib(5)
print(call_count)   # 30 <- not 15! It accumulated!
```

**This is the classic trap of global variables.** You expect the second call to restart from 15, but it keeps accumulating on top of 15. When debugging recursion with a global variable that counts calls or maximum depth, you must reset it before every test.

A better approach is to pass a mutable object (such as a list) as a parameter, avoiding global variables altogether:

```python
def fib(n, counter=None):
    if counter is not None:
        counter[0] += 1
    if n <= 1:
        return n
    return fib(n - 1, counter) + fib(n - 2, counter)

counter = [0]
fib(5, counter)
print(counter[0])   # 15
fib(5, counter)
print(counter[0])   # 30 <- still accumulates, because the same list is passed
# correct: create a new one
counter = [0]
fib(5, counter)
print(counter[0])   # 15
```

**Lesson: helper variables used for recursion debugging must either be passed in as parameters (and re-created each time) or explicitly reset before every call.** Do not rely on global state.

## The two phases of recursion: expansion and reduction

Every recursion has two phases, and this must be etched into your brain:

```
Phase one "expansion": not yet at the base case, keeps calling itself downward
Phase two "reduction": after reaching the base case, returns layer by layer and combines results
```

**Code written before the recursive call belongs to the expansion phase; code written after the recursive call belongs to the reduction phase.**

```python
def example(n, depth=0):
    indent = "  " * depth
    print(f"{indent}[expand] enter {n}")        # <- expansion phase (runs while going down)
    if n <= 0:
        print(f"{indent}[base] return 0")
        return 0
    result = example(n - 1, depth + 1)
    print(f"{indent}[reduce] {n} receives {result}")   # <- reduction phase (runs while going up)
    return result + 1
```

**This "before-and-after ordering" is the lifeblood of backtracking:** making a choice happens in the expansion phase; undoing a choice happens in the reduction phase. Forget to undo and you get the classic crash in lesson 30.

## WRONG: putting a side-effecting operation in the reduction phase causes repeated execution

```python
# WRONG: putting something that should happen only once inside recursion, so it runs repeatedly
results = []

def collect(n):
    if n <= 0:
        return
    collect(n - 1)
    results.append(n)   # <- looks like append happens once? Actually every layer appends

collect(3)
print(results)   # [1, 2, 3]   looks correct
```

In this example the result happens to be right. But if you change it to `print`:

```python
def show(n):
    if n <= 0:
        return
    show(n - 1)
    print(n)   # reduction phase: 1 2 3

show(3)
```

The output is `1 2 3`. **If you think "the reduction phase runs once per layer," congratulations, you got it right.** The reduction phase really does run once per layer, and so does the expansion phase. Each layer of recursion only executes its own code once — the problem was never "how many times does it run," but "how many layers did you build."

**The truly easy mistake is the opposite: putting a side-effecting operation in the wrong phase, so the order is not what you expected.** If you print first and recurse second (printing in the expansion phase), the result is `3 2 1`. If you recurse first and print second (printing in the reduction phase), the result is `1 2 3`. **The order difference between pre-order and post-order traversal has its roots right here.**

## Summary

- Recursion runs on the **call stack**: each call pushes a frame, and returning pops it; stack depth equals recursion depth.
- Stack frames consume memory, so recursion has a space cost and is not free.
- **Print + indentation** is the most effective way to debug recursion: indentation equals depth, making the execution trace clear at a glance.
- Recursion has two phases: **expansion** (before the recursive call) and **reduction** (after the recursive call).
- The number of nodes in the recursion tree determines the time cost; fib's tree is 2^n-sized, and its slowness comes from duplicate nodes.
- Global counters used for debugging must be reset before every test, otherwise results accumulate and bleed across calls.

answer: 0
