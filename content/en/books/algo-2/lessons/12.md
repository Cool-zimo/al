# Matching Parentheses: The Textbook Use of a Stack

> Given a string of brackets, decide whether they close correctly. This is the interview "entry ticket" for stacks, and a textbook demonstration of the "nearest match" idea.

## Why a Stack Is the Right Tool

A closing bracket `)` must match the **nearest unmatched opening bracket to its left**. "Nearest" is exactly what a stack is good at—the top is always the last thing added.

> On an opening bracket → push. On a closing bracket → pop the top and check whether they match.

Could you use something else? A counter works for **one kind** of bracket: increment on `(`, decrement on `)`, and accept when the result is zero. But the moment `()`, `[]`, and `{}` are mixed, counting fails:

```
([)]    <- a counter accepts it (two opens, two closes), but it is clearly invalid
```

So **a stack is the only clean solution.**

## The Core Algorithm in Three Lines

```python
def is_valid(s: str) -> bool:
    pair = {')': '(', ']': '[', '}': '{'}   # closing -> opening map
    stack = []
    for ch in s:
        if ch in pair:            # it is a closing bracket
            if not stack:         # stack is empty, so there is no opener to match
                return False
            if stack.pop() != pair[ch]:
                return False      # the types do not match
        else:                     # it is an opening bracket
            stack.append(ch)
    return len(stack) == 0        # the stack must be empty, or an opener is left over
```

**Trace `({[]})` character by character:**

```
(  -> push      stack: ['(']
{  -> push      stack: ['(', '{']
[  -> push      stack: ['(', '{', '[']
]  -> pop [     matches, stack: ['(', '{']
}  -> pop {     matches, stack: ['(']
)  -> pop (     matches, stack: []
end, stack empty -> True
```

Now trace the invalid `([)]`:

```
(  -> push   ['(']
[  -> push   ['(', '[']
)  -> pop [    but pair[')'] is '(', so [ != (, fail
```

The type check catches it on the spot.

## Three Boundaries You Must Handle

### 1. A Closing Bracket Meets an Empty Stack → Return False Immediately

```python
if ch in pair:
    if not stack:          # no opening bracket available
        return False
    ...
```

Skip this check and `stack.pop()` raises `IndexError`.

### 2. The Stack Must Be Empty at the End

```python
return len(stack) == 0
```

Skip this and `((` is wrongly accepted.

### 3. Only Opening Brackets Go on the Stack

Closing brackets never get pushed—they only trigger pops and comparisons. The most common beginner mistake is pushing every character, including the closers.

## # WRONG 1 — Forgetting to Check for an Empty Stack Before Popping

```python
# WRONG
def is_valid_bad(s):
    stack = []
    pair = {')':'(', ']':'[', '}':'{'}
    for ch in s:
        if ch in pair:
            if stack.pop() != pair[ch]:   # no check for an empty stack
                return False
        else:
            stack.append(ch)
    return len(stack) == 0

is_valid_bad(")(")
```

Error:

```
Traceback (most recent call last):
  File "<stdin>", line 1, in <module>
  File "<stdin>", line 6, in is_valid_bad
IndexError: pop from empty stack
```

The input `")("` begins with a closer, so the stack is empty. You must test `if not stack: return False` first.

## # WRONG 2 — The Loop Finishes but the Stack Is Not Checked

```python
# WRONG
def is_valid_bad2(s):
    stack = []
    pair = {')':'(', ']':'[', '}':'{'}
    for ch in s:
        if ch in pair:
            if not stack: return False
            stack.pop()
        else:
            stack.append(ch)
    return True          # wrong! the leftover openers are ignored

print(is_valid_bad2("(("))    # True (wrong!)
print(is_valid_bad2("(()"))   # True (wrong!)
```

Any surplus opening bracket slips through. **Both conditions are required:** a mid-loop empty-stack rejection, and an end-of-loop empty-stack acceptance.

## # WRONG 3 — Pushing Closing Brackets Too

```python
# WRONG
stack = []
for ch in s:
    stack.append(ch)         # every character goes on the stack
# then try to "compare from start to finish" -- there is no sensible way to do it
```

The stack now holds closing brackets, so you can neither use it for nearest-neighbor matching nor preserve the "an opener waits for a closer" semantics. The correct branch is `else: stack.append(ch)`—only openers are pushed.

## Variant 1: The Longest Valid Parentheses Substring

LeetCode 32. The trick is to store **indices** in the stack, not characters:

```python
def longest_valid(s):
    stack = [-1]          # anchor index, used to measure lengths
    ans = 0
    for i, ch in enumerate(s):
        if ch == '(':
            stack.append(i)
        else:
            stack.pop()
            if not stack:          # popped the anchor, so this ) has no match
                stack.append(i)    # start a new anchor here
            else:
                ans = max(ans, i - stack[-1])   # current valid length
    return ans
```

Why store indices? Because length equals `current position - position of the last unmatched bracket`, and that position is exactly what sits at the top of the stack.

## Variant 2: Generate All Valid Parentheses

LeetCode 22. Surprisingly, this one **does not need a stack**—backtracking plus two counters is enough:

```python
def generate(n):
    res = []
    def backtrack(path, left, right):
        if len(path) == 2 * n:
            res.append(path); return
        if left < n:                    # openers still available
            backtrack(path + '(', left + 1, right)
        if right < left:                # can only add a closer when one is pending
            backtrack(path + ')', left, right + 1)
    backtrack('', 0, 0)
    return res
```

The condition `right < left` guarantees that at no point can there be more closers than openers—two counters do the work a stack would have done.

## Complexity

| Metric | Value |
|---|---|
| Time | O(n), each character is pushed and popped at most once |
| Space | O(n), worst case is all opening brackets |

## Why This Pattern Keeps Repeating

Once you see the structure, the same idea shows up in HTML/XML tag matching, in matching `begin`/`end` blocks in a compiler, in matching transactions in a log file, and in any parser that needs to know which opening token a closing token belongs to. The invariant is always: **the most recent unmatched opener is the one that must close next.** That is the stack's contract in one sentence.

## Summary

- Matching parentheses is the classic "nearest match" stack problem.
- Push openers, pop the top on a closer and compare; empty stack or type mismatch means failure.
- **Three boundaries, none optional:** check for an empty stack, check the types, check that the stack is empty at the end.
- Only openers go on the stack; closers only pop and compare.
- Storing indices instead of characters solves "longest valid parentheses substring."
- When the job is generation rather than validation, two counters and backtracking are enough—no stack required.
