# Collisions and Resolution: Separate Chaining, Open Addressing, Load Factor, and Resizing

> Collisions are the destiny of hash tables — squeezing an infinite world into a finite array guarantees a crash. But how you handle the crash decides whether your hash table is fast or slow.

## Collisions: An Inevitable Destiny

Recall last lesson's core formula: `index = hash(key) % table_size`.

Here's the problem: **table_size is finite (say 10), but the possible keys are infinite (every string).** By the pigeonhole principle, different keys must eventually map to the same index.

```python
hash("Alice") % 10 = 3
hash("Carol") % 10 = 3   # crash!
```

This is a **collision**.

**Collisions aren't scary; handling them poorly is.**

## Method 1: Separate Chaining

Instead of storing one element per array slot, each slot holds a **linked list** (a Python list). Every key that maps to the same index hangs off that list.

```
index = hash(key) % 10

table[3] -> [("Alice", 95), ("Carol", 88), ("Dave", 72)]
              ^ three keys all mapped to index 3

Looking up "Carol": hash("Carol") % 10 = 3 -> table[3] -> scan the list -> found
```

Implementation:

```python
class ChainingHash:
    def __init__(self, size=8):
        self.size = size
        self.table = [[] for _ in range(size)]
    
    def _hash(self, key):
        return sum(ord(c) for c in key) % self.size
    
    def put(self, key, value):
        idx = self._hash(key)
        # scan the bucket for an existing key
        for i, (k, v) in enumerate(self.table[idx]):
            if k == key:
                self.table[idx][i] = (key, value)  # update
                return
        self.table[idx].append((key, value))  # insert new
    
    def get(self, key):
        idx = self._hash(key)
        for k, v in self.table[idx]:
            if k == key:
                return v
        return -1

h = ChainingHash()
h.put("Alice", 95)
h.put("Carol", 88)
print(h.get("Alice"))   # 95
```

**Pros**: simple to implement, easy deletion, and severe collisions only make the list longer.
**Cons**: extra pointer/list overhead; a long list degrades to O(n).

## Method 2: Open Addressing

Instead of adding a linked list, **when a collision occurs, look for the next empty slot.**

```
table[3] is occupied -> try table[4]
table[4] is also occupied -> try table[5]
table[5] is empty -> place it there!
```

```python
class OpenAddressingHash:
    def __init__(self, size=8):
        self.size = size
        self.table = [None] * size
    
    def _hash(self, key):
        return sum(ord(c) for c in key) % self.size
    
    def put(self, key, value):
        idx = self._hash(key)
        # linear probing: scan forward for an empty slot
        while self.table[idx] is not None:
            idx = (idx + 1) % self.size
        self.table[idx] = (key, value)
    
    def get(self, key):
        idx = self._hash(key)
        while self.table[idx] is not None:
            k, v = self.table[idx]
            if k == key:
                return v
            idx = (idx + 1) % self.size
        return -1

h = OpenAddressingHash()
h.put("Alice", 95)
h.put("Carol", 88)  # suppose this also maps to 3, so it goes to 4
print(h.get("Alice"))   # 95
```

**Pros**: no extra linked-list nodes, cache-friendly (data is stored contiguously), saves memory.
**Cons**: deletion is hard (you can't simply set to None, or you break the probe chain), and it suffers from "clustering."

## Comparing the Two Methods

| Feature | Separate chaining | Open addressing |
|---|---|---|
| Implementation | simple | harder (deletion is tricky) |
| Memory overhead | one extra pointer per node | no extra overhead |
| Cache friendly | no (nodes scattered) | yes (contiguous) |
| Max load factor | can exceed 1 | must stay below 1 |
| Deletion | simple (remove a list node) | complex (needs tombstones) |

**Python's `dict` uses open addressing.** Java's `HashMap` used separate chaining before JDK8; with severe collisions, the list becomes a red-black tree.

## Load Factor: When to Resize

**Load factor = number of stored elements / array capacity**

```python
load_factor = len(hash_table) / table_size
```

- Load factor 0.5 -> average 0.5 elements per bucket, comfortable
- Load factor 1.0 -> average 1 element per bucket, getting tight
- Load factor 2.0 -> average 2 elements per bucket, lists start growing

**Higher load factor -> more collisions -> worse performance.**

```python
# Intuition
table_size = 10
num_elements = 10
load_factor = 1.0
# With a perfect hash, every bucket holds exactly 1 element

num_elements = 50
load_factor = 5.0
# Average 5 elements per bucket -> lookup scans 5 -> O(1) drifts toward O(5)
# But if distribution is uneven, some buckets may hold 10+ elements
```

**Rules of thumb:**
- Separate chaining: resize when load factor > 0.75
- Open addressing: resize when load factor > 0.5~0.7

## Resizing: The Costly "Move"

Resizing isn't just making the array bigger — it's **rehashing every element**.

```python
def resize(self):
    old_table = self.table
    self.size *= 2
    self.table = [[] for _ in range(self.size)]
    for bucket in old_table:
        for key, value in bucket:
            self.put(key, value)  # recompute hash % new_size
```

**Why must we rehash?** Because `hash(key) % old_size ≠ hash(key) % new_size`.

```python
key = "Alice"
old_size = 8
new_size = 16
hash(key) % 8   # maybe 3
hash(key) % 16  # maybe 11, completely different!
```

**Resizing costs O(n)** — every element moves in one shot. But amortized across all insertions, the average stays O(1).

**That's why insertion is amortized O(1): an occasional O(n) resize is spread across many O(1) operations.**

## WRONG: Modifying a dict During Iteration

```python
# WRONG: adding keys while iterating can raise RuntimeError or loop forever
d = {"a": 1, "b": 2, "c": 3}
for k in d:
    if k == "b":
        d["d"] = 4   # In Python 3 this raises RuntimeError
```

Actual output:

```python
d = {"a": 1, "b": 2, "c": 3}
for k in d:
    if k == "b":
        d["d"] = 4
# RuntimeError: dictionary changed size during iteration
```

**The fix:**

```python
# RIGHT: collect changes first, then apply them
d = {"a": 1, "b": 2, "c": 3}
to_add = {}
for k in d:
    if k == "b":
        to_add["d"] = 4

d.update(to_add)
print(d)   # {'a': 1, 'b': 2, 'c': 3, 'd': 4}
```

Or use `list(d.keys())` to iterate over a snapshot:

```python
d = {"a": 1, "b": 2, "c": 3}
for k in list(d.keys()):
    if k == "b":
        d["d"] = 4   # safe, iterating over a copy
```

## WRONG: Deleting from Open Addressing by Setting to None

```python
# WRONG: setting to None breaks the probe chain
h = OpenAddressingHash(size=5)
h.put("a", 1)   # suppose it maps to index 0
h.put("f", 2)   # suppose it also maps to 0, probes to index 1
# table: [(a,1), (f,2), None, None, None]

h.table[0] = None  # delete "a"
# table: [None, (f,2), None, None, None]

h.get("f")  # starts probing at index 0; index 0 is None -> "not found" -> returns -1!
# But "f" is clearly at index 1!
```

**The fix: use a tombstone marker**

```python
class OpenAddressingHashV2:
    DELETED = object()  # tombstone marker
    
    def delete(self, key):
        idx = self._hash(key)
        while self.table[idx] is not None:
            if self.table[idx] is self.DELETED:
                idx = (idx + 1) % self.size
                continue
            k, v = self.table[idx]
            if k == key:
                self.table[idx] = self.DELETED  # mark as deleted, don't break the chain
                return
            idx = (idx + 1) % self.size
    
    def get(self, key):
        idx = self._hash(key)
        while self.table[idx] is not None:
            if self.table[idx] is not self.DELETED:
                k, v = self.table[idx]
                if k == key:
                    return v
            idx = (idx + 1) % self.size
        return -1
```

**A tombstone is just a "something was deleted here" placeholder — the probe chain stays intact.** But too many tombstones also need cleaning up (rebuilding the table).

## WRONG: Order Changes After Resizing

```python
d = {}
for i in range(100):
    d[i] = i

# Traversal order depends on the internal layout
keys_before = list(d.keys())

d[99999] = 99999  # may trigger a resize

keys_after = list(d.keys())
# keys_before and keys_after may be in completely different orders!
```

**Real-world impact**: Python 3.7+ guarantees insertion order, but **resizing/rebuilding rearranges internal storage**, so traversal order can change. Don't write business logic that depends on traversal order (unless all you need is "insertion order").

## Summary

- Collisions are unavoidable: a finite array holding infinite keys, the pigeonhole principle guarantees collisions
- Separate chaining: each bucket hangs a linked list; simple, easy deletion
- Open addressing: on collision, linearly probe for the next empty slot; memory-efficient but deletion is hard (needs tombstones)
- Python's dict uses open addressing; Java's HashMap uses separate chaining (JDK8+ converts to red-black tree)
- Load factor = elements / capacity; resize past the threshold (0.5~0.75)
- Resizing = rehash every element; O(n) but amortized to O(1) per insertion
- Modifying a dict during iteration raises RuntimeError; never set an open-addressing slot to None on deletion
