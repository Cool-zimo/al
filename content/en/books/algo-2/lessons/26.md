# Recursion's Three Elements: Base Case, Recursive Relation, and Return Value

> Recursion is not just "a function that calls itself." To write a correct recursive function you only need to answer three questions clearly: when to stop, how to break the big problem into a smaller one, and what to bring back once the smaller one is solved.

## A function calling itself — what is actually happening?

Before any definitions, look at an example you have certainly written before:

```python
def factorial(n):
    if n <= 1:
        return 1
    return n * factorial(n - 1)

print(factorial(5))   # 120
```

`factorial(5)` returns `5 * factorial(4)`. That one returns `4 * factorial(3)`. It keeps drilling down until `factorial(1)` returns 1 directly, and then the multiplications unwind one layer at a time.

**The essence of recursion: turn a "big problem" into a "slightly smaller version of the same problem" until it is so small that no further splitting is needed.**

Recursion is not the same thing as a loop. A loop "repeats the same action"; recursion "keeps calling the same function to solve a smaller self." Some loops can be written recursively and some cannot; some recursions are naturally iterative but not necessarily better that way. The first step to understanding recursion is to accept how counter-intuitive it feels: **a function calls itself before it has finished being written.**

## Element one: the base case

The most urgent concern in recursion is "being able to stop." The branch that makes the recursion stop calling itself is the **base case**.

For factorial the base case is `n <= 1`, which returns 1. For Fibonacci it is `n <= 1`, which returns `n` itself. Without a base case the recursion keeps drilling until Python stops it for you.

```python
def factorial(n):
    if n <= 1:        # ← base case
        return 1
    return n * factorial(n - 1)
```

**How do you find the base case?** Ask yourself: what is the smallest, simplest version of this problem whose answer is obvious at a glance?

- Factorial: `factorial(1)` and `factorial(0)` are both 1; no more splitting needed.
- Fibonacci: `fib(0) = 0`, `fib(1) = 1` are the starting points of the sequence.
- List sum: `sum([])` is 0; an empty list needs no further splitting.

**A wrong base case is more dangerous than no base case at all**, because the program may run and even produce output — only the output is wrong.

## Element two: the recursive relation

The recursive relation is "how the big problem becomes a smaller problem." It decides the **shape** of the recursion: linear, tree-like, or branching.

**Factorial is linear**: `n! = n × (n-1)!`

```python
def factorial(n):
    if n <= 1:
        return 1
    return n * factorial(n - 1)   # ← this is the recursive relation
```

Each layer calls itself exactly once, forming a chain. Computing `factorial(5)` takes 5 layers, so time is O(n) and space is O(n) (because each layer occupies a stack frame).

**Fibonacci is tree-shaped**: `F(n) = F(n-1) + F(n-2)`

```python
def fib(n):
    if n <= 1:
        return n                 # ← base case
    return fib(n - 1) + fib(n - 2)   # ← one call becomes two!
```

Each layer calls **two** versions of itself. This is the recursion tree, and it explodes exponentially.

## WRONG: forgetting the base case ends in RecursionError

```python
# WRONG: no base case
def factorial(n):
    return n * factorial(n - 1)   # calls forever, never stops

print(factorial(5))
```

Error output:

```
RecursionError: maximum recursion depth exceeded
```

Python's default recursion limit is 1000 (you can check it with `sys.getrecursionlimit()`). **This is not Python being stingy; it is Python protecting you** — infinite recursion keeps consuming memory until the program crashes. Python cuts you off at 1000 frames, which is much gentler than running out of memory for real.

**The real trap is that missing a base case can look completely normal.** The indentation, syntax, and logic are all fine; you just forgot those two lines of `if`. The compiler cannot catch this bug. You have to think through "where is the boundary" yourself.

## Element three: the return value

A recursive function **must have a return value** (unless it exists purely for side effects). And the return value of each layer must be **used by the layer above it**.

Watch how the return value flows back through factorial:

```
factorial(5)
= 5 * factorial(4)
= 5 * (4 * factorial(3))
= 5 * (4 * (3 * factorial(2)))
= 5 * (4 * (3 * (2 * factorial(1))))
= 5 * (4 * (3 * (2 * 1)))
= 5 * (4 * (3 * 2))
= 5 * (4 * 6)
= 5 * 24
= 120
```

**The return value is "wrapped" inside the outermost expression.** If you casually write `factorial(n - 1)` but forget to `return` it, the upper layer receives `None`, and the whole expression explodes.

## WRONG: forgetting return yields None and then TypeError

```python
# WRONG: the recursive branch has no return
def factorial(n):
    if n <= 1:
        return 1
    n * factorial(n - 1)   # ← it is computed, but not returned! Returns None

print(factorial(5))
```

Error output:

```
TypeError: unsupported operand type(s) for *: 'int' and 'NoneType'
```

The expression `n * factorial(n - 1)` does produce a result, but **it is never handed to `return`**, so the function returns `None` by default. The layer above then receives `None` and tries to compute `4 * None`, immediately raising `TypeError`.

**This trap is especially sneaky** because every deeper layer actually "computed correctly"; only the result was never passed back. When you single-step through it you will see that the deepest call returns 1, but the layer above receives `None`. **Whenever you see a `NoneType` error in recursion, check first whether you forgot a `return`.**

## Fibonacci: a beautiful but painfully slow recursion

```python
def fib(n):
    if n <= 1:
        return n
    return fib(n - 1) + fib(n - 2)

for i in range(10):
    print(f"fib({i}) = {fib(i)}")
```

Output:

```
fib(0) = 0
fib(1) = 1
fib(2) = 1
fib(3) = 2
fib(4) = 3
fib(5) = 5
fib(6) = 8
fib(7) = 13
fib(8) = 21
fib(9) = 34
```

The sequence is correct. But how slow is it?

## WRONG: fib(50) takes half a minute

```python
import time

def fib(n):
    if n <= 1:
        return n
    return fib(n - 1) + fib(n - 2)

t0 = time.time()
print(fib(35))        # 9227465
print(f"took {time.time() - t0:.2f} seconds")
```

Output (machine-dependent):

```
9227465
took 1.83 seconds
```

`fib(40)` takes roughly ten seconds; `fib(50)` can make you question your life choices. Why?

## The recursion tree: why fib is O(2^n)

Draw the call process of `fib(5)` as a tree:

```
                        fib(5)
                     /            \
              fib(4)              fib(3)
             /      \             /     \
        fib(3)      fib(2)    fib(2)   fib(1)
       /    \       /   \     /   \
  fib(2) fib(1) fib(1) fib(0) fib(1) fib(0)
  /   \
fib(1) fib(0)
```

**Notice that `fib(3)` is computed twice and `fib(2)` is computed three times.** The same input, the same computation, repeated over and over. This tree has roughly 2^n nodes (strictly about 1.618^n — the golden-ratio root — but asymptotically it is O(2^n)).

**Each time n grows by 1, the running time almost doubles.** That is the horror of exponential explosion: n=5 takes microseconds, while n=50 needs hundreds of millions of calls.

**Key insight: it is slow not because of recursion, but because of repeated computation.** The next lesson shows how "memoization" rescues fib from O(2^n) back to O(n) — that is the core idea behind dynamic programming. For now, just remember: **if the same subproblem is solved over and over during recursion, that is the root of the slowness.**

## Linear recursion vs tree recursion

| Feature | Factorial `factorial` | Fibonacci `fib` |
|---|---|---|
| Calls per layer | 1 | 2 |
| Recursion shape | A chain | A tree |
| Time complexity | O(n) | O(2^n) |
| Space complexity | O(n) (stack depth) | O(n) (deepest chain) |
| Repeated computation? | No | Yes, severely |

**The same recursion can differ in performance by an exponential factor.** The only difference is "how many times does each layer call itself."

## WRONG: the wrong type of n causes infinite recursion

```python
# WRONG: a float is passed in, and n never equals 1
def factorial(n):
    if n == 1:        # ← using == instead of <=, and a float may never reach 1
        return 1
    return n * factorial(n - 1)

print(factorial(5.0))
```

`5.0 - 1` is fine, but if the argument is `5.1` it keeps subtracting: `4.1, 3.1, 2.1, 1.1, 0.1, -0.9...` It never equals 1, and you get a RecursionError.

**Even with the argument `5.0`, this style is fragile.** A better base case is `if n <= 1` or `if n in (0, 1)`, and normally a recursive function should agree to "accept only non-negative integers." If you are writing a general-purpose utility, validating the input should be the first thing you do:

```python
def factorial(n):
    if not isinstance(n, int) or n < 0:
        raise ValueError("factorial accepts only non-negative integers")
    if n <= 1:
        return 1
    return n * factorial(n - 1)
```

**Defensive programming matters especially in recursion**, because one illegal input propagates all the way down until it blows up.

## Three-element quick reference

Before you write any recursive function, answer these three questions in order:

1. **Base case**: what is the smallest case that needs no further splitting? What should it return?
2. **Recursive relation**: how do you break the big problem into a slightly smaller self? How many times do you call?
3. **Return value**: how is each layer's result used by the layer above? Must it be `returned`?

**Answer these three and recursion is more than half solved.** What remains is the code — and the most error-prone parts of the code are always "forgot the return" and "the base case is wrong or missing."

## Summary

- The three elements of recursion are the **base case** (stop), the **recursive relation** (split), and the **return value** (combine).
- The base case is recursion's "brake." Miss it and you get `RecursionError: maximum recursion depth exceeded`.
- Forgetting `return` is the sneakiest trap; it shows up as `TypeError: NoneType`, because the upper layer received `None`.
- Factorial is linear recursion (one call per layer), O(n). Naive Fibonacci is tree recursion (two calls per layer), O(2^n).
- The root cause of slow tree recursion is **recomputing the same subproblem**; `fib(3)` and `fib(2)` are solved again and again.
- Recursion parameters need defensive validation: floats and negative numbers can prevent the base case from ever triggering.

  def sum_list(nums):

      return 0

- assert sum_list([1, 2, 3, 4, 5]) == 15
- assert sum_list([]) == 0
- assert sum_list([7]) == 7
- assert sum_list([-1, -2, -3]) == -6
hint: The base case is nums == [], which returns 0. The recursive relation is nums[0] + sum_list(nums[1:]).
