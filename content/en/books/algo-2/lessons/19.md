# Monotonic Queues: Sliding Window Maximum

> Given an array and a window size k, slide the window from left to right and ask "what's the maximum in the window" each time. Brute force is O(nk); a monotonic queue is O(n) — each element enters and leaves the queue exactly once.

## The Problem

```
nums = [1, 3, -1, -3, 5, 3, 6, 7], k = 3

Sliding process:
[1  3  -1] -3  5  3  6  7  -> max = 3
 1 [3  -1  -3] 5  3  6  7  -> max = 3
 1  3 [-1  -3  5] 3  6  7  -> max = 5
 1  3  -1 [-3  5  3] 6  7  -> max = 5
 1  3  -1  -3 [5  3  6] 7  -> max = 6
 1  3  -1  -3  5 [3  6  7] -> max = 7

Output: [3, 3, 5, 5, 6, 7]
```

Brute force: scan k elements for the maximum in every window. There are n-k+1 windows, each O(k), for a total of **O(nk)**. With n=10⁵, k=10⁵, that's 10¹⁰ operations — guaranteed TLE.

## Core Idea: Keep Only the "Promising" Candidates

The key insight of a monotonic queue: **if a small value sits in the window while a larger value is to its left, that small value can never be the maximum as long as the larger value is still alive.**

In other words: **while the big value is alive, the small value has no reason to exist.**

```python
from collections import deque

def max_sliding_window(nums, k):
    q = deque()              # stores INDICES; values decrease from front to back
    result = []

    for i, x in enumerate(nums):
        # 1) maintain monotonicity: only indices with values > x deserve to stay
        #    if the value at the back <= x, it can never be max while x is alive
        while q and nums[q[-1]] <= x:
            q.pop()
        q.append(i)

        # 2) remove the stale element at the front (it slid out of the window)
        if q[0] == i - k:
            q.popleft()

        # 3) once the window has formed, the front is the current maximum
        if i >= k - 1:
            result.append(nums[q[0]])

    return result
```

**Trace it by hand** with `nums = [1, 3, -1, -1, 5, 3, 6, 7]`, `k = 3`:

```
i=0, x=1:  q empty, enqueue [0]             window not formed
i=1, x=3:  nums[0]=1<=3, pop 0, enqueue [1]   window not formed
            (3 beats 1, so 1 can never be the maximum)
i=2, x=-1: nums[1]=3>-1, don't pop, enqueue [1,2]  window formed! front nums[1]=3 -> [3]
i=3, x=-1: nums[2]=-1<=-1, pop 2, enqueue [1,3]    front nums[1]=3 -> [3,3]
            (-1<=-1 pops index 2 because when two values tie, the older one
             expires sooner)
i=4, x=5:  nums[3]=-1<=5, pop 3; nums[1]=3<=5, pop 1; enqueue [4]
            front nums[4]=5 -> [3,3,5]
i=5, x=3:  nums[4]=5>3, don't pop, enqueue [4,5]   front nums[4]=5 -> [3,3,5,5]
i=6, x=6:  nums[5]=3<=6, pop 5; nums[4]=5<=6, pop 4; enqueue [6]
            front nums[6]=6 -> [3,3,5,5,6]
i=7, x=7:  nums[6]=6<=7, pop 6; enqueue [7]        front nums[7]=7 -> [3,3,5,5,6,7]
Result: [3, 3, 5, 5, 6, 7]
```

## Why It's O(n): Each Element Enters and Leaves Once

| Operation | Frequency | Reason |
|---|---|---|
| `while q and ...: q.pop()` | at most n total | each element is popped at most once |
| `q.append(i)` | exactly n times | each element enters once |
| `q.popleft()` | exactly n times | each element becomes the front at most once |

Even though the while loop looks nested, **all pop operations combined don't exceed n** — because each element enters once and is popped at most once. That's what "amortized O(1)" means. Total complexity: **O(n)**.

Compared to O(nk) brute force, the gap is enormous when k is large.

## WRONG: Storing Values Instead of Indices

```python
# WRONG: storing values in the queue
q = deque()
for x in nums:
    while q and q[-1] <= x:
        q.pop()
    q.append(x)          # storing the VALUE
    # problem: how do you know whether the front has slid out of the window?
    # You have no idea WHERE in the array the front value appeared!
```

**The fatal flaw of storing values**: you can't tell whether the front element has slid out of the window. The same value can appear multiple times, and you won't know which occurrence to remove.

```python
# RIGHT: store INDICES
q = deque()
for i, x in enumerate(nums):
    while q and nums[q[-1]] <= x:
        q.pop()
    q.append(i)              # store the INDEX
    # check expiration: has the front index slid out?
    if q[0] == i - k:
        q.popleft()
    # the value at the front index is the maximum
```

**Storing indices gives you both: `nums[front]` for the value, and the index itself for the expiration check.**

## WRONG: Getting the Expiration Condition Wrong

```python
# WRONG: using q[0] < i - k (strict less-than)
if q[0] < i - k:
    q.popleft()
# When q[0] == i - k, that element sits exactly one spot to the left of the window.
# The window is [i-k+1, i-k+2, ..., i], so its left boundary is i-k+1.
# q[0] == i-k means it's already outside!

# WRONG2: using q[0] <= i - k + 1 (overthinking it)
# The correct condition: remove when the front index is <= i - k

# RIGHT: q[0] == i - k is the exact moment it expires
if q[0] <= i - k:
    q.popleft()
```

**Memory aid**: the window covers indices `[i-k+1, i]`. If the front index is `<= i-k`, it's to the left of the window and must go.

## WRONG: Mixing Up `<` and `<=`

```python
# Does it matter whether you use <= or < ? It depends on whether you keep ties
while q and nums[q[-1]] <= x:   # using <= : also pop equal values
    q.pop()
```

For the sliding-window maximum problem, both `<=` and `<` work, but they mean different things:

- `<=`: old equal values get popped, so the queue holds no duplicates. The new element sits further right and lives longer, so popping the old one is reasonable.
- `<`: equal values stay in the queue. The answer is still correct, because the front still yields the maximum.

**But if you use `<` and the problem requires strict monotonicity, duplicates in the queue can break later logic.** Stick with `<=` to keep things strictly monotonic.

## Monotonic Queue vs. Heap (Chapter 6)

You may have learned to solve sliding-window maximum with a **max-heap**:

| Method | Insert | Get max | Remove expired | Total |
|---|---|---|---|---|
| Brute force | O(1) | O(k) | — | O(nk) |
| Max-heap | O(log k) | O(1) | O(log k) lazy delete | O(n log k) |
| **Monotonic queue** | amortized O(1) | O(1) | O(1) | **O(n)** |

**The monotonic queue's advantage**: it doesn't just track "who's the current max" — it exploits the **sequential nature** of a sliding window. The window moves one slot at a time, so you can precisely keep the "promising candidates" and pre-emptively discard the "hopeless" ones. A heap can't do that.

**When to use which?**
- Fixed window size, only need max/min -> monotonic queue O(n) is optimal
- Variable window size, or need the Kth largest -> heap is more flexible

## Complexity

| Metric | Value |
|---|---|
| Time | **O(n)** — each element enters and leaves once |
| Space | **O(k)** — the queue holds at most k elements |

The leap from O(nk) to O(n) comes from eliminating the inner loop that scans for the maximum in every window.

## Summary

- Monotonic queue = elements stay monotonically decreasing (front to back)
- **The front is always the current window's maximum** — O(1) access
- Maintain two things: (1) before enqueueing, kick out every back element `<= x`; (2) popleft the front when it expires
- **Store indices**, because you must detect when elements slide out of the window
- Each element enters and leaves once — amortized O(1), total O(n)
- Monotonic queue beats heap when the window is fixed and you only need max/min
