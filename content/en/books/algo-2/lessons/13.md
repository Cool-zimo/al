# Monotonic Stack: Next Greater Element

> The question is: for every element, "who is the first element to my right that is bigger than me?" Brute force is O(n²); a monotonic stack does it in one pass at O(n). It is the most elegant use of a stack — the elements inside stay monotonic.

## The Problem

Given `nums = [2, 1, 2, 4, 3]`, for each element find the **first element to its right** that is larger. If none exists, put `-1`.

```
index:  0   1   2   3   4
value:  2   1   2   4   3
answer: 4   2   4  -1  -1
```

The brute-force way: scan rightward from every element. O(n²). Can we do better? Yes — with a **monotonic stack**.

## Core Idea: Keep the "Waiting" Elements on the Stack

Think about it from a different angle. As we walk left to right, we maintain a stack. **The stack holds the indices of elements that are still waiting for a larger element to claim them**, and the values at those indices are in **strictly decreasing** order (from bottom to top).

Why must they be decreasing? Because as soon as a new element is smaller than the top, it cannot claim the top — it has to push itself on and keep waiting. This is exactly the LIFO semantics of a stack at work.

```python
def next_greater(nums):
    n = len(nums)
    ans = [-1] * n
    stack = []                      # stores indices; bottom->top values decrease
    for i, x in enumerate(nums):
        while stack and nums[stack[-1]] < x:   # ★ current x can claim the top
            j = stack.pop()
            ans[j] = x                          # x is the next greater for nums[j]
        stack.append(i)
    return ans
```

Hand trace `nums = [2, 1, 2, 4, 3]`:

```
i=0,x=2  stack empty, push         stack:[0]          (values[2])
i=1,x=1  nums[0]=2>1, no pop      stack:[0,1]        (values[2,1])
i=2,x=2  nums[1]=1<2 -> pop j=1, ans[1]=2   stack:[0]
         nums[0]=2<2? no, equal, skip       stack:[0,2]      (values[2,2])
i=3,x=4  nums[2]=2<4 -> pop j=2, ans[2]=4   stack:[0]
         nums[0]=2<4 -> pop j=0, ans[0]=4   stack:[]
         push                                  stack:[3]
i=4,x=3  nums[3]=4>3, no pop                   stack:[3,4]
done: unclaimed indices stay -1 -> ans[3]=ans[4]=-1
ans = [4, 2, 4, -1, -1]
```

## Why the Popped One Is the Answer

This is the key question about monotonic stacks. Look at the moment `j = stack.pop()`:

- `j` is the top — the index **closest to `i`** that is still waiting for an answer;
- `nums[i] > nums[j]` holds (otherwise we would not have entered the while);
- and there is no element between `j` and `i` that is larger than `nums[j]` — otherwise that element would have popped `j` earlier.

So `nums[i]` is the **first** element to the right of `nums[j]` that is larger. All three conditions hold at once; the definition of "next greater" is hit exactly.

## Where the Name Comes From

The values at the indices on the stack are always **monotonically decreasing**. The moment a new element breaks that monotonicity, we pop the top — **and popping is exactly the "settle the answer" action**. This is the most beautiful part of a monotonic stack: **you do not first find the answer and then store it; the answer is determined at the moment it gets popped.**

> Notation: looking for the next **greater** → use `<` in the while, stack is **decreasing**. Looking for the next smaller is the reverse.

## Crash Scene: Comparison Direction Is Backwards

```python
# WRONG: wrote > instead of <
while stack and nums[stack[-1]] > x:   # wanted greater, but popped the ones bigger than x
    j = stack.pop()
    ans[j] = x
```

This pops the elements that are bigger than `x` and leaves the smaller ones behind. The answer ends up wrong, and the bug is very sneaky — the code runs fine and some test cases may even pass.

The correct correspondence is worth memorizing:

| Looking for | while condition | stack monotonicity |
|---|---|---|
| next greater | `nums[top] < x` | decreasing |
| next smaller | `nums[top] > x` | increasing |

## Crash Scene: Storing Values Instead of Indices

```python
# WRONG
stack = []
for x in nums:
    while stack and stack[-1] < x:
        ans[???] = x        # the popped thing is a value, how do I know whose answer it is?
    stack.append(x)
```

The problem with storing values: **you have no idea where the popped number was in the original array**, so you cannot fill in `ans`. **A monotonic stack almost always stores indices**; the value is fetched on demand with `nums[top]`.

## Crash Scene: Mixing Up `<=` and `<`

```python
# looking for "strictly greater"
while stack and nums[stack[-1]] < x:     # only pop when strictly less; equals are not claimed
# if "greater or equal counts", use <=
```

In "Next Greater Element I", the two arrays may contain **duplicates** (for example, two 2s in `nums2`). If you use `<=`, you will wrongly claim the element with the same value. Using `<` gives you "strictly greater". **Decide whether equality counts as greater before you pick the operator.**

## Real World: Daily Temperatures

LeetCode 739. Given daily temperatures, find how many days you must wait for a warmer day:

```python
def daily_temperatures(t):
    ans = [0] * len(t)
    stack = []
    for i, x in enumerate(t):
        while stack and t[stack[-1]] < x:
            j = stack.pop()
            ans[j] = i - j          # the answer is "day difference", not the value
        stack.append(i)
    return ans
```

The only difference from the previous problem is one line: `ans[j] = i - j` instead of `ans[j] = x`. **This is where storing indices really pays off** — you get both the value and the distance.

## Complexity

| Metric | Value |
|---|---|
| Time | **O(n)** — each element is pushed and popped at most once |
| Space | O(n) — the stack may hold the whole array in the worst case |

Going from O(n²) to O(n) saves you exactly the inner loop that "keeps looking right" — the monotonic stack remembers for you who is still waiting.

## Summary

- Monotonic stack = elements in the stack stay monotonic; **popping = settling the answer**
- Next greater: `while nums[top] < x`, stack decreasing
- Next smaller: `while nums[top] > x`, stack increasing
- **Always store indices**, otherwise you cannot settle the answer; indices also let you compute distances
- Mind the difference between `<` and `<=`, which depends on whether equality counts as greater
- Each element enters and leaves once, total complexity O(n)
