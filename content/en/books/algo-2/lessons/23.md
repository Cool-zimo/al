# Python's dict and set: Both Backed by Hash Tables

> Python's `dict` and `set` are hash tables' "favorite children." Why did dict suddenly become ordered in 3.7+? Why can't a list be a key? The answers all live inside the hash table.

## dict Is a Hash Table

Python's `dict` is backed by a **hash table** under the hood. That's why lookup, insertion, and deletion are all O(1).

```python
d = {"name": "Alice", "age": 18}
print(d["name"])   # "Alice", O(1)
d["score"] = 95    # insert, amortized O(1)
del d["age"]       # delete, amortized O(1)
```

Last lesson we hand-rolled a simple hash table; Python's `dict` does essentially the same thing, only:
- The hash function is stronger (SipHash, defending against collision attacks)
- It uses **open addressing** for collisions
- It resizes automatically (capacity stays a power of two)
- The memory layout is heavily optimized

## set Is Also a Hash Table

A `set` is likewise a hash table — it just **stores keys and no values**.

```python
s = {1, 2, 3, 2, 1}
print(s)   # {1, 2, 3}, automatic deduplication

# Core set operations are all O(1)
3 in s        # True, O(1) lookup
s.add(4)     # O(1)
s.remove(1)  # O(1)
```

**Why can a set deduplicate?** Because it's a hash table — the same key hashes to the same slot, so it's only stored once.

**Why can a set test membership in O(1)?** Because it's a hash table — `in` is just a hash + probe.

## WRONG: Using a list as a dict Key

```python
# WRONG: list is unhashable
d = {}
d[[1, 2, 3]] = "hello"
```

Error:

```
TypeError: unhashable type: 'list'
```

**Why can't a list be a key?** Because a list is **mutable** — if its contents change, its hash should change too, but a hash table depends on "a key's hash never changes."

```python
# Imagine if a list could be a key
k = [1, 2, 3]
d = {k: "hello"}
k.append(4)     # k changed
d[k]            # hash changed, not found -> the hash table is彻底 broken
```

**Only immutable types can be keys:**
- immutable `int`, `float`, `str`, `bool`
- `tuple` (provided it contains no mutable elements)
- `frozenset`
- Custom classes (default uses id; not recommended)
- mutable `list`, `dict`, `set`

```python
# RIGHT: use a tuple instead of a list as a key
d = {}
d[(1, 2, 3)] = "hello"   # tuple is immutable, valid as a key
print(d[(1, 2, 3)])      # "hello"

# Nested tuples work too
d2 = {(1, 2): "a", (3, 4): "b"}
```

**But a tuple must not contain a list!**

```python
# WRONG: tuple contains a mutable element
d = {(1, [2, 3]): "hello"}
# TypeError: unhashable type: 'list'
```

## WRONG: Assuming dict Is Unordered and Writing Order-Dependent Code

```python
# In Python 3.6 and earlier:
d = {"c": 3, "a": 1, "b": 2}
print(list(d.keys()))   # order was unpredictable! Could be ['a', 'c', 'b'] or anything
```

A lot of legacy code relies on this:

```python
# WRONG: relying on dict traversal order
config = {"host": "localhost", "port": 8080, "debug": True}
keys = list(config.keys())
first_key = keys[0]
# Python 3.6 and earlier: first_key could be any key
# Python 3.7+: first_key is guaranteed to be "host"
```

**What Python 3.7+ guarantees:** Starting with 3.7, dict traversal order **equals insertion order** (this is part of the language spec, not just a CPython implementation detail).

```python
# Python 3.7+
d = {}
d["first"] = 1
d["second"] = 2
d["third"] = 3
print(list(d.keys()))   # ['first', 'second', 'third']  guaranteed
```

**But note: this does NOT mean "sorted by key"!**

```python
d = {}
d["zebra"] = 1
d["apple"] = 2
d["monkey"] = 3
print(list(d.keys()))   # ['zebra', 'apple', 'monkey']  insertion order, not alphabetical!
```

If you need sorted output, call `sorted()` explicitly:

```python
d = {"zebra": 1, "apple": 2, "monkey": 3}
for k in sorted(d.keys()):
    print(k, d[k])
# apple 2
# monkey 3
# zebra 1
```

## Why dict Became Ordered in Python 3.7+

**The key change: an extra "index array" records insertion order.**

```
Before Python 3.6:
  hash table: [entry0, None, entry1, None, entry2, None, None, None]
  traversing requires skipping None -> slow

Python 3.7+:
  hash table: [entry0, entry1, entry2, None, None, ...]
  indices:    [0, 2, 1, ...]  <- records insertion order
  traverse indices to emit in order
```

**Practical effect:**
- Traversal changed from "skip holes" to "read in indices order"
- A small amount of extra memory (one indices array) buys faster traversal and deterministic order
- CPython implemented this in 3.6 but it wasn't part of the spec until 3.7

**The cost of insertion-order preservation:**

```python
import sys
# An ordered dict carries an extra indices array
d = {i: i for i in range(1000)}
print(sys.getsizeof(d))  # roughly 8KB more than a plain hash table (1000 indices * 8 bytes)
```

**One-liner: Python 3.7+ dict trades space for order guarantees.**

## WRONG: dict Key Comparison Uses __eq__, Not is

```python
# Two different objects, but __eq__ returns True -> they're the same key
class Number:
    def __init__(self, value):
        self.value = value
    def __eq__(self, other):
        return self.value == other.value
    def __hash__(self):
        return hash(self.value)

a = Number(42)
b = Number(42)
print(a is b)        # False, not the same object
print(a == b)        # True, equal values

d = {a: "answer"}
print(d[b])          # "answer"! Same hash and == True
```

**Rule: two keys are "the same" iff `hash(a) == hash(b) and a == b`.**

Which means:

```python
# WRONG: __eq__ returns True but __hash__ differs -> violates the contract
class Bad:
    def __eq__(self, other):
        return True
    def __hash__(self):
        return id(self)   # every instance has a different hash

b1 = Bad()
b2 = Bad()
d = {b1: 1}
print(d[b2])   # KeyError! Even though b1 == b2, their hashes differ
```

**Python's safeguard:**

```python
class Broken:
    def __eq__(self, other):
        return True
    # no __hash__ -> Python sets __hash__ = None -> unhashable

b = Broken()
d = {b: 1}   # TypeError: unhashable type: 'Broken'
```

**If you override `__eq__` without overriding `__hash__`, Python makes instances of that class unhashable.** It's Python hitting the brakes for you.

## Quick Reference: dict and set Operations

```python
# dict
d = {"a": 1, "b": 2}

d.get("c", 0)        # 0, returns default for missing keys, never raises KeyError
d.setdefault("c", 0) # 0, sets the default if the key is missing
d.update({"c": 3})   # bulk update
d.pop("a")           # 1, remove the key and return its value
d.keys()             # view object, reflects dict changes live
d.values()           # view object
d.items()            # view object, use this for iteration

# set
s = {1, 2, 3}
s | {3, 4}           # union {1, 2, 3, 4}
s & {2, 3, 4}        # intersection {2, 3}
s - {1, 2}           # difference {3}
s ^ {3, 4}           # symmetric difference {1, 2, 4}

{1, 2} <= {1, 2, 3}  # subset test True
```

**View objects vs. lists:**

```python
d = {"a": 1, "b": 2}
keys = d.keys()      # dict_keys VIEW, not a list!
print(keys)          # dict_keys(['a', 'b'])
d["c"] = 3
print(keys)          # dict_keys(['a', 'b', 'c'])  updated live!

# If you need a list, convert explicitly
key_list = list(d.keys())
```

## WRONG: The get() Default and the setdefault() Trap

```python
# WRONG: get's default is never written back to the dict
d = {}
value = d.get("key", [])
value.append(1)
print(d)          # {}  the dict didn't change! value is a new empty list, never stored

# RIGHT: use setdefault
d = {}
d.setdefault("key", []).append(1)
print(d)          # {'key': [1]}

# Or use defaultdict
from collections import defaultdict
d = defaultdict(list)
d["key"].append(1)
print(d)          # defaultdict(<class 'list'>, {'key': [1]})
```

**The `setdefault` trap: the default is evaluated every time**

```python
# WRONG: mutable default inside a loop
d = {}
for i in range(3):
    d.setdefault("key", []).append(i)
print(d)   # {'key': [0, 1, 2]}  this is actually correct

# But if you write it by hand:
d = {}
for i in range(3):
    if "key" not in d:
        d["key"] = []   # created only the first time
    d["key"].append(i)
print(d)   # {'key': [0, 1, 2]}  also correct
```

The catch is that `setdefault` evaluates the default expression every call:

```python
def make_list():
    print("creating a new list")
    return []

d = {}
d.setdefault("a", make_list())  # prints "creating a new list"
d.setdefault("a", make_list())  # prints "creating a new list" again! Not used, but evaluated
```

**If constructing the default is expensive, use `defaultdict` or check for the key first.**

## Complexity Cheat Sheet

| Operation | dict | list | set |
|---|---|---|---|
| Lookup | O(1) | O(n) | O(1) |
| Insert | amortized O(1) | O(1) tail / O(n) middle | amortized O(1) |
| Delete | amortized O(1) | O(n) | amortized O(1) |
| Traverse | O(n) | O(n) | O(n) |
| Min/max | O(n) | O(n) / O(1) sorted | O(n) |

**Core advice:**
- Need "fast lookup/dedup" -> `set`
- Need "key-value mapping" -> `dict`
- Need "insertion order + mapping" -> `dict` (3.7+ is ordered by default)
- Need "sorted traversal" -> `sorted(dict.items())`

## Summary

- Python's `dict` and `set` are both hash tables under the hood; core ops are O(1)
- A `set` stores only keys, so it deduplicates naturally
- `list`, `dict`, `set` are unhashable (mutable) and can't be dict keys
- A tuple is hashable only if it contains no mutable elements
- Python 3.7+ dict guarantees insertion order (via an indices array), but is not sorted by key
- Two dict keys are equal iff `hash(a) == hash(b) and a == b`
- Override `__eq__` and you must override `__hash__`, otherwise Python makes instances unhashable
- `get()`'s default is never written back; `setdefault()` does write it; use `defaultdict` for expensive defaults
