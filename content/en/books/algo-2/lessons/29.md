# Divide and Conquer: Writing Merge Sort Recursively

> Divide and Conquer (D&C) is recursion's most natural application. It has only three steps: divide, conquer, combine. Merge sort performs these three steps to perfection, and it is also the best textbook for understanding where O(n log n) comes from.

## The three steps of divide and conquer

The core idea of divide and conquer:

1. **Divide:** break the big problem into two or more smaller problems.
2. **Conquer:** solve each smaller problem recursively.
3. **Combine:** merge the solutions of the smaller problems into the solution of the big problem.

**Note that the "conquer" step uses recursion itself** — so divide and conquer is naturally recursive. The difference is that divide and conquer requires the splitting to be uniform and independent, with each subproblem not interfering with the others.

## Merge sort: a standard divide-and-conquer algorithm

The steps of merge sort:

- **Divide:** cut the array in half at the middle.
- **Conquer:** recursively sort the left and right halves.
- **Combine:** merge the two **already-sorted** halves into one sorted array.

```python
def mergesort(nums):
    # base case: arrays of length 0 or 1 are already sorted
    if len(nums) <= 1:
        return nums
    
    mid = len(nums) // 2
    left = mergesort(nums[:mid])     # conquer: left half
    right = mergesort(nums[mid:])    # conquer: right half
    return merge(left, right)        # combine: merge
```

**Notice how clean this structure is:** divide is `mid = len(nums) // 2`, conquer is two recursive calls, and combine is `merge`. Three steps, no more and no fewer.

## Merging two sorted arrays: implementing merge

Merging is the "soul" of merge sort. The premise: **both the left and right halves are already sorted.**

```python
def merge(left, right):
    result = []
    i = j = 0
    # two pointers: each time take the smaller of the two pointers
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:
            result.append(left[i])
            i += 1
        else:
            result.append(right[j])
            j += 1
    # append whatever remains
    result.extend(left[i:])
    result.extend(right[j:])
    return result
```

**Use two pointers `i` and `j` pointing at the start of each segment, and each time pick the smaller one to append.** Because both sides are sorted, the order you pick them in is globally sorted.

A concrete example, `merge([1, 4, 7], [2, 3, 6])`:

```
i->1  4  7   <- left
j->2  3  6   <- right

round 1: left[0]=1 vs right[0]=2 -> take 1, i=1
round 2: left[1]=4 vs right[0]=2 -> take 2, j=1
round 3: left[1]=4 vs right[1]=3 -> take 3, j=2
round 4: left[1]=4 vs right[2]=6 -> take 4, i=2
round 5: left[2]=7 vs right[2]=6 -> take 6, j=3 (right exhausted)
remaining: append left[2:]=7

result: [1, 2, 3, 4, 6, 7]
```

**`merge` is O(n):** every element is compared and appended exactly once, and the two pointers take a total of n steps.

## Running through the complete version

```python
def merge(left, right):
    result = []
    i = j = 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:
            result.append(left[i]); i += 1
        else:
            result.append(right[j]); j += 1
    result.extend(left[i:])
    result.extend(right[j:])
    return result

def mergesort(nums):
    if len(nums) <= 1:
        return nums
    mid = len(nums) // 2
    left = mergesort(nums[:mid])
    right = mergesort(nums[mid:])
    return merge(left, right)

print(mergesort([38, 27, 43, 3, 9, 82, 10]))
# [3, 9, 10, 27, 38, 43, 82]
```

**Look at the recursion tree layer by layer**, using `[38, 27, 43, 3, 9, 82, 10]` as an example:

```
layer 1 (combine): merge([3,27,38,43], [9,10,82])
layer 2 (conquer): merge([27,38], [3,43])    merge([9,82], [10])
layer 3 (conquer): merge([38],[27])  merge([43],[3])  merge([82],[9])  merge([10])
layer 4 (divide): ... length<=1, return directly
```

**The sum of all merges on each layer processes exactly n elements.** Because each layer together covers every element of the original array exactly once.

## WRONG: using > instead of <= in merge breaks stability

```python
# WRONG: wrote > instead of <=, merge order is wrong
def merge(left, right):
    result = []
    i = j = 0
    while i < len(left) and j < len(right):
        if left[i] > right[j]:    # <- should be <=
            result.append(left[i])
            i += 1
        else:
            result.append(right[j])
            j += 1
    result.extend(left[i:])
    result.extend(right[j:])
    return result
```

This example happens to "run" with `>`, but **the order is reversed** — the result becomes descending, or worse, inconsistent with what you expected. And if you use `>=`:

```python
if left[i] >= right[j]:   # <- used >=
```

**The result is an "unstable sort":** the relative order of equal elements may be scrambled. Merge sort is supposed to be a **stable sort** (equal elements keep their original order), and only `<=` guarantees stability.

```python
pairs = [("Alice", 2), ("Bob", 1), ("Carol", 2)]
# sort by the second element
# stable sort result: [("Bob",1), ("Alice",2), ("Carol",2)]  <- ("Alice","Carol") keeps original order
# unstable result:    [("Bob",1), ("Carol",2), ("Alice",2)]  <- order is scrambled
```

**Stable sorting matters when sorting by multiple fields:** first by score, then by name. If the sort is stable, records with the same score keep the name order established in the previous step.

## Where O(n log n) comes from

This is the core derivation of the lesson. **Look at it in two steps:**

**Step one: how many layers?** Each time you split in half, from n to n/2 to n/4 ... to 1. That is log n layers.

```
n -> n/2 -> n/4 -> ... -> 1   total log n layers
```

**Step two: how much work per layer?** The sum of all merges on each layer processes n elements in total (because the subarrays on each layer together make up the original array).

```
layer 1: 1 merge, processes n elements   -> n
layer 2: 2 merges, n/2 each              -> n
layer 3: 4 merges, n/4 each              -> n
...
total: log n layers x n per layer = n log n
```

**So the time complexity of merge sort is O(n log n).**

Compare:

| Sort | Best | Average | Worst | Space |
|---|---|---|---|---|
| Bubble / Insertion | O(n) | O(n^2) | O(n^2) | O(1) |
| Merge sort | O(n log n) | O(n log n) | O(n log n) | O(n) |
| Quick sort | O(n log n) | O(n log n) | O(n^2) | O(log n) |

**The beauty of merge sort: even the worst case is O(n log n).** Quick sort degenerates to O(n^2) on unlucky inputs like "the array is already sorted"; merge sort does not — it is n log n for any input. The cost is **O(n) extra space** to hold the merged result.

## WRONG: forgetting to merge, only "dividing"

```python
# WRONG: only recurses, never merges
def mergesort(nums):
    if len(nums) <= 1:
        return nums
    mid = len(nums) // 2
    mergesort(nums[:mid])      # <- sorted, but the result is discarded
    mergesort(nums[mid:])      # <- sorted, but the result is discarded
    return nums                # <- returns as-is, nothing happened
```

Run it:

```python
print(mergesort([3, 1, 2]))   # [3, 1, 2] returned as-is!
```

**Both halves were indeed sorted, but the "combine" step was never done, and the sorted results were thrown away.** The return value of a recursion must be used — either merge it or return it. This is the easiest "dropped result" mistake when rewriting recursion.

Correct version: `return merge(mergesort(nums[:mid]), mergesort(nums[mid:]))`. **The return value of a recursion is not decoration; it is the data flow.**

## WRONG: slice copies double the space

```python
# WRONG: every recursion layer slices, producing many temporary lists
def mergesort(nums):
    if len(nums) <= 1:
        return nums
    mid = len(nums) // 2
    left = mergesort(nums[:mid])   # slice copy, O(n) extra space
    right = mergesort(nums[mid:])
    return merge(left, right)
```

**This is not a bug; it is a performance problem.** `nums[:mid]` and `nums[mid:]` each produce a new list, and every recursion layer needs O(n) space to hold the copies. Total space is O(n log n) instead of the ideal O(n).

A production-grade merge sort **pre-allocates a temporary array** and uses index ranges `[l, r]` to represent "this segment," avoiding repeated copying:

```python
def mergesort_inplace(nums):
    tmp = [0] * len(nums)
    
    def sort(l, r):
        if r - l <= 1:
            return
        mid = (l + r) // 2
        sort(l, mid)
        sort(mid, r)
        # merge nums[l:r] into tmp, then copy back to nums
        i, j, k = l, mid, l
        while i < mid and j < r:
            if nums[i] <= nums[j]:
                tmp[k] = nums[i]; i += 1
            else:
                tmp[k] = nums[j]; j += 1
            k += 1
        while i < mid:
            tmp[k] = nums[i]; i += 1; k += 1
        while j < r:
            tmp[k] = nums[j]; j += 1; k += 1
        for i in range(l, r):
            nums[i] = tmp[i]
    
    sort(0, len(nums))
    return nums
```

**This version uses only one tmp array, so space is O(n), and it avoids the overhead of recursive slicing.** The slice-based version is fine for algorithm problems; for production code this version should be considered.

## When divide and conquer applies

Not every problem can be solved by divide and conquer. To use divide and conquer, three conditions must be met:

1. **The problem can be split:** the big problem can be divided into independent smaller problems.
2. **The subproblems share the same solution:** the smaller problem and the big problem are the same kind of problem (the recursive relation).
3. **Merging is feasible:** the solutions of the smaller problems can be combined into the big solution at low cost.

**Merge sort qualifies: splitting is one cut (O(1)), merging is two pointers (O(n)).**

## Summary

- Divide and conquer in three steps: **divide** (cut in half), **conquer** (recursively solve subproblems), **combine** (merge results).
- Merge sort: `mid = len(nums)//2` to divide; two recursive calls to conquer; `merge` to combine.
- `merge` uses two pointers, O(n); merge sort as a whole is O(n log n), even in the worst case.
- **log n layers x O(n) per layer = O(n log n)** — this is the key to the derivation.
- Merge sort is a **stable sort**, which requires `<=` rather than `<` in merge.
- The slice-based merge uses O(n log n) space; the production version uses index ranges + one tmp array for O(n) space.
- Conditions for divide and conquer: splittable, isomorphic subproblems, low-cost merging.
