# Recursion and the Stack: Call Stack, Stack Frames, and RecursionError

> Recursion is not magic. Behind it is just a stack — every time you call a function, the system pushes a frame onto the "call stack"; when the function returns, that frame is popped. Once you understand this, `RecursionError` will never surprise you again.

## Recursion = Calling Yourself

```python
def factorial(n):
    if n <= 1:            # base case (termination condition)
        return 1
    return n * factorial(n - 1)
```

Writing recursion is just about two things: **the termination condition** and **the recursive relation**. But how do these two actually run on the machine? The answer is the **call stack**.

## What Is the Function Call Stack

Every time a function is called, Python pushes a **stack frame** onto the call stack. Each frame holds:

- the function's local variables (the parameter `n`, local variables)
- where it is currently executing (the return address)
- the context of the caller

When the function executes `return`, that frame is popped and the result is handed back to the line that called it.

Hand trace `factorial(3)`:

```
factorial(3)  -> 3 * factorial(2)   push frame [3]
factorial(2)  -> 2 * factorial(1)   push frame [3, 2]
factorial(1)  -> return 1           push frame [3, 2, 1]
                                   v start returning
factorial(1)=1  -> factorial(2)=2*1=2
factorial(2)=2  -> factorial(3)=3*2=6
final result 6
```

The whole process is **push frames -> hit bottom -> pop frames in sequence**. The order of `return` is the reverse of the order of calls — which is exactly the LIFO of a stack.

## Seeing the Stack with inspect

```python
import inspect

def f(n):
    if n == 0:
        # print the current call stack depth
        print("stack depth:", len(inspect.stack()))
        return
    f(n - 1)

f(4)      # output: stack depth: 5   (f(4)->f(3)->f(2)->f(1)->f(0), 5 frames total)
```

`inspect.stack()` returns all frames currently on the call stack. You can literally see how many layers you have pushed.

## Crash Scene: No Termination Condition, Infinite Recursion

```python
# WRONG
def factorial(n):
    return n * factorial(n - 1)     # always getting smaller, never stops
```

Running it:

```
RecursionError: maximum recursion depth exceeded
```

Why is it an error and not just a hang? Because Python **actively limits the maximum recursion depth** (default 1000) to keep the stack from growing forever and eating all memory. You can check the limit:

```python
import sys
print(sys.getrecursionlimit())      # 1000
```

You can change it (but you probably should not, see below).

## Crash Scene: Wrong Termination Condition, Off by One and It Blows Up

```python
# WRONG: termination condition is n == 1 but the argument can reach 0
def sum_to(n):
    if n == 1:          # when n=0 this is never true
        return 1
    return n + sum_to(n - 1)

sum_to(3)    # 3+2+1=6, happens to work
sum_to(0)    # 0 + (-1) + (-2) + ... infinite recursion -> RecursionError
```

`sum_to(3)` working gives you the illusion that "the code is correct", but `sum_to(0)` blows up. **Test cases must cover the boundary values** (0, negative numbers, empty input).

The correct version:

```python
def sum_to(n):
    if n <= 0:           # guard with <= 0
        return 0
    return n + sum_to(n - 1)
```

## Crash Scene: Raising the Recursion Limit Just Turns "Crash Early" into "Crash Slow"

```python
import sys
sys.setrecursionlimit(100000)     # looks like it solves the problem?

def f(n):
    return f(n - 1)

f(50000)      # RecursionError: still blows up, just later
f(100000)     # this time it is not an error - it is a Segmentation fault / process killed, even worse
```

Raising the limit only delays the problem. **Stack space is finite memory**, not infinite. Python's recursion depth limit is essentially a memory guard. The real fixes are:

1. **Rewrite as iteration**: use a loop instead of recursion whenever you can;
2. **Tail recursion optimization**: Python does not support it, do not count on it;
3. **Use a list as a manual stack**: push the "recursive state" into a list instead of actually calling a function.

## Rewriting Recursion as a "Manual Stack"

The same factorial, but with a list simulating the call stack by hand:

```python
def factorial_iter(n):
    if n <= 1:
        return 1
    stack = list(range(1, n + 1))   # simulate the "still owed" subproblems
    res = 1
    while stack:
        res *= stack.pop()
    return res
```

This is just "flattening" recursion into iteration. The information that lives in stack frames can be held just as well by a list plus a few variables — and **it uses no call-stack depth at all**.

## What "Stack Overflow" Really Means

A lot of people ask questions on the site Stack Overflow, but the original meaning of the phrase is **the call stack getting blown up**: recursion is too deep, each layer defines a big array, the stack space is exhausted, and the operating system kills the process.

> recursion depth x frame size > stack capacity -> stack overflow

Because Python actively sets a recursion cap, it usually raises `RecursionError` rather than truly overflowing. But in C/C++, there is no such protection — get it wrong and you get a segfault.

## Recursion-to-Stack Correspondence Table

| Recursion concept | Stack concept |
|---|---|
| calling a function | push a frame |
| `return` | pop a frame |
| call order | push order (forward) |
| return order | pop order (reverse) |
| local variables | data inside the frame |
| termination condition | the "stop pushing" switch |
| `RecursionError` | stack depth exceeded the system limit |

## Complexity: Recursion's Hidden Space Cost

```python
# O(n) time, O(n) space (stack depth n)
def rec(n):
    if n <= 0: return
    rec(n - 1)
```

For recursive factorial or a recursive linked-list traversal, the space is O(n) — **because the call stack holds n frames**. The iterative version uses only O(1). This is recursion's most common cost: **short code, deep stack**.

## Summary

- Recursion is backed by the call stack: call = push frame, return = pop frame
- A frame holds local variables, the return address, and the caller's context
- The termination condition is the "stop pushing" switch; without it you recurse forever
- `RecursionError` is Python's active protection; the default limit is 1000
- Raising the recursion limit is not fixing a bug, it is just delaying the crash
- Recursive versions use O(n) space (stack depth); iteration or a manual stack drops it to O(1)
- When writing recursion, always test the boundary values: 0, negative numbers, empty input

  def reverse_print(s):
      # recursively print s in reverse
      pass

  reverse_print(input())
  print("在这里改")
tests:
- assert __out.strip().splitlines() == ['o','l','l','e','h']
hint: def reverse_print(s): if not s: return; reverse_print(s[1:]); print(s[0]). Recurse before printing, so the deepest level prints first - i.e. reverse order. Empty string returning immediately is the termination condition.
explain: The print comes after the recursive call, so the deepest level (the last character) is printed first, and as the calls return the earlier characters are printed in turn - overall reversed. This is a classic example of "recursion is naturally reverse-order".

- The recursive function had the wrong parameter type
answer: 1
