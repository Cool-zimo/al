# Turning Recursion into Iteration: When You Must Convert, and How

> Recursion looks elegant when you write it and can blow up when you run it. This lesson covers three things: when recursion blows up, whether `sys.setrecursionlimit` really saves you, and three patterns for rewriting recursion as iteration.

## Recursion is not free: it eats the stack

Every recursive call pushes a frame onto the call stack. The stack has a finite size — Python's default maximum is 1000 frames.

```python
import sys
print(sys.getrecursionlimit())   # 1000
```

This means **any input whose recursion depth exceeds 1000 will blow up right in your face.**

```python
def factorial(n):
    if n <= 1:
        return 1
    return n * factorial(n - 1)

print(factorial(500))    # works
print(factorial(2000))   # RecursionError!
```

**`factorial(2000)` only needs 2000 multiplications, and the amount of computation is perfectly fine. It blows up purely because the stack is not deep enough.**

This kind of scenario is far too common in practice: processing a file with tens of thousands of lines, traversing a very deep tree, or parsing a very deep JSON. The data itself is fine; the depth of the recursion kills it.

## WRONG: sys.setrecursionlimit treats the symptom, not the disease

Python leaves a back door:

```python
import sys
sys.setrecursionlimit(100000)   # raise the limit
```

**Does this solve `RecursionError`? Yes — but it only pushes the explosion a little further into the future.**

```python
import sys
sys.setrecursionlimit(100000)

def factorial(n):
    if n <= 1:
        return 1
    return n * factorial(n - 1)

print(factorial(50000))   # RecursionError: maximum recursion depth exceeded
                          # even though the limit is 100000, Python's own startup stack already occupies several hundred frames
```

**Even worse:** if you set it too high, say `setrecursionlimit(10000000)`, the program does not report an error — it just **crashes directly with a Segmentation fault** — Python's exception handling never even gets a chance to intervene before the process is gone.

```python
import sys
sys.setrecursionlimit(10000000)

def infinite():
    return infinite()

infinite()
# the process directly Segmentation faults; you do not even see a RecursionError
```

**Why this is wrong:** `setrecursionlimit` only raises the threshold for Python's own check; it does not actually allocate more memory for the stack. Stack space is given by the operating system and is usually only a few MB. You tell Python "go ahead and recurse freely," Python believes you, then keeps pushing frames until the operating system loses patience and kills the process.

**Conclusion: `setrecursionlimit` can only handle legitimate scenarios where the depth is "just a little over 1000" (such as a tree 2000 frames deep). If you need 100,000 frames of recursion, this approach is wrong at its root.**

## When you must convert to iteration

| Scenario | Can you use recursion? | Explanation |
|---|---|---|
| Depth is limited (< 1000) | Yes | Tail recursion and tree traversal are both fine |
| Depth may be large (tied to data size) | Must convert | List summation, chain/tree traversal |
| Needs backtracking (state must be undone) | Not necessarily | Recursion is natural, but can be simulated with an explicit stack |
| Divide and conquer (merge sort, quick sort) | Yes | Depth is only log n, very safe |

**One-line judgment: if the recursion depth is proportional to "the input size n," you must consider converting to iteration.** If the depth is only proportional to log n (as in divide and conquer), you do not need to worry.

## Pattern one: linear recursion to a while loop (accumulator)

The most straightforward rewrite. Using factorial as an example:

```python
# recursive version
def factorial_rec(n):
    if n <= 1:
        return 1
    return n * factorial_rec(n - 1)

# iterative version
def factorial_iter(n):
    result = 1
    for i in range(2, n + 1):
        result *= i
    return result
```

**Key technique: put "what each layer was supposed to compute" into a variable, and use a loop to simulate "going down layer by layer."**

Look at summation again:

```python
# recursive
def sum_list(nums):
    if not nums:
        return 0
    return nums[0] + sum_list(nums[1:])

# iterative
def sum_list_iter(nums):
    total = 0
    for x in nums:
        total += x
    return total
```

**This rewrite is almost mechanical:** the "minus one" that recursion drops each time corresponds to "the accumulator taking one step forward" in iteration.

## Pattern two: tail recursion to a while loop (mutate the parameters)

If a recursion is **tail-recursive** (the recursive call is the very last thing in the function, and its return value is returned without further computation), the rewrite is especially clean — just treat the parameters as state and let a while loop run once around.

```python
# tail-recursive version (returns the recursive call without further processing)
def factorial_tail(n, acc=1):
    if n <= 1:
        return acc
    return factorial_tail(n - 1, acc * n)

# iterative version: treat parameters as loop variables
def factorial_iter(n):
    acc = 1
    while n > 1:
        acc *= n
        n -= 1
    return acc
```

**Compare the shapes:**

| Tail recursion | while iteration |
|---|---|
| `factorial_tail(n-1, acc*n)` | `n -= 1; acc *= n` |
| Parameters `n`, `acc` | Loop variables `n`, `acc` |
| Base case `n <= 1` | Loop condition `n > 1` |

**Tail recursion and iteration are almost two ways of writing the same thing.** In languages like Scheme and Scala, tail recursion is automatically optimized into a loop (tail-call optimization, TCO). **But Python does no tail-call optimization** — so even if you write tail recursion in Python, 10,000 frames will still blow up. This must be clear.

## Pattern three: tree recursion to an explicit stack

Some recursions "cannot be turned directly into a loop," such as tree traversal and backtracking. For these you use an **explicit stack** to simulate the call stack.

```python
# recursive version: binary tree pre-order traversal
def preorder(node):
    if node is None:
        return
    print(node.val)
    preorder(node.left)
    preorder(node.right)

# iterative version: explicit stack
def preorder_iter(root):
    if root is None:
        return
    stack = [root]
    while stack:
        node = stack.pop()
        print(node.val)
        if node.right:
            stack.append(node.right)
        if node.left:
            stack.append(node.left)
```

**The advantage of an explicit stack: you allocate the stack on the heap, which is far larger than the call stack (several GB vs several MB).** The call stack depth is limited by the system; a list can hold millions of elements.

**The cost: the code gets longer and harder to read.** Recursion's elegance buys you a space limit; iteration's ugliness buys you the ability to not blow up.

## WRONG: forgetting to initialize the accumulator when converting

```python
# WRONG: forgot to give result an initial value
def factorial_iter(n):
    for i in range(2, n + 1):
        result *= i     # UnboundLocalError!
    return result
```

Error output:

```
UnboundLocalError: local variable 'result' referenced before assignment
```

**This kind of bug is especially common in "recursion to iteration,"** because your mind is thinking "each layer's result is automatically passed back," and it is easy to forget "initialize the result to zero / an initial value" when converting to iteration. The first line of almost every iterative version is `result = initial value`.

Correct version:

```python
def factorial_iter(n):
    result = 1        # <- the initial value is exactly the return value of the base case
    for i in range(2, n + 1):
        result *= i
    return result
```

**Rule: the initial value of the iterative accumulator = the value returned by the recursive base case.** Figure out what the recursive base case returns; that number is your initial value.

## WRONG: a wrong loop condition computes one extra or one fewer time

```python
# WRONG: range written as range(1, n+1), multiplying by 1 one extra time (actually harmless)
# the truly harmful one: the condition is wrong
def factorial_iter(n):
    result = 1
    i = 1
    while i <= n:     # <- when n=0, i=1 > n=0, the loop never runs and returns 1. Looks right?
        result *= i
        i += 1
    return result

print(factorial_iter(0))   # 1, correct
print(factorial_iter(5))   # 120, correct
```

This example actually gives correct results. The truly error-prone scenario is **the boundary containing 0:**

```python
# WRONG: n=0 needs to return 1, but the loop condition is i < n
def factorial_iter(n):
    result = 1
    i = 2
    while i < n:      # n=0: i=2, 2<0 is false, no loop, returns 1 -- accidentally correct
        result *= i   # n=2: i=2, 2<2 is false, no loop, returns 1 -- WRONG! Should be 2
        i += 1
    return result

print(factorial_iter(2))   # 1, but the correct answer is 2
```

**Boundary conditions are handled automatically by the base case in recursion, but you have to write them correctly yourself in iteration.** This is also why recursion is less error-prone — the base case is written at the very top, visible at a glance; iteration's boundaries are hidden in the loop condition and initial value, easy to miss.

**Self-check list for conversion:** run it once each with the three smallest inputs n=0, n=1, and n=2, then run one normal input. If the boundaries are right, it is usually right.

## When not to convert

Recursion is not the enemy. In the following scenarios recursion is correct, elegant, and efficient:

```python
# divide and conquer: depth is only log n
def mergesort(nums):
    if len(nums) <= 1:
        return nums
    mid = len(nums) // 2
    left = mergesort(nums[:mid])
    right = mergesort(nums[mid:])
    return merge(left, right)
# at n=1000000 the depth is only 20 frames, far below 1000

# tree traversal: trees are usually short
def dfs(node):
    if node is None: return
    dfs(node.left)
    dfs(node.right)
# a balanced binary tree with 1,000,000 nodes is only 20 frames deep
```

**Let me emphasize the standard one more time: is the depth proportional to n?** Proportional to n -> must convert. Proportional only to log n -> use recursion with confidence.

## Summary

- Recursion eats the stack: one frame per layer, Python's default limit is 1000 frames.
- `sys.setrecursionlimit` treats the symptom, not the disease; set it too high and you get a Segmentation fault before exception handling can even run.
- **If depth is proportional to n, you must convert to iteration;** if depth is proportional only to log n (divide and conquer, balanced trees), it is safe.
- Three rewrite patterns: linear recursion -> accumulator loop, tail recursion -> while loop mutating parameters, tree recursion -> explicit stack.
- The initial value of the iterative accumulator = the return value of the recursive base case.
- After converting to iteration, always self-check with the three boundary inputs n=0, n=1, and n=2.
