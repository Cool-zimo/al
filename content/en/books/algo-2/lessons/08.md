# Merging Two Sorted Lists

> Two already-sorted lists, one sorted result. This is the most-asked linked-list problem for a reason: it tests whether you can actually manipulate pointers without losing your place.

## The Problem

```
l1: 1 -> 3 -> 5
l2: 2 -> 4 -> 6
result: 1 -> 2 -> 3 -> 4 -> 5 -> 6
```

Note what this is **not**. It is not "collect all the values, sort them, and build a new list"—that would cost O(n) extra space and completely ignore the fact that both inputs are already sorted. The requirement is **in-place node splicing**.

## The Idea

It is identical to merging two sorted arrays. Two pointers, each aimed at the current node of its list. Whichever node is smaller gets attached to the result, and that pointer advances.

```python
def merge_two_lists(l1, l2):
    dummy = ListNode(0)
    cur = dummy
    while l1 and l2:
        if l1.val <= l2.val:
            cur.next = l1
            l1 = l1.next
        else:
            cur.next = l2
            l2 = l2.next
        cur = cur.next
    cur.next = l1 if l1 else l2      # splice the remaining segment wholesale
    return dummy.next
```

**Three points deserve their own section.**

## 1. The Dummy Node Eliminates the "First Node" Special Case

Without a dummy, you must decide the head of the result up front:

```python
# the verbose version
if l1.val <= l2.val:
    head = l1; l1 = l1.next
else:
    head = l2; l2 = l2.next
cur = head
...
```

With a dummy, `head` is a fixed sentinel and you return `dummy.next` at the end. **This is the single highest-frequency linked-list trick.**

## 2. After the Loop, Do Not Splice Node by Node

When `while l1 and l2` exits, at least one pointer is `None`. But the **other** pointer still leads into an entire sorted tail, and every value in that tail is larger than everything you have already merged. So `cur.next = l1 if l1 else l2` hangs the whole segment in one operation.

This is not laziness. The tail is already a perfectly good chain; attaching it once is exactly what the structure allows.

## 3. Never Skip `cur = cur.next`

What happens if you omit it? `cur` stays parked on the dummy, so every `cur.next = ...` writes to the same slot. You keep overwriting the second node and end up with a one-node list:

```python
# WRONG
def merge_bad(l1, l2):
    dummy = ListNode(0)
    cur = dummy
    while l1 and l2:
        if l1.val <= l2.val:
            cur.next = l1
            l1 = l1.next
        else:
            cur.next = l2
            l2 = l2.next
        # forgot cur = cur.next
    return dummy.next
```

The output list has one node and everything else is leaked.

## A Frame-by-Frame Walkthrough

```
l1: 1 -> 3 -> 5
l2: 2 -> 4 -> 6

init:  dummy -> None,   cur = dummy
1<=2:  cur.next=1, l1=3, cur=1     dummy->1
3>2:   cur.next=2, l2=4, cur=2     dummy->1->2
3<=4:  cur.next=3, l1=5, cur=3     dummy->1->2->3
5>4:   cur.next=4, l2=6, cur=4     dummy->1->2->3->4
5<=6:  cur.next=5, l1=None, cur=5  dummy->1->2->3->4->5
loop exits: cur.next = l2 (=6)
final: 1->2->3->4->5->6
```

## The Recursive Version

The same operation, written recursively, is strikingly short:

```python
def merge_two_lists_rec(l1, l2):
    if not l1:
        return l2
    if not l2:
        return l1
    if l1.val <= l2.val:
        l1.next = merge_two_lists_rec(l1.next, l2)
        return l1
    else:
        l2.next = merge_two_lists_rec(l1, l2.next)
        return l2
```

**But the recursive version uses O(n) space**—the call-stack depth equals the total number of nodes. On a long list it raises `RecursionError`. Write it in an interview if you like; ship the iterative version.

## Complexity and the Trade-Off

| Version | Time | Space | Note |
|---|---|---|---|
| Iterative + dummy | O(n+m) | **O(1)** | Recommended |
| Recursive | O(n+m) | O(n+m) | Deep stack, long lists blow up |
| Extract, sort, rebuild | O((n+m) log(n+m)) | O(n+m) | Ignores the sorted precondition, worst of all |

## # WRONG 1 — Comparing Nodes Instead of Values

```python
# WRONG
if l1 <= l2:          # TypeError: '<=' not supported between instances of 'ListNode' and 'ListNode'
```

You must compare `.val`. Unless you implement `__lt__` on `ListNode`, Python has no idea which of two nodes is smaller.

## # WRONG 2 — Pointing `cur` at `l1` Instead of Attaching `l1`

```python
# WRONG
cur = l1          # intended to "attach l1", but actually aims cur at l1 itself
l1 = l1.next
```

Now `dummy.next` was never set, so the return value is still a solitary dummy. The correct move is `cur.next = l1`, then `cur = cur.next`.

## Extending to K Lists

Merging K sorted lists can be done by repeated pairwise merging:

```python
def merge_k(lists):
    if not lists:
        return None
    res = lists[0]
    for l in lists[1:]:
        res = merge_two_lists(res, l)
    return res
```

Complexity is O(kN) where k is the number of lists and N the total node count. A better approach is **divide-and-conquer merging** (pair them up, recursively) or a **heap**, both of which reach O(N log k). Divide and conquer comes back in Chapter 6.

## When "Stable Merge" Matters

Notice the comparison uses `<=`, not `<`. That choice preserves the relative order of equal elements: if both lists contain the same value, the one from `l1` is emitted first. In many domains—sorting records by a timestamp while keeping original order for ties—that stability is the whole point. If you switch to `<`, equal values get pulled from `l2` first and the merge becomes unstable. The algorithm still produces a sorted list; the tie-breaking changes.

## Summary

- Two pointers, one per list; attach the smaller, advance that pointer, and move `cur` forward.
- **A dummy sentinel** removes the "which node is the head" special case; return `dummy.next`.
- When the loop exits, splice the remaining whole segment in one assignment.
- Never, ever forget `cur = cur.next`.
- Compare `.val`, not node objects.
- Iterative: O(1) space. Recursive: prettier, but O(n) stack space.
