# Case Study: The Design of an LRU Cache

> An LRU cache is an interview litmus test: it demands O(1) lookup, O(1) move-to-front, and O(1) eviction from the tail. Neither a hash map nor a singly linked list can do all three—you need both.

## The Problem

Design an LRU cache supporting two operations:

- `get(key)`: return the value if the key exists, and mark that key **most recently used**; return `-1` otherwise.
- `put(key, value)`: insert or update. If the key exists, update its value and mark it most recently used. If the capacity is full, **evict the least recently used key first**, then insert.

Both `get` and `put` must run in **O(1)** time.

Example, capacity 2:

```
cache = LRUCache(2)
cache.put(1, 1)   # [1]
cache.put(2, 2)   # [2, 1]  2 is most recent
cache.get(1)      # returns 1, [1, 2]
cache.put(3, 3)   # capacity full, evict 2 -> [3, 1]
cache.get(2)      # returns -1 (evicted)
cache.put(4, 4)   # evict 1 -> [4, 3]
cache.get(1)      # -1
cache.get(3)      # 3
cache.get(4)      # 4
```

## Why Any Single Structure Fails

| Structure | Lookup | Move to front | Remove tail | Verdict |
|---|---|---|---|---|
| Hash map | O(1) | — | — | Cannot tell who is least recent |
| Array / list | — | O(n) shifts | O(1) | Neither put nor get is O(1) |
| Singly linked list | — | O(n) to find predecessor | O(n) | Every operation is O(n) |

**A singly linked list takes O(n) to remove the tail**—finding the tail is easy, but changing its predecessor's `next` means walking from the head. A doubly linked list gives every node a pointer to its predecessor, so removing any node is O(1).

So the solution needs two weapons:

- **A hash map**: `key -> node`, O(1) lookup.
- **A doubly linked list**: maintains the "recently used" order, with the head = most recent and the tail = least recent; insertion and removal are O(1).

## The Complete Implementation

```python
class Node:
    def __init__(self, key=0, val=0):
        self.key = key
        self.val = val
        self.prev = None
        self.next = None

class LRUCache:
    def __init__(self, capacity):
        self.cap = capacity
        self.cache = {}                  # key -> Node
        # sentinel head and tail eliminate empty-list and boundary checks
        self.head = Node()               # most recent lives right after head
        self.tail = Node()               # least recent lives right before tail
        self.head.next = self.tail
        self.tail.prev = self.head

    def _remove(self, node):
        """unlink node from the doubly linked list"""
        node.prev.next = node.next
        node.next.prev = node.prev

    def _add_to_head(self, node):
        """insert node right after head (mark it most recently used)"""
        node.next = self.head.next
        node.prev = self.head
        self.head.next.prev = node
        self.head.next = node

    def get(self, key):
        if key not in self.cache:
            return -1
        node = self.cache[key]
        self._remove(node)        # unlink
        self._add_to_head(node)   # reattach at the head
        return node.val

    def put(self, key, value):
        if key in self.cache:
            # already exists: update the value and move to head
            self._remove(self.cache[key])
        node = Node(key, value)
        self._add_to_head(node)
        self.cache[key] = node
        if len(self.cache) > self.cap:
            # over capacity: evict the node right before tail
            lru = self.tail.prev
            self._remove(lru)
            del self.cache[lru.key]
```

**Four logical pieces to memorize:**

1. **`get` hit** = hash lookup O(1) + unlink + relink at head. All three pointer operations are O(1).
2. **`put` on an existing key** = `_remove` the old node, then link the new one (its position changes and its value changes).
3. **Capacity exceeded** = evict `tail.prev`, the least recently used node.
4. **Unlinking order matters**: rewrite both neighboring pointers before dropping the references. If you overwrite `node.prev.next` after `node` is already garbage, you have a bug.

## A Hand-Run Trace

Capacity 2. Execute `put(1,1)`, `put(2,2)`, `get(1)`, `put(3,3)`:

```
put(1,1): cache={1:node1},  list head <-> 1 <-> tail
put(2,2): cache={1,2},     list head <-> 2 <-> 1 <-> tail  (2 is at head, newest)
get(1):   hit, unlink 1 and relink at head -> head <-> 1 <-> 2 <-> tail
put(3,3): capacity 2 is full -> evict tail.prev, which is node 2
           -> head <-> 3 <-> 1 <-> tail
```

Notice the eviction order: `2` was least recent (it sat right before `tail`), so it is removed. `1` was just accessed and stays.

## Why the Sentinels Are Worth It

Without sentinels, `_add_to_head` must branch on "is the list empty," and `_remove` must check whether the node is the last one. With two empty sentinel nodes:

- The list is never empty, and `head` / `tail` never move.
- `_remove` never needs to ask whether the node is at the head or tail—it always has both a predecessor and a successor.
- `_add_to_head` always inserts between `head` and `head.next`.

This is the same idea as the dummy node in list problems.

## Complexity

| Operation | Time | Space |
|---|---|---|
| get | O(1) | — |
| put | O(1) | — |
| Overall | — | O(capacity) |

Technically this is **amortized O(1)**: a hash map can degenerate to O(n) in the worst case, but both interviews and production code treat it as O(1).

## # WRONG 1 — Using a List to Track Order, Calling `remove` on Every Get

```python
# WRONG
class LRUList:
    def __init__(self, cap):
        self.cap = cap
        self.d = {}
        self.order = []           # track access order in a Python list

    def get(self, key):
        if key not in self.d:
            return -1
        self.order.remove(key)    # O(n)! removing from the middle copies elements
        self.order.append(key)
        return self.d[key]
```

`list.remove()` is O(n). A single `get` drags the whole complexity down to O(n). With a large capacity and heavy access, the cache falls off a performance cliff.

```
# what goes wrong (output is correct but it times out)
>>> l = LRUList(2)
>>> l.put(1, 1); l.put(2, 2); l.get(1); l.put(3, 3)
>>> l.get(2)
-1            # answer is right, but remove() silently made it slow
```

The whole point of the question is that a doubly linked list drops removal to O(1). A list cheats around the actual requirement.

## # WRONG 2 — Using a Singly Linked List, Forced to Evict From the Head

```python
# WRONG
class LRUSingle:
    def __init__(self, cap):
        self.cap = cap
        self.d = {}
        self.head = None

    def get(self, key):
        if key not in self.d:
            return -1
        return self.d[key].val

    def put(self, key, value):
        if key in self.d:
            self.d[key].val = value
            return               # only updated the value; the node stayed put!
        node = self.Node(value)
        self.d[key] = node
        if not self.head:
            self.head = node
        else:
            # a singly linked list cannot move an arbitrary node to the head
            cur = self.head
            while cur.next:
                cur = cur.next
            cur.next = node
        if len(self.d) > self.cap:
            k = self.head.val
            self.head = self.head.next
            del self.d[k]
```

Two fatal problems:

1. **No way to "move to the front":** a singly linked list has no predecessor pointer. Once you have found a node, you cannot rewrite the pointer that points at it, so it stays where it is. `get(1)` leaves node 1 in place and the LRU semantics silently break.
2. **The eviction logic is wrong:** it deletes `head`, but it never maintained the order correctly in the first place.

```
actual run:
put(1,1), put(2,2) -> list 1 -> 2
get(1)              -> should move 1 to front, but does nothing
put(3,3)            -> over capacity, delete head (1); the least recent was 2
afterwards get(1) still returns 1 (should have been evicted); LRU is broken
```

This is exactly why a doubly linked list is irreplaceable: **every node can remove itself in O(1), and every node can insert itself anywhere in O(1).**

## Where LRU Shows Up Outside Interviews

The principle is everywhere: operating-system page replacement, database buffer pools, CPU cache lines, content-delivery edge caches, and even your browser's back-forward navigation history. The names change—MRU, ARC, Clock—but the core invariant stays put: **fast key lookup plus ordered recency, maintained under heavy mutation.**

If you ever reach for "a dict plus a list of keys," stop and ask whether deletions happen in the middle. If they do, you want a linked structure.

## Summary

- An LRU cache needs "O(1) lookup + O(1) insertion and deletion anywhere," which no single structure provides.
- **A hash map stores key→node; a doubly linked list stores the usage order** (head = newest, tail = oldest).
- Two sentinels, `head` and `tail`, remove the need for empty-list and boundary checks.
- `get` hit = unlink + relink at head; `put` existing = remove the old node then add the new one; over capacity = delete `tail.prev`.
- Never use `list.remove()` or a singly linked list to fake this—the complexity or the semantics will break.
- This is a high-frequency interview problem, and it is the standard demonstration of "hash map + doubly linked list" working as a pair.

```quiz

exam: true
q: Why must an LRU cache combine a hash map with a doubly linked list instead of using either one alone?
options:
- The hash map deduplicates keys and the doubly linked list sorts them; their roles do not overlap so they must be used together
- The hash map finds keys in O(1) but has no notion of usage order; the doubly linked list moves any node to the head or removes the tail in O(1). Neither alone gives both O(1) lookup and O(1) order maintenance
- The doubly linked list saves memory and the hash map provides speed
- Python's dict does not preserve insertion order, so a linked list is needed to add order
answer: 1
explain: The question tests why the combination is necessary. A hash map locates a node in O(1) but is unordered, so it cannot answer "which key is least recent." A doubly linked list maintains order and any node can be inserted or removed in O(1), but it has no key index and would require traversal to find a node. They complement each other: the map maps key to node, the list maintains recency. A singly linked list cannot self-delete in O(1) (no predecessor pointer), and a list's remove is O(n), so the doubly linked list is required.
```
