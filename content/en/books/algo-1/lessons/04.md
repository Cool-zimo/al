# Space complexity

> Last lesson compared time. This one compares memory — **trading space for time** is the most common optimisation, but it isn't free.

## What space complexity means

**The extra memory an algorithm needs, as it grows with the input size n.**

The keyword is **extra**: the input itself doesn't count (that memory was already committed).

```python
def find_max(items):          # the memory for items doesn't count
    m = items[0]              # just one extra variable
    for x in items:
        if x > m:
            m = x
    return m                  # extra space O(1)
```

Whether items holds 10 or 10 million entries, this adds one variable → **space O(1)**.

```python
def copy_double(items):
    result = []
    for x in items:
        result.append(x * 2)  # builds a new list as long as the input
    return result             # extra space O(n)
```

The new `result` is as long as `items` → **space O(n)**.

## The classic case: two sum

**Problem:** given an array and a target, find the indices of the two numbers that **add up to the target**.

```python
nums = [2, 7, 11, 15]
target = 9
# 2 + 7 = 9, so the answer is indices [0, 1]
```

### Solution one: brute force (O(n²) time, O(1) space)

```python
def two_sum_brute(nums, target):
    n = len(nums)
    for i in range(n):
        for j in range(i + 1, n):
            if nums[i] + nums[j] == target:
                return [i, j]
    return []       # nothing found

print(two_sum_brute([2, 7, 11, 15], 9))     # [0, 1]
```

Only loop variables — no new array → **space O(1)**, but time O(n²).

### Solution two: hash-assisted (O(n) time, O(n) space)

**Idea:** walk the array once, recording "value → its index" in a dict. For each new value x, check whether `target - x` has been seen.

```python
def two_sum_hash(nums, target):
    seen = {}                      # value -> index
    for i, x in enumerate(nums):
        need = target - x
        if need in seen:           # we've seen the value we need
            return [seen[need], i]
        seen[x] = i                # remember this one
    return []

print(two_sum_hash([2, 7, 11, 15], 9))       # [0, 1]
```

There's now a dict holding up to n entries → **space O(n)**, while time drops to O(n).

### Measured

```python
import time
# build cases with no answer, forcing both functions to run to completion
for n in [500, 1000, 2000, 4000]:
    nums = list(range(n))
    target = -1                   # guarantees no answer
    ...
```

Measured results:

```
n=  500  brute     4.50 ms   hash   0.027 ms   168× faster
n= 1000  brute    18.38 ms   hash   0.052 ms   353× faster
n= 2000  brute    72.97 ms   hash   0.107 ms   680× faster
n= 4000  brute   292.80 ms   hash   0.247 ms  1183× faster
```

**That's trading space for time**: spend O(n) extra memory (the dict), and jump from O(n²) down to O(n).

## When the trade isn't worth it

**Trading space for time isn't always right.** Three situations call for caution:

**1. Memory is genuinely tight.**

Embedded devices, huge datasets. With n = 100 million, an O(n) helper dict takes gigabytes — you'd hit an out-of-memory error.

**2. When the data is too big to hold, an O(1)-space method can be more practical.**

Take duplicate detection again. There's a **sort-then-compare-neighbours** approach:

```python
def has_duplicate_sort(items):
    items = sorted(items)         # sort: O(n log n) time
    for i in range(1, len(items)):
        if items[i] == items[i - 1]:
            return True
    return False
```

(Note `sorted()` returns a new list, so strictly that's O(n) space too; if you may modify the input, `items.sort()` is O(1) extra space.)

Three approaches compared:

| Approach | Time | Extra space |
|---|---|---|
| nested loops | O(n²) | O(1) |
| set | O(n) | O(n) |
| sort, compare neighbours | O(n log n) | O(1) if sorted in place |

**Sorting is the middle ground**: slightly slower than the set, but it saves that O(n) of memory.

**3. Problems that demand "in place".**

Many problems require "**modify in place**, no new arrays" — you'll meet these in the two-pointer chapter. Then O(1) space is a hard requirement.

## Trading time for space: the reverse

It works the other way too — **spend time to save memory**:

```python

# the cost is much more careful index handling (chapter 2 covers this)
```

Rarer, but the only option when memory is constrained.

## Space cost of common operations

| Code | Extra space |
|---|---|
| `for x in items` | O(1) |
| `set(items)` / a dict | O(n) |
| `sorted(items)` | O(n) (returns a new list) |
| `items.sort()` | O(1) (in place, depending on implementation) |
| `items[:]` / `items[1:]` | O(n) (slicing copies) |
| `list(range(n))` | O(n) |

> ⚠️ **Slicing copies!** `items[1:3]` looks like "take a part of it", but it builds a new list. Repeated slicing inside a loop is a sneaky source of memory waste.

## How to work out space complexity

Same rules as time, except you're counting **memory** rather than operations:

1. Did you build a data structure as long as n (list, set, dict)? That's O(n)
2. How deep does recursion go? Depth d means O(d) (later chapters)
3. Just a fixed handful of variables? O(1)

## Summary

- Space complexity measures **extra memory** growth with n
- **Trading space for time** is the classic optimisation (hash assistance is the typical case)
- When memory is tight, in-place is required, or data is enormous, think the other way
- Slicing, `sorted()` and building sets all cost O(n) extra space
