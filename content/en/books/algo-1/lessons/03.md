# Comparing the common complexities

> Line the usual complexities up and see how many orders of magnitude separate them.

## Smallest to largest

| Complexity | Name | Rough operations at n=1000 |
|---|---|---|
| `O(1)` | constant | 1 |
| `O(log n)` | logarithmic | about 10 |
| `O(n)` | linear | 1 000 |
| `O(n log n)` | linearithmic | about 10 000 |
| `O(n²)` | quadratic | 1 000 000 |
| `O(2ⁿ)` | exponential | about 10³⁰⁰ (not finishable) |

**From O(n) to O(n²) is a 1000× gap at n=1000. O(2ⁿ) is outright impossible.**

## O(1): independent of size

```python
def get_middle(items):
    return items[len(items) // 2]      # one step, however long the list
```

Typical operations: indexing, dictionary/set lookups, arithmetic.

**Careful:** O(1) doesn't mean "fast", only "doesn't get slower as n grows". An O(1) operation that reads a huge file can still take a long time.

## O(log n): halving each step

**The second-best complexity, and the one that best shows what an algorithm can do.**

The intuition: **finding a page in a book**. You want page 700 of a 1000-page book:

1. Open somewhere in the middle → it's page 500, too early, continue in the **right half**
2. Open the middle of that half → page 750, too far, continue in the **left part**
3. …each step discards half the remaining range

**How many halvings until only one candidate is left?**

```
1000 → 500 → 250 → 125 → 62 → 31 → 15 → 7 → 3 → 1
```

**Nine steps.** Flipping page by page would take 1000.

Mathematically: **log₂(1000) ≈ 10**, hence "logarithmic".

| n | page by page O(n) | halving O(log n) |
|---|---|---|
| 1 000 | 1 000 steps | 10 steps |
| 1 000 000 | 1 000 000 steps | 20 steps |
| 1 000 000 000 | a billion steps | 30 steps |

**A thousandfold increase in data adds just 10 steps.** That's why binary search is compulsory — it's the subject of the next chapter.

```python
def binary_steps(n):
    """how many steps binary search needs over n sorted items, at worst"""
    steps = 0
    while n > 0:
        n //= 2          # halve each time
        steps += 1
    return steps

print(binary_steps(1000))       # 10
print(binary_steps(1000000))    # 20
```

## O(n): one pass

The most intuitive one: look at each element once.

```python
def find_max(items):
    m = items[0]
    for x in items:          # each element looked at exactly once
        if x > m:
            m = x
    return m
```

**O(n) is usually the best you can hope for** — after all, you have to look at the data at least once to know anything about it.

## O(n log n): the limit of efficient sorting

"n elements, each handled log n times". Every **comparison-based sort** (merge, quick, heap) bottoms out at O(n log n).

The intuition: sorting n items means "divide and conquer, halving each level" × "all n elements handled at every level".

```python
# Python's built-in sort is O(n log n)
items = [5, 2, 8, 1]
items.sort()
print(items)        # [1, 2, 5, 8]
```

**This is provably the best a comparison sort can do** (it's a proven lower bound).

## O(n²): nested loops

Pairwise comparison, naive sorting. Lesson one showed what this means in practice:

```
n = 1000  → 1 000 000 operations
n = 10000 → 100 000 000 operations
```

**Rule of thumb: once n passes a few thousand, treat O(n²) with suspicion.**

## O(2ⁿ): brute-force enumeration, the forbidden zone

Every extra element doubles the possibilities. The classic case: enumerating every subset of a set.

```python
# all subsets of n elements: 2ⁿ of them
# n=20 → about a million
# n=30 → about a billion
# n=60 → more than the atoms in the observable universe
```

**Once n reaches about 30, O(2ⁿ) is effectively impossible.** The answer then is a different approach (dynamic programming, greedy), not a faster constant.

## A table that makes the gap tangible

Assuming 100 million operations per second:

| Complexity | n=50 | n=1000 | n=100 000 |
|---|---|---|---|
| O(log n) | instant | instant | instant |
| O(n) | instant | instant | 0.001 s |
| O(n log n) | instant | instant | 0.002 s |
| O(n²) | instant | 0.01 s | **10 s** |
| O(2ⁿ) | **3.5 years** | heat death | heat death |

**Look at the O(2ⁿ) row**: n=50 already costs 3.5 years. It's far worse than O(n²) — O(n²) is merely slow, O(2ⁿ) is infeasible.

## How to judge what you can afford

| Data size | Highest complexity you can afford |
|---|---|
| n ≤ 100 | O(n²) is tolerable |
| n ≤ 1000 | O(n²) works, O(n log n) preferred |
| n ≤ 100 000 | must be O(n log n) or better |
| n ≥ 1 000 000 | basically only O(n) or O(log n) |

**A useful rule of thumb:** read the problem's size constraints, set yourself a "complexity budget", then pick the algorithm.

## Summary

- Smallest to largest: `O(1)` < `O(log n)` < `O(n)` < `O(n log n)` < `O(n²)` < `O(2ⁿ)`
- **O(log n) means "halve each time"** — a thousandfold more data costs 10 extra steps
- **O(n log n) is the ceiling for comparison sorting**
- **O(n²) struggles past a few thousand**; **O(2ⁿ) is off-limits**
- Given a data size, set a complexity budget first

**Next: space complexity** — time can be traded, and so can memory.
