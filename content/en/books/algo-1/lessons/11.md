# Why Preprocessing Matters: Range Sums from O(n) to O(1)

> In the previous chapters we learned how two pointers can reduce dimensionality. This chapter takes a different angle: **preprocessing** — compute the answer in advance and store it, then fetch it directly when queried.

## A Naive Requirement

**Problem**: You are given an array and repeatedly asked "what is the sum of elements in the interval [l, r]?"

```python
nums = [1, 3, 5, 7, 9, 11]
# query [1, 3] -> 3+5+7 = 15
# query [0, 4] -> 1+3+5+7+9 = 25
# query [2, 2] -> 5
```

The naive approach: for every query, accumulate from scratch.

```python
def range_sum(nums, l, r):
    total = 0
    for i in range(l, r + 1):
        total += nums[i]
    return total

nums = [1, 3, 5, 7, 9, 11]
print(range_sum(nums, 1, 3))    # 15
print(range_sum(nums, 0, 4))    # 25
```

**Every query costs O(n).** If you ask 100,000 times, the total work is 100,000 × n — a guaranteed timeout.

## The Core Insight: Trading Space for Time

If you spend O(n) **up front** to compute and store all the "prefix" information, then every subsequent query becomes O(1).

This is the idea of **prefix sums**.

## The Prefix Sum Array

**Definition**: `prefix[i]` stores the sum of all elements in `nums[0..i-1]` (the sum of the first i elements).

```python
nums   = [1, 3, 5, 7, 9, 11]
prefix = [0, 1, 4, 9, 16, 25, 36]
# prefix[0] = 0 (sum of 0 elements)
# prefix[1] = 1
# prefix[2] = 1+3 = 4
# prefix[3] = 1+3+5 = 9
# ...
# prefix[6] = 1+3+5+7+9+11 = 36
```

**How to compute prefix**:

```python
def build_prefix(nums):
    n = len(nums)
    prefix = [0] * (n + 1)
    for i in range(n):
        prefix[i + 1] = prefix[i] + nums[i]
    return prefix

nums = [1, 3, 5, 7, 9, 11]
prefix = build_prefix(nums)
print(prefix)    # [0, 1, 4, 9, 16, 25, 36]
```

**O(n) once, use forever.**

## Querying with Prefix Sums

**Sum of interval [l, r] = prefix[r+1] - prefix[l]**

Why? Let's visualize:

```
prefix[r+1] = nums[0] + nums[1] + ... + nums[l-1] + nums[l] + ... + nums[r]
prefix[l]   = nums[0] + nums[1] + ... + nums[l-1]
```

Subtracting the two, the entire common prefix cancels out, leaving exactly the sum of `nums[l..r]`.

```python
def query(prefix, l, r):
    return prefix[r + 1] - prefix[l]

prefix = [0, 1, 4, 9, 16, 25, 36]
print(query(prefix, 1, 3))    # prefix[4] - prefix[1] = 16 - 1 = 15 ✓
print(query(prefix, 0, 4))    # prefix[5] - prefix[0] = 25 - 0 = 25 ✓
print(query(prefix, 2, 2))    # prefix[3] - prefix[2] = 9 - 4 = 5 ✓
```

**O(1) query!** From O(n) to O(1) — this is a quantum leap.

## Why prefix Needs a Leading Zero

This is the part that confuses beginners the most.

**Problem**: If `l=0`, we need to compute `prefix[0]`. Without a leading zero, `prefix[0]` would be `nums[0]` instead of 0.

```python
# Version without leading zero (WRONG)
prefix = [1, 4, 9, 16, 25, 36]   # store prefix sums directly
# Query [0, 3] needs prefix[3] - prefix[-1] -> IndexError!
```

**Version with leading zero**:

```python
prefix = [0, 1, 4, 9, 16, 25, 36]   # prefix[0]=0
# Query [0, 3] = prefix[4] - prefix[0] = 16 - 0 = 16 ✓
```

**The leading zero makes "starting at position 0" use the same formula as every other case**, eliminating the need for special handling.

| Query | Formula | With leading 0 | Without leading 0 |
|---|---|---|---|
| [0, 3] | prefix[4] - prefix[0] | 16 - 0 = 16 ✓ | Needs special case |
| [1, 3] | prefix[4] - prefix[1] | 16 - 1 = 15 ✓ | 16 - 1 = 15 ✓ |
| [2, 2] | prefix[3] - prefix[2] | 9 - 4 = 5 ✓ | 9 - 4 = 5 ✓ |

**With the leading zero, every query uses the same formula — no special case for l==0.**

## Complexity Comparison

| Operation | Naive | Prefix Sum |
|---|---|---|
| Preprocessing | — | O(n) |
| Single query | O(n) | **O(1)** |
| m queries | O(mn) | O(n + m) |

When m is large, the difference is astronomical:

```
m=100000, n=1000:
Naive:  100000 × 1000 = 100 million operations
Prefix: 1000 + 100000 = 101 thousand operations
~1000x faster
```

## When Prefix Sums Apply

**Not every problem is suited to prefix sums.** The conditions are:

- You need to **repeatedly query** interval information (sum, product, XOR, etc.)
- The number of queries m is much larger than the array length n
- The interval information satisfies **additivity / subtractability** (sums can be added and subtracted; maximums cannot)

| Scenario | Prefix Sum? |
|---|---|
| Range sum | ✅ |
| Range XOR sum | ✅ |
| Range maximum | ❌ (no additivity) |
| Counting elements in range | ✅ |
| Range product (modulo) | ✅ |

> 💡 **Rule of thumb**: If the problem asks "something in a certain interval" and asks it many times, think prefix sums.

## A Crash Site: Off-by-One in the Query

The most common bug is mixing up the indices. Consider this broken attempt:

```python
# WRONG
def query_buggy(prefix, l, r):
    return prefix[r] - prefix[l - 1]

prefix = [0, 1, 4, 9, 16, 25, 36]
print(query_buggy(prefix, 0, 3))    # prefix[3] - prefix[-1] = 9 - 36 = -27  ✗
print(query_buggy(prefix, 1, 3))    # prefix[3] - prefix[0]  = 9 - 0  = 9   ✗
```

When `l=0`, `prefix[l-1]` is `prefix[-1]` — Python's negative indexing wraps around to the **last element**, not what we want at all. The second query also fails: `prefix[3] - prefix[0]` gives the sum of `nums[0..2]`, not `nums[1..3]`.

The fix: use `prefix[r+1] - prefix[l]`, which works for **all** valid l and r without any guard clauses.

## Summary

- Prefix sum: preprocessing O(n), query O(1)
- `prefix[i]` = sum of the first i elements, `prefix[0] = 0`
- Sum of interval [l, r] = `prefix[r+1] - prefix[l]`
- The leading zero unifies the formula — no special case for l==0
- Applicable when: repeated queries on additive interval data
