# What algorithmic complexity means

> Two solutions to the same problem both give the right answer. On 8000 items, one runs in 0.2 ms and the other takes 916 ms — **4000× apart**.

## A real problem first

Given a list of names, decide whether **any name appears twice**.

```python
names = ["Alice", "Bob", "Cara", "Alice"]
```

"Alice" appears twice, so the answer is "yes".

**Solution one: compare everything with everything.** Take the first name and check it against everyone after it, then the second, and so on.

```python
def has_duplicate_v1(items):
    n = len(items)
    for i in range(n):
        for j in range(i + 1, n):
            if items[i] == items[j]:
                return True      # found a matching pair
    return False                  # compared everything, no match

print(has_duplicate_v1(["Alice", "Bob", "Cara", "Alice"]))   # True
print(has_duplicate_v1(["Alice", "Bob", "Cara"]))            # False
```

**Solution two: remember as you go.** Keep a set of names already seen, and check each new one against it.

```python
def has_duplicate_v2(items):
    seen = set()            # empty set of names seen so far
    for x in items:
        if x in seen:       # seen it before → duplicate
            return True
        seen.add(x)         # new one → remember it
    return False

print(has_duplicate_v2(["Alice", "Bob", "Cara", "Alice"]))   # True
print(has_duplicate_v2(["Alice", "Bob", "Cara"]))            # False
```

Both give the right answer. **And that's exactly where the real question begins.**

## How far apart are they? Let's measure

Build lists that contain no duplicates at all (so both functions must run to completion before answering "no"), then time them:

```python
import time

def time_ms(fn, items):
    best = float('inf')
    for _ in range(3):                  # run 3 times, keep the fastest
        t0 = time.perf_counter()
        fn(items)
        best = min(best, (time.perf_counter() - t0) * 1000)
    return best

for n in [500, 1000, 2000, 4000, 8000]:
    items = list(range(n))              # 0..n-1, no duplicates at all
    print(f"n={n:>5}  nested loops {time_ms(has_duplicate_v1, items):>8.2f} ms"
          f"   set {time_ms(has_duplicate_v2, items):>7.3f} ms")
```

Measured on an ordinary laptop (Python 3.10):

```
n=  500  nested loops     3.41 ms   set   0.015 ms
n= 1000  nested loops    13.74 ms   set   0.028 ms
n= 2000  nested loops    54.95 ms   set   0.067 ms
n= 4000  nested loops   221.78 ms   set   0.121 ms
n= 8000  nested loops   916.58 ms   set   0.228 ms
```

**At n=8000 the nested loop takes nearly a second; the set takes 0.0002 seconds — 4000× apart.**

> 📌 Your numbers will differ (faster or slower), but **the magnitude of the gap holds everywhere**. What matters isn't the exact milliseconds — it's how far apart they are, and why.

## Why the gap is so large

It comes down to **how many comparisons happen**.

**Solution one (nested loops):** with n items, the first is compared n-1 times, the second n-2 times… totalling roughly

```
(n-1) + (n-2) + ... + 1 = n × (n-1) / 2 ≈ n² / 2 comparisons
```

- n = 100 → about 5 000
- n = 1000 → about 500 000
- n = 8000 → about 32 million

**Solution two (set):** each item is looked up exactly once, so exactly n lookups.

- n = 100 → 100
- n = 1000 → 1000
- n = 8000 → 8000

**Spot the pattern.** When n doubles:

- solution one does **4×** the comparisons (it's n²)
- solution two does **2×** the comparisons (it's n)

The measurements confirm it perfectly:

```
nested loops: n 1000 → 2000, time 13.74 → 54.95 ms, exactly 4.00×
set:          n 1000 → 2000, time 0.028 → 0.067 ms, about 2.4×
```

## Three things worth taking away

**One: correctness is only the pass mark.**

Both functions are "right". But one needs a second of your time on 8000 items and the other needs 0.0002 seconds. **In interviews, in production, in contests, "produces the right answer" is never the finish line.**

**Two: data size is a magnifying glass.**

At small sizes the difference is invisible (at n=100 both are sub-millisecond and you'd never notice). **As n grows the gap explodes:**

Extrapolating from the measurements:

| Items | Nested loops | Set |
|---|---|---|
| 8 000 | 0.92 s | 0.0002 s |
| 100 000 | about 143 s (2 min 23 s) | about 0.003 s |
| 1 000 000 | about 4 hours | about 0.03 s |

**At a million items one takes four hours, the other takes less than a millisecond.** That isn't "optimisation" — it's the difference between usable and unusable.

**Three: speed can be worked out in advance, without guessing.**

You don't have to run the code to know which is faster — you just count how the number of operations grows with n. That's **complexity analysis**, and it's what this chapter is about.

## The syntax this book assumes (30-second recap)

Algorithm problems are written as functions, so let's confirm the handful of things you need:

```python
# 1. defining a function: def + name + parameters, return sends a value back
def add(a, b):
    return a + b

# 2. a for loop iterates
for x in [1, 2, 3]:
    print(x)

# 3. range(n) produces 0..n-1
for i in range(3):        # i is 0, then 1, then 2
    print(i)

# 4. conditionals
if x > 0:
    print("positive")

# 5. a set holds distinct values; "is it in there" is very fast
s = set()
s.add(1)
print(1 in s)      # True
print(2 in s)      # False

# 6. len() gives the length
print(len([1, 2, 3]))     # 3
```

**That's all you need.** Every problem from here is a `def` containing `for` / `if` / `return`.

> 💡 If `def` and `return` still feel unfamiliar, work through the relevant chapters of *Python Basics 1* first — everything here will feel easier afterwards.

## Summary

- One problem can have many solutions — **all correct, wildly different in speed**
- The difference comes from **how the operation count grows with n**
- Quadratic growth (nested loops) is a disaster at scale; linear growth (one pass) handles it easily
- **Complexity analysis** lets you predict speed without running anything

**Next: big-O notation** — the standard name for this kind of growth.
