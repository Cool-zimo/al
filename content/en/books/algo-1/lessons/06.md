# Two Pointers: Why Brute Force O(n²) Collapses to O(n)

> Two nested loops scan every pair. That is O(n²) — and for most array problems, most of those pairs are wasted work.

## Start with a concrete problem

You have a **sorted** array. Find two numbers that add up to a target, and return their indices.

```
nums   = [1, 3, 5, 7, 9, 11]
target = 12
answer = [1, 4]     # 3 + 9 = 12
```

### The brute force way

```python
nums = [1, 3, 5, 7, 9, 11]
target = 12

for i in range(len(nums)):
    for j in range(i + 1, len(nums)):
        if nums[i] + nums[j] == target:
            print(i, j)
            break
```

This works. It is also O(n²): for n = 6 it checks 15 pairs, for n = 1000 it checks about 500,000.

**Here is the thing nobody tells you: almost all of those checks are pointless.**

## The wasted work

Look at what happens when `i = 0` (value 1):

```
1 + 3  = 4    too small
1 + 5  = 6    too small
1 + 7  = 8    too small
1 + 9  = 10   too small
1 + 11 = 12   <- found it? no wait
```

With `target = 12`, as soon as `1 + 11 = 12` we are done. But suppose `target = 18`:

```
1 + 3  = 4
1 + 5  = 6
1 + 7  = 8
1 + 9  = 10
1 + 11 = 12   <- still too small, and this is the LARGEST partner 1 can have
```

Once `1 + 11 < 18`, we know **for free** that `1 + 3`, `1 + 5`, `1 + 7`, `1 + 9` are all too small too. The inner loop did five checks to learn one fact.

**That is the waste.** The array is sorted, so the largest possible partner tells you everything.

## One pointer at each end

Put `left` at the start and `right` at the end:

```python
nums = [1, 3, 5, 7, 9, 11]
target = 18

left, right = 0, len(nums) - 1
while left < right:
    s = nums[left] + nums[right]
    print(f"left={left}({nums[left]}) right={right}({nums[right]}) sum={s}")
    if s == target:
        print("found:", left, right)
        break
    elif s < target:
        left += 1      # too small -> need a bigger number -> move left rightward
    else:
        right -= 1     # too big   -> need a smaller number -> move right leftward
```

Run it and you see the whole journey:

```
left=0(1) right=5(11) sum=12
left=1(3) right=5(11) sum=14
left=2(5) right=5(11) sum=16
left=3(7) right=5(11) sum=18   <- found
```

**Four steps instead of fifteen.** And each step is *forced* — there is no other move that could possibly work.

## Why this is correct (the part that matters)

The whole trick rests on one sentence:

> Because the array is sorted, moving `left` rightward can only increase the sum, and moving `right` leftward can only decrease it.

So at each step there is exactly one thing to do:

| Situation | What you know | Move |
|---|---|---|
| `sum == target` | done | stop |
| `sum < target` | even the biggest partner is not enough → this `left` is hopeless | `left += 1` |
| `sum > target` | even the smallest partner is too much → this `right` is hopeless | `right -= 1` |

"Hopeless" is the key word. Brute force keeps trying a hopeless `left` against every `right`. Two pointers **discard** it in one step.

That is why the cost drops from O(n²) to O(n): each element is looked at at most once, and then never again.

## The loop condition: `left < right`, not `left <= right`

This bites everyone once.

```python
# WRONG
while left <= right:
    ...
```

When `left == right` you are pairing an element with **itself**. If the answer were allowed to use the same element twice, `nums = [5]`, `target = 10` would "work" — but that is not the problem.

```python
nums = [5]
target = 10
left, right = 0, 0
print(nums[left] + nums[right])    # 10 — but it used index 0 twice!
```

Two different elements means two different indices, so the pointers must never meet. `left < right` enforces that.

## It only works because the array is sorted

This is the condition people forget. Try it on an unsorted array:

```python
# WRONG: nums is not sorted
nums = [3, 1, 5]
target = 6
left, right = 0, len(nums) - 1
while left < right:
    s = nums[left] + nums[right]
    if s == target:
        print("found", left, right); break
    elif s < target:
        left += 1
    else:
        right -= 1
else:
    print("not found — but 1 + 5 = 6 exists at indices 1 and 2!")
```

The answer `[1, 2]` exists and the algorithm misses it. Why? Because "move `left` rightward to get a bigger sum" is **false** on an unsorted array — index 1 holds `1`, which is *smaller* than index 0's `3`.

**Rule: two-pointer sum search requires sorted input.** If the array is unsorted, either sort it first (O(n log n), and you lose the original indices), or use a hash map.

## The shape of the pattern

Every two-pointer solution has the same skeleton:

```python
left, right = 0, len(arr) - 1
while left < right:
    # 1. look at the pair
    # 2. is it the answer? -> return
    # 3. is it too small / too big? -> move exactly one pointer
    ...
# fell out of the loop -> no answer
return None
```

Three things to internalize:

1. **Both pointers start at the ends** — that is what "对撞 / collision" means.
2. **Exactly one pointer moves per step.** Never both.
3. **The loop moves at most n times total**, because `left` only increases and `right` only decreases, and they can never cross.

## Cost comparison

```python
def count_pairs_brute(n):
    return n * (n - 1) // 2

for n in (10, 100, 1000, 10000):
    print(f"n={n:6d}  brute={count_pairs_brute(n):12d}  two-pointer={n}")
```

```
n=    10  brute=        45  two-pointer=10
n=   100  brute=      4950  two-pointer=100
n=  1000  brute=    499500  two-pointer=1000
n= 10000  brute=  49995000  two-pointer=10000
```

At n = 10,000 that is 50 million operations versus 10 thousand — **a factor of 5,000**.

## A crash site: forgetting the no-answer case

```python
def two_sum_sorted(nums, target):
    left, right = 0, len(nums) - 1
    while left < right:
        s = nums[left] + nums[right]
        if s == target:
            return [left, right]
        elif s < target:
            left += 1
        else:
            right -= 1
    # WRONG: no return here!
```

```python
print(two_sum_sorted([1, 2, 3], 100))    # None
```

Python silently returns `None`. Your caller does `idx = two_sum_sorted(...)` then `nums[idx[0]]` → `TypeError: 'NoneType' object is not subscriptable`.

**Always decide what "not found" means** and return it explicitly — `None`, `-1`, or `[]` — and say so in the docstring.

## Another crash site: moving the wrong pointer

```python
# WRONG: directions swapped
if s < target:
    right -= 1     # makes the sum even smaller — infinite no-progress loop
else:
    left += 1
```

This does not crash. It just never finds anything, or `left` and `right` cross and it reports "not found" for an answer that exists. **Silent wrong answers are worse than crashes.** When you write the two branches, say out loud which direction makes the sum bigger.

## Summary

- Two pointers work when **the input is sorted** and you are looking for a **pair** (or a pair-like condition)
- `sum < target` → `left += 1`; `sum > target` → `right -= 1`
- Loop condition is `left < right` — never `<=`, or you pair an element with itself
- Cost: **O(n) time, O(1) extra space** (no new array, no hash map)
- Always handle "not found" explicitly

```quiz
type: choice
exam: true
q: With collision pointers on a sorted array, what happens if you write the loop as `left <= right` instead of `left < right`?
options:
- It runs one extra iteration where left == right, pairing an element with itself
- It becomes faster
- It causes an IndexError
- Nothing changes
answer: 0
explain: `left <= right` adds one final iteration where both pointers sit on the same index. For a "two different elements" problem that comparison is meaningless — and for something like `nums=[5], target=10` it produces a bogus match. The infinite-loop risk is nil, but the bogus match is real.
```
