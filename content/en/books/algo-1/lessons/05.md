# Measuring complexity yourself

> You analysed it as O(n²) — how do you check? **Run it and see what happens to the time when n doubles.** This lesson gives you a reusable way to measure.

## How to time things

### Method one: time.perf_counter()

```python
import time

t0 = time.perf_counter()
# ... code being measured ...
elapsed = (time.perf_counter() - t0) * 1000    # milliseconds
print(f"took {elapsed:.3f} ms")
```

**Why `perf_counter` rather than `time.time()`:** `perf_counter` is a high-resolution clock built for timing, and it isn't affected by adjustments to the system clock.

### Method two: the timeit module (more rigorous)

```python
import timeit

t = timeit.timeit(lambda: sum(range(1000)), number=1000)
print(f"1000 runs: {t*1000:.1f} ms, per run {t*1000/1000:.4f} ms")
```

**`number=N` repeats the call N times** and returns the total. It handles the repetition for you, which makes it more reliable than hand-written timing.

## The key: run it several times, keep the smallest

**A single measurement is barely trustworthy.** Running the same operation five times gave:

```
run 1  14.5 ms
run 2  11.2 ms
run 3  10.8 ms
run 4  10.8 ms
run 5  10.5 ms   ← the minimum
```

The first run is clearly slower (Python is still warming up internals); afterwards it settles.

**Why the minimum rather than the average?**

Because timing can only be made **worse** by interference — system scheduling, background programs, CPU throttling all **add** time, never remove it. So **the minimum is closest to the clean time the code genuinely needs**.

```python
def time_ms(fn, *args, reps=3):
    best = float('inf')
    for _ in range(reps):
        t0 = time.perf_counter()
        fn(*args)
        best = min(best, (time.perf_counter() - t0) * 1000)
    return best
```

**Memorise this `time_ms` template** — every measurement from here uses it.

## Verifying complexity: the doubling method

**The core method:** double n and see what happens to the time.

- **2×** → it's O(n)
- **4×** → it's O(n²)
- **8×** → it's O(n³)
- barely **changes** → O(1) or O(log n)

```python
import time

def count_pairs(items):        # O(n²): pairwise
    c = 0
    n = len(items)
    for i in range(n):
        for j in range(i + 1, n):
            if items[i] < items[j]:
                c += 1
    return c

def count_all(items):          # O(n): one pass
    c = 0
    for x in items:
        c += 1
    return c

def measure(fn, n):
    items = list(range(n))
    best = float('inf')
    for _ in range(3):
        t0 = time.perf_counter()
        fn(items)
        best = min(best, (time.perf_counter() - t0) * 1000)
    return best

prev = None
for n in [500, 1000, 2000, 4000]:
    t = measure(count_pairs, n)
    ratio = f"{t/prev:.2f}" if prev else "—"
    print(f"n={n:>5}  {t:>8.2f} ms   (vs previous: {ratio}x)")
    prev = t
```

We ran this in lesson one. The measured result:

```
n=  500     3.41 ms
n= 1000    13.74 ms   (4.03x)
n= 2000    54.95 ms   (4.00x)
n= 4000   221.78 ms   (4.04x)
```

**Every step is about 4.00× — a textbook confirmation of O(n²).** Swap in the O(n) `count_all` and you'd see roughly 2×.

## A complication you must know: built-ins are written in C

```python
import time

items = list(range(100000))

def manual_sum(xs):          # pure Python loop
    total = 0
    for x in xs:
        total += x
    return total

# measured: manual loop 1.81 ms, built-in sum() 0.20 ms → built-in is 9× faster
```

**The same O(n) work, 9× faster as a built-in.** The reason: `sum()` runs a C loop internally, without the per-line cost of the Python interpreter.

**What this means:**

- **Big-O tells you the growth trend** (double n → double the time)
- **The constant factor sets the baseline** (same O(n), but C is nearly 10× faster than a Python loop)

So there are two ways to optimise:

1. **Drop a complexity class** (O(n²) → O(n)) — enormous payoff, do this first
2. **Reduce the constant** (use built-ins, use C libraries) — smaller, but worthwhile within a class

> 💡 **Order matters:** drop complexity first, shave constants second. The 4000× gap in lesson one came from a complexity drop; this 9× is only a constant.

## Four traps when measuring

**1. Too little data to see anything.**

At n=10, both O(n) and O(n²) take microseconds, and noise hides the difference entirely. **Measure into the thousands** before the trend appears.

**2. Early exits hide the worst case.**

If the data happens to contain a duplicate, the check returns at the first hit and looks blindingly fast. **To measure the worst case, build data that can't exit early** (`list(range(n))` guarantees no duplicates).

**3. The first run carries warm-up cost.**

Python has various lazy loading mechanisms, so the first call tends to be slow. **Three runs, take the minimum** avoids this.

**4. Background programs interfere.**

Turn off downloads, video, virus scans. **Using the minimum** is a defence here too.

## A complete measurement template

Fix this whole routine in place so you can reuse it any time:

```python
import time

def measure(fn, make_data, sizes, reps=3):
    """Time fn at several data sizes; returns [(n, ms, ratio_vs_previous)]"""
    out = []
    prev = None
    for n in sizes:
        data = make_data(n)
        best = float('inf')
        for _ in range(reps):
            t0 = time.perf_counter()
            fn(data)
            best = min(best, (time.perf_counter() - t0) * 1000)
        ratio = (best / prev) if prev else None
        out.append((n, best, ratio))
        prev = best
    return out

# usage
sizes = [500, 1000, 2000, 4000]
for n, ms, ratio in measure(count_pairs, lambda n: list(range(n)), sizes):
    r = f"{ratio:.2f}x" if ratio else "—"
    print(f"n={n:>5}  {ms:>8.2f} ms  {r}")
```

**Read the ratio column and you know the complexity.**

## Inferring complexity from measurements

| Time multiplier when n doubles | Complexity |
|---|---|
| ≈ 1 (barely changes) | O(1) or O(log n) |
| ≈ 2 | O(n) |
| ≈ 2.x (a little above 2) | O(n log n) |
| ≈ 4 | O(n²) |
| ≈ 8 | O(n³) |

**The most practical trick in engineering:** don't read the code — run two sizes and the bottleneck reveals itself.

## Summary

- Time with `time.perf_counter()` or `timeit`
- **Run several times, keep the minimum** (interference only ever slows things down)
- **The doubling method**: 2× means O(n), 4× means O(n²)
- Built-ins are implemented in C and much faster within the same complexity — **drop complexity first, shave constants second**
- Four traps: tiny data, early exits, first-run warm-up, background load
