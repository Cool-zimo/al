# Hands On: Taking Apart the Three-Sum Thought Process

> Three-sum is an interview favorite and the most classic two-pointer exercise in practice. This lesson tears the thinking apart layer by layer: **sort first, then pin one and hunt for two**.

## The problem

**Given an integer array `nums`, find every triple `[nums[i], nums[j], nums[k]]` such that `i < j < k` and the three values add up to 0. The answer must not contain duplicate triples.**

```python
nums = [-1, 0, 1, 2, -1, -4]
# all unique triples:
# [-1, -1, 2]
# [-1, 0, 1]
```

## Step 1: sort

Why sort at all? Because **a sorted array unlocks two-pointer techniques**, and sorting also herds equal values together, which makes dedup possible.

```python
nums.sort()   # [-4, -1, -1, 0, 1, 2]
```

**Sorting costs O(n log n)** — far less than the brute-force O(n³) we are about to get rid of.

## Step 2: pin one, find two

Brute force uses three nested loops, O(n³). The optimization rests on one idea:

> First fix one number `nums[i]`. Then, **in the part of the array after `i`, find two numbers that sum to `-nums[i]`**.

**Finding two numbers** — that is exactly the two-sum problem from lesson 06. But now the array is sorted, so you can solve it in O(n) with **collision pointers**.

```python
for i in range(n):
    target = -nums[i]          # find two numbers after i that sum to -nums[i]
    left = i + 1               # left pointer starts at i+1
    right = n - 1              # right pointer starts at the end
    while left < right:
        s = nums[left] + nums[right]
        if s == target:
            # found a triple
            ...
        elif s < target:
            left += 1
        else:
            right -= 1
```

**Outer loop O(n), inner two-pointer O(n) → overall O(n²).**

## Step 3: dedup

This is the tricky part. The problem demands **no duplicate triples**.

### Dedup on i

If `nums[i] == nums[i-1]`, the current element is the same as the previous one. So the triples you find by pinning it will be identical to the ones you already found in the last round → skip it.

```python
if i > 0 and nums[i] == nums[i - 1]:
    continue
```

### Dedup on left and right

Once you find a valid triple, `left` and `right` may still be pointing at copies of the same element. You must skip them.

```python
if s == target:
    result.append([nums[i], nums[left], nums[right]])
    # dedup left
    while left < right and nums[left] == nums[left + 1]:
        left += 1
    # dedup right
    while left < right and nums[right] == nums[right - 1]:
        right -= 1
    # normal advance
    left += 1
    right -= 1
```

## The full code

```python
def three_sum(nums):
    nums.sort()
    n = len(nums)
    result = []

    for i in range(n - 2):                          # i can go at most to n-3
        # dedup i
        if i > 0 and nums[i] == nums[i - 1]:
            continue
        # small optimization: if nums[i] > 0, everything after it is positive too
        if nums[i] > 0:
            break

        target = -nums[i]
        left = i + 1
        right = n - 1

        while left < right:
            s = nums[left] + nums[right]
            if s == target:
                result.append([nums[i], nums[left], nums[right]])
                # dedup left and right
                while left < right and nums[left] == nums[left + 1]:
                    left += 1
                while left < right and nums[right] == nums[right - 1]:
                    right -= 1
                left += 1
                right -= 1
            elif s < target:
                left += 1
            else:
                right -= 1

    return result

print(three_sum([-1, 0, 1, 2, -1, -4]))
# [[-1, -1, 2], [-1, 0, 1]]
```

## Trace it by hand

`nums = [-1, 0, 1, 2, -1, -4]` → after sorting `[-4, -1, -1, 0, 1, 2]`

```
i=0: nums[0]=-4, target=4
  left=1, right=5: nums[1]+nums[5] = -1+2 = 1 < 4 -> left++
  left=2, right=5: -1+2 = 1 < 4 -> left++
  ... no match, right keeps shrinking until left==right

i=1: nums[1]=-1, target=1
  left=2, right=5: -1+2 = 1 == 1 -> found [-1,-1,2]! dedup left/right
  left=3, right=4: 0+1 = 1 == 1 -> found [-1,0,1]!

i=2: nums[2]==nums[1] (-1==-1) -> skip (dedup)

i=3: nums[3]=0 > 0 -> break (everything after is >0, sum can't be 0)
```

## Complexity analysis

| Step | Complexity |
|---|---|
| sort | O(n log n) |
| outer loop on i | O(n) |
| inner two-pointer | O(n) |
| **total** | **O(n log n) + O(n²) = O(n²)** |

**We dropped from brute-force O(n³) to O(n²)** — at n = 1000 that is a 1000x difference.

## Common mistakes

### Mistake 1: forgetting to sort

Two pointers only make sense on a sorted array. If you skip the sort, the pointer logic silently falls apart and you miss answers.

```python
# WRONG: never sorted
def three_sum_buggy(nums):
    n = len(nums)
    for i in range(n - 2):
        left = i + 1
        right = n - 1
        while left < right:
            s = nums[i] + nums[left] + nums[right]
            if s == 0:
                ...
            elif s < 0:
                left += 1
            else:
                right -= 1
```

With `nums = [3, 0, -1, -2, 1, 1, 2]`, running two pointers on the unsorted array makes the comparison `s < 0` meaningless — you cannot tell which side to move, so you miss valid triples that the sorted version would catch immediately.

**WRONG output** (running the unsorted version on `[-1, 0, 1, 2, -1, -4]`):

```
[]
# empty! the triple [-1, 0, 1] exists, but the unsorted pointers never see it.
```

### Mistake 2: dedup in the wrong place

```python
# WRONG: dedup before appending
if nums[left] == nums[left + 1]:
    left += 1
# this skips valid elements!
```

**Dedup must happen AFTER you record the answer.** If you move `left` and `right` past duplicates before appending, you throw away a perfectly good triple. Always append first, then skip the copies.

**WRONG output** (deduping before append on `[-4, -1, -1, 0, 1, 2]`, i=1):

```
[]   # you skipped both the (-1, 2) and (0, 1) pairs before recording them
```

### Mistake 3: `i` loop goes to `range(n)`

```python
# WRONG: i walks off the cliff
for i in range(n):        # at i=n-2, left=n-1 and right=n-1, loop body still runs
                          # at i=n-1, left=n -> IndexError
```

**`i` can reach at most n-3** — you must leave room behind it for `left` and `right`. Going to `n-2` lets the inner `while left < right` fail (both point at the same slot), and going to `n-1` blows up with an `IndexError`.

**WRONG output** (looping to `range(n)` on `[-4, -1, -1, 0, 1, 2]`):

```
IndexError: list index out of range
```

## Crash site: all three at once

```python
# WRONG: unsorted + early dedup + runaway i
def three_sum_disaster(nums):
    n = len(nums)
    result = []
    for i in range(n):                     # 1) i runs to n-1 -> out of bounds
        left = i + 1
        right = n - 1
        while left < right:
            s = nums[left] + nums[right]
            if s == -nums[i]:
                if nums[left] == nums[left + 1]:   # 2) dedup before recording
                    left += 1
                if nums[right] == nums[right - 1]: # 2) dedup before recording
                    right -= 1
                # result.append(...)  <- 3) forgot to append entirely
                left += 1
                right -= 1
            elif s < -nums[i]:
                left += 1
            else:
                right -= 1
    return result

print(three_sum_disaster([3, 0, -1, -2, 1, 1, 2]))
# []     <- WRONG, should contain triples; the array was never sorted so
#           the pointer logic is meaningless, dedup ate valid pairs before
#           they were recorded, and append was never called anyway.
```

This is the triple-whammy. It runs, it prints, it is completely wrong — and that is exactly why dedup order and the `i` bound deserve their own section.

## The general recipe

The three-sum trick generalizes to **any problem that asks you to find k numbers satisfying some condition**:

1. **Sort** (enables two pointers + makes dedup easy)
2. **Pin one, find the rest** (turns a k-sum into a (k-1)-sum)
3. **Two pointers to find two numbers** O(n)
4. **Dedup** (skip repeated elements)

**Four-sum**: pin two, two-pointer the other two → O(n³).
**k-sum**: recursively pin k-2 values, then use two pointers on the remainder → O(n^(k-1)).

## Summary

- Three-sum: sort first, then "pin one, find two"
- "Find two numbers summing to target" is solved with collision pointers in O(n)
- Outer loop pins `i`, giving O(n²) overall — far better than brute O(n³)
- Dedup is the key move: dedup `i`, then dedup `left`/`right` after recording
- The recipe generalizes: sort + pin (k-2) + two pointers
