# Fixed Windows: Maximum Sum of Size k and Moving Averages

> Fixed windows are the gateway to all window techniques. The window length k stays constant; each slide is just "drop the leftmost, add the rightmost." This lesson breaks down the pattern and exposes a hidden performance trap.

## The Core Operation

A fixed window has a three-step skeleton:

```python
nums = [3, 1, 4, 1, 5, 9, 2, 6]
k = 4

# Step 1: compute the first window
window_sum = sum(nums[:k])
max_sum = window_sum

# Step 2: slide one position at a time
for i in range(k, len(nums)):
    window_sum = window_sum - nums[i - k] + nums[i]
    max_sum = max(max_sum, window_sum)

# Step 3: output the result
print(max_sum)  # 21
```

`window_sum - nums[i-k] + nums[i]` is the soul of every fixed window. **Remove the element leaving the window; add the element entering it.**

## Why O(n), Not O(nk)

Here's how many people naively write it:

```python
# Naive: recompute every window from scratch
nums = [3, 1, 4, 1, 5, 9, 2, 6]
k = 4
max_sum = 0

for i in range(len(nums) - k + 1):
    current_sum = sum(nums[i:i + k])  # O(k) every time!
    max_sum = max(max_sum, current_sum)

print(max_sum)  # 21
```

**The result is correct, but the performance is terrible.** `sum(nums[i:i+k])` rescans k elements each iteration, and the outer loop runs n-k+1 times → **O(nk)**. With n=100,000 and k=50,000, that's five billion operations.

With a sliding window, each element is **added once and removed once** → **O(n)**, regardless of k.

## Crash Scene 1: Integer Division for Averages

"Maximum average subarray of length k" is LeetCode 643. A common buggy attempt:

```python
nums = [1, 12, -5, -6, 50, 3]
k = 4

window_sum = sum(nums[:k])
max_avg = window_sum // k  # WRONG! Integer division

for i in range(k, len(nums)):
    window_sum = window_sum - nums[i - k] + nums[i]
    max_avg = max(max_avg, window_sum // k)

print(max_avg)  # 12 (WRONG)
```

The correct output is 12.75 (window `[12, -5, -6, 50]` sums to 51, and 51/4 = 12.75).

**Why it fails**: `//` is floor division, truncating the fractional part. `51 // 4 = 12`, but the correct answer needs `51 / 4 = 12.75`.

```python
# Correct version
window_sum = sum(nums[:k])
max_avg = window_sum / k  # Use true division

for i in range(k, len(nums)):
    window_sum = window_sum - nums[i - k] + nums[i]
    max_avg = max(max_avg, window_sum / k)

print(f"{max_avg:.2f}")  # 12.75
```

**Lesson**: For averages, ratios, or probabilities, always use `/` not `//`.

## Crash Scene 2: Not Handling Arrays Shorter Than k

What if the input array is shorter than k?

```python
nums = [1, 2]
k = 5

window_sum = sum(nums[:k])  # No error! Returns 3
print(window_sum)
```

`nums[:5]` **silently returns all elements** when the list is too short. This causes all downstream logic to be wrong.

```python
# Defensive version
def max_sum_k(nums, k):
    if len(nums) < k:
        return None  # or raise, or return 0 — depends on spec
    window_sum = sum(nums[:k])
    max_sum = window_sum
    for i in range(k, len(nums)):
        window_sum = window_sum - nums[i - k] + nums[i]
        max_sum = max(max_sum, window_sum)
    return max_sum

print(max_sum_k([1, 2], 5))        # None
print(max_sum_k([1, 2, 3, 4, 5], 3))  # 12
```

**Lesson**: Always consider invalid inputs, especially when slicing or dividing.

## Printing All Window Averages

Sometimes you need **every** window's average, not just the max:

```python
temps = [68, 77, 73, 82, 86, 81, 79]
k = 3

# Compute 3-day moving average
averages = []
window_sum = sum(temps[:k])
averages.append(window_sum / k)

for i in range(k, len(temps)):
    window_sum = window_sum - temps[i - k] + temps[i]
    averages.append(window_sum / k)

for i, avg in enumerate(averages):
    day_start = i + 1
    day_end = i + k
    print(f"Day {day_start}-{day_end} avg: {avg:.1f}°F")

# Day 1-3 avg: 72.7°F
# Day 2-4 avg: 77.3°F
# Day 3-5 avg: 80.3°F
# Day 4-6 avg: 83.0°F
# Day 5-7 avg: 82.0°F
```

This is a **moving average** — ubiquitous in finance, weather, and signal processing.

## The Universal Fixed-Window Template

Abstract the pattern into a reusable template:

```python
def fixed_window_template(nums, k):
    if len(nums) < k:
        return  # handle edge case

    # 1. Initialize: compute state of the first window
    window_state = compute_state(nums[:k])

    # 2. Slide
    for i in range(k, len(nums)):
        # Remove nums[i - k]
        remove_from_state(nums[i - k])
        # Add nums[i]
        add_to_state(nums[i])
        # Update answer
        update_answer(window_state)

    # 3. Return result
    return answer
```

Replace `compute_state`, `remove_from_state`, `add_to_state`, and `update_answer` with whatever the problem demands.

## Crash Scene 3: Confusing Add/Subtract Direction

Look at this code:

```python
nums = [5, 2, 8, 1, 9, 3]
k = 3
n = len(nums)

window_sum = sum(nums[:k])
max_sum = window_sum

for i in range(k, n):
    # Which is correct?
    window_sum = window_sum + nums[i] - nums[i - k]   # A
    window_sum = window_sum - nums[i - k] + nums[i]   # B
    window_sum = window_sum - nums[i] + nums[i - k]   # C (WRONG!)
    max_sum = max(max_sum, window_sum)

print(max_sum)
```

A and B are both correct (addition is commutative). C is wrong — the author **reversed the signs**: it should be "subtract old, add new," but they wrote "subtract new, add old."

**Debugging tip**: Draw the window on paper, mark which element leaves and which enters, then check the signs in your code against your diagram.

## Summary

- Fixed window length never changes; the core is `window_sum - nums[i-k] + nums[i]`
- Sliding window is O(n); recomputing each window is O(nk) — a massive difference
- Use `/` not `//` for averages, or you'll lose precision
- Guard against `len(nums) < k` at the start
- Be disciplined about variable naming and sign direction; standardize as "subtract first, add second"
