# The after() Timer: Why You Must Not Use while True for Animation

> When you want something to move on screen, the first idea is often "just add a loop". But in a GUI program, `while True` will freeze the interface outright. This lesson introduces tkinter's proper timing mechanism: `after()`.

## The Problem: How Do You Make a Shape "Move by Itself"?

**Requirement:** make a square move 5 pixels every 50 milliseconds to simulate "automatic movement".

The intuitive version:

```python
import time

while True:
    canvas.move(rect, 5, 0)
    time.sleep(0.05)
```

**This version freezes the program completely.** Why? Because tkinter's event loop (`mainloop`) is hijacked by your `while` loop and can never move on to redraw the window or handle the mouse.

## Why while True Does Not Work

**tkinter uses a single-threaded, event-driven model:** `mainloop()` constantly "fetches an event, processes it, redraws the interface".

```
A simplified view of mainloop:
  while the program is running:
      fetch an event (click, keypress, timer)
      call the matching handler
      refresh the display
```

**Once you put `while True` inside a handler**, the event loop is stuck in that infinite loop and cannot escape — it cannot fetch the next event, cannot redraw, and cannot respond to a window drag. It may even **ignore a click on the close button** (forcing you to terminate the program from the operating system).

## The Correct Approach: after()

**`widget.after(milliseconds, function)` means: "call this function after this many milliseconds."** It does not block and wait; instead it "registers" a future task with the event loop, then returns immediately so `mainloop` can keep running.

```python
import tkinter as tk

root = tk.Tk()
canvas = tk.Canvas(root, width=400, height=200, bg="white")
canvas.pack()

rect = canvas.create_rectangle(10, 50, 60, 100, fill="orange")

def move_step():
    canvas.move(rect, 5, 0)
    # Register the next call
    root.after(50, move_step)

move_step()          # start the first invocation
root.mainloop()
```

**The key point: `move_step` registers the next `after` call before it returns.** That way the event loop is free after each move to handle other events and redraw the display.

**This is "recursive timing"** — the function schedules itself to run again, producing a continuous loop, but yields back to the event loop between each pair of calls.

## The Two Uses of after

| Use | Purpose |
|---|---|
| `after(ms, func)` | Run the function after a delay (func takes no arguments) |
| `after(ms)` | Wait only; returns an "id" that can be used with `after_cancel` |

**The no-function form `after(ms)` is rarely used on its own**; its main role is "do something after a delay".

## Crash Site One: Calling the after Callback with Parentheses

```
root.after(1000, move_step())   # executes move_step immediately, not after 1 second
```

**Symptom:** `move_step()` runs straight away, and its return value (None) is treated as "the function to call", so after 1 second an error is raised.

**Cause:** `after(ms, func)` expects a function object. `move_step()` with parentheses means "call it right now", and the return value is passed to `after` instead.

**Fix:** drop the parentheses and pass the function itself:

```python
root.after(1000, move_step)
```

**If the callback needs arguments, use a lambda:**

```python
root.after(1000, lambda: move_step(5))
```

## Crash Site Two: Forgetting to Re-register the Timer, So It Runs Once

```
def move_step():
    canvas.move(rect, 5, 0)
    # after was forgotten

move_step()
```

**Symptom:** the square moves exactly once and then stops.

**Cause:** only one call was registered. The body of `move_step` must include another `root.after(50, move_step)` to keep the loop going. That is the essential structure of "recursive timing".

## Crash Site Three: Trying to Slow the Animation Down with time.sleep

```
def move_step():
    canvas.move(rect, 5, 0)
    time.sleep(0.05)          # WRONG! freezes the interface
    root.after(50, move_step)
```

**Symptom:** the animation is jerky, the window lags, and may even become unresponsive.

**Cause:** `time.sleep` is **blocking** — while it runs, the entire thread is suspended and the event loop cannot do its work. **Never** use `time.sleep` to pace an animation in a GUI.

**The correct approach:** schedule everything with `after`. "I want to take the next step in 50 ms" becomes `after(50, next_step)`.

## Using after for a "Delayed One-Off Task"

**after is not only for loops; it is also useful for "do something automatically a few seconds from now":**

```python
def show_tip():
    label.configure(text="Done!", fg="green")

def on_click():
    label.configure(text="Working...", fg="gray")
    root.after(1500, show_tip)   # show success after 1.5 seconds

tk.Button(root, text="Submit", command=on_click).pack()
```

**This is "fake asynchronous" behaviour:** the button gives feedback immediately and `after` schedules the follow-up. The interface never freezes and the user experience is far better.

## Cancelling a Timer: after_cancel

**`after` returns a "job ID" that can be passed to `after_cancel(id)` to cancel a task that has not run yet:**

```python
job_id = root.after(3000, some_func)

def cancel():
    root.after_cancel(job_id)
```

**Common scenarios:** countdowns, auto-save and carousels — whenever you need to "restart", cancel the old timer before scheduling the new one.

```python
self.timer = None

def start_countdown(self):
    if self.timer:
        root.after_cancel(self.timer)   # cancel the old one first
    self.timer = root.after(1000, self.tick)
```

## Summary

- tkinter runs a single-threaded event loop, so **`while True` and `time.sleep` will both freeze the interface**
- `after(ms, func)` registers a future task without blocking, yielding time back to the event loop
- For continuous animation use "recursive timing": have `func` call `after` on itself
- Do **not** add parentheses to the callback; pass the function object, or use `lambda` for arguments
- `after` returns an id that can be cancelled with `after_cancel`
- To "slow things down", control the pace with `after`; never use `time.sleep`
