# State Management: Using One Variable to Switch Between Start, Playing, and Game Over

> Your first game only had one state: "playing". But real games have start menus, pause screens, and result screens. This lesson covers how to use **one `state` variable** to connect all these screens.

## Why You Need State

**Without state management, your code looks like this:**

```python
running = True
while running:
    for event in pygame.event.get():
        if event.type == pygame.QUIT:
            running = False
    # Here you draw the menu, the game, and the end screen
    # Using a bunch of if statements to figure out what to draw...
```

**The problem**: all logic crams into one loop — whether the menu should respond to clicks, whether the game should track score, whether the end screen should show the high score — all decided by nested `if` statements, quickly turning into "spaghetti."

**Solution**: use a variable to remember "which screen we're on", and branch in the loop based on it.

## Using Strings as States

**The simplest approach: `state` is a string with values like `'menu'` / `'playing'` / `'gameover'`.**

```python
state = 'menu'          # Start on the menu

running = True
while running:
    for event in pygame.event.get():
        if event.type == pygame.QUIT:
            running = False

        if state == 'menu':
            if event.type == pygame.KEYDOWN and event.key == pygame.K_RETURN:
                state = 'playing'          # Press Enter to start

        elif state == 'playing':
            if event.type == pygame.KEYDOWN and event.key == pygame.K_ESCAPE:
                state = 'menu'              # Press Esc to return to menu

        elif state == 'gameover':
            if event.type == pygame.KEYDOWN and event.key == pygame.K_r:
                state = 'playing'           # Press R to restart

    screen.fill((0, 0, 0))

    if state == 'menu':
        screen.blit(title_text, (250, 200))
    elif state == 'playing':
        # Game logic + drawing
        pass
    elif state == 'gameover':
        screen.blit(over_text, (250, 200))

    pygame.display.flip()
    clock.tick(60)
```

**This is the beginning of a state machine**: `state` is the current state, events change it, and drawing branches on it.

## State Transitions Must Include "Cleanup"

**Just changing `state` is often not enough.** Going from menu to game, you must reset the score and put the player back at the start; going from game to game over, you must record the final score.

**Do initialization at the moment of transition, not later:**

```python
if state == 'menu' and key == pygame.K_RETURN:
    score = 0                          # Reset score
    player.rect.center = (400, 300)    # Reset player position
    state = 'playing'
```

**Anti-example**: putting `score = 0` inside `if state == 'playing':` every frame — then the score would always be zero and the game would be unplayable.

## Crash Scene 1: Too Many States Causes if-Nesting to Spiral Out of Control

```python
if state == 'menu':
    if event.type == pygame.KEYDOWN:
        if event.key == pygame.K_RETURN:
            if score > 100:            # Only allow play if unlocked
                state = 'playing'
```

**Symptom**: Logic keeps piling up, indentation reaches 8 levels deep, change one thing and three things break.

**Why**: "State checking" and "actual logic" are mixed together.

**Solution**: **extract each state into a function**, and only call them from the loop.

```python
def handle_menu(event):
    if event.type == pygame.KEYDOWN and event.key == pygame.K_RETURN:
        return 'playing'
    return 'menu'

def handle_playing(event):
    if event.type == pygame.KEYDOWN and event.key == pygame.K_ESCAPE:
        return 'menu'
    return 'playing'

while running:
    for event in pygame.event.get():
        if event.type == pygame.QUIT:
            running = False
        state = {
            'menu': handle_menu,
            'playing': handle_playing,
        }[state](event)
```

**This is the "lookup table" approach**: map state names to handler functions; adding a state means adding one function and one dictionary entry.

## Crash Scene 2: Changed state but Forgot to Redraw

```python
if event.key == pygame.K_RETURN:
    state = 'playing'
# Then nothing is drawn
```

**Symptom**: Press Enter, but the screen stays frozen on the menu, looking like nothing happened. It refreshes after a while.

**Why**: You changed `state`, but **this frame's drawing code is still drawing the menu**. It won't take the new branch until after `flip()` and the next frame.

**This isn't a bug — it's normal frame-driven behavior.** But if you have **an expensive operation** during the transition (loading images, reading files), it will hang. So **load heavy resources upfront**, not at the moment of transition.

## Crash Scene 3: Events Get "Swallowed" or Processed Twice

```python
for event in pygame.event.get():
    if state == 'menu':
        if event.key == pygame.K_SPACE:
            state = 'playing'
    if state == 'playing':          # Note: still the same event loop
        if event.key == pygame.K_SPACE:
            fire()                  # Just entered the game and immediately fired!
```

**Symptom**: Press Enter to enter the game, and the character instantly casts a skill / a bullet fires.

**Why**: The same event object is checked by multiple `if` branches; after `state` changes, the lower branches still check against the **old event's attributes**.

**Solution**: use `elif` instead of a series of independent `if` statements.

```python
if state == 'menu':
    ...
elif state == 'playing':     # Only one branch will be entered
    ...
```

## Crash Scene 4: Typo in state String But No Error

```python
state = 'playeing'          # Typo
# Later, if state == 'playing': never matches
```

**Symptom**: No error at all, but nothing responds no matter what you press.

**Why**: String comparison doesn't error out; a typo just means the comparison fails. This is a "silent error."

**Countermeasure**: **use constants (variables) instead of literal strings** — a typo will raise `NameError` when referenced:

```python
MENU = 'menu'
PLAYING = 'playing'
GAMEOVER = 'gameover'

state = MENU
# Later writing if state == PLAYIGN:  ← immediate NameError, caught right away
```

You can go further and use integer enums — faster comparison and typos guaranteed to error out.

## Summary

- State management = one `state` variable + modify it in events + branch on it in drawing
- Common three states: `menu` (start) → `playing` (in-game) → `gameover` (end)
- On transition, reset data: score to zero, character to start, timer to zero
- As states multiply, extract functions + use lookup tables instead of stacking if-nesting
- Use `elif` to branch on the same event, otherwise you'll get double-triggering
- Use constants instead of state strings to turn silent typos into errors
