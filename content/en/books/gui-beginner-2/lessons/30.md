# Final Project: A Complete Mini-Game and What to Learn Next

> The previous five chapters covered sprites, collision, sound, state, saving, and debugging. This lesson **brings it all together** into a complete mini-game that you can play, save scores in, with a menu, sound effects, and an end screen — and tells you where to go from here.

## What a Complete Game Looks Like

**"Complete" doesn't mean "complex" — it means "a closed loop".** At minimum, a mini-game should have:

1. **Menu** (with a start entry point)
2. **Game loop** (with gameplay and scoring)
3. **End screen** (showing results, with a restart option)
4. **Save system** (high score persists between sessions)
5. **Sound** (feedback)
6. **Fault tolerance** (corrupted saves don't crash, missing images don't crash)

**This lesson turns these into a "catch game": a paddle moves left/right at the bottom, a ball falls automatically, catch it for points, miss it and lose points, settle the score after 30 seconds, and save the new high score to disk.**

## Complete Code (Broken Into Pieces)

**Step 1: initialization and utility functions.**

```python
import json
import os
import random
import pygame

pygame.init()
pygame.mixer.init()
screen = pygame.display.set_mode((600, 500))
clock = pygame.time.Clock()
font = pygame.font.Font(None, 36)

SAVE_FILE = "save.json"
DEFAULT = {"high_score": 0}

def load_save():
    try:
        with open(SAVE_FILE, "r", encoding="utf-8") as f:
            return json.load(f)
    except (json.JSONDecodeError, FileNotFoundError, OSError):
        return dict(DEFAULT)

def save_high(score):
    data = load_save()
    if score > data["high_score"]:
        data["high_score"] = score
        tmp = SAVE_FILE + ".tmp"
        with open(tmp, "w", encoding="utf-8") as f:
            json.dump(data, f, ensure_ascii=False, indent=2)
        os.replace(tmp, SAVE_FILE)
```

**Step 2: define sprites — the ball and paddle.**

```python
class Paddle(pygame.sprite.Sprite):
    def __init__(self):
        super().__init__()
        self.image = pygame.Surface((100, 15))
        self.image.fill((0, 200, 255))
        self.rect = self.image.get_rect(center=(300, 470))

    def update(self, keys):
        if keys[pygame.K_LEFT] and self.rect.left > 0:
            self.rect.x -= 6
        if keys[pygame.K_RIGHT] and self.rect.right < 600:
            self.rect.x += 6

class Ball(pygame.sprite.Sprite):
    def __init__(self):
        super().__init__()
        self.image = pygame.Surface((20, 20))
        self.image.fill((255, 200, 0))
        self.rect = self.image.get_rect(center=(300, 50))
        self.vy = 4

    def update(self):
        self.rect.y += self.vy
```

**Step 3: state machine + main loop.**

```python
MENU, PLAYING, GAMEOVER = 'menu', 'playing', 'gameover'
state = MENU
save = load_save()
score = 0
time_left = 30
start_ticks = 0

paddle = Paddle()
ball = Ball()
all_sprites = pygame.sprite.Group(paddle, ball)

running = True
while running:
    keys = pygame.key.get_pressed()

    for event in pygame.event.get():
        if event.type == pygame.QUIT:
            running = False

        if state == MENU:
            if event.type == pygame.KEYDOWN and event.key == pygame.K_SPACE:
                score = 0
                time_left = 30
                start_ticks = pygame.time.get_ticks()
                ball.rect.center = (random.randint(20, 580), 50)
                state = PLAYING

        elif state == PLAYING:
            if event.type == pygame.KEYDOWN and event.key == pygame.K_ESCAPE:
                state = MENU

        elif state == GAMEOVER:
            if event.type == pygame.KEYDOWN and event.key == pygame.K_r:
                state = MENU

    # ---- Logic ----
    if state == PLAYING:
        paddle.update(keys)
        ball.update()

        if ball.rect.colliderect(paddle.rect):
            score += 10
            ball.rect.center = (random.randint(20, 580), 50)

        if ball.rect.top > 500:
            score = max(0, score - 5)
            ball.rect.center = (random.randint(20, 580), 50)

        elapsed = (pygame.time.get_ticks() - start_ticks) // 1000
        time_left = 30 - elapsed
        if time_left <= 0:
            save_high(score)
            save = load_save()
            state = GAMEOVER

    # ---- Rendering ----
    screen.fill((20, 20, 40))
    if state == MENU:
        screen.blit(font.render("Catch Game", True, (255, 255, 255)), (240, 180))
        screen.blit(font.render("Press SPACE to start", True, (200, 200, 200)), (220, 240))
    elif state == PLAYING:
        all_sprites.draw(screen)
        screen.blit(font.render(f"Score: {score}  Time: {time_left}", True, (255, 255, 0)), (10, 10))
    elif state == GAMEOVER:
        screen.blit(font.render(f"Game Over! Score: {score}", True, (255, 100, 100)), (200, 180))
        screen.blit(font.render(f"Best: {save['high_score']}  Press R to retry", True, (200, 200, 200)), (170, 240))

    pygame.display.flip()
    clock.tick(60)

pygame.quit()
```

**This is a complete closed loop**: menu to game, catch for points, miss to lose points, settle when time runs out, save high score, restart without losing the save.

## Crash Scene 1: Writing the Entire Game in One File

**Symptom**: `main.py` grows to 500 lines; finding the ball speed means scrolling forever, and adding features feels risky.

**Why**: No separation of concerns.

**Fix: one folder, four files.**

```
my_game/
├── main.py          # Main loop, events, state machine
├── sprites.py       # Paddle / Ball classes
├── save.py          # load_save / save_high
└── settings.py      # Constants: window size, colors, paths
```

**In `main.py`, write `from sprites import Paddle, Ball`** — the main file contains only the "flow", readable at a glance.

## Crash Scene 2: Loading Images and Reading Saves Every Frame

```python
while running:
    img = pygame.image.load("ball.png")       # Reading disk every frame!
```

**Symptom**: The game gets slower over time, the disk light flashes wildly.

**Why**: File I/O is slow, and creating Surfaces has overhead.

**Fix**: **load outside the loop, as a global constant.**

```python
BALL_IMG = pygame.image.load(os.path.join(base, "ball.png")).convert_alpha()
```

## Crash Scene 3: Magic Numbers Everywhere

```python
rect = img.get_rect(center=(300, 470))     # Where does 470 come from?
if rect.right < 600:
    ...
if ball.rect.top > 500:
    ...
```

**Symptom**: Wanting to change from 600x500 to 800x600 means editing 20 numbers, and missing one creates a bug.

**Fix**: **centralize constants.**

```python
WIDTH, HEIGHT = 600, 500
PADDLE_Y = HEIGHT - 30
if self.rect.right < WIDTH:
    ...
```

**Change `WIDTH` once and the whole program follows.**

## Crash Scene 4: Dumping Logic Directly in the Main Loop Instead of Using update

**Symptom**: 200 indented lines under `if state == PLAYING:`, and adding a new state means more nesting.

**Fix**: **extract each state's handling into a function** (`handle_menu` / `handle_playing` / `handle_gameover`); the main loop only handles scheduling.

## What to Learn Next

**《Python Window Basics 3》covers "complete desktop projects".** You now know pygame for mini-games, but real applications are **tool-style software**:

| What you already know | What to learn next |
|---|---|
| Event loops, state machines | More complete program architecture (MVC layering) |
| Hand-rolled collision, hand-drawn UI | Ready-made widgets: buttons, input boxes, tables, menu bars |
| One window, one canvas | Multi-window, dialogs, system tray |
| Calculating your own coordinate layout | Layout managers for automatic arrangement |
| pygame's fixed frame loop | Event-driven desktop program model |

**Qt or Tkinter?**

- **Tkinter**: comes with Python, zero installation, great for small tools. But it's plain-looking, has few widgets, and modern interfaces are hard to build.
- **Qt (PySide6/PyQt6)**: industrial-strength, cross-platform, rich widgets, capable of commercial software; requires a separate library install.

**《Window Basics 3》will guide you through building a complete desktop application with Qt**: designing the interface with a UI designer, connecting signals and slots to logic, using threads so the UI never freezes, packaging it as an exe/app, and ultimately delivering "software you can hand to someone else."

**If you want to keep building games**, the pygame basics from 《Window Basics 2》are enough to make most 2D mini-games. You can study on your own: particle systems, tilemaps, advanced state machines, and packaging with PyInstaller into an exe.

## Summary

- "Complete game" = menu + gameplay + results + save + sound + fault tolerance — all six make a closed loop
- Layered architecture: sprites in their own file, saving in its own file, main loop only handles flow
- Load resources outside the loop as constants; manage sizes with centralized constants, not scattered magic numbers
- Extract state handling into functions; main loop only schedules
- Next step: 《Window Basics 3》for Qt desktop projects, or self-study advanced pygame

q: To change a pygame mini-game from 600x500 to 800x600, which approach requires the fewest changes and is least likely to miss something?
options:
- Globally search and replace 600 and 500 one by one
- Define WIDTH and HEIGHT constants at the top of the file, reference them everywhere sizes are used, and only change those two lines
- Write window size in a comment and pass it as a runtime argument
- Use an external command like sed for batch replacement
answer: 1
explain: Centralizing size in constants means changing it in one place updates the whole program — a clean "change two lines" approach. Searching and replacing one by one is time-consuming and error-prone, especially since 600 might appear in color values, timers, audio parameters, and other semantically different places. Comments and sed can't guarantee consistency at the language level.
