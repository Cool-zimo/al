# Frame Rate and Delta Time: Why a Fixed Step Runs at Different Speeds

> In the previous lesson we animated by "moving 4 pixels per frame". But that hides a problem: on different machines and under different loads, the frame rate varies, so the animation speed changes too. This lesson introduces "delta time", which makes an animation run at the same speed on any machine.

## The Problem: Fixed-Step Animation Is Not Reliable

**Recall the bouncing ball from Lesson 7: move `dx=4` pixels per frame, one frame every 20 milliseconds.**

```
speed = 4 pixels/frame * 50 frames/second = 200 pixels/second
```

**That "200 pixels per second" is an ideal value calculated on paper.** In reality:

- On a fast computer, `after(20, ...)` really does fire every 20 ms → speed is close to 200
- On a busy computer (many programs running), the actual interval is 40 ms → speed is only 100
- On a slower computer with an even lower frame rate → the animation is slower still

**The same code runs at different speeds in different environments.** In a game this is fatal: Alice's ball reaches the goal in 2 seconds while Bob's takes 4.

## The Core Idea: Delta Time

**Delta time (abbreviated dt) is "how much time has passed since the previous frame".** Its unit is seconds (or milliseconds). Scale the movement amount by dt and "movement speed" becomes "pixels per second", independent of the frame rate.

```
movement this frame = speed * dt
```

**A large dt (long frame interval) means a large movement; a small dt (short interval) means a small movement. The average speed stays constant.**

## Measuring dt with time.time

**Python's standard library `time.time()` returns the current timestamp in seconds:**

```python
import time

t = time.time()
# do something
time.sleep(0.1)
print(time.time() - t)   # about 0.1
```

**Use it to calculate dt inside an animation:**

```python
import tkinter as tk
import time

root = tk.Tk()
canvas = tk.Canvas(root, width=400, height=200, bg="white")
canvas.pack()

ball = canvas.create_oval(10, 80, 40, 110, fill="tomato")
speed = 200          # 200 pixels per second
last_time = time.time()

def animate():
    global last_time
    now = time.time()
    dt = now - last_time      # seconds since the previous frame
    last_time = now

    canvas.move(ball, speed * dt, 0)

    # Boundary bounce
    x1, y1, x2, y2 = canvas.coords(ball)
    if x2 >= 400 or x1 <= 0:
        # Note: keep the ball inside the boundary
        pass

    root.after(16, animate)

animate()
root.mainloop()
```

**The key change:** `canvas.move(ball, speed * dt, 0)`. When dt is 0.02 seconds (20 ms per frame), the movement is `200 * 0.02 = 4` pixels — the same as before. If the frame rate drops to 40 ms, dt becomes 0.04 and the movement is 8 pixels — catching up in one step so the average speed stays the same.

## Crash Site One: A Huge dt on the First Frame

```
last_time = time.time()   # recorded when the program starts
animate()                 # first frame: now - last_time could be several seconds!
```

**Symptom:** on the first frame the ball "teleports" a long way, possibly leaving the canvas.

**Cause:** the time between `last_time = time.time()` and the first `animate()` call can be large (loading resources, creating the window). dt works out at several seconds, which multiplied by the speed sends the ball flying.

**Fix: resample last_time inside the first call to animate and treat dt as 0:**

```python
def animate():
    global last_time
    now = time.time()
    dt = now - last_time
    last_time = now
    if dt > 0.1:        # an abnormally large gap (stutter or first frame) -> treat as 0
        dt = 0
    canvas.move(ball, speed * dt, 0)
    root.after(16, animate)
```

**This is called "clamping dt"** — setting an upper limit so it never has to catch up by too much.

## Crash Site Two: Lost Precision in Coordinates (Integer Versus Float)

```
speed = 200
dt = 0.016          # 60 fps
move_x = speed * dt  # 3.2
canvas.move(ball, move_x, 0)
```

**When `move` receives a float, tkinter rounds it (it stores floats internally but displays rounded values).** Tiny sub-pixel movements are lost over time.

**Countermeasure:** maintain the ball's "precise floating-point position" yourself and use `coords` for absolute positioning instead of accumulating `move` calls:

```python
ball_x = 10.0      # precise position
ball_y = 80.0

def animate():
    global ball_x, ball_y, last_time
    now = time.time()
    dt = now - last_time
    last_time = now
    if dt > 0.1:
        dt = 0
    ball_x += speed * dt
    # Bounce
    if ball_x > 370:
        ball_x = 370
        speed = -abs(speed)
    if ball_x < 0:
        ball_x = 0
        speed = abs(speed)
    # Position it absolutely with coords
    canvas.coords(ball, ball_x, ball_y, ball_x+30, ball_y+30)
    root.after(16, animate)
```

**This is the standard game-development approach:** store the precise state yourself and "draw" it onto the canvas with `coords` each frame. `move` is only suitable for coarse, quick animations.

## Crash Site Three: Using time.sleep to Measure dt

```
time.sleep(0.5)
dt = time.time() - last_time   # it really is 0.5
```

**Although the calculated dt is correct, `sleep` freezes the interface** — you have defeated your own purpose. Inside a GUI, measure dt only by subtracting timestamps; **let `after` drive the pace.**

## "Constant Speed at the Target Frame Rate" Versus "Fixed Step"

**A comparison of the two main approaches:**

| Approach | Movement amount | Advantage | Disadvantage |
|---|---|---|---|
| Fixed step | Fixed 4px per frame | Simple | Speed changes with the frame rate |
| Delta time | speed * dt | Frame-rate independent and stable | Must track precise position and handle the first-frame jump |

**For small tkinter animations, a fixed step is usually enough.** As soon as you write a game and need "the same speed across devices", you must use dt. The `Clock.tick` in the pygame part (Lesson 20) is essentially doing dt plus rate limiting for you.

## Using dt for "Smooth Interpolation"

**dt can also produce "easing". For example, move a ball from x=10 to x=300 in 2 seconds at a constant speed:**

```python
start_x = 10
target_x = 300
duration = 2.0       # 2 seconds
elapsed = 0.0

def move():
    global elapsed
    dt = 1/60        # approximation
    elapsed += dt
    if elapsed > duration:
        elapsed = duration
    progress = elapsed / duration     # 0..1
    x = start_x + (target_x - start_x) * progress
    canvas.coords(ball, x, 80, x+30, 110)
    if elapsed < duration:
        root.after(16, move)
```

**`progress` is "how complete the motion is"**, and `start + (target-start)*progress` is the linear interpolation formula. This is the basis of transition animations and filling progress bars.

## Summary

- Fixed-step animation ties its speed to the frame rate, so it varies across devices
- **Delta time = current time minus the previous frame's time**, making the movement amount proportional to the frame interval
- Movement amount = speed * dt, with units of "pixels per second"
- Guard against the first-frame jump: if dt exceeds a threshold (such as 0.1), treat it as 0
- For precision, maintain floating-point coordinates yourself and use `coords` for absolute positioning
- A fixed step is enough for small tkinter animations, but games require dt
