# Frame Rate Control: Clock and tick, and Why You Shouldn't Run at Full CPU

> The game loops from earlier lessons "work", but is faster always better? This lesson covers `pygame.time.Clock` — locking your game's frame rate, saving CPU, and understanding the relationship between "frame rate" and "speed".

## The Problem: How Fast Does an Uncontrolled Game Run?

**Recall the previous loop:**

```python
while running:
    for event in pygame.event.get():
        ...
    player_x += speed
    screen.fill(BLACK)
    pygame.draw.rect(screen, RED, (player_x, 200, 50, 50))
    pygame.display.flip()
```

**This loop has no speed limit at all.** It spins as fast as the CPU allows: on a modern machine it might hit thousands of FPS.

**The consequences:**

1. **CPU usage hits 100%**: a "do-nothing" little window maxes out an entire core — your computer gets hot, fans spin wildly.
2. **Speed varies by machine**: Player A's fast computer (3000 FPS) moves the ball 3000×4 = 12000 pixels per second; Player B's slower machine (500 FPS) only moves 2000 pixels per second. **Same game, six times the speed difference.**

**This is the same root cause as the "fixed step" problem from Lesson 8 with tkinter** — when the frame rate isn't fixed, neither is the speed.

## Controlling Frame Rate with Clock

**`pygame.time.Clock()` creates a clock object; `clock.tick(target_FPS)` controls the frame rate:**

```python
import pygame

pygame.init()
screen = pygame.display.set_mode((800, 600))
clock = pygame.time.Clock()          # Create the clock

player_x = 375
speed = 4

running = True
while running:
    for event in pygame.event.get():
        if event.type == pygame.QUIT:
            running = False

    player_x += speed
    if player_x <= 0 or player_x >= 750:
        speed = -speed

    screen.fill((0, 0, 0))
    pygame.draw.rect(screen, (255, 0, 0), (player_x, 275, 50, 50))
    pygame.display.flip()

    clock.tick(60)                   # Lock to 60 FPS

pygame.quit()
```

**`clock.tick(60)` means: "this frame is done; if less than 1/60 of a second has passed, sleep until it has."** This keeps the loop stable at 60 FPS and drastically reduces CPU usage.

## tick's Return Value: Actual Frame Interval

**`tick()` returns the number of milliseconds since the last frame**, which you can use to calculate dt:

```python
clock = pygame.time.Clock()

while running:
    dt = clock.tick(60)              # dt is about 16.7 (milliseconds)
    # Use dt for frame-rate-independent movement
    player_x += speed * (dt / 1000) * 60   # Normalize to 60FPS baseline
```

**But in pygame, a more common approach is: fixed step size + tick for locking.** Since tick already guarantees a stable frame rate, speed stays consistent naturally. True "dt physics" is only needed in more complex games.

## Crash Scene 1: Forgetting to Call tick, CPU Maxes Out

```
while running:
    ...
    pygame.display.flip()
    # clock.tick(60)  forgot to call
```

**Symptom**: The window runs, but CPU usage is 100% and the computer overheats.

**Why**: Without tick there's no sleeping at all — the loop spins at maximum speed. This is the most common performance bug among pygame beginners.

**Fix**: Add `clock.tick(target_frame_rate)` at the end of the loop.

## Crash Scene 2: Passing 0 or a Negative Number to tick

```
clock.tick(0)     # No limit, same as not calling
clock.tick(-1)    # Error
```

**`tick(0)` means "no limit", so it's pointless. Only positive numbers make sense.**

## Crash Scene 3: Putting tick at the Start of the Loop

```
while running:
    clock.tick(60)          # At the start
    for event in pygame.event.get():
        ...
    pygame.display.flip()
```

**Technically it runs, but it's not standard.** The conventional place is **at the end of the loop** (after rendering). Logically, "tick closes out this frame" is clearer, and it avoids a first-frame delay.

**More fundamentally**: putting it at the start means **event handling and rendering get "stuck" around tick's sleep**, hurting responsiveness. Putting it at the end lets "handle + render" flow smoothly, then sleep.

## Crash Scene 4: Thinking tick Can Make a Slow Machine Faster

**`tick(60)` only guarantees "no more than 60", not "reaches 60".** If one frame's logic is too heavy (lots of computation, file loading), the actual frame rate falls below 60 and tick can't help.

**Countermeasures**: optimize heavy logic, use `pygame.time.get_ticks()` for frame-splitting, or move expensive tasks to a thread.

## Choosing a Target Frame Rate

**Common choices:**

| Frame Rate | Best For |
|---|---|
| 60 FPS | Mainstream, smooth (tick = 16.7ms) |
| 30 FPS | Simple games, mobile power saving |
| 120 FPS | High-refresh displays, requires monitor support |

**`clock.tick(60)` is the standard for pygame projects** — almost every tutorial writes it this way.

## Displaying Actual FPS with get_fps

**`clock.get_fps()` returns the smoothed actual frame rate (as a float):**

```python
font = pygame.font.SysFont(None, 24)
fps_text = font.render(f"{clock.get_fps():.0f} FPS", True, (255, 255, 255))
screen.blit(fps_text, (10, 10))
```

**Showing FPS while debugging is good practice** — it makes stuttering immediately visible. We'll cover font rendering in Lesson 26.

## Locked Frame Rate vs. Frame-Rate Independence

**Two approaches:**

| Approach | Method | Best For |
|---|---|---|
| Lock frames + fixed step | `tick(60)` + fixed displacement per frame | pygame mini-games, simple and reliable |
| Unlocked + dt | Calculate dt each frame, displacement = speed × dt | Precise physics, cross-platform consistency |

**pygame's official examples and most mini-games use the first approach**: `tick(60)` already makes the frame rate stable enough that speed stays consistent — simple and worry-free. Master tick-based control in this lesson; the dt approach was covered in tkinter Lesson 8, and the principle is the same.

## Summary

- No frame control → CPU maxes out, speed varies by machine
- `clock = pygame.time.Clock()` + `clock.tick(60)` locks to 60 FPS
- tick makes the loop sleep between frames, drastically reducing CPU usage
- tick goes at the **end** of the loop (after rendering)
- tick(0) means no limit; tick can only cap speed, not accelerate it
- 60 FPS is the mainstream pygame choice
- Simple games work fine with "lock frames + fixed step"
