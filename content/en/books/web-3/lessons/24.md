# Canvas Animation: requestAnimationFrame and the Animation Loop

> This lesson covers how to make a Canvas move, and why `requestAnimationFrame` beats `setInterval` for animation.

## What animation really is: erase and redraw

Animation is simply **clearing and redrawing the frame on every tick, with each tick drawn slightly differently**. The core three steps: update state → clear the screen → redraw.

```js
const canvas = document.querySelector('#board');
const ctx = canvas.getContext('2d');
let x = 0;

function draw() {
  ctx.clearRect(0, 0, canvas.width, canvas.height); // 1. clear
  ctx.fillStyle = 'rgb(33, 150, 243)';
  ctx.fillRect(x, 80, 30, 30);                      // 2. draw at current state
  x += 3;                                           // 3. update state
  requestAnimationFrame(draw);                       // 4. draw the next frame in ~16.7ms
}
draw();
```

Each frame x grows by 3, so the square creeps right. At 60 times per second, your eye sees smooth motion.

## What requestAnimationFrame is

`requestAnimationFrame(fn)` tells the browser: **call `fn` once, just before the next repaint**. The browser matches the refresh rate automatically (usually 60 times per second, about 16.7ms per frame).

```js
function step() {
  // do this frame's work
  requestAnimationFrame(step);   // schedule the next frame at the end
}
requestAnimationFrame(step);     // kick off
```

It **schedules only one frame**, so for a continuous animation you must call `requestAnimationFrame` again inside the callback.

## Comparing setInterval: four advantages

| Dimension | requestAnimationFrame | setInterval |
|---|---|---|
| Timing | Synced to screen refresh | Fixed time slice, may drift from refresh |
| Background tabs | Pauses automatically, saves power | Keeps running, wastes CPU |
| Dropped frames | Can sense it within one callback | Callbacks queue up |
| Time precision | Callback gets a high-precision timestamp | Depends on the system timer |

```js
// ❌ setInterval: drifts from refresh rate, keeps running in the background
setInterval(() => {
  x += 3;
  draw();      // might draw twice in one frame, or skip a frame
}, 16);

// ✅ rAF: synced to refresh, pauses when the tab is hidden
function loop() {
  x += 3;
  draw();
  requestAnimationFrame(loop);
}
requestAnimationFrame(loop);
```

**Crash Site 1:** assuming requestAnimationFrame loops "automatically" like setInterval.

```js
// ❌ Only one frame, then it stops
requestAnimationFrame(draw);   // stops after draw runs once

// ✅ Re-schedule from inside the callback
function draw() {
  // ...
  requestAnimationFrame(draw);
}
requestAnimationFrame(draw);
```

**Why it crashes:** rAF is a **single-shot schedule**, not a timer. Forgetting to call it again inside the callback means the animation runs for exactly one frame. This is the classic beginner trap.

## Time-based motion with the timestamp

The rAF callback receives a `timestamp` argument (in milliseconds). Using it for motion is more robust than "add 3 every frame" — even if a frame is dropped, the object still lands in the right place.

```js
let start = null;
function step(ts) {
  if (start === null) start = ts;
  const elapsed = ts - start;     // how many ms have passed
  const x = elapsed * 0.2;        // speed: 0.2 px/ms
  ctx.clearRect(0, 0, canvas.width, canvas.height);
  ctx.fillRect(x, 80, 30, 30);
  if (elapsed < 5000) requestAnimationFrame(step);  // stop after 5s
}
requestAnimationFrame(step);
```

## Stopping animation: cancelAnimationFrame

`requestAnimationFrame` returns an id; pass it to `cancelAnimationFrame(id)` to cancel the pending schedule.

```js
let rafId = null;
function loop() {
  x += 3;
  draw();
  rafId = requestAnimationFrame(loop);
}
rafId = requestAnimationFrame(loop);

// stop when a condition is met
function stop() {
  cancelAnimationFrame(rafId);
}
```

**Crash Site 2:** forgetting to clear the canvas after stopping, so the frame freezes mid-animation.

```js
// ❌ After cancelling, the frame is frozen, the object "stuck" mid-air
cancelAnimationFrame(rafId);

// ✅ Clear manually if you want it gone, or redraw once at the initial state
cancelAnimationFrame(rafId);
ctx.clearRect(0, 0, canvas.width, canvas.height);   // wipe it clean
```

**Why it crashes:** `cancelAnimationFrame` only prevents the **next** callback; it doesn't touch the canvas. The canvas still shows the last frame. To clear it you must call `clearRect` yourself.

## Recap

- Animation = clear → redraw → update state → schedule the next frame.
- `requestAnimationFrame(fn)` schedules one frame, syncs to refresh rate, and pauses in hidden tabs.
- It is **not** a timer — a continuous animation must re-call it inside the callback.
- Use the callback's `timestamp` for time-based motion; it stays accurate even if frames drop.
- Stop with `cancelAnimationFrame(id)`, and decide for yourself whether to clear the canvas.
