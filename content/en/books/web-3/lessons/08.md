# fetch Does Not Reject on HTTP 404/500

> This is the classic `fetch` pitfall: **network-level success ≠ business-level success**. You must manually check `res.ok`.

## The nature of the pitfall

`fetch` only rejects when there is a **true network-level failure** (no network, DNS resolution failed, request blocked). As long as the server **returns an HTTP response** (even 404 or 500), the Promise returned by `fetch` will be **fulfilled (resolved)**.

```js
// Suppose we request a non-existent endpoint and the server returns 404
fetch('/api/not-exist')
  .then(res => {
    console.log(res.status);  // 404
    console.log(res.ok);      // false
    // ⚠️ The Promise is successful here — it goes into then, not catch!
    return res.json();
  })
  .then(data => {
    // The 404 page content might not be valid JSON
    console.log(data);  // might throw or produce unexpected data
  })
  .catch(error => {
    console.error('This block actually never runs');  // 404 won't trigger it
  });
```

### Crash Site 1: assuming 404/500 automatically goes to catch, so error handling never takes effect

```js
// ❌ Wrong approach
async function getUser() {
  const res = await fetch('/api/user/999');  // user doesn't exist, returns 404
  const data = await res.json();   // continues anyway
  return data;   // returns the 404 page content, not user info
}

const user = await getUser();
console.log(user.name);  // possibly TypeError
```

**Why it crashes:** On 404, `fetch` **does not reject** — the code keeps running. If the 404 response body isn't valid JSON, `res.json()` will throw an exception; if it's an HTML error page, `data` will be a string. In both cases, the caller gets unexpected data.

## The solution: manually check res.ok

The correct approach is to **check the response status on every request**:

```js
async function getUser(id) {
  const res = await fetch(`/api/user/${id}`);
  if (!res.ok) {
    // manually throw an error so the flow enters catch
    throw new Error(`Request failed: ${res.status} ${res.statusText}`);
  }
  return res.json();
}

// Usage
try {
  const user = await getUser(999);
  console.log(user);
} catch (error) {
  console.error(error.message);  // Request failed: 404 Not Found
}
```

`res.ok` is a convenience property that is `true` when `res.status` is in the **200–299** range — more convenient than manually checking `status === 200`.

## Wrapping a safe request function

Extract the "check status" logic so business code doesn't have to repeat it:

```js
async function safeFetch(url, options = {}) {
  const res = await fetch(url, options);
  if (!res.ok) {
    throw new Error(`HTTP ${res.status}: ${res.statusText}`);
  }
  // decide how to read based on Content-Type
  const contentType = res.headers.get('content-type') || '';
  if (contentType.includes('application/json')) {
    return res.json();
  }
  return res.text();
}

// Usage
try {
  const data = await safeFetch('/api/user/1');
} catch (error) {
  console.error(error);  // both network errors and HTTP errors end up here
}
```

This way, **both network errors and HTTP errors follow the same `catch` path**, so business code doesn't need to distinguish between them.

### Crash Site 2: only checking status in `then`, forgetting that 500 might also return a JSON error

```js
// ❌ Only looks at the status code, doesn't handle the error body format
async function load() {
  const res = await fetch('/api/data');
  if (res.status === 200) {
    return res.json();
  }
  // 404/500 ends up here, but the error body might be { message: '...' } JSON
  throw new Error('Something went wrong');
}

// ✅ Try to read the error body
async function load() {
  const res = await fetch('/api/data');
  if (!res.ok) {
    let msg = res.statusText;
    try {
      const errBody = await res.json();
      msg = errBody.message || msg;  // prefer the server's error message
    } catch (e) {
      // error body isn't JSON, ignore
    }
    throw new Error(msg);
  }
  return res.json();
}
```

**Why it crashes:** Many backends return structured error info like `{ message: 'User not found' }` in the response body for 4xx/5xx. If you only throw a generic "something went wrong," you lose the specific reason provided by the server, making it hard to show a useful message to the user.

## When does fetch actually reject?

| Scenario | Does fetch reject? |
|---|---|
| No network / server unreachable | ✅ rejects (TypeError) |
| CORS blocked by the browser | ✅ rejects (TypeError) |
| HTTP 404 | ❌ resolves, res.ok = false |
| HTTP 500 | ❌ resolves, res.ok = false |
| HTTP 200 | ❌ resolves, res.ok = true |

## Comparison with Python

Python's `requests` also **does not throw an exception by default** — you must check manually:

```python
# Python requests: also requires manual checking
r = requests.get('/api/user/999')
r.raise_for_status()  # actively throw; similar to manually checking res.ok
data = r.json()
```

JS and Python are consistent on this point — both separate "HTTP status code" from "whether to throw an exception," requiring the developer to check explicitly.

## Recap

- `fetch` **only rejects on network-level failures**; 404/500 both resolve normally.
- You must **manually check `res.ok` or `res.status`**, otherwise errors are silently ignored.
- Recommended: wrap a `safeFetch` that checks status + reads the response body based on Content-Type.
- The error body might also be JSON; try to read the `message` to give a more specific提示.
- Network errors and CORS blocks are the scenarios where fetch actually rejects.
