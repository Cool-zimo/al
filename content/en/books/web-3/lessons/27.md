# Structure and Styling: the HTML Skeleton and CSS Layout

> This lesson turns last chapter's sketch into real HTML and CSS, with an emphasis on semantic structure and state switching.

## The skeleton: semantic markup plus state hooks

```html
<main class="app">
  <header class="app__header">
    <h1>Weather &amp; Exchange Rates</h1>
  </header>

  <section class="card">
    <label class="field">
      <span class="field__label">City</span>
      <input id="cityInput" type="text" placeholder="Enter a city, e.g. Paris" />
      <button id="searchBtn" type="button">Search</button>
    </label>
  </section>

  <section id="status" class="status" hidden></section>

  <section id="weather" class="card weather" hidden>
    <h2 id="wCity"></h2>
    <p class="weather__temp"><span id="wTemp"></span> °C</p>
    <p id="wCondition"></p>
    <p>Humidity: <span id="wHumidity"></span>%</p>
    <p>Wind: <span id="wWind"></span> m/s</p>
  </section>

  <section class="card">
    <label class="field">
      <span class="field__label">Currency</span>
      <select id="baseSel"><option>USD</option><option>GBP</option></select>
      <span>→</span>
      <select id="targetSel"><option>GBP</option><option>USD</option></select>
      <button id="rateBtn" type="button">Convert</button>
    </label>
    <p id="rateResult"></p>
  </section>
</main>
```

Every data field gets its own `span`, so JS can fill values precisely. The `hidden` attribute controls visibility — cleaner than a `display:none` class.

## The status area: switch with a data attribute

The four states (empty/loading/error/success) are controlled by one container with a `data-state` attribute:

```html
<section id="status" class="status" data-state="idle">
  <p class="status__loading" data-show="loading">⏳ Loading...</p>
  <p class="status__error" data-show="error"></p>
</section>
```

```css
.status [data-show] { display: none; }
.status[data-state="loading"] [data-show="loading"] { display: block; }
.status[data-state="error"]   [data-show="error"]   { display: block; }
```

JS only changes `data-state`; CSS decides what to show. State logic and styling are completely separated.

**Crash Site 1:** stuffing user input straight into the page with `innerHTML`.

```js
// ❌ If the user types <script>, it runs
status.innerHTML = 'Search for ' + city + ' failed';   // XSS risk

// ✅ Use textContent, so it's treated as text only
status.textContent = 'Search for ' + city + ' failed';
```

**Why it crashes:** `innerHTML` parses HTML tags. If user input contains `<script>` or `<img onerror>`, you've got an XSS hole. For anything the user or an API provides, always use `textContent`.

## Layout: flex makes the form row

```css
.app {
  max-width: 640px;
  margin: 0 auto;
  padding: 24px 16px;
  font-family: -apple-system, "Segoe UI", "PingFang SC", "Microsoft YaHei", sans-serif;
}

.card {
  background: #fff;
  border-radius: 12px;
  padding: 20px;
  margin-bottom: 16px;
  box-shadow: 0 2px 8px rgba(0, 0, 0, 0.06);
}

.field {
  display: flex;
  align-items: center;
  gap: 12px;
  flex-wrap: wrap;
}

.field input,
.field select {
  flex: 1 1 160px;
  min-width: 0;
  padding: 8px 12px;
  border: 1px solid #ccc;
  border-radius: 8px;
  font-size: 16px;
}

button {
  padding: 8px 18px;
  border: none;
  border-radius: 8px;
  background: rgb(33, 150, 243);
  color: #fff;
  cursor: pointer;
}

.weather__temp {
  font-size: 48px;
  font-weight: 700;
  color: rgb(33, 150, 243);
}
```

`flex: 1 1 160px` lets the input fill the row on wide screens and wrap onto a new line on narrow ones. `min-width: 0` is the key detail — without it, flex children can blow out the container.

## Responsive: one media query to finish

```css
@media (max-width: 480px) {
  .app { padding: 16px 12px; }
  .field { gap: 8px; }
  .weather__temp { font-size: 36px; }
}
```

On phones you just tighten the spacing and font sizes; the layout structure stays put — that's the benefit of flex.

**Crash Site 2:** an input's padding makes the element wider than expected, blowing out the layout.

```css
/* ❌ width fixed at 100%, plus padding pushes it past the parent */
input { width: 100%; padding: 8px 12px; }   /* actual width = 100% + 24px */

/* ✅ Unify with box-sizing */
*, *::before, *::after { box-sizing: border-box; }
```

**Why it crashes:** by default `box-sizing: content-box` adds padding and border outside the width, producing a horizontal scrollbar. `border-box` makes width include padding and border, so layouts behave predictably.

## Recap

- Give every data field its own `span` for precise JS filling; use `hidden` for visibility.
- To switch states, only change `data-state`; let CSS's `[data-show]` rules decide what's visible.
- Always use `textContent` for user input — never concatenate with `innerHTML`.
- A flex layout of `flex: 1 1 160px` plus `min-width: 0` handles both wide and narrow screens.
- Set `box-sizing: border-box` globally to stop padding from blowing out widths.
