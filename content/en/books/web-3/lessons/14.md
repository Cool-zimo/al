# IndexedDB: When to Use It and When Not To

> This lesson gives you a "storage selection map" so you can understand the boundary between IndexedDB and localStorage.

## What is IndexedDB

IndexedDB is the browser's **large-scale, structured, transactional** local database. Compared to localStorage, it differs by orders of magnitude across several dimensions:

| Dimension | localStorage | IndexedDB |
|---|---|---|
| Capacity | ~5MB | **Hundreds of MB or more** |
| Data types | Strings only | **Any JS value** (objects, binary, Blobs) |
| Read/write | Synchronous (blocks main thread) | **Asynchronous** (non-blocking) |
| Querying | Key-only full scan | **Supports indexes, range queries** |
| Transactions | None | Yes (ACID) |

## The simplest usage: storing one piece of data

IndexedDB's API is quite verbose; here we only demonstrate the core flow:

```js
// open (or create) the database
const request = indexedDB.open('my-app', 1);

request.onupgradeneeded = (event) => {
  const db = event.target.result;
  // create an "object store," similar to a table
  if (!db.objectStoreNames.contains('users')) {
    db.createObjectStore('users', { keyPath: 'id' });
  }
};

request.onsuccess = (event) => {
  const db = event.target.result;
  console.log('Database opened successfully');
  // all subsequent CRUD operations are based on db
};
```

Because the native API is so verbose, real projects typically use wrapper libraries (like `idb` or `Dexie.js`).

## Using the idb library: async/await style

```js
import { openDB } from 'idb';

const db = await openDB('my-app', 1, {
  upgrade(db) {
    db.createObjectStore('users', { keyPath: 'id' });
  }
});

// create
await db.add('users', { id: 1, name: 'Alice' });

// read
const user = await db.get('users', 1);

// update
await db.put('users', { id: 1, name: 'Bob' });

// delete
await db.delete('users', 1);

// iterate
const all = await db.getAll('users');
```

## When to use IndexedDB

**Good use cases:**

- Storing **large amounts of data** (far beyond 5MB): offline documents, chat history, music/video metadata
- Needing to **query by field or range**: e.g., "get records where score > 90"
- Needing to store **binary data**: images, file Blobs
- Needing **transactional guarantees**: a batch of operations either all succeed or all fail

```js
// Example: an offline messaging app storing thousands of messages with range queries by time
const messages = await db.getAllFromIndex('messages', 'by-time',
  IDBKeyRange.bound(lastSync, Date.now()));
```

### Crash Site 1: using IndexedDB just to store a username — overkill

```js
// ❌ Over-engineered: storing a single string requires opening a DB, creating a table, using transactions
const db = await openDB('app', 1, { upgrade(db) { db.createObjectStore('kv'); } });
await db.put('kv', 'Alice', 'name');
const name = await db.get('kv', 'name');

// ✅ For this case, localStorage handles it in one line
localStorage.setItem('name', 'Alice');
const name = localStorage.getItem('name');
```

**Why it crashes:** The **async API + database/table creation + version upgrades** that IndexedDB requires add far more complexity than localStorage. Using it to store a few strings doubles your code volume and increases the chance of bugs — for almost zero benefit.

## When you don't need it

**Stick with localStorage for these scenarios:**

- Small amounts of data (a few config items, a token, user preferences)
- Only key-value access needed, no querying
- You want to keep the code simple, with no third-party dependencies

**Don't store locally at all in these scenarios:**

- Sensitive information (passwords, bank cards): belongs on the server
- Data that needs to sync across devices: local storage can't跨 devices

### Crash Site 2: storing a token in IndexedDB long-term, thinking it's "more secure than localStorage"

```js
// ❌ Misconception: IndexedDB isn't any more secure than localStorage
await db.put('auth', { token: 'sk-xxx', password: '123456' });

// ✅ Both run on the client and are readable; store sensitive info on the server,
//    and only hold a short-lived token in the frontend
```

**Why it crashes:** IndexedDB and localStorage both live on the client and have the **same security level**. Any attacker who can execute JS can read both. Neither should hold truly sensitive information long-term, and tokens should have short expiration times.

## Selection summary

| Need | Choice |
|---|---|
| A few config items / a token | localStorage |
| Under 5MB, simple structure | localStorage |
| Large amounts of data, querying/indexing needed | IndexedDB |
| Binary / Blobs | IndexedDB |
| Offline app, data sync | IndexedDB |

## Comparison with Python

Python local persistence commonly uses `sqlite3` (relational, structured queries) or `pickle` (serialization). IndexedDB is closer in positioning to SQLite, but it's a NoSQL key-value/object store.

```python
# Python sqlite3: structured, supports SQL queries
import sqlite3
conn = sqlite3.connect('app.db')
conn.execute('CREATE TABLE IF NOT EXISTS users (id INT, name TEXT)')
```

```js
// JS IndexedDB: object store + index queries, async API
const db = await openDB('app', 1);
await db.add('users', { id: 1, name: 'Alice' });
```

## Recap

- IndexedDB is a large-scale, asynchronous, indexable local database with far greater capacity than localStorage.
- The **native API is verbose**; in practice, use wrapper libraries like `idb` / `Dexie.js`.
- For storing a few strings or config items, localStorage is sufficient — don't over-engineer.
- Large data, querying needs, binary data → IndexedDB.
- IndexedDB and localStorage have the **same security level**; neither should store sensitive information long-term.
