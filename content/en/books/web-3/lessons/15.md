# Data Sync: Local Cache + Network Updates, and Optimistic Updates

> This lesson covers common patterns in real applications: displaying the cache first then updating from the network, and "pretending it succeeded" with optimistic updates.

## Pattern 1: Cache First

**Flow:** read the local cache and display it immediately, then fire off a network request, and once you have fresh data, update the UI.

```js
async function loadProfile() {
  // Step 1: show the cache first (fast)
  const cached = localStorage.getItem('profile');
  if (cached) {
    renderProfile(JSON.parse(cached));
  } else {
    showLoading();
  }

  // Step 2: request from the network (slow)
  try {
    const res = await fetch('/api/profile');
    if (!res.ok) throw new Error('Network error');
    const fresh = await res.json();

    // Step 3: update cache + update UI
    localStorage.setItem('profile', JSON.stringify(fresh));
    renderProfile(fresh);
  } catch (error) {
    if (!cached) showError(error.message);
    // when there's a cache, fail silently — the user at least sees old data
  }
}
```

The user experience is: **see content instantly**, with no white screen even if the network is slow.

### Crash Site 1: on network failure, clearing the old cache leaves the user staring at a blank page

```js
// ❌ Clearing the cache on failure too
async function load() {
  const cached = getCache();
  render(cached);
  try {
    const fresh = await fetchData();
    saveCache(fresh);
  } catch (e) {
    clearCache();   // wrong! the network is down but you just deleted the usable old data
    render(null);
  }
}

// ✅ On failure, only update the UI提示; keep the cache
async function load() {
  const cached = getCache();
  render(cached);
  try {
    const fresh = await fetchData();
    saveCache(fresh);
    render(fresh);
  } catch (e) {
    showToast('Network error; showing cached data');  // keep the cache, just提示
  }
}
```

**Why it crashes:** On network failure, deleting the still-usable old cache means **you've also destroyed your fallback plan**. The user could have seen the last known data, but now sees a blank page. The whole point of having a cache is to fall back on it when the network is unavailable — deleting it defeats that purpose.

## Pattern 2: Optimistic Updates

**Flow:** user action → **immediately update the UI** (pretend it succeeded) → send the request → keep it on success, roll back on failure.

```js
async function toggleLike(postId) {
  // 1. immediately update the UI
  const post = getPost(postId);
  post.liked = !post.liked;
  post.likes += post.liked ? 1 : -1;
  render(post);

  // 2. then send the request
  try {
    await fetch(`/api/posts/${postId}/like`, { method: 'POST' });
    // success — do nothing
  } catch (error) {
    // 3. failure: roll back
    post.liked = !post.liked;
    post.likes += post.liked ? 1 : -1;
    render(post);
    showToast('Like failed, undone');
  }
}
```

The user **feels like the action took effect instantly**, with no lag even on a slow network.

### Crash Site 2: after an optimistic update, the request fails, but you forgot to save the "original state," so you can't roll back

```js
// ❌ No original value saved; incorrect rollback
async function updateName(newName) {
  const oldName = user.name;
  user.name = newName;     // modified directly
  render(user);
  try {
    await saveName(newName);
  } catch (e) {
    user.name = oldName;   // works for this simple case
    render(user);
  }
}

// ❌ Complex objects are a problem: multiple fields changed, easy to miss one during rollback
async function updateProfile(changes) {
  const oldProfile = profile;   // just a reference copy!
  Object.assign(profile, changes);  // the original object is already modified, oldProfile too
  render(profile);
  try {
    await saveProfile(profile);
  } catch (e) {
    profile = oldProfile;  // oldProfile was modified too — rollback is无效
  }
}

// ✅ Deep-clone a snapshot before rolling back
async function updateProfile(changes) {
  const snapshot = structuredClone(profile);  // save the original snapshot
  Object.assign(profile, changes);
  render(profile);
  try {
    await saveProfile(profile);
  } catch (e) {
    profile = snapshot;  // use the snapshot for a full rollback
    render(profile);
    showToast('Save failed');
  }
}
```

**Why it crashes:** If you only save a reference without deep-cloning, the snapshot and the original object point to the same block of memory. When you roll back, the snapshot has already been modified too — meaning **you have no backup**. Before doing an optimistic update on a complex object, always `structuredClone` a snapshot.

## Comparing the two patterns

| Pattern | Core idea | Best for |
|---|---|---|
| Cache First | Show the old data first, then quietly refresh | Content display, lists, profile |
| Optimistic Update | Pretend it succeeded first, roll back on failure | Likes, toggles, inline editing |

## Comparison with Python

This "local-first + background sync" pattern is especially common in the frontend (particularly PWAs / offline apps). Python backends are more often "request-response" direct模式. Because JS is single-threaded + asynchronous, it's naturally suited to this "respond first, sync later" style of UX optimization.

## Recap

- **Cache First:** show the cache first → request from the network → update cache and UI; on network failure, keep the cache as a fallback.
- On network failure, **don't clear** the still-usable old cache.
- **Optimistic Update:** update the UI first → send the request → keep on success / roll back on failure.
- Before an optimistic update, use `structuredClone` to save a **snapshot** — a reference copy won't work for rollback.
- Both patterns exist to optimize the user experience (instant feedback vs. no white screen).
