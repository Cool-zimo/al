# Why We Need Asynchronous Code: JS Single Thread and the Event Loop

> This lesson answers the question "why does `alert` freeze the entire page?" and explains why time-consuming operations must be asynchronous.

## JavaScript is single-threaded

"Single-threaded" means **the JS engine can only execute one instruction at a time**. In the browser, rendering, event handling, and JS execution share the main thread (more precisely, rendering is paused while JS executes).

```js
// Imagine this is a synchronous computation that takes 3 seconds
function heavyTask() {
  let sum = 0;
  for (let i = 0; i < 3_000_000_000; i++) {
    sum += i;
  }
  return sum;
}
heavyTask();
console.log('Done calculating');
```

During those 3 seconds while `heavyTask()` runs, the page is **completely frozen**: buttons don't respond, animations stop, and text input is ignored. The main thread is occupied by this loop, and everything else has to wait in line.

### Crash Site 1: using a loop to "wait one second" before executing

```js
// ❌ Common mistake: using a loop to simulate sleep
function sleepSync(ms) {
  const start = Date.now();
  while (Date.now() - start < ms) {
    // spinning — does nothing, just never yields the main thread
  }
}

console.log('Start');
sleepSync(2000);      // page freezes for 2 seconds
console.log('End');    // only outputs after 2 seconds
```

**Why it crashes:** `sleepSync` appears to "wait 2 seconds," but it actually makes the CPU spin for 2 seconds. During that time, the entire page is unresponsive. The user sees a white screen or a frozen page. In JS, you must never simulate waiting this way — always use asynchronous mechanisms (timers, Promises, async/await).

## Asynchrony: delegating expensive tasks to others

Operations like file reading, network requests, and timers aren't performed by JS itself. Instead, JS **delegates them to browser-provided underlying capabilities** (Web APIs), continues executing the code that follows, and then runs the registered callback when the operation completes.

```js
console.log('1');
setTimeout(() => {
  console.log('2');  // this function is a callback, executed later
}, 0);
console.log('3');
// Output order: 1 → 3 → 2
```

Setting the delay to `0` doesn't mean "execute immediately" — it means "put the callback into the task queue as soon as possible." The current synchronous code must finish first.

## The event loop: how callbacks queue up and execute

The event loop's job can be summarized in one sentence: **when the main thread is idle, it takes a callback from the task queue and executes it.**

```
┌──────────────────────────────────────┐
│  JS main thread (call stack)          │
│    ↓ when stack is empty              │
│  Event loop: take a callback → push   │
│  onto stack and execute               │
│    ↓                                  │
│  Task queue: holds callbacks ready    │
│  to run                              │
└──────────────────────────────────────┘
```

There are actually two kinds of queues in the browser: **macrotasks** (such as `setTimeout`, `setInterval`, I/O) and **microtasks** (such as Promise `.then`). Microtasks have higher priority — **after each macrotask completes, the engine first drains the entire microtask queue before picking up the next macrotask.**

```js
console.log('A');

setTimeout(() => console.log('B'), 0);       // macrotask

Promise.resolve().then(() => console.log('C')); // microtask

console.log('D');
// Output order: A → D → C → B
```

### Crash Site 2: expecting `setTimeout(..., 0)` to control order precisely, only to be interrupted by a microtask

```js
// ❌ Naive code
setTimeout(() => console.log('macrotask1'), 0);
Promise.resolve().then(() => console.log('microtask1'));
setTimeout(() => console.log('macrotask2'), 0);
// Actual output: microtask1 → macrotask1 → macrotask2
// The microtask runs before all queued macrotasks
```

**Why it crashes:** If your code relies on a rhythm of "macrotasks alternating," and someone slips a microtask in between (such as a Promise `.then`), the execution order will be unexpected. Never assume that a `setTimeout(0)` callback is "the very next thing that runs."

## Why network requests must be asynchronous

Network requests (to a server) can take anywhere from tens to hundreds of milliseconds, or even longer. If you made a synchronous request:

```js
// ❌ Synchronous request (deprecated API, shown only for illustration)
const data = fetchSync('/api/data');  // if this existed, the page would freeze
render(data);
```

This line would freeze the page for several seconds. Asynchronous code lets JS keep handling user interactions while waiting for the response:

```js
// ✅ Asynchronous style (illustrative; lesson 6 covers fetch in detail)
fetch('/api/data')
  .then(response => response.json())
  .then(data => render(data));
console.log('I will keep going; I will render once the response arrives');
```

## Comparison with Python

Python is single-threaded and sequential by default, but there is a key difference: **Python's `time.sleep(1)` truly puts the current thread to sleep for 1 second, during which the thread does nothing.** In contrast, JS's `setTimeout` hands the callback to the event loop and the main thread immediately becomes free to do other work.

```python
# Python: synchronous wait, the thread is occupied
import time
time.sleep(2)
print("After 2 seconds")
```

```js
// JS: registers a callback and continues immediately
setTimeout(() => console.log('After 2 seconds'), 2000);
console.log('I do not wait; I output right now');
```

JS's asynchrony is "non-blocking": during the waiting period, the main thread isn't idle — it processes other tasks.

## Recap

- JS is single-threaded; long synchronous operations freeze the page.
- Asynchronous operations (timers, network, events) are delegated to the browser, which notifies results via callbacks.
- The event loop picks up callbacks from the queue **when the main thread is idle**.
- **Microtasks have higher priority than macrotasks**: after each macrotask, the microtask queue is fully drained.
- To "wait a moment," use asynchronous code — never simulate sleep with a spinning loop.
