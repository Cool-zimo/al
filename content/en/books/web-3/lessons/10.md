## Practice: a word lookup app

```html
<input id="word" placeholder="Enter an English word, e.g. hello">
<button id="search">Search</button>
<div id="loading" style="display:none;">Loading...</div>
<div id="error" style="display:none;"></div>
<div id="result"></div>
```

```js
async function searchWord() {
  const word = document.querySelector('#word').value.trim();
  const resultEl = document.querySelector('#result');
  const loadingEl = document.querySelector('#loading');
  const errorEl = document.querySelector('#error');

  resultEl.textContent = '';
  errorEl.style.display = 'none';
  loadingEl.style.display = 'block';

  try {
    const res = await fetch(`https://api.dictionaryapi.dev/api/v2/entries/en/${word}`);
    if (!res.ok) throw new Error(`No definition found: ${word}`);
    const data = await res.json();

    const meanings = data[0].meanings
      .map(m => `<li>${m.partOfSpeech}: ${m.definitions[0].definition}</li>`)
      .join('');
    resultEl.innerHTML = `<h3>${data[0].word}</h3><ul>${meanings}</ul>`;
  } catch (error) {
    errorEl.textContent = error.message;
    errorEl.style.display = 'block';
  } finally {
    loadingEl.style.display = 'none';
  }
}

document.querySelector('#search').addEventListener('click', searchWord);
```

Notice that this app **runs by simply opening it in the browser**, because the API it calls has CORS configured on the server.

## CORS: Cross-Origin Resource Sharing

**CORS issues only exist in the browser.** When you use JS to request a different domain from the one your page is on, the browser checks whether the response headers declare that the current origin is allowed.

```
Your page: https://myapp.com
The API:   https://api.other.com/data
```

The browser first asks the server: "Can `myapp.com` access you?" — by looking at the response header:

```
Access-Control-Allow-Origin: https://myapp.com
```

If this header allows your origin, the browser hands the response to your JS; otherwise it **blocks** it and logs a CORS error in the console.

### Crash Site 1: requesting an API that hasn't configured CORS directly in the browser, getting a "cross-origin error"

```js
// ❌ Requesting an API without CORS configuration in the browser
fetch('https://another-domain.com/api/data')
  .then(res => res.json())
  .then(data => console.log(data))
  .catch(err => console.log(err));  // TypeError: Failed to fetch
// Console: Access to fetch at '...' from origin '...' has been blocked by CORS policy
```

**Why it crashes:** The request **was sent**, and the server may have even processed it, but the browser **blocked the response** — your JS can't get the data. This isn't a code bug; it's the browser's security policy. Common solutions:

1. **Add CORS headers on the backend** (the proper approach, if you control the backend)
2. **Use a proxy**: have your same-origin backend forward the request
3. **Dev environment proxy**: both `vite` and `webpack-dev-server` support proxy configuration

### Crash Site 2: assuming a CORS error means the request never went out, and retrying over and over

```js
// ❌ Pointless retries
async function load() {
  for (let i = 0; i < 3; i++) {
    try {
      return await fetch('https://no-cors.com/api/data');
    } catch (e) {
      console.log('Retrying...');  // all 3 retries fail because the server config never changed
    }
  }
}

// ✅ Face the real problem: either fix the backend headers or use a proxy
// In dev, configure a proxy in vite.config.js
// server: { proxy: { '/api': 'https://no-cors.com' } }
```

**Why it crashes:** CORS is a **blocked response**, not a network failure. Retrying won't change the response headers — it just makes the problem repeat. The solution is to change the server configuration or add a proxy.

## The two headers CORS requires

Response headers the server needs to return:

```
Access-Control-Allow-Origin: https://myapp.com   # which origin is allowed
Access-Control-Allow-Methods: GET, POST, PUT     # which methods are allowed
```

For requests with custom headers (like `Authorization`), the browser first sends a **preflight request (OPTIONS)** to confirm permission before sending the actual request. This is automatic browser behavior — developers usually don't need to write it by hand.

## Comparison with Python

Python's `requests` library **has no cross-origin issue** when requesting other domains — CORS is a **browser** security policy; server-to-server communication has no such restriction.

```python
# Python server-side request: no CORS concept
import requests
r = requests.get('https://another-domain.com/api/data')
print(r.json())  # works fine
```

JS in the browser is constrained by the same-origin policy, which is why "frontend/backend分离" projects frequently have to deal with CORS.

## Recap

- Public APIs are great practice for `fetch`; start with ones that require no login.
- Full flow: `loading` → `fetch` → check `res.ok` → `res.json()` → render → `catch` errors → `finally` closes loading.
- CORS is a **browser** security policy; there is no such thing between servers.
- A CORS error means the **response is blocked**; retrying is useless — the backend needs to add the `Access-Control-Allow-Origin` header or you need a proxy.
- Requests with custom headers trigger an automatic browser preflight (OPTIONS).
