# Error Handling: try/catch with await and finally

> This lesson covers how to catch errors in asynchronous code, and how to avoid letting `.catch` "swallow" errors.

## try/catch with await

One of the greatest conveniences of `async/await` is that **you can use synchronous-style `try/catch` to catch asynchronous errors.**

```js
async function loadUser() {
  try {
    const response = await fetch('/api/user');
    const user = await response.json();
    return user;
  } catch (error) {
    console.error('Load failed:', error.message);
    return null;  // provide a fallback value
  }
}
```

When the Promise after `await` **rejects**, the program jumps into the `catch` block just like a synchronous exception. This makes error handling feel identical to writing regular synchronous code.

### Crash Site 1: `.catch` doesn't return, so the error is "swallowed" and the caller gets undefined

```js
// ❌ Error is silently swallowed
async function loadData() {
  return fetchData()
    .then(data => {
      return data.value;
    })
    .catch(error => {
      console.error(error);  // only logs, no return
      // function implicitly returns undefined
    });
}

// Caller thinks it got a value, but actually got undefined
const value = await loadData();
console.log(value.toFixed(2));  // TypeError: Cannot read properties of undefined
```

**Why it crashes:** If `.catch` neither `return`s nor `throw`s, it returns a **resolved (successful)** Promise with the value `undefined`. The caller has no idea anything went wrong and continues on to crash. The fix is to **either return a fallback value or re-throw**:

```js
// ✅ Option A: return a fallback value
.catch(error => {
  console.error(error);
  return { value: 0 };  // give the caller something usable
})

// ✅ Option B: re-throw so the upper layer can handle it
.catch(error => {
  console.error('Logged locally');
  throw error;  // propagate upward
})
```

## Three "disguises" of swallowed errors

`.catch` turns an async flow failure **into a success (with an `undefined` value)**. This kind of bug is very sneaky because the code doesn't throw, and no breakpoint is hit.

```js
// Scenario: the error handler itself throws an error
async function process() {
  try {
    await mayFail();
  } catch (error) {
    // Suppose this accesses a non-existent object
    console.log(error.message.toUpperCase());  // if message is undefined, this crashes
  }
}
```

### Crash Site 2: an error inside the catch block isn't caught, becoming an "unhandled Promise rejection"

```js
// ❌ Error inside catch isn't caught by anything
async function process() {
  try {
    await mayFail();
  } catch (error) {
    reportError(error);  // suppose this function throws internally
  }
  console.log('Continue');  // if reportError throws, this line never runs
}

// ✅ Double protection
async function process() {
  try {
    await mayFail();
  } catch (error) {
    try {
      reportError(error);
    } catch (e) {
      console.error('Even error reporting failed:', e);
    }
  }
}
```

**Why it crashes:** An error inside a `catch` block will **replace** the original error and continue propagating upward. If there's no outer `try/catch`, it becomes an unhandled Promise rejection, leaving a warning in the console and interrupting the subsequent logic.

## finally: always runs, whether you succeed or fail

`finally` is for **cleanup work** — regardless of whether the `try` succeeded or the `catch` threw an error, it will execute.

```js
let loading = true;

async function loadData() {
  try {
    return await fetchData();
  } catch (error) {
    console.error(error);
    return null;
  } finally {
    loading = false;   // whether success or failure, turn off loading
    console.log('Request finished');
  }
}
```

Typical scenarios: closing a loading state, releasing resources, disconnecting.

```js
async function withLock(resource, task) {
  resource.lock();
  try {
    return await task();
  } finally {
    resource.unlock();  // guarantee the lock is released after the task ends
  }
}
```

**Note: a `return` inside `finally` will override the return value of `try`/`catch`.**

```js
// ❌ return in finally overrides the return from try
async function example() {
  try {
    return 'from try';
  } finally {
    return 'from finally';  // this is what gets returned
  }
}
example().then(v => console.log(v));  // from finally
```

**Why it crashes:** A `return` in `finally` **overrides** the return value from `try` or `catch`, causing the caller to receive the wrong result. So in `finally`, **only do cleanup — never `return`**.

## Three error propagation paths compared

| Approach | Where the error goes |
|---|---|
| `try { await x() } catch(e) { ... }` | Error is caught by catch, flow continues |
| `await x().catch(e => ...)` | Equivalent to try/catch, but reads more like "value handling" |
| Nothing at all | Error bubbles up, eventually becoming an unhandled Promise rejection |

```js
// Global fallback (browser environment)
window.addEventListener('unhandledrejection', (event) => {
  console.error('Unhandled Promise rejection:', event.reason);
});
```

## Comparison with Python

Python's `try/except/finally` semantics are identical to JS's, including pitfalls like re-throwing inside `except` and `finally` overriding the return value.

```python
# Python
try:
    result = await fetch_data()
except Exception as e:
    print(e)
finally:
    loading = False
```

```js
// JS
try {
  const result = await fetchData();
} catch (error) {
  console.error(error);
} finally {
  loading = false;
}
```

## Recap

- `try/catch` can catch `await` async errors, with the same syntax as synchronous code.
- When `.catch` neither returns nor throws, it turns a failure into an `undefined` success value — **the error is swallowed**.
- The catch block itself can throw; use double try/catch protection when necessary.
- `finally` is for cleanup (closing loading, releasing resources); **never `return` inside it**.
- Unhandled Promise rejections trigger the `unhandledrejection` event.
