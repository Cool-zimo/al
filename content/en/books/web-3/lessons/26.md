# Project Design: Breaking Down a Weather and Exchange-Rate App

> This lesson writes no code. It figures out what we're building first — requirements, data structures, API choices, and a wireframe sketch, in four steps.

## Start with a requirements list

For a "weather + exchange rate" app, list out **what the user can do** first. Don't rush into code; a clear list prevents rework later.

**Core requirements (the MVP)**
- Enter a city name and look up its current weather (temperature, conditions, humidity, wind speed).
- Pick two currencies and look up their live exchange rate.
- Show a loading state while fetching.
- Show an error message on failure and allow retrying.

**Nice-to-have requirements**
- Save recently looked-up cities/rates locally and restore them on the next open.
- Debounce the city-name search so requests fire only after the user stops typing.
- Support switching temperature units (°C/°F).
- Make it responsive so it looks good on phones too.

A requirements list needs **priorities**. Get the core requirements solid first, then touch the extras. Adding requirements mid-build is the single biggest reason projects slip their deadlines.

## Data structures: decide what you'll actually keep

You store whatever the backend returns. Designing the data shape up front makes rendering and caching simpler later.

```js
// Weather data
{
  city: 'Paris',
  temp: 23,
  condition: 'Sunny',
  humidity: 45,      // humidity %
  windSpeed: 3.2,    // wind speed m/s
  updatedAt: 1717500000000
}

// Exchange-rate data
{
  base: 'USD',
  target: 'GBP',
  rate: 0.79,
  updatedAt: 1717500000000
}
```

Design tip: **keep only the fields the page actually displays**. Drop the rest — it saves memory and network. Store `updatedAt` as a timestamp so you can tell whether it's stale.

## Picking APIs: free does not mean usable

For a practice-grade project, an API needs three hard requirements: **no login or key, has CORS, and has clear docs**.

| Use case | Candidates | Watch out for |
|---|---|---|
| Weather | Open-Meteo (free, no key) | You must convert city names to latitude/longitude first |
| Exchange rates | exchangerate-api / public central-bank feeds | Mind the rate limits |

**Crash Site 1:** calling an API that doesn't allow cross-origin requests, so the browser throws an error.

```js
// ❌ No CORS allowed, console shows a CORS error
fetch('http://some-weather-site-without-cors/Paris')
  .then(r => r.json())   // fails outright

// ✅ Pick an endpoint that sends Access-Control-Allow-Origin
fetch('https://api.open-meteo.com/v1/forecast?latitude=48.8567&longitude=2.3522&current=temperature_2m')
  .then(r => r.json())
```

**Why it crashes:** the browser's same-origin policy blocks cross-origin responses. When choosing an API, confirm the response headers include `Access-Control-Allow-Origin: *` or your domain — otherwise the frontend can never reach it directly.

## A wireframe: sketch it on paper first

Before you start coding, turn the interface into an ASCII sketch. It saves a huge amount of rework.

```
┌──────────────────────────────────────────┐
│  [Paris        ]  [Search]              │  <- search box + button
├──────────────────────────────────────────┤
│  ⏳ Loading... / ❌ Failed, click retry  │  <- status area
├──────────────────────────────────────────┤
│  City: Paris                             │
│  Temp: 23 °C      Conditions: Sunny      │  <- weather card
│  Humidity: 45%   Wind: 3.2 m/s          │
├──────────────────────────────────────────┤
│  [USD ▼]  →  [GBP ▼]  [Convert]         │  <- exchange rate area
│  1 USD = 0.79 GBP                       │
└──────────────────────────────────────────┘
```

The sketch should mark out the **status area** (loading/error/empty/success) and the **data area**. A real app handles at least these four states — success is not the only one.

## Modules: one file does one thing

Split the work into modules by responsibility; each chapter from here on maps to one of them:

```text
weather-app/
├── index.html        # skeleton
├── style.css         # layout and styling
└── main.js           # entry point: wires API + cache + rendering
                      # internally split into: api.js (requests) / storage.js (cache) / ui.js (rendering)
```

| Module | Responsibility | Depends on |
|---|---|---|
| `api.js` | Wraps fetch and error handling | nothing |
| `storage.js` | localStorage read/write | nothing |
| `ui.js` | Renders data, switches states | api, storage |

Dependencies go one way: `ui` uses `api` and `storage`, never the reverse. That way every module is testable on its own.

## Recap

- Split requirements into **core** and **extras**, and get the core solid first.
- Keep only the fields you display, plus an `updatedAt` timestamp.
- Always check for CORS when picking an API, or the frontend will never reach it.
- Sketch the UI first and be explicit about the four states: empty, loading, error, success.
- Split by responsibility with one-way dependencies, for testability and reuse.
