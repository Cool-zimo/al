# Wrapping Up: Code Organisation, Performance, Accessibility, and What's Next

> The final lesson turns the project from "it runs" into "it's maintainable": splitting modules, tightening performance, caring about accessibility, and learning to debug.

## Code organisation: from one file to modules

A small exercise fits in a single `main.js`, but as features grow you need to split. Browsers support ES Modules natively:

```html
<script type="module" src="./main.js"></script>
```

```js
// api.js
export async function getWeather(city) { /* ... */ }
export async function getRate(base, target) { /* ... */ }

// storage.js
export const cache = {
  read() { /* ... */ },
  save(data) { /* ... */ }
};

// ui.js
export function render(data) { /* ... */ }
export function showStatus(state, msg) { /* ... */ }

// main.js
import { getWeather } from './api.js';
import { cache } from './storage.js';
import { render, showStatus } from './ui.js';
```

Rule: **dependencies go one way**. `ui` uses `api` and `storage`; never the other way around. Each module is independently testable and replaceable.

## Performance: the four highest-value wins

1. **Debounce input-driven requests:** 300ms on search and autocomplete pays off immediately.
2. **Cache repeated requests:** localStorage or an in-memory Map avoids duplicate network round trips.
3. **Cancel useless requests:** use `AbortController` to abort when the page or component goes away.
4. **Batch DOM work and avoid layout thrash:** update the data first, render once, and don't read `offsetWidth` inside a loop.

```js
// ❌ Reading layout inside a loop triggers multiple reflows
items.forEach(it => {
  el.appendChild(renderItem(it));
  console.log(el.offsetHeight);   // forces synchronous layout
});

// ✅ Insert in a batch, then read once at the end
const frag = document.createDocumentFragment();
items.forEach(it => frag.appendChild(renderItem(it)));
el.appendChild(frag);
console.log(el.offsetHeight);
```

**Crash Site 1:** reading layout properties synchronously inside an animation loop.

```js
function loop() {
  el.style.width = x + 'px';
  const w = el.offsetWidth;   // forces the browser to reflow right now — drops a frame
  x += 3;
  requestAnimationFrame(loop);
}
```

**Why it crashes:** writing a style and then immediately reading `offsetWidth` or `getBoundingClientRect` forces the browser to complete a layout calculation. That eats the frame's time budget, and the animation stutters. Write in batches, read once at the end.

## Accessibility: making it usable for everyone

- **Semantic tags:** `<main>`, `<nav>`, `<button>` instead of `<div>` everywhere.
- **Form associations:** pair `<input id="kw">` with `<label for="kw">` so clicking the label focuses the input.
- **Announce state:** `aria-live="polite"` lets screen readers speak dynamic content.

```html
<label for="cityInput">City</label>
<input id="cityInput" type="text" aria-describedby="cityHint" />
<span id="cityHint">Enter a city name</span>

<section id="status" aria-live="polite"></section>
```

- **Keyboard reachable:** use `tabindex` for custom controls, and native `<button>` elements (they activate on Space/Enter automatically).
- **Colour contrast:** text needs at least a 4.5:1 ratio against its background.

**Crash Site 2:** relying only on colour to distinguish state.

```html
<!-- ❌ Colour-blind users can't tell the difference -->
<span style="color:red">Failed</span>
<span style="color:green">Success</span>

<!-- ✅ Colour plus text or an icon -->
<span class="status status--error">✕ Failed</span>
<span class="status status--success">✓ Success</span>
```

**Why it crashes:** roughly 8% of men have some form of colour-vision deficiency. Relying only on colour loses critical information. State and errors must always have text or an icon too.

## Debugging tips: beyond console.log

- **Breakpoints:** click a line number in the DevTools Sources panel — far more efficient than `console.log`.
- **Network:** the Network panel shows whether a request was sent, its status code, and the response body.
- **Conditional breakpoints:** pause only when a specific value appears, like `city === 'Paris'`.
- **Watch expressions:** keep an eye on `seq`, `cache`, and similar variables in the Watch panel.
- **Logpoints:** don't pause; just print on hit, replacing throwaway `console.log` calls.

For race-condition bugs, the single most useful trick is to **number every request**. Log `[req #3] sent Paris` when it's fired and again when it returns, and you'll see who came first at a glance.

## Where to go from here

By finishing this volume, you can build a working web app on your own — one that fetches data, caches it, and manages state. Next steps:

| Direction | What to learn | Why |
|---|---|---|
| Frameworks | React / Vue | Data and the view stay in sync automatically — no more hand-written DOM |
| Tooling | Vite / Webpack, ESM | Hot module replacement, bundling, and on-demand loading |
| Types | TypeScript | Type-safe API data, so refactoring is much safer |
| Backend | Node.js + Express | Write your own APIs and stop fighting CORS |
| Full stack | Next.js / Nuxt | SSR, routing, and data fetching in one place |

## Recap

- Split into ES Modules: api / storage / ui, with one-way dependencies.
- The performance four: debounce, cache, cancel, batch DOM.
- Accessibility: semantic tags + form associations + aria-live + keyboard reachability + contrast.
- Don't rely on colour alone — always add text or an icon.
- For race bugs: number every request and watch the Network panel.
- Next up: React or Vue, tooling, TypeScript, and a Node backend.
