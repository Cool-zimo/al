# Loading States and Error Handling: Three States and AbortController

> This lesson covers the essential "three-state management" of any real application, and how to cancel a request that has already been sent.

## Three states: loading / error / empty

Any interface that "fetches data from a server and displays it" has at least three states:

| State | Meaning | UI representation |
|---|---|---|
| `loading` | Request in progress | Spinner, skeleton screen |
| `error` | Request failed | Error message, retry button |
| `success` | Request succeeded | Display the data |

If the data might be an empty list, you also need an `empty` state:

```js
async function loadUsers() {
  setStatus('loading');
  try {
    const res = await fetch('/api/users');
    if (!res.ok) throw new Error('Load failed');
    const data = await res.json();
    if (data.length === 0) {
      setStatus('empty');
    } else {
      setStatus('success');
      render(data);
    }
  } catch (error) {
    setStatus('error');
    showError(error.message);
  }
}
```

### Crash Site 1: on request failure, the interface stays on loading forever, spinning endlessly

```js
// ❌ No error handling, gets stuck on failure
async function load() {
  setStatus('loading');
  const res = await fetch('/api/data');
  const data = await res.json();
  render(data);
  setStatus('success');  // if anything above throws, this line never runs
}

// ✅ try/catch as a safety net
async function load() {
  setStatus('loading');
  try {
    const res = await fetch('/api/data');
    if (!res.ok) throw new Error('HTTP ' + res.status);
    const data = await res.json();
    render(data);
    setStatus('success');
  } catch (error) {
    setStatus('error');  // on failure, still update the state
  }
}
```

**Why it crashes:** Without `catch`, once the request fails (no network, 404, 500), the function throws and `setStatus('success')` never executes. The interface **stays in the loading state forever**. The user sees a spinner that never stops, with no idea what happened.

## Mapping state to UI

```html
<div id="app">
  <div id="loading" style="display:none;">Loading...</div>
  <div id="error" style="display:none;">Something went wrong, <button id="retry">Retry</button></div>
  <div id="empty" style="display:none;">No data yet</div>
  <ul id="list"></ul>
</div>
```

```js
function setStatus(status) {
  document.querySelector('#loading').style.display = status === 'loading' ? 'block' : 'none';
  document.querySelector('#error').style.display = status === 'error' ? 'block' : 'none';
  document.querySelector('#empty').style.display = status === 'empty' ? 'block' : 'none';
}
```

## AbortController: cancelling a request

Scenario: a user quickly types "L", "Lon", "London" in a search box, triggering 3 requests. The response for request 1 might arrive **after** request 3, causing the interface to display stale results.

```js
let controller = null;

async function search(keyword) {
  // cancel the previous unfinished request
  if (controller) {
    controller.abort();
  }
  controller = new AbortController();

  try {
    const res = await fetch(`/api/search?q=${keyword}`, {
      signal: controller.signal  // attach the signal
    });
    const data = await res.json();
    render(data);
  } catch (error) {
    if (error.name === 'AbortError') {
      console.log('Request cancelled');  // cancellation isn't a real error; handle silently
      return;
    }
    console.error('Request failed:', error);
  }
}
```

The three core steps of `AbortController`:

1. `new AbortController()` creates a controller
2. Pass `controller.signal` to fetch's `signal` option
3. Call `controller.abort()` to cancel the request (fetch will throw `AbortError`)

### Crash Site 2: with AbortController, forgetting to distinguish AbortError from real errors, causing cancellations to also show error messages

```js
// ❌ Cancellation is treated as an error too
async function load() {
  try {
    const res = await fetch(url, { signal: controller.signal });
    render(await res.json());
  } catch (error) {
    showError('Load failed');  // every cancellation also shows "Load failed" — bad UX
  }
}

// ✅ Distinguish cancellation from failure
async function load() {
  try {
    const res = await fetch(url, { signal: controller.signal });
    render(await res.json());
  } catch (error) {
    if (error.name === 'AbortError') return;  // cancellation, silent
    showError('Load failed');  // only show on real failure
  }
}
```

**Why it crashes:** Every time the user types quickly, the old request is cancelled and shows a "load failed" message. The user sees a flood of mysterious error messages — a terrible experience. Checking `error.name === 'AbortError'` is the standard way to handle cancellations.

## Timeout control

`AbortController` can also be combined with `setTimeout` to implement timeouts:

```js
async function fetchWithTimeout(url, ms) {
  const controller = new AbortController();
  const timer = setTimeout(() => controller.abort(), ms);

  try {
    const res = await fetch(url, { signal: controller.signal });
    clearTimeout(timer);
    return res;
  } catch (error) {
    clearTimeout(timer);
    throw error;
  }
}

// cancel after 5 seconds
fetchWithTimeout('/api/slow', 5000).catch(error => {
  if (error.name === 'AbortError') console.log('Timed out');
});
```

## Recap

- Any data-loading interface has at least **loading / error / empty** states, each with corresponding UI.
- On request failure, you must update the state, otherwise the interface **stays on loading forever**.
- `AbortController` cancels requests in three steps: create, attach signal, abort.
- Cancellation throws `AbortError`, which should be handled separately and ignored silently — don't show it to the user.
- `AbortController` + `setTimeout` can implement request timeouts.
