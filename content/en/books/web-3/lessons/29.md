# Adding Cache, Debounced Search, and Request Race Handling

> This lesson solves three common real-world problems: storing results in localStorage, not searching on every keystroke, and handling "late responses arriving early."

## localStorage cache: what to store, and for how long

localStorage only stores strings, so objects and arrays need `JSON.stringify` first.

```js
const CACHE_KEY = 'weather_cache';
const CACHE_TTL = 10 * 60 * 1000;   // 10 minutes

function saveCache(data) {
  const payload = { data, savedAt: Date.now() };
  localStorage.setItem(CACHE_KEY, JSON.stringify(payload));
}

function readCache() {
  const raw = localStorage.getItem(CACHE_KEY);
  if (!raw) return null;
  try {
    const { data, savedAt } = JSON.parse(raw);
    if (Date.now() - savedAt > CACHE_TTL) return null;   // expired
    return data;
  } catch (e) {
    return null;   // treat parse failure as no cache
  }
}
```

A cache needs a **timestamp**, and expired means gone. Otherwise users see yesterday's weather forever.

## Combining cache and requests

```js
async function search(city) {
  const cache = readCache();
  if (cache && cache.city === city) {
    render(cache);          // cache hit: render immediately, no request
    return;
  }
  showStatus('loading');
  try {
    const data = await getWeather(city);
    saveCache(data);
    render(data);
    showStatus('success');
  } catch (e) {
    // request failed but we have a stale cache: degrade to old data
    if (cache) render(cache);
    showStatus('error', e.message);
  }
}
```

Strategy: **read the cache first → render if present → then fetch to update**. If the fetch fails but a stale cache exists, show the stale data rather than a blank screen.

**Crash Site 1:** parsing the cache with raw `JSON.parse`, so bad data crashes the whole app.

```js
// ❌ Cache was edited by hand; the app shows a blank white screen
const data = JSON.parse(localStorage.getItem(CACHE_KEY));

// ✅ Wrap it in try/catch; on parse failure, treat as no cache
let data = null;
try { data = JSON.parse(raw); } catch (e) { data = null; }
```

**Why it crashes:** localStorage can be edited by the user or other scripts. It might contain `undefined`, a malformed string like `"{bad json"`, or an object of the wrong shape. A bare `JSON.parse` throws and stops every later line of code.

## Debounced search: wait for the user to stop typing

When the user types "P", "Pa", "Par", "Paris", you don't want a request for every keystroke.

```js
function debounce(fn, delay) {
  let timer = null;
  return function (...args) {
    clearTimeout(timer);
    timer = setTimeout(() => fn.apply(this, args), delay);
  };
}

const onInput = debounce((city) => {
  if (city) search(city);
}, 400);

cityInput.addEventListener('input', (e) => {
  onInput(e.target.value.trim());
});
```

A `delay` of 300–500ms is typical. Too short and it does nothing; too long and the UI feels laggy.

## Request races: the "late response arriving first" problem

This is the classic autocomplete trap. The user types "Paris" (request A), then "London" (request B). **B can come back before A**, and if you blindly use A's result to overwrite, the page shows "the weather for Paris under the London input."

```js
// ❌ Late-arriving A overwrites the already-rendered B
async function search(city) {
  const data = await getWeather(city);
  render(data);     // when A returns, city is already 'London', but it renders old Paris data
}

// ✅ Approach: grab a sequence number when requesting, check it on callback
let seq = 0;
async function search(city) {
  const mySeq = ++seq;                  // take a number
  try {
    const data = await getWeather(city);
    if (mySeq !== seq) return;          // I'm stale, discard
    render(data);
  } catch (e) {
    if (mySeq !== seq) return;
    showStatus('error', e.message);
  }
}
```

Each new request does `seq++`, and only the callback whose sequence number matches the latest value is allowed to update the page. This is the **"take a number + check"** pattern.

**Crash Site 2:** putting `AbortController` in the wrong place, so you cancel the fresh request instead.

```js
// ❌ Every new input creates a new one, which accidentally cancels the correct request just sent
let controller = null;
async function search(city) {
  controller = new AbortController();     // the previous line's controller is overwritten
  const data = await fetch(url, { signal: controller.signal });
}

// ✅ Abort the old request BEFORE creating the new one
let controller = null;
async function search(city) {
  if (controller) controller.abort();     // cancel the old request first
  controller = new AbortController();     // then create a new one
  const data = await fetch(url, { signal: controller.signal });
}
```

**Why it crashes:** with the order reversed, the new request is cancelled by the very next line. The correct order is **abort the old one first, then create the new one**.

## Recap

- localStorage stores strings only — `JSON.stringify` to save, `JSON.parse` to read, and wrap the parse in try/catch.
- Cache carries a `savedAt` timestamp; expired means no cache.
- Strategy: render on cache hit → then fetch to update → on failure, degrade to stale data.
- Debounce waits for "400ms of quiet" before firing, cutting wasted requests.
- Races are handled with **sequence-number checks** or **AbortController to cancel old requests**.
