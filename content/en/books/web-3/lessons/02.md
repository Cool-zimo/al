# Callbacks: The Original Asynchronous Pattern and Callback Hell

> This lesson covers callbacks — the original form of asynchrony in JavaScript — and why too much nesting becomes "hell."

## What is a callback?

A callback is **passing a function as an argument to another function, so it can be called at some point later (usually when an operation completes).**

```js
// The most basic callback
function fetchData(callback) {
  setTimeout(() => {
    const data = { name: 'Alice', age: 28 };
    callback(data);  // call the callback once the data is ready
  }, 1000);
}

fetchData((data) => {
  console.log('Got data:', data.name);  // 1 second later: Got data: Alice
});
```

Here, `callback` is not a JS keyword — it is just a conventional parameter name. You could just as well write `onDone`, `handler`, or `cb`.

## The value of asynchronous callbacks

Callbacks make "**register now, execute later**" possible. Synchronous code can't do this — it must have the result before it can continue.

```js
// Simulate fetching a user, then fetching their posts
function getUser(id, callback) {
  setTimeout(() => {
    callback({ id, name: 'Bob' });
  }, 500);
}

getUser(1, (user) => {
  console.log('User:', user.name);
});
```

### Crash Site 1: forgetting to handle "no result" in a callback, causing a logic gap

```js
// ❌ Does not account for "not found"
function findUser(id, callback) {
  const users = [{ id: 1, name: 'Alice' }, { id: 2, name: 'Bob' }];
  const found = users.find(u => u.id === id);
  callback(found);  // when id=3, found is undefined; the caller receives undefined
}

findUser(3, (user) => {
  console.log(user.name.toUpperCase());  // TypeError: Cannot read properties of undefined
});
```

**Why it crashes:** When the callback receives `undefined` and you immediately access a property on it, a runtime error is thrown and all subsequent code is interrupted. The correct approach is to **pass two values to the callback: an error and a result** — this is Node.js's classic "error-first callback" convention:

```js
// ✅ Error-first: first argument is err
function findUser(id, callback) {
  const users = [{ id: 1, name: 'Alice' }];
  const found = users.find(u => u.id === id);
  if (!found) {
    callback(new Error('User not found'), null);
  } else {
    callback(null, found);
  }
}

findUser(3, (err, user) => {
  if (err) {
    console.error(err.message);
    return;
  }
  console.log(user.name);
});
```

## Callback hell: nesting gets out of control

When each subsequent step depends on the result of the previous one, callbacks nest layer upon layer:

```js
// ❌ Callback hell: nesting grows deeper and deeper, harder to read
getUser(1, (user) => {
  getPosts(user.id, (posts) => {
    getComments(posts[0].id, (comments) => {
      getAuthor(comments[0].authorId, (author) => {
        console.log('Finally got the author:', author.name);
        // If you keep nesting, the code keeps marching to the right
      });
    });
  });
});
```

The problems with this code go beyond just **runaway indentation** (colloquially called the "rightward arrow"). There are three pain points:

1. **Duplicated error handling**: every layer must check for errors, creating massive redundancy.
2. **Hard to reuse**: nested callbacks are difficult to extract into standalone functions.
3. **Hard to follow the flow**: adding branches or conditionals makes the structure even messier.

### Crash Site 2: using an async callback inside a loop causes index chaos

```js
// ❌ The classic "loop + async" index trap
const names = ['Alice', 'Bob', 'Charlie'];
for (var i = 0; i < names.length; i++) {
  setTimeout(() => {
    console.log(names[i]);  // all three output undefined
  }, 100);
}
```

**Why it crashes:** All three output `undefined`. The reason is that `var` has no block scope — `i` is shared. By the time the `setTimeout` callbacks execute, the loop has long since finished and `i` is `3`. The fix is to use `let` (block scope) or pass the index into a closure.

```js
// ✅ Use let
for (let i = 0; i < names.length; i++) {
  setTimeout(() => {
    console.log(names[i]);  // Alice / Bob / Charlie
  }, 100);
}
```

## The preview of a cure for callback hell

The essence of callback hell is "**expressing sequence through nesting**." The two solutions that follow address this problem:

- **Promises**: use `.then()` chaining to **flatten** nested code into a top-to-bottom flow.
- **async/await**: express asynchrony with synchronous-looking code.

```js
// ✅ Rewrite the nesting above with async/await
async function loadAuthor() {
  const user = await getUser(1);
  const posts = await getPosts(user.id);
  const comments = await getComments(posts[0].id);
  const author = await getAuthor(comments[0].authorId);
  console.log('Author:', author.name);
}
```

## Comparison with Python

Python's callback mechanism is similar, but its ecosystem more commonly uses **generators + yield** or `asyncio` coroutines to express asynchronous flows. Deep callback nesting is rarely seen. In JS, because of historical reasons, early APIs were largely callback-style (such as Node.js's filesystem module), making "callback hell" a uniquely common JS interview topic.

## Recap

- A callback is an asynchronous pattern of "pass a function as an argument, call it later"; the parameter name has no special meaning.
- Callbacks should follow the **error-first** convention: `callback(err, result)`; always check `err` first.
- Multiple layers of dependent nesting create **callback hell**: runaway indentation, redundant error handling, and poor reusability.
- In loops, watch out for the shared-index problem with async callbacks — use `let` instead.
- Promises and async/await are the two generations of solutions to callback hell.
