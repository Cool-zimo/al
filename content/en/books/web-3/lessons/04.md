# async/await: Writing Asynchronous Code Synchronously

> This lesson covers the `async/await` syntax sugar and the critical performance concept of "parallel execution."

## What is async/await?

`async/await` is **syntax sugar built on top of Promises**: it lets you write asynchronous code that looks almost identical to synchronous code.

```js
// Promise chain without async/await
function loadUser() {
  return fetchUser(1)
    .then(user => fetchPosts(user.id))
    .then(posts => posts.length);
}

// ✅ With async/await: the code is "straight"
async function loadUser() {
  const user = await fetchUser(1);    // wait for the Promise, get the result
  const posts = await fetchPosts(user.id);
  return posts.length;
}
```

`await` is followed by a Promise; it **pauses execution of the current async function** and assigns the result to the variable on the left once the Promise settles. Important: **only this function is paused, not the entire main thread** — other code continues running normally.

## async functions always return a Promise

Whether you explicitly return a Promise or not, the return value of an `async` function is automatically wrapped in a Promise:

```js
async function add(a, b) {
  return a + b;   // equivalent to return Promise.resolve(a + b)
}

add(1, 2).then(result => console.log(result));  // 3
```

So async functions can `await` each other:

```js
async function getName() {
  return 'Alice';
}
async function greet() {
  const name = await getName();  // await an async function
  return `Hello, ${name}`;
}
```

### Crash Site 1: using `await` in a regular function or at the top level causes a syntax error

```js
// ❌ Syntax error: await can only be used inside async functions
function normalFn() {
  const data = await fetchData();  // SyntaxError
  return data;
}

// await at the top level also throws in older environments
const data = await fetchData();  // some older versions throw directly
```

**Why it crashes:** The code **won't run at all** — it throws a syntax error immediately. The solution is to add `async` to the function:

```js
// ✅ Add async
async function normalFn() {
  const data = await fetchData();
  return data;
}
```

(Note: modern JS supports top-level `await`, but only inside ES Modules; it is still restricted in script tags.)

## Serial vs. parallel: the performance dividing line

This is the easiest performance pitfall with async/await. Look at these two code snippets:

```js
// ❌ Serial: wait for A, then wait for B — about 2 seconds total
async function serial() {
  const a = await fetchA();  // assume 1 second
  const b = await fetchB();  // then wait another 1 second
  return [a, b];
}

// ✅ Parallel: A and B start at the same time — about 1 second total
async function parallel() {
  const p1 = fetchA();   // start immediately, returns a Promise
  const p2 = fetchB();   // start immediately
  const a = await p1;    // wait for both to finish
  const b = await p2;
  return [a, b];
}
```

In the serial version, the two `await`s are **queued one after another**, so the times add up. In the parallel version, both Promises are **started first**, then `await`ed together — the total time is the maximum of the two.

### Crash Site 2: thinking that putting `await` expressions inside `Promise.all` achieves parallelism

```js
// ❌ This is still serial
async function wrong() {
  const results = await Promise.all([
    await fetchA(),   // await here waits for fetchA to complete first
    await fetchB()    // then waits for fetchB to complete
  ]);
  return results;
}
// Promise.all receives [result of a, result of b] — both plain values,
// so the "wait together" benefit is lost, and the code is confusing.

// ✅ Correct: pass the Promises themselves
async function right() {
  const results = await Promise.all([
    fetchA(),   // pass the Promise, not the awaited result
    fetchB()
  ]);
  return results;
}
```

**Why it crashes:** The first version technically runs, but **there is no parallelism**, and the purpose of `Promise.all` is wasted. Remember the rule: **`Promise.all` receives Promises, not awaited results.**

## Promise.all failure semantics

`Promise.all` is **"one failure means total failure"**: as soon as any Promise rejects, the entire thing rejects immediately. The other still-running Promises are not cancelled (their results are just ignored).

```js
// If one fails, the whole thing fails
Promise.all([
  Promise.resolve(1),
  Promise.reject(new Error('Failed')),
  Promise.resolve(3)
])
  .then(values => console.log(values))
  .catch(error => console.error('Total failure:', error.message));  // Total failure: Failed
```

If your requirement is "**collect all results even if some fail**," you should use `Promise.allSettled`:

```js
Promise.allSettled([
  Promise.resolve(1),
  Promise.reject(new Error('Failed'))
]).then(results => {
  // results: [{status:'fulfilled', value:1}, {status:'rejected', reason: Error}]
  console.log(results[1].status);  // 'rejected'
});
```

## Comparison with Python

Python's `async/await` is almost isomorphic to JS's; JS Promises correspond to Python coroutines, and `Promise.all` corresponds to `asyncio.gather`:

```python
# Python
import asyncio
async def main():
    results = await asyncio.gather(fetch_a(), fetch_b())
```

```js
// JS
async function main() {
  const results = await Promise.all([fetchA(), fetchB()]);
}
```

The semantics and the serial/parallel pitfalls are identical in both languages.

## Recap

- `async/await` is syntax sugar over Promises, making async code look like sync code.
- `await` **can only be used inside async functions** (top-level await has restrictions).
- An async function's return value is **automatically wrapped in a Promise**.
- `await` pauses the function but does **not** block the main thread.
- Performance key: **when you need parallelism, pass Promises themselves to `Promise.all`, don't `await` them first.**
- `Promise.all` is "one failure means total failure"; `Promise.allSettled` collects all outcomes.
