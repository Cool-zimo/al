# Map and Set: Knowing When to Use Them Instead of Object / Array

> This lesson covers two "enhanced" data structures: Map (key-value pairs) and Set (unique-value collections), and when you should reach for them instead of Object/Array.

## Map: keys can be any type

With a plain Object, keys **can only be strings or Symbols**. With a Map, keys can be **any type at all**: objects, functions, numbers — anything works.

```js
const map = new Map();

map.set('name', 'Alice');
map.set(1, 'number key');
map.set({ id: 1 }, 'object as key');
map.set(() => {}, 'function as key');

console.log(map.get('name'));  // 'Alice'
console.log(map.size);         // 4
```

An Object can't do this:

```js
const obj = {};
obj[{ id: 1 }] = 'value';       // the object key gets toString'd to "[object Object]"
console.log(obj);               // { '[object Object]': 'value' }
```

## Common Map API

```js
const map = new Map();

map.set('a', 1);             // add / update
map.get('a');                // get: 1
map.has('a');                // check existence: true
map.delete('a');             // delete
map.clear();                 // clear all
map.size;                    // size

// iteration
map.forEach((value, key) => console.log(key, value));
for (const [key, value] of map) console.log(key, value);
```

Compared to an Object, a Map has **better performance** in scenarios where you **frequently add and remove keys**, because Map is optimized for frequent additions and deletions.

### Crash Site 1: using an Object for "counting/deduplication," where the number 1 and the string '1' are treated as the same key

```js
// ❌ Object keys all get coerced to strings
const counts = {};
counts[1] = 1;
counts['1'] = 2;
console.log(counts);  // { '1': 2 } — 1 and '1' collide

// ✅ Map keys preserve their type
const map = new Map();
map.set(1, 1);
map.set('1', 2);
console.log(map.get(1));   // 1
console.log(map.get('1')); // 2 — different types, no collision
```

**Why it crashes:** An Object **forces all keys through toString**, so the number `1` and the string `'1'` collide, the number `true` and the string `'true'` collide. If your business logic might use mixed-type keys, only a Map can preserve fidelity.

## Set: a collection of unique values

A Set is a collection where **elements are never duplicated** — commonly used for deduplication:

```js
const set = new Set();

set.add(1);
set.add(1);        // duplicate, won't be added
set.add(2);
console.log(set.size);   // 2

set.has(1);      // true
set.delete(1);   // true
```

The most common use case — **array deduplication**:

```js
const arr = [1, 2, 2, 3, 3, 3];
const unique = [...new Set(arr)];  // [1, 2, 3]
```

### Crash Site 2: assuming `new Set()` deduplicates by an object's "content"

```js
// ❌ Object deduplication fails
const set = new Set();
set.add({ id: 1 });
set.add({ id: 1 });   // looks identical, but these are two different object references
console.log(set.size);  // 2 — not deduplicated!

// Set uses "reference equality" for uniqueness — nothing to do with object content
console.log({id:1} === {id:1});  // false

// ✅ When you need to deduplicate by content, use a Map or extract a unique key first
const seen = new Map();
items.forEach(item => seen.set(item.id, item));
const unique = [...seen.values()];
```

**Why it crashes:** A Set's uniqueness is based on **reference equality (===)**, not "looking the same." Two objects with identical content but different references are treated as different elements, so deduplication fails. When you need to deduplicate by content, you must first extract a unique primitive key (like an id).

## When to use which

| Need | Use | Why |
|---|---|---|
| Key-value, keys are strings/Symbols | Object | Concise literal syntax, JSON-friendly |
| Key-value, keys are any type | Map | Key types preserved, better add/remove perf |
| Deduplication, membership checks | Set | Natural deduplication, `has` is O(1) |
| Ordered collection, needs indices | Array | Has index, slice, map, etc. |
| Needs JSON serialization | Object / Array | Map and Set can't be directly JSON.stringify'd |

```js
// Map / Set can't be serialized directly
JSON.stringify(new Map([['a', 1]]));  // '{}'
JSON.stringify(new Set([1, 2]));      // '{}'
```

## Comparison with Python

Python's `dict` can use any hashable type as a key, and `set` also naturally deduplicates — both align closely with JS's Map/Set:

```python
# Python
d = {1: 'number key', '1': 'string key'}  # no collision, keys preserve type
s = set([1, 1, 2])  # {1, 2}
```

```js
// JS
const map = new Map();
map.set(1, 'number key');
map.set('1', 'string key');  // no collision
const set = new Set([1, 1, 2]);  // Set {1, 2}
```

Python's dict is stronger than JS's Object when it comes to "preserving key types" — it's closer to JS's Map.

## Recap

- Map keys can be **any type**; Object keys are coerced to strings.
- Map is better suited to scenarios with frequent key additions and deletions, outperforming Object.
- Set naturally deduplicates, but its uniqueness check is based on **reference equality** — use a unique key for object deduplication.
- Map and Set **can't be directly JSON-serialized**; convert them to Array/Object first.
- Choosing: string keys + need serialization → Object; any key → Map; deduplication → Set; ordered → Array.
