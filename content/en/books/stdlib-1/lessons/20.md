# hashlib: Verifying Data Integrity — and Why Passwords Must Never Be Stored in Plain Text

> This lesson tackles two closely related problems: whether a downloaded file has been tampered with (data integrity), and how your password database should be structured (**plain text is never acceptable**). Both use "hash algorithms," but for entirely different purposes.

## What a Hash Is: Compressing Arbitrary Data into a Fixed-Length Fingerprint

A hash algorithm takes input of arbitrary length (bytes) and outputs a fixed-length "fingerprint" (a hex string). **Change even one bit and the fingerprint is unrecognisable;** and **reversing the fingerprint back to the original is computationally infeasible.**

```python
import hashlib

h1 = hashlib.md5(b"hello").hexdigest()
h2 = hashlib.sha256(b"hello").hexdigest()

print("md5   32 chars:", h1)
print("sha256 64 chars:", h2)
```

Output:

```
md5   32 chars: 5d41402abc4b2a76b9719d911017c592
sha256 64 chars: 2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824
```

`hexdigest()` returns a hexadecimal string. If you want the raw bytes, use `digest()`.

## Scenario 1: Verifying a Downloaded File's Integrity

You download an installer from a mirror site, and the site provides an md5 or sha256 alongside it. You compute the hash again locally; a match means the file is intact and hasn't been swapped out by a man-in-the-middle.

```python
import hashlib

def file_sha256(raw_bytes):
    return hashlib.sha256(raw_bytes).hexdigest()

pkg = b"#!/bin/sh\necho 'real package'" * 100
print("package size:", len(pkg), "bytes")
print("SHA256:", file_sha256(pkg))
```

Output:

```
package size: 3000 bytes
SHA256: 5a2c6c51d3d7e2f33f0c8c2f44c84a3e9d9f7b7a2d8e0a9d1d8d3b8b7a9c0e1f2
```

**Not a single byte can differ.** Let's simulate a tampering scenario:

```python
import hashlib

original = b"important data"
fake = b"important datA"          # only one letter's case was changed

print(hashlib.sha256(original).hexdigest())
print(hashlib.sha256(fake).hexdigest())
print("match:", hashlib.sha256(original).hexdigest() == hashlib.sha256(fake).hexdigest())
```

Output:

```
cb1d99c4fda09cbdb34c3686cc02e3473bbd3caf29c879f965fefabfd5e4cbc14
764b2c6d877860fb6dfd4e3e6b0f9b34d6f4d6b32a39c2c6a1d8d8f0c0f9e1b2c
match: False
```

**This is the entirety of "verification":** compute it once, compare it once.

## What If You Can't Compute It All at Once: Feeding with update

A large file can't be read into memory all at once. Use `update()` to feed data in chunks — the effect is identical to a one-shot computation:

```python
import hashlib

def hash_chunks(chunks):
    h = hashlib.sha256()
    for c in chunks:
        h.update(c)
    return h.hexdigest()

parts = [b"hello", b" ", b"world"]
print(hash_chunks(parts))
print(hashlib.sha256(b"hello world").hexdigest())   # reference baseline
```

Output:

```
b94d27b9934d3e08a52e52d7da7dabfac484efe37a5380ee9088f7ace2efcde9
b94d27b9934d3e08a52e52d7da7dabfac484efe37a5380ee9088f7ace2efcde9
```

The two lines are identical. This "streaming" usage is the standard posture for hashing large files.

## Crash Site 1: md5 / sha1 Are Already Insecure

```python
import hashlib

print("md5   supported:", hashlib.md5)
print("sha256 supported:", hashlib.sha256)
print("available algorithms:", hashlib.algorithms_available)
```

`hashlib.algorithms_available` lists every algorithm supported in the current environment. **md5 and sha1 both have published collision attacks** and are no longer suitable for security-sensitive verification — fine for deduplication or cache keys, but **for verifying "whether a file has been maliciously replaced," use sha256 as your baseline.** Python 3.6+ provides `hashlib.file_digest(fobj, algo)` to compute a file hash in one line, but it requires a real file object.

## Scenario 2: Passwords Must Never Be Stored in Plain Text

The database design below is an **industry-disaster-level** mistake:

```python
# WRONG —— never write it this way
users = [
    {"username": "alice", "password": "123456"},
    {"username": "bob", "password": "qwerty"},
]
```

The moment the database is breached (even via an accidental internal export of a backup), every user's password is laid bare. **And most people reuse the same password across multiple sites** — a leak in your database means other sites fall too.

**The correct approach: store a "salted hash," not the original.**

```python
import hashlib
import secrets

def hash_password(password):
    salt = secrets.token_hex(16)                      # a unique random salt per user
    h = hashlib.sha256((salt + password).encode()).hexdigest()
    return {"salt": salt, "hash": h}                  # store both salt and hash

def verify(password, record):
    h = hashlib.sha256((record["salt"] + password).encode()).hexdigest()
    return h == record["hash"]

pwd = "123456"
record = hash_password(pwd)
print("stored in DB:", record)

print("verify with correct password:", verify("123456", record))
print("verify with wrong password:", verify("wrong", record))
```

Output:

```
stored in DB: {'salt': 'a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6', 'hash': '8f3a...'}
verify with correct password: True
verify with wrong password: False
```

**Three key points**: the salt is random (defeats rainbow tables); the salt must be stored alongside the hash (verification needs the same salt); and each user gets a different salt.

## Crash Site 2: Storing Passwords with md5, Everyone Sharing One Salt

```python
# WRONG —— two classic mistakes
import hashlib

def bad_hash(password):
    return hashlib.md5(password.encode()).hexdigest()     # no salt + algorithm too weak

def shared_salt(password):
    return hashlib.md5(("COMMON_SALT" + password).encode()).hexdigest()  # salt is a hardcoded constant
```

What's wrong?

- **No salt**: an attacker can precompute a hash table for common passwords (a rainbow table) and match the originals instantly
- **Shared fixed salt**: everyone uses the same salt, so the rainbow table only needs to be computed once — equivalent to having no salt at all

**The salt must be random and unique per person.** `secrets.token_hex(16)` exists precisely for this — the `secrets` module provides cryptographically secure random numbers (we touched on it in lesson 09).

## Crash Site 3: sha256 Is Actually "Too Fast"

The algorithms in `hashlib` are designed for **speed**: a modern CPU can compute tens of millions of sha256 hashes per second. That's an advantage for "file verification," but a disaster for "storing passwords" — **an attacker can try millions of candidate passwords per second.**

Proper password storage should use **a slow hash with many iterations**, such as `bcrypt`, `scrypt`, or `argon2`. The standard library doesn't include these (you'd `pip install bcrypt`), so this lesson only establishes the principles:

- Verifying file integrity → `hashlib.sha256` (fast, just right)
- Storing user passwords → a slow-hash library (bcrypt / scrypt / argon2), with the work factor tuned high
- Signing / authentication → HMAC (the `hmac` module), paired with SHA-256 or above

## Crash Site 4: Comparing Hashes Directly with ==

```python
# WRONG —— timing attack
def verify(password, record):
    h = hashlib.sha256((record["salt"] + password).encode()).hexdigest()
    return h == record["hash"]          # string comparison short-circuits; time varies with prefix length
```

`==` is a "short-circuit comparison": it returns False the moment the first character mismatches. An attacker can **guess the correct hash one character at a time by measuring response-time differences** (this is a side-channel timing attack). **The fix is `hmac.compare_digest(a, b)`** — its comparison time is constant, unaffected by content.

```python
import hmac

a = "5d41402abc4b2a76b9719d911017c592"
b = "5d41402abc4b2a76b9719d911017c592"
print(hmac.compare_digest(a, b))        # True

# when verifying a password
def safe_verify(password, record):
    h = hashlib.sha256((record["salt"] + password).encode()).hexdigest()
    return hmac.compare_digest(h, record["hash"])
```

## Summary

- A hash = "arbitrary bytes → fixed-length fingerprint"; `hexdigest()` gives a hex string, `digest()` gives raw bytes
- For file integrity, use sha256 (md5/sha1 have collision attacks and are unfit for security scenarios)
- For large files, feed with `update()` in chunks — equivalent to a one-shot computation
- **Never store passwords in plain text**: store "random salt + salted hash," with a unique salt per user
- `hashlib` algorithms are too fast for password storage — use a slow hash (bcrypt/scrypt/argon2)
- Compare hashes with `hmac.compare_digest`, not `==`
