# When JSON Is Not Enough

> This lesson gives you a "boundary checklist": dates, binary data, circular references, tuples/sets — JSON cannot represent these. Learning to recognize them tells you when it is time to switch approaches.

## JSON Can Only Express Six Types

To recap: JSON only has object, array, string, number, true/false, and null. These six can combine into very complex structures, but **they have hard boundaries**.

When you try to serialize the following, you will get an immediate error:

```python
import json

# Dates
import datetime
json.dumps(datetime.date(2026, 9, 27))
# TypeError: Object of type date is not JSON serializable

# Datetime
json.dumps(datetime.datetime.now())
# TypeError

# Binary
json.dumps(b"\xe4\xbd\xa0")
# TypeError

# Sets
json.dumps({1, 2, 3})
# TypeError

# Custom objects (without default)
class User: pass
json.dumps(User())
# TypeError
```

All these errors say the same thing: **JSON has no corresponding data type**.

## Dates and Times: You Must Define Your Own Convention

Dates are the most common thing in business and the easiest to trip over in JSON. There are three common "serialization conventions":

```python
import json
import datetime

d = datetime.datetime(2026, 9, 27, 14, 30, 0)

# Plan A: ISO 8601 string (most recommended)
s1 = d.isoformat()
print(s1)                      # 2026-09-27T14:30:00

# Plan B: timestamp (seconds/milliseconds)
s2 = d.timestamp()             # float seconds
print(s2)

# Plan C: split into a dict of year, month, and day
s3 = {"year": 2026, "month": 9, "day": 27}
print(s3)
```

**ISO 8601 is the de facto standard**: `2026-09-27T14:30:00`, with `T` separating the date and time. Its advantages are that **humans can read it, programs can parse it, and it can express time zones**.

To deserialize it back:

```python
text = "2026-09-27T14:30:00"
back = datetime.datetime.fromisoformat(text)
print(back.year, back.month, back.day)      # 2026 9 27
```

## Crash Site: Concatenating Dates as Strings Makes Parsing Impossible

Alice invented her own format `"September 27, 2026"` and stored it in JSON:

```python
# WRONG
raw = '{"date": "September 27, 2026"}'
# How does the parsing end restore this to datetime? Only with a bunch of string splitting
```

The biggest problem with this "custom format" is that **no one knows how to parse it**. As soon as someone else takes over the code, they have to guess all over again.

**The correct approach**: unify on ISO 8601 — everyone recognizes it.

```python
import json
import datetime

def datetime_default(o):
    if isinstance(o, (datetime.datetime, datetime.date)):
        return o.isoformat()
    raise TypeError(f"Unsupported: {type(o)}")

data = {"event": "school starts", "date": datetime.date(2026, 9, 1)}
text = json.dumps(data, default=datetime_default)
print(text)            # {"event": "school starts", "date": "2026-09-01"}
```

## Binary Data: base64 Is the Standard Answer

Images, compressed archives, and encrypted content are all `bytes`. JSON is a text format and **cannot hold bytes**.

```python
import json

signature = b"\x00\x01\x02\xff\xfe\xfd"
json.dumps({"sig": signature})
# TypeError
```

**The standard approach: base64 encoding**, which converts bytes into a pure ASCII string:

```python
import base64
import json

raw_bytes = b"\x00\x01\x02\xff\xfe\xfd"

encoded = base64.b64encode(raw_bytes).decode("ascii")
print(encoded)                      # AAA=//79

text = json.dumps({"sig": encoded})
print(text)                         # {"sig": "AAA=//79"}

# Reading it back
back = json.loads(text)
decoded = base64.b64decode(back["sig"])
print(decoded)                       # b'\x00\x01\x02\xff\xfe\xfd'
```

`base64.b64encode` returns bytes, so you must `.decode("ascii")` to turn it into a string that can go into JSON. When reading, `b64decode` restores it.

**The cost**: base64 increases the size by about 1.37x. So for large amounts of binary data, a better approach is to store the file directly and put only the file path in the JSON.

## Circular References: JSON Simply Cannot Write Them

```python
import json

a = []
a.append(a)              # a contains a reference to itself

json.dumps(a)
```

Error:

```
ValueError: Circular reference detected
```

This is not a bug — it is **logically impossible to write out**: `a` is `[...]`, and its first element is itself, which would require writing `[[[[...` infinitely deep.

**Real-world circular references** usually involve objects referencing each other:

```python
class Node:
    def __init__(self, name):
        self.name = name
        self.parent = None

root = Node("root")
child = Node("child")
child.parent = root       # back-reference
```

Such structures cannot be `dumps`'d directly. **The solution**: during serialization, **store only the ID, not the reference**, or agree that "parent-child relationships are stored in only one direction."

## Tuples and Sets: Information Is Lost

```python
import json

t = (1, 2, 3)            # tuple: immutable
s = {1, 2, 3}            # set: unordered, deduplicated

text = json.dumps([t, list(s)])     # sets must be manually converted to list first
print(text)                          # [[1, 2, 3], [1, 2, 3]]

back = json.loads(text)
print(type(back[0]))                 # <class 'list'>  not tuple!
```

**Tuples** become lists and are no longer tuples when they return; **sets** must be manually converted to lists, and they also become lists when they return, with **no guarantee of order**.

If your business genuinely needs "immutable sequences" or "deduplicated sets," JSON itself cannot express this — you need to restore them according to a convention in `object_hook` (see the type-tag technique in Lesson 07).

## Crash Site: Using JSON as a Database Leads to a Crash with Huge Data Volumes

```python
import json

# Pretend this is a list of 1 million records
big = [{"id": i, "name": f"user{i}"} for i in range(1_000_000)]

# Serialize everything into memory
text = json.dumps(big)           # could占用 hundreds of MB of memory
```

**JSON is an "all-at-once load" format**: `json.load` reads the entire file into memory and turns it into an object in one go. When data reaches millions of records and several GB, this will directly cause an OOM (Out Of Memory) error.

**When should you switch approaches?**

| Need | Is JSON enough? | Better alternative |
|---|---|---|
| Config files (a few KB ~ a few MB) | Yes | JSON / YAML / TOML |
| API data transfer | Yes | JSON |
| Millions of records, querying needed | No | Database (SQLite/MySQL) |
| Big data streaming processing | No | Line-delimited JSONL / CSV / Parquet |
| Large binary files (images/video) | No | Store files directly + path index |
| Complex object reference relationships | No | Database or graph database |

## JSONL: A Streaming Alternative with One JSON Object Per Line

If your data consists of a large number of **independent records** and you want to use JSON, you can use the JSONL (JSON Lines) format: one JSON object per line, rather than one big array.

```python
import json

records = [
    {"id": 1, "name": "Alice"},
    {"id": 2, "name": "Bob"},
    {"id": 3, "name": "Carol"}
]

# Write as JSONL: one per line
with open("users.jsonl", "w", encoding="utf-8") as f:
    for r in records:
        f.write(json.dumps(r, ensure_ascii=False) + "\n")

# Can be read line by line without loading everything into memory
with open("users.jsonl", encoding="utf-8") as f:
    for line in f:
        obj = json.loads(line)
        print(obj["name"])
```

Output:

```
Alice
Bob
Carol
```

**Advantages**: it can be processed line by line with minimal memory usage; it supports append-only writes (no need to read the entire file before writing back); it is ideal for logs and export files.

**Cost**: it cannot be treated as a single large array and requires tooling support.

## Summary

- JSON has only six types; **dates, binary data, circular references, and tuples/sets cannot be expressed**
- Use **ISO 8601** for dates (`2026-09-27T14:30:00`) — readable by humans and parseable by programs
- Use **base64** to encode binary data into strings, at a cost of about 1.37x size increase
- Circular references cannot be serialized; you need to store IDs instead or use one-way references
- Tuples and sets become lists after a round trip — information is lost
- JSON is an **all-at-once load** format; for millions of records, consider a database or JSONL
- **JSONL** is a streaming format with one JSON object per line, ideal for logs and bulk exports
