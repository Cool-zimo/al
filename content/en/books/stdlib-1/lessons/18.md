# pickle Security Warning: Never Unpickle Untrusted Data

> This lesson covers exactly one thing, but it's the most critical security red line in the entire standard library: **if you can construct a pickle byte string, you can execute arbitrary code on the machine doing the deserialisation.** Don't believe it? This lesson demonstrates it live.

## The Scene First: A pickle That Pops Up a Calculator

The code below is the complete attack. Run it, and you'll see `"malicious code executed"` printed — and the "trigger" is nothing more than a single `pickle.loads`.

```python
import pickle

class Bomb:
    def __reduce__(self):
        # __reduce__ tells pickle: what callable to invoke on restore, with what arguments
        return (print, ("malicious code executed",))

b = Bomb()
data = pickle.dumps(b)        # looks like harmless bytes
print("bytes:", data[:30], "...")

pickle.loads(data)            # this is where print("malicious code executed") runs
```

Output:

```
bytes: b'\x80\x04\x95\x1a\x00\x00\x00\x00\x00\x00\x00\x8c\x05print\x94\x8c\x10 ...'
malicious code executed
```

**Note the full chain of causality**: the attacker only needs you to `loads` a byte string they provide. They need no access to your source code, no password, no other permissions whatsoever. The moment deserialisation happens, the callable returned by `__reduce__` is invoked.

## `__reduce__` Is a Back Door — and It's by Design

`__reduce__` is not a vulnerability; it's pickle's **official protocol** — it tells the serialiser "how to reconstruct this object." Reconstructable entry points include:

- Any function in any module: `os.system`, `subprocess.run`, `shutil.rmtree`...
- Any constructor: `int` (used as a callable), `exec`, `eval`...
- Attackers can chain calls, importing first and then executing

Try swapping `print` for something genuinely dangerous (**only on your own machine, and only when you fully understand the consequences**):

```python
import pickle
import os

class Bomb:
    def __reduce__(self):
        return (os.system, ("echo PWNED && id",))

data = pickle.dumps(Bomb())
pickle.loads(data)        # will execute a shell command
```

## Crash Site 1: Passing "User Uploads" Directly to loads

```python
# WRONG —— has happened countless times in real projects
import pickle

def load_user_session(uploaded_bytes):
    # "session file" uploaded by a user, deserialised directly
    return pickle.loads(uploaded_bytes)   # fatal
```

**No data from any external source should ever enter `pickle.loads`.** This includes, without limitation: network packets, HTTP request bodies, user-uploaded files, messages in a queue, return values from third-party APIs, and blob columns in a database "written by who-knows-who."

The only criterion that matters: **did the same trusted environment, running the same version of the code, produce this data via `dumps`?** If not, don't load it.

## Crash Site 2: Thinking "Inspecting the Bytes" Offers Protection

Some argue: "I'll check whether the byte string contains `os` before deciding whether to load it."

```python
# WRONG —— utterly pointless
import pickle

data = pickle.dumps({"safe": "data"})
if b"os" not in data and b"system" not in data:
    pickle.loads(data)
```

This doesn't work, for three reasons:

1. pickle opcodes can be encoded in multiple forms — `b"os"` is just one byte representation
2. An attacker can do `__import__('o'+'s')`, bypassing the string check via concatenation
3. **Once you load, the code has already executed** — a check that happens afterwards is meaningless

Protection can only happen **before** `loads`, and the most effective approach is simply "never load untrusted data."

## Crash Site 3: Thinking Switching to JSON Is Automatically Safe

"So I'll just use JSON?" — the direction is right, but don't assume too much. JSON itself won't execute code, but if your code does `eval()` or `getattr()` on a user-supplied string immediately after `json.loads`, you're still compromised. Real security comes from defending **both the data format and your processing logic**.

```python
import json

# WRONG
data = json.loads('{"op": "delete", "path": "/etc/passwd"}')
op = data["op"]
# using a user-supplied string for getattr or reflection is equally an injection vector
```

## Safe Alternatives

| Scenario | Recommendation |
|---|---|
| Exchanging data with external systems / front-ends / other languages | **JSON** (chapters 2–3), or MessagePack, Protobuf |
| Temporary on-disk storage within the same code, in a trusted environment | **pickle** (watch the protocol version) |
| Encryption needed, cross-language | JSON + signing (HMAC) or JWT |
| Long-term archival, with evolving versions | JSON / YAML + an explicit version field |

**If you absolutely must use pickle for cross-process communication** (e.g. multiprocessing, early Celery versions), make the channel a **trusted channel**: a local Unix socket, an authenticated queue, signature verification. Never expose pickle on a public internet port.

## So, Is Signed pickle OK?

It can be, but don't roll your own. Use `hmac` to sign the byte string, and verify the signature before loading on the receiving end:

```python
import pickle
import hmac
import hashlib

SECRET = b"a key that only I know"

def dump_signed(obj):
    raw = pickle.dumps(obj)
    sig = hmac.new(SECRET, raw, hashlib.sha256).digest()
    return sig + raw          # signature first, data after

def load_signed(signed):
    sig, raw = signed[:32], signed[32:]
    expect = hmac.new(SECRET, raw, hashlib.sha256).digest()
    if not hmac.compare_digest(sig, expect):
        raise ValueError("signature mismatch — data may have been tampered with")
    return pickle.loads(raw)

data = dump_signed({"user": "Alice"})
print(load_signed(data))                 # {'user': 'Alice'}

# tamper: flip one byte
bad = bytearray(data); bad[40] ^= 1
try:
    load_signed(bytes(bad))
except ValueError as e:
    print("caught:", e)
```

Output:

```
{'user': 'Alice'}
caught: signature mismatch — data may have been tampered with
```

**Note**: signing only guarantees "the data wasn't modified" — it does **not** guarantee "there's no bomb in the data." If the signing key and data key are both held by the same party, this is fine; but the moment you expose signing capability to the outside, the signature becomes meaningless. So **signing = authentication of source, not sanitisation**.

## Summary

- `pickle.loads` executes the `__reduce__` instructions embedded in the byte string — **it can run arbitrary code**. This is by design, not a bug
- Never unpickle data from the network, user uploads, third-party interfaces, or unknown blob columns in a database
- Inspecting byte content or maintaining a keyword blacklist is useless — **the only effective control is whether the source is trusted**
- Use JSON / MessagePack / Protobuf for external exchange; use pickle only in trusted internal environments
- When cross-process pickle is unavoidable, use trusted channels + HMAC signing; signing handles authentication, not sanitisation
