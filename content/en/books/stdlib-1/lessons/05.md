# Chinese Characters and Encoding: Why Files Become Garbled

> This lesson explains exactly why "reading and writing files produces garbled text." You will never again say "I just opened it casually" without being able to pinpoint whether the problem lies with UTF-8, GBK, or the BOM.

## Strings, Bytes, and Encoding: Three Concepts to Distinguish

There are two kinds of "text-related things" in Python:

```python
s = "Hello"            # str: a string, a sequence of "characters"
b = b"\xe4\xbd\xa0\xe5\xa5\xbd"   # bytes: a byte string, a sequence of "bytes"
```

`str` is for humans to read; `bytes` is for computers to store. The conversion between the two is called **encoding** and **decoding**:

```python
s = "Hello"
b = s.encode("utf-8")       # str -> bytes
print(b)                    # b'\xe4\xbd\xa0\xe5\xa5\xbd'

back = b.decode("utf-8")    # bytes -> str
print(back)                 # Hello
```

**What is stored on disk is always bytes**. When you `open()` a text file, Python must help you decode those bytes into a `str` — and this "how to decode" is precisely the encoding issue.

## The Default Encoding of `open`: A Cross-Platform Landmine

```python
# This might cause problems on Windows
open("data.txt", "w").write("Hello")
```

On Linux/macOS, `open()` defaults to UTF-8; on **Chinese-language Windows, the default is GBK**.

```python
import sys
print(sys.platform)         # win32 / linux / darwin
# On Windows: the default encoding for open is 'cp936' (i.e., GBK)
```

The consequence: you write a UTF-8 file on Windows but interpret it with GBK, and the result is garbled text — things like "æˆ‘ä»¬" or "����".

**The solution: always specify the encoding explicitly**:

```python
with open("data.txt", "w", encoding="utf-8") as f:
    f.write("Hello")

with open("data.txt", encoding="utf-8") as f:
    print(f.read())         # Hello
```

The same applies to `json.dump` and `json.load` — they are built on top of `open`, and the encoding is determined by the arguments you pass to `open`.

## Crash Site: A GBK File Read as Garbled on Linux

Alice saved a `users.json` file in Windows Notepad with the content `{"name": "Alice"}`. Notepad saves in GBK by default. Bob reads it on a Linux server using the default UTF-8:

```python
import json

# Assume content is bytes read in GBK, simulating a file saved by Windows Notepad
raw_gbk = "{\"name\": \"Alice\"}".encode("gbk")

# WRONG: decoding as UTF-8
s = raw_gbk.decode("utf-8")
print(s)
```

Error:

```
UnicodeDecodeError: 'utf-8' codec can't decode byte 0xd5 in position ...: invalid continuation byte
```

**How to fix it**: decode with the correct encoding, or simply resave the file as UTF-8.

```python
# Correct: decode using the actual encoding
s = raw_gbk.decode("gbk")
data = json.loads(s)
print(data)                 # {'name': 'Alice'}

# Alternatively: specify an errors handling policy when reading (tolerant but not recommended, as it loses characters)
s2 = raw_gbk.decode("utf-8", errors="replace")
print(s2)                   # {"name": "??"}  garbled characters are replaced with ?
```

## Crash Site: The BOM Makes the First Key Mysteriously Unreadable

The BOM (Byte Order Mark, `\ufeff`) is three bytes that some editors (especially Windows Notepad's "Save as UTF-8") secretly add to the **beginning of a file** to mark "this is a UTF-8 file."

```python
# Simulate a file with a BOM
bom_json = "\ufeff{\"name\": \"Alice\"}"

import json
data = json.loads(bom_json)
print(data)                 # It can actually be parsed; the key is normal

# But if you are reading line by line or doing string processing yourself:
first_char = bom_json[0]
print(repr(first_char))     # '\ufeff'  an invisible character
print(first_char == "{")    # False
```

The most treacherous scenario with a BOM is when **you do your own parsing** — an invisible `\ufeff` at the beginning causes all your checks and slicing to be off by one.

```python
# WRONG: directly matching keys against a string with a BOM
line = "\ufeffadmin: 1"
if line.startswith("admin"):
    print("is admin")
else:
    print("is not")            # this branch is taken, because the first character is \ufeff
```

**How to fix it**: use `encoding="utf-8-sig"` when calling `open()`, which automatically consumes the BOM:

```python
with open("with_bom.json", "w", encoding="utf-8-sig") as f:
    f.write("\ufeff")        # simulate a pre-existing BOM
    f.write('{"name": "Alice"}')

with open("with_bom.json", encoding="utf-8-sig") as f:
    data = json.load(f)      # automatically skips the BOM
print(data)                  # {'name': 'Alice'}
```

## The Relationship Between `ensure_ascii` and Encoding

To recap: `ensure_ascii=False` controls **whether strings are escaped**, while encoding controls **what bytes the characters are ultimately stored as**.

```python
import json

data = {"city": "London"}

# Plan A: ensure_ascii=True (default) + store as UTF-8
t1 = json.dumps(data)                        # '{"city": "\\u6d6e\\u6566"}'
t1.encode("utf-8")                           # pure ASCII bytes, readable by any system

# Plan B: ensure_ascii=False + store as UTF-8 (recommended)
t2 = json.dumps(data, ensure_ascii=False)    # '{"city": "London"}'
t2.encode("utf-8")                           # contains Chinese bytes, requires UTF-8 decoding
```

**Both plans are correct and can be understood by any JSON parser** (the JSON standard mandates interpretation as Unicode). The difference is:

- Plan A: the file is all ASCII, with the best compatibility, but it is unreadable to humans
- Plan B: Chinese is clear, but the reader must know it is UTF-8

As long as **the writer and reader use the same encoding** (both UTF-8), Plan B is the optimal solution.

## Crash Site: Misusing the `errors` Parameter Causes Silent Data Corruption

```python
# WRONG: using errors="ignore" to swallow undecodable bytes
with open("data.txt", "rb") as f:
    raw = f.read()
text = raw.decode("utf-8", errors="ignore")   # bad bytes are simply discarded
print(text)        # characters may be missing, and you would never know
```

Both `errors="ignore"` and `errors="replace"` are "fault-tolerant" measures, but they **silently corrupt data**. Never use them during debugging, as they make problems even harder to find.

```python
# Better to let it error out
text = raw.decode("utf-8")   # if decoding fails, error out early and fix early
```

## Hands-On: Writing a Cross-Platform JSON Read/Write Utility

```python
import json
import os

def read_json(path, default=None):
    """Read JSON. Return default if the file does not exist; handle BOM automatically; use UTF-8 encoding."""
    if not os.path.exists(path):
        return default
    with open(path, encoding="utf-8-sig") as f:
        return json.load(f)

def write_json(obj, path):
    """Write JSON. Chinese is readable, indented, UTF-8 without BOM."""
    with open(path, "w", encoding="utf-8") as f:
        json.dump(obj, f, ensure_ascii=False, indent=2)

# Usage
profile = {"name": "Alice", "city": "London", "hobbies": ["coding", "basketball"]}
write_json(profile, "profile.json")

loaded = read_json("profile.json")
print(loaded["name"], "from", loaded["city"])
```

Output:

```
Alice from London
```

This utility function covers every key point in this chapter: `utf-8-sig` handles the BOM, `ensure_ascii=False` keeps Chinese readable, `indent=2` keeps the format clean, and `encoding="utf-8"` ensures cross-platform consistency.

## Summary

- `str` is characters, `bytes` is bytes; `encode` encodes, `decode` decodes
- **What is stored on disk is always bytes** — write with an encoding, read with the same encoding
- Windows defaults to GBK, Linux/macOS default to UTF-8; always specify `encoding="utf-8"` for cross-platform work
- **BOM** is an invisible `\ufeff` at the start of a file; use `encoding="utf-8-sig"` to skip it automatically
- `ensure_ascii=False` controls "whether to escape"; encoding controls "what bytes to store" — they are orthogonal
- `errors="ignore"/"replace"` silently lose data; do not use them during debugging
- Wrapping `read_json`/`write_json` to handle encoding and BOM uniformly is a project-level best practice
