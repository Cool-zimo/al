# fractions: Exact Computation with Fractions, Avoiding Float Error

> When a business deals in "ratios," "recipes," or "allocations," floats drift further off the mark with every calculation. This lesson gets you fluent with `fractions.Fraction` and spells out the pitfall of mixing it with floats.

## Basic Fraction Usage: Numerator and Denominator, Straightforward

The `fractions` module provides `Fraction`, which represents a fraction using two integers — never subject to binary truncation.

```python
from fractions import Fraction

a = Fraction(1, 3)
b = Fraction(2, 5)
print(a)            # 1/3
print(a + b)        # 11/15
print(float(a))     # 0.3333333333333333
```

Output:

```
1/3
11/15
0.3333333333333333
```

**The key point: in `Fraction(n, d)`, both n and d are integers** — writing `Fraction(1, 3)` is far more reliable than `1/3`.

## String Construction Works Too, and Reduces Automatically

`Fraction` supports construction from strings, and **reduces automatically:**

```python
from fractions import Fraction

print(Fraction("2/4"))      # 1/2
print(Fraction("0.25"))     # 1/4
print(Fraction(4, 6))       # 2/3
print(Fraction(0, 1))       # 0
```

Output:

```
1/2
1/4
2/3
0
```

`Fraction(4, 6)` is reduced automatically to `2/3` — the denominator has no common factor left.

## Crash Site 1: Mixing Fraction with float Yields a float

This is the biggest trap. **The moment a float appears in an operation, the result becomes a float**, and the fraction's precision is lost on the spot:

```python
from fractions import Fraction

a = Fraction(1, 3)
# WRONG: adding a float
result = a + 0.5
print(result)
print(type(result))
```

Output:

```
0.8333333333333333
<class 'float'>
```

The result is a `float`! Per Python's rules, the result of an operation involving a `Fraction` and a `float` is promoted to float, and all exactness is lost.

```python
from fractions import Fraction

a = Fraction(1, 3)
# correct: use Fraction throughout
result = a + Fraction(1, 2)
print(result)            # 5/6
print(type(result))      # <class 'fractions.Fraction'>
```

## Crash Site 2: Fraction(float) Inherits float Error

Constructing a `Fraction` from a float carries the float's binary error in unchanged:

```python
from fractions import Fraction

# WRONG: Fraction(0.1) carries in the float error
print(Fraction(0.1))
```

Output:

```
3602879701896397/36028797018963968
```

That denominator is deeply strange, because `0.1` itself isn't exact. The correct approach is to pass a string:

```python
from fractions import Fraction

print(Fraction("0.1"))   # 1/10
```

**Same principle as `Decimal`: when a decimal comes in from outside, construct from a string.**

## When It Beats Float: Exact Ratios

Use `Fraction` when you need an **exact ratio, recipe, or allocation** — the result is always an exact fraction.

```python
from fractions import Fraction

# recipe: 3 parts flour to 5 parts water — how much water for 2 parts flour?
flour = Fraction(3)
water = Fraction(5)
ratio = water / flour           # 5/3
need = ratio * 2                # 10/3
print(need)                     # 10/3
print(f"need {float(need):.2f} parts water")
```

Output:

```
10/3
need 3.33 parts water
```

With float, computing `5/3 * 2` gives an approximation; `Fraction` stays exact throughout and only converts to float when you need to display it.

## When Not to Use It: High-Frequency, Bulk Computation

A `Fraction`'s denominator grows without bound, getting slower and more memory-hungry the longer you compute. **For CPU-intensive pure numerical simulation, stick with float or Decimal.**

```python
from fractions import Fraction

# repeated multiplication makes the denominator explode
x = Fraction(1, 2)
for _ in range(10):
    x *= Fraction(3, 2)
print(x)        # 59049/1024
```

Output:

```
59049/1024
```

That huge denominator in `59049/1024` is computationally expensive. **The decision rule: use `Fraction` for "exact ratios," `float` for "fast / memory-efficient," and `Decimal` for "money accurate to the penny."**

## Common Operations at a Glance

| Operation | Syntax | Notes |
| --- | --- | --- |
| Construct | `Fraction(1, 3)` / `Fraction("0.25")` | integer pair or string |
| Reduce | Automatic | internal gcd handling |
| Convert to float | `float(f)` | for display |
| Convert to int | `f.numerator // f.denominator` | floor division |
| Numerator | `f.numerator` | attribute |
| Denominator | `f.denominator` | attribute |
| Limit denominator | `f.limit_denominator(100)` | find an approximate simple fraction |

`limit_denominator` is especially handy for "turning a float result back into a nice fraction":

```python
from fractions import Fraction

x = Fraction(355, 113)
print(x)                            # 355/113
print(x.limit_denominator(10))      # 3 = approximately 3.14159
```

## Summary

- `Fraction(n, d)` uses two integers to represent a fraction and **reduces automatically**
- Supports string construction `Fraction("0.25")` for exact results
- **Mixing with float produces a float**, losing all exactness — use Fraction throughout
- `Fraction(float)` inherits float error — construct external decimals from strings
- Great for exact ratios / recipes / allocations; poor fit for high-frequency bulk numerics
- Comparison: exact ratios → Fraction, money → Decimal, general numerics → float
