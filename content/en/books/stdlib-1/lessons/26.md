# Lesson 26 · The Data Pipeline Toolkit: Project Design

> Putting every tool from the first 25 lessons into one real project — a command-line data pipeline that actually runs.

## Why Build This Project

In the previous 25 lessons you've learned to read and write JSON, CSV, and INI, to compute money with `decimal`, manage state with `enum`, and carry structure with `dataclasses`. But these are scattered tools. **In real development they have to be strung together into a pipeline** — a file flows from ingestion to cleaning to output, and if anything breaks along the way, the whole program must not come crashing down.

Alice works in data support at an e-commerce company in Manchester, processing data from three departments every day:

- JSON from the engineering team (API exports)
- CSV from the finance team (saved from Excel)
- INI from the operations team (manually maintained config tables)

The formats differ, but they all describe the same thing — **transaction records**. Alice needs to read them in, unify them into one internal structure, clean and validate them, then output a uniform report.

That's exactly what we're building: **a data pipeline toolkit.**

## The Pipeline's Four-Layer Structure

A robust pipeline must be layered. Each layer has a single responsibility, and none interferes with the others:

```
┌─────────────┐
│ load layer  │  JSON / CSV / INI → list[dict]
├─────────────┤
│ norm layer  │  list[dict] → list[Record]
├─────────────┤
│ check layer │  validate each record → (passed_list, failed_list)
├─────────────┤
│ dump layer  │  passed_list → JSON / CSV file
└─────────────┘
```

**Why layers are mandatory:** because each layer has a different *reason to change*:

- The load layer changes because "a new format arrived" (say, XML tomorrow)
- The check layer changes because "the business rules changed" (say, the amount threshold rose from 0.01 to 1)
- The dump layer changes because "the boss wants a different report layout"

If all four layers live in one function, changing any one of them means re-reading the entire function. With layers, **each layer can be tested and replaced independently.**

## A Unified Internal Data Structure

The three input formats converge on one shared structure — `list[dict]`:

```python
# regardless of JSON / CSV / INI, this is what everything becomes:
records = [
    {"id": "T001", "amount": "19.90", "status": "paid", "qty": 2},
    {"id": "T002", "amount": "5.00",  "status": "pending", "qty": 1},
]
```

**Every dict's keys are fixed as `id` / `amount` / `status` / `qty`.** The load layer is responsible for "translating" each format's field names into this standard set. For example, CSV might use `order_no,amount,status,quantity`, while INI might use `id = T001` — the load layer maps them all to `id/amount/status/qty`.

This step is called **normalisation**, and it's the soul of the pipeline.

## Carrying Records with a Dataclass

A dict is flexible but error-prone — a misspelled key only blows up at runtime. A dataclass locks the structure down:

```python
from dataclasses import dataclass
from decimal import Decimal
from enum import Enum

class Status(Enum):
    PENDING = "pending"
    PAID = "paid"
    SHIPPED = "shipped"

@dataclass
class Record:
    id: str
    amount: Decimal
    status: Status
    qty: int
```

`Record` is our **domain model**. All business logic (validation, calculation, transformation) revolves around it, never tangled up with dict keys.

## Why Not One Giant Function

```python
# WRONG: every concern crammed together
def process(filepath):
    # check extension, open file, parse, transform, validate, output...
    # 200 lines
    pass
```

This approach has three fatal flaws:

1. **Untestable** — to test the validation logic you must prepare a real file
2. **Unreusable** — a new input format means rewriting this function
3. **Hard to locate failures** — when an error fires on line 150, you don't know whether parsing or validation broke

The right approach is one function per layer, each doing exactly one thing, each callable and testable on its own.

## What This Project Delivers

By the end of this chapter you'll have a complete, runnable command-line tool:

```bash
python pipe.py input.json output.csv
python pipe.py orders.csv report.json
python pipe.py data.ini result.csv
```

It will auto-detect the input format, clean and validate, produce output, and give you a validation report telling you which records had problems.

## Summary

- A data pipeline has four layers: load → transform → validate → output, each independently replaceable
- The unified internal structure is `list[dict]`, with keys fixed to the standard names `id/amount/status/qty`
- Use a dataclass to carry the domain model, avoiding dict key typos
- Layering exists for testability, reusability, and easy fault localisation
- The final form of this project is a command-line tool that auto-detects formats and runs the full flow

## Crash Site 1: A Dict Key Typo Only Blows Up at Runtime

```python
from dataclasses import dataclass
from decimal import Decimal
from enum import Enum

class Status(Enum):
    PENDING = "pending"
    PAID = "paid"

@dataclass
class Record:
    id: str
    amount: Decimal
    status: Status
    qty: int

raw = {"id": "T001", "amount": "19.90", "status": "paid", "qty": 2}
# WRONG: hand-written dict lookup with a typo
# print(raw["amout"])    # KeyError: 'amout'
```

**Once you switch to a dataclass, `r.amount` with a typo gets flagged by your IDE at development time**, whereas `raw["amout"]` only fails at runtime. That's why you should convert from dict to domain model as early as possible.

## Crash Site 2: Constructing Decimal Directly from float

```python
from decimal import Decimal

# WRONG
d = Decimal(19.90)
print(d)
# correct
print(Decimal("19.90"))
```

Output:

```
19.9000000000000003552713678800500929355621337890625
19.90
```

**Always construct Decimal from a string when the data comes from outside** — that's the lesson from chapter 5, and it applies here too: the moment an amount comes in from JSON or CSV, it must become `Decimal(str(...))`.
