# decimal: Why £0.1 + £0.2 Does Not Equal £0.3

> This lesson settles, once and for all, the question of "why you must never use float for money." You'll see the `0.1 + 0.2` trap for yourself, and learn to do it right with `decimal.Decimal` — **construct with strings, never floats.**

## The Classic Float Trap: 0.1 + 0.2 ≠ 0.3

A quick recap (touched on in lesson 03, but explained fully here).

```python
a = 0.1 + 0.2
print(a)              # 0.30000000000000004
print(a == 0.3)       # False
```

Why? Because computers store decimals in binary, and `0.1` is a **repeating binary fraction** — storing it in a 64-bit float necessarily involves truncation. After ten additions, the error is enough to break your reconciliation.

**Where it hurts**: the error doesn't show up immediately; it **only surfaces once it has accumulated to a certain magnitude** — potentially three months after launch, after millions of transactions have run. So "I tried a few numbers and they all worked" doesn't count as validation.

## Decimal: Exact Computation in Base Ten

The `decimal` module stores decimals in **base ten** rather than binary, with as many digits as you need — no binary truncation.

```python
from decimal import Decimal

a = Decimal("0.1") + Decimal("0.2")
print(a)              # 0.3
print(a == Decimal("0.3"))   # True
```

Output:

```
0.3
True
```

Clean and decisive.

## Crash Site 1: Decimal(0.1) Is Wrong

This is the easiest mistake to make, and the most insidious. `Decimal(0.1)` **preserves the float's error first, then wraps that error in a Decimal** — garbage in, garbage out.

```python
from decimal import Decimal

print(Decimal(0.1))          # 0.1000000000000000055511151231257827021181583404541015625
print(Decimal("0.1"))        # 0.1
```

Output:

```
0.1000000000000000055511151231257827021181583404541015625
0.1
```

**Remember the rule: when an amount comes in from outside, always construct with a string — `Decimal("19.90")`. Only use `Decimal(1990)` when you're certain you're dealing with integers (e.g. storing in "pence").**

```python
from decimal import Decimal

# correct
price = Decimal("19.90")
qty = 3
total = price * qty
print(total)          # 59.70

# also correct: store all amounts in "pence" as integers
pence = Decimal(1990) * Decimal(3) / Decimal(100)
print(pence)          # 59.70
```

## Crash Site 2: Division Produces an Infinite Decimal; Insufficient Precision Raises

```python
from decimal import Decimal

# WRONG: non-terminating division at default precision
Decimal(1) / Decimal(3)
```

Output:

```
Decimal('0.3333333333333333333333333333')
```

It looks fine, but if you compute `1 / 3 * 3` you'd naively expect to get back to 1. And **if the context precision has been reduced**, it raises `DivisionByZero` or `InvalidOperation`. More importantly: **without a cap, division can produce infinitely many digits.**

```python
from decimal import Decimal, getcontext

getcontext().prec = 4          # temporarily set precision to 4 digits
try:
    print(Decimal(1) / Decimal(3))
except Exception as e:
    print(type(e).__name__, e)

# restore default precision
getcontext().prec = 28
```

Output:

```
DivisionByZero [<class 'decimal.DivisionImpossible'>]
```

(The exact exception depends on the precision and rounding mode, but the core point is "insufficient precision raises an error.")

## quantize: Rounding the Result "to the Penny"

After computing an amount, you must "land it on pence" — you can't have `59.7000001` or an infinitely long result. Use `quantize` to specify the precision:

```python
from decimal import Decimal

price = Decimal("19.876")
qty = Decimal("3")
total = price * qty
print("raw:", total)                 # 59.628

rounded = total.quantize(Decimal("0.01"))   # round to pence
print("to pence:", rounded)                  # 59.63
```

The argument `Decimal("0.01")` is the template for "how precise I want to be" — `"0.1"` means tens of pence, `"0.01"` means pence, `"0.0001"` means ten-thousandths.

## Crash Site 3: round Uses "Banker's Rounding"

Python's `round` uses **banker's rounding** (round half to even): 5 rounds towards the nearest even number, to reduce cumulative bias across large numbers of statistics. But banker's rounding **is not the same as "round half up":**

```python
from decimal import Decimal, ROUND_HALF_UP

print(round(Decimal("1.25"), 1))   # 1.2  ← banker's: .25 rounds toward the even 1.2
print(round(Decimal("1.35"), 1))   # 1.4  ← .35 rounds toward the even 1.4

# to get a true "round half up", specify it explicitly
print(Decimal("1.25").quantize(Decimal("0.1"), rounding=ROUND_HALF_UP))   # 1.3
print(Decimal("1.35").quantize(Decimal("0.1"), rounding=ROUND_HALF_UP))   # 1.4
```

Output:

```
1.2
1.4
1.3
1.4
```

**For business "round half up," use `quantize(..., rounding=ROUND_HALF_UP)` — don't rely on `round`.**

## The Pitfall of Rounding Negative Numbers

Rounding rules can be counter-intuitive for negatives:

```python
from decimal import Decimal, ROUND_HALF_UP, ROUND_HALF_EVEN

print(Decimal("-1.5").quantize(Decimal("1."), rounding=ROUND_HALF_UP))    # -1.5 → -2
print(Decimal("-1.5").quantize(Decimal("1."), rounding=ROUND_HALF_EVEN))  # -1.5 → -2
```

`ROUND_HALF_UP` rounds "away from zero," while `ROUND_HALF_EVEN` rounds toward even. When handling refunds or negative balances, confirm which accounting convention you're using.

## In Practice: Computing a Tax-Inclusive Order Total

```python
from decimal import Decimal, ROUND_HALF_UP

def order_total(unit_price, qty, tax_rate):
    """Tax-inclusive amount, rounded to pence using round half up."""
    price = Decimal(unit_price)
    subtotal = price * qty
    tax = subtotal * Decimal(tax_rate)
    total = subtotal + tax
    return total.quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)

print(order_total("19.90", 3, "0.13"))    # unit price £19.90, qty 3, tax 13%
print(order_total("9.99", 7, "0.06"))
```

Output:

```
67.40
74.03
```

## Summary

- Floats store decimals in binary, so `0.1+0.2` has truncation error — never touch float in money scenarios
- **Always construct Decimal from a string**: `Decimal("0.1")` is right, `Decimal(0.1)` is wrong
- `quantize(Decimal("0.01"))` rounds the result to pence; `"0.1"` is tens of pence, `"0.01"` is pence
- `round` uses banker's rounding — **for business "round half up," use `ROUND_HALF_UP`**
- Division can produce infinitely many digits, so `quantize` before persisting; confirm the accounting convention when negatives are involved
