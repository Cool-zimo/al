# The Type Mapping Table: What Converts and What Crashes

> This lesson explains the type conversion rules between Python and JSON. If you do not memorize them, you will get bugs: `(1, 2)` goes in and comes back as `[1, 2]`.

## One Table for the Bidirectional Mapping

JSON has only six data types, while Python has far more than six. So the conversion is not a "one-to-one correspondence" — it is **map what you can,报错 on what you cannot**.

| Python → JSON | JSON → Python |
|---|---|
| `dict` | `object` → `dict` |
| `list` | `array` → `list` |
| `str` | `string` → `str` |
| `int`, `float` | `number` → `int` (no decimal) / `float` (has decimal) |
| `True` / `False` | `true` / `false` → `True` / `False` |
| `None` | `null` → `None` |

In other words, a JSON `number` may come back as `int` or `float`, depending on whether it has a decimal point. This rarely matters in business logic, but if you use `type()` for strict checks, keep it in mind.

## Crash Site: Tuples Become Lists

This is the most classic example of a "lossy conversion":

```python
import json

t = (1, 2, 3)
print("Original type:", type(t))          # <class 'tuple'>

text = json.dumps(t)
print("Serialized result:", text)          # [1, 2, 3]

back = json.loads(text)
print("Type after restore:", type(back))    # <class 'list'>
print("Value after restore:", back)          # [1, 2, 3]
```

**Tuples have no corresponding type in JSON**, so they can only be treated as arrays, exiting as the list `[1, 2, 3]` and naturally coming back as a `list`.

If your code relies on "this is a tuple, it cannot be modified," that guarantee disappears after a single JSON round trip:

```python
point = (3, 4)
data = json.loads(json.dumps(point))
data.append(5)          # succeeds! a tuple should be immutable
print(data)             # [3, 4, 5]
```

**How to avoid this**: manually convert back to a tuple between serialization and deserialization, or simply use lists throughout your business logic.

```python
def tuple_roundtrip(t):
    return tuple(json.loads(json.dumps(t)))

print(tuple_roundtrip((3, 4)))      # (3, 4), still a tuple
```

## Crash Site: Dictionary Keys Must Be Strings or Integers

JSON specifies that object keys **must be strings**. Python dictionary keys can be integers, floats, or even tuples, but once you `dumps` them, non-string keys cause problems:

```python
import json

# Integer keys: silently coerced to strings
d = {1: "one", 2: "two"}
text = json.dumps(d)
print(text)              # {"1": "one", "2": "two"}

back = json.loads(text)
print(back)              # {'1': 'one', '2': 'two'}  ← keys are now strings "1"
print(back[1])           # KeyError: 1  (you wanted the integer 1, but got the string "1")
```

**Integer keys are silently converted to strings**, and when they come back, using an integer to look them up raises a `KeyError`. This bug is incredibly sneaky because the code does not crash — it just cannot find the value.

```python
# Tuples as keys: outright error, cannot be dumped at all
d2 = {(1, 2): "coordinates"}
json.dumps(d2)
```

Error:

```
TypeError: keys must be str, int, float, bool or None, not tuple
```

## Crash Site: Boolean Values and `None` — Watch the Capitalization

Python uses `True`/`False`/`None`; JSON uses `true`/`false`/`null` — all lowercase:

```python
import json

# WRONG: used Python syntax when hand-writing a JSON string
raw = '{"paid": True, "note": None}'
json.loads(raw)
```

Error:

```
JSONDecodeError: Expecting value: line 1 column 9 (char 8)
```

The parser expected a JSON value (`true`/`false`/`null`/string/number) at the position of `True`, and got completely confused by the capital `T`.

**The correct approach is still to let the library handle it**: `json.dumps({"paid": True, "note": None})` will output `{"paid": true, "note": null}`.

## Types JSON Simply Cannot Handle

The following common Python types will **raise an error** if you try to `dumps` them directly:

| Python type | Error |
|---|---|
| `set` | `TypeError: Object of type set is not JSON serializable` |
| `datetime.date` / `datetime.datetime` | same as above |
| Instances of custom classes | same as above |
| `bytes` | same as above |
| Structures with circular references | `ValueError: Circular reference detected` |

```python
import json

tags = {"python", "json", "tutorial"}
json.dumps(tags)
```

Error:

```
TypeError: Object of type set is not JSON serializable
```

What can you do? **Convert it to a type it can handle**. A set can become a list:

```python
tags = {"python", "json", "tutorial"}
print(json.dumps(list(tags)))       # ["json", "tutorial", "python"]  (order not guaranteed)
```

> Date and custom object serialization are covered in Lesson 07 using the `default=` parameter.

## Numbers: Precision and Boundary Pitfalls

```python
import json

# Floating-point precision issues still apply
d = {"pi": 0.1 + 0.2}
print(json.dumps(d))        # {"pi": 0.30000000000000004}

# The JSON standard places no limit on number size, but JS numbers are double-precision floats
big = 10 ** 20
print(json.dumps(big))      # 100000000000000000000  (integers are fine)
```

**Note**: Python's `int` has arbitrary precision, but if a large JSON integer is read by JavaScript, anything beyond 2^53 loses precision. For precise large integers (such as order numbers or Snowflake IDs), it is recommended to pass them as strings:

```python
order = {"order_id": "79228162514264337593543950336"}   # strings are safest
print(json.dumps(order))
```

## Hands-On: Analyzing Type Changes Before and After a Round Trip

```python
import json

data = {
    "name": "Alice",
    "scores": (88, 92, 95),          # tuple
    "tags": {"vip", "new"},          # set
    "info": {"age": 20}              # nested dict
}

# Cannot dumps directly — tags is a set, will error
# Preprocess: convert the set to a list
data["tags"] = list(data["tags"])

text = json.dumps(data)
print("Outgoing string:", text)

back = json.loads(text)
print("Type of scores after return:", type(back["scores"]))   # list, no longer tuple
print("Type of tags after return:", type(back["tags"]))       # list
print("Type of info after return:", type(back["info"]))       # dict, normal
```

Output:

```
Outgoing string: {"name": "Alice", "scores": [88, 92, 95], "tags": ["new", "vip", "tutorial"], "info": {"age": 20}}
Type of scores after return: <class 'list'>
Type of tags after return: <class 'list'>
Type of info after return: <class 'dict'>
```

**Conclusion**: a JSON round trip is **lossy**. Structures like tuples and sets that "have no corresponding type" all come back as lists. Keep this in mind when designing your data structures.

## Summary

- JSON has six types: object, array, string, number, true/false, null
- **Tuples → lists**, and the immutability guarantee disappears after a round trip
- **Integer keys → string keys**; using an integer to look them up afterward raises `KeyError`
- **Tuples/sets/dates/custom objects/circular references** will all报错 if you `dumps` them directly
- Large integers (order numbers, etc.) should be passed as strings to avoid precision loss on the JS side
- A JSON round trip is a **lossy** conversion; design your data structures with this in mind
- Hand-writing JSON strings will almost always lead to errors — always delegate to the `json` module
