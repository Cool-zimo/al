# Lesson 29 · The Data Pipeline: Output and Logging

> The dump layer writes the cleaned data out; logging tells developers what happened inside the program.

## Output to JSON

The passed records need to be written back to a file. First, convert them to a serialisable format:

```python
import json
from decimal import Decimal
from enum import Enum

class Status(Enum):
    PENDING = "pending"
    PAID = "paid"
    SHIPPED = "shipped"

def record_to_dict(rec):
    """Convert a standard dict into a JSON-serialisable dict"""
    return {
        "id": rec["id"],
        "amount": str(rec["amount"]),       # Decimal → str
        "status": rec["status"],            # already a string
        "qty": int(rec["qty"]),
    }

def dump_json(records, filepath):
    data = [record_to_dict(r) for r in records]
    with open(filepath, "w", encoding="utf-8") as f:
        json.dump(data, f, ensure_ascii=False, indent=2)
```

**`record_to_dict` handles the type conversion**: Decimal to str, Enum to its value. As lesson 25 emphasised — `json.dump` doesn't understand custom types.

## Output to CSV

```python
import csv

def dump_csv(records, filepath):
    fieldnames = ["id", "amount", "status", "qty"]
    with open(filepath, "w", encoding="utf-8", newline="") as f:
        writer = csv.DictWriter(f, fieldnames=fieldnames)
        writer.writeheader()
        for rec in records:
            writer.writerow(record_to_dict(rec))
```

`csv.DictWriter` requires the `fieldnames` parameter. Call `writeheader()` once for the header row, then `writerow` for each record.

## Dispatching Output by Extension

Symmetrically with the load layer, the dump layer also dispatches by extension:

```python
def dump(records, filepath):
    if filepath.endswith(".json"):
        dump_json(records, filepath)
    elif filepath.endswith(".csv"):
        dump_csv(records, filepath)
    else:
        raise ValueError(f"unsupported output format: {filepath}")
```

**Input and output formats can differ** — read JSON, write CSV, for example. That's exactly where the pipeline's flexibility comes from.

## Why `print` Isn't Enough

As the pipeline runs, your terminal fills up with information:

- How many files were read
- The validation result of each record
- Final pass/fail counts
- Detailed stack traces when something goes wrong

If you use `print` for all of it, you get an undifferentiated mess. **What you need is a logging system with levels, formatting, and toggles** — that's `logging`.

```python
import logging

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s [%(levelname)s] %(message)s",
    datefmt="%H:%M:%S",
)
logging.info("started processing data")
logging.warning("3 records have format issues")
logging.error("cannot open file data.json")
```

Output:

```
14:30:05 [INFO] started processing data
14:30:05 [WARNING] 3 records have format issues
14:30:05 [ERROR] cannot open file data.json
```

**Timestamps, levels, formatting** — that's what `print` can't give you.

## The Five Log Levels

| Level | Numeric Value | Purpose |
|------|------|------|
| `DEBUG` | 10 | Development debugging detail — hidden by default |
| `INFO` | 20 | Normal flow information |
| `WARNING` | 30 | Non-fatal but worth noting |
| `ERROR` | 40 | Something broke, but the program keeps running |
| `CRITICAL` | 50 | Fatal error — the program is about to crash |

```python
import logging

logging.debug("parsing line 3")       # hidden by default
logging.info("read 100 records")     # visible
logging.warning("amount field missing")       # visible
logging.error("JSON parse failed")        # visible
```

**`basicConfig(level=...)` controls the minimum visible level.** At `INFO`, `DEBUG` is filtered out; at `DEBUG`, everything shows.

## Common basicConfig Parameters

```python
import logging

logging.basicConfig(
    level=logging.DEBUG,                    # minimum visible level
    format="%(asctime)s %(levelname)s %(name)s - %(message)s",
    datefmt="%Y-%m-%d %H:%M:%S",           # time format
    filename="pipeline.log",               # output to file instead of terminal
    filemode="a",                          # append mode
)
```

| Parameter | Purpose |
|------|------|
| `level` | Minimum visible level |
| `format` | Log format string |
| `datefmt` | Time format |
| `filename` | Output to file (terminal if omitted) |
| `filemode` | File mode: `w` overwrites / `a` appends |

## For Users vs For Developers

**This is the core principle of log design:**

- Information **for the user** → `print()` or a dedicated output function — concise and clear
- Information **for the developer** → `logging` — levelled and contextual

```python
import logging

logging.basicConfig(level=logging.INFO, format="%(levelname)s: %(message)s")

def process_with_log(records):
    logging.info(f"started processing {len(records)} records")
    passed, failed = check_all(records)  # assumed already defined
    logging.info(f"done: {len(passed)} passed")
    if failed:
        logging.warning(f"{len(failed)} records failed validation")
    # the report is for the user
    print("✓ processing complete")
    return passed, failed
```

**Logs are "the narration," output is "the dialogue."** Narration is for the crew behind the scenes, dialogue is for the audience — never mix the two.

## Summary

- The dump layer uses `record_to_dict` for type conversion (Decimal→str)
- JSON uses `json.dump`, CSV uses `csv.DictWriter`
- Output is also dispatched by extension; input and output formats can differ
- `logging` provides levelled, formatted, toggleable logs
- Five levels: DEBUG < INFO < WARNING < ERROR < CRITICAL
- `basicConfig` configures the level, format, and output target
- Logs are for developers, print is for users — don't mix them

## Crash Site 1: Forgetting newline="" with CSV

```python
import csv

# WRONG
# with open("out.csv", "w") as f:
#     writer = csv.writer(f)
#     writer.writerows(data)
# Windows will insert blank lines between rows

# correct
with open("out.csv", "w", encoding="utf-8", newline="") as f:
    writer = csv.writer(f)
    writer.writerows([["id", "amount"], ["T001", "19.90"]])
```

**The `csv` module requires `newline=""` when opening files**, otherwise the CSV written on Windows will have blank lines between rows.

## Crash Site 2: Calling basicConfig Repeatedly Has No Effect

```python
import logging

logging.basicConfig(level=logging.WARNING, format="%(levelname)s: %(message)s")
logging.warning("first message")  # shown

# WRONG: expecting the second call to change the level
logging.basicConfig(level=logging.DEBUG, format="%(levelname)s: %(message)s")
logging.debug("second message")   # not shown! level is still WARNING

# correct approach: use a logger object
logger = logging.getLogger("myapp")
logger.setLevel(logging.DEBUG)
logger.debug("second message")    # shown
```

**`basicConfig` only takes effect on the first call** — subsequent calls are ignored. To change the level dynamically, use `getLogger()` to get a logger object and then call `setLevel()`.
