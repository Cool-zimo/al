# Empty States and Feedback: What to Show When There Is No Data

> A detail often overlooked: the first time the program starts and the database is empty, the table is a blank space. An empty table cannot speak for itself, and the user is simply confused — this lesson covers how to handle the "empty state".

## The Awkward Empty Table

**On a brand-new launch of the ledger, the table contains nothing.** The user sees a table with column headings but no rows, and wonders:

- "Is the software broken?"
- "Did I open the wrong file?"
- "Where did my records go?"

**A good application actively explains this state:** it says "there are no records yet — go and add your first one", and may even point the user to where to do it.

## Approach: An Empty-State Placeholder Frame

**The idea is simple: show the Treeview when there is data, and show a hint instead when there is not. Use one container Frame with two child widgets and swap between them.**

```python
list_container = tk.Frame(root)

self.tree = ttk.Treeview(list_container, columns=cols, show="headings")
self.tree.pack(fill="both", expand=True)

self.empty_label = tk.Label(list_container,
                            text="No records yet\n\nUse the entry area below to record your first transaction",
                            justify="center", fg="#999", font=("", 12))
# Hidden for now; refresh will decide which to show
```

**The key is a decision inside `refresh_table`:**

```python
def refresh_table(tree, empty_label, conn):
    rows = db.get_all(conn)
    if len(rows) == 0:
        tree.pack_forget()              # Hide the table
        empty_label.pack(fill="both", expand=True, pady=80)
    else:
        empty_label.pack_forget()       # Hide the hint
        tree.pack(fill="both", expand=True)
        # Clear and refill
        for iid in tree.get_children():
            tree.delete(iid)
        for r in rows:
            tree.insert("", "end", iid=str(r["id"]), values=(...))
```

**`pack_forget()` is the standard way to "temporarily hide" a widget.** It does not destroy the widget, only removes it from the layout, so it can be packed again later. Do not use `destroy()` — that truly deletes it and it must be rebuilt.

## Two Small Feedback Touches

**Besides the empty state, there are two more places where the user deserves feedback:**

1. **A success message after saving:** a flash of "saved" in the bottom-right corner. `messagebox` is too heavy (it needs a click), so use a status-bar message or `after` to clear it after a delay.
2. **A failure message:** validation failures use `showerror`.

**A status-bar implementation (building on the status Frame from lesson 11):**

```python
self.status_var = tk.StringVar(value="Ready")
tk.Label(status_bar, textvariable=self.status_var, anchor="w").pack(side="left", padx=8)

# After a successful save
self.status_var.set(f"Saved · {len(rows)} records")
root.after(3000, lambda: self.status_var.set("Ready"))   # Restore after 3 seconds
```

**`root.after(3000, func)` is tkinter's "run this later" mechanism** — it runs `func` once after 3000 milliseconds. Use it for "a temporary hint that disappears by itself", which is far friendlier than a popup.

## Confirmation Before Deleting

**Delete is irreversible and always deserves a second confirmation. Use `askyesno`:**

```python
def on_delete():
    sel = tree.selection()
    if not sel:
        mb.showwarning("Hint", "Please select a record first")
        return
    rid = int(sel[0])
    ok = mb.askyesno("Confirm delete", "Delete this record? This cannot be undone.")
    if not ok:
        return
    db.delete_record(conn, rid)
    refresh_table(tree, empty_label, conn)
```

**All three pieces are in place:** warn when nothing is selected, confirm before deleting, refresh afterwards. This is the standard "anti-accidental-delete" sequence.

## Crash Site 1: No Empty-State Hint, So the User Assumes It Is Broken

**Symptom:** a blank interface on first launch, and the user sends a message saying "your app will not run".

**Fix:** add an empty-state placeholder Label that clearly tells the user "there is no data here yet" and points to the next action.

## Crash Site 2: Using destroy Hides the Widget Permanently

```python
if empty:
    tree.destroy()          # Wrong: it really is gone
    empty_label.pack()
# Later, when there is data...
tree.pack(fill="both", expand=True)    # AttributeError: 'NoneType' object has no attribute 'pack'
```

**Symptom:** `AttributeError`, because the tree has been destroyed.

**Cause:** `destroy()` removes the widget from memory; the reference remains but the object is dead.

**Fix:** use `pack_forget()` to hide without destroying. To bring it back, just pack it again.

## Crash Site 3: Forgetting to Switch State, So the Table and Hint Overlap

```python
def refresh_table(tree, empty_label, conn):
    rows = db.get_all(conn)
    if not rows:
        empty_label.pack(...)      # Show the hint
    # No else, no pack_forget on the tree
    for iid in tree.get_children():
        tree.delete(iid)
    for r in rows:
        tree.insert(...)
    tree.pack(...)                 # Result: hint and table overlap
```

**Symptom:** the hint text and the table appear on top of each other, overlapping and looking broken.

**Cause:** both widgets were packed, stacking vertically.

**Fix:** in either state, `pack_forget` the other widget first. The two branches of the `if/else` each manage their own visibility, guaranteeing that exactly one is visible at a time.

## Summary

- On first launch the table is empty; use a placeholder Label to explain and guide the user
- To hide and show, use pack_forget, not destroy (destroy truly deletes)
- Each branch of the if/else manages its own visibility, so exactly one widget is shown
- Success messages use a status bar plus after to clear; friendlier than a popup
- Delete is irreversible and needs an askyesno confirmation
- Four kinds of feedback are needed: empty state, success, error and confirmation
