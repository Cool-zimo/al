# A Prototype Sketch: Draw the Interface Before You Code

> The code is now layered. One last thing before you start: draw what the interface will look like. Not with design software — with ASCII characters on paper. First settle "what the user sees and where they click", then decide "how many widgets go in the code".

## Why Sketch First

**People who skip the sketch and start coding usually end up with a "fighting widgets" interface:** the buttons in the entry area cover the last row of the table, the date box is too narrow for ten characters, and the category dropdown is absurdly wide.

**The value of a sketch is cheap trial and error.** A bad drawing can be rubbed out and redone in ten seconds; code that turns out to have the wrong layout means trawling through several files to fix.

## Our Interface: Top, Middle and Bottom

**Looking at requirements F1 (record an entry) and F2 (view the list), the interface falls naturally into three blocks:**

```
+-------------------------------------------------+
|  Ledger                               [Chart]   |  <- Top: title + chart button
+-------------------------------------------------+
|  Date         Amount    Category    Note         |
|  2026-09-27   38.50     Food        Lunch        |  <- Middle: record list
|  2026-09-26   120.00    Transport   Taxi         |
|  2026-09-25   8000.00   Salary      Payday       |
|  ...                                            |
+-------------------------------------------------+
|  Date [____] Amount [____] Category [v]         |
|  Note [________________]        [+ Add entry]    |  <- Bottom: entry form
+-------------------------------------------------+
```

**Each block has a single job:** the top bar holds global actions (switch page, view statistics); the middle is the star of the show — the table; the bottom is the entry area, with all input controls on one line and the "Add entry" button at the far right.

## Which Requirement Does Each Widget Serve?

**A sketch is not just widgets scattered around; every widget should point back to a requirement:**

| Widget | Serves requirement |
|---|---|
| The Treeview table in the middle | F2 view the list |
| The "Add entry" button at the bottom | F1 record an entry |
| The date/amount/category/note inputs at the bottom | F1 record an entry |
| The "Chart" button at the top | F3 summarise by category |
| The database file ledger.db | F4 persist data |

**Exercise: on your own sketch, label every widget with the requirement it serves.** A widget you cannot label is probably surplus.

## Small Decisions About Field Placement

**How the controls in the entry area are arranged is not random:**

- **Date goes on the far left:** the user fills in left to right, and date is the first thing to enter.
- **Amount comes next:** it is the core field, so give it a prominent, slightly wider box.
- **Category uses a Combobox:** do not let the user type freely, or you will end up with "Food", "food", "lunch" all treated as different categories and the statistics will fall apart.
- **Note gets a long single-line box:** notes are usually long; one Entry is enough.
- **The button goes on the far right:** after filling in the last field, the user's hand naturally lands in the bottom-right corner.

## Crash Site 1: Using an Entry for Category

```python
cat_entry = tk.Entry(form_frame)   # Wrong: free text input
```

**Symptom:** today the user types "Food", tomorrow "lunch", the day after "food". Three "different categories" appear in the database and three separate amounts are totalled.

**Cause:** a category should be a fixed option, not free text.

**Fix:** use `ttk.Combobox` with `values=("Food","Transport","Shopping","Salary",...)` and, when necessary, `state="readonly"` to force a choice.

## Crash Site 2: Putting the Form at the Top and the List at the Bottom

**Some beginners, following the "input first, display second" idea, put the form at the top and the table at the bottom.**

**Symptom:** after twenty records, the newest entry (which should be at the top, sorted newest first) is right at the bottom, and the user has to scroll down to find it.

**Cause:** "order of actions" and "order of importance" have been muddled. The thing the user looks at most often is the history list, so it should take the most space in the most natural position.

**Fix:** put the entry area at the bottom (one row at a time is enough) and let the list occupy the main middle region.

## How to Size Things

**Do not agonise over pixels; think in proportions first.** This interface needs just three `pack` cuts:

- The top toolbar uses `side="top"` with a fixed height.
- The bottom entry area uses `side="bottom"` with a fixed height.
- The middle table uses `side="top"` with `fill="both", expand=True` so it soaks up the remaining space.

**The middle table must be stretchy:** `expand=True` guarantees that the table grows when the window is enlarged, so a user on a large screen does not see a huge empty area.

## Summary

- Draw an ASCII sketch before coding; it is the cheapest form of trial and error
- The interface has three layers: toolbar / table / entry area
- Every widget must point back to a requirement; one that cannot is probably surplus
- Category uses a Combobox with fixed options; do not let free text ruin the statistics
- The list occupies the main area; the entry area sits at the bottom, matching "order of importance"
