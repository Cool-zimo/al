# Designing the Data Model: What Fields Does a Record Have?

> The previous lesson set out "what we are building". This lesson sets out "what the data looks like". The data model is the foundation of the whole project — once it is decided, the database table, the interface fields and the reporting dimensions all follow from it.

## What Is Inside One Ledger Record?

**Look at requirement F1 (record an entry) and ask: what is the minimum information needed to record one transaction?**

| Field | Meaning | Example |
|---|---|---|
| amount | How much money | 38.5 |
| category | Where it was spent or earned | Food, Salary |
| date | When it happened | 2026-09-27 |
| note | Extra detail | Lunch with colleagues |
| type | Income or expense | expense |

**Now add two "system fields" that the user does not fill in, but that must exist:**

| Field | Meaning |
|---|---|
| id | A unique number for each record (the primary key) |
| created_at | When this record was entered into the system |

## Why a Primary Key Is Mandatory

**Can "date + amount + note" be used as the primary key?** No. You might spend the same amount on the same meal on the same day and enter it twice — the two rows would be identical in every field except id. Without id there is no way to tell them apart, and no way to delete just one of them.

**The job of a primary key is to identify one row uniquely.** In SQLite the usual choice is `INTEGER PRIMARY KEY AUTOINCREMENT`: you do not set it when inserting; the database assigns an incrementing integer automatically.

## How to Store the Date

**This is the easiest trap for beginners.** There are three ways to store a date; here is the conclusion first:

| Storage | Example | Verdict |
|---|---|---|
| Store the string "2026-09-27" | Readable as-is | ✅ Recommended; sorts and groups by year/month easily |
| Store a timestamp such as 1780000000 | One integer | Sorts fast but is unreadable; needs conversion |
| Store three columns: year/month/day | Three separate fields | Fiddly; not recommended |

**We will store the date as a `YYYY-MM-DD` string.** It sorts correctly in SQLite (`"2026-10-01" > "2026-09-27"` is true) and the first 7 characters can be used for a "monthly summary" (`"2026-09"`).

**Crash site:** if you store `"Sept 27"` or `"27/09/2026"`, string sorting breaks — `"10/01"` sorts before `"09/27"` because `'1' < '0'`. **Always use the "biggest unit first" format `YYYY-MM-DD`.**

## How to Store the Amount

**The amount must be stored as a number (integer or float). It must never be stored as a string.** Two reasons:

1. When totalling, you need to add things up; `SUM()` only works on numeric columns.
2. Adding the strings `"38.5"` and `"100"` will raise an error or produce nonsense.

**A common worry about using `REAL` (floating point) for money is precision.** Money does demand accuracy, but for a personal ledger rounding to the nearest 10 cents is enough, and float rounding error (around 1e-15) is acceptable at that scale. If you were building accounting software where "not a penny can be lost", you would use integer cents (`3850` meaning £38.50) or a `DECIMAL` type — but SQLite has no `DECIMAL`, so integer cents are the safest fallback.

**In this project we store the amount in pounds using `REAL`, rounded to the nearest 10p.** At input time we just check that the value is a valid number.

## Should Category Get Its Own Table?

**Categories (Food, Transport, Salary, ...) are a fixed short list.** You could write the category name into every record, or you could create a separate `categories` table and reference it by category id.

**This project uses the simplest approach: category is a text field `category TEXT` inside the records table.** Reason: the list is short and rarely changes, so there is no need to add a table just for normalisation. When categories need "an icon and a colour each", *then* it is time to split them out into their own table.

## Crash Site: Amount Stored as a String

```sql
-- Wrong: amount is TEXT
CREATE TABLE records (amount TEXT, category TEXT, ...);

-- When totalling:
SELECT SUM(amount) FROM records;
-- The result might be 0 or an error, because SQLite does an implicit
-- conversion and chokes on something like "12.5 GBP", turning it into 0
```

**Symptom:** `SUM(amount)` returns a mysteriously small number, or just 0.

**Cause:** a string like `"12.5 GBP"` cannot be fully converted to a number, so SQLite loses part of it.

**Fix:** store the amount as `REAL`; at input time only accept plain numbers. The currency unit (£) is added only when displaying in the interface.

## Crash Site: Using a Hand-Made Code as the Primary Key

```sql
-- Wrong: using "date + sequence number" as the primary key
INSERT INTO records VALUES ('20260927-001', 38.5, 'Food');
-- What about the second entry on the same day? -002?
-- And deleting one in the middle leaves a gap.
```

**Symptom:** `UNIQUE constraint failed` on insert, or gaps appearing in the numbering.

**Cause:** managing your own numbering means handling duplicates and concurrency yourself — easy to get wrong.

**Fix:** hand it to the database: `id INTEGER PRIMARY KEY AUTOINCREMENT`, and leave the id empty on insert.

## Summary

- One record = amount (REAL) + category (TEXT) + date (TEXT) + note (TEXT) + type (TEXT) + primary key id
- The primary key uses `AUTOINCREMENT`, an auto-incrementing integer; do not invent your own numbering
- The date is always a `YYYY-MM-DD` string, easy to sort and group by month
- The amount is stored as `REAL`, never as a string
- Category stays inside the records table for now; no separate table yet
