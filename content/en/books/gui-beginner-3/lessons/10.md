# Transactions and Connection Management

> This lesson closes out the data layer: what exactly do commit and rollback manage, and when should the connection be opened and closed? Get these two right and your program will not suffer from "data mysteriously disappears" or "the file is locked".

## A Transaction: All or Nothing

**A transaction is a core database concept.** It guarantees that a group of operations either all succeed or all fail; it never stops halfway.

**A ledger scenario:** a user wants to change a £100 "Food" entry to "Transport" and add a note at the same time. Those two steps should be tied together — if the first succeeds and the second fails, the database is left inconsistent.

```python
try:
    cur.execute("UPDATE records SET category='Transport' WHERE id=?", (1,))
    cur.execute("UPDATE records SET note='corrected' WHERE id=?", (1,))
    conn.commit()        # Commit only when both succeed
except Exception:
    conn.rollback()      # Any failure rolls back to the original state
    raise
```

**A world without transactions:** a network blip, a program crash or a full disk could leave a group of operations half done. With transactions, any problem lets you `rollback()` to the state before the operations began.

## Autocommit Mode

**By default, SQLite is "deferred commit": INSERT/UPDATE/DELETE must be followed by an explicit commit.**

**But autocommit can be switched on:** each statement commits immediately with no manual commit. For a small desktop program that saves a few lines of code, but at the cost of **losing atomicity** — multiple statements can no longer be grouped.

**This project stays with manual commit** because "add one record" looks simple now, but later you may want "insert a record + update a statistics cache + write a log" in the same transaction. Keeping transaction support makes that flexible.

## with: A Context Manager for the Connection

**`sqlite3.connect()` returns a connection that supports `with`, but many people use it wrong (mentioned in lesson 6; explained fully here):**

```python
with sqlite3.connect("ledger.db") as conn:
    cur = conn.cursor()
    cur.execute("INSERT INTO records(amount) VALUES (38.5)")
    # No exception -> automatically commit on leaving the with block
# Exception -> automatically roll back on leaving the with block
```

**Key point: `with` ends the transaction, not the connection.** After leaving the block the connection object is still valid and usable — it is just that the transaction has been committed.

**This is the counter-intuitive part:** `with` is not a "connection lifetime manager"; it is a "transaction boundary". To manage the connection lifetime you must write it yourself:

```python
conn = sqlite3.connect("ledger.db")
try:
    with conn:                      # Manages only this group of operations
        cur = conn.cursor()
        cur.execute("INSERT INTO records(amount) VALUES (38.5)")
    # Here conn is still open and can do more
finally:
    conn.close()                    # The real close
```

## When to Close the Connection

**The standard approach for a desktop app: open one global connection at startup, close it on exit.**

```python
# main.py
import tkinter as tk
import sqlite3
import db

def on_close():
    db.close_conn()     # Close the database before destroying the window
    root.destroy()

root = tk.Tk()
db.init_global_conn("ledger.db")
root.protocol("WM_DELETE_WINDOW", on_close)
root.mainloop()
```

**Why register `WM_DELETE_WINDOW`?** Because when the user clicks the close button, tkinter by default kills the process immediately and `conn.close()` may never run. Registering this protocol means your cleanup logic runs first.

**What if you do not close it?** Usually SQLite auto-rolls back uncommitted transactions and releases the file when the process exits — but **uncommitted data may be lost**, and the file lock may not release in time, causing `database is locked` briefly on the next launch.

## Short-Lived vs Long-Lived Connections

**Two styles compared:**

| Style | Approach | Pros | Cons |
|---|---|---|---|
| Short-lived | connect + close inside each function | Simple; no forgetting to close | Repeated open/close has overhead |
| Long-lived | one global connection, reused | Fast; keeps transactions | Must stay single-threaded |

**A tkinter program runs a single-threaded event loop**, which is a natural fit for a long-lived connection. Multiple connections writing to the same database concurrently would also trigger `database is locked`, so this project uses long-lived connections throughout.

## Crash Site 1: An Exception Skips commit and Data Is Lost

```python
cur.execute("INSERT INTO records(amount) VALUES (38.5)")
1/0                        # Deliberate exception
conn.commit()              # Never reached
```

**Symptom:** no error (the exception propagates up and is caught at the top level), but the data was not stored and cannot be queried.

**Cause:** commit sits after the exception and never runs. As the exception leaves the scope, SQLite rolls back the uncommitted transaction automatically.

**Fix:** wrap writes in try/except, or do them inside a `with` block — `with` auto-rolls back on exception, so at least no half-finished state is left behind.

## Crash Site 2: Using the Cursor After with

```python
with sqlite3.connect("ledger.db") as conn:
    cur = conn.cursor()
    cur.execute("SELECT * FROM records")

rows = cur.fetchall()      # Sometimes works, sometimes "Cannot operate on a closed database"
```

**Symptom:** intermittent `sqlite3.ProgrammingError: Cannot operate on a closed database`.

**Cause:** on leaving the `with` block, SQLite commits the transaction and in some situations also marks the underlying connection as unusable. **The deeper problem: you still hold a cursor after the block, and the cursor's lifetime is bound to the connection.**

**Fix:** do the query and fetch the results inside the `with` block, storing the result in a variable before leaving:

```python
with sqlite3.connect("ledger.db") as conn:
    cur = conn.cursor()
    cur.execute("SELECT * FROM records")
    rows = cur.fetchall()     # Fetched inside the block
# Use rows here, not cur
```

## Crash Site 3: Forgetting to Close Leaves the File Locked

**Symptom:** after a program crashes out, the next launch raises `database is locked` from `connect()`; it may take tens of seconds or a full reboot to recover.

**Cause:** the previous process did not close the connection cleanly, leaving the file lock behind. This is especially common on Windows.

**Fix:** always register `WM_DELETE_WINDOW` for cleanup. During development, if you kill the process with Ctrl+C, manually delete the `-journal` or `-wal` files left in the same directory (SQLite uses them for crash recovery).

## Summary

- A transaction guarantees atomicity: all or nothing
- Deferred commit is the default; writes need an explicit commit, errors need rollback
- `with` manages the transaction boundary, not the connection lifetime
- A desktop program uses one long-lived global connection and registers WM_DELETE_WINDOW to close it
- Queries and fetches must both happen inside the `with` block
- A crash on exit can leave a file lock; in development the wal/journal files may need cleaning up

```quiz
type: local
q: In db.py, implement global connection management: init_global_conn(path) opens the connection and stores it in a module variable, close_conn() closes it, get_conn() returns it. In main.py, register WM_DELETE_WINDOW to call close_conn() when the window closes. Note: sqlite3 runs locally; no program can run in the page. Click "Open in VS Code" and run it.
starter: |
  # db.py
  _CONN = None

  def init_global_conn(path):
      global _CONN
      _CONN = sqlite3.connect(path)
      _CONN.row_factory = sqlite3.Row

  def get_conn():
      return _CONN

  def close_conn():
      global _CONN
      if _CONN is not None:
          _CONN.close()
          _CONN = None

  # main.py
  import tkinter as tk
  import db
  root = tk.Tk()
  db.init_global_conn("ledger.db")
  # Register WM_DELETE_WINDOW
  root.mainloop()
checklist:
- init_global_conn opens the connection
- get_conn returns the global connection
- close_conn closes it and sets it to None
- main.py registers WM_DELETE_WINDOW to close the database on exit
```
