# Refresh Strategies: Full Refresh Versus Incremental Update

> Lesson 19 made the display refresh whenever data changes. This lesson answers a performance question: when you refresh, do you wipe the whole table and redraw it, or do you touch only the changed row? Both strategies have their place, and mixing them up gives you either a freeze or a wrong display.

## Two Strategies

**Full refresh (the one we have been using):**

```python
def refresh_table(tree, empty_label, conn):
    rows = db.get_all(conn)
    if not rows:
        tree.pack_forget(); empty_label.pack(); return
    empty_label.pack_forget(); tree.pack(fill="both", expand=True)
    for iid in tree.get_children():
        tree.delete(iid)
    for r in rows:
        tree.insert("", "end", iid=str(r["id"]), values=(...))
```

**Traits:** simple, and always correct. The price is deleting everything and inserting everything each time.

**Incremental update (touch only the changed row):**

```python
def update_row(tree, rid, r):
    # remove the old row, then insert the new one
    tree.delete(str(rid))
    tree.insert("", "end", iid=str(rid), values=(...))
```

**Traits:** precise and fast. The price is a fiddly problem — you must maintain the correct position.

## When Full Refresh Is the Right Call

**Full refresh fits these cases:**

- **Small data sets** (a few thousand rows or fewer): deleting and inserting thousands of rows takes milliseconds in tkinter, invisible to the user.
- **The order can change**: if you edit a date or an amount, the sort position changes, and updating only the value leaves a wrong display.
- **There is filtering or sorting**: after the change, the row may need to move to a different page or position.
- **Just started or just switched pages**: the whole view needed rebuilding anyway.

**Our ledger falls into the first two buckets**: the data set is small and users usually sort by date. So **full refresh by default is fine.**

## When Incremental Is Worth It

**With large data (tens of thousands of rows) or very frequent operations, full refresh stalls.** Incremental touches one row; the catch is maintaining its position.

**The hard part is "where does it go":** the table is sorted by date descending, and you changed an entry's date from 09-27 to 09-01, so that row should move to the bottom. An incremental update that merely does `delete + insert` at the end will put it in the wrong place.

**Solution: either re-sort before inserting, or fall back to a full refresh.** For a sorted view, full refresh is actually the safer bet — you do not maintain positions, you just re-query and you are right.

## A Mixed Approach: Pick by Action Type

**Use the action name passed by lesson 19's notify to choose a strategy per action:**

```python
def _on_data_changed(action, rid):
    conn = db.get_conn()
    if action in ("delete",):                     # delete: can be incremental
        app["tree"].delete(str(rid))
        if not db.count_records(conn):
            app["tree"].pack_forget()
            app["empty_label"].pack(fill="both", expand=True, pady=80)
    elif action == "update":                      # update: position may move, full
        refresh_table(app["tree"], app["empty_label"], conn)
    else:                                         # add: append at the end
        r = db.get_by_id(conn, rid)
        app["tree"].pack_forget()
        app["empty_label"].pack_forget()
        app["tree"].pack(fill="both", expand=True)
        app["tree"].insert("", "end", iid=str(rid), values=_fmt(r))
    app["status_var"].set(f"Data updated ({action})")
    root.after(3000, lambda: app["status_var"].set("Ready"))
```

**Delete incrementally** (removing a row never changes positions), **update with a full refresh** (position may change), **add by appending** (provided the current view is ordered by id descending — if it is sorted by date, the new row might belong in the middle, and that calls for a full refresh too).

**That is the essence of strategy choice: think one step further and ask "could this operation change the order?".**

## Pagination: The Ultimate Answer for Huge Data

**If records really reach six figures, even a full refresh will stall.** Then you paginate:

```python
def load_page(tree, page, page_size=100):
    offset = page * page_size
    rows = db.get_page(conn, offset, page_size)   # LIMIT ? OFFSET ?
    # clear and insert just this page
```

**`LIMIT 100 OFFSET 0` in SQL fetches only the first 100 rows**, and the Treeview holds only 100 rows — never a freeze.

**A ledger rarely needs pagination** — a personal account book grows by hundreds of rows per year. But knowing the concept pays off the day you build something with a large user base.

## Crash Site 1: An Incremental Update Changes the Value but Not the Position

```python
def update_row(tree, rid, r):
    # just change the value
    tree.item(str(rid), values=_fmt(r))    # value changed, position did not
```

**Symptom:** the amount changed from 38.5 to 1200 and the displayed value is correct, but it stayed put — in a view sorted by amount it should have jumped to the top.

**Cause:** `tree.item()` changes content only, not order.

**Fix:** in a sorted view, just do a full refresh; or `delete + insert` in the correct position (which means computing that position).

## Crash Site 2: Full Refresh on a Large Data Set Freezes the Interface

**Symptom:** after importing 50,000 records, every add hangs for 2 seconds and the interface shows "not responding".

**Cause:** `refresh_table` deletes 50,000 rows and inserts 50,000 rows, monopolising the GUI thread.

**Fix:** either paginate or go incremental. A ledger will not hit this, but remember it during bulk imports — refresh once after the import is done, never inside the insert loop.

## Crash Site 3: Forgetting the Empty State After Deleting the Last Row

```python
def _on_data_changed(action, rid):
    if action == "delete":
        tree.delete(str(rid))
        # forgot to check: is the table empty now?
```

**Symptom:** after deleting the last row, the screen shows an empty table (column headings, no data) instead of the friendly "no records yet" message.

**Cause:** the delete happened, but the remaining count was never checked and the empty state was never swapped in.

**Fix:** after a delete, check `count_records`; if it is 0, `pack_forget(tree)` and `empty_label.pack()`.

## Summary

- Full refresh: simple and always correct, ideal when data is small or order can change.
- Incremental update: one row, fast, but you must handle insertion position.
- In a sorted view, incremental updates are easy to get wrong, so a full refresh is usually safer.
- Mixed strategy: pick by action — delete can be incremental, update is usually full, add appends at the end.
- At ten thousand rows or more, paginate with LIMIT/OFFSET; a ledger does not need it.
- After deleting the last row, check and switch to the empty state.

```quiz
type: local
q: Implement a "smart refresh" function smart_refresh(action, rid): on delete, remove just that row and check the empty state; on add, if the current sort is "by id descending" append one row, otherwise do a full refresh; on update, always do a full refresh. Subscribe to the "records_changed" event through the observer and pass (action, rid). Trigger each of the three actions once and watch the table respond. A window can't open inside a web page — click 'Open in VS Code' to run it.
starter: |
  import tkinter as tk
  import tkinter.ttk as ttk
  import db, ui, observer

  def smart_refresh(action, rid):
      conn = db.get_conn()
      tree = app["tree"]
      if action == "delete":
          tree.delete(str(rid))
          if db.count_records(conn) == 0:
              tree.pack_forget()
              app["empty_label"].pack(fill="both", expand=True, pady=80)
      elif action == "add":
          r = db.get_by_id(conn, rid)
          app["empty_label"].pack_forget()
          tree.pack(fill="both", expand=True)
          tree.insert("", "end", iid=str(rid), values=_fmt(r))
      elif action == "update":
          ui.refresh_table(tree, app["empty_label"], conn)

  observer.subscribe(smart_refresh)
checklist:
- Delete removes only that one row
- Deleting the last row switches to the empty state
- Add appends one row at the end
- Update takes the full-refresh path
- Triggered through the observer

Demo: the database holds 250 rows, the page size is 100, and clicking Next reaches page 2. A window can't open inside a web page — click 'Open in VS Code' to run it.

  import tkinter as tk
  import tkinter.ttk as ttk
  import math
  import db, ui

  app = {"page": [0]}

  def load_page(page, page_size=100):
      offset = page * page_size
      rows = db.get_page(db.get_conn(), offset, page_size)
      ui._refill(app["tree"], rows)          # clear and insert only, no sorting

      app["page_label"].config(text=f"{page+1} / {pages}")

  def next_page():
      app["page"][0] += 1
      load_page(app["page"][0])

  def prev_page():
      if app["page"][0] > 0:
          app["page"][0] -= 1
          load_page(app["page"][0])

- Previous and Next buttons change pages

- Boundaries are handled (page one cannot go backwards)
