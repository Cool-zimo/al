# SQLite and Connections: The sqlite3 Standard Library

> This lesson begins the data layer. SQLite is the data heart of this book — every record you write and every statistic you calculate passes through it. The first lesson is simply "how to connect to it".

## sqlite3 Is Part of the Standard Library

**Python ships with the `sqlite3` module, ready to use with no `pip` required:**

```python
import sqlite3

conn = sqlite3.connect("ledger.db")
print(conn)
# <sqlite3.Connection object at 0x...>
```

**`connect("ledger.db")` does two things:**

1. If `ledger.db` does not exist in the current directory, it is **created automatically**.
2. A connection to that file is opened and a `Connection` object is returned.

**This is what "single-file database" means in SQLite:** the whole database is one `.db` file. You can see it, copy it and back it up in the file manager.

## Connection and Cursor

**Once you have a connection, you also need a "cursor" to run SQL:**

```python
conn = sqlite3.connect("ledger.db")
cur = conn.cursor()

cur.execute("CREATE TABLE IF NOT EXISTS t(x INT)")
cur.execute("INSERT INTO t VALUES (1)")

conn.commit()      # INSERT/UPDATE/DELETE must be committed, or nothing happens
conn.close()
```

**The two objects and their jobs:**

| Object | What it does |
|---|---|
| `Connection` | Manages the connection, transactions (commit/rollback) and closing |
| `Cursor` | Runs SQL and fetches results |

**Rule to remember: INSERT/UPDATE/DELETE need `commit()`; a SELECT does not.** This is SQLite's transaction model: changes sit in memory until commit writes them to the file.

## Where the Connection Lives, and How Many

**A desktop app usually needs just one global connection** — opened at startup and closed on exit. Put it in `db.py`:

```python
import sqlite3

_conn = None

def get_conn():
    global _conn
    if _conn is None:
        _conn = sqlite3.connect("ledger.db")
    return _conn
```

**Why not open a new connection for every operation?** Because opening a connection has a cost; doing it repeatedly will make the interface feel sluggish (SQLite is fast, but it adds up). **Keep one long-lived connection and reuse it throughout** — the standard approach for a desktop application.

## Making Results Easier to Use: row_factory

**By default, `cur.fetchall()` returns a list of tuples, and you must use indexes to read them:**

```python
cur.execute("SELECT id, amount, category FROM records")
rows = cur.fetchall()
for r in rows:
    print(r[0], r[1], r[2])   # Indexes 0, 1, 2 — easy to forget
```

**To fetch "by column name" instead, set `row_factory`:**

```python
conn = sqlite3.connect("ledger.db")
conn.row_factory = sqlite3.Row

cur = conn.cursor()
cur.execute("SELECT id, amount, category FROM records")
rows = cur.fetchall()
for r in rows:
    print(r["id"], r["amount"], r["category"])   # By name — much clearer
```

**Once `Row` is in use, the returned object works both ways:** `r["id"]` by name or `r[0]` as a tuple. Setting this once in the data layer makes life much easier for the interface layer.

## Crash Site 1: Forgotten commit — Data Never Saved

```python
conn = sqlite3.connect("ledger.db")
cur = conn.cursor()
cur.execute("INSERT INTO records(amount) VALUES (38.5)")
# conn.commit() was forgotten
conn.close()
```

**Symptom:** no error, everything looks normal — but the next time the program opens, the record is gone.

**Cause:** SQLite's default is deferred commit. After INSERT/UPDATE/DELETE you must call `commit()` explicitly or the changes are never written to the file. If there is an uncommitted transaction when the connection closes, SQLite **rolls it back** (drops it).

**Fix:** make it a habit — every write operation is immediately followed by `commit()`. Better still, wrap writes in `try/except` and call `rollback()` on error.

## Crash Site 2: Two Connections Writing to the Same Database

```python
# Thread A
conn1 = sqlite3.connect("ledger.db")
# Thread B
conn2 = sqlite3.connect("ledger.db")
```

**Symptom:** the second connection raises `database is locked`, or the two connections overwrite each other.

**Cause:** SQLite uses a file-level lock and allows only one writer at a time. Two threads, each with its own connection, collide.

**Fix:** this project is a single-threaded tkinter program, so **one global connection means no collision**. If threads really are needed, add locking or move to a database that supports concurrency.

## Crash Site 3: The Program Crashes and the Connection Never Closes

**Symptom:** when an exception occurs, `conn.close()` never runs and the connection leaks. At best the next `connect` reports the database as busy; at worst a file lock is left behind.

**Fix:** use `try/finally` to guarantee closure, or use a context manager. But note — **a `Connection` supports context management, but it manages the transaction, not the connection lifetime:**

```python
with sqlite3.connect("ledger.db") as conn:    # On exit, commit or rollback
    cur = conn.cursor()
    cur.execute("INSERT INTO records(amount) VALUES (38.5)")
# Leaving the with block: commit on success, rollback on exception
# Note: the connection itself is NOT closed! conn.close() is still required.
```

**This is highly counter-intuitive and worth memorising: `with conn` manages the transaction, not the close.**

## Summary

- `sqlite3` is in the standard library; `connect()` creates the file if it does not exist
- The connection manages transactions, the cursor runs SQL; writes must be committed
- A desktop app keeps one global connection and reuses it; do not open and close repeatedly
- Setting `row_factory = sqlite3.Row` allows fetching by column name
- A forgotten commit is the most common cause of "data mysteriously disappearing"
- `with conn` manages transaction commit/rollback only; the connection still has to be closed
