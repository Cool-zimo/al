# Input Validation: The Amount Must Be a Number, the Category Cannot Be Empty

> The form accepts input now, but users will type anything: "abc" in the amount box, "yesterday" in the date box, or a blank category before clicking save. This lesson blocks that "dirty data" before it reaches the database.

## Validation Belongs in the Logic Layer

**Following the layering from lesson 3, validation is a logic-layer job. Create `logic.py`:**

```python
import re

def validate(date, amt, cat, note=""):
    """Returns (ok: bool, msg: str)"""
    if not date:
        return False, "Date cannot be empty"
    if not _is_valid_date(date):
        return False, "Date must be in YYYY-MM-DD format"
    if not amt:
        return False, "Amount cannot be empty"
    try:
        f = float(amt)
    except ValueError:
        return False, "Amount must be a number"
    if f <= 0:
        return False, "Amount must be greater than 0"
    if not cat:
        return False, "Please choose a category"
    return True, ""
```

**The standard signature for a validation function is to return `(passed, error_message)`.** That way the interface layer can decide what to do: show an error popup on failure, proceed on success.

## Validating the Amount: float() Means a Number

**To decide "is this a number?", do not guess with a regex — just try to convert it:**

```python
try:
    f = float(amt_str)
except ValueError:
    return False, "Amount must be a number"
```

**Why not a regex?** Because valid numbers come in more forms than you might expect: `1.5`, `0.5`, `.5`, `1e3`, `-3`, `+2.0` — all accepted by `float()`. A hand-written regex misses some and rejects others by mistake.

**Should negative numbers be allowed?** Not in this project — income and expense are already separated by the "type" field, so the amount is always positive. Add an explicit `f > 0` check.

**Should the amount be limited to a certain number of decimal places?** Two decimals is enough for a personal ledger. You can add `round(f, 2)` in the validation, or simply leave it (SQLite stores a float and formatting handles display).

## Validating the Date: Format Plus Validity

**A date must satisfy both "the format is right" and "the value is real":**

```python
from datetime import datetime

def _is_valid_date(s):
    try:
        d = datetime.strptime(s, "%Y-%m-%d")
    except ValueError:
        return False
    return True
```

**`datetime.strptime("2026-02-30", "%Y-%m-%d")` raises ValueError** because February has no 30th. A regex such as `^\d{4}-\d{2}-\d{2}$` checks format only and would happily accept "February 30th".

**A looser alternative:** if you wanted users to type natural language like "yesterday", you would need a third-party library such as `dateparser` — but that violates the "standard library wherever possible" rule, so this project sticks with `YYYY-MM-DD`.

## Validating the Category: Not Empty

**With a readonly Combobox the category should never be empty — but the first item might be blank, or the program might not set a default on startup.**

**Defensive validation:**

```python
if not cat:
    return False, "Please choose a category"
```

**Even if you are certain the Combobox has a value, keep this line.** Defensive programming pays off when code is changed, refactored or a new field is added: the day you switch the Combobox to allow input, the validation is still there, and no bad data slips through.

## Unified Feedback: messagebox

**On validation failure, show an error dialog:**

```python
ok, msg = logic.validate(date, amt, cat)
if not ok:
    mb.showerror("Invalid input", msg)
    return
```

**Use `showerror` (title + red icon) for errors and `showinfo` for success.** Do not use `showinfo` for everything, or the user cannot visually distinguish an error from a notification.

## Crash Site 1: float() Accepts What You Did Not Expect

**Symptom:** you assumed `float("1e3")` would error, but it returns 1000.0, passes validation and lands in the database.

**This is not a bug, it is a feature** — but it may not match the product intent. Is `1e3` really acceptable?

**Decision:** in a ledger, storing `1e3` as 1000 is acceptable. What must be avoided is "abc" or "twelve pounds". **Keep the `float()` conversion plus `> 0` check.** If scientific notation really must be forbidden, add the regex `^[0-9]+(\.[0-9]+)?$` as an extra rule.

## Crash Site 2: Validation Scattered Across Callbacks

```python
def on_add():
    if not date_var.get():
        mb.showerror("Error", "Date cannot be empty")
        return
    try:
        float(amt_var.get())
    except ValueError:
        mb.showerror("Error", "Amount must be a number")
        return
    # Category, note... several more lines
    db.add_record(...)
```

**Symptom:** validation is tied to the interface controls. When you want the same validation in a "CSV import" feature, all you can do is copy and paste.

**Cause:** validation was not extracted into a logic-layer function.

**Fix:** move it into `logic.validate(...)`. Both CSV import and the button callback call it.

## Crash Site 3: An Error Message Saying Only "Format Error" Leaves the User Guessing

**Symptom:** `mb.showerror("Error", "Bad date format")` — the user is baffled: what format is expected?

**Fix:** make the error message **specific and actionable:**

```python
return False, "Date must be in YYYY-MM-DD format, for example 2026-09-27"
```

**A good error message = state what is wrong + state the correct format + give an example.** It is the cheapest way to add a sense of polish.

## Summary

- Validation belongs in the logic layer and returns (passed, error_message)
- Validate the amount with float(); do not guess with a regex
- Validate the date with datetime.strptime for format and validity; it catches February 30th
- Even a readonly category needs a non-empty defensive check
- Error messages must be specific and actionable: what is wrong, the right format, and an example
- Keep validation in one place; do not scatter it across callbacks
