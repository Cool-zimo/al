# Creating Tables: CREATE TABLE

> Connections are covered. This lesson turns the data model from lesson 2 into real SQL `CREATE TABLE` statements. Whether the table is designed well decides whether every later query is smooth or awkward.

## The Complete CREATE TABLE Statement

**Following the data model from lesson 2, here is the SQL for the records table:**

```sql
CREATE TABLE IF NOT EXISTS records (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    amount      REAL    NOT NULL,
    category    TEXT    NOT NULL,
    date        TEXT    NOT NULL,
    note        TEXT,
    type        TEXT    NOT NULL DEFAULT 'expense',
    created_at  TEXT    NOT NULL
);
```

**Field by field:**

| Field | Type | Constraint | Meaning |
|---|---|---|---|
| id | INTEGER | PK AUTOINCREMENT | Primary key, auto-increment; leave empty on insert |
| amount | REAL | NOT NULL | The amount, must be a number |
| category | TEXT | NOT NULL | Category, must not be empty |
| date | TEXT | NOT NULL | Date in YYYY-MM-DD |
| note | TEXT | nullable | Note, may be left blank |
| type | TEXT | NOT NULL DEFAULT 'expense' | Income or expense; defaults to expense |
| created_at | TEXT | NOT NULL | When entered, filled in by the system |

## Why IF NOT EXISTS Matters

**If you run `CREATE TABLE records(...)` twice, the second run raises an error: `table records already exists`.**

**Fix:** add `IF NOT EXISTS` so that an existing table is skipped without an error.

**This matters especially for desktop applications:** your program runs "create the table if it does not exist" once on every startup. With this clause, the first launch creates it and later launches skip it — one piece of code serving both cases.

## The Truth About Field Types in SQLite

**SQLite's type system differs from other databases, and it is worth understanding.**

**SQLite has only five "storage classes":** NULL, INTEGER, REAL, TEXT and BLOB. Writing `VARCHAR(50)`, `DECIMAL(10,2)` or `DATETIME will all be accepted, but SQLite does **not** actually enforce "length 50" or "2 decimal places".

**What this means:**

- `amount REAL` stores a float; it does not guarantee two decimal places.
- `date TEXT` stores a string; it does not validate the format.
- `category VARCHAR(10)` and `category TEXT` are almost identical in SQLite.

**So should types be written at all? Yes.** The reason is for people and tools: writing `REAL` tells the reader that this field holds a number; the type hint is also useful when migrating to another database.

## NOT NULL and Defaults

**`NOT NULL` is the first line of defence for data integrity.** With it, leaving the field empty on insert raises an error instead of storing a "half-empty" row.

**`DEFAULT 'expense'` makes inserting easier:** when `type` is not specified, the database fills in `'expense'` automatically. For an income you explicitly set `type='income'`.

## The Detail of AUTOINCREMENT

**When you write `INTEGER PRIMARY KEY`, that column becomes an auto-incrementing "row number" automatically; inserting NULL gives it the next value.**

**So why write `AUTOINCREMENT` at all?** The difference is subtle:

- `INTEGER PRIMARY KEY`: inserting NULL gives the current maximum id + 1.
- `INTEGER PRIMARY KEY AUTOINCREMENT`: additionally guarantees that id is **monotonically increasing and never reused**.

**Example:** the table has ids 1, 2 and 3. Delete id 3, then insert a new row.

- Without AUTOINCREMENT: the new row gets id 3 (the just-deleted maximum is reused).
- With AUTOINCREMENT: the new row gets id 4 (strictly increasing).

**This project uses AUTOINCREMENT** because a ledger entry "should not reuse its id after deletion" — that keeps logs and foreign-key references stable.

## When to Initialise the Table

**Put the table creation in `db.py` and call it once at startup:**

```python
import sqlite3

_SCHEMA = """
CREATE TABLE IF NOT EXISTS records (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    amount     REAL    NOT NULL,
    category   TEXT    NOT NULL,
    date       TEXT    NOT NULL,
    note       TEXT,
    type       TEXT    NOT NULL DEFAULT 'expense',
    created_at TEXT    NOT NULL
);
"""

def init_db(path="ledger.db"):
    conn = sqlite3.connect(path)
    conn.execute(_SCHEMA)
    conn.commit()
    return conn
```

**`main.py` calls `init_db()` on its very first line**, so the rest of the program can safely assume "the table exists".

## Crash Site 1: Wrong Type Turns the Amount Into a String

```sql
-- Wrong: REAL was mistyped as TEXT
CREATE TABLE records (
    amount TEXT NOT NULL,
    ...
);
```

**Symptom:** inserting `"38.5"` (a string) succeeds, but `SUM(amount)` returns a strange result — SQLite converts strings it can, but `"38.5 GBP"` becomes 0.

**Cause:** the type name was wrong, so the constraint did nothing.

**Fix:** after creating the table, immediately insert a test row and run `SELECT SUM(amount)` to confirm a number comes back.

## Crash Site 2: Querying Before the Table Is Created

```python
conn = sqlite3.connect("ledger.db")
cur = conn.cursor()
cur.execute("SELECT * FROM records")   # sqlite3.OperationalError: no such table
```

**Symptom:** `OperationalError: no such table: records`.

**Cause:** the CREATE TABLE statement was never executed (perhaps it is inside a function that was never called).

**Fix:** confirm that `init_db()` is called before the first query. You can put the table creation inside `get_conn()` so that "fetching a connection also creates the table".

## Crash Site 3: Altering the Schema Requires Care

**Halfway through the project you decide to add an `account` field (which account the money came from). A beginner simply edits the CREATE TABLE and reruns it.**

**Symptom:** the table already has data; you edit `_SCHEMA` and rerun, but the `CREATE TABLE` with `IF NOT EXISTS` **skips entirely** — it sees the table is already there and leaves it alone, so the new field is never added.

**Fix:** to change a live database you need `ALTER TABLE records ADD COLUMN account TEXT;`. During development you can delete the old `ledger.db` and let it be rebuilt.

## Summary

- Create tables with `CREATE TABLE IF NOT EXISTS`: built on first launch, skipped afterwards
- SQLite recognises only five storage classes; types are written mainly for human readers
- NOT NULL + DEFAULT protect data integrity
- AUTOINCREMENT guarantees ids increase strictly and are never reused
- Table creation lives in `init_db()`, called by main.py at startup
- Changing the schema needs ALTER TABLE, not rerunning CREATE
