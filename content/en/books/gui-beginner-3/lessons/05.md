# Technology Choices: Why SQLite?

> This lesson locks in the entire technology stack for the book: where the data is stored, which library draws the charts, whether any third-party packages are needed. Once this lesson is done, the next five chapters are about filling in the details of these choices.

## Comparing the Candidates

**For a single-user ledger there are at least four approaches to storing data:**

| Option | Strengths | Fatal weakness |
|---|---|---|
| Plain text / CSV | Nothing new to learn; readable in Notepad | Changing one row means rewriting the whole file; no types; a comma inside a multi-line field breaks it |
| JSON file | Handles nested structures | Like CSV, changing one record means rewriting the whole file; no sorting or filtering |
| Excel | Familiar to users; they can edit it | Depends on a third-party library (openpyxl); the file is locked while open |
| **SQLite** | Built into the standard library; single file; full SQL queries and sorting | Almost none |

**Conclusion: SQLite is the default answer for single-user desktop applications.** It is a real database (SQL, indexes, transactions) but the whole thing is one file — no server required.

## Why Not a Plain Text File

**You might think "the data is so small, isn't CSV enough?" It is — but you have to solve three problems yourself:**

1. **Changing one record means rewriting the whole file.** Delete one record and you read 1000 lines, skip that line, and write back 999. SQLite does it with one `DELETE`.
2. **There are no types.** CSV is all strings; `"12.5"` and `"2026-09-27"` must be converted by you. SQLite has REAL, TEXT and DATE types and hands back numbers directly.
3. **Filtering and sorting must be hand-written.** Want "Food in September"? With CSV you write a loop plus a condition plus a manual sort. With SQLite it is one line: `SELECT ... WHERE category='Food' AND date LIKE '2026-09-%' ORDER BY date DESC`.

**Using a text file means rewriting a crude database.** The standard library already has one, so why bother.

## Why Not Excel

**Excel is tempting: the user can open it directly and edit it.** But it has three serious problems:

1. **It needs a third party.** `openpyxl` and `xlrd` are not in the standard library, so packaging needs extra handling.
2. **The file lock.** If the user double-clicks the xlsx, your program cannot read or write it and throws a permissions error.
3. **Concurrent writes.** SQLite has a write lock and operations queue up; an Excel file does not.

**This project follows the "is the standard library enough?" rule, so Excel is out.**

## Is the Standard Library Enough?

**Here is what this book needs, and whether the standard library covers it:**

| Need | Library | Standard library? |
|---|---|---|
| Interface | tkinter + ttk | ✅ Yes |
| Table | ttk.Treeview | ✅ Yes |
| Database | sqlite3 | ✅ Yes |
| Charts | matplotlib | ❌ Third party |
| Packaging | PyInstaller | ❌ Third party |

**Only charts and packaging need third-party packages.** That is the plan: chapters 2–4 use only the standard library to build the project skeleton; chapter 5 introduces matplotlib for charts; chapter 6 introduces PyInstaller for packaging.

**Why introduce third parties in stages?** Because every extra dependency makes the packaged file larger and adds another thing that can go wrong. Finish the "offline, zero-dependency" part first, then add the two that are genuinely needed.

## Why matplotlib Is Acceptable

**Charts are the highlight of this book, and drawing them by hand would be far too much work.** matplotlib is the de facto standard in scientific computing; almost everyone who learns Python ends up installing it, so the cost is low. It also supports embedding directly inside tkinter (covered later with `FigureCanvasTkAgg`) instead of using `plt.show()` to pop up a separate window.

## The Full Stack

**Write the choices and version policy down so they can be checked later:**

```
Python 3.9+          (no walrus operator := ; keep compatible with 3.8+)
tkinter / ttk        (standard library)
sqlite3              (standard library)
matplotlib >= 3.5    (pip install matplotlib)
PyInstaller >= 5.0   (pip install pyinstaller, build time only)
```

**There is no need to pin a precise minor version**, since GUI programs are not sensitive to small library versions. But the version of PyInstaller used for packaging is worth pinning and recording in the README, so that someone following the tutorial does not hit a bug in a newer release.

## Crash Site: Putting Data Inside a File Bundled Into an exe

**Some beginners put `ledger.db` inside the source directory, assuming it will be packed into the exe.**

**Symptom:** the first run after packaging raises `sqlite3.OperationalError: unable to open database file`, or the data simply never saves.

**Cause:** a PyInstaller bundle unpacks into a temporary directory (`sys._MEIPASS`) at runtime, and **that directory is read-only**. Writing a database there means writing to a read-only area.

**Fix:** put the database file in the user's data directory (covered later with `appdirs` or `os.path.expanduser("~/.ledger/ledger.db")`), creating it if it does not already exist.

## Summary

- Data lives in SQLite: single file, standard library, full SQL — the default for desktop apps
- Plain text or CSV means rewriting a database by hand, which is not worth it
- Excel needs third parties and has file-locking issues, so it is out
- The standard library covers interface, tables and database; only charts and packaging need third parties
- Third parties arrive in two waves: matplotlib in chapter 5, PyInstaller in chapter 6
- The database file belongs in the user's directory, not in the read-only bundled area
