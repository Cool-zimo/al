# Parameterised Queries: Why SQL Must Not Be Concatenated

> Every SQL statement in the previous lesson used `?` placeholders. This lesson explains why — because string concatenation in SQL is a fatal security hole, and even if "this program is just for you" it pays to build good habits.

## The "Convenient" f-string Approach

**Beginners love this style:**

```python
category = "Food"
cur.execute(f"SELECT * FROM records WHERE category = '{category}'")
```

**It runs, and it looks harmless enough.** But the moment that `category` comes from anywhere other than a constant you typed yourself — a user's input box, for example — disaster follows.

## A SQL Injection Demo

**Imagine a user types the following into the category box (it looks like gibberish, but it is carefully constructed):**

```python
category = "Food'; DROP TABLE records; --"
cur.execute(f"SELECT * FROM records WHERE category = '{category}'")
```

**After concatenation, the SQL actually sent to the database is:**

```sql
SELECT * FROM records WHERE category = 'Food'; DROP TABLE records; --'
```

**Three statements are executed in one go:**

1. The normal query.
2. `DROP TABLE records;` — your table is deleted.
3. `--` comments out the leftover `'`, keeping the syntax valid.

**Your ledger, and every record in it, vanishes in an instant.** That is SQL injection.

## "But It Is Only for Me" Is No Excuse

**You might say: "I am the only user — who would type that?"**

**In reality, the input does not have to come from you:**

- Importing records from a CSV — the data file might contain malicious content.
- Pasting a note that happens to contain a quote.
- If the program is ever networked or accepts input from others, the trap is already set.

**The practical reason is even simpler: concatenated SQL will break in your own hands first.** See the next crash site.

## The Placeholder Syntax

**Replace the "parts that change" with `?`, and pass the values as a separate parameter tuple:**

```python
cur.execute("SELECT * FROM records WHERE category = ? AND date LIKE ?",
            ("Food", "2026-09%"))
```

**SQLite does three things:**

1. It **escapes** any quotes in the parameters so they can never be treated as SQL syntax.
2. It checks that the types match.
3. It caches the execution plan, making repeated runs faster.

**To the database, the injected string is just ordinary data with no special meaning.**

## Matching Parameters to Placeholders

**The number of `?` placeholders must match the length of the parameter tuple:**

```python
cur.execute("""
    INSERT INTO records(amount, category, date, note, type, created_at)
    VALUES (?, ?, ?, ?, ?, ?)
""", (38.5, "Food", "2026-09-27", "Lunch", "expense", now))
# Six ? matching six values
```

**The order must line up.** A mismatch puts data into the wrong field — and worse, **it does not raise an error**; you just find "a date string in the amount column".

## Crash Site 1: An Unescaped Quote Causes a Syntax Error

```python
note = "Tom's lunch"
cur.execute(f"INSERT INTO records(note) VALUES ('{note}')")
# SQL: INSERT INTO records(note) VALUES ('Tom's lunch')
#                                     ^ ends early here — syntax error
```

**Symptom:** `sqlite3.OperationalError: unrecognized token` or `near "s": syntax error`.

**Cause:** the single quote in `note` terminates the SQL string early.

**Fix:** use the `?` placeholder and let SQLite escape it. This also neatly explains how injection succeeds — the attacker deliberately inserts quotes to alter the syntax.

## Crash Site 2: An IN Clause Cannot Take a List in One Placeholder

```python
cats = ("Food", "Transport", "Shopping")
cur.execute(f"SELECT * FROM records WHERE category IN {cats}")
# SQL: WHERE category IN ('Food','Transport','Shopping')  -- happens to work,
# but only because it is a tuple
```

**It seems to work, but it breaks with user input.** The correct approach uses `?` placeholders and builds the right number of question marks:

```python
cats = ("Food", "Transport", "Shopping")
placeholders = ",".join("?" * len(cats))          # "?,?,?"
sql = f"SELECT * FROM records WHERE category IN ({placeholders})"
cur.execute(sql, cats)
```

**Note:** only the parentheses part uses an f-string; the values are passed as placeholders. Both flexible **and** safe.

## Crash Site 3: Table and Column Names Cannot Be Placeholders

```python
col = "amount"
cur.execute("SELECT ? FROM records", (col,))
# The result is a column containing the string "amount" — not the values of amount!
```

**Symptom:** the result is not data but the column name itself.

**Cause:** a `?` placeholder can only stand in for a **value**. It cannot replace a table name, column name or sort direction. SQLite treats the `?` as a string value wherever it is filled in.

**Fix:** when a table or column name really must be dynamic, string concatenation is the only option — but it must be **whitelist-validated**:

```python
VALID_COLS = {"amount", "category", "date"}
def get_sorted(col):
    if col not in VALID_COLS:
        raise ValueError(f"Invalid column name: {col}")
    cur.execute(f"SELECT * FROM records ORDER BY {col}")
```

**A whitelist = only known-safe names are allowed through**, eliminating injection at its source.

## Summary

- Concatenating SQL leads to SQL injection; in the worst case DROP TABLE wipes out everything
- Every "value" uses a `?` placeholder plus a parameter tuple, so SQLite escapes it
- The number of `?` must match the number of parameters; a mismatch silently puts data in the wrong field
- For IN clauses, build placeholders dynamically with `",".join("?"*len(seq))`
- Table and column names cannot be placeholders; concatenate with a whitelist instead
- Even for personal use, placeholders are the right habit — and they prevent quote-related syntax errors
