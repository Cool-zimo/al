# Exception Handling and Fallbacks: Never Let the Program Crash on the User

> The disk is full, a colleague deleted `ledger.db`, someone typed "abc" in the amount box — these things will happen. This lesson fits your ledger with a "safety belt": a global exception hook catches what escapes, a full disk gets a message, bad input gets validation, and the user never sees a wall of red errors.

## Why Fallbacks Matter

**A desktop program faces real users, not just you.** You would never delete `ledger.db` by hand, type "two hundred quid" in the amount box, or try to write while the C drive has 1KB free. Your users will.

**A program with no exception handling crashes like this:**

```
Traceback (most recent call last):
  File "app.py", line 42, in on_save
    self.db.insert(amount=float(self.amount.get()), ...)
ValueError: could not convert string to float: 'abc'
```

**The window vanishes, the user loses data, gets a fright, and never opens it again.** This is not a UX issue, it is a trust issue.

## A Global Exception Hook: The Final Roadblock

**tkinter has a quirk: exceptions thrown inside callbacks are printed to the console by default and the program keeps running, but an uncaught exception that escapes the event loop brings the whole thing down.** The fix is a global hook.

**Python's `sys.excepthook` is called whenever any uncaught exception occurs:**

```
import sys
import tkinter.messagebox as mb

def global_exc_handler(exc_type, exc_value, exc_tb):
    import traceback
    text = "".join(traceback.format_exception(exc_type, exc_value, exc_tb))
    print("Uncaught exception:\n", text)          # developer view: full stack
    mb.showerror("Something went wrong",
        f"An unexpected error occurred:\n{exc_value}\n\nPlease restart the app. Your data has been saved automatically.")

sys.excepthook = global_exc_handler
```

**Three rules:**

1. **Print the full stack first** — that is the developer's debugging trail, the user never sees it.
2. **Then show a friendly messagebox** — tell the user what happened and what to do, no stack dump.
3. **Put it at the very top of `main.py`**, before any business code runs.

**tkinter's own exceptions travel a different path**, and some GUI frameworks swallow exceptions in the event loop. As a belt-and-braces measure, still wrap your own callbacks in `try/except`.

## Disk Full: Catching IOError

**Scenario:** the user keeps the ledger on a USB stick, then pulls it out. Or the system drive is full. SQLite raises `sqlite3.OperationalError` when `COMMIT` runs.

**Wrong, doing nothing:**

```
def save(self):
    self.db.insert(...)
    mb.showinfo("Saved")    # if insert failed, this line still runs
```

**Right, wrap the save in try and tell the user clearly:**

```
def on_save(self):
    try:
        self.db.insert(
            category=self.category.get(),
            amount=float(self.amount.get()),
            note=self.note.get(),
            date=self.date.get(),
        )
    except OSError as e:              # disk full, no permission, USB pulled
        mb.showerror("Save failed", f"Could not write to the data file:\n{e}\nCheck disk space and file permissions.")
        return
    except ValueError as e:           # bad amount format
        mb.showwarning("Bad input", f"The amount must be a number: {e}")
        return
    self.on_changed()
    mb.showinfo("Success", "One record saved")
```

**`OSError` is the parent of `PermissionError` and `FileNotFoundError`**, so it catches them all in one net. The user sees guidance they can act on, not a red stack.

## Bad User Input: Validate Before Inserting

**Validation has two gates, the sooner the better:**

| Layer | Timing | Example |
|---|---|---|
| Interface validation | The moment the user clicks save | Amount is empty, date format wrong |
| Data-layer constraints | At the SQL level | NOT NULL, CHECK constraints |

**Interface validation:**

```
def validate(self):
    category = self.category.get().strip()
    if not category:
        mb.showwarning("Validation failed", "Please choose a category")
        return False
    amount_str = self.amount.get().strip()
    if not amount_str:
        mb.showwarning("Validation failed", "Amount cannot be empty")
        return False
    try:
        amount = float(amount_str)
    except ValueError:
        mb.showwarning("Validation failed", f"Amount '{amount_str}' is not a valid number")
        return False
    if amount <= 0:
        mb.showwarning("Validation failed", "Amount must be greater than 0")
        return False
    if len(self.note.get()) > 200:
        mb.showwarning("Validation failed", "Note is limited to 200 characters")
        return False
    return True
```

**The save button uses it like this:**

```
def on_save(self):
    if not self.validate():
        return                    # stop right here on failure
    try:
        ...
    except ...
```

**Data-layer constraints are the second gate:** `amount REAL NOT NULL CHECK(amount > 0)` in the table definition means that if anyone bypasses the interface and calls `db.insert` directly, SQL still rejects it. Interface validation is for the user; data-layer constraints are your own backstop. Keep both.

## Crash Site 1: A Bare `except` Swallows the Real Bug

**Symptom:** the program "does not crash" but saves nothing and gives no feedback.

**Cause:** `except:` swallowed everything, including your own typo.

**Wrong:**

```
try:
    self.db.insert(amount=float(self.amount.get()), ...)
except:                  # bare except, eats even KeyboardInterrupt
    pass                 # does nothing, the bug is completely hidden
```

**Right, catch specific exceptions and log the rest:**

```
try:
    self.db.insert(...)
except (ValueError, OSError) as e:
    mb.showerror("Save failed", str(e))
except Exception as e:              # backstop for genuine surprises
    logging.exception("Unexpected error during save")   # lesson 28 covers logging
    mb.showerror("Something went wrong", "Please contact the developer")
```

**Rule: `except` is always followed by a specific exception type.** If you truly need a backstop, catch `Exception` and log it.

## Crash Site 2: A Corrupt Database File Brings the Program Down

**Symptom:** `ledger.db` was half-overwritten by a sync tool and truncated; the next open fails immediately.

```
sqlite3.DatabaseError: file is not a database
```

**Approach:** detect it on open, back up the bad file, then tell the user.

```
import os, shutil

def open_db(path):
    try:
        db = LedgerDB(path)
        db.test_connection()        # run a SELECT 1 to probe
        return db
    except sqlite3.DatabaseError as e:
        logging.exception("Database corrupt")
        bad = path + ".corrupt"
        shutil.move(path, bad)     # preserve the bad file, do not overwrite it
        mb.showerror("Data file corrupt",
            f"The data file could not be read and was backed up as:\n{bad}\n\nThe app will create a new empty ledger.")
        return LedgerDB(path)      # create a fresh one
```

**The key: back it up before recreating.** Overwriting the bad file destroys the only evidence and the user's only chance of recovery.

## Crash Site 3: The Global Hook Cannot Even Show a Messagebox

**Symptom:** with `sys.excepthook` installed, a crash shows no dialog and prints nothing to the console.

**Cause:** by the time the exception fired, the main loop had already exited, `tk.Tk()` no longer existed, and `messagebox.showerror` raised another `RuntimeError: main thread is not in main loop`.

**Fix: in the hook, check whether a dialog can be shown; if not, log only.**

```
def global_exc_handler(exc_type, exc_value, exc_tb):
    import traceback
    text = "".join(traceback.format_exception(exc_type, exc_value, exc_tb))
    logging.error("Uncaught exception:\n%s", text)
    try:
        if tk._default_root is not None:
            mb.showerror("Something went wrong", str(exc_value))
    except Exception:
        pass    # if even the dialog fails, at least the log was written
```

## Summary

- A desktop program must have fallbacks; a crash is a trust issue, not a minor detail.
- `sys.excepthook` is the last line of defence: log and show a friendly message.
- Disk-full and permission problems are all `OSError`; catch them together.
- Validation has two layers: interface validation for the user, SQL constraints as your backstop.
- Catch specific exceptions; a bare `except: pass` hides bugs.
- When the database is corrupt, back up the bad file before creating a new one.
