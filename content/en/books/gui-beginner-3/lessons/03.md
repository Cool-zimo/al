# Slicing the Modules: A Three-Layer Architecture

> Requirements? Done. Data model? Done. Now it is time to write code. The first decision is **not** to build the window, but to split the code into three layers: data, interface and logic. This lesson explains why to separate them, and how.

## Why the Code Must Be Sliced Up

**The classic beginner mistake is "one big pot" code:** database calls sit inside a button's callback, SQL statements and `tree.insert(...)` crowd into the same function, and changing one field means scrolling through the whole file.

**The cost of this style explodes as the project grows:**

- You want to swap the database (say, from SQLite to files); the interface code must all change too.
- You want unit tests, but the test code has to launch the window.
- You want to reuse "totals by category" for charts and exports; all you can do is copy and paste.

**Splitting code by *responsibility* is how you keep change local.** Swap the database and only the data layer changes. Redo the interface and only the interface layer changes. The business logic stays put.

## What Each Layer Is Responsible For

| Layer | Responsibility | May import | Must not do |
|---|---|---|---|
| Data layer `db.py` | Connect, create tables, insert/select/update/delete | Only sqlite3 | Know about windows or buttons |
| Interface layer `ui.py` | Draw the window, table and form; handle clicks | Data layer, logic layer | Write SQL |
| Logic layer `logic.py` | Validate input, calculate statistics, format values | Data layer | Create widgets |

**Key rule: dependencies point one way.** The data layer sits at the bottom and depends on nothing. The interface layer depends on the data layer. The logic layer also depends on the data layer. Reverse dependencies are forbidden — the data layer must never `import ui`.

## Directory Layout

```
ledger/
├── main.py        # Entry point: only creates the App and starts the main loop
├── db.py          # Data layer
├── logic.py       # Logic layer
├── ui.py          # Interface layer
└── ledger.db      # Database file created at runtime (not hand-written; the program builds it)
```

**Each file has one job.** `main.py` should contain no SQL and no cluster of `Label` widgets; it only wires the layers together.

## Seeing the Layers in Action

**Imagine the user clicks "Add" and records a £38.50 Food expense. Here is the division of labour:**

1. The interface layer `ui.py` reads the strings `"38.5"` and `"Food"` out of the entries and hands them to the logic layer.
2. The logic layer `logic.py` checks that `"38.5"` converts to a number and that the category is not empty, then asks the data layer to store it.
3. The data layer `db.py` runs `INSERT INTO records ...`.

**The reverse flow (refreshing the list):**

1. The interface layer asks the logic layer for "all records".
2. The logic layer asks the data layer to query them.
3. The data layer returns a Python list; the interface layer pushes it into the Treeview.

**Each layer talks only to its neighbours; nothing skips a level.** The interface layer never builds SQL, and the data layer never reads the value of an Entry directly.

## Crash Site 1: Writing SQL Inside a Button Callback

```python
def on_add():
    conn = sqlite3.connect("ledger.db")
    c = conn.cursor()
    c.execute("INSERT INTO records(amount,category) VALUES(?,?)",
              (amt_entry.get(), cat_entry.get()))
    conn.commit()
    conn.close()
    # And now manually refresh the table...
    for row in tree.get_children():
        tree.delete(row)
    for r in load_all():
        tree.insert("", "end", values=r)
```

**Symptom:** the same "refresh the table" code is copied into the add, delete and edit handlers. Change it in one place, forget the other two, and the bug returns.

**Cause:** data operations and interface refresh are mixed together; responsibilities are unclear.

**Fix:** extract "load and refresh the table" into a standalone function `refresh_table()` in `ui.py`; add, delete and edit all call it. Better still, use the observer pattern (covered in a later lesson) so that any change in the data layer notifies the interface automatically.

## Crash Site 2: The Data Layer Imports the Interface Layer

```python
# db.py
from ui import tree   # Wrong! The data layer now depends on the interface

def add_record(r):
    # ...insert...
    for row in tree.get_children():   # The data layer touches a widget
        tree.delete(row)
```

**Symptom:** a circular-dependency error — `ImportError: cannot import name 'tree'` — or changing the interface theme drags the database code down with it.

**Cause:** the "dependencies point one way" rule has been broken. The data layer is the bottom layer and should not know there is a window above it.

**Fix:** the data layer returns data only (lists, dictionaries); refreshing widgets is left to the interface layer itself.

## What Belongs in the Logic Layer?

**The logic layer is "the layer that draws no interface, writes no SQL, but understands the business rules".** Typical contents:

- Validation: is the amount a valid number, is the date in `YYYY-MM-DD`, is the category empty?
- Conversion: turn the `(id, amount, category, date)` tuple from the database into a dictionary that the interface finds convenient.
- Statistics: group by category, sum by month, calculate the balance.

**These belong in the logic layer rather than inside an interface callback for the sake of reuse and testing.** A statistics function can be called by the chart, the export and the interface. When writing tests, no window needs to be launched — feed data straight into the function.

## Summary

- Three layers: data layer (db.py), interface layer (ui.py), logic layer (logic.py); entry point is main.py
- Dependencies point one way: interface/logic → data; the reverse is never allowed
- The data layer handles SQL and connections; the interface layer handles widgets; the logic layer handles validation and statistics
- Benefits of layering: swap the database by changing one layer, reuse logic, write tests
- Interface callbacks should be short: hand off immediately and do not write SQL
