# What We Are Building: A Requirements List for a Ledger

> In the first two books you learned to "make parts" — buttons, entries, canvases, tables. In this book you will "assemble a machine": a real, working desktop application. The first thing to do is **not** to write code. It is to figure out exactly what you are building.

## Why Clarity Comes Before Code

**Many beginners open their IDE the moment they get the assignment.** Halfway through, they realise that "category" and "tag" are two different things and the database has to be rebuilt. Or they finish the interface, only to discover that what the user really wanted was "a monthly summary", not "a complete list of every transaction".

**The project in this book is called Ledger (a personal expense tracker).** It is small enough to finish in a week or two, yet large enough to walk you through every part of a desktop application: how data is stored, how the interface is laid out, how charts are drawn, and finally how everything is packaged for someone else to run.

## Start by Asking Three Questions

**Before you type a single line of code, write down the answers to these three questions:**

1. **Who is this for?** (For the author to track personal spending — single user, single computer.)
2. **What must it do?** (Record an income or expense, view the history, group totals by category, and persist the data to disk.)
3. **What will it *not* do?** (No multi-user support, no cloud sync, no budget reminders.)

**The answers to these three questions decide every technical choice that follows.** "Single user, data saved to disk" means a single-file SQLite database is enough. "No network" means there is no need for a server or an account system.

## The Requirements: Four Things It Must Do

**We compress the scope down to four core requirements, each one testable:**

| ID | Requirement | How to verify it |
|---|---|---|
| F1 Record an entry | Record one income/expense with an amount, category, date and note | After saving, that entry appears in the list |
| F2 View the list | See all entries, sorted newest first | The list scrolls and shows the amount and category |
| F3 Summarise by category | See where the money went: totals and percentages per category | A pie chart or bar chart is shown |
| F4 Persist data | Data survives closing and reopening the program | Entries are still there after a restart |

**These four lines are the teaching roadmap for the whole book.** F1, F2 and F4 are covered in chapters 2–4 (data layer + interface). F3 is covered in chapter 5 (charts). Packaging and delivery come in chapter 6.

## Also Decide What It Will *Not* Do

**Saying what you will *not* do is just as important as saying what you will do. It stops the project from growing out of control:**

- No multi-user login
- No data encryption (it is single-user on one machine; the OS handles permissions)
- No cross-device synchronisation
- No automatic categorisation or OCR
- No third-party GUI library (tkinter only, from the standard library)

**Why insist on "no third-party GUI library"?** Because the goal of this book is "a complete desktop project". Once you introduce a third-party library, packaging size and dependency management both become complicated — and right now what you need most is to master the standard library.

## Crash Site 1: Skipping the Requirements and Coding Straight Away

**Symptoms:** you code for a whole weekend, then realise that "category" is hard-coded into the interface — adding a "Transport" category means editing the source. Or the amount is stored as a string, so when you "sum the total" you have to convert every row first.

**Cause:** you never defined "what a single record looks like" (this is the data model, covered in the next lesson). **Vague requirements lead to an undefined data structure, and an undefined data structure means code that has to be rewritten as you go.**

## Crash Site 2: Writing "Build a Nice Ledger App"

**"Nice" is not a requirement, it is an adjective.** It cannot be verified or tested. Rewrite it as something testable:

- Vague: "the interface should look nice"
- Testable: "the window is 800 by 600, the entry area is at the bottom, and the list takes up 70% of the height"

**Every requirement must answer the question "how will I know when it is done?".**

## Summary

- Before coding, decide "who is it for, what does it do, what does it not do"
- Four core requirements: record an entry, view the list, summarise by category, persist to disk
- Deciding what *not* to do prevents the project from bloating
- Requirements must be testable; adjectives are not requirements

```quiz
type: local
q: Add one "non-core requirement" to your ledger — "warn me when I go over budget" — and rewrite it as at least two testable requirements (for example, "on the 1st of every month when the app starts, pop up last month's total spending"). Note that this is a text exercise; no program can run in the page. Click "Open in VS Code" and write your answer in a text editor.
starter: |
  # My non-core requirement: warn me when I go over budget
  # Rewrite as testable requirements:
  # 1.
  # 2.
checklist:
- Each requirement you wrote starts with a verb describing a concrete action
- Each one can be checked for "done or not done"
- No adjectives like "nice", "pretty" or "friendly" appear
```
