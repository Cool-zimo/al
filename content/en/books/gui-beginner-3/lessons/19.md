# Decoupling with the Observer Pattern: Notifying the Interface When Data Changes

> The last three lessons made us call `refresh_table` by hand after every write. Miss one and you get a bug; write it three times and it is redundant. This lesson automates "refresh" with the observer pattern, so the display updates the moment the data changes and you never have to remember to call refresh again.

## The Problem: Refreshes Scattered Everywhere

**Look at the code so far, refreshes appear in three places:**

```python
def on_add():
    db.add_record(...)
    refresh_table(...)        # once here

def on_delete():
    db.delete_record(...)
    refresh_table(...)        # once here

def on_edit():
    db.update_record(...)
    refresh_table(...)        # once here
```

**The cost:** adding an operation (say, "bulk import") means remembering to add a refresh line; changing the refresh logic (say, adding an animation) means editing three places. Miss one and it is a bug.

## The Core Idea of the Observer Pattern

**The observer motto is: "do not ask, subscribe."**

- The interface layer **subscribes** to an event (say, `"records_changed"`).
- The data layer **fires that event** whenever any write happens.
- Subscribers receive the event and refresh automatically.

**From now on the interface layer no longer needs to know "when should I refresh". It only needs to know "when notified, refresh".**

## The Simplest Implementation: A List of Callbacks

**In Python, an observer can be as short as a few lines:**

```python
# observer.py
_listeners = []

def subscribe(fn):
    _listeners.append(fn)

def notify(*args, **kwargs):
    for fn in _listeners:
        fn(*args, **kwargs)
```

**That is the whole thing.** The data layer writes and then `notify()`s, and the interface subscribes with `subscribe(refresh_table)` when it starts up.

## The Data Layer Fires Notifications

**Edit `db.py` so every write ends with a notify:**

```python
import observer

def add_record(conn, amount, category, date, note="", rtype="expense"):
    cur = conn.cursor()
    cur.execute("""INSERT INTO records(amount,category,date,note,type,created_at)
                   VALUES (?,?,?,?,?,?)""",
                (amount, category, date, note, rtype, datetime.now().isoformat(timespec="seconds")))
    conn.commit()
    observer.notify("add", cur.lastrowid)      # notify!
    return cur.lastrowid

def delete_record(conn, rid):
    cur = conn.cursor()
    cur.execute("DELETE FROM records WHERE id=?", (rid,))
    conn.commit()
    observer.notify("delete", rid)

def update_record(conn, rid, ...):
    ...
    conn.commit()
    observer.notify("update", rid)
```

**Note that notify passes the action name and the id**, so subscribers can decide "full refresh or incremental" (useful in lesson 20).

## The Interface Layer Subscribes

**Subscribe once at the end of `ui.build`:**

```python
import observer

def build(root):
    app = {}
    # ... build the interface ...
    app["tree"] = ttk.Treeview(...)

    def _on_data_changed(action, rid):
        refresh_table(app["tree"], app["empty_label"], db.get_conn())
        app["status_var"].set(f"Data updated ({action})")
        root.after(3000, lambda: app["status_var"].set("Ready"))

    observer.subscribe(_on_data_changed)
    return app
```

**The callback closes over `app`, `tree`, `status_var`, and `root`**, so it knows exactly which table to refresh and which status bar to update.

## Now `on_add` Is Clean

**The callback no longer has to remember to refresh:**

```python
def on_add():
    # ... read values, validate ...
    db.add_record(conn, float(amt), cat, date, note, rtype)
    # no refresh_table here, the observer handles it
```

**The data layer and the interface layer are now properly decoupled:** the data layer has no idea a window exists, and the interface only knows "refresh when told". Add a chart page or an export feature later and, as long as they subscribe to the same event, they stay in sync automatically.

## Crash Site 1: Subscribed Twice, Refreshed Twice

**Symptom:** each add makes the table flash the old data then the new, or the status bar message jumps twice.

**Cause:** `observer.subscribe` was called twice (once in `build`, once somewhere else). The same callback lands in the list twice, so `notify` runs it twice.

**Fix:** either guarantee subscribe runs exactly once, or deduplicate:

```python
def subscribe(fn):
    if fn not in _listeners:
        _listeners.append(fn)
```

**While debugging, print `len(_listeners)` to confirm it is 1, not 2.**

## Crash Site 2: A Notification Inside the Notification Callback, Causing Infinite Recursion

```python
def _on_data_changed(action, rid):
    # accidentally write inside a refresh
    db.update_record(conn, rid, ...)    # this notifies again, which calls us again
    refresh_table(...)
```

**Symptom:** `RecursionError: maximum recursion depth exceeded`, and the program locks up instantly.

**Cause:** the notification callback triggered a new notification, which called the callback again, and so on forever.

**Fix:** refreshing (`refresh_table`) is read-only, never write inside a callback. If you genuinely need a chained write, add a "currently notifying" lock flag to prevent re-entry.

## Crash Site 3: Forgotten Subscription, and the Interface Goes Quiet Again

**Symptom:** the data was written and the database has it, but the screen never refreshes. After some digging the cause turns out to be... you forgot to subscribe.

**Cause:** a refactor deleted or misplaced the subscribe line.

**Fix:** put subscribe at the very end of `build`, before the return, as a deliberate "startup hook". On a team, this line is hard to miss in code review.

## Summary

- The observer pattern = subscribe to an event + notify from the data layer + automatic refresh in the interface.
- The motto is "do not ask, subscribe"; the interface no longer needs to know when to refresh.
- In Python, a callback list does the job in a handful of lines.
- The data layer notifies after writing, passing the action name and id for later incremental updates.
- Prevent duplicate subscriptions by deduplicating inside `subscribe`.
- Prevent recursion by never triggering a write inside a notification callback.
