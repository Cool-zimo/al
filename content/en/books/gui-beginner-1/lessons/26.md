# Planning a Real Program: The Text Statistics Tool

> Lessons 1-25 taught you the pieces. Now you'll build something real: a tool that loads a text file and counts characters, words, lines, and how often each word appears. Before writing any code, this lesson is about turning a vague idea into a checklist you can actually implement.

## The Idea, Stated Vaguely

**"I want a program that analyses text files" is not a plan — it's a wish.** It doesn't say what numbers to show, how the user picks the file, what the screen looks like, or what happens with a 50 MB novel. Programming starts by refusing to stay vague.

```
# Vague version (do not start here)
def analyse_text():
    ...   # ???
```

**The three dots are honest, but they're also a warning: if you can't name the steps, you can't code them.** So before any widgets appear, sit down and write out what success looks like.

## Step 1: Write Down the Features

**A feature list is just a set of sentences, one per thing the program must do.**

1. The user picks a `.txt` file from disk.
2. The program reads the file's text.
3. It counts: total characters, characters excluding spaces, words, lines.
4. It counts how often each word appears and shows the top results.
5. The results appear in the window, not in the terminal.
6. If something goes wrong (file missing, unreadable), the user sees a message instead of a crash.

**Each sentence is small enough to map onto a function or a widget.** If a sentence is still doing two jobs, split it. "Read the file and count everything" is really two steps; keep them separate and the code will be testable.

## Step 2: Draw the Screen Before You Code It

**A quick sketch decides your layout before you're emotionally attached to a bad one.** No art skills required — boxes and labels are enough.

```
+---------------------------------------------------+
|  [ Open file... ]                                 |
+---------------------------------------------------+
|  File: (none)                                     |
|  Characters:  0                                   |
|  Characters (no spaces):  0                       |
|  Words:  0                                        |
|  Lines:  0                                        |
+---------------------------------------------------+
|  Top words:                                       |
|  (list of words and counts)                       |
+---------------------------------------------------+
```

**Three regions emerge: a button row at the top, a stats panel in the middle, a results list at the bottom.** That's a layout decision, and it lets you plan which widgets you need before writing a single `pack()` call.

## Step 3: Assign Widgets to Jobs

**Every feature needs a widget or a function — write the assignment down.**

| Feature | Widget / function |
|---|---|
| Pick a file | `Button` + `filedialog.askopenfilename` |
| Show the file path | `Label` |
| Show each stat | one `Label` per stat |
| Show word frequencies | `Listbox` (or a `Text` widget) |
| Do the counting | a plain Python function, no GUI involved |

**The last row is the important one: the counting itself is ordinary code that takes a string and returns numbers.** Keeping it outside the GUI means you can test it with `print()` before the window exists — a habit that saves hours.

## Crash Scene 1: Skipping the Plan and Coding the Window First

```
root = tk.Tk()
# ... build 15 widgets ...
# ... now wonder what the program is supposed to do ...
```

**Starting with widgets before features produces a beautiful window that does nothing useful.** You'll either throw it away or pile logic into button callbacks until they're unreadable. A ten-minute plan up front is the cheapest debugging you'll ever do.

## Step 4: Break the Logic Into Pure Functions

**A pure function takes data in and returns data out — no widgets, no `mainloop`, no surprises.**

```
def count_stats(text):
    chars = len(text)
    chars_no_spaces = len(text.replace(" ", ""))
    words = text.split()
    word_count = len(words)
    lines = text.count("\n") + 1 if text else 0
    return chars, chars_no_spaces, word_count, lines
```

**This function can be tested in a Python shell with a string literal, long before the GUI exists.** That's the whole point: the hard part of the program — getting the counts right — never needed a window in the first place.

## Crash Scene 2: Counting Lines Wrong on an Empty File

```
lines = text.count("\n") + 1
# WRONG when text == "": reports 1 line for an empty file
```

**`text.count("\n") + 1` says an empty file has one line, which isn't how any editor reports it.** Guard with `lines = text.count("\n") + 1 if text else 0`. A small bug, but one your users will notice the first time they open a blank file.

## Step 5: Word Frequency

**Counting word occurrences is a `collections.Counter` job, with one choice to make about what "a word" means.**

```
import re
from collections import Counter

def top_words(text, n=10):
    # keep only letters and apostrophes, lowercased
    words = re.findall(r"[A-Za-z']+", text.lower())
    return Counter(words).most_common(n)
```

**`re.findall` with a pattern is more honest than `str.split()`: it drops punctuation instead of letting `"don't"` and `"don't."` count as different words.** For a learning project this is good enough; you can refine the rule later without touching the GUI.

## Crash Scene 3: Case Sensitivity Makes "The" and "the" Different

```
words = text.split()          # WRONG-ish: "The" and "the" count separately
```

**Without lowercasing, your frequency table lies: "The" appears once and "the" appears twenty times, looking like two different words.** Lowercase the text before you count, or accept that your tool is case-sensitive and say so in the UI.

## What You're Building Across Lessons 27-30

**Here's the roadmap so you know what's coming and why each lesson exists.**

- **Lesson 27** — lay out the regions with `Frame` and `grid`.
- **Lesson 28** — keep the counting functions separate from the widgets (logic/UI separation).
- **Lesson 29** — wire up `filedialog` and file reading, then display the results.
- **Lesson 30** — add exception handling, empty-input handling, and a progress safeguard for large files.

**Each lesson adds one layer and leaves the previous ones intact.** That's how real programs grow: not in one big rewrite, but in small changes you can run after each step.

## Summary

- Vague ideas ("analyse text") must become feature sentences before coding
- Sketch the screen first: regions and widgets, not code
- Assign every feature to a widget or a function and write it down
- Keep the hard work (counting) in pure functions that take strings and return values
- Test pure functions in a shell before the GUI exists
- Watch for off-by-one bugs: empty files, case differences, trailing newlines
