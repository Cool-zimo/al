# Capstone: a complete data analysis report

> You have now seen every tool in this course. This lesson strings them into one pipeline — from dirty data to a single conclusion, skipping no step along the way.

## The questions we need to answer

Alice runs three bubble-tea shops in London (Camden, Canary Wharf, Shoreditch) and has nine months of 2026 sales spread across three files, plus a promotions file for September. She wants to know:

1. Which shop sells the most, and what is its monthly average?
2. Is the business growing or shrinking? What does day-on-day and year-on-year look like?
3. Which promotion was worth it? Can we measure the lift during the campaign?

That is what a real report does — **not run a few functions, but start from the question and work step by step to the conclusion.**

## Step one: build the data

The first move in any hands-on task is "having data to run." We deterministically fabricate a dirty dataset that buries all the usual problems in it.

```python
import pandas as pd
import numpy as np

# Three shops, 2026-01 through 2026-09, daily sales
shops = ['Camden', 'Canary Wharf', 'Shoreditch']
records = []
for shop in shops:
    for month in range(1, 10):
        days = 28
        for d in range(1, days + 1):
            date = pd.Timestamp(f'2026-{month:02d}-{d:02d}')
            revenue = round(2000 + hash((shop, month, d)) % 3000, 2)
            records.append({'shop': shop, 'date': date, 'revenue': revenue})

sales = pd.DataFrame(records)
print(sales.shape)        # (756, 3)
print(sales.head())
```

**756 rows = 3 shops × 9 months × 28 days.** Note that we deliberately did not use 30/31 days, so the data is naturally "incomplete" — we will deal with that later.

A promotions table, covering only September:

```python
promo = pd.DataFrame({
    'shop': ['Camden', 'Canary Wharf', 'Shoreditch', 'Camden'],
    'month': ['2026-09', '2026-09', '2026-09', '2026-08'],
    'campaign': ['Back to School', 'City Workers', 'Local Delivery', 'Summer Reload'],
    'spend': [3000, 5000, 2000, 1500]
})
print(promo)
```

**The two tables have different grain:** the sales table is `shop × date`, while the promo table is `shop × month`. That means joining them will necessarily be one-to-many.

## Step two: clean it (review from chapter 3)

Suppose the sales table picked up a few dirty values along the way. In the real world you will see exactly this:

```python
# Simulate a few dirty values
sales.loc[0, 'revenue'] = 'missing'
sales.loc[5, 'revenue'] = None

print(sales['revenue'].dtype)   # object (contaminated by a string)
```

**An `object` dtype is the classic tell of dirty data.** Three steps to clean it up:

```python
sales['revenue'] = pd.to_numeric(sales['revenue'], errors='coerce')
sales = sales.dropna(subset=['revenue'])
sales['month'] = sales['date'].dt.to_period('M')
sales = sales.sort_values(['shop', 'date']).reset_index(drop=True)

print(sales.dtypes)
print(sales.shape)
```

| operation | what it does |
|---|---|
| `to_numeric(errors='coerce')` | turn anything non-numeric into NaN |
| `dropna(subset=[...])` | drop rows missing a key column |
| `dt.to_period('M')` | extract the month for monthly rollups |
| `sort_values + reset_index` | put things in order and reindex |

**After cleaning, the data is tidy, ordered, and carries a month field** — every later step can stand on it.

## Step three: join (review from chapter 5)

Bring the promo information into the sales table with a merge:

```python
promo['month'] = pd.to_datetime(promo['month']).dt.to_period('M')
merged = sales.merge(promo, on=['shop', 'month'], how='left')
print(merged.shape)                    # (756, 5)
print(merged['campaign'].notna().sum())   # only September matches
```

**A left join keeps every row of the sales table**, filling in NaN where there is no promo match. That is the safest join for preserving raw data.

Note that **there is no one-to-many inflation here:** the sales table's smallest grain is "day," and the promo table's is "month." When joining on `shop + month`, every day in a month lines up with exactly one promo row, so the row count stays at 756.

If you joined only on `shop`, the September promo table would have 4 rows (Camden appears twice) and one-to-many inflation would kick in.

## Step four: group and aggregate (review from chapter 4)

```python
monthly = (sales.groupby(['shop', 'month'], observed=True)['revenue']
                .agg(['sum', 'mean', 'count'])
                .round(2))
monthly.columns = ['total_revenue', 'daily_avg', 'days']
print(monthly)
```

| shop | month | total_revenue | daily_avg | days |
|---|---|---|---|---|
| Camden | 2026-01 | 61384.31 | 2192.30 | 28 |
| Canary Wharf | 2026-01 | 71884.04 | 2567.29 | 28 |
| Shoreditch | 2026-01 | 61086.68 | 2181.67 | 28 |

**`agg` produces several metrics in one pass**, much faster than calling groupby three separate times. This is the standard shape for a real report.

To answer "which shop sells the most":

```python
ranking = (sales.groupby('shop')['revenue'].sum()
                .sort_values(ascending=False))
print(ranking)
```

## Step five: time series (review from chapter 6)

Roll all shops up to a daily total and look at the overall trajectory:

```python
daily = (sales.groupby('date')['revenue'].sum()
              .asfreq('D'))    # ensure daily frequency, leaving gaps empty

ma7 = daily.rolling(7, min_periods=1).mean()
```

**`asfreq('D')` fills in the missing dates**; without it, `resample` could skip a day that has no data. `rolling(7)` smooths the daily noise.

Day-on-day and year-on-year (lesson 29):

```python
daily['day_on_day'] = daily.pct_change()
daily['year_on_year'] = daily / daily.shift(28) - 1   # 28 days back (same day last month for our 28-day data)
```

**We use `shift(28)` here because our fabricated data has 28 days per month**; real data should align by calendar using `DateOffset(months=1)`.

## Step six: state the conclusion

```python
# Campaign period (September) vs. non-campaign (Jan-Aug)
non_campaign = sales[sales['month'].astype(str) < '2026-09']['revenue'].mean()
campaign = sales[sales['month'].astype(str) == '2026-09']['revenue'].mean()
lift = (campaign / non_campaign - 1) * 100

print(f'Non-campaign daily avg: £{non_campaign:.0f}')
print(f'Campaign daily avg: £{campaign:.0f}')
print(f'Lift from campaign: {lift:.1f}%')
```

**A conclusion is not "calculated" — it is "stated clearly":** spell out the comparison's scope, base period, and magnitude. That is the actual deliverable of the report.

## The full pipeline at a glance

```python
def build_report(sales_table, promo_table):
    # 1. clean
    sales_table['revenue'] = pd.to_numeric(sales_table['revenue'], errors='coerce')
    sales_table = sales_table.dropna(subset=['revenue']).copy()
    sales_table['month'] = sales_table['date'].dt.to_period('M')

    # 2. join
    promo_table = promo_table.copy()
    promo_table['month'] = pd.to_datetime(promo_table['month']).dt.to_period('M')
    combined = sales_table.merge(promo_table, on=['shop', 'month'], how='left')

    # 3. aggregate
    monthly = sales_table.groupby(['shop', 'month'], observed=True)['revenue'].sum()

    # 4. time series
    daily = sales_table.groupby('date')['revenue'].sum().asfreq('D')
    daily_ma7 = daily.rolling(7, min_periods=1).mean()

    # 5. conclusion
    result = {
        'shop_ranking': sales_table.groupby('shop')['revenue'].sum()
                                   .sort_values(ascending=False).to_dict(),
        'trend_7d_avg': daily_ma7.round(0).to_dict(),
        'promo_coverage_days': int(combined['campaign'].notna().sum()),
    }
    return result
```

**Five linked stages:** dirty data cannot enter stage 2; a failed join starves stage 3; a missing date misaligns stage 4. **Cut a corner anywhere and everything after it is wrong.**

## Crash site: merge keys of mismatched types produce an empty join

```python
# WRONG
sales_table['month'] = '2026-01'               # string
promo_table['month'] = pd.to_datetime('2026-01')   # Timestamp
combined = sales_table.merge(promo_table, on='month')   # 0 rows!
print(len(combined))
```

**The types differ and pandas will not convert them for you** — the result is an empty table. Always run `print(df.dtypes)` on both sides before joining.

## Crash site: aggregating before joining loses granularity

```python
# WRONG
monthly_summary = sales_table.groupby(['shop', 'month']).sum().reset_index()
monthly_summary.merge(promo_table, on='month')   # shop detail is gone, only month remains
```

**Aggregating first collapses the row-level detail** (such as which day had a promotion). The correct order is: join first (keep the detail), then aggregate. When you need both detail and summary, use `.copy()` and split into two paths.

## Crash site: pct_change leaves NaN in the report

```python
# WRONG
report = sales_table.groupby('date')['revenue'].sum().pct_change()
print(report.iloc[0])    # NaN
```

**The first value is NaN and will render as a blank in the report.** Use `.fillna(0)` or `.dropna()` before output, and add a footnote such as "no day-on-day available for day one."

## Recap

- **A real report is a pipeline:** construct → clean → join → aggregate → time series → conclusion; the order cannot change
- **`errors='coerce'` + `dropna` is the standard cleaning pair**
- **Left joins preserve raw data, and key types must match**
- **`agg` produces multiple metrics at once**, far more efficient than repeated groupbys
- **`asfreq('D')` fills dates; `rolling(7)` reveals the trend**
- **A conclusion states the scope, base, and magnitude** — the numbers are only evidence
