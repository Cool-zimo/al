# Common Real-World Patterns: Email, Phone, IP, Date, URL

> This lesson stitches the syntax you've learned into ready-to-use patterns you can copy. It also makes a more important point: **don't chase the perfect regex**—good enough is good enough; boundary cases belong to business rules.

## Phone Numbers: 11 Digits, Second Digit 3-9

Mainland Chinese mobile numbers are 11 digits: the first is always 1, the second is 3-9 (corresponding to carrier number blocks).

```python
import re

PHONE_RE = re.compile(r'1[3-9]\d{9}')

text = "Alice 13812345678, Bob 13800138000, Charlie has only 13812"
print(PHONE_RE.findall(text))
```

Output:

```
['13812345678', '13800138000']
```

**Why `[3-9]` and not `[0-9]`**: historically the second digit has only used 3-9. New blocks like 12 have appeared recently, but for everyday data cleaning, hardcoding `[3-9]` covers the vast majority of real data. Writing `[0-9]` would wrongly admit strings like "10000000000" that are clearly not phone numbers.

## Crash Site: Writing a Regex That's "Too Perfect"

Alice spent an afternoon writing what she thought was the "perfect" email regex:

```python
# Overly long, hard to maintain, easy to miss edge cases
EMAIL_PERFECT = re.compile(
    r'^[a-zA-Z0-9.!#$%&\'*+/=?^_`{|}~-]+'
    r'@[a-zA-Z0-9](?:[a-zA-Z0-9-]{0,61}[a-zA-Z0-9])?'
    r'(?:\.[a-zA-Z0-9](?:[a-zA-Z0-9-]{0,61}[a-zA-Z0-9])?)+$'
)
```

Three days later someone registered an email with an internationalized domain name, and the regex broke again. In real production, **the correct approach to email validation is "reject obvious nonsense first, then send a verification email."**

```python
import re

# Good-enough email regex: something before and after @, at least one dot after @
EMAIL_RE = re.compile(r'[\w.+-]+@[\w-]+\.[\w.-]+')

text = "Contact support@acme.co or bug-report_01@test.org.cn"
print(EMAIL_RE.findall(text))
```

Output:

```
['support@acme.co', 'bug-report_01@test.org.cn']
```

**Core idea**: regex validates that something **looks like** a format—not that it **actually exists**. The only reliable way to confirm an email is real is to send a verification email.

## IP Address: Dotted-Quad Decimal

An IPv4 address is "four numbers from 0-255 separated by dots." Writing `\d+\.\d+\.\d+\.\d+` would also match `999.999.999.999`, so we need range constraints:

```python
import re

IP_RE = re.compile(r'(?:(?:25[0-5]|2[0-4]\d|1\d{2}|[1-9]?\d)\.){3}(?:25[0-5]|2[0-4]\d|1\d{2}|[1-9]?\d)')

text = "Servers 192.168.1.1 and 8.8.8.8, bad address 999.0.0.1"
print(IP_RE.findall(text))
```

Output:

```
['192.168.1.1', '8.8.8.8']
```

Read `(?:25[0-5]|2[0-4]\d|1\d{2}|[1-9]?\d)` as: either 250-255, or 200-249, or 100-199, or 0-99 (with optional leading zeros). The four alternatives listed out cover 0-255 exactly.

**Practical advice**: if you only need "looks like an IP," `\d+\.\d+\.\d+\.\d+` is plenty. Reach for the big block above only when you need strict range validation.

## Dates: YYYY-MM-DD and YYYY/MM/DD

```python
import re

DATE_RE = re.compile(r'(\d{4})[-/](\d{1,2})[-/](\d{1,2})')

text = "Shipped 2026-09-28, arrives 2026/10/05"
for m in DATE_RE.finditer(text):
    y, mo, d = m.groups()
    print(f"year={y} month={mo} day={d}")     # note: extract only, don't validate legality
```

Output:

```
year=2026 month=09 day=28
year=2026 month=10 day=05
```

**This regex does NOT validate date legality**: `2026-02-30` matches just fine. Real date validation belongs to `datetime.strptime` (covered in Volume 2)—**regex handles format, datetime handles semantics**. That's the cleanest division of labor.

## URLs: Starting With http/https

```python
import re

URL_RE = re.compile(r'https?://[\w.-]+(?:\.[\w.-]+)+(?:/[\w./?%&=~-]*)?')

text = "See https://www.python.org/doc and http://example.com/path?a=1"
print(URL_RE.findall(text))
```

Output:

```
['https://www.python.org/doc', 'http://example.com/path?a=1']
```

The `(?:/[\w./?%&=~-]*)?` part handles the path and query string; the trailing `?` means "optional"—the path after the domain might not exist.

## Crash Site: Putting the Dash in the Wrong Place in []

Inside `[]`, the dash `-` is a range operator. To make it a literal "matchable character," either **put it at the start or end** or **escape it**:

```python
import re

text = "version v1.2-rc and v1.3-beta"

# WRONG-ish: [.-] puts the dash in the middle where it could be read as a range
print(re.findall(r'[\w.-]+', text))    # happens not to error, but semantically unclear

# Correct: dash at the end makes it clearly a literal dash
print(re.findall(r'[\w.-]+', text))
```

Output:

```
['v1.2-rc', 'v1.3-beta']
```

`[\w.-]` and `[\w\.-]` do the same thing (dash at the end or escaped): "word character + dot + dash." Writing `[\w-]` with the dash in the middle and nothing after it—Python handles it literally, but many other regex engines will error out. Portability suffers.

## Summary

- Phone: `1[3-9]\d{9}`; Email: `[\w.+-]+@[\w-]+\.[\w.-]+` (good enough)
- Don't chase the perfect regex: looking valid ≠ actually existing; business validation means sending mail / checking a database
- Strict IP uses a big `|` enumeration of 0-255; loose IP uses `\d+\.\d+\.\d+\.\d+`
- Date regex validates format only; date legality belongs to `datetime.strptime`
- In character classes `[]`, put the dash at the end or escape it for cross-engine portability
