# Why Tests Matter

> This lesson covers the need for tests: you change one line and have no idea what else broke, and clicking through manually is slow. Tests are insurance for your code — a small price for a large saving.

## Change One Line, Break Three Things

Alice wrote a shopping cart checkout function:

```python
def checkout(cart, vip=False):
    total = sum(item["price"] * item["qty"] for item in cart)
    if vip:
        total *= 0.9   # VIP gets 10% off
    return round(total, 2)
```

Later the product manager says "VIPs should get 20% off", so Alice changes one line:

```python
    if vip:
        total *= 0.8   # changed here
```

**Looks harmless, right?** But if the code also has a "spend £100, get £10 off" offer, a points calculation, and a shipping calculation, all of which reference the discounted amount, changing 0.9 to 0.8 means every dependent piece needs re-verifying. Doing it by hand, one click at a time, eats a whole day.

**The value of tests**: change the code, run `pytest`, and 30 seconds later it tells you exactly what broke.

## How Slow Manual Testing Really Is

Bob's web project has 50 endpoints. Every release he tests them by hand:

| Step | Action | Time |
|---|---|---|
| Log in | open the browser, enter credentials | 30 seconds |
| Place order | select item, fill address, click submit | 1 minute |
| Refund | find the order, click refund | 1 minute |
| View order | paginate, apply filters | 30 seconds |
| ... | 50 endpoints | **roughly 2 hours** |

**Those two hours repeat after every code change.** Change things three times a day and six hours vanish into manual testing. An automated test suite runs in 30 seconds.

## A Real Incident Caused by No Tests

An e-commerce site's coupon calculation function:

```python
def calc_coupon(total, coupon):
    if coupon["type"] == "percent":
        return total * coupon["value"] / 100
    elif coupon["type"] == "fixed":
        return min(total, coupon["value"])
    return 0
```

Someone added a new coupon type, "shipping" (a shipping discount), and added a check at the call site but forgot to add it to `calc_coupon`:

```python
def apply_coupon(order, coupon):
    discount = calc_coupon(order["total"], coupon)
    order["total"] -= discount
    if coupon["type"] == "shipping":   # newly added logic
        order["shipping"] = 0
    return order
```

**Result**: a user picked a shipping coupon, `calc_coupon` returned 0 (it didn't recognise the type), shipping wasn't deducted, and the user overpaid. If a test had covered "a shipping coupon zeroes the shipping cost", this would have been caught before release.

## Crash Site: Using `print` as a Test

```python
def add(a, b):
    return a + b

print(add(1, 2))       # 3
print(add(-1, 1))      # 0
print(add(0, 0))       # 0
print("all good!")
```

Output:

```
3
0
0
all good!
```

**"all good!" was decided by a human looking at the output**, not by a machine. Alice saw it today and will have forgotten by tomorrow; Bob doesn't even know what to look for; three months from now nobody dares touch the function. `print` tests have fatal flaws:

- **No automatic judgement**: a human reads the output and humans miss things.
- **No regression protection**: changing the code doesn't re-run them automatically.
- **Not batchable**: dozens of cases can't be reviewed at a glance.
- **Mixed into production code**: they must be deleted before shipping.

## Crash Site: Changing the Test So It Passes

Charlie wrote a test, found a bug in the code, and instead of fixing the code, he changed the test's expected value:

```python
# code (has a bug)
def discount(total, vip):
    return total * 0.9 if vip else total

# test
def test_discount():
    assert discount(100, True) == 90   # 90, passes
    assert discount(100, False) == 90  # should be 100, but Charlie changed it to 90
```

**That's self-deception.** The whole point of a test is to catch a deviation between code and expectation; changing the expectation tells the test "I expect it to be wrong." Fix the code so it matches the real business requirement.

## Crash Site: Tests Only Ever Ran on the Development Machine

```bash
$ python test_cart.py
All tests passed!

$ ssh prod-server
$ python test_cart.py
ImportError: No module named 'requests'
```

**The development machine had every dependency installed; production didn't.** A test that only ran on your laptop might as well not have run at all. The fix: use a virtual environment plus `requirements.txt` to pin dependencies, and let CI (continuous integration) run the tests on a clean machine.

## Summary

- Changing one line can affect many places; tests are the only fast way to verify regressions.
- Manual testing is slow and non-repeatable; automated tests finish a full suite in 30 seconds.
- `print` is not a test: it lacks automatic judgement, regression protection, and batchability.
- Test expectations must never be changed just to make them pass — that's self-deception.
- Tests must run in a clean environment (CI), not just on a developer's machine.
- Tests are insurance for your code: they feel unnecessary until the day they save you.

## In-Class Exercise

```quiz
type: code
q: Write a few assertion tests for a function calc_price. It takes a unit price price and a quantity qty, returning the total (with a 10% discount when the quantity exceeds 10). Write at least 4 asserts covering: the normal case, exactly 10 items (no discount), 11 items (discount applies), and a qty of 0.
starter: |
  def calc_price(price, qty):
      if qty > 10:
          return round(price * qty * 0.9, 2)
      return price * qty

  # write test assertions here
  assert calc_price(10, 5) == 50
  assert calc_price(10, 10) == 100
  assert calc_price(10, 11) == 99.0
  assert calc_price(10, 0) == 0
  print("All tests passed")
tests:
- assert "All tests passed" in __out
- assert "assert calc_price(10, 11) == 99.0" in __out
hint: Cover both branches — qty<=10 (no discount) and qty>10 (10% off) — plus a boundary and a zero value.
explain: This is the simplest "test with assert", laying the groundwork for unittest and pytest later.
```
