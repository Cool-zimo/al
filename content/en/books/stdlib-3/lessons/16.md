# Logging Basics: Stop Debugging with `print`

> This lesson answers "why isn't `print` good enough?" and covers the five logging levels plus the correct use of `basicConfig`. Think of `print` as a sticky note you scribble on; `logging` is a proper system with severity, timestamps, and an on/off switch.

## Why `print` Falls Short

Alice wrote an order-processing script. When something broke, she littered it with `print("got here")` and `print(x)`. Before deploying she had to delete them line by line — and the ones she forgot leaked internal data straight to the user. Worse still:

- **No severity**: Which line means "this must be seen" and which is just a debugging note? They all look the same.
- **No way to silence**: You can't say "show debug info during development, hide it in production."
- **No time or location**: A bare `Error!` tells you nothing about when or where it happened.
- **One destination only**: It goes to the console and nowhere else — no file, no remote service.

```python
# Alice's print debugging
def process_order(order_id):
    print("Processing order", order_id)
    if order_id <= 0:
        print("Bad order id")
        return
    print("Done")
    return True

process_order(123)
process_order(-1)
```

Output:

```
Processing order 123
Done
Processing order -1
Bad order id
```

It looks usable, but run this on a server processing thousands of orders a day and that output is useless for diagnosis.

## The Five Levels of `logging`

The `logging` module defines five standard levels, listed here from **lowest to highest severity**:

| Level | Numeric Value | Typical Use |
|---|---|---|
| `DEBUG` | 10 | Implementation details, only useful during development |
| `INFO` | 20 | Confirmation that key parts of the system are working |
| `WARNING` | 30 | Something unexpected but non-fatal |
| `ERROR` | 40 | A failure that prevents a function from completing |
| `CRITICAL` | 50 | A severe error, the program may be unable to continue |

**A level is a filter**: set the threshold to `INFO` and every `DEBUG` record is automatically suppressed — no code changes required.

```python
import logging

logging.debug("Debugging details")        # not visible by default
logging.info("Application started")       # not visible by default
logging.warning("Disk almost full")       # visible
logging.error("Database connection lost") # visible
logging.critical("Out of memory, shutting down")  # visible
```

Output:

```
WARNING:root:Disk almost full
ERROR:root:Database connection lost
CRITICAL:root:Out of memory, shutting down
```

**The default level is `WARNING`**, which is why `DEBUG` and `INFO` don't appear. That's the whole "on/off" trick: change one setting instead of deleting lines.

## `basicConfig`: The Simplest Configuration

`logging.basicConfig()` is a quick setup entry point for small programs. One call sets the level, format, and destination.

```python
import logging

logging.basicConfig(
    level=logging.DEBUG,
    format="%(asctime)s [%(levelname)s] %(name)s - %(message)s",
    datefmt="%Y-%m-%d %H:%M:%S"
)

logging.debug("Debug: parsing config file")
logging.info("Info: user Alice logged in")
logging.warning("Warning: password expires in 3 days")
```

Output:

```
2026-09-28 10:30:00 [DEBUG] root - Debug: parsing config file
2026-09-28 10:30:00 [INFO] root - Info: user Alice logged in
2026-09-28 10:30:00 [WARNING] root - Warning: password expires in 3 days
```

**The placeholders in the format string are logging's own**: `%(asctime)s` for time, `%(levelname)s` for the level name, `%(name)s` for the logger name, `%(message)s` for the message. You'll use this exact vocabulary throughout the next lesson.

## Crash Site: `basicConfig` Appears to Do Nothing

The most common head-scratcher: you set `level=logging.DEBUG` but your `debug()` calls stay silent.

```python
import logging

logging.error("I got called first")   # first ever logging call; default config is locked in

logging.basicConfig(level=logging.DEBUG)  # too late! configuration was already set

logging.debug("This never shows up")
```

Output:

```
ERROR:root:I got called first
```

**`basicConfig` only works on the very first logging call.** Behind the scenes, logging uses lazy initialization: the moment any log call happens before configuration, a default setup is installed. `basicConfig` must come **before every other logging call**.

```python
import logging

logging.basicConfig(level=logging.DEBUG)  # first thing, every time

logging.debug("Now I can see this")
```

Output:

```
DEBUG:root:Now I can see this
```

## Crash Site: Sensitive Data Ends Up in the Logs

Bob logged an entire user request. Later, a teammate copied the log file, complete with ID numbers, phone numbers, and passwords.

```python
import logging

logging.basicConfig(level=logging.INFO, format="%(message)s")

def login(user, password):
    logging.info(f"User {user} attempting login, password is {password}")  # crash!
    return True

login("alice", "123456")
```

Output:

```
User alice attempting login, password is 123456
```

**Logs get retained, forwarded, and ingested by third parties** — never put a password, token, national ID, or card number in one. Do this instead:

```python
def login(user, password):
    logging.info(f"User {user} attempting login")
    # password only at debug level, and even then redacted
    logging.debug(f"password length={len(password)}")
```

**Never write anything to a log that you wouldn't pin to the office notice board.**

## Summary

- `print` has no severity, can't be silenced, carries no timestamp — it's only for throwaway debugging.
- The five levels are `DEBUG < INFO < WARNING < ERROR < CRITICAL`; the default is `WARNING`.
- A level acts as a filter: set it to `INFO` and every `DEBUG` is hidden automatically.
- `basicConfig` configures level, format, and time format in one call, but only before any other log call.
- `%(asctime)s`, `%(levelname)s`, and `%(message)s` are placeholders inside the format string.
- Logs must never contain passwords, tokens, or personal identification data.
