# functools: Caching, Partial Application, and Reduction

> This lesson covers the three most practical tools in `functools`: `lru_cache` cuts repeated computation to O(1); `partial` turns "binding arguments" into a new function; `reduce` folds a stream of values into one. Together they're core parts of writing in a functional style.

## lru_cache: Trading Cache for Speed

First, a naive Fibonacci:

```python
def fib(n):
    if n < 2:
        return n
    return fib(n - 1) + fib(n - 2)

print(fib(10))
print(fib(20))
```

Output:

```
55
6765
```

Looks fine, but `fib(30)` hangs for several seconds—because `fib(5)` gets computed thousands of times, recalculated from scratch every time.

**Add one decorator and it becomes instant**:

```python
from functools import lru_cache

@lru_cache(maxsize=None)
def fib(n):
    if n < 2:
        return n
    return fib(n - 1) + fib(n - 2)

print(fib(100))    # without caching, this would never finish in our lifetime
```

Output:

```
354224848179261915075
```

`fib(100)` returns instantly. `lru_cache`'s principle: **store each call's arguments and return value in a dict**; the next time you call with the same arguments, return the cached value without re-executing the function body.

## Crash Site: lru_cache Doesn't Work With Mutable Arguments

`lru_cache`'s key is "the tuple of arguments." If an argument is a **mutable object** (list, dict), it can't safely serve as a dict key:

```python
from functools import lru_cache

@lru_cache(maxsize=None)
def sum_list(lst):
    print(f"computing {lst}")
    return sum(lst)

sum_list([1, 2, 3])
sum_list([1, 2, 3])     # list is unhashable, so the cache misses and recomputes
```

Error:

```
TypeError: unhashable type: 'list'
```

**The fix**: use an immutable type like a tuple for arguments, or convert mutable objects into an immutable form.

```python
from functools import lru_cache

@lru_cache(maxsize=None)
def sum_tuple(tup):
    print(f"computing {tup}")
    return sum(tup)

sum_tuple((1, 2, 3))
sum_tuple((1, 2, 3))     # tuple is hashable; cache hits, "computing" is not printed again
```

Output:

```
computing (1, 2, 3)
6
6
```

The second call **did not** print "computing"—meaning it hit the cache and the function body didn't run again.

## partial: "Freeze" Arguments Into a New Function

`partial` pre-binds **some arguments** of a function and returns a new function:

```python
from functools import partial

def power(base, exp):
    return base ** exp

square = partial(power, exp=2)      # freeze exp at 2
cube   = partial(power, exp=3)      # freeze exp at 3

print(square(5))
print(cube(5))
print(square(10))
```

Output:

```
25
125
100
```

`square` is a new function with "only `base` left unfilled." It's similar in effect to "writing a lambda by hand," but **clearer in intent, marginally faster, and it carries metadata like `__name__`.**

## Crash Site: partial's Positional-Argument Ordering

```python
from functools import partial

def divide(a, b):
    return a / b

# Want "divide by 2"; should freeze b at 2
half = partial(divide, b=2)

print(half(10))      # 10 / 2 = 5
print(half(a=20))    # keyword also works
```

Output:

```
5.0
10.0
```

But with positional arguments, the order must align:

```python
from functools import partial

def divide(a, b):
    return a / b

# WRONG: a positional arg fills the first parameter a, so a becomes 2
half = partial(divide, 2)
print(half(10))      # actually divide(2, 10) = 0.2
```

Output:

```
0.2
```

**The fix**: when binding later parameters with `partial`, **always use keyword arguments** to avoid positional mismatch.

## reduce: "Folding" a Stream of Values Into One

`reduce` applies a **binary function** across a sequence, reducing n values into 1:

```python
from functools import reduce

nums = [1, 2, 3, 4, 5]

# reduce(function, sequence) => merge cumulatively
result = reduce(lambda acc, x: acc + x, nums)
print("sum:", result)

# The third argument is the initial value
product = reduce(lambda acc, x: acc * x, nums, 1)
print("product:", product)
```

Output:

```
sum: 15
product: 120
```

Here's how it unfolds: first `1+2=3`, then `3+3=6`, then `6+4=10`, then `10+5=15`. `reduce` is "folding a binary operation all the way down."

## Crash Site: reduce on an Empty Sequence With No Initial Value Crashes

```python
from functools import reduce

# WRONG: empty sequence + no initial value
print(reduce(lambda a, b: a + b, []))
```

Error:

```
TypeError: reduce() of empty sequence with no initial value
```

**The fix**: pass an initial value; `reduce` will use it as "the left operand of the first computation":

```python
from functools import reduce

print(reduce(lambda a, b: a + b, [], 0))      # empty sum is 0
print(reduce(lambda a, b: a * b, [], 1))      # empty product is 1
```

Output:

```
0
1
```

**Rule of thumb**: **always pass an initial value** to `reduce`. This was Guido's own advice, and one reason Python 3 moved `reduce` out of built-ins and into `functools`—it's not a universal tool. For simple cases, `sum()`, `max()`, `any()` are clearer.

## Summary

- `lru_cache` caches repeated calls with identical arguments; the speedup is most dramatic for recursion (like Fibonacci)
- `lru_cache` requires arguments to be **hashable**; lists/dicts as arguments cause TypeError—use tuples or other immutable types
- `partial` binds some arguments into a new function; when binding later parameters, **use keyword arguments** to avoid positional mismatch
- `reduce` applies a binary function cumulatively across a sequence, folding n values into 1
- `reduce` errors on an empty sequence with no initial value—**always passing one is safer**
- For simple aggregation (sum, max), prefer `sum()`/`max()`; don't force reduce
