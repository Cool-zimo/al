# Test Organisation: One Function Per Test, Boundary Values, Repeatability

> This lesson covers how to organise tests so they're reliable: one test verifies one thing, covers boundary values (empty, single, huge), and produces stable, repeatable results — no leaning on randomness or the current time.

## One Function, One Test

A good test "verifies exactly one thing." Compare the two styles:

```python
# wrong: one test verifies three things
def test_cart(self):
    cart = Cart()
    cart.add("apple", 2)
    self.assertEqual(cart.total, 2)        # verifies adding
    cart.remove("apple")
    self.assertEqual(cart.total, 0)        # verifies removing
    cart.apply_coupon("VIP")
    self.assertEqual(cart.discount, 0.1)   # verifies the coupon

# right: one behaviour per test
def test_add_item(self):
    cart = Cart()
    cart.add("apple", 2)
    self.assertEqual(cart.total, 2)

def test_remove_item(self):
    cart = Cart()
    cart.add("apple", 2)
    cart.remove("apple")
    self.assertEqual(cart.total, 0)

def test_apply_coupon(self):
    cart = Cart()
    cart.apply_coupon("VIP")
    self.assertEqual(cart.discount, 0.1)
```

**Why split them?** If `remove` has a bug, the first version only reports "test_cart failed" and you won't know whether adding, removing, or the coupon is at fault. Splitting tells you `test_remove_item` failed, cutting diagnosis from ten minutes to ten seconds.

## Boundary Values: Empty, Single, Huge

Any function operating on a collection should be tested against these input classes:

```python
import unittest

def average(nums):
    if not nums:
        raise ValueError("list cannot be empty")
    return sum(nums) / len(nums)

class TestAverage(unittest.TestCase):
    def test_empty(self):
        # boundary: empty list
        with self.assertRaises(ValueError):
            average([])

    def test_single(self):
        # boundary: exactly one element
        self.assertEqual(average([42]), 42.0)

    def test_normal(self):
        self.assertEqual(average([1, 2, 3]), 2.0)

    def test_large(self):
        # boundary: extremely large values
        self.assertEqual(average([10**15, 10**15]), 10**15)

    def test_negative(self):
        self.assertEqual(average([-2, 2]), 0.0)

    def test_float(self):
        self.assertAlmostEqual(average([0.1, 0.2, 0.3]), 0.2)

if __name__ == "__main__":
    unittest.main()
```

Output:

```
......
----------------------------------------------------------------------
Ran 6 tests in 0.000s

OK
```

**`assertAlmostEqual` is for comparing floats** — `0.1 + 0.2` isn't exactly `0.3` in a computer, so `==` would fail.

## Crash Site: Tests That Depend on Randomness Are Unstable

```python
import unittest
import random

def pick_winner(players):
    return random.choice(players)

class TestWinner(unittest.TestCase):
    def test_pick(self):
        players = ["Alice", "Bob", "Charlie"]
        winner = pick_winner(players)
        self.assertEqual(winner, "Alice")   # sometimes passes, sometimes fails
```

**`random.choice`'s result isn't deterministic**, so this test is flaky — it passes sometimes and fails others. Once it sneaks into CI, you get false alarms ("the code didn't change but the tests went red") until nobody trusts the test results anymore.

The fix: **seed the random number generator during testing, or mock out the randomness source.**

```python
class TestWinner(unittest.TestCase):
    def test_pick(self):
        players = ["Alice", "Bob", "Charlie"]
        random.seed(42)   # fixed seed, predictable result
        winner = pick_winner(players)
        self.assertEqual(winner, "Charlie")   # fixed result under seed 42
```

**Alternatively, replace the randomness source with `unittest.mock`**, making the test fully controllable.

## Crash Site: Tests That Depend on the Current Time

```python
import unittest
from datetime import datetime

def is_expired(deadline_str):
    deadline = datetime.fromisoformat(deadline_str)
    return datetime.now() > deadline

class TestExpired(unittest.TestCase):
    def test_expired(self):
        self.assertTrue(is_expired("2020-01-01"))   # passes in 2026
        self.assertFalse(is_expired("2030-01-01"))  # will fail in 2030
```

**The second assertion will fail in 2030** — the test depends on the external state of "current time." The fix: pass time in as a parameter, or mock `datetime.now`.

```python
from unittest.mock import patch

class TestExpired(unittest.TestCase):
    def test_expired(self):
        fixed_now = datetime(2026, 9, 28)
        with patch("datetime.datetime") as mock_dt:
            mock_dt.now.return_value = fixed_now
            mock_dt.fromisoformat = datetime.fromisoformat
            self.assertFalse(is_expired("2030-01-01"))
```

**Time, random numbers, and network requests — every external dependency must be controllable**, otherwise the tests aren't repeatable.

## Crash Site: Tests Sharing State

```python
import unittest

_database = []   # module-level shared state

def test_insert(self):
    _database.append("a")
    self.assertEqual(len(_database), 1)

def test_clear(self):
    _database.clear()
    self.assertEqual(len(_database), 0)
```

**If `test_clear` runs before `test_insert`, `test_insert` will behave differently because `_database` is already empty.** Test execution order should never affect the outcome. Reset state in `setUp`:

```python
class TestDB(unittest.TestCase):
    def setUp(self):
        self.db = []   # a brand-new empty list for every test

    def test_insert(self):
        self.db.append("a")
        self.assertEqual(len(self.db), 1)

    def test_clear(self):
        self.db.append("x")
        self.db.clear()
        self.assertEqual(len(self.db), 0)
```

## Crash Site: The Precision Trap in `assertAlmostEqual`

```python
import unittest

class TestFloat(unittest.TestCase):
    def test_money(self):
        result = 0.1 + 0.2
        self.assertEqual(result, 0.3)   # fails!
```

Output:

```
FAIL: test_money
AssertionError: 0.30000000000000004 != 0.3
```

**Floating-point precision.** For financial calculations, don't use `float` — use `decimal.Decimal`. In tests, use `assertAlmostEqual(actual, expected, places=2)` to set the precision explicitly.

## Summary

- One test verifies one thing; when it fails you go straight to the specific behaviour.
- Boundary values are mandatory: empty lists, single elements, huge and tiny numbers, negatives, floats.
- Compare floats with `assertAlmostEqual`, never with `==`.
- Tests must not depend on randomness or the current time, or they won't be repeatable.
- Seed the random generator or mock external dependencies to isolate them.
- Tests must share no state; use `setUp` to give every test a clean environment.
- An unreliable (flaky) test is worse than no test — it teaches people to ignore results.

## In-Class Exercise

```quiz
type: code
q: Write a function safe_divide and its tests. safe_divide(a, b) returns None when b==0 and a/b otherwise. Write three tests: test_normal (10/2==5), test_zero (b=0 returns None), and test_float (3/2==1.5, using assertAlmostEqual). Organise them with unittest.TestCase.
starter: |
  import unittest

  def safe_divide(a, b):
      if b == 0:
          return None
      return a / b

  class TestSafeDivide(unittest.TestCase):
      def test_normal(self):
          self.assertEqual(safe_divide(10, 2), 5)

      def test_zero(self):
          self.assertIsNone(safe_divide(10, 0))

      def test_float(self):
          self.assertAlmostEqual(safe_divide(3, 2), 1.5)

  if __name__ == "__main__":
      unittest.main()
tests:
- assert "test_normal" in __out or "Ran 3 tests" in __out
- assert "assertIsNone" in __out
hint: The three test_ methods use assertEqual, assertIsNone, and assertAlmostEqual respectively.
explain: This covers normal, boundary (division by zero), and float scenarios — a practical exercise in boundary-value testing.
```
