# Logging In Depth: Loggers, Handlers, and Formatters

> This lesson lays out the internal architecture of the logging system: a logger decides what to emit, a handler decides where it goes, and a formatter decides how it looks. Plus two classic traps — never call `basicConfig` in every module, and beware of duplicate output.

## How the Three Fit Together

Picture the logging system as a postal service:

- **Logger**: the sender. Calling `logger.info("...")` drops a letter into the system.
- **Handler**: the delivery route. Where does the letter go? Console? File? Network?
- **Formatter**: the envelope layout. What's written on it? Time? Sender address?

One logger can carry several handlers, which gives you "a short version on screen, a detailed version in the file."

```python
import logging

# 1. Get a logger (named, so you can tell modules apart)
logger = logging.getLogger("myapp")

# 2. Create a handler (send to the console)
console_handler = logging.StreamHandler()
console_handler.setLevel(logging.WARNING)  # console shows WARNING and above only

# 3. Create a formatter
fmt = logging.Formatter("%(asctime)s [%(levelname)s] %(message)s")
console_handler.setFormatter(fmt)

# 4. Attach the handler to the logger
logger.addHandler(console_handler)
logger.setLevel(logging.DEBUG)  # the logger's own gate

logger.debug("debugging detail")   # passes the logger gate, blocked by the handler
logger.warning("warning message") # passes both gates, so it's emitted
```

Output:

```
2026-09-28 10:30:00 [WARNING] warning message
```

**There are two gates**: the logger's level is the master switch (`DEBUG`, letting everything through), and the handler's level is a per-route filter (`WARNING`, only letting warnings through). A record must clear both.

## Namespacing in `getLogger`

`getLogger("a.b.c")` isn't just decorative — those dots form a **hierarchy**, and a child logger propagates messages to its parent by default.

```python
import logging

parent = logging.getLogger("parent")
child = logging.getLogger("parent.child")

handler = logging.StreamHandler()
handler.setFormatter(logging.Formatter("%(name)s - %(levelname)s - %(message)s"))
parent.addHandler(handler)
parent.setLevel(logging.DEBUG)

child.debug("a message from the child logger")
```

Output:

```
parent.child - DEBUG - a message from the child logger
```

**The parent-child relationship is automatic**: names separated by dots mean the child's messages bubble up to the parent's handlers. That's the mechanism behind centrally controlled module-level logging.

## Crash Site: Calling `basicConfig` in Every Module

Charlie's project has twenty files, each opening with `logging.basicConfig(...)`. Only the first one took effect; the rest were silently ignored.

```python
# a.py
import logging
logging.basicConfig(level=logging.DEBUG, format="A: %(message)s")

# b.py
import logging
logging.basicConfig(level=logging.INFO, format="B: %(message)s")

# main.py
import a  # imported first
import b  # imported second

import logging
logging.info("testing")
```

Output:

```
A: testing
```

**`basicConfig` is globally unique and only runs once.** Calling it repeatedly in multiple modules is a no-op after the first. The fix: configure it exactly once at the program entry point (e.g. `main.py`); every other module uses `getLogger(__name__)`.

```python
# utils.py (the correct submodule pattern)
import logging
logger = logging.getLogger(__name__)  # module name becomes the logger name

def do_something():
    logger.info("utils is doing work")

# main.py (the entry point, configured once)
import logging
logging.basicConfig(level=logging.INFO, format="%(name)s - %(message)s")
import utils
utils.do_something()
```

Output:

```
__main__ - utils is doing work
```

## Crash Site: The Same Log Line Appears Twice, Then Three Times

This is the most common complaint from newcomers: one record prints twice, then three times.

```python
import logging

logger = logging.getLogger("dup")

# first addHandler
h1 = logging.StreamHandler()
h1.setFormatter(logging.Formatter("handler1: %(message)s"))
logger.addHandler(h1)

# second addHandler (duplicate!)
h2 = logging.StreamHandler()
h2.setFormatter(logging.Formatter("handler2: %(message)s"))
logger.addHandler(h2)

logger.warning("one message")
```

Output:

```
handler1: one message
handler2: one message
```

**The same logger grew two handlers, so the message is emitted once per handler.** This is especially easy to hit in interactive shells or during repeated imports.

More subtly, there's **propagation**: a child logger's messages bubble up to its parent (all the way to root) by default, so if the parent also has a handler, you get duplicates.

```python
import logging

root_handler = logging.StreamHandler()
root_handler.setFormatter(logging.Formatter("root: %(message)s"))
logging.getLogger().addHandler(root_handler)  # root logger now has a handler

child = logging.getLogger("child")
child_handler = logging.StreamHandler()
child_handler.setFormatter(logging.Formatter("child: %(message)s"))
child.addHandler(child_handler)

child.warning("a message")  # travels through child handler AND bubbles to root handler
```

Output:

```
child: a message
root: a message
```

**Two fixes**: either set the child's `propagate` to `False`, or only configure handlers on the root logger and let children bubble instead of adding their own.

```python
child.propagate = False  # stop bubbling to the parent
child.warning("a message")    # emitted exactly once
```

Output:

```
child: a message
```

## Crash Site: Adding a Handler After `basicConfig` Skews the Levels

```python
import logging

logging.basicConfig(level=logging.DEBUG)
logger = logging.getLogger()

# basicConfig already added a handler to root
# now we add another one by hand
h = logging.StreamHandler()
h.setLevel(logging.ERROR)
logger.addHandler(h)

logger.info("an info message")
logger.error("an error message")
```

Output:

```
INFO:root:an info message
ERROR:root:an error message
ERROR:root:an error message
```

**`info` appears once (the basicConfig handler emits it) while `error` appears twice** — both handlers passed it through. This is another source of duplicates: forgetting that `basicConfig` already installed a handler.

## Summary

- A logger emits, a handler picks a destination, a formatter sets the appearance; each has a single job.
- A record clears two gates: the logger's level (master) and the handler's level (per-route).
- `getLogger("a.b.c")` creates parent-child relationships; children bubble up by default.
- **Don't call `basicConfig` in every module** — configure once at the entry point, use `getLogger(__name__)` elsewhere.
- `basicConfig` is globally effective exactly once; repeat calls do nothing.
- The two causes of duplicate output: the same logger grew duplicate handlers, or a child logger's messages bubbled into a parent's handler.
- Fix duplication by auditing handler counts and, when needed, setting `propagate = False`.

  console.setFormatter(logging.Formatter("console: %(message)s"))

  logger.warning("low stock")

  # return the handler count
  print(len(logger.handlers))

- assert "console: low stock" in __out
- assert "2" in __out
