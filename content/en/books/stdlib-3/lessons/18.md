# Logging in Practice: What Developers Need vs. What Users Need

> This lesson covers the two audiences for log output: developers want detailed exception traces and context; users want one plain sentence. It also covers logging exceptions with `exc_info` and rotating files by date.

## Two Audiences, Two Kinds of Log

Inside any system, two groups read logs and their needs are completely different:

| Audience | Needs | Example |
|---|---|---|
| Developers | Exception tracebacks, variable values, call chains | `ERROR order.py:45 process_order() - KeyError: 'sku'` |
| End users | One plain sentence they can understand | `Order submission failed, please try again later` |

**Mixing the two is a disaster**: pasting `Traceback (most recent call last)...` at a user teaches them nothing and looks like the program crashed. Logging only "operation failed" leaves developers with no线索 (no clue) when they try to diagnose it.

```python
import logging

dev_logger = logging.getLogger("dev")
dev_logger.addHandler(logging.StreamHandler())
dev_logger.handlers[0].setFormatter(
    logging.Formatter("%(levelname)s %(filename)s:%(lineno)d %(funcName)s - %(message)s")
)

def process_order(order):
    try:
        result = order["sku"] / order["qty"]
    except KeyError as e:
        # for the developer: full exception traceback
        dev_logger.error(f"Missing order field: {e}", exc_info=True)
        # for the user: one plain sentence
        return "Order information is incomplete, please check and retry"
    return result

print(process_order({"qty": 2}))
```

Output:

```
ERROR 18_practice.py:12 process_order - Missing order field: 'sku'
Traceback (most recent call last):
  File "18_practice.py", line 10, in process_order
    result = order["sku"] / order["qty"]
KeyError: 'sku'
Order information is incomplete, please check and retry
```

**`exc_info=True` is the key**: it writes the complete current traceback into the log. Without it you only see "something broke" and have no idea which line caused it.

## Crash Site: Swallowing the Exception Leaves the Log Empty

Dana wrote a "universal" exception handler that catches `Exception` and logs a bare "something went wrong".

```python
import logging

logging.basicConfig(level=logging.ERROR, format="%(message)s")

def divide(a, b):
    try:
        return a / b
    except Exception:
        logging.error("something went wrong")   # no exc_info, no variable values
        return None

divide(1, 0)
```

Output:

```
something went wrong
```

**"something went wrong" has zero diagnostic value** — you don't know what exception it was, what arguments were passed, or which line. The correct version:

```python
def divide(a, b):
    try:
        return a / b
    except Exception as e:
        logging.error(f"Division failed: a={a}, b={b}, exception={e}", exc_info=True)
        return None

divide(1, 0)
```

Output:

```
Division failed: a=1, b=0, exception=division by zero
Traceback (most recent call last):
  File "<stdin>", line 3, in divide
ZeroDivisionError: division by zero
```

**Always include the key variable values in the log line** — they're your only evidence after the fact. Without them you're guessing.

## Crash Site: Showing the Stack Trace Directly to the User

```python
import logging

def pay(amount):
    try:
        # simulate a payment failure
        raise ConnectionError("Bank API timed out")
    except Exception as e:
        return str(e)  # hand the raw technical exception to the user

print(pay(100))
```

Output:

```
Bank API timed out
```

That looks harmless — but what about an uncaught internal exception:

```
TypeError: 'NoneType' object is not subscriptable
  File "/app/payment.py", line 88, in _do_pay
    bank_resp["data"]["code"]
```

**Exposing the raw internal exception tells the user your code structure, your library versions, and your server paths** — it's both ugly and unsafe. The correct pattern:

```python
def pay(amount):
    try:
        raise ConnectionError("Bank API timed out")
    except Exception:
        logging.exception("Payment failed, manual follow-up required")  # detail for developers
        return "Payment could not be completed right now; we have logged it and will follow up"  # plain words for users

print(pay(100))
```

Output:

```
Payment could not be completed right now; we have logged it and will follow up
```

## Rotating by Day: Don't Let the Log File Grow to Tens of Gigabytes

A long-running program — a web service, a crawler — keeps appending. A single file can hit tens of gigabytes and become impossible to open. Use `TimedRotatingFileHandler` to split it by time:

```python
import logging
from logging.handlers import TimedRotatingFileHandler

logger = logging.getLogger("app")
logger.setLevel(logging.INFO)

# rotate at midnight every day, keep 7 backups
handler = TimedRotatingFileHandler(
    "app.log",
    when="midnight",   # rotate at midnight
    interval=1,        # every 1 day
    backupCount=7      # how many backups to keep
)
handler.setFormatter(logging.Formatter("%(asctime)s %(levelname)s %(message)s"))
logger.addHandler(handler)

logger.info("service started")
```

**After rotation you get files like `app.log.2026-09-28` and `app.log.2026-09-29`**; once you exceed seven, the oldest is deleted automatically. There's also `RotatingFileHandler`, which rotates by file size (e.g. split when one file goes over 10 MB).

## Summary

- Logs serve two audiences: developers need traces and variables; users need one plain sentence.
- `exc_info=True` (or `logging.exception`) captures the full traceback and is central to diagnosing failures.
- Exception logs should include key variable values, otherwise you can't reconstruct the scene.
- Never return a raw internal exception to the user — translate it into a friendly message.
- `TimedRotatingFileHandler` rotates by time; `RotatingFileHandler` rotates by size.
- Long-running programs must rotate logs, or a single file grows beyond manageability.
