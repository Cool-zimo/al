# When Not to Use Regex

> This lesson is about **knowing when to stop**. Regex isn't a silver bullet: it loses to dedicated tools for structured text, and for simple splitting, string methods are faster and more readable. Learning to judge "this isn't worth a regex" is more valuable than learning more regex syntax.

## Don't Use Regex to Parse HTML

HTML is **nested structure**: tags wrap inside one another. Regex is a **one-dimensional linear pattern**—the two don't operate in the same dimension. Alice wants to extract every link from a web page:

```python
import re

html = '<a href="https://a.com">A</a><a href="https://b.com">B</a>'

# Looks like it works
print(re.findall(r'href="(.*?)"', html))
```

Output:

```
['https://a.com', 'https://b.com']
```

This time it "happens" to work. But the moment the HTML contains a **newline** or **single quotes**, or the attributes appear in a different order, the regex fails:

```python
import re

html = """<a
  href='https://a.com'
  target='_blank'>A</a>"""

print(re.findall(r'href="(.*?)"', html))   # single quotes + newline, both miss
```

Output:

```
[]
```

**The fix**: use a dedicated HTML parser. `html.parser` (from the standard library) or the third-party `BeautifulSoup` first builds the HTML into a tree; you then fetch by tag and by attribute—rock solid.

```python
from html.parser import HTMLParser

class LinkParser(HTMLParser):
    def __init__(self):
        super().__init__()
        self.links = []
    def handle_starttag(self, tag, attrs):
        if tag == 'a':
            for name, value in attrs:
                if name == 'href':
                    self.links.append(value)

p = LinkParser()
p.feed("""<a
  href='https://a.com'
  target='_blank'>A</a>""")
print(p.links)
```

Output:

```
['https://a.com']
```

Newlines, single vs. double quotes, and attribute order no longer matter. **Structured text belongs in tools that understand structure.**

## Don't Use Regex to Parse JSON

`json` was covered in Volume 2. Using regex to pry values out of JSON means hand-rolling a broken JSON parser:

```python
import re

raw = '{"name": "Alice", "tags": ["a", "b"]}'

# WRONG: regex can't pull out the tags array
print(re.findall(r'"name": "(.*?)"', raw))
```

Output:

```
['Alice']
```

But the moment a value contains an escaped quote `\"` or nested structures, regex falls apart. Meanwhile `json.loads` does it in one line:

```python
import json

data = json.loads(raw)
print(data['tags'])
```

Output:

```
['a', 'b']
```

**Decision rule**: if the input is **structured data** (has keys, hierarchy, arrays), use `json`, `csv`, or `configparser`. If it's **plain text** (logs, chat transcripts, natural language), regex is the right tool.

## Crash Site: Using Regex for a Simple Task Is Slower and Harder to Read

The regex engine has startup and compilation overhead. For **extremely simple** tasks like "split, check a prefix, strip whitespace," string methods are not only faster but universally understandable.

```python
import re

text = "apples, bananas, oranges, melons"

# With regex: compile, understand the pattern, handle possible whitespace
print(re.split(r',\s*', text))

# With string methods: obvious at a glance, no thinking required
print([x.strip() for x in text.split(',')])
```

Output:

```
['apples', 'bananas', 'oranges', 'melons']
['apples', 'bananas', 'oranges', 'melons']
```

Checking a prefix is another example:

```python
import re

filename = "data_2026.csv"

# Regex: higher cost to write wrong, higher maintenance cost
print(bool(re.match(r'data_', filename)))

# startswith: the intent is obvious
print(filename.startswith("data_"))
```

Output:

```
True
True
```

**Principle**: when `split`, `startswith`, `endswith`, `strip`, or `replace` can solve it in three lines, **don't reach for regex**. Regex's value is in "complex patterns," not in "being able to do string operations."

## Decision Checklist

Before writing a regex, ask three questions:

| Question | If yes | Conclusion |
|---|---|---|
| Does the input have nesting/hierarchy? | Yes | Use a dedicated parser (HTML/JSON/XML) |
| Is the pattern just a simple action like "split / prefix / strip"? | Yes | Use string methods |
| Is the pattern genuinely complex (multiple formats, need grouping)? | Yes | Use regex |

```python
def choose_tool(text, goal):
    """Three questions, one answer"""
    if goal == "parse_html":
        return "use html.parser or BeautifulSoup"
    if goal == "parse_json":
        return "use json.loads"
    if goal in ("split", "prefix", "strip", "replace"):
        return "use string methods"
    return "use regex"

print(choose_tool("", "parse_html"))
print(choose_tool("", "split"))
print(choose_tool("", "extract_phone"))
```

Output:

```
use html.parser or BeautifulSoup
use string methods
use regex
```

## Crash Site: Using Regex as Full-Text Search

Alice wanted to find the word "Python" in an English passage and wrote:

```python
import re

text = "I'm learning Python and python"
print(re.findall(r'python', text))      # case-sensitive by default, misses the capital
```

Output:

```
['python']
```

If all you want is "find this word somewhere," the `in` operator is more direct. For case insensitivity, use `re.IGNORECASE`—or just `.lower()` first and then `in`.

```python
text = "I'm learning Python and python"
print("python" in text.lower())        # True
```

**The `in` operator is O(n) but with a tiny constant and zero compilation overhead.** For a short text and a one-off lookup, it's the best answer.

## Summary

- HTML is nested structure, regex is one-dimensional—they're dimensionally mismatched. Use `html.parser` or BeautifulSoup
- JSON belongs to `json.loads`; prying values out with regex means hand-rolling a broken parser
- Structured data (with keys and hierarchy) uses dedicated modules; plain text is where regex belongs
- Simple actions (split, prefix, strip) belong to `split`/`startswith`/`strip`—faster and more readable
- The standard for "should I use regex": structural complexity > regex value; otherwise string methods win
- For one-off lookups on short text, `in` beats regex
