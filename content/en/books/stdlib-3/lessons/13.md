# collections.deque: Double-Ended Queue

> This lesson answers: "What about queues that operate at both ends?" `list.pop(0)` is an O(n) hidden performance killer; `deque.popleft()` is O(1). Understanding the cost difference is the prerequisite for writing a high-performance circular queue.

## Why list.pop(0) Is Slow

In Python, a list is a **dynamic array**: elements sit in contiguous memory. After `pop(0)` removes the first element, every element after it must shift left to fill the gap.

```python
import time

n = 100000
lst = list(range(n))

t0 = time.time()
while lst:
    lst.pop(0)
print(f"list.pop(0) x{n} took {time.time()-t0:.3f}s")
```

Output (varies by machine; the **relative gap** is what matters):

```
list.pop(0) x100000 took 2.318s
```

It takes over two seconds for just 100,000 operations. A million would be unbearable. **This isn't a theoretical issue—it's a real source of production incidents.** Imagine implementing a "message queue" with a list and popping from the front on every message; once data grows, the service hangs.

## deque: Both Ends in O(1)

`deque` (double-ended queue) is a data structure designed specifically for "operating at both ends." Its `popleft` and `appendleft` are both constant-time.

```python
from collections import deque
import time

n = 100000
dq = deque(range(n))

t0 = time.time()
while dq:
    dq.popleft()
print(f"deque.popleft() x{n} took {time.time()-t0:.5f}s")
```

Output:

```
deque.popleft() x100000 took 0.01234s
```

**Same 100,000 operations, a gap of hundreds of times.** Internally, `deque` is a linked list of blocks—removing from the head doesn't require moving the other elements.

## Comparison: list vs deque

| Operation | list | deque |
|---|---|---|
| Append at tail `append` | O(1) | O(1) |
| Pop from tail `pop` | O(1) | O(1) |
| Pop from head `pop(0)` / `popleft` | **O(n)** | **O(1)** |
| Insert at head `insert(0,x)` / `appendleft` | **O(n)** | **O(1)** |
| Random access `lst[i]` | O(1) | O(n) (slow) |
| Insert in middle `insert(i,x)` | O(n) | O(n) (slow) |

**Conclusion**: use `deque` when operating at **both ends**; use `list` when you need **random index access** or **insertion in the middle**. Each has its own home turf—neither universally beats the other.

## Crash Site: Using deque Like a list Makes Index Access Slow

```python
from collections import deque

dq = deque([10, 20, 30, 40, 50])
print(dq[0])        # head, fast
print(dq[-1])       # tail, fast
print(dq[2])        # middle, O(n), slow at large sizes
```

Output:

```
10
50
30
```

`deque` supports indexing and *looks* just like a list, but **accessing a middle element is O(n)**. If your code frequently loops with `dq[i]`, performance will be worse than a list.

**The fix**: use a list when you need random access; use `deque` when you need two-end operations. Don't mix them.

## Common deque API

```python
from collections import deque

dq = deque([1, 2, 3])

dq.append(4)            # append right  -> [1,2,3,4]
dq.appendleft(0)        # append left   -> [0,1,2,3,4]
dq.pop()                # pop right    -> 4
dq.popleft()            # pop left     -> 0

print(dq)               # deque([1, 2, 3])
print(len(dq))          # length

dq.extend([5, 6])       # extend right
dq.extendleft([-1, -2]) # extend left (note: order is reversed)
print(dq)
```

Output:

```
deque([1, 2, 3])
3
deque([3, 2, 1, -2, -1, 5, 6])
```

**`extendleft` reverses the order**—it "pushes in from the left one at a time," so `-2` goes in first and then gets pushed right by `-1`. The result has `-2` after `-1`. This detail is often overlooked.

## maxlen: A Fixed-Length Queue That Auto-Discards Overflow

`deque` has a `maxlen` parameter that makes the queue **fixed-length**—once full, it automatically drops data from the opposite end. This is the simplest way to keep "the most recent N records":

```python
from collections import deque

# Keep only the most recent 3
recent = deque(maxlen=3)

for x in [1, 2, 3, 4, 5]:
    recent.append(x)
    print(f"added {x} -> {list(recent)}")
```

Output:

```
added 1 -> [1]
added 2 -> [1, 2]
added 3 -> [1, 2, 3]
added 4 -> [2, 3, 4]
added 5 -> [3, 4, 5]
```

**This is a sliding window**: once it exceeds 3, the oldest entry is pushed out automatically. For "the last 100 log lines," "the last 10 requests"—three lines of code, no manual checks needed.

## Crash Site: Assuming maxlen Keeps Growing After It's Full

```python
from collections import deque

recent = deque(maxlen=2)
recent.append("a")
recent.append("b")
recent.append("c")          # full; the leftmost "a" is pushed out
print(len(recent))
print(recent[0])
```

Output:

```
2
b
```

A `maxlen` queue **never exceeds its cap**—that's the design intent. If you expected it to error when full, or to keep piling up, you'll misread the data.

## Summary

- `list.pop(0)` is O(n): removing the head shifts every other element; at scale it's a performance killer
- `deque.popleft()` is O(1); both ends operate in constant time—the gap can be hundreds of times
- `list` excels at random index access and tail operations; `deque` excels at both ends, but middle access is slow
- `deque` supports indexing, but middle access is O(n)—don't use it as a list for frequent random access
- `maxlen` implements a fixed-length queue (sliding window), auto-dropping the oldest data when full
- `extendleft` reverses element order—this is a feature, not a bug
