# Introducing pytest: Why So Many People Use It

> This lesson covers pytest's core strengths: a far simpler assertion syntax and the fixture mechanism. It also explains how pytest relates to unittest. No installation required — this is concepts and comparison only.

## Cleaner Assertions

unittest requires memorising a family of `assertXxx` methods; pytest uses Python's native `assert` keyword directly:

```python
# unittest style
class TestCart(unittest.TestCase):
    def test_total(self):
        cart = Cart()
        cart.add("apple", 2)
        self.assertEqual(cart.total, 2)
        self.assertTrue(cart.has_items())
        self.assertIn("apple", cart.items)

# pytest style
def test_total():
    cart = Cart()
    cart.add("apple", 2)
    assert cart.total == 2
    assert cart.has_items()
    assert "apple" in cart.items
```

**pytest intelligently analyses both sides of the `assert` expression**, showing you the actual values when something fails. For example, when `assert cart.total == 5` fails, pytest displays:

```
>       assert cart.total == 5
E       assert 2 == 5
E        +  where 2 = cart.total
```

**No need to memorise the names `assertEqual`, `assertTrue`, or `assertIn`** — a single `assert` covers everything.

## Fixtures: More Flexible Than `setUp`

unittest's `setUp` runs once per method. Write too much of it and it's either wasteful or not enough. pytest fixtures are **injected on demand**:

```python
import pytest

@pytest.fixture
def cart():
    c = Cart()
    c.add("apple", 2)
    return c

def test_total(cart):          # parameter name matches the fixture name; injected automatically
    assert cart.total == 2

def test_add_more(cart):       # each test gets a fresh cart
    cart.add("banana", 1)
    assert cart.total == 3
```

**Key characteristics of fixtures:**

| Feature | Description |
|---|---|
| On-demand injection | Only tests declaring a matching parameter receive it |
| Controllable scope | `scope="function"/"module"/"session"` |
| Supports teardown | Code before `yield` is setup; code after is teardown |
| Composable | Fixtures can depend on other fixtures |

```python
import pytest

@pytest.fixture
def db():
    print("\nconnecting to database")
    yield "db_connection"   # yielded to the test
    print("\nclosing database")     # runs after the test finishes

def test_query(db):
    assert db == "db_connection"
```

**Code before `yield` is the setup; code after it is the teardown** — more intuitive than setUp/tearDown.

## How pytest Relates to unittest

pytest and unittest are **compatible**: pytest can discover and run unittest `TestCase` classes without any code changes.

```bash
# the same TestCase class can be run either way
python -m unittest test_cart.py
pytest test_cart.py -v
```

**They coexist rather than replace each other:**

| Dimension | unittest | pytest |
|---|---|---|
| Origin | Python standard library, no install needed | Third-party, requires pip install |
| Assertions | `self.assertXxx` family | Native `assert` |
| Preparation | setUp/tearDown | Fixtures (more flexible) |
| Parameterisation | manual loops or subTest | `@pytest.mark.parametrize` built in |
| Plugin ecosystem | Limited | Rich (coverage, concurrency, reporting, etc.) |
| Learning curve | Gentler, OOP style | More Pythonic, more powerful |

**If your project already uses unittest, there's no need to migrate** — pytest runs it seamlessly. For a new project where third-party dependencies are acceptable, pytest offers a better development experience.

## Crash Site: Importing pytest When It Isn't Installed

```python
import pytest  # ImportError if it's not installed
```

Output:

```
ModuleNotFoundError: No module named 'pytest'
```

**pytest is a third-party library, not part of the standard library.** The standard-library `unittest` is available everywhere. This lesson covers concepts only and does not require installation.

## Crash Site: Fixture and Parameter Names Don't Match

```python
import pytest

@pytest.fixture
def my_cart():
    return Cart()

def test_something(cart):   # parameter name cart != fixture name my_cart
    assert cart.total == 0  # NameError!
```

**pytest matches fixtures by parameter name.** A mismatch means it's treated as a normal parameter, raising `TypeError: test_something() missing required argument`. Fix: rename the parameter to `my_cart`.

## Crash Site: Fixtures in the Wrong File

```python
# conftest.py (correct: here or inside a test file)
@pytest.fixture
def shared():
    return "shared"

# utils.py (wrong: inside a non-test module)
@pytest.fixture
def shared():
    return "shared"
```

**pytest only auto-discovers fixtures in `conftest.py` and test files.** Put one in an ordinary business module and other test files can't see it. Fix: place shared fixtures in `conftest.py` (at the test directory level).

## Crash Site: Assuming a Fixture Is Shared State When It's Rebuilt Each Time

```python
import pytest

counter = 0

@pytest.fixture
def count():
    global counter
    counter += 1
    return counter

def test_a(count):
    assert count == 1

def test_b(count):
    assert count == 1   # passes! because the fixture is rebuilt each time
```

**With the default `scope="function"`, the fixture re-executes for every test**, so `test_b` gets a brand-new `count`. To share state, set `scope="module"` or `scope="session"`.

## Summary

- pytest replaces the `assertXxx` family with native `assert`, making tests shorter and failure messages more detailed.
- Fixtures are more flexible than setUp: injected on demand, controllable scope, `yield` for teardown.
- pytest is compatible with unittest and can run `TestCase` classes directly.
- pytest is a third-party library, not part of the standard library; unittest ships with Python.
- Fixtures are matched by parameter name; a mismatch causes an error.
- Shared fixtures belong in `conftest.py`; fixtures rebuild by default for each test.
