# try / except: keeping the program alive

> A program that dies at the first error is one nobody dares use. This lesson is about catching them.

## The basic shape

```python
try:
    code that might fail
except ErrorType:
    what to do about it
```

**How it runs:**

1. Python runs the `try` block
2. **No error** → skip `except` and carry on
3. **Error** → jump straight to `except`, run it, then carry on

```python
try:
    n = int(input("enter a number: "))
    print(f"you entered {n}")
except ValueError:
    print("that isn't a number")

print("still running")        # ← runs either way
```

## A realistic case

```python
# ❌ typing letters crashes this
age = int(input("age: "))
print(f"next year you'll be {age + 1}")

# ✅ wrapped in try/except
try:
    age = int(input("age: "))
    print(f"next year you'll be {age + 1}")
except ValueError:
    print("please enter a number")
```

**User input is unpredictable** — the classic home of `try/except`.

## Catch only what you expect

```python
try:
    value = int(user_input)
except ValueError:          # ← name the type
    print("not a number")
```

> ⚠️ **Never use a bare `except:`.** It swallows **everything**, including bugs you never anticipated:

```python
# ❌ bad: swallows typos and Ctrl+C too
try:
    result = calculate()
except:
    print("something went wrong")
```

The trouble: if `calculate` has a typo (NameError), you also just see "something went wrong" and **never find the real bug**.

**Principle: catch only the exception types you know how to handle.**

## Getting the message

```python
try:
    n = int("abc")
except ValueError as e:          # as e binds the exception object
    print(f"reason: {e}")
```

```
reason: invalid literal for int() with base 10: 'abc'
```

**`as e` stores the exception** so you can print it or log it.

## Several exception types

```python
try:
    value = int(user_input)
    result = 100 / value
except ValueError:
    print("not a number")
except ZeroDivisionError:
    print("can't be zero")
```

**Write several `except` clauses**, one per case.

**Or catch several in one tuple:**

```python
try:
    ...
except (ValueError, TypeError):
    print("bad input")
```

## Not sure what might go wrong?

```python
try:
    risky_operation()
except Exception as e:          # Exception is the parent of most errors
    print(f"unexpected: {e}")
```

**`Exception` beats a bare `except:`** — it excludes `KeyboardInterrupt` (Ctrl+C) and `SystemExit`, so your program can still be interrupted.

**Order matters:**

```python
try:
    ...
except ValueError:
    print("bad value")
except Exception as e:
    print(f"other: {e}")
```

**Specific first, general last.** Reverse them and `Exception` catches everything up front, so the `ValueError` branch never runs.

## Practice: keep asking until it's valid

```python
while True:
    try:
        age = int(input("age: "))
        if age < 0:
            print("age can't be negative, try again")
            continue
        break                    # success — leave the loop
    except ValueError:
        print("please enter a number")

print(f"your age is {age}")
```

**This is the standard input-validation shape** — retry until you get something usable.

## Practice: reading a file safely

```python
try:
    with open('data.txt', 'r', encoding='utf-8') as f:
        content = f.read()
except FileNotFoundError:
    print("no such file — using defaults")
    content = ""
except PermissionError:
    print("no permission to read")
    content = ""
except UnicodeDecodeError:
    print("can't decode with this encoding")
    content = ""

print(f"read {len(content)} characters")
```

**Better than checking `os.path.exists` first** — because besides "missing", there's permissions, encoding, and more.

## Comparison

| Approach | Problem |
|---|---|
| No handling | crashes on the first error |
| `os.path.exists` check first | only guards "missing", not permissions or encoding |
| **`try/except`** | **guards everything at once** |

> 💡 **Python has a saying for this: EAFP** — Easier to Ask Forgiveness than Permission. Just try it and handle the fallout; it's cleaner than checking everything up front.

## Summary

- `try` holds the risky code; `except Type` catches it
- **Catch only what you can handle** — never a bare `except:`
- `as e` gives you the details
- With several `except` clauses, **specific first**
- **User input and file I/O** are the two main battlefields
