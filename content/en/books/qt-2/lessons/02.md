# Model and View Responsibilities: QAbstractItemModel, QTableView, index, row, and column

> Last lesson you were sold on Model/View. This lesson takes it apart: the model is the data's "interface," the view is the data's "mouthpiece," and they communicate through a protocol. The model never knows about any widget.

## Each Role Does Exactly One Thing

**Model/View is not three new classes — it is a division of labor among three roles.** In Qt, the common pairing is Model + View; Delegate is an optional third role (covered in Chapter 2).

| Role | Class | Responsibility |
|---|---|---|
| Model | `QAbstractItemModel` and subclasses | Store data, answer "what is at row r, column c" |
| View | `QTableView` / `QListView` / `QTreeView` | Display, mouse/keyboard handling, selection |
| (Preview) Delegate | `QStyledItemDelegate` | How a cell is drawn and edited |

**Core idea: the model doesn't know who displays it; the view doesn't know what the data looks like.** This is decoupling in its purest form.

```python
from PySide6.QtWidgets import QApplication, QTableView
from PySide6.QtCore import QStringListModel

app = QApplication([])

# Model: an "interface" over a string list
model = QStringListModel(["Apple", "Banana", "Orange"])

# View: something that only knows how to draw a table
view = QTableView()
view.setModel(model)      # Connect them
view.show()
app.exec()
```

**Pay attention to the `setModel` step.** Once the view has the model, it asks on its own: "How many rows do you have? What is each cell?" The model only answers; it never says "view, you should refresh now."

## index: The "Coordinate" the View Uses to Ask Questions

**The model does not expose "row 5" as an object. It uses `QModelIndex` — a temporary, lightweight coordinate token.**

When the view wants to draw row 2, column 1, it first asks the model for an index at that position:

```python
index = model.index(row=2, column=1)   # Get a QModelIndex
value = model.data(index, Qt.DisplayRole)   # Then ask for the value at that position
```

**An index is a temporary pass, not the data itself.** It records only (row, column, parent) and a pointer back to the model. It is tiny and cheap — created and discarded freely. Its purpose is to let the view avoid "holding" data objects; data always belongs to the model.

**Why not just use model.get(row, col)?** Because in tree structures (QTreeView), "which child" only makes sense relative to a parent. The index carries parent information, so this same API serves both tables and trees. In a table there is only one level, so "parent" is always `QModelIndex()` (an invalid index representing the root) — it looks verbose, but it works identically for trees.

## Crash Site 1: Forgetting the parent Parameter of index — Tree Data Breaks

**Symptom: Switching to QTreeView, data refuses to display, or only the top level appears.**

```python
# ❌ Used to table habits; lost the parent in tree model
def index(self, row, column, parent=QModelIndex()):
    # Directly access internal list
    return self.createIndex(row, column, None)   # Didn't check who parent is
```

**Root cause: For a tree's second-level nodes, "row 0" means "row 0 among some parent's children," not "row 0 of the entire tree."** Ignoring parent treats all nodes as top-level, breaking the hierarchy.

**✅ Fix: First resolve "which parent am I" from the parent parameter, then get its row-th child.**

```python
def index(self, row, column, parent=QModelIndex()):
    if not parent.isValid():
        parent_node = self._root
    else:
        parent_node = parent.internalPointer()
    if row < 0 or row >= len(parent_node.children):
        return QModelIndex()
    child = parent_node.children[row]
    return self.createIndex(row, column, child)   # Attach node pointer to index
```

**`createIndex(row, column, ptr)` takes a custom data payload as its third argument (typically an internal node pointer), retrieved via `index.internalPointer()`.** This is the most common tag-team in custom models.

## The Model Knows No Widgets — And That's Good

**Your model should not import QPushButton, QLabel, or call any QWidget methods. Its world contains only data, indices, roles, and signals.**

```python
# ❌ A classic coupling mistake
class BadModel(QAbstractTableModel):
    def __init__(self, table_widget):
        super().__init__()
        self._table = table_widget    # ❌ Model holds a reference to the view

    def data(self, index, role):
        val = self._rows[index.row()][index.column()]
        if role == Qt.DisplayRole:
            self._table.some_label.setText(...)   # ❌ Model directly modifies the UI
            return str(val)
```

**This error drags you right back into the "data-display coupling" swamp.** Once the model knows about the view, you cannot reuse it with another view — say you want the same data in a QTableView, a QListView, and a QComboBox dropdown. All three can accept the same model, provided the model knows nothing about them.

## Crash Site 2: Binding the Model to a Specific Widget Kills Reusability

**Symptom: You wrote a model in window A. Window B wants the same data, but the model constructor demands a QPushButton that window B doesn't have.**

```python
class ScoreModel(QAbstractTableModel):
    def __init__(self, submit_btn):
        super().__init__()
        self._submit_btn = submit_btn     # This button belongs to window A
        self._submit_btn.setEnabled(False)

# Window B wants to reuse → error, no submit_btn to pass
```

**✅ Fix: The model only emits signals; let the view or controller decide "should the button be enabled?"**

```python
class ScoreModel(QAbstractTableModel):
    data_dirty = Signal(bool)    # Whether data has been modified

    def setData(self, index, value, role):
        # Change data...
        self.data_dirty.emit(True)   # Tell the outside world "it's dirty"
        return True

# View layer decides button state
model.data_dirty.connect(submit_btn.setEnabled)
```

**This is where the "C" in MVC lives: the controller connects model signals to view slots.** The model only shouts "I changed"; whether "the button should light up after changing" is the controller's job.

## Roles: Multiple Questions for the Same Cell

**The view asks more than just "what to display" — it also asks "what value when editing," "what for sorting," "what background color." These different questions are roles.**

| Role | What it asks |
|---|---|
| `Qt.DisplayRole` | Text shown to the user |
| `Qt.EditRole` | Raw value when editing |
| `Qt.DecorationRole` | Icon |
| `Qt.ForegroundRole` / `BackgroundRole` | Foreground / background color |
| `Qt.TextAlignmentRole` | Alignment |
| `Qt.UserRole` | Anything custom you define |

**The separation of DisplayRole and EditRole is the design's genius.** When displaying, you want commas, units, and rounding; when editing, you want the raw number. With only one role, these two needs fight each other.

```python
def data(self, index, role):
    value = self._rows[index.row()][index.column()]
    if role == Qt.DisplayRole:
        return f"{value:,} USD"          # Display: 1,000,000 USD
    if role == Qt.EditRole:
        return value                     # Edit: 1000000
    return None
```

**Roles are the "dimensions" your model exposes to the outside world.** Provide more dimensions and the view can do more elaborate things. Provide nothing but DisplayRole and you get a plain table; add alignment, colors, and icons and you get a report-grade interface.

## Summary

- Model manages data, view manages display, delegate manages editing and rendering — they communicate by protocol
- The model knows no widgets; it answers questions only via index and role
- index is a temporary coordinate token; in tables parent is invalid; in trees, parent matters
- `createIndex(row, col, ptr)` stores a custom node pointer; retrieve with `internalPointer()`
- A model holding a view reference loses reusability; use signals to notify the outside world
- Roles distinguish "what to show" from "what to edit" — the foundation of data diversity
