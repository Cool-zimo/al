# Wrapping Up: Packaging for Release and What Two Volumes Leave You With

> The project is finished. Two things remain: turn it into an executable you can hand to someone, and look back at what these two volumes have actually given you.

## Packaging: PyInstaller Needs Qt Plugins

A plain Python script is easy to package: `pyinstaller main.py`. A Qt application needs one more step — **the Qt plugin directories must be bundled too**. At runtime PySide6 dynamically loads platform plugins (windows / linux / android), image-format plugins, and style plugins. If it cannot find them, the program simply will not start.

**Symptom: double-click the exe and it flashes then disappears; running from the command line reports `qt.qpa.plugin: Could not find the Qt platform plugin "windows"`.**

The packaging command:

```bash
pyinstaller --onefile --windowed ^
    --add-data "venv/Lib/site-packages/PySide6/plugins;PySide6/plugins" ^
    main.py
```

On Linux and macOS, use a colon instead of a semicolon:

```bash
pyinstaller --onefile --windowed \
    --add-data "venv/lib/python3.12/site-packages/PySide6/plugins:PySide6/plugins" \
    main.py
```

`--windowed` (called `--noconsole` on macOS) is for GUI programs: no black console window. `--add-data` copies the plugin directory into the bundle, where Qt looks for it on startup.

**An easier and more reliable option: let PyInstaller find everything itself.** `--collect-all PySide6` pulls in every Qt-related file in one go. The bundle is a little larger, but you stop worrying about which plugin is missing:

```bash
pyinstaller --onefile --windowed --collect-all PySide6 main.py
```

## The spec File: Do Not Retype the Command Every Time

Once the first build succeeds, PyInstaller generates `main.spec`. After that, whenever you change the code, just run:

```bash
pyinstaller main.spec
```

The plugin paths inside the spec file are hard-coded, so if you switch machines or virtual environments it is safer to re-run the command with `--add-data` once and regenerate the spec.

## Bundle Size: Why a Qt exe Starts at 50MB

PySide6 plus the Qt core libraries, platform plugins, and image plugins add up to 40–60MB as a matter of course. That is the fixed cost of Qt. **If you are building a desktop app to hand to other people and it does more than a toy, that size is perfectly acceptable.** If you just want a tiny utility and a few MB matters, tkinter is the better fit — it ships with Python, so there is no Qt to bundle at all.

**Do not try to slim the bundle by manually deleting `.dll` files from the plugins folder.** You will almost certainly misjudge which ones are unused, and the result is the same platform-plugin error. If size really matters, use UPX compression (`--upx-dir`), accepting that startup will be a little slower.

## What About the Database File?

The SQLite file `ledger.db` has to travel with the executable. There are two reasonable approaches.

**1. Same directory as the exe, relative path.** Find `ledger.db` next to the executable on startup:

```python
import os, sys

def app_dir():
    if getattr(sys, "frozen", False):
        return os.path.dirname(sys.executable)   # after packaging: the exe directory
    return os.path.dirname(os.path.abspath(__file__))

DB_PATH = os.path.join(app_dir(), "ledger.db")
```

**2. A user directory — far safer across machines.** On Windows that is `%APPDATA%/Ledger/ledger.db`. Reinstalling the OS or moving machines will not wipe it.

**Option 2 is strongly recommended.** Option 1 puts the exe on the desktop, the database on the desktop, and both disappear on the next reinstall. Financial data is not something you want to lose.

## What Two Volumes of Qt Leave You With

Looking back over "Window Basics 4" and this volume, here is the ground we covered:

**Volume 1 — "Window Basics 4": getting an interface on screen**
- `QWidget`, layout managers, signals and slots
- Common widgets: buttons, input boxes, lists, dialogs
- Events, mouse and keyboard
- Menu bar, tool bar, status bar

**Volume 2 — this volume: making the interface live peacefully with data**
- The Model/View trio: the model supplies data, the view displays it, the delegate paints and edits it
- The three methods: `rowCount`, `columnCount`, `data`
- Custom delegates: progress-bar cells, row and column sizing, headers
- View selection: `QItemSelectionModel`
- Proxy sorting and filtering: `QSortFilterProxyModel`
- Drawing: `QPainter`, coordinate transforms, gradients, vector paths
- Data: `QtSql`, `QSqlTableModel`, parameterised `QSqlQuery`
- Networking: `QNetworkAccessManager` async plus JSON fed into a model

**One thread runs through all of it: keep "what the data is" separate from "how it is displayed".** That is the way of thinking Model/View teaches you, and it is not unique to Qt. Front-end frameworks have MVVM, back-end code has MVC, and any interface you design yourself is the same idea.

## Compared With the Three tkinter Volumes You Already Know

| Capability | tkinter — three volumes | Qt — two volumes |
|---|---|---|
| Building an interface | Adequate; layouts are fairly manual | Layout managers plus Designer |
| Data binding | Refresh a Listbox yourself | Model/View reacts automatically |
| Custom cells | Almost none | Delegate — draw whatever you want |
| Sorting and filtering | Reorder the list yourself | A proxy model in a few lines |
| Drawing | matplotlib images | Vector drawing with QPainter |
| Database | Hand-written sqlite3 | QtSql binds straight to a view |
| Networking | requests plus a thread | Async signals, UI never blocks |
| Packaging | PyInstaller | PyInstaller plus Qt plugins |
| Bundle size | Small | Starts at 40MB |

**It is not that "Qt is better than tkinter" — it is that Qt suits larger projects.** A 200-line tool is faster to write and smaller to ship in tkinter. A ledger you will maintain for three years, with sorting, filtering and charts, will repay Qt's structure many times over.

## Where to Go Next

**Engineering practice**
- Unit tests: pytest, plus tests for the model layer (the easiest layer to test)
- Code organisation: split the project into a package with `__main__.py` as the entry point
- Multiple windows and documents: `QMdiArea`, modal dialogs, wizard-style flows
- Styling: `QSS` (Qt Style Sheets) for theming and dark mode
- Internationalisation: `Qt Linguist` for multi-language support

**Data-analysis direction**
- pandas plus Model/View: connect a DataFrame to `QAbstractTableModel` and a million rows stays smooth
- matplotlib embedding: `FigureCanvasQTAgg` drops a figure into a QWidget
- PyQtGraph: high-performance real-time plots — a monitoring dashboard runs far faster than with matplotlib

**Algorithms direction**
- Custom views: mind maps, flow charts, node editors (all QPainter plus events)
- Heavy computation in the model: cache it, update incrementally; never make the view compute it
- Threading: `QThread` plus `QObject.moveToThread` to push expensive algorithms to the background and return results through signals

**One very practical suggestion: rebuild the ledger with a different data source.** Plug in a real exchange-rate API to show currency conversions, or import in bulk from a CSV. Build a different data shape against the same architecture and you will genuinely understand the value of Model/View — **swap the data without touching the interface.**

## Crash Site 1: Platform Plugin Not Found After Packaging

**Symptom:** `qt.qpa.plugin: Could not find the Qt platform plugin "windows"`.

**Cause:** `PySide6/plugins` was not bundled into the package.

**The fix:**

```bash
pyinstaller --onefile --windowed --collect-all PySide6 main.py
```

## Crash Site 2: `--onefile` Without `--windowed` Opens a Console

**Symptom:** The program runs, but a black window sits next to it and will not close.

**The fix: GUI programs always get `--windowed` (or `--noconsole` on macOS).**

## Crash Site 3: Database Path Hard-Coded as a Relative Path

**WRONG — Do not do this:**

```python
DB_PATH = "ledger.db"                 # relative to the current working directory - very fragile
```

**The fix: use the executable's directory or the user's AppData directory after packaging.**

## Crash Site 4: Packaged Program Seems Dead on Startup

**Cause:** `--onefile` unpacks everything to a temp directory before running, and 50MB takes a couple of seconds.

**The fix: release with `--onedir` for faster startup, or accept the onefile delay.** Do not assume the program has hung.

## Crash Site 5: The Whole Virtual Environment Got Bundled

**Symptom:** A 200MB bundle stuffed with development packages — pytest, ipython, the lot.

**The fix: use a clean virtual environment that holds only the dependencies you need to package. Do not package from your development environment.**

## Crash Site 6: Assuming "Qt Is Faster Than tkinter, So My Program Runs Faster"

**The correct understanding: Qt's performance advantage shows up in rendering complex interfaces, large tables and vector drawing — not in executing your loop any faster. Your `for` loop runs the same speed either way.**

## Summary

- Packaging Qt with PyInstaller requires the plugins: `--collect-all PySide6`
- GUI programs add `--windowed` to hide the console
- Database paths should use the exe directory or a user directory — never a bare relative path
- The thread running through both volumes is an architecture that separates data from display
- Qt suits larger projects, tkinter suits small tools; each has its place
- Next steps: engineering practice (tests, styling, threading), data analysis (pandas, PyQtGraph), algorithms (custom views)
- The best next exercise: rebuild the same architecture against a different data source
