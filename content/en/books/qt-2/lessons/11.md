# Why Custom Widgets: When Stock Widgets Cannot Build the Look You Need

> `QPushButton`, `QLabel`, `QProgressBar` are already excellent. But sooner or later the PM points at a design and says: "I want this rounded, gradient-filled button with a ripple on click." That is when you discover that snapping widgets together cannot get you there.

## How Far Can Stock Widgets Take You?

**Qt's widget library covers about 90% of everyday needs. Buttons, input fields, tables, menus, sliders, progress bars, tabs... if you can snap pieces together, that is the cheapest and most correct answer.**

```python
from PySide6.QtWidgets import QApplication, QWidget, QPushButton, QHBoxLayout, QLineEdit

app = QApplication([])

win = QWidget()
search = QLineEdit()
search.setPlaceholderText("Search...")
btn = QPushButton("Search")

layout = QHBoxLayout(win)
layout.addWidget(search)
layout.addWidget(btn)
win.show()
app.exec()
```

**QSS can change colour, rounded corners, borders, gradients, and states — covered in the previous volume, "Qt Advanced 1", and not repeated here.** QSS solves "style", never "behaviour".

## Where QSS Hits Its Limit

**QSS can change "the look of parts that already exist": background, border, radius, font, padding. It cannot:**

- Draw an annular (ring) progress bar — a progress bar can only be a horizontal bar
- Make a button ripple on click
- Draw a dashboard, speedometer, or waveform graph
- Build a draggable knob or rotary dial
- Render a chat bubble with a tail pointing to one side
- Build a star-rating control

**What these all share is that their geometry is computed, not positioned.** A ring progress bar's angle changes with the value; a ripple's centre follows the click position — these must be calculated, not configured.

## Three Approaches to Custom Widgets

| Approach | How | When to use |
|---|---|---|
| Subclass an existing widget | `class MyButton(QPushButton)` — add properties, signals, override a few methods | The stock widget covers 90% and you only need a little extra behaviour |
| Full custom paint (subclass `QWidget`) | Override `paintEvent`, draw with `QPainter` | A brand-new look unlike anything on the market |
| Composite widget | Pack several child widgets into a `QWidget` with a layout | One "card" needs an image, a title, and a button |

**The three approaches increase in effort from left to right.** Compose whenever you can (Lesson 12 explains why this is "encapsulation", not "custom drawing"), subclass to extend when almost there, and only paint from scratch when nothing else fits.

## Crash Site 1: 100 QLabel Widgets for a Dial, Performance Collapses

**Symptom: to draw a gauge, you create 100 `QLabel` widgets arranged along an arc, each showing one tick mark. With a few windows open, memory and CPU both spike.**

```python
# ❌ 100 QLabel widgets for the tick marks
for angle in range(0, 181, 2):
    label = QLabel("|")
    label.setGeometry(...)     # Each one needs layout computation
    label.show()
# 100 widget objects, each with its own window handle and event handling
```

**Root cause: every `QWidget` subclass is a real window object, with a handle, an event queue, and a place in the layout.** Once you have many of them, construction and painting both become expensive.

**✅ Fix: one `QWidget`, one `paintEvent`, and a loop that draws 100 lines with `QPainter`.**

```python
class Gauge(QWidget):
    def paintEvent(self, event):
        painter = QPainter(self)
        painter.setRenderHint(QPainter.Antialiasing)
        cx, cy = self.width() // 2, self.height() // 2
        for angle in range(0, 181, 2):
            rad = math.radians(angle)
            x1 = cx + 80 * math.cos(rad)
            y1 = cy - 80 * math.sin(rad)
            x2 = cx + 90 * math.cos(rad)
            y2 = cy - 90 * math.sin(rad)
            painter.drawLine(int(x1), int(y1), int(x2), int(y2))
        painter.end()
```

**One widget, one paint event, one hundred lines — far cheaper than one hundred widgets.** This is the core value of custom painting: turn N objects into one object plus a loop.

## Crash Site 2: Copying the Entire Qt Source to Change One Property

**Symptom: you only wanted `QPushButton` to auto-disable itself for a countdown, so you copied the button's source (thousands of lines) and edited it — and now you have a dozen new bugs.**

```python
# ❌ Wrong approach: copy the QPushButton implementation and edit it
class MyButton(QPushButton):
    def __init__(self, text, parent=None):
        super().__init__(text, parent)
        # ... copied a pile of private methods ...
```

**Root cause: Qt widgets are meant to be subclassed, not copied.** Their private internals are impossible to copy fully or correctly.

**✅ Fix: subclass and compose.**

```python
from PySide6.QtCore import QTimer

class CountdownButton(QPushButton):
    def __init__(self, text, seconds=10, parent=None):
        super().__init__(text, parent)
        self._seconds = seconds
        self._remaining = seconds
        self._timer = QTimer(self)
        self._timer.timeout.connect(self._tick)

    def start_countdown(self):
        self._remaining = self._seconds
        self.setEnabled(False)
        self._timer.start(1000)

    def _tick(self):
        self._remaining -= 1
        self.setText(f"Please wait {self._remaining}s")
        if self._remaining <= 0:
            self._timer.stop()
            self.setEnabled(True)
            self.setText("Click me now")
```

**Subclass `QPushButton`, inherit all its existing behaviour (clicking, styling, focus), and add only the countdown logic you need.** This is object orientation doing its job.

## Crash Site 3: Painting Directly Inside mousePressEvent

**Symptom: you want to draw a red dot where the user clicks, so you create a `QPainter` right inside `mousePressEvent`. The first click works; the second click erases the first; and occasionally you get an error.**

```python
def mousePressEvent(self, event):
    painter = QPainter(self)
    painter.setPen(Qt.red)
    painter.drawPoint(event.position().toPoint())   # ❌ Painting straight inside the event
    painter.end()
```

**Root cause: painting outside `paintEvent` is not persistent. Qt may repaint the widget at any time (after being obscured, on resize, or after you call `update()`), and your red dot vanishes. The paint-device state may also be wrong.**

**✅ Fix: record data inside the event handler, call `update()` to trigger `paintEvent`, and do the drawing inside `paintEvent`.**

```python
class DotWidget(QWidget):
    def __init__(self, parent=None):
        super().__init__(parent)
        self._points = []          # The points to draw

    def mousePressEvent(self, event):
        self._points.append(event.position().toPoint())
        self.update()              # Mark for repaint; Qt will call paintEvent

    def paintEvent(self, event):
        painter = QPainter(self)
        painter.setPen(Qt.red)
        for p in self._points:
            painter.drawPoint(p)
        painter.end()
```

**This is an iron rule of Qt painting: always paint inside `paintEvent`; event handlers only mutate data and call `update()`.**

## How to Choose Among the Three Approaches

**Decision flow:**

```
A new requirement arrives
  ├─ Can QSS handle the styling? → Use QSS
  ├─ Does an existing widget cover 90%, needing only a little behaviour? → Subclass (Lesson 12)
  ├─ Is the shape "computed"? → Full custom paint (Lesson 13)
  └─ Do multiple widgets need to be packaged as one unit? → Composite widget (Lesson 12)
```

**This lesson is the prologue to Chapter 3. The next three lessons are: subclass-and-extend (12), full custom paint (13), and event handling (14). Lesson 15 ties them all together in a circular progress indicator.**

## Summary

- Stock widgets plus QSS solve roughly 90% of needs — use them first
- QSS can change styling but never geometry or behaviour
- Three approaches: subclass-and-extend, full custom paint, and composite widgets, in order of increasing effort
- Large numbers of repeated child widgets should be replaced by custom painting: one widget drawing N lines is far faster than N widgets
- Never copy Qt widget source — subclassing is the answer
- Always paint inside `paintEvent`; mutate data and call `update()` inside event handlers
