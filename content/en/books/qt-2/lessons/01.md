# Why Model/View Exists: QTableWidget Works Fine Until It Doesn't

> You built a 100-row table with QTableWidget and it felt great. Then product asks for "10,000 rows, live sorting, keyword filtering" and your code collapses.

## Let's Be Honest: QTableWidget Is Wonderful

**QTableWidget is Qt's gift to the "lazy" developer. When data is small, it is perfect.**

You give it rows and columns, then fill cells one by one with `setItem(row, col, QTableWidgetItem(...))`. Want a button in a cell? Fine. Change data? Just grab `item(row, col).setText(...)`. Boom, the display updates. This is the intuition of "manipulating widgets directly" — everyone loves it.

```python
from PySide6.QtWidgets import QApplication, QTableWidget, QTableWidgetItem

app = QApplication([])

table = QTableWidget(3, 2)                 # 3 rows, 2 columns
table.setHorizontalHeaderLabels(["Name", "Score"])

table.setItem(0, 0, QTableWidgetItem("Alice"))
table.setItem(0, 1, QTableWidgetItem("92"))
table.setItem(1, 0, QTableWidgetItem("Bob"))
table.setItem(1, 1, QTableWidgetItem("85"))

table.show()
app.exec()
```

**The hidden assumption: every row of data "lives" inside a QTableWidgetItem object.** Data is part of the widget, not an independently existing dataset. This is harmless at small scale; at large scale it is a disaster.

## Problem 1: 10,000 Rows = Freezing

**QTableWidget literally creates 10,000 QTableWidgetItem objects.** Every row and every column is a separate object with coordinates, styles, state, and signal connections. 10,000 rows × 10 columns = 100,000 objects alive simultaneously.

```python
# ❌ Shoving 10,000 rows in directly
table = QTableWidget(10000, 10)
for r in range(10000):
    for c in range(10):
        table.setItem(r, c, QTableWidgetItem(f"data{r}-{c}"))
# Window takes several seconds to appear; scrolling may stutter
```

**It stalls in three places.** Memory: 100,000 objects, the Python object header alone eats tens of MB plus Qt's internal C++ objects. Creation time: constructing 100,000 objects in a loop, plus signal-slot connections, adds up. Rendering: even with viewport clipping, QTableWidget must reserve space and compute sizes for all items during layout.

**The Model/View solution: the view only asks the model "what is at row r, column c" and the model computes and returns on demand.** 10,000 cells, but only 30 rows are visible on screen, so the model is only asked 300 times. Scroll away and back, still the same 300. This is "lazy fetching" or "on-demand rendering."

## Problem 2: Changing Data Means Writing a Ton of setItem Calls

**In real projects, your data is usually a list, a dict, or something read from a database. QTableWidget forces you to "flatten" it into cells.**

```python
# Your real data
students = [
    {"name": "Alice", "chinese": 92, "math": 88, "english": 95},
    {"name": "Bob", "chinese": 85, "math": 91, "english": 78},
]

# ❌ Manually flattening into cells
table = QTableWidget(len(students), 4)
for r, s in enumerate(students):
    table.setItem(r, 0, QTableWidgetItem(s["name"]))
    table.setItem(r, 1, QTableWidgetItem(str(s["chinese"])))
    table.setItem(r, 2, QTableWidgetItem(str(s["math"])))
    table.setItem(r, 3, QTableWidgetItem(str(s["english"])))

# Now the data changes. What next?
students[0]["chinese"] = 99
# You also have to remember to sync the table, otherwise the display is wrong:
table.item(0, 1).setText("99")   # Miss this line and UI/data diverge
```

**This is the cost of "data-display coupling": you maintain the same truth in two places.** Add a row — change data AND add an item. Delete a row — delete in both. Change a value — change in both. As code grows, missing a sync is inevitable, not accidental.

## Crash Site 1: Data Changed but UI Didn't — Sync Forgotten

**Symptom: `students[0]["chinese"] = 99` executed fine, but the table still shows 92. Breakpoints confirm data is correct; UI never refreshes.**

```python
students[0]["chinese"] = 99
print(students[0])          # {'name': 'Alice', 'chinese': 99, ...} — data is right
# Table still shows 92 — nobody told the table
```

**Root cause: QTableWidget doesn't know about your `students` list.** It reads display content from items, and the item still holds "92". These are two parallel lines; changing one side never notifies the other.

**✅ Fix (band-aid in QTableWidget world): manually sync after every change, or use setData to modify the item value directly.**

```python
# ✅ Either change the item, or change both — pick one and stick with it
students[0]["chinese"] = 99
table.item(0, 1).setText(str(students[0]["chinese"]))   # Change both
```

**But this fix treats the symptom, not the disease. The real answer: let the UI read your data directly instead of reading a pile of items.** That is Model/View — you maintain one dataset, the view asks your data every time it needs to display, and when data changes you notify the view "I changed here" and the view repaints automatically. There is only ever one source of truth.

## Crash Site 2: Sorting Requires Copying and Re-inserting

**Symptom: PM wants "click the header to sort." You find QTableWidget has `sortItems`, but it only sorts strings — "100" comes before "9".**

```python
table.setItem(0, 1, QTableWidgetItem("9"))
table.setItem(1, 1, QTableWidgetItem("100"))
table.sortItems(1, Qt.AscendingOrder)
# Order becomes 100, 9 — because QTableWidgetItem compares text by default
```

**Root cause: QTableWidgetItem stores "display text," and sorting compares text by default.** You can use `setData` to store a numeric role then sort, but it is awkward.

**✅ Fix: Switch to Model/View. The model stores real data types (int), so sorting compares numerically.**

```python
# In the model, data() returns a real int — sorting naturally uses number magnitude
def data(self, index, role):
    if role == Qt.DisplayRole:
        return self._rows[index.row()][index.column()]   # This is an int
```

**Sorting and filtering are fundamentally "transformations on data."** When data lives in the model, transformations are natural. When data is flattened into items, you must fish items out and put them back — painful.

## Crash Site 3: "Keyword Filter" Means Rebuilding the Entire Table

**Symptom: PM is back — a search box that shows only rows containing "张" when you type "张".**

```python
# ❌ QTableWidget approach: clear current display, re-insert filtered results
table.setRowCount(0)                        # Clear
for s in students:
    if keyword in s["name"]:
        r = table.rowCount()
        table.insertRow(r)
        table.setItem(r, 0, QTableWidgetItem(s["name"]))
        # ... more repetitive code
# Problem: pre-filter selection state and scroll position are lost
```

**✅ Model/View approach: add a ProxyModel layer. Filtering is delegated to it; original data stays untouched.**

```python
proxy = QSortFilterProxyModel()
proxy.setSourceModel(model)
proxy.setFilterFixedString("张")
proxy.setFilterKeyColumn(0)
view.setModel(proxy)        # View only talks to the proxy
```

**The original model always holds the complete, untouched data. The proxy filters in the middle. The view only draws.** This "insert a proxy layer" pattern is one of Model/View's most elegant products.

## The Big Picture: What Model/View Is Really About

**One sentence: data is data, display is display, and they connect through a protocol (the model).**

| | QTableWidget | Model/View |
|---|---|---|
| Where data lives | Scattered across items | You maintain one copy |
| 10,000 objects | Actually creates 10,000 | Only renders what is visible |
| Sync on data change? | Yes, manually | No, just notify refresh |
| Sort/filter | Rebuild or hack | Swap model or add proxy |

**In this chapter you will learn: how model and view divide responsibilities (02), how to get started fast with QStandardItemModel (03), how to write your own model (04), and what the "notification-refresh" protocol actually looks like (05).** The next chapter covers sorting, filtering, and delegates — where Model/View truly shines.

## Summary

- QTableWidget is convenient but stores data in items, coupling data and display
- 10,000 rows means 100,000 objects — memory, creation time, and layout all suffer
- Changing data requires manual sync; miss once and you have a display bug
- Default sorting is text-based; filtering requires rebuild — all costs of "widget manipulation"
- Model/View lets the UI read your data and refresh on notification — one source of truth always
- Proxies can sort and filter without modifying original data
