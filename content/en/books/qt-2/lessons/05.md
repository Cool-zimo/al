# Data Change Notifications: beginInsertRows/endInsertRows — Modifying the Internal List Without Notifying Means No Refresh (The Classic Trap)

> This is the most core and most easily overlooked lesson in Model/View. Previous lessons' signals were "automatic." This lesson covers the notifications you must send manually: telling the view "I'm about to insert a row" and "I just finished deleting a row." Skip them and you have a bug.

## Why begin/end Pairs Are Needed

**Modifying internal data directly means the view never knows.** This is the inevitable consequence of Model/View decoupling — the model and view are two independent objects; you changed the model's internal list and the view has no way to find out.

```python
# Pure logic demonstration: modifying internal list without notification
class SilentModel:
    def __init__(self):
        self._rows = [["Alice", 92], ["Bob", 85]]

    def add_row(self, row):
        self._rows.append(row)          # Directly modify internal list
        # ❌ Nobody is notified

model = SilentModel()
model.add_row(["Charlie", 77])
print("Internal data is now:", model._rows)
# But the view still draws the old two rows — it doesn't know
```

**The solution is for the model to emit signals proactively. But signals cannot be emitted carelessly; they must follow Qt's "transaction" protocol: announce "I'm starting," then change data, then announce "I'm done."**

```python
# Pseudocode illustrating this "transaction" structure
def insert_row(self, row, data):
    self.beginInsertRows(QModelIndex(), row, row)   # ① Transaction begins
    self._rows.insert(row, data)                    # ② Actually change data
    self.endInsertRows()                            # ③ Transaction ends
```

**begin and end must appear in pairs, with only data modification between them.** This pair tells the view: "a structural change is about to happen in this row range; prepare yourself, then repaint once I say we're done."

## Crash Site 1: Appending Without Notification — View Doesn't Refresh (The #1 Trap)

**Symptom: Click "Add Row"; the internal data clearly has one more row (print confirms it), but the table UI shows no reaction. You must manually drag the window or click elsewhere for an occasional refresh.**

**This is the single most frequent Model/View bug — bar none.**

```python
def add_student(self):
    self._rows.append(["New Student", 60])    # ❌ Internal list changed; view doesn't know
    print("Now have", len(self._rows), "rows")  # Number is correct
    # But the table still shows the old row count
```

**Root cause: The view only adjusts its row count, scrollbar, and selection state upon receiving structural change signals (rowsInserted / rowsRemoved / layoutChanged).** You silently modified the underlying data; the view cannot perceive it.

**✅ Fix: Wrap the modification with beginInsertRows / endInsertRows.**

```python
def add_student(self, row_data):
    row = self.rowCount()
    self.beginInsertRows(QModelIndex(), row, row)   # start=end=position to insert
    self._rows.append(row_data)
    self.endInsertRows()                             # Must be paired
    # View now repaints automatically; the new row appears
```

**The three arguments to beginInsertRows: `parent` (always QModelIndex() in a table), `first` (start of the insertion range), `last` (end of the insertion range).** Inserting one row means first==last; inserting multiple rows means passing a range.

## Crash Site 2: begin/end Not Paired — Immediate Crash

**Symptom: Program crashes with `ASSERT failure in QAbstractItemModel::endInsertRows: "Called endInsertRows() with no matching beginInsertRows()"`.**

```python
def add_student(self, row_data):
    # ❌ Missing begin
    self._rows.append(row_data)
    self.endInsertRows()
    # Assertion failure, program exits
```

**Or conversely:**

```python
def add_student(self, row_data):
    self.beginInsertRows(QModelIndex(), self.rowCount(), self.rowCount())
    if some_condition:
        return                 # ❌ Early return; endInsertRows never called
    self._rows.append(row_data)
    self.endInsertRows()
```

**Root cause: Qt internally tracks "whether a structural change is in progress" with a counter.** begin increments, end decrements; if they don't match, an assertion fails. Early returns are the most common cause of "mismatch."

**✅ Fix: Keep the modification and end in the same scope; guard exceptions with try/finally.**

```python
def add_student(self, row_data):
    row = self.rowCount()
    self.beginInsertRows(QModelIndex(), row, row)
    try:
        self._rows.append(row_data)
    finally:
        self.endInsertRows()        # ✅ Always paired, even on exception
```

**try/finally is the best practice for this discipline.** Even if an exception is thrown mid-way, finally guarantees end is called and Qt's internal state stays consistent.

## Correct Insertion (Including Position Parameter)

**Appending goes to the end; inserting in the middle uses insert. Both must be wrapped in begin/end.**

```python
def insert_student(self, position, row_data):
    if position < 0 or position > self.rowCount():
        return
    self.beginInsertRows(QModelIndex(), position, position)
    self._rows.insert(position, row_data)
    self.endInsertRows()
```

**Deletion uses beginRemoveRows / endRemoveRows, with identical argument semantics.**

```python
def remove_student(self, position):
    if position < 0 or position >= self.rowCount():
        return
    self.beginRemoveRows(QModelIndex(), position, position)
    self._rows.pop(position)
    self.endRemoveRows()
```

**Note: begin's range must be computed against the "before modification" state.** You cannot pop first then call begin, because at the begin moment the view still uses the old rowCount to validate the range.

## Crash Site 3: Modifying Before begin — Order Reversed

**Symptom: The UI occasionally shows "the last row duplicated" or crashes outright.**

```python
def add_student(self, row_data):
    self._rows.append(row_data)                              # ❌ Modified first
    self.beginInsertRows(QModelIndex(), len(self._rows)-1, len(self._rows)-1)
    self.endInsertRows()
```

**Root cause: At the begin moment, Qt queries the model's current rowCount as a "baseline."** You already appended, so rowCount has changed; the baseline begin receives is wrong, and the view miscalculates "which rows were inserted."

**✅ Fix: Always follow the order begin → modify → end. Never reverse it.**

```python
def add_student(self, row_data):
    row = self.rowCount()                    # Remember insertion position first (based on old rowCount)
    self.beginInsertRows(QModelIndex(), row, row)
    self._rows.append(row_data)             # Then modify
    self.endInsertRows()
```

**This ordering issue is especially lethal during batch operations.** Remember the rule: notify first, act second, finish last.

## Batch Operations: Inserting Multiple Rows at Once

**When inserting a range, first and last are the row numbers of the rows you are inserting in the "after insertion" coordinate space.**

```python
def insert_many(self, position, rows):
    n = len(rows)
    if n == 0:
        return
    self.beginInsertRows(QModelIndex(), position, position + n - 1)
    for r in reversed(rows):                # Insert from back to front so positions stay anchored
        self._rows.insert(position, r)
    self.endInsertRows()
```

**Why reversed?** If you insert 3 rows starting at position 2 from the front, after inserting the first row the original row 2 becomes row 3, and all subsequent insertion positions shift. Inserting from the back keeps position 2 as a stable anchor.

## Crash Site 4: layoutChanged Abuse — The Heavy Weapon of Full Refresh

**Symptom: Every data change calls `self.layoutChanged.emit()`, which works but causes noticeable UI lag at large data sizes.**

```python
def shuffle(self):
    random.shuffle(self._rows)
    self.layoutChanged.emit()       # ❌ Tells the view "everything changed"; full repaint
```

**Root cause: `layoutChanged` is the heaviest notification, meaning "everything changed; repaint everything."** For a 1000-row table, changing one cell and emitting layoutChanged forces the view to do 1000 rows' worth of pointless work.

**✅ Fix: Use structural signals (rowsInserted/rowsRemoved) when possible, dataChanged for value changes, and layoutChanged only for "rows and columns both changed" scenarios.**

| Notification | Use Case | Cost |
|---|---|---|
| `dataChanged` | Value changed, cell style changed | Lightest — only repaints the specified region |
| `rowsInserted` / `rowsRemoved` | Row added/removed | Medium — restructures |
| `layoutChanged` | Rows/columns changed, full reorder | Heaviest — full repaint |

## Summary

- Modifying the internal list directly means the view won't refresh; you must notify manually — this is Model/View's #1 trap
- beginInsertRows / endInsertRows must be paired; order is always begin → modify → end
- begin's first/last are based on rowCount "before modification"; remember the position before acting
- Early returns cause begin/end mismatch; guard with try/finally
- For batch inserts, insert from back to front so the position anchor doesn't drift
- layoutChanged is a heavy weapon; avoid it when possible; prefer dataChanged and structural signals
