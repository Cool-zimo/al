# The Data Layer and the Model: Turning Database Rows into Qt Data

> The previous lesson settled the layering. This lesson does the actual work: write a `TransactionModel` that turns the result of an SQLite query into something a `QAbstractTableModel` can hand back to a view. The data layer stays exactly what it was — the Model is the translator.

## A Complete Skeleton for `TransactionModel`

Revisit the "three methods" from Chapter 1: `rowCount`, `columnCount`, and `data`. Add `headerData` and you have the smallest usable Model. Everything else in this lesson is layered on top of that skeleton:

```python
from PySide6.QtCore import Qt, QAbstractTableModel, QModelIndex

from data import all_records, add as db_add, delete as db_delete


class TransactionModel(QAbstractTableModel):
    HEADERS = ["Date", "Category", "Amount", "Note"]

    def __init__(self, parent=None):
        super().__init__(parent)
        self._records = []           # each item is an sqlite3.Row or a dict
        self.refresh()

    def rowCount(self, parent=QModelIndex()):
        return len(self._records)

    def columnCount(self, parent=QModelIndex()):
        return len(self.HEADERS)

    def data(self, index, role=Qt.ItemDataRole.DisplayRole):
        if not index.isValid():
            return None
        record = self._records[index.row()]
        col = index.column()
        if role == Qt.ItemDataRole.DisplayRole:
            if col == 0:
                return str(record["date"])
            if col == 1:
                return str(record["category"])
            if col == 2:
                return f"{record['amount']:.2f}"
            if col == 3:
                return str(record["note"] or "")
        return None

    def headerData(self, section, orientation, role=Qt.ItemDataRole.DisplayRole):
        if role == Qt.ItemDataRole.DisplayRole and orientation == Qt.Orientation.Horizontal:
            return self.HEADERS[section]
        return None
```

**Watch the column mapping.** `col == 2` is the amount column, and the formatting logic lives here. As Chapter 1 said, the view asks `data` whenever it needs something — you do not have to worry about when or how often.

## Plugging in the Data Layer

`refresh()` pulls rows from the database and wraps them in `beginResetModel` / `endResetModel`, which tells every attached view "everything changed":

```python
def refresh(self):
    self.beginResetModel()
    self._records = list(all_records())   # the query from data.py
    self.endResetModel()
```

If `all_records()` returns `sqlite3.Row`, you can read fields by name as `record["date"]`. If it returns plain tuples, you must use positional indexing as `record[0]`. **Either style works, but you must pick one.** Mixing them is one of the hardest bugs to spot.

**Prefer `sqlite3.Row`.** Names like `"date"` and `"amount"` are far more readable than positional indices 0, 1, 2, 3, and they survive schema changes without silently shifting your columns around.

## Insert and Delete: Use the Fine-Grained Notifications

`refresh` is a sledgehammer — perfect for reloading everything at once. When you insert one new record, `beginInsertRows` / `endInsertRows` is the more elegant choice: the view inserts just that row, and the scroll position plus the selection state stay put:

```python
def add_record(self, date, category, amount, note=""):
    db_add(date, category, amount, note)          # write to the database first
    row = self.rowCount()
    self.beginInsertRows(QModelIndex(), row, row) # announce one new row at the end
    self._records.append(None)                    # placeholder; refresh overwrites it
    self.endInsertRows()
    self.refresh()                               # re-pull so ordering is correct
```

**Wait — isn't appending and then refreshing redundant?** It is. If the order of your query does not matter, a single `self.refresh()` does the job. The correct way to use `beginInsertRows` looks like this:

```python
def add_record(self, date, category, amount, note=""):
    db_add(date, category, amount, note)
    self.refresh()   # beginResetModel / endResetModel are already inside refresh
```

**For this project, where records are shown newest-first by date, `refresh` is enough.** Fine-grained insert and remove pay off when the list is huge — tens of thousands of rows — and you would rather not re-query the whole table on every change. In that case you insert only the new row and maintain `_records` order yourself.

## Removing a Row

Deletion needs the **real row number in the source model**, because the view may be sitting behind a proxy that filters or reorders rows. The row that *looks* like row 3 in the view is not necessarily row 3 in the source. We cover that trap in Lesson 28; for now here is deletion in the source model itself:

```python
def remove_row(self, row):
    if 0 <= row < len(self._records):
        tid = self._records[row]["id"]
        self.beginRemoveRows(QModelIndex(), row, row)
        del self._records[row]
        self.endRemoveRows()
        db_delete(tid)           # delete from the database after the model changes
```

**The order matters: mutate the model first, then the database.** If you delete from the database and it raises an exception, the model has already told the view "I am gone", and the UI no longer matches reality. A safer version wraps `db_delete` in a try block and restores the data on failure — for a small local SQLite project that complexity is usually not worth it.

## Multiple Roles: Right-Aligned Amounts and Red for Negative Numbers

Chapter 1 covered how `data()` can answer several roles. That is genuinely useful in a ledger:

```python
def data(self, index, role=Qt.ItemDataRole.DisplayRole):
    if not index.isValid():
        return None
    record = self._records[index.row()]
    col = index.column()

    if role == Qt.ItemDataRole.DisplayRole:
        # ... column values omitted for brevity
        if col == 2:
            return f"{record['amount']:.2f}"

    if role == Qt.ItemDataRole.TextAlignmentRole and col == 2:
        return Qt.AlignmentFlag.AlignRight | Qt.AlignmentFlag.AlignVCenter

    if role == Qt.ItemDataRole.ForegroundRole and col == 2:
        if record["amount"] < 0:
            return QBrush(QColor(200, 0, 0))      # expenses in red

    return None
```

Remember to add `from PySide6.QtGui import QBrush, QColor` to your imports. **Handling five or six roles inside one `data()` method is the norm**, not a code smell — resist the urge to subclass a hundred role-specific classes. Just stack `if role ==` checks.

## Serving Aggregates to the Charts

The model is the right place for derived data. The pie and bar charts both need pre-aggregated values, and the model is where that calculation belongs:

```python
def total_by_category(self):
    """Return {category: total}."""
    result = {}
    for r in self._records:
        cat = r["category"]
        result[cat] = result.get(cat, 0.0) + r["amount"]
    return result

def total_by_month(self):
    """Return {"2026-09": total, ...}."""
    result = {}
    for r in self._records:
        month = str(r["date"])[:7]
        result[month] = result.get(month, 0.0) + r["amount"]
    return result
```

**Why put it in the model instead of the view?** Because these two aggregates are just another *shape* of the same data. Whoever needs them calls the model; the view does not have to iterate the records all over again.

## Crash Site 1: Forgetting beginResetModel / endResetModel, UI Stuck on Old Data

**Symptom:** You call `self._records.append(...)` directly inside `add_record` and expect a new row to appear. Nothing happens.

**WRONG — Do not do this:**

```python
def add_record(self, date, category, amount, note=""):
    db_add(date, category, amount, note)
    self._records = list(all_records())   # the view has no idea anything changed
```

**The fix:**

```python
def refresh(self):
    self.beginResetModel()
    self._records = list(all_records())
    self.endResetModel()
```

## Crash Site 2: Wrong Start and End Indices for beginInsertRows

**Symptom:** An assertion failure `ASSERT: "last >= first"`, or the UI inserts multiple rows / inserts them in the wrong place.

**WRONG — Do not do this:**

```python
self.beginInsertRows(QModelIndex(), row, row + 1)   # inserting at row, not two rows
```

**The fix:**

```python
self.beginInsertRows(QModelIndex(), row, row)        # first == last means one row
```

`beginInsertRows(parent, first, last)` uses an *inclusive* last index. One row is `row, row`; three rows are `row, row + 2`.

## Crash Site 3: `data()` Returns "" Instead of None, Roles Cross-Contaminate

**Symptom:** Every role other than `DisplayRole` returns a string, so alignment and colors stop working and the program occasionally crashes.

**WRONG — Do not do this:**

```python
def data(self, index, role):
    if role == Qt.ItemDataRole.DisplayRole:
        return str(self._records[index.row()][index.column()])
    return ""   # Qt treats this empty string as a real value for whatever role asked
```

**The fix:**

```python
def data(self, index, role):
    if role == Qt.ItemDataRole.DisplayRole:
        return ...
    return None   # "I have nothing for this role"
```

**The difference between `return None` and `return ""` is fatal.** `None` tells the view "I have no value for this role, use the default". An empty string says "I have a value and it is empty", so Qt will genuinely paint an empty something — and odd things follow.

## Crash Site 4: Mixing Tuple Indexing with Dictionary-Style Access

**Symptom:** `all_records()` returns tuples, but your `data` uses both `record[2]` and `record["amount"]`. Half of it works, half raises `KeyError`.

**The fix: pick one style.** Either make `all_records()` return `sqlite3.Row` (recommended) or use positional indexing everywhere. Do not trust yourself to remember which column holds the amount.

## Crash Site 5: Swallowing the `db_add` Exception, UI Thinks It Succeeded

**Symptom:** You click the entry button, nothing happens, and there is no record in the database. Digging in, you find the date format was wrong and the SQL raised — but some layer swallowed it with `except: pass`.

**The fix: let the exception propagate to the UI layer so it can show a message.** The model must not pop up a dialog — it should not even know a UI exists. Let the exception bubble up to the slot that called it, and display a `QMessageBox.warning` there.

## Crash Site 6: Holding a Database Connection in the Model

**Symptom:** After running for a while the program reports "too many open connections", or the database is locked on exit.

**The fix: use `with connect() as conn` as a context manager so every operation opens and closes its own connection.** Never store `conn` as `self._conn` for the long term — SQLite's write lock is per connection, and one long-lived connection blocks every other writer.

## Summary

- `TransactionModel` subclasses `QAbstractTableModel`; the core is `rowCount` / `columnCount` / `data` / `headerData`
- `data()` dispatches by `if role ==` and can handle many roles (alignment, colour, display format)
- Use `beginResetModel` / `endResetModel` for a full reload; use `beginInsertRows` / `beginRemoveRows` for surgical changes
- For inserts, `first` and `last` are inclusive — one row is `row, row`
- Return `None` for roles you do not handle; never return an empty string
- Aggregates (by category, by month) belong in the model
- Always use a context manager for database operations; never hold the connection long-term
