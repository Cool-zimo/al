# Custom Models: Subclassing QAbstractTableModel and the Three Methods You Must Implement

> QStandardItemModel is enough — until your data lives in a CSV, a database, or a network API. Then you write your own model: tell Qt how many rows, how many columns, and what each cell contains.

## The Minimal Skeleton of a Custom Model

**Subclass `QAbstractTableModel` (use `QAbstractListModel` for lists, `QAbstractItemModel` for trees).** A table model must implement three methods: `rowCount`, `columnCount`, `data`. Add `headerData` for complete headers.

```python
from PySide6.QtCore import QAbstractTableModel, Qt

class ScoreModel(QAbstractTableModel):
    def __init__(self, rows=None):
        super().__init__()
        self._rows = rows or []

    def rowCount(self, parent=Qt.QModelIndex()):
        return len(self._rows)

    def columnCount(self, parent=Qt.QModelIndex()):
        return 3

    def data(self, index, role=Qt.DisplayRole):
        if not index.isValid():
            return None
        if role == Qt.DisplayRole:
            return str(self._rows[index.row()][index.column()])
        return None

    def headerData(self, section, orientation, role=Qt.DisplayRole):
        if role == Qt.DisplayRole:
            if orientation == Qt.Horizontal:
                return ["Name", "Subject", "Score"][section]
            return f"Row {section + 1}"
        return None
```

**Four methods, each answering one specific question.** rowCount answers "how many rows," columnCount answers "how many columns," data answers "what does this cell display," and headerData answers "what does the header say." The view draws the entire table by asking these four questions.

## Crash Site 1: data() Doesn't Handle DisplayRole — Everything Is Blank

**Symptom: The model is connected, the table draws, but every cell is empty. No error, just a white UI.**

```python
def data(self, index, role=Qt.DisplayRole):
    value = self._rows[index.row()][index.column()]
    if role == Qt.EditRole:        # ❌ Only handled EditRole
        return value
    return None                    # DisplayRole falls through to None
```

**Root cause: QTableView fetches display content via DisplayRole by default.** You only implemented EditRole, which is used when double-clicking to edit. For normal display, the view asks for DisplayRole; you returned None, so nothing is drawn.

**✅ Fix: At minimum, handle DisplayRole.**

```python
def data(self, index, role=Qt.DisplayRole):
    value = self._rows[index.row()][index.column()]
    if role == Qt.DisplayRole:
        return str(value)          # ✅ For display
    if role == Qt.EditRole:
        return value               # ✅ For editing
    return None
```

**DisplayRole must return a string (or a string-convertible type).** Returning None means "I have no value to display," leaving the cell empty.

## Crash Site 2: Forgetting index.isValid() — Out-of-Bounds Crash

**Symptom: Occasional crash with `IndexError: list index out of range`.**

```python
def data(self, index, role=Qt.DisplayRole):
    r, c = index.row(), index.column()
    return str(self._rows[r][c])      # ❌ No validation; index may be invalid
```

**Root cause: During layout, drag-and-drop, and editing, the view may ask about an invalid index** (e.g., parent is invalid, or the row count just changed). At that point `index.isValid()` is False, `row()` returns -1, and using it as a subscript blows up.

**✅ Fix: Always validate with isValid first.**

```python
def data(self, index, role=Qt.DisplayRole):
    if not index.isValid():              # ✅ Always validate first
        return None
    if index.row() >= len(self._rows):
        return None
    if index.column() >= len(self._rows[0]):
        return None
    # Business logic goes below
```

**This isValid check is not defensive-programming hygiene — it is part of the Qt protocol.** Skip it and your model becomes crash-prone during dynamic inserts and deletes.

## Crash Site 3: Forgetting headerData — Headers Show 1, 2, 3

**Symptom: Data displays fine, but headers are numbers 1, 2, 3 instead of your desired "Name," "Subject," "Score."**

```python
class ScoreModel(QAbstractTableModel):
    # ❌ No headerData implemented
    def rowCount(self, parent=Qt.QModelIndex()):
        return len(self._rows)
    def columnCount(self, parent=Qt.QModelIndex()):
        return 3
    def data(self, index, role=Qt.DisplayRole):
        return str(self._rows[index.row()][index.column()])

# View shows headers 1, 2, 3
```

**Root cause: Without overriding headerData, the base class default returns section + 1 (i.e., 1, 2, 3).**

**✅ Fix: Implement headerData, distinguishing row vs. column headers by orientation.**

```python
def headerData(self, section, orientation, role=Qt.DisplayRole):
    if role != Qt.DisplayRole:
        return None
    if orientation == Qt.Horizontal:
        headers = ["Name", "Subject", "Score"]
        return headers[section] if section < len(headers) else None
    return f"Row {section + 1}"     # Vertical header (row number)
```

**Headers are the user's first entry point to understanding a table.** Without them your model works but looks "ugly" — like writing a function without a docstring.

## Crash Site 4: Forgetting to Implement index() — Assumed the Base Class Handles It

**Symptom: When writing a custom model, index() was not implemented; the runtime raises `NotImplementedError`, or index() returns all-invalid indices.**

```python
class MyModel(QAbstractTableModel):
    # ❌ Forgot to implement index(); the base class index() returns an invalid index
    def rowCount(self, parent=Qt.QModelIndex()):
        return len(self._rows)
    # ... everything else implemented
```

**Root cause: `QAbstractTableModel` actually provides a default index implementation (returning createIndex(row,col)), but many developers think they must write it themselves and produce a broken version.** Conversely, if you subclass the bottom-level `QAbstractItemModel`, index is a pure virtual that must be implemented.

**✅ Fix: QAbstractTableModel already provides a default index. Use it as-is, or customize by attaching a pointer in data.**

```python
# QAbstractTableModel already has a default index() implementation
# Equivalent to:
def index(self, row, column, parent=Qt.QModelIndex()):
    if not self.hasIndex(row, column, parent):
        return Qt.QModelIndex()
    return self.createIndex(row, column, None)

# For a table this is sufficient — no need to override
```

**`hasIndex(row, column, parent)` is Qt's convenience method, equivalent to checking whether row/column are within valid bounds.** Table models can use the base class index directly without writing it by hand.

## setData and flags: Making a Model Editable

**Display alone is not enough — you want cells to be editable. Two requirements: `flags()` must return `ItemIsEditable`, and `setData()` must handle EditRole.**

```python
def flags(self, index):
    f = super().flags(index)
    return f | Qt.ItemIsEditable         # Add the editable flag

def setData(self, index, value, role=Qt.EditRole):
    if not index.isValid() or role != Qt.EditRole:
        return False
    self._rows[index.row()][index.column()] = value
    self.dataChanged.emit(index, index, [role])   # ✅ Must emit the signal
    return True
```

**`flags()` determines what a cell "can do."** Common flags:

| Flag | Meaning |
|---|---|
| `Qt.ItemIsSelectable` | Can be selected |
| `Qt.ItemIsEditable` | Can be double-clicked to edit |
| `Qt.ItemIsEnabled` | Enabled (removing it grays the item out) |
| `Qt.ItemIsUserCheckable` | Can be checked (paired with CheckStateRole) |
| `Qt.ItemIsDragEnabled` / `ItemIsDropEnabled` | Can be dragged/dropped |

**Flags are combined with bitwise OR.** Call `super().flags(index)` first to get default flags, then `|` on what you want to add. Do not just return a new value (that discards default behavior).

## Crash Site 5: setData Doesn't Emit dataChanged — UI Doesn't Refresh

**Symptom: Double-click a cell to edit, type a new value, press Enter. Once focus leaves, the value snaps back.**

```python
def setData(self, index, value, role=Qt.EditRole):
    self._rows[index.row()][index.column()] = value
    # ❌ No dataChanged signal emitted
    return True
```

**Root cause: The internal data did change, but the view doesn't know.** The view only repaints that area upon receiving dataChanged. No signal means the display stays at the old value.

**✅ Fix: After changing, immediately emit dataChanged, telling the view "which range changed."**

```python
self.dataChanged.emit(index, index, [role])
#                    start    end     role list
```

**The two indices in dataChanged are the "dirty region's" top-left and bottom-right corners.** For a single cell, pass the same index twice. For multiple rows, pass the first and last rows. Qt only repaints that region — efficient.

## Summary

- A custom table model must implement rowCount / columnCount / data; headerData is recommended
- data() must at least handle DisplayRole, otherwise the UI is blank with no error
- index.isValid() validation always comes first — it is Qt protocol, not paranoia
- headerData distinguishes row/column headers by orientation; skip it and you get 1, 2, 3
- QAbstractTableModel's index() has a default implementation; table models need not write it by hand
- Editable requires flags with ItemIsEditable + setData handling EditRole
- setData must emit dataChanged after changing, otherwise the display won't refresh
