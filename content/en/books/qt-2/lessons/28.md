# The Interface and Interaction: Sorting, Filtering, Entry and Delete

> The model is ready. This lesson wires it up to a view. The two key pieces are `QSortFilterProxyModel` for sorting and category filtering, and `QItemSelectionModel` for "select and delete".

## QSortFilterProxyModel Sits in the Middle

Its position never changes: it is always **source model → proxy → view**:

```text
TransactionModel (source)
       |  setSourceModel
QSortFilterProxyModel (filter + sort)
       |  setModel
QTableView
```

**The proxy is not a second copy of your data; it is a "view of a view".** The source model is unchanged — the proxy only decides which rows are visible and in what order. That also means: when you delete data, you must delete the row in the **source** model, not the row the proxy is showing.

## Category Filtering: Override filterAcceptsRow

`QSortFilterProxyModel` can match a string against a single column by default. To get "pick a category from a dropdown, show only that category", you need a custom rule:

```python
from PySide6.QtCore import QSortFilterProxyModel, Qt

class CategoryFilterProxy(QSortFilterProxyModel):
    def __init__(self, parent=None):
        super().__init__(parent)
        self._category = ""                      # empty string means "all"

    def set_category(self, category):
        self._category = category
        self.invalidateFilter()                  # tell Qt to re-filter now

    def filterAcceptsRow(self, source_row, source_parent):
        if not self._category:
            return True                          # show everything
        model = self.sourceModel()
        idx = model.index(source_row, 1, source_parent)   # column 1 is category
        return model.data(idx) == self._category
```

**`invalidateFilter()` is the key line.** Changing `_category` is not enough — the proxy will keep its old filter result and the UI will not move. `set_category` is the public API you expose; outside code calls it instead of poking at the proxy's internals.

## Sorting: Override lessThan or Set a sortRole

The easiest way to make the amount column sortable by clicking the header is to hand the proxy a *comparable value* through `UserRole`, then tell it to sort by that role:

```python
from PySide6.QtCore import Qt

# Add this branch inside TransactionModel.data
def data(self, index, role=Qt.ItemDataRole.DisplayRole):
    ...
    if role == Qt.ItemDataRole.UserRole and index.column() == 2:
        return self._records[index.row()]["amount"]   # a float, directly comparable
```

Then enable sorting in the main window:

```python
self.proxy = CategoryFilterProxy(self)
self.proxy.setSourceModel(self.model)
self.table.setModel(self.proxy)
self.table.setSortingEnabled(True)
self.proxy.setSortRole(Qt.ItemDataRole.UserRole)
```

**Why not sort by the display string?** Because the display value is `"38.50"`, and in string order `"9.00"` comes after `"38.50"` (the first character `'9'` is greater than `'3'`). Returning a float through `UserRole` makes numeric sorting correct.

## Selecting and Deleting: QItemSelectionModel

`QTableView` already has a `selectionModel()`, and it is a `QItemSelectionModel`. Ask it for the user's selected rows:

```python
def on_delete(self):
    sel = self.table.selectionModel()
    indexes = sel.selectedRows()          # a list of QModelIndex in the proxy's view
    if not indexes:
        QMessageBox.information(self, "Notice", "Select a row first")
        return

    # Map back to source-model row numbers — this step is not optional
    source_rows = []
    for idx in indexes:
        source_idx = self.proxy.mapToSource(idx)
        source_rows.append(source_idx.row())

    for row in sorted(source_rows, reverse=True):   # delete from the back
        self.model.remove_row(row)

    sel.clearSelection()
```

**`mapToSource` is the single easiest place to go wrong in this lesson.** After filtering or sorting, row 0 in the proxy may be row 3 in the source model. Calling `remove_row` with the proxy index deletes the wrong record at best and crashes with an out-of-bounds error at worst.

## Why Delete from Back to Front

Suppose the user selected rows 2 and 5 in the source model. If you delete row 2 first, the old row 5 becomes row 4 — so deleting "row 5" next deletes the wrong thing. Going from largest to smallest means earlier deletions never disturb the indices still waiting to be removed:

```python
rows = [2, 5]
for r in sorted(rows, reverse=True):   # [5, 2]
    self.model.remove_row(r)          # delete 5 first (2 is unaffected), then 2
```

**`sorted(..., reverse=True)` is not showing off — it is correctness.** Rule of thumb: whenever you delete several items by index, always go from the back.

## Crash Site 1: Using a Proxy Index Directly Against the Source Model

**Symptom:** After filtering to "Food", you delete one row — and a "Transport" record disappears. While filtered, the table's row 0 is source row 3, so deleting by 0 removes the wrong thing.

**WRONG — Do not do this:**

```python
idx = self.table.selectionModel().currentIndex()
self.model.remove_row(idx.row())          # idx is from the proxy's point of view
```

**The fix:**

```python
idx = self.table.selectionModel().currentIndex()
source_idx = self.proxy.mapToSource(idx)
self.model.remove_row(source_idx.row())
```

## Crash Site 2: Forgetting invalidateFilter, the Dropdown Does Nothing

**Symptom:** You pick "Food" and the table does not move. Picking "All" does nothing either.

**Cause:** You changed `_category` but never told the proxy to re-filter.

**The fix:**

```python
def set_category(self, category):
    self._category = category
    self.invalidateFilter()              # required
```

## Crash Site 3: Sorting Amounts as Strings, 9.00 Lands After 38.50

**Symptom:** After clicking the header, the amount column shows `"9.00"` below `"38.50"` (string lexicographic order: `'9'` > `'3'`).

**The fix: expose the amount as a float through `UserRole` and call `proxy.setSortRole(UserRole)`.**

## Crash Site 4: Mixing Up currentIndex and selectedRows

**Symptom:** After a multi-select, only one row is deleted; or with nothing selected, `currentIndex()` returns an invalid index and `.row()` produces a meaningless number.

**The fix: use `selectedRows()` to get every selected row for a delete operation. For a single-row action use `currentIndex()`, but always check `isValid()` first.**

## Crash Site 5: Deleting Front to Back, Shifting the Wrong Rows

**Symptom:** You selected rows 2 and 5, and rows 2 and 6 got deleted.

**The fix: delete from back to front with `sorted(rows, reverse=True)`.**

## Crash Site 6: Not Clearing the Selection After Deleting

**Symptom:** After the deletion, the old row position stays highlighted in blue even though the selection now points at nothing; pressing Delete again raises an out-of-bounds error.

**The fix: call `selectionModel().clearSelection()` after the delete loop.**

## Crash Site 7: setSortingEnabled(True) But the Header Click Does Nothing

**Symptom:** The header is clickable but the data does not sort.

**Cause:** `sortRole` is not set, or the source model's `data()` does not handle `UserRole`. **You need both: the proxy must know which role to compare, and the model must be able to supply that role's value.**

## Summary

- A `ProxyModel` is the middle layer between the source model and the view; it holds no copy of the data
- Custom filtering means overriding `filterAcceptsRow`; call `invalidateFilter` after changing the condition
- Numeric sorting needs a comparable value via `UserRole` plus `setSortRole`
- Before deleting, always `mapToSource` to convert proxy coordinates back to source coordinates
- When deleting multiple rows, iterate from back to front with `sorted(rows, reverse=True)`
- Clear the selection after deletion
- While filtered, proxy row numbers and source row numbers do not correspond — never mix them
