# Project Design: Rewriting the tkinter Ledger with Qt

> This volume has taken you from Model/View to drawing to networking. The capstone project is to **rewrite the tkinter ledger app you built in "Window Basics 3" entirely in Qt** — same database, completely different UI layer.

## What You Built Before

That ledger app from "Window Basics 3" looked roughly like this: an SQLite store for income and expense records, a tkinter entry window and listbox, and a matplotlib pie chart. It had four layers:

```
Data layer     data.py       table creation, add/delete/query, summaries by category/month
Model layer    models.py     a record-object wrapper (optional)
UI layer       app.py        tkinter windows, Entry, Button, Listbox
Chart layer    charts.py     matplotlib generates an image and drops it into a tkinter.Label
```

That structure was good. **A maintainable project is never "all code in one file" — it's code organized by responsibility, with each layer doing exactly one thing.** What we reuse is this layered thinking; what we swap out is the technology stack inside it.

## What You Can Reuse As-Is

**The data layer changes almost not at all.** The table-creation statement, the add/delete/query SQL, and the summary-by-category and summary-by-month query functions all stay untouched. Why? Because they only depend on `sqlite3` and have nothing to do with the UI.

```
# data.py -- this layer is byte-for-byte identical in the Qt version
import sqlite3

def connect():
    return sqlite3.connect("ledger.db")

def init_db():
    with connect() as conn:
        conn.execute("""
            CREATE TABLE IF NOT EXISTS transactions (
                id INTEGER PRIMARY KEY AUTOINCREMENT,
                date TEXT NOT NULL,
                category TEXT NOT NULL,
                amount REAL NOT NULL,
                note TEXT
            )
        """)

def add(date, category, amount, note=""):
    with connect() as conn:
        conn.execute(
            "INSERT INTO transactions(date, category, amount, note) VALUES (?, ?, ?, ?)",
            (date, category, amount, note))

def delete(tid):
    with connect() as conn:
        conn.execute("DELETE FROM transactions WHERE id = ?", (tid,))

def all_records():
    with connect() as conn:
        conn.row_factory = sqlite3.Row
        return conn.execute(
            "SELECT * FROM transactions ORDER BY date DESC").fetchall()
```

**The model layer stays too:** `Category` enums, date-formatting helpers — all pure logic functions keep working.

## What You Must Rewrite

**The UI and chart layers are fully replaced**, and that's the heart of this chapter:

| Original (tkinter) | Now (Qt) | What changes |
|---|---|---|
| `Listbox` for records | `QTableView` + `TransactionModel` | Records become "data in a model"; the view responds automatically |
| `Entry` + `Button` entry | `QFormLayout` + signals and slots | Cleaner layout; validation fits naturally |
| Refreshing the list on a button click | The Model notifies the View to refresh automatically | No more manual `listbox.delete(0, END)` |
| matplotlib image in a Label | Charts drawn with `QPainter` | Zero dependencies, vector output, scales with the window |

## What the Qt Version Adds

These are the four things this chapter implements, one by one — and they're the real value of the Qt rewrite:

**1. Sorting and filtering.** Click a header to sort by amount or date; use a dropdown to show only "Dining." A tkinter Listbox would force you to reorder the list by hand. With Qt, a single `QSortFilterProxyModel` sits between the Model and the View and you're done in a few lines.

**2. A progress-bar cell.** Draw a horizontal bar in each category row, its length representing that category's share of total expenses. This is where Chapter 3's Delegate pays off — a custom `paint` lets you draw anything inside a cell.

**3. Hand-drawn charts.** Pie and bar charts both drawn with `QPainter`, no matplotlib dependency. The benefits: a lighter program, charts that scale with the window, and a visual style unified with the rest of the UI. The trade-off: you compute the angles and handle the legend yourself.

**4. Select-to-act.** Click a row to highlight it, press Delete to remove it. This is `QItemSelectionModel` under the hood — far more elegant than "remembering the selected index" in tkinter.

## The Three-Layer Architecture in the Qt Version

```
data.py              Data layer: SQLite (unchanged)
   |  returns list[dict] or sqlite3.Row
models.py           TransactionModel: turns records into a QAbstractTableModel
   |  data
QSortFilterProxyModel  Sorting/filtering (optional extra layer)
   |
QTableView           View + custom Delegate
   |  signals
MainWindow           Window: entry form, buttons, chart control, delete on select
   |
ChartView(QWidget)   Hand-drawn pie + bar charts
```

**The key insight: the Model is the translator between the "data layer" and the "UI layer."** The data layer only understands SQL and rows; the View only understands three methods — `rowCount`, `columnCount`, and `data`. The Model bridges them, which means the data layer can be swapped (to a JSON file, to a network API) without touching the UI at all.

## Why Not matplotlib Anymore

matplotlib isn't bad — it's an **extra dependency**, and a large one. A 200-line ledger suddenly doubles in size once you bundle matplotlib. More importantly, matplotlib produces a **bitmap**, which goes fuzzy when scaled; `QPainter` draws vector paths, which stay crisp at any zoom level.

**It's not that matplotlib is bad; it's that the right tool depends on the scale.** A small embedded chart belongs in `QPainter`. For 3D visualization, scientific plotting, or exporting a high-resolution figure, matplotlib (or PyQtGraph) is the better choice. We'll revisit that trade-off in Chapter 29.

## Crash Site 1: SQL in a Slot Function, Data Logic Leaking into the UI

**Symptoms:** `on_add` writes `conn.execute("INSERT ...")` directly; later, when you add a "CSV import" feature, you have to copy the same SQL all over again.

**WRONG — Do not do this:**

```
def on_add(self):
    conn = sqlite3.connect("ledger.db")
    conn.execute("INSERT INTO transactions(...) VALUES (...)")
    conn.commit()
    # Refresh the list
    self.refresh_listbox()
```

**The fix: Keep all data operations in `data.py`; the UI only calls functions.** That way, swapping the database, adding a cache, or adding logging means changing exactly one place.

## Crash Site 2: "Qt Is a Rewrite, So I'll Recreate the Table Too"

**Symptoms:** The new program creates a new table, losing all old data; or the two table-creation statements drift out of sync, making migration painful.

**The fix: `init_db()` runs once at startup, and `IF NOT EXISTS` makes it idempotent.** Existing database files are reused; on a fresh machine it creates the table automatically.

## Crash Site 3: Building the UI Before the Data Structure, Discovering a Mismatch Halfway

**Symptoms:** The entry form has a "type (income/expense)" field, but the database table has no such column — now you must change either the schema or the form, redoing both.

**The fix: Before writing code, sketch the table structure and the Model's column definitions on paper.** Settle the `transactions` columns first, then `TransactionModel.HEADERS`, and only then the UI. The data contract comes first; the UI follows it.

## Crash Site 4: Chart and Table Logic in the Same Class

**Symptoms:** `MainWindow` contains both table logic and drawing logic; 500 lines in one class, and finding the legend position means scrolling forever.

**The fix: Make the chart its own `ChartView(QWidget)` subclass that only exposes `set_data(records)`.** The main window only feeds it data — how it's drawn and whether it finishes drawing is none of the window's business.

## Crash Site 5: Assuming Qt Is Automatically Faster Than tkinter

**Symptoms:** The same add/delete operations feel no faster in Qt, and there's actually more code.

**The proper understanding: Qt's advantage isn't "it runs faster" — it's "cleaner structure, fuller features, easier maintenance."** Sorting, filtering, custom cell rendering, vector charts — all things tkinter would force you to build from scratch, Qt ships with. The extra code exists because you're using a proper architecture, not because Qt is bloated.

## Summary

- The original project's four layers (data/model/UI/chart) are all preserved in the Qt version
- The data layer (SQLite) is reused as-is; the UI and chart layers are rewritten
- The Model is the translator between data and UI, keeping both decoupled
- The Qt version adds: sorting/filtering, progress-bar cells, hand-drawn vector charts, select-to-act
- matplotlib suits scientific plotting; `QPainter` suits embedded small charts — pick by scale
- Settle the data contract (table schema + Model columns) before writing the UI
- Wrap the chart in its own control; don't stuff it into the main window
