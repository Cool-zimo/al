# Event Handling: mousePressEvent and keyPressEvent, and the Difference Between event and eventFilter

> A hand-painted widget does not respond to clicks by itself — you handle mouse and keyboard events yourself. This lesson covers the event dispatch mechanism and the difference between `event()` and event filters.

## The Event Mechanism: Who Sends What to Whom

**Qt is event-driven. Every mouse click, keypress, and window resize becomes a `QEvent` object, dispatched by Qt's event loop to the relevant widget.**

**When a widget receives an event, it calls the matching handler:**

| Event | Handler |
|---|---|
| Mouse pressed | `mousePressEvent(event)` |
| Mouse released | `mouseReleaseEvent(event)` |
| Mouse moved | `mouseMoveEvent(event)` |
| Double-click | `mouseDoubleClickEvent(event)` |
| Key pressed | `keyPressEvent(event)` |
| Key released | `keyReleaseEvent(event)` |
| Wheel | `wheelEvent(event)` |
| Enter / leave | `enterEvent(event)` / `leaveEvent(event)` |
| Paint | `paintEvent(event)` |
| Resize | `resizeEvent(event)` |

**To handle an event, override the corresponding method.**

## The Basics of Mouse Events

```python
from PySide6.QtCore import Qt
from PySide6.QtWidgets import QWidget, QApplication

class ClickWidget(QWidget):
    def __init__(self, parent=None):
        super().__init__(parent)
        self.setMinimumSize(200, 200)

    def mousePressEvent(self, event):
        if event.button() == Qt.LeftButton:
            pos = event.position().toPoint()       # Click position (relative to this widget)
            print(f"Left click at ({pos.x()}, {pos.y()})")
        elif event.button() == Qt.RightButton:
            print("Right click")
        super().mousePressEvent(event)              # Hand the event to the parent class

    def mouseMoveEvent(self, event):
        pos = event.position().toPoint()
        print(f"Mouse moved to ({pos.x()}, {pos.y()})")
        super().mouseMoveEvent(event)

    def keyPressEvent(self, event):
        if event.key() == Qt.Key_Escape:
            print("Esc pressed")
        elif event.key() == Qt.Key_A:
            print("A pressed")
        super().keyPressEvent(event)
```

**`event.position().toPoint()` returns coordinates relative to the widget's own top-left.** The origin is the widget's top-left, not the screen's.

## Crash Site 1: Forgetting super(), Parent Behaviour Disappears

**Symptom: you overrode `mousePressEvent` to add your own logic, but all the widget's normal click behaviour is gone — a `QPushButton` no longer highlights on press, and a `QLineEdit` loses its cursor.**

```python
class MyButton(QPushButton):
    def mousePressEvent(self, event):
        print("Clicked")
        # ❌ super() was never called, so the button's press-highlight and click signal never fire
```

**Root cause: the parent's `mousePressEvent` implements press-highlighting, state changes, and the click signal. Skip `super()` and all of that is lost.**

**✅ Fix: do your work, then call `super()`.**

```python
def mousePressEvent(self, event):
    if event.button() == Qt.LeftButton:
        print("Custom handling")
    super().mousePressEvent(event)     # ✅ Hand it to the parent class
```

**The exception is when you deliberately want to fully take over the event and not let the parent handle it — but that case is rare.**

## Crash Site 2: mouseMoveEvent Only Fires While a Button Is Held

**Symptom: you want "highlight on hover", but `mouseMoveEvent` only fires while you drag with a button held; moving the mouse alone does nothing.**

```python
def mouseMoveEvent(self, event):
    print("Moved")      # Only prints while dragging
```

**Root cause: by default a widget only receives continuous `mouseMove` events while a mouse button is held down. This is a performance optimisation.**

**✅ Fix: call `setMouseTracking(True)`.**

```python
class HoverWidget(QWidget):
    def __init__(self, parent=None):
        super().__init__(parent)
        self.setMouseTracking(True)        # ✅ Receive mouseMove even with no buttons held

    def mouseMoveEvent(self, event):
        pos = event.position().toPoint()
        print(f"Hover at ({pos.x()}, {pos.y()})")
        super().mouseMoveEvent(event)
```

## Crash Site 3: No Keyboard Events Arrive Because Focus Is Elsewhere

**Symptom: you overrode `keyPressEvent`, but pressing keys does nothing at all.**

```python
class KeyWidget(QWidget):
    def __init__(self, parent=None):
        super().__init__(parent)
        # ❌ No focus policy set, so the widget never receives keyboard focus

    def keyPressEvent(self, event):
        print("Key:", event.key())
```

**Root cause: keyboard events go only to the widget that currently has focus. A plain `QWidget` defaults to `NoFocus`, so it never enters the focus chain and keyboard events never reach it.**

**✅ Fix: set a focus policy.**

```python
class KeyWidget(QWidget):
    def __init__(self, parent=None):
        super().__init__(parent)
        self.setFocusPolicy(Qt.StrongFocus)   # ✅ Can receive focus

    def keyPressEvent(self, event):
        if event.key() == Qt.Key_Left:
            print("Left")
        elif event.key() == Qt.Key_Right:
            print("Right")
        super().keyPressEvent(event)
```

**`Qt.StrongFocus` means the widget can receive focus by clicking or via Tab. `Qt.ClickFocus` means it receives focus only by clicking.**

## event(): The Single Entry Point for All Events

**`event(event)` is the "front door" that every event passes through before reaching a specific handler. Its default implementation dispatches by event type to methods like `mousePressEvent`.**

```python
def event(self, event):
    if event.type() == QEvent.KeyPress:
        key_event = QKeyEvent(event)
        if key_event.key() == Qt.Key_F5:
            print("Intercepted F5; not passing it on to keyPressEvent")
            return True          # True means "I handled it; stop dispatching"
    return super().event(event)  # Everything else follows the normal path
```

**Return `True` to mean "the event is handled, stop dispatching"; return `False` or call `super()` to mean "continue the normal dispatch flow".**

**`event()` is ideal for interception and unified handling of several event types.** If you do not want to override five methods just to react to one event, override `event()` instead.

## Event Filters, eventFilter: Monitoring Someone Else's Events Without Subclassing

**`eventFilter` is one of the most-asked concepts. It lets you monitor another widget's events without subclassing it.**

```python
class Watcher(QObject):
    def eventFilter(self, watched, event):
        if event.type() == QEvent.MouseButtonPress:
            print(f"{watched.objectName()} was clicked")
            return False        # False = do not intercept; let the event continue
        return False

watcher = Watcher()
button = QPushButton("Button")
button.setObjectName("MyButton")
button.installEventFilter(watcher)     # Install the filter on the button
```

**Three steps: ① define a `QObject` subclass and override `eventFilter`; ② call `installEventFilter` on the target widget; ③ return `True` to intercept, `False` to let it through.**

## The Difference Between event() and eventFilter()

**This is the core distinction of the lesson:**

| | `event()` | `eventFilter()` |
|---|---|---|
| Who it watches | This widget's own events | Someone else's events |
| Prerequisite | Requires subclassing the widget | No subclassing needed; any `QObject` can be a filter |
| Purpose | Intercept or pre-process inside your own widget | Add monitoring without changing someone else's code |
| Return value | `True` = handled, stop dispatching | `True` = intercepted (target never sees it); `False` = let it through |

**`event()` is "my own front door"; `eventFilter` is "a security camera I attach to someone else's front door".**

## Crash Site 4: eventFilter Returns True but You Did Not Actually Handle the Event

**Symptom: you installed an event filter just to log clicks, but after clicking, the button no longer does anything — no click signal, no highlight.**

```python
class Logger(QObject):
    def eventFilter(self, watched, event):
        if event.type() == QEvent.MouseButtonPress:
            print("Clicked")
            return True         # ❌ Returned True without doing real work, so the event was swallowed
        return False
```

**Root cause: returning `True` means "the event is handled, do not dispatch it to the target's handler any more".** You only printed a message but told Qt "done", so the target's `mousePressEvent` was never called.

**✅ Fix: when you only want to observe, return `False` (let it through).**

```python
def eventFilter(self, watched, event):
    if event.type() == QEvent.MouseButtonPress:
        print("Clicked")
        return False            # ✅ Let it through
    return False
```

**Only return `True` when you genuinely mean to handle the event yourself — and usually you then need to perform the work the target would have done.**

## Crash Site 5: The Filter Object Gets Garbage-Collected and Filtering Silently Stops

**Symptom: after the program runs for a while, `eventFilter` is no longer called, even though nothing in the code changed.**

```python
def setup(widget):
    watcher = Watcher()
    widget.installEventFilter(watcher)
    # ❌ watcher is a local variable and may be garbage-collected after the function returns
```

**Root cause: `installEventFilter` stores only a pointer and does not increase the reference count. Python's GC reclaims `watcher`, and the filter silently dies.**

**✅ Fix: keep a reference, for example by storing it as an attribute.**

```python
self._watcher = Watcher()
widget.installEventFilter(self._watcher)
```

## Summary

- Events: `QEvent` objects are dispatched by the event loop, and widgets handle them by overriding the matching handler
- For mouse events, `event.position().toPoint()` gives you local coordinates
- Overridden handlers should normally call `super()`, or the parent's default behaviour is lost
- Hover tracking requires `setMouseTracking(True)`
- Receiving keyboard events first requires `setFocusPolicy`
- `event()` is the single entry point, used for interception and unified pre-processing; returning `True` stops dispatch
- `eventFilter` monitors another widget's events without subclassing; `False` lets the event through, `True` intercepts it
- Keep a reference to any filter object to prevent it being garbage-collected
