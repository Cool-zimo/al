# Parameters in Detail: Positional, Default, Keyword, and Order

> The previous lesson showed you *how to write `def`*. This one goes deep on the **parameters**: positional, default, keyword, and **the order they must appear in**.
>
> Two traps in this lesson are legendary: **a mutable object as a default value** and **that default "remembering" what you did last time**.

## 1. Positional arguments: matched by position

The most common style: arguments are lined up against parameters by position.

```python
def greet(city, name):
    return f"Hello {name} of {city}!"

print(greet("Beijing", "Alice"))      # Hello Alice of Beijing!
```

The first argument `"Beijing"` goes to `city`, the second `"Alice"` goes to `name` — they are matched by **position**.

⚠️ **Crash: swapping the arguments produces the wrong meaning, with no error.**

```python
def greet(city, name):
    return f"Hello {name} of {city}!"

print(greet("Alice", "Beijing"))      # Hello Beijing of Alice!  -- wrong, but no error
```

This does not raise anything, but the meaning is completely backwards. When the parameters are all the same type (here, both are strings), swapping them is very hard to spot. **Good parameter names help reviewers catch this** just by reading the call.

## 2. Default arguments: giving a parameter a fallback value

When one parameter almost always takes the same value, give it a default:

```python
def make_url(host, scheme="https"):
    return f"{scheme}://{host}"

print(make_url("example.com"))              # https://example.com
print(make_url("example.com", "http"))      # http://example.com
```

`scheme="https"` is a default argument. **If you skip it, the default is used; if you pass one, yours wins.**

⚠️ **Crash: putting a default argument before a positional one.**

```python
def make_url(scheme="https", host):     # WRONG  SyntaxError
    return f"{scheme}://{host}"
```

Python's rule is: **defaults must come after positionals**. The reason is "match the positional ones first, then fill the rest with defaults"; reverse the order and the interpreter cannot decide which position goes where. The iron rule: **positionals first, defaults after**.

## 3. Keyword arguments: naming the value you pass

When you call a function you can say which parameter each value belongs to:

```python
def connect(host, port, timeout):
    print(f"Connecting to {host}:{port}, timeout {timeout}s")

connect(host="localhost", port=3306, timeout=5)
connect(port=3306, host="localhost", timeout=5)     # order no longer matters
```

Writing `name=` lets you ignore the order, and it reads more clearly.

⚠️ **Crash: a positional argument after a keyword argument.**

```python
connect("localhost", port=3306, 5)      # WRONG  SyntaxError: positional argument follows keyword argument
```

The rule is: **positionals first, keywords after**. Once you have used a keyword, you cannot go back to positional style.

⚠️ **Crash: passing the same parameter twice.**

```python
connect(host="localhost", port=3306, host="127.0.0.1")
# WRONG  SyntaxError: keyword argument repeated: host
```

You cannot pass one parameter both positionally and by keyword, nor use a keyword twice.

## 4. The classic trap: a mutable default value

This is **the most famous and sneaky trap in Python** — almost everyone falls into it once.

```python
def add_item(item, bag=[]):        # BAD: default is a mutable object!
    bag.append(item)
    return bag

print(add_item("apple"))        # ['apple']
print(add_item("banana"))       # ['apple', 'banana']  <- not just ['banana']!
```

On the second call, `bag` **still contains last time's `"apple"`**. Why?

**The reason:** the default value (that `[]`) is **created once, when the function is defined**, and then shared by every call. A list is mutable, so every `append` pollutes the one "default bag" that everybody shares.

⚠️ **Crash: a "helpful default" that becomes a bug factory.**

```python
def register(name, scores=[]):
    scores.append(0)           # trying to initialise a new user with 0 points
    print(name, scores)

register("Alice")              # Alice [0]
register("Bob")                # Bob [0, 0]  <- why does Bob carry Alice's 0?
```

`[]` is created only once, at definition time, and every call shares that same list. Alice's 0 stays in it, and Bob gets appended on top.

**The fix: use `None` as a placeholder, and create the list inside the function.**

```python
def add_item(item, bag=None):
    if bag is None:
        bag = []               # a brand-new list, every call
    bag.append(item)
    return bag

print(add_item("apple"))        # ['apple']
print(add_item("banana"))       # ['banana']  <- clean
```

`None` is immutable, so it cannot "remember" anything. `bag = []` runs on each call, so each call starts with a blank sheet.

⚠️ **Crash: thinking "you can never use a list as a default" — the real rule is "never use a mutable object as the default instance".**

```python
def get_config(key, default=None):      # OK  None as the default, no problem
    return default

def get_config(key, default=[]):       # BAD  a list as the default, trap
    return default
```

The point is not "lists are forbidden as arguments", it is "**the default value must be immutable**". `None`, numbers, strings and tuples are fine; lists, dictionaries and sets are not.

## 5. The full ordering rule

Putting everything together:

```python
def order(a, b, c=3, d=4):
    return (a, b, c, d)

print(order(1, 2))              # (1, 2, 3, 4)
print(order(1, 2, 30))          # (1, 2, 30, 4)
print(order(1, 2, d=40))        # (1, 2, 3, 40)
print(order(1, 2, 30, 40))      # (1, 2, 30, 40)
```

**Iron rule for the definition:** positional → default. (Lessons 27 and 28 add `*args` and `**kwargs` after that.) If you cannot remember the full list, just write the positionals first and the defaults after.

## 6. A practical example: connecting to a database

```python
def connect_db(host, port=3306, user="root", charset="utf8mb4"):
    return f"mysql://{user}@{host}:{port}?charset={charset}"

print(connect_db("localhost"))
# mysql://root@localhost:3306?charset=utf8mb4

print(connect_db("10.0.0.1", port=5432, user="app"))
# mysql://app@10.0.0.1:5432?charset=utf8mb4
```

`host` is required (no default), and the rest have sensible defaults. This "**one required plus several optional**" shape is where default arguments really earn their keep.

⚠️ **Crash: the mutable-default trap in real code, with alarmingly subtle symptoms.**

```python
def fetch_users(ids, cache={}):
    uncached = [i for i in ids if i not in cache]
    for i in uncached:
        cache[i] = f"user{i}"        # pretending to hit the database
    return [cache[i] for i in ids]

fetch_users([1, 2])
fetch_users([2, 3])        # 2 is a cache hit (correct), but cache keeps growing
```

`cache` is created at definition time and lives across calls. At first it looks like you "saved a repeated lookup"; later you realise **the cache never expires and only grows**. In real code this is a memory leak. **A cache should be passed in by the caller, or live at module level — never hide in a default argument.**

## Summary

- Positional arguments line up by position; when types match, swapping them is silent but wrong
- Default arguments: omit them and the default is used
- Keyword arguments: `name=value`, order does not matter, very readable
- Ordering rule: positional → default in the definition; positional → keyword at the call
- **Never use a mutable object (list, dict, set) as a default**; use `None` and create it inside the body
- A default value is created once at definition time and shared — that is the trap

  def greet(name, greeting="Hello"):

- assert "Hello, Alice!" in __out
