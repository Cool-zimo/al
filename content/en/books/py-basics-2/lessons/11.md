# Why Dictionaries Exist: Look Up by Name, Not by Position

> Everything we have stored so far — lists and tuples — is fetched by **position**: `scores[0]` is the first item, `scores[1]` is the second.
>
> But in real life you usually know the **name** and want the value that goes with it: Alice's score, the price of an apple, the area code for London. Fetching by position forces you to hunt through parallel lists.
>
> This lesson introduces the **dictionary (dict)**: you look up by name, it is fast, and the code reads naturally.

## 1. A real problem

Suppose you want to store a few people's scores in a list:

```python
scores = [92, 78, 100, 65]
```

Question: what is Alice's score? You **cannot tell**. A list remembers "which position", not "who is who". To find Alice you must keep a parallel list of names:

```python
names = ["Alice", "Bob", "Carol", "Diana"]
scores = [92, 78, 100, 65]

# find Alice's score
i = names.index("Alice")
print(scores[i])        # 92
```

It works, but the two lists must stay **perfectly aligned** — miss by one and everything is wrong.

**A dictionary binds the name and the score together:**

```python
scores = {
    "Alice": 92,
    "Bob": 78,
    "Carol": 100,
    "Diana": 65,
}

print(scores["Alice"])        # 92
```

`"Alice"` is the **key**, and `92` is its **value**. Keys and values come in pairs, joined by a colon `:`. The whole dictionary sits inside curly braces `{ }`.

To find Alice's score you write `scores["Alice"]` — **you never need to know she is "number three"**.

## 2. Dictionary literals and `dict()`

The most common way to build a dictionary is a **literal** — writing the key-value pairs directly:

```python
phone = {
    "Alice": "02079460001",
    "Bob": "02079460002",
}
print(phone["Alice"])        # 02079460001
```

You can also start empty and add entries afterwards (covered in detail in Lesson 12):

```python
phone = {}
phone["Alice"] = "02079460001"
```

The `dict()` constructor builds a dictionary from `key=value` arguments. The keys must be valid identifiers, so this only works for plain names:

```python
d = dict(a=1, b=2)
print(d)        # {'a': 1, 'b': 2}
```

⚠️ **Crash: a `dict()` call cannot use a string as a key.**

```python
d = dict(Alice=92)        # WRONG  SyntaxError: keyword can't be an expression
```

`dict(name=value)` demands that the key part looks like a variable name; `"Alice"` does not. For a string key you must write the literal form `{"Alice": 92}`.

## 3. Real-world mappings

A dictionary is a **lookup table**: give it a key, get the value back. These relationships are everywhere:

| Situation | Key | Value |
|---|---|---|
| Phone book | Name | Phone number |
| Price list | Product name | Unit price |
| Area codes | City name | Code |
| Configuration | Setting name | Setting value |
| Word count | Word | How often it appears |

```python
prices = {
    "apple": 0.55,
    "milk": 0.80,
    "bread": 0.35,
}
print(prices["apple"])        # 0.55
```

`prices["apple"]` reads exactly like English: "the price of an apple".

## 4. Keys and values can be different types

A dictionary's value can be anything — a number, a string, a list, even another dictionary:

```python
student = {
    "name": "Alice",
    "age": 20,
    "scores": [92, 78, 100],
    "address": {
        "city": "London",
        "district": "Camden",
    },
}

print(student["scores"][0])            # 92
print(student["address"]["city"])      # London
```

**Keys** are stricter: they must be **immutable** (strings, numbers, and tuples are fine; lists are not). Lesson 14 explains the reason.

Using **strings as keys** is the common case:

```python
config = {
    "host": "localhost",
    "port": 3306,
    "debug": True,
}
```

⚠️ **Crash: using a list as a key.**

```python
d = {["London", "Paris"]: "city pair"}      # WRONG  TypeError: unhashable type: 'list'
```

A list cannot be a key. When you need "several things" as a key, use a tuple:

```python
d = {("London", "Paris"): "city pair"}
print(d[("London", "Paris")])      # city pair
```

## 5. Dictionaries vs lists: which one?

A simple rule of thumb:

| What you want to do | Use | Example |
|---|---|---|
| "Look up information by name" | dictionary | Alice's score, a price |
| "Hold a sequence of items" | list | every score, a shopping basket |
| "Both key and value, and it can change" | dictionary | a user record |
| "Just values, fetched by position" | list | a run of numbers |

```python
# list: just "some scores", order matters
scores = [92, 78, 100]

# dictionary: each score belongs to a person
scores_by_name = {"Alice": 92, "Bob": 78, "Carol": 100}
```

**In one sentence:** if your first thought when fetching is "the one called such-and-such", use a dictionary; if it is "the third one", use a list.

⚠️ **Crash: using a list when a dictionary is called for, then aligning by index.**

```python
names = ["Alice", "Bob", "Carol"]
scores = [92, 78, 100]
# trying to change Alice's score
i = names.index("Alice")
scores[i] = 95           # works, but brittle
```

The moment an insert or a delete knocks the two lists out of sync, the data is wrong. That "two parallel lists" pattern is exactly where a dictionary should appear — names and scores stay bound together and you never worry about alignment.

## Summary

- A dictionary stores `{key: value}` and is fetched **by key**, not by position.
- A dictionary models a mapping: name → phone, product → price, city → area code.
- Values can be any type, including lists and other dictionaries; keys must be immutable (strings are the usual choice).
- The signal that you want a dictionary: you keep thinking "the one called …".
- A list cannot be a key; a tuple can.
