# Choosing Among List, Tuple, Dict and Set

> You have now seen the four built-in containers. The most practical question is: **given a requirement, which one should you pick?**
>
> This lesson gives you a decision table, compares the four containers side by side, and works through some real scenarios.

## 1. The four containers at a glance

| Type | Literal | Ordered? | Mutable? | Duplicates? | How to access | Typical use |
|---|---|---|---|---|---|---|
| `list` | `[1, 2, 3]` | ordered | yes | yes | index `[i]` | a collection of similar items |
| `tuple` | `(1, 2, 3)` | ordered | no | yes | index `[i]` | fixed fields, usable as a key |
| `dict` | `{"a": 1}` | insertion order kept | yes | keys unique | key `d[k]` | key-to-value mapping |
| `set` | `{1, 2, 3}` | unordered | add/remove | no | membership only | dedup, existence checks |

Reading across the rows:

- **Ordered vs unordered**: lists, tuples and dicts all have a positional feel; a set is completely unordered and cannot be indexed
- **Mutable vs immutable**: lists, dicts and sets can all be changed; a tuple cannot
- **Duplicates allowed?**: lists, tuples and dict keys allow repeats; set elements are naturally unique
- **How you fetch values**: lists and tuples use position, dicts use keys, sets use "is it in there?"

⚠️ **Crash: assuming dictionaries and sets are both "unordered".**

Since Python 3.7, a dict **preserves insertion order**. Only a set is unordered. Do not conflate the two.

## 2. The decision table: four questions in order

Ask yourself these four questions, one after another.

### Question 1: am I storing key-value pairs?

If yes — **use a dict**. Think "name → phone", "product → price", "config name → config value".

```python
phone = {"Alice": "07700900001", "Bob": "07700900002"}
```

If not, move on.

### Question 2: do I need frequent "is it in there?" checks or deduplication?

If yes — **use a set**. Blocklists, unique visitors, finding mutual friends.

```python
vip = {"Alice", "Bob", "Carol"}
```

Otherwise keep going.

### Question 3: is this data **not supposed to change**? (fixed fields, needs to be a key)

If yes — **use a tuple**. Coordinates `(x, y)`, one database record, multiple return values from a function.

```python
point = (51.5074, -0.1278)    # a location: latitude, longitude
```

Otherwise use a list.

### Question 4: it is just a bunch of items, with adding, removing and sorting

— **use a list**. This is the default, and it is the most flexible.

```python
scores = [87, 92, 78, 65, 100]
```

⚠️ **Crash: reaching for a list by default without considering the alternatives.**

A list is the most flexible container, but also the one with the least distinctive character. When you notice yourself doing `in` checks over and over on a list, or maintaining "two parallel lists", it is time to think about a dict or a set.

## 3. Real-world scenarios

### Scenario 1: a shopping cart

Requirement: add items, remove items, calculate the total, and allow the same product several times (three apples).

→ **A list**. Duplicates are allowed, you need to add and remove, and order matters.

```python
cart = ["apple", "milk", "apple", "bread"]
cart.append("apple")        # one more apple
```

If the requirement changes to "count how many of each item", switch to a **dict**:

```python
cart_count = {"apple": 3, "milk": 1, "bread": 1}
```

### Scenario 2: an address book

Requirement: look up a phone number by name, with no duplicate names.

→ **A dict**. Fetch by key (the name), naturally one-to-one.

```python
contacts = {"Alice": "07700900001", "Bob": "07700900002"}
print(contacts["Alice"])
```

### Scenario 3: a class register

Requirement: just a list of names, in order, with the occasional new arrival.

→ **A list**. Order matters, and duplicates are allowed (handling identical names is a separate concern).

```python
roster = ["Alice", "Bob", "Carol"]
roster.append("David")
```

### Scenario 4: currently logged-in users

Requirement: check whether a user is logged in, with no duplicates.

→ **A set**. Dedupes automatically and membership checks are instant.

```python
logged_in = {"Alice", "Bob"}
if "Alice" in logged_in:
    print("already logged in")
```

### Scenario 5: one order record

Requirement: order ID, customer and amount — three fields bound together, not to be changed.

→ **A tuple** (or, more commonly, a named tuple / class — those come later).

```python
order = ("ORD001", "Alice", 128.50)
```

### Scenario 6: word-frequency counting

Requirement: count how many times each word appears in a chunk of text.

→ **A dict**. The `{word: count}` counting pattern.

```python
text = ["I", "love", "Python", "I", "love", "coding"]
count = {}
for w in text:
    count[w] = count.get(w, 0) + 1
print(count)      # {'I': 2, 'love': 2, 'Python': 1, 'coding': 1}
```

### Scenario 7: find the words two texts have in common

Requirement: take the intersection.

→ **A set**. `set(words1) & set(words2)`.

```python
words1 = {"Python", "Java", "Go"}
words2 = {"Go", "Rust", "Python"}
print(words1 & words2)        # {'Python', 'Go'}
```

⚠️ **Crash: reaching for a set intersection but writing a nested loop over lists.**

```python
# it works, but it is verbose and slow
common = [w for w in words1 if w in words2]
```

When the lists are large, `in` on a list is slow. Converting to sets gives you one clean, fast line.

## 4. Combining them: nested containers

Real data is often nested. The four containers can be combined freely:

```python
# a dict whose values are lists: each student has several scores
class_scores = {
    "Alice": [92, 78, 88],
    "Bob": [85, 90, 77],
}

# a list holding tuples: records with a fixed structure
students = [("Alice", 92), ("Bob", 78)]

# a dict whose values are sets: the skills each person has
skills = {
    "Alice": {"Python", "SQL"},
    "Bob": {"Java", "Python", "Go"},
}
```

The rule for choosing does not change when you nest — you just choose **layer by layer, from the outside in**:

1. The outer layer is "look up by name" → dict
2. The inner layer is "an ordered, growable collection of scores" → list
3. Another inner layer is "skill tags, deduped and checkable" → set

⚠️ **Crash: after nesting, forgetting what operations each layer supports.**

```python
data = {"tags": {"python", "java"}}   # the value is a set
data["tags"].append("go")             # WRONG  AttributeError: 'set' object has no attribute 'append'
```

A set has no `append`; you must use `add`. The deeper the nesting, the more important it is to know **what type each layer really is**.

## Summary

- Key-value mapping → dict; existence checks / dedup → set; fixed fields / needs to be a key → tuple; otherwise → list
- The list is the default, but do not make everything a list
- In real projects the four containers are often **combined**
- When nesting, know the type of every layer and do not treat a set like a list

- 'A list, because it is the most flexible'
- 'A tuple, because it is immutable'
- 'A dict, because key lookup is fast'
- 'A set: it dedupes and `in` is fast'
answer: 3
explain: Two signals point to a set: no duplicates allowed (set elements are unique) and frequent `in` checks (the hash table makes those instant). A dict is also fast for lookup, but it stores key-value pairs — there is no "value" to store here, so a dict would be wasteful.
