# Scope: What Happens Inside Stays Inside

> In earlier lessons we touched on "local variables" in passing. This lesson goes all the way: **where a name is visible, where it is not, and whether a function can change a name from outside.**
>
> The two key ideas: Python has three lookup rules (**LEGB**), and `global` is a switch you reach for only when nothing else works.

## 1. Local variables: the function's private things

A variable defined inside a function exists only inside that function — the outside cannot see it:

```python
def calc():
    result = 10 + 20        # result is local
    return result

print(calc())               # 30
print(result)               # WRONG  NameError: name 'result' is not defined
```

`result` is **local to `calc`**, and it "disappears" when the function ends. The outside world never knew it existed.

⚠️ **Crash: expecting a name defined inside a function to survive outside.**

```python
def greet():
    message = "Hello"

greet()
print(message)              # WRONG  NameError: name 'message' is not defined
```

This is one of the most common beginner assumptions. **A function's job is to isolate**: its insides are hidden; by default, its outsides are visible (see below).

## 2. You can read an outside name (but not casually rebind it)

A function **can read** a variable from outside:

```python
tax_rate = 0.13

def calc_price(price):
    return price * (1 + tax_rate)        # reads tax_rate from outside

print(calc_price(100))        # 113.0
```

But it **cannot casually change** it:

```python
counter = 0

def increment():
    counter += 1            # WRONG  UnboundLocalError: local variable 'counter' referenced before assignment

increment()
```

Why? Because Python sees `counter += 1` *assigning* to `counter` and decides `counter` is a **local variable**. That line first *reads* `counter` and then adds 1, but the local `counter` has not been assigned yet — hence `UnboundLocalError`.

⚠️ **Crash: reading is fine, assigning blows up.**

```python
counter = 0

def show():
    print(counter)          # fine, prints 0

def add():
    counter += 1            # error
```

The very same name `counter`: read it and it is treated as outside; assign to it and it becomes local. **Python decides based on "is there an assignment to it inside the function?", not on what you intended.**

## 3. `global`: explicitly saying "I mean the outside one"

To change a global variable from inside a function, declare it with `global`:

```python
counter = 0

def increment():
    global counter          # declare: I am talking about the outside counter
    counter += 1

increment()
increment()
print(counter)              # 2
```

`global counter` means: "do not make a new local variable; I want the global one."

⚠️ **Crash: forgetting `global`, and changing nothing at all.**

```python
counter = 0

def increment():
    counter = 1             # this creates a NEW local variable, not the global

increment()
print(counter)              # 0 -- the global one did not move
```

`counter = 1` inside the function only creates a local variable, and the global `counter` stays at 0. **This bug is nasty: no error, the logic "looks right", and the outside world simply does not react.**

## 4. Avoid `global` whenever you can

`global` does solve the problem, but **it is strongly discouraged**. Why:

1. **Hard to read**: one function changes `counter`, but someone reading the file far away has no idea
2. **Hard to debug**: any function may touch it, so a bug means inspecting every function
3. **Hard to test**: the function's result depends on outside state, so it cannot be tested in isolation

```python
# not recommended: relying on a global to carry state
total = 0

def add_price(p):
    global total
    total += p

add_price(100)
add_price(200)
print(total)        # 300
```

**Recommended: pass the state in, return the new state out.**

```python
def add_price(total, p):
    return total + p

total = 0
total = add_price(total, 100)
total = add_price(total, 200)
print(total)        # 300
```

Same logic, but this version: `add_price`'s input and output are **completely explicit**, anyone can read it, and it can be tested on its own.

⚠️ **Crash: two functions in a team both changing the same global.**

```python
cart = []

def add_item(item):
    global cart
    cart.append(item)

def clear_cart():
    global cart
    cart = []          # wiped!

add_item("apple")
clear_cart()
add_item("banana")
print(cart)            # ['banana'] -- caller expected the apple to still be there
```

A global is **shared state**: one change affects every user. In a large project these bugs are almost impossible to trace. **In 99% of cases, returning the result is cleaner than `global`.**

## 5. LEGB: Python's four lookup rules

The order in which Python looks up a name is **LEGB**:

- **L**ocal: look in the current function first
- **E**nclosing: then in the function that wraps this one (nested functions)
- **G**lobal: then at global scope
- **B**uilt-in: finally the built-ins (`len`, `print`, `max`, ...)

```python
x = "global"

def outer():
    x = "outer"
    def inner():
        # x = "inner"          # uncomment this and it prints "inner"
        print(x)              # prints "outer"
    inner()

outer()
```

`inner` has no `x`, so it walks up to `outer`'s `x`; above that is global. **Closest wins, and it stops at the first match.**

⚠️ **Crash: accidentally shadowing a built-in name.**

```python
id = 123        # shadows the built-in function id()

obj = {"a": 1}
print(id(obj))  # WRONG  TypeError: 'int' object is not callable
```

`id` is a built-in function (it returns an object's identity). Once you use it as a variable name, the built-in `id` is "shadowed", and any later call to `id()` fails. **Never use `id`, `list`, `str`, `sum` etc. as variable names.**

## 6. Worked example: a shopping cart

**The global version (not recommended):**

```python
cart = []

def add(item):
    global cart
    cart.append(item)

def total(prices):
    global cart
    return sum(prices[i] for i in cart)

add("apple")
add("banana")
```

**The return-value version (recommended):**

```python
def add_item(cart, item):
    cart = cart + [item]          # returns a new list
    return cart

def calc_total(cart, prices):
    return sum(prices[item] for item in cart)

cart = []
cart = add_item(cart, "apple")
cart = add_item(cart, "banana")
```

In the second version, every function's **input and output are crystal clear** — no smoke and mirrors.

## Summary

- A variable defined inside a function is **local**, invisible from outside
- A function can **read** an outside name, but cannot casually **change** it (assignment makes it local)
- To change a global, write `global`; but **avoid it when you can**
- The alternative to `global`: pass state in as an argument, return the result
- A global is shared state, a frequent source of team bugs
- Name lookup order: **LEGB** (Local → Enclosing → Global → Built-in); do not reuse built-in names

```quiz
q: Write a function `increment(n)` that adds 1 to the number it receives and returns it (do not use `global`, and do not assign to the global variable `n` inside the function). Define `n = 5` outside, then reassign `n` from the call and print it.
starter: |
  n = 5

  def increment(n):
      # return n + 1

  n = increment(n)
  print(n)
tests:
- assert "6" in __out
hint: The function receives n as a parameter and returns n + 1. Leave the global n alone and let return hand the result back, then reassign.
explain: The answer is def increment(n): return n + 1, then n = increment(n). This demonstrates "changing outside state without global": return the result and reassign the global — far cleaner than using global.
```

```quiz
  x = 10
  def f():
      x = 20
  f()
  print(x)

- '20'
- '10'
- 'error'
- 'None'
answer: 1
explain: The x = 20 inside f creates a local x; the global x is never touched. print(x) uses the global 10. This is the classic "assignment inside a function does not alter the global" demonstration.
```
