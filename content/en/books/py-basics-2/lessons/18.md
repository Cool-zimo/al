# Why `in` Is So Fast on a Set

> The last lesson said a set lookup is lightning fast. This lesson will not quote any formulas or talk about big-O; instead it gives you an intuition for **why checking a set is so much faster than checking a list**.
>
> Once this clicks, you will know exactly when to choose a set and when to stick with a list.

## 1. A small, concrete experiment

Let us run a little thought experiment and just count **how many comparisons have to happen**.

Imagine you are looking for someone in a list. The list holds ten thousand names, and the person you want — "Alice" — happens to be last.

### With a list: check them one by one

```python
names = ["user0001", "user0002", ..., "user9999"]     # ten thousand names
# looking for "user9999"
```

A list is a single line: to find something you must **walk from the front to the back**. The first one is not a match, neither is the second... you keep going until the 9,999th entry before you finally find it.

If you are unlucky and "Alice" is at the very end or does not exist at all, you have to **compare against all ten thousand names** before giving up.

### With a set: calculate once and jump straight there

```python
names = {"user0001", "user0002", ..., "user9999"}
# looking for "user9999"
```

A set does not check things one by one. Instead it **first turns each name into a number**, then uses that number to jump straight to the right slot and look there — a hit means it is found.

⚠️ **The key difference: a list compares; a set calculates.**

- Looking in a list: **compare one by one**, up to ten thousand comparisons
- Looking in a set: **calculate a number once** and jump straight to the slot — one check

That is why, whether a set holds a thousand or a million elements, **membership tests take essentially the same amount of time**, while a list gets slower the more items it holds.

## 2. The intuition behind a hash table

This "calculate a number, then jump" mechanism is called a **hash table**. Both dictionaries and sets work this way.

### How the "number" is calculated

Python calls each element's **hash function** to get a number — like giving every name a "student ID":

```python
print(hash("Alice"))         # some integer, for example 123456789
print(hash(42))              # 42
print(hash("Alice"))         # the same string always produces the same number
```

The same object always hashes to the same value, no matter when you ask. That is exactly why **mutable things (like lists) cannot go inside a set** — if the element changes, its hash changes too, and you could never find it again.

### How Python "jumps" to the right place

Once it has the hash, Python uses it to **work out which slot the element belongs in**, then goes straight to that slot to take a look.

A good analogy:

> Looking for a book in a library. A list is "lay all the books out on the floor and flip through them one by one"; a set is "use the catalogue number to walk straight to the right shelf and pull one book".

⚠️ **Crash: assuming the set's slots are "sorted".**

They are not. A set has no order; it has merely **grouped its elements into slots**. This is completely different from a binary search, which needs sorted data to be fast. A set is not sorted, yet it is still fast.

## 3. Collisions: when two elements land in the same slot

In the real world, two elements can end up with the same number (a bit like two students being assigned the same seat). Python handles this by **hanging a small chain off that slot**, so when a collision occurs it compares inside that little chain.

So strictly speaking, a set's `in` is not **always** a single check — in an unlucky case it has to compare a few extra times. But that "little chain" is normally very short, and most of the time it is a one-shot hit.

That is why we keep saying **"essentially the same speed"** rather than "always one check".

⚠️ **Crash: assuming a set is always faster, so you should use it for everything.**

Not so. A hash table carries overhead: calculating hashes and maintaining slots both cost something. When the data is **very small** (say a few dozen elements), the cost of comparing a list item by item is negligible and a set can actually be marginally slower.

**A practical rule of thumb:**

| Size of the data | Recommendation |
|---|---|
| Up to a few dozen | Either list or set is fine; a list is simpler |
| Hundreds, thousands, with frequent `in` checks | **A set** — the advantage is clear |
| Order matters, or duplicates are allowed | A list |

## 4. Dictionaries and sets share one mechanism

In the previous chapter we said dictionary keys must be hashable. That is exactly the same reason — **dictionaries and sets are both built on hash tables**.

```python
d = {}
d["Alice"] = 92       # hash "Alice" -> jump to the right slot -> store 92

s = set()
s.add("Alice")        # hash "Alice" -> jump to the right slot -> store the element itself
```

One stores "key → value"; the other stores just "is the element in here?". **The underlying principle is identical.**

⚠️ **Crash: assuming Python will "magically speed up" your list.**

If you build a list and then search it repeatedly with `in`, Python **will not** quietly convert it into a set for you. You have to make that choice yourself:

```python
data = ["a", "b", "c", ...]        # a list
"target" in data                   # slow, checks one by one

# fix: convert once before searching
lookup = set(data)
"target" in lookup                 # fast
```

**Convert once, and you benefit forever** — as long as `data` does not change, you pay the conversion cost once and then enjoy thousands of fast lookups.

## 5. When to use a set

Here is a decision checklist:

- Frequent "is it in there?" checks? → use a set ✅
- Need to dedupe? → use a set ✅
- Need intersection / union / difference? → use a set ✅
- Need to preserve order? → use a list ❌
- Need to allow duplicates? → use a list ❌
- Need key-to-value mapping? → use a dict ❌

In one sentence: **a set is strong at "testing existence" and "set operations", not at "remembering the order things arrived in".**

⚠️ **Crash: using a set for "speed" and losing your order in the process.**

```python
# we wanted to preserve the order of the user's actions
steps = ["log in", "browse", "add to cart", "pay"]
# someone "optimised" it into a set
steps = {"log in", "browse", "add to cart", "pay"}
print(steps)        # the order is gone!
```

When the order carries business meaning, you should accept the list's lookup cost rather than reaching for a set. If you genuinely need both order and fast lookup, use the "list for order + set for lookups" combo (the `dedup` example in Lesson 16 does exactly this).

## Summary

- A list finds things by **checking one by one** and gets slower as it grows; a set finds things by **hashing and jumping straight to a slot**
- This mechanism is called a **hash table**, and both dictionaries and sets rely on it
- A set is not "sorted", it is "grouped into slots"; on a collision the chain inside that slot is compared
- For large data with frequent `in` checks, a set wins decisively; for tiny data a list is simpler
- Dictionaries and sets share the same mechanism, so both keys and set elements must be hashable
