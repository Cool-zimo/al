# Dictionary Pitfalls: Keys Must Be Hashable, and Do Not Rely on Order

> Dictionaries are pleasant to use, but there are three traps almost everyone hits. This lesson walks through all three so you can avoid losing sleep over them.

## Pitfall 1: keys must be "hashable"

The short version: **a dictionary key must be an immutable object.** Strings, numbers, and tuples are fine as keys; lists and dictionaries are not.

```python
d = {}
d["London"] = "capital"          # string key, fine
d[42] = "answer"                # number key, fine
d[(51, 0)] = "coordinates"      # tuple key, fine
```

```python
d[["London", "Paris"]] = "city pair"      # WRONG  TypeError: unhashable type: 'list'
```

The keyword in the error is **unhashable**. It really means: "this thing can change, so I cannot use it as an index."

### Why a "changeable" object cannot be a key

A dictionary fetches values quickly because of a **hash table**: Python computes a "hash value" for each key to decide where that entry lives. If a key could change, its hash would change — computed once when stored and once when looked up, the two would differ, and the value could never be found.

So Python simply **refuses mutable objects as keys** — the problem is prevented at the language level.

⚠️ **Crash: assuming "a tuple is always usable as a key".**

A tuple is immutable, but if it contains a mutable object it still cannot be a key:

```python
d = {([1, 2], 3): "value"}        # WRONG  TypeError: unhashable type: 'list'
```

The first element of the tuple is a list. The real test is that **the key object and everything inside it must be immutable**.

### A useful rule of thumb

> If an object can be placed into a `set()`, it can be a dictionary key — both follow the same rule.

```python
{ [1, 2] }          # WRONG  lists are not hashable
{ (1, 2) }          # OK   tuples are
```

### Common hashable vs unhashable types

| Hashable (valid keys) | Unhashable (invalid keys) |
|---|---|
| `str` | `list` |
| `int`, `float` | `dict` |
| `tuple` (its elements must also be hashable) | `set` |
| `True` / `False` / `None` | `bytearray` |

⚠️ **Crash: using a dictionary as a key.**

```python
d = {{"a": 1}: "value"}      # WRONG  TypeError: unhashable type: 'dict'
```

A dictionary cannot be a key either — dictionaries are mutable.

## Pitfall 2: a missing key raises `KeyError`

Lesson 12 covered `get`, but ordinary code still uses square brackets constantly:

```python
scores = {"Alice": 92}
print(scores["Bob"])        # WRONG  KeyError: 'Bob'
```

**`KeyError` is one of the most common runtime errors with dictionaries.** When you see it you have exactly three routes:

1. **You are certain it exists:** use square brackets. If it breaks, the data is wrong — let it break.
2. **It may be absent and you have a fallback:** use `get(key, default)`.
3. **Check first, then read:** `if key in dictionary:`

```python
# get is the most carefree
age = info.get("age", 0)
```

⚠️ **Crash: calling `get` but forgetting to handle the "not found" case.**

```python
value = d.get("key")
print(value.upper())         # WRONG  AttributeError: 'NoneType' object has no attribute 'upper'
```

If the key is absent and you gave no default, `get` returns `None`. Treat that `None` as a string and it blows up. So either supply a default, or check for `None` after fetching.

## Pitfall 3: dictionaries are "ordered", but do not rely on the order

Since Python 3.7, dictionaries **preserve insertion order**:

```python
d = {}
d["London"] = 1
d["Paris"] = 2
d["Tokyo"] = 3
print(list(d.keys()))        # ['London', 'Paris', 'Tokyo']
```

That looks "ordered". But note: **this is a guarantee promoted from an implementation detail; logically you should not expect it to mean "sorted".**

What that really means: a dictionary's order is "the order you inserted things in", **not smallest-to-largest and not alphabetical**.

⚠️ **Crash: expecting a dictionary to sort itself automatically.**

```python
d = {"banana": 3, "apple": 1, "cherry": 2}
print(list(d.keys()))        # ['banana', 'apple', 'cherry'] — insertion order, not alphabetical
```

It does **not** sort alphabetically. To sort, you must ask explicitly with `sorted`:

```python
for k in sorted(d):
    print(k, d[k])
```

```
apple 1
banana 3
cherry 2
```

⚠️ **Crash: treating "the same order" as "the dictionaries are equal".**

```python
a = {"x": 1, "y": 2}
b = {"y": 2, "x": 1}
print(a == b)           # True
```

Dictionary equality **only compares key-value pairs**, not order. So although order is preserved, it does not affect whether two dictionaries are considered equal — do not treat order as a core feature of a dictionary.

## Summary

- Dictionary keys must be hashable: strings, numbers, and tuples work; lists, dictionaries, and sets do not.
- For a tuple to be a key, **every element inside it** must also be hashable.
- A missing key raises `KeyError`; avoid it with `get` or an `in` check first.
- Dictionaries preserve insertion order but **do not sort automatically**; sort explicitly with `sorted`.
- Dictionary equality ignores order — it only cares whether the key-value pairs match.
