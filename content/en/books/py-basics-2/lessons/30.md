# Putting It All Together: Refactoring a Mess into Functions

> This is the final lesson of Chapter 6. It uses every technique from the previous five lessons: **take the contacts mini-tool we wrote as "one big lump of code" and reshape it into "a set of functions, each with one job".**
>
> The point is not that the code gets shorter — it is that **every block now has a name and a responsibility.**

## 1. The "lump of code" before refactoring

Suppose it is a minimal contacts book, using a list of dictionaries:

```python
# the lump version
book = []

print("Adding Alice")
book.append({"name": "Alice", "phone": "07123456789"})
print("Adding Bob")
book.append({"name": "Bob", "phone": "07987654321"})

print("Looking up Alice")
found = None
for c in book:
    if c["name"] == "Alice":
        found = c
        break
if found:
    print(found["phone"])
else:
    print("Not found")

print("All contacts")
for c in book:
    print(c["name"], c["phone"])
```

It runs, but **the problems pile up**: the logic is all tangled together, adding a feature means editing the middle of the file, the "look up" routine cannot be reused, and reading it feels like reading a diary.

## 2. Step one: cut out the "actions"

A contacts book really has four operations: **add, find, list, remove**. Wrap each in its own function:

```python
def add_contact(book, name, phone):
    book.append({"name": name, "phone": phone})

def find_contact(book, name):
    for c in book:
        if c["name"] == name:
            return c
    return None

def list_contacts(book):
    for c in book:
        print(c["name"], c["phone"])

def remove_contact(book, name):
    for i, c in enumerate(book):
        if c["name"] == name:
            book.pop(i)
            return True
    return False
```

Each function **does exactly one thing**: `add_contact` only adds, `find_contact` only searches, `list_contacts` only lists, `remove_contact` only removes. That is the **Single Responsibility Principle**.

⚠️ **Crash: one function trying to do four jobs.**

```python
def manage(book, name, phone, action):      # BAD  one function, four jobs
    if action == "add":
        book.append(...)
    elif action == "find":
        ...
    elif action == "list":
        ...
    elif action == "remove":
        ...
```

A "do-everything" function that branches on an `action` string is really four functions crammed into one. **Change one piece and you have to hunt through the big function while praying you did not break the others.** Splitting them up is the answer.

## 3. The main flow after refactoring

The main flow becomes **as readable as a description**:

```python
def main():
    book = []

    add_contact(book, "Alice", "07123456789")
    add_contact(book, "Bob", "07987654321")

    print("Looking up Alice:")
    result = find_contact(book, "Alice")
    if result:
        print(result["phone"])
    else:
        print("Not found")

    print("All contacts:")
    list_contacts(book)

    remove_contact(book, "Alice")
    print("After removal:")
    list_contacts(book)

main()
```

Inside `main()` you see **no implementation details** — only "what gets done". That is the real value of refactoring.

## 4. The complete code

```python
def add_contact(book, name, phone):
    """Add a contact"""
    book.append({"name": name, "phone": phone})

def find_contact(book, name):
    """Find a contact; return the dict if found, None otherwise"""
    for c in book:
        if c["name"] == name:
            return c
    return None

def list_contacts(book):
    """List every contact"""
    for c in book:
        print(f"{c['name']}: {c['phone']}")

def remove_contact(book, name):
    """Remove a contact; return True on success, False if not found"""
    for i, c in enumerate(book):
        if c["name"] == name:
            book.pop(i)
            return True
    return False

def main():
    book = []
    add_contact(book, "Alice", "07123456789")
    add_contact(book, "Bob", "07987654321")

    print("Looking up Alice:")
    result = find_contact(book, "Alice")
    print(result["phone"] if result else "Not found")

    print("\nAll contacts:")
    list_contacts(book)

    print("\nAfter removing Alice:")
    remove_contact(book, "Alice")
    list_contacts(book)

main()
```

Output:

```
Looking up Alice:
07123456789

All contacts:
Alice: 07123456789
Bob: 07987654321

After removing Alice:
Bob: 07987654321
```

⚠️ **Crash: passing state between functions through a global `book`.**

```python
book = []           # global

def add_contact(name, phone):       # BAD  depends on the global book
    book.append({"name": name, "phone": phone})
```

This runs, but `add_contact`'s correctness **depends on some global variable called `book` existing**. It falls apart under testing, and again when you want two address books at once. **Pass `book` in as an argument so the function is independent and reusable.**

## 5. How to carve it up: three rules of thumb

**1. Look for verbs.** "Add a contact", "find a contact", "remove a contact" — the verb in the sentence is often the function. Contacts → add / find / list / remove. A score tracker → add_score / average / top_student / fail_list.

**2. Each function does one thing.** The test: **can you give it one accurate verb as a name?** If you cannot, it is doing too much and should be split.

**3. Pass data in, hand results back with `return`.** Do not use globals as a messenger.

⚠️ **Crash: a vague function name usually means unclear responsibility.**

```python
def process_data(book, name):       # "process" says nothing
    ...

def handle_user(x):                 # "handle" is far too vague
    ...
```

Names like these usually appear when a function is stuffed with too much. **If you can say what it does, it is a good name.**

## 6. The payoff of refactoring: tests

Once refactored, every function can be **tested on its own**:

```python
# testing find_contact
book = [{"name": "Alice", "phone": "07123"}]
assert find_contact(book, "Alice")["phone"] == "07123"
assert find_contact(book, "Bob") is None

# testing remove_contact
book = [{"name": "Alice"}]
assert remove_contact(book, "Alice") is True
assert remove_contact(book, "Bob") is False
```

**The "lump of code" version cannot do this** — you cannot test just the "find" part when it is glued to the rest of the program. With functions, input and output are clear, so writing tests is natural.

⚠️ **Crash: changing behaviour during a refactor without noticing.**

```python
# before: not found returned "Not found"
# after:  not found returns None
```

The code still runs, but the behaviour changed. That is exactly why tests matter — **refactoring only changes structure, never behaviour**, and tests hold that line.

## 7. Using functions "as objects": a menu dispatcher

The "function dictionary" from the previous chapter slots in perfectly here:

```python
MENU = {
    "1": ("Add",    add_contact),
    "2": ("Find",   find_contact),
    "3": ("List",   list_contacts),
    "4": ("Remove", remove_contact),
}

def show_menu():
    for key, (label, _) in MENU.items():
        print(f"{key}. {label}")

show_menu()
```

Bind each "action name" to its function, and **adding a feature is one new line in `MENU`** — the main loop does not move. This is the "open/closed principle": open for extension, closed for modification.

## Summary

- The goal of refactoring is not "shorter code", but **every block has one job and a name that says so**
- How to carve it up: find the verbs, one job per function, pass data in and return results
- A "do-four-things" function is an anti-pattern
- Do not pass state through globals; keep functions independent and testable
- Refactoring changes structure, never behaviour — tests guard that line
- A function dictionary as a menu dispatcher is the most practical use of functions as objects
