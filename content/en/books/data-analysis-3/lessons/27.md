# Cleaning and Features: From Dirty Data to Usable Data

> The previous lesson set the cleaning checklist; this one carries it out. Turn strings into numbers, fill or drop the missing values, hunt down the outliers, then derive a few new fields on the side. Cleaning is not tidying up - it is preparing food the model can actually eat.

## Step 1: type conversion, the first gate for dirty data

Numbers that have been read in are often still strings. To pandas, `1000` and `'1000'` are completely different things, so you cannot add, subtract, multiply or divide until you convert them.

```python
import matplotlib
matplotlib.use('Agg')
import pandas as pd
import numpy as np

df = pd.DataFrame({
    'store': ['London', 'New York', 'London', 'New York', 'Manchester'],
    'date': ['2025-01-01', '2025-01-02', '2025-01-03', '2025-01-04', '2025-01-05'],
    'revenue': ['1000', '1,200', '980', '1,500', '3200 GBP'],
    'footfall': [120, 130, 'no record', 150, 90],
    'is_member': ['yes', 'no', 'yes', 'yes', 'no'],
    'note': ['normal', None, 'returned', 'normal', 'normal'],
})

print(df.dtypes)
# revenue   object
# footfall  object   <- "no record" pushed the integer column to object
```

The workhorse for conversion is `pd.to_numeric`:

```python
df['revenue_gbp'] = pd.to_numeric(
    df['revenue'].str.replace('[ GBP,]', '', regex=True),
    errors='coerce'
)
print(df['revenue_gbp'])
# 0    1000.0
# 1    1200.0
# 2     980.0
# 3    1500.0
# 4    3200.0
```

`errors='coerce'` turns values it cannot parse into `NaN`, so the program keeps running instead of crashing on the spot. The regex in `str.replace` strips out `,` and ` GBP`, which is the standard move for "units mixed in".

**Wreck of the day 1: forgetting `errors='coerce'` makes the whole column fail.**

```python
# WRONG: converting a column containing "1,200" and "3200 GBP" directly
# raises an error on the first non-numeric value
pd.to_numeric(df['revenue'])
# ValueError: Unable to parse string "1,200" at position 1
```

The error is explicit: it cannot parse `"1,200"` at position 1. **The default `errors='raise'` stops everything the moment it hits one bad value.** Real data almost always contains dirty values, so in daily work `errors='coerce'` should be your default mindset. `errors='ignore'`, on the other hand, returns the original column unchanged (without even changing the type) - it is the option that "looks like nothing went wrong while actually doing nothing".

| Value | Behaviour on dirty values | When to use it |
|---|---|---|
| `raise` | throw an exception and stop | you are certain the data must be clean |
| `coerce` | become NaN and continue | everyday cleaning, the most common |
| `ignore` | keep the original value | you only want to try a conversion and do not want NaN |

## Step 2: missing values - fill or drop

Missing is not dirty; it is "incomplete information". There are only two approaches: drop the row, or fill it with something. Which one depends on whether the missingness is random and how large the share is.

```python
print('missing situation:')
print(df.isna().sum())
# revenue     0
# footfall    0   <- note: "no record" is a string, not counted as missing
# note        1

# First handle "no record" in footfall - it is currently a legitimate string
df['footfall'] = pd.to_numeric(df['footfall'], errors='coerce')
print(df['footfall'].isna().sum())   # 1
```

Common ways to fill numeric columns:

```python
# Mean fill (for revenue) - suitable for an approximately normal distribution
df['revenue_mean_fill'] = df['revenue_gbp'].fillna(df['revenue_gbp'].mean())

# Median fill - more stable when there are extremes
df['revenue_median_fill'] = df['revenue_gbp'].fillna(df['revenue_gbp'].median())

# Categorical columns take the mode or "unknown"
df['note'] = df['note'].fillna('normal')

# Or just drop the rows with missing values
df_dropped = df.dropna(subset=['revenue_gbp'])
```

The choice between mean and median matters: **when a column has a large outlier (say a day with 1 million in sales), the mean is pulled up, so a mean fill inflates an ordinary day into a high number**. In that case the median is more trustworthy. Dropping rows cuts both ways - when missingness is concentrated in one store, dropping removes that store from the sample entirely and biases the conclusion towards the others.

**Wreck of the day 2: NaN cannot go straight to int.**

```python
# WRONG: converting an integer column containing NaN always fails
df['footfall_int'] = df['footfall'].astype(int)
# ValueError: cannot convert float NaN to integer
```

Pandas integer types cannot represent missingness, so NaN (which is fundamentally a float) and int are incompatible. **The thinking is fill first, then convert**: `df['footfall'].fillna(0).astype(int)`. Or just keep it as float - in many businesses `footfall=0` and `footfall=unknown` are two different things, and forcing unknowns to 0 is another kind of distortion. Pandas `Int64` (capital I) is a nullable integer type that holds both integers and missing values, and is the recommended style in newer versions: `df['footfall'].astype('Int64')`.

## Step 3: outliers - classify before you touch them

An outlier is not necessarily wrong. A London store selling 100,000 on Singles' Day is extreme but real. The cleaning task is to **identify it**, not to delete it mindlessly.

```python
sales = pd.Series([980, 1000, 1200, 1300, 1500, 3200, 8800, 1050, 1100, 1250])
q1, q3 = sales.quantile(0.25), sales.quantile(0.75)
iqr = q3 - q1
lower, upper = q1 - 1.5 * iqr, q3 + 1.5 * iqr
print(f'Q1={q1}, Q3={q3}, IQR={iqr}')
print(f'bounds: [{lower}, {upper}]')
# Q1=1050.0, Q3=1350.0, IQR=300.0
# bounds: [600.0, 1800.0]

mask = (sales < lower) | (sales > upper)
print('outliers:', sales[mask].tolist())   # [3200, 8800]
```

This is the **IQR (interquartile range) method**: anything below Q1 - 1.5*IQR or above Q3 + 1.5*IQR counts as an outlier. It does not depend on the mean or variance, so it is naturally friendly to skewed distributions - which is why it is used more often than "mean +/- 3 standard deviations".

**Wreck of the day 3: getting the IQR bounds wrong.**

```python
# WRONG: writing the subtraction in reverse and taking abs
lower_wrong = abs(q1 - 1.5 * iqr)      # many people intuitively reach for abs
print(lower_wrong)                      # 350.0  <- completely wrong
```

`abs(q1 - 1.5*iqr)` gives 350 instead of -300, and the question of a natural lower bound is lost. **With the direction wrong, every later judgement flips**: low values that should have been caught are let through, and ordinary values can be branded as outliers. The correct form is `q1 - 1.5*iqr` and `q3 + 1.5*iqr` - no `abs`, no reversed subtraction. If your data really is all positive and you want a non-negative lower bound, that is a business-level clip (`max(0, lower)`), not part of the algorithm.

## Step 4: derived fields - squeeze the information out

Once type, missingness and outliers are handled, the next move is to make fields. A good derived field brings hidden information up to the model.

```python
df['date_dt'] = pd.to_datetime(df['date'], errors='coerce')
df['month'] = df['date_dt'].dt.month
df['weekday'] = df['date_dt'].dt.dayofweek          # 0 = Monday
df['is_weekend'] = df['weekday'].isin([5, 6]).astype(int)
df['avg_spend'] = (df['revenue_gbp'] / df['footfall']).round(2)

# Store-level aggregated feature
store_avg = df.groupby('store')['revenue_gbp'].transform('mean')
df['vs_store_avg'] = (df['revenue_gbp'] - store_avg).round(2)

print(df[['store', 'month', 'is_weekend', 'avg_spend', 'vs_store_avg']])
```

The `dt` accessor splits out month, day, weekday and quarter. `transform('mean')` combined with groupby broadcasts "the average revenue of that store" back to the original rows, and subtracting gives "above or below the store average" - a high-frequency relative metric in retail analysis.

Derived fields have three layers of value: they **reduce the model's comprehension cost** (weekday beats a raw date string), **create interpretable features** (average spend directly reflects efficiency), and **enable group comparison** (vs store average shows which store is underperforming).

But do not overdo it. Two highly correlated fields (`revenue` and `revenue_gbp`) sitting in the same table make linear-regression coefficients a mess to interpret; leaking the target into a feature (for example using "total revenue" to predict "daily revenue") is a more subtle error.

## The cleaning pipeline: one step at a time, no skipping

```python
def clean_store(df):
    out = df.copy()
    # 1. type conversion
    out['revenue_gbp'] = pd.to_numeric(
        out['revenue'].str.replace('[ GBP,]', '', regex=True), errors='coerce')
    out['footfall'] = pd.to_numeric(out['footfall'], errors='coerce')
    # 2. missing: median for numbers, "normal" for categories
    out['footfall'] = out['footfall'].fillna(out['footfall'].median())
    out['note'] = out['note'].fillna('normal')
    # 3. outliers: clip to the IQR bounds rather than deleting
    q1, q3 = out['revenue_gbp'].quantile([.25, .75])
    lo, hi = q1 - 1.5*(q3-q1), q3 + 1.5*(q3-q1)
    out['revenue_gbp'] = out['revenue_gbp'].clip(lo, hi)
    # 4. derived fields
    out['date_dt'] = pd.to_datetime(out['date'], errors='coerce')
    out['month'] = out['date_dt'].dt.month
    out['avg_spend'] = (out['revenue_gbp'] / out['footfall']).round(2)
    return out

print(clean_store(df))
```

This pipeline demonstrates the ordering principle: **convert types, then fill missingness, then handle outliers, then derive.** Reverse the order and you get trouble - computing a median on a string column full of commas is meaningless; computing the IQR before missingness is handled means the median is already polluted by NaN; deriving average spend while footfall is still a string raises an error on the spot. Each step depends on the output of the previous one, which is why skipping is not allowed.

## Summary

- `pd.to_numeric(errors='coerce')` is the everyday default; dirty values become NaN instead of crashing
- Strip symbols with `str.replace` before converting when units are mixed in
- Missing values: mean works for an approximately normal distribution, median resists outliers; dropping rows removes stores with concentrated missingness from the sample
- NaN cannot go straight to `astype(int)`; fill first or use the nullable integer `Int64`
- Outliers use the IQR method: bounds are Q1-1.5*IQR and Q3+1.5*IQR; do not reverse them and do not add `abs`
- Derived fields reduce comprehension cost, create interpretable features and enable group comparison
- Fixed cleaning order: convert -> fill -> outliers -> derive
