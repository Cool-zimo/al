# The subprocess Module Basics

> This lesson shows how to invoke external commands safely from Python. The core is `subprocess.run()`: `capture_output` collects output, `check=True` turns failures into exceptions, and one rule is non-negotiable—**never pass user input to `shell=True`.**

## run(): The Basic Form

```python
import subprocess

result = subprocess.run(["ls", "-la"], capture_output=True, text=True)
print(result.stdout)        # Standard output as a string.
print(result.stderr)        # Standard error.
print(result.returncode)    # 0 means success.
```

Three parameters matter:

- `capture_output=True`: captures stdout and stderr (equivalent to `stdout=PIPE, stderr=PIPE`).
- `text=True` (or `encoding="utf-8"`): gives you strings instead of bytes.
- `check=True`: raises `CalledProcessError` whenever the exit code is non-zero.

## Arguments Are a List, Not a String

```python
import subprocess

# Correct: command and arguments are separate list items.
subprocess.run(["git", "log", "--oneline", "-n", "5"], capture_output=True, text=True)

# WRONG: the string form depends on shell parsing; spaces will break it.
subprocess.run("git log --oneline -n 5", capture_output=True, text=True)
# Without shell=True, Python treats the whole string as one program name
# and raises FileNotFoundError.
```

The error:

```
FileNotFoundError: [Errno 2] No such file or directory: 'git log --oneline -n 5'
```

Python interprets the entire string as the program name. **Always use a list**, unless you genuinely need shell features such as pipes or glob expansion.

## check=True: Make Failures Visible

```python
import subprocess

# WRONG: without check=True, a failed command is treated as success.
result = subprocess.run(["grep", "xyz", "missing file"])
print("Continuing...")   # grep exits with code 2 here, but execution just rolls on.
```

The `grep` call above fails, yet the program continues as if nothing happened. That is a classic silent failure.

```python
import subprocess

# Correct: check=True raises an exception on a non-zero exit code.
try:
    result = subprocess.run(
        ["grep", "xyz", "/etc/hosts"],
        capture_output=True, text=True, check=True,
    )
    print(result.stdout)
except subprocess.CalledProcessError as e:
    print(f"Command failed with exit code {e.returncode}: {e.stderr}")
```

With `check=True`, child-process failures become Python exceptions. You handle them in one place instead of writing `if result.returncode != 0` everywhere.

## Crash Site: `shell=True` Plus User Input Equals Command Injection

This is a security red line. When you concatenate user input into a `shell=True` command, you hand over the shell.

```python
import subprocess

# WRONG: filename came from a web form, an API, or another user.
filename = input("Which file should I inspect? ")
# Attacker types: "; rm -rf /"
subprocess.run(f"cat {filename}", shell=True)
# Actual execution: cat ; rm -rf /
# Every file on the system is now at risk.
```

If the input contains `;`, `&&`, `|`, backticks, or a newline, the attacker can inject arbitrary commands. That is **command injection**.

**Never do this.** Use the list form instead:

```python
import subprocess

filename = input("Which file should I inspect? ")

# Correct: a list, never shell=True.
subprocess.run(["cat", filename])

# Even if filename is "; rm -rf /", cat simply reports that
# the file does not exist and nothing is deleted.
```

List arguments **never pass through the shell**, so special characters are treated as literal text.

## Crash Site: `shell=True` Is Not a Performance Trick

```python
import subprocess

# WRONG: you believe shell=True is faster.
for i in range(10000):
    subprocess.run(f"echo {i}", shell=True)
# Each call forks a /bin/sh process. This is painfully slow and wasteful.
```

`shell=True` launches an extra shell process to parse the command. Ten thousand calls spawn ten thousand shells—slow and expensive.

```python
import subprocess

# Correct: the list form goes straight to exec with no shell overhead.
for i in range(10000):
    subprocess.run(["echo", str(i)])
```

Reach for `shell=True` only when you **genuinely need** shell features: pipes `|`, redirection `>`, glob `*` expansion, or `$VAR` expansion. And when you do, **the command must be hardcoded with no external input**:

```python
# The only reasonable shell=True use case: a pipeline.
subprocess.run("ps aux | grep python | wc -l", shell=True, capture_output=True, text=True)
```

## Hands-On: A Safe Wrapper Around an External Command

```python
import subprocess

def run_git(args):
    """Run a git subcommand safely. Return (success, output or error message)."""
    try:
        result = subprocess.run(
            ["git"] + args,
            capture_output=True, text=True, check=True, timeout=30,
        )
        return True, result.stdout.strip()
    except subprocess.CalledProcessError as e:
        return False, e.stderr.strip()
    except subprocess.TimeoutExpired:
        return False, "Command timed out"

ok, output = run_git(["status", "--short"])
print(ok, output)

ok, output = run_git(["log", "-1", "--format=%H"])
print(ok, output)
```

A production-quality call combines three things: a list, `check=True`, and a `timeout`.

## Recap

- `subprocess.run(args, capture_output=True, text=True)` is the form you will use most.
- Arguments are **always a list**, never a string (unless `shell=True` and the content is hardcoded).
- `check=True` raises `CalledProcessError` on a non-zero exit code.
- `timeout=` prevents commands from hanging forever.
- **`shell=True` plus user input equals command injection.** Never allow it.
- `shell=True` adds an extra process and should be avoided in loops.
