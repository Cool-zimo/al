# Time Zones: naive vs aware

> This lesson answers "why can't I mix zoned and unzoned times, and how do I work with time zones properly using zoneinfo?" You will learn the golden rule: store UTC, display local.

## naive and aware at a glance

| Type | Meaning | `tzinfo` |
|---|---|---|
| **naive** | Does not know which zone it belongs to | `None` |
| **aware** | Explicitly bound to a time zone | not `None` |

```python
from datetime import datetime, timezone, timedelta

naive = datetime(2026, 9, 27, 14, 30)
print(naive.tzinfo)   # None -> naive

tz_utc1 = timezone(timedelta(hours=1))
aware = datetime(2026, 9, 27, 14, 30, tzinfo=tz_utc1)
print(aware.tzinfo)   # UTC+01:00 -> aware
```

**A naive object is just a number** — it says "14:30," but it does not say whether that is London time or New York time. Only you, the programmer, know. That is where bugs are born.

## Crash Site: naive and aware cannot be compared

```python
from datetime import datetime, timezone, timedelta

tz_utc1 = timezone(timedelta(hours=1))
aware = datetime(2026, 9, 27, 14, 30, tzinfo=tz_utc1)
naive = datetime(2026, 9, 27, 14, 30)

# WRONG: mixing naive and aware
print(aware > naive)
```

Error:

```
TypeError: can't compare offset-naive and offset-aware datetimes
```

Python refuses the comparison because it cannot tell whether the two values represent the same moment. 14:30 London time is eight hours ahead of 14:30 UTC — those are not the same moment at all.

## zoneinfo: a real time-zone database (Python 3.9+)

`timezone(timedelta(hours=1))` can only express a fixed offset. But many real zones observe **daylight saving** — they shift between summer and winter offsets. A fixed offset gets this wrong.

Python 3.9 introduced `zoneinfo`, which uses the system's IANA time-zone database and handles DST correctly.

```python
from datetime import datetime
from zoneinfo import ZoneInfo

# build datetimes with real zones
dt_london = datetime(2026, 9, 27, 14, 30, tzinfo=ZoneInfo("Europe/London"))
dt_ny = datetime(2026, 9, 27, 14, 30, tzinfo=ZoneInfo("America/New_York"))

print(dt_london)   # 2026-09-27 14:30:00+01:00
print(dt_ny)       # 2026-09-27 14:30:00-04:00 (daylight saving)

# now they can be compared!
print(dt_london > dt_ny)   # True
```

## Converting zones with astimezone

The same moment, displayed in two different zones — that is what `astimezone` is for.

```python
from datetime import datetime
from zoneinfo import ZoneInfo

# 14:30 in London on 27 Sep 2026
dt_london = datetime(2026, 9, 27, 14, 30, tzinfo=ZoneInfo("Europe/London"))

# convert to New York time
dt_ny = dt_london.astimezone(ZoneInfo("America/New_York"))
print(dt_ny.strftime("%Y-%m-%d %H:%M:%S %Z"))  # 2026-09-27 09:30:00 EDT

# convert to UTC
dt_utc = dt_london.astimezone(ZoneInfo("UTC"))
print(dt_utc.strftime("%Y-%m-%d %H:%M:%S"))   # 2026-09-27 13:30:00
```

**The key idea**: `astimezone` does not change **the moment** — it only changes **how you display it**. Like the same football match shown at 19:00 in London and 14:00 in New York: one moment, two clocks.

## The golden rule: store UTC, display local

This is the consensus best practice in the industry:

1. **Store** everything in UTC
2. **Calculate** in UTC
3. **Display** converted to the user's zone

```python
from datetime import datetime
from zoneinfo import ZoneInfo

# 1. capture the current time in UTC (aware)
now_utc = datetime.now(ZoneInfo("UTC"))
print(now_utc)   # 2026-09-27 13:30:00+00:00

# 2. store it (as a UTC timestamp or a UTC datetime)
ts = now_utc.timestamp()

# 3. convert to the user's zone when displaying
user_tz = ZoneInfo("Europe/London")
display = now_utc.astimezone(user_tz)
print(display.strftime("%Y-%m-%d %H:%M:%S"))  # 2026-09-27 14:30:00
```

## Attaching a zone to a naive datetime with replace

If you have a naive datetime that you know is London time, you can **label** it with a zone:

```python
from datetime import datetime
from zoneinfo import ZoneInfo

naive = datetime(2026, 9, 27, 14, 30)
aware = naive.replace(tzinfo=ZoneInfo("Europe/London"))
print(aware)   # 2026-09-27 14:30:00+01:00
```

**Be careful**: `replace` here **declares** that the time was always in that zone. It does not *convert* zones. To convert a naive time from zone A to zone B, first `replace` with A, then `astimezone(B)`.

## Summary

- **naive** = no time zone (tzinfo is None); **aware** = has a time zone
- Comparing naive and aware raises `TypeError`
- `zoneinfo.ZoneInfo("Europe/London")` uses a real zone database and handles DST
- `astimezone()` changes the display zone without changing the moment
- Golden rule: **store UTC, calculate UTC, display local**
- `replace(tzinfo=...)` labels a naive datetime with a zone
