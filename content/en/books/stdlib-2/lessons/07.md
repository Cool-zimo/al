# Timing: perf_counter vs time.time

> This lesson answers "how do I measure how long my code takes to run?" You will learn why `time.time()` is the wrong tool for timing, and why `perf_counter` is the right one.

## Why time.time is unsafe for timing

`time.time()` returns the current Unix timestamp. Using it to measure a time difference seems natural:

```python
import time

start = time.time()
# ... do some work ...
end = time.time()
print(f"Elapsed: {end - start:.4f} seconds")
```

**The problem**: `time.time()` returns **wall-clock** time. The system wall clock can move backward or jump forward — NTP corrections, a manual clock change, or a daylight-saving transition can all move it.

```python
# imagine the system clock is stepped forward by 2 seconds during your measurement
start = time.time()    # 1000.0
# ... your code actually ran for 1 second ...
end = time.time()      # 1003.0 <- the clock was corrected!
print(end - start)     # 3.0 <- wrong! it was really 1 second
```

This occasional "time travel" makes wall-clock timing completely unreliable.

## perf_counter: built for measuring

`time.perf_counter()` returns a **monotonically increasing** counter that is not affected by system clock adjustments:

```python
import time

start = time.perf_counter()
# ... some work ...
end = time.perf_counter()
elapsed = end - start
print(f"Elapsed: {elapsed:.6f} seconds")
```

The characteristics of `perf_counter`:

- **Monotonic** — it never goes backward, regardless of clock corrections
- **High resolution** — typically nanosecond-level on modern hardware
- **Arbitrary starting point** — only the *difference* is meaningful; the absolute value is not (do not treat it as a timestamp)

```python
import time

print(time.perf_counter())  # 1234567.890123 <- the number itself means nothing
print(time.perf_counter())  # 1234567.890456 <- only the difference matters
```

## Worked example: benchmarking code

```python
import time

def benchmark():
    start = time.perf_counter()
    total = 0
    for i in range(1_000_000):
        total += i
    elapsed = time.perf_counter() - start
    return elapsed

t = benchmark()
print(f"One million iterations took: {t*1000:.2f} ms")
```

Output (the exact number depends on the machine):

```
One million iterations took: 35.42 ms
```

## Crash Site: using time.time to time a short sleep

```python
import time

# WRONG: timing with time.time is not guaranteed to be accurate
start = time.time()
time.sleep(0.5)
end = time.time()
print(f"slept for {end - start:.2f} seconds")
```

While this usually "works," it is not **guaranteed**. On some Windows systems, `time.time()` has a resolution of around 15.6 ms (roughly 1/64 of a second), so measuring a 5 ms operation would be wildly inaccurate. `perf_counter` delivers the best available resolution on every platform.

## time.monotonic: the other alternative

`time.monotonic()` is also monotonic, but it does **not** promise high resolution. If you only need to know "how much time passed" — for a timeout, say — it is fine:

```python
import time

start = time.monotonic()
time.sleep(1)
print(f"Elapsed: {time.monotonic() - start:.2f} seconds")  # 1.00
```

**Bottom line**: use `perf_counter` for performance, `monotonic` for timeouts, and **never use `time.time()` for elapsed time**.

## Worked example: a timing decorator

```python
import time

def timer(func):
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        result = func(*args, **kwargs)
        elapsed = time.perf_counter() - start
        print(f"{func.__name__} took {elapsed*1000:.2f} ms")
        return result
    return wrapper

@timer
def slow_task():
    total = 0
    for i in range(10_000_000):
        total += i
    return total

slow_task()  # output: slow_task took XX.XX ms
```

## Comparing the three time functions

| Function | Purpose | Affected by clock changes? | Resolution |
|---|---|---|---|
| `time.time()` | timestamps / wall clock | yes | medium |
| `time.perf_counter()` | measuring performance | no | highest |
| `time.monotonic()` | timeout checks | no | medium |

## Summary

- `time.time()` is wall-clock time and can jump due to NTP or manual changes — **not for timing**
- `time.perf_counter()` is monotonic and high-resolution — **the right tool for performance**
- `time.monotonic()` is monotonic — fine for timeouts
- The absolute value of `perf_counter` is meaningless; only the difference matters
- Use `perf_counter` whenever you write a decorator or a timing helper
