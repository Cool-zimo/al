# Form validation: required fields, patterns and friendly messages

> This lesson answers: how do you check whether the user's input is valid before sending it, and how do you tell them exactly what to fix?

## Why validate in the browser first

Client-side validation has three jobs:

1. **Immediate feedback** — the user learns about a problem while still filling in the field.
2. **Fewer bad requests** — invalid data should not travel to the server.
3. **Better experience** — show the right message in the right place.

It is not a replacement for server validation; it is the fast, friendly first line of defence.

## Required fields

The simplest check is whether a value is empty. Use `trim()` so that spaces alone are not accepted.

```html
<form id="login-form">
  <input type="text" id="username" placeholder="Username">
  <input type="password" id="password" placeholder="Password">
  <button type="submit">Log in</button>
  <p id="error-msg" style="color: red;"></p>
</form>
```

```js
document.querySelector('#login-form').addEventListener('submit', (event) => {
  event.preventDefault();

  const username = document.querySelector('#username').value.trim();
  const password = document.querySelector('#password').value;
  const errorMsg = document.querySelector('#error-msg');

  if (username === '') {
    errorMsg.textContent = 'Username is required.';
    return;
  }

  if (password === '') {
    errorMsg.textContent = 'Password is required.';
    return;
  }

  errorMsg.textContent = '';
  console.log('Submitting:', username);
});
```

`return` stops the rest of the handler once you already know the form is invalid.

## Patterns with regular expressions

Regular expressions are good for structure: an email has an `@`, a UK mobile number has a known shape, and a strong password has a minimum mix of characters.

```js
function isValidEmail(email) {
  const re = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;
  return re.test(email);
}

function isValidUkMobile(phone) {
  const re = /^07\d{9}$/;
  return re.test(phone);
}

function isStrongPassword(pwd) {
  return pwd.length >= 8 && /[a-zA-Z]/.test(pwd) && /\d/.test(pwd);
}
```

`.test()` returns `true` or `false`, which is exactly what a validator needs. Keep the expressions as simple as the real requirement; an overly strict "email regex" often rejects valid addresses.

## A good message names the field, the problem and the fix

### Crash Site 1: saying only "error"

```js
if (!isValid) {
  alert('Error');
}
```

**Why it crashes:** the user is told that something is wrong but not what, where, or how to repair it. They either guess or abandon the form.

```js
function showError(fieldName, reason) {
  document.querySelector('#error-msg').textContent =
    `${fieldName} is not valid: ${reason}`;
}

if (!isValidEmail(email)) {
  showError('Email', 'Enter a valid address such as alice@example.com.');
  return;
}

if (!isValidUkMobile(phone)) {
  showError('Phone', 'Enter an 11-digit UK mobile number such as 07123456789.');
  return;
}

if (!isStrongPassword(password)) {
  showError('Password', 'Use at least 8 characters with both letters and numbers.');
  return;
}
```

A good message has three parts: the field, the problem, and an example that points at the fix.

## Collect every problem, then show them together

If you stop after the first failure, the user fixes one field, submits again, and hits the next error.

```js
function validateForm(data) {
  const errors = [];

  if (!data.username.trim()) {
    errors.push({ field: 'username', message: 'Username is required.' });
  } else if (data.username.length < 3) {
    errors.push({ field: 'username', message: 'Username must be at least 3 characters.' });
  }

  if (!data.email.trim()) {
    errors.push({ field: 'email', message: 'Email is required.' });
  } else if (!isValidEmail(data.email)) {
    errors.push({ field: 'email', message: 'Enter a valid email such as alice@example.com.' });
  }

  if (!data.phone.trim()) {
    errors.push({ field: 'phone', message: 'Phone is required.' });
  } else if (!isValidUkMobile(data.phone)) {
    errors.push({ field: 'phone', message: 'Enter an 11-digit UK mobile number.' });
  }

  return errors;
}
```

```js
document.querySelector('#my-form').addEventListener('submit', (event) => {
  event.preventDefault();

  const data = {
    username: document.querySelector('#username').value,
    email: document.querySelector('#email').value,
    phone: document.querySelector('#phone').value
  };

  const errors = validateForm(data);

  if (errors.length > 0) {
    document.querySelector('#error-msg').textContent = errors[0].message;
    document.querySelector(`#${errors[0].field}`).focus();
    return;
  }

  document.querySelector('#error-msg').textContent = '';
  console.log('Valid:', data);
});
```

### Crash Site 2: reporting one error at a time

```js
if (!data.username) { alert('Username is required.'); return; }
if (!data.email)    { alert('Email is required.'); return; }
if (!data.phone)    { alert('Phone is required.'); return; }
```

**Why it crashes:** the user must submit three times to discover three problems. Returning the full error list lets the page show them all at once.

## Real-time validation on `input`

Checking only on submit means the user fills the whole form before learning about an early mistake. Validate while typing instead.

```js
document.querySelector('#email').addEventListener('input', (event) => {
  const value = event.target.value;
  const hint = document.querySelector('#email-hint');

  if (value === '') {
    hint.textContent = '';
    return;
  }

  if (!isValidEmail(value)) {
    hint.textContent = 'Enter a valid email such as alice@example.com.';
    hint.style.color = 'red';
  } else {
    hint.textContent = 'Email looks good.';
    hint.style.color = 'green';
  }
});
```

This is especially useful for weak-password hints and availability checks, where the cost of waiting until submit is high.

## HTML5 attributes are a useful backup

The browser can perform basic checks with `required`, `minlength`, `type` and `pattern`.

```html
<form id="my-form">
  <input type="email" required placeholder="Email">
  <input type="password" minlength="8" required placeholder="Password">
  <input type="tel" pattern="^07[0-9]{9}$" placeholder="UK mobile">
  <button type="submit">Submit</button>
</form>
```

```js
document.querySelector('#my-form').addEventListener('submit', (event) => {
  event.preventDefault();

  if (!event.target.checkValidity()) {
    event.target.reportValidity();
    return;
  }

  console.log('Valid');
});
```

### Crash Site 3: relying only on built-in messages

```html
<input type="email" required placeholder="Email">
```

**Why it crashes:** the browser's message is generic and its wording depends on the browser and language. It also appears one field at a time. Keep HTML5 validation as a fallback, but write your own messages when the product needs a specific voice.

## Comparison with Python

Server-side frameworks usually declare rules on a form class:

```python
from wtforms import StringField, validators

class LoginForm(Form):
    username = StringField('Username', [validators.Length(min=3, max=20)])
    email = StringField('Email', [validators.Email()])
```

JavaScript validation's advantage is timing: it runs before the data leaves the page, so the user can correct mistakes in the same context where they made them.

## Recap

- Client-side validation gives immediate feedback and reduces bad requests, but the server must still validate.
- Use `value.trim()` to reject whitespace-only required fields.
- Regular expressions answer structural questions; use `.test()` to get a boolean.
- A useful error message identifies the field, states the problem and gives an example fix.
- Collect all validation errors before reporting, so the user sees the full picture.
- Real-time checks on `input` are better than waiting until submit.
- HTML5 validation is a fallback, not a complete user-experience solution.
