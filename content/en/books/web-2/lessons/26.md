# Project design: breaking down a to-do list into features and data

> This lesson answers: when you are handed a project brief, how do you split it into features, define the data structure, and sketch the interface?

## The project goal

You are going to build a to-do list application. It needs six things:

1. **Create** — type a task and click add.
2. **Delete** — click a button to remove a task.
3. **Update** — click a task to flip its completed state.
4. **Read** — display the full list.
5. **Persist** — survive a page refresh.
6. **Filter** — show all, active, or completed tasks.

That is the whole brief. Six verbs, one screen. The trick is not writing the code; it is deciding what the code operates on before you open the editor.

## Splitting the features

A large requirement becomes manageable once you separate it into layers.

```
To-do list
├── View layer
│   ├── Input box + add button
│   ├── Task list (checkbox, text, delete button per item)
│   └── Filter buttons (all / active / completed)
├── Data layer
│   ├── Task array (in memory)
│   ├── localStorage read and write
│   └── Render function (data → DOM)
└── Interaction layer
    ├── Add a task
    ├── Delete a task
    ├── Toggle completed
    └── Switch filter
```

Notice the direction of dependencies: the view and the interaction layer both depend on the data layer, but the data layer knows nothing about the DOM. That separation is what keeps the code testable. If your render function reaches into `localStorage` and your delete function reaches into `document`, a change to either one forces a change to the other.

## Designing the data structure

Each task is an object with three fields:

```js
// A single task
{
  id: 1,        // stable identity (timestamp or auto-increment)
  text: 'Buy milk',
  done: false   // completed or not
}

// The list (an array)
const todos = [
  { id: 1, text: 'Buy milk', done: false },
  { id: 2, text: 'Write code', done: true },
  { id: 3, text: 'Read a book', done: false }
];
```

**Why an `id` at all?** Because `text` is not unique. Two people can both need to "Buy milk". Without a stable identifier, you cannot tell their tasks apart, and you certainly cannot delete or toggle the right one.

### Crash Site 1: using the array index as the identity

```js
const todos = [
  { text: 'Buy milk', done: false },
  { text: 'Write code', done: true }
];

// Remove index 0
todos.splice(0, 1);
// "Write code" was at index 1, now it is at index 0.
// If the DOM still stores the old index, you operate on the wrong object.
```

The array is dynamic. Every deletion shifts every later element left by one. Anything you attached to "index 1" is now pointing at a different task. The fix is not cleverer indexing; it is a stable `id` that the array cannot move out from under you.

## Strategies for generating an id

```js
// Strategy 1: timestamp (simple, collisions possible under load)
function generateId() {
  return Date.now();
}

// Strategy 2: auto-increment counter (the safest default)
let nextId = 1;
function generateId() {
  return nextId++;
}

// Strategy 3: UUID (strictest, but long)
function generateId() {
  return crypto.randomUUID();
}
```

For a single-user, single-tab application, the auto-increment counter is enough. Timestamps are tempting because they need no state, but two tasks created in the same millisecond collide, and a collision means two checkboxes control the same record. In a classroom, that shows up as "I checked one box and a different line crossed out." Reach for `randomUUID` only when you need ids before the item reaches the server.

```
├─────────────────────────────┤
│  [ New task...         ] [+] │  ← input area
├─────────────────────────────┤

│  │ ☑ Write code     [del]  ││
│  │ ☐ Read a book    [del]  ││
│  └─────────────────────────┘│
├─────────────────────────────┤

├─────────────────────────────┤
│  3 total, 2 active          │  ← stats
└─────────────────────────────┘
```

A sketch is cheap planning. Draw it before you write CSS and you will notice that the delete button must sit on the right edge of every row, which tells you the row is a flex container before you have written a single rule.

## The state management idea

```js
// One source of truth: every visible state derives from the todos array.
let todos = loadFromStorage();  // restore from localStorage
let filter = 'all';             // current view: 'all' | 'active' | 'completed'

// Render: read todos + filter, rebuild the DOM.
function render() {
  // 1. filter
  const filtered = todos.filter(todo => {
    if (filter === 'active') return !todo.done;
    if (filter === 'completed') return todo.done;
    return true;
  });

  // 2. build the DOM
  list.innerHTML = '';
  filtered.forEach(todo => {
    const li = document.createElement('li');
    li.className = todo.done ? 'done' : '';
    li.innerHTML = `
      <input type="checkbox" ${todo.done ? 'checked' : ''}>
      <span>${todo.text}</span>
      <button class="delete-btn">Delete</button>
    `;
    list.appendChild(li);
  });

  // 3. update the counts
  updateStats();
}

// Call render() after every change to the data.
function addTodo(text) {
  todos.push({ id: generateId(), text, done: false });
  saveToStorage();
  render();  // re-render
}

function toggleTodo(id) {
  const todo = todos.find(t => t.id === id);
  if (todo) todo.done = !todo.done;
  saveToStorage();
  render();
}

function deleteTodo(id) {
  todos = todos.filter(t => t.id !== id);
  saveToStorage();
  render();
}
```

**The core pattern is data-driven rendering.** You do not poke at the DOM to change state. You change the data, then call `render()` to rebuild the list from scratch. This is simpler and more reliable than manually inserting and removing individual elements, because there is only one place where the DOM can get out of sync with the data: the render function.

## Comparison with Python

A Python command-line to-do program works directly with the list:

```python
# Python: manipulate a list and print it
todos = []

def add_todo(text):
    todos.append({"id": len(todos) + 1, "text": text, "done": False})

def show_todos():
    for t in todos:
        status = "✓" if t["done"] else "☐"
        print(f"{status} {t['text']}")

# The interaction loop
while True:
    cmd = input("> ")
    if cmd.startswith("add "):
        add_todo(cmd[4:])
    show_todos()
```

The JavaScript version adds exactly one extra step: mapping the data into the DOM. The thinking is otherwise identical. **The data is the single source of truth; the interface is a projection of that data.**

## Recap

- Start a project by splitting features: create, read, update, delete, persist, filter.
- Each task needs a stable `id`; you cannot use the array index because the index moves.
- Data drives the view: change the data, then call `render()` to rebuild the DOM.
- A sketch nails down the layout; the data shape nails down the logic.
- One source of truth (`todos` plus `filter`) from which every render derives.
