# Console debugging: `log`, `table` and `dir`, breakpoints, and reading the stack

> This lesson answers: when your code does not work, how do you find out why? You will use console output, step through execution with breakpoints, and read a stack trace to locate the real source of an error.

## The `console` toolbox

### `console.log`: the everyday inspector

```js
const name = 'Alice';
const age = 25;

console.log('name:', name);
console.log('age:', age, 'years old');
console.log({ name, age });
```

A label makes the output readable, and logging an object as a single argument lets the console show its structure.

### `console.table`: structured rows and columns

```js
const users = [
  { name: 'Alice', age: 25, city: 'London' },
  { name: 'Bob', age: 30, city: 'Paris' },
  { name: 'Cara', age: 28, city: 'Berlin' }
];

console.table(users);
```

`console.table` turns an array of objects into a table. It is especially useful for lists returned from a server or generated by a loop.

### `console.dir`: properties of a DOM object

```js
const button = document.querySelector('button');

console.log(button);  // the element rendered as markup
console.dir(button);  // the DOM object's properties
```

**Difference:** `log` displays the element as HTML, while `dir` exposes the JavaScript property tree. When you want `tagName`, `className`, `dataset` or event handlers, `dir` is the better view.

### Other helpers worth knowing

```js
console.warn('Heads up: deprecated function used.');
console.error('Failed to fetch user data.');

console.group('Request details');
console.log('URL: /api/users');
console.log('Status: 200');
console.groupEnd();

console.count('render');
console.count('render'); // render: 2

console.time('filter');
// work happens here
console.timeEnd('filter'); // filter: 1.2ms
```

## Breakpoints beat sprinkling logs everywhere

### How to set a breakpoint

1. Open DevTools with F12 and choose the **Sources** panel.
2. Find your JavaScript file in the tree.
3. Click the line number; a blue marker appears.
4. Trigger the code and execution pauses at that line.

### What you can do while paused

| Action | Shortcut | Effect |
|---|---|---|
| Step over | F10 | Run the current line and move to the next one |
| Step into | F11 | Enter the function called on this line |
| Step out | Shift+F11 | Finish the current function and return to its caller |
| Resume | F8 | Continue until the next breakpoint |
| Watch | — | Add a variable name to see its current value |

### Crash Site 1: too many logs hide the real value

```js
function calculateTotal(items) {
  console.log('items:', items);
  let total = 0;
  for (const item of items) {
    console.log('item:', item);
    total += item.price * item.qty;
    console.log('total:', total);
  }
  return total;
}
```

**Why it crashes:** ten items produce dozens of lines, and the value you care about disappears in the noise. A breakpoint lets you inspect every variable at one paused moment without changing the code.

## Reading an error message

### The structure

```
TypeError: Cannot read properties of null (reading 'value')
    at handleSubmit (app.js:15:23)
    at HTMLFormElement.<anonymous> (app.js:8:5)
```

Read it from bottom to top:

1. **The bottom line** is where the action started, often a user click.
2. **The middle lines** are the call chain: who called whom.
3. **The top line** names the error type and the exact file, line and column.

### Common errors

| Error | Meaning | Typical cause |
|---|---|---|
| `TypeError: Cannot read properties of null` | A property was read on `null` | `querySelector` found nothing |
| `TypeError: ... is not a function` | Something was called as a function | Typo or wrong type |
| `ReferenceError: ... is not defined` | An undeclared variable was used | Misspelled or missing declaration |
| `SyntaxError: Unexpected token` | The parser could not read the code | Missing bracket, parenthesis or quote |
| `RangeError: Maximum call stack size exceeded` | Recursion never stopped | Missing base case |

### Following the stack

```js
document.querySelector('#btn').addEventListener('click', () => {
  handleSubmit(); // app.js:8
});

function handleSubmit() {
  const input = document.querySelector('#username');
  console.log(input.value); // app.js:15 — fails because #username is missing
}
```

```
TypeError: Cannot read properties of null (reading 'value')
    at handleSubmit (app.js:15:23)             // the failing line
    at HTMLButtonElement.<anonymous> (app.js:8:5) // the caller
```

**The debugging path:**

1. The type is `TypeError`, so an unexpected value was used as an object.
2. The message says the value is `null` and `.value` was read.
3. The location is `app.js:15`; open that line.
4. Pause there and inspect `input`; it is `null`.
5. Trace back: the selector `#username` does not match any element.

## Breakpoints versus logging

| Aspect | `console.log` | Breakpoints |
|---|---|---|
| Setup cost | One extra line | DevTools open and a click |
| Information | Values at print time only | Every variable, the call stack and the scope chain |
| Code change | You edit the source | You do not |
| Conditional pausing | Wrap the log in an `if` | Right-click the breakpoint and add a condition |
| Loops | Logs can flood the console | Pause only for the iteration you need |
| Production code | Logs are easy to forget | Breakpoints leave no trace |

### Crash Site 2: expecting an async callback to pause immediately

```js
document.querySelector('#btn').addEventListener('click', () => {
  setTimeout(() => {
    const data = fetchData();
    console.log(data);
  }, 3000);
});
```

**Why it crashes:** the breakpoint is inside a callback that runs three seconds later. You cannot predict exactly when it will hit. Set the breakpoint first, then trigger the event; DevTools will stop the moment the callback runs.

## A practical debugging routine

```
Something is wrong
  ↓
Check the console for red errors
  ↓ yes → read the error and open the file at the line number
  ↓ no  → the code runs but the logic is wrong
  ↓
Add a breakpoint or a log near the suspect code
  ↓
Inspect values at that point
  ↓
Form a theory, change one thing, then reload and verify
```

Change one thing at a time. If you alter three lines and the output changes, you will not know which line fixed it.

## Comparison with Python

Python debugging typically uses `print` or `pdb`:

```python
def calculate(items):
    print(f"items: {items}")
    total = 0
    for item in items:
        total += item.price
    return total

import pdb; pdb.set_trace()  # similar to JavaScript's debugger;
```

Browser breakpoints are graphical and let you inspect scope, watch expressions and the call stack without adding code. That workflow is one of the most useful skills in front-end development.

## Recap

- `console.log` is quick, `console.table` handles lists cleanly, and `console.dir` exposes a DOM object's properties.
- Breakpoints let you inspect everything without editing the source.
- Read stack traces from bottom to top: the bottom is the trigger, the top is the failure.
- `TypeError: ... of null` usually means a selector found nothing.
- Change one thing, then reload and verify; never guess at three fixes at once.
