# Exceptions: try / except / finally

> By the end of this lesson you will be able to make your programs fail gracefully instead of crashing in a wall of red text.

## Crashing Is Not a Polite Way to Exit

```python
age = int(input("Your age: "))
print("you were probably born around", 2026 - age)
```

What happens if the user types `twenty`?

```
ValueError: invalid literal for int() with base 10: 'twenty'
```

The program crashes on the spot. That is a terrible user experience — **errors you can anticipate should be caught by you.**

## try / except: Catching the Fallout

```python
try:
    age = int(input("Your age: "))
    print("you were probably born around", 2026 - age)
except ValueError:
    print("please enter a number, like 18")
```

The structure: put the **code that might fail** inside `try`, and put the **recovery logic** in `except`.

- If nothing goes wrong in the `try` block, execution continues normally and `except` is skipped
- If a `ValueError` occurs inside `try`, Python jumps straight to `except` and runs your fallback logic

## Catching Specific Errors

Always write a **specific exception type** after `except` — do not grab everything at once. The common ones:

| Exception | When it is raised |
|---|---|
| `ValueError` | conversion failed, e.g. `int("abc")` |
| `ZeroDivisionError` | division by zero |
| `FileNotFoundError` | the file does not exist |
| `KeyError` | a dictionary key is missing |
| `IndexError` | a list index is out of range |
| `TypeError` | types do not match |

```python
try:
    num = int(input("enter a number: "))
    result = 100 / num
    print("100 /", num, "=", result)
except ValueError:
    print("that is not a number")
except ZeroDivisionError:
    print("cannot divide by zero")
```

Two `except` blocks, each handling its own error — much more targeted.

## Crash Scene: Catching Too Broadly

```python
# WRONG: looks safe, is actually dangerous
try:
    age = int(input("age: "))
    print(2026 - age)
except Exception:
    print("something went wrong")
```

**What is the problem:** `Exception` is the base class of almost every exception, so this **silently swallows your own bugs as well**. Suppose you accidentally typed `year2026` instead of `2026`; that name error would also land in `except`, and you would never know you had a typo in your code.

**The right approach:** only catch the errors you can actually handle:

```python
try:
    age = int(input("age: "))
    print(2026 - age)
except ValueError:
    print("please enter a valid number")
```

> Rule of thumb: **catch specific errors, never catch `Exception`.**

## `else` and `finally`

```python
try:
    f = open("data.txt", "r", encoding="utf-8")
    content = f.read()
except FileNotFoundError:
    print("file not found")
else:
    print("read successful, length:", len(content))   # runs only if nothing went wrong
finally:
    f.close()                                         # runs no matter what
```

- `else`: runs **only if no error occurred**, used for "the rest of the normal flow"
- `finally`: runs **regardless of success or failure**, used for "cleanup" (closing files, releasing resources)

> Once you use the `with` statement you no longer need to call `close()` manually, so `finally` is less common for files — but it is still essential for **network connections and database transactions.**

## When to Catch, When Not to Catch

**Catch** errors you can anticipate and know how to handle.

```python
try:
    config = json.load(open("config.json", encoding="utf-8"))
except FileNotFoundError:
    config = {}         # no config file means use the defaults — perfectly reasonable
```

**Do not catch** unexpected bugs at the application level.

```python
try:
    do_something()
except Exception as e:
    pass                # silently swallowed, leaving zero clues — worst practice
```

Even printing the exception is better than nothing, so you keep a trail:

```python
try:
    age = int(input("age: "))
except ValueError as e:
    print("conversion failed:", e)    # e is the exception object; printing it shows why
```

## Summary

- `try/except` separates "code that might fail" from "what to do about it"
- Put a **specific exception type** after `except`, not `Exception`
- Common errors: `ValueError`, `ZeroDivisionError`, `FileNotFoundError`, `KeyError`, `IndexError`
- `else` runs only on success, `finally` runs in every case
- Only catch errors you can handle; silently swallowing `except: pass` is the worst practice
- `except ... as e` gives you the exception object so you can print it for debugging
