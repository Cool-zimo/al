# 26 Sessions & Connection Reuse: Why Your Loop Is Ten Times Slower

> Write a loop that sends 100 requests to the same API and you might wait ten seconds. Change one line — swap `requests.get()` for `session.get()` — and the same 100 requests finish in two. **This lesson explains exactly where that tenfold gap comes from, and what else a Session gives you besides speed.**

## First, a Confusing Phenomenon

```python
import requests
import time

url = "https://httpbin.org/get"

# Style A: requests.get every time
start = time.time()
for i in range(10):
    requests.get(url, timeout=10)
print(f"requests.get  : {time.time() - start:.2f}s")

# Style B: use a Session
start = time.time()
with requests.Session() as s:
    for i in range(10):
        s.get(url, timeout=10)
print(f"Session       : {time.time() - start:.2f}s")
```

**Typical output** (numbers vary by network, but the ratio is remarkably stable):

```
requests.get  : 6.83s
Session       : 0.94s
```

**Same 10 requests, a 7× gap.** If your script sends 1000 requests, that's the difference between "runs 11 minutes" and "runs 90 seconds."

Seeing this for the first time, many people assume Session does something magical. It doesn't. It simply **doesn't throw away the connection it already built.**

To understand that sentence, you need to know how much actually happens behind a single request.

## Behind One Request: You Think It's One Step, It's Six

When you write `requests.get("https://api.github.com/user")`, this happens underneath:

```
① DNS lookup        → what's the IP for api.github.com?
② TCP 3-way handshake → hello / got it / ok, channel established
③ TLS handshake     → negotiate the encrypted channel (HTTPS only, but that's nearly everything now)
④ Send HTTP request → GET /user HTTP/1.1 ...
⑤ Wait and receive  → server processes + data comes back
⑥ Close connection  → four-way wave, goodbye
```

**Only steps ④⑤ do the actual work.** ①②③⑥ are all **setup and teardown**.

### An Analogy: Phone Call vs. Fax

- **TCP handshake**: you dial, they pick up and say "hello," you say "it's me" — **confirming both sides are online and can hear each other**. Physically, three packets making one round trip
- **TLS handshake**: after confirming you're both there, you still have to agree on "which cipher we'll speak in" and exchange keys — **another round trip**
- **HTTP request**: finally, you get to the point
- **Close connection**: hang up

**The problem**: if you hang up and redial and re-agree on the cipher for every single question, most of your time goes to dialing and cipher-agreeing, not to the actual business.

### Let's Use Numbers: RTT

Networking has a concept called **RTT (Round-Trip Time)** — how long a packet takes to travel from you to the server and back.

- Within the same country: maybe **5~30ms**
- From China to a US server: typically **150~300ms**

**Every "round trip" costs one RTT.** So the setup cost of one HTTPS request:

| Step | RTTs needed | Notes |
|---|---|---|
| DNS lookup | 0~1 | **0 if cached locally** |
| TCP 3-way handshake | **1** | unavoidable |
| TLS 1.2 handshake | **2** | |
| TLS 1.3 handshake | **1** | newer servers |
| HTTP request + response | **1** | the actual work |

In other words: **sending one HTTPS request spends 2~3 RTTs on setup and only 1 RTT on real work.**

With RTT = 200ms to a US server:

```
No reuse: each request ≈ 3 RTT setup + 1 RTT work
Reuse   : each request ≈ 0 RTT setup + 1 RTT work
```

**That's why connection reuse brings multi-fold speedups** — you're not saving "work" time, you're eliminating the repeated "redial + re-cipher" time.

## Why `requests.get()` Doesn't Reuse

Look at this:

```python
import requests

requests.get("https://httpbin.org/get")     # connect → request → close
requests.get("https://httpbin.org/get")     # connect → request → close (all over again)
```

**`requests.get()` is a one-shot function.** Internally it's essentially:

```python
def get(url, params=None, **kwargs):
    # actual internal implementation (simplified)
    with sessions.Session() as session:      # ① create a new Session
        return session.request("GET", url, params=params, **kwargs)
    # ② with block ends → Session closes → pool destroyed → connections discarded
```

> **Line-by-line**
>
> - **① A brand new Session on every call.** This is the key — **`requests.get()` never "has no Session"; it uses a fresh temporary one every time**
> - **② Destroyed immediately after use.** The TCP connection just built, the TLS keys just negotiated — **all thrown away**

**So the truth is**: it's not that `requests.get()` doesn't support reuse; it's that it **uses and discards**. Every call re-pays the "connection tax" of 2~3 RTTs.

## Session: Keep the Connection

```python
import requests

with requests.Session() as s:                    # ① create a Session
    for i in range(10):
        r = s.get("https://httpbin.org/get", timeout=10)   # ② s.get, not requests.get
        print(r.status_code)
# ③ with block ends, Session closes, pool released
```

> **Line-by-line**
>
> - **① `requests.Session()`**: creates an object **with a connection pool**. No server has been contacted yet
> - **② `s.get(...)`**: the first call establishes a connection (pays the tax); **when done, the connection isn't closed — it goes back into the pool**. The second call takes it straight out — **zero setup cost**
> - **③ `with`**: Session implements the context manager. **Always close it**, or the pool never releases

**Why `with`**: the connections a Session holds are **real operating system sockets**. Leaving them open keeps those sockets occupied until the Python process exits. In a long-running service, that's a **file descriptor leak**.

### Without `with` (and why it's riskier)

```python
import requests

s = requests.Session()
try:
    r = s.get("https://httpbin.org/get", timeout=10)
    print(r.status_code)
finally:
    s.close()          # ① mandatory!
```

> - **① `s.close()`**: does what the `with` block does on exit. **Forget it and the connection leaks**

**Recommendation**: use `with` whenever you can. The only reason for `try/finally` is when the Session's lifetime crosses function boundaries (e.g., living as an object attribute).

## Three Freebies a Session Gives You

Besides speed, a Session gives you three more things. In practice these matter more than the speed.

### Freebie One: Automatic Cookie Persistence (Login State)

**This is the most useful one.**

```python
import requests

with requests.Session() as s:
    # Step 1: log in
    r = s.post("https://httpbin.org/cookies/set/session_id/abc123", timeout=10)
    print("login response:", r.status_code)

    # Step 2: visit a page that requires login
    r = s.get("https://httpbin.org/cookies", timeout=10)
    print(r.json())
    # {'cookies': {'session_id': 'abc123'}}     ← cookie attached automatically!
```

> **Line-by-line**
>
> - **The first POST**: the server returns `Set-Cookie: session_id=abc123`. The Session **automatically stores it in its cookie jar**
> - **The second GET**: the Session **automatically adds `Cookie: session_id=abc123`** to the request headers. You write nothing

**Without a Session**, you'd do it manually:

```python
# ❌ The painful no-Session way
r1 = requests.post("https://httpbin.org/cookies/set/session_id/abc123")
cookie_value = r1.cookies["session_id"]            # extract by hand

r2 = requests.get("https://httpbin.org/cookies",
                  cookies={"session_id": cookie_value})   # attach by hand
```

Fine once or twice, but a site requiring login has five or six requests, and you'd pass five or six cookies by hand — **and the moment the server changes the cookie's contents, your code silently breaks**.

> **This echoes lesson 10**: HTTP itself is stateless; cookies are a bolted-on memory mechanism. Session manages that bolt-on for you.

### Freebie Two: Default Headers

Repeating the same header is a common code smell:

```python
# ❌ Writing it out every single time
headers = {"Authorization": "Bearer ghp_xxx", "User-Agent": "MyApp/1.0"}
requests.get(url1, headers=headers)
requests.get(url2, headers=headers)
requests.get(url3, headers=headers)
```

Set it once on the Session:

```python
import requests

with requests.Session() as s:
    s.headers.update({                                  # ① set defaults
        "Authorization": "Bearer ghp_xxx",
        "User-Agent": "MyApp/1.0",
        "Accept": "application/json",
    })

    s.get("https://api.github.com/user", timeout=10)     # ② attached automatically
    s.get("https://api.github.com/repos", timeout=10)    #    attached automatically
```

> **Line-by-line**
>
> - **① `s.headers.update(...)`**: modifies the Session's own headers dict. **Note `update`, not assignment** — the Session already ships with `Accept-Encoding`, `User-Agent: python-requests/...`, etc.; assigning directly wipes them all out
> - **② Every subsequent request carries them**

#### Merge Rule: Per-Request Headers Win

This is an easy trap. **Headers passed to a single request are not a "replacement" — they're a "merge"**:

```python
import requests

with requests.Session() as s:
    s.headers.update({"User-Agent": "MyApp/1.0"})

    r = s.get("https://httpbin.org/headers",
              headers={"User-Agent": "Special/2.0"},      # ① temporary override
              timeout=10)
    print(r.json()["headers"]["User-Agent"])   # Special/2.0   ← per-request wins
```

> - **① This request's User-Agent is `Special/2.0`, not `MyApp/1.0`**
>
> **The rule**: requests **merges** the Session headers with the per-request headers into a new dict (per-request wins on conflicts), **then discards that new dict afterwards**, leaving the Session untouched.
>
> So the next request that passes no headers still uses `MyApp/1.0`.

**This "temporary override" behavior is extremely useful** — e.g., most requests use JSON, but the one file upload needs a different Content-Type; just override it on that single request.

### Freebie Three: Default params / auth / More

Nearly anything you can pass to `requests.get()` can be set as a default on the Session:

```python
import requests

with requests.Session() as s:
    s.params.update({"api_key": "xxxx"})        # ① default query params
    s.auth = ("user", "pass")                   # ② default auth (lesson 21)
    s.proxies = {"https": "http://127.0.0.1:7890"}   # ③ proxy

    s.get("https://httpbin.org/get", timeout=10)
```

> - **① `s.params`**: every request's URL automatically gets `?api_key=xxxx`
> - **② `s.auth`**: Basic auth (lesson 21)
> - **③ `s.proxies`**: **all traffic through a proxy** — common on corporate networks

**Note**: `s.params` and per-request `params` **also merge**, same rule as headers.

## The Connection Pool: What's Really Inside a Session

A Session isn't "one connection" — it's **a pool**.

```python
import requests

s = requests.Session()
print(s.adapters)           # ① which adapters are mounted
# {'https://': <requests.adapters.HTTPAdapter object at 0x...>,
#  'http://':  <requests.adapters.HTTPAdapter object at 0x...>}
```

> - **① `s.adapters`** is a dict: **URL prefix → adapter**. Two rules by default: one for `https://`, one for `http://`
>
> **The adapter (HTTPAdapter)** is what actually manages the pool. Lookup is **longest-prefix match** — `https://api.github.com/` beats `https://`.

### Two Key Parameters

```python
from requests.adapters import HTTPAdapter
import requests

s = requests.Session()
adapter = HTTPAdapter(
    pool_connections=10,      # ① number of pools
    pool_maxsize=10,          # ② max connections per pool
    max_retries=0,            # ③ connection-level retries (not lesson 24's mechanism)
)
s.mount("https://", adapter)   # ④ mount it
```

> **Line-by-line**
>
> - **① `pool_connections=10`**: **how many distinct hosts it can remember**. `github.com`, `httpbin.org`, `example.com` each take one. Default 10
> - **② `pool_maxsize=10`**: **max connections kept per host**. Default 10
> - **③ `max_retries=0`**: retries at the connection layer. **Note this is not the same as lesson 24's `urllib3.Retry`** (that's HTTP-layer); this is "retry connecting N times"
> - **④ `s.mount(...)`**: attach the adapter to a URL prefix. **Must be done before any request**

### When the Default of 10 Isn't Enough

**Single-threaded: essentially never.** You can only use one connection at a time.

**Under concurrency, it's not enough** (lesson 29 covers concurrency in depth). With 50 threads sharing one Session:

```
WARNING: Connection pool is full, discarding connection: api.github.com
```

**What it means**: the pool is full, so a connection that finished has **nowhere to go and is discarded** — next time it must be rebuilt.

**The consequence isn't an error, it's silent slowness.** Your concurrent program discards and rebuilds while running, degrading to near "no reuse" performance — and if you only skim the logs you'll see warnings, never failures.

```python
# Correct config for concurrent use
adapter = HTTPAdapter(pool_connections=50, pool_maxsize=50)
s.mount("https://", adapter)
```

**Rule of thumb**: set `pool_maxsize` to **your concurrency level**. 50 threads → 50.

## When Not to Use a Session

Using a Session isn't unconditional. Think twice in these three cases:

### One: You're Sending a Single Request

```python
# requests.get() is perfectly fine here, and one line shorter
r = requests.get("https://api.github.com/user", timeout=10)
```

A Session's value is **reuse**. One request, nothing to reuse, an object built for nothing.

### Two: Sharing One Session Across Threads

**This is where people get burned.** requests' Session is **not strictly thread-safe**.

```python
# ❌ Dangerous: multiple threads sharing one Session
s = requests.Session()
def worker(url):
    return s.get(url)          # several threads mutating the same Session state

# ✅ Correct: one Session per thread
def worker(url):
    with requests.Session() as s:
        return s.get(url)
```

> **Why**: a Session holds **shared mutable state** — cookie jar, connection pool. Concurrent reads/writes can overwrite cookies or hand the same connection to two threads.
>
> **But note**: **one Session per thread loses the reuse benefit** (thread A's connection can't serve thread B). That looks contradictory; in practice the answer is — if you truly need concurrent reuse, go **async** (lesson 29). For multithreading, "one Session per thread" is simple and safe.

### Three: Requests Must Be Fully Isolated

Sometimes you **don't want** cookies or headers carried over:

```python
# Testing user A's permissions — but the Session still holds user B's cookie
s.get(...)   # leftover login state from the previous test
```

**This "flavor bleed" is lethal when writing tests**: tests contaminate each other, showing up as "passes alone, fails together." The fix is a fresh Session per test.

> **Incidentally**: this is the same class of problem as "multiple accounts got mixed up" — **shared mutable state whose scope was wrong**.

## Crash Site

### Crash One: Creating a Session and Never Closing It

```python
# ❌ Wrong
import requests

def fetch_all(urls):
    s = requests.Session()          # created
    results = [s.get(u, timeout=10) for u in urls]
    return results                  # returned, but s is still alive, connections unreleased

# called ten thousand times → ten thousand Sessions, each holding sockets
```

**Symptom**: the program gets slower over time and eventually raises `OSError: [Errno 24] Too many open files`.

**Cause**: each Session's sockets never close; file descriptors exhausted.

**Lesson**: use `with`, or `close()` in `finally`. **This is a chronic bug — fine for minutes, crashes after hours.**

### Crash Two: Treating Session as a Global Singleton

```python
# ❌ Thought: "I'll build one global Session at module import; the whole program reuses it. Cheapest!"
import requests
S = requests.Session()        # module-level global

def a(): return S.get(url1)
def b(): return S.post(url2, json=data)
```

**Symptom**: works fine, but **weird bugs appear the moment threads enter the picture**; also connections stay open until the process exits.

**Cause**: global mutable state + not thread-safe.

**Lesson**: **A Session's scope should match "one batch of related requests," not "the whole program."** 10 requests inside a function → `with` inside the function. An object that keeps requesting → an instance attribute, closed when the object dies.

### Crash Three: Ignoring the Pool-Full Warning

```
WARNING: Connection pool is full, discarding connection: api.github.com
```

**Symptom**: logs flood, but results still come back, so it's ignored.

**Cause**: concurrency exceeds `pool_maxsize`; connections discarded and rebuilt.

**Consequence**: **performance silently degrades**. You may blame the API when it's your own undersized pool.

**Lesson**: see that warning, go raise `pool_maxsize`. **It's a warning, not an error, but its price is "your optimization was for nothing."**

### Crash Four: Mounting After Sending

```python
# ❌ Wrong order
s = requests.Session()
s.get("https://api.github.com/user")          # ① request sent first
adapter = HTTPAdapter(pool_maxsize=50)
s.mount("https://", adapter)                  # ② mount after → no effect on existing connections
```

**Cause**: request ① used the default adapter; its connection is already built and stored in the old pool.

**Lesson**: **`mount` must happen before any request.** A sneaky trap — the code looks "fully configured," but ordering makes it a no-op.

### Crash Five: Assigning to s.headers Directly

```python
# ❌ Wrong: wipes the Session's built-in default headers
s.headers = {"Authorization": "Bearer xxx"}

# ✅ Right: add to what's already there
s.headers.update({"Authorization": "Bearer xxx"})
```

**Symptom**: requests fail for no clear reason, or the server returns a strange format.

**Cause**: the Session ships with `Accept-Encoding: gzip, deflate`, `Accept: */*` and more. Assigning directly erases them, **so the server may skip gzip or not know what format to return**.

**Lesson**: **always `update`, never `=`**.

## Why This Matters for Your Code

This lesson looks like "performance tuning," but three ideas behind it recur everywhere:

**One: Setup often costs more than the work.**

In a single HTTP request, real work is 1 RTT and setup is 2~3. That ratio is everywhere in engineering — opening a DB connection, opening/closing files, spawning processes. **Spotting which costs can be amortized is step one of optimization.**

**Two: Which layer holds state determines complexity.**

Cookies are HTTP-layer state (given by the server); Session is a client-side state container. Session auto-returns "the state the server gave you" — **that's the simplification you get from putting state on the right layer.** Compare with the manual cookie-passing version; the complexity gap is obvious.

**Three: Shared mutable state breeds bugs.**

Session is fast because it **shares** connections; Session breaks under threads also because it **shares**. One feature, a strength in one context, a flaw in another. **The test: can two execution flows mutate this shared thing at once?**

## Summary

- **Cost of one HTTPS request**: DNS(0~1) + TCP(1) + TLS(1~2) + work(1) — **setup dominates**
- **`requests.get()` creates and destroys a Session each time** — it's not that reuse is unsupported, it's use-and-discard
- **Session reuses connections**: pay the tax once, then zero cost, multi-fold speedup
- **Must close**: use `with`, or `finally: s.close()`, or sockets leak
- **Three freebies**: automatic cookies (login state), default headers, default params/auth/proxies
- **headers/params merge, not replace**: per-request overrides win, discarded after use, Session untouched
- **Use `update` on default headers, not `=`**, or you wipe the built-ins
- **Connection pool**: `HTTPAdapter(pool_connections=, pool_maxsize=)`, `s.mount()` **before any request**
- **Pool-full means silent slowness**: on `Connection pool is full`, raise `pool_maxsize` to your concurrency
- **Session isn't thread-safe**: one per thread
- ❌ Don't create without closing; don't make it a global; don't ignore pool-full; don't mount after requesting; don't assign to headers
