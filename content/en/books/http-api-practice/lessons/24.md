# 24 Retries & Backoff: Surviving Network Flakiness

> Lesson 15 gave a naive retry; this lesson does it properly: **what to retry, what not to, how to space attempts, and how to avoid hammering the server.** This is the dividing line between "a script that runs" and "a service that ships".

## First: What Should Be Retried

Recap from Lessons 07 and 15:

| Situation | Retry? | Why |
|---|---|---|
| **Connect timeout / failure** | ✅ | a network hiccup; it may work next time |
| **Read timeout** | ⚠️ carefully | the server may be slow; hammering makes it worse |
| **429 rate limited** | ✅ | the server explicitly says "come back later" |
| **500 / 502 / 503 / 504** | ✅ | transient server fault that may clear |
| **400 / 401 / 403 / 404 / 422** | ❌ | the request itself is wrong; ten thousand tries won't fix it |
| **SSL error** | ❌ | could be a man-in-the-middle attack |

**The core test**:

> **Retry only when "trying again might succeed."**

4xx fails that test — your request is wrong and **it won't become right through repetition**.

## Exponential Backoff: Why Not a Fixed Interval

### The problem with fixed intervals

```python
# ❌ Poor
for i in range(5):
    try:
        return requests.get(url, timeout=10)
    except:
        time.sleep(1)        # always 1 second
```

**Problems**:

1. **The server needs recovery time.** If 1 second isn't enough, all five attempts land while it's still down
2. **Clients synchronise.** If 100 clients all fail and all wait 1 second, they retry **simultaneously** — a **thundering herd** that knocks the server over again right as it recovers
3. **Wasted quota**: for rate limiting, fast retries just get you blocked sooner

### Exponential backoff

```python
wait = base * (2 ** attempt)
```

```
1st failure → wait 1s
2nd failure → wait 2s
3rd failure → wait 4s
4th failure → wait 8s
```

**Benefits**:

- **gives the server progressively more recovery time**
- **retries thin out**, so pressure doesn't persist
- after a few attempts it effectively gives up instead of harassing forever

### It must be capped

```python
wait = min(base * (2 ** attempt), cap)
```

**What happens uncapped**? The 20th retry waits `2^20 = 1048576` seconds ≈ **12 days**. The program just hangs.

**Suggested cap = 60 seconds.**

## Jitter: Solving the Thundering Herd

**Exponential backoff still has a flaw**: 100 clients failing at the same moment share **identical** backoff rhythm — 1s, 2s, 4s, 8s… so they retry **at the same instant**.

**That's the thundering herd.**

**Fix**: **add randomness to the wait.**

```python
import random
import time

def backoff_with_jitter(attempt, base=1, cap=60):
    """Exponential backoff + jitter"""
    delay = min(base * (2 ** attempt), cap)      # ① exponential part
    jitter = random.uniform(0, delay * 0.1)      # ② up to 10% extra randomness
    return delay + jitter

# Or the more common approach: random within [0, delay]
def backoff_full_jitter(attempt, base=1, cap=60):
    """Full Jitter (AWS recommended)"""
    delay = min(base * (2 ** attempt), cap)
    return random.uniform(0, delay)              # ③ fully random
```

> **Line-by-line**
>
> - **①** standard exponential backoff
> - **② Additive jitter**: a bit of randomness on top (up to 10%)
> - **③ Full Jitter**: random across `[0, delay]`. **AWS's official blog recommends this** — it spreads retries most evenly
>
> **Full Jitter's effect**: average wait halves versus fixed backoff, but **retries are thoroughly scattered**, greatly reducing peak server load

**Remember**: **fixed backoff + jitter = correct retry.**

## Respect Retry-After

**When the server tells you how long to wait, wait that long.**

```python
import requests
import time

r = requests.get(url, timeout=10)

if r.status_code == 429:
    retry_after = r.headers.get("Retry-After")

    if retry_after is not None:
        try:
            wait = int(retry_after)               # ① usually seconds
        except ValueError:
            wait = 60                             # ② may be an HTTP date; simplified
        print(f"server asks us to wait {wait}s")
        time.sleep(wait)
```

> **Line-by-line**
>
> - **①** `Retry-After` is usually **seconds**
> - **②** the spec also allows an HTTP date (e.g. `Wed, 21 Oct 2026 07:28:00 GMT`). **Simplified: if unparseable, wait 60s**
>
> **Why honour it**: the server knows better than you when it'll recover. **Ignoring it and hammering only gets you blocked longer**

## A Complete Retry Implementation

Putting it together:

```python
import requests
import time
import random
import logging

# ① which status codes are retryable
RETRY_STATUS = {429, 500, 502, 503, 504}

# ② which exceptions are retryable
RETRY_EXCEPTIONS = (
    requests.exceptions.ConnectTimeout,
    requests.exceptions.ReadTimeout,
    requests.exceptions.ConnectionError,
)

def fetch_with_retry(url, tries=4, timeout=10, base=1, cap=60, **kwargs):
    """GET with exponential backoff and jitter"""
    last_error = None

    for attempt in range(tries):
        try:
            r = requests.get(url, timeout=timeout, **kwargs)

            # ③ status decides whether to retry
            if r.status_code in RETRY_STATUS:
                last_error = f"HTTP {r.status_code}"

                # ④ prefer the server's Retry-After
                wait = None
                ra = r.headers.get("Retry-After")
                if ra:
                    try:
                        wait = int(ra)
                    except ValueError:
                        wait = None

                if wait is None:                      # ⑤ otherwise compute it
                    wait = min(base * (2 ** attempt), cap)
                    wait = random.uniform(0, wait)     #    Full Jitter
            else:
                return r                              # ⑥ no retry needed, return

        except RETRY_EXCEPTIONS as e:                 # ⑦ network errors
            last_error = str(e)
            wait = min(base * (2 ** attempt), cap)
            wait = random.uniform(0, wait)

        # ⑧ don't wait after the last attempt
        if attempt == tries - 1:
            break

        logging.warning(f"attempt {attempt+1}/{tries} failed ({last_error}), waiting {wait:.1f}s")
        time.sleep(wait)

    raise RuntimeError(f"failed after {tries} attempts: {last_error}")
```

> **Line-by-line**
>
> - **①** Retryable status set. **A set, not a list** — faster lookup and clearer intent
> - **②** Retryable exception tuple. **Note SSLError is excluded**
> - **③** **Check status first.** Anything outside the set returns immediately (including 4xx — no retry)
> - **④** **Honour `Retry-After` first**
> - **⑤** Otherwise exponential backoff + Full Jitter
> - **⑥** Success (or a non-retryable error) **returns at once**
> - **⑦** Network errors take the other branch
> - **⑧** **Don't wait after the final attempt** — pointless; raise instead
>
> **Key point**: **raise at the end rather than returning None.** Lesson 15: silently returning None makes the caller think it worked.

## Using urllib3's Retry (Recommended)

`requests` is built on `urllib3`, which **has retry machinery built in** — more complete than hand-rolling:

```python
import requests
from requests.adapters import HTTPAdapter
from urllib3.util.retry import Retry

# ① configure the retry policy
retry = Retry(
    total=3,                      # at most 3 retries
    backoff_factor=1,             # ② wait = factor * (2 ** (retry_number-1))
    status_forcelist=[429, 500, 502, 503, 504],   # ③ which statuses retry
    allowed_methods=["GET", "HEAD"],              # ④ only safe methods
    respect_retry_after_header=True,              # ⑤ honour Retry-After
    raise_on_status=False,                        # ⑥ return the response when exhausted
)

# ⑦ mount on a Session
s = requests.Session()
s.mount("https://", HTTPAdapter(max_retries=retry))
s.mount("http://", HTTPAdapter(max_retries=retry))

r = s.get("https://api.github.com/user", timeout=10)
```

> **Line-by-line**
>
> - **① `Retry(...)`** is urllib3's policy object
> - **② `backoff_factor=1`**: wait = `1 * (2 ** (n-1))` → 0s, 1s, 2s, 4s (**no wait before the first retry**). **It includes jitter**
> - **③** retry only these statuses. **4xx isn't included**
> - **④ `allowed_methods`**: **retry only idempotent methods!** Critical — **POST must not auto-retry** (duplicate orders). Lesson 06's idempotency pays off here
> - **⑤** honour `Retry-After`
> - **⑥ `raise_on_status=False`**: when retries are exhausted **return the last response** rather than raising, so you handle it
> - **⑦ `s.mount()`** attaches the adapter. **Note both http and https need mounting**
>
> **This is the recommended production approach.** Well-tested and more reliable than hand-written code.

### urllib3's wait times

```
with backoff_factor = 1:
before 1st retry: 0s
before 2nd retry: 2s (1 * 2^1)
before 3rd retry: 4s (1 * 2^2)
```

**Formula**: `backoff_factor * (2 ** (retry_count - 1))`

**Note**: **urllib3's count excludes the initial request.** `total=3` means "at most 3 retries", i.e. **at most 4 requests**.

## Idempotency: Can POST Be Retried?

**Lesson 06's core idea cashes out here**:

| Method | Idempotent | Auto-retry? |
|---|---|---|
| GET | ✅ | ✅ **yes** |
| HEAD | ✅ | ✅ **yes** |
| PUT | ✅ | ✅ yes (but beware concurrency) |
| DELETE | ✅ | ✅ yes |
| **POST** | ❌ | ❌ **shouldn't by default** |
| PATCH | ❌ not guaranteed | ❌ shouldn't by default |

**Why POST can't auto-retry**:

```
POST /orders  → create an order
it times out; you don't know whether the order exists
retry → possibly two orders
```

### If you must retry POST

**Option one: an idempotency key** (Lesson 06)

```python
import uuid

key = str(uuid.uuid4())
for attempt in range(3):
    r = requests.post(url, json=data,
                      headers={"Idempotency-Key": key},   # same key
                      timeout=10)
    if r.ok:
        break
```

**Option two: query first, then decide**

```python
# After a timeout, check whether the order was created
r = requests.get(f"{url}?order_ref={ref}", timeout=10)
if r.json()["exists"]:
    print("it actually succeeded already")
else:
    requests.post(url, json=data, timeout=10)      # retry only if absent
```

**Note**: **option two has a race condition** (another request may slip in between check and create). **The idempotency key is the correct approach** — but it needs server support.

## Global vs Per-Call

**Prefer Session level** (Lesson 26 covers Sessions in depth):

```python
s = requests.Session()
adapter = HTTPAdapter(max_retries=retry)
s.mount("https://", adapter)
s.mount("http://", adapter)

# every request now retries
```

**Benefits**:
- configure once, applies everywhere
- reuses the connection pool automatically (Lesson 26)
- no per-call parameters

## Crash Site

### Crash 1: retrying 4xx

```python
# ❌ Wrong
retry = Retry(total=3, status_forcelist=[400, 401, 403, 404, 500])
```

**Symptom**: parameters are wrong; three retries all return 400; you burn three requests and several seconds.

**Worse**: a 403 retry. Insufficient permission — ten thousand retries won't help.

**Lesson**: **`status_forcelist` gets only 429 and 5xx.**

### Crash 2: auto-retrying POST

```python
# ❌ Dangerous (if allowed_methods includes POST)
retry = Retry(total=3, allowed_methods=["GET", "POST"])
```

**Symptom**: the order endpoint times out, auto-retries, and the user gets two orders charged twice.

**Cause**: POST isn't idempotent.

**Lesson**: **`allowed_methods` takes only idempotent methods.** urllib3's default already does this — **don't change it**.

### Crash 3: uncapped backoff

```python
# ❌ Wrong
wait = 2 ** attempt        # no cap
```

**Symptom**: by attempt fifteen or twenty the wait is hours or days. The program appears frozen.

**Lesson**: **always `min(..., cap)`.**

### Crash 4: miscounting retries

```python
retry = Retry(total=3)
```

**You think**: at most 3 requests.
**Actually**: **at most 4** (initial + 3 retries).

**Why it matters**: with a strict quota, **this off-by-one busts your budget**.

**Lesson**: **`total` is retries, excluding the initial request.**

## Why This Matters for Your Code

1. **Never retry 4xx** — the single most important rule
2. **Exponential backoff + jitter** is standard; fixed intervals cause thundering herds
3. **Honour `Retry-After`** — the server knows better
4. **Don't retry POST by default**, unless you have an idempotency key
5. **Use urllib3's `Retry`** rather than hand-rolling (unless you have special needs)
6. **Always cap**, or wait times explode
7. **`total` excludes the initial request** — count it when budgeting

## Summary

- **Retryable**: connect failures/timeouts, 429, 5xx. **Not retryable**: 4xx, SSL errors
- **Exponential backoff** `base * 2^n` **gives the server recovery time**
- **Cap it** (cap=60) or wait times explode
- **Add jitter** against thundering herds; **Full Jitter** (`uniform(0, delay)`) is AWS's recommendation
- **Honour the `Retry-After` header**
- **urllib3's `Retry`** is production-grade: `total` / `backoff_factor` / `status_forcelist` / `allowed_methods`
- **`allowed_methods` holds only idempotent methods** — no POST (unless an idempotency key exists)
- **`total` excludes the initial request** (total=3 → at most 4 requests)
- **Raise when retries are exhausted**, don't return None silently
- ❌ Don't retry 4xx; don't auto-retry POST; don't forget the cap
