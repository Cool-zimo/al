# 15 Timeouts & Errors: Let the Program Survive

> Lesson 11 said "every request needs a timeout." This lesson finishes that thought — what happens after a timeout — and lays out `requests`' whole exception hierarchy: which exceptions to retry, which to fail on immediately, and how to catch without missing any.

## What Happens After a Timeout

```python
import requests

try:
    r = requests.get("https://httpbin.org/delay/20", timeout=3)
except requests.exceptions.Timeout:
    print("timed out")
```

`httpbin.org/delay/20` **deliberately waits 20 seconds** before responding. We set a 3-second timeout, so after 3 seconds a `Timeout` exception is raised.

**Note**: **a timeout raises an exception; it doesn't return None.** Without catching it, your program crashes out.

## requests' Exception Hierarchy

Every `requests` exception inherits from `RequestException`:

```
RequestException                    ← ancestor of all requests exceptions
├── Timeout                         ← timed out
│   ├── ConnectTimeout              ← connect phase timed out (TCP handshake未完成)
│   └── ReadTimeout                 ← connected, but reading data timed out
├── ConnectionError                 ← connection failed
│   ├── ProxyError                  ← proxy problem
│   └── SSLError                    ← SSL/TLS certificate problem
├── HTTPError                       ← raised by raise_for_status() (4xx/5xx)
├── TooManyRedirects                ← too many redirects
├── URLRequired / MissingSchema     ← invalid URL (e.g. forgot https://)
└── InvalidURL / InvalidHeader      ← malformed URL or header
```

**This tree determines catch order.**

### Why order matters

```python
# ❌ Wrong order
try:
    r = requests.get(url, timeout=10)
except requests.exceptions.RequestException:      # parent first!
    print("something went wrong")                  # everything lands here
except requests.exceptions.Timeout:               # never reached
    print("timed out")
```

**Python matches `except` clauses top-down and stops at the first match.** Since `Timeout` is a subclass of `RequestException`, the parent **swallows every subclass**, and the later branches never run.

```python
# ✅ Right order: subclass first, parent last
try:
    r = requests.get(url, timeout=10)
except requests.exceptions.Timeout:
    print("timed out")
except requests.exceptions.ConnectionError:
    print("can't connect")
except requests.exceptions.RequestException as e:
    print(f"other error: {e}")
```

**Rule of thumb**: **specific first, general last.**

## What to Do About Each Exception

The most valuable part of this lesson — **different exceptions need completely different strategies**:

| Exception | Meaning | Retry? | What to do |
|---|---|---|---|
| `ConnectTimeout` | couldn't connect (no TCP within the limit) | ✅ yes | wait, then retry |
| `ReadTimeout` | connected but the server is slow | ⚠️ carefully | server may be overloaded; don't hammer it |
| `ConnectionError` | DNS failure / connection refused | ✅ yes | check the network, retry |
| `SSLError` | certificate problem | ❌ no | **don't ignore it** — could be a MITM attack |
| `HTTPError` (4xx) | your request is wrong | ❌ no | fix your code |
| `HTTPError` (5xx) | server error | ✅ yes | back off, then retry |
| `TooManyRedirects` | redirect loop | ❌ no | the URL is broken |
| `MissingSchema` | no scheme in URL | ❌ no | fix the code; add `https://` |

**Core judgement**:

> **Network-layer errors (can't connect, timeout) are retryable; application-layer errors (4xx) are not.**

## The Two Phases of timeout

Mentioned in Lesson 11; expanded here:

```python
requests.get(url, timeout=(3.05, 27))
#                         ↑     ↑
#                   connect timeout  read timeout
```

**The difference**:

```
[connect phase]  DNS → TCP handshake → TLS handshake  ← governed by connect timeout
[read phase]     send request → server processes → receive response ← governed by read timeout
```

### When to split them

**Scenario**: you call an API that sometimes computes for 30 seconds, but the network itself is fast.

```python
# 3s is plenty to connect (good network), but processing may take 30s
requests.get(url, timeout=(3, 30))
```

With a single `timeout=30`, even "the server is simply down" costs you 30 seconds. **Split them and you know in 3 seconds.**

### A common misunderstanding

> **A read timeout isn't "27 seconds total" — it's "at most 27 seconds between two chunks of data."**

So if the server dribbles a little data every 20 seconds (a streaming response), **you could wait forever**.

**Not a bug** — it's what allows streaming. If you need a hard total limit, implement it yourself; Lesson 24 approaches it differently.

## The Complete Error-Handling Template

The skeleton you'll reuse constantly. **Worth memorising**:

```python
import requests
import logging

def fetch(url, timeout=10):
    """Send a GET request, handling everything that can go wrong"""
    try:
        r = requests.get(url, timeout=timeout)

    except requests.exceptions.ConnectTimeout:
        # ① couldn't connect: network trouble or the other side is down
        logging.warning(f"connect timeout: {url}")
        return None

    except requests.exceptions.ReadTimeout:
        # ② connected but no response: the other side is slow
        logging.warning(f"read timeout: {url}")
        return None

    except requests.exceptions.SSLError as e:
        # ③ certificate problem: don't ignore!
        logging.error(f"SSL error: {url} -> {e}")
        return None

    except requests.exceptions.ConnectionError as e:
        # ④ other connection issues: DNS failure, refused
        logging.warning(f"connection failed: {url} -> {e}")
        return None

    except requests.exceptions.TooManyRedirects:
        # ⑤ redirect loop
        logging.error(f"too many redirects: {url}")
        return None

    except requests.exceptions.RequestException as e:
        # ⑥ catch-all: any requests error we didn't anticipate
        logging.error(f"request exception: {url} -> {e}")
        return None

    # ⑦ if we get here, the request went out and a response came back
    try:
        r.raise_for_status()          # 4xx/5xx become exceptions here
    except requests.exceptions.HTTPError as e:
        logging.error(f"HTTP {r.status_code}: {url}")
        return None

    # ⑧ passed everything
    return r
```

> **Line-by-line**
>
> - **①②③④⑤⑥** Six `except` clauses, specific to general. **Note `RequestException` catches the rest at the end**
> - **`logging`, not `print`**: production code logs. It has levels (warning/error), can write to files, and can be turned off. `print` does none of that
> - **Return `None` rather than raising**: let the caller decide. The caller writes `if data is None: ...`
> - **⑦ `raise_for_status()` sits separately afterwards**: it can only be judged once a response arrived. **Outside the first `try` because it's a different phase of failure**
> - **⑧** Only returns the response when everything passed

**Usage**:

```python
r = fetch("https://api.github.com/user")
if r is None:
    print("failed, skipping")
else:
    print(r.json())
```

## Logging: Why Not print

This is the dividing line between "writing a script" and "writing a project":

```python
# Script level
print("something went wrong")

# Project level
import logging
logging.basicConfig(level=logging.INFO)
logging.warning("connect timeout: %s", url)
```

**Why `logging` wins**:

1. **Levels**: `debug` / `info` / `warning` / `error` / `critical`. In production you can show errors only
2. **Automatic time and location**: one config line gives `[2026-10-21 10:30:15] WARNING connect timeout`
3. **Can write to a file**: `logging.basicConfig(filename="app.log")`
4. **Toggle without code changes**: change one level parameter

**Cost**: two extra config lines. For anything over 200 lines, entirely worth it.

## TooManyRedirects: Redirect Loops

```python
# Follows up to 30 redirects by default
r = requests.get("https://httpbin.org/redirect/10", timeout=10)   # OK

# More than 30
r = requests.get("https://httpbin.org/redirect/50", timeout=10)
# requests.exceptions.TooManyRedirects: Exceeded 30 redirects
```

**Real-world cases**:

- **Cookie misconfiguration**: the server redirects you to login because you have no cookie; login redirects back → **infinite loop**
- **Broken URL rules**: A redirects to B, B redirects to A

**You can set your own cap**:

```python
s = requests.Session()
s.max_redirects = 5          # follow at most 5

r = s.get(url, timeout=10)
```

**Why 30 is too many by default**: each redirect is a full round trip. Thirty means enormous latency. **Set it lower in production.**

## SSLError: Never Ignore It

```python
import requests

r = requests.get("https://self-signed.example.com", timeout=10)
# requests.exceptions.SSLError: certificate verify failed
```

**The most common "fix" found online**:

```python
# ❌❌❌ Dangerous
r = requests.get(url, verify=False, timeout=10)
```

**What that does**: **disables certificate verification.** Meaning:

- You no longer confirm the other side is really who it claims
- **Man-in-the-middle attacks succeed**: an attacker forges a certificate and you connect anyway
- `requests` prints warnings but **connects regardless**

**When `verify=False` is acceptable**:

- local development against a self-signed test service
- **with full awareness of the risk**

**The right fix**: for a corporate intranet with a self-signed CA, add that CA:

```python
r = requests.get(url, verify="/path/to/company-ca.pem", timeout=10)
```

That way you're **still verifying**, just trusting a CA you named.

## A Simple Retry (Full Version in Lesson 24)

```python
import requests
import time

def fetch_with_retry(url, tries=3, timeout=10):
    """Retry a few times on failure"""
    for i in range(tries):
        try:
            r = requests.get(url, timeout=timeout)
            r.raise_for_status()
            return r                            # ① return on success
        except requests.exceptions.RequestException as e:
            if i == tries - 1:                  # ② last attempt also failed
                raise                            #    re-raise, stop trying
            wait = 2 ** i                        # ③ backoff: 1s, 2s, 4s
            print(f"attempt {i+1} failed, retrying in {wait}s: {e}")
            time.sleep(wait)
```

> **Line-by-line**
>
> - **①** Return immediately on success; stop looping
> - **②** **On the final failure, re-raise** rather than returning None silently. Otherwise the caller thinks it worked
> - **③** `2 ** i` is **exponential backoff**: 1s, then 2s, then 4s. **Gives the server time to recover and keeps you out of their blocklist**
>
> **Limitation**: it retries **every** exception, including 4xx. Lesson 24 does it properly (retry only network errors and 5xx).

## Crash Site

### Crash 1: except clauses in the wrong order

```python
# ❌ Wrong
try:
    r = requests.get(url, timeout=10)
except Exception:                    # most general first
    print("error")
except requests.exceptions.Timeout:  # never runs
    print("timeout")
```

**Symptom**: on timeout it prints "error"; you never learn whether it was a timeout or something else.

**Cause**: `Exception` is the parent of everything and swallows all.

**Lesson**: **specific before general.** And **never use a bare `except Exception`** — it swallows `KeyboardInterrupt` (Ctrl+C) too.

### Crash 2: catching and doing nothing

```python
# ❌ The worst
try:
    r = requests.get(url, timeout=10)
    return r.json()
except:
    pass            # silently swallow everything
```

**Symptom**: the program runs "fine" but accomplishes nothing. You spend a day wondering why the data is empty.

**Cause**: **`except: pass` destroys all error information.**

**Lesson**: **never write an empty `except`.** At minimum `logging.error(...)`. If you truly must ignore one specific error, **catch only that one** and comment why.

### Crash 3: assuming retry fixes everything

```python
# ❌ Retrying a 400 too
for i in range(5):
    r = requests.post(url, json={"bad": "data"}, timeout=10)
    if r.ok:
        break
```

**Symptom**: the parameters are wrong; five retries all return 400; you burn five requests and five seconds.

**Cause**: Lesson 07 — **4xx means your request is wrong; ten thousand resends stay wrong.**

**Lesson**: **retry only network errors and 5xx.** Lesson 24 implements it correctly.

## Why This Matters for Your Code

1. **Uncaught exception = crash.** Network failure is normal, not exceptional
2. **`except` specific → general**; a parent first swallows children
3. **Different exceptions, different strategies**: can't-connect is retryable; 4xx needs a code fix; SSL errors must not be ignored
4. **`raise_for_status()` goes after a response arrives** — it's a different phase
5. **Use `logging`, not `print`** — the script/project dividing line
6. **Never `except: pass`** — that's destroying evidence with your own hands
7. **Back off when retrying**, and retry only retryable errors

## Summary

- **A timeout raises, it doesn't return None.** Uncaught means a crash
- **Exception tree**: `RequestException` is the ancestor, with `Timeout`, `ConnectionError`, `HTTPError` beneath
- **`except` must go specific → general**, or the parent eats the children
- **`timeout=(3, 27)`** sets connect and read timeouts separately
- **A read timeout is "the gap between chunks"**, not the total duration
- **`ConnectTimeout` / `ConnectionError` are retryable; `SSLError` / 4xx are not**
- **`raise_for_status()` turns 4xx/5xx into `HTTPError`**
- **`TooManyRedirects`** usually means bad cookies or URL rules
- **`verify=False` disables certificate verification and is a security risk** — local development only
- **Use `logging`, not `print`**; **never write `except: pass`**
