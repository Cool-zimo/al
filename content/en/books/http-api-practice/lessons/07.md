# 07 The Philosophy of Status Codes: Why Not Just Return 200 With "not found"?

> Almost everyone learning APIs asks this: if a resource is missing, why not return 200 with `{"error": "not found"}` in the body? Why invent a whole 404? This lesson answers that, and walks through the dozen-plus status codes you'll actually use — including the pair people mix up most: 401 and 403.

## Status Codes Are For Programs, Not Humans

Start with the conclusion, because it's the key to all of it:

> **The single purpose of HTTP status codes is to let a client program classify the outcome without reading the response body.**

Picture a caching server. It gets a response and must decide, in microseconds: can I cache this?

- **200**: yes
- **404**: yes, briefly
- **500**: absolutely not

When it makes that call, **it never reads your JSON**. It looks at three digits in the status line.

If your API returns 200 for everything, then:

- Caches will **store your error responses** and serve "not found" to every user for the next half hour
- Browsers won't know whether to retry
- Monitoring shows **0% error rate** forever, until users complain and you discover the service died hours ago
- Load balancers won't know to pull a broken machine out of rotation

**That's why status codes aren't optional.** They aren't human-readable hints — they're the **semantic layer of the protocol**, the thing that lets every program on the path that doesn't know you behave correctly.

## The Structure of Three Digits

Status codes are three decimal digits. **The first digit sets the class**:

| First | Class | In one line | Who acts |
|---|---|---|---|
| **1xx** | Informational | Got it, continue | client keeps sending |
| **2xx** | Success | Here's your thing | client processes the response |
| **3xx** | Redirection | Look elsewhere | client follows automatically |
| **4xx** | Client Error | Your request is wrong | client fixes the request |
| **5xx** | Server Error | I broke | retry may help |

**The last two digits are the specific code within the class.** The spec defines the common ones and leaves the rest for you to extend (many companies use unused 4xx numbers for domain-specific errors — that's allowed).

A memory trick: **"4 means you're wrong, 5 means I'm wrong."** This distinction matters enormously because it decides **who has to fix it**:

```
4xx → your request is malformed; fix your code; retrying is pointless
5xx → the server had a problem; retrying may work
```

## 1xx: I'm Still Listening

1xx are provisional responses: request received, still processing.

The important one is **100 Continue**:

When a client wants to send a very large body, it can send headers first with:

```text
Expect: 100-continue
```

The server glances at the headers, and if they look fine (auth checks out, say), replies `100 Continue` — only then does the client push up several gigabytes. **If the server instead replies 417 (Expectation Failed) or 401, the client never wasted the upload.**

**You'll rarely see 1xx in everyday Python**, because `requests` handles it. But know it exists, or a `100` in a packet capture will look like an error.

You *have* seen **101 Switching Protocols** — that's what establishes a **WebSocket**. The client says "I'd like to upgrade to WebSocket," the server says `101`, and from then on neither side speaks HTTP.

## 2xx: It Worked

### 200 OK

The most common success. **Note: 200 means "the request was processed successfully", not "you got what you wanted."**

That sounds like a tautology, but it's the biggest beginner trap. Look:

```python
r = requests.get("https://api.example.com/user", timeout=10)
print(r.status_code)      # 200
print(r.json())           # {"error": "invalid token"} ← also 200!
```

Some poorly designed APIs return 200 even on auth failure. **So always check status first — but don't check status only.**

### 201 Created

**A new resource was created.** The difference from 200 is semantic: a successful `POST /users` should return **201**, not 200.

The spec also says a 201 should carry a **`Location` header** pointing at the new resource:

```text
HTTP/1.1 201 Created
Location: /users/456
```

### 202 Accepted

**Got it, but not finished yet.** Typical case: you submit a long-running task (transcode a video, generate a report) and the server won't make you wait — it returns 202 plus a job ID to poll.

Very common in async APIs.

### 204 No Content

**Success, but no body.**

DELETE usually returns 204. The difference from 200: **a 204 body must be empty**, and browsers shouldn't navigate away.

```python
r = requests.delete(url, timeout=10)
if r.status_code == 204:
    print("Deleted successfully, no content returned")
print(r.content)          # b"" — always empty
```

**One trap with 204**: `r.json()` raises, because there's nothing to parse. **So test `== 204` for deletes; don't blindly call `.json()`.**

## 3xx: Go Elsewhere

### 301 vs 302: Permanent vs Temporary

The difference directly affects **whether the browser caches the redirect**:

| | Meaning | Cache the redirect? | SEO |
|---|---|---|---|
| **301** | Moved permanently | ✅ remember it; go straight to the new URL | link equity moves to new URL |
| **302** | Go there for now | ❌ ask again each time | equity stays with the original |

**Practical impact**: migrating a site from HTTP to HTTPS — use 301, and on the second visit users jump straight to HTTPS. Use 302, and every visit pays an extra round trip through HTTP, with added hijacking risk.

### 304 Not Modified: The Bandwidth Saver

This one is special — **not an error, but a kind of "you already have the latest" success**.

The flow:

1. Browser requests the first time; server returns the resource plus an **`ETag`** (a fingerprint, e.g. a hash of the content)
2. Browser caches it
3. On the next request, the browser sends `If-None-Match: <previous ETag>`
4. Server compares: fingerprint unchanged → returns **304** with **no body**
5. Browser sees 304 and uses its local cache

**The entire response body is skipped** — just a tiny header round trip. This is one of the foundations of web performance.

```python
import requests

r1 = requests.get("https://api.github.com/user", timeout=10)
etag = r1.headers.get("ETag")           # ① grab the fingerprint

r2 = requests.get(                       # ② request again, sending the fingerprint
    "https://api.github.com/user",
    headers={"If-None-Match": etag},     #    "I have this version"
    timeout=10,
)

print(r2.status_code)                    # ③ either 200 (changed) or 304 (same)
if r2.status_code == 304:
    print("Unchanged — use the cache, saved the whole body")
```

> **Line-by-line**
>
> - **①** `ETag` is the server's fingerprint for this resource. Not mandatory, but mainstream services send it
> - **②** `If-None-Match` is a **conditional request header**. It means "only send me the body if the fingerprint isn't this one"
> - **③** **Critical**: with a 304, `r2.text` is empty. **You must check the status before touching the body** — otherwise you'll read an empty string and think the content went blank

## 4xx: You're Wrong

### 400 Bad Request

Something is wrong with the request itself: malformed JSON, missing parameter, wrong field type.

**This is "I can't parse what you said."**

### 401 Unauthorized vs 403 Forbidden: The Most Confusing Pair

The single most muddled pair in all of HTTP, worth unpacking alone:

| | 401 | 403 |
|---|---|---|
| Literal | Unauthorized | Forbidden |
| **Real meaning** | **You haven't proven who you are** | **I know who you are, and you're not allowed** |
| Analogy | Building requires a badge; you don't have one | You badged in, but as a visitor you can't enter the server room |
| What to do | Go authenticate; send a token | **Stop retrying**; switch accounts or request access |
| Should include | `WWW-Authenticate` header | nothing |

**Mnemonic**:
- **401 = no ID** (the name "Unauthorized" is unfortunate — it really means **unauthenticated**)
- **403 = ID presented, clearance insufficient**

Why it matters practically: **401 can succeed on retry with a token; 403 will fail ten thousand more times.** So never write auto-retry for 403.

### 404 Not Found

The resource doesn't exist.

**A classic design debate**: user A requests user B's private resource — should that be 404 or 403?

From an information-leak standpoint, **404**: returning 403 confirms "a resource with this ID exists," enabling enumeration. **404 means not acknowledging its existence.** This is standard security practice.

### 405 Method Not Allowed

The method isn't supported — e.g. PUT against a read-only resource.

The spec requires this response to carry an **`Allow` header** listing what *is* permitted:

```text
HTTP/1.1 405 Method Not Allowed
Allow: GET, HEAD
```

### 409 Conflict

**The request is fine, but conflicts with current server state.** Classic: creating a username that already exists.

The difference from 400: **400 is "I can't understand you"; 409 is "I understand, but doing this now would clash."**

### 418 I'm a teapot

An **officially specified joke**. From RFC 2324 (Hyper Text Coffee Pot Control Protocol, published 1 April 1998):

```text
418 I'm a teapot
```

Meaning "the server refuses to brew coffee with a teapot." An April Fools RFC that stuck around. **Some services genuinely use it for "I decline to process this."**

Why know it: **when you see 418 in logs, don't assume your framework is broken.**

### 429 Too Many Requests

**Rate limited.** You're calling too often.

Crucially it **should come with a `Retry-After` header** telling you how long to wait:

```python
import requests
import time

r = requests.get("https://api.github.com/rate_limit", timeout=10)

if r.status_code == 429:                      # ① rate limited
    wait = int(r.headers.get("Retry-After", 60))  # ② how long the server says to wait
    print(f"Rate limited, waiting {wait}s")
    time.sleep(wait)                            # ③ actually wait
    r = requests.get("https://api.github.com/rate_limit", timeout=10)
```

> **Line-by-line**
>
> - **①** Check 429 explicitly. Without it you'd treat an error response as normal data
> - **②** `Retry-After` is in **seconds** (sometimes an HTTP date, but seconds is typical). The `60` is a **fallback**: if the header is missing, wait a minute
> - **③** `time.sleep()` **blocks the whole program**. Fine for a script; in a web service it freezes everything — that needs the async approach (Lesson 29)

**429 is the only error that explicitly says "come back later"**, so it's the retryable one.

## 5xx: I'm Wrong

### 500 Internal Server Error

Server code threw an exception. **For you it means: probably not your fault.**

### 502 vs 503 vs 504: Three Kinds of "Server Down"

Easy to mix up, but the differences are practical:

| | Name | Who's broken | Typical scenario |
|---|---|---|---|
| **502** | Bad Gateway | **Gateway/proxy** got an invalid response from upstream | The Python process behind Nginx died |
| **503** | Service Unavailable | **Server is overloaded or under maintenance** | Traffic spike, restarting |
| **504** | Gateway Timeout | **Gateway timed out waiting on upstream** | Backend query ran 60s without finishing |

**What it means for your code**:

- **502 / 504**: backend trouble — **retry later**
- **503**: depends. Maintenance → wait for `Retry-After`. Overload → retrying makes it worse (**back off instead; Lesson 24**)

## Code: Status Codes in requests

```python
import requests

r = requests.get("https://api.github.com/user", timeout=10)

print(r.status_code)        # ① an int: 200, 404, 500…
print(r.reason)             # ② text: "OK", "Not Found"
print(r.ok)                 # ③ bool: True when status < 400

r.raise_for_status()        # ④ raises on 4xx/5xx, does nothing on 2xx/3xx
```

> **Line-by-line**
>
> - **①** `status_code` is an **integer**, not a string. `r.status_code == "200"` is always False — a very common rookie slip
> - **②** `reason` is the human-readable text from the status line. **Never branch on it** (wording varies by server)
> - **③** `r.ok` means `r.status_code < 400`. Note **3xx counts as ok** (redirects aren't errors). Handiest quick check
> - **④** `raise_for_status()` raises `requests.exceptions.HTTPError`. **On 2xx/3xx it returns None silently** — safe to drop after any request

**The value of `raise_for_status()`**: you don't have to write a dozen `if status == ...`. One line covers "anything not 2xx/3xx is an exception."

The idiomatic pairing:

```python
import requests

try:
    r = requests.get("https://api.example.com/data", timeout=10)
    r.raise_for_status()                  # ① 4xx/5xx become exceptions here
    data = r.json()                       # ② only reached if ① passed
except requests.exceptions.HTTPError as e:
    print(f"HTTP error: {e}")               # ③ handle
except requests.exceptions.Timeout:
    print("Timed out")
```

> **Line-by-line**
>
> - **①** Place it after the request, before parsing. **Order matters** — confirm the response is sane, then parse
> - **②** Only runs if ① passed. You'll never call `.json()` on an HTML error page
> - **③** `HTTPError` covers only 4xx/5xx. **Network problems are different exception types**, so you also need `Timeout` and `ConnectionError`

**Lesson 24 expands this**: here we catch two; real systems also need retry logic.

## Crash Site

### Crash 1: checking only for 200

```python
# ❌ Wrong
r = requests.get(url, timeout=10)
if r.status_code == 200:
    return r.json()
# everything else silently returns None
```

**Symptom**: the server returns 201 (created) or 204 (deleted) and your code treats it as failure, quietly returning `None`. The caller carries on with `None` and crashes several steps later, far from the real cause.

**Cause**: **there are seven or eight 2xx codes**, not just 200.

**Lesson**: test success with `r.ok` (i.e. < 400), not `== 200`.

### Crash 2: retrying a 403 over and over

```python
# ❌ Wrong
for i in range(5):                    # retry 5 times
    r = requests.get(url, timeout=10)
    if r.ok:
        break
    time.sleep(1)
```

**Symptom**: insufficient permissions (403) or bad parameters (400) — five retries produce the same error, burn five seconds, and eat your rate limit.

**Cause**: **4xx is not retryable**. Send it ten thousand times and the request is still wrong.

**Lesson**: **retrying only makes sense for 5xx and 429.** For 4xx, fail fast and surface the error.

## Why This Matters for Your Code

1. **Status codes are protocol layer, not application layer.** Every middleware that doesn't know you (cache, load balancer, monitoring, CDN) relies on them. Returning 200 + an error field in the body blinds the entire chain
2. **The first digit says who fixes it**: 4xx → your code; 5xx → the backend
3. **The 401/403 difference decides retry**: 401 add a token and retry; 403 give up
4. **429 is the only "friendly" error** — it tells you how long to wait. Always honour `Retry-After`
5. **`raise_for_status()` is your default** unless you have a specific reason to handle each code manually

## Summary

- Status codes are **read by programs** so results can be classified without parsing the body. **Returning 200 for everything blinds caches, monitoring, and load balancers**
- **First digit sets the class: 4 = your fault, 5 = my fault**
- **2xx isn't only 200**: 201 created, 202 accepted-async, 204 success-with-no-body (**don't call `.json()` on it**)
- **301 permanent (redirect cacheable) / 302 temporary**; **304 uses ETag to skip the whole body**
- **401 = no ID (recoverable), 403 = ID present but insufficient (don't retry)** — the most confused pair
- **409 is "understood but state conflicts"; 400 is "didn't understand"**
- **429 pairs with `Retry-After` and is retryable**
- **502 bad upstream response / 503 busy or maintenance / 504 upstream timeout**
- `r.ok` means status < 400; **`raise_for_status()` raises on anything not 2xx/3xx**
- ❌ **Don't test `== 200`; don't retry 4xx**
