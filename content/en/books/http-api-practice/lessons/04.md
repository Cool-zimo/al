# 04 Three Versions: From "One Line" to Ruling the World for Nearly Twenty Years

> HTTP in 1991 had a single command, no status codes, no headers — not even a version number. Five years later it grew status codes and headers. A year after that it became the HTTP/1.1 we still use today — and that version then reigned for nearly two decades.

## HTTP/0.9: One Line Was Enough (1991)

The version Berners-Lee first implemented was so simple it barely looks like a protocol.

To tell it apart later, people called it **HTTP/0.9** — a name applied after the fact; nobody called it 0.9 at the time.

### What a Request Looked Like

One line:

```
GET /index.html
```

That's all.

Notice what's missing:

- **No version number** (no `HTTP/0.9`)
- **No request headers**
- **Only one method, GET**
- **The path is a bare path** — no query parameters

### What a Response Looked Like

**Just the HTML body. Nothing else.**

```
<html>
  <body>Hello</body>
</html>
```

No status code, no response headers, no `Content-Type`.

Once the server finished sending the HTML, it **closed the TCP connection**. The close *was* the "I'm done" signal.

### How Crude That Was

It meant:

- **You couldn't tell success from failure.** On error the server could only return an HTML page with an error message — the client had no way to tell that from a normal page
- **You couldn't tell what type you got.** Everything was HTML; no images, no binary
- **Caching, compression, language negotiation — none of it existed**

### But It Did Work

Why? Because the thing it had to solve — **fetch one hypertext document** — was covered by exactly that.

An important principle: **version one of a protocol only needs to solve today's problem; don't over-engineer for an imagined future.** Later versions add what turns out to be needed.

## HTTP/1.0: Growing Status Codes and Headers (1996)

As the Web exploded, 0.9 was instantly insufficient.

In May 1996, **RFC 1945** was published, defining **HTTP/1.0**.

### What Got Added

**1. A version number**

The request had to state it:

```
GET /index.html HTTP/1.0
```

**2. Status codes**

The first line of the response became a status line:

```
HTTP/1.0 200 OK
```

Now a client could see at a glance whether it succeeded.

**3. Request and response headers**

The biggest change. Headers are an extensible **key-value** system:

```
GET /index.html HTTP/1.0
User-Agent: Mozilla/1.0
Accept: text/html
```

Responses carried headers too:

```
HTTP/1.0 200 OK
Content-Type: text/html
Content-Length: 1234
```

**Why do headers matter?** Because they make the protocol **extensible**. New features don't change the protocol's structure — you just define a new header field. That design carried every extension for the next thirty years.

**4. More methods**

0.9 had only GET. 1.0 added **POST** and **HEAD**.

**5. Content-Type**

Now things other than HTML could be sent — images, plain text, binary. That's the precondition for the Web going from "document system" to "multimedia platform".

### HTTP/1.0's Fatal Flaw: A New Connection Per Request

This was 1.0's biggest weakness and the reason it was replaced so fast.

**1.0's default behaviour: one request, one TCP connection, close when done.**

But establishing TCP takes a **three-way handshake**:

```
Client → Server: SYN        (I want to connect)
Server → Client: SYN-ACK    (OK, I'm ready too)
Client → Server: ACK        (Got it, let's go)
```

Those three round trips can take longer than transferring the data itself (especially on 1990s networks).

**A web page now loads dozens of resources** (HTML, CSS, JS, images…), each needing its own handshake. Pages became unbearably slow.

Worse, TCP has a mechanism called **slow start**: a fresh connection dares not send much data at first; it probes bandwidth gradually. Every new connection has to "warm up" again, so you never reach full throughput.

### A Semi-Official Patch: Connection: keep-alive

1.0's spec defined no persistent connections. But implementers couldn't stand it, so an unofficial practice appeared:

```
GET /a.html HTTP/1.0
Connection: keep-alive
```

The client adds that header meaning "don't close, I'm not done". If the server recognizes it, it keeps the connection open.

**The problem: it's not standard.** Both sides must understand it, and if a proxy sits in the middle, one party may not — and the connection gets closed anyway. **Unreliable.**

That's why 1.1 had to standardize it.

### Another Thing 1.0 Missed: One Server, One Website

1.0 requests have **no Host header**:

```
GET /index.html HTTP/1.0
```

The server knows the client wants `/index.html` — but **not which website's** `/index.html`.

That wasn't a problem at the time: one server ran one site, one IP mapped to one domain.

But **virtual hosting** spread fast: **one server, one IP, hosting dozens of different sites**. `www.a.com` and `www.b.com` resolve to the same IP.

Now the server is stuck: you ask for `/index.html` — whose should I give you?

**HTTP/1.1 solved this with the Host header, and made it mandatory.**

## HTTP/1.1: The Version We Still Use (1997)

HTTP/1.1 arrived fast. **January 1997, RFC 2068** — barely six months after 1.0.

It was revised several times: **RFC 2616 (1999)**, then **RFC 7230-7235 (2014)**, which split the one big document into six.

### Key Improvement 1: Persistent Connections by Default

The most important one.

**HTTP/1.1 keeps the connection open by default.**

```
GET /a.html HTTP/1.1
Host: www.example.com
```

After this request, the connection **stays open** and a second request can follow without a new handshake.

To close it, you must say so explicitly:

```
Connection: close
```

**Notice how "default" flipped:**

| Version | Default | To change it, say |
|---|---|---|
| HTTP/1.0 | close when done | `Connection: keep-alive` |
| HTTP/1.1 | keep open | `Connection: close` |

That flip matters. If your code speaks HTTP/1.0 without keep-alive, every request rebuilds the connection.

### Key Improvement 2: Host Becomes Mandatory

HTTP/1.1 requires: **every request must carry Host**.

```
GET /index.html HTTP/1.1
Host: www.example.com
```

With it, one server can tell which site you want.

**The spec says plainly: an HTTP/1.1 request without a Host header should get 400 Bad Request.**

That's why, when you typed by hand over telnet in lesson 03, the `Host:` line couldn't be skipped.

#### What That Meant for Virtual Hosting

With Host, one machine serving hundreds of sites became possible:

```
Same IP: 1.2.3.4
├── Host: www.a.com  → serve A's homepage
├── Host: www.b.com  → serve B's homepage
└── Host: www.c.com  → serve C's homepage
```

**This is the bedrock of modern web hosting and cloud services.** Without Host, one IP could serve one domain, and costs would be unimaginable.

#### What It Means for You

When you call an API, if you hand-assemble HTTP (not using requests), **forgetting Host gets you a 400**. It's a common trap, and the error rarely says "you're missing Host".

### Key Improvement 3: Pipelining — A Design That Failed

1.1 defined **pipelining**: the client may **send several requests without waiting for the previous response**.

```
req1 → req2 → req3          (sent back to back)
  ← resp1 ← resp2 ← resp3   (returned in order)
```

Sounds great — no waiting. But **it was essentially never used in practice**, for one fatal reason:

**Responses must come back in request order.** If request 1 is slow, responses 2 and 3 must wait even if computed already — **stuck behind it**.

That's **Head-of-Line Blocking**.

The result: pipelining brought little gain and a pile of implementation complexity (e.g. how to recover when one request fails). **Most browsers ended up disabling it by default.**

> **A lesson worth keeping**: a design that "sounds right" isn't necessarily usable in the real world. Pipelining is theoretically perfect, but with proxies, slow requests and retries, the costs outweighed the benefits.
>
> HTTP/2 later solved this with a completely different approach (lesson 05).

### Key Improvement 4: Chunked Transfer

In HTTP/1.0 the server had to state `Content-Length` in the response header.

Problem: **if the content is generated dynamically, the server may not know the total length when it starts sending.**

A database query — you don't know the byte count until you've fetched it all. Or a report generated on the fly.

HTTP/1.1 introduced **chunked transfer encoding**:

```
Transfer-Encoding: chunked
```

The server sends the body in chunks, each preceded by that chunk's length, ending with a zero-length chunk:

```
5\r\n        ← first chunk, 5 bytes
hello\r\n    ← the content
6\r\n        ← second chunk, 6 bytes
 world\r\n
0\r\n        ← length 0, done
\r\n
```

So the server **doesn't need to know the total up front**.

### Key Improvement 5: Much Better Caching

1.0's caching was crude (mostly `Expires`, an absolute expiry time).

1.1 introduced finer control:

- **`Cache-Control`**: relative expiry (`max-age=3600` means valid for an hour), plus `no-cache`, `no-store` and more
- **`ETag`**: a fingerprint of the resource. The client sends `If-None-Match` next time; the server compares and, if unchanged, replies **304 Not Modified** (no body — saves the whole transfer)
- **`If-Modified-Since`**: similar, but comparing by time

**304 is a neat design**: the server sends no body, just says "what you cached is still current". The client uses its local copy. **The entire response body's bandwidth is saved.**

If you see a 304 when calling APIs later, don't treat it as an error — **it means "nothing changed", and it's normal**.

### Other Improvements

- **Range requests**: ask for part of a file (`Range: bytes=0-999`), used for resumable downloads. Server replies **206 Partial Content**
- **More methods**: PUT, DELETE, OPTIONS, TRACE
- **Better content negotiation**: `Accept-Language`, `Accept-Encoding` (gzip)
- **100 Continue**: before sending a huge body, the client asks "will you accept it?"; a 100 means "go ahead"

## Why HTTP/1.1 Lasted So Long

HTTP/1.1 was finalized in 1997. HTTP/2 came out in **2015**.

**Eighteen years in between.**

In a field where things change monthly, an 18-year protocol life is remarkable. Why?

**1. It was good enough.**

Persistent connections, Host, caching, chunked transfer — those solved the core pains. In most scenarios it wasn't unbearably slow.

**2. It's text — easy to implement and debug.**

Every language, framework and tool supports it. Migration cost is enormous.

**3. Engineers found workarounds outside it.**

Since each connection suffers head-of-line blocking, **open more connections**. Browsers open 6-8 concurrent connections per domain, dodging the single-connection limit.

Since headers are verbose, **compress content, merge files, use a CDN**.

**Those workarounds were effective enough to extend HTTP/1.1's life by over a decade.** Only in the mobile era did their cost start exceeding the cost of switching protocols.

**4. Switching costs too much.**

Servers, clients, proxies, firewalls, load balancers — every device in the chain must support it. Any link that doesn't recognize the new protocol breaks communication.

### A Fun Historical Detail: Google Got Impatient

HTTP/1.1's problems grew obvious in the late 2000s, but standardization crawled.

Google's answer: **don't wait for the standard, build one.**

In 2009 Google announced **SPDY** (pronounced "speedy"), an experimental protocol that kept HTTP semantics but fixed the transport layer:

- Binary framing
- Multiplexing (many requests concurrently on one connection — head-of-line blocking gone)
- Header compression
- Server push

Google deployed SPDY in Chrome and on its own services, with clear measured gains.

**SPDY later became the basis of HTTP/2.** The HTTP/2 spec is largely "SPDY, standardized".

An interesting pattern: **when standards are too slow, capable companies ship a de facto standard first, then turn it into a formal one.**

## Version Timeline

| Version | Year | Key changes |
|---|---|---|
| **0.9** | 1991 | GET only, no status codes or headers, HTML only, close after sending |
| **1.0** | 1996 (RFC 1945) | Version number, status codes, headers, POST/HEAD, Content-Type; **one connection per request** |
| **1.1** | 1997 (RFC 2068) | **Persistent by default**, **Host mandatory**, chunked transfer, better caching, Range requests |
| **2** | 2015 (RFC 7540) | Binary, multiplexing, header compression, server push |
| **3** | 2022 (RFC 9114) | Transport switched from TCP to QUIC (over UDP) |

## Why This Lesson Helps You Write Code

### 1. Host Is Mandatory; Omit It and You Get 400

If you assemble HTTP by hand (no library), **Host cannot be omitted**. HTTP/1.1 requires it.

Libraries like requests add it automatically. But the moment you debug, capture packets, or write low-level code, the trap is waiting.

### 2. Persistent Connections Mean "Connection" Is a Reusable Resource

HTTP/1.1 keeps connections open by default. That means **reusing one connection for many requests is fast** and creating a new one each time is slow.

`requests`' `Session` does exactly that (lesson 26). For now just know: **if you're sending many requests, using a Session is noticeably faster.**

### 3. 304 Is Not an Error

You may see 304 when calling APIs. It's not failure — it's "your cache is still valid, I won't resend". **Handling 304 properly saves a lot of traffic.**

### 4. Head-of-Line Blocking Is the Key to Understanding HTTP/2

1.1's head-of-line blocking (and why pipelining failed) is the key to why HTTP/2 is designed as it is. **That's the next lesson.**

### 5. Content-Length and chunked — Pick One

The server either tells you the total length or uses chunked encoding. **Never both.** Watch for that when parsing responses.

## Recap

- **HTTP/0.9 (1991)**: one line `GET /path`, no status codes or headers, HTML only, **close after sending**. The version number was applied retroactively
- **HTTP/1.0 (1996, RFC 1945)**: grew **version number, status codes, headers**, added POST/HEAD and Content-Type; **fatal flaw: a new TCP connection per request** (handshake + slow start)
- The 1.0 era patched it with the non-standard `Connection: keep-alive`, which **wasn't reliable**
- **HTTP/1.1 (1997, RFC 2068)**: **persistent by default** (to close, write `Connection: close` explicitly)
- **Host became mandatory** — it made **virtual hosting** (many domains on one IP) possible, the bedrock of modern cloud services. Without it the server should return 400
- **Pipelining failed**: responses must return in request order, causing **head-of-line blocking**; browsers ended up disabling it
- **Chunked transfer** (`Transfer-Encoding: chunked`) lets the server start sending without knowing the total length
- **Better caching**: `Cache-Control`, `ETag`, and **304 Not Modified** (not an error — it means "unchanged, use your cache")
- 1.1 ruled for **18 years** (1997-2015): good enough, text-based, and workarounds like "open more connections" existed
- **Google got tired of waiting and shipped SPDY in 2009, which became the basis of HTTP/2**

func: parse_request_line
starter: |
  def parse_request_line(line):
      # Hint: split on whitespace
      # Three parts? method, path, version
      # Only two parts? no version, so it's 0.9
      pass
cases: |
  "GET /index.html HTTP/1.1" -> ("GET", "/index.html", "HTTP/1.1")
  "GET /index.html HTTP/1.0" -> ("GET", "/index.html", "HTTP/1.0")
  "GET /index.html" -> ("GET", "/index.html", "HTTP/0.9")
  "POST /api/users HTTP/1.1" -> ("POST", "/api/users", "HTTP/1.1")
hint: Use line.split() with no argument (it handles extra spaces), then check whether len(parts) is 3 or 2
explain: This is the scar tissue of protocol evolution. The "third part" of a request line was only added in HTTP/1.0, so a two-part request line must belong to an earlier version. split() with no argument is safer than split(" ") — it handles runs of consecutive spaces
