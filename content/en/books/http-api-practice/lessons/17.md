# 17 Forms vs JSON: The Three enctypes Taken Apart

> Last lesson showed that `data=` produces form format. This lesson covers forms completely: where they came from, the three varieties, why file uploads require them, and what those "random-looking" boundaries actually are.

## Where Forms Come From: HTML's <form>

Form format wasn't designed for APIs. It comes from **HTML forms in 1993**.

```html
<form action="/login" method="post">
  <input name="username" value="cool">
  <input name="password" type="password">
  <button type="submit">Login</button>
</form>
```

When the user submits, **the browser encodes the form contents into a request body**. The encoding is decided by the `enctype` attribute:

```html
<form enctype="application/x-www-form-urlencoded">   <!-- default -->
<form enctype="multipart/form-data">                  <!-- when uploading files -->
<form enctype="text/plain">                           <!-- almost nobody uses this -->
```

**Key point**: **this is browser behaviour, not an HTTP rule.** HTTP only carries bytes; `enctype` is an HTML-level convention that APIs later inherited.

## The Three enctypes

### One: application/x-www-form-urlencoded (default)

**What it looks like**:

```text
POST /login HTTP/1.1
Content-Type: application/x-www-form-urlencoded

username=cool&password=secret123
```

**Rule**: `key=value`, joined with `&`, **encoded exactly like a URL query string** (hence `urlencoded` in the name).

**This is what `data={dict}` produces** (previous lesson).

**Pros**: simple, compact
**Cons**:
- **flat key-value pairs only** — no nesting
- **every value is a string** — no numbers, booleans, or arrays
- **binary data must be encoded, inflating ~33%**

### Two: multipart/form-data (for file uploads)

**What it looks like**:

```text
POST /upload HTTP/1.1
Content-Type: multipart/form-data; boundary=----WebKitFormBoundary7MA4YWxk

------WebKitFormBoundary7MA4YWxk
Content-Disposition: form-data; name="username"

cool
------WebKitFormBoundary7MA4YWxk
Content-Disposition: form-data; name="avatar"; filename="photo.jpg"
Content-Type: image/jpeg

(raw binary bytes of the image go here)
------WebKitFormBoundary7MA4YWxk--
```

**Rules**:

1. A **boundary** string separates the fields
2. Each field has its own mini-headers (`Content-Disposition`)
3. **Binary data goes in raw** — no encoding at all

**What the boundary is**: a random string that **must not appear in your data** (or it would be misread as a separator). Browsers generate a long random string to make collision essentially impossible.

**Why it's needed**: an image contains arbitrary bytes — including `&`, `=`, and newlines. **With urlencoded, all of those need escaping and the server must handle one enormous single line.** Multipart segments cleanly instead.

### Three: text/plain (rarely used)

```text
username=cool
password=secret123
```

Plain text `key=value`, newline-separated, **with no URL encoding**.

**Why nobody uses it**: no encoding means values containing `&` or newlines break it, and there's no standard parsing rule, so servers disagree.

**Its only value**: human readability while debugging. Never in production.

## Comparison: Why APIs Use JSON

| | urlencoded | multipart | **JSON** |
|---|---|---|---|
| Nested structures | ❌ | ❌ | ✅ |
| Arrays | ⚠️ via repeated keys | ❌ | ✅ |
| Types (number/boolean) | ❌ all strings | ❌ | ✅ |
| Binary | ⚠️ +33% | ✅ raw | ❌ needs base64 |
| Readability | fair | poor | good |
| API support | fair | rare | **overwhelming** |

**Conclusion**:

- **Normal API calls → JSON**
- **File uploads → multipart**
- **urlencoded → only when explicitly required** (legacy forms, OAuth tokens)

## Using Multipart in requests

### Trigger it with files=

**Key mechanism**: **`requests` switches to multipart only when you pass `files=`.**

```python
import requests

r = requests.post(
    "https://httpbin.org/post",
    files={"avatar": ("photo.jpg", b"fake-image-bytes", "image/jpeg")},
    timeout=10,
)

print(r.request.headers["Content-Type"])
# multipart/form-data; boundary=...     ← ① automatically switched
```

> **①** As soon as you pass `files=`, `requests`:
> - changes Content-Type to `multipart/form-data`
> - generates a random boundary
> - assembles the body in the right format
>
> **You never touch the boundary.**

### Three ways to write files=

```python
import requests

# Way one: read from disk (most common)
with open("photo.jpg", "rb") as f:
    r = requests.post(url, files={"avatar": f}, timeout=10)

# Way two: specify filename and content type (recommended)
with open("photo.jpg", "rb") as f:
    r = requests.post(
        url,
        files={"avatar": ("photo.jpg", f, "image/jpeg")},   # ① a tuple
        timeout=10,
    )

# Way three: bytes in memory (no disk needed)
r = requests.post(
    url,
    files={"avatar": ("photo.jpg", b"\x89PNG...", "image/png")},
    timeout=10,
)
```

> **Line-by-line**
>
> - **Way one** is simplest, but **the server sees the filename as `avatar` (the dict key)**, not `photo.jpg`. Many servers need the real name
> - **Way two ①** the tuple form is `(filename, file object or bytes, MIME type)`. **Recommended** — filename and type are explicit
> - **Way three** suits "content already in memory" (just generated, downloaded from elsewhere)

### Mixing: form fields + file

```python
import requests

r = requests.post(
    url,
    data={"username": "cool", "description": "my avatar"},   # ① normal fields
    files={"avatar": ("photo.jpg", b"...", "image/jpeg")},   # ② the file
    timeout=10,
)
```

> **① ②** **`data=` and `files=` can be used together.** Normal fields go in `data=`; files go in `files=`.
>
> **Note**: the whole thing is then multipart, and **the `data=` fields are encoded as multipart segments too**, not urlencoded.

**That's why `data=` and `files=` aren't mutually exclusive the way `json=` and `data=` are** — they have different jobs.

## Real World: OAuth Token Endpoints Require Forms

A scenario **you will definitely hit**.

Most OAuth2 providers (GitHub, Google, WeChat…) require **`application/x-www-form-urlencoded`** on the token endpoint, even though every other endpoint uses JSON:

```python
import requests

r = requests.post(
    "https://github.com/login/oauth/access_token",
    data={                                   # ① note data=, not json=
        "client_id": "your_client_id",
        "client_secret": "your_secret",
        "code": "the_code_you_got",
    },
    headers={"Accept": "application/json"},   # ② but we want JSON back
    timeout=10,
)

token = r.json()["access_token"]
```

> **Line-by-line**
>
> - **①** **`data=`, not `json=`.** Required by the OAuth2 spec (RFC 6749). Using `json=` gets you rejected
> - **②** `Accept` says "what I want back" — **a different thing from Content-Type (what I'm sending).** Here we send a form and want JSON
>
> **This is the easiest trap in the lesson**: sending a form while requesting JSON is entirely normal. The two headers are independent.

## Side-by-Side: How the Server Parses

```python
import requests

# A: data= only (urlencoded)
rA = requests.post("https://httpbin.org/post",
                   data={"user": "cool", "tag": ["a", "b"]}, timeout=10)
dA = rA.json()
print("A Content-Type:", dA["headers"]["Content-Type"])
print("A form:", dA["form"])
print("A json:", dA["json"])

# B: data= + files= (multipart)
rB = requests.post("https://httpbin.org/post",
                   data={"user": "cool"},
                   files={"f": ("a.txt", b"hello", "text/plain")}, timeout=10)
dB = rB.json()
print("B Content-Type:", dB["headers"]["Content-Type"])
print("B form:", dB["form"])
print("B files:", dB["files"])
```

**What to notice**:

- **A's `tag` list**: becomes `tag=a&tag=b`, and whether the server parses it as an array or keeps only the last value **depends on the server**. That's urlencoded's only way to express arrays, and it's fragile
- **B's Content-Type**: includes a boundary
- **B's form and files are separate**: httpbin shows normal fields and files separately

## Crash Site

### Crash 1: uploading a file with json=

```python
# ❌ Wrong
r = requests.post(url, json={"avatar": open("photo.jpg", "rb")}, timeout=10)
# TypeError: Object of type BufferedReader is not JSON serializable
```

**Symptom**: an immediate error.

**Cause**: **JSON can't represent binary.** A file object isn't serialisable.

**Lesson**: **use `files=` whenever a file is involved.** If an API insists on JSON, you must base64-encode the file into a string (+33% size; Lesson 25).

### Crash 2: setting Content-Type manually with files=

```python
# ❌ Wrong
r = requests.post(
    url,
    files={"f": ("a.txt", b"x")},
    headers={"Content-Type": "multipart/form-data"},     # manual, no boundary
    timeout=10,
)
```

**Symptom**: the server says it can't parse the multipart, or gets empty data.

**Cause**: **`multipart/form-data` must carry `boundary=xxx`.** Your manual header has no boundary, so the server can't split the fields.

**Lesson**: **don't set Content-Type by hand when using `files=`** — let requests generate the complete value including boundary.

### Crash 3: using json= on OAuth

```python
# ❌ Wrong
r = requests.post(token_url, json={"client_id": ..., "code": ...}, timeout=10)
# 400 Bad Request
```

**Symptom**: 400, often with a vague message like "invalid request".

**Cause**: they required a form; you sent JSON.

**Lesson**: **OAuth token endpoints almost always use `data=`.** Check the docs' example — if the curl example uses `-d "a=b"`, that's a form.

## Why This Matters for Your Code

1. **Forms come from 1993 HTML**, not from HTTP. Three enctypes exist
2. **urlencoded is query-string encoding** — flat key-values only
3. **Multipart segments with a boundary** — the only format carrying binary as-is
4. **`files=` triggers multipart**, and you should **let requests generate the boundary**
5. **`data=` + `files=` coexist** — not exclusive, different jobs
6. **OAuth token endpoints usually use `data=`**, even when the response is JSON. **Content-Type and Accept are independent**

## Summary

- **Forms come from HTML `<form>`**; `enctype` sets the encoding, and APIs inherited it
- **Three enctypes**: `x-www-form-urlencoded` (default, flat) · `multipart/form-data` (file upload) · `text/plain` (rarely used)
- **Multipart segments with a boundary**, carrying binary raw, **and must include the boundary parameter**
- **APIs overwhelmingly use JSON** (nesting, arrays, types); **file uploads use multipart**
- **`files=` triggers multipart** and requests generates the boundary — **never set the header by hand**
- **Prefer the tuple form** `(filename, content, MIME)` for `files=`
- **`data=` + `files=` can coexist**; normal fields land in form, files in files
- **OAuth token endpoints use `data=`** (form), **while `Accept` can still be JSON**
- ❌ Don't send files with `json=`; don't set a multipart header without a boundary
