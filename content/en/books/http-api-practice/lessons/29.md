# 29 Concurrent Requests: From 100 Seconds to 5

> 100 requests at 1 second each take 100 seconds serially. With 20 concurrent workers, theoretically 5. **But cranking threads to 200 won't be faster — it may hammer the API and get your account banned.** This lesson covers why concurrency speeds things up, whether Python's GIL holds you back, how the three approaches compare, and **why concurrency must be paired with rate limiting**.

## First, Where Does the Time Go?

```python
import requests
import time

urls = ["https://httpbin.org/delay/1"] * 20      # server deliberately sleeps 1s per request

start = time.time()
for url in urls:
    requests.get(url, timeout=10)
print(f"serial: {time.time() - start:.1f}s")     # about 20 seconds
```

**During those 20 seconds, what is your CPU doing?**

**Almost nothing.**

```
send request ──→ [wait 1s] ──→ receive ──→ send next ──→ [wait 1s] ──→ ...
                  ↑
         the CPU is completely idle here
```

**Network waiting is idle waiting** — data travels the wire while your program just sits there. The CPU is free, but you never let it do anything else.

**The essence of concurrency: while waiting, go send the next request.**

```
thread1: send ──→ [wait] ──→ receive
thread2:   send ──→ [wait] ──→ receive
thread3:     send ──→ [wait] ──→ receive
...
the wait times of 20 requests overlap
```

## The GIL: Python's Concurrency "Shackle," and Why It Doesn't Matter Here

You may have heard of the **GIL (Global Interpreter Lock)** and that "Python multithreading is fake."

**That's half true.**

### What the GIL Is

CPython (the Python you installed) has a global lock: **only one thread executes Python bytecode at a time.**

**So**: for pure computation (calculating pi), 10 threads give **zero speedup** — only one runs at any instant.

### But I/O Releases the GIL

**The key**: when a thread performs **I/O** (network request, file read), **it releases the GIL**, letting others run.

```
thread1: send → enters wait → [releases GIL] → ... → receives → [re-acquires GIL] → process
                                   ↓
thread2:              [takes GIL] → send → enters wait → [releases GIL]
```

**Therefore**: **I/O-bound work (network requests) gets real speedup from threads.**

> **In one line**: the GIL blocks "parallel computing," not "parallel waiting." **HTTP requests spend 99% of their time waiting**, so threads work fine.

## Approach One: ThreadPoolExecutor (Best Starting Point)

Built into the standard library — nothing to install.

```python
import requests
from concurrent.futures import ThreadPoolExecutor
import time

urls = ["https://httpbin.org/delay/1"] * 20

def fetch(url):
    """Each thread runs this function"""
    r = requests.get(url, timeout=10)          # ① send request inside a thread
    return r.status_code

start = time.time()
with ThreadPoolExecutor(max_workers=10) as ex:    # ② 10 threads
    results = list(ex.map(fetch, urls))           # ③ submit jobs
print(f"concurrent: {time.time() - start:.1f}s")  # about 2 seconds
print(results)                                     # [200, 200, ...]
```

> **Line-by-line**
>
> - **① `fetch(url)`**: **an ordinary function.** It doesn't know it's running in a thread — that's what makes thread pools pleasant
> - **② `max_workers=10`**: **at most 10 threads at once.** The key parameter; choosing it comes later
> - **③ `ex.map(func, iterable)`**: hands each item of `urls` to `fetch`, **allocating threads automatically**. Results come back **in input order**
> - **`with`**: on exit the pool automatically joins (waits for all threads)

**20 seconds → 2 seconds, a 10× win.**

### When to Use as_completed Instead of map

`map`'s downside: **you can't get the first result until everything finishes.** If you want to **process as they complete** (e.g., show progress), use `as_completed`:

```python
from concurrent.futures import ThreadPoolExecutor, as_completed

with ThreadPoolExecutor(max_workers=10) as ex:
    # ① submit everything, keep the future objects
    future_to_url = {ex.submit(fetch, url): url for url in urls}

    for i, future in enumerate(as_completed(future_to_url), 1):   # ② whoever finishes first comes out first
        url = future_to_url[future]
        try:
            result = future.result()          # ③ get the result; exceptions surface here
            print(f"[{i}/{len(urls)}] {url} → {result}")
        except Exception as e:
            print(f"[{i}/{len(urls)}] {url} failed: {e}")
```

> **Line-by-line**
>
> - **① `ex.submit()`** returns a **Future** ("a result that will exist"). The dict maps future → url — **because `as_completed` doesn't preserve order, you must remember which is which**
> - **② `as_completed(futures)`**: **yields whichever finishes first.** Note **results come out of order**
> - **③ `future.result()`**: **retrieves the result. If `fetch` raised, the exception is re-raised right here**
> - **Wrap `result()` in `try/except`**: **mandatory.** Otherwise one failed request kills the loop and you lose all remaining results

### The Ordering Issue (Important)

```python
# map: result order == input order
results = list(ex.map(fetch, urls))       # reliable

# as_completed: result order == completion order (scrambled)
for f in as_completed(futures): ...       # you must map back yourself if order matters
```

**If you need "the result for the 3rd URL," use `map`.** If you just need "everything collected," `as_completed` also lets you show progress.

## Approach Two: Threads + Session (Mind Thread Safety)

Lesson 26 said it: **Session isn't thread-safe.** So in concurrent code, **one Session per thread**.

### Using threading.local()

```python
import requests
import threading
from concurrent.futures import ThreadPoolExecutor

# ① thread-local storage: each thread sees its own copy
_local = threading.local()

def get_session():
    """Return a Session dedicated to the current thread"""
    if not hasattr(_local, "session"):     # ② this thread hasn't made one yet
        _local.session = requests.Session()
        _local.session.headers.update({"User-Agent": "MyApp/1.0"})
    return _local.session                  # ③ return this thread's own

def fetch(url):
    s = get_session()                      # ④ get this thread's Session
    return s.get(url, timeout=10).status_code

with ThreadPoolExecutor(max_workers=10) as ex:
    results = list(ex.map(fetch, urls))
```

> **Line-by-line**
>
> - **① `threading.local()`**: a special container where **each thread sees different contents**. What thread A writes, thread B can't see
> - **② `hasattr(_local, "session")`**: checks whether **the current thread** has built a Session
> - **③ Reuse**: subsequent requests in the same thread reuse that Session (connection reuse works!)
> - **④ Each thread calling `fetch` gets its own Session**

**Benefit**: avoids thread-safety problems **while still reusing connections** across multiple requests in one thread.

**Remember to close** (when the pool exits):

```python
# Simple scripts can skip this (the process exit cleans up)
# Long-running services must close:
def close_all():
    if hasattr(_local, "session"):
        _local.session.close()
```

**In practice**: for a script that exits when done, not closing is fine (the OS reclaims). **Long-running services must close.**

## Approach Three: asyncio + aiohttp (First Choice for High Concurrency)

**Threads aren't free**: each costs roughly 8MB of memory (stack). **1000 threads = 8GB.**

**Async has no such problem** — it switches tasks **within one thread**, at negligible cost.

### Understanding async/await First

```python
import asyncio

async def fetch(url):          # ① async defines a coroutine
    print("start", url)
    await asyncio.sleep(1)     # ② await: yield control, go do something else
    print("done", url)
    return url

async def main():
    # ③ run three concurrently
    results = await asyncio.gather(
        fetch("a"), fetch("b"), fetch("c")
    )
    return results

asyncio.run(main())            # ④ start the event loop
```

**Output** (note the order):

```
start a
start b
start c
done a      ← finish almost simultaneously
done b
done c
```

> **Line-by-line**
>
> - **① `async def`**: defines a **coroutine**, not a normal function. Calling it doesn't execute it immediately
> - **② `await`**: **this is the key.** On `await`, the current coroutine **pauses and yields control**, and the event loop runs other coroutines. **When the awaited thing is ready, it resumes**
> - **③ `asyncio.gather()`**: **runs multiple coroutines concurrently**, waiting for all
> - **④ `asyncio.run()`**: starts the event loop (Python 3.7+)

**Without `await`**:

```python
# ❌ This is serial, not concurrent
async def main():
    await fetch("a")      # wait for a
    await fetch("b")      # then b
    await fetch("c")
# 3 seconds total
```

**`await` on a coroutine = wait for it to finish.** **Concurrency requires `gather` or `create_task`.**

### Sending Requests With aiohttp

**`requests` is synchronous and can't be used inside async** (it blocks the entire event loop).

You need `aiohttp`:

```bash
pip install aiohttp
```

```python
import aiohttp
import asyncio
import time

async def fetch(session, url):
    async with session.get(url, timeout=10) as r:    # ① async with
        return r.status

async def main(urls):
    async with aiohttp.ClientSession() as session:   # ② one Session for all coroutines
        tasks = [fetch(session, url) for url in urls]    # ③ build the task list
        results = await asyncio.gather(*tasks)           # ④ run concurrently
        return results

urls = ["https://httpbin.org/delay/1"] * 100
start = time.time()
results = asyncio.run(main(urls))
print(f"100 requests: {time.time() - start:.1f}s")     # about 2-3 seconds
```

> **Line-by-line**
>
> - **① `async with session.get(...)`**: aiohttp responses also need `async with` to close
> - **② `aiohttp.ClientSession()`**: **the async Session.** Note — **aiohttp's Session is designed to be shared** (unlike requests'); one Session for all coroutines is the correct用法
> - **③ List comprehension builds tasks**: **nothing has executed yet**
> - **④ `asyncio.gather(*tasks)`**: `*` unpacks the list into arguments. **This line actually starts concurrent execution**
> - **`asyncio.run()`**: called exactly once for the whole program

**100 requests in 2-3 seconds, with minimal memory.**

### Capping Concurrency: Semaphores

**Problem**: `gather` fires **all 100 requests at once**. That may hammer the server or trip rate limits (lesson 28).

**Solution**: a **Semaphore** to cap "requests in flight."

```python
import aiohttp
import asyncio

async def fetch(session, url, sem):
    async with sem:                          # ① acquire a permit
        async with session.get(url, timeout=10) as r:
            return r.status
    # ② leaving the async with returns the permit

async def main(urls, limit=10):
    sem = asyncio.Semaphore(limit)           # ③ at most 10 at once
    async with aiohttp.ClientSession() as session:
        tasks = [fetch(session, url, sem) for url in urls]
        return await asyncio.gather(*tasks)

results = asyncio.run(main(urls, limit=10))
```

> **Line-by-line**
>
> - **① `async with sem`**: **a semaphore is a counter.** Entering the `async with` decrements, exiting increments. **At zero, later coroutines suspend here and wait**
> - **② Auto-return**: `async with` guarantees the permit is returned even on exception (same as `with`)
> - **③ `Semaphore(limit)`**: **total permits = max concurrency**

**This is the standard "concurrency + rate limiting" combo.** 100 requests, at most 10 in flight, one refills as another finishes.

## How Many Concurrent Workers?

**More is not better.** Three constraints:

### One: Your Own Resources

| Approach | Reference ceiling |
|---|---|
| Threads | **20~50**. Beyond that, context-switch overhead cancels the gains and memory grows |
| Async | **several hundred**. But consider the other server too |

### Two: The Other Side's Limits

**This is the real decider.** Lesson 28 covered GitHub's secondary limits: **100 points per minute, 100 concurrent**.

**Consequences of exceeding them**: 403/429, or a temporary ban.

### Three: Politeness

**If you slow down someone's service alone, everyone else suffers.** Public APIs usually suggest **5~10 concurrent**.

**Rules of thumb**:

```python
# Public API: conservative
max_workers = 5

# Your own service / explicitly allowed: can go higher
max_workers = 20

# Unsure: start at 5, raise gradually, watch the response times
```

## Choosing Among the Three

| | ThreadPoolExecutor | asyncio + aiohttp |
|---|---|---|
| **Install** | nothing (stdlib) | `pip install aiohttp` |
| **Code changes** | **small** (plain functions) | **large** (everything becomes async) |
| **Concurrency ceiling** | tens | **hundreds to thousands** |
| **Memory** | ~8MB per thread | **tiny** |
| **Good for** | scripts, tens of requests | services, hundreds+ |
| **Session** | one per thread | one shared |
| **Ecosystem** | requests' ecosystem is mature | some libraries lack async support |

**Recommendations**:
- **< 50 requests**: thread pool — simple and sufficient
- **> 100 requests or writing a service**: asyncio
- **Large existing requests codebase**: thread pool; don't rewrite

## Crash Site

### Crash One: Threads Sharing One Session

```python
# ❌ Dangerous
s = requests.Session()
def fetch(url):
    return s.get(url)          # 10 threads using the same s

with ThreadPoolExecutor(max_workers=10) as ex:
    ex.map(fetch, urls)
```

**Symptom**: occasional bizarre errors — mixed-up cookies, connection errors, sporadic `ConnectionError`. **And you can't reproduce it**; sometimes it takes ten runs.

**Cause**: Session's internal state (cookie jar, connection pool) is read and written concurrently.

**Lesson**: **use `threading.local()` to give each thread its own Session** (lesson 26).

### Crash Two: Concurrency Set Too High

```python
# ❌ Greedy
with ThreadPoolExecutor(max_workers=500) as ex:
    ex.map(fetch, urls)
```

**Symptom**: fast for a few seconds, then **a flood of 429/403**, or an IP ban.

**Cause**: hundreds of requests land at once, tripping the other side's limits.

**Consequence**: **worse than slow** — not only does this run fail, you may be blocked for a while.

**Lesson**: **concurrency requires rate limiting.** Better slow than banned.

### Crash Three: Not Catching Exceptions in as_completed

```python
# ❌ One failure kills everything
for future in as_completed(futures):
    result = future.result()      # ① raises here
    process(result)               #     nothing after this runs
```

**Symptom**: request #5 of 100 fails → **the program crashes and you lose the other 95 results.**

**Cause**: `future.result()` re-raises exceptions from the worker thread.

**Lesson**: **wrap every `future.result()` in `try/except`.**

### Crash Four: Using requests or time.sleep Inside async

```python
# ❌ Fatal
async def fetch(session, url):
    time.sleep(1)                       # ① blocks the entire event loop!
    r = requests.get(url)               # ② also blocking!
    return r.status_code
```

**Symptom**: **no concurrency at all** — even slower than serial. The whole event loop stalls; every coroutine stops.

**Cause**: `time.sleep()` and `requests.get()` are **synchronous and blocking**. Calling them inside an async function **blocks the event loop** — no other coroutine gets to run.

**Lesson**:
- `time.sleep(1)` → `await asyncio.sleep(1)`
- `requests.get()` → aiohttp's `session.get()`
- **Rule: no blocking calls inside async functions**

### Crash Five: Assuming More Threads Is Faster

```python
# ❌ Assuming 500 threads is 25× faster than 20
```

**In reality**:

| Threads | Time |
|---|---|
| 1 | 20.0s |
| 10 | 2.1s |
| 20 | 1.5s |
| 50 | 1.4s |
| 200 | 1.6s ← **slower again** |

**Causes**:
1. **Context switching costs**
2. **The other server's throughput ceiling** — it can only handle so much per second
3. **Your own bandwidth cap**

**Lesson**: **concurrency has a point of diminishing returns.** Past it, you only add overhead and risk.

## Why This Matters for Your Code

**One: First, figure out the ratio of waiting to computing.**

Concurrency only helps "waiting" workloads. If your work is CPU-bound (image processing, heavy math), threads won't help — use processes. **How to tell: check CPU usage.** If CPU sits at 0% while a request is out → waiting-bound → concurrency fits.

**Two: With great power comes great responsibility.**

Concurrency takes you from "can't be killed" to "can kill the other side." **Rate limiting isn't optional; it's the companion of concurrency.** A concurrent program without limiting is essentially an attack tool.

**Three: Choose the right level of complexity.**

Don't reach for asyncio when a thread pool suffices. Async makes **the entire call chain async** (the "function coloring" problem) — an async function can't call ordinary blocking functions, and that constraint spreads through the codebase. **Confirm the payoff before adding complexity.**

## Summary

- **Concurrency's value**: network waits are idle waits; overlap them
- **The GIL doesn't block I/O concurrency**: threads release it during I/O, so requests genuinely benefit
- **Thread pool**: `ThreadPoolExecutor(max_workers=)` — stdlib, minimal changes
- **`map` preserves order; `as_completed` processes as they finish**
- **`future.result()` re-raises — always try/except**
- **Session isn't thread-safe**: `threading.local()`, one per thread
- **asyncio + aiohttp**: first choice at high concurrency, but all code must go async
- **No blocking calls in async**: `time.sleep` → `await asyncio.sleep`; `requests` → `aiohttp`
- **Semaphore caps concurrency**: `async with sem` — a necessity, not an option
- **Concurrency level**: public APIs 5~10, your own service 20~50, **beyond that gains shrink and risk grows**
- ❌ Don't share Sessions; don't go huge; don't skip exception handling; don't use requests in async; don't assume more is faster
