# 25 Uploads & Downloads: From a Few KB to Several GB

> Every example so far handled "small data" — tens of KB of JSON. This lesson handles real files: multi-MB images, hundreds-of-MB videos. The core problem is **memory** — reading a 1GB file into RAM before sending crashes your program.

## Downloading: Small Files First

```python
import requests

r = requests.get("https://example.com/photo.jpg", timeout=10)
r.raise_for_status()

with open("photo.jpg", "wb") as f:        # ① "wb" binary write
    f.write(r.content)                     # ② r.content is bytes

print(f"saved {len(r.content)} bytes")
```

> **Line-by-line**
>
> - **① `"wb"`**: `w` = write, `b` = binary. **Writing bytes requires the `b`**
> - **② `r.content`**: **not `r.text`** (Lesson 09 — using `.text` corrupts the image)
>
> **The problem with this**: **`r.content` reads the entire response into memory.**
>
> - a 5MB image → 5MB in RAM, fine
> - **a 1GB video → 1GB in RAM**, possibly OOM

## Streaming Downloads: stream=True

**Large files must be streamed** — write as you receive, keeping only a small buffer in memory.

```python
import requests

url = "https://example.com/big-video.mp4"

with requests.get(url, stream=True, timeout=10) as r:      # ① stream=True
    r.raise_for_status()

    with open("video.mp4", "wb") as f:
        for chunk in r.iter_content(chunk_size=8192):       # ② read in chunks
            f.write(chunk)                                   # ③ write as you go
```

> **Line-by-line**
>
> - **① `stream=True`**: tells requests to **download only the headers first, not the body**. The body is fetched when you read it
> - **② `iter_content(chunk_size=8192)`**: a **generator** yielding 8192 bytes (8KB) at a time. **Crucially it doesn't load everything at once**
> - **③** Write each chunk to disk. **Memory stays at 8KB**
>
> **Two nested `with` statements**: the outer closes the connection, the inner closes the file. **Missing either leaks a resource**

### Why 8192

`chunk_size=8192` (8KB) is a common value. **The reasoning**:

- too small (e.g. 100) → too many loop iterations, Python overhead dominates
- too large (e.g. 10MB) → big memory footprint, defeats streaming
- **8KB–64KB is the sweet spot**

**In reality**: this isn't "how much the network receives at a time" but "how much Python takes from the buffer each time". The network layer has its own buffering.

### Two things you must know with stream=True

**One: without `with`, close manually**

```python
r = requests.get(url, stream=True, timeout=10)
try:
    for chunk in r.iter_content(8192):
        f.write(chunk)
finally:
    r.close()          # required! otherwise the connection isn't released
```

**Two: if you don't read it all, the connection isn't reused**

```python
r = requests.get(url, stream=True, timeout=10)
print(r.headers["Content-Length"])      # headers only, no body
r.close()                                # connection discarded, not reusable
```

**That's effectively an alternative to HEAD** (Lesson 06) — though **HEAD is the more appropriate tool**.

## Downloads With a Progress Bar

```python
import requests
import os

def download_with_progress(url, path, chunk_size=8192):
    """Download a file, showing progress"""
    with requests.get(url, stream=True, timeout=10) as r:
        r.raise_for_status()

        total = int(r.headers.get("Content-Length", 0))    # ① total size
        downloaded = 0

        with open(path, "wb") as f:
            for chunk in r.iter_content(chunk_size=chunk_size):
                if not chunk:                               # ② filter keep-alive blanks
                    continue
                f.write(chunk)
                downloaded += len(chunk)

                if total:                                   # ③ only if total is known
                    pct = downloaded * 100 // total
                    print(f"\rprogress: {pct}%  ({downloaded}/{total} bytes)", end="")

        print()          # newline

download_with_progress("https://example.com/big.zip", "big.zip")
```

> **Line-by-line**
>
> - **① `Content-Length`** may be absent (it isn't sent with chunked transfer). **Fall back to 0**
> - **② `if not chunk: continue`** — **`iter_content` sometimes yields empty keep-alive chunks.** `f.write(b"")` is harmless, but it confuses the counting
> - **③ `if total:`** — when the size is unknown, skip percentages and show bytes downloaded
> - **`\r` + `end=""`**: refresh the progress on one line. **The standard terminal progress trick**

## Resumable Downloads: The Range Header

**If a download breaks halfway, can you continue?** Yes, with `Range`.

```python
import requests
import os

def resume_download(url, path):
    """Download with resume support"""
    # ① how much do we already have?
    if os.path.exists(path):
        downloaded = os.path.getsize(path)
    else:
        downloaded = 0

    headers = {}
    if downloaded:
        headers["Range"] = f"bytes={downloaded}-"      # ② ask from the offset

    with requests.get(url, headers=headers, stream=True, timeout=10) as r:
        # ③ the server may not support resume
        if downloaded and r.status_code != 206:
            print("server doesn't support resume — restarting")
            downloaded = 0          # start over

        r.raise_for_status()

        mode = "ab" if downloaded else "wb"             # ④ append or create
        with open(path, mode) as f:
            for chunk in r.iter_content(8192):
                if chunk:
                    f.write(chunk)
                    downloaded += len(chunk)

    return downloaded
```

> **Line-by-line**
>
> - **①** Check the local file size to use as the offset
> - **② `Range: bytes=5000-`** means "give me from byte 5000 onward"
> - **③ status 206 Partial Content** means the server honoured it and returned part. **A 200 means it ignored Range and sent the whole file** — you must then write from scratch (`"wb"`)
> - **④ `"ab"`** appends (binary), `"wb"` creates fresh (truncating)
>
> **That check is critical**: **appending blindly without confirming 206 gives you a corrupted "old first half + new second half" file**

## Uploading: Small Files

Lesson 17 covered the basics; here's the complete version:

```python
import requests

with open("photo.jpg", "rb") as f:                    # ① "rb" binary read
    r = requests.post(
        "https://httpbin.org/post",
        files={"avatar": ("photo.jpg", f, "image/jpeg")},   # ② tuple form
        timeout=30,                                    # ③ longer timeout for uploads
    )

print(r.status_code)
```

> **Line-by-line**
>
> - **① `"rb"`**: read binary. **The `with` guarantees the file closes**
> - **② the tuple `(filename, file object, MIME)`.** Lesson 17 — **preferred**, because the server gets the real filename
> - **③ `timeout=30`**: **uploads are slower than downloads**; allow more time. 1MB on a slow link can take tens of seconds

**Why not `files={"avatar": open(...)}` directly?** That **leaves the handle unclosed** (no `with`). requests closes it after reading, but explicit `with` is better.

## Uploading: Large Files

**The problem with `files=`**: requests reads the whole file into memory before encoding multipart.

**A 100MB file → 200MB+ in memory.**

### Option one: stream with requests-toolbelt

```bash
pip install requests-toolbelt
```

```python
from requests_toolbelt.multipart.encoder import MultipartEncoder
import requests

# ① a streaming encoder — never loads everything at once
encoder = MultipartEncoder(
    fields={
        "description": "my video",
        "video": ("video.mp4", open("video.mp4", "rb"), "video/mp4"),
    }
)

r = requests.post(
    "https://httpbin.org/post",
    data=encoder,                                        # ② pass the encoder
    headers={"Content-Type": encoder.content_type},       # ③ must include boundary
    timeout=60,
)
```

> **Line-by-line**
>
> - **① `MultipartEncoder`** is requests-toolbelt's **streaming** multipart encoder
> - **② `data=encoder`**: hand the encoder to `data=`; requests streams from it
> - **③ `encoder.content_type`**: **must be set manually**, because it carries the boundary (Lesson 17)
>
> **Note ③ is the exception** to Lesson 17's "don't set Content-Type with files=" — here you must, since `data=` won't add it.

### Option two: chunked upload (common with cloud storage)

Large-file services often do this: **cut the file into pieces, send one at a time**.

```python
import requests
import os

def upload_in_chunks(path, upload_url, chunk_size=5 * 1024 * 1024):
    """Chunked upload (illustrative; real APIs differ)"""
    total_size = os.path.getsize(path)
    uploaded = 0

    with open(path, "rb") as f:
        index = 0
        while True:
            chunk = f.read(chunk_size)          # ① read one chunk
            if not chunk:
                break

            # ② tell the server which chunk this is
            r = requests.post(
                upload_url,
                data=chunk,
                headers={
                    "Content-Type": "application/octet-stream",
                    "X-Chunk-Index": str(index),
                    "X-Total-Size": str(total_size),
                },
                timeout=60,
            )
            r.raise_for_status()

            uploaded += len(chunk)
            index += 1
            print(f"uploaded {uploaded}/{total_size}")

    return uploaded
```

> **Line-by-line**
>
> - **① `f.read(chunk_size)`** reads one chunk (5MB here). **Constant memory**
> - **②** custom headers tell the server the chunk index. **Header names vary by service** (AWS S3, Qiniu, Aliyun all differ)
>
> **That's the principle of chunked upload.** In real projects **use the provider's SDK** — each protocol has many details.

## Verifying: Confirm the File Isn't Corrupt

Checking a hash after download (or before upload) is good practice:

```python
import requests
import hashlib

def sha256_file(path, chunk_size=8192):
    """Stream a file's SHA256 (no memory blow-up)"""
    h = hashlib.sha256()
    with open(path, "rb") as f:
        for chunk in iter(lambda: f.read(chunk_size), b""):   # ① until empty
            h.update(chunk)
    return h.hexdigest()

print(sha256_file("big.zip"))
```

> **Line-by-line**
>
> - **① `iter(lambda: f.read(chunk_size), b"")`**: **the Python idiom for reading a file in chunks until EOF.**
>   - `iter(callable, sentinel)`: keep calling until the sentinel `b""` is returned
>   - cleaner than `while True` + `if not chunk: break`
>   - **must be `b""` (empty bytes), not `""`**, because we're reading binary
>
> **Why stream**: a 1GB `f.read()` blows memory. **Hashing can be incremental** (call `h.update()` repeatedly), so streaming works

**Comparing**:

```python
expected = "abc123..."          # the official hash from the download page
actual = sha256_file("big.zip")

if actual == expected:
    print("file intact ✓")
else:
    print("corrupted or tampered ✗")
```

## A Complete Download Function

Putting the lesson together:

```python
import requests
import os
import hashlib
import logging

def download(url, path, chunk_size=8192, timeout=30, expected_sha256=None):
    """
    Download a file (streaming, resumable, optional verification).
    Returns True on success.
    """
    # ① resume
    resume = 0
    headers = {}
    if os.path.exists(path):
        resume = os.path.getsize(path)
        if resume:
            headers["Range"] = f"bytes={resume}-"
            logging.info(f"resuming, {resume} bytes already present")

    mode = "ab" if resume else "wb"

    try:
        with requests.get(url, headers=headers, stream=True, timeout=timeout) as r:
            # ② restart if resume isn't supported
            if resume and r.status_code != 206:
                logging.warning("server doesn't support resume — restarting")
                resume = 0
                mode = "wb"

            if not r.ok:
                logging.error(f"HTTP {r.status_code}")
                return False

            with open(path, mode) as f:
                for chunk in r.iter_content(chunk_size):
                    if chunk:
                        f.write(chunk)

    except requests.exceptions.RequestException as e:
        logging.error(f"download failed: {e}")
        return False

    # ③ optional verification
    if expected_sha256:
        actual = sha256_file(path)
        if actual != expected_sha256:
            logging.error(f"checksum mismatch: expected {expected_sha256}, got {actual}")
            return False
        logging.info("checksum OK ✓")

    return True
```

> **Line-by-line**
>
> - **①** Check the local file and prepare to resume
> - **② the 206 check** (the critical judgement from above)
> - **③** Verify last. **Only when `expected_sha256` is provided**
>
> **Keep this in your toolbox** — it covers the main needs of large-file downloading.

## Crash Site

### Crash 1: downloading with r.text

Lesson 09 covered it; repeated here because **it's so common**:

```python
# ❌ Corrupted image
with open("photo.jpg", "w") as f:
    f.write(r.text)
```

**Lesson**: **binary files always use `.content` + `"wb"`.**

### Crash 2: forgetting stream=True for large files

```python
# ❌ 1GB straight into memory
r = requests.get(big_url, timeout=10)
with open("big.zip", "wb") as f:
    f.write(r.content)          # memory explodes
```

**Symptom**: fine in small-file tests; MemoryError or a frozen system on real files.

**Lesson**: **above ~10MB, use `stream=True` + `iter_content`.**

### Crash 3: resuming without checking 206

```python
# ❌ Wrong
headers = {"Range": f"bytes={resume}-"}
r = requests.get(url, headers=headers, stream=True, timeout=10)
with open(path, "ab") as f:        # blind append
    ...
```

**Symptom**: the server ignores Range, returns 200 with the full file, and you append it → **double the size, corrupted.**

**Lesson**: **always check `r.status_code == 206`**; otherwise write from scratch.

### Crash 4: timeout too short for uploads

```python
# ❌ Wrong
requests.post(url, files={"f": big_file}, timeout=10)     # 10s isn't enough
```

**Symptom**: a large upload times out midway. The file wasn't fully sent, though the server may have part of it.

**Lesson**: **upload/download timeouts should exceed normal API timeouts** (30–120s depending on size).

## Why This Matters for Your Code

1. **Small files: `.content` + `"wb"`. Large files: `stream=True` + `iter_content`**
2. **`chunk_size` of 8KB–64KB is the sweet spot**
3. **Resume must check 206**, or you'll assemble a corrupt file
4. **Upload with the `files=` tuple form**; huge files need toolbelt streaming or chunking
5. **Hash verification should stream** (incremental `h.update()`)
6. **File operations need longer timeouts than API calls**
7. **`iter(lambda: f.read(n), b"")`** is the chunked-read idiom

## Summary

- **Small files**: `f.write(r.content)` with `"wb"`
- **Large files**: `stream=True` + `iter_content(chunk_size=8192)`, **memory holds one chunk**
- **Two streaming rules**: use `with` or `close()` manually; unread connections aren't reused
- **Progress**: percentage from `Content-Length`, `\r` + `end=""` for same-line refresh, **filter empty chunks**
- **Resume**: `Range: bytes=N-` + **check 206** + append with `"ab"`
- **Upload**: `files={"k": ("name", f, "mime")}`, **open with `with`**
- **Huge files**: toolbelt's `MultipartEncoder` (**set Content-Type manually**) or chunked upload
- **Verify**: `hashlib` + streaming `update()`, via **`iter(lambda: f.read(n), b"")`**
- ❌ Never download binary with `.text`; don't forget stream for big files; **don't forget the 206 check**; give file ops longer timeouts
