# 10 Cookies & State: How HTTP "Remembers" You

> Lesson 03 said it: HTTP is **stateless** — the server doesn't remember what you did on the previous request. Yet in reality you log in once and browse all day without logging in again. How? Cookies. This lesson covers the invention story, how it works, the attributes that cause so much grief, and why cookies ended up at the centre of the privacy debate.

## The Trouble With Being Stateless

In 1994, Netscape was building something: a **shopping cart** for the browser that came after Mosaic.

The problem was blunt:

```
User adds item A to cart  → server records "A"
User adds item B to cart  → server records… what?
```

**HTTP is stateless.** When the second request arrives, the server has no idea that "the person who added A" and "this person" are the same. It just sees an isolated request.

Programmers at the time tried several things, all awkward:

- **Hide state in the URL**: `?session=abc123`. Problem: URLs are visible, bookmarkable, and leakable
- **Hidden form fields**: stuff `<input type="hidden">` into every form. Problem: POST only, and every page needs manual work
- **Identify by IP**: completely unreliable. Hundreds of people in one company share an egress IP

## Lou Montulli's Invention

In 1994, Netscape engineer **Lou Montulli** proposed the cookie.

**His insight**: if the server can't remember, **let the client remember for it**.

How it works:

1. Server adds a header to the **response**: `Set-Cookie: cart=A`
2. Browser sees it and **stores `cart=A` on disk**
3. From then on, when this browser visits **the same domain**, it automatically includes in the **request**: `Cookie: cart=A`
4. Server reads `Cookie` and knows "ah, this is the person whose cart has A"

**The key idea**: state lives on the **client** and is attached to every request. **The server is still stateless** — it's simply told the state each time.

Brilliant, because **it preserves HTTP's stateless nature while delivering a stateful experience**. Server code stores nothing in memory.

### Where the name came from

"Cookie" comes from the programming term **magic cookie** — a small piece of data passed between programs and returned verbatim. That term in turn comes from the fortune cookie, with its slip of paper inside.

Montulli later said he just wanted a memorable word.

### One astonishing detail

From 1994 until 2011, cookies had **no official specification**. Every browser in the world implemented them from an **informal note** Netscape published back then.

RFC 6265 finally standardised them in 2011 — **seventeen years later**.

## How It Works: Two Headers

### Set-Cookie (server → browser)

```text
HTTP/1.1 200 OK
Set-Cookie: session_id=abc123; Path=/; HttpOnly
```

### Cookie (browser → server)

```text
GET /cart HTTP/1.1
Cookie: session_id=abc123
```

**Note how different these two are**:

- `Set-Cookie` is a **response header** and may appear **many times** (to issue several cookies)
- `Cookie` is a **request header** carrying all cookies for that site joined into **one long string** with `; `

## Cookie Attributes: Where the Trouble Starts

A full Set-Cookie looks like:

```text
Set-Cookie: id=a3fWa; Expires=Thu, 31 Oct 2026 07:28:00 GMT; Path=/; Domain=.example.com; Secure; HttpOnly; SameSite=Lax
```

One by one:

### Expires / Max-Age: how long it lives

| | Meaning |
|---|---|
| **Expires** | an exact expiry moment (GMT format) |
| **Max-Age** | how many **seconds** it should live |

**When both are set, `Max-Age` wins.**

**Neither set → session cookie**: gone when the browser closes.

**Set to a future time → persistent cookie**: written to disk, survives closing the browser and rebooting, until it expires.

> **Practically**: ticking "Remember me" means the server set `Max-Age` to 30 days. Not ticking it means a session cookie.

### Domain and Path: which requests get it

```text
Domain=.example.com      ← both shop.example.com and www.example.com receive it
Path=/admin              ← only sent for paths starting /admin
```

**Domain is the easiest one to get wrong**:

- No Domain → **sent only to the current domain** (strictest; also called a host-only cookie)
- `.example.com` → every subdomain receives it

**Note**: **a cookie's Domain may only be the current domain or a parent of it.** A server at `shop.example.com` **cannot** set `Domain=google.com` — browsers reject it outright. That's a security restriction.

### Secure: HTTPS only

```text
Secure          ← only sent over HTTPS
```

**A cookie without Secure is transmitted in plaintext over HTTP**, which is equivalent to broadcasting your credentials on public WiFi.

**Today's advice: every cookie should have Secure.**

### HttpOnly: JavaScript can't touch it

```text
HttpOnly        ← document.cookie can't read it
```

This is the key XSS defence:

```
No HttpOnly: malicious JS on the page can steal session_id via document.cookie
HttpOnly: JS can't read it; only the browser attaches it automatically
```

**Note**: HttpOnly blocks JS, **not your own eyes in devtools**. It defends against *other people's scripts*.

### SameSite: defending against CSRF

Added in **2016**, and one of the most important security attributes. First, what it defends against.

A **CSRF (Cross-Site Request Forgery)** scenario:

1. You're logged into `bank.com`; the browser holds the session cookie
2. You visit `evil.com`
3. `evil.com` contains: `<img src="https://bank.com/transfer?to=attacker&amount=10000">`
4. When the browser loads that "image", it **automatically attaches bank.com's cookie**
5. The bank sees a request with a valid session → **transfer succeeds**

**You did nothing, and the money is gone.**

`SameSite` fixes exactly this. Three values:

| Value | Behaviour | Use |
|---|---|---|
| **Strict** | **never** sent on cross-site requests | safest, but clicking an external link shows you as logged out |
| **Lax** | sent for cross-site **top-level navigation** (link clicks) only | **today's default**; balances safety and UX |
| **None** | sent cross-site (**requires Secure**) | cross-site needs like embedded widgets |

**Important**: modern browsers (Chrome 80+, 2020) **treat cookies without SameSite as Lax by default**. That means **legacy cross-site cookies suddenly stopped working** — a lot of sites broke "inexplicably" in 2020.

## Cookie vs Session: Two Commonly Confused Words

People use these interchangeably, but they aren't on the same level:

| | Cookie | Session |
|---|---|---|
| **What it is** | a **transport mechanism** (HTTP header) | a kind of **server-side storage** |
| **Where it lives** | client (browser) | server (memory / Redis / database) |
| **Typical content** | an ID string | complete user data |
| **Relationship** | Sessions **usually ride on cookies for the ID** | depends on cookies, but isn't one |

Typical flow:

```
1. User submits username and password
2. Server verifies, stores {"user_id": 123, "role": "admin"} in Redis under id sess_xyz
3. Server responds Set-Cookie: session=sess_xyz
4. Browser stores session=sess_xyz
5. Every later request automatically carries Cookie: session=sess_xyz
6. Server looks up sess_xyz in Redis and gets the full user record
```

**So**: the cookie holds only a **key**; the real thing (the session) lives on the server.

### Why not put all the data in the cookie?

Technically possible (some do — "JWT in a cookie"), with two hard problems:

1. **Size limits**: a single cookie **can't exceed 4KB**, generally **max ~50 cookies per domain**
2. **Users can edit it**: cookies sit on the user's disk and can be changed freely. **You must never trust `role=admin` from a cookie**

## Third-Party Cookies & Privacy

Everything above is a **first-party cookie** (set by the site you visited).

A **third-party cookie**: you visit `news.com`, the page embeds an image from `ad.com`, and the advertiser sets an `ad.com` cookie.

**That's how ad tracking works**:

```
You visit news.com  → ad.com records "this person read the news"
You visit shop.com  → ad.com records "this person viewed product X"
You visit blog.com  → ad.com records "this person read article Y"
```

You never visited `ad.com` directly, yet through resources embedded across sites **it assembled a complete profile of you**.

That has driven two decades of privacy controversy. The outcome:

- **Safari (2017)**: **blocks third-party cookies entirely** by default
- **Firefox (2019)**: blocks known trackers by default
- **Chrome**: promised phase-out from 2020, repeatedly delayed in practice

## Code: Cookies in requests

### Reading cookies the server set

```python
import requests

r = requests.get("https://httpbin.org/cookies/set?name=cool", timeout=10)

print(r.cookies)                          # ① a RequestsCookieJar object
print(dict(r.cookies))                    # ② {'name': 'cool'}
print(r.cookies.get("name"))              # ③ 'cool'
```

> **Line-by-line**
>
> - **①** `r.cookies` is not a plain dict but a `RequestsCookieJar` — **though it supports most dict operations**
> - **②** Want a real dict? Convert with `dict()`
> - **③** `.get()` returns `None` when missing rather than raising

### Sending cookies

```python
import requests

# Way one: a dict
r = requests.get(
    "https://httpbin.org/cookies",
    cookies={"session": "abc123"},         # ① dict form
    timeout=10,
)

# Way two: set the header by hand (not recommended)
r = requests.get(
    "https://httpbin.org/cookies",
    headers={"Cookie": "session=abc123"},  # ② manual string
    timeout=10,
)
```

> **Line-by-line**
>
> - **①** Preferred. `requests` handles the encoding
> - **②** Works but painful. **With special characters (spaces, `;`, non-ASCII) you must encode yourself.** Worse, **on redirects a manually-set Cookie header isn't updated**, while `cookies=` is

### Keeping state automatically: the Session object

**This is what real projects actually use**:

```python
import requests

s = requests.Session()                    # ① create a session

r1 = s.get("https://httpbin.org/cookies/set?user=cool", timeout=10)
# server issued a cookie; the Session stores it automatically

r2 = s.get("https://httpbin.org/cookies", timeout=10)
print(r2.text)                            # ② the cookie from before is sent automatically
```

> **Line-by-line**
>
> - **①** A `Session` **carries its own cookie jar** and **stores every cookie the server issues**
> - **②** The second request **automatically carries** the cookie from the first. **You do nothing**

**Compare with not using a Session**:

```python
# ❌ No Session: the cookie is lost
requests.get("https://httpbin.org/cookies/set?user=cool", timeout=10)
r = requests.get("https://httpbin.org/cookies", timeout=10)
print(r.text)        # {"cookies": {}} ← empty!
```

**Every `requests.get()` is independent**; cookies don't survive across calls.

> **The second most common beginner confusion**: "I definitely logged in — why is the next request still unauthenticated?" Because you used `requests.get()` instead of `session.get()`

**A complete login flow looks like this**:

```python
import requests

s = requests.Session()                                  # ① one object throughout

r = s.post(                                             # ② log in
    "https://example.com/login",
    json={"username": "cool", "password": "xxx"},
    timeout=10,
)
r.raise_for_status()                                    # ③ confirm success

r = s.get("https://example.com/profile", timeout=10)    # ④ request with the session
print(r.json())                                         #    personal data comes back
```

> **Line-by-line**
>
> - **①** One Session for the whole flow. **Don't mix `s.get()` with `requests.get()`** — the latter's cookies never enter the session
> - **②** The login request
> - **③** As always: check the status code first
> - **④** By now the cookie is attached automatically

## Crash Site

### Crash 1: mixing Session with requests

```python
# ❌ Wrong
s = requests.Session()
s.post("https://example.com/login", json={...})      # logged in; cookie in session

requests.get("https://example.com/profile")          # ← module-level function!
# Result: 401 unauthenticated
```

**Symptom**: login clearly succeeded, but the next request is still 401.

**Cause**: `requests.get()` is a **module-level function** that **creates a brand-new temporary Session each call** and discards it. It **does not** use the cookies in your `s`.

**Lesson**: **once you choose a Session, use `s` for everything.** Mixing is the number one source of this bug.

### Crash 2: trusting sensitive data in a cookie

```python
# ❌ Bad server design
Set-Cookie: role=admin; user_id=123

# Attacker edits it
Cookie: role=admin; user_id=1        ← changed to someone else's ID
```

**Symptom**: an authorisation hole. Users see others' data, or escalate to admin.

**Cause**: **cookies live on the user's disk and can be edited freely.** Whatever you write there is meaningless, because what arrives may be forged.

**Lesson**: **put only an unguessable random ID in the cookie**; keep real data server-side. **Never trust business data from a cookie.**

### Crash 3: forgetting to close the Session

```python
# ⚠️ Imperfect
for user in users:
    s = requests.Session()              # new session each iteration
    s.get(...)
    # forgot s.close()
```

**Symptom**: after a long run, connection counts explode, you get `Too many open files`, or the server complains about too many connections.

**Cause**: a Session **reuses underlying TCP connections** (Lesson 26). Without closing, pooled connections are never released.

**Lesson**: **use a `with` statement**, or reuse one Session throughout:

```python
with requests.Session() as s:           # ✅ closes automatically
    for user in users:
        s.get(...)
```

## Why This Matters for Your Code

1. **Cookies give stateless HTTP a way to "remember"** while server code stays stateless. That idea shaped all later web architecture
2. **Session is your default for authenticated flows.** `requests.get()` is one-shot
3. **Mixing `s.get()` and `requests.get()` is a bug factory** — the single most important takeaway here
4. **Cookies are user-controlled; never trust business data in them**
5. **Don't forget `with` or `close()`**, or long-running scripts exhaust connections

## Summary

- **HTTP is stateless**; in 1994 Lou Montulli invented cookies to "remember" users by **storing state on the client**
- **No formal standard from 1994 to 2011** — just a Netscape note; RFC 6265 standardised it
- **Two headers**: `Set-Cookie` (response, repeatable), `Cookie` (request, one joined string)
- **Attributes**: `Expires`/`Max-Age` lifetime · `Domain`/`Path` scope · `Secure` HTTPS-only · `HttpOnly` unreadable by JS · **`SameSite` anti-CSRF**
- **No expiry = session cookie** (gone when the browser closes); with expiry = persistent
- **Cookie is transport; Session is server storage.** Cookie holds the key; data stays on the server
- **Third-party cookies underpin ad tracking**; major browsers are phasing them out
- **`requests.Session()` manages cookies automatically**, attaching them across requests
- ❌ **Don't mix `s.get()` with `requests.get()`**; **don't trust business data in cookies**; **don't forget `close()`**
