# 03 What a Protocol Is: Why HTTP Deliberately Lets You Type It

> Most network protocols are a string of binary you can't read. HTTP isn't — it's plain text, and you can type a request by hand with the `telnet` that ships with your system, and the server will really answer. That design isn't an accident; it determined everything that followed.

## First: What Is a "Protocol"?

"Protocol" sounds abstract. It's really just **a set of rules for speaking**.

### An Everyday Example

You call a friend:

1. You dial; they pick up and say "Hello?"
2. You say "It's me"
3. They say "Oh, hey!"
4. Then the actual conversation
5. Both say "Bye", and you hang up

That whole thing is a protocol. Notice it has several features:

- **A fixed opening** — "Hello?" and "It's me". If they picked up and launched straight into business, it would feel wrong
- **Back and forth** — you speak, they reply; it's not one-way broadcast
- **A fixed closing** — only after "Bye" do you hang up
- **Implicit rules** — who speaks first, when it's OK to interrupt, how long silence means the call dropped

If the two people come from different cultures, those rules may differ (Japanese phone openings are longer, for instance) and the conversation jams.

**A computer protocol is that same thing, except the participants are two machines and the rules are written down precisely.**

### The Three Elements of Any Protocol

Every protocol breaks into three things:

**1. Syntax: what the data looks like**

For example, the first line of an HTTP request must be:

```
GET /index.html HTTP/1.1
```

Three parts separated by single spaces, order fixed. `GET HTTP/1.1 /index.html` is wrong.

That's like "Hello?" having to come first.

**2. Semantics: what each part means**

`GET` means "I want to fetch", not "I want to delete". `/index.html` is the path. `HTTP/1.1` is the version I'm speaking.

Syntax without semantics: both sides can align the format but not know what the other wants.

**3. Timing: who goes first, what happens under what conditions**

HTTP says: **the client sends a request first; the server replies only after receiving it.** The server cannot spontaneously send you things (absent special mechanisms).

That's like "you may only speak after they pick up and say Hello?".

**Fail at any one of the three and communication breaks.** Almost every API error you'll hit later is one of these three mismatched — wrong format, misunderstood meaning, or wrong order.

## Which Floor Is HTTP On?

Network protocols are layered. Knowing which layer HTTP sits on explains a lot of weirdness you'll meet later.

### Why Layer at All

Think of posting a letter:

- The content of your letter ("Hi Mum, I'm fine") — **you care**
- The address on the envelope, the stamp — **you care**
- How the mail truck gets it from Beijing to Shanghai — **you don't care**
- Which highway the truck takes, the driver's name — **you care even less**

The division of labour is clear: **each layer uses only the layer directly below, and doesn't care how that one does its job.**

Same with network protocols. Each layer offers services to the layer above and calls the layer below. **The interfaces between layers are standardized; the internals can be swapped freely.**

### Two Models

There are two common layering models; what you need is roughly how they map:

**The OSI seven-layer model** (theoretical, textbooks love it):

| Layer | Name | What it does |
|---|---|---|
| 7 | Application | HTTP, FTP, SMTP |
| 6 | Presentation | Encryption, compression, encoding |
| 5 | Session | Establish and manage sessions |
| 4 | Transport | TCP, UDP |
| 3 | Network | IP |
| 2 | Data link | Ethernet, WiFi |
| 1 | Physical | Cables, fibre, radio |

**The TCP/IP four-layer model** (what's actually used):

| Layer | Maps to OSI | Examples |
|---|---|---|
| Application | 5-7 merged | **HTTP**, DNS, SMTP |
| Transport | 4 | TCP, UDP |
| Internet | 3 | IP |
| Network interface | 1-2 | Ethernet, WiFi |

**HTTP lives in the application layer — the top one.**

### The Practical Consequence: Encapsulation

When you send an HTTP request, the data is wrapped layer by layer:

```
HTTP request:  GET /index.html HTTP/1.1\r\nHost: ...\r\n\r\n
                  ↓ add TCP header (ports, sequence number, checksum)
TCP segment:   [TCP hdr][HTTP request]
                  ↓ add IP header (source IP, destination IP)
IP packet:     [IP hdr][TCP hdr][HTTP request]
                  ↓ add Ethernet header (MAC addresses)
Ethernet frame:[frame hdr][IP hdr][TCP hdr][HTTP request][frame trailer]
```

The sender **adds headers** going down; the receiver **strips them** going up.

**The HTTP layer sees only its own part. It doesn't know, and cannot control, what happens below.**

Remember this, because it explains something you will definitely hit:

> **HTTP cannot know when the underlying connection dropped.**

TCP resets, IP retransmits, WiFi switches — **the HTTP layer can't see any of it**. All it can notice is "I waited a long time and got no answer". That's a **timeout**.

So you must set `timeout` in your code: **not because HTTP is unreliable, but because it was designed to be blind to the reliability below.** Lesson 15 covers this properly.

## Why HTTP Is a Text Protocol

This is the most important part of the lesson.

### Two Kinds: Binary vs Text

**Binary protocols**: data is a run of bytes where every byte (sometimes every bit) has a precise meaning. Compact and efficient, but **unreadable to humans**.

DNS, TLS, and later HTTP/2 are binary. A packet capture shows you a wall of hex digits.

**Text protocols**: the data is readable characters. HTTP/1.1 is one of these.

A complete HTTP request looks like this (this one really works):

```
GET /index.html HTTP/1.1
Host: www.example.com
User-Agent: my-test-client

```

That's it. **Plain ASCII, a human can read every line.**

### Why Design It That Way

When Berners-Lee designed HTTP in 1990, he chose plain text for very practical reasons:

**1. Humans could debug directly**

In 1990 there were no mature HTTP debugging tools. With a binary protocol you'd have to write a parser just to see what you'd sent.

A text protocol means: **anything that can display text can display HTTP**. You can send a request by hand with `telnet`, read the response with `cat`, filter it with `grep`.

**2. Errors are readable**

A server error in binary means consulting docs to decode bytes. A text protocol hands you a human-readable line.

**3. No special library needed**

Any program that can read and write strings can implement HTTP. That mattered in 1990, when network libraries were scarce.

### Try It Yourself

This is the only hands-on part of the lesson, and **it's worth actually doing** — doing it once changes how you understand HTTP.

Open a terminal and type:

```bash
telnet example.com 80
```

Once it connects, **type these lines** (note the blank line at the end):

```
GET / HTTP/1.1
Host: example.com

```

You'll get a big block of text back, starting with:

```
HTTP/1.1 200 OK
```

**You just completed an HTTP request without a browser and without any library — just typing.**

> **Line by line**
>
> - **`telnet example.com 80`**: telnet is a tool that "sends your keystrokes to the other side verbatim". `80` is HTTP's default port (next section explains why)
> - **`GET / HTTP/1.1`**: the request line. Three parts — method `GET`, path `/`, version `HTTP/1.1`
> - **`Host: example.com`**: a request header. In HTTP/1.1 this line is **required** (lesson 04 explains why)
> - **The blank line**: this is the crucial bit. **An empty line marks the end of the headers.** Skip it and the server waits until it times out
> - **`HTTP/1.1 200 OK`**: the status line. `200` is the status code, `OK` the reason phrase

**If it's your first time, the most likely failure is forgetting that blank line.** That's not a trivial detail — it's a core convention of the HTTP message format, and it comes back constantly when we cover headers.

> **Windows users**: recent Windows doesn't install telnet by default; turn it on in "Turn Windows features on or off". If that's a hassle, lesson 11 does the same thing from Python.

### The Cost of Text

Plain text isn't free. Its downsides:

- **Verbose**. Headers run to hundreds of bytes, and repeated fields get re-sent every time
- **Slow to parse**. You scan characters, hunt for newlines, split strings
- **Ambiguous**. Handling spaces, newlines and encodings is error-prone — a common source of security bugs, such as request smuggling

**HTTP/2 later switched to binary precisely to fix these.** Lesson 05 covers that.

So it's a clear trade-off:

| | Text (HTTP/1.1) | Binary (HTTP/2) |
|---|---|---|
| Human-readable | ✅ you can telnet it | ❌ needs a tool |
| Size | Large | Small (compressed) |
| Parse speed | Slow | Fast |
| Debugging | Easy | Harder |

**Choosing text in 1990 was right** (easy to debug and implement). **Switching to binary in 2015 was also right** (performance had become the bottleneck). Technical choices aren't absolutely right or wrong — only "which hurts more at this stage".

## Port 80: A Number Fixed in 1990

You just connected to port 80. Why 80?

### What a Port Is

A machine has one IP address, but runs many network programs: web, mail, SSH…

The IP address gets you to the **right machine**; the port number gets you to the **right program on that machine**.

A port is a number from 0 to 65535.

### Why 80 for HTTP

80 is the "well-known port" that **IANA** (the Internet Assigned Numbers Authority, which runs global internet numbering) assigned to HTTP.

IANA maintains a table allocating 0-1023 to common services:

| Port | Service |
|---|---|
| 21 | FTP |
| 22 | SSH |
| 25 | SMTP (sending mail) |
| 53 | DNS |
| **80** | **HTTP** |
| 443 | HTTPS |

**That allocation happened when HTTP was still very young** — it was simply "pick a number nobody's using". No special meaning.

**But because it's the default, browsers use 80 whenever you omit the port.** Thirty-odd years later, the world's web traffic still runs on 80 and 443.

### Practical Meaning

**The default port can be omitted.** These are equivalent:

```
http://example.com:80/index.html
http://example.com/index.html        ← :80 omitted
```

Same for HTTPS, default 443.

**But a non-default port must be written out**:

```
http://localhost:8000/       ← common in local dev; 8000 is required
```

You'll see `localhost:8000` constantly when running local services or testing APIs. **Omit the port and it's 80; get it wrong and the connection is refused.**

## Statelessness: HTTP's Most Famous and Most Misread Property

You'll see it everywhere: **HTTP is a stateless protocol**.

### What That Means

**The server does not remember what you did in your last request.**

Every request stands alone. The server forgets once it has responded. When you send a second request, the server has **no idea** you sent a first one.

Concretely:

```
You:    GET /login  (with username and password)
Server: 200 OK, login succeeded
You:    GET /my-profile
Server: 200 OK, here's your profile
You:    GET /my-profile
Server: 200 OK, here's your profile
```

Notice the last two — **the server doesn't know who "you" are**. It didn't remember that you logged in.

### Why Design It That Way

Back to lessons 01 and 02: Berners-Lee's problem was **documents linking to each other**.

Fetch a document — one self-contained action. Done, the interaction ends. **No state needed at all.**

And statelessness has a huge upside: **simple and scalable**.

The server keeps nothing per client, which means:

- A server crash and restart doesn't affect any client
- A request can go to **any** server (hence load balancing, hence adding machines)
- No session expiry, no memory pressure

If HTTP had been stateful from the start, load balancing and multi-server deployment would be far harder.

### The Cost: State Got Bolted Back On

Statelessness is perfect for "fetch a document" and immediately insufficient for **login, shopping carts, personalization**.

So a series of mechanisms were added to fake state back:

- **Cookie** (lesson 10): the server makes the browser store a small piece of data and send it next time
- **Session**: the server stores the state and gives the browser only an ID
- **Token / JWT** (lesson 22): encode the state into a string the client carries

**All of these share one essence: attach extra information to the request so the server can "recognize you".**

Get this and you'll understand why API calls always carry an `Authorization` header — **because HTTP itself doesn't remember who you are; you must identify yourself every single time.**

### A Common Misunderstanding

Some people read "HTTP is stateless" as "HTTP can't keep a connection open".

**Those are different things.**

- **Stateless** is about **semantics**: the server doesn't record your identity or history
- **Persistent connections** (HTTP/1.1 keep-alive) are about **transport**: whether the TCP connection can be reused

HTTP/1.1 can reuse the TCP connection (lesson 04), but **each request is still semantically independent**. Reusing the connection only saves a handshake; the server still doesn't remember you.

## Request-Response: An Order That Can't Be Reversed

HTTP is a strict **request-response model**:

1. The client sends a request
2. The server sends a response
3. The exchange ends

**The server cannot initiate anything to the client.**

That limitation feels awkward today — push notifications, live chat, stock tickers all need the server to push. But HTTP had no such ability originally.

### How It Got Worked Around

To dodge "the server can't push", engineers came up with a series of tricks:

| Technique | How it works |
|---|---|
| **Polling** | The client asks "anything new?" every few seconds |
| **Long polling** | The client sends a request and the server **deliberately doesn't answer** until it has data |
| **SSE** | The server holds the connection and keeps pushing text |
| **WebSocket** | A different protocol that upgrades to a true two-way channel |

Note the first three are **still fundamentally request-response** — they just stretch out the "response". WebSocket is what actually escapes the model (it handshakes over HTTP, then is no longer HTTP).

### What It Means for Your Code

Your mental model when calling an API is always this:

```python
r = requests.get(url)        # ① send the request, then stop here and wait
print(r.status_code)         # ② only with a response in hand can you look
```

> **Line by line**
>
> - **①** This line **blocks**: the program stops here until the server responds or you time out. That's the request-response model showing up directly in your code — **send nothing and you receive nothing**
> - **②** The response is the answer to *this* request. Want it again? Send again. `r` never updates itself

**You can never write "wait for the server to notify me".** Only "I go ask".

## Why This Lesson Helps You Write Code

### 1. Layering Decides What You Can Control

HTTP can't see TCP. Therefore:

- **It doesn't know when the connection drops**, so it shows up only as a timeout → set `timeout`
- **Retransmission is TCP's job**, not HTTP's → you needn't write retry logic, but you must handle "waited too long"
- **It doesn't know the IP changed** → a phone switching from WiFi to 4G kills in-flight requests

### 2. Text Means You Can Look Yourself

When an API misbehaves later, your first move **shouldn't be editing code** — it should be **looking at what was actually sent and received**.

Because HTTP is text, that's easy — later you'll learn to print the raw message from Python.

**The great majority of "the API doesn't work" problems become obvious the moment you look at the raw message.** Wrong parameter, missing header, bad encoding — all instantly visible.

### 3. Statelessness Decides How Auth Is Written

Because the server doesn't remember you, **every request must carry identity**. That isn't one API's quirk; it's forced by HTTP's design, and every API does it.

### 4. The Default Port Saves Typing — and Bites

`localhost:8000`, `localhost:3000`, `localhost:8080` — local dev uses all sorts. **A wrong port is the most common cause of "connection refused"**, and the error message is rarely helpful.

## Recap

- **A protocol = syntax + semantics + timing**. API errors later are almost always one of these three mismatched
- HTTP is in the **application layer** (top of the TCP/IP model) and **can't see below**, so a dropped connection shows up only as a **timeout**
- Data gets **headers added going down** and **stripped going up**
- **HTTP/1.1 is a plain-text protocol** — chosen deliberately in 1990 for easy debugging and implementation, at the cost of verbosity and slow parsing (which is why HTTP/2 went binary)
- **You can send a request by hand with `telnet example.com 80`**: request line + headers + **one blank line** (forgetting it is the #1 beginner trap)
- **Port 80 is IANA-assigned**, no special meaning, just the default; HTTPS is 443; non-default ports must be written out
- **Stateless**: the server doesn't remember your last request. Simple and scalable, at the cost of needing Cookies or Tokens for login and carts
- **Stateless ≠ can't keep a connection**. keep-alive reuses the TCP connection; each request is still semantically independent
- **Request-response**: the server can't push. Polling, long polling and SSE stretch the response; WebSocket truly escapes
