# 05 HTTP/2 and HTTP/3: One Hole Filled, the Ground Collapses Again

> HTTP/2 used multiplexing to finally fix the head-of-line blocking left over from the last lesson. After launch, people found it was indeed faster — but once packets started dropping, it was worse than HTTP/1.1. The cause wasn't in HTTP; it was in TCP. Hence HTTP/3.

## Recap: Where Exactly 1.1 Got Stuck

The last lesson ended with a problem HTTP/1.1 couldn't avoid: **head-of-line blocking**.

On one connection, requests queue. Until the previous one returns, the rest wait.

Engineers' workaround: **open more connections** — browsers open 6 to 8 TCP connections per domain and spread requests across them.

### What That Cost

Opening more connections dodges the blocking, but at real cost:

- **Every connection pays a three-way handshake plus slow start** — 8 connections, 8 times
- **HTTP headers can't be shared between connections**; each one re-sends `User-Agent`, `Cookie`, `Accept` and the rest
- **The server maintains state for all 8**, doubling memory and CPU

**More importantly: that "6-8" is an empirical guess, not an optimum.** Too few requests and you waste them; too many and requests queue anyway.

By the 2010s it got worse:

- **Pages got heavier.** Hundreds of resources per page became normal
- **Mobile networks spread.** Phones have far higher latency and loss than wired networks, magnifying the handshake cost
- **HTTPS became universal.** Handshaking on top of TLS means more round trips

**The cost of every workaround finally exceeded the cost of switching protocols.**

## HTTP/2: 2015, RFC 7540

HTTP/2 was published in **May 2015** (RFC 7540), essentially the standardized version of Google's SPDY.

It made one very clever trade-off:

> **Don't change HTTP's semantics. Change only how it's transported.**

What does that mean?

- Methods are still `GET` / `POST`
- Status codes are still `200` / `404` / `500`
- Headers are still those fields
- URLs are still those URLs

**Only how those bytes get packaged and shipped changed.**

That trade-off matters enormously: **applications barely need to change code.** Your API paths, parameters and status-code logic all stay. Only the transport layer got swapped.

### Core Change 1: Binary Framing

HTTP/1.1 is text, line by line. HTTP/2 cuts everything into **frames**.

```
HTTP/1.1:  GET /index.html HTTP/1.1\r\nHost: ...\r\n\r\n
              ↑ plain text, parsed character by character

HTTP/2:    [HEADERS frame][DATA frame][DATA frame]
              ↑ binary, parsed frame by frame
```

Every frame has a fixed structure:

```
+-----------------------------------------------+
| Length (24 bits) | Type (8) | Flags (8)        |
+-----------------------------------------------+
| Stream Identifier (31 bits)                    |
+-----------------------------------------------+
| Frame Payload (Length bytes)                   |
+-----------------------------------------------+
```

Common frame types:

| Type | Purpose |
|---|---|
| `HEADERS` | Carries request or response headers |
| `DATA` | Carries the body |
| `SETTINGS` | Negotiates connection parameters |
| `RST_STREAM` | Cancels a stream |
| `PING` | Keepalive / latency measurement |

**Why go binary?**

- **Faster parsing.** Read fixed byte offsets instead of scanning for newlines
- **No ambiguity.** No "does this newline count as content?" edge cases — exactly the ambiguity behind HTTP/1.1 request smuggling
- **More compact**

**The cost**: humans can't read it. You can no longer telnet an HTTP/2 request by hand.

> **A real trade-off**: HTTP/2 sacrificed "debuggable by hand" for performance and safety. To debug HTTP/2 today you need a proper tool (Wireshark, or the Protocol column in browser DevTools).

### Core Change 2: Multiplexing

**The single most important change in HTTP/2, and how it fixes head-of-line blocking.**

In HTTP/1.1, requests on one connection must queue.

In HTTP/2, **many requests run concurrently on one connection** — each request is an independent **stream**, distinguished by the stream identifier in the frame header.

```
One TCP connection
├── Stream 1: request index.html
├── Stream 3: request style.css
├── Stream 5: request app.js
└── Stream 7: request logo.png
```

The frames of these streams are **interleaved**:

```
[stream1 HEADERS][stream3 HEADERS][stream1 DATA][stream5 HEADERS][stream3 DATA][stream1 DATA]...
```

The server reassembles by stream identifier. **Whichever stream finishes first sends its frames back first — no queueing.**

**Head-of-line blocking, solved.**

Compare:

| | HTTP/1.1 | HTTP/2 |
|---|---|---|
| Concurrent requests | via many connections | **many streams on one** |
| A slow request blocks others | Yes | **No** |
| Connections needed | 6-8 | **1** |
| Handshake cost | 6-8 times | **1 time** |

That's why HTTP/2 showed clear gains: **fewer handshakes, less slow start, no head-of-line blocking.**

### Core Change 3: Header Compression (HPACK)

Every HTTP/1.1 request carries a pile of repeated headers:

```
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) ...
Accept: text/html,application/xhtml+xml,...
Accept-Language: zh-CN,zh;q=0.9,...
Cookie: session=abc123; theme=dark; ...
```

That `User-Agent` line can be 100+ bytes, **re-sent verbatim on every request**.

Several hundred requests per page, and headers alone waste tens of KB.

HTTP/2 compresses headers with **HPACK**, based on:

**1. A static table**

The protocol ships with a built-in table of the 61 most common header fields. Sending `:method: GET` doesn't need the literal text — just a numeric index.

**2. A dynamic table**

Both ends maintain a table of headers seen on this connection. The second time the same content appears, only the index is sent.

**3. Huffman coding**

When a literal must be sent (a new cookie value, say), the string is Huffman-coded.

**Effect**: headers typically shrink by **50%-90%**. Sites with long cookies benefit most.

> **One detail worth noting**: the dynamic table is **maintained per connection**. That means HTTP/2 header compression **depends on the connection staying open** — one reason it tends to clash with store-and-forward middleboxes.

### Core Change 4: Server Push

In HTTP/1.1 the server could only respond passively.

HTTP/2 lets the server **push proactively**:

```
Client:  I want index.html
Server:  Here it is — and I know you'll also need style.css and app.js, so here are those too
```

Sounds great: it removes the round trip of "get HTML → parse → request CSS/JS".

**But in practice, server push failed.**

For very practical reasons:

- **It's hard for the server to know what the client has cached.** Push something already cached and you've purely wasted bandwidth
- **Implementation is complex**, and browser behaviour was inconsistent
- **CDNs and caching policies make that judgment harder still**

Result: **major browsers removed server push support one by one.** Chrome removed it in 2022.

> **This is the second "sounded great, failed" design in HTTP/2, after pipelining.** Worth remembering: speculative optimizations often become *negative* optimizations in the real world because the guess is wrong.
>
> The replacement is an older, dumber, more reliable mechanism: the `Link: rel=preload` response header — the server **hints** that the client should preload, rather than pushing.

### Core Change 5: Stream Priority

Each stream can carry a priority, telling the server "this one matters more".

HTML most important, CSS next, images last. The server can allocate bandwidth accordingly.

**Its real-world effect was limited too** — priority is advisory, the server may ignore it, and intermediate proxies may not forward it.

## HTTP/2's Problem: It Pushed the Blocking Down a Layer

After HTTP/2 launched, benchmarks showed something counter-intuitive:

**On good networks HTTP/2 is clearly faster. But when packet loss is high, HTTP/2 is *slower* than HTTP/1.1.**

Why?

### The Key: Head-of-Line Blocking at the TCP Layer

HTTP/2 fixed head-of-line blocking **at the application layer** — streams no longer queue behind each other.

But all those streams **share a single TCP connection**.

And TCP has one iron rule: **data must be delivered in order.**

TCP guarantees the byte stream arrives in the order sent. If a packet is lost mid-flight, TCP must wait for its retransmission — **even if all later data has already arrived, it cannot be handed to the application; it must wait.**

```
TCP layer:
  pkt1  pkt2  pkt3  pkt4  pkt5
        ↑ lost
        ↓
  pkt1  [wait]  pkt3 pkt4 pkt5  ← arrived, but can't be delivered
```

So in HTTP/2:

- Streams 1, 3, 5, 7 all interleave on **one TCP connection**
- One TCP packet lost → **every stream waits for that retransmission**
- The higher the loss rate, the longer the wait

**HTTP/1.1 had 6-8 connections: one stalls, the other 5-7 keep going.**
**HTTP/2 has one connection: stall it and everything stalls.**

That's why HTTP/2 is slower on lossy networks — **it put all the eggs in one basket**.

### Root Cause: TCP Can't Be Changed

You might think: then change TCP.

**It can't be changed.**

Two reasons:

**1. TCP lives in the operating system kernel.**

TCP is implemented in the kernel. Changing its behaviour requires **every operating system in the world to upgrade** — servers, clients, routers, firewalls. That cycle is measured in decades.

**2. Middleboxes "help".**

Many devices in the network path (firewalls, NATs, load balancers) inspect and even rewrite TCP packets. They have hard-coded assumptions about TCP's format. **Change the format and they treat it as illegal and drop it.**

This is called **protocol ossification**: the longer a protocol is used and the more middleboxes exist, the harder it is to change.

## HTTP/3: A New Foundation (2022)

Since TCP can't change, **don't use TCP**.

HTTP/3's answer: replace the transport with **QUIC** — a transport protocol **built on UDP**.

**June 2022, RFC 9114**: HTTP/3 formally standardized.

### Why UDP

UDP is extremely simple: **send the datagram; don't care about order, reliability, or retransmission.**

It's so simple there's almost nothing to change, which means:

- **Middleboxes assume the least about UDP** (it's too simple to assume much)
- **UDP's implementation is at the application layer** (not deep in the kernel), so it's easy to change

So QUIC's strategy:

> **Use UDP as the substrate (so it passes every middlebox), then re-implement a better reliable transport on top of it.**

**Move transport functionality out of the kernel and into user space.** Now it can change whenever, without waiting for OS upgrades.

### What QUIC Fixes

**1. Complete isolation of head-of-line blocking**

QUIC implements its own reliability, and does it **per stream**:

- Each stream has independent sequence numbers and retransmission logic
- **Stream 3 loses a packet → only stream 3 waits. Streams 1, 5, 7 are unaffected.**

That's true multiplexing — **isolated not just at the application layer, but at the transport layer too.**

**2. Faster connection setup**

TCP + TLS needs several round trips (TCP handshake, then TLS handshake).

QUIC **merges the transport and crypto handshakes**:

- First connection: **1 round trip** (1-RTT) to a secure connection
- Resumption: **0-RTT** — if the client cached the key, the very first packet can carry data

On mobile networks (high latency) that's a big win.

**3. Connection migration**

TCP identifies a connection by a 4-tuple: **(source IP, source port, dest IP, dest port)**.

Your phone switches from WiFi to 4G — **the IP changes, the connection breaks**, every in-flight request fails, and you re-handshake.

QUIC identifies a connection by a **connection ID**, independent of IP.

**The IP changes, the ID doesn't, the connection continues.** Transfers in progress survive a network switch.

That's a huge mobile win — no more requests dying in a lift, on the subway, or during a WiFi handoff.

**4. Mandatory encryption**

QUIC **has encryption built in and it cannot be turned off.** There's no such thing as plaintext QUIC.

Good for privacy, with a side effect: **middleboxes that rely on inspecting plaintext (some corporate firewalls) can't inspect QUIC**, and some networks simply block UDP 443.

### HTTP/3's Structure

```
HTTP/3 = HTTP/2's semantics + QUIC transport
```

That is:

- Methods, status codes, header semantics — **same as HTTP/2**
- Transport — TCP+TLS replaced by QUIC

**Your application code doesn't change.** That's deliberate: semantics unchanged, only the transport swapped.

### Current State

HTTP/3 adoption is growing fast, but isn't everywhere:

- Major browsers (Chrome, Firefox, Safari, Edge) all support it
- Big sites and CDNs (Google, Cloudflare, Facebook) have it on
- **Some networks block UDP**, making HTTP/3 unusable

**So real deployments do this: try HTTP/3, fall back to HTTP/2 on failure.** The negotiation happens through the HTTPS `Alt-Svc` response header.

## Transport Layer Comparison

| | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| Transport | TCP | TCP | **QUIC (UDP)** |
| Message format | Text | **Binary frames** | Binary frames |
| Concurrency per connection | 1 request | **Many streams** | Many streams |
| App-layer HOL blocking | Yes | **No** | No |
| **Transport**-layer HOL blocking | **Yes** | **Yes** | **No** |
| Header compression | None | **HPACK** | QPACK |
| Connection setup | TCP+TLS handshake | TCP+TLS handshake | **1-RTT / 0-RTT** |
| Network switch | Breaks | Breaks | **Connection migration** |

**Note the crucial row: transport-layer head-of-line blocking.** HTTP/2 didn't fix it; HTTP/3 did. That's why HTTP/3 exists at all.

## Why This Lesson Helps You Write Code

### 1. You Barely Need to Care Which Version Runs

One of the most important takeaways.

**HTTP/2 and HTTP/3 both deliberately keep semantics unchanged.** You write:

```python
r = requests.get("https://api.example.com/users")   # This line is identical under HTTP/1.1, 2, and 3
```

**Whether the wire speaks 1.1, 2, or 3, this line is the same.** Version negotiation happens automatically between client library and server.

(Strictly: Python's `requests` currently speaks only HTTP/1.1; you'd need something like `httpx` for HTTP/2. But **from your code's perspective, the API is identical**.)

### 2. Head-of-Line Blocking Explains Why Bulk Requests Need Concurrency

When you later send many requests, you'll find **doing them serially is slow**.

That's head-of-line blocking: **one slow request drags down everything behind it.**

The fix (lesson 29): use concurrency so several requests are in flight at once.

### 3. On Lossy Networks, "More Advanced" Isn't Always Faster

HTTP/2 is slower than 1.1 under heavy loss — a fact that should remind you:

**Benchmark under realistic conditions.** A conclusion drawn on your office WiFi may invert on a user's 4G.

### 4. Connection Migration Explains Why Mobile Fails So Often

Your phone app's request failing isn't necessarily the server's fault — **the IP may have changed and the TCP connection dropped.**

Which is why mobile clients need retry logic (lesson 24).

### 5. "Can't Be Changed" Is a Real Constraint

TCP isn't unchanged because nobody wanted to — it's because of **every kernel and every middlebox on earth**.

Understand that, and the next time you face "why doesn't this old system move to something better", you'll think: **sometimes tech debt isn't laziness; the migration cost is genuinely impossible.**

## Recap

- HTTP/1.1 dodged head-of-line blocking by **opening 6-8 connections**, at the cost of repeated handshakes, duplicated headers and doubled server state
- **HTTP/2 (2015, RFC 7540)** = standardized SPDY. **Semantics unchanged, transport changed**
- Four core changes: **binary framing**, **multiplexing** (many streams on one connection, fixing app-layer blocking), **HPACK header compression** (static + dynamic tables + Huffman, saving 50%-90%), and server push
- **Server push failed** (browsers removed it) — speculative optimizations often turn negative because the guess is wrong; `Link: rel=preload` is the reliable alternative
- **HTTP/2 did NOT fix TCP-layer head-of-line blocking**: all streams share one TCP connection, so one lost packet stalls everything. **On lossy networks HTTP/2 is slower than 1.1**
- **TCP can't be changed**: it's in the kernel, and middleboxes hard-code assumptions about its format (**protocol ossification**)
- **HTTP/3 (2022, RFC 9114)** replaces the transport with **QUIC (over UDP)** — UDP is simple enough that middleboxes assume little, so transport gets reimplemented in user space
- QUIC's four wins: **per-stream loss isolation** (true no-HOL), **1-RTT/0-RTT setup**, **connection migration** (survives network switches), mandatory encryption
- **HTTP/3 = HTTP/2 semantics + QUIC transport**; application code doesn't change
- Real deployments: try HTTP/3, fall back to HTTP/2 (negotiated via `Alt-Svc`)
