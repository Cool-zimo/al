# 28 Rate Limiting: Why Your Program Suddenly Gets 403

> Your script runs fine, then every request starts returning 403. You check the token — fine. You check permissions — fine. **You've been rate-limited** — this lesson covers why servers limit you, how to see your remaining quota, how long to wait once limited, and **a timestamp trap that catches 90% of people**.

## First, Tell the Two "Forbidden"s Apart

When rejected, the status code decides what you do:

| Status | Meaning | Retry? |
|---|---|---|
| **401** | Not authenticated / invalid token | ❌ Retrying is pointless; fix auth first |
| **403** | **Authenticated, but not allowed** | ⚠️ Depends on the cause |
| **429** | **Too many requests** | ✅ Wait, then retry |
| **403 + rate-limit headers** | **Rate-limited** (many APIs use 403 for this) | ✅ Wait |

**The key trap**: **429 is the dedicated rate-limit status, but many APIs signal rate limiting with 403.** GitHub is one of them.

So you can't go by status code alone — **check the headers**:

```python
import requests

r = requests.get("https://api.github.com/rate_limit", timeout=10)
print(r.status_code)
print(r.headers.get("X-RateLimit-Remaining"))    # remaining quota
```

**Rule of thumb**: on a 403 or 429, **look for rate-limit headers first** before you go auditing permissions.

## Why Rate Limits Exist

Not stinginess — three very practical reasons:

**One: stop one user from dragging down the service.**

An API serves hundreds of thousands of users at once. If one user writes an infinite loop sending 1000 requests per second, **everyone else's experience degrades**. Limits guarantee "each user gets at most this much."

**Two: prevent abuse and scraping.**

Without limits, one person could copy the entire database in minutes.

**Three: cost.**

Bandwidth and CPU cost money. **Unlimited free quota doesn't exist.**

## GitHub's Limits

GitHub makes a good example because it's typical and you can try it right now:

| Scenario | Quota |
|---|---|
| **Unauthenticated** (no token) | **60/hour** |
| **Authenticated** (with token) | **5000/hour** |

**60/hour** — what does that mean? **One request per minute on average.** A few manual clicks and you're over.

That's why **nearly every tutorial tells you to configure a token** — not for "security," simply to **go from 60 to 5000**.

### Check Your Own Quota

```python
import requests
import os

token = os.environ.get("GITHUB_TOKEN", "")       # ① read from env
headers = {"Authorization": f"Bearer {token}"} if token else {}

r = requests.get("https://api.github.com/rate_limit", timeout=10, headers=headers)
data = r.json()

core = data["resources"]["core"]
print(f"limit     : {core['limit']}")               # 5000 or 60
print(f"remaining : {core['remaining']}")
print(f"reset     : {core['reset']}")
```

**Typical output**:

```
limit     : 5000
remaining : 4987
reset     : 1761091200
```

> **Line-by-line**
>
> - **① `os.environ.get(...)`**: **never hardcode a token** (lesson 22)
> - **`core['reset']`** is a **10-digit integer second-level timestamp**, e.g. `1761091200`. **This is UTC** — the next section shows how badly that trips people up

### The Three Rate-Limit Headers

Every response carries them:

| Header | Meaning |
|---|---|
| `X-RateLimit-Limit` | Total quota (5000) |
| `X-RateLimit-Remaining` | **How many calls are left** |
| `X-RateLimit-Reset` | **Timestamp when the quota resets** |

```python
r = requests.get("https://api.github.com/user", timeout=10, headers=headers)

print(r.headers.get("X-RateLimit-Limit"))        # 5000
print(r.headers.get("X-RateLimit-Remaining"))    # 4986
print(r.headers.get("X-RateLimit-Reset"))        # 1761091200
```

**These three come with every response** — no extra request needed.

## The Trap 90% Fall Into: reset Is a UTC Timestamp

How do you read `X-RateLimit-Reset: 1761091200`?

**It's a Unix timestamp in UTC** (seconds since 1970-01-01 00:00:00 UTC).

### The Wrong Way: Comparing Against Local Time

```python
# ❌ Wrong
import time
reset = int(r.headers["X-RateLimit-Reset"])
if reset > time.time():          # ① looks right — is it?
    time.sleep(reset - time.time())
```

> - **① `time.time()` also returns a Unix timestamp** (UTC-based), **so this comparison is actually fine** — as long as you don't convert to a local-time string and back

**The real trap lies in two things: "displaying" and "computing how many seconds to wait"**:

```python
# ❌ Wrong: sleeping on it as if it were "how long to wait"
reset = int(r.headers["X-RateLimit-Reset"])
time.sleep(reset)          # sleeping 1761091200 seconds ≈ 55 years!!!
```

**This mistake is silly but genuinely happens**: `reset` is an **absolute timestamp** ("when it resets"), not **a relative duration** ("how much longer").

### The Right Way

```python
import time
from datetime import datetime, timezone

reset = int(r.headers["X-RateLimit-Reset"])

# ① How many seconds left to wait
wait = reset - time.time()
print(f"wait {max(0, int(wait))} more seconds")

# ② Convert to a readable time (UTC)
print(datetime.fromtimestamp(reset, tz=timezone.utc))
# 2025-10-22 08:00:00+00:00

# ③ Convert to local time (UTC+8)
from datetime import timedelta
local = datetime.fromtimestamp(reset, tz=timezone(timedelta(hours=8)))
print(local)
# 2025-10-22 16:00:00+08:00
```

> **Line-by-line**
>
> - **① `reset - time.time()`**: both are UTC-based timestamps, **so the difference is seconds**. `max(0, ...)` prevents a negative when it's already past
> - **② `datetime.fromtimestamp(reset, tz=timezone.utc)`**: **you must pass `tz`.** Without it Python uses **your system's local timezone** — off by 8 hours, so you'd think "8 more hours" when it already reset
> - **③ UTC+8**: `timezone(timedelta(hours=8))`

**One line to remember**: **`X-RateLimit-Reset` is a "when," not a "how long."**

## Check Proactively: Don't Wait to Be Rejected

**The best rate-limit handling is not getting limited.**

```python
import requests
import time
import os

class RateLimiter:
    """Proactively check GitHub quota; wait when it runs low"""

    def __init__(self, session, min_remaining=10):
        self.s = session
        self.min_remaining = min_remaining      # ① wait below this

    def check(self, response):
        """Call after each request; waits if needed"""
        remaining = response.headers.get("X-RateLimit-Remaining")
        if remaining is None:
            return                              # ② no header, nothing to do

        remaining = int(remaining)
        if remaining >= self.min_remaining:
            return                              # ③ plenty left, carry on

        reset = int(response.headers["X-RateLimit-Reset"])
        wait = reset - time.time() + 1          # ④ +1s safety margin
        if wait > 0:
            print(f"only {remaining} left, waiting {int(wait)}s")
            time.sleep(wait)
```

**Usage**:

```python
with requests.Session() as s:
    s.headers.update({"Authorization": f"Bearer {os.environ['GITHUB_TOKEN']}"})
    limiter = RateLimiter(s)

    for i in range(200):
        r = s.get(f"https://api.github.com/repos/Cool-zimo/repo{i}", timeout=10)
        limiter.check(r)        # ① check after every request
        if r.status_code == 200:
            print(r.json()["full_name"])
```

> **Line-by-line**
>
> - **① `min_remaining=10`**: **leave a buffer.** Acting only at 0 is too late — concurrent requests may be in flight
> - **② Skip if the header is absent**: not every API provides one
> - **④ `+1` second**: the server's reset may lag a few seconds; the extra second avoids "just woke up and got rejected again"

## Reacting Passively: Read Retry-After on a 429

**However careful you are, you'll get limited eventually.** The right response then is **do what the server says**.

The server tells you how long to wait:

```
HTTP/1.1 429 Too Many Requests
Retry-After: 60
```

**`Retry-After` is "how many more seconds"** (a **relative** value this time — different from `X-RateLimit-Reset`!).

```python
import requests
import time

def fetch_with_retry(url, headers=None, max_wait=300):
    """On rate limit, wait per Retry-After then retry"""
    for attempt in range(5):
        r = requests.get(url, headers=headers, timeout=10)

        if r.status_code == 429:                          # ① explicit rate limit
            wait = int(r.headers.get("Retry-After", 60))  # ② server says how long
            if wait > max_wait:
                print(f"would wait {wait}s, too long, giving up")
                return None
            print(f"rate limited, waiting {wait}s")
            time.sleep(wait)
            continue                                      # ③ retry

        if r.status_code == 403:                          # ④ some APIs use 403
            remaining = r.headers.get("X-RateLimit-Remaining")
            if remaining == "0":                          # ⑤ confirm it's a limit
                reset = int(r.headers["X-RateLimit-Reset"])
                wait = min(reset - time.time() + 1, max_wait)
                print(f"quota exhausted, waiting {int(wait)}s")
                time.sleep(max(0, wait))
                continue
            # Not a limit — a genuine permissions problem
            print("403 but not rate limiting, check permissions")
            return None

        r.raise_for_status()
        return r

    return None
```

> **Line-by-line**
>
> - **① `429`**: the standard "too many requests"
> - **② `Retry-After`**: **relative seconds** — feed it straight to `time.sleep()`. **Note the difference from `X-RateLimit-Reset` (absolute timestamp)**
> - **③ `continue`**: back to the top of the loop to retry
> - **④ `403`**: **crucial** — don't assume every 403 is permissions
> - **⑤ `remaining == "0"`**: **this is how you tell whether a 403 is rate limiting.** With 500 left, a 403 means you genuinely lack access

**The difference between the two "waits" — the most important comparison in this lesson:**

| Header | Value type | How to use |
|---|---|---|
| `Retry-After` | **relative seconds** | `time.sleep(wait)` |
| `X-RateLimit-Reset` | **absolute timestamp** | `time.sleep(reset - time.time())` |

## Implementing Your Own Send-Rate Control

Beyond "wait until the quota runs out," a better approach is **actively controlling your send rate** so the program runs evenly start to finish.

### Simplest: Fixed Interval

```python
import time
import requests

def fetch_slowly(urls, delay=0.5):
    """Fixed delay seconds between requests"""
    results = []
    with requests.Session() as s:
        for i, url in enumerate(urls):
            if i > 0:                    # ① no wait before the first
                time.sleep(delay)
            r = s.get(url, timeout=10)
            results.append(r)
    return results
```

**Pro**: simple; works for APIs without explicit quota headers
**Con**: **slow.** 5000 requests × 0.5s = 42 minutes

### Smarter: Token Bucket

**Idea**: imagine a bucket that gains N "tokens" per second. Sending a request takes one token; **no token means wait**.

**Benefit**: it caps the average rate while still allowing short bursts (tokens accumulate while idle).

```python
import time
import threading

class TokenBucket:
    """Token bucket rate limiter"""

    def __init__(self, rate, capacity=None):
        """
        :param rate: tokens added per second (average rate)
        :param capacity: bucket capacity (allowed burst), defaults to rate
        """
        self.rate = rate
        self.capacity = capacity or rate
        self.tokens = self.capacity          # ① start full
        self.last = time.time()
        self.lock = threading.Lock()         # ② thread safety

    def _refill(self):
        """Add tokens based on elapsed time"""
        now = time.time()
        elapsed = now - self.last            # ③ time since last refill
        self.tokens = min(                   # ④ refill but don't overflow
            self.capacity,
            self.tokens + elapsed * self.rate
        )
        self.last = now

    def acquire(self, count=1):
        """Take count tokens, blocking until available"""
        with self.lock:                      # ⑤ lock it
            self._refill()
            if self.tokens < count:
                # figure out how long to wait
                deficit = count - self.tokens
                wait = deficit / self.rate
                time.sleep(wait)             # ⑥ sleep it off
                self._refill()

            self.tokens -= count             # ⑦ deduct
```

**Usage**:

```python
bucket = TokenBucket(rate=10)        # at most 10 requests/second

for url in urls:
    bucket.acquire()                 # ① take a token (may wait)
    requests.get(url, timeout=10)
```

> **Line-by-line**
>
> - **① Starts full**: so **you can burst up to `capacity` at the start**, after which the average rate applies
> - **② `threading.Lock`**: under threads, `_refill` and `acquire` must not interleave (shared mutable state — lesson 26)
> - **③ `elapsed`**: time since the last refill
> - **④ `min(capacity, ...)`**: **stop accumulating at full** — otherwise idling an hour leaves 36000 tokens, i.e. no limit at all
> - **⑥ `time.sleep(wait)`**: **note this blocks.** In async code use `await asyncio.sleep()` (lesson 29)
> - **⑦ Deduct**

**Why `capacity` exists**: real workloads are usually "steady trickle, occasionally a burst." Bucket capacity lets you bank a little credit and spend it at once.

## GitHub's Secondary Limits (Easy to Miss)

Beyond 5000/hour, GitHub has **secondary limits** specifically against short bursts:

- **Max 100 points per minute** (different operations cost different points)
- **Max 100 concurrent requests**
- **Max 80 content writes per second**

**What violating them looks like**: **403 or 429 while `X-RateLimit-Remaining` still shows thousands.**

```python
# Hit this case: quota clearly remains, yet rejected
print(r.headers.get("X-RateLimit-Remaining"))    # 4986  ← plenty left!
print(r.status_code)                             # 403
```

**What to do**: **don't retry — slow down.** Secondary limits are solved by going slower, not by waiting an hour.

```python
# "Quota remains but rejected" → slow down instead of waiting for reset
if r.status_code in (403, 429) and int(r.headers.get("X-RateLimit-Remaining", 0)) > 100:
    print("secondary limit, slowing down")
    time.sleep(5)          # just go slower
```

## Crash Site

### Crash One: Treating a Rate-Limit 403 as a Permissions Problem

```python
# ❌ Wrong call
r = requests.get(url, headers=headers)
if r.status_code == 403:
    print("no permission!")           # may not be permissions at all
    return None
```

**Symptom**: the program "mysteriously" decides every resource is forbidden, while you can access them fine in a browser.

**Cause**: conflating rate-limit 403s with permission 403s.

**Lesson**: **on a 403, always read `X-RateLimit-Remaining`.** Zero means rate limit; non-zero means permissions.

### Crash Two: Treating reset as "How Long to Wait"

```python
# ❌ Disaster
reset = int(r.headers["X-RateLimit-Reset"])
time.sleep(reset)          # sleeps 55 years
```

**Symptom**: the program "hangs"; you blame the network and kill it.

**Cause**: `reset` is an absolute timestamp (~1.7 billion seconds), not a duration.

**Lesson**: **`time.sleep(reset - time.time())`**, and clamp with `max(0, ...)`.

### Crash Three: Parsing reset With Local Timezone

```python
# ❌ Wrong
import datetime
reset = int(r.headers["X-RateLimit-Reset"])
print(datetime.datetime.fromtimestamp(reset))     # uses system local timezone
# 2025-10-22 16:00:00    ← you think it's UTC, it's local
```

**Symptom**: computed wait is off by 8 hours (in China). **May show up as "waited too long" or "still limited after waking."**

**Note**: the **subtraction** `reset - time.time()` is correct (both UTC-based). **What's wrong is displaying it as a readable time without specifying a timezone.**

**Lesson**: when displaying, **pass `tz=timezone.utc` explicitly**.

### Crash Four: Concurrent Requests Ignoring the Limit

```python
# ❌ 50 threads at once, quota gone in seconds
from concurrent.futures import ThreadPoolExecutor

with ThreadPoolExecutor(max_workers=50) as ex:
    ex.map(lambda u: requests.get(u, headers=headers), urls)
```

**Symptom**: the 5000/hour quota is burned in seconds, then everything 403s.

**Cause**: **limits are per-account, not per-thread.** 50 threads are fast, but there's only one quota.

**Lesson**: **concurrency must be paired with rate limiting.** Share one token bucket across threads (so lock it), or just lower concurrency. That's the focus of lesson 29.

### Crash Five: Ignoring Retry-After and Guessing

```python
# ❌ Guessing a duration
if r.status_code == 429:
    time.sleep(1)          # the server clearly said 60 seconds
```

**Symptom**: retry → 429, retry → 429… **and the ban gets longer.**

**Cause**: **the server told you exactly how long; you didn't listen.**

**Lesson**: **always prefer `Retry-After`.** Fall back to exponential backoff (lesson 24) only when it's absent. **Some servers penalize non-compliant clients harder.**

## Why This Matters for Your Code

**One: Limits aren't obstacles — they're part of the contract.**

Quota, rate, concurrency caps: these are as much a part of the API contract as URLs and parameters. "It works" isn't "it's used correctly." **A program that ignores rate limits isn't "fast," it's "about to stop working."**

**Two: The server tells you what to do — learn to read it.**

`X-RateLimit-*` and `Retry-After` exist precisely so clients can self-regulate. Ignoring them and guessing is throwing away a free source of truth.

**Three: "When" and "how long" are different things.**

This is the hidden theme of the lesson. `X-RateLimit-Reset` is a moment; `Retry-After` is a duration, **and they're handled completely differently**. This distinction is everywhere: absolute vs relative time, Unix timestamp vs interval. **See a number, ask: is it "when" or "how long"?**

## Summary

- **401 / 403 / 429**: 401 unauthenticated; 403 may be permissions or rate limit; **429 is explicitly rate limiting**
- **Is that 403 a rate limit?** Check `X-RateLimit-Remaining`; 0 means rate limit
- **GitHub quota**: 60/hour unauthenticated, 5000/hour authenticated
- **`X-RateLimit-Reset` is an absolute UTC timestamp** ("when it resets"); **`Retry-After` is relative seconds** ("how much longer")
- **Correct wait**: `time.sleep(max(0, reset - time.time() + 1))` — **never `sleep(reset)`**
- **Display timestamps with an explicit timezone**: `datetime.fromtimestamp(reset, tz=timezone.utc)`
- **Proactive beats reactive**: check `remaining` after each request; wait early when it drops below a threshold
- **Token bucket**: `rate` caps the average, `capacity` allows bursts, lock it under threads
- **GitHub secondary limits**: rejected with quota remaining → secondary limit, **slow down, don't wait for reset**
- **Concurrency doesn't add quota**: limits are per-account; 50 threads just exhaust it faster
- ❌ Don't read a limit 403 as permissions; don't `sleep(reset)`; don't ignore timezones; don't ignore Retry-After
