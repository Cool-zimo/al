# 06 Methods & Idempotency: Why Refreshing Pops Up "Resubmit?"

> You've seen this: fill in a form, click submit, then hit F5 — and the browser immediately warns "Confirm Form Resubmission?". Refresh a normal article and nothing happens. Why the difference? Because the browser knows the last request was a POST, and doing it twice might have consequences. This lesson unpacks the whole set of conventions behind that.

## A World With Only GET

Back to HTTP/0.9 from Lesson 04. That version of the protocol had **exactly one method: GET**.

The entire request was one line:

```text
GET /index.html
```

No headers, no version number, nothing but that. Why? Because the web back then did one thing: **fetch documents**.

No login boxes, no shopping carts, no comment sections, no "like" buttons. Pages were read-only — someone wrote an HTML file with an editor, put it on a server, and others fetched it with a browser. **"Fetch" was the only operation, so one method was enough.**

That held until 1993, when Marc Andreessen and Eric Bina built the Mosaic browser at NCSA and added one thing: **`<form>`**. Users could type into a web page and submit it.

Trouble: **how should the submitted data be sent?**

GET could do it — append fields to the URL:

```text
GET /search?q=python
```

But that has real problems:

1. **URLs have length limits**. Early servers and browsers imposed all kinds of caps (Internet Explorer famously stopped at 2083 characters), so a long essay would be silently truncated
2. **Everything is exposed in the URL**. Passwords, body text, long passages — all visible in the address bar and saved into browser history
3. **The semantics are wrong**. "Search" really is just fetching, but "place an order" is clearly not fetching — you're asking the server to **do something**

So HTTP/1.0 (RFC 1945, 1996) added two methods:

- **POST** — I'm submitting data, please process it
- **HEAD** — same as GET, but **headers only, no body**

HTTP/1.1 (RFC 2616, 1999) added another batch:

- **PUT** — **completely replace** the resource with what I'm sending
- **DELETE** — remove this resource
- **OPTIONS** — which methods do you support?
- **TRACE** — echo my request back to me (for debugging proxies; effectively disabled today due to security risks)
- **CONNECT** — build me a tunnel (mainly for HTTPS proxies)

**PATCH** came much later as its own RFC 5789, published March 2010 — a full 11 years after HTTP/1.1. It solved: "I only want to change one field, why must I resend the whole object?"

## A Method Is Not a Function Name — It's a Statement of Intent

This is the most common misunderstanding, so let's settle it first:

> **A method tells the server "what I intend to do", but the server is free to ignore it.**

```
GET    /users/123      →  I'm here to read; don't change anything
DELETE /users/123      →  I want this deleted
```

After receiving `GET /users/123`, the server **technically can delete user 123 as a side effect**. Nothing stops it. HTTP is a **convention**, not an **enforcement mechanism**.

Then what's the convention worth? A lot:

1. **Browsers use it to decide whether to warn you** (that popup from the intro)
2. **Caches use it to decide whether caching is allowed** (GET responses may be cached; POST responses should not be)
3. **Crawlers use it to decide what's safe to visit** (well-behaved crawlers never follow a DELETE link)
4. **Middleware uses it to decide whether auto-retry is safe** (you'll see why this matters in a moment)

So the value of methods isn't enforcement — it's **letting every party in the chain predict your behavior**.

## Two Orthogonal Properties: Safe vs Idempotent

The HTTP spec defines two properties for each method. People use these words interchangeably, but they are **completely different things**.

### Safe

> Safe methods **should not** change server state.

In other words, safe methods are meant to be read-only. GET, HEAD, OPTIONS, and TRACE are safe.

Note the wording is "should not" — as above, the server can still misbehave. But from the caller's perspective, **you should not expect a safe method to change anything**.

### Idempotent

From Latin (*idem* "same" + *potens* "power"). The definition:

> An idempotent method: doing it 1 time and doing it N times leaves the server in **the same final state**.

Note the key phrase: **final state, not response body**.

Example, `DELETE /users/123`:

```
1st call: user exists → deleted → returns 200, user gone
2nd call: user doesn't exist → returns 404, user still gone
```

The two **responses differ** (200 vs 404), but the **server state is identical** (user absent both times). So DELETE is idempotent.

This distinction is crucial. Many people first learn "idempotent" as "returns the same result," and then can't figure out why DELETE qualifies.

### Quick Reference

| Method | Safe | Idempotent | In one line |
|---|---|---|---|
| `GET` | ✅ | ✅ | read, don't change |
| `HEAD` | ✅ | ✅ | headers only, don't change |
| `OPTIONS` | ✅ | ✅ | ask what's supported, don't change |
| `TRACE` | ✅ | ✅ | echo the request (mostly disabled now) |
| `POST` | ❌ | ❌ | submit, changes things, repeats have effects |
| `PUT` | ❌ | ✅ | full replace; N times = same result |
| `PATCH` | ❌ | ❌ (not guaranteed) | partial update; depends on semantics |
| `DELETE` | ❌ | ✅ | delete; N times = same result |

`POST` is the only commonly used method that is **neither safe nor idempotent**. That's not a design flaw — it's exactly **what it's for**. When you need something that produces a new effect every time (place an order, post a message), POST is correct.

## What Idempotency Is Actually Worth: Retry

Back to the end-to-end principle from Lesson 01. The network is **unreliable**, and the network layer deliberately doesn't handle reliability, so:

> You send a request. It **times out**. Did the server receive it? **You will never know.**

Either the request never arrived, or it arrived, the work was done, and the response was lost on the way back. **These two are indistinguishable to you**: both are just "timeout."

You have two options:

1. **Don't retry** — fine if it was case two (work already done)
2. **Retry** — if it was case two, you just **did it twice**

**If the request is idempotent, you can retry with your eyes closed.** One call and N calls leave the same state, so extra attempts cost nothing.

**If it's not idempotent, retrying is a gamble.** User clicks "Pay", it times out, you retry — the user is charged twice.

That's the entire practical meaning of idempotency: **it makes uncertainty manageable.**

In real systems, to let non-idempotent operations retry safely, people attach an **idempotency key**:

```python
import uuid                       # ① stdlib for unique IDs
import requests

key = str(uuid.uuid4())           # ② generate a globally unique random string

r1 = requests.post(               # ③ first attempt
    "https://api.example.com/orders",
    json={"item": "book", "qty": 1},
    headers={"Idempotency-Key": key},   #    attach the key
    timeout=10,
)

# Suppose this times out — you don't know if the order exists
r2 = requests.post(               # ④ retry: same key
    "https://api.example.com/orders",
    json={"item": "book", "qty": 1},
    headers={"Idempotency-Key": key},   #    ★ critical: same key
    timeout=10,
)
```

> **Line-by-line**
>
> - **①** `uuid` is in the standard library — no `pip install` needed. It exists purely to generate unique identifiers
> - **②** `uuid4()` produces a **random** UUID (version 4); collision probability is low enough to treat as zero in practice. `str()` is required because HTTP header values must be strings
> - **③** The first request carries the `Idempotency-Key` header. The server records that key and associates it with the order it creates
> - **④** On retry you **must reuse the same key**. The server looks it up: "I've already processed this key" → it **does not create a second order**, it returns the previous result

**Note**: `Idempotency-Key` is not an HTTP standard header — it's an industry convention (Stripe, PayPal, and most payment APIs use it). The server has to support it explicitly; it won't work by magic.

## PUT vs PATCH: Full Replace vs Partial Update

These two are the easiest to confuse. Concretely:

User `123` currently is:

```json
{"id": 123, "name": "Alice", "email": "alice@example.com", "age": 30}
```

### PUT: send the complete new object

```python
requests.put(
    "https://api.example.com/users/123",
    json={"id": 123, "name": "Alicia", "email": "alice@example.com", "age": 30},
)
```

You must send **every field**, even if you only changed `name`. Fields you omit should, by convention, be **cleared or reset to defaults**.

**Why is it idempotent?** One call makes it A; ten calls still make it A. State unchanged.

### PATCH: send only the fields to change

```python
requests.patch(
    "https://api.example.com/users/123",
    json={"name": "Alicia"},          # one field only
)
```

Send just the one you're changing.

**Why isn't it guaranteed idempotent?** It depends on what "change" means:

```
{"name": "Alicia"}         → idempotent. Setting 1 or 10 times is the same
{"age": 30}                → idempotent. All "set to value" ops are
{"balance": "+100"}        → NOT idempotent. 10 calls add 1000
{"tags": ["a"]}            → depends: append or overwrite?
```

**Rule of thumb**: if the PATCH means **"set it to this value"**, it's idempotent. If it means **"add/subtract from the current value"**, it isn't.

That's why the spec says PATCH is "not guaranteed idempotent" — it depends on the semantics of the data you send.

## Code: Methods in requests

`requests` provides a same-named function for every method, but **they all funnel into one entry point**:

```python
import requests                    # ① import the library

# ② seven methods, one function each
requests.get(url)                  #     GET    — fetch a resource
requests.post(url, json=...)       #     POST   — submit
requests.put(url, json=...)        #     PUT    — full replace
requests.patch(url, json=...)      #     PATCH  — partial update
requests.delete(url)               #     DELETE — remove
requests.head(url)                 #     HEAD   — headers only
requests.options(url)              #     OPTIONS— ask what's supported

# ③ they're all thin wrappers around this generic function
requests.request("GET", url)       #     identical to requests.get(url)
requests.request("POST", url, json=...)
```

> **Line-by-line**
>
> - **①** Same as always: `requests` is third-party, install it with `pip install requests`
> - **②** These seven functions exist **only to save you keystrokes** — `requests.get(u)` beats `requests.request("GET", u)`. Their parameters are identical
> - **③** `requests.request()` is the real entry point. First argument is the method name as a string. **When you need to treat the method as a variable** (e.g. building a tool that can send anything), use this

Point two deserves emphasis: in Lesson 30, when you build a command-line HTTP tool, the user's `GET` / `POST` input will be a **string**. `requests.request(method_str, url)` is far cleaner than a long `if method == "GET": ... elif ...` chain.

### HEAD: headers only, skip the whole download

A HEAD response has **no body** — only the status line and headers. Its classic use: **look first, then decide whether to download**.

```python
import requests

r = requests.head(                      # ① HEAD, not GET
    "https://api.github.com/repos/psf/requests",
    timeout=10,
)

print(r.status_code)                    # ② 200 means the resource exists
print(r.headers.get("Content-Length"))  # ③ size in bytes, without downloading
print(r.headers.get("Content-Type"))    # ④ what kind of thing it is
print(len(r.content))                   # ⑤ always 0 — HEAD has no body
```

> **Line-by-line**
>
> - **①** Swap `get` for `head` and change nothing else. That's the value of method semantics: **change the method = change the intent, nothing else**
> - **②** HEAD's status code matches GET's. 404 means missing, 403 means no permission — **you can tell without downloading the body**
> - **③** `Content-Length` is what the server **claims**. **It's a claim, not a guarantee** — servers can lie, or omit it entirely (it's absent with chunked transfer). That's why we use `r.headers.get(...)` instead of `r.headers[...]`: missing yields `None` rather than `KeyError`
> - **④** `Content-Type` tells you whether it's JSON, HTML, or an image
> - **⑤** `r.content` is always `b""`. Not a bug — that's HEAD's definition: **same response structure as GET, minus the body**

**Real use**: writing a bulk downloader? HEAD first to get the size, skip anything over 100MB — **you just saved the entire transfer**. That's why HEAD exists.

### OPTIONS: ask what the server supports

```python
import requests

r = requests.options(              # ① send OPTIONS
    "https://api.github.com/user",
    timeout=10,
)

print(r.headers.get("Allow"))      # ② methods the server permits
print(r.headers.get("Access-Control-Allow-Methods"))  # ③ CORS-related
```

> **Line-by-line**
>
> - **①** OPTIONS is safe, so feel free to send it — it shouldn't change anything
> - **②** `Allow` is the standard response header for OPTIONS, listing supported methods for that resource, e.g. `GET, HEAD, PATCH`. **Many servers don't send it**, so getting `None` is normal, not an error
> - **③** In cross-origin (CORS) scenarios, browsers automatically send an OPTIONS **preflight** first, and only send the real request once the server permits it. **Those mysterious OPTIONS requests you see in devtools are this**

## Crash Site

### Crash 1: passing a password via GET

```python
# ❌ Wrong
requests.get("https://api.example.com/login?user=admin&password=123456")
```

**Symptom**: works fine, login succeeds, tests all pass. Three months after launch, you discover the password is sitting in at least five places:

1. **The browser address bar** (a colleague walking by sees it plainly)
2. **Browser history** (anyone who opens your laptop can see it)
3. **Server access logs** (plaintext in `/var/log/nginx/access.log`)
4. **Proxy / CDN logs** (every intermediate device records it)
5. **The `Referer` header** (if the page contains any external image, the browser sends the full URL as Referer to that third-party site)

**Cause**: URLs were never designed to carry sensitive data. A URL is "the address of a resource" — a public, visible identifier.

**Lesson**: passwords, tokens, ID numbers — **belong in the body or headers, never in the URL**.

### Crash 2: implementing delete as GET

```python
# ❌ Wrong: delete via GET
requests.get("https://api.example.com/users/123/delete")
```

**Symptom**: local testing is flawless. After launch, user data starts vanishing inexplicably.

**Cause**: GET is a safe method, and everyone treats it as safe:

- **Browser prefetching**: modern browsers pre-fetch links on the page — visited before the user ever clicks
- **Crawlers**: search engines crawl every GET link they find
- **Caches**: a CDN may cache that URL's response, so the second visit never even reaches your server
- **History**: a user misclicks that address in history and something gets deleted

**Lesson**: **GET is for reading only. Any state change belongs in POST / PUT / DELETE / PATCH.**

The irony: **you wrote a delete link, someone "normally" visited it, and data was gone.** You can't blame them — you broke the convention first.

## Why This Matters for Your Code

Tying this back to earlier lessons:

1. **It connects directly to the end-to-end principle (Lesson 01)**. Network unreliable → you must handle timeouts → you must decide whether to retry → **idempotency decides whether retrying is safe**. The whole chain is linked
2. **Pick the wrong method and the bug surfaces late**. Delete-as-GET never fails locally — locally there are no crawlers, no CDNs, no prefetching. You find out when a search engine crawls your data away
3. **Idempotency is designed, not innate**. POST is born non-idempotent, but one `Idempotency-Key` header makes it retryable. **When you need reliable retries, think of this first**
4. **Remember `requests.request()`**. When your tool needs to pass the method as a variable, it's the only option

## Summary

- HTTP/0.9 had only **GET** because the web was read-only. POST arrived with forms
- **Methods declare intent, they don't enforce it**. Servers can violate them, but browsers, caches, and crawlers all rely on the convention
- **Safe** = doesn't change state; **idempotent** = 1 call and N calls leave the **same final state**. Orthogonal concepts
- DELETE is idempotent even though the second call returns 404 — **idempotency is about state, not response**
- **Idempotency's whole value: it lets you retry safely.** Networks are unreliable; this is a hard requirement
- **PUT replaces wholesale (idempotent); PATCH modifies partially ("set" is idempotent, "increment" is not)**
- The seven `requests` methods are all wrappers for `requests.request(method, url)`
- **HEAD returns headers without a body** — learn the size without downloading
- ❌ **Never put sensitive data in a URL; never use GET for writes**
