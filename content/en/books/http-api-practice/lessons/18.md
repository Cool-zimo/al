# 18 Encoding on the Request Side: Why Your Non-ASCII Text Arrives Garbled

> Lesson 09 covered **response** mojibake (the server's content decoded wrongly). This lesson covers the other half: **request** encoding — why the non-ASCII text, filenames, and form fields you send arrive as something else. It's symmetric; both directions must be right.

## Encoding Problems Are Symmetric

Lesson 09's core:

```
sender: text --encode--> bytes --transfer--> bytes --decode--> text: receiver
```

**Wrong decoding produces mojibake** (Lesson 09); **wrong encoding produces it too** (this lesson).

And on the request side it's **harder to diagnose**, because:

> **You can't see what the server received.**

You can `print()` response mojibake. Request garbling happens **on their machine** — you can only infer.

**That's why echo services like httpbin matter so much** — they show you the request from the server's perspective.

## Scenario One: Non-ASCII in a JSON Body

### What requests does

```python
import requests

r = requests.post(
    "https://httpbin.org/post",
    json={"name": "张三", "city": "北京"},
    timeout=10,
)

print(r.request.headers["Content-Type"])
# application/json
```

**With `json=`, requests internally**:

1. `json.dumps(obj)` → a string. **Default `ensure_ascii=True`**, so non-ASCII becomes `\u5f20\u4e09`
2. encodes to bytes (UTF-8)
3. sends

**So in the bytes on the wire, non-ASCII exists as ASCII escapes like `\u5f20\u4e09`.**

**Is that a problem?** No. Because:

- **`\u5f20\u4e09` is valid JSON** and every standard parser restores the original characters
- it's all ASCII, so **there's no encoding problem at all** — no matter what encoding the server assumes

**This is actually an elegant part of JSON's design**: ASCII escaping sidesteps every charset dispute.

### When it does go wrong

**Case one: their JSON parser has a bug** (rare, but real).

**Case two: you want the body readable** (so a packet capture shows real characters).

**Fix**: dumps yourself with escaping off:

```python
import json
import requests

payload = json.dumps({"name": "张三"}, ensure_ascii=False)   # ① disable escaping

r = requests.post(
    "https://httpbin.org/post",
    data=payload.encode("utf-8"),                             # ② encode manually
    headers={"Content-Type": "application/json; charset=utf-8"},  # ③ declare
    timeout=10,
)
```

> **Line-by-line**
>
> - **①** `ensure_ascii=False` keeps literal characters
> - **②** **You must encode yourself.** With a string, `data=` won't encode for you, and HTTP needs bytes
> - **③** Declare UTF-8 explicitly. **JSON is specified as UTF-8 anyway**; stating it is safer

**The trap in ②**: writing just `data=payload` (a str, not bytes) makes requests encode with **Latin-1**, and non-ASCII either raises or produces wrong bytes.

## Scenario Two: Non-ASCII in a Form

```python
import requests

r = requests.post(
    "https://httpbin.org/post",
    data={"name": "张三"},
    timeout=10,
)

print(r.request.body)
# name=%E5%BC%A0%E4%B8%89        ← percent-encoded
```

**That's correct.** The form format requires percent-encoding for non-ASCII (Lesson 13).

The server receives `name=%E5%BC%A0%E4%B8%89`, decodes it, and gets the original. **Standard flow, can't go wrong.**

**Where it breaks**:

```python
# ❌ Wrong: building the form string yourself
data = f"name={name}"        # no encoding
r = requests.post(url, data=data, timeout=10)
```

**Cause**: nobody performed the percent-encoding; raw characters went into the body. The server may:
- read them as Latin-1 → mojibake
- reject outright

**Lesson**: **use `data={dict}` for forms; never hand-build the string.**

## Scenario Three: Non-ASCII in a URL (recap)

Lesson 13 covered it; here's the easily-forgotten bit:

```python
# ✅ Right
requests.get(url, params={"q": "中文"})

# ❌ Wrong
requests.get(f"{url}?q=中文")
```

**requests encodes it to `%E4%B8%AD%E6%96%87`.** Unencoded, some servers or proxies fail.

## Scenario Four: Non-ASCII Filenames (a real trap)

Uploading with a non-ASCII filename is **one of the most problem-prone scenarios**.

### The old problem: RFC 2231 and inconsistent implementations

In HTTP, a filename appears in the `Content-Disposition` header:

```text
Content-Disposition: form-data; name="file"; filename="头像.jpg"
```

**The problem**: **HTTP headers are theoretically ASCII-only.** How do you put non-ASCII in one?

Historically implementations disagreed, mainly between:

```
Way A: filename="%E5%A4%B4%E5%83%8F.jpg"     ← percent-encoding
Way B: filename="头像.jpg"; filename*=UTF-8''%E5%A4%B4%E5%83%8F.jpg
                                              ↑ the standard per RFC 5987
```

**Way B is today's standard** (RFC 5987, 2007): `filename` holds an ASCII fallback, `filename*` holds the full UTF-8-encoded version.

### How requests handles it

```python
import requests

r = requests.post(
    "https://httpbin.org/post",
    files={"file": ("头像.jpg", b"image-bytes", "image/jpeg")},
    timeout=10,
)
```

**requests handles it automatically** — it generates the correct value per RFC 5987. **You just pass the right filename.**

### But the receiver may misbehave

**If their server is old**, it may only understand percent-encoding or Latin-1. **Then the stored filename is mojibake.**

**How to investigate**:

```python
print(r.request.body[:500])        # see how filename was encoded
```

If you see `filename="å¤´åƒ.jpg"` (the classic symptom of UTF-8 bytes read as Latin-1), **the sender used the wrong encoding**. That's requests' internal behaviour and hard to change.

**Fixes**:
- upgrade requests
- or **rename the file to ASCII** (pinyin or English) — the most pragmatic solution

## A Methodology for Debugging Request Encoding

The most practical section here. **When "the server says the data is wrong," investigate in this order**:

### Step one: echo with httpbin

```python
import requests

r = requests.post("https://httpbin.org/post", json={"name": "张三"}, timeout=10)
d = r.json()

print("Content-Type:", d["headers"].get("Content-Type"))
print("server parsed JSON:", d["json"])       # ① the parse result
print("raw body:", d["data"][:300])           # ② the raw bytes
```

> **①** If this shows the correct characters, everything is fine
> **②** If ① is wrong, inspect the raw bytes to tell an encoding problem from a format problem

### Step two: look at the bytes you sent

```python
print(r.request.body)                # the body that went out
print(type(r.request.body))          # bytes or str
print(r.request.headers)             # does Content-Type carry a charset?
```

**Key checks**:

| Check | Expected |
|---|---|
| `Content-Type` | matches your actual format |
| with non-ASCII | should declare `charset=utf-8` or use `\u` escapes |
| `body` is bytes | encoding is correct |

### Step three: confirm what they expect

**Many "encoding problems" are actually "format problems"**: you sent JSON but they wanted a form, or vice versa. Lesson 16 covered that.

**Confirm the format from the docs before investigating encoding. Don't reverse that order.**

## A General "Encoding-Safe" Checker

```python
def check_request_encoding(prepared):
    """Inspect a PreparedRequest's encoding, for debugging"""
    body = prepared.body
    ct = prepared.headers.get("Content-Type", "")

    print(f"Content-Type: {ct}")

    if body is None:
        print("body: none")
        return

    if isinstance(body, bytes):
        print(f"body type: bytes, length {len(body)}")
        # ① try decoding as UTF-8
        try:
            text = body.decode("utf-8")
            print(f"UTF-8 decode OK: {text[:100]}")
        except UnicodeDecodeError:
            print("UTF-8 decode failed (binary data — probably fine)")
    else:
        print(f"body type: str (requests will use Latin-1 — non-ASCII will break!)")

    # ② check whether a charset is declared
    if "charset" in ct.lower():
        print("charset declared ✓")
    else:
        print("no charset ⚠️ the other side may guess wrong")

r = requests.post("https://httpbin.org/post", json={"name": "张三"}, timeout=10)
check_request_encoding(r.request)
```

> **Line-by-line**
>
> - **①** Try UTF-8 decoding. **Success means the content is UTF-8 text**; failure means binary (fine) or another encoding (a problem)
> - **②** Check for a declared charset. **Without one, they can only guess**
>
> **Why check `isinstance(body, bytes)`**: **if body is a str, requests encodes it with Latin-1** — catastrophic for non-ASCII. This only happens when you pass a string yourself (`json=` and `files=` never do)

## Crash Site

### Crash 1: passing a str to data=

```python
# ❌ Wrong
payload = json.dumps({"name": "张三"}, ensure_ascii=False)   # a str with real chars
r = requests.post(url, data=payload, timeout=10)
# UnicodeEncodeError, or the server gets garbage
```

**Symptom**: either `UnicodeEncodeError: 'latin-1' codec can't encode characters` or the server receives garbage bytes.

**Cause**: **with a str, `data=` encodes using Latin-1** (a legacy HTTP/1.1 default), which can't hold non-ASCII at all.

**Lesson**: **use `json=`**, or `.encode("utf-8")` first **and declare the charset**.

### Crash 2: thinking \uXXXX is mojibake

```python
r = requests.post(url, json={"name": "张三"}, timeout=10)
print(r.request.body)
# b'{"name": "\\u5f20\\u4e09"}'      ← you think it's broken
```

**Symptom**: you see `\u5f20`, assume encoding is broken, and spend an afternoon "fixing" it.

**Cause**: **valid JSON escaping** — `json.dumps`' `ensure_ascii=True` default.

**Verify**:

```python
import json
print(json.loads('{"name": "\\u5f20\\u4e09"}')["name"])
# 张三        ← perfectly fine
```

**Lesson**: **`\uXXXX` is not a bug.** Verify with `json.loads` before concluding.

### Crash 3: non-ASCII filename becomes mojibake on the server

**Symptom**: upload succeeds, but the stored filename is `å¤´åƒ.jpg` or `???`.

**Cause**: three-way inconsistency — the encoding you sent, how they parse, and how they store. Any one being wrong does it.

**Investigate**:

```python
r = requests.post(url, files={"f": ("头像.jpg", b"x")}, timeout=10)
print(r.request.body[:400])       # see how filename was encoded
```

**Pragmatic fixes**:

1. upgrade requests
2. **rename to ASCII** (`touxiang.jpg`) — solves 90% of cases
3. if you must keep non-ASCII, agree the encoding with the backend

## Why This Matters for Your Code

1. **Encoding must be right in both directions**: decode responses correctly, encode requests correctly
2. **The request side is harder** because you can't see what they got — **echo with httpbin**
3. **JSON's `\uXXXX` escaping isn't a bug**; it sidesteps charset issues entirely
4. **`data=` with a str encodes Latin-1** — non-ASCII dies. Use `json=`, or encode yourself
5. **Form non-ASCII is auto-encoded by `data={dict}`**; don't hand-build strings
6. **Non-ASCII filenames are a genuinely frequent trap**; ASCII names are the pragmatic fix

## Summary

- **Both sides must encode correctly.** Requests are harder to debug because you can't see the other end — **echo with httpbin**
- **JSON non-ASCII defaults to `\uXXXX` escapes** (`ensure_ascii=True`). **Correct, not mojibake**
- **For literal characters**: `json.dumps(..., ensure_ascii=False)` + `.encode("utf-8")` + declare charset
- **Form non-ASCII is auto percent-encoded by `data={dict}`**; never hand-build strings
- **URL non-ASCII is auto-encoded by `params=`**
- **Non-ASCII filenames are a frequent trap**: RFC 5987 defines `filename*`, but old servers may not honour it
- **`data=` with a str uses Latin-1** → non-ASCII breaks
- **Debug in three steps**: httpbin echo → inspect your own bytes → confirm the format they expect
