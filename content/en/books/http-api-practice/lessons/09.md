# 09 Content Negotiation & Encoding: Why You Got Mojibake

> You've hit this: `r.text` prints a mess like `æ\x97\xa0`, or all the non-ASCII characters turn into question marks. This lesson starts from "how do client and server agree on a format" and goes all the way to charsets, compression, and the relationship between `r.text` / `r.content` / `r.encoding`. After this, mojibake won't stop you again.

## Content Negotiation: One Resource, Many Representations

Consider this scenario.

One URL, `https://example.com/report`, has three versions on the server:

- a PDF in Chinese
- HTML in English
- JSON in English

**Which does the client get?** You can't expect the client to guess, and you don't want three separate URLs (that means maintaining three address schemes).

HTTP's answer is **content negotiation**:

> The client declares in request headers "what I can accept and what I prefer"; the server picks the most suitable version based on those declarations.

That's the entire reason the `Accept` family of headers exists.

## The Accept Family: Four Kinds of "I Accept"

### Accept: which format

```text
Accept: application/json
```

Tells the server: JSON only, I can't handle anything else.

You can also list **several options with priorities**:

```text
Accept: application/json, text/html;q=0.9, */*;q=0.8
```

That `q` is the **quality factor**, 0 to 1, defaulting to 1. The line above means:

1. JSON preferred (q=1, omitted)
2. HTML if no JSON (q=0.9)
3. Anything if neither (`*/*`, q=0.8)

**q=0 means "absolutely not"**:

```text
Accept: text/html, application/xml;q=0
```

Meaning: give me HTML, **never XML**.

### Accept-Encoding: which compression

```text
Accept-Encoding: gzip, deflate, br
```

Three common algorithms:

| Algorithm | Origin | Status |
|---|---|---|
| **gzip** | GNU zip, 1992 | most universal |
| **deflate** | zlib | supported, rarely used |
| **br** | Brotli, Google 2015 | ~20% better than gzip; all modern browsers |

**This header is worth a lot in practice**: a 500KB JSON may gzip down to 50KB — a 90% transfer reduction.

`requests` **sends `Accept-Encoding: gzip, deflate` by default** and **decompresses automatically**, so you never handle it yourself.

### Accept-Language: which language

```text
Accept-Language: zh-CN, zh;q=0.9, en;q=0.8
```

Meaning: Simplified Chinese first, then Chinese generally, then English.

**Browsers send this automatically** (based on your OS language). That's why the same site shows Chinese to a Chinese visitor and English to an American — **the server decides from this header.**

### Accept-Charset: which character set

```text
Accept-Charset: utf-8
```

**Essentially nobody uses this any more.** For a practical reason: over 98% of today's web is UTF-8, so negotiating is pointless. It also carries a risk — declare only one charset and the server may respond **406 Not Acceptable** if it has something else.

Modern browsers **no longer send `Accept-Charset`.** It's a header **obsoleted by reality**.

## The Server's Answer: Content-Type

Once the server picks a version, it says what it's sending via `Content-Type`:

```text
Content-Type: application/json; charset=utf-8
```

Two parts in one header:

```
application/json    ← MIME type: what kind of thing this is
charset=utf-8       ← charset: how the text is encoded
```

### MIME types

MIME (Multipurpose Internet Mail Extensions) **also comes from the mail standards** — another case of mail-protocol machinery carried into HTTP.

Common ones:

| MIME | Meaning |
|---|---|
| `text/html` | HTML page |
| `text/plain` | plain text |
| `application/json` | JSON data |
| `application/xml` | XML |
| `application/octet-stream` | binary blob (fallback for downloads) |
| `image/png` / `image/jpeg` | images |
| `application/pdf` | PDF |
| `multipart/form-data` | form with file upload |
| `application/x-www-form-urlencoded` | simple form |

### charset is the real source of mojibake

**Key point**:

> `application/json` only says "this is JSON" — **it does not say how non-ASCII text inside is encoded**. That's charset's job.

**The JSON spec (RFC 8259) mandates UTF-8**, so JSON theoretically needs no charset. HTML has no such rule, so you'll see:

```text
Content-Type: text/html; charset=gbk      ← older Chinese sites
Content-Type: text/html; charset=utf-8    ← today's mainstream
```

**GBK is a China-specific encoding** (along with GB2312 and GB18030). Decode a GBK-encoded page as UTF-8 and you get mojibake.

## How Mojibake Happens

Encoding and decoding must use **the same rule**:

```
your text  --encode-->  bytes  --decode-->  displayed text
   "中"       UTF-8     E4 B8 AD   UTF-8      "中"
   "中"       GBK       D6 D0      GBK        "中"
   "中"       UTF-8     E4 B8 AD   GBK        "涓" ← mojibake
```

**Mojibake means: bytes interpreted with the wrong rule.**

Note the crucial part: **mojibake is not corrupted data.** Not one byte was lost — you just read it wrong. Decode again with the correct encoding and the content returns.

```python
s = "café"
b_utf8 = s.encode("utf-8")      # b'caf\xc3\xa9'
b_gbk  = s.encode("gbk")        # b'caf\xa9\xe9'  (approximate)

print(b_utf8.decode("gbk"))     # 'caf茅' ← wrong rule, mojibake
print(b_utf8.decode("utf-8"))   # 'café'  ← correct again
```

## Three Attributes in requests: content / text / encoding

The most practical part of this lesson.

```python
import requests

r = requests.get("https://example.com", timeout=10)

r.content      # ① bytes: raw bytes, no interpretation
r.text         # ② str: content decoded using some encoding
r.encoding     # ③ the encoding used (may be guessed!)
```

### r.content: raw bytes

**Always `bytes`.** The exact data the server sent, untouched.

**When to use it**:

- downloading images, PDFs, archives (**binary files must use `.content`**)
- when you hit mojibake, re-decode from here

```python
# Downloading an image: must use content
r = requests.get("https://example.com/photo.jpg", timeout=10)
with open("photo.jpg", "wb") as f:      # note "wb" — binary write
    f.write(r.content)                   # write bytes, not str
```

> **Line-by-line**
>
> - **`"wb"`**: `w` = write, `b` = binary mode. **Writing bytes requires the `b`**; plain `"w"` raises `TypeError`
> - **`r.content`**: not `r.text`. An image isn't text; `.text` runs a decode pass that **corrupts the image data and the file won't open**

### r.text: the decoded string

`r.text` is equivalent to `r.content.decode(r.encoding)`.

**The problem: `r.encoding` may be a guess.**

### r.encoding: this encoding may be wrong

How `requests` picks `r.encoding`:

1. **Look for charset in the response `Content-Type` header.** If present, trust it
2. **No charset, and Content-Type is `text/*`** → per the RFC, default to **ISO-8859-1 (Latin-1)**
3. **`application/json`** → default to **UTF-8**
4. **Neither** → guess with `apparent_encoding`

**Where's the trap**: many older non-English sites (GBK-encoded) **don't declare charset in the HTTP header**, only in the HTML via `<meta charset="gbk">`.

By rule 2 above, `requests` decodes GBK bytes as ISO-8859-1 → **mojibake**.

```python
r = requests.get("http://old-chinese-site.com", timeout=10)
print(r.encoding)              # 'ISO-8859-1' ← guessed wrong
print(r.text[:20])             # 'ÖÐÎÄµÄÍøÕ¾' ← mojibake
```

### apparent_encoding: let it re-guess

`requests` bundles an encoding detector (based on `chardet` / `charset_normalizer`) that **analyses the byte content** to guess the real encoding:

```python
r = requests.get("http://old-chinese-site.com", timeout=10)

print(r.encoding)               # 'ISO-8859-1' ← from the header (wrong)
print(r.apparent_encoding)      # 'GB2312'      ← guessed from content (right)

r.encoding = r.apparent_encoding    # ① correct it manually
print(r.text[:20])              # '中文的网站' ← correct now
```

> **Line-by-line**
>
> - **`r.apparent_encoding`** is an **attribute**, not a method — **no parentheses**
> - **①** This is the standard mojibake fix. **Set encoding to the detected value, then read `r.text` again**
> - **Order matters**: change `r.encoding` **before** reading `r.text`. `r.text` is **computed fresh on each access** — after changing encoding, reading `r.text` re-decodes with the new one

### The bulletproof option: work from content directly

If those rules feel convoluted, here's an approach that never fails:

```python
r = requests.get(url, timeout=10)

# Option A: I know it's UTF-8
text = r.content.decode("utf-8")

# Option B: tolerate a few undecodable bytes
text = r.content.decode("utf-8", errors="replace")

# Option C: unknown encoding — let the detector guess
text = r.content.decode(r.apparent_encoding or "utf-8")
```

> **Line-by-line**
>
> - **A** is simplest. **API JSON is essentially always UTF-8**, so this is the safest bet
> - **B** `errors="replace"` means undecodable bytes become `�` instead of raising. **The default is `errors="strict"`, which raises `UnicodeDecodeError`**
> - **C** `apparent_encoding` occasionally returns `None` (too little content to guess), hence `or "utf-8"` as a fallback

## Compression: requests handles it, but know it's there

```python
import requests

r = requests.get("https://api.github.com/user", timeout=10)

print(r.headers.get("Content-Encoding"))    # ① may be 'gzip'
print(len(r.content))                       # ② length after decompression
```

> **Line-by-line**
>
> - **①** `Content-Encoding: gzip` means the server compressed the body with gzip
> - **②** **`r.content` is the decompressed bytes.** `requests` did that automatically — it sees `Content-Encoding: gzip` and decompresses

**So you never need to gunzip manually.** But understand: **what travelled over the network was compressed; `len(r.content)` is the decompressed size.** The two can differ by 10×.

One related but different header:

| Header | Meaning | Handled automatically? |
|---|---|---|
| `Content-Encoding` | compressed in transit (gzip) | ✅ requests decompresses |
| `Transfer-Encoding: chunked` | chunked transfer (length unknown) | ✅ urllib3 handles it |
| charset in `Content-Type` | character encoding | ❌ **you must get this right** |

**charset is the only one you need to worry about**, because it can be guessed wrong, whereas compression and chunking are machine-to-machine and never wrong.

## Crash Site

### Crash 1: downloading an image with r.text

```python
# ❌ Wrong
r = requests.get("https://example.com/photo.jpg", timeout=10)
with open("photo.jpg", "w") as f:       # "w" instead of "wb"
    f.write(r.text)                      # .text instead of .content
```

**Symptom**: the file saves fine, the size looks about right, but **double-clicking does nothing** and the viewer says "file is corrupted."

**Cause**: `.text` decoded the binary image data as text; byte sequences invalid in UTF-8 got replaced with `U+FFFD`. **The image data is permanently damaged.**

**Lesson**: **every binary file (image/video/archive/PDF/Excel) uses `r.content` + `"wb"`.**

### Crash 2: using apparent_encoding on JSON

```python
# ❌ Unnecessary
r = requests.get("https://api.example.com/data", timeout=10)
r.encoding = r.apparent_encoding      # pointless, and risky
data = r.json()
```

**Symptom**: works most of the time, occasionally fails to parse.

**Cause**: **the JSON spec mandates UTF-8.** `apparent_encoding` is a statistical guess that **gets short content wrong**. You overwrote a certainly-correct value with a possibly-wrong one.

**Lesson**: **for API JSON, call `r.json()` directly and leave `r.encoding` alone.** `r.json()` handles UTF-8 correctly internally.

### Crash 3: changing encoding after reading text

```python
# ❌ Wrong
r = requests.get(url, timeout=10)
print(r.text)                         # read first
r.encoding = "gbk"                    # then change
print(r.text)                         # expecting it fixed
```

**Symptom**: **the second read actually is correct.** Because `r.text` isn't cached — it's computed on each access.

**But this is fragile** — it depends on the implementation detail "text is not cached." **And if other code reads `r.text` in between, you won't know which version it got.**

**Lesson**: **set the encoding first, then read.** Fix the order; don't lean on implementation details.

## Why This Matters for Your Code

1. **Mojibake is not corruption.** The bytes are intact, just decoded wrong. Knowing this keeps you calm
2. **`r.content` is the truth; `r.text` is an interpretation.** When unsure, decode from `content` manually — fully under your control
3. **Always use `r.json()` for API JSON**; don't hand-manage encodings
4. **Binary files always use `r.content` + `"wb"`**
5. **`apparent_encoding` is only for legacy sites** — a legacy of HTML that doesn't declare charset
6. **Compression is automatic**, but know that `len(r.content)` is the post-decompression size

## Summary

- **Content negotiation**: the client declares preferences via `Accept`; the server picks a version. `q=` sets priority
- `Accept` format · `Accept-Encoding` compression · `Accept-Language` language · **`Accept-Charset` is obsolete**
- **`Content-Type` = MIME type + charset**. MIME says "what is it"; charset says "how text is encoded"
- **Mojibake means decoding bytes with the wrong rule.** Data isn't damaged; use the right rule and it's fine
- `r.content` = raw bytes · `r.text` = decoded text · **`r.encoding` may be a guess**
- **Standard fix**: `r.encoding = r.apparent_encoding` (**before** reading `.text`)
- **`apparent_encoding` is an attribute — no parentheses**; may return None, so add a fallback
- **JSON is always UTF-8; don't override with apparent_encoding**
- **Binary files use `.content` + `"wb"`**; **decompression is automatic**
- `errors="replace"` substitutes `�` instead of raising
