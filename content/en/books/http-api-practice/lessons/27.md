# 27 Pagination: Why APIs Won't Hand You Everything at Once

> You ask for "all my repos" and the server returns 30, telling you there's a next page. It feels stingy. Pagination actually **protects both sides** — this lesson covers what the three styles look like, when each one breaks, and **why your pagination loop may be silently dropping data**.

## First, Accept a Fact: Pagination Isn't Stinginess

```python
import requests

r = requests.get("https://api.github.com/users/Cool-zimo/repos", timeout=10)
data = r.json()
print(len(data))        # 30
```

You may have 200 repos. Why only 30?

**Three reasons, every one of them solid:**

**One: the server can't take it.**

If your account has 50,000 repos (common for bot accounts), serializing 50,000 objects at once takes hundreds of MB of RAM and seconds of CPU. **And that's just one user's request** — 100 such requests at once and the server is down.

**Two: the network can't take it.**

A few hundred MB takes tens of seconds to transfer. **Any network hiccup inside those tens of seconds fails the whole request**, and you start over. At 30 per page, a failure only re-sends that one page.

**Three: you probably don't need all of it.**

Most cases are "show page one, load more when the user scrolls." **Send everything at once and 99% of the data is wasted bandwidth.**

> **Analogy**: borrowing 200 books from a library — the librarian won't haul all 200 at once; she gives you 20, and you come back when you're done. **Pagination is "fetch on demand," not "deliberate obstruction."**

## What the Three Styles Look Like

This is the key insight: **pagination has no universal standard.** Different APIs do it differently, and you must read the docs to know which one you're dealing with.

### Style One: Page Number (page / per_page)

```
GET /repos?page=1&per_page=30
GET /repos?page=2&per_page=30
```

**Most common and easiest to grasp.** You tell the server "which page, how many per page."

**How to spot it**: a `page` or `page_num` parameter.

### Style Two: Offset (offset / limit)

```
GET /items?offset=0&limit=30
GET /items?offset=30&limit=30
GET /items?offset=60&limit=30
```

**Note: offset is "how many to skip," not "which page"**:

```
offset = (page - 1) * limit
```

**How to spot it**: an `offset` or `skip` parameter.

### Style Three: Cursor (cursor / after)

```
GET /items?limit=30
GET /items?limit=30&after=eyJpZCI6MTIzfQ    ← cursor of the last item from the previous page
GET /items?limit=30&after=eyJpZCI6MTU2fQ
```

The server returns an **opaque cursor string** (usually base64) meaning "continue from here."

**How to spot it**: a `next_cursor` / `cursor` / `after` field in the response, or a `cursor` parameter.

**This is the most robust style** — the reason comes later.

## Page-Number Pagination: Start With the Simplest Loop

```python
import requests

def fetch_all_repos(user, token=None):
    """Fetch all repos for a user"""
    all_repos = []
    page = 1

    headers = {}
    if token:
        headers["Authorization"] = f"Bearer {token}"

    with requests.Session() as s:                    # ① Session reuses connections
        s.headers.update(headers)

        while True:
            r = s.get(                               # ② request one page
                f"https://api.github.com/users/{user}/repos",
                params={"page": page, "per_page": 100},   # ③ 100 is the max
                timeout=10,
            )
            r.raise_for_status()                     # ④ raise on error

            batch = r.json()
            if not batch:                            # ⑤ empty → done
                break

            all_repos.extend(batch)                  # ⑥ accumulate
            page += 1                                # ⑦ next page

    return all_repos
```

> **Line-by-line**
>
> - **① `Session`**: straight from the last lesson — pagination means dozens of requests; no reuse means several times slower
> - **② `s.get(...)`**: fetch page `page`
> - **③ `per_page=100`**: **GitHub's cap is 100**; passing 200 gets treated as 100. Every API differs — **read the docs**
> - **④ `raise_for_status()`**: **mandatory** inside a pagination loop. Without it, a 404 returns an empty list, your loop concludes "no more data," and exits normally — **silently returning incomplete data**
> - **⑤ `if not batch: break`**: **the termination condition.** The most universal check for page-number style — an empty array means you've gone past the end
> - **⑥ `extend`, not `append`**: `append` would insert the whole list as a single element
> - **⑦ `page += 1`**

**④ is the easiest thing to get wrong here.** Picture it missing: token expired → server returns 401 plus a JSON error → `r.json()` gives you a **dict** (not a list) → `if not batch` is also true for an empty dict → loop exits cleanly → **you get zero items and the function returns as if all is well.**

## Termination: How Do You Know You're Done?

**This is where pagination bugs breed.** There are four ways to decide, and their reliability differs a lot.

### Check One: Empty Array (Most Universal)

```python
if not batch:
    break
```

✅ **Pro**: works with nearly every API
❌ **Con**: **costs one extra request** (you must page past the end to learn you're done)

### Check Two: Fewer Items Than per_page

```python
if len(batch) < 100:      # fewer than requested per page
    break                  # this was the last page
```

✅ **Pro**: **saves that extra empty request**
❌ **Con**: **breaks when the total divides evenly** — with 200 items at 100 per page, the last page is exactly 100, so you'd send one more request and get an empty array. **So pair this with the empty check**

```python
# ✅ The safe way: use both
if len(batch) < per_page or not batch:
    break
```

### Check Three: A total Field in the Response

Many APIs tell you the total:

```json
{
  "total": 137,
  "page": 1,
  "per_page": 100,
  "items": [...]
}
```

```python
total = data["total"]
all_items.extend(data["items"])
if len(all_items) >= total:      # ① stop once we have enough
    break
```

> - **① Compare collected count against the total**, not "pages × per_page" — the latter miscounts when the total doesn't divide evenly

✅ **Pro**: you can compute how many requests you'll need up front, and show progress
❌ **Con**: **not every API provides total**; and **`total` can change mid-pagination** (new data arriving)

### Check Four: A next Link in the Response (Most Reliable)

```json
{
  "items": [...],
  "next": "https://api.example.com/items?page=2",
  "has_more": true
}
```

```python
while url:                        # ① url is the next page's link
    r = s.get(url, timeout=10)
    r.raise_for_status()
    data = r.json()
    all_items.extend(data["items"])
    url = data.get("next")        # ② no next → None → loop ends
```

✅ **Pro**: **the server tells you where the next page is**; no guessing
❌ **Con**: you must use whatever field name the API chose

## GitHub's Link Header: The Most Elegant Approach

GitHub doesn't use a response body field — it **puts it in a header**:

```
Link: <https://api.github.com/user/repos?page=2>; rel="next",
      <https://api.github.com/user/repos?page=7>; rel="last"
```

That one line tells you **two things**: the next page is page=2, the last is page=7. **You don't even have to loop and probe — you know the total page count immediately.**

### Parsing It Yourself

```python
import re
import requests

def parse_link_header(link):
    """Parse a Link header into a {rel: url} dict"""
    result = {}
    if not link:
        return result

    for part in link.split(","):                       # ① split on commas
        m = re.search(r'<([^>]+)>;\s*rel="?(\w+)"?', part)   # ② regex extract
        if m:
            result[m.group(2)] = m.group(1)            # ③ rel → url

    return result

r = requests.get("https://api.github.com/users/Cool-zimo/repos", timeout=10)
links = parse_link_header(r.headers.get("Link"))
print(links)
# {'next': 'https://api.github.com/user/repos?page=2',
#  'last': 'https://api.github.com/user/repos?page=7'}
```

> **Line-by-line**
>
> - **① `split(",")`**: multiple links in a Link header are comma-separated
> - **② Regex `<([^>]+)>;\s*rel="?(\w+)"?`**:
>   - `<([^>]+)>` matches the URL inside angle brackets (`[^>]` means "any char that isn't `>`")
>   - `;\s*rel=` matches the semicolon and rel
>   - `"?(\w+)"?` matches the rel value, **quotes optional**
> - **③ Store as `{rel: url}`**, then `links.get("next")` just works

**Why regex instead of split**: `part.split(";")` also works, but the header's formatting details (spaces, quotes, extra params) break split easily. **Regex is sturdier.**

### requests Already Parsed It For You

**Good news: you don't need the function above.** It's built in:

```python
import requests

r = requests.get("https://api.github.com/users/Cool-zimo/repos", timeout=10)
print(r.links)
# {'next': {'url': 'https://...page=2', 'rel': 'next'},
#  'last': {'url': 'https://...page=7', 'rel': 'last'}}

next_url = r.links.get("next", {}).get("url")     # ① grab it directly
if next_url:
    r2 = requests.get(next_url, timeout=10)
```

> - **① `r.links`** is parsed automatically by requests. **Use it if present; write your own only if not**

**Full pagination using the Link header**:

```python
import requests

def fetch_all_with_link(url, headers=None):
    """Follow the Link header's next until the end"""
    items = []

    with requests.Session() as s:
        if headers:
            s.headers.update(headers)

        while url:                                    # ① ends when url is None
            r = s.get(url, timeout=10)
            r.raise_for_status()

            items.extend(r.json())                    # ② accumulate this page

            url = r.links.get("next", {}).get("url")  # ③ next page

    return items
```

> - **① `while url`**: the initial URL first, then next. **When the server gives no next, it's None and the loop ends naturally**
> - **③ This line is the heart of pagination** — the server says where the next page is, and we go there

## Offset's Fatal Flaw: It Drops Data

Page-number and offset styles look similar, but **when data changes**, offset has a serious problem.

### Demonstrating the Problem

Say you fetch newest-first, 3 per page:

```
Request 1, offset=0  → get [D, C, B]      (the three newest)
                                           ↓
                          someone posts a new item E
                                           ↓
Request 2, offset=3  → skip first 3 → get [B, A, ?]
                                  ↑
                            now the first three are [E, D, C]
                            skipping them → start at B
                            → B fetched twice! And E is never fetched
```

**Two consequences**:
1. **B is duplicated** (appears on both page 1 and page 2)
2. **E is lost** (it got inserted in front, pushing others into the range you already fetched)

> **Analogy**: page through a ring binder while someone inserts a page at the front — **every later page number shifts**, so you see one page twice and never see one at all.

### Why Cursors Don't Have This Problem

A cursor records **"which item was last"**, not "how many to skip":

```
Request 1: get 3 → returns [D, C, B], cursor = "B's ID"
                                    ↓ E inserted
Request 2: get 3 after "B's ID" → [A, ?, ?]     ← correct!
```

**The cursor points at a concrete item.** No matter how many new items land in front, continuing after B is still right.

**Conclusion**: **APIs with live-changing data (timelines, message streams, order lists) must use cursors.** Page/offset styles only suit "data basically doesn't change" cases (like a repo list).

## Write a Reusable Pagination Fetcher

Collapse all cases into one function, **using a generator** (memory-friendly — the streaming idea from lesson 25):

```python
import requests

def paginate(url, params=None, page_param="page", per_page=100,
             max_pages=100, session=None, **kwargs):
    """
    Generic pagination generator: yields one page at a time, process as you go

    :param url: starting URL
    :param page_param: name of the page parameter (page, offset, ...)
    :param per_page: items per page
    :param max_pages: safety valve against infinite loops
    :param session: optional Session (connection reuse)
    """
    s = session or requests.Session()       # ① build one if not given
    own_session = session is None           #    remember whether it's ours
    base_params = dict(params or {})        # ② copy, don't mutate caller's dict

    try:
        for page in range(1, max_pages + 1):        # ③ bounded loop
            req_params = dict(base_params)
            req_params[page_param] = page           # ④ page number
            req_params["per_page"] = per_page

            r = s.get(url, params=req_params, timeout=10, **kwargs)
            r.raise_for_status()

            batch = r.json()
            if not batch:                           # ⑤ empty → stop
                return

            yield batch                             # ⑥ yield a page, pause here

            if len(batch) < per_page:               # ⑦ last page
                return
    finally:
        if own_session:
            s.close()                               # ⑧ close only what we made
```

**Usage**:

```python
# Process as you go, no memory build-up
for batch in paginate("https://api.github.com/users/Cool-zimo/repos"):
    for repo in batch:
        print(repo["name"])

# Or if you really want everything
all_repos = [repo for batch in paginate(url) for repo in batch]
```

> **Line-by-line**
>
> - **① `session or requests.Session()`**: lets the caller pass their own Session (connection reuse); otherwise build one
> - **② `dict(params or {})`**: **a copy.** Mutating `params` in place would pollute the caller's dict — a sneaky side effect
> - **③ `range(1, max_pages + 1)`**: **`for` instead of `while True`.** This is the safety valve — **even if the termination check is wrong, it stops after 100 pages instead of hammering the API**
> - **④ `req_params[page_param]`**: configurable page param name, compatible with `page` / `offset` / `page_num`
> - **⑥ `yield batch`**: **a generator.** The function pauses after yielding; the caller processes, then it continues. **Only one page lives in memory at a time**
> - **⑧ close in `finally`**: only what we created. **Closing a Session the caller passed in is rude** — they may still need it

### Why a Generator Instead of a Big List

```python
# ❌ Return everything at once: 100k objects in memory
def fetch_all(url):
    result = []
    ...
    return result        # 100k objects in RAM

# ✅ Generator: use a page, drop a page
def paginate(url):
    ...
    yield batch          # only 100 in RAM at a time
```

**This continues the streaming idea from lesson 25**: you rarely need all the data in memory at once — you usually need to **iterate over it once**.

## Crash Site

### Crash One: `while True` With No Safety Valve

```python
# ❌ Dangerous
while True:
    r = s.get(url, params={"page": page})
    data = r.json()
    if not data:
        break
    ...
```

**Symptom**: once the termination check is wrong (e.g., the API changed its response shape), **this loop never ends** and your program hammers the API.

**Consequence**: **rate-limited at best (lesson 28), IP-banned at worst.** And because it's infinite, logs fill the disk in seconds.

**Lesson**: **always bound pagination loops.** `for page in range(1, max_pages+1)` is an order of magnitude safer than `while True`.

### Crash Two: Offset Pagination Drops Data

```python
# ❌ Using offset on live data
for offset in range(0, 1000, 50):
    r = s.get(url, params={"offset": offset, "limit": 50})
```

**Symptom**: duplicates in the results, or "this item should exist but wasn't fetched." **And it only appears when data changes frequently** — test data is static, so everything looks fine until production.

**Cause**: as shown above, insertions shift the offsets.

**Lesson**: **use cursors for live data.** If the API only supports offset, either **pull everything quickly in one burst** (shrinking the change window) or **sort newest-first and dedupe by tracking the max ID already processed**.

### Crash Three: Assuming per_page Is Unlimited

```python
# ❌ Too clever
r = s.get(url, params={"per_page": 10000})     # trying to get it all at once
```

**Symptom**: the server returns 100 (or 30) items and you believe you got everything.

**Cause**: **every API has a cap, and exceeding it is silently truncated.** GitHub is 100; many APIs are 50 or 20.

**Lesson**: **check the docs for the cap.** And verify:

```python
# ✅ Verify how many you actually got
print(len(r.json()))      # if it's exactly 100, it may have been truncated — keep paging
```

### Crash Four: Storing Every Page in a List Until You OOM

```python
# ❌ Blows up on large datasets
all_data = []
for page in range(1, 1000):
    all_data.extend(fetch_page(page))
```

**Symptom**: fetching 100k items eats several GB and the process gets OOM-killed.

**Cause**: **you don't actually need it all in memory at once** — you may only need to count, filter, or write to a file.

**Lesson**: use a generator and **process as you go**, or write to disk as you fetch.

### Crash Five: Forgetting raise_for_status

```python
# ❌ Fatal
batch = r.json()
if not batch:
    break
```

**Symptom**: after the token expires, the function returns an **empty or partial list** and **raises nothing**. You conclude "this user has no repos."

**Cause**: a 401 body is a dict like `{"message": "Bad credentials"}`; `if not batch` may behave unexpectedly on it, and the loop ends or continues for the wrong reason.

**Lesson**: **`raise_for_status()` is mandatory in pagination loops.** It's the only thing that distinguishes "genuinely no data" from "something broke."

## Why This Matters for Your Code

**One: API design constraints often exist to protect you.**

Pagination looks inconvenient, but it turns "one big request" into "several small ones," any of which can be retried alone. **A lot of what feels like "bad API design" is the API absorbing risk on your behalf.**

**Two: The correctness of the termination condition matters far more than the loop body.**

Get the body wrong and you get bad data; get the termination wrong and you either loop forever hammering the API or silently receive incomplete data. **Silently incomplete is the worst kind of failure — because it looks like success.**

**Three: "Works when tested" and "works while things change" are different claims.**

Offset pagination is perfect in a test environment, then drops data once production data moves. Bugs of this class share a signature: **correct under static conditions, broken under dynamic ones.** The test question is: "**while I'm iterating, can this collection change?**"

## Summary

- **Three reasons for pagination**: the server can't take it, the network can't take it, you probably won't use it all
- **Three styles**: page-number `page/per_page`, offset `offset/limit`, cursor `cursor/after`
- **`offset = (page-1) * limit`**
- **Four termination checks**: empty array (most universal), fewer than per_page (saves a request, pair with the empty check), a total field, a next link (most reliable)
- **GitHub's Link header**: requests auto-parses it into `r.links`; use `r.links["next"]["url"]`
- **Offset drops data**: inserts during traversal cause duplicates and losses; **live data must use cursors**
- **`for page in range(1, max_pages+1)`, not `while True`** — safety valve
- **`per_page` has a cap**; exceeding it truncates silently; check the docs
- **Use a generator and `yield` to process as you go**; don't pile it all into memory
- **`raise_for_status()` is mandatory in pagination loops**, or errors masquerade as "no data"
- ❌ No `while True`; no offset on live data; no assuming per_page is unlimited; don't load it all into RAM; don't skip raise_for_status
