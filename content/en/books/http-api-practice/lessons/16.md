# 16 Request Bodies & Content-Type: Sending Data Out

> Earlier lessons were about *fetching* (GET). This one is about *sending* — how POST, PUT, and PATCH put data into a request. The core is two parameters, `data=` and `json=`, plus the `Content-Type` header that decides whether the server can parse you at all.

## What a Request Body Is

Recall the message structure from Lesson 03:

```text
POST /users HTTP/1.1          ← request line
Host: api.example.com         ← headers
Content-Type: application/json
Content-Length: 27
                              ← blank line
{"name": "Alice", "age": 30}   ← request body
```

**The request body is whatever comes after the blank line.** GET usually has no body (and shouldn't have a meaningful one); POST/PUT/PATCH use it to carry data.

### Why GET shouldn't have a body

Technically `requests.get(url, json=...)` sends one, but:

1. **Many servers ignore** a GET body outright
2. **Some proxies drop it**
3. **Semantically, GET means "fetch"** — a body is wrong

**To pass data with GET, use query parameters (`params=`).**

## Content-Type: Telling the Server What You Sent

The heart of this lesson.

> **`Content-Type` tells the server: this is the format of the body; parse it this way.**

The server has no idea what you sent. It reads only this header:

```
Content-Type: application/json        → parse as JSON
Content-Type: application/x-www-form-urlencoded  → parse as a form
Content-Type: text/plain              → treat as plain text
Content-Type: multipart/form-data     → parse as a multipart form (file upload)
```

**If the declared format doesn't match the actual content, parsing fails.** That's the number-one problem this lesson guards against.

## Two Parameters: data= and json=

`requests` offers two ways to send a body. **The difference is the biggest source of beginner confusion.**

### json=: send JSON

```python
import requests

r = requests.post(
    "https://httpbin.org/post",
    json={"name": "张三", "age": 30},        # ① pass a Python dict
    timeout=10,
)

print(r.request.headers["Content-Type"])     # ② application/json
print(r.request.body)                        # ③ what actually went out
```

> **Line-by-line**
>
> - **①** You hand over a **Python dict**; `requests` then:
>   1. converts it with `json.dumps()`
>   2. encodes to UTF-8 bytes
>   3. sets `Content-Type: application/json` automatically
> - **②** Confirm the header was added
> - **③** `r.request.body` is **the bytes that went out**

### data=: send raw content

```python
import requests

# Passing a dict → becomes form format
r = requests.post(
    "https://httpbin.org/post",
    data={"name": "张三", "age": 30},        # ① same dict
    timeout=10,
)

print(r.request.headers["Content-Type"])
# application/x-www-form-urlencoded          ← ② note! different from json=
print(r.request.body)
# name=%E5%BC%A0%E4%B8%89&age=30             ← ③ form format
```

> **Line-by-line**
>
> - **①** Same dict, but `data=` handles it completely differently
> - **②** `data=` + dict → automatically **form type**
> - **③** The dict became `name=xxx&age=30` with URL encoding (Lesson 13)

**That's the key difference**:

| Parameter | With a dict | Automatic Content-Type | Encoded result |
|---|---|---|---|
| `json=` | dict | `application/json` | `{"name": "张三", "age": 30}` |
| `data=` | dict | `application/x-www-form-urlencoded` | `name=%E5%BC%A0%E4%B8%89&age=30` |

**One dict, two completely different requests.** The server accepts only one of them.

### data= with a string: no conversion at all

```python
import requests

r = requests.post(
    "https://httpbin.org/post",
    data='{"name": "张三"}',                 # ① a string
    timeout=10,
)

print(r.request.headers["Content-Type"])     # ② no Content-Type!
```

> **Line-by-line**
>
> - **①** With a string, `data=` **sends it verbatim, no conversion**
> - **②** **`requests` does not add a Content-Type.** You never told it the format
>
> **This is a trap**: the server gets bytes with no idea whether they're JSON, and may fail to parse.

**Correct approach** — declare it yourself:

```python
r = requests.post(
    "https://httpbin.org/post",
    data='{"name": "张三"}',
    headers={"Content-Type": "application/json"},    # ① manual declaration
    timeout=10,
)
```

> **①** Content and declaration agree, so the server can parse.

### data= with bytes: also no conversion

```python
r = requests.post(
    url,
    data=b"\x00\x01\x02",                    # binary data
    headers={"Content-Type": "application/octet-stream"},
    timeout=10,
)
```

**When used**: uploading binary content (raw image data, protobuf, etc.).

## Choosing Between the Three

| What you're sending | Use | Set Content-Type manually? |
|---|---|---|
| **JSON** (most common) | `json={...}` | ❌ automatic |
| **Form data** (simulating a web form) | `data={...}` | ❌ automatic |
| **Plain text** | `data="string"` | ✅ yes |
| **Binary** | `data=b"..."` | ✅ yes |
| **File upload** | `files={...}` | ❌ automatic (Lesson 25) |

**The vast majority of APIs use `json=`.** Forms appear mainly in two places:
1. legacy web forms
2. OAuth token endpoints (many require form format)

## The Trap of Serialising JSON Yourself

Some people like to convert manually:

```python
# ❌ Redundant and risky
import json
r = requests.post(url, data=json.dumps({"name": "张三"}), timeout=10)
# forgot Content-Type → server doesn't know it's JSON
```

**Why `json=` is better**:

1. **Content-Type is set automatically**
2. **Consistent handling**: `json.dumps()` defaults to `ensure_ascii=True`, turning non-ASCII into `\u5f20\u4e09` escapes. Legal, but less readable and **some servers handle it poorly**
3. **One line less**

If you **must** dumps yourself (e.g. to control formatting), set the header:

```python
import json

payload = json.dumps({"name": "张三"}, ensure_ascii=False).encode("utf-8")
r = requests.post(
    url,
    data=payload,
    headers={"Content-Type": "application/json; charset=utf-8"},    # ①
    timeout=10,
)
```

> **①** Note `charset=utf-8` added. **JSON is required to be UTF-8**; stating it is clearer.

## A Real Side-by-Side Experiment

Post both ways to httpbin and print the results — **the best way to internalise the difference**:

```python
import requests
import json

payload = {"name": "张三", "tags": ["a", "b"]}

print("=== with json= ===")
r1 = requests.post("https://httpbin.org/post", json=payload, timeout=10)
d1 = r1.json()
print("Content-Type:", d1["headers"].get("Content-Type"))
print("server parsed json:", d1["json"])
print("server parsed form:", d1["form"])

print("\n=== with data= ===")
r2 = requests.post("https://httpbin.org/post", data=payload, timeout=10)
d2 = r2.json()
print("Content-Type:", d2["headers"].get("Content-Type"))
print("server parsed json:", d2["json"])
print("server parsed form:", d2["form"])
```

**You'll see**:

```
=== with json= ===
Content-Type: application/json
server parsed json: {'name': '张三', 'tags': ['a', 'b']}
server parsed form: {}          ← form is empty

=== with data= ===
Content-Type: application/x-www-form-urlencoded
server parsed json: None        ← JSON is empty
server parsed form: {'name': '张三', 'tags': ['a', 'b']}
```

**The most direct proof possible**: the server picks a parsing path from Content-Type, and **the two are entirely different paths**.

> **Line-by-line**
>
> - **`d1["json"]` / `d1["form"]`**: httpbin returns both parse results, so **you can see with your own eyes how the server handled it**
> - **Note the `tags` list**: with `data=` it becomes `tags=a&tags=b` (repeated keys, Lesson 13), and the server may keep only one

## PUT and PATCH Work the Same

```python
import requests

# PUT: full replace, with json=
requests.put(url, json={"name": "new", "age": 30}, timeout=10)

# PATCH: partial update, with json=
requests.patch(url, json={"name": "new"}, timeout=10)
```

**`json=` and `data=` behave identically on these methods.** Lesson 06 covered the semantic difference between PUT and PATCH; here it's just a different method name.

## Crash Site

### Crash 1: mixing json= and data=

```python
# ❌ Wrong
r = requests.post(
    url,
    json={"a": 1},
    data={"b": 2},          # both passed
    timeout=10,
)
```

**Symptom**: only one is sent, the other vanishes. And no error.

**Cause**: **when both are given, `json=` wins and `data=` is ignored.**

**Lesson**: **always pass exactly one.**

### Crash 2: setting the wrong Content-Type by hand

```python
# ❌ Wrong
r = requests.post(
    url,
    json={"name": "张三"},
    headers={"Content-Type": "application/x-www-form-urlencoded"},   # manual
    timeout=10,
)
```

**Symptom**: the server says it can't parse the body, or gets empty data.

**Cause**: Lesson 08 — **the body is JSON but declares itself a form.** The server parses a JSON string as a form and fails.

**Lesson**: **with `json=`, don't touch Content-Type.**

### Crash 3: expecting data= to detect a string

```python
# ❌ Wrong
r = requests.post(url, data='{"name": "张三"}', timeout=10)
# no Content-Type; the server doesn't know it's JSON
```

**Symptom**: some servers guess (looks like JSON, treat as JSON), some refuse outright. **Intermittent.**

**Cause**: `data=` with a string never sets a header for you.

**Lesson**: **add `Content-Type: application/json` manually**, or just use `json=`.

### Crash 4: non-ASCII turned into \uXXXX

```python
import json
print(json.dumps({"name": "张三"}))
# {"name": "\u5f20\u4e09"}     ← escaped
```

**Symptom**: you see `\u5f20` in the body and think it's mojibake.

**Cause**: **not mojibake — valid JSON escaping.** JSON allows `\uXXXX` for any character, and parsers restore it to the original.

**Should you change it**: usually not. `\u` escapes are legal JSON; every standard parser restores them.

**If you truly need literal characters** (readability, or a buggy parser on the other side):

```python
import json
s = json.dumps({"name": "张三"}, ensure_ascii=False)    # the key argument
print(s)
# {"name": "张三"}
```

## Why This Matters for Your Code

1. **`json=` and `data=` turn the same dict into completely different requests.** Pick wrong → 400
2. **`json=` sets Content-Type automatically; `data=` with a string doesn't** — the most accident-prone spot
3. **Don't set Content-Type manually** (when using `json=`)
4. **Don't pass both `json=` and `data=`** — json wins, silently
5. **`\uXXXX` is not mojibake** — it's legal JSON escaping
6. **Verify with httpbin** — unsure what you sent? POST to `httpbin.org/post` and read the echo

## Summary

- The **request body** is the data after the blank line; POST/PUT/PATCH carry content there. **GET shouldn't have one**
- **`Content-Type` tells the server how to parse the body.** A mismatch between declaration and content means parse failure
- **`json={dict}`** → JSON string + automatic `application/json`
- **`data={dict}`** → `k=v&k=v` form + automatic `x-www-form-urlencoded`
- **`data="string"`** → **sent verbatim, no Content-Type** (set it yourself!)
- **Most APIs use `json=`**; forms are for legacy web pages and OAuth token endpoints
- **Don't mix `json=` and `data=`** (json wins, silently); **don't touch Content-Type with `json=`**
- **`\uXXXX` is valid JSON escaping, not mojibake**; use `ensure_ascii=False` for literal characters
