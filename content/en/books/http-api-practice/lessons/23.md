# 23 OAuth: Letting Third-Party Apps Access Accounts With Limits

> You've clicked "Log in with GitHub". Afterwards the site can see your GitHub username and avatar but **can't** delete your repositories — how? OAuth. This lesson covers the full flow and why it's the most complex of the three auth schemes.

## What Problem OAuth Solves

### The scenario

A third-party app (say an online code editor) wants to read your GitHub repo list.

**The worst solution**: hand over your GitHub username and password.

**Consequences**:

- It now has your **full password**
- It can do **anything you can** (delete repos, change settings, read private data)
- You **can't revoke just its access** — only change your password (which breaks every other app)
- If it stores the password badly, your entire account leaks

**OAuth's solution**:

> **Don't give the password to the third party. Let GitHub itself issue them a limited credential.**

```
Third party → GitHub: "this user wants me to read their repos, ok?"
GitHub → user:        "this app wants to read your repos — allow?"
User → GitHub:        "allow" (password entered only here, only on GitHub's page)
GitHub → third party: "here's a token: read-repos only, valid 30 days"
```

**The core insight**:

> **Your password never leaves GitHub.** The third party gets only a limited, revocable token.

## The Three Roles

OAuth has three participants; learn the names:

| Role | English | Example |
|---|---|---|
| **Resource Owner** | Resource Owner | **you** (the user) |
| **Client** | Client | the third-party app (online editor) |
| **Authorization Server** | Authorization Server | GitHub's auth service |

**Plus one more**: the **Resource Server** — where the data lives (GitHub API). **It's usually the same system as the authorization server**, so people merge them.

## The Authorization Code Flow (Most Common)

OAuth2 has several flows; **Authorization Code Flow** is the most common and most secure.

### The complete flow

```
① Client redirects the user to GitHub
   https://github.com/login/oauth/authorize
     ?client_id=xxx
     &redirect_uri=https://myapp.com/callback
     &scope=repo
     &state=random_string

② User logs in on GitHub's page and clicks "Authorize"
   (this happens on GitHub; the client never sees what the user typed)

③ GitHub redirects back to the client with an authorization code
   https://myapp.com/callback?code=abc123&state=random_string

④ Client exchanges code + client_secret for a token [server-side]
   POST https://github.com/login/oauth/access_token
   (this request never passes through the browser, so client_secret isn't exposed)

⑤ GitHub returns an access_token
   {"access_token": "gho_xxxx", "scope": "repo"}

⑥ Client calls the API with the token
   GET https://api.github.com/user/repos
   Authorization: Bearer gho_xxxx
```

### Why steps ③ and ④ exist (why not hand over the token directly?)

**Good question.** Why not just give the token at step ③ instead of going around?

**Because**:

- **③ travels via a browser redirect**, so URL parameters land in **browser history, the Referer header, and all kinds of logs**
- **the `code` is one-time and expires in minutes**, so leaking it is useless (exchanging it also needs `client_secret`)
- **the `access_token` is long-lived** — leaking it is catastrophic

**Hence**: **pass the long-lived credential over a server-to-server channel (④)**, which is encrypted and never touches the browser.

### Details of each step

#### ① Build the authorization URL

```python
import secrets
import urllib.parse

client_id = "your_client_id"
redirect_uri = "https://myapp.com/callback"
scope = "repo"

state = secrets.token_urlsafe(16)      # ① random state, anti-CSRF
# store it in session/db — step ③ verifies it

params = {
    "client_id": client_id,
    "redirect_uri": redirect_uri,
    "scope": scope,
    "state": state,
}
auth_url = "https://github.com/login/oauth/authorize?" + urllib.parse.urlencode(params)
print(auth_url)
# redirect the user here
```

> **① `secrets.token_urlsafe(16)`** generates a random, URL-safe string.
>
> **Why `state` is needed**: **anti-CSRF.** At step ③ GitHub returns the state verbatim, and **you verify it matches what you sent.** A mismatch means the callback may be forged by an attacker.
>
> **Note**: **use `secrets`, not `random`** — the former is cryptographically secure.

#### ③ Handle the callback

```python
# Your callback handler (Flask-flavoured pseudocode)
def handle_callback(request):
    code = request.args.get("code")
    returned_state = request.args.get("state")

    # ① verify state (anti-CSRF)
    if returned_state != saved_state:
        return "state mismatch — possible CSRF attack", 403

    # ② check whether the user denied consent
    if not code:
        return "user denied authorization", 400

    # ③ exchange code for token (next step)
    token = exchange_code_for_token(code)
```

#### ④ Exchange the code for a token

```python
import requests

def exchange_code_for_token(code):
    r = requests.post(
        "https://github.com/login/oauth/access_token",
        data={                                   # ① note data=, not json=
            "client_id": CLIENT_ID,
            "client_secret": CLIENT_SECRET,       # ② server-side only
            "code": code,
            "redirect_uri": REDIRECT_URI,
        },
        headers={"Accept": "application/json"},   # ③ ask GitHub for JSON
        timeout=10,
    )
    r.raise_for_status()
    return r.json()["access_token"]
```

> **Line-by-line**
>
> - **① `data=`**: Lesson 17 — **RFC 6749 requires form format.** `json=` gets rejected
> - **② `client_secret`**: **server-side only.** That's why step ④ must happen on your backend
> - **③ `Accept: application/json`**: GitHub returns a form-encoded string by default; this header gets you JSON
>
> **The classic "send a form, want JSON" case** — straight from Lesson 17.

#### ⑥ Call the API with the token

```python
import requests

def get_user_repos(access_token):
    r = requests.get(
        "https://api.github.com/user/repos",
        headers={
            "Authorization": f"Bearer {access_token}",
            "Accept": "application/vnd.github+json",
            "User-Agent": "MyApp/1.0",
        },
        timeout=10,
    )
    r.raise_for_status()
    return r.json()
```

**Step ⑥ is exactly Lesson 22** — OAuth's complexity is in **steps ①-⑤**; once you have a token it's ordinary Bearer auth.

## Why client_secret Is "Confidential"

**This is the core of OAuth security**:

```
client_id      = public (like your username)
client_secret  = secret (like your password)
```

**What `client_secret` proves**: "this request really came from my app, not someone impersonating it."

**If it leaks**: an attacker can impersonate your app. **Therefore**:

- **never in frontend JS** (users open F12 and see it)
- **never in a mobile app** (apps can be decompiled)
- **only on your server**

### Pure frontend / mobile: PKCE

**The problem**: if your app is a pure SPA or mobile app with **no server**, nowhere is safe for `client_secret`.

**The fix**: **PKCE** (Proof Key for Code Exchange, pronounced "pixy").

**How it works**: instead of a fixed secret, **generate a dynamic pair for each authorization**:

```
1. Client generates a random code_verifier
2. SHA256-hash it to get code_challenge
3. Step ① sends the code_challenge
4. Step ④ sends the code_verifier (the original)
5. Server checks: hash(code_verifier) == code_challenge ?
```

**Why that's safe**: even if an attacker intercepts `code`, they lack `code_verifier` and can't exchange it.

```python
import secrets
import hashlib
import base64

# ① generate a random verifier
verifier = secrets.token_urlsafe(32)

# ② challenge = base64url(sha256(verifier))
digest = hashlib.sha256(verifier.encode("ascii")).digest()
challenge = base64.urlsafe_b64encode(digest).rstrip(b"=").decode("ascii")

print(f"verifier  = {verifier}")     # used at step ④
print(f"challenge = {challenge}")    # used at step ①
```

> **Line-by-line**
>
> - **①** `secrets.token_urlsafe(32)` produces a cryptographically secure random string
> - **②** PKCE's **S256** method: SHA256 hash + base64url + **strip trailing `=`** (`rstrip(b"=")`)
>
> **Note**: **PKCE is now recommended everywhere**, including server-side web apps. OAuth 2.1 makes it mandatory.

## Other OAuth Flows (Just to Know Them)

| Flow | Use | Still use it? |
|---|---|---|
| **Auth code + PKCE** | standard user-facing scenario | ✅ **recommended** |
| Implicit | legacy pure frontend | ❌ **deprecated**, insecure |
| Password | user gives the app their password | ❌ **deprecated**, defeats OAuth's purpose |
| Client Credentials | server accessing its own resources, no user | ✅ for M2M (machine-to-machine) |

**Remember**: **both the implicit and password flows are deprecated in OAuth 2.1.** Old tutorials still teaching them are outdated.

## When You Need to Write OAuth Code

**Honestly: usually you don't write it from scratch.**

**Option one: use a library**

```bash
pip install authlib        # or requests-oauthlib
```

```python
from authlib.integrations.requests_client import OAuth2Session

client = OAuth2Session(client_id, client_secret, scope="repo")
uri, state = client.create_authorization_url(
    "https://github.com/login/oauth/authorize")
# redirect the user to uri

# in the callback:
token = client.fetch_token(
    "https://github.com/login/oauth/access_token",
    code=request.args.get("code"),
)
```

**The library handles**: state generation and verification, PKCE, token refresh, error classification. **Use a library.**

**Option two: just use a PAT** (Lesson 22)

**If it's only for yourself** (a script managing your own repos), **you don't need OAuth at all** — generate a Personal Access Token on GitHub.

**OAuth exists for "someone else's app accessing someone else's account."** For your own account, a PAT suffices.

## Crash Site

### Crash 1: client_secret in the frontend

```javascript
// ❌ Disaster (frontend JS)
const CLIENT_SECRET = "abc123";   // visible via F12
```

**Consequence**: anyone can impersonate your app, and user data flows to attackers.

**Lesson**: **`client_secret` is server-side only.** Pure frontends use PKCE.

### Crash 2: not verifying state

```python
# ❌ Dangerous
code = request.args.get("code")
token = exchange_code_for_token(code)      # no state check
```

**Consequence**: **CSRF.** An attacker crafts a callback using **their own authorization code**, binding your account to their GitHub.

**Lesson**: **always verify state.** The most commonly skipped step in OAuth, with the worst consequences.

### Crash 3: thinking OAuth is the same as "logging in"

**Common confusion**: is "Log in with GitHub" OAuth?

**Precisely**:

- **OAuth solves authorisation** — letting an app access your data
- **Login (authentication) is a different problem** — confirming "who you are"

**OpenID Connect (OIDC)** is an authentication layer built on OAuth2 that solves login. It adds an **id_token** (a JWT) carrying identity info.

**Practical advice**: **if you're building "log in with X", use OIDC, not bare OAuth2.**

### Crash 4: storing tokens unencrypted

```python
# ❌ Dangerous
with open("tokens.txt", "w") as f:
    f.write(access_token)      # plaintext on disk
```

**Consequence**: anyone or anything that can read that file on your server gets the user's token.

**Lesson**: **encrypt stored tokens**, or use the OS key management service. At minimum **set file permissions to 600**.

## Why This Matters for Your Code

1. **OAuth's core is "don't give the password to the third party"** — understand that and the rest is detail
2. **The extra step (④) exists to keep the long-lived credential out of the browser**
3. **Use `data=`, not `json=`** (RFC 6749 requires a form)
4. **Always verify `state`** — skipping it enables CSRF
5. **`client_secret` stays server-side**; pure frontends use PKCE
6. **Usually you don't write this yourself** — PAT for personal use, authlib for products
7. **Once you have a token, it's Lesson 22's Bearer auth**

## Summary

- **OAuth solves "limited third-party access"**: your password never leaves the authorization server
- **Three roles**: resource owner (you) · client (third party) · authorization server (GitHub)
- **Six steps**: auth URL → user consents → callback with code → **exchange server-side** → get token → call API
- **The detour at ④ keeps the access_token out of the browser**
- **Token exchange uses `data=` (form)**, while `Accept` can be JSON
- **`state` prevents CSRF and must be verified** (generate with `secrets`)
- **`client_secret` is server-side only — never in the frontend**
- **Pure frontend/mobile uses PKCE** (dynamic verifier + challenge instead of a fixed secret)
- **Implicit and password flows are deprecated**
- **Personal use → PAT; building a product → `authlib`**
- ❌ Don't put the secret in the frontend; don't skip state verification; don't store tokens in plaintext
