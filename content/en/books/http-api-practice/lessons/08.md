# 08 Headers: HTTP's Metadata System

> An HTTP/0.9 request was one line — `GET /index.html` — with no headers. Open any web page today and you'll find a dozen request headers and twenty or thirty response headers. This lesson explains what headers actually are, why they're a key-value dictionary rather than something else, which ones you must know, and a 30-year-old mix-up involving the `X-` prefix.

## Why Headers Were Needed

Back to Lesson 04. HTTP/0.9 had no headers because there was no "extra information" to convey — just one action (GET) and one target (a path).

Problems appeared almost immediately:

**Problem one**: the browser wants to tell the server "I'm Netscape, I can display images." Nowhere to say it.

**Problem two**: the server wants to tell the browser "this is HTML, not an image." Nowhere to say it.

**Problem three**: a user filled in a form; the server wants to know "how long is this data?" Nowhere to say it.

**Problem four**: two websites run on one server, which needs to know "which domain do you want?" **Nowhere to say it** — and this was the fatal one. As Lesson 04 covered, it's why HTTP/1.1 had to introduce the `Host` header.

So HTTP/1.0 (RFC 1945) formally introduced headers. The design was dead simple — **a pile of plain-text key-value pairs**:

```text
GET /index.html HTTP/1.0
User-Agent: NCSA_Mosaic/2.0 (Windows 3.1)
Accept: text/html
```

One per line, formatted `Name: value`, with header block and body separated by a **blank line**.

## Why Text, and Why This Shape

Three consequences worth spelling out, because they shaped everything since:

### Consequence one: you can hand-write an HTTP request with telnet

Because headers are plain text, in principle any tool that can send text can send HTTP:

```text
$ telnet example.com 80
GET / HTTP/1.1
Host: example.com

```

Hit enter twice (that blank line) and the server responds. **No code at all, just typing.**

That wasn't showing off back then — it was **how you debugged**. Today you have curl, Postman, and browser devtools, but internalising "HTTP is just text" gives you confidence when you look at a raw packet capture.

### Consequence two: extension costs nothing

Want to add a custom field? Add a line `My-Thing: hello`. Servers that don't know it ignore it; those that do act on it.

**That's why headers could grow to dozens while the HTTP version number took 30 years to go from 1.1 to 3.** Header extensibility absorbed most new requirements. Compare that to binary protocols with fixed fields, where adding one field means shipping a new version.

### Consequence three: they got big, and they're repeated every time

That's the cost. Every request carries a dozen-plus headers, and `Cookie`, `User-Agent`, `Accept-Language` are nearly identical every time.

**HTTP/2's header compression (HPACK) exists specifically for this** — as Lesson 05 covered, it maintains a "header dictionary" so repeated headers are sent as a single index number.

## Four Rules of Headers

### Rule one: names are case-insensitive

```text
Content-Type: application/json
content-type: application/json
CONTENT-TYPE: application/json
```

**All three are exactly equivalent.** The spec states plainly that header field names are case-insensitive.

`requests` implements this with `CaseInsensitiveDict`:

```python
import requests

r = requests.get("https://api.github.com", timeout=10)
print(r.headers["content-type"])     # ① lowercase works
print(r.headers["Content-Type"])     # ② uppercase works
print(r.headers["CONTENT-TYPE"])     # ③ all caps works too
```

> **Line-by-line**
>
> - **①②③** All three print the same thing. Not coincidence — `requests` deliberately stores response headers in a `CaseInsensitiveDict`
> - **Why care**: the server sends `Content-Type` today and `content-type` tomorrow, and your code still works. **If you parse raw text yourself, this trap will bite you**

### Rule two: a blank line is mandatory between headers and body

A request/response looks like:

```text
request line / status line
Header1: value1
Header2: value2
              ← this blank line is required
body content…
```

**Without it, the server can't tell where headers end.** It's the single most common mistake when writing the protocol by hand.

### Rule three: the same header may appear multiple times

`Set-Cookie`, for instance — a server can issue several cookies by sending several `Set-Cookie` lines.

**In that case `r.headers["Set-Cookie"]` returns only one of them** — a classic trap in HTTP header handling.

### Rule four: order doesn't matter (with one exception)

The spec says header field order carries **no meaning** (unless a specific field defines one). Servers shouldn't rely on `Accept` preceding `Host`.

The one exception is **Host**: it must be the first header in an HTTP/1.1 request (because the server needs to know which site you want up front).

## Request Headers You Must Know

| Header | Purpose | If you omit it |
|---|---|---|
| **Host** | target domain (required in HTTP/1.1) | server returns 400 |
| **User-Agent** | who I am (browser/scraper identity) | many sites refuse outright |
| **Accept** | which formats I can handle | server doesn't know to send JSON vs XML |
| **Accept-Encoding** | which compressions I support (gzip/br) | no compression; double the traffic |
| **Authorization** | credentials | 401 |
| **Content-Type** | what format my body is | server fails to parse |
| **Content-Length** | how long the body is | server doesn't know where to stop |
| **Cookie** | session state | every request looks like a new user |
| **Referer** | which page I came from | hotlink protection breaks |
| **If-None-Match** | I have this version (ETag) | no 304; can't save bandwidth |

## Response Headers You Must Know

| Header | Purpose |
|---|---|
| **Content-Type** | body format (**with charset** is the complete form) |
| **Content-Length** | body size in bytes |
| **Set-Cookie** | issue a cookie |
| **Cache-Control** | how to cache |
| **ETag** | resource fingerprint (pairs with 304) |
| **Location** | redirect target (pairs with 3xx) |
| **WWW-Authenticate** | mandatory with 401; explains how to authenticate |
| **Retry-After** | with 429/503, how long to wait |
| **Access-Control-Allow-Origin** | cross-origin permission (CORS) |

## Code: Headers in requests

### Sending custom headers

```python
import requests

headers = {                                   # ① organise as a dict
    "User-Agent": "MyApp/1.0",                #    identity
    "Accept": "application/json",             #    JSON only, please
    "Accept-Language": "zh-CN",               #    Chinese please
}

r = requests.get(                             # ② pass via headers=
    "https://api.github.com/user",
    headers=headers,                          #    note: keyword argument
    timeout=10,
)
```

> **Line-by-line**
>
> - **①** Headers are just an ordinary dict. **Keys are header names, values are strings**
> - **②** `headers=` is a keyword argument. **Don't pass it positionally** — `requests.get()`'s second positional parameter is `params`, so your headers would silently become query parameters. The request still sends, but no headers get set, and you'll be confused for a long time

### Header values are strings, not numbers

```python
# ❌ Wrong
headers = {"X-Count": 42}            # an int; may fail in some cases

# ✅ Right
headers = {"X-Count": "42"}          # a string
```

HTTP headers are a **text protocol**; values must be strings. `requests` sometimes converts for you, but that's not guaranteed — **always use strings**.

### Reading response headers: use .get(), not []

```python
r = requests.get("https://api.github.com/user", timeout=10)

print(r.headers.get("Content-Type"))       # ① recommended
print(r.headers.get("X-RateLimit-Remaining"))  # ② may be None
# print(r.headers["X-RateLimit-Limit"])    # ③ raises KeyError if absent
```

> **Line-by-line**
>
> - **①** `.get()` returns `None` when missing instead of raising
> - **②** GitHub's remaining rate limit lives in this header. **Getting None is perfectly normal** (e.g. before any limiting happens, or the server version changed)
> - **③** `[]` raises `KeyError` for absent headers. **Use `.get()` unless you're certain it's there**

### See what a real request actually sent

This trick is invaluable — **if you're unsure what went out on the wire, print it**:

```python
import requests

r = requests.get("https://api.github.com/user", timeout=10)

print("—— headers I sent ——")
for k, v in r.request.headers.items():      # ① note: r.request.headers
    print(f"{k}: {v}")

print("—— headers the server returned ——")
for k, v in r.headers.items():              # ② this one is the response
    print(f"{k}: {v}")
```

> **Line-by-line**
>
> - **①** **`r.request.headers` is the request; `r.headers` is the response.** Confusing these is among the most common beginner mistakes — `r.headers` is what the server sent back, not what you sent
> - **②** `r.headers` is the response headers
>
> **Why this matters**: when you find "I clearly set the Authorization header but the server says 401," the first move is printing `r.request.headers` to see whether it was actually sent. Eight times out of ten it was dropped by a redirect, or never set at all

## The X- Prefix Mix-Up

You've probably seen `X-Requested-With`, `X-API-Key` and friends. The story is worth telling: it's officially deprecated, yet the whole world still uses it.

### Origin

In 1982, the mail standard RFC 822 specified that **custom, non-standard mail headers must start with `X-`** to avoid colliding with standard ones. A fine idea.

### Spread

People carried the convention into HTTP. Throughout the 1990s and 2000s, every custom HTTP header got an `X-`:

```text
X-Forwarded-For: the client's real IP
X-Requested-With: XMLHttpRequest
X-RateLimit-Remaining: remaining quota
```

### The problem

**Once an `X-` header is widely used, it becomes a de facto standard. Then it's too late to drop the prefix** — every existing line of code says `X-`, and renaming breaks everything.

That's why `X-Forwarded-For` is used constantly yet permanently carries the "non-standard" marker. **It is standard; the name just can't change.**

### Official stop

In 2012, RFC 6648 said plainly: **stop adding `X-` to new headers.** Reasoning: since removing it is practically impossible, the prefix has lost its meaning and only creates confusion.

**But** — developers worldwide collectively ignored the advice. New APIs today still ship `X-API-Key` and `X-Request-ID` everywhere.

**Advice for you**: **follow the API's documentation.** If it says `X-API-Key`, write `X-API-Key`; don't "improve" it. If you're designing the API yourself, an unprefixed name (`Api-Key`) matches current guidance — but be ready for colleagues asking "why no X-?"

## Crash Site

### Crash 1: setting Content-Length by hand

```python
# ❌ Wrong
data = '{"name": "Alice"}'
requests.post(
    url,
    data=data.encode("utf-8"),
    headers={"Content-Length": str(len(data))},   # computing it manually
)
```

**Symptom**: sometimes the server receives truncated data; sometimes it waits until timeout.

**Cause**: `len(data)` counts **characters**, but `Content-Length` must be **bytes**. Non-ASCII characters take multiple bytes in UTF-8:

```python
s = "café"
print(len(s))                       # 4   ← characters
print(len(s.encode("utf-8")))       # 5   ← bytes ★ this is Content-Length
```

You told the server "I'm sending 4 bytes" but actually sent 5 — the server stops at byte 4, and **the remainder is treated as the next request** or simply discarded.

**Lesson**: **always let `requests` compute `Content-Length`.** It's automatic; don't set it yourself.

### Crash 2: mixing json= with a manual Content-Type

```python
# ❌ Wrong
requests.post(
    url,
    json={"name": "Alice"},
    headers={"Content-Type": "application/x-www-form-urlencoded"},  # overridden
)
```

**Symptom**: server says it can't parse the body.

**Cause**: `json=` automatically sets `Content-Type: application/json`. Your manual header claims form encoding, so the **body is JSON but declares itself a form** — the server parses JSON as a form and fails.

**Lesson**: **when you use `json=`, don't set Content-Type yourself.** The two must agree. Lesson 17 covers the difference in detail.

### Crash 3: redirects drop the Authorization header

```python
# Request site A; it 302-redirects to site B
r = requests.get("https://a.com/data", headers={"Authorization": "Bearer xxx"})
```

**Symptom**: A returns 302, you follow to B, and B says 401.

**Cause**: **`requests` deliberately strips `Authorization` on cross-domain redirects.** Intentional, not a bug.

Why? Carrying credentials meant for A over to B **hands A's password to B**. That's a serious security problem, so `requests` removes it by default.

**Lesson**: **to keep auth across domains, handle it yourself** — either follow manually (`allow_redirects=False`, then send the second request) or confirm both hostnames belong to the same service.

## Why This Matters for Your Code

1. **`r.headers` is the response; `r.request.headers` is the request.** Mixing them wastes enormous time — debugging any "I set it but it didn't take" starts by printing `r.request.headers`
2. **Read headers with `.get()`.** Servers don't guarantee any given header; `[]` throws `KeyError` in production
3. **Names are case-insensitive, but values are arbitrary strings** — `Content-Length` arrives as `"1234"`, so `int()` it before doing arithmetic
4. **Don't set `Content-Length` or `Content-Type` by hand** (when using `json=`). Let the library compute them
5. **Redirects drop Authorization** — that's a security design, not a bug to "fix"

## Summary

- Headers are **plain-text key-value pairs**, introduced in HTTP/1.0 to carry "extra information"
- Because they're text, **you can hand-write requests with telnet** — and **they gained enormous extensibility**
- The cost: **a big pile of headers repeated on every request** — HPACK in HTTP/2 compresses them
- **Names are case-insensitive** (via `CaseInsensitiveDict`); **values must be strings**
- **A blank line is required between headers and body** — easiest thing to forget when hand-writing
- A header may repeat (e.g. `Set-Cookie`); `[]` returns only one
- **Must know** — request: Host / User-Agent / Accept / Authorization / Content-Type; response: Content-Type / Set-Cookie / ETag / Location / Retry-After
- **The `X-` prefix comes from the 1982 mail standard, was deprecated by RFC 6648 in 2012, and is still used everywhere**
- ❌ Don't set `Content-Length` manually (characters ≠ bytes); don't override Content-Type with `json=`
