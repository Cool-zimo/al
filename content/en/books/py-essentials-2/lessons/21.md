# Exception Handling Review

> This lesson does not re-teach concepts. It does three things: **recap the key points in thirty seconds, correct the three most common mistakes, and test whether you really understand it.**
> If anything in the recap looks unfamiliar, go back and read Lesson 21 of the *Learning* book first, then come back and do the exercises.

## 30-Second Recap

```python
try:
    x = int(input("Enter a number: "))   # may raise ValueError
    y = 10 / x                      # may raise ZeroDivisionError
except ValueError:
    print("That is not a number")
except ZeroDivisionError:
    print("Cannot divide by zero")
else:
    print("The result is", y)          # runs only if nothing was raised
finally:
    print("This always runs")     # always runs
```

| Clause | When it runs | Common use |
|---|---|---|
| `try` | Holds code that might fail | Wrap "unsure if it will succeed" operations |
| `except E:` | An exception `E` was raised in `try` | Provide an alternative or a message |
| `else:` | **No** exception was raised | Logic for "success only" |
| `finally:` | No matter what | Release resources, clean up |

`raise` is used to raise an exception deliberately; a bare `raise` **re-raises the current exception exactly as it is.**

## Three Things People Get Wrong

### 1. A bare `except:` swallows keyboard interrupts

```python
# WRONG
try:
    do_something()
except:                     # equivalent to except BaseException:
    print("Something went wrong")
```

A bare `except:` catches `BaseException`, **including `KeyboardInterrupt` (Ctrl+C) and `SystemExit`.** The result: the user hits Ctrl+C to interrupt the program, and the program acts as if nothing happened and keeps running — a disaster in command-line tools.

Even worse, it hides the real bug:

```python
try:
    result = 100 / n
except:
    result = None            # whether n is None, a string, or zero... one message for all
```

```python
# RIGHT
try:
    result = 100 / n
except ZeroDivisionError:
    print("Divisor cannot be zero; please check your input")
    result = None
```

**Only catch exceptions you know how to handle.** If you do not know how to handle it, do not catch it — let it bubble up, and the traceback will tell you exactly what went wrong.

### 2. `except` ordering: subclasses must come first

```python
# WRONG
try:
    x = int(input())
    y = 10 / x
except Exception:
    print("General error")
except ZeroDivisionError:    # never reachable
    print("Division by zero")
```

`Exception` is the parent of `ZeroDivisionError`. With `except Exception` first, it swallows everything, and the branch below becomes dead code.

```python
# RIGHT: most specific first
try:
    x = int(input())
    y = 10 / x
except ValueError:
    print("Please enter a valid number")
except ZeroDivisionError:
    print("Cannot divide by zero")
except Exception as e:
    print(f"Other error: {e}")
```

**Rule of thumb: child before parent, specific before broad.** Getting this order wrong is one of the easiest mistakes to spot in a code review.

### 3. `else` and `finally` are often conflated

```python
# WRONG: stuffing "success-only" logic into try
try:
    data = load_data()
    print(f"Loaded {len(data)} records")   # this line will not raise, yet it sits in try
    save_result(process(data))
except IOError:
    print("Failed to read")
```

The `try` block should be **as short as possible**, wrapping only the one line that can actually fail. Otherwise, if `print` or `save_result` raises, it gets misattributed to "failed to read."

```python
# RIGHT: try only handles loading
try:
    data = load_data()
except IOError:
    print("Failed to read")
else:
    print(f"Loaded {len(data)} records")
    save_result(process(data))
finally:
    cleanup()
```

`else` = logic for after success; `finally` = cleanup that must happen no matter what (close files, return connections, delete temp files). And here is an interview classic: if you `return` inside `finally`, it **overrides** the return value from `try`/`else`:

```python
def f():
    try:
        return 1
    finally:
        return 2     # the function ultimately returns 2; the return 1 in try is overridden

print(f())           # 2
```

## Crash Site: Re-raising must be a bare `raise`

```python
import json

def load_config(path):
    try:
        with open(path) as f:
            return json.load(f)
    except json.JSONDecodeError as e:
        print("Bad config format; using defaults")
        raise e          # looks fine, but it is not
```

**Problem 1: redundant.** `raise e` re-raises this exception, but the traceback will start at the line `raise e`, cutting off the original `json.load` line — making it impossible to locate the real culprit while debugging.

**Problem 2: if `e` is an exception class rather than an instance, `raise e` constructs a new instance and loses the original context.**

The correct form is a **bare `raise`**:

```python
import json

def load_config(path):
    try:
        with open(path) as f:
            return json.load(f)
    except json.JSONDecodeError:
        print("Bad config format; using defaults")
        raise                # re-raise as-is, preserving the full traceback
```

This rule also has a practical application — **log, then re-raise**: catch, log, and then `raise` so the layer above decides what to do, instead of swallowing it on the spot. This is the flip side of "only catch what you know how to handle": logging does not count as "handling," and you still need to pass it to whoever can.

## Summary

- Never write a bare `except:`; at least write `except Exception`, and be as specific as possible
- `except` order is **child before parent**; a parent first blocks the child branch
- Keep the `try` block short; put success logic in `else`, cleanup in `finally`; a `return` in `finally` overrides earlier returns
- Re-raise with a bare `raise`, not `raise e`
- If you do not know how to handle an exception, do not catch it — let it bubble up

## Section Quiz

```quiz
type: choice
exam: true
q: What does this code output?
code: |
  try:
      x = int("abc")
  except ValueError:
      print("A")
  except Exception:
      print("B")
  else:
      print("C")
  finally:
      print("D")
options:
- A D
- B D
- A
- A C D
answer: 0
explain: int("abc") raises ValueError, hitting the first except and printing A; finally always runs, printing D. else runs only if nothing was raised, so C is not printed. Exception is the parent of ValueError but comes later, so it never gets a turn.
```

type: function

func: safe_average
starter: |
  def safe_average(nums):

      # summing may encounter a non-number; catch TypeError

  [1, 2, 3, 4] -> 2.5

  [] -> ValueError("List cannot be empty")
