## 30-Second Recap

```python
# Data looks like this: each student has one or more subjects
students = [
    {"name": "Alice", "scores": {"Math": 88, "English": 92, "Science": 76}},
    {"name": "Bob", "scores": {"Math": 95, "English": 87, "Science": 90}},
]

# Common statistical patterns
avg = sum(s["scores"].values()) / len(s["scores"])   # individual average
total = sum(s["scores"].values())                     # individual total
ranked = sorted(students, key=lambda s: total, reverse=True)  # rank by total
```

A grade system is harder than a contact book because: **each student has multiple subjects, and you must compute totals, averages, ranks, the highest score per subject, and class-wide statistics.** That means you will use nested dicts, comprehensions, `sorted` with a `key`, and function encapsulation all at once — everything from the previous lessons converges here.

## Three Things People Get Wrong

### 1. Computing rank with "index + 1" and forgetting ties

```python
# WRONG
ranked = sorted(students, key=lambda s: sum(s["scores"].values()), reverse=True)
for i, s in enumerate(ranked):
    print(i + 1, s["name"])      # two students with the same score get 1, 2
```

If Alice and Bob both total 260, users expect two first places and the next student to be third — not 1, 2.

```python
# RIGHT: same score keeps the same rank; skip a number after a tie
def rank_students(students):
    totals = [(sum(s["scores"].values()), s["name"], s) for s in students]
    totals.sort(reverse=True, key=lambda t: t[0])
    result = []
    rank = 1
    for i, (total, name, s) in enumerate(totals):
        if i > 0 and total != totals[i - 1][0]:
            rank = i + 1          # only update the rank when the score changes
        result.append((rank, s))
    return result
```

This is the difference between a "real ranking" and "just a sorted order." Many beginners assume that `enumerate` plus one *is* the rank; ship it, and ties immediately give it away.

### 2. Computing the wrong average: the wrong denominator when subjects are missing

```python
# WRONG
def average(scores_dict):
    return sum(scores_dict.values()) / len(scores_dict)   # number of subjects
```

This looks fine, but if a student missed one subject (it is not in the dict), the denominator is too small. The really sneaky case is **the class average for one subject**:

```python
# WRONG: take every score, then divide
all_math = [s["scores"]["Math"] for s in students]        # KeyError if someone missed it
avg_math = sum(all_math) / len(all_math)
```

```python
# RIGHT: count only students who actually have this subject
def subject_average(students, subject):
    scores = [s["scores"][subject] for s in students if subject in s["scores"]]
    if not scores:                    # must check for empty, or ZeroDivisionError
        return 0.0
    return sum(scores) / len(scores)
```

**The check `if not scores` is mandatory** — without it, a class where everyone missed the exam crashes the program instead of giving "0.0." This is the same family of problem as `all([])` in Lesson 21: empty sets need special handling.

### 3. Mixing statistical computation with print formatting

```python
# WRONG
def report(students):
    for s in students:
        total = sum(s["scores"].values())
        avg = total / len(s["scores"])
        print(f"{s['name']}: total {total} avg {avg:.1f}")
        if avg >= 90:
            print("  Grade: Excellent")
        elif avg >= 60:
            print("  Grade: Pass")
        else:
            print("  Grade: Fail")
```

This function **can only print.** If you want to turn it into a web table, an Excel sheet, or an SMS to the student, you have to rewrite the statistics.

```python
# RIGHT: compute first, render after
def compute_stats(students):
    """Pure function: returns structured data, does not print."""
    return [{
        "name": s["name"],
        "total": sum(s["scores"].values()),
        "average": sum(s["scores"].values()) / len(s["scores"]),
        "level": level_of(sum(s["scores"].values()) / len(s["scores"])),
    } for s in students]

def level_of(avg):
    if avg >= 90: return "Excellent"
    if avg >= 60: return "Pass"
    return "Fail"

def render_text(stats):
    """Only turns structured data into strings."""
    for st in stats:
        print(f"{st['name']}  total {st['total']}  avg {st['average']:.1f}  {st['level']}")
```

**Separating computation from display is the single most valuable lesson of this project.** It makes your statistics reusable and your tests simple — asserting on a dict is a hundred times more reliable than parsing a printed line.

## Crash Site: Boundary values in grade levels

```python
# WRONG
def level(avg):
    if avg > 90:
        return "Excellent"
    elif avg > 60:
        return "Pass"
    else:
        return "Fail"
```

A student who scored exactly 90 gets "Pass" — and the user will complain. This **off-by-one in conditions** is the most common bug beginners make, and the easiest one for users to spot.

```python
# RIGHT
def level(avg):
    if avg >= 90:     # note: >=
        return "Excellent"
    if avg >= 60:
        return "Pass"
    return "Fail"
```

When testing boundaries, **specifically test 89.9, 90, and 60**:

```python
assert level(89.9) == "Pass"
assert level(90) == "Excellent"      # the WRONG version fails here
assert level(60) == "Pass"
assert level(59.9) == "Fail"
```

This habit is called **boundary-value testing**, and it gives you the most bang for your buck. Anywhere you write `>= 90`, test the three points 89, 90, and 91. If your program survives that, it is truly correct.

## Summary

- Multi-subject grades use nested dicts: `{"name": ..., "scores": {"Math": 88, ...}}`
- Ranking must handle ties: update the rank only when the score changes, skipping numbers after a tie
- Before computing statistics, decide whether the denominator is the **number of subjects or the number of students**; return 0.0 for empty sets
- Grade levels use `>=` and **specifically test the boundaries 89/90/60**
- Separate computation from display: pure functions return structured data; renderers are written separately
- Finishing this project means you can already write "usable programs"

## Appendix: Which Path Should You Take Next?

You have now mastered **all the foundational syntax of Python.** Where you go from here depends on what you want to do with it. Four paths, each with a first step:

**1. Data Analysis**
Learn `pandas` (filter, group, aggregate DataFrames) + `matplotlib` / `seaborn` (plotting). First step: download a real dataset from Kaggle and use it to answer three questions you genuinely care about. This path leads to operations analysis, business analysis, and data science.

**2. Algorithms and Competitive Programming**
Work through LeetCode easy-to-medium problems, focusing on **arrays, hash maps, two pointers, sliding windows, trees, and graphs.** At the same time, study complexity analysis (time and space). First step: one problem a day, and always read the optimal solution in the editorial afterward. This path leads to backend engineering, algorithm roles, and technical interviews.

**3. Desktop and Visual Apps**
Learn `tkinter` (ships with the standard library) or `PySide6` to build windowed applications. Take the grade system you just built and give it a graphical interface. First step: turn the Lesson 24 contact book into a windowed app with buttons and a table. This path leads to tool development and internal systems.

**4. Software Engineering**
Learn `git` + GitHub, unit testing (`pytest`), virtual environments, type annotations, code style (`ruff` / `black`), and packaging (`pyproject.toml`). First step: put your contact book in a Git repo, write a README, and add unit tests. This path leads to software engineer and open-source contributor.

Whichever path you choose, **writing code consistently matters more than picking the perfect path.** Your syntax is already sufficient — everything from here on is "build projects."
