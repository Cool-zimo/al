# Modules and Imports Review

> If anything in the recap looks unfamiliar, go back and read Lesson 22 of the *Learning* book first, then come back and do the exercises.

## 30-Second Recap

```python
import math                  # usage: math.sqrt(2)
import os.path as osp        # alias, to avoid long names
from random import choice    # import one name; use choice([1,2,3]) directly
from collections import *    # import all public names (not recommended in real code)
```

| Form | What gets imported | How to call |
|---|---|---|
| `import math` | The whole module | `math.sqrt(2)` |
| `import math as m` | The whole module, aliased as `m` | `m.sqrt(2)` |
| `from math import sqrt` | Just the name `sqrt` | `sqrt(2)` |
| `from math import *` | All public names | `sqrt(2)` (pollutes the namespace) |

A module is **one `.py` file**. A package is **a folder with an `__init__.py`** (Python 3.3+ allows namespace packages without it, but adding one is clearer).

## Three Things People Get Wrong

### 1. `from x import *` overwrites your variables

```python
# WRONG
from math import *
sqrt = 3.14            # you meant to name the "circle constant"
print(sqrt(9))         # TypeError: 'float' object is not callable
```

`from math import *` dumps dozens of names — `sqrt`, `sin`, `cos`, `pi` — into the current namespace. After that, using `sqrt` as a variable name silently shadows the function, and Python gives no warning at all.

`import *` has two more hard flaws: when reading code you cannot see where a name came from, and tools cannot statically analyze which names are actually used.

```python
# RIGHT
import math
sqrt = 3.14
print(math.sqrt(9))    # 3.0   -- the module name acts as a namespace; no interference
```

Using `from x import *` for convenience is fine during interactive exploration, but in files you must use `import x`.

### 2. `if __name__ == "__main__":` is not decoration — it is the dividing line between "reusable" and "not"

```python
# tools.py
def double(x):
    return x * 2

print(double(10))      # left over from debugging
```

Another file, `main.py`:

```python
import tools           # importing immediately prints 20, polluting main.py's output
print(tools.double(5))
```

```python
# the correct tools.py
def double(x):
    return x * 2

if __name__ == "__main__":
    print(double(10))  # only runs when you execute python tools.py directly
```

`__name__` is the module's "name." **When run directly it is set to `"__main__"`; when imported it is set to the filename** (`"tools"`). The meaning of this check is: "Only run this block when used as the program's entry point. When imported by others, just provide functions — do not cause side effects."

### 3. A module is imported only once; editing it does not reload it

```python
# config.py
TIMEOUT = 30
```

```python
import config
print(config.TIMEOUT)   # 30
# Now you edit config.py in your editor to TIMEOUT = 60 and save
print(config.TIMEOUT)   # still 30!
```

On the first `import`, Python executes the module's top-level code and caches the result in `sys.modules`. Every subsequent `import` fetches from that cache **without re-reading the file**. This is deliberate — re-executing top-level code would be both slow and dangerous.

To force a reload:

```python
import importlib
import config
importlib.reload(config)   # debugging only; never in production
```

The real solution is to **restart the interpreter**. This is also why an IDE's "run" button always launches a fresh process.

## Crash Site: `__pycache__` looks like junk, but it is not

```bash
$ python main.py
$ ls
main.py  utils.py  __pycache__/
$ ls __pycache__/
utils.cpython-311.pyc
```

```python
# Deleting __pycache__ and running again: the program still works
# But after deleting utils.py...
$ python main.py
ModuleNotFoundError: No module named 'utils'
```

`__pycache__` holds `.pyc` files — Python caches the compiled bytecode so that **next time it skips compilation and loads directly**, saving tens of milliseconds. It is managed entirely by Python: you can delete it and rebuild it; it is not something you need to maintain manually.

The real trap is **circular imports**:

```python
# a.py
import b
def fa():
    return b.gb() + 1

# b.py
import a                 # a is not finished loading yet; a.fa does not exist yet
def gb():
    return a.fa() - 1    # AttributeError: module 'a' has no attribute 'fa'
```

Importing `a` executes `a.py`, which hits `import b` and switches to `b.py`. Then `b.py` tries to `import a`, but `a` is only halfway done — so `b` gets a **half-built `a` module object** in which `a.fa` simply does not exist yet.

The fixes: move the import inside the function (a deferred import), or refactor the common parts into a third module. This is also why the convention of "put all imports at the top of the file" has to be broken when you hit a circular dependency.

## Summary

- Each of the four `import` styles has trade-offs; in files, prefer `import x` — never use `from x import *`
- `from x import *` pollutes the namespace, shadows same-named variables, and gives no warning
- `if __name__ == "__main__"` lets a file "be both a script and an importable module" — the dividing line of reusability
- A module is loaded once and cached in `sys.modules`; to pick up source changes, restart the interpreter
- `__pycache__` is a bytecode cache — deletable and rebuildable; circular imports are the real problem

## Section Quiz

```quiz
type: choice
exam: true
q: Which of the following is correct about these two forms?
code: |
  # Form A
  from math import sqrt, pi

  # Form B
  import math
options:
- The two forms are completely equivalent; A is just less typing
- A imports every function from math; B imports only two
- A binds sqrt and pi directly into the current namespace; B requires math.sqrt. A does not affect the names inside the math module itself
- B executes every function in math and uses a lot of memory
answer: 2
explain: from ... import simply binds the named references into the current scope; the names still live in the math module. Neither form "imports everything then picks two" — a module is the smallest unit of import. The difference is how much you pollute the namespace.
```

  def make_greeter(greeting):

      def inner(name):

This problem uses a closure to mimic module-level encapsulation: greeting is like a config constant inside the module; inner is like a function in the module. Once you understand this, "why put code in a module" stops being a syntax question and becomes a design question.
