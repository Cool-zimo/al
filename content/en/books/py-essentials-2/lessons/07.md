# Truthiness Rules — Reinforced

> This lesson does not introduce new concepts. It does three things: **recaps the key points in thirty seconds, corrects the three mistakes people make most often, and tests whether you actually understand it through exercises.**
> If any sentence in the recap looks unfamiliar, go back to Lesson 7 of *Essential Python* and come back to the exercises afterwards.

## 30-Second Recap

In Python, every value carries a kind of "truthiness". When used in an `if` condition, Python **converts it to a boolean automatically**.

```python
if name:            # is name an empty string? no -> True
    print("has a name")

if age:             # is age 0? no -> True
    print("has an age")
```

**The following values count as "false"** in a condition; everything else counts as "true":

| Value | Meaning |
|---|---|
| `False` | boolean false |
| `None` | the null value |
| `0`, `0.0` | numeric zero |
| `""` | empty string |
| `[]`, `()` | empty list, empty tuple |
| `{}` | empty dict |
| `set()` | empty set |

Everything else is true — including `"0"`, `[0]`, and `"False"`. **They look false, but none of them is empty.**

```python
if "0":
    print("this runs")      # "0" is not an empty string, so it is true

if [0]:
    print("this also runs")    # [0] is not an empty list, so it is true
```

## Three Things People Get Wrong

### 1. Thinking `and` / `or` only return `True` / `False`

`and` and `or` return **one of the operands themselves**, not a boolean.

```python
print(3 and 5)         # 5
print(0 and 5)         # 0
print(3 or 5)          # 3
print(0 or 5)          # 5
```

The rules:

- `and`: if the left side is false, return it; otherwise return the right side
- `or`: if the left side is true, return it; otherwise return the right side

This is called **short-circuit evaluation**: as soon as `and` sees a false left side, the right side is never even evaluated; likewise, `or` skips the right side once the left is true.

```python
# short-circuit: the right side never runs, so x is never changed to 999
x = 0
x != 0 and print("x is non-zero")     # prints nothing
```

This property is often used for defaults:

```python
name = input() or "anonymous"       # if input() is empty (false), use "anonymous"
```

### 2. Testing truthiness with `==`, writing `if x == True`

```python
# redundant: == True is unnecessary
if x == True:
    print("x is true")
```

Python converts to boolean for you automatically, so `if x:` is enough. `if x == True:` is not only unnecessary but easy to get wrong — for instance, `if x is True:` is stricter still, and only passes when `x` really is the `True` object; even `1` fails.

Even more dangerous is **comparing `[]` to `True`/`False`**:

```python
[] == False      # False  <- an empty list is not equal to False
[] == True       # False  <- and not equal to True either
bool([])         # False  <- but converting it to bool gives false
```

Remember: **`==` is "equal in value"; `bool()` is "convert to boolean"** — they are not the same thing. To test "is it empty?", use `if lst:`, not `if lst == True`.

### 3. `not` has lower precedence than you expect

```python
# WRONG: expecting not to bind tightest
not x == 0       # actually not (x == 0), equivalent to x != 0 — "accidentally right"
not x in [1,2,3] # actually not (x in [1,2,3]), equivalent to x not in [1,2,3]
```

`not` has **lower precedence than comparison operators** (`==`, `in`, `<`, etc.), but **higher precedence than `and` / `or`**. So `not x == 0` really is `not (x == 0)`, and the result happens to be correct — but it is easy to misread.

The real trap is mixing `not` with `and`:

```python
not x and y      # equivalent to (not x) and y
not (x and y)    # this one means "x and y are not both true"
```

Recommendation: **whenever you mix operators, add parentheses**. Code is for humans to read; the compiler will not complain about an extra pair.

## Crash Site: The ripple effect of `or`'s return value

```python
# WRONG: trying to test "is username or password empty"
username = ""
password = "123"

if username or password == "":      # intent: warn if either is empty
    print("username and password cannot be empty")
else:
    print("OK")
```

It looks fine, but `username or password == ""` is parsed as:

```python
(username) or (password == "")      # username is "" (false); password=="" is False
# result is False -> goes to else, prints "OK"
```

The empty username slips through. The issue is **operator precedence**: `==` binds tighter than `or`, so the real grouping is `(username) or (password == "")`.

The correct versions test both explicitly:

```python
if username == "" or password == "":
    print("username and password cannot be empty")
else:
    print("OK")        # username is empty -> prints "username and password cannot be empty"
```

Or, more concisely:

```python
if not username or not password:    # not binds tighter than or
    print("username and password cannot be empty")
```

## Summary

- `False`, `None`, `0`, `0.0`, `""`, `[]`, `()`, `{}`, `set()` are all false; everything else is true
- `"0"`, `[0]`, `"False"` are all true, because they are not empty
- `and`/`or` return one of the operands themselves, and short-circuit (if the left decides it, the right never runs)
- Do not write `== True` / `== False`; use `if x:` / `if not x:`
- `not` has lower precedence than comparisons; add parentheses when mixing
- The classic use of `or`: supplying a default (`name = input() or "anonymous"`)

## In-Class Practice

```quiz
type: code
q: Read one line. If it is empty (user just pressed Enter), print "you entered nothing"; otherwise print "you entered: XXX". The system will feed in an empty line.
starter: |
  # an empty string is falsy in an if; just use if s:
  s = input()
  print("TODO: replace this line with your output")
stdin: |

tests:
- assert "you entered nothing" in __out
hints: if s: tests for non-empty; the else handles empty strings. Writing if s == "": works too, but is wordier.
explain: The empty string "" is falsy in a boolean context, so if s: is False and we go to else. A counter-example if s == True: is never true (an empty string does not equal True), so any input would be judged "nothing entered".
```

## Section Quiz

```quiz
type: choice
exam: true
q: What is the value of the following expression?
code: |
  "" or [] or 0 or "London" or "New York"
options:
- ""
- 0
- "London"
- "New York"
answer: 2
explain: or short-circuits left to right and returns the first truthy value. "" , [] and 0 are all falsy and skipped; "London" is truthy (a non-empty string), so it is returned immediately and "New York" is never evaluated. This is exactly the property that or returns an operand rather than a boolean.
```

```quiz
type: function
exam: true
q: Write first_truthy(a, b, c): return the first "truthy" value among the three arguments (in a, b, c order); if all are false, return "all false".
func: first_truthy
starter: |
  def first_truthy(a, b, c):
      # use the short-circuit property of or, or check with if-elif
      return ""
cases: |
  (0, "", "Alice") -> "Alice"
  (18, "Bob", 0) -> 18
  ([], (), {}) -> "all false"
  ("London", "", 0) -> "London"
hints: Just return a or b or c or "all false". or returns the first truthy value, and when all are false it returns the final "all false".
explain: a or b or c or "all false" exploits the fact that or returns the first truthy value. Note that 18 is returned as the integer 18, not a string; only when all three are false do we return "all false". A counter-example returning True would lose the actual value, failing the requirement to "return the first truthy value".
```
