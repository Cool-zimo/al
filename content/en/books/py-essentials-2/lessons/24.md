# Project I: Contact Book

> This is the first real project of the *Review* book. Everything you learned in the first four chapters — strings, containers, functions and exceptions, files and modules — comes together here.
> The goal is a command-line contact book that can **add, search, edit, delete, persist to disk, and tolerate errors.** Length is not the point; what matters is clear structure, with each layer doing one job.

## 30-Second Recap

```python
def load_contacts(path): ...
def save_contacts(contacts, path): ...
def add_contact(contacts, name, phone): ...
def find_contact(contacts, keyword): ...
def update_contact(contacts, name, new_phone): ...
def delete_contact(contacts, name): ...

def main():
    contacts = load_contacts("contacts.txt")
    while True:
        cmd = input("> ")
        if cmd == "1":
            add_contact(contacts, input("Name: "), input("Phone: "))
        ...
```

A shippable project looks like this: **data (list/dict) + pure functions (no input, no print) + an interaction layer (handles I/O) + persistence (file read/write)** — four layers, clearly separated. Every pitfall in this lesson comes from smashing those four layers into one.

## Three Things People Get Wrong

### 1. Cramming input, computation, and output into a single function

A beginner's contact book usually looks like this:

```python
# WRONG
def add():
    name = input("Name: ")
    phone = input("Phone: ")
    contacts.append({"name": name, "phone": phone})
    print("Added")
    save(contacts)
```

It runs, but **it is untestable**. `add()` embeds `input()`, so writing a unit test means simulating a keyboard. It embeds `print()`, so asserting output means parsing strings. It embeds `save()`, so every test writes to disk for real.

**The correct separation:**

```python
def add_contact(contacts, name, phone):
    """Pure function: only mutates contacts, returns whether it succeeded. No input/print/file."""
    if any(c["name"] == name for c in contacts):
        return False          # duplicate
    contacts.append({"name": name, "phone": phone})
    return True

def cmd_add(contacts):
    """Interaction layer: handles input and print; delegates the business logic to add_contact."""
    name = input("Name: ")
    phone = input("Phone: ")
    if add_contact(contacts, name, phone):
        print("Added")
    else:
        print("Name already exists")
```

Why this split pays off: **`add_contact` can be tested any way you like** — just pass a list and a string. No keyboard, no file, no need to touch a single line of interaction code.

### 2. Inventing your own storage format, then failing to read it back

```python
# WRONG
def save(contacts):
    with open("contacts.txt", "w") as f:
        f.write(str(contacts))   # writes "[{'name': 'Alice', 'phone': '138...'}]"
```

`str(contacts)` looks like Python syntax, but **it is not a reliable serialization format.** Reading it back with `eval()` is even worse — it lets any string in that file execute arbitrary code in your program. That is a classic security hole.

```python
# RIGHT: use json
import json

def save_contacts(contacts, path):
    with open(path, "w", encoding="utf-8") as f:
        json.dump(contacts, f, ensure_ascii=False, indent=2)

def load_contacts(path):
    try:
        with open(path, "r", encoding="utf-8") as f:
            return json.load(f)
    except FileNotFoundError:
        return []                # first run, no file yet -- return an empty list
    except json.JSONDecodeError:
        print("Contact file is corrupted; resetting")
        return []
```

Three details:
- `ensure_ascii=False` writes Chinese **directly**, instead of `\u5f20\u4e09`;
- `FileNotFoundError` must be caught separately — having no file on the first run is normal and should not error out;
- `JSONDecodeError` should also be caught — if someone hand-edits the file into nonsense, the program should not crash.

### 3. Checking for duplicates and looking up by name with handwritten `for` loops

```python
# WRONG: traversing again and again
def find(contacts, name):
    for c in contacts:
        if c["name"] == name:
            return c
    return None

def exists(contacts, name):
    for c in contacts:
        if c["name"] == name:
            return True
    return False
```

There is a cleaner alternative — **use a dict as an index**:

```python
def index_by_name(contacts):
    return {c["name"]: c for c in contacts}

idx = index_by_name(contacts)
if "Alice" in idx:        # O(1) lookup
    print(idx["Alice"]["phone"])
```

But a contact book should **allow duplicate names**, so an index is not a universal solution. For duplicates, use `filter` or a comprehension:

```python
matches = [c for c in contacts if keyword in c["name"]]
```

`in` does substring matching on strings, so entering "Al" finds everyone whose name contains "Al" — far more useful than "must be an exact match."

## Crash Site: A menu loop with no exit condition

```python
# WRONG
while True:
    print("1 Add  2 Find  3 Quit")
    choice = input("> ")
    if choice == "1":
        ...
    elif choice == "2":
        ...
    # forgot elif choice == "3": break
```

The user can never leave the program — only Ctrl+C works. No one notices this when testing on their own machine; hand it to someone else and it shows up immediately.

```python
while True:
    print("\n=== Contact Book ===")
    print("1 Add  2 Find  3 Edit  4 Delete  5 List all  q Quit")
    choice = input("> ").strip().lower()
    if choice == "q":
        save_contacts(contacts, PATH)
        print("Saved. Goodbye.")
        break
    elif choice == "1":
        cmd_add(contacts)
    elif choice == "2":
        cmd_find(contacts)
    elif choice == "3":
        cmd_update(contacts)
    elif choice == "4":
        cmd_delete(contacts)
    elif choice == "5":
        cmd_list(contacts)
    else:
        print("No such option")
```

Three good habits: save on exit rather than after every operation (less disk I/O, and if something crashes you keep the last saved version); `strip().lower()` the choice to tolerate whitespace and capitals; and an `else` branch to catch unknown input instead of silently ignoring it.

## Summary

- A project has four layers: **data / pure functions / interaction / persistence**; pure functions touch no input, print, or file
- Separate for testability, not separation for separation's sake
- Persist with `json.dump(..., ensure_ascii=False)`, not `str()` + `eval()`
- Catch both `FileNotFoundError` (first run) and `JSONDecodeError` (corrupted file)
- Check for duplicates with `in` + comprehensions; allow multiple results when names duplicate
- A menu loop must have an exit condition; save before exiting; handle unknown options
