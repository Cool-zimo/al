# What the Browser, HTML and CSS Each Do

> This lesson answers the question: "How does the text I write become a web page?" Understanding the division of labour makes it obvious where to look when something goes wrong.

## A page is a three-person collaboration

You have already met Python: you write code, the interpreter runs it line by line, and out comes a result. The front end is also "write text, let a machine process it", but this time the machine is the **browser**, and it works with three files, each with its own job.

Think of building a web page like building a house:

| Role | Front-end equivalent | In charge of |
|---|---|---|
| Structural worker | **HTML** | Where the walls are, where the doors are, how many rooms |
| Decorating team | **CSS** | What colour the walls are painted, how wide the floor is laid |
| Electrician / smart devices | **JavaScript** | How the lights come on, what happens when the doorbell is pressed |

Alice bought a plot of land and drew a structural plan (HTML): a bedroom here, a living room there. The plan does **not** say "the walls are beige, the floor is oak" - that is the job of the decorating team (CSS). Likewise, HTML should not say "this text is red"; colour belongs to CSS.

## The browser is a translator

The `.html` file you write is essentially plain text. When you double-click to open it, the first thing the browser reads is a string:

```html
<!DOCTYPE html>
<html>
  <head>
    <title>Alice's homepage</title>
  </head>
  <body>
    <h1>Hello</h1>
    <p>This is my first page.</p>
  </body>
</html>
```

The browser does three things:

1. **Parse**: it splits this text into nodes and builds a tree structure called the **DOM** (Document Object Model).
2. **Compute styles**: it works out "what does this element finally look like".
3. **Paint**: it draws the result on the screen.

In Python you have worked with data structures like dictionaries and lists. The DOM is also a data structure - it is just one the browser builds **automatically** from the HTML you wrote, rather than one you built by hand. When you write `<h1>Hello</h1>`, the browser creates an h1 node whose content is "Hello".

**The DOM is the object of every front-end operation.** When you later write CSS to select elements, or JS to change text, you are essentially working with this tree. This matters far more than memorising tag names.

## HTML only says "what it is", not "what it looks like"

```html
<h1>Alice's CV</h1>
<p>I am a front-end developer.</p>
```

Here `<h1>` means "this is a level-one heading", and `<p>` means "this is a paragraph of body text". You have **not** said how big it is, what font it uses, or what colour it is. Those things belong to CSS.

Someone might ask: but h1 already looks big by default? That is because the browser ships with a built-in "factory stylesheet" (called the user agent stylesheet) that gives h1 a default font size. That comes from the browser, not from HTML. You can, and should, override it in your own CSS.

## CSS only handles "what it looks like"

```css
h1 {
  color: #2c7a7b;
  font-size: 32px;
}
```

This CSS says: every h1 uses this teal colour and a font size of 32 pixels. Notice that it does **not** change the fact that h1 is "a level-one heading" - the semantics are still h1, only the appearance has changed.

## Crash site 1: using a tag to fake an appearance

Someone wants large text, so they write:

```html
<h1>Subheading, but I want it bigger</h1>
<h1>Another subheading</h1>
```

Consequence: the text on the page is big, but search engines, screen readers and the browser's document outline all believe there are two level-one headings. Alice's CV will show two "main titles" in search results, and a visually impaired user listening to a screen reader hears "heading one, heading one" - the structure is broken. The correct approach is `<h2>` plus a CSS font-size adjustment.

## Crash site 2: putting styles inside HTML

```html
<p style="color: red; font-size: 20px; margin: 10px;">Some text</p>
<p style="color: red; font-size: 20px; margin: 10px;">Some other text</p>
<p style="color: red; font-size: 20px; margin: 10px;">Yet more text</p>
```

Consequence: when you need to change the colour in three places, you change it three times; if you want every paragraph on the site to be consistent, you have to search through every file. Styles scattered through the structure turn maintenance into a nightmare. Lesson 06 explains why an **external stylesheet** is the real answer.

## A minimal runnable page

Create a new file called `index.html` with the following content, then double-click it to open in a browser:

```html
<!DOCTYPE html>
<html lang="en">
  <head>
    <meta charset="UTF-8">
    <title>Alice's homepage</title>
    <style>
      h1 { color: #2c7a7b; }
    </style>
  </head>
  <body>
    <h1>Hi, I'm Alice</h1>
    <p>This is my first web page.</p>
  </body>
</html>
```

`<meta charset="UTF-8">` tells the browser to decode the file as UTF-8, so characters do not turn into gibberish. Just remember to include it for now; lesson 02 will explain each tag one by one.

## Summary

- The three-piece division of labour: **HTML is structure, CSS is presentation, JavaScript is behaviour**.
- The browser parses HTML into a **DOM tree**, and every later style and interaction operates on that tree.
- Tags express **semantics** (what something is), not appearance (what it looks like).
- Do not misuse tags to fake an appearance, and do not put presentation inside HTML structure.

## In-class exercise

```quiz
type: html
q: Write three empty structural tags: an h1, a p and a div, in any order, all placed directly inside the body.
starter: |
  <h1></h1>
checks:
- document.querySelectorAll('h1').length === 1
- document.querySelectorAll('p').length === 1
- document.querySelectorAll('div').length === 1
hint: Just write the tags side by side; there is no need to nest them.
explain: h1, p and div are all block-level structural tags, each forming its own independent node.
```

- HTML is in charge of appearance and CSS is in charge of structure
