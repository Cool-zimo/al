# Forms Basics: form, input, label, button, textarea and select

> This lesson answers the question: "How do I let a user enter information and submit it?" The focus is on how a label is associated - it decides whether every user can click and fill in the form easily.

## A complete small form

```html
<form action="/submit" method="post">
  <div>
    <label for="name">Name</label>
    <input type="text" id="name" name="name">
  </div>
  <div>
    <label for="city">City</label>
    <select id="city" name="city">
      <option value="beijing">Beijing</option>
      <option value="shanghai">Shanghai</option>
      <option value="guangzhou">Guangzhou</option>
    </select>
  </div>
  <div>
    <label for="msg">Message</label>
    <textarea id="msg" name="msg" rows="4"></textarea>
  </div>
  <button type="submit">Submit</button>
</form>
```

| Tag | Role |
|---|---|
| `<form>` | The form container; `action` is the submission URL, `method` is the submission method |
| `<label>` | The description for an input |
| `<input>` | A single-line input; the type decides what kind |
| `<textarea>` | A multi-line text input |
| `<select>` + `<option>` | A dropdown selection |
| `<button>` | A button |

## A label's for and accessibility

```html
<label for="name">Name</label>
<input type="text" id="name">
```

The label's `for` value must be **equal to** the input's `id` value, which creates the association. Once associated:

1. **Clicking the text focuses the input** - this is especially important for radio buttons and checkboxes, which are fiddly to click precisely. Clicking the text next to them selects the option, which is a much better experience.
2. **A screen reader reads out the label's content** as the input's description, so a visually impaired user knows what to fill in.

Crash site 1: a label's for is wrong.

```html
<label for="username">Name</label>
<input type="text" id="name">
```

Consequence: `for="username"` but `id="name"` - they do not match, so no association is created. Clicking "Name" does not focus the input, and the screen reader has nothing to announce. Alice wrote ten inputs and got three for values wrong; users reported that "clicking the text does nothing".

Crash site 2: no label, only a placeholder.

```html
<input type="text" placeholder="Please enter your name">
```

Consequence: a placeholder is a **sample hint**, not a label. Two problems: once the user starts typing, the hint disappears and there is no clue what this field is for; and placeholder text is faint, so a screen reader often does not treat it as a formal description. A label is the correct solution.

## Common input types

```html
<input type="text" name="name">        <!-- single-line text -->
<input type="email" name="email">      <!-- email; mobile keyboards show the matching layout -->
<input type="password" name="pwd">     <!-- password; content is hidden -->
<input type="number" name="age">       <!-- a number -->
<input type="checkbox" name="hobby">   <!-- a checkbox -->
<input type="radio" name="gender">     <!-- a radio button -->
<input type="date" name="birthday">    <!-- a date picker -->
```

## Grouping radio buttons with name

```html
<p>Gender:</p>
<input type="radio" name="gender" id="male" value="male">
<label for="male">Male</label>
<input type="radio" name="gender" id="female" value="female">
<label for="female">Female</label>
```

Radio buttons that share the same `name` form a group, and only one in the group can be selected. If the names differ, both can be selected at once and the logic is broken.

## textarea and select

```html
<textarea name="intro" rows="4" cols="40"></textarea>
```

`<textarea>` has separate opening and closing tags, and its content is written **between** them (rather than in a value attribute as with input).

```html
<select name="city">
  <option value="">Please select</option>
  <option value="beijing">Beijing</option>
  <option value="shanghai">Shanghai</option>
</select>
```

The `value` of an `<option>` is what is actually sent on submission, while the text **between** `<option>` and `</option>` is what the user sees.

## Summary

- form is the form container; input, textarea and select collect input, and button triggers submission.
- A label's `for` must match the input's `id` to create an association.
- That association enables click-to-focus and screen reader announcements - a basic accessibility requirement.
- A placeholder cannot replace a label; radio buttons with the same name form a group.
- A textarea's content is written between its tags, and select options use option.

## In-class exercise

```quiz
type: html
q: Write a label with for "email" and text "Email", followed by an input of type "email" with id "email" and name "email", forming an association.
starter: |
  <label for="email">Email</label>
checks:
- document.querySelector('label').getAttribute('for') === 'email'
- document.querySelector('input').getAttribute('type') === 'email'
- document.querySelector('input').getAttribute('id') === 'email'
- document.querySelector('input').getAttribute('name') === 'email'
- document.querySelector('label').textContent.trim() === 'Email'
hint: The label's for and the input's id must match, and the input also needs type and name attributes.
explain: The label is associated with the input through for and id, while the input's type and name set the input type and the key name used on submission.
```
