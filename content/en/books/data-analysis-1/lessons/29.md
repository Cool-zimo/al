# Performance: avoid the slow idioms

> No new API here — just one thing: **measured evidence of which idioms are slow, and by how much**.

## A way to measure

```python
import numpy as np
import time

def timeit(fn, *args):
    fn(*args)                       # warm up (the first call carries extra cost)
    t0 = time.perf_counter()
    r = fn(*args)
    return (time.perf_counter() - t0) * 1000    # milliseconds
```

**Warming up matters** — the first call often includes setup cost that would skew the result.

## Versus one: loop versus vectorisation

```python
n = 200_000
a = np.arange(n, dtype=float)

def by_loop(x):
    total = 0.0
    for v in x:
        total += v * v
    return total

def by_vector(x):
    return (x ** 2).sum()

print(f"loop: {timeit(by_loop, a):.1f} ms")
print(f"vectorised: {timeit(by_vector, a):.1f} ms")
```

A typical result for 200k values:

```
loop: 12.4 ms
vectorised: 0.4 ms
```

**Roughly 30×.** And the gap widens as the data grows.

**Why:** a Python loop repeats type checks and bounds checks on every iteration; vectorisation hands all 200k values to a C loop in one go.

## Versus two: np.append versus pre-allocation

**The trap beginners hit most:**

```python
n = 20_000

def by_append(n):
    arr = np.array([])
    for i in range(n):
        arr = np.append(arr, i)      # builds a new array every time!
    return arr

def by_prealloc(n):
    arr = np.empty(n)
    for i in range(n):
        arr[i] = i
    return arr

print(f"np.append: {timeit(by_append, n):.1f} ms")
print(f"pre-allocated: {timeit(by_prealloc, n):.1f} ms")
```

**`np.append` does not append in place** — it **allocates a bigger array and copies everything across**, every single time. Done n times that's n full copies: O(n²).

> 💡 **Never call np.append inside a loop.** Pre-allocate with `np.empty(n)`, or collect into a Python list and convert once with `np.array(list)`.

## Versus three: fancy versus boolean indexing

```python
n = 500_000
a = np.random.rand(n)
idx = np.arange(0, n, 2)              # even indices

t0 = time.perf_counter(); x = a[idx]; t1 = time.perf_counter()
mask = a > 0.5
t2 = time.perf_counter(); y = a[mask]; t3 = time.perf_counter()

print(f"fancy: {(t1-t0)*1000:.2f} ms")
print(f"boolean: {(t3-t2)*1000:.2f} ms")
```

Both **copy** (neither is a view). If you read the same selection repeatedly, pull it out once.

## Versus four: view versus copy

```python
big = np.random.rand(3000, 3000)      # about 72 MB

# a view: effectively instant
t0 = time.perf_counter(); v = big[:1500]; t1 = time.perf_counter()
# a copy: really moves 36 MB
t2 = time.perf_counter(); c = big[:1500].copy(); t3 = time.perf_counter()

print(f"slice (view): {(t1-t0)*1000:.3f} ms")
print(f"copy: {(t3-t2)*1000:.1f} ms")
```

**Slicing is instantaneous; copying really moves memory.** With large images or matrices, avoid copies you don't need.

## Versus five: the axis direction matters too

```python
m = np.random.rand(2000, 2000)

def sum_rows(x):  return x.sum(axis=0)    # collapse down the rows
def sum_cols(x):  return x.sum(axis=1)    # collapse across the columns

print(f"axis=0: {timeit(sum_rows, m):.1f} ms")
print(f"axis=1: {timeit(sum_cols, m):.1f} ms")
```

**`axis=0` is usually faster** because NumPy arrays are **row-major (C order) by default** — elements in the same column aren't contiguous in memory, so reading down a column means jumping around.

Irrelevant for small arrays; a 2–5× difference at millions of elements.

## The slow-idiom list

| ❌ Slow | ✅ Fast | Why |
|---|---|---|
| `for` loop per element | a vectorised expression | Python loop overhead |
| `np.append` in a loop | pre-allocate / collect in a list | append is O(n²) |
| an unnecessary `.copy()` | use the view | don't move memory |
| `np.concatenate` one at a time | a single `concatenate([...])` | fewer intermediate arrays |
| repeated `np.array(list)` | convert once | fewer conversions |
| complex expressions on tiny arrays | just compute it | call overhead dominates when data is small |

## When not to optimise

**Premature optimisation is the root of much wasted effort.** Skip it when:

- There are fewer than ~10k values (the difference is milliseconds nobody notices)
- The code runs once (you'd spend more time than you save)
- Clarity would suffer (readability wins)

**Principle: get it right first, then measure, then optimise what's actually slow.** Use `timeit` to find the real bottleneck rather than guessing.

## The measuring tool

```python
import timeit

# more rigorous: run many times and average
t = timeit.timeit(lambda: (a ** 2).sum(), number=100)
print(f"100 runs: {t*1000:.1f} ms, per run {t*1000/100:.3f} ms")
```

The `timeit` module repeats and averages for you — more reliable than hand-written `time.perf_counter()`.
