# Why lists aren't enough

> You already know Python lists. So why learn NumPy?
> This lesson teaches no code — it answers one question: **what exactly is wrong with lists**.

## A very ordinary task first

Add two lists "position by position":

```python
a = [1, 2, 3, 4, 5]
b = [10, 20, 30, 40, 50]

# you want [11, 22, 33, 44, 55]
print(a + b)
```

You don't get that:

```
[1, 2, 3, 4, 5, 10, 20, 30, 40, 50]
```

**For lists, `+` means concatenate, not add.** That's the first awkward thing: a list is a container, not a mathematical object.

To actually add, you write a loop:

```python
result = []
for i in range(len(a)):
    result.append(a[i] + b[i])
print(result)      # [11, 22, 33, 44, 55]
```

Five lines for one addition.

## The NumPy way

```python
import numpy as np

a = np.array([1, 2, 3, 4, 5])
b = np.array([10, 20, 30, 40, 50])
print(a + b)       # [11 22 33 44 55]
```

One line. `+` means addition again.

**That's NumPy's core claim:** treat a pile of numbers as one thing, not as items to walk through one by one.

## Three limits of lists

### Limit one: verbose

Seen above. Any maths on a list usually drags a `for` along with it.

### Limit two: slow

The gap is startling. Let's measure it — square a million numbers:

```python
import numpy as np
import time

data = list(range(1_000_000))
arr = np.array(data)

# list: loop
t0 = time.time()
result_list = [x ** 2 for x in data]
t1 = time.time()

# array: vectorised
result_arr = arr ** 2
t2 = time.time()

print(f"list: {(t1 - t0) * 1000:.1f} ms")
print(f"array: {(t2 - t1) * 1000:.1f} ms")
```

Typical output (your numbers will differ, the ratio won't):

```
list: 78.3 ms
array: 2.1 ms
```

**Tens of times faster.** The bigger the data, the wider the gap.

### Limit three: memory hungry

A list doesn't hold the numbers themselves — it holds **references to number objects**. Every Python int object also carries type information, a reference count, and so on.

An array holds **raw numbers**, one right after another.

```python
import numpy as np
import sys

data = list(range(1000))
arr = np.array(data)

print(sys.getsizeof(data[0]))   # 28  ← one int object alone
print(arr.itemsize)             # 8   ← one element in the array
```

For 1000 numbers, the list stores 1000 references plus 1000 objects; the array needs 1000 × 8 bytes of contiguous space.

## Why arrays are fast

Two reasons, both worth knowing:

**1. Contiguous memory.** Elements sit next to each other, so the CPU can pull in a big chunk at once (cache friendly). List elements are scattered, so every access is a jump.

**2. Batch work happens underneath.** `arr ** 2` is executed by a loop written in C inside NumPy — it never goes through the Python interpreter instruction by instruction. A Python `for` loop does a type check and a bounds check every single pass; that overhead is amplified a million times.

> 💡 Term: **vectorisation**. It means turning an operation on single elements into one operation on the whole array. This is the central NumPy mindset, and chapter 2 is entirely about it.

## So should lists be retired?

No. Lists still own their territory:

| Situation | Use | Why |
|---|---|---|
| Holding mixed types | **list** | arrays require one type |
| Frequent insert / delete | **list** | array size is fixed; resizing rebuilds |
| Large-scale numeric work | **array** | fast, compact, concise |
| Just a handful of values | **list** | array creation overhead isn't worth it |

The test is simple: **if you're going to do maths with the data, use an array; if you're only storing it, use a list.**

## NumPy's rule: every element must share a type

This is what makes arrays fast, and it's also their biggest constraint.

```python
import numpy as np

# what happens if we mix?
arr = np.array([1, 2.5, 3])
print(arr)        # [1.  2.5 3. ]
print(arr.dtype)  # float64  ← the integers were promoted
```

Python doesn't complain; it **unifies everything to one type** (here, float).

Strings mixed with numbers:

```python
arr = np.array([1, 2, "three"])
print(arr)        # ['1' '2' 'three']  ← everything became text
print(arr.dtype)  # <U21
```

The numbers silently became strings. When you later hunt a bug that says "why won't this compute", `dtype` is the first thing to look at.
