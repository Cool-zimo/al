# How to Choose an Algorithm: Reverse-Engineering from Data Ranges

> When you get a problem, don't rush to code. First check the data range, work backward to the maximum allowable time complexity, and then choose your algorithm. This is the most practical "problem-reading technique" for contests and interviews.

## First Check How Big n Is, Then Decide How to Write

**The first step when getting a problem isn't thinking about the algorithm—it's checking the data range.** Because the data range directly determines how fast your algorithm must run.

**The time complexity conversion formula:**

> Roughly 10⁸ basic operations per second in C++ (Python is slower, around 10⁶ ~ 10⁷).

**So the relationship between data range and algorithm choice:**

| n range | Usable complexity | Common algorithms |
|---|---|---|
| n ≤ 20 | O(n·2ⁿ), O(n!) | Brute force, backtracking, bitmask DP |
| n ≤ 10³ | O(n²), O(n² log n) | Double loops, Floyd, DP |
| n ≤ 10⁵ | O(n log n), O(n) | Sorting, binary search, monotonic stack, DFS |
| n ≤ 10⁶ | O(n log n) risky, O(n) | Linear scan, counting sort |
| n ≤ 10⁷ | Only O(n) with small constant | Prefix sums, difference arrays, bucket counting |

**For example:**

- Problem says n ≤ 20 → you can confidently write O(2ⁿ) bitmask DP or backtracking
- Problem says n ≤ 10⁵ → O(n²) means 10¹⁰ operations, guaranteed TLE, must think of O(n log n) or O(n)
- Problem says n ≤ 10⁷ → even O(n log n) won't work (log n ≈ 23, 23×10⁷ ≈ 2.3×10⁸, too slow for Python), only pure O(n)

**This is the "reverse-engineer from data range" method: check n first, then work backward to the algorithm.**

## n ≤ 20: The Comfort Zone for Brute Force / Backtracking

**When n is small (≤ 20), exponential algorithms are feasible.** Because 2²⁰ ≈ 1 million, and 20! while large can work with pruning.

```python
# n=20, enumerate all subsets
def subset_sum(nums, target):
    n = len(nums)
    ans = 0
    for mask in range(1 << n):          # 2^n states
        s = 0
        for i in range(n):
            if mask >> i & 1:
                s += nums[i]
        if s == target:
            ans += 1
    return ans

print(subset_sum([1, 2, 3], 3))   # 2 ({3} and {1,2})
```

**2²⁰ ≈ 10⁶, easily runs within 1 second on modern computers.** So when you see n ≤ 20, don't fear exponential algorithms—just write them correctly.

## n ≤ 10³: O(n²) Is the Workhorse

**When n ≤ 10³, O(n²) is about 10⁶ operations—very safe.**

```python
# n=1000, longest increasing subsequence is a classic O(n²)
def lis(nums):
    n = len(nums)
    dp = [1] * n
    for i in range(n):
        for j in range(i):
            if nums[j] < nums[i]:
                dp[i] = max(dp[i], dp[j] + 1)
    return max(dp)

print(lis([10, 9, 2, 5, 3, 7, 101, 18]))   # 4
```

**O(n²) at n=1000 is 10⁶, safe; but at n=10⁵ it's 10¹⁰, guaranteed TLE.**

## n ≤ 10⁵: Must Use O(n log n) or O(n)

**n=10⁵ is the watershed. O(n²) will definitely die; you must level up.**

```python
# Optimize LIS to O(n log n) using binary search
import bisect

def lis_fast(nums):
    tail = []
    for x in nums:
        i = bisect.bisect_left(tail, x)
        if i == len(tail):
            tail.append(x)
        else:
            tail[i] = x
    return len(tail)

print(lis_fast([10, 9, 2, 5, 3, 7, 101, 18]))   # 4
```

**From O(n²) to O(n log n), at n=10⁵ we go from 10¹⁰ down to 1.7×10⁶—a 5000x difference.** This is why optimization is necessary.

## n ≤ 10⁷: Only O(n), and Small Constant

**At n=10⁷, even O(n log n) is risky (about 2.3×10⁸ operations, too slow for Python). You can only use pure O(n).**

```python
# Prefix sums: O(n) preprocessing + O(1) queries
def range_sum(nums, queries):
    n = len(nums)
    pref = [0] * (n + 1)
    for i in range(n):
        pref[i + 1] = pref[i] + nums[i]
    
    res = []
    for l, r in queries:               # Each query is O(1)
        res.append(pref[r + 1] - pref[l])
    return res

print(range_sum([1, 2, 3, 4, 5], [(0, 2), (1, 4)]))   # [6, 14]
```

**Prefix sums reduce each query from O(n) to O(1), bringing the total from O(nq) down to O(n+q).** This is exactly the "optimization forced by data range."

## Quick Reference: Common Algorithm Complexities

**Memorize this table, and you'll have a good sense of things when solving problems:**

| Algorithm | Complexity | Usable at 10⁵? |
|---|---|---|
| Bubble/Insertion sort | O(n²) | No |
| Quick/Merge/Heap sort | O(n log n) | Yes |
| Binary search | O(log n) | Yes |
| Hash table lookup | O(1) amortized | Yes |
| Prefix sums | O(n) preprocessing | Yes |
| Monotonic stack/queue | O(n) | Yes |
| DFS/BFS | O(n+m) | Yes |
| Naive DP (O(n²)) | O(n²) | No |
| Bitmask DP | O(n·2ⁿ) | Only if n≤20 |
| Floyd | O(n³) | Only if n≤300 |

**Decision process:**

```
1. Check the range of n
2. Calculate the maximum allowable complexity
3. Choose an algorithm within that limit
4. Check for constant-factor issues (Python is slower than C++)
```

## WRONG: n=10⁵ with O(n²) Double Loop, Guaranteed TLE

**This is the most common failure—writing code without checking the data range first.**

```python
# WRONG: n=10^5 still using a double loop
def count_pairs(nums, target):
    n = len(nums)
    ans = 0
    for i in range(n):            # O(n^2)
        for j in range(i + 1, n):
            if nums[i] + nums[j] < target:
                ans += 1
    return ans

# n = 100000 → about 5×10^9 iterations
# Actual result: TLE (Time Limit Exceeded)
```

**Why does it time out?** With 10⁵ elements, the double loop does about 5 billion comparisons. Even at 1ns per comparison, that's 5 seconds; Python takes at least tens of ns per loop iteration, so it could take minutes.

**Fix: sort first, then use two pointers or binary search to get O(n log n).**

```python
def count_pairs_fast(nums, target):
    nums.sort()
    ans = 0
    for i in range(len(nums)):
        # Binary search for the first nums[j] >= target - nums[i]
        left, right = i + 1, len(nums)
        while left < right:
            mid = (left + right) // 2
            if nums[mid] < target - nums[i]:
                left = mid + 1
            else:
                right = mid
        ans += left - i - 1
    return ans

print(count_pairs_fast([1, 2, 3, 4, 5], 5))   # 4
```

## WRONG: n=10⁷ Using Sorting, TLE

**At n=10⁷, even O(n log n) won't run in time.**

```python
# WRONG: n=10^7 still using sorted()
def find_most_frequent(nums):
    nums = sorted(nums)          # O(n log n): 10^7 * 23 ≈ 2.3×10^8 operations
    # Sorting 10^7 elements in Python could take 10+ seconds
    return nums

# Actual result: TLE
```

**Fix: use counting sort (if the value range is small) or hash counting, O(n).**

```python
from collections import Counter

def find_most_frequent_fast(nums):
    cnt = Counter(nums)          # O(n) single pass
    return cnt.most_common(1)[0][0]

print(find_most_frequent_fast([1, 2, 2, 3, 2, 1, 2]))   # 2
```

## WRONG: Misjudging Complexity, Thinking O(n log n) Will TLE at n=10⁵

**Some people panic when they see n=10⁵ and abandon an O(n log n) solution that would work perfectly fine.**

```python
# Some think sorting at n=10^5 will TLE, but it's totally fine
def sort_and_process(nums):
    nums.sort()          # O(n log n) = 10^5 * 17 ≈ 1.7×10^6 operations
    # 1.7×10^6 operations easily completes within 1 second
    return nums

print(sort_and_process([3, 1, 2]))   # [1, 2, 3]
```

**n log n at n=10⁵ is only about 1.7 million operations—completely safe.** The real dangers are O(n²) (10 billion) and O(n log n) at n=10⁷ (230 million, risky in Python).

**The judgment must be precise: it's not "n is big so no log," but rather "check the absolute value of n log n."**

## Summary

- **Reverse-engineer from data range**: check n first, work backward to max allowable complexity, then pick the algorithm
- **n ≤ 20**: you can write O(2ⁿ), O(n!) backtracking/bitmask DP
- **n ≤ 10³**: O(n²) is safe and is the workhorse complexity
- **n ≤ 10⁵**: must use O(n log n) or O(n); O(n²) is fatal
- **n ≤ 10⁷**: only O(n), small constant, no sorting
- **1 second ≈ 10⁸ operations** (Python: about 10⁶ ~ 10⁷)
- Common pitfalls: coding without checking data range, assuming O(n²) is safe, misjudging O(n log n) as too slow
