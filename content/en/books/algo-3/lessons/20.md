# Heap Sort and Non-Comparison Sorting: Breaking the O(n log n) Barrier

> The theoretical lower bound for comparison sorts is Ω(n log n) — you cannot do better than that. But counting sort, bucket sort, and radix sort do not need to compare element values. They exploit numerical range information in the data to achieve O(n). This lesson clarifies the distinction between heap sort and "non-comparison sorting".

## Heap Sort: In-Place O(n log n) with No Extra Space

**Heap sort has two steps: 1) build a heap (turn the array into a max-heap); 2) repeatedly extract the maximum from the heap top and place it at the end.**

```python
def heap_sort(a):
    n = len(a)
    # Step 1: Build heap (sink from the last non-leaf node)
    for i in range(n // 2 - 1, -1, -1):
        heapify(a, n, i)
    # Step 2: Repeatedly swap the heap top (maximum) to the end
    for i in range(n - 1, 0, -1):
        a[0], a[i] = a[i], a[0]    # Swap heap top with the end
        heapify(a, i, 0)            # Re-heapify [0:i]
    return a

def heapify(a, n, i):
    largest = i
    left = 2 * i + 1
    right = 2 * i + 2
    if left < n and a[left] > a[largest]:
        largest = left
    if right < n and a[right] > a[largest]:
        largest = right
    if largest != i:
        a[i], a[largest] = a[largest], a[i]
        heapify(a, n, largest)      # Recursively sink down
```

**Building the heap takes O(n), and n extractions each take O(log n) = O(n log n).** Space is O(1) (in-place).

**Why is building a heap O(n)?** At first glance, `heapify` is O(log n) and there are n/2 nodes to heapify… but the actual total is O(n). Because at level k there are n/2^(k+1) nodes, each sinking at most k levels, total work = Σ k · n/2^(k+1) = O(n).

## Heap Sort vs Quick Sort vs Merge Sort

| | Time | Space | Stable | In-place |
|---|---|---|---|---|
| Quick | O(n log n) expected / O(n²) worst | O(log n) stack | No | Yes |
| Merge | O(n log n) | O(n) | **Yes** | No |
| Heap | O(n log n) | O(1) | No | **Yes** |

**Heap sort is the only sort that achieves both O(n log n) and O(1) extra space in the worst case.** But its cache performance is poor — parent and child nodes are far apart in the array, unlike quick sort's locality.

## # WRONG: Getting the heapify Index Formula Wrong

**The most common heap bug: miscalculating the left and right child indices.**

```python
# WRONG: Right child index is wrong
def heapify_wrong(a, n, i):
    largest = i
    left = 2 * i        # WRONG! Should be 2*i + 1
    right = 2 * i + 1   # WRONG! Should be 2*i + 2
    if left < n and a[left] > a[largest]:
        largest = left
    if right < n and a[right] > a[largest]:
        largest = right
    if largest != i:
        a[i], a[largest] = a[largest], a[i]
        heapify_wrong(a, n, largest)
```

**For a 0-based heap, node i's left child is `2i+1`, right child is `2i+2`, and parent is `(i-1)//2`.**

**For a 1-based heap (heap root at position 1), the left child is `2i`, right child is `2i+1`, and parent is `i//2`.** Python's `heapq` module uses 0-based indexing, so you must use `2i+1` and `2i+2`.

## Non-Comparison Sorting: Why It Can Break Through O(n log n)

**The Ω(n log n) lower bound for comparison sorts comes from the decision tree — n! permutations need at least log₂(n!) ≈ n log n comparisons.**

**But counting sort, bucket sort, and radix sort do not compare element values. They exploit the fact that "element values occupy a finite range", directly "placing" each element into its corresponding position.**

```python
# Counting sort: knowing the element range is 0~k
def counting_sort(a, k):
    count = [0] * (k + 1)
    for x in a:
        count[x] += 1          # Count occurrences of each value
    result = []
    for val in range(k + 1):
        result.extend([val] * count[val])  # Output values in increasing order
    return result

print(counting_sort([4, 2, 2, 8, 3, 3, 1], 8))
# [1, 2, 2, 3, 3, 4, 8]
```

**Time complexity is O(n + k), where k is the range size.** If k = O(n), that is O(n)!

**Why is this not "cheating"?** Because counting sort assumes "the data range is known and not too large". If you are only told "here is a set of numbers to sort" with no range information, comparison sort is the most general tool. But in reality, huge amounts of data (ages, scores, pixel values) have natural range limits.

## The Counting Sort Index Trap

**The easiest mistake in counting sort: misjudging the range k and causing an index out of bounds.**

```python
# WRONG: Assuming all elements are >= 0, but the input contains negatives
def counting_sort_wrong(a):
    k = max(a)
    count = [0] * (k + 1)
    for x in a:
        count[x] += 1     # IndexError: x is negative!
    return []

counting_sort_wrong([5, -2, 3, -1])  # Crashes!
```

```python
# WRONG: k is too small, missing the maximum value
def counting_sort_wrong2(a):
    count = [0] * 10      # Assuming all elements < 10
    for x in a:
        count[x] += 1     # IndexError: x=15 is out of bounds!
    return []

counting_sort_wrong2([3, 7, 15, 2])  # Crashes!
```

**Fix: handle the offset correctly.**

```python
def counting_sort_safe(a):
    mn, mx = min(a), max(a)
    count = [0] * (mx - mn + 1)
    for x in a:
        count[x - mn] += 1      # Map to a valid index using the offset
    result = []
    for i, c in enumerate(count):
        result.extend([i + mn] * c)
    return result
```

## Bucket Sort: The "Blocked" Upgrade of Counting Sort

**The idea behind bucket sort: divide the range into several buckets, sort within each bucket using insertion sort, then concatenate the buckets in order.**

```python
def bucket_sort(a, bucket_count=10):
    if not a:
        return []
    mn, mx = min(a), max(a)
    bucket_size = (mx - mn) / bucket_count + 1e-9
    buckets = [[] for _ in range(bucket_count)]
    
    for x in a:
        idx = int((x - mn) / bucket_size)
        idx = min(idx, bucket_count - 1)   # Prevent boundary overflow
        buckets[idx].append(x)
    
    result = []
    for bucket in buckets:
        insertion_sort(bucket)       # Sort within each bucket using insertion sort
        result.extend(bucket)
    return result
```

**Bucket sort's time complexity depends on the data distribution.** If the data is uniformly distributed, each bucket has an average of n/bucket_count elements. Sorting within a bucket costs O((n/k)²), for a total of O(n + k·(n/k)²) = O(n + n²/k). When k = Θ(n), it reaches O(n).

**Comparison: counting sort is the special case where bucket size is 1. Bucket sort is suitable when bucket size > 1.**

## # WRONG: Believing sorted() Uses Quick Sort

**A frequent interview mistake: claiming that Python's `sorted()` uses quick sort.**

```python
# Wrong: "Python's sorted() uses quick sort"
# Actually: Python uses Timsort

a = [3, 1, 4, 1, 5, 9, 2, 6]
sorted_a = sorted(a)   # Timsort: hybrid insertion sort + merge sort
# Traits: exploits existing sorted runs, O(n) best case, O(n log n) worst case, stable
```

**Why is Timsort better than pure quick sort?** Real-world data often contains many "partially sorted" fragments. Timsort identifies these natural runs, expands short ones with insertion sort, and merges runs with merging. It stays at O(n log n) in the worst case and is stable.

**Sorting algorithm quick-reference by language:**
- Python `sorted()` / `list.sort()` → Timsort
- C++ `std::sort` → Introsort (hybrid of quick, heap, and insertion)
- Java `Arrays.sort(int[])` → dual-pivot quick sort variant
- Java `Arrays.sort(Object[])` → Timsort

## Summary

- Heap sort: O(n log n) worst case, O(1) space, unstable, in-place, cache-unfriendly
- 0-based heap: left child `2i+1`, right child `2i+2`, parent `(i-1)//2`
- The Ω(n log n) lower bound for comparison sorts comes from the decision tree information argument
- Non-comparison sorts break the lower bound using data range information:
  - Counting sort O(n+k), ideal for small integers where k=O(n)
  - Bucket sort O(n + n²/k), ideal for uniformly distributed data
- Counting sort must handle offsets (negative numbers); bucket sort must watch for boundary overflow
- Python `sorted()` uses Timsort, not quick sort
