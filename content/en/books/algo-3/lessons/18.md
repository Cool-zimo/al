# Merge Sort: Divide and Conquer, with Stability

> Merge sort is the first truly O(n log n) sort, and it is **stable**. The cost is O(n) of extra space. This lesson goes from the divide-and-conquer idea to the merge operation, breaking it all down.

## Divide and Conquer: Split, Then Merge

**Merge sort has just two core steps: Divide and Conquer.**

1. **Divide**: split the array in half and recursively sort the left and right halves
2. **Conquer (merge)**: merge the two sorted subarrays into one sorted array

```python
def merge_sort(a):
    if len(a) <= 1:          # Base case: 0 or 1 element is already sorted
        return a
    mid = len(a) // 2
    left = merge_sort(a[:mid])    # Divide: recursively sort left half
    right = merge_sort(a[mid:])  # Divide: recursively sort right half
    return merge(left, right)    # Conquer: merge the two sorted arrays
```

**The recursion tree has depth log n, and each level processes a total of n elements.** So the time complexity is O(n log n).

**Compare this with bubble/selection/insertion at O(n²): their inner loops "cannot see the whole picture" because they only handle local portions.** Merge sort covers all elements at every level and does only O(n) work per level.

## The Merge Operation: Two Pointers, One Result Array

**Merging is the soul of merge sort. It exploits the fact that both subarrays are already sorted, using two pointers to scan linearly and merge.**

```python
def merge(left, right):
    result = []
    i = j = 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:     # Use <= for stability
            result.append(left[i])
            i += 1
        else:
            result.append(right[j])
            j += 1
    result.extend(left[i:])    # Remaining left half
    result.extend(right[j:])   # Remaining right half
    return result

print(merge([1, 4, 7], [2, 3, 6]))
# [1, 2, 3, 4, 6, 7]
```

**Why `<=` instead of `<`?** When `left[i] == right[j]`, taking the left element first guarantees that equal elements preserve their relative order → **stability**.

**Merging is O(n): each element is compared and moved exactly once.**

## Recursion Unrolled: What Merge Sort Actually Does

**Take `[38, 27, 43, 3, 9, 82, 10]` as an example:**

```
[38, 27, 43, 3, 9, 82, 10]
        /              \
[38, 27, 43, 3]    [9, 82, 10]
   /      \          /      \
[38,27]  [43,3]   [9,82]   [10]
 /  \    /  \     /  \     |
[38][27][43][3] [9][82]   [10]
 \  /    \  /     \  /     |
[27,38] [3,43]   [9,82]   [10]
    \      /          \     /
 [3,27,38,43]      [9,10,82]
        \              /
     [3, 9, 10, 27, 38, 43, 82]
```

**Each level of merging costs O(n), the tree depth is log n, total O(n log n).**

**No matter what order the input is in, merge sort is always O(n log n).** There is no "best case" or "worst case" difference — that is what makes it more "reliable" than quick sort.

## # WRONG: Forgetting to Append the Remaining Elements After Merging

**This is the most common bug: once one pointer finishes, forgetting to append the rest of the other array to the result.**

```python
# WRONG: Forgot to extend the remaining elements
def merge_wrong(left, right):
    result = []
    i = j = 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:
            result.append(left[i])
            i += 1
        else:
            result.append(right[j])
            j += 1
    # Forgot: result.extend(left[i:]) and result.extend(right[j:])
    return result

print(merge_wrong([1, 2, 3], [4, 5, 6]))
# [1, 2, 3]  <- Only got the left half, the right half is lost!
```

**The output is `[1, 2, 3]` instead of `[1, 2, 3, 4, 5, 6]`.** Because all left-half elements are smaller than the right half, i finishes first while j is still at 0, and the right half `[4, 5, 6]` is never added.

**Fix: after the while loop, you must `result.extend(left[i:])` and `result.extend(right[j:])`.**

## # WRONG: Using `<` Instead of `<=` in Merge Breaks Stability

**Using `<` causes equal elements to come from the right half, breaking stability.**

```python
# WRONG: Using < breaks stability
def merge_unstable(left, right):
    result = []
    i = j = 0
    while i < len(left) and j < len(right):
        if left[i] < right[j]:    # < instead of <=
            result.append(left[i])
            i += 1
        else:                     # When equal, this branch runs, taking from the right
            result.append(right[j])
            j += 1
    result.extend(left[i:])
    result.extend(right[j:])
    return result

# Testing stability
# Suppose two equal-valued objects, the left one comes first
# With <, equal values take from the right, pushing the left one "back"
```

**The difference between `<` and `<=`: when `left[i] == right[j]`, `<` puts the right element into the result first, so the element that was originally in front ends up behind → unstable.**

**Stability matters in practice:** for example, sort by score first, then by name. If the second sort is not stable, the order from the first sort is destroyed.

## The Space Cost: O(n) Extra Array

**Merge sort needs an O(n) auxiliary array to hold the merge results.** This is its core difference from heap sort, which uses O(1) extra space.

```python
# In-place merge (saves space but is very complex) vs. auxiliary array (simple and direct)
# Python slicing implicitly creates new lists, costing even more space
# Optimized version: allocate the auxiliary array once and reuse it during recursion

def merge_sort_inplace(a, temp=None, left=0, right=None):
    if right is None:
        right = len(a) - 1
    if temp is None:
        temp = [0] * len(a)    # Allocate only once
    if left >= right:
        return
    mid = (left + right) // 2
    merge_sort_inplace(a, temp, left, mid)
    merge_sort_inplace(a, temp, mid + 1, right)
    # Use temp as a staging area during merge
```

**Summary of space costs:**
- Python slicing version: `O(n log n)` temporary space (a new list at every recursion level)
- Optimized version (reusing the temp array): `O(n)` extra space

**If memory is extremely constrained (embedded systems, large-scale external sort), merge sort's O(n) space may be unacceptable. Heap sort is a better choice then.**

## Summary

- Merge sort: divide-and-conquer — recursively split, then merge; O(n log n) regardless of input
- **Merging is the soul**: two-pointer linear merge of two sorted arrays, O(n)
- Use `<=` for stability; `<` breaks stability
- **Always handle the remaining elements**: after the loop, extend the left/right remainder
- Space cost: O(n) (reusing an array) or O(n log n) (Python slicing version)
- Merge sort is stable and reliable at O(n log n), great for external sort and linked lists
