# Project Design: Breaking Down a To-Do List

> Starting from this lesson, we build a real web project: a To-Do List. It is the classic beginner exercise in frontend, and it ties together everything from the first 25 lessons. The first step is not writing code — it is getting the requirements straight.

## What we are building

A usable to-do list needs at least these features:

1. Display a task list (apples, bananas, write some code…).
2. Add a new task.
3. Delete a task.
4. Mark a task as done or not done.
5. Remember the data after a refresh (with `localStorage`).

The slow track focuses on the first three; the last two are left as extras.

## From requirements to data: figure out what the data looks like first

**The correct order for building a web page is: design the data first, then the interface, then the interactions.** Do not start by drawing the interface.

A single task is an object. It needs at least two fields:

```js
let todo = {
    id: 1,
    text: "Buy groceries"
};
```

To support "done or not done", add a `done` field:

```js
let todo = {
    id: 1,
    text: "Buy groceries",
    done: false
};
```

The whole list is an array of objects:

```js
let todos = [
    { id: 1, text: "Buy groceries", done: false },
    { id: 2, text: "Write some code", done: true },
    { id: 3, text: "Watch a film", done: false }
];
```

**This is the "single source of truth": the entire application state lives in this one array.** The interface is just a "projection" of this array.

## From requirements to functions: each feature is a function

| Requirement | The function | What it does |
|---|---|---|
| Display the list | `render()` | Turn the `todos` array into `<li>` elements on the page |
| Add a task | `addTodo(text)` | Push one item into `todos`, then re-render |
| Delete a task | `deleteTodo(id)` | Remove the matching item from `todos`, then re-render |

**Notice the pattern: every operation that changes the data must re-render afterwards.** This is the most important idea in the whole project, and we will keep coming back to it.

## Write the function skeletons first

```js
let todos = [];           // single source of truth

function render() {
    // turn todos into <li> elements (implemented next lesson)
}

function addTodo(text) {
    // push one item into todos
}

function deleteTodo(id) {
    // remove the item with this id from todos
}
```

Fix these three names and their parameters first; there is no need to fill in the bodies yet. **Writing down "which functions exist and what each one does" before coding is ten times more efficient than diving in blindly.**

## Crash site 1: designing the interface before the data

Many beginners start writing HTML straight away. Halfway through they realise they have no idea how to store the data, or how to find the right item when deleting.

**The correct order is: data → functions → interface.** Data is the foundation; the interface is only the display layer.

## Crash site 2: starting before the requirements are broken down

"Build a to-do list" is far too vague. You need to break it down this far: how is a task added (Enter key or a button)? Where is the delete button? Do we support editing? **Vague requirements guarantee rework.**

## Requirements = acceptance criteria

Before writing code, write down these three lines as your "acceptance criteria". Tick each one off as you finish it:

- [ ] Type text and click the button → the list gains one item.
- [ ] Click delete → that item disappears.
- [ ] Refresh the page → the list is still there.

**Code with acceptance criteria never goes off the rails.** The next three lessons implement these three lines one by one.

## Summary

- The order for a project: design the data → design the functions → build the interface.
- Single source of truth: the whole application state lives in one array.
- Each requirement maps to a function; after changing the data, re-render.
- List the acceptance criteria before writing code, and tick them off as you go.
