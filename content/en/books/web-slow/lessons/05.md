# Output and Debugging: Making Your Program Tell You What It Did

> This lesson answers the question: "How do I know what my code is doing wrong?" Learning to read error messages and print things out means you can solve most problems by yourself.

## Three ways to make your program speak

Once your program is running, how do you find out what is going on inside it? There are three common ways to talk to it:

| Method | How you write it | Where you see it | Best for |
|---|---|---|---|
| Console print | `console.log(...)` | The browser Console panel | Everyday debugging, anything goes |
| Pop-up box | `alert(...)` | A dialog box | A quick check, testing |
| Show on the page | DOM manipulation | The page itself | The real thing the user sees |

## `console.log`: the workhorse

You have been using it for the last four lessons. It prints anything you give it:

```js
console.log("a message");
console.log(123);
console.log(true);

let name = "Alice";
console.log(name);

let user = { name: "Bob", age: 20 };
console.log(user);
```

That last line prints the whole object structure, which is incredibly useful when you are staring at complicated data.

**Debugging trick:** when something is not behaving, drop a few `console.log` lines at key points and check whether the values are what you expect:

```js
let price = "50";
let count = 3;
console.log("price is:", price);  // what is actually in price?
console.log("count is:", count);
let total = price * count;  // this might be the problem
console.log("total =", total);
```

## `alert`: a box that pops up

```js
alert("Operation successful!");
```

This makes the browser show a dialog box, and the user has to click "OK" to dismiss it. It **blocks the page** while it is open, so it is a bad idea inside a loop and generally overused in real products.

But when you are just starting out, it has one big advantage: **you can see the result without even opening the console.** Save a tiny page, double-click to open it, add one `alert`, and you have proved your code ran.

## Reading the first line of an error

When your code is broken, the browser prints a red error in the console. Learning to read that message gets you halfway to the fix.

Here is an example:

```js
let name = "Alice";
console.log(nam);  // I missed the final e
```

The error:

```
Uncaught ReferenceError: nam is not defined
    at index.html:5
```

There are really only three things you need to see:

1. **`ReferenceError`** → the type: a reference error (the variable cannot be found)
2. **`nam is not defined`** → the reason: `nam` has not been defined
3. **`at index.html:5`** → the location: line 5 of index.html

**That first line is your best clue.** It tells you what went wrong and roughly which line to look at.

## A quick reference for common errors

| Error message | What it means | Common cause |
|---|---|---|
| `xxx is not defined` | You used a variable before declaring it | Typo, or forgot `let`/`const` |
| `Unexpected token` | Your syntax is broken | Missing semicolon, unmatched brackets |
| `Cannot read properties of null` | You tried to operate on something that is not there | The element you looked up does not exist |
| `xxx is not a function` | You tried to call something that is not callable | Name clash, or a typo |

## Crash site 1: a typo that triggers `is not defined`

```js
let userName = "Alice";
console.log(usreName);  // typo!
```

**Consequence:** `ReferenceError: usreName is not defined`. Find the line the error points at and check the spelling. **This kind of small mistake makes up a huge share of beginner bugs** -- train yourself to look at variable names carefully.

## Crash site 2: putting `alert` inside a loop

```js
for (let i = 0; i < 100; i++) {
    alert(i);  // 100 pop-ups!
}
```

**Consequence:** the page freezes and you have to click "OK" a hundred times. `alert` **blocks** the code from continuing. When debugging loops, use `console.log` instead.

## Summary

- `console.log()` prints to the console and is your everyday debugging tool.
- `alert()` pops up a box, blocks the page, handy while learning but do not overdo it.
- The first line of an error tells you what broke and which line to check.
- When code misbehaves, sprinkle `console.log` at key points and trace it step by step.
