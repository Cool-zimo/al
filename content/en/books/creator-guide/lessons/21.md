# 21 Local questions: things a browser cannot run

> GUIs, files, subprocesses — the reader has to run these.

## When to use it

Some things simply do not exist in a browser sandbox:

- graphical windows (tkinter, Qt)
- the real file system
- subprocesses
- anything needing network or hardware

These cannot be auto-graded. Use `type: local`.

## The syntax

```
type: local
q: Build a tkinter window with a button
starter: |
  import tkinter as tk

  root = tk.Tk()
  root.title("My window")
  root.mainloop()
checklist: |
  - The window opens
  - There is a button
  - Clicking the button does something
hint: Use "Open in VS Code" to run it
```

## The checklist is the whole question

With no auto-grading, **the checklist is all there is**. Readers judge themselves against it.

How to write one:

```
- The window opens              good, verifiable
- The code is elegant           bad, unjudgeable
- Clicking prints a line        good, verifiable
- You understand layout         bad, a feeling, not a result
```

Every item must be something the reader can answer **yes or no** to.

## Give a starter that runs

Same principle as function questions: the starter should at least open without error, so the reader can build on it.

## What it looks like

A local question shows an "Open in VS Code" button that writes the starter to a local file and opens the editor. The reader runs it there, comes back and ticks the boxes.

## Recap

- Use `local` when the browser cannot run it
- `checklist` items must be verifiable
- starter must run

```quiz
- When the question is hard
- When you want the reader to think
- When the code is long

explain: GUIs, real file operations and subprocesses cannot run in a browser, so the reader runs them locally.
```
