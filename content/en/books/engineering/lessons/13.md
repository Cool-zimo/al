# Branching Strategy: Why You Must Not Edit main Directly

> You edit main directly, push it, CI fails, and a colleague pulls half-written code that will not run. Worse, halfway through you realise the approach was wrong and want to undo — but main's history is already polluted. A branch exists for one reason: **keep work in progress separate from the version that works.**

## Why main Must Not Be Edited Directly

`main` (or `master`) should always be in a usable, deployable state. That is both a team convention and an assumption made by your automation.

```bash
$ git checkout main
$ vim login.py
$ git commit -am "tweak login"
$ git push
```

**Crash Site: an urgent bug arrives while you are halfway through editing main**

```bash
$ git checkout main
$ vim login.py
# half-finished; the login module is in a half-working state
$ git status
modified:   login.py
# suddenly production reports a bug that needs fixing now
$ git checkout -b hotfix/urgent
error: Your local changes to the following files would be lost:
        login.py
```

**What you see:** the checkout is blocked because the working tree has uncommitted changes. You are forced to either commit a half-finished state to main or stash it. Either way, main is polluted.

**The fix: branch off main, then edit**

```bash
$ git checkout main
$ git pull
$ git checkout -b feature/phone-login
# edit freely, even half-done
$ git commit -am "WIP: login refactor in progress"
```

Your half-finished work lives on `feature/phone-login`; main stays clean. When the urgent bug arrives, just switch back to main and open a hotfix branch.

## The Feature-Branch Workflow

The standard flow:

```bash
# 1. Make sure main is current
$ git checkout main
$ git pull

# 2. Open a branch
$ git checkout -b feature/order-export

# 3. Develop and commit on the branch
$ git add src/export.py
$ git commit -m "feat(export): support CSV export"
$ git add tests/test_export.py
$ git commit -m "test(export): cover CSV export edge cases"

# 4. Push to the remote (use -u the first time)
$ git push -u origin feature/order-export

# 5. Open a Pull Request / Merge Request on GitHub / GitLab

# 6. After review, merge, then delete the branch
$ git checkout main
$ git pull
$ git branch -d feature/order-export
```

Branch names conventionally carry a **prefix and a purpose**: `feature/...`, `fix/...`, `hotfix/...`, `refactor/...` — matching the commit types.

## Merge vs Rebase

Two ways to integrate a branch into main.

**Merge** — preserves the branch history and creates a merge commit.

```bash
$ git checkout main
$ git merge feature/order-export
```

The result:

```text
*   a1b2c3d Merge branch 'feature/order-export'  <- merge commit
|\
| * d4e5f6g feat: add CSV export
| * e7f8g9h feat: add the export button
* | f1a2b3c fix: paginate results
|/
* g4h5i6j feat: pagination
```

The history **faithfully records the development process**, but enough forks and it starts to look like spaghetti.

**Rebase** — lifts your branch's commits onto the tip of main, producing a straight line.

```bash
$ git checkout feature/order-export
$ git rebase main
```

The result:

```text
* e7f8g9h feat: add the export button
* d4e5f6g feat: add CSV export
* f1a2b3c fix: paginate results
* g4h5i6j feat: pagination
```

History is **one straight line**, no merge node, and it reads more cleanly.

**Which to use when:**

| Situation | Recommended |
|---|---|
| A local branch that has never been pushed | rebase (clean up history) |
| A branch already pushed, with others working on it | merge (rebase rewrites history and conflicts for collaborators) |
| You want the full branching process preserved | merge |
| You want a linear main line | rebase |

**Crash Site: rebasing a branch that was already pushed**

```bash
$ git push origin feature/x
# a colleague pulls this branch and starts work
$ git rebase main
$ git push
# rejected: histories have diverged
$ git push --force
# the colleague pulls again; history is a mess
```

**Consequence:** you rewrote a public branch's history; your colleague's local branch is based on the old history, and pulling produces a storm of conflicts — sometimes requiring `git reflog` to recover.

**Rule: for a branch others have already pulled, merge only — never rebase. Rebase only your own local, unpushed commits.**

## Summary

- main must always remain usable and deployable.
- All changes happen on feature/fix/hotfix branches.
- The workflow: branch → develop → push → PR → merge → delete.
- Rebase unpushed commits to tidy them; merge pushed branches.
- Never force-push plus rebase on a public branch.

## In-Class Exercise

```quiz
type: choice
q: You have three commits on feature/login and have not pushed the branch. You want to combine them into one clean commit before pushing. What is the correct move?
options:
- git merge main, keeping all three commits
- git rebase -i HEAD~3 to combine the three commits into one
- push as-is; the commit count does not matter
- delete the branch and start over
answer: 1
explain: An interactive rebase (git rebase -i HEAD~3) lets you squash several commits into one. Because nothing has been pushed, rewriting history is safe. Merge does not reduce the commit count, and pushing as-is sends all three upstream.
```

```quiz

exam: true
q: Regarding merge and rebase, which is correct?
options:
- merge and rebase do exactly the same thing; only the command differs
- rebase rewrites commit history, so it must be used only on local unpushed commits; use merge for branches already pushed
- rebase is cleaner for pushed branches and should be preferred
- merge discards commit history and is not recommended
answer: 1
explain: rebase replays history by rewriting commit hashes, which corrupts shared history, so it fits only local unpushed commits. For pushed branches, merge preserves the complete history and does not create conflicts for your collaborators.
```
