# The Test Pyramid: Not Every Test Should Start From the UI

> Your project has 200 tests, and every single one "launches a browser, clicks a button, and watches the page." A full run takes 40 minutes, CI is red every day, and nobody looks at it anymore. The more tests you add, the slower everything gets, until nobody even runs them locally — that is not a test suite, it is a burden. The test pyramid answers the question of "how many tests, and where do they live?"

## What each layer owns

The test pyramid has three layers. From top to bottom the count drops, the speed rises, and the ability to pinpoint a failure falls.

| Layer | Owns | Speed | Share | Typical tools |
|---|---|---|---|---|
| End-to-end (E2E) | The whole system wired together works | seconds to minutes | at most ~10% | Selenium, Playwright |
| Integration | modules connect (database, network, filesystem) | milliseconds to seconds | 20%~30% | pytest + a real database |
| Unit | one function or one class behaves correctly | microseconds | 60%~80% | pytest + unittest |

**Unit tests** cover a single function or method. No database, no network, no file reads. They are the fastest and the easiest to pin down — when one fails, you know exactly which function is wrong.

```python
# The function under test
def calculate_discount(price, vip_level):
    if price < 0:
        raise ValueError("price must be non-negative")
    rates = {1: 0.05, 2: 0.10, 3: 0.20}
    return round(price * (1 - rates.get(vip_level, 0)), 2)

# Unit test: pass arguments, assert, done — no external resources touched
def test_calculate_discount():
    assert calculate_discount(100, 1) == 95.0
    assert calculate_discount(100, 3) == 80.0
    assert calculate_discount(100, 99) == 100.0  # unknown level => no discount
```

**Integration tests** verify that "my code works together with the real dependency." For example: after the order service writes to PostgreSQL, can it read the row back? Does a published message actually get consumed? They are allowed to use a real database, but they do not start the whole web service.

**End-to-end tests** walk the full flow from the user's perspective: open the browser → log in → place an order → pay → see the order. They are closest to reality, but also slow, brittle, and hard to diagnose.

## Why the proportions look the way they do

**The higher you go, the slower the feedback.** One unit test averages around 1 ms; 1,000 of them finish in about a second. One E2E test takes 30 seconds from launching the browser to tearing it down; 200 of them take 100 minutes. When you change a line of code you want to run the suite immediately, and an E2E-heavy suite will talk you out of running it locally at all.

**The higher you go, the harder a failure is to diagnose.** A unit test failure points at one assertion line. An E2E failure only tells you "payment did not succeed" — was it a missing frontend button, a 500 from the backend, a dead database connection, or the third-party payment sandbox being down?

**The higher you go, the more the environment can interfere.** Network jitter, dirty test data, another test mutating global state — any of these produces a flaky test. Unit tests do not depend on them, so their results are deterministic.

## The cost of an all-E2E suite

The most common beginner mistake: believing that "running it through the UI is the only real test," and therefore writing nothing but E2E. The cost is real.

**Crash site: 200 E2E tests, one CI run takes 47 minutes**

```text
$ pytest tests/
tests/test_login.py::test_login_success                PASSED  31.2s
tests/test_login.py::test_login_wrong_password         PASSED  28.7s
tests/test_order.py::test_create_order                 PASSED  42.1s
...
=====================================
200 passed in 47 minutes 12 seconds
```

**Consequence**: developers push and go to lunch before the result comes back. CI is red every day because a few tests die on network jitter. A month later nobody reads CI anymore and the suite is theatre.

**Crash site: E2E fails and you have no idea why**

```text
$ pytest tests/test_checkout.py::test_checkout_flow
>       assert page.locator(".order-success").is_visible()
E       AssertionError: the order-success page never rendered
```

Three hours of digging later, the real cause turned out to be a boundary check inside the price-calculation function. A problem that should have taken one millisecond to locate ate three hours instead.

**The fix: split the same scenario across layers**

```python
# Unit test: price-calculation logic (about 70%)
def test_price_calculator_boundary():
    assert calculate_total([{"price": 10, "qty": 3}], discount=0.1) == 27.0
    assert calculate_total([], discount=0) == 0

# Integration test: the order can be written and read back (about 20%)
def test_order_persisted(db_connection):
    order_id = create_order(db_connection, user_id=1, items=[1, 2])
    assert get_order(db_connection, order_id)["status"] == "paid"

# E2E test: from login to the success page — keep only 2~3 critical paths (about 10%)
def test_happy_path_checkout(browser):
    browser.goto("/login")
    # ...verify only that the main flow works
```

**The key judgment: how do you split a new feature across the layers?** Complex business logic gets lots of unit tests; integration points get integration tests; and only a handful of "golden paths" become E2E.

## The pyramid is not a silver bullet

Some cases are exceptions. A pure-frontend project or a CLI tool has only one external entry point, so E2E naturally takes a larger share. A database engine has internal logic that almost overlaps with its external interface. Proportions are heuristics, not dogma — but "all E2E, no exceptions" never makes sense.

## Summary

- The pyramid from bottom to top: unit tests (60~80%) → integration (20~30%) → E2E (at most ~10%).
- Higher layers are slower, more brittle, and harder to diagnose, so they should be fewer.
- An all-E2E suite leads to CI timeouts, flaky failures, undiagnosable errors, and eventual abandonment.
- The right move is to split one scenario across layers by "logic / integration / main flow."
- Proportions are heuristics; interface-heavy projects can lean higher, but an all-E2E suite is always a problem.

## In-class exercise

```quiz
type: choice
q: Your project has only E2E tests, and developers complain that "I change one line and wait 40 minutes to find out if it works," so nobody runs the suite anymore. What is the most reasonable improvement?
options:
- Buy a faster server for CI so E2E gets fast too.
- Push most logic-level checks down into unit tests, keeping only a handful of critical paths as E2E.
- Delete all the E2E tests and rely on manual testing.
- Reduce the number of tests so each feature is covered by exactly one path.
answer: 1
explain: The root cause is an unbalanced suite — E2E is doing the logic verification that unit tests should own. Moving logic checks down into unit tests makes them fast and pinpoints failures precisely; E2E keeps the critical paths, and both CI time and maintainability recover.
```

- Integration tests can fully replace unit tests because they cover more surface area.
answer: 1
explain: The pyramid's core rule is "many at the bottom, few at the top": unit tests dominate in count, speed, and precision, while E2E is the smallest slice and the closest to the user experience. Each layer owns a distinct job and none is a complete substitute for another.
