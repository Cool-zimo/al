# Performance Basics: Measure First, Then Change

> The first rule of optimization is "do not guess" — rewriting code on instinct usually changes nothing and sometimes introduces bugs. This lesson uses `cProfile` and `timeit` to find the real bottleneck before touching anything.

## Why gut feelings fail

When a program is slow, human intuition is almost always wrong. You stare at an "ugly-looking" loop, spend two hours rewriting it, and discover the real bottleneck was somewhere else — a database query, a full table scan, a function called in a loop. That is what "premature optimization is the root of all evil" really means: **before you know where the bottleneck is, any optimization is a gamble.**

Worse, optimized code is often harder to read and easier to break. Trading 1% performance for 20% readability is usually a bad deal. So the correct order is:

1. **Measure** — run a profile and get real data.
2. **Locate** — find the function or line that takes the most time.
3. **Optimize** — change only the hotspot, and change one thing at a time to verify it.
4. **Measure again** — run it again to confirm it actually got faster.

**Crash site: guessing the wrong target**

```python
# WRONG: list comprehension "feels too slow", so you rewrite it as a hand-rolled loop
result = []
for i in range(100000):
    if i % 2 == 0:
        result.append(i * i)

# the real bottleneck is not here at all; it is this line:
rows = load_from_db()   # a full table scan, taking 95% of the time
```

```text
$ python -m cProfile -s cumulative app.py
         500 function calls in 3.200 seconds

   Ordered by: cumulative time

   ncalls  tottime  cumtime  filename:lineno(function)
        1  0.000    3.198    db.py:42(load_from_db)
  100000  0.045    0.045    app.py:10(<listcomp>)
# the list comprehension took 0.045s; optimizing it is pointless
```

**Lesson**: after measuring, you find that most of the time goes where few people expect. Profile before optimizing — it is discipline, not a suggestion.

## Tool 1: timeit for small code snippets

`timeit` compares which of two small code blocks is faster. It runs the code many times automatically and averages the result, filtering out system noise. **Do not use `time.time()` to time things by hand** — that is the workshop approach.

```python
import timeit

setup = "data = list(range(1000))"

stmt_a = """
result = []
for x in data:
    if x % 2 == 0:
        result.append(x)
"""

stmt_b = "result = [x for x in data if x % 2 == 0]"

t_a = timeit.timeit(stmt_a, setup, number=10000)
t_b = timeit.timeit(stmt_b, setup, number=10000)

print(f"for loop: {t_a:.3f}s")
print(f"list comprehension: {t_b:.3f}s")
print(f"{t_a / t_b:.1f}x faster")
```

The command line works too, handy for a quick comparison:

```bash
$ python -m timeit -s "data = list(range(1000))" "[x for x in data if x % 2 == 0]"
50000 loops, best of 5: 6.23 usec per loop
```

**Crash site: measuring a meaningless result**

```python
# WRONG: number is too small, so system jitter drowns the real difference
t_a = timeit.timeit(stmt_a, setup, number=1)
t_b = timeit.timeit(stmt_b, setup, number=1)
print(t_a < t_b)   # sometimes True, sometimes False — useless
```

```text
first run:  for loop: 0.00012s
second run: for loop: 0.00008s
# at number=1, the noise is louder than the signal
```

**The fix**: let `timeit` run enough times (the default `number` auto-adjusts based on duration) and read the **average across many runs**, not a single sample.

## Tool 2: cProfile to find the hotspots

`timeit` is for comparing small snippets; `cProfile` is for giving the whole program a checkup — it tells you how many times each function was called and how long it took.

```python
import cProfile, pstats

def load_data():
    return [x for x in range(100000)]

def process(data):
    result = []
    for x in data:
        result.append(x * x)   # hotspot: called 100,000 times
    return result

def report(result):
    return sum(result)

cProfile.run("report(process(load_data()))", "stats.prof")
```

Inspect with `pstats`, or just use the command line:

```bash
$ python -m cProfile -s tottime my_script.py
```

| Column | Meaning |
|---|---|
| ncalls | how many times the function was called |
| tottime | time spent in the function itself (excluding callees) |
| cumtime | cumulative time (including callees) |
| percall | average time per call |

**How to read it**: start with the top of `tottime` — those are places where the function itself is genuinely slow. Then look for unusually large `ncalls` — that may be a place being called more than it should be.

## Common bottlenecks and fixes

These are the most common "slow" patterns, each with a reproducible example. **Do not memorize optimization slogans; read the profile data first and then decide which applies.**

**Bottleneck 1: repeated work inside a loop**

```python
# WRONG: recomputing len(items) every iteration (Python actually optimizes this one,
# this is only illustrative; the real problem is usually much heavier work)
def normalize(items):
    result = []
    for i in range(len(items)):
        for j in range(len(items)):    # O(n^2); disastrous for large n
            result.append(items[i] + items[j])
    return result
```

```python
# RIGHT: hoist the invariant computation out of the loop
def normalize(items):
    n = len(items)
    result = []
    for i in range(n):
        for j in range(n):
            result.append(items[i] + items[j])
    return result

# even better: if the algorithm itself is O(n^2) for large n, change the algorithm
# instead of the syntax
```

**Bottleneck 2: string concatenation with `+=` inside a loop**

```python
# WRONG: every += allocates a new string, O(n^2)
parts = []
for line in lines:
    parts += line   # character-by-character concatenation

# RIGHT: collect into a list, then join once
parts = []
for line in lines:
    parts.append(line)
result = "".join(parts)
```

**Bottleneck 3: unnecessary full traversal**

```python
# WRONG: finds the answer at element 5 but keeps scanning everything
def find_user(users, target):
    found = None
    for u in users:
        if u.name == target:
            found = u
    return found

# RIGHT: return as soon as you have it, or use next(...) with a generator expression
def find_user(users, target):
    for u in users:
        if u.name == target:
            return u
    return None
```

**Crash site: writing ugly code "for performance"**

```python
# WRONG: looks optimized, is hard to read, and the profile shows no gain
def weird_square(data):
    return list(map(lambda x: x*x, filter(lambda x: x % 2 == 0, data)))
```

```text
$ python -m cProfile -s tottime app.py
   ncalls  tottime  cumtime
        1  0.002    0.002    app.py:20(<listcomp>)
# the two styles take almost the same time, but the list comprehension is readable at a glance
```

**Lesson**: if the profile shows less than a 10% difference, pick the clearer, more maintainable version. **Readability is itself a kind of performance** — code that is easy to read is code someone is willing to optimize.

## The limits of optimization

Optimization is about return on investment. This rule is useful:

> **Make it correct and clear first; then make it fast.**

- In 90% of cases, picking the right data structure (a dict lookup instead of scanning a list) matters far more than fiddling with loop syntax.
- When a real bottleneck appears, ask whether you can **reduce the number of calls** or **improve the algorithm's complexity** before micro-tuning the syntax.
- If optimization makes the code harder to maintain and the gain is only a few percent, do not optimize.
- Measure, optimize, measure again — a closed loop, not a gut feeling at the end.

**Crash site: optimization introduces a bug**

```python
# WRONG: "saving a traversal" while accidentally changing the logic
def get_active(users):
    active = []
    for u in users:
        if u.is_active:
            active.append(u)
    return active

# optimized
def get_active(users):
    return [u for u in users if u.is_active]   # looks equivalent, but the original order was lost
```

```text
Test output:
expected: [u3, u1, u2]   # original logic preserved the original order
actual:   [u1, u2, u3]   # new logic changed the order
```

**Lesson**: have tests covering the current behavior before optimizing, and re-run them immediately after. Optimization without tests is gambling.

## Summary

- The first step of optimization is always measurement; guessing is guessing.
- `timeit` compares small snippets; `cProfile` checks the whole program for hotspots.
- When reading profiles, focus on `tottime` (where it is slow) and `ncalls` (called too often).
- Common bottlenecks: repeated computation in loops, string concatenation, unnecessary full scans.
- Skip optimizations with small gains and poor readability; verify every change with tests.
