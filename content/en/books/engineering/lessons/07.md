# Function Design: One Job Per Function

> You open a 400-line function that parses, validates, queries the database, sends email, and logs — all in passing. You want to change the retry logic when sending fails, but you are afraid to touch it because one change might ripple everywhere. Every problem in function design comes from one function doing too many things.

## One Job Per Function

This is not rhetoric; it is an executable standard: **if your description of a function contains connectors like "and", "then", or "while", it does more than one thing.**

```python
# WRONG: does three things
def process_order(order):
    # 1. Validate
    if order.amount <= 0:
        raise ValueError("amount must be positive")
    # 2. Write to the database
    db.insert(order)
    # 3. Send email
    smtp.send(f"order {order.id} created")
```

After splitting:

```python
def validate_order(order):
    if order.amount <= 0:
        raise ValueError("amount must be positive")

def save_order(order):
    db.insert(order)

def notify_order_created(order):
    smtp.send(f"order {order.id} created")

def process_order(order):
    validate_order(order)
    save_order(order)
    notify_order_created(order)
```

The top-level `process_order` now reads like a flow checklist — exactly what good code should look like. **Each function operates at one level of abstraction**, never mixing a detail like "validate the amount" with a flow step like "save and notify."

## Do Not Take Too Many Parameters

The parameter list is the function's interface. The wider the interface, the easier it is to call it wrong.

```python
# WRONG: seven parameters; nobody remembers the order
def create_user(name, email, phone, age, city, country, is_admin):
    ...
```

**Crash Site: arguments passed in the wrong order — no error, silently wrong data**

```python
# WRONG
create_user("Alice", "alice@qq.com", "13800138000", 25, "Hangzhou", "China", False)

# Three months later a field is added and a caller forgets to update
create_user("Bob", "bob@qq.com", "13900139000", 30, "Beijing", "China", False)
# Bob should have been an admin, but the caller forgot to pass it
```

This kind of bug does not raise an error; it just "silently corrupts data," which is a hundred times harder to find than a crash.

**The fix: pack parameters into a data structure**

```python
from dataclasses import dataclass

@dataclass
class UserSpec:
    name: str
    email: str
    phone: str
    age: int
    city: str
    country: str
    is_admin: bool = False

def create_user(spec: UserSpec):
    ...
```

Now the call is `create_user(UserSpec(name="Alice", email="...", ...))` — **every argument has a name**, a missing one raises an error, and argument order no longer matters.

Rule of thumb: **once you pass 3–4 arguments, consider packing them into an object.** It is not a hard rule, but it is worth pausing to ask "are these all attributes of the same thing?"

## Side Effects Must Be Explicit

**Crash Site: global state mutated deep inside**

```python
# WRONG: reads like a pure function, actually mutates global state
_users_cache = {}

def get_user(user_id):
    if user_id in _users_cache:
        return _users_cache[user_id]
    user = db.fetch(user_id)
    _users_cache[user_id] = user  # side effect hidden here
    return user
```

Callers do not know it touches a cache. In a test, the first and second calls for the same `user_id` return the same value (looks fine), but the cumulative effect of the cache produces bizarre bugs in long flows.

**Improve it: make the side effect explicit**

```python
def get_user(user_id, cache=None):
    if cache is not None and user_id in cache:
        return cache[user_id]
    user = db.fetch(user_id)
    if cache is not None:
        cache[user_id] = user
    return user
```

Now the caller **sees** the `cache` parameter and knows the state may change. Better still: without a cache the function is pure; caching activates only when explicitly passed. This "pure by default, stateful on demand" design is common.

## When to Split

Not every long function should be split. The criterion is **one level of abstraction**:

```python
def generate_report(orders):
    # All at the same level: flow steps
    validated = [validate(o) for o in orders]
    summary = calculate_summary(validated)
    rendered = render_html(summary)
    send_email(rendered)
```

`generate_report` has four steps, but each step is **a function call** — the abstraction level is uniform, so it stays intact.

Contrast with:

```python
def generate_report(orders):
    # Step one: 40 lines of validation inlined
    for o in orders:
        if o.amount < 0:
            ...
        if not o.email:
            ...
        # 20 more lines of validation
    # Step two: statistics inlined
    total = 0
    for o in orders:
        total += o.amount
        # another 15 lines of statistics
    # Step three: HTML assembly inlined
    html = "<html>"
    for item in summary:
        html += f"<li>{item}</li>"
    # another 30 lines of assembly
```

This "mixing implementation detail with flow control in the same function" is what must be split.

## Summary

- A function description containing "and" or "then" is a signal to split.
- A top-level function should read like a flow checklist.
- Beyond 3–4 parameters, pack them into an object to prevent ordering mistakes.
- Side effects must be explicit: let the caller see the state change.
- The split criterion is "uniform abstraction level."

```quiz
type: choice
q: You have a function `def config(server, port, user, password, db, timeout, retry):` and callers frequently pass the wrong arguments. What is the most reasonable improvement?
options:
- Document the argument order in a comment and consult it when calling
- Pack the related arguments into a config object using a dataclass or dict
- Reduce the parameter count below three and put the rest in global variables
- Split it into seven tiny functions, each taking one parameter
answer: 1
explain: Packing related parameters into an object is the standard solution: every field has a name at the call site, omissions and misordering are caught. Comments are unreliable; globals make dependencies more obscure; splitting into seven single-argument functions merely chops the logic into pieces.
```
