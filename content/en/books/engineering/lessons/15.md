# Code Review: Not Fault-Finding, but Shared Responsibility

> You open a PR and find twenty comments, fifteen of which say "missing a space here" or "bad variable name." You spend two days fixing formatting, and not one design issue gets discussed. Code review is the first gate of project quality; done wrong, it is a waste of time.

## What Review Actually Looks At

Review is not about whether the code runs — CI already verified that. Review is about **what lies beyond the code:**

1. **Design soundness** — does this change belong here? Is there a simpler approach? Is it solving at the wrong level of abstraction?
2. **Readability** — can someone arriving six months from now understand it? Do the names, comments, and structure explain themselves?
3. **Test coverage** — are the boundaries covered? Are error paths tested? Did changing the logic come with updated tests?
4. **Impact on existing code** — could this break another module? Did it touch a public API?
5. **Security and configuration** — any hardcoded secrets? Is input validated? Are permission checks complete?

**Crash Site: review turns into a formatting audit**

```text
PR #128: implement order export
  ├─ utils.py:42 should be two spaces here
  ├─ models.py:88 line too long, break it
  ├─ api.py:12 quote style is inconsistent
  ├─ ...
```

Formatting belongs to black / ruff, automatically. **If your review contains formatting comments, your toolchain is misconfigured.**

## How to Give Feedback

**Three principles:**

**1. State why, not just what**

```text
# Poor
- Rename this function to fetch_and_cache

# Good
- The name fetch_user implies a pure query, but it also writes to the cache.
  Suggest find_user_or_load_cache so the caller knows a side effect is possible.
```

**2. Separate "must change" from "open for discussion"**

```text
# Must change (blocks merging)
- There is no input validation here; malicious data goes straight into SQL.
  Parameterised queries are required, otherwise this cannot merge.

# Open for discussion (does not block)
- Personal preference: I find a dataclass clearer than a dict here,
  but if the team has no such convention, no pressure — what do you think?
```

GitHub / GitLab support marking with prefixes:

- `blocking:` or `must:` — must be resolved before merging.
- `nit:` — a nitpick, may be ignored.
- `question:` — a question, not a request for change.

**3. Address the code, never the person**

```text
# Poor
- You forgot to handle None again

# Good
- user can be None here (line 30 returns None), and it is used directly
  on line 45, which will raise AttributeError.
```

The first targets a person; the second targets the code and the problem itself.

## How to Receive Feedback

**How you respond determines how efficient the review is.**

**Do not get defensive on the spot:**

```text
Reviewer: this loop could break early; otherwise it runs a few extra rounds
You:      but the data set is tiny, performance is not an issue
# This is a debate, not a resolution
```

**Do understand first, then respond:**

```text
You: got it, switched to breaking early. And just to confirm,
     if the data grows later this change will still cover it — thanks.
```

When you genuinely disagree, give a reason rather than an emotion:

```text
You: I did not use a parameterised query here; instead I used
     an allow-list plus escaping, because the condition contains
     a dynamic table name that parameterisation does not support.
     The allow-list is at line 12 — does that approach look acceptable?
```

Keep the discussion focused on **the approach and the reasoning**, not on "who is right."

**Crash Site: mass-resolving every comment**

```text
Reviewer leaves 15 comments → you click "Resolve conversation" 15 times
→ in reality only 3 were addressed; the other 12 were untouched
```

**Consequence:** the reviewer believes everything is fixed, the merge goes through, and the remaining twelve problems quietly enter main. Before clicking "resolved," **the code must actually have changed.**

## Summary

- Review covers design, readability, tests, impact, and security — not formatting.
- Formatting is the tool's job; humans focus on design.
- Feedback states why, separates must-change from open, and addresses the code not the person.
- Receive feedback by understanding first, and give reasoning when you disagree.
- "Resolved" means the code really changed, not that the comment was closed.

## In-Class Exercise

```quiz
type: choice
q: As a reviewer you see a PR with 30 comments, 25 of which are about indentation, whitespace, and quote style. What is the most reasonable response?
options:
- Reply to every formatting point and ask the author to fix them
- Explain that the project has black/ruff auto-checking, suggest the author run them locally first, then focus on design and logic
- Reject the merge outright and wait for every formatting issue to be fixed
- Fix the formatting yourself and merge
answer: 1
explain: Formatting is the tool's responsibility; a human reviewing it is waste. Have the author run the formatter before resubmitting, and let the reviewer spend their effort on design and logic — the healthy review flow.
```
