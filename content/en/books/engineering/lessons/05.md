# Configuration: Secrets, Feature Flags, and "Works on My Machine"

> Alice hardcoded the database password in source and `git push`ed it — now the whole company can read it. Worse, production and staging share the same password. The core rule of configuration management is one line: **do not hardcode what changes.**

## Configuration Must Not Be Hardcoded

"Configuration" means anything that **varies by environment or deployment but is not business logic**:

- Database connection strings and API endpoints
- Secrets, tokens, passwords
- Feature flags (gradual rollout switches, debug mode)
- Timeouts and retry counts
- Log levels

What happens when values are hardcoded?

```python
# WRONG: configuration hardcoded
DATABASE_URL = "mysql://root:123456@192.168.1.100:3306/prod_db"
API_KEY = "sk-prod-abcdefghijklmn"
DEBUG = True

def get_user(uid):
    print(f"connecting to: {DATABASE_URL}")  # forgot to remove this debug line
    ...
```

**Crash Site: tests connect to production**

```python
# WRONG: forgot to change it
DATABASE_URL = "mysql://root:123456@10.0.0.5:3306/prod_db"
DEBUG = True

# Alice runs tests locally
$ python manage.py test
Creating test database...
# The test suite is genuinely wiping the production database
```

**Consequence:** the test suite starts purging production data, because the configuration was hardcoded and nobody noticed it pointed at production. When this happens, it leaves a mark on your career.

## Environment Variables vs Config Files

Two主流 approaches.

**Environment variables** — read from the process environment; right for secrets and deployment-specific values.

```python
import os

database_url = os.environ["DATABASE_URL"]
api_key = os.environ["API_KEY"]
debug = os.environ.get("DEBUG", "false").lower() == "true"
```

**Config files** — right for non-sensitive, structured, frequently tuned parameters.

```yaml
# config.yaml
database:
  host: localhost
  port: 3306
  name: app_db
server:
  host: 0.0.0.0
  port: 8000
  timeout: 30
```

| Aspect | Environment variables | Config files |
|---|---|---|
| What to put here | Secrets, tokens, deploy addresses | Business params, timeouts, flags |
| Secret safety | Relatively safe (out of the repo) | Should not hold secrets |
| Structural complexity | Flat; nesting is awkward | Supports nesting and lists |
| 12-Factor compatible | Yes (recommended) | Not recommended for secrets |
| Local dev ergonomics | Must export or use .env | Edit a file directly |

The **12-Factor App** principle states that configuration should live in environment variables. That way the same code deployed to dev, staging, and production needs only a switch of environment variables — no code change, no config-file change.

## .env and python-dotenv

Environment variables have one pain point: during local development you must `export` by hand every time. The `.env` file is the answer.

```text
# .env (project root, never committed)
DATABASE_URL=mysql://root:123456@localhost:3306/dev_db
API_KEY=sk-test-xxxxxxxx
DEBUG=true
```

```python
# main.py
from dotenv import load_dotenv
import os

load_dotenv()  # loads .env into the environment

database_url = os.environ["DATABASE_URL"]
api_key = os.environ["API_KEY"]
```

`load_dotenv()` reads `.env` and writes it into `os.environ`. When deployed to a server you set no `.env` and rely on the system's environment variables instead — **production does not depend on a .env file.**

**Key point: `.env` must be in `.gitignore`.**

```gitignore
.env
.env.local
.env.*.local
```

**Crash Site: `.env` enters Git history**

```bash
$ git add .env
$ git commit -m "add env"
$ git push
```

Even if you delete `.env` and commit the next second, the secret remains in Git history — anyone who clones the repo can read it. The fix is `git filter-repo` to rewrite history, and you **must rotate every leaked secret**, on the assumption that someone already has it.

## Secrets Must Never Enter the Repository

This deserves单独 emphasis because it is irreversible.

- A secret in the repository is a key taped to the office door.
- Git history keeps it forever; deleting the file does nothing.
- "Leaked" is not fixed by "deleted" — it is fixed by "changed."
- Test secrets count. Manage them to the same standard as production secrets.

**The correct secret-management flow:**

```bash
# 1. Local development: use .env, load it into environment variables
$ echo "API_KEY=xxx" > .env

# 2. Production deployment: use the platform's environment-variable mechanism
#    Heroku:  heroku config:set API_KEY=xxx
#    Vercel:  fill it in via the dashboard
#    Kubernetes: a Secret object
#    Bare server: systemd EnvironmentFile or an export in the deploy script
```

## Summary

- Configuration (connection strings, secrets, flags, timeouts) must not be hardcoded.
- Environment variables suit secrets and deployment differences; config files suit structured business parameters.
- `.env` is loaded with python-dotenv, which makes local development convenient.
- `.env` must be in `.gitignore`; once in history, it counts as leaked.
- A leaked secret is handled by **rotation**, not deletion.

## In-Class Exercise

```quiz
type: choice
q: You need to run a project locally and it requires an API_KEY. What is the correct approach?
options:
- Hardcode API_KEY in the source and commit it so the team can share it
- Put it in a .env file, load it with python-dotenv, and keep .env in .gitignore
- Put it in config.py and commit it because it is only a test secret
- Manually export API_KEY before every run, and hardcode it because exporting is tedious
answer: 1
explain: .env + python-dotenv is the standard local-dev pattern, and .env must be gitignored. Test secrets are still secrets and do not belong in the repository; manual exports do not scale.
```
