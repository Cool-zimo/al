# Virtual Environments: Give Every Project Its Own Room

> You have three projects on your machine: one needs Django 3, another needs Django 5, and a third is a script written three years ago whose dependencies nobody remembers. Without isolation they will eventually step on each other's toes — a virtual environment gives each project a separate room where they cannot interfere.

## Why You Shouldn't Install into System Python

The most common beginner move is `pip install requests`, seeing it work, and feeling happy. The trouble shows up six months later.

System Python belongs to the operating system. Ubuntu's `apt` and several macOS system tools depend on it. Every package you install or upgrade there is like moving the furniture in someone else's house.

**Crash Site: upgrading a system package breaks a system command**

```bash
# WRONG: installing straight into system Python
$ sudo pip install --upgrade requests
$ sudo pip install -r requirements.txt
# Everything seems fine
$ sudo apt update
Traceback (most recent call last):
  File "/usr/bin/apt", line 3, in <module>
    import apt_pkg
ModuleNotFoundError: No module named 'apt_pkg'
```

**What you see:** the system's own `apt` command crashes because a dependency you upgraded became incompatible. Fixing it costs an hour that should never have existed.

The more subtle problem is **dependency conflict**. Project A needs `requests==2.28`, project B needs `requests==2.31`. Only one can live in the system at a time; install B's version and A may fail on a code path you never tested.

A virtual environment solves exactly these two things: isolate projects, and leave the system alone.

## How to Build One with venv

Python 3.3+ ships `venv` in the standard library — no extra install needed.

```bash
# Run this in your project root
$ python3 -m venv .venv
```

This creates a `.venv/` folder containing an independent copy of the Python interpreter and an empty `site-packages`. From then on, every `python` and `pip` inside that directory sees only the packages in this room.

Activation differs by shell:

```bash
# macOS / Linux
$ source .venv/bin/activate

# Windows (cmd)
> .venv\Scripts\activate

# Windows (PowerShell)
> .venv\Scripts\Activate.ps1
```

Once activated, your prompt gains a `(.venv)` prefix:

```bash
(.venv) $ which python
/data/workspace/myproject/.venv/bin/python
```

## Why Activation Matters

Activation does one simple thing: it prepends the virtual environment's `bin/` directory to `PATH`. So when you type `python` or `pip`, the shell finds `.venv/bin/python` instead of the system one.

**Crash Site: forgetting to activate, installing packages all evening, finding them gone the next day**

```bash
$ cd myproject
$ pip install requests pandas numpy
Successfully installed requests-2.31.0 pandas-2.1.0 numpy-1.26.0
$ python -c "import requests; print(requests.__version__)"
2.31.0
# The next day
$ cd myproject
$ python -c "import requests"
Traceback (most recent call last):
  ModuleNotFoundError: No module named 'requests'
```

**What you see:** `ModuleNotFoundError`. Because you skipped activation yesterday, the packages landed in system Python — or in some other virtual environment. Today a fresh terminal finds no environment at all, so `requests` is naturally missing.

If you truly refuse to activate, you can still call the interpreter by its full path:

```bash
$ .venv/bin/pip install requests
$ .venv/bin/python main.py
```

Same effect, just more typing. Activation exists to spare you those keystrokes.

## What Belongs in .gitignore

A virtual environment directory **must never** be committed to Git. It weighs hundreds of megabytes, contains binaries tied to your operating system, and is useless to anyone who clones the repo.

Place a `.gitignore` in the project root:

```gitignore
# Virtual environments
.venv/
venv/
env/

# Python bytecode cache
__pycache__/
*.pyc
*.pyo

# Sensitive configuration
.env
.env.local

# Editor files
.vscode/
.idea/
```

**Crash Site: accidentally committing `.venv`**

```bash
$ git add .
$ git status
On branch main
Changes to be committed:
  new file:   .venv/bin/python3.11
  new file:   .venv/lib/python3.11/site-packages/numpy/...
  ... (8,000+ files)
```

**Consequence:** the repo balloons from a few hundred kilobytes to hundreds of megabytes; a clone takes five minutes, and every CI run downloads the lot. Your teammates want to strangle you.

If it is already committed, `git rm` alone does not fix it — the files remain in Git history and the repo stays bloated. Truly cleaning it requires `git filter-repo`, which is a story for another chapter.

## The Lifecycle of a Virtual Environment

A good habit: **one environment per project, and rebuild that environment from the requirements.**

```bash
# On a fresh machine, three steps to recover the environment
$ git clone <repo>
$ cd repo
$ python3 -m venv .venv
$ source .venv/bin/activate
(..venv) $ pip install -r requirements.txt
```

The virtual environment itself is **disposable**. You can delete `.venv` and rebuild it at any time; the real "environment specification" is `requirements.txt` (covered in the next lesson). So `.venv` goes into `.gitignore` while `requirements.txt` must stay in Git — this distinction matters.

## Summary

- System Python belongs to the OS; never install project dependencies into it.
- `python3 -m venv .venv` creates an environment; `source .venv/bin/activate` activates it.
- Activation is just a `PATH` tweak; forget it and you install in the wrong place.
- `.venv/`, `__pycache__/`, and `.env` all belong in `.gitignore`.
- Environments are disposable; dependency lists are not — that is the core rule.

## In-Class Exercise

```quiz
type: choice
q: You have just cloned a project on a new machine and want to install its dependencies. Which approach is correct?
options:
- Run `pip install -r requirements.txt` directly, ignoring virtual environments
- First `python3 -m venv .venv`, then activate and `pip install -r requirements.txt`
- Run `sudo pip install -r requirements.txt` because system Python is more stable
- Reuse an old `.venv` by copying the project folder into it
answer: 1
explain: The correct flow is create, activate, install. Installing directly pollutes system Python; sudo is even riskier; an old .venv contains binaries and paths tied to a different machine, so reusing it causes obscure errors.
```
