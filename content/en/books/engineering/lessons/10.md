# The Philosophy of Error Handling: Exceptions Should Not Be Seen — and Never Swallowed

> Your API page starts告警 at midnight: 500 errors, and the logs hold only `Internal Server Error` — no stack trace, no context. It takes you four hours to trace it to an `except:` that swallowed the exception. The whole art of error handling lies in "catch when you can act, and let it bubble when you cannot."

## When to Catch

Catch an exception only when you can do something about it. The test: **what can you do with this exception?**

```python
# You can act: retry, degrade, give a friendly message
def fetch_user(user_id):
    try:
        return db.find(user_id)
    except ConnectionError:
        # What you can do: retry once
        return db.find(user_id)
```

```python
# You cannot act: let the caller decide
def parse_config(path):
    with open(path) as f:
        return json.load(f)
    # FileNotFoundError and json.JSONDecodeError should not be caught here
    # The caller knows whether to show a dialog, use a default, or crash
```

**Crash Site: converting an exception into a return value inside a function**

```python
# WRONG: using a return value to signal failure
def read_file(path):
    try:
        with open(path) as f:
            return f.read()
    except Exception:
        return None
```

The caller:

```python
content = read_file("config.json")
if content is None:
    # File missing? Permission problem? Encoding error? All lost
    print("read failed")
```

**What you see:** it prints "read failed" and gives you no idea which failure occurred. The exception object carried a type and a stack trace; you erased both with a single `None`.

## Never Swallow an Exception

**The single most dangerous line of Python:**

```python
try:
    do_something()
except:
    pass
```

`except:` (with no type) catches **every** exception — including `KeyboardInterrupt` (Ctrl+C) and `SystemExit`. And `pass` does nothing at all.

**Crash Site: bare except + pass makes bugs invisible**

```python
# WRONG
def send_notification(user, msg):
    try:
        smtp.send(user.email, msg)
    except:
        pass  # if sending fails, never mind, it's not important
```

In production, users complain "I never got the notification." You check the logs — nothing, because the exception was swallowed by `pass`. You can only add logging, redeploy, and wait for it to happen again.

**Fix it: at least log.**

```python
import logging

def send_notification(user, msg):
    try:
        smtp.send(user.email, msg)
    except Exception as e:  # catch a concrete exception, not a bare except
        logging.exception("notification failed user=%s", user.id)
        # Also possible: retry, queue it, raise a custom exception
```

`logging.exception` attaches the full stack trace automatically — the key to debugging.

**If you really must catch everything, at least spare KeyboardInterrupt:**

```python
try:
    do_work()
except Exception:  # does not catch KeyboardInterrupt/SystemExit (BaseException subclasses)
    handle_error()
```

`except Exception` is better than `except:` because it lets `KeyboardInterrupt` through — otherwise Ctrl+C cannot stop your program.

## Custom Exceptions

When the standard library's exceptions are enough, use them (`ValueError`, `FileNotFoundError`). But when your library or module needs to express **domain-specific failure reasons**, a custom exception lets the caller distinguish them precisely.

```python
class InsufficientBalanceError(Exception):
    """Raised when the account balance is too low."""

class OrderCancelledError(Exception):
    """Raised when the order has been cancelled and cannot be acted on."""
```

```python
def pay(order, amount):
    if order.status == "cancelled":
        raise OrderCancelledError(f"order {order.id} is cancelled")
    if balance < amount:
        raise InsufficientBalanceError(
            f"insufficient balance: need {amount}, have {balance}"
        )
```

The caller:

```python
try:
    pay(order, 100)
except InsufficientBalanceError as e:
    show_message("insufficient balance, please top up")
except OrderCancelledError as e:
    show_message("this order has been cancelled")
```

**Crash Site: using only Exception leaves the caller unable to tell errors apart**

```python
# WRONG
def pay(order, amount):
    if order.status == "cancelled":
        raise Exception("order cancelled")
    if balance < amount:
        raise Exception("insufficient balance")
```

The caller can only `except Exception` and then inspect the string — **using a string as an error code is the most fragile design**, because one wording change silently breaks the logic.

## assert Is Not for Input Validation

`assert` exists for **internal invariants**, not for validating user input.

```python
def withdraw(account, amount):
    assert amount > 0, "amount must be positive"
    ...
```

**The problem:** Python can be started with `-O` (optimize mode), and then every `assert` is **removed**.

```bash
$ python -O main.py
# all assert statements are skipped
```

**Crash Site: parameter validation disappears in optimized mode**

```python
def divide(a, b):
    assert b != 0, "divisor must not be zero"
    return a / b
```

```bash
$ python main.py
>>> divide(1, 0)
AssertionError: divisor must not be zero
$ python -O main.py
>>> divide(1, 0)
ZeroDivisionError: division by zero
```

**What you see:** in optimized mode the `assert` is gone and you get a raw `ZeroDivisionError` instead — inconsistent behaviour. Worse, if production runs in optimized mode, your validation is effectively absent.

**For parameter validation, use `if` + raise:**

```python
def withdraw(account, amount):
    if amount <= 0:
        raise ValueError(f"amount must be positive, got {amount}")
    ...
```

`raise ValueError` is never optimized away.

**So where does assert belong?** On "should never happen" internal checks:

```python
def _internal_sort(items):
    # Internal invariant: the input is always a list
    assert isinstance(items, list)
    ...
```

If this assert fires, **your own code has a bug** — not the user's.

## Summary

- Catch only when you can act (retry, degrade, inform); otherwise let it bubble up.
- Never write `except: pass`; at least log, and prefer `except Exception` to a bare except.
- Use custom exceptions for domain-specific errors so the caller can distinguish them.
- `assert` is removed by `python -O`; use `if` + `raise` for validation.
- `assert` is for internal invariants; if it fires, you have a bug.
