# CI Basics: Why "It Worked on My Machine" Is Not a Strategy

> You ran the tests locally, committed, pushed, merged. The next day a colleague pulls the code and the tests fail — their environment has a different `pandas` version. Later, someone forgets to run the tests and pushes; a bug lands on main. "It works on my machine" is the most useless sentence in software engineering, because it is not true on anyone else's machine. CI turns "build + check + test" into an action that runs on every commit.

## Why CI exists

CI (Continuous Integration) boils down to one idea: **integrate code into the main branch frequently, and verify it automatically on every integration.** Its value is not speed; it is that every commit runs the same checks, and everyone gets the same result.

**Crash site: passes locally, fails in CI**

```text
$ git push origin feature/login
# two minutes later, an email arrives
> CI FAILED: ModuleNotFoundError: No module named 'requests'
```

Cause: the author installed `requests` but never added it to `requirements.txt`, so it existed locally but was absent in CI's clean environment.

**Crash site: forgot to run the tests**

```text
Coworker: I changed one line, trivial, no need to run the suite.
Coworker: git push
> CI FAILED: 12 tests failed
# A problem that should have taken 30 seconds now surfaces after the push.
```

**CI solves "inconsistent verification standards":** local environments differ wildly, but CI is one clean machine, one set of commands, one result. When it passes, others can pull with confidence.

## The shape of a GitHub Actions workflow

GitHub Actions configuration lives in `.github/workflows/` as YAML.

```yaml
# .github/workflows/ci.yml
name: CI

# when to run: on push and on PR
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

# environment variables available to the whole workflow
env:
  PYTHON_VERSION: "3.12"

jobs:
  lint-and-test:
    runs-on: ubuntu-latest          # the runner
    steps:
      - uses: actions/checkout@v4   # step 1: check out the code

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: ${{ env.PYTHON_VERSION }}

      - name: Install dependencies
        run: |
          python -m pip install --upgrade pip
          pip install -r requirements.txt
          pip install pytest ruff

      - name: Lint
        run: ruff check .

      - name: Test
        run: pytest tests/ -v
```

**A few key concepts**:

- `on`: when to run. Common triggers are `push` and `pull_request`; you can also run on a schedule.
- `jobs`: a workflow can have several jobs, which run in parallel by default. Here there is only `lint-and-test`.
- `runs-on`: which machine. `ubuntu-latest` is the most common; there is also `windows-latest` and `macos-latest`.
- `steps`: the ordered sequence. `uses` references an existing action; `run` executes a shell command.
- `actions/checkout@v4`: almost always the first step, pulling the repo onto the runner.

## Lint first, then test

**A good workflow runs the cheap checks first and the slow checks after** — lint takes seconds, tests take tens of seconds, so run lint first; if the formatting is wrong, do not waste time on tests.

```yaml
jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install ruff
      - run: ruff check .

  test:
    runs-on: ubuntu-latest
    needs: lint                # wait for lint to pass first
    strategy:
      matrix:
        python-version: ["3.10", "3.11", "3.12"]   # version matrix
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: ${{ matrix.python-version }}
      - run: pip install -r requirements.txt pytest
      - run: pytest tests/ --tb=short
```

`needs: lint` means the test job waits for lint. `strategy.matrix` runs the tests across three Python versions at once, catching version-compatibility problems immediately.

**Crash site: a secret leaks**

```yaml
# WRONG
- name: Deploy
  run: |
    echo "the password is ${{ secrets.DB_PASSWORD }}"
    deploy.sh
```

```text
> the password appears in plaintext in the log: the password is s3cret!
```

Even with `secrets`, echoing it writes it into the log, where anyone with workflow-log access can read it. **Rule: pass secrets only into environment variables for the process that needs them; never print them, never concatenate them into a URL, never write them to a file.**

The correct version:

```yaml
- name: Deploy
  env:
    DB_PASSWORD: ${{ secrets.DB_PASSWORD }}
  run: deploy.sh        # the script reads from the environment; nothing in the log
```

## Common CI patterns

| Scenario | Approach |
|---|---|
| Multi-version compatibility | `strategy.matrix` runs several Python versions |
| Slow tasks (deploy, publish) | a separate job; `needs` the test job so it only runs after tests pass |
| Cache dependencies to speed up | `actions/cache` for the pip download directory |
| Run on specific branches only | `if: github.ref == 'refs/heads/main'` |
| Run slow tests on a schedule | `schedule: - cron: "0 0 * * *"` (once a day) |

**A healthy CI finishes within 5 minutes.** If it takes too long, nobody waits, and if nobody waits, nobody reads it — and then CI is dead. Same logic as the test pyramid.

## Summary

- CI's value is turning verification into a repeatable process: same checks, same result, every time.
- GitHub Actions lives in `.github/workflows/*.yml`.
- The core structure: `on` (triggers) → `jobs` → `runs-on` → `steps` (`uses` / `run`).
- Run fast lint first, then slow tests; chain them with `needs`.
- Use `strategy.matrix` to verify across Python versions.
- Secrets go through `env` and into a process; never print them to the log.

## In-class exercise

```quiz
type: choice
q: You set up CI, but every run takes 25 minutes, so developers push without waiting for results and CI is effectively dead. What is the most reasonable optimization?
options:
- Turn CI off and rely on code review for quality.
- Rebalance the test pyramid so unit tests dominate, shorten the suite, and split lint and test into separate jobs so fast feedback comes first.
- Add more tests for broader coverage.
- Run CI only on Fridays.
answer: 1
explain: Slow CI feedback is the main reason CI dies. Shortening the suite (unit tests dominate, E2E stays lean) while letting fast checks report first is what makes developers willing to wait. Turning CI off or running it rarely throws away continuous integration's value.
```

## Lesson quiz

```quiz
type: choice
exam: true
q: Which statement about secrets in GitHub Actions is correct?
options:
- You can echo them in a run step just to confirm they are configured correctly.
- They should be injected through env into an environment variable, read by the program, and never printed, logged, or concatenated into a URL.
- Secrets are public; anyone who can access the repo can read them.
- Secrets can only be used in local development, not in CI.
answer: 1
explain: env injection is the safest route: the process reads from the environment and the plaintext never appears in the log. Echoing leaks it; secrets are encrypted, not public; and they are designed specifically for CI.
```
