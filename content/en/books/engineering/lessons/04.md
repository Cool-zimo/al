# Project Layout: Helping a Newcomer Read Your Project in 30 Seconds

> You open an open-source project whose root dumps `main.py`, `utils.py`, `test_main.py`, `data.csv`, and `config.ini` into the same folder. You want to change a feature and have no idea where to start. A good directory layout is a navigation map.

## src Layout vs Flat Layout

**Flat layout** — every source file sits at the project root.

```text
myproject/
├── main.py
├── utils.py
├── models.py
├── config.py
├── tests/
│   └── test_main.py
├── requirements.txt
└── README.md
```

**src layout** — source code lives under one `src/` directory.

```text
myproject/
├── src/
│   └── myproject/
│       ├── __init__.py
│       ├── main.py
│       ├── utils.py
│       └── models.py
├── tests/
│   └── test_main.py
├── pyproject.toml
└── README.md
```

**The difference is not aesthetics; it changes how tests behave.**

Under flat layout, `tests/` sits at the same level as the source. When you run tests, Python starts from the root, so `import main` works immediately. The problem: **tests exercise the source on disk, not the installed package.** If you forget to include a file in the package, the tests still pass — because they never went through the installation path.

The src layout forces you to **install the package first** (`pip install -e .`), so tests import the installed version. Local testing and real usage now follow the same path, and a missing file surfaces during testing.

## Why tests/ and README Matter

**tests/** is not just "a folder for test files." It sends a signal: this project has tests, and they live separately from the code under test.

```text
tests/
├── __init__.py
├── test_user.py
├── test_order.py
└── conftest.py
```

Name each test file after its target module (`test_xxx.py` tests `xxx.py`) and the mapping is obvious at a glance. Because test files live in `tests/`, imports look like `from myproject import user` — identical to how a user would import — which is precisely why the src layout is the stricter choice.

**README** is the project's front door. It should cover at least three things:

1. What this project does (one sentence).
2. How to install and run it.
3. How to test it.

```markdown
# Order Processing Service

Batch-imports CSV orders into a database, with dedup and format validation.

## Installation

    python3 -m venv .venv
    source .venv/bin/activate
    pip install -r requirements.txt

## Running

    python -m order_service --input orders.csv

## Testing

    pytest
```

**Crash Site: no README, so a newcomer needs two days to run anything**

```text
myproject/
├── app.py
├── config_dev.ini
├── config_prod.ini
└── run.sh
```

A newcomer clones the repo, has no idea what to install, which config file to use, or whether `./run.sh` needs executable permissions. So they message you; you are away; they read the code; eventually they guess a config and run — against the production database.

## Editable Installs with pip install -e

While developing, you want edits to take effect immediately *and* tests to import the package the way a user would. An editable install does both.

```bash
# In the project root (where pyproject.toml lives)
$ pip install -e .
```

The `-e` stands for editable. It does not copy code; it creates a link in the environment pointing at your source directory. From then on:

```python
# From any directory, this import works
from myproject import utils

# Edits to utils.py take effect immediately — no reinstall needed
```

This solves the classic flat-layout problem — the **import trap**:

```text
# WRONG: flat layout + running a script directly
myproject/
├── main.py        # from utils import helper
└── utils.py       # def helper(): ...

$ cd myproject
$ python main.py   # works

$ cd ..
$ python -m myproject.main
ModuleNotFoundError: No module named 'myproject'
```

After an editable install, `myproject` is a proper package no matter where you launch from, and the import path is unified.

## A Recommended Complete Structure

```text
myproject/
├── src/
│   └── myproject/
│       ├── __init__.py
│       ├── main.py
│       ├── api/
│       │   ├── __init__.py
│       │   └── client.py
│       └── core/
│           ├── __init__.py
│           └── engine.py
├── tests/
│   ├── __init__.py
│   ├── conftest.py
│   └── test_engine.py
├── docs/
│   └── design.md
├── .gitignore
├── pyproject.toml
├── README.md
└── LICENSE
```

Sub-packages are layered by responsibility (`api/`, `core/`); the test tree mirrors the source tree; documentation gets its own directory.

## Summary

- The src layout forces the installation path, keeping local tests and real usage consistent.
- Flat layout is simple but can hide problems such as missing files in the package.
- `tests/` names files after modules and keeps them separate from the code under test.
- A README must state: what it does, how to install, how to run, how to test.
- `pip install -e .` unifies import paths between development and installation.

## In-Class Exercise

```quiz
type: choice
q: You have inherited a legacy flat-layout project in which main.py does `import utils` at the root. You plan to add tests. Which approach is most reasonable?
options:
- Just create tests/ and run them; working is good enough
- Migrate to src layout with an editable install so tests import the same way users do
- Convert every import to a relative import
- Put the test files in the same directory as the source
answer: 1
explain: src layout plus an editable install ensures tests follow the installation path, matching how users actually consume the package — the stricter long-term choice. Simply adding tests works but is not rigorous; relative imports do not solve the test-path problem.
```
