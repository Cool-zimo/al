# The Basic Git Workflow: The add / commit / push Trio

> You changed three files and want to commit. "git add . then git commit -m 'update' then git push" — that works, but it treats git like a file-syncing service. In a real workflow, every commit is a **meaningful node** that explains what you did and lets you roll back at any time.

## The Three States: Working Tree → Staging Area → Repository

Git has three areas. Understand them and you will never again ask "why did my change not get committed?"

```text
Working Directory        the files you are editing, really on disk
        │  git add
        ▼
Staging Area / Index     the things you "intend" to put into this commit
        │  git commit
        ▼
Repository / HEAD        permanent record with commit history
        │  git push
        ▼
Remote                   the version on GitHub / GitLab
```

**Crash Site: `git add .` stages everything, including what should not be staged**

```bash
$ git status
On branch main
Changes not staged for commit:
        modified:   src/main.py
        modified:   src/config.py
Untracked files:
        .env
        __pycache__/main.cpython-311.pyc
        .venv/lib/python3.11/site-packages/numpy/... (thousands of files)

$ git add .
$ git status
# .env and .venv are now in the staging area
```

**Consequence:** a secret config and hundreds of megabytes of virtual environment get pushed to the remote. `.gitignore` was configured too late, and recovery is painful.

**The fix: stage precisely, or use the interactive form**

```bash
# Stage only the business files you changed
$ git add src/main.py src/config.py

# Or use the interactive mode and confirm chunk by chunk
$ git add -p
```

`git add -p` (`-p` for patch) asks you chunk by chunk "do you want this hunk staged?" — finer-grained than files, and invaluable when you changed two things in one file but only want to commit one of them.

## Commit Granularity: One Thing Per Commit

**Crash Site: the kitchen-sink commit**

```bash
$ git commit -m "update"
```

`git show` reveals a 500-line diff: login logic changed, three files reformatted along the way, a test fixed, and a typo corrected in the README.

Three days later you want to revert "the login logic change," but it is tangled with the reformatting and the README in the same commit. You cannot revert the login portion alone — **granularity this coarse destroys the value of version control.**

**A good commit** does exactly one thing, and that one thing fits in the subject line.

```bash
$ git log --oneline
a3f2c1e fix(auth): restore the typed input on failed login
d7b8e91 refactor: extract validation out of views.py into validators.py
5c0a2b7 feat(auth): support phone-number login
```

Each subject is an **independent, reversible** unit of change.

## Controlling Granularity: Keep Changes Small

The practical method: open a new branch, then make one small commit per small goal.

```bash
$ git checkout -b feature/phone-login

# Step 1: add the field to the data model
$ git add models.py
$ git commit -m "feat(models): add User.phone field"

# Step 2: add validation
$ git add validators.py
$ git commit -m "feat(auth): validate phone-number format"

# Step 3: wire up the login endpoint
$ git add api/auth.py
$ git commit -m "feat(auth): support phone login on the endpoint"
```

Three commits, each reviewable and revertible on its own.

**Crash Site: halfway through committing, you spot one more small change**

```bash
$ git commit -m "refactor: split the validation module"
# after committing you notice a typo in validators.py
```

Do not open a separate "fix typo" commit. Use `git commit --amend` to fold it into the previous commit — **but only for commits that have not been pushed.** Amending a pushed commit rewrites history and requires a force push, which will make your collaborators hate you.

## Essential Workflow Commands

```bash
# See the current state (the four words you type most)
$ git status

# See what changed (working tree vs staging area)
$ git diff

# See the staged changes vs the last commit (what is about to be committed)
$ git diff --staged

# View commit history
$ git log --oneline

# Discard working-tree changes (dangerous, unrecoverable)
$ git checkout -- src/main.py

# Unstage (changes stay in the working tree)
$ git reset HEAD src/main.py

# Fetch remote updates and merge
$ git pull

# Push to the remote
$ git push
```

**Crash Site: pushing without pulling first, getting rejected**

```bash
$ git push
To github.com:you/repo.git
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'github.com:you/repo.git'
hint: Updates were rejected because the remote contains work that you do
hint: not have locally.
```

**What you see:** the push is rejected because the remote has commits you lack (a colleague just pushed, for instance). Fix: `git pull --rebase` to bring the remote work down first, replay your commits on top, then push.

## Summary

- Git's three areas: working tree → staging area → repository → remote.
- Do not `git add .` in one sweep; stage precisely or use `git add -p`.
- One thing per commit; fine enough to revert and review.
- Rely on `git status` / `git diff` / `git log` to know where you stand.
- Pull before pushing; if there is a conflict, rebase first, then push.

## In-Class Exercise

```quiz
type: choice
q: You changed login.py and utils.py, but only want to commit the change to login.py and leave utils.py for next time. What is the correct move?
options:
- git add . then commit, taking both at once
- git add login.py then commit, leaving utils.py in the working tree
- commit without add and git will find the changes automatically
- git stash everything first, then commit login.py
answer: 1
explain: Naming the file after git add puts only that file into the staging area; the rest stays in the working tree for next time. git add . stages both; a commit without add only commits what is already staged (here, nothing).
```
