# Deployment and Operations: From "Runs on My Machine" to "Runs in Production"

> "It works on my machine" is the classic programmer joke and the most expensive kind of failure. This lesson covers the real gap between local and production: how to manage processes, how to know the service is alive, how to roll back when something breaks, and a **checklist that must be walked through before every release.**

## What local has that production does not

Running a script locally means you type a command in a terminal, watch the output, and handle errors on the spot. A production service is completely different: **nobody is watching, it crashes on its own, it must restart on its own, and it must serve many requests at once.**

| Dimension | Local | Production |
|---|---|---|
| Startup | typed by hand | a process manager starts it automatically |
| Crash | you see the error | automatic restart + alert |
| Configuration | hardcoded in code | environment variables / config center |
| Logs | terminal output | written to disk + collected centrally |
| Health checks | unnecessary | required, so the load balancer can decide |
| Rollback | manual `git checkout` | one-click switch to the previous version |
| Resources | sole use of your machine | constrained, resource usage must be monitored |

**Crash site: thinking `python app.py` is deployment**

```bash
# WRONG: close the terminal and the service dies
$ ssh server
$ python app.py
 * Running on http://0.0.0.0:8000
# closing the SSH session -> the process receives SIGHUP -> service goes down
```

```text
User report:
the site is unreachable, but nothing in the code changed
# cause: the session ended and the foreground process was killed
```

**The fix**: use a process manager (systemd, supervisor) or an orchestrator (Docker Compose, K8s) to host the process, ensuring it restarts on crash and starts on boot.

## Process management: keeping the service on its feet

Two of the most common setups:

**systemd (the standard on Linux servers)**

```ini
# /etc/systemd/system/myapp.service
[Unit]
Description=My Python App
After=network.target

[Service]
Type=simple
User=appuser
WorkingDirectory=/opt/myapp
EnvironmentFile=/opt/myapp/.env
ExecStart=/opt/myapp/.venv/bin/python -m myapp.cli
Restart=on-failure       # restart automatically on crash
RestartSec=5
StandardOutput=append:/var/log/myapp/out.log
StandardError=append:/var/log/myapp/err.log

[Install]
WantedBy=multi-user.target
```

```bash
$ sudo systemctl daemon-reload
$ sudo systemctl enable --now myapp      # start on boot + start now
$ sudo systemctl status myapp
$ sudo systemctl restart myapp           # restart after a release
```

**Containers (Docker Compose)**

```yaml
# docker-compose.yml
services:
  app:
    build: .
    restart: unless-stopped             # restart on exit, unless stopped manually
    env_file: .env
    ports:
      - "8000:8000"
    healthcheck:
      test: ["CMD", "python", "-c", "import urllib.request; urllib.request.urlopen('http://localhost:8000/health')"]
      interval: 30s
      timeout: 3s
      retries: 3
```

**Crash site: the wrong restart policy**

```yaml
# WRONG: endlessly restarting a container that always fails
restart: always
# the app has a config error and crashes on startup -> one crash per second, 10,000 restarts
```

```text
System log:
myapp[12345]: ConfigurationError: missing DATABASE_URL
myapp[12346]: ConfigurationError: missing DATABASE_URL
myapp[12347]: ConfigurationError: missing DATABASE_URL
# infinite restart loop, CPU pinned, logs exploding
```

**Lesson**: `restart: on-failure` / `unless-stopped` is safer than `always`; pair it with `RestartSec` for backoff so it cannot restart itself to death.

## Health checks: letting the outside world know you are alive

A health check is how a load balancer or orchestrator decides whether to send you traffic. **It must be a separate, lightweight endpoint**, decoupled from business logic — a `/health` should check only whether the process itself responds, at most probing whether the most critical dependency (such as the database) is reachable.

```python
from http.server import BaseHTTPRequestHandler, HTTPServer
import json

class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        if self.path == "/health":
            self.send_response(200)
            self.send_header("Content-Type", "application/json")
            self.end_headers()
            self.wfile.write(json.dumps({"status": "ok"}).encode())
        elif self.path == "/ready":
            # readiness: only ready if the database is reachable
            db_ok = check_db()
            code = 200 if db_ok else 503
            self.send_response(code)
            self.end_headers()
        else:
            self.send_response(404)
            self.end_headers()

def check_db():
    # in a real app, run a lightweight query and return False on failure
    return True

if __name__ == "__main__":
    HTTPServer(("0.0.0.0", 8000), Handler).serve_forever()
```

The two checks have different jobs:

| Endpoint | Answers the question | Failure means |
|---|---|---|
| `/health` | is the process alive? | process is dead, restart it |
| `/ready` | can it accept traffic? | a dependency is not ready; stop traffic but do not kill me |

**Crash site: making the health check a heavy query**

```python
# WRONG: the health check runs a full-table COUNT
def health():
    rows = db.query("SELECT COUNT(*) FROM huge_table")  # 30 seconds
    return 200 if rows > 0 else 503
```

```text
The load balancer probes every 5 seconds -> the database gets hammered
# the health check itself becomes a DDoS source
```

**Lesson**: health checks must be **light** — probe liveness and critical-dependency reachability only; do no heavy operations.

## Rollback: releases always break, so you must be able to go back

A release with no rollback plan is gambling with the production environment. Rollback needs three properties: **fast, deterministic, repeatable.**

**Container-based rollback (the simplest and most reliable)**:

```bash
# publish the new version
$ docker build -t myapp:v1.2.0 .
$ docker tag myapp:v1.2.0 myapp:latest

# something goes wrong; roll back immediately
$ docker tag myapp:v1.1.0 myapp:latest
$ docker compose up -d
# back from 1.2.0 to 1.1.0, in minutes
```

**systemd rollback (with versioned directories)**:

```bash
# WRONG: editing code directly in the live directory
$ ssh server "cd /opt/myapp && git pull"
# once something goes wrong, you can only git revert, and it may conflict with newer commits
```

```bash
# RIGHT: maintain a `current` symlink; switching it is the rollback
$ ls /opt/myapp/
v1.1.0/  v1.2.0/  current -> v1.2.0

$ sudo systemctl stop myapp
$ ln -sfn /opt/myapp/v1.1.0 /opt/myapp/current
$ sudo systemctl start myapp
# rollback complete
```

**Crash site: discovering at rollback time that the previous version was not kept**

```text
v1.3.0 is released and data corruption appears
-> time to roll back
-> but the v1.2.0 image was overwritten by `docker build`
-> the only option is an emergency fix; the outage lasts 2 hours
```

**Lesson**: every released version needs a **traceable build artifact** (a tagged image, an archived source package). Rollback is not "pull the code again"; it is "switch back to the thing that was already verified."

## The pre-release checklist

This is the chapter's core deliverable and the seed of the book's closing tool. **Walk through it item by item before every release; if anything is missing, do not ship.**

- [ ] **Dependencies locked** — `requirements.txt` / `pyproject.lock` generated, versions pinned.
- [ ] **Dependency audit** — `pip-audit` passes with no known high-severity vulnerabilities.
- [ ] **Secrets out of the repo** — `.env`, secrets, and tokens are gitignored; everything goes through environment variables or a KMS.
- [ ] **Configuration externalized** — every environment-specific setting is injected via environment variable or config file.
- [ ] **Tests pass** — `pytest` is fully green, with critical paths covered.
- [ ] **CI passes** — automated checks (lint, tests, security scan) all green.
- [ ] **Code review complete** — at least one review and approval.
- [ ] **Logs compliant** — `logging` with a structured format, sensitive data redacted, request IDs attached.
- [ ] **Health checks ready** — `/health` and `/ready` endpoints available.
- [ ] **Process managed** — systemd / Compose / K8s config present, with the correct `restart` policy.
- [ ] **Monitoring and alerting** — logs collected, with alerts on error rate, latency, and resource usage.
- [ ] **Rollback plan** — the previous version's image/package is retained, and the rollback steps have been rehearsed.
- [ ] **Database migration** — backed up, with forward and rollback scripts, validated in staging first.
- [ ] **Docs in sync** — README, CHANGELOG, and operations manual updated.
- [ ] **Rollout plan** — whether to validate with a small slice of traffic first, then ramp to 100%.

**Crash site: skipping the checklist to make a release**

```text
PM: we have to ship today; the checklist can wait.
Dev: (uneasy) okay.
-> 20 minutes after release: 500 errors everywhere
-> investigation: forgot to set the DATABASE_URL environment variable
-> rollback: no previous-version image was kept
-> total downtime: 3 hours 42 minutes
```

**Lesson**: a checklist looks tedious, but it exists to fight **collective amnesia under time pressure. The more urgent the release, the more strictly you follow the checklist.**

## Summary

- The gap from "runs locally" to "runs in production": managed processes, auto-restart, externalized config, probeable health.
- Host processes with systemd or an orchestrator; use `on-failure` / `unless-stopped` for restart policy.
- Health checks split into `/health` (liveness) and `/ready` (readiness), both kept light.
- Rollback must be fast, deterministic, and repeatable, relying on build artifacts for every version.
- Walk the release checklist item by item; it is the last line of defense against omissions under pressure.
