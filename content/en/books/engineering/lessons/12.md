# Writing Good Commit Messages: "fix" Is Not Information

> Six months from now you will search 5,000 commits for "the one that changed the login timeout." You run `git log --grep="fix"` and get 800 hits. A commit message is an index you build for your future self — `fix` is not an index.

## Why "fix" Says Nothing

`git log` is the project's **behaviour log**. A good commit message tells you what happened to the project without you having to read the diff.

```bash
$ git log --oneline
f3a1b2c fix
e8d7c6b update
a9b8c7d tweaked something
d2e3f4a fix bug
```

These four messages provide **zero information**. You know something changed, but not what, why, or where it mattered.

**Crash Site: relying on commit messages to investigate a production incident**

```bash
$ git log --oneline --since="2024-01-01" | grep -i fix
a1b2c3d fix
d4e5f6g fix login
h7i8j9k fix bug
```

When production breaks, the on-call engineer must figure out "which version introduced this." A history full of `fix` is no history at all — the only recourse is to revert versions one by one.

## An Introduction to Conventional Commits

[Conventional Commits](https://www.conventionalcommits.org/) is a lightweight convention. Its format:

```text
<type>(<scope>): <subject>

<body>

<footer>
```

**Type** is the heart of the convention:

| Type | Meaning |
|---|---|
| `feat` | A new feature |
| `fix` | A bug fix |
| `docs` | Documentation only |
| `style` | Formatting, missing semicolons, etc. (no logic change) |
| `refactor` | Refactoring (neither a bug fix nor a feature) |
| `perf` | Performance improvement |
| `test` | Adding or changing tests |
| `chore` | Build, dependencies, tooling — the odds and ends |
| `build` | Changes to the build system or external dependencies |

**Good examples:**

```text
feat(auth): support SMS-code login

Adds a phone-number + verification-code entry point on the login page,
reusing the existing session-management logic. The code is valid for
5 minutes; after 5 consecutive failures the account is locked for 15.

Closes #123
```

```text
fix(payment): raise the timeout that caused sporadic failures

The 3-second timeout fired frequently under load; raised to 10 seconds
with exponential-backoff retries.
```

```text
refactor(utils): extract the date-formatting function into its own module

No logic changes; code was only relocated.
```

**Format essentials:**

- The subject stays under 72 characters (so `git log --oneline` shows it完整 in a terminal).
- The subject uses the imperative mood ("add", not "added"; "fix", not "fixed").
- The body explains **why** (background, motivation, trade-offs), not the what (the diff already shows the what).
- Leave a blank line between the subject and the body.

**Crash Site: the subject line reads like a novel**

```text
fix: I tweaked that login issue Alice mentioned earlier that sometimes
fails, then I found the timeout was too short, I tested it locally
a bunch of times, asked Bob and he thought 10 seconds was about right,
so I changed it to 10, and by the way I also touched ...
```

Two hundred characters in the subject, the body is a diary. Anyone running `git log --oneline` sees nothing (it gets truncated); anyone reading the body drowns in noise.

## The Value of a Scope

The `auth` in `feat(auth)` is the scope — it tells you which module changed. In a multi-module project this is an invaluable filter:

```bash
$ git log --oneline | grep "payment"
$ git log --oneline --grep="payment"
```

Without a scope you can only guess at keywords. With one, filtering is deterministic.

## Summary

- Messages like `fix` carry zero information: not searchable, not locatable.
- Conventional Commits: `type(scope): subject` + body.
- The type expresses intent (feat/fix/refactor/docs/...).
- The subject uses the imperative mood and stays under 72 characters.
- The body explains why, never what (the diff is already the what).
- The scope is a module name and a reliable filter dimension.

## In-Class Exercise

```quiz
type: choice
q: Which commit message best follows the Conventional Commits convention?
options:
- fix: I fixed that login thing
- fix(auth): restore the typed input on failed login
- update: changed some stuff
- feat: new feature
answer: 1
explain: "fix(auth): restore the typed input on failed login" has a clear type (fix), an accurate scope (auth), and a subject that plainly states what changed. The others lack a scope or have a vague subject.
```

```quiz
type: choice
exam: true
q: Regarding what belongs in the commit-message body, which is correct?
options:
- The body should narrate line by line what code changed, mirroring the diff
- The body should explain why the change was made (context, motivation, trade-offs), not duplicate the diff
- The longer the body the better; more detail means more professional
- A subject is enough; the body is unnecessary
answer: 1
explain: The body's value is recording the "why" that the diff cannot show — the context, rationale, and trade-offs at the time. Restating code changes (the what) is redundant because git show already reveals it.
```
