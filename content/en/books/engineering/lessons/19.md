# Coverage: 100% Does Not Mean Bug-Free

> The report says "100% coverage" and you feel good. The next day production reports a bug: an empty-string username crashes everything. Coverage measures "was this code executed," not "was this code verified correct." Reading coverage means looking at **which line is not covered**, not staring at the percentage.

## What coverage actually measures

Line coverage answers one question: was each line of code **executed at least once**? It does not answer "did it produce the right result?"

```python
def divide(a, b):
    if b == 0:
        raise ValueError("cannot divide by zero")
    return a / b

# The test
def test_divide():
    assert divide(6, 3) == 2
```

This test drives `divide`'s coverage close to 100% — the normal branch runs — but it never touches the `b == 0` exception branch. Any caller passing `b=0` crashes, and you never knew.

## How to measure coverage

Use the `coverage` tool with pytest to generate a report:

```bash
# install
$ pip install coverage

# run the tests and collect coverage
$ coverage run -m pytest tests/

# terminal report
$ coverage report -m
Name                Stmts   Miss  Cover   Missing
-------------------------------------------------
src/calculator.py      28      3    89%   42, 57-58
src/parser.py          40      0   100%
-------------------------------------------------
TOTAL                  68      3    96%

# HTML report: open it in a browser to see exactly which lines were hit
$ coverage html
$ open htmlcov/index.html
```

The `-m` flag lists the **uncovered line numbers** in the `Missing` column, which is the most valuable part of the report.

## Why 100% coverage is not bug-free

**Counterexample 1: code ran, but nothing was asserted**

```python
def withdraw(balance, amount):
    if amount > balance:
        raise ValueError("insufficient funds")
    return balance - amount

def test_withdraw():
    withdraw(100, 30)    # called, no assertion
    withdraw(50, 100)    # called, no assertion
```

Coverage is 100%, but nothing is verified. If the function returns `None`, the tests still go green.

**Counterexample 2: boundaries were never tested**

```python
def get_discount(total):
    if total >= 1000:
        return 0.2
    elif total >= 500:
        return 0.1
    return 0

def test_get_discount():
    assert get_discount(500) == 0.1
```

Only `500` was tested. The boundaries `499` (returns 0) and `1000` (returns 0.2) were never touched. Full coverage, boundary bug still present.

**Counterexample 3: exception paths were never tested**

```python
def load_config(path):
    try:
        with open(path) as f:
            return json.load(f)
    except FileNotFoundError:
        return {"default": True}
```

Only the "file exists" path is tested, so the exception branch is uncovered. In production, when the config file is missing, that behavior was never validated.

**Crash site: coverage used as a KPI**

```text
Boss: coverage must stay above 90% or we do not merge.
Dev: writes assertion-free tests, tests getters/setters, tests one-line return functions.
Result: 92% coverage, zero validation of core business logic.
```

The moment coverage becomes a hard metric, people game it — and that is not coverage's fault, it is the wrong target being measured.

## What to actually look at

| Look at this | Not just this |
|---|---|
| Which **important functions/modules** are uncovered | The single overall percentage |
| The exact line numbers in the `Missing` column | Whether the number is an integer |
| Whether both branches were taken (`--branch`) | How many tests you have |
| Exception paths and boundary values | Whether you hit 100% |

Branch coverage:

```bash
$ coverage run --branch -m pytest tests/
$ coverage report -m
Name                Stmts   Miss Branch BrPart  Cover   Missing
----------------------------------------------------------------
src/calculator.py      28      0     12      1     97%   42->45
```

`BrPart` is "partial branch coverage": that `if` took the True side but not the False side (or vice versa). `42->45` tells you that line 42's False branch was never taken.

**The right use**: treat coverage as a **tool for finding blind spots**, not a **quality certificate**. When the `Missing` column points at lines of core business logic, write a test. For code that genuinely cannot be covered (defensive fallbacks, platform-specific branches), keep it in mind and move on.

## A sensible coverage target

Do not pin a number. A more reasonable approach:

- Core business modules and calculation logic: **as high as you can** (above 90%).
- Glue code, CLI argument parsing, framework-generated code: you can relax the bar.
- **Incremental coverage** (diff coverage) of newly added code makes a much better PR gate than a blanket 90% rule.

Some teams use `diff-cover` to check only the lines changed in a PR, which maps better to how real work gets done than an all-up 90% threshold.

## Summary

- Coverage measures "this code was executed," not "this code is correct."
- Measure with `coverage run -m pytest` plus `coverage report -m`.
- `--branch` reveals "took the if but not the else" partial coverage.
- 100% coverage can still miss: assertion-free tests, untested boundaries, and untaken exception paths.
- Do not turn coverage into a KPI — it incentivizes pointless tests.
- The `Missing` column and uncovered branches are worth more than the headline percentage.

## In-class exercise

```quiz
type: choice
q: Your coverage report shows 100%, but a core function has an obvious boundary bug (it returns the wrong value for an input of 0). What is the most likely cause?
options:
- The coverage tool's statistics are inaccurate.
- The tests only prove the code was executed; they never asserted the boundary values, or never tested boundary inputs at all.
- The function is fine and the report is wrong.
- You need to upgrade the coverage tool to the latest version.
answer: 1
explain: 100% coverage only means every line ran, not that the result was correct. If the tests never asserted boundary values (0, None, empty string), the boundary bug stays hidden. This is the most common misunderstanding of coverage.
```
