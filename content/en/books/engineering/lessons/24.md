# Documentation: README, CHANGELOG, and Design Docs

> Finishing the code is not the finish line. The moment someone else — including you, three months from now — can read it, run it, and change it without fear, that is delivery. Documentation is the part most often skipped and most often complained about. A good README gets a newcomer running in ten minutes; a bad README leaves a decent project untouched.

## What a README should contain

The README is the front door of your project, the first thing anyone sees when they open the repository. A solid open-source README has these sections, in order:

1. **Project introduction**: one sentence on what it does, what problem it solves, and who it is for.
2. **Installation**: the complete path from zero to running, including the Python version, dependency installation, and any system-level dependencies.
3. **Quick start / usage example**: the smallest runnable example, ideally copy-pasteable.
4. **Configuration**: environment variables, config files, what the user must supply.
5. **Basic usage**: common operations, CLI flags, API entry points.
6. **How to contribute**: branch conventions, the PR flow, code style, whether to open an issue first.
7. **Testing and development**: how to run tests and set up a dev environment.
8. **License**: which license you chose.

A short skeleton:

```markdown
# Project name

One-sentence introduction.

## Installation

    python -m venv .venv && source .venv/bin/activate
    pip install -r requirements.txt

## Quick start

    python app.py --input data.csv --output result.json

## Configuration

Set the environment variables `DATABASE_URL` and `API_KEY` (see `.env.example`).

## How to contribute

1. Fork and create a branch.
2. Run the tests: pytest.
3. Submit a PR.

## License

MIT
```

## Why "a README that does not run" is the most common problem

The biggest failure of a README is not that it is short, but that **it is wrong and cannot be executed**. Typical symptoms:

- It says `pip install` but never mentions the Python version, so 3.8 fails.
- A command fails when copied verbatim: wrong path, a missing virtualenv activation step, dependencies in the wrong order.
- It references a config file that does not exist in the repo and gives no format.
- The quick start uses an API that was deleted years ago.
- After installing, nobody knows what command to run next.

```text
Newcomer log:
$ git clone <repo>
$ pip install -r requirements.txt
ERROR: Could not find a version that satisfies the requirement django==5.0
# the README never mentioned needing Python 3.10+
```

**Why this is fatal**: when a user, a colleague, or your future self clones the repo and cannot get it running, they usually try two or three times and then give up. A README that does not run locks out potential users and your future self, regardless of code quality.

**Crash site: writing the README as a "done" list and forgetting it**

```text
# WRONG: the README was never updated after a refactor
Current repo: the entry point moved from app.py to cli.py, and --file became --input
README still says:
    python app.py --file data.csv
```

```text
Feedback:
issue #47: following the README, app.py is not found — did the structure change?
issue #48: --file errors out; is the doc wrong or is the command wrong?
```

**Consequence**: when documentation and code diverge, the first impression is "this project is unmaintained," and trust collapses. The README is part of the code; changing the API means updating the docs.

## What a CHANGELOG is for

A CHANGELOG is a user-facing record of changes, listed in reverse version order: what changed in each version. It is not a git log — a git log is "what I committed on which day" for developers; a CHANGELOG is "what you get by upgrading to 1.3.0, and what to watch out for" for users.

The common format (Keep a Changelog style):

```markdown
# Changelog

## [1.3.0] - 2026-09-20
### Added
- New export_csv() function.
- Configurable timeout through an environment variable.

### Changed
- import_json() now accepts an optional encoding argument.

## [1.2.4] - 2026-08-15
### Fixed
- Crash on an empty input file.

## [1.2.3] - 2026-07-02
### Removed
- Deleted the deprecated old_api() (deprecated since 1.0).
```

The standard categories: `Added`, `Changed`, `Deprecated`, `Removed`, `Fixed`, `Security`.

**What a CHANGELOG does**:

- Tells users whether to upgrade and whether to change their code (combined with SemVer to spot breaking changes).
- Lets maintainers look back at the project's evolution instead of wondering "what did I actually change?"
- Makes it possible to pinpoint which version introduced a problem.

**Crash site: using the git log as a CHANGELOG**

```text
# WRONG: the contents of CHANGELOG.md
## Changes
- fix bug
- update
- WIP
- changed some stuff
- merge master
```

**Consequence**: unreadable, which means useless. A CHANGELOG must describe "things that matter to the user," not your commit habits.

## When a design document is warranted

Not every piece of code needs a design document. The test is: **if this decision is wrong, how expensive is the rewrite?**

Worth writing down:

- Introducing a new core abstraction or architecture (splitting a monolith into modules).
- Choosing a stack or a third-party dependency (why A and not B).
- Designing a public API or a data format (every caller is affected).
- Large changes that touch many modules or many people.
- Key designs around performance or security.

Not worth a design document:

- Changing a function's internal implementation.
- Fixing a bug or adding a test.
- Refactoring internals while the interface stays the same.

A design document usually covers: **background and goals / options compared / the chosen approach / impact / risks and alternatives / a deprecation plan**. It does not need to be long — a few pages of markdown is enough. The point is to let reviewers see your reasoning and trade-offs.

**Crash site: write the code first, document it after**

```text
# WRONG workflow
1. Spend two weeks building a big feature, then open a 3000-line PR.
2. Review comes back: why Redis and not a database?
3. Defend the design by drawing diagrams on the spot.
4. Finally, you are asked to write the design document.
```

```text
Review comment:
"The approach is workable, but why a message queue instead of a cron job? That should have been settled before the implementation."
```

**Consequence**: the rewrite cost is enormous. A design document's value is in **exposing disagreement early**, not in defending the code afterward.

## Summary

- A README is the front door: introduction, install, quick start, configuration, usage, contribution, testing, license — none missing.
- "Does not run" is the deadliest README failure: commands must be copy-pasteable, versions explicit, configuration complete.
- Changing code means updating the README; documentation is part of the code.
- A CHANGELOG is for users: versioned, reverse-order, explaining what changed and what to watch for.
- A design document belongs on decisions whose failure is expensive; its job is to surface disagreement early.

## In-class exercise

```quiz
type: choice
q: You refactored a project, moving the entry point from app.py to cli.py and changing the arguments. How should the README and CHANGELOG be handled?
options:
- Leave the README alone since the code still runs; skip the CHANGELOG because users cannot see internal changes.
- Only update the CHANGELOG; nobody reads the README anyway.
- Update the install and quick-start examples in the README, and record this change under the corresponding version in the CHANGELOG (mark it breaking if the interface changed).
- Delete the README and rewrite it from scratch because the old content is outdated.
answer: 2
explain: Docs are part of the code; changing the interface requires updating the README, otherwise users following the old docs will error out. The CHANGELOG records changes so users can judge the impact of upgrading. You do not need to delete and rewrite it, just update the affected parts.
```

## Lesson quiz

```quiz
type: choice
exam: true
q: Which statement about READMEs and CHANGELOGs is correct?
options:
- The README is for developers only and users do not need it; the CHANGELOG is just an alias for the git log.
- The README must let someone copy and paste commands into a working state (install, use, configure, contribute, license); the CHANGELOG is a user-facing, reverse-order record of what changed in each version.
- A README only needs a one-line project name; everything else is extra.
- A CHANGELOG should only record Fixed items; Added and Changed do not matter.
answer: 1
explain: The README is the front door and must get the user running; the CHANGELOG is aimed at users, documenting each version's changes across Added/Changed/Fixed/Removed and others — not a git log.
```
