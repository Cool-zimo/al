# Mocks and Monkey-Patching: Isolate External Dependencies, but Do Not Mock Everything

> Your function makes an HTTP request, queries a database, and reads the system clock. Without mocks, your tests need the network, a running database, and a clock you cannot control — so they are slow and flaky. A mock is "a stand-in that replaces the real object." But over-mock and you stop testing real behavior and start testing the stand-in.

## Why mock at all

Three kinds of dependency must be isolated:

**1. Uncontrollable dependencies** — network requests, third-party APIs, the system clock. You do not own them, and you cannot guarantee they are online or returning consistent results.

**2. Side-effecting dependencies** — sending email, charging a card, writing a file. You cannot actually send an email on every test run.

**3. Slow dependencies** — a real database call takes dozens of milliseconds; times 1,000 tests, that is half a minute.

**Crash site: a test that really makes an HTTP request**

```python
# WRONG
import requests

def get_user_name(user_id):
    resp = requests.get(f"https://api.example.com/users/{user_id}")
    return resp.json()["name"]

def test_get_user_name():
    assert get_user_name(1) == "Alice"     # needs the network and a live service
```

```text
$ pytest tests/test_user.py
E   requests.exceptions.ConnectionError: ...
```

Every now and then CI's network jitters and the test fails at random. And this test is checking "is the network up," not "is my code correct."

**The fix: mock `requests.get` and verify how it was called**

```python
from unittest.mock import patch

def get_user_name(user_id):
    resp = requests.get(f"https://api.example.com/users/{user_id}")
    return resp.json()["name"]

@patch("requests.get")
def test_get_user_name(mock_get):
    # Build the stand-in return value: make resp.json() return the given dict
    mock_get.return_value.json.return_value = {"name": "Alice"}
    mock_get.return_value.status_code = 200

    result = get_user_name(1)

    assert result == "Alice"
    # Also verify: the correct URL was requested, with the right argument
    mock_get.assert_called_once_with("https://api.example.com/users/1")
```

Now the test depends only on `get_user_name`'s logic, not on the network.

## monkeypatch: swapping objects in a module

pytest's built-in `monkeypatch` fixture is designed for temporarily replacing attributes, environment variables, and dict entries, then restoring them automatically when the test ends.

```python
import os
import time

def is_promotion_period():
    return time.localtime().tm_mon == 11  # November is promotion month

def get_db_url():
    return os.environ.get("DATABASE_URL", "sqlite:///default.db")

def test_promotion_in_november(monkeypatch):
    # Replace time.localtime with a fake that reports "November"
    class FakeTime:
        tm_mon = 11
    monkeypatch.setattr(time, "localtime", lambda: FakeTime())
    assert is_promotion_period() is True

def test_default_db_url(monkeypatch):
    monkeypatch.delenv("DATABASE_URL", raising=False)
    assert get_db_url() == "sqlite:///default.db"

def test_custom_db_url(monkeypatch):
    monkeypatch.setenv("DATABASE_URL", "postgres://prod:5432/app")
    assert get_db_url() == "postgres://prod:5432/app"
```

The advantage of `monkeypatch` is **automatic restoration**: when the test ends, the patched attribute is restored, so it cannot pollute other tests.

## When NOT to mock

Mocking has a cost. In these three cases it makes things worse.

**1. Do not mock your own business code**

```python
# WRONG: mocking the very function you are supposed to test
@patch("mymodule.calculate_total")
def test_checkout(mock_calc):
    mock_calc.return_value = 100
    assert checkout(["a", "b"]) == 100   # nothing is actually tested
```

You replaced `calculate_total` with "always return 100," so the test verifies that 100 equals 100. **When the function under test and the mocked function are part of the same business logic, you have skipped the real logic.**

**2. Do not over-mock into tight coupling with the implementation**

```python
# WRONG: mocking internal methods; the whole suite breaks on rename
@patch("mymodule.Order._validate_items")
@patch("mymodule.Order._check_inventory")
@patch("mymodule.Order._deduct_balance")
@patch("mymodule.Order._write_to_db")
def test_create_order(m1, m2, m3, m4):
    Order.create()
    m4.assert_called_once()     # rename a method and this dies instantly
```

This kind of test nails down internal implementation details. When you refactor — renaming a method while preserving behavior — every test goes red. **Stop mocking at the module boundary; never mock private methods.**

**3. Do not let mocks replace integration tests**

A mock proves "I called the dependency the way I intended." It does **not** prove "the dependency actually works." The request was shaped correctly, but you will never notice that the other side changed its response field. That kind of integration correctness needs real integration tests (a real database, a real local service).

**Crash site: all mocks green, production on fire**

```python
@patch("requests.get")
def test_fetch_profile(mock_get):
    mock_get.return_value.json.return_value = {"nickname": "Tom"}
    assert fetch_profile(1) == "Tom"    # test passes

# After release: the real API returns "display_name" instead of "nickname"
# The whole suite is green, production raises KeyError
```

**The fix: cover key external integrations with integration or contract tests**; mocks stay at the unit level.

## The mock decision table

| Scenario | Should you mock? |
|---|---|
| A third-party HTTP API | yes |
| System time, random numbers | yes |
| Sending email, charging a card, SMS | yes |
| Your own business-logic function | no |
| Private methods, internal implementation details | no |
| A database (in an integration test) | no |
| A database (in a unit test, when the function should not touch the DB directly) | yes — but you still need an integration test separately |

**One line: mock dependencies, never the object under test; mock boundaries, never internals.**

## Summary

- Mocks isolate uncontrollable, side-effecting, and slow external dependencies.
- `unittest.mock.patch` replaces objects; `mock.return_value` sets the return value.
- pytest's `monkeypatch` fixture replaces attributes and environment variables, then restores them.
- Do not mock your own business code, private methods, or database integration logic.
- Mocks only prove "the call was shaped right"; they do not prove "the integration works" — that needs integration tests.
- Rule of thumb: mock dependencies, not the object under test; mock boundaries, not internals.

## In-class exercise

```quiz
type: choice
q: You used @patch to mock three private methods inside a function, and the tests pass. Later you refactor the implementation (rename methods, merge some), keeping the behavior identical, and every test fails. Where is the problem?
options:
- Too many test methods; you should reduce the number of tests.
- The mocks nailed down internal implementation details, so the tests are tightly coupled to that implementation and necessarily break on refactor.
- The mock itself has a bug.
- You should have used a session-scoped fixture instead of a mock.
answer: 1
explain: Over-mocking internal methods binds the tests to a specific implementation. Mocks should stop at the module boundary, so internal refactors do not invalidate the suite. This is the classic misuse of mocking.
```

```quiz
type: choice
exam: true
q: In which scenario is mocking the best fit?
options:
- Verifying that your own order-amount calculation function is correct.
- Testing whether a function that calls a payment gateway to charge a card passes the correct amount and order number.
- Verifying that a row inserted into the users table can be queried back out.
- Verifying that your own JSON-parsing logic is robust.
answer: 1
explain: A payment gateway is an external dependency with real side effects and no guarantees, so mocking it and asserting the call arguments is appropriate. Amount calculation and JSON parsing are your own logic and should be tested directly; inserting and querying a database is integration correctness, tested with a real database rather than mocks.
```
