# Beyond pip: uv and the Modern Toolchain

> Running `pip install` makes you wait half a minute, then watch ten dependencies download one by one. Three people on the team end up with three different environments. The modern Python toolchain attacks exactly two pains — *slow* and *inconsistent* — and uv is the fastest runner in that race.

## Why pip Is Slow

pip is Python's official package installer: stable and reliable, but slow. The slowness lives in two places:

1. **Dependency resolution** — given a list of requirements, pip must find mutually compatible versions for every package. That solver runs in Python, and on a complex project it can take tens of seconds.
2. **Installation** — download the wheel, unpack it, compile it (if no prebuilt wheel exists), and copy it into `site-packages`. Packages are processed one at a time.

Neither bottleneck is pip being lazy; both are consequences of its design. So the community built faster tools.

## Why uv Is Fast

[uv](https://github.com/astral-sh/uv) is a Python package manager and project manager written in Rust by Astral — the same team behind Ruff. Its headline is speed: official benchmarks put it 10–100× faster than pip.

Where the speed comes from:

- **Dependency resolution in Rust** — the same solving problem finishes in milliseconds instead of tens of seconds.
- **Parallel downloads and installs** — unlike pip's serial pipeline.
- **A global package cache** — different projects share one cache directory, so an already-downloaded package is never fetched twice.
- **Built-in virtual environment management** — no need to `python -m venv` first and then activate.

```bash
# Install uv (once)
$ curl -LsSf https://astral.sh/uv/install.sh | sh

# Scaffold a project (creates the environment and pyproject.toml at once)
$ uv init myproject
$ cd myproject

# Add a dependency (creates .venv, installs the package, and writes to pyproject.toml)
$ uv add requests pandas

# Run a script (runs inside .venv automatically)
$ uv run main.py
```

Notice that `uv add requests` creates `.venv`, installs the package, and records the dependency in `pyproject.toml` — three steps collapsed into one.

## Command Comparison

| Task | pip + venv | uv |
|---|---|---|
| Create an environment | `python3 -m venv .venv` | `uv venv` |
| Activate | `source .venv/bin/activate` | activate after `uv venv`, or skip activation with `uv run` |
| Install a package | `pip install requests` | `uv pip install requests` or `uv add requests` |
| Install from a list | `pip install -r requirements.txt` | `uv pip install -r requirements.txt` |
| Initialise a project | Create files by hand | `uv init` |
| Run a script | `python main.py` after activation | `uv run main.py` |
| Add a dev dependency | Maintain a dev group by hand | `uv add --dev pytest` |
| Lock file | `pip-tools compile` | `uv lock` (automatic) |

## The Trade-offs of uv

**When to use uv:** new projects, personal projects, situations where install speed matters, and teams that want an all-in-one toolchain. Its ecosystem is the most active today, and it is broadly seen as the direction of travel.

**When not to use it:** maintaining a legacy project whose team already runs pip + requirements.txt, where migration buys nothing; or CI environments so constrained that a Rust-compiled tool cannot be installed. Tools are a means; stable delivery is the goal.

**Crash Site: mixing pip and uv produces an inconsistent environment**

```bash
$ uv venv
$ source .venv/bin/activate
(.venv) $ uv add requests
(.venv) $ pip install pandas
(.venv) $ uv lock
# uv's lock file contains only requests, because it tracks only what it installed
```

**Consequence:** `uv.lock` has no `pandas` entry, so when a colleague rebuilds from the lock file the environment is missing pandas. The same environment, managed by two tools, will always drift.

**The rule is simple: one project, one package manager.** All pip or all uv — never both.

## pip-tools: the Middle Road

If you want reproducible builds without changing tools, `pip-tools` is the answer:

```bash
# requirements.in holds the direct dependencies
$ cat requirements.in
requests>=2.28
pandas>=2.0,<3.0

# compile generates a lock file
$ pip-compile requirements.in
# outputs requirements.txt with every transitive dependency and its exact version

# sync installs strictly from the lock file
$ pip-sync requirements.txt
```

`pip-sync` is stricter than `pip install -r`: it **uninstalls** anything absent from the list, guaranteeing a clean environment.

## Summary

- pip is slow at dependency resolution (a Python solver) and serial installation.
- uv reimplements both in Rust, gaining a 10–100× speed improvement.
- uv also manages environments, project structure, and lock files — an integrated toolkit.
- One project, one package manager; never mix.
- If you will not switch tools, use pip-tools for reproducible builds.

## In-Class Exercise

```quiz
type: choice
q: Your team project has run on pip + venv for a year and works perfectly. You now want to introduce uv. Which approach is most reasonable?
options:
- Migrate the whole project to uv immediately and rewrite every script
- Use uv for new projects and keep the old one on pip, each staying consistent
- Alternate between uv and pip in the same project, using whichever is faster
- Use uv only to create environments and keep installing packages with pip
answer: 1
explain: Tool migration has no free payoff. Leave a stable legacy project alone and try a modern tool on new work. Mixing two tools inside one project causes inconsistent dependency tracking, which is exactly what to avoid.
```
