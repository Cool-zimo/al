# Logging and Observability: What Tells You Something Is Wrong in Production

> `print` is fine for local development; it is not fine for production. Bugs in production disappear in an instant, and what you need is **searchable, traceable logs that can reconstruct one request end to end**. This lesson covers how to log, what to log, and **what must never be logged**.

## Why print is not enough

`print` is a great helper during development, but in production it has three fatal flaws:

1. **No levels** — there is no way to tell whether this is debug info or a fatal error; it all blends together.
2. **No context** — you know "something failed," but which request, which user, what parameters? Nobody knows.
3. **Not searchable** — once the log volume grows, reading text by eye is the same as not logging at all.

When production breaks, your investigation path is: **alert → locate the service → filter logs by time or request ID → reconstruct what happened.** Every step of that path depends on structured, contextual logs.

Python's standard library ships `logging`, which is enough — no extra install required:

```python
import logging

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s [%(levelname)s] %(name)s: %(message)s",
)
logger = logging.getLogger(__name__)

logger.debug("debug info, hidden by default in production")
logger.info("service started")
logger.warning("config file missing, using defaults")
logger.error("database connection failed: %s", err)
```

## Structured logs: only machine-readable logs are useful

"A line of plain text" is comfortable for human eyes but hard for machines to parse. Structured logs (typically one JSON object per line) have one big advantage: **you can filter, aggregate, and graph them by field.**

```python
import json, logging

class JsonFormatter(logging.Formatter):
    def format(self, record):
        payload = {
            "ts": self.formatTime(record),
            "level": record.levelname,
            "logger": record.name,
            "msg": record.getMessage(),
        }
        # also carry extra fields like user_id and request_id
        for k, v in record.__dict__.items():
            if k not in payload and not k.startswith("_"):
                payload[k] = v
        return json.dumps(payload, ensure_ascii=False)

handler = logging.StreamHandler()
handler.setFormatter(JsonFormatter())
logger = logging.getLogger("app")
logger.addHandler(handler)
logger.setLevel(logging.INFO)

logger.info("user login", extra={"user_id": 42, "ip": "127.0.0.1"})
```

Output:

```text
{"ts": "2026-09-29 10:00:00,123", "level": "INFO", "logger": "app", "msg": "user login", "user_id": 42, "ip": "127.0.0.1"}
```

**Crash site: cramming everything into the message string**

```python
# WRONG: all the information is mushed into one string; filtering by user_id later is impossible
logger.info(f"user {user_id} login from {ip} with token {token}")
```

```text
To find "every log where user_id=42" you would have to regex the raw text
# and the token was logged anyway (see the next section)
```

**The fix**: pass structured fields via `extra={}` and put only the event name in the message. "Filter by user_id" then becomes an exact query instead of a full-text regex.

## The red line: what must never be logged

This is the most important rule in the lesson. **Logs land in files, centralized log systems, and backups, and may be seen by many people** — once a password, token, or secret is written in, it is a second leak.

```python
# WRONG: logging a password
logger.info(f"login failed for user={name} password={password}")
# WRONG: logging a token
logger.info(f"calling api with token={api_key}")
# WRONG: logging full ID numbers / phone numbers
logger.info(f"user id_card={id_card} phone={phone}")
```

```text
Consequences:
- log files sit on disk; anyone who can read the server can see them
- centralized logs (ELK and the like) are kept for 30+ days, widening the leak window
- backups, monitoring screenshots, and alert notifications can all carry sensitive fields
```

**The fix**: log only redacted information — enough to diagnose the issue, nothing more.

```python
import re

SENSITIVE_KEYS = {"password", "passwd", "token", "api_key", "secret", "authorization"}

def sanitize(record):
    """Redact a dict payload, returning a new dict without mutating the original."""
    if not isinstance(record, dict):
        return record
    out = {}
    for k, v in record.items():
        if k.lower() in SENSITIVE_KEYS:
            out[k] = "***"
        else:
            out[k] = v
    return out

# usage
payload = {"user": "alice", "password": "s3cret", "token": "tk_123"}
logger.info("auth attempt", extra=sanitize(payload))
# in the output, password and token become ***
```

**Crash site: redacting password but forgetting token**

```python
def log_auth(user, pwd, token):
    safe = {"user": user, "pwd": "***"}   # only pwd was handled
    logger.info("auth", extra=safe)
    # the token was concatenated somewhere else
    logger.info(f"token used: {token}")    # leaked
```

```text
Compliance audit:
1 unredacted sensitive field found -> the whole log batch needs cleanup + secret rotation
```

**Lesson**: redaction must **cover every known sensitive field name** and be applied uniformly, not written ad hoc as "mask this one here." Compare field names case-insensitively, so `Token` / `TOKEN` cannot slip through.

## Request IDs: stitching one request together

A user request crosses many functions and services, and hundreds of requests may be handled concurrently. **Scrolling through logs by timestamp will never reconstruct one request's full path** — you need a `request_id` that stays with it from start to finish.

```python
import uuid, logging, contextvars

# contextvars (Python 3.7+) is the context variable that isolates across async / threads
request_id_var: contextvars.ContextVar[str] = contextvars.ContextVar("request_id")

class RequestIdFilter(logging.Filter):
    def filter(self, record):
        record.request_id = request_id_var.get("unknown")
        return True

logger = logging.getLogger("app")
logger.addFilter(RequestIdFilter())

def handle_request(user_input):
    request_id_var.set(str(uuid.uuid4())[:8])
    logger.info("request start", extra={"input_len": len(user_input)})
    result = process(user_input)          # any log anywhere inside carries request_id
    logger.info("request done", extra={"result_len": len(result)})
    return result

def process(data):
    logger.info("processing step1")       # automatically tagged with request_id
    return data.upper()
```

Output:

```text
2026-09-29 10:00:00 [INFO] app: request start | request_id=a1b2c3d4 input_len=5
2026-09-29 10:00:00 [INFO] app: processing step1 | request_id=a1b2c3d4
2026-09-29 10:00:00 [INFO] app: request done | request_id=a1b2c3d4 result_len=5
```

**Crash site: using a thread-local variable as the request ID carrier in an async environment**

```python
# WRONG: threading.local() does not isolate by coroutine under asyncio
import threading
_local = threading.local()

async def handle():
    _local.rid = uuid.uuid4()
    await fetch()              # switches to another coroutine; rid may be overwritten
    logger.info("done")        # request_id is now cross-contaminated
```

```text
Resulting logs:
request_ids are mixed up across concurrent requests; there is no way to diagnose anything
```

**The fix**: in Python 3.7+, use `contextvars.ContextVar` — it is designed for async contexts and correctly isolates each coroutine or request.

## What to log, what not to log: a quick reference

| Log this | Not this |
|---|---|
| event name, timestamp, level | passwords, tokens, API keys |
| request_id, user_id (redacted) | full ID numbers, phone numbers, card numbers |
| input length / type, never the raw content | large request bodies verbatim (unless necessary and redacted) |
| duration, status code, error type | sensitive values inside stack traces |
| target service name for external calls | internal network topology details (security) |

**The golden rule**: logs exist to **reproduce and locate a problem**, not to store business data. Log enough to diagnose, and no more.

## Summary

- `print` has no levels and no context; production must use `logging`.
- Structured (JSON) logs can be filtered, aggregated, and graphed by tools.
- Sensitive information (passwords, tokens, keys) **must never enter logs**; apply uniform redaction.
- A request ID carried through every log line is the key to tracing distributed or concurrent problems.
- Use `contextvars` rather than thread-local storage to carry request context.
- Log only as much as needed to diagnose; do not use logs as a business database.
