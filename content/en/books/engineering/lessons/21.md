# Semantic Versioning: When to Bump major, minor, and patch

> You made a small change and bumped the version from 1.2.3 straight to 2.0.0. Every project that depends on yours is now forced to check for a breaking change. A version number is not a counter that goes up whenever you feel like it; it is a **contract with your users**. Seeing 1.3.0 tells them it is safe to upgrade; seeing 2.0.0 tells them to expect code changes.

## When each segment goes up

Semantic Versioning (SemVer) uses the format `MAJOR.MINOR.PATCH`, for example `2.13.7`.

**PATCH** — a **backward-compatible bug fix**. No interface changes, no semantic behavior changes, just a bug fixed.

```text
1.2.3 → 1.2.4   fixed a null-pointer case; the call signature is untouched
```

**MINOR** — a **backward-compatible addition**. New functionality, new parameters (with defaults), new modules, while old code still works.

```text
1.2.4 → 1.3.0   added export_csv(); the existing import_json() still behaves the same
```

**MAJOR** — an **incompatible API change**. A function was removed, a parameter order changed, a return type changed, or the semantic behavior changed.

```text
1.3.0 → 2.0.0   get_user() now returns an object instead of a dict; every old caller breaks
```

**Crash site: promoting a bug fix to a major version**

```text
# WRONG: chaotic release discipline
v1.0.1 → v1.1.0   "fixed a bug and slipped in a small feature"
v1.1.0 → v2.0.0   "not really breaking, just felt like it was time"
```

```text
Downstream log:
WARNING  bumped to 2.0.0, assuming breaking change, blocking upgrade
```

**Consequence**: users see the major bump and assume you introduced a breaking change, so they do not upgrade. A "trivial" release slows the ecosystem's adoption of your library. The version number stops carrying signal.

## What counts as a breaking change

The test is simple: **can existing users keep working without changing a single line of code after they upgrade?**

| Change | Breaking? |
|---|---|
| Adding a function, adding an optional parameter (with a default) | no |
| Fixing a bug (including making a "wrong" behavior correct) | no (it is a patch, unless users depended on the bug) |
| Renaming a function | yes |
| Removing a function or a parameter | yes |
| Changing a parameter order or its default | yes |
| Changing a return type or a field name | yes |
| Rewriting the internals while keeping the interface identical | no (transparent to users) |

**Watch out for "behavior people depended on because it was a bug":** if a "bug" is already widely treated as a feature — say, a function that should return a list instead returned `None`, and someone wrote `if result is None` to accommodate it — fixing it may break them. In that case, a MINOR release with a warning is the safer move, followed by removing the old behavior in the next MAJOR.

## Pre-release versions and build metadata

A version can carry a suffix:

```text
1.3.0-alpha.1    pre-release: internal testing, unstable
1.3.0-beta.2     pre-release: features frozen, public test
1.3.0-rc.1       pre-release: release candidate, essentially usable
1.3.0            stable release
```

A pre-release version has **lower precedence than the stable version**. Package managers treat `1.3.0-alpha` as older than `1.3.0`, so `pip install >=1.3.0` will not pull an alpha.

Build metadata (after a plus sign) is not part of precedence:

```text
1.3.0+build.123   is the same version as 1.3.0, just a different build number
```

## Why you cannot just bump at random

A version number is **a promise you make to your users**. It has three concrete effects:

**1. Dependents use it to decide an upgrade policy**

```toml
# someone else's pyproject.toml
dependencies = [
    "mypackage>=1.3,<2.0",   # accept only backward-compatible updates
]
```

They wrote `<2.0` because they trust you: as long as you do not bump MAJOR, the interface will not break. If you bump to 2.0 for no reason, their constraint stops working and an upgrade may crash.

**2. Package managers rely on it for dependency resolution**

`pip` and `poetry` interpret `^1.3.0` (a compatibility range) as accepting `1.4.0` and `1.9.0`, but never `2.0.0`. Bumping at random breaks both automated updates and lockfiles.

**3. Random bumps make the number meaningless**

```text
v1 → v2: nothing changed
v2 → v3: only the README changed
# From now on nobody reads your version number and nobody reads the CHANGELOG either
```

Once versions are cheap, users have to inspect every release by hand, which is expensive.

## The right way to release

1. Decide which **single highest-impact** change this release contains, and work downward from there.
2. Breaking change → MAJOR; new features only → MINOR; bug fixes only → PATCH.
3. When several kinds of change ship together, take the **highest** tier.
4. Update the `version` field in `pyproject.toml`.
5. Write a CHANGELOG, grouped under Added / Changed / Fixed / Removed.
6. Tag the commit: `git tag v1.3.0 && git push origin v1.3.0`.

## Summary

- `MAJOR.MINOR.PATCH` = incompatible change / backward-compatible feature / backward-compatible fix.
- The breaking-change test: can existing users keep working without changing their code?
- Pre-release suffixes `-alpha`, `-beta`, `-rc` rank below the stable release.
- A version number is a contract with your users; random bumps break dependents' auto-updates and their trust.
- Release flow: pick a version → update `version` → write a CHANGELOG → tag.

## In-class exercise

```quiz
type: choice
q: Your library's next release adds an optional parameter with a default to one function and fixes a bug; nothing else changes. What is the correct version change?
options:
- 1.2.3 → 2.0.0, because there is more than one change.
- 1.2.3 → 1.3.0, since an optional parameter with a default is a backward-compatible addition and the bug fix ships with it.
- 1.2.3 → 1.2.4, because bug fixes outrank feature additions.
- 1.2.3 → 1.3.1, you must bump both PATCH and MINOR.
answer: 1
explain: An optional parameter with a default is a backward-compatible feature, so it belongs in MINOR; the bug fix is included in the same release. Take the higher tier, do not add PATCH as well, and the resulting version is 1.3.0.
```

type: choice
exam: true
q: Which statement about semantic versioning is correct?
options:
- A version number is just an auto-incrementing counter; bump it however you like, users do not care.
- Fixing a bug with no interface change should bump PATCH; removing a public function should bump MAJOR.
- MINOR releases may contain breaking changes as long as the change is small.
- MAJOR should only be bumped when the codebase doubles in size.
answer: 1
explain: The SemVer rule: a backward-compatible bug fix is PATCH, a backward-compatible addition is MINOR, and an incompatible API change (like removing a public function) is MAJOR. The version is a contract with users, not a measure of code volume.
