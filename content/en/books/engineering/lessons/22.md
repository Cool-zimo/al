# Packaging and Publishing: From Source to `pip install`

> Your project is done and a colleague says "send it to me." You zip the whole directory, they unzip it, set up the paths by hand, and get an import error. That is what happens without packaging. Packaging turns a project into a standard, distributable form so anyone can install it with a single `pip install`.

## The build artifacts: sdist and wheel

Python packaging produces two artifacts:

| Artifact | What it is | Characteristics |
|---|---|---|
| `sdist` (source distribution) | a compressed archive of source plus build scripts (.tar.gz) | needs a local compiler; slower install |
| `wheel` (built package, .whl) | a pre-built binary package | install = unzip; no compilation; fast |

**Publish a wheel whenever you can.** A wheel installs an order of magnitude faster and does not require the user to have a C compiler. The sdist is generally uploaded alongside it as a source backup.

```bash
# build both with the build tool
$ pip install build
$ python -m build
# produces:
#   dist/yourpkg-0.1.0.tar.gz      (sdist)
#   dist/yourpkg-0.1.0-py3-none-any.whl   (wheel)
```

## Build configuration in pyproject.toml

`pyproject.toml` is the project configuration entry point defined by PEP 518/621. Build-related information goes here:

```toml
[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[project]
name = "mypackage"
version = "0.1.0"
description = "An example toolkit"
readme = "README.md"
requires-python = ">=3.10"
license = {text = "MIT"}
authors = [{name = "Zhang San", email = "zs@example.com"}]
keywords = ["demo", "tool"]
classifiers = [
    "Programming Language :: Python :: 3",
    "License :: OSI Approved :: MIT License",
    "Operating System :: OS Independent",
]

dependencies = [
    "requests>=2.28",
    "rich>=13.0",
]

[project.optional-dependencies]
dev = ["pytest>=8.0", "ruff"]

[project.scripts]
mypkg-cli = "mypackage.cli:main"

[tool.hatch.build.targets.wheel]
packages = ["src/mypackage"]
```

**Key fields explained**:

- `[build-system]`: declares the build backend (`hatchling`, `setuptools`, `flit` all work) and its dependencies.
- `[project]`: project metadata; this is exactly what shows up on the PyPI page.
- `dependencies`: runtime dependencies, installed automatically when someone installs your package.
- `[project.optional-dependencies]`: optional dependency groups, installed only with `pip install mypackage[dev]`.
- `[project.scripts]`: generates a command-line entry point, so `mypkg-cli` works right after `pip install`.
- `[tool.hatch.build.targets.wheel]`: tells the backend which directories to include in the wheel.

**Crash site: forgetting to declare a dependency**

```toml
# WRONG: no dependencies declared in pyproject.toml
[project]
name = "mypackage"
version = "0.1.0"

# after install
$ mypkg-cli
ModuleNotFoundError: No module named 'requests'
```

```text
The user installed your package, but requests was not installed.
dependencies was never declared, so pip had no idea it was needed.
```

**The fix: list every runtime dependency in `dependencies`**; development-only tools (pytest, ruff) go in the `dev` group under `[project.optional-dependencies]`.

## Publishing to PyPI

**Step 1: create an account**

Register on [TestPyPI](https://test.pypi.org) and [PyPI](https://pypi.org), then generate an API token (use a token, not a password — tokens can be revoked).

**Step 2: build locally**

```bash
$ rm -rf dist/ build/
$ python -m build
$ ls dist/
mypackage-0.1.0.tar.gz  mypackage-0.1.0-py3-none-any.whl
```

**Step 3: inspect the artifacts**

```bash
$ pip install twine
$ twine check dist/*     # check README and metadata for compliance
$ python -m pip install dist/*.whl   # install locally to confirm it works
```

**Step 4: try it on TestPyPI first**

```bash
$ twine upload --repository testpypi dist/*
# use a TestPyPI token
# then visit https://test.pypi.org to check the page and try installing
$ pip install --index-url https://test.pypi.org/simple/ mypackage
```

**Step 5: publish to real PyPI**

```bash
$ twine upload dist/*    # use a real PyPI token
# done — anyone in the world can pip install it
```

**Crash site: a leaked token**

```text
# token pasted in plaintext into a CI config file and pushed
$ git push
> token appears in commit history, scraped by a bot, attacker publishes a malicious release
```

**The fix: tokens belong only in GitHub Secrets / CI encrypted variables**, injected via `${{ secrets.PYPI_TOKEN }}` and never written into a file.

**Crash site: republishing the same version**

```bash
$ twine upload dist/*
403 Client Error: File already exists.
```

PyPI **does not allow overwriting a published version**. Once `0.1.0` is out, the only move is `0.1.1`. So validate locally before uploading, or you will be forced to bump the version to fix a one-character mistake.

## Modern shortcut: one-click publishing

Many projects use GitHub Actions to build and publish on tag:

```yaml
name: Publish
on:
  push:
    tags: ["v*"]
jobs:
  publish:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install build twine
      - run: python -m build
      - run: twine upload dist/*
        env:
          TWINE_USERNAME: __token__
          TWINE_PASSWORD: ${{ secrets.PYPI_TOKEN }}
```

Push a `v0.1.0` tag and the release happens automatically.

## Summary

- Two artifacts: sdist (source) and wheel (pre-built); publish a wheel whenever possible.
- `python -m build` builds both at once.
- `pyproject.toml` declares metadata, dependencies, and entry points; runtime deps go in `dependencies`.
- Release flow: build → `twine check` → TestPyPI trial → real PyPI.
- PyPI never overwrites a published version, so always validate locally first.
- Tokens go only in CI Secrets; they must never enter the repository's history.

```quiz
type: choice
q: You are publishing your first package and want to confirm that the README and metadata render correctly on the PyPI page and that the wheel installs properly. What is the recommended dry run?
options:
- Publish straight to real PyPI; you can always delete it and re-upload.
- Upload to TestPyPI first with twine, install it once to confirm, then publish to real PyPI.
- Send the package to a few colleagues for manual installation.
- Creating a release on GitHub is enough.
answer: 1
explain: TestPyPI is an official isolated staging repository for rehearsing a real release. PyPI never overwrites a published version, so a mistake forces a version bump; a trial run is necessary.
```
