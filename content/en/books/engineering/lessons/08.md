# Comments and Docstrings: Say Why, Not What

> You see a comment reading `# increment i`, followed by `i += 1`. It states the code's what — and anyone who can read Python already knows what `i += 1` does. A good comment tells **why**; a bad comment tells **what**.

## When to Write a Comment

The test: **is the intent of this line obvious at a glance?**

```python
# WRONG: comments that state what — pure noise
# increment count
count += 1

# iterate over users with a for loop
for user in users:
    process(user)
```

```python
# GOOD: comments that state why — informative
# Validate before querying: validation rejects most bad requests,
# avoiding an expensive database round trip for every dirty record.
validate(order)
save_order(order)

# Subtract 1 because months are 1-based but timedelta expects a 0-based index
target = now - timedelta(days=date(2024, month - 1, 1).day)
```

**Crash Site: comment and implementation diverge**

```python
# WRONG: the comment is stale
# retry at most 3 times
for attempt in range(5):
    try:
        do_request()
        break
    except RequestError:
        continue
```

**Consequence:** the comment says three, the code retries five. Someone reading the comment assumes three retries is enough; during a failure drill they discover five and suspect a bug, spending twenty minutes investigating — when the truth is only that the comment was never updated. A comment that **lies** is worse than no comment at all, because it gives you false information.

**Hard rule: when you change the code, update the comment. If you cannot, delete it.**

## Docstring Conventions

A docstring is a string placed as the first statement of a function, class, or module; `help()` and IDEs can read it.

```python
def calculate_discount(user, amount):
    """Calculate the discounted amount based on the user's membership tier.

    Gold members get 20% off, silver get 10%, regular users get no discount.

    Args:
        user: A user object that must expose a vip_level attribute.
        amount: The original price, in yuan.

    Returns:
        The discounted amount (float).

    Raises:
        ValueError: If amount is negative.
    """
    if amount < 0:
        raise ValueError("amount must not be negative")
    if user.vip_level == "gold":
        return amount * 0.8
    elif user.vip_level == "silver":
        return amount * 0.9
    return amount
```

```python
>>> help(calculate_discount)
# Displays the docstring above
```

Key points:

- The first line is a **one-sentence summary** of what it does.
- Leave a blank line, then add a detailed description.
- Use `Args`, `Returns`, and `Raises` to document parameters, return value, and exceptions.
- This is not the only format — Google, NumPy, and reST styles are all common — pick one and stay consistent.

**Module-level docstrings** sit at the very top of a file:

```python
"""Order processing module.

Responsible for order validation, persistence, and notification.
Exposes process_order publicly.
"""
```

**Crash Site: writing a docstring as a comment**

```python
# WRONG
def fetch_data(url):
    # Fetch data from url
    # Return the parsed dict
    ...
```

This is not a docstring; it is an ordinary comment. `help()` cannot see it and the IDE shows nothing on hover. A string makes it a docstring:

```python
def fetch_data(url):
    """Fetch data from url and return the parsed dict."""
    ...
```

## The Basics of Type Hints

Type hints do not change runtime behaviour, but they let IDEs and static checkers (mypy, pyright) find mistakes for you.

```python
def greet(name: str) -> str:
    return f"Hello, {name}"

def get_user(user_id: int) -> dict | None:
    user = db.find(user_id)
    return user  # dict or None
```

`dict | None` is the Python 3.10+ spelling, equivalent to `Optional[dict]`.

**Write out container types completely:**

```python
from collections.abc import Sequence

def average(values: Sequence[float]) -> float:
    return sum(values) / len(values)
```

Use `Sequence` rather than `list`, because the function only needs "subscriptable and sized" — tuples and `range` qualify, so there is no need to nail it to `list`.

**Crash Site: no annotation, so the IDE cannot help**

```python
# WRONG
def process(items, threshold):
    result = []
    for item in items:
        if item["score"] > threshold:
            result.append(item)
    return result
```

You pass `threshold="high"` and the error surfaces only at runtime on `item["score"] > "high"` — **a type error caught at runtime**. With annotations, the IDE would mark it red the instant you typed it.

Type hints are "documentation for humans and tools"; they do not enforce runtime checks. For enforcement you need mypy or pyright.

## Summary

- Comments explain why, never what.
- Update comments with the code; otherwise delete them.
- A docstring uses `"""`, readable by `help()` and IDEs.
- Docstrings document Args / Returns / Raises; agree a style as a team.
- Type hints are documentation and a signal to static checkers.

## In-Class Exercise

```quiz
type: choice
q: Which comment is the most informative and worth keeping?
options:
- # set total to 0
- # Check the cache before hitting the database because the hit rate is 95%; a direct query would hurt p99
- # iterate over items with a for loop
- # end of function
answer: 1
explain: Only the second explains the reason behind a design decision. The other three merely describe what the code is doing — noise that easily turns into a lie once the code changes.
```
