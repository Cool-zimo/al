# Dependency Management: From "Works on My Machine" to "Works Anywhere"

> Alice sends you a project whose README says only "just pip install and run." You install, run it, and the first line raises `ImportError`. The code is not broken — nobody wrote down what it actually needs. Dependency management answers two questions: *what* do we need, and *which version*.

## requirements.txt vs pyproject.toml

These are the two most common dependency清单 formats — do not confuse them.

**requirements.txt** is an installation instruction sheet, plain and direct:

```txt
requests==2.31.0
pandas>=2.0,<3.0
python-dotenv
```

One package per line. `==` pins a version, `>=` sets a minimum, and a bare name like `python-dotenv` means "any version will do." It does one job: tell pip what to install.

**pyproject.toml** is a project description, standardized by PEP 621, and carries more information:

```toml
[project]
name = "myapp"
version = "0.1.0"
dependencies = [
    "requests>=2.28",
    "pandas>=2.0,<3.0",
]

[project.optional-dependencies]
dev = ["pytest>=7", "ruff"]
```

Besides dependencies it records the project name, version, entry points, and optional dependency groups. New projects **should prefer pyproject.toml** — it is a complete description, whereas requirements.txt is only an installation list.

| Aspect | requirements.txt | pyproject.toml |
|---|---|---|
| Role | Installation list | Full project description |
| Consumed by | pip directly | pip, poetry, hatch, uv |
| Can express versions | Yes | Yes |
| Can hold author, licence | No | Yes |
| Learning curve | Minimal | Slightly steeper |

## Why You Must Pin Versions

Leaving versions unpinned hands your project's fate to "whatever is latest on PyPI today."

**Crash Site: reinstalling six months later, everything collapses**

```txt
# requirements.txt — no pinned versions
requests
pandas
flask
```

```bash
# Alice developed it six months ago
$ pip install -r requirements.txt
Successfully installed requests-2.28.0 pandas-1.5.0 flask-2.2.0

# Bob clones the code and reinstalls six months later
$ pip install -r requirements.txt
Successfully installed requests-2.31.0 pandas-2.1.0 flask-3.0.0

$ python main.py
Traceback (most recent call last):
  File "main.py", line 3, in <module>
    from flask import Flask, Request
AttributeError: 'Request' is not exported from flask
```

**What you see:** `AttributeError`. Flask 3.0 restructured its exports and `Request` moved. Not one line of code changed — only the environment changed — and the project broke.

**Pinning removes that uncertainty:**

```txt
requests==2.31.0
pandas==2.1.0
flask==3.0.0
```

Now every machine, at any time, installs the exact same environment. The cost is that you must periodically upgrade and test, but that cost is far smaller than "break at random on some future date."

## The Pitfalls of pip freeze

`pip freeze` exports every package in the current environment with its exact version — sounds perfect. Its big flaw: **it exports everything in the environment, including transitive dependencies.**

```bash
(.venv) $ pip freeze > requirements.txt
(.venv) $ cat requirements.txt
requests==2.31.0
charset-normalizer==3.3.0
idna==3.4
urllib3==2.1.0
certifi==2023.11.17
pandas==2.1.0
numpy==1.26.0
python-dateutil==2.8.2
pytz==2023.3
six==1.16.0
```

You installed only `requests` and `pandas`, yet ten packages came out. The transitive ones (`charset-normalizer`, `six`, `pytz`) were pulled in by your direct dependencies.

**Where it hurts:** versions get frozen solid. Two months later `requests` ships a new release with a performance fix and a security patch you care about, but `pip install -r requirements.txt` still installs the old one — every transitive dependency is pinned, so pip cannot pick a compatible newer set.

**The right split is direct dependencies versus a lock file:**

- Direct dependencies (the ones you `import`) are written by hand in `requirements.txt`, using `>=` or `==` as you choose.
- For strict reproducibility, use a lock file: `pip-tools`'s `requirements.lock`, `poetry.lock`, or `uv.lock`.

A small project can maintain a direct-dependency list. A reproducible build needs a lock file.

## Direct vs Transitive

| Type | Meaning | Imported by your code | Hand-written in the list? |
|---|---|---|---|
| Direct | A library you `import` yourself | Yes | Always |
| Transitive | A library your dependency depends on | No | Usually left to tooling |

If you `import requests`, and `requests` depends on `urllib3`, then `urllib3` is transitive. You should not write `urllib3==x.x.x` unless you genuinely need to pin it — let pip choose a compatible version.

**Crash Site: handwriting a pile of transitive dependencies**

```txt
# WRONG: piping pip freeze straight into requirements.txt, then annotating by hand
requests==2.31.0
urllib3==2.1.0        # pulled in by requests
certifi==2023.11.17   # pulled in by requests
charset-normalizer==3.3.0  # pulled in by requests
pandas==2.1.0
numpy==1.26.0         # pulled in by pandas
```

Six months later you try to upgrade `requests`. `urllib3` is nailed to 2.1.0, but the new `requests` wants `urllib3>=2.2`. Conflict. You spend half an hour debugging, only to find the culprit was your own handwritten line.

## Summary

- `requirements.txt` is an installation list; `pyproject.toml` is a full project description — prefer the latter for new projects.
- Pinning (`==`) buys reproducibility; leaving versions open bets your project on "the latest."
- `pip freeze` exports transitive dependencies too; used as a hand-written list it blocks automatic upgrades.
- Maintain direct dependencies yourself and let tooling manage the transitive ones.
- A simple project needs a list; a reproducible build needs a lock file.

## In-Class Exercise

```quiz
type: choice
q: You maintain a small internal tool that uses only requests and pandas. What is the most reasonable way to write requirements.txt?
options:
- Use the raw output of pip freeze — the more packages the safer
- List only requests and pandas with their versions, and leave their transitive dependencies alone
- Hand-write every transitive dependency with pinned versions
- Leave it empty and let users pip install whatever they need
answer: 1
explain: Maintaining only direct dependencies is the sensible split. Handwriting transitive ones pins them and causes conflicts when you later upgrade a direct dependency. A pip freeze result makes a good lock file but a poor hand-written list.
```
