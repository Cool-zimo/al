# pytest in Practice: Fixtures, Parametrization, and Test Isolation

> You have 50 tests, each one copying the same "create the database, insert test data, tear down the database" block. Then the schema changes and you edit that block 50 times. Fixtures exist to remove exactly that repetition. And "tests leaking into each other" is the easiest trap to fall into.

## Fixtures: hand the setup and teardown to pytest

A `fixture` is pytest's dependency-injection mechanism. A test function names a fixture in its parameters and pytest calls it automatically, passing the result in.

```python
import pytest

@pytest.fixture
def sample_users():
    # setup: build the test data
    return [
        {"id": 1, "name": "Alice", "age": 28},
        {"id": 2, "name": "Bob",   "age": 17},
        {"id": 3, "name": "Carol", "age": 35},
    ]

def test_filter_adults(sample_users):
    adults = [u for u in sample_users if u["age"] >= 18]
    assert len(adults) == 2

def test_find_by_name(sample_users):
    result = [u for u in sample_users if u["name"] == "Alice"]
    assert result[0]["id"] == 1
```

`sample_users` is never written out by hand in every test — pytest injects it. The test only says "what data do I need," not "where does that data come from."

**Fixture scope**: by default the fixture re-runs once per test function (`function`). There is also `module` (once per module) and `session` (once per test session). An expensive resource like a database connection belongs at `session` scope so you avoid reconnecting over and over.

```python
@pytest.fixture(scope="session")
def db_connection():
    conn = create_connection("sqlite:///:memory:")
    yield conn          # tests use this conn
    conn.close()        # cleanup runs after every test is done
```

The code before `yield` is the setup, the code after it is the teardown. This is the standard pytest idiom for "cleanup."

## Parametrization: one logic, many inputs

The dumbest way to test ten input/output pairs is to copy the test function ten times. `@pytest.mark.parametrize` generates separate test cases from one list of inputs.

```python
import pytest

def parse_age(text):
    """Convert the input to an integer age; illegal input returns None."""
    if not text or not str(text).strip():
        return None
    try:
        n = int(str(text).strip())
    except ValueError:
        return None
    return n if n >= 0 else None

@pytest.mark.parametrize("text,expected", [
    ("18", 18),
    ("  25  ", 25),
    ("0", 0),
    ("", None),
    ("  ", None),
    ("abc", None),
    ("-3", None),
    ("18.5", None),
])
def test_parse_age(text, expected):
    assert parse_age(text) == expected
```

After running, you get 8 independent cases, each passing or failing on its own, so you can see at a glance which input broke.

```text
$ pytest tests/test_parser.py -v
tests/test_parser.py::test_parse_age[18-18] PASSED
tests/test_parser.py::test_parse_age[abc-None] PASSED
...
```

## conftest.py: shared fixtures

When several test modules need the same fixture, do not copy and paste. Create a `conftest.py` at the project root or inside a directory; everything in it is automatically visible to tests in that directory and its subdirectories.

```python
# tests/conftest.py
import pytest

@pytest.fixture
def tmp_log_dir(tmp_path):
    log_dir = tmp_path / "logs"
    log_dir.mkdir()
    return log_dir

@pytest.fixture(scope="module")
def app_config():
    return {"debug": True, "max_retries": 3, "timeout": 30}
```

```python
# tests/test_logger.py
def test_log_writes_file(tmp_log_dir):        # tmp_log_dir comes from conftest.py
    log_file = tmp_log_dir / "app.log"
    log_file.write_text("hello")
    assert log_file.read_text() == "hello"
```

**Rule: do not put tests inside `conftest.py`, only fixtures and hooks.** A test file should run on its own with `pytest tests/test_xxx.py`, with fixtures discovered automatically.

## Tests must be isolated from one another

This is the easiest trap. **Every test should run independently, and in any order.**

**Crash site: test A pollutes test B**

```python
# WRONG
cart = []

def test_add_item():
    cart.append("apple")
    assert len(cart) == 1

def test_cart_starts_empty():
    assert cart == []      # fails if test_add_item ran first
```

```text
$ pytest tests/test_cart.py::test_cart_starts_empty
>       assert cart == []
E       AssertionError: assert ['apple'] == []
```

**Why it fails**: `cart` is a module-level global, so a mutation from one test survives into the next. pytest makes no guarantees about test execution order.

**The fix: rebuild with a fixture every time**

```python
@pytest.fixture
def cart():
    return []              # every test gets a brand-new empty list

def test_add_item(cart):
    cart.append("apple")
    assert len(cart) == 1

def test_cart_starts_empty(cart):
    assert cart == []       # always passes
```

**Crash site: a test passing because of leftover data**

```python
# WRONG
def test_create_user(db):
    create_user(db, "alice")       # inserts alice
    assert count_users(db) == 1

def test_user_unique(db):
    create_user(db, "alice")       # depends on the previous row not being cleaned up
    create_user(db, "alice")       # expects a unique-constraint error
```

When the first test runs first, alice already exists, so the second test raises "duplicate user" instead of the expected "unique constraint." Swap the order and both fail.

**The fix: clean up in the fixture's teardown, or use an isolated transaction per test**

```python
@pytest.fixture
def clean_db(db_connection):
    yield db_connection
    # teardown: remove the data this test created
    db_connection.execute("DELETE FROM users WHERE name = 'alice'")
```

**Three isolation rules**:

1. Do not put mutable state (lists, dicts, counters) at module or class level.
2. Inject shared resources through fixtures, and let the fixture rebuild or clean them up.
3. Do not depend on test order — and do not assume `pytest -p no:randomly` is the answer.

## Summary

- A fixture is pytest's dependency injection: decorate with `@pytest.fixture`, then name it in a test's parameters.
- Code before `yield` is setup, code after it is teardown — the standard way to manage resource lifetime.
- Use `scope` to control how often a fixture runs: `function` (default) / `module` / `session`.
- `@pytest.mark.parametrize` tests many inputs with one logic block and reports failures precisely.
- `conftest.py` holds shared fixtures for several modules to reuse, with no import required.
- Tests must be isolated: never share mutable globals; rebuild and clean up through fixtures.

## In-class exercise

```quiz
type: choice
q: You want a group of tests to share one expensive database connection, but you do not want it closed and reopened after every single test. What is the correct fixture setup?
options:
- A plain @pytest.fixture is enough — pytest will reuse it automatically.
- @pytest.fixture(scope="session"), with the connection closed after the yield.
- Store the connection in a module-level global variable and manage it by hand.
- @pytest.fixture(scope="function"), closing the connection before the yield.
answer: 1
explain: scope="session" makes the fixture run exactly once for the whole test session, avoiding repeated connections; the yield form lets you close the connection after all tests finish. The default scope is function, which would reconnect every time.
```

## Lesson quiz

```quiz
type: choice
exam: true
q: Which situation most likely causes "test A passes alone, test B passes alone, but they fail together"?
options:
- Tests A and B both use a fixture, but the fixture's scope is set to session.
- Test A mutates a module-level global list and test B assumes that list is empty.
- Tests A and B both use parametrize.
- Tests A and B live in two different files.
answer: 1
explain: Mutable module-level state is mutated by one test and inherited by the next, breaking isolation. A session-scoped fixture is deliberately shared and does not cause random failures; parametrize and file location do not break isolation either.
```
