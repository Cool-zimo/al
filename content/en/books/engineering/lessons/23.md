# Containers: Turning "It Runs on My Machine" Into "It Runs Anywhere"

> A script that works on a colleague's laptop crashes on yours; CI passes but production explodes. Usually the code is fine and the environment is the problem. Docker packages the code together with its operating system, dependencies, and runtime, so "it runs on my machine" finally stops being a punchline.

## Why Docker

The classic development argument is an environment mismatch:

```text
Colleague: Works for me — Python 3.11, dependencies installed.
You:       I'm on 3.9 and cannot install that package.
Ops:       Production is 3.8 and the behavior is different.
```

Three machines, three Python versions, three results. The issue is not who is right; it is that **the code was never bound to its environment**.

Docker's answer: package the application with everything it needs — operating system, Python interpreter, libraries, environment variables — into an **image**, then run that image anywhere Docker is installed and get the same **container** every time.

- An image = a packaged "template," like an ISO installer; it is a static file.
- A container = an "instance" of that image, like a machine installed from the disc; it is a running process.

One image can start any number of containers. A container that runs on your laptop behaves identically when dropped into CI or onto a server.

**Crash site: assuming "Docker means consistent environments"**

```text
# WRONG: the version in the image drifts from what you actually run locally
FROM python:latest          # local is 3.11, then one day latest quietly becomes 3.13
RUN pip install requests    # installs whatever is current that day
```

```text
The error three weeks later:
TypeError: requests.get() missing 1 required positional argument: 'xxx'
# because requests shipped a major version and changed its signature
```

**Consequence**: `latest` is a floating tag, so every build can pull a different version. The image that builds today may fail to build tomorrow, or behave differently. The environment only looks consistent.

## Images vs. containers

A useful analogy: **image is to container as class is to object.**

```text
Image                                     Container
├─ static file, distributable             ├─ a running instance
├─ built from a Dockerfile                ├─ started from an image: docker run
├─ read-only                              ├─ has a read/write layer, mutable
└─ stored in a registry (Docker Hub)      └─ state can be kept or discarded when stopped
```

Key concepts:

1. **Layers** — each instruction in a Dockerfile usually becomes a layer. `FROM` is one layer, `RUN pip install` is another. Layers are cached; when one layer changes, every layer after it has to be rebuilt.
2. **Copy-on-write** — all containers share the same read-only image and each adds its own writable layer on top. When a container is removed, that writable content is gone by default.
3. **Build once, run anywhere** — build the image once, push it to a registry, and CI, testing, and production all pull the same image, guaranteeing that what you tested is what ships.

```bash
# common operations
docker build -t myapp:1.0 .      # build an image from the Dockerfile in the current directory
docker images                    # list local images
docker run -p 8000:8000 myapp:1.0   # start a container, publishing port 8000
docker ps                        # list running containers
docker stop <container-id>       # stop a container
docker rmi myapp:1.0             # remove an image
```

## A minimal Dockerfile

A Dockerfile is the recipe that builds an image, one instruction per line. Here is a minimal, usable image for a Python project:

```dockerfile
# 1. pick a base image and pin the version
FROM python:3.11-slim

# 2. set the working directory (inside the container)
WORKDIR /app

# 3. copy the dependency manifest first, to take advantage of caching
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# 4. copy the source code
COPY . .

# 5. expose the port (a declaration; actual mapping happens with docker run -p)
EXPOSE 8000

# 6. the startup command
CMD ["python", "app.py"]
```

A few points:

- **Pin the base image's version tag**: `python:3.11-slim`, not `python:latest`. The `-slim` variant is smaller.
- **Copy the dependency manifest first, then the source**: Docker caches by layer. Source changes daily, dependencies rarely do; copying `requirements.txt` first means the install layer is reused whenever dependencies stay the same, avoiding hundreds of megabytes of reinstalls.
- **Use the exec form of CMD** (a JSON array): the process becomes PID 1 and receives stop signals correctly.

**Crash site: copying the whole working directory into the image**

```dockerfile
# WRONG
FROM python:3.11-slim
WORKDIR /app
COPY . .                       # copies .git, __pycache__, .venv, .env — all of it
RUN pip install -r requirements.txt
CMD ["python", "app.py"]
```

```text
Build log:
Step 4/5 : COPY . .
 ---> 1.2GB                     # the image should have been ~150MB
# The image now carries hundreds of MB of .git history and the local virtualenv.
```

**Consequence**: bloated images, slow pushes and pulls, frequent CI cache invalidation; and, far worse, sensitive files (`.env`, secrets) can land inside the image and become public the moment it is pushed.

## Never bake secrets into the image

This is the **safety incident** containers make easiest to cause. Once an image is built, what is inside stays inside — even if you `RUN rm .env` on the next line, the secret remains in the earlier read-only layer, and anyone with the image can read it via `docker history` or by mounting the layer directly.

```text
# WRONG: hardcoding secrets in the Dockerfile
ENV DATABASE_PASSWORD=supersecret123
COPY .env .env
RUN echo "API_KEY=sk-xxxxxx" >> /app/config.py
```

The right approach:

1. **Use `.dockerignore` to exclude sensitive files** (next section).
2. **Inject at runtime through environment variables**: `docker run -e DATABASE_PASSWORD=xxx`, or mount a `.env` file only at runtime.
3. **Use a secret manager in production**: Docker Secrets, Kubernetes Secret, or a cloud provider's secret service.
4. **Scan images**: `docker scan` or a CI tool that scans for image vulnerabilities.

```bash
# correct: injected at runtime, so the image never contains the secret
docker run \
  -e DATABASE_PASSWORD="$DB_PASS" \
  -e API_KEY="$API_KEY" \
  myapp:1.0
```

**Crash site: thinking deletion removes the secret**

```dockerfile
# WRONG: self-deception
COPY .env .env
RUN cat .env >> /app/config.py && rm .env
```

```text
Post-build inspection:
$ docker history myapp:1.0
<missing>   RUN cat .env >> /app/config.py && rm .env
# .env's contents are now baked into the config.py layer, and the earlier COPY layer still has a copy
```

**Consequence**: anyone who gets the image (even from a private registry, which may be breached) can recover every secret. Incidents like this are common in the industry, and the repair cost is far higher than doing it right from the start.

## .dockerignore: the build-time blacklist

`.dockerignore` works like `.gitignore`, but it controls **which files never get copied into the image**. The syntax is almost identical:

```text
# .dockerignore
.git
.gitignore
.env
*.env
.venv
venv
__pycache__
*.pyc
.pytest_cache
.mypy_cache
node_modules
README.md
tests/
docker-compose.yml
.DS_Store
```

Why it is mandatory:

- **Security** — blocks `.env`, secret files, and local config.
- **Size** — blocks `.git` (often hundreds of MB), `.venv`, and cache directories.
- **Cache hits** — blocks `tests/` and other irrelevant files, so changing tests does not invalidate the source layer.

```bash
# verify that .dockerignore is taking effect
docker build -t myapp:test .
docker run --rm -it myapp:test ls -la /app
# check the output for .env, .git, __pycache__, or anything that should not be there
```

## Summary

- Docker solves environment drift: the image packages code plus environment, the container is a running instance of that image.
- An image is read-only and distributable; a container has a writable layer that can be discarded on stop.
- A Dockerfile is the recipe: pin the base image version, install dependencies before copying source, and use exec form for CMD.
- **Never bake secrets into an image**; use `.dockerignore` plus runtime-injected environment variables.
- `.dockerignore` simultaneously protects security, controls image size, and improves cache hit rates.

## In-class exercise

```quiz
type: choice
q: Your Dockerfile copies the whole source tree with COPY . . before running pip install. Why is the recommended order the reverse — copy requirements.txt first, install dependencies, then copy the source?
options:
- Because pip needs to see requirements.txt before it can work.
- Dependencies rarely change while source changes constantly; installing dependencies first lets that layer stay cached, avoiding hundreds of megabytes of reinstalls on every code change.
- COPY . . is only allowed on the last line of a Dockerfile.
- Copying source first prevents the image from starting.
answer: 1
explain: Docker caches by layer. Moving the rarely-changing dependency install earlier and the frequently-changing source copy later lets the dependency layer stay cached even when source changes, which dramatically speeds up builds.
```

- Images and containers are the same thing, just different names.

- Images can only be used locally and cannot be pushed to a remote registry.
answer: 1
explain: An image is a read-only static template; a container is its running instance. Their relationship is like class and object. Changes inside a stopped container are not kept by default — you must explicitly commit or mount a volume; images can be pushed to a registry.
