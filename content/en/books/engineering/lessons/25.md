# Capstone: Engineering an Existing Small Project

> This is the chapter's capstone. The previous lessons covered versioning, packaging, containers, and documentation; this lesson ties them together. You take "a script that runs" and turn it into "a project that can be delivered." You will see the full改造 workflow — adding tests, CI, a README, a version, and a .gitignore — and how isolated topics combine into one finished deliverable.

## The starting point: a project that runs but cannot be delivered

Here is a typical "script that runs": it reads a CSV, cleans the data, and writes JSON. It works, but nobody wants to touch it, nobody can collaborate on it, and it cannot go live.

```text
data_tool/
├── data_tool.py      # all the logic crammed into one 400-line file
├── config.py         # a hardcoded database password
├── data.csv          # a sample data file
├── .env              # contains API_KEY=sk-xxxxx
└── run.sh            # one line: python data_tool.py
```

`data_tool.py` looks like this (abridged) — hardcoded secret, one giant function, paths written directly into the code:

```python
import csv, json, os, sys

API_KEY = "sk-abcdef123456"   # hardcoded secret

def load_data(path):
    rows = []
    with open(path, encoding="utf-8") as f:
        for r in csv.DictReader(f):
            rows.append(r)
    return rows

def clean(row):
    if not row.get("name"):
        return None
    row["name"] = row["name"].strip()
    row["age"] = int(row["age"]) if row.get("age") else 0
    return row

def main():
    data = load_data("data.csv")
    cleaned = [clean(r) for r in data if clean(r)]
    with open("out.json", "w") as f:
        json.dump(cleaned, f, ensure_ascii=False)
    print("done")

if __name__ == "__main__":
    main()
```

**The problem list (read it before touching anything)**:

| Problem | Consequence |
|---|---|
| No tests | Changing one line means not knowing what else broke |
| Hardcoded secret | One commit leaks it; once pushed, it is public |
| No .gitignore | `.env`, caches, and virtualenvs all enter version control |
| No README | Newcomers have no idea how to install or run it |
| No version, not packaged | Nobody can depend on it as a library, and it cannot be released |
| No CI | Nobody runs the tests for you; errors rely on human memory |

## The goal: from script to project

This is not a rewrite. The goal is to add the engineering pieces a deliverable needs **without breaking the existing functionality**. The order matters: control risk first (secrets, gitignore), then add quality (tests, CI), then add the deliverables (README, version, packaging, container).

The final layout (a package + a test directory + configuration files):

```text
data_tool/
├── data_tool/           # package: loader.py / cleaner.py / cli.py
├── tests/               # test_loader.py / test_cleaner.py
├── .gitignore  .dockerignore
├── Dockerfile  README.md  CHANGELOG.md
├── pyproject.toml  requirements.txt
└── data.csv
```

**Crash site: refactoring everything on day one**

```text
# WRONG order
Day 1: split 400 lines into 20 files and a new directory structure.
Day 2: nothing runs; git diff is thousands of lines with no way to bisect.
Day 3: revert everything and start over.
```

```text
Lesson learned:
error: too many changes in one commit, cannot bisect
# changing too much at once means you cannot tell which step introduced the breakage
```

**The fix**: one category of change at a time, one small commit, every step left in a runnable state. Lock the secrets first, then add tests, then split files, then add CI...

## Step 1: control risk — .gitignore and secret cleanup

Handle the most urgent thing first: keep `.env` out of version control and clean up any secrets that may already be in the history.

```gitignore
# .gitignore
.env
*.env
__pycache__/
*.pyc
.venv/
venv/
.pytest_cache/
.mypy_cache/
build/
dist/
*.egg-info/
.DS_Store
```

```bash
git rm --cached .env        # for anything already in history, also clean history
# (git filter-repo --invert-paths --path .env)
# after cleanup, rotate (invalidate) the leaked secret — old ones are dead
```

**Principle**: once a secret leaks, deleting the file is not enough — you must rotate it. Copies may remain in repo history, forks, and CI caches.

## Step 2: split the modules and add tests

Split `data_tool.py` into three single-responsibility modules, and write the tests first. Note the order: **tests before the split**, because the tests prove the split did not change behavior.

```python
# data_tool/loader.py
import csv

def load_data(path):
    with open(path, encoding="utf-8") as f:
        return list(csv.DictReader(f))
```

```python
# data_tool/cleaner.py — returns a new dict; blank names return None
def clean(row):
    if not row.get("name"):
        return None
    result = dict(row)
    result["name"] = result["name"].strip()
    result["age"] = int(result["age"]) if result.get("age") else 0
    return result
```

```python
# data_tool/cli.py
import json, sys
from .loader import load_data
from .cleaner import clean

def main(argv=None):
    argv = argv if argv is not None else sys.argv[1:]
    if not argv:
        print("usage: data_tool <input.csv> [output.json]")
        return 1
    data = load_data(argv[0])
    cleaned = [r for r in (clean(x) for x in data) if r is not None]
    out = argv[1] if len(argv) > 1 else "out.json"
    with open(out, "w", encoding="utf-8") as f:
        json.dump(cleaned, f, ensure_ascii=False)
    print(f"wrote {len(cleaned)} rows to {out}")
    return 0
```

The tests (under `tests/`, using `pytest` and `parametrize` to cover several inputs):

```python
# tests/test_cleaner.py
import pytest
from data_tool.cleaner import clean

@pytest.mark.parametrize("row,expected", [
    ({"name": "  Alice  ", "age": "30"}, {"name": "Alice", "age": 30}),
    ({"name": "", "age": "20"}, None),          # blank name -> drop
    ({"age": "20"}, None),                      # missing name -> drop
    ({"name": "Bob", "age": ""}, {"name": "Bob", "age": 0}),
])
def test_clean(row, expected):
    assert clean(row) == expected
```

```python
# tests/test_loader.py
from data_tool.loader import load_data

def test_load_data(tmp_path):
    f = tmp_path / "t.csv"
    f.write_text("name,age\nAlice,30\n", encoding="utf-8")
    assert load_data(str(f)) == [{"name": "Alice", "age": "30"}]
```

Run the tests (`tmp_path` is pytest's built-in temporary-directory fixture; it cleans up automatically):

```bash
$ pytest -v
tests/test_cleaner.py::test_clean[...] PASSED
tests/test_loader.py::test_load_data PASSED
```

**Crash site: changing behavior during the refactor**

```python
# WRONG: "improvement" slipped in during the refactor
def clean(row):
    if not row.get("name"):
        row["name"] = "(unknown)"   # used to return None; now fills a blank string
        return row
    ...
```

```text
$ pytest
FAILED tests/test_cleaner.py::test_clean[...] - AssertionError: expected None, got {...}
# the functionality "looks" fine and manual testing missed it
```

**Consequence**: without tests, this kind of "while we are at it" change goes unnoticed; with tests, it raises the alarm instantly. That is the value of tests — they lock behavior.

## Step 3: add CI to enforce discipline automatically

CI runs tests and style checks on every push / PR. This example uses GitHub Actions, validating on both 3.9 and 3.11 with `matrix`:

```yaml
# .github/workflows/ci.yml
name: CI
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        python: ["3.9", "3.11"]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: ${{ matrix.python }}
      - run: pip install -r requirements.txt pytest
      - run: pytest -v
```

The value of CI is not "saving effort"; it is **turning discipline into enforcement**: you cannot merge without running tests, and a style failure blocks the merge.

## Step 4: set a version and write the CHANGELOG

Give the project a starting version and explain what this改造 did. `0.1.0` signals that the API may still change, because the functionality is not yet stable:

```text
# CHANGELOG.md
## [0.1.0] - 2026-09-29
### Added
- Project engineering pass: split into loader / cleaner / cli modules.
- Unit tests for loader and cleaner.
- CI configuration.
- README and CHANGELOG.

### Changed
- clean() keeps its original behavior; only the internal implementation changed.
```

## Step 5: package, containerize, and write the README

`pyproject.toml` describes the metadata and declares the command-line entry `data_tool = data_tool.cli:main`. The `Dockerfile` pins `python:3.11-slim`, installs dependencies before copying source, uses exec form for CMD (with `.dockerignore` excluding `.env`). The `README.md` explains what the project does, how to install and use it, how to run the tests, and how to contribute.

```toml
[project]
name = "data_tool"
version = "0.1.0"
description = "A small CSV data-cleaning utility"
requires-python = ">=3.9"
dependencies = []

[project.scripts]
data_tool = "data_tool.cli:main"

[build-system]
requires = ["setuptools>=68"]
build-backend = "setuptools.build_meta"
```

The `Dockerfile` (`.dockerignore` excludes `.env`):

```dockerfile
FROM python:3.11-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["python", "-m", "data_tool.cli", "data.csv", "out.json"]
```

**Crash site: forgetting to run it in a clean environment before shipping**

```text
# WRONG: validating on a preconfigured machine
$ pytest         # passes because pytest is installed globally
$ python -m data_tool.cli data.csv out.json   # runs
Then tag and release.
```

```text
On a fresh machine:
$ git clone <repo> && cd data_tool && pytest
pytest: command not found   # it was never in requirements-dev.txt, and the README never said so
```

**Consequence**: "it worked on my machine" is meaningless. You must validate in a clean environment — a container, a fresh VM, or CI — and confirm every README step runs.

## Summary

- Order: control risk (.gitignore + secret cleanup) → add quality (tests + CI) → add deliverables (README, version, packaging, container).
- One category of change at a time, always leaving the project runnable, so you can bisect failures.
- Write tests before the refactor to lock behavior; they catch regressions the moment they are introduced.
- A leaked secret must be rotated; deleting the file is not enough.
- Before delivery, validate every README step in a fresh environment.

```quiz
type: choice
q: You are engineering an existing runnable script. Which order is most reasonable?

- Rewrite the whole thing as microservices, then add tests, then write the README.
- Control risk first (add .gitignore, clean up any leaked secrets), then add tests and CI, then the README, version, and packaging.
- Write a very detailed README first, then slowly change the code.

answer: 1
```
