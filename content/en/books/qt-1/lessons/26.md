# Why You Must Not Do Heavy Work in the GUI

> The most damaging mistake in a GUI app is not a crash — it is "freezing". This lesson explains how the main-thread blocking actually works and which jobs belong elsewhere.

## The Single-Threaded Truth

**After a PySide6 program starts, only one "main thread" is doing the work.** That thread has two jobs: running your business logic, and running the event loop. The event loop constantly handles mouse clicks, keyboard input, and repaint requests to keep the interface "alive".

```
while True:
    event = get_next_event()      # click, repaint, timer timeout...
    handle(event)                # calls your slot function
```

**Key fact: `app.exec()` *is* that while loop.** Your `on_clicked()` slot is called from inside the event loop. Until `on_clicked()` returns, the event loop is stuck there — new clicks cannot get in, repaint requests cannot be processed, and the window goes "not responding".

```
import sys
import time
from PySide6.QtWidgets import QApplication, QWidget, QPushButton, QVBoxLayout

app = QApplication(sys.argv)

def heavy():
    time.sleep(5)  # simulate a slow operation: the event loop is blocked for 5 seconds

win = QWidget()
btn = QPushButton("Click me (freezes for 5s)")
btn.clicked.connect(heavy)
QVBoxLayout(win).addWidget(btn)
win.show()
app.exec()
```

**After clicking that button, the window freezes completely — you cannot drag it, you cannot click it, and the system may flag it as "not responding".** This is not a bug; the event loop is being strangled by your `time.sleep(5)`.

## What Counts as "Heavy"

**One-line rule: any operation taking more than 100ms has no business in a main-thread slot.** The human perception threshold is roughly 100ms — past that, the interface feels noticeably "laggy".

| Operation type | Example | Time scale | Safe on main thread? |
|---|---|---|---|
| Network request | requests.get(url) | 100ms - 30s+ | no, must be moved out |
| Large file I/O | open(huge_file).read() | 10ms - several seconds | no, depends on size |
| Heavy computation | image processing, sorting data | 100ms - several minutes | no, must be moved out |
| Database query | cursor.execute("SELECT ...") | 10ms - several seconds | no, a network DB must be moved out |
| Simple string work | concatenation, formatting | under 1ms | yes, fine |
| Creating a control | QPushButton("xxx") | under 5ms | yes, fine |

**The most common culprit is a network request:**

```
import requests

def on_fetch():
    resp = requests.get("https://api.example.com/data")  # might take 3 seconds
    label.setText(resp.text)
```

**When the network is slow, this freezes the interface for 3 seconds.** The user thinks the program crashed, clicks frantically, and the event queue piles up — then everything fires at once when it finally unfreezes. It makes a bad situation worse.

## Crash Site #1: Your Loop Never Gives the Event Loop a Chance

**Symptom: you want a "process a huge file line by line" progress display, but the progress bar never updates — it jumps straight to 100% at the end.**

```
def process_file():
    for i, line in enumerate(huge_file):
        do_something(line)          # 10ms per line
        progress_bar.setValue(i)    # value is set, but the UI never repaints!
    # only after the loop ends does the event loop resume, and the bar jumps to 100%
```

**Why: your `process_file` runs to completion in one go. Until it returns, Qt has no chance to execute a repaint.** `setValue` only updates an internal number; the actual repaint is scheduled by the event loop.

**✅ Correct approach: break the big job into small chunks and run them with `QTimer` so each chunk yields control back to the event loop.** Or — use a thread (next lesson).

## Crash Site #2: Thinking `QApplication.processEvents()` Is a Magic Fix

**Symptom: someone tells you "just call processEvents inside the loop to refresh the UI", so you do — and the progress bar moves, but the program becomes extremely unstable.**

```
from PySide6.QtCore import QCoreApplication

def process_file():
    for i, line in enumerate(huge_file):
        do_something(line)
        progress_bar.setValue(i)
        QCoreApplication.processEvents()  # "force a refresh"
```

**The problem: `processEvents()` processes every pending event — including the user's "Cancel" button and the window-close button.** If handling those events triggers more slots, you can get re-entrant calls and hard-to-debug crashes. And you are essentially "manually driving the event loop", which is neither as performant nor as stable as the proper threading solution.

**✅ Correct: `processEvents()` is only for very short-term temporary refreshes (like a 500ms loading animation). The real answer is moving the heavy work into a `QThread`.**

## Crash Site #3: A Network Request Inside `__init__`

**Symptom: it takes several seconds after launch before the window even appears.**

```
class MainWindow(QMainWindow):
    def __init__(self):
        super().__init__()
        self.data = requests.get("https://api.example.com/init").json()  # blocks for 3 seconds
        self.init_ui()  # runs 3 seconds later

app = QApplication(sys.argv)
win = MainWindow()  # construction itself blocks
win.show()
app.exec()
```

**Why: everything that happens before `show` runs synchronously on the main thread.** What the user sees is "I double-clicked, then waited 3 seconds for a window" — a terrible experience.

**✅ Correct: show the window first, then kick off the request asynchronously (with signals / threads / Qt's network module).**

## The Deep Reason for Blocking

**The event loop is "cooperative" — it relies on every slot returning quickly.** This is not a flaw in PySide6; it is how nearly every GUI framework works (including browsers, Electron, and Swing). The upside is simplicity and efficiency — no locks are needed to make UI operations safe. The price is: you cannot do heavy work in there.

**Analogy:** the event loop is the only waiter in a restaurant, and he can only serve one table at a time. If one table takes 5 minutes to decide what to order, every other table waits.

**A thread is "hiring another waiter" — let the new one wait in the kitchen while the original keeps serving the other tables.**

## Summary

- A GUI program has only one main thread, which runs both the business logic and the event loop
- `app.exec()` *is* the event loop; until a slot returns, the loop is frozen
- Any operation over 100ms is "heavy": network requests, large file I/O, heavy computation
- Heavy work on the main thread = frozen interface = "not responding"
- `processEvents()` is a temporary workaround, not a real solution; threads are the real fix
- The next lesson covers the Worker pattern for moving work onto a background thread correctly

```quiz
type: local
q: Write a program that demonstrates "main-thread blocking": the window has a QLabel (showing the current time), a QPushButton ("Simulate slow work"), and a QLineEdit. When the button is clicked, the slot runs a for-loop doing 10 million math operations (simulating heavy work) and updates the QLabel with a progress percentage during the loop. Observe whether the label updates in real time during the loop or jumps all at once at the end. Then try adding time.sleep(0.01) in each iteration to "yield" and compare. Note: this is a windowed program and cannot run inside a web page — click "Open in VS Code" to run it.
starter: |
  import sys
  import time
  from PySide6.QtWidgets import (
      QApplication, QWidget, QPushButton, QLabel, QLineEdit, QVBoxLayout
  )

  app = QApplication(sys.argv)
  win = QWidget()
  win.setWindowTitle("Main-Thread Blocking Demo")
  win.resize(400, 200)

  time_label = QLabel("Time will stop")
  result_edit = QLineEdit()
  result_edit.setPlaceholderText("Loop result will appear here")
  btn = QPushButton("Start heavy computation")

  def on_click():
      total = 0
      for i in range(10_000_000):
          total += i * i
      result_edit.setText(str(total))

  btn.clicked.connect(on_click)

  # update the time label every second with QTimer
  from PySide6.QtCore import QTimer
  def update_time():
      from datetime import datetime
      time_label.setText(datetime.now().strftime("%H:%M:%S"))
  timer = QTimer()
  timer.timeout.connect(update_time)
  timer.start(1000)
  update_time()

  layout = QVBoxLayout(win)
  layout.addWidget(time_label)
  layout.addWidget(result_edit)
  layout.addWidget(btn)
  win.show()
  app.exec()
checklist:
- You can observe that the time label stops updating after the button is clicked (the event loop is blocked)
- The computation result is eventually displayed correctly
- You understand that both time.sleep and pure computation block the event loop
- The program displays and runs normally
```

## Lesson Quiz

```quiz
type: choice
exam: true
q: Which statement about GUI main-thread blocking is correct?
options:
- As long as the slow operation is placed in a separate Python function, the interface will not block
- A slow operation inside a slot blocks the event loop and the interface becomes "not responding", because the slot runs on the main thread
- PySide6 automatically moves slow operations to a background thread so the developer does not need to worry
- QTimer solves every blocking problem because it creates its own thread
answer: 1
explain: A slot is called synchronously on the main thread's event loop; if it does not return, it blocks the whole loop. QTimer only triggers on a schedule — it does not create a thread. PySide6 does not automatically background your code.
```
