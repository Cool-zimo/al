# Why PySide6

> The first decision when learning Qt is which binding to pick: PySide6 or PyQt6. Their APIs are nearly identical — the difference is the license. This lesson lays it out so you don't finish a project and discover you can't ship it commercially.

## Two Bindings, One Qt

**Qt itself is written in C++.** For Python to use it, someone has to build a bridge. That "someone" is the binding library. The two most popular are:

| Aspect | PySide6 | PyQt6 |
|---|---|---|
| Maintainer | The Qt Company (official) | Riverbank Computing (third-party) |
| License | LGPL 3.0 | GPL 3.0 / commercial dual-track |
| Qt version tracking | Fastest — official同步 releases | Slightly delayed |
| API style | snake_case (`exec()`) | camelCase (naming习惯 differs) |
| Commercial projects | **Free to use** — dynamic linking is enough | Either open-source your code or buy a commercial license |
| Documentation | Official docs solid, community growing | Longer history, more old tutorials |

**Both use the exact same underlying Qt C++ library, so behavior, performance, and how widgets look are identical.** A button in either binding is the same Qt button — the only difference is "which license, which naming style".

## Licenses: This Decides Whether You Can Ship Commercially

**Bottom line: for closed-source commercial projects, choose PySide6.** The reason lies in the fundamental difference between LGPL and GPL.

**GPL (PyQt's default) is "viral":** if you use GPL code, your entire project must be released under GPL — publish the source, allow others to modify and redistribute. For internal company tools or desktop software sold to clients, this is a deal-breaker: you can't hand over the source.

**LGPL (PySide6's license) is far more lenient:** it allows use in closed-source projects provided you "dynamically link". PySide6 itself is a dynamic library (.so / .pyd), and a normal `pip install` gives you dynamic linking — you satisfy the condition automatically. As long as you don't modify PySide6's own source code, you have nothing to worry about.

**An analogy:** GPL is like "if you use my recipe, your cookbook must be public too"; LGPL is like "you can cook with my pot, just don't modify my pot".

**What is a commercial license?** Riverbank's PyQt commercial license is essentially "buying an exemption" — you pay to avoid the GPL. A few hundred dollars per developer seat adds up fast for a team. PySide6 has no such problem.

## Crash Site 1: Discovering you must open-source after the project is done

**This tragedy happens in real life, especially at outsourcing shops and small companies.**

Alice took on a contract to build an internal data-entry tool. She knew PyQt, started coding, and shipped after two months. At acceptance, the client asked: "Can we just get the exe? We'll keep the source ourselves."

**Here's the problem:** PyQt is GPL. For closed-source commercial use, Alice either had to open-source the entire project (breaching the contract), buy PyQt commercial licenses (extra cost), or rewrite everything in PySide6 (another two months).

**Fix:** **pick PySide6 at project start.** If you're halfway through in PyQt6, migration is actually cheap (see below), but earlier is always cheaper.

## Naming Differences: PySide6 vs PyQt6

**Over 90% of their APIs are identical. The remaining differences are mostly naming style and one import detail.**

**1. Module import paths differ:**

```
# PySide6
from PySide6.QtWidgets import QApplication, QPushButton
from PySide6.QtCore import Qt, QPoint

# PyQt6
from PyQt6.QtWidgets import QApplication, QPushButton
from PyQt6.QtCore import Qt, QPoint
```

**It's just `PySide6` → `PyQt6`. The module names and class names are identical.** This is the easiest thing to change.

**2. Enum syntax differs (important):**

```
# PySide6: enums accessed as attributes — clean
button.setCheckable(True)
window.setWindowFlags(Qt.WindowType.Dialog)

# PyQt6: historically needed enum-class prefixes and .value
from PyQt6.QtCore import Qt
window.setWindowFlags(Qt.WindowType.Dialog)   # has converged
```

**PySide6 enums can be written as `Qt.AlignmentFlag.AlignCenter`** directly. PyQt6 sometimes requires `Qt.AlignmentFlag.AlignCenter.value`. This is one of PySide6's conveniences — no `.value` needed.

**3. `exec()` (covered above):**

PySide6 uses `app.exec()`. PyQt6 also uses `app.exec()` (PyQt6 standardized to no underscore). **Only the ancient PyQt5 used `app.exec_()`** — any tutorial showing that syntax is a decade out of date.

## Crash Site 2: Copying a PyQt6 tutorial, every import fails

**Symptom:** you installed PySide6 but found a PyQt6 tutorial and copied it:

```
from PyQt6.QtWidgets import QApplication   # ModuleNotFoundError
```

**Why:** the `PyQt6` package was never installed — you installed `PySide6`.

**Fix:** globally replace `PyQt6` → `PySide6`. Module names and class names stay the same, so it usually works immediately after the swap. If you see `.value` suffixes or `exec_()`, remove them.

**Recommendation:** when searching for tutorials, include "PySide6" in your query. Don't search "PyQt6 tutorial" — the volume difference is huge (PyQt's longer history means far more old tutorials), and searching wrong sends you down a rabbit hole.

## Qt Version Mapping

**PySide6 corresponds to Qt 6.** This isn't wordplay — it has real consequences:

| PySide version | Qt version | Python requirement |
|---|---|---|
| PySide2 | Qt 5 | Python 2.7 / 3.x |
| PySide6 | Qt 6 | Python 3.6+ (newer versions require 3.8+) |

**Qt 6 and Qt 5 have breaking changes:** some modules were removed (e.g. `QtWebKit`), some classes moved (e.g. `QRandomGenerator` now comes from `QtCore`), and enums require a prefix (`Qt.AlignmentFlag.AlignCenter` instead of `Qt.AlignCenter`).

**If you find `from PySide2 import ...` code online, that's Qt 5.** With PySide6 you must update imports and handle the enum prefix changes.

## Crash Site 3: Missing enum prefix, TypeError

**PySide6 forces you to write the full enum path. It's a Qt 6 safety feature.**

```
from PySide6.QtCore import Qt

label = QLabel("Centered text")
label.setAlignment(Qt.AlignCenter)   # Error!
```

**Error message:** `TypeError: setAlignment(self, alignment: Qt.AlignmentFlag): argument 1 has unexpected type 'EnumType'`.

**Why:** in Qt 6, `Qt.AlignCenter` must be written as `Qt.AlignmentFlag.AlignCenter`. Likewise `Qt.AlignLeft` → `Qt.AlignmentFlag.AlignLeft`.

**Fix:** **write the full enum path.** Memorize the common ones:

```
Qt.AlignmentFlag.AlignCenter
Qt.AlignmentFlag.AlignLeft
Qt.AlignmentFlag.AlignRight
Qt.AlignmentFlag.AlignTop
Qt.AlignmentFlag.AlignBottom
Qt.Orientation.Horizontal
Qt.Orientation.Vertical
Qt.CheckState.Checked
Qt.CheckState.Unchecked
```

**To save typing,** import at the top with `from PySide6.QtCore import Qt`. Your IDE's autocomplete will fill in the enum paths for you.

## When Should You Pick PyQt6?

**To be fair, PySide6 isn't the optimal choice in every scenario:**

- **Maintaining legacy projects:** the company codebase is PyQt5/PyQt6; migration cost exceeds the benefit, so keep using PyQt.
- **Depending on a third-party library that only has PyQt bindings:** a very small number of commercial libraries only provide PyQt interfaces.
- **You're going open-source anyway:** GPL doesn't matter to you; either PySide6 or PyQt6 works.

**But for a brand-new learning project — especially one that might go commercial — PySide6 is the easier choice.** Officially maintained, license-friendly, fastest to adopt new features. That's why this book chose it.

## Summary

- Python has two Qt bindings: PySide6 (official, LGPL) and PyQt6 (third-party, GPL)
- **LGPL allows closed-source commercial use; GPL requires open-sourcing** — this is the core difference
- Over 90% API overlap; migration is just import replacement plus enum prefix handling
- PySide6 enums need full paths: `Qt.AlignmentFlag.AlignCenter`
- PySide6 = Qt 6, PySide2 = Qt 5 — don't mix them
- Search "PySide6" tutorials, not "PyQt6", or your imports will all fail
