# Custom Dialogs with QDialog

> Built-in dialogs can only fetch a single value. A real interaction needs its own layout. This lesson shows how to build a `QDialog` — and why `exec()` can return a value while `show()` cannot.

## QDialog Is a Dialog You Lay Out Yourself

**Inherit from `QDialog`, drop in a layout and some widgets, and you have a custom dialog.**

```
from PySide6.QtWidgets import QDialog, QFormLayout, QLineEdit, QPushButton, QVBoxLayout

class LoginDialog(QDialog):
    def __init__(self, parent=None):
        super().__init__(parent)
        self.setWindowTitle("Log in")
        self.resize(250, 150)

        self.user_edit = QLineEdit()
        self.pass_edit = QLineEdit()
        self.pass_edit.setEchoMode(QLineEdit.Password)

        form = QFormLayout()
        form.addRow("Username:", self.user_edit)
        form.addRow("Password:", self.pass_edit)

        self.ok_btn = QPushButton("OK")
        self.cancel_btn = QPushButton("Cancel")
        btn_row = QHBoxLayout()
        btn_row.addStretch()
        btn_row.addWidget(self.ok_btn)
        btn_row.addWidget(self.cancel_btn)

        main = QVBoxLayout(self)
        main.addLayout(form)
        main.addLayout(btn_row)

        self.ok_btn.clicked.connect(self.accept)
        self.cancel_btn.clicked.connect(self.reject)
```

**`accept()` and `reject()` are built-in slots: they set the dialog's status to Accepted or Rejected and close it.** Connect them to your buttons and you don't need to write any closing logic yourself.

## exec() vs. show()

**`exec()` is modal: execution stops on that line until the dialog is closed, and the return value is Accepted/Rejected.**

```
dlg = LoginDialog(window)
result = dlg.exec()          # blocks until the user finishes
if result == QDialog.Accepted:
    print("Username:", dlg.user_edit.text())
    print("Password:", dlg.pass_edit.text())
```

**`show()` is modeless: the dialog appears and execution continues immediately, without waiting for the user.**

```
dlg = LoginDialog(window)
dlg.show()                   # returns right away; the next line runs at once
print("This prints first")   # the user has not typed anything yet
# dlg.user_edit.text() is empty here
```

**The key difference: modal `exec` blocks the main flow, so you can "fill it in, then read". Modeless `show` does not wait, so you have no idea when the user has finished.**

## Crash Site #1: Using show() to Read Dialog Data — All You Get Is Empty Strings

**Symptom: the dialog appears, but the username and password printed immediately are empty, as if the user typed nothing.**

```
dlg = LoginDialog(window)
dlg.show()                          # WRONG - non-blocking
print(dlg.user_edit.text())          # empty string!
print(dlg.pass_edit.text())          # empty string!
# execution has already reached here; the keyboard has not been touched
```

**Why: `show()` returns as soon as it has initiated the display; the main flow keeps running.** When you read on line 2, the dialog has only just been drawn — of course the input boxes are empty.

**✅ Correct: use `exec()`:**

```
dlg = LoginDialog(window)
if dlg.exec() == QDialog.Accepted:    # blocks until the user clicks OK
    username = dlg.user_edit.text()    # the user has finished typing
    password = dlg.pass_edit.text()
    do_login(username, password)
```

**There is a flip side: you must validate input *before* accepting, not after `exec()` returns and discover the input is invalid.** Override the `accept` method:

```
def accept(self):
    if not self.user_edit.text().strip():
        QMessageBox.warning(self, "Notice", "Username cannot be empty")
        return              # not calling super().accept() keeps the dialog open
    super().accept()
```

**Returning out of `accept` leaves the dialog open so the user can keep editing.** Only when validation passes does `super().accept()` actually close it.

## Crash Site #2: exec() Returns an Enum, Not 1 or 0

**Symptom: in PySide6, `exec()` returns the enum `QDialog.Accepted` (value 1). Writing `if dlg.exec():` happens to work, but `if dlg.exec() == 1` errors out.**

```
if dlg.exec() == 1:      # WRONG - you cannot compare an enum to an int like this
    ...
```

**Why: PySide6 returns the `QDialog.DialogCode` enum. Its values are 1 and 0, but its type is an enum, not `int`.** In a boolean context it is truthy (Accepted is truthy), so `if dlg.exec():` does not error — but an explicit comparison must use the enum.

**✅ Correct:**

```
result = dlg.exec()
if result == QDialog.Accepted:
    ...
elif result == QDialog.Rejected:
    ...
```

**Don't write `if dlg.exec():` — it runs, but the intent is murky; a reader cannot tell which of Accepted and Rejected is truthy.** Always spell out the enum.

## When Modeless Dialogs Make Sense

**`show()` is not wrong; it just has a different job: use it when the user needs to switch back and forth between the main window and the dialog.**

```
class ToolWindow(QDialog):
    def __init__(self, parent=None):
        super().__init__(parent)
        self.setWindowTitle("Tool panel")
        # no accept/reject needed; the user closes it with the X button

tool = ToolWindow(window)
tool.show()    # modeless: the main window stays usable, the tool panel stays open
```

**A modeless dialog has to manage its own lifetime.** If you write `dlg = ToolWindow()` then `dlg.show()`, the local variable is reclaimed when the function returns and the dialog vanishes instantly.

**✅ Fix: attach it to `self` to keep it alive:**

```
self.tool = ToolWindow(self)
self.tool.show()
```

**The rule of thumb: use `exec` when you need to "fill it in, then read the data"; use `show` (and keep it alive) when you need "a panel that stays open for interaction".**

## Summary

- Inherit `QDialog` and lay it out yourself; `accept()`/`reject()` close it and set its status
- `exec()` is modal and blocking; `show()` is modeless and non-blocking
- ⚠️ Classic traps: reading dialog data after `show()` gives empty values; comparing the `exec()` return to an integer
- For validation, override `accept`; on failure, `return` so the dialog stays open
- A modeless dialog must be kept alive by attaching it to `self`, or it is collected on function return
- Read values after `exec`; you cannot read them immediately after `show`
