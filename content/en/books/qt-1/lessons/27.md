# QThread and the Worker Pattern

> Move the heavy work to a background thread so the interface is always smooth. This lesson covers the correct use of `QThread` — and the one landmine everyone steps on.

## The Basic Idea Behind QThread

**`QThread` is Qt's thread wrapper. The core pattern: create a `QThread` object + a `Worker` object, use `moveToThread` to move the Worker onto the background thread, and trigger the Worker's work via signals.**

```
from PySide6.QtCore import QThread, QObject, Signal, Slot

class Worker(QObject):
    finished = Signal()           # task-complete signal
    progress = Signal(int)        # progress signal

    @Slot()
    def do_work(self):
        for i in range(100):
            import time
            time.sleep(0.05)
            self.progress.emit(i + 1)
        self.finished.emit()

# ---- main thread ----
worker = Worker()
thread = QThread()

worker.moveToThread(thread)              # the key step: move the worker to the background thread
thread.started.connect(worker.do_work)  # start the work automatically once the thread starts
worker.finished.connect(thread.quit)     # quit the thread when done
worker.finished.connect(worker.deleteLater)
thread.finished.connect(thread.deleteLater)

thread.start()  # start the thread
```

**Flow: `thread.start()` → fires the `started` signal → calls `worker.do_work()` → `do_work` runs on the background thread → reports progress back to the main thread via the `progress` signal → when done → `quit()` ends the thread.**

## The Right Way to Use moveToThread

**Three steps: ① create `QThread` ② `moveToThread` ③ connect the startup logic with a signal.**

```
# correct
worker = Worker()
thread = QThread()
worker.moveToThread(thread)
thread.started.connect(worker.do_work)
thread.start()
```

**Key point: the Worker must have no parent object.** If you pass a parent when constructing the Worker, `moveToThread` will fail — Qt does not allow a `QObject` with a parent to cross threads.

```
# wrong: the Worker has a parent
worker = Worker(parent=some_widget)
worker.moveToThread(thread)  # fails silently! moveToThread does nothing
```

**The Worker's signals are the bridge between the main thread and the background thread.** The background thread must not touch the UI directly; it emits signals, which connect to slots on the main thread, and Qt schedules the cross-thread call automatically.

## Crash Site #1: Modifying the UI Directly From a Background Thread → Crash

**Symptom: the program runs for a while, then crashes with `Cannot send events to objects owned by a different thread` — or a raw segmentation fault.**

```
class Worker(QObject):
    def do_work(self):
        for i in range(100):
            time.sleep(0.05)
            progress_bar.setValue(i)   # WRONG - modifying a UI control from a background thread!
```

**Why: every `QWidget` instance "belongs" to the main thread.** Calling `setValue` directly from another thread is not thread-safe; Qt detects it and warns you, and in severe cases it crashes outright. This is undefined behavior — it may work perfectly 1,000 times and crash on the 1,001st.

**✅ Correct: the background thread only emits signals; a main-thread slot updates the UI.**

```
class Worker(QObject):
    progress = Signal(int)   # emitted from the background thread

    def do_work(self):
        for i in range(100):
            time.sleep(0.05)
            self.progress.emit(i)   # emit a signal

# main-thread connection
worker.progress.connect(progress_bar.setValue)  # a main-thread slot updates the UI
```

**This is the "signal bridge" pattern: the background thread never touches the UI, it just says "here is a new value", and the main thread updates it.**

## Crash Site #2: Subclassing QThread but Putting the Work Outside run()

**Symptom: you thought using `QThread` fixed everything, but the interface still freezes.**

```
class MyThread(QThread):
    def __init__(self):
        super().__init__()
        self.heavy_result = None

    def prepare(self):
        # WRONG - this method is called on the main thread!
        result = requests.get("https://slow-api.com")  # blocks the main thread
        self.heavy_result = result

    def run(self):
        # only run() executes on the background thread
        print("thread running")

thread = MyThread()
thread.prepare()   # called on the main thread -> blocks!
thread.start()
```

**Why: `run()` does run on the background thread, but `prepare()` runs on the thread that created the object (the main thread).** Many people put initialization logic in other methods, assuming "if it's in a thread object it's on a thread" — no.

**✅ Correct: put the slow logic in `run()`, or use the `moveToThread` pattern (recommended).**

```
class MyThread(QThread):
    result_ready = Signal(str)

    def run(self):
        # run() executes on the background thread
        result = requests.get("https://slow-api.com").text
        self.result_ready.emit(result)

thread = MyThread()
thread.result_ready.connect(label.setText)
thread.start()
```

## Crash Site #3: Forgetting quit() and wait() — The Process Lingers After the Window Closes

**Symptom: you click X to close the window; the window vanishes, but the Python process is still running in the background, visible in the task manager.**

```
class MainWindow(QMainWindow):
    def __init__(self):
        super().__init__()
        self.thread = QThread()
        self.worker = Worker()
        self.worker.moveToThread(self.thread)
        self.thread.started.connect(self.worker.do_work)
        self.thread.start()

    # no override of closeEvent
```

**Why: while a background thread is still running, the Python process will not exit.** Closing the window only hides the UI; the background thread keeps going.

**✅ Correct: override `closeEvent` to make sure the thread quits and wait.**

```
class MainWindow(QMainWindow):
    def closeEvent(self, event):
        self.thread.quit()       # ask the thread to exit its event loop
        self.thread.wait(3000)   # wait up to 3 seconds
        super().closeEvent(event)
```

**`quit()` is "politely ask the thread to exit"; `wait()` is "block until it has actually exited".** You need both.

## A Production-Grade Worker Template

**A production Worker should have: a start signal, a progress signal, a finished signal, an error signal, and cancellation support.**

```
from PySide6.QtCore import QThread, QObject, Signal, Slot

class Worker(QObject):
    started = Signal()
    progress = Signal(int)
    finished = Signal(object)    # carries the result
    error = Signal(str)
    cancelled = Signal()

    def __init__(self):
        super().__init__()
        self._is_cancelled = False

    @Slot()
    def do_work(self, param):
        self.started.emit()
        try:
            result = []
            for i in range(100):
                if self._is_cancelled:
                    self.cancelled.emit()
                    return
                time.sleep(0.05)
                result.append(i * param)
                self.progress.emit(i + 1)
            self.finished.emit(result)
        except Exception as e:
            self.error.emit(str(e))

    def cancel(self):
        self._is_cancelled = True


# assembly on the main thread
worker = Worker()
thread = QThread()
worker.moveToThread(thread)

thread.started.connect(lambda: worker.do_work(42))
worker.progress.connect(progress_bar.setValue)
worker.finished.connect(on_success)
worker.error.connect(on_error)
worker.finished.connect(thread.quit)
worker.finished.connect(worker.deleteLater)
thread.finished.connect(thread.deleteLater)

thread.start()
```

## Summary

- The correct `QThread` pattern is `moveToThread` + signal-driven work, not subclassing `run()`
- The Worker must have no parent, or `moveToThread` fails silently
- ⚠️ A background thread must never touch the UI — modifying controls directly will crash; only a signal bridge is safe
- Make sure the slow logic actually runs on the background thread; do not put it in a method outside `run()`
- Always call `quit()` + `wait()` when closing the window, or the process will linger
- A Worker needs cancellation and error handling — required for production code
- The next lesson covers `QTimer` — a lighter "non-blocking" alternative
